# V4 Flash 架构师-开发者工作流

## 概述

本 SKILL 定义了 **6a8（DeepSeek V4 Pro）↔ DeepSeek V4 Flash 子代理** 的协作模式：
- **6a8** 负责架构设计、ADR 编写、任务拆分
- **V4 Flash 子代理** 按 ADR 执行原子施工任务
- 每次 `spawn_sub_agent` 调用只完成 **一个原子任务**

## 工作流（5 步）

### 步骤 1：架构设计（6a8 执行）

收到需求 → 分析现有代码库 → 设计架构方案。

输出：**ADR（Architecture Decision Record）**，包含：
- 标题、状态、日期
- 背景与问题
- 决策方案
- 替代方案
- 影响分析

### 步骤 2：任务拆分（6a8 执行）

将 ADR 拆分为 **原子任务列表**。

原子任务特征：
- 单一职责：一个任务只做一件事
- 可独立验证：完成后有明确的成功/失败标准
- 可回滚：失败时不影响其他任务
- 依赖最少：尽量减少任务间依赖

### 步骤 3：委派施工（6a8 委派 V4 Flash）

每个原子任务用 `spawn_sub_agent` 委派给 V4 Flash：

```json
{
  "model": "deepseek-v4-flash",
  "question": "执行以下原子任务：...",
  "scope": "文件路径范围",
  "already_known": "已有上下文（来自 ADR）",
  "effort": "quick",
  "stop_condition": "任务完成或遇到明确错误",
  "output": "SUMMARY, CHANGES, EVIDENCE, RISKS, BLOCKERS",
  "timeout_seconds": 120,
  "max_rounds": 20
}
```

**关键约束**：
- 一次只派一个原子任务，不批量
- 等当前子代理完成后再派下一个
- 有依赖的任务按拓扑序串行

### 步骤 4：结果验证（6a8 执行）

子代理返回后：
- 审查 CHANGES 和 EVIDENCE
- 如有关键文件变更，用 `file_read` 抽查
- 通过 → 标记任务完成，继续下一个
- 失败 → 分析 BLOCKERS，决定重试/调整方案/回滚

### 步骤 5：集成收尾（6a8 执行）

全部任务完成后：
- 运行 `dotnet build` 验证整体编译
- 可选：运行关联测试
- 生成交付摘要
- 可选：git commit

## V4 Flash 适用/不适用清单

| ✅ 适用（委派给 V4 Flash） | ❌ 不适用（6a8 自己做） |
|---------------------------|------------------------|
| 代码搜索（grep/搜索特定模式） | 架构设计决策 |
| 文件扫描与信息提取 | 多步骤因果推理 |
| 编译验证（`dotnet build`） | 跨多个子系统的重构 |
| 简单 Bug 诊断（已定位到文件级） | 创造性代码生成（新算法/新架构） |
| 文档生成（从代码提取） | 安全敏感操作 |
| 测试运行与结果收集 | 需要深度业务理解的任务 |
| 单文件重构（重命名、提取方法） | 跨仓库协调 |
| 配置文件修改 | 用户交互 |

## 质量门禁

- [ ] ADR 包含背景、决策、替代方案、影响分析
- [ ] 原子任务列表完整覆盖 ADR 所有需求
- [ ] 每个任务有明确的成功标准
- [ ] 子代理只委派给 `deepseek-v4-flash`
- [ ] 每次只派一个原子任务
- [ ] 所有任务完成后 `dotnet build` 通过
- [ ] 交付摘要记录所有变更和决策
