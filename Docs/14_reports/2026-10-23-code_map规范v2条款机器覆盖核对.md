# 2026-10-23 code_map 规范 v2 条款 ↔ 检查器机器覆盖核对

## 一、方法与口径

**问题**：规范 v2 多处写「机器可校验」「检查器必须实现」。实现存在不等于**被守住** —— 一条判定若没有能失败的断言，删掉它自测依旧全绿。本报告把条款对到「实现」和「断言」两级，找出只有实现、没有断言，或连实现都没有的条款。

**覆盖分级（只对规范自称可由机器判定的条款评级）**

| 级别 | 判定 | 取红能力 |
|---|---|---|
| **A** | 机器可判定 + 检查器已实现 + selftest 有**能失败**的断言 | 破坏实现 ⇒ 自测立刻红 |
| **B** | 机器可判定 + 已实现，但无专属断言 | 删掉该判定 ⇒ 自测仍全绿 |
| **C** | 规范未要求机器判定（启发式/流程约束/不可判定），或**连实现都没有** | 不适用（须在规范里诚实标注） |

**证据源（本轮现场实测，非文档引用）**

| 项 | 值 |
|---|---|
| 规范 | `Docs/10_conventions/code-map-规范-v2.md`，169 行，§1–§9 |
| 检查器 | `Tools/Docs/code_map_check.py`，sha256 `bd06254d…`，`LIMITS` 17 键、`RULES` 11 条、`RULE_ORDER` 11 条 |
| 自测 | `Tools/Docs/code_map_check_selftest.py`，**68 断言 / 18 stage** |
| 门禁 | `--check --report` → 48 个 `code_map.md`、`error 0 / warn 82 / info 0`、`gate PASS`、指纹 `verified=148 mismatched=0` |
| 分布 | 反模式 80 条 = 清单型 F 33 + 路线图 26 + 演进叙事 17 + 过度宣称 4 |

> 判级只看「能不能取红」，不看「命中多不多」。真实仓库里 复述型 S 与 空值写法 都是 0 命中 —— 0 命中既不能证明实现正确，也不能证明断言有效，故一律用合成夹具判定。

## 三、本轮闭合的三处不一致

### ① 清单型 F 的阈值原本不在 `LIMITS`（§8.1 违约）

§8.1 写死「上限/常量的唯一真源是 `LIMITS`」，但清单型 F 的阈值一直是判定处字面量 `len(items) >= 3`：规范说“以代码为准”，代码里却指认不出这个常量，`--report` 的 `limits` 段也自证不了它。而这条阈值恰好是待裁定焦点（§2「3 个以上」vs §6「≥3」），硬编码让“改阈值”变成“改判定逻辑”。

**已修**（commit `1ae50b3`）：新增 `"LIST_MIN_ITEMS": 3`，判定改为读常量，自测补「2 项不命中」「常量必须存在」两条断言把阈值两侧夹住。判定语义零变化 —— 反模式仍 80 条、warn 82、gate PASS、指纹 148/148。变异取红：常量改 4 ⇒ 3 failed；复原后 `code_map_check.py` sha256 逐位相同。

### ② 复述型 S 与 空值写法 只有实现、没有断言（B 级）

把这两段判定整体从检查器里删掉，自测原来依旧 63 passed 全绿。规范把它们列进“机器可执行”的七类反模式，实际却是 B 级。

**已修**（commit `232fcf0`）：新增 `stage_anti_pattern_placeholder_and_restated`，四行夹具把两类各夹在命中侧 + 对照侧（复述型 S：Jaccard 0.75 命中 / 0.00 不命中；空值写法：`待定` 命中且 info / 规范允许的 `—` 不命中），并断言阈值取自 `LIMITS`。自测 63 → **68 passed / 0 failed**，stage 18。

### ③ 逐文件免检旁路完全没有断言（B 级）

§6 承认“从 code_map 文本看不出脚本是否真加了旁路”，所以把它的**处置**列为 warn 级 review 项；但**词级启发式本身是机器判定** —— 三个词写错一个或整个删掉，门禁只会静默少报一类违规。实测把 `SKIP_BYPASS_WORDS` 三个词全删，自测依旧 68 passed 全绿。

**已修**：新增 `stage_anti_pattern_skip_bypass`，四行夹具（三行各含一个旁路词，第四行不含任何旁路词作对照），断言每个词命中**自己那一行**（行号 + 词逐一对应，防止词表顺序错位）、等级为 `warn`、对照行 0 命中，并断言旁路词表与 §6 词表七类**互不相交**（避免同一格被双重打标）。自测 68 → **72 passed / 0 failed**，stage 18 → **19**。

这一条要先记下两个坑，它们比结论更值钱：

- **第一版断言是个假绿**。写的是 `words == sorted(mod.SKIP_BYPASS_WORDS)` —— 期望值取自**被测实现自己**，从常量里删掉 `免检` 后实现与期望同时变，断言恒真，变异跑出来 **72 passed 全绿**。改成写死三词的字面量后才取红（`got={7:…,8:…} expect={6:…,7:…,8:…}`）。**“有断言”不等于“能取红”**，只有变异能分辨。
- **变异脚本被 shell 超时打断会留下变异态**。第一版变异脚本没有 `try/finally`、也没落盘备份，30 s 超时被杀后检查器**停在变异态**（sha256 `5f60d4d1…`），下一次“绿色基线”跑出 1 failed 才暴露。改为「先写 `temp/cm_backup.bin` 硬备份 + `finally` 复原 + 复原后比对 sha256」并给足超时后，三连跑干净：绿 72/0 → 变异 71/1 → 复原绿 72/0。

**三处都做了变异取红与逐位复原**

| 变异 | 期望红 | 实测 |
|---|---|---|
| `JACCARD_THRESHOLD` 0.5 → 0.8 | 2 failed | `66 passed, 2 failed`（两条新断言同时红） |
| `PLACEHOLDER_RE` 去掉 `待定` | 1 failed | `67 passed, 1 failed` |
| `SKIP_BYPASS_WORDS` 去掉 `免检` | 1 failed | `71 passed, 1 failed` |
| `LIST_MIN_ITEMS` 3 → 4（上轮） | 3 failed | 3 failed |

两次复原后 `code_map_check.py` sha256 = `bd06254db6b53dc09445f8cd7e0672f9ed5406178f3df538f2ea4d15d420d16d`，与变异前逐位相同；`git status` 只显示预期的 selftest / `code_map.md` 指纹两处改动。

## 四、尚未闭合的不一致（待裁定，本轮语义不变）

### ① 清单型 F 的阈值语义：§2「3 个以上」vs §6「≥3」

同一件事两处写法不同：§2 字段表写「不得罗列 **3 个以上**并列动作」（自然语言 = 4 个及以上），§6 反模式表写「并列**短语** **≥3** 个」。同时 §2 说的是“动作”、§6 说的是“短语”，粒度也不同。

**实测分布**（当前阈值为 3，共 33 命中 / 15 个 code_map）：

| 并列项数 | 3 | 4 | 5 | 6 | 7 |
|---|---|---|---|---|---|
| 命中条数 | **14** | 12 | 3 | 2 | 2 |

即 **42% 的命中恰好卡在 3 项**，其中 **8 个文件只在 3 项这一档命中**。若按 §2 语义把 `LIST_MIN_ITEMS` 改成 4，命中从 33 降到 19 —— 这是**一处常量**的改动（路线 B，可回滚、不触碰判定逻辑），但它是规范裁定，不是我可以自己决定的：改的是“哪 14 条算不算违规”。

### ② §5 触发条件 ②「语义变更数 ≥ 30」没有规则 ID

§5 把“语义变更数 ≥ 30”列为触发整理的条件之一，但 §7 的规则表里没有对应规则，检查器也没有统计“语义变更数”的能力。结论：这条**不由机器判定**。当前规范没有诚实标注它，读者容易以为 `--check` 会提示。建议在 §5 与 §9 各加一句标注（纯文档改动，不触碰语义）。**已落地（2026-10-23）**：规范 §5「触发整理」下加了机器判定边界说明、§9 增加了「不由机器判定」清单；词表与阈值语义均未改（diff 6 行全为新增、0 删除）。

### ③ §6 中文词表按子串匹配，领域用法照旧命中

§6 的检查器口径已诚实写明：ASCII 词按标识符边界 + 区分大小写匹配，中文词仍按子串。于是 `执行计划`、`本次运行`、架构断言里的 `单一真源`、`100%` 之类**领域名词/文档引用**照样命中（详见 `2026-10-23-code_map词表命中归因-47条.md`：47 条中 32 条误报、10 条真演进叙事）。是否改按意图/上下文判定属未裁定事项；一旦改成意图判定，就不再是“机器可执行词表”，需要同步改 §6 的措辞。

### ④ 新发现：`PLACEHOLDER_ALLOWED` 是一个恒真的 guard（死判据）

`LIMITS["PLACEHOLDER_ALLOWED"] = ["none", "n/a", "无", "-", "—", ""]` 与 `PLACEHOLDER_RE = ^(?:暂无|待补|待定|tbd|todo|--)$` 的覆盖集合**没有交集**：`无` ≠ `暂无`、`-` ≠ `--`、`none`/`n/a` 根本不匹配该正则。因此 `code_map_check.py:708` 的 `cell.lower() not in allowed_placeholders` 恒为真，删掉它不改变任何输出。

不改的理由：**放宽**正则（改成“任意占位写法”）或**删除**该键，都会改变 §6 空值写法的判定边界 —— 按 §8.2 需先给实测分布与信息损失评估，并走规范修订。本轮只登记为待裁定项。

### 观察项（不阻塞，供裁定参考）

- **#9/#10 必填列没有校验**：§2 把「文件 / 目录」「用途」标为必填，但检查器不校验列是否存在；表头缺 `用途` 时只是**静默少检**（F/S 相关判据全部失效）而不报错。若要机器化，需新增规则 ID，属规范变更，不是本轮可顺手做的事。**已加诚实标注（2026-10-23）**：规范 §2 schema 表后注明必填列存在性不由机器校验、缺列即静默少检；检查器仍未改动。
- **#12 L2 禁跨项目调用链**：无法从文本判定“是否跨项目”，保持 C 级最诚实。

## 五、结论与优先级

1. **规范 v2 的机器面整体是扎实的**：33 条里 24 条 A 级（实现 + 取红断言），包括最危险的“只读性”“严禁静默截断”“指纹算法”“11 规则等级逐字落地”都有断言守着；只读性还额外有静态检查（无破坏性写 API、写点位置、路径守卫）。
2. **B 级已清零**：清单型 F 阈值进了 `LIMITS`（§8.1 违约消除）、复述型 S 与 空值写法 有了取红断言、逐文件免检旁路有了逐词取红断言。其中新加的旁路断言第一版写成了“与实现自比”的假绿（删掉常量里的词，实现与期望同时变 ⇒ 恒真），是变异测试把它抓出来的 —— “有断言”不等于“能取红”，这是本轮最该复用到别处的一条经验。
3. **最该先裁定的是清单型 F 阈值**：33 命中里 14 条恰好 3 项，两种口径的差别是“14 条算不算违规”，代价只是一处常量。其次是 §5② 与 #9/#10 的诚实标注 —— 这两处是“规范让人以为机器管了、实际没管”，比反模式误报更容易误导读者。
4. **不建议**在没有分布与信息损失评估的前提下动 §6 中文词表匹配（会更进一步偏离“机器可执行”的定位），也不建议为让门禁变绿而调上限 —— §7 已明文禁止。

## 六、2026-11-22 复测：#9/#10「静默少检」的影响面（本轮量化，不改上文结论）

**实测口径（只读，未写任何 code_map）**

1. 遍历全仓 166 个 `code_map.md`（沿用 `LIMITS["EXCLUDE_DIR_NAMES"]` 的排除集）；
2. 每个文件取**第一张含「用途类」列名的表**的表头，与 `LIMITS["MAX_FIELD_LEN"]` 的 5 个键（`文件 / 目录`、`用途`、`关键符号`、`关联`、`约束`）求交集；
3. 与 `--report` 的 error 清单交叉，只看**当前 error: 0** 的文件。

| 表头含部分规范列名 | **37** | 缺的列不校验（最常见是只有 `用途`，即 `关键符号`/`关联`/`约束` 三项全不校验） |

即：166 个文件里只有 **45 个**真正受 §2 字段上限约束。

**38 个「零规范列名」文件的表头分布**

| 表头 | 文件数 |
|---|---|
| `File \| Responsibility` | 12 |
| `File \| Purpose` | 8 |
| `文件 \| 契约` | 2 |
| `文件 \| 用途 / 不变量`、`文件 \| 职责与限制`、`文件 \| 职责与不变量`（2）、`文件 \| 职责与边界`、`文件 \| 职责` 类 | 6 |
| `文件 \| 内容`（3）、`表 \| 内容`、`概念 \| 权威位置 \| 要点 / 不变量`、`入口 \| 职责`、`关键类型 / 职责 \| 何时读`、`覆盖的不变量 \| 变异验证`、`覆盖 \| 何时读` | 10 |

> 口径说明：检测是启发式的（「首张含用途类词的表」）。其中 3 个文件
> （`PuddingConversationReadModel` / `PuddingFullTextIndex.Cli` / `PuddingPathFiltering`）
> 表现在**没有用途类表头**、说明写在数据行里，属启发式判定的边缘，人工复核时按「表头不合规」计。

**最能说明问题的一个例子**：`Source/PuddingFullTextIndex.Cli/code_map.md`，65 行，通篇是
「用途 / 命令与退出码 / 关键语义 / 与组件实现的耦合点 / 门禁 / 边界」正文，文件清单表头是 `| 文件 | 作用 |`。
它**通过门禁**（`error: 0`）：行都不超 300、无围栏、表头不匹配任何规范列名 ⇒ 字段上限整段豁免。
这正是 §1「code_map 是索引不是正文」要拦的形态，却因为列名不映射而漏过。

**一个已有的仪器事实（本轮才注意到，属好消息）**

`code_map_check.py` **已经在收集**这些列名：`parse_tables()` 之后把 `canonical_column()` 返回 `None` 的列名
收进 `unmapped`，写进 JSON 报告的 `per_file[].unmapped_headers` 与顶层 `unmapped_headers`
（本次实测顶层 **80 个**不同列名，含 `File` / `Purpose` / `Responsibility` / `职责` / `契约` / `概念` / `目录/文件` 等）。

也就是说：**数据早就在报告里，只是 `--check` 的文本输出不打印它**。
维护者跑门禁看到的永远是 `gate: PASS`，永远不知道有 38 个文件被豁免 —— 这不是「没有能力」，是「没有出口」。

**建议（均未实施，属工具/规范变更，需裁定）**

1. **低成本、不动门禁语义**：在 `--check` 文本输出里把 `unmapped_headers` 打成一段提示
   （如 `unmapped columns (non-gating): 80 distinct names; see JSON per_file[].unmapped_headers`）。
   不改 severity 模型、不加规则 ID、不动 `RULES` / `RULE_ORDER` / selftest 契约，因此 `gate` 判据不变。
2. **要能取红**才需要新增规则 ID（如 `unknown-column`）—— 按 §8.2 属规范修订，
   需先给分布与信息损失评估。本轮只登记，不动。

这两条与本报告 §四观察项的 #9/#10 是同一件事的两个层面：#9/#10 说「没有校验」，本节补上「当前有多少文件因此被豁免」。

### 七、2026-11-22 追加：两个口径的数字必须分开看（本节修正 §六 的表述）

§六 报的是「38 个文件表头零规范列名」。本轮给检查器加了 `per_file[].recognized_columns`
（该文件**所有表**里被识别到的规范列名集合）之后，同一份仓库测出的是 **21**。

**这两个数字都对，但回答的不是同一个问题**：

| 口径 | 定义 | 本次实测 |
|---|---|---|
| §六 的 38 | 该文件**第一张**含用途类列名的表，其表头里没有任何规范列名 | 38 |
| 检查器新增的 21 | 该文件**所有表**的列名里，一个规范列名都没有（完全豁免） | **21** |

差出来的 17 个文件，是「至少有一张表不受 §2 字段上限约束，但另有表受约束」。
⇒ §六 的 38 说的是**漏洞面**（有多少张表逃逸），21 说的是**完全逃逸的文件数**。
引用时不能混用；把 38 说成「38 个文件完全不受约束」是错的。

**检查器侧的改动（本轮已落地，`--check` 文本输出新增一段）**

```
unmapped_columns (non-gating, spec §2 fixed column names):
  distinct=78  files_with_unmapped=59  files_with_zero_recognized=21
  zero_recognized: <前 8 个路径> ...(+13)
  note: these column names are NOT subject to §2 field limits ...
```

性质：**只增加文本输出与 JSON 字段，不新增规则 ID、不改 severity、不改 `gate` 判据**
（`error` 仍为 0、`gate` 仍为 PASS）。自测从 72 条增到 74 条，两条新断言都能取红
（变异：去掉 `recognized.add(col)` ⇒ `73 passed, 1 failed`，失败信息 `rec=[]`）。

这样「静默少检」就从「只有 JSON 里能看到」变成「每次跑门禁都打印一行」。至于要不要让它能取红
（新增 `unknown-column` 规则 ID），仍属 §8.2 的规范修订，**未做**。

## 八、2026-11-22 `files_with_unmapped` 不是债务：它有合法下限

批次 F（`2e6689c`）把 `files_with_zero_recognized` 从 21 归零后，检查器仍报：

```
unmapped_columns (non-gating, spec §2 fixed column names):
  distinct=75  files_with_unmapped=38  files_with_zero_recognized=0
```

表面看「还有 38 个文件要改」。**实际不能这么读** —— 我按每个文件的**主表表头**逐个分类后：

| 类别 | 数量 | 例子 | 该不该改成五列 |
|---|---|---|---|
| 主表**已经是**标准五列 | **1** | `PuddingCore`（164 行主表就是五列） | 不用改；它被计数只因文件里另带非规范的表 |
| `文件 \| <非规范列名>` | 15 | `文件\|职责与不变量`、`文件\|契约`、`文件\|权责` | **该改** |
| `文件 \| 用途`（缺 3 列） | 5 | `CapabilityBroker`、`Contracts`、`MemoryEngine`、`TaskRecall.Cli` | 可改（`用途` 已被校验，其余 3 项没有） |
| `文件 \| 职责 \| 关键符号 \| 约束`（缺 `关联`） | 3 | `ContextPolicy`、`HomeAssistant`、`Ssh` | 可改 |
| `文件 \| 工具 \| 用途`（多一列领域信息） | 1 | `Browser.AgentTools` | **不宜强改**：`工具` 列是真实信息，砍掉是损失 |
| `插件交付 \| 用途`（文件表但首列名不同） | 1 | `PuddingHost` | 该改 |
| **领域表，不是文件表** | ~12 | `关注点\|实现`、`属于本组件\|不属于本组件`、`项\|说明`、`命令\|作用\|关键约束`、`规则\|断言`、`类型\|用途`、`表\|内容`、`能力\|入口\|不承担`、`目录\|语言\|说明` | **不该改** |

### 决定性反例

`Source/PuddingCore/code_map.md` 的**主表就是** `| 文件 / 目录 | 用途 | 关键符号 | 关联 | 约束 |`，164 行，
字段校验全量生效 —— 可它仍出现在 `files_with_unmapped=38` 里，因为文件里另有几张非规范的表。

⇒ 这个指标的语义是「**存在至少一张非规范表**」，不是「这个文件不合规」。
把它当债务清零，只有两条路：把领域表硬塞进文件表 schema（**制造错误**），或者让检查器能区分表的角色。

### 因此不做批量转换

「38 → 0」不是一个正确目标。**真正可改的是 25 个**（15 + 5 + 3 + 1 + 1），
剩下 12 个领域表 + 1 个 `PuddingCore` 应保持原样。

若要让这个指标变成可行动的数字，正确做法是**给检查器加「文件表」识别**（首列单元格全部是
反引号路径 / 已知扩展名 ⇒ 才算该受 §2 字段上限约束的表），而不是改文档去迎合指标。
那属于规则语义变更，需先裁定，本轮不做。
