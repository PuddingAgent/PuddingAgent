# 2026-10-23 code_map 规范 v2 条款 ↔ 检查器机器覆盖核对

## 一、方法与口径

**问题**：规范 v2 多处写「机器可校验」「检查器必须实现」。实现存在不等于**被守住** —— 一条判定若没有能失败的断言，删掉它自测依旧全绿。本报告把条款对到「实现」和「断言」两级，找出只有实现、没有断言，或连实现都没有的条款。

**覆盖分级（只对规范自称可由机器判定的条款评级）**

| 级别 | 判定 | 取红能力 |
|---|---|---|
| **A** | 机器可判定 + 检查器已实现 + selftest 有**能失败**的断言 | 破坏实现 ⇒ 自测立刻红 |
| **B** | 机器可判定 + 已实现，但无专属断言 | 删掉该判定 ⇒ 自测仍全绿 |
| **C** | 规范未要求机器判定（启发式/流程约束/不可判定），或**连实现都没有** | 不适用（须在规范里诚实标注） |

**证据源（本轮现场实测，非文档引用）**

| 项 | 值 |
|---|---|
| 规范 | `Docs/10_conventions/code-map-规范-v2.md`，169 行，§1–§9 |
| 检查器 | `Tools/Docs/code_map_check.py`，sha256 `bd06254d…`，`LIMITS` 17 键、`RULES` 11 条、`RULE_ORDER` 11 条 |
| 自测 | `Tools/Docs/code_map_check_selftest.py`，**68 断言 / 18 stage** |
| 门禁 | `--check --report` → 48 个 `code_map.md`、`error 0 / warn 82 / info 0`、`gate PASS`、指纹 `verified=148 mismatched=0` |
| 分布 | 反模式 80 条 = 清单型 F 33 + 路线图 26 + 演进叙事 17 + 过度宣称 4 |

> 判级只看「能不能取红」，不看「命中多不多」。真实仓库里 复述型 S 与 空值写法 都是 0 命中 —— 0 命中既不能证明实现正确，也不能证明断言有效，故一律用合成夹具判定。

## 三、本轮闭合的三处不一致

### ① 清单型 F 的阈值原本不在 `LIMITS`（§8.1 违约）

§8.1 写死「上限/常量的唯一真源是 `LIMITS`」，但清单型 F 的阈值一直是判定处字面量 `len(items) >= 3`：规范说“以代码为准”，代码里却指认不出这个常量，`--report` 的 `limits` 段也自证不了它。而这条阈值恰好是待裁定焦点（§2「3 个以上」vs §6「≥3」），硬编码让“改阈值”变成“改判定逻辑”。

**已修**（commit `1ae50b3`）：新增 `"LIST_MIN_ITEMS": 3`，判定改为读常量，自测补「2 项不命中」「常量必须存在」两条断言把阈值两侧夹住。判定语义零变化 —— 反模式仍 80 条、warn 82、gate PASS、指纹 148/148。变异取红：常量改 4 ⇒ 3 failed；复原后 `code_map_check.py` sha256 逐位相同。

### ② 复述型 S 与 空值写法 只有实现、没有断言（B 级）

把这两段判定整体从检查器里删掉，自测原来依旧 63 passed 全绿。规范把它们列进“机器可执行”的七类反模式，实际却是 B 级。

**已修**（commit `232fcf0`）：新增 `stage_anti_pattern_placeholder_and_restated`，四行夹具把两类各夹在命中侧 + 对照侧（复述型 S：Jaccard 0.75 命中 / 0.00 不命中；空值写法：`待定` 命中且 info / 规范允许的 `—` 不命中），并断言阈值取自 `LIMITS`。自测 63 → **68 passed / 0 failed**，stage 18。

### ③ 逐文件免检旁路完全没有断言（B 级）

§6 承认“从 code_map 文本看不出脚本是否真加了旁路”，所以把它的**处置**列为 warn 级 review 项；但**词级启发式本身是机器判定** —— 三个词写错一个或整个删掉，门禁只会静默少报一类违规。实测把 `SKIP_BYPASS_WORDS` 三个词全删，自测依旧 68 passed 全绿。

**已修**：新增 `stage_anti_pattern_skip_bypass`，四行夹具（三行各含一个旁路词，第四行不含任何旁路词作对照），断言每个词命中**自己那一行**（行号 + 词逐一对应，防止词表顺序错位）、等级为 `warn`、对照行 0 命中，并断言旁路词表与 §6 词表七类**互不相交**（避免同一格被双重打标）。自测 68 → **72 passed / 0 failed**，stage 18 → **19**。

这一条要先记下两个坑，它们比结论更值钱：

- **第一版断言是个假绿**。写的是 `words == sorted(mod.SKIP_BYPASS_WORDS)` —— 期望值取自**被测实现自己**，从常量里删掉 `免检` 后实现与期望同时变，断言恒真，变异跑出来 **72 passed 全绿**。改成写死三词的字面量后才取红（`got={7:…,8:…} expect={6:…,7:…,8:…}`）。**“有断言”不等于“能取红”**，只有变异能分辨。
- **变异脚本被 shell 超时打断会留下变异态**。第一版变异脚本没有 `try/finally`、也没落盘备份，30 s 超时被杀后检查器**停在变异态**（sha256 `5f60d4d1…`），下一次“绿色基线”跑出 1 failed 才暴露。改为「先写 `temp/cm_backup.bin` 硬备份 + `finally` 复原 + 复原后比对 sha256」并给足超时后，三连跑干净：绿 72/0 → 变异 71/1 → 复原绿 72/0。

**三处都做了变异取红与逐位复原**

| 变异 | 期望红 | 实测 |
|---|---|---|
| `JACCARD_THRESHOLD` 0.5 → 0.8 | 2 failed | `66 passed, 2 failed`（两条新断言同时红） |
| `PLACEHOLDER_RE` 去掉 `待定` | 1 failed | `67 passed, 1 failed` |
| `SKIP_BYPASS_WORDS` 去掉 `免检` | 1 failed | `71 passed, 1 failed` |
| `LIST_MIN_ITEMS` 3 → 4（上轮） | 3 failed | 3 failed |

两次复原后 `code_map_check.py` sha256 = `bd06254db6b53dc09445f8cd7e0672f9ed5406178f3df538f2ea4d15d420d16d`，与变异前逐位相同；`git status` 只显示预期的 selftest / `code_map.md` 指纹两处改动。

## 四、尚未闭合的不一致（待裁定，本轮语义不变）

### ① 清单型 F 的阈值语义：§2「3 个以上」vs §6「≥3」

同一件事两处写法不同：§2 字段表写「不得罗列 **3 个以上**并列动作」（自然语言 = 4 个及以上），§6 反模式表写「并列**短语** **≥3** 个」。同时 §2 说的是“动作”、§6 说的是“短语”，粒度也不同。

**实测分布**（当前阈值为 3，共 33 命中 / 15 个 code_map）：

| 并列项数 | 3 | 4 | 5 | 6 | 7 |
|---|---|---|---|---|---|
| 命中条数 | **14** | 12 | 3 | 2 | 2 |

即 **42% 的命中恰好卡在 3 项**，其中 **8 个文件只在 3 项这一档命中**。若按 §2 语义把 `LIST_MIN_ITEMS` 改成 4，命中从 33 降到 19 —— 这是**一处常量**的改动（路线 B，可回滚、不触碰判定逻辑），但它是规范裁定，不是我可以自己决定的：改的是“哪 14 条算不算违规”。

### ② §5 触发条件 ②「语义变更数 ≥ 30」没有规则 ID

§5 把“语义变更数 ≥ 30”列为触发整理的条件之一，但 §7 的规则表里没有对应规则，检查器也没有统计“语义变更数”的能力。结论：这条**不由机器判定**。当前规范没有诚实标注它，读者容易以为 `--check` 会提示。建议在 §5 与 §9 各加一句标注（纯文档改动，不触碰语义）。

### ③ §6 中文词表按子串匹配，领域用法照旧命中

§6 的检查器口径已诚实写明：ASCII 词按标识符边界 + 区分大小写匹配，中文词仍按子串。于是 `执行计划`、`本次运行`、架构断言里的 `单一真源`、`100%` 之类**领域名词/文档引用**照样命中（详见 `2026-10-23-code_map词表命中归因-47条.md`：47 条中 32 条误报、10 条真演进叙事）。是否改按意图/上下文判定属未裁定事项；一旦改成意图判定，就不再是“机器可执行词表”，需要同步改 §6 的措辞。

### ④ 新发现：`PLACEHOLDER_ALLOWED` 是一个恒真的 guard（死判据）

`LIMITS["PLACEHOLDER_ALLOWED"] = ["none", "n/a", "无", "-", "—", ""]` 与 `PLACEHOLDER_RE = ^(?:暂无|待补|待定|tbd|todo|--)$` 的覆盖集合**没有交集**：`无` ≠ `暂无`、`-` ≠ `--`、`none`/`n/a` 根本不匹配该正则。因此 `code_map_check.py:708` 的 `cell.lower() not in allowed_placeholders` 恒为真，删掉它不改变任何输出。

不改的理由：**放宽**正则（改成“任意占位写法”）或**删除**该键，都会改变 §6 空值写法的判定边界 —— 按 §8.2 需先给实测分布与信息损失评估，并走规范修订。本轮只登记为待裁定项。

### 观察项（不阻塞，供裁定参考）

- **#9/#10 必填列没有校验**：§2 把「文件 / 目录」「用途」标为必填，但检查器不校验列是否存在；表头缺 `用途` 时只是**静默少检**（F/S 相关判据全部失效）而不报错。若要机器化，需新增规则 ID，属规范变更，不是本轮可顺手做的事。
- **#12 L2 禁跨项目调用链**：无法从文本判定“是否跨项目”，保持 C 级最诚实。

## 五、结论与优先级

1. **规范 v2 的机器面整体是扎实的**：33 条里 24 条 A 级（实现 + 取红断言），包括最危险的“只读性”“严禁静默截断”“指纹算法”“11 规则等级逐字落地”都有断言守着；只读性还额外有静态检查（无破坏性写 API、写点位置、路径守卫）。
2. **B 级已清零**：清单型 F 阈值进了 `LIMITS`（§8.1 违约消除）、复述型 S 与 空值写法 有了取红断言、逐文件免检旁路有了逐词取红断言。其中新加的旁路断言第一版写成了“与实现自比”的假绿（删掉常量里的词，实现与期望同时变 ⇒ 恒真），是变异测试把它抓出来的 —— “有断言”不等于“能取红”，这是本轮最该复用到别处的一条经验。
3. **最该先裁定的是清单型 F 阈值**：33 命中里 14 条恰好 3 项，两种口径的差别是“14 条算不算违规”，代价只是一处常量。其次是 §5② 与 #9/#10 的诚实标注 —— 这两处是“规范让人以为机器管了、实际没管”，比反模式误报更容易误导读者。
4. **不建议**在没有分布与信息损失评估的前提下动 §6 中文词表匹配（会更进一步偏离“机器可执行”的定位），也不建议为让门禁变绿而调上限 —— §7 已明文禁止。
