# 会话转录的 Agent 归属丢失与 FTS 语料缺失

## 1. 摘要

两个症状，两个不同的断点，但后果叠加：

| 症状 | 首次发生 | 已证实的机制 |
|---|---|---|
| `query_session_logs` 的 fts 模式在近期日期恒空 | 2026-09-21 之后无新语料 | FTS 只检索 `logs/messages/<yyyy-MM-dd>/<sessionId>.md`；该目录自 09-21 起不再有新日期 |
| `ChatMessages.AgentInstanceId` 全为空 | 2026-11-21 起 | 写入方是 canonical Turn 受理路径；该路径的落库没有把 `Recipients.AgentIds` 带到 `ChatMessages.AgentInstanceId` |

**不要把两者当成同一个缺陷**：断点时间相差两个月，写入方也不同。它们的共同点只是"同一批下游能力被一起削弱"——历史检索、记忆召回片段、按 agent 的审计统计都依赖这两条链路。

## 2. 证据一：`ChatMessages` 的 agent 归属（数据库只读实测）

```sql
SELECT date(CreatedAt/1000,'unixepoch') d,
       SUM(AgentInstanceId='') empty,
       SUM(AgentInstanceId='default.global_general-assistant.6a8') a6a8
FROM ChatMessages GROUP BY d ORDER BY d DESC LIMIT 12;
```

| 日期 | 空归属 | 本 agent |
|---|---|---|
| 2026-11-27 | 1 | 0 |
| 2026-11-26 | 84 | 0 |
| 2026-11-25 | 82 | 0 |
| 2026-11-24 | 141 | 0 |
| 2026-11-23 | 122 | 0 |
| 2026-11-22 | 167 | 0 |
| **2026-11-21** | **254** | **2** |
| 2026-11-20 | 215 | 0 |
| 2026-11-19 | 160 | 2 |

最新 6 行的 `message_id` 是 `fabric-turn-message:<hash>` / 32 位十六进制两种形态，`AgentInstanceId` 全部为空。

## 3. 证据二：写出这些行的是哪条路径

`Source/PuddingRuntime/Services/Messaging/MessageDeliveryDispatcher.cs:1678`
以 `StableMessageFabricId("fabric-turn-message", claimed.DeliveryId)` 生成 `ClientMessageId`，
随后 `AcceptMessageFabricConversationTurnAsync`（`:1693`）把它连同
`Recipients.AgentIds = [claimed.Target.Id]` 一起提交为 `SubmitTurnCommand`。

对照：同一个文件里两条**携带身份**的 old path（`:1135`、`:1227`）都显式传
`agentInstanceId: agentId`，它们写出的行会是 `transcript-{guid}` 或信封 messageId。
近期数据库里没有这种形态的行 ⇒ 近期所有转录都由 canonical Turn 受理路径写入，
而该路径的落库环节丢失了 agent 身份。

投递侧的身份是完好的：`message_deliveries.target_id` 在 2026-11-20 之后
535 行的值都是 `default.global_general-assistant.6a8`。
⇒ **不是投递归一化的问题，是"受理 → 落库"之间的字段丢失。**

未证实：对话命令管线内部具体哪一处没有把 `Recipients.AgentIds` 映射到
`ChatMessages.AgentInstanceId`。这是下一步要定位的点，本文不猜。

## 4. 证据三：FTS 语料在磁盘上的真实状态

```text
D:\Data\agents\default.global_general-assistant.6a8\logs\messages
  日期目录 59 个：FIRST=2026-07-14  LAST=2026-09-21
  最后 3 天：2026-09-19(1 文件) 2026-09-20(1 文件) 2026-09-21(1 文件)
其他 agent 对照：default.agent.567f… -> 2026-10-20（说明不是全局关停）
```

`Source/PuddingPlatform/Services/RawSessionLogService.Fts.cs:54` 取
`_dataPaths.AgentInstanceMessageLogsRoot(agentId)` 下的 `*.md` 作为唯一语料；
`:49` 先用 `conversation_catalog` 约束归属。

实测 `conversation_catalog` 中本会话 `3f52368a…` 的 `agent_id` **有值**
（`default.global_general-assistant.6a8`）⇒ 目录匹配这一步能通过，
**卡住的是语料**：`<day>/<sessionId>.md` 不存在 ⇒ 任何查询都只能是空结果。

这解释了长期记录在工作记忆里的「`query_session_logs` 的 FTS 取不到数，
阳性对照也失败」——不是查询解析问题，是没有可检索的文件。

## 5. 影响面

- 历史证据检索：fts 模式对 2026-09-21 之后的所有会话无效。
- 记忆召回：`MemorySnippetRelevanceCalculator` 走同一个 `IRawSessionLogService`，
  召回片段同样退化（未单独取样，属推断，列为待验证）。
- 审计与统计：按 agent 聚合转录时，2026-11-21 之后的行全部落到"空归属"桶。

## 6. 复现方式（全只读）

三个探针都是 `mode=ro` 打开 `D:\Data\databases\pudding_platform.db`，
不写库、不改文件：

1. 按日统计 `ChatMessages.AgentInstanceId`（§2 的 SQL）。
2. 取最新 6 行的 `message_id` 前缀（判定写入方）。
3. 数 `logs/messages` 的日期目录与文件数（判定语料是否存在）。

## 7. 建议的修复顺序（未实施）

1. **先定位受理 → 落库的字段丢失点**：从 `SubmitTurnCommand.Recipients.AgentIds`
   跟到 `ChatMessages` 插入点，确认是否有单一映射层可修；不要在每个调用点各补一次。
2. **再恢复私有语料写入**：`AgentConversationLogService.PersistPrivateFilesAsync`
   目前只有 `ChatTranscriptWriter` 一条生产调用链；若 canonical 受理路径不再经过它，
   需要在受理路径里补一次写入，或让 FTS 直接读 canonical 存储（二选一，属架构裁定）。
3. **最后才谈 fts 语义**：语料恢复之前，`query_session_logs` 的 fts 模式应显式回报
   "corpus missing for date range"，而不是让调用方从空结果反推"历史里没有"。

## 8. 局限

- §3 的写入方归属基于 `message_id` 形态 + 投递表对照，未做运行期断点取证。
- §5 中记忆召回的影响是推断，未单独取样。
- 09-21 语料停写与 11-21 身份丢失之间的因果关系**未建立**，本文按两条独立断点处理。

## 9. 修复（2026-11-27，commit 2e502a8）

定位到单一映射层：`ConversationProjector` 把事件投影成 ChatMessages 时传了
`workspaceId / messageId / turnId / commandId`，**没有传 agent**。
而事件本身又不带身份（§3：`conversation_events.agent_id` 最近 500 行全空，
且 `command_id` 列被 `msg-…`/`warm-prefix:…` 复用，join 不可靠）。

身份的真源因此只能是受理命令表：`chat_execution_commands` 的
`(command_id, session_id, turn_id, agent_instance_id)`；最新 agent 消息的
`turn_id` 与其中一行逐字对得上。

改法：投影批次内按 `turn_id` 一次性解析 turn → agent（`affectedTurnIds`
本来就有），无匹配时留空、不阻断投影；用户消息行不在此路径（受理事务写入，
属会话级）。

变异取红：M1 删实参 / M2 改用事件字段 → 同在
`ProjectAsync_ProjectsAgentIdentityFromAcceptanceCommand` 变红；M3 缺命令时
回落 `"unattributed"` → 在负向对照 `…LeavesAgentIdentityEmpty` 变红（不同用例）。
恢复后 SHA 与备份逐字节相同，`-t:Rebuild` 9/9。

**仍未做的**：① 私有 md 语料从 2026-09-21 起停写，是另一条断点，需要单独的
写入恢复或改由 FTS 直读 canonical 存储（§7 的架构裁定）；② 本轮未部署验证——
修复要在重启后才会影响新投影的消息。

## 10. 部署验收（2026-11-27 09:20–09:30）

三层证据，缺任一层都只能算「重启过」。

### 10.1 产物与进程

```
HEAD       0ac94f3 @ 09:08:14（父提交 2e502a8 @ 09:04:14）
live DLL   PuddingPlatform 09:10:41 · Runtime 09:10:41 · Agent 09:10:47
进程       PID 156516 @ 09:11:29
路径       temp\build\winui3\bin\PuddingDesktop\Debug\net10.0-windows10.0.19041.0\win-x64\core\
```

模块路径取自 `Get-Process.Modules`，不是按目录猜的；DLL 晚于提交、进程晚于 DLL。

### 10.2 修复确实在运行的程序集里

单凭 mtime 无法排除「构建产物没换」或「改了别的文件」，所以直接扫字节：

| 探针 | 命中数 | 作用 |
|---|---|---|
| `ConversationProjector` | 7 | 正向对照（符号必在） |
| `ResolveTurnAgentsAsync` | **3** | 本次修复新增的私有方法 |
| `PersistMessageInTransactionAsync` | 3 | 调用点 |
| `ResolveTurnAgentsAsyncXYZ` | **0** | 负对照（任意拼接串） |
| `ZZ_NoSuchSymbol_1127` | **0** | 负对照 |

两个负对照为 0 才说明扫描不是恒真；`PuddingPlatform.dll` 8,552,960 字节。

### 10.3 被修的写入方就是生产路径

`Source/PuddingPlatform` 内 `ChatMessages.Add` 有 6 处（播报、系统命令、
转录兜底、受理事务、私有日志、投影）。用运行日志定归属：

```
2026-11-27 09:11:01.711 [INF] [tag:ConversationProjector]
  [ConversationProjector] Projected conv=3f52368a35ef49ab834991e897e8715f …
```

该时刻写入的正是仓库里那条 agent 行（CM_ID=18565）。也就是说
`ConversationProjector` 确实是 agent 回复行的写入者，修复点没有打偏。

### 10.4 DB 端仍无后代样本（诚实结论）

`ChatMessages` 最近 8 条 agent 行 `AgentInstanceId` 仍为空，但**全部早于
09:11:29 的重启**：最新一条 09:11:01 比进程启动早 28 秒。本轮无法产出
「重启后写入的 agent 行」——那需要本回合结束后的一次投影。

可验证的前置条件已经闭合：

- 8/8 条 turn_id 在 `chat_execution_commands` 中各查到 1 行，
  `agent_instance_id` 全为 `default.global_general-assistant.6a8`；
- 该表 6846 行 `empty_agent = 0`，即修复里的 `!= ''` 过滤不会误杀。

因此下一步只需在下一回合查一行：新的 agent 行应带本 agent id。

### 10.5 顺带查清 md 语料为何停在 09-21

`AgentConversationLogService.PersistPrivateFilesAsync` 的唯一生产调用链是
`ChatTranscriptWriter.PersistAsync`（非事务版，`ChatTranscriptWriter.cs:86`）；
而投影走的是 `PersistMessageInTransactionAsync`——这条路径**不写私有 md**。

事实吻合：今日 `[AgentConversationLog]` 日志 **0 条**（同名 3 次命中全是我自己
的命令输出）；`logs/messages` 最新文件 `2026-09-21 21:26:57`。

结论：md 停写是「写入方切换」的结果，与 11-21 的身份丢失**无因果关系**
（§8 的判断成立，这里补上了机制）。但 §7 第 2 条的代价因此上升：
「补写」不是加个参数，而是要把 md 写入重新接进投影路径；
「FTS 直读 canonical」更省——`ChatMessages` 已有 18566 行可用。

## 12. 局限

- §10.4 的「新行应带 id」是待验预测，本文写的是前置条件已闭合，不是已完成。
- §10.5 未定位「写入方何时从 ChatTranscriptWriter 切到投影」，只证明当前两者
  不是同一条路径；09-21 这个日期与切换时刻是否重合尚未取证。
