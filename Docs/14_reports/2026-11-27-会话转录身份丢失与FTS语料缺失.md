# 会话转录的 Agent 归属丢失与 FTS 语料缺失

## 1. 摘要

两个症状，两个不同的断点，但后果叠加：

| 症状 | 首次发生 | 已证实的机制 |
|---|---|---|
| `query_session_logs` 的 fts 模式在近期日期恒空 | 2026-09-21 之后无新语料 | FTS 只检索 `logs/messages/<yyyy-MM-dd>/<sessionId>.md`；该目录自 09-21 起不再有新日期 |
| `ChatMessages.AgentInstanceId` 全为空 | 2026-11-21 起 | 写入方是 canonical Turn 受理路径；该路径的落库没有把 `Recipients.AgentIds` 带到 `ChatMessages.AgentInstanceId` |

**不要把两者当成同一个缺陷**：断点时间相差两个月，写入方也不同。它们的共同点只是"同一批下游能力被一起削弱"——历史检索、记忆召回片段、按 agent 的审计统计都依赖这两条链路。

## 2. 证据一：`ChatMessages` 的 agent 归属（数据库只读实测）

```sql
SELECT date(CreatedAt/1000,'unixepoch') d,
       SUM(AgentInstanceId='') empty,
       SUM(AgentInstanceId='default.global_general-assistant.6a8') a6a8
FROM ChatMessages GROUP BY d ORDER BY d DESC LIMIT 12;
```

| 日期 | 空归属 | 本 agent |
|---|---|---|
| 2026-11-27 | 1 | 0 |
| 2026-11-26 | 84 | 0 |
| 2026-11-25 | 82 | 0 |
| 2026-11-24 | 141 | 0 |
| 2026-11-23 | 122 | 0 |
| 2026-11-22 | 167 | 0 |
| **2026-11-21** | **254** | **2** |
| 2026-11-20 | 215 | 0 |
| 2026-11-19 | 160 | 2 |

最新 6 行的 `message_id` 是 `fabric-turn-message:<hash>` / 32 位十六进制两种形态，`AgentInstanceId` 全部为空。

## 3. 证据二：写出这些行的是哪条路径

`Source/PuddingRuntime/Services/Messaging/MessageDeliveryDispatcher.cs:1678`
以 `StableMessageFabricId("fabric-turn-message", claimed.DeliveryId)` 生成 `ClientMessageId`，
随后 `AcceptMessageFabricConversationTurnAsync`（`:1693`）把它连同
`Recipients.AgentIds = [claimed.Target.Id]` 一起提交为 `SubmitTurnCommand`。

对照：同一个文件里两条**携带身份**的 old path（`:1135`、`:1227`）都显式传
`agentInstanceId: agentId`，它们写出的行会是 `transcript-{guid}` 或信封 messageId。
近期数据库里没有这种形态的行 ⇒ 近期所有转录都由 canonical Turn 受理路径写入，
而该路径的落库环节丢失了 agent 身份。

投递侧的身份是完好的：`message_deliveries.target_id` 在 2026-11-20 之后
535 行的值都是 `default.global_general-assistant.6a8`。
⇒ **不是投递归一化的问题，是"受理 → 落库"之间的字段丢失。**

未证实：对话命令管线内部具体哪一处没有把 `Recipients.AgentIds` 映射到
`ChatMessages.AgentInstanceId`。这是下一步要定位的点，本文不猜。

## 4. 证据三：FTS 语料在磁盘上的真实状态

```text
D:\Data\agents\default.global_general-assistant.6a8\logs\messages
  日期目录 59 个：FIRST=2026-07-14  LAST=2026-09-21
  最后 3 天：2026-09-19(1 文件) 2026-09-20(1 文件) 2026-09-21(1 文件)
其他 agent 对照：default.agent.567f… -> 2026-10-20（说明不是全局关停）
```

`Source/PuddingPlatform/Services/RawSessionLogService.Fts.cs:54` 取
`_dataPaths.AgentInstanceMessageLogsRoot(agentId)` 下的 `*.md` 作为唯一语料；
`:49` 先用 `conversation_catalog` 约束归属。

实测 `conversation_catalog` 中本会话 `3f52368a…` 的 `agent_id` **有值**
（`default.global_general-assistant.6a8`）⇒ 目录匹配这一步能通过，
**卡住的是语料**：`<day>/<sessionId>.md` 不存在 ⇒ 任何查询都只能是空结果。

这解释了长期记录在工作记忆里的「`query_session_logs` 的 FTS 取不到数，
阳性对照也失败」——不是查询解析问题，是没有可检索的文件。

## 5. 影响面

- 历史证据检索：fts 模式对 2026-09-21 之后的所有会话无效。
- 记忆召回：`MemorySnippetRelevanceCalculator` 走同一个 `IRawSessionLogService`，
  召回片段同样退化（未单独取样，属推断，列为待验证）。
- 审计与统计：按 agent 聚合转录时，2026-11-21 之后的行全部落到"空归属"桶。

## 6. 复现方式（全只读）

三个探针都是 `mode=ro` 打开 `D:\Data\databases\pudding_platform.db`，
不写库、不改文件：

1. 按日统计 `ChatMessages.AgentInstanceId`（§2 的 SQL）。
2. 取最新 6 行的 `message_id` 前缀（判定写入方）。
3. 数 `logs/messages` 的日期目录与文件数（判定语料是否存在）。

## 7. 建议的修复顺序（未实施）

1. **先定位受理 → 落库的字段丢失点**：从 `SubmitTurnCommand.Recipients.AgentIds`
   跟到 `ChatMessages` 插入点，确认是否有单一映射层可修；不要在每个调用点各补一次。
2. **再恢复私有语料写入**：`AgentConversationLogService.PersistPrivateFilesAsync`
   目前只有 `ChatTranscriptWriter` 一条生产调用链；若 canonical 受理路径不再经过它，
   需要在受理路径里补一次写入，或让 FTS 直接读 canonical 存储（二选一，属架构裁定）。
3. **最后才谈 fts 语义**：语料恢复之前，`query_session_logs` 的 fts 模式应显式回报
   "corpus missing for date range"，而不是让调用方从空结果反推"历史里没有"。

## 8. 局限

- §3 的写入方归属基于 `message_id` 形态 + 投递表对照，未做运行期断点取证。
- §5 中记忆召回的影响是推断，未单独取样。
- 09-21 语料停写与 11-21 身份丢失之间的因果关系**未建立**，本文按两条独立断点处理。
