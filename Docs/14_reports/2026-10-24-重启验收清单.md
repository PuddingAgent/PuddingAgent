## 2. 重启时（部署连续性判据）

重启后**第一件事**：比较 DLL 时间戳与**进程启动时间** —— 这才是「进程内到底是新是旧」的判据。
光看「DLL 是否存在」会误判（见下方同日实测）。

```powershell
$runDir = 'D:\CodeProject\PuddingAgent\PuddingAgent\Source\PuddingAgent\bin\Debug\net10.0'
$proc = Get-Process PuddingAgent
"PROC_START=$($proc.StartTime.ToString('yyyy-MM-dd HH:mm:ss'))"
foreach($n in 'PuddingHtml.dll','PuddingRuntime.dll'){
  $i = Get-Item "$runDir\$n"
  "$n  SIZE=$($i.Length)  MTIME=$($i.LastWriteTime.ToString('yyyy-MM-dd HH:mm:ss'))"
}
```

**判据**：DLL 的 MTIME **晚于**进程启动时间 ⇒ 进程内加载的是旧版，修复尚未生效。

> **2026-10-24 实测修正**：原清单预期「重启前 `PuddingHtml.dll` 应为 False」，实际是 **True**。
> 原因是宿主运行目录**就是构建输出目录** —— 跑过门禁（`build-all-tests.cmd`）之后，
> 盘上所有 DLL（含新增的 `PuddingHtml.dll`、以及 `PuddingRuntime.dll`）都已是新构建：
> `PuddingRuntime.dll` 07:24:20、`PuddingHtml.dll` 07:24:17，而进程 PID 121568 启动于 **21:36:19**（前一晚）。
> ⇒ 盘上新、内存旧，**重启即生效，不需要重新构建**。判据因此从「DLL 是否存在」改为「时间戳 vs 进程启动时间」。

## 4. 重启后（`http_fetch` 行为，⑤）

**A. 分页（这是本次最大行为变化）**

任选一篇长文档：

```
http_fetch url=<长页面> output_format=markdown
```

| 期望 | 说明 |
|---|---|
| 输出末尾含 `[partial: N / M chars read; pass cursor=...]` | 分页标记 |
| 不再出现 `... [truncated]` 的硬切 | 旧行为已移除 |
| 把 `cursor=` 原样回传 | 返回 `[resumed at char N of M]` |
| 换 `output_format` 再用同一个 cursor | **明确拒绝**，提示该 cursor 属于哪个表示 |

**B. outline 格式**

```
http_fetch url=<长文档> output_format=outline
```

期望只返回标题树（`Outline: N headings, M chars total.`），几百 token 量级。

**C. 错误可操作性（⑤ 的核心验收）**

```
http_fetch url=https://github.com/<任意仓库>
```

本机对 `github.com` 是 SSL 被代理阻断（实测 3/3）。期望错误形如：

```
TlsHandshake: HttpRequestException: The SSL connection could not be established ... |
通常由本机代理或网络拦截引起，重试同一域名仍会失败；可改用 deepseek_fetch 或站点的镜像/原始源。
```

关键判断：**能看出「要不要重试」**。如果只看到裸 `see inner exception` ⇒ 说明 `PuddingRuntime.dll` 没换新。

**D. `deepseek_fetch` 传输失败**

同上 SSL 场景，期望错误含 `TLS handshake failed` + 指向 `http_fetch`，且**不得**出现 `use deepseek_fetch`（那会自指矛盾）。
