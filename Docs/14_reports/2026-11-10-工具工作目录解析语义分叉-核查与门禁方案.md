# 工具工作目录解析 · 语义分叉核查与门禁方案

> 本文先更正架构评审第 ② 条的措辞，再给可执行的收口方案。
> **更正的部分在 §2**：原判断"同一语义多处实现、缺少单一入口"不准确。

## 1. 结论速览

| 原判断 | 核实后的判断 |
|---|---|
| 缺少单一入口，路径解析各写一套 | **入口存在且被广泛使用**（25+ 调用点），但有 **6~7 处绕过它** |
| 属普遍性缺失 | 属**离群绕过 + 兜底语义不一致** |

**性质改了，严重度没降**：绕过者的兜底目标是 `Process cwd`，而入口的兜底目标是 `WorkspaceRoot`——两者是**不同答案**，不是同一答案的两种写法。

## 2. 单一入口（确切位置）

`Source/PuddingRuntime/Tools/BuiltIns/Files/FileTools.cs:14`

```csharp
internal static class HostFileToolPaths          // ← 定义在 FileTools.cs 文件内，非独立文件
{
    private static Lazy<string> s_workspaceRoot = new(ResolveWorkspaceRootInternal);
    public static string WorkspaceRoot => s_workspaceRoot.Value;

    private static string ResolveWorkspaceRootInternal()
    {
        // 1) PUDDING_REPOSITORY_ROOT
        // 2) 从 BaseDirectory 上溯 8 层找 .git / dev-up.py / checkpoint.json
        // 3) 回退 Directory.GetCurrentDirectory()
    }

    public static string ResolveWorkspaceRoot(string? executionWorkingDirectory) =>
        string.IsNullOrWhiteSpace(executionWorkingDirectory)
            ? WorkspaceRoot
            : Path.GetFullPath(executionWorkingDirectory);
}
```

**注**：评审初稿把 `FileTools.cs:58` 的 `ResolveWorkspaceRoot` 当成第二个实现——错。它是 `HostFileToolPaths` 的成员方法，只是宿主文件恰好叫 `FileTools.cs`。

**采纳情况良好**：全部 20 个 Git 工具、`FileSearchTool`、`SearchGrepTool`、`HostShellExecutor`、`ToolResultContextPolicy` 均调用此入口。

## 4. 已发生的实际后果（不是假设）

`goal.md`「已证伪」节记录过一条：

> `file_write` 相对路径按仓库根 —— **实际按进程 cwd**

这条的历史结论与本核查同源：**兜底语义分叉会产生"我以为按 A、实际按 B"的静默偏差**，且它只在下游以"文件写错地方"的形式暴露，报错信息不会指向目录解析。

## 5. 门禁方案（未实施）

### 5.1 不采用「统一重构」

一次性改 7 处涉及 Terminal 的 `Cwd` 语义、Search 的 scope 语义、Diagnostics 的 data 目录语义——**每处的"正确兜底"可能本就不同**（终端本就该用进程 cwd？待确认）。贸然统一会引入新语义错误。

### 5.2 采用「先门禁，后逐个裁定」

加一条**能取红**的源码扫描断言（放 `PuddingRuntimeTests`）：

```
扫描 Source/PuddingRuntime/Tools/**/*.cs
断言：出现 Directory.GetCurrentDirectory / Environment.CurrentDirectory 的位置
      必须落在白名单内（当前：FileTools.cs 的 HostFileToolPaths 内部）
违规 → 红，错误消息列出文件:行
```

**为什么用测试而不是 analyzer**：项目当前无 analyzer 插件（`BoundaryTests.cs` 已记录这一约束），测试是既有惯例；且这条能与 36 个 `ComponentBoundaryTests` 放在一起，不被遗忘。

**为什么不是直接禁止**：白名单机制强制**每一处新增都得显式登记理由**。绕过从"静默"变成"要写一行白名单 + 一句为什么"。

### 5.3 逐个裁定的判据

对每个已登记的绕过点问一句：**这里的兜底目标应该等于工作区根，还是等于进程 cwd？**

- `PluginTools` → 应为工作区根（与 `file_*` 同一上下文，已在 `2026-11-10-工具插件自举能力核查.md` §5 给出改法）
- `Terminal*` → **待定**（终端在无 `Cwd` 时用进程 cwd 可能是有意为之）
- `SearchGrepTool` → 需读两处上下文再定
- `AgentDiagnostics` → 待定

## 8. 逐点裁定（2026-11-11 读实现后）

### 8.1 先更正一个口径

§3 的 7 处是**按字符串匹配扫出来的**，召回里有假阳性。7 = 待裁定条目数，**不等于 7 处语义分叉**。逐个读实现后的结果如下。

### 8.2 裁定表

| # | 位置 | 读实现后的裁定 | 依据 |
|---|---|---|---|
| 1 | `PluginTools.cs:30` | **已修复，不再是静默错位** | `515e6a1` 后改为 fail-closed：`WorkingDirectory` 为空或非绝对即抛显式错 |
| 2 | `TerminalSkill.cs:40` | **可接受** | 三级回退 `args.Cwd → context.WorkingDirectory → 进程 cwd`；终端本就允许用进程 cwd |
| 3 | `TerminalTools.cs:194` | **可接受** | 同上，且额外 `Directory.Exists` 校验并报清晰错误 |
| 4 | `SearchGrepTool.cs:186` | **真缺陷 ★** | 见 §8.3 |
| 5 | `SearchGrepTool.cs:834` | **冗余兜底，与 #4 同源** | 实参 `directory` 来自 `managedDirectory`，已是绝对路径 |
| 6 | `FileSearchTool.cs:386` | **假阳性** | 不是路径解析：是 `DriveInfo.GetDrives()` 失败后给盘符列表的兜底 |
| 7 | `AgentDiagnosticsTool.cs:556` | **低危，非工作区路径** | 是数据目录兜底（`_dataPaths` 正常已注入）；为 null 时会静默指向错误目录 |

### 8.3 #4 是最强证据：注释与实现直接矛盾

`SearchGrepTool.ExecuteCoreAsync` 第 146–148 行注释：

```csharp
// Lucene 分支保持原始 directory 语义（相对索引根）；托管 grep 分支使用
// 执行快照冻结的 WorkingDirectory 解析出的绝对路径（与 file 工具同源），
// 避免回落到进程 Environment.CurrentDirectory（运行时 bin 目录）。
var managedDirectory = ResolveManagedSearchDirectory(args.Directory, context);
```

而被调用的函数（第 184–190 行）在未传 `directory` 时做的正是注释说要避免的事：

```csharp
private static string ResolveManagedSearchDirectory(string? directory, ToolExecutionContext context)
{
    if (string.IsNullOrWhiteSpace(directory))
        return Directory.GetCurrentDirectory();          // ← 注释明说要避开它
    if (Path.IsPathRooted(directory))
        return directory;
    return Path.GetFullPath(Path.Combine(
        HostFileToolPaths.ResolveWorkspaceRoot(context.WorkingDirectory), directory));
}
```

**只有相对路径分支走了入口，空参数分支没有**。同函数内两分支用了不同语义。

另：第 836 行的错误文案写「or omit it to search the workspace root ({cwd})」——当 `cwd` 等于进程 cwd 时，**这句是在错的情形下说对了话**。

### 8.4 一个外部佐证（工具使用惯例反推）

我自己的工具使用惯例里长期存在一条：「`search_grep` 必须显式传 `directory`，否则走进程 cwd → `scanned 0/2000`」。这条惯例本身就是 #4 的**长期规避手段**，也说明它从未被当成缺陷，而是被当成了使用注意事项。

### 8.7 行为证据（2026-11-11 00:58 实探，把 #4 从代码推断升级为非推断）

直接拿 `search_grep` 本工具做对照实验，query 固定为 `HostFileToolPaths`（它确定存在于仓库）。

**对照组（显式传 directory）**：`scanned 1/2000 files, 29406 bytes`，首屏即命中 5 行。

**处理组（省略 directory）**：零命中，且预算被烧到上限：

```
scanned 718/2000 files, 67143425/67108864 bytes
searched_scope=D:\CodeProject\PuddingAgent\PuddingAgent\temp\build\winui3\bin\
               PuddingDesktop\Debug\net10.0-windows10.0.19041.0\win-x64\core
limit_reason=scan_budget|large_files_skipped
```

**三件事被这一对输出同时定下**：

1. 省略 `directory` 时扫描的确实不是工作区根（`D:\Data\workspaces\default`），也不是仓库，而是 **Core 安装目录** —— `Directory.GetCurrentDirectory()` 的实价值。
2. 这不是理论风险：默认参数下工具**会把 67 MB 预算烧在构建产物上**，然后返回空结果。除了错，还贵。
3. 回执里的 `searched_scope` 把真实目录报了出来 —— 这一点做得对，是它可以被当场拆穿的原因。

**矛盾点也在这里**：工具文档说「不传 directory 走进程 cwd」，长期被我当成使用注意事项；但 `SearchGrepTool.cs:836` 的错误文案又说「omit it to search the workspace root」。两句话不一致，而以代码为准。
