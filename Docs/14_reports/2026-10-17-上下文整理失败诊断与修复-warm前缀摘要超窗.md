# 上下文整理失败诊断与修复：warm-prefix 摘要超窗与同轮双尝试

> **性质**：只读诊断（D:\data 日志 + SQLite + 源码逐行核对）→ 最小修复 → 定向回归。
> 现象：默认助手会话（`206a9b48…`）在 2026-10-17 05:34:20 / 05:34:44（+08）出现两张「上下文整理失败」卡片。

## 一、结论

**warm-prefix 压缩把「整段未裁剪 outbound 历史（2,140 条）+ 1 条固定摘要指令」原样重放成摘要请求**（`WarmPrefixCompaction.TryCreatePlan`：`summaryRequest = exactOutboundHistory.Append(SummaryInstruction)`），该请求从不经过 `LlmRequestBudgetGuard`。事故时该会话内存历史估算 **2,840,821 tokens**（provider 实测 **1,683,727** messages tokens、请求体 **8,063,740 B**），远超过 deepseek-flash 的 **1,048,576** 窗口与配置窗口 1,000,000 ⇒ provider 400（`summary_rejected`）⇒ UI 两张失败卡片。失败后仅裁剪**本次出站副本**（removed=1,838 → 302 条 / 603,640 估算），完整历史保留，于是下一轮必然重犯。

## 二、关键证据

- 时间线（UTC / +08）：05:34:06 heartbeat `turn.accepted`（idle 28,803s）→ 07.3 hydrate（history_count=2,139，`hydration_source=richer_in_memory_history`）→ 07.5 `context` 事件 messageCount=2,140 → 19.85 compaction started（before 2,840,821 / effectiveInputLimit 605,760 / 候选 2,047 条、771,015 tokens）→ 19.86 摘要 `chat`（message_count=2,141、tool_count=101、max_output_tokens=8,192）→ 20.9 HTTP 400 → 32.16 `context.request.trimmed`（removed=1,838，estimatedAfterTokens=603,640）→ 43.8 第二次相同请求 → 44.8 同一个 400 → 44.8 主 `chat_stream`（302 条，prompt 361,886，cache hit 360,064）成功 → 05:39:18 turn.completed。
- `agent.llm.prepare` 共 **37,271 ms**：两次计划生成（各约 11–12s 的整段 tiktoken 计量）+ 两次注定失败的 provider 调用 + 一次请求副本裁剪。
- 本地估算/provider 实测比 ≈ **1.69×**（2,840,821/1,683,727=1.687；1,738,395/1,029,366=1.689；603,640/361,886=1.668）⇒ 本地 1.77M 估算即约 provider 1.05M；事故时已越窗。
- 该 session 166 次压缩失败 / 94 次完成：10-13 有 86 次「摘要生成成功但持久提交失败」（`durable_commit_coveredmessagesnotfound`，historyPreserved=true），历史 607K→1.48M；10-14T05:23Z 起 52 次 context-length 失败（beforeTokens 1,765,556 → 2,840,821），此后 0 次 completed。10-17 23:07 进程重启后冷启动重水合只保留 66 条，症状消失但代码缺陷仍在。

## 三、修复（本批）

1. **确定性摘要失败 → 本地抽取式兜底**（`AgentExecutionService.TryWarmPrefixCompactionAsync`）：仅当 ① provider 明确拒绝输入长度（`TryGetProviderMaxInputTokens` 命中，即摘要重放本身超过模型窗口），或 ② provider 调用成功但输出不可用（空内容/工具调用）时，改用 `ExtractiveContextCompactionSummaryGenerator` 对**被替换跨度**（`WarmPrefixCompaction.SelectRemovedMessages`）生成有界摘要，之后仍走同一 `VerifyApplication` + 持久提交边界；成功时发 `completed`（增量字段 `summarySource`、`degraded`），不再让「整理」永久失败。auth/限流/5xx/超时等可恢复错误**保持 fail-closed**（不让一次瞬时故障用低质量摘要永久覆盖历史）。兜底不可用（未注册/空摘要/异常）时保持既有 `failed` 语义。
2. **同 round 双尝试去重**（`WarmPrefixMaintenanceAdmission.RecordAttempt`）：软维护调用若已走同步硬保护（`RequiresSynchronousProtection=true`），同时置 `hardProtectionAttempted`，同一 round 不得再发字节级相同的摘要请求（事故里正是两次相同请求、两张卡片、约 12s 重复计量）。缓冲与流式两条路径都已接线。
3. **provider 限长文案解析**（`LlmRequestBudgetGuard.TryGetProviderMaxInputTokens`）：新增 DeepSeek `maximum context length is N tokens` 正则（支持 `1,048,576` / `200_000`），使 provider 输入恢复/校准能识别这类 400。
4. **纪律**：摘要 raw 不得写回主请求校准（ADR-095 D6）——兜底路径**不**调用 `RecordProviderInputLimitFailure`，仅记日志。
5. **诊断性**：completed 事件新增 `summarySource`（provider / extractive_fallback）与 `degraded`；apply/持久提交被拒时 rejected 事件保留 `summarySource` 与 `summaryFallbackError`，避免 provider 失败事实丢失。

## 四、验证

- `dotnet build Source/PuddingRuntimeTests/PuddingRuntimeTests.csproj --no-restore --artifacts-path temp/build/fix-warm-prefix`：**0 error**。
- 定向 `WarmPrefix*` + `LlmRequestBudgetGuard*` 过滤：**81/81 通过**，新增用例覆盖：
  - provider 超窗拒绝 → 本地兜底 → 持久提交落库 + 内存 checkpoint；
  - 第 0 轮已越界（软准入即同步保护）+ provider 超窗拒绝 + **兜底关闭** → 同 round 仅 1 次摘要尝试，历史保持原样（不落库）；
  - 第 0 轮已越界 + provider **401** + 兜底开启 → 不触发兜底，同 round 仅 1 次摘要尝试（可恢复错误 fail-closed）；
  - DeepSeek 限长文案解析 DataRow；同 round 去重纯函数单测；`Range of input length` 旧文案兼容。
- **变异取红（证伪能力）**：把 `RecordAttempt` 的硬保护标记回退成旧语义后，两条「第 0 轮已越界」用例均如期失败（`summaryAttempts` 实际=2）；恢复后 81/81 通过。
- **全量 PuddingRuntimeTests（正常布局）**：2130 条中 **2117 通过 / 5 失败 / 8 跳过**；5 条失败均为既有环境问题（4 条终端/宿主 Shell 用例依赖 PATH `python`，命中 Windows Store 别名；1 条 Jev 真实资源池 live 调用网络超时），与本次改动无关（详见 changelog）。
- `code_map_check.py --check --paths Source/PuddingRuntime`：**gate PASS**。
- 未部署：运行中的 Desktop/Core 仍是旧构建；需外部控制器重建/重启后才能做进程内功能 smoke。

## 五、未完成 / 风险

- 未实现「摘要请求发出前预算预检」：本批是**反应式**修复（provider 拒绝一次后才本地兜底，约多 1s 延迟）；后续可加持久化负缓存/冷却，避免陷阱态每轮先发一次注定失败的请求。
- 本地兜底摘要质量低于语义摘要（仅有界抽取），事件已标注 `degraded=true`/`summarySource`，但 **UI 卡片与平台诊断/DB manifest 尚未消费该标记**（manifest 仍写死 `Degraded=false`）——这是本批明确未完成项。
- 未在真实 DeepSeek API 上重放「2.84M 历史」场景；未覆盖其它 provider 无法解析的限长文案（这类仍 fail-closed）；未做前端卡片冒烟。
- 事故会话的持久提交缺陷（10-13 的 86 次 `durable_commit_coveredmessagesnotfound`）不在本批范围：本修复只保证摘要生成不再必然失败，若跨度内容键仍不可解析，仍会按既有语义发 `durable_commit_*` 失败。
- 事故会话的 2.84M 历史在重启后已按 49,152 重水合预算收敛；本修复不回溯改写历史数据。
