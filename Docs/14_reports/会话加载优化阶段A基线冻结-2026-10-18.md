# 会话加载优化阶段A基线冻结

## 1 目的与边界

本文是《[会话首屏与渐进加载架构优化方案](../12_features/会话首屏与渐进加载架构优化方案-2026-10-18.md)》阶段 A（基线与合同）的交付记录，回答方案 §12 要求施工前冻结的四组参数：

1. 当前 SQLite 实际版本、索引定义、可删除的冗余索引与最小新增集合。
2. 每类 `ChatMessages` 写入 owner，以及旧运行状态能否构造一致最小基线。
3. 页大小、字节预算、SSE 总恢复预算与缓存容量是否覆盖实际超长消息/多模态样本。
4. 热库、冷进程、WebView2 冷初始化的测试环境与性能预算校准。

**本阶段只做只读证据与合同冻结**：没有修改 `D:\data` 数据库、没有创建/删除索引、没有执行 `ANALYZE`、没有重启 Core/Desktop、没有修改业务代码。阶段 B 的纯组件已按同一份冻结预算实现（见 [PuddingConversationReadModel](../../Source/PuddingConversationReadModel/code_map.md)）。

## 2 冻结结论摘要

| 组 | 冻结结论 |
|---|---|
| 慢查询 | 当前 `/conversation` 的关键问题不是「最近消息取太多」，而是**三个事件子查询仍按会话扫描 182 万行**：EF 原形在活库实测 `messageProcess=1,941.8ms`、`terminal=1,855.0ms`、`rootTerminalExists=1,732.7ms`（best-of-2），合计约 5.5s。 |
| 索引 | **只加索引不能解决**：合成 fixture 上加候选索引（甚至 `ANALYZE`）后，EF 原形 IN-list 查询仍约 1.4–1.5s，因为计划器继续选择 `(conversation_id, sequence)` 扫描。必须同时把查询改写为按值收敛（VALUES-JOIN/逐值查询）：fixture 实测 `messageProcess` 17.8ms、`terminal` 0.1ms。 |
| 最小新增索引 | 仅两条：`conversation_events(conversation_id, message_id, sequence)` 与 `conversation_events(conversation_id, turn_id, sequence)`；**不新增** `(conversation_id, run_id)`，根终态改用 `turn_id` 收敛（fixture 0.0ms）。`ChatMessages` 现有 `(SessionId, CreatedAt)` 已覆盖最近候选（2.5ms）；键集 `(created_at, id)` 是否需补列留给阶段 C 用真实 `EXPLAIN QUERY PLAN` 判定。 |
| 预算 | 页大小/字节/SSE/缓存/回填预算已冻结为单一常量源（`ConversationReadModelLimits`），见 §5；任何一页/一次恢复超限必须显式截断并返回继续游标，不能隐藏或伪造完整。 |
| 写入 owner | 5 类 `ChatMessages` owner 已核对：事务受理/通知/系统命令属 ingress 强身份；`ChatTranscriptWriter`、`AgentConversationLogService` 是**独立 scope 的终态兜底写入**，无法证明与投影 checkpoint 原子，旧 Turn 只能按 `syncing/partial` 处理。详见 §6。 |
| 游标/失败语义 | `eventHead`/`snapshotCursor`/`lastAppliedSequence` 三游标分离，约束 `C <= H`；失败必须区分 not-found / archived / unavailable / syncing / invalid-cursor / snapshot_required，不得伪造空会话或零计数（§7）。 |
| 测试环境 | 同一机器/构建/SQLite 版本/DataRoot 副本/fixture；热库、冷进程、WebView2 冷初始化分开报告；API 每场景 ≥30 样本、浏览器冷启动 ≥10 样本；通过线沿用方案 §10.1（§8）。 |

## 3 当前源码的真实查询形状

证据来源：当前源码 `AgentConversationProjectionService.GetConversationAsync`（`Source/PuddingPlatform/Services/AgentChat/AgentConversationProjectionService.cs`），以及用 EF Core 10 / Microsoft.Data.Sqlite 10.0.0 复刻真实 LINQ 的临时只读探针（探针源码与输出在 `temp/test-out/efprobe`，不进入版本库）。

当前真实请求（会话 `206a9b48ec904ebb93e7541131fbb835`，运行库 `sqlite_version=3.53.3`、`ChatMessages` 目标会话 4,146 行、`conversation_events` 目标会话 1,818,705 行 / 全表 3,120,332 行）的 best-of-2 实测：

| 查询 | 实测 | 行数 | 计划/说明 |
|---|---|---|---|
| `ChatMessages` 候选（limit 60） | 2.5ms | 60 | `SEARCH ChatMessages USING INDEX IX_ChatMessages_SessionId_CreatedAt` |
| `ChatExecutionCommands` by messageIds | 3.9ms | 10 | 小表，索引足够 |
| `messageProcess`：`conversation_id=? AND message_id IN(20) AND type IN(13) ORDER BY sequence` | **1,941.8ms** | 4,940 | `SEARCH ... USING INDEX IX_conversation_events_conversation_id_sequence (conversation_id=?)` → 扫目标会话 182 万行后过滤 |
| `terminal`：`conversation_id=? AND turn_id IN(10) AND type IN(4)` | **1,855.0ms** | 10 | 同上 |
| `rootTurnStarted`：最新 `turn.started` | 0.4ms | 1 | 已有 `(conversation_id, sequence)` 反向扫描 |
| `rootTerminalExists`：`conversation_id=? AND run_id=? AND type IN(4)` | **1,732.7ms** | 0 | 无 `run_id` 索引；计划器仍沿会话索引扫描 |
| `eventCursor`：`MAX(sequence)` | 0.2ms | 1 | covering index |
| activeRun 分支（仅根未终态时） | 1,670–1,673ms/查询 | — | 本会话根已终态，真实请求未执行；若执行会再叠加数秒 |

- 冷缓存第一次 `messageProcess` 曾达 **34,085ms**（OS/页缓存未热），说明首次打开还要叠加 I/O；该样本单独记录、不与热库 p95 混报。
- 真实 `/conversation` API 在 2026-10-18 08:18 诊断中实测 5.5–6.6s，与上述三条热查询之和一致；`rootTerminalExists=True` 证实真实请求未进入 activeRun 分支。
- 关键结论：**消息数量限制（60 候选/20 显示）没有限制事件扫描量**。三个查询的输入虽然各自只有 20/10 个值，但执行计划仍按整个会话扫描。

新增脚本 [`Tools/Diagnostics/conversation_scan_baseline.py`](../../Tools/Diagnostics/conversation_scan_baseline.py)（仅 Python 标准库 sqlite3；不读生产库、不写 `D:\data`）：


full 规模实测（Python `sqlite3 3.53.1`，2026-10-18）：

| 项目 | 结果 |
|---|---|
| 事件总量 / 目标会话 / 目标会话 turns | 3,120,000 / 1,818,000 / 1,820 |
| 目标会话 ChatMessages | 1,820 |
| 建库+插入总耗时 | 28.1s |
| 现有 EF 形状索引创建 | 16.4s |
| 候选索引创建 | 7.1s |
| `ANALYZE conversation_events` | 2.7s |
| fixture DB 大小 | 约 2,210 MiB（temp，任务结束可清理） |

三阶段查询对比（同一 fixture、同一 20 个 messageIds/10 个 turnIds）：

| 查询形状 | 只有现有索引 | 加候选索引（无 ANALYZE） | 加候选索引 + ANALYZE | 按值收敛改写 |
|---|---|---|---|---|
| messageProcess（IN-list） | 1,446.9ms | 1,435.5ms | 1,436.9ms | **17.8ms**（VALUES-JOIN，逐 messageId 走候选索引） |
| terminal（IN-list） | 1,488.7ms | 1,432.7ms | 1,409.7ms | **0.1ms**（逐 turnId 走 `(turn_id,type)`） |
| rootTerminalExists（run_id） | 1,357.5ms | 1,442.0ms | 1,401.3ms | **0.0ms**（改用 `turn_id` 收敛；无需 run_id 索引） |
| eventCursor（MAX sequence） | 0.0ms | 0.0ms | 0.0ms | 0.0ms |
| ChatMessages 最近候选 60 | 0.1ms | 0.1ms | 0.1ms | 0.1ms |

**冻结要求（阶段 C 必须实现）**：

1. `messageProcess` 不复用单条 IN 大查询，按有界 messageId 集合逐值/VALUES-JOIN 查询，能走 `(conversation_id, message_id, sequence)`；类型过滤不得迫使回退全会话扫描。
2. `terminal` 按有界 turnId 集合逐值查询，走既有 `(turn_id, type)` 或新 `(conversation_id, turn_id, sequence)`；返回项受 Turn 窗口限制。
3. 根终态检查改为 `rootTurnStarted.TurnId` 的终态查询（等价判定），不再按 `run_id` 扫会话。
4. 阶段 C 的 SQLite 集成测试必须打印**真实 EF SQL 的 `EXPLAIN QUERY PLAN`**；只出现 `SEARCH ... (conversation_id=?)` 不算通过，必须验证每个查询按实体键/序号收敛。
5. 若保留 activeRun 查询，则全部按 `turn_id` 收敛并计入总预算；按方案目标，首屏最终从读模型读取，不再在线推导整回合。

## 5 最小索引集与预算冻结

### 5.1 索引定义（冻结）

| 类别 | 定义 | 决策 |
|---|---|---|
| 新增 | `conversation_events(conversation_id, message_id, sequence)` | 必需：消息过程分页/首屏消息过程摘要 |
| 新增 | `conversation_events(conversation_id, turn_id, sequence)` | 必需：Turn 过程分页、后台重建、根终态 turn 收敛 |
| 保留 | `conversation_events(conversation_id, sequence)` unique | SSE 追赶、eventHead、MAX(sequence)；唯一性保护不得删除 |
| 保留 | `conversation_events(event_id)` unique | 事件稳定身份/去重 |
| 保留 | `conversation_events(turn_id, type)` | turn 级收敛（fixture C2/B2 使用） |
| 保留 | `conversation_events(committed_at)` 保留/清理相关索引 | 数据生命周期，不属于首屏查询 |
| 保留 | `conversation_events(trace_id, sequence)` | 运行时时间线诊断；阶段 C 核对消费者后再决定去留 |
| 不新增 | `conversation_events(conversation_id, run_id)` | 根终态改为 turn 收敛后无消费方 |
| ChatMessages | 现有 `(SessionId, CreatedAt)` 已覆盖最近候选；键集 `(created_at, id)` | 阶段 C 用真实 EXPLAIN 验证；`Id` 为 rowid，可能已被索引覆盖，不先建 |
| 冗余清理 | `ix_ce_seq` / `ix_ce_eid` / `ix_ce_turn`（与 EF 同名索引重复） | 复用 `StorageMaintenanceService`，核对列/顺序/唯一性/替代索引存在后再删；不在启动期盲删 |

索引创建/统计维护约束：

- 新索引与旧库升级属于**显式维护窗口**，记录创建耗时、磁盘增长、取消恢复；不计入「正常启动已变快」。
- 统计更新使用有界 `PRAGMA optimize`；完整 `ANALYZE` 只在明确维护/基准步骤执行，不在每次 Ready 前执行。
- 所有索引由 EF 模型与 schema ensure 的**同一份定义**生成/校验，新库与存量库不得出现两套名字。
- 以 fixture 数据参考：生产规模创建两条索引预计秒级到十秒级（合成库 7.1s/两条，真实库需在副本上实测），并需额外磁盘。

### 5.2 页大小与字节预算（冻结，单一来源 `ConversationReadModelLimits`）

| 对象 | 冻结值 | 超限行为 |
|---|---|---|
| 最近消息页 | 默认 20 条可显示消息，服务端硬上限 50 | 缩短预览/继续定位，保留身份与状态 |
| 打开/历史页 JSON | 128 KiB（含固定 JSON 开销估算 256B/条） | 停止返回并给继续游标 |
| 单条首屏正文预览 | 8 KiB UTF-8 | 显式「展开全文」，不裁 typed image 身份 |
| 活动正文预览 | 16 KiB UTF-8，保留尾部 | 标记此前正文可加载；不切断码点 |
| 过程明细页 | 默认 100 项、最大 200 项、单页 256 KiB | 先到哪项预算停哪项，继续游标前进 |
| 单个巨型事件/工具结果预览 | 16 KiB | 返回详情引用；全文分段读取 |
| 首屏子代理摘要 | 最多 20 项、32 KiB | 活动优先；其余另页读取 |
| 历史页候选扫描 | 200 | 不为凑满页无限扩展候选 |
| 过程页候选扫描 | 400 | 空展示页也必须推进扫描边界 |

### 5.3 SSE / 缓存 / 回填预算（冻结）

| 对象 | 冻结值 | 语义 |
|---|---|---|
| SSE 单次恢复 | 2,000 条 / 2 MiB / 1s，任一触顶即停 | 触发限额的事件不消费；停止转 `snapshot_required`，不长时间自动追赶 |
| 首屏缓存 | 5 个会话 / 5 MiB | 只缓存首屏窗口，不缓存整个大会话 |
| 后台回填 | 50 条/批、50ms 工作预算、200ms 间隔 | Ready 后先给首屏保护窗口（默认 60s），SQLite 忙时退避 |
| 回填断点 | 持久 checkpoint（数据集身份+索引版本+水位） | 重启接续，不每次从 lastId=0 重扫 |

## 6 `ChatMessages` 写入 owner 审计

| # | owner / 位置 | 写入角色 | 事务与原子性 | 身份/关联 | 对最小基线的影响 |
|---|---|---|---|---|---|
| 1 | [`ConversationAcceptanceStore`](../../Source/PuddingPlatform/Services/ConversationAcceptanceStore.cs)（`ChatMessages.Add` 约 L92-104） | user | **单事务**：用户消息 + AcceptanceBatch + ChatExecutionCommands（同一 `BeginTransaction`） | `ClientMessageId`；返回 `AcceptedSequence` | 强 owner。快照只能纳入其游标所覆盖的受理消息；用户消息由 ingress 直接写入，不得为统一而重复投影 |
| 2 | [`ConversationNotificationStore`](../../Source/PuddingPlatform/Services/Conversation/ConversationNotificationStore.cs)（约 L57-69） | user（通知） | **单事务**：消息 + ConversationEvent（含稳定 EventId/Sequence） | `request.MessageId` + `StableEventId` | 强 owner；消息与 canonical 事件同事务，可绑定接受序号 |
| 3 | [`SystemCommandHandler`](../../Source/PuddingPlatform/Services/Conversation/SystemCommandHandler.cs)（约 L143-175） | user 命令 + agent 默认回复 | **单事务**：两条消息 + ConversationEvent | `ClientMessageId` / `ResponseMessageId` | 系统命令回复不经过投影器；快照要么纳入该事务事件覆盖，要么显式标该 Turn `syncing/partial`，不能当作已投影完成 |
| 4 | [`ChatTranscriptWriter`](../../Source/PuddingPlatform/Services/ChatTranscriptWriter.cs)（约 L108-158） | assistant/user 兜底转录 | **独立 scope + 独立 SaveChanges**，与投影 checkpoint 非原子；±2s 窗口/稳定 messageId 去重；fire-and-forget 索引 | 有稳定 `MessageId` 用之，否则生成 `transcript-{guid}` | 无法证明与 checkpoint 原子。旧 Turn 若只有该路径写入 ⇒ 按 `syncing/partial`；阶段 C 必须拆出共享事务的持久化适配，不能靠外层事务补救 |
| 5 | [`AgentConversationLogService`](../../Source/PuddingPlatform/Services/AgentConversationLogService.cs)（约 L56-105） | assistant/user 兜底转录 + 私有日志文件 | 自有 `DbContext`/SaveChanges，与投影/checkpoint 非原子 | 稳定 `MessageId` 优先，否则 `transcript-{guid}` | 同 #4；还承担私有文件镜像，文件副作用不得参与首屏事务成败或游标 |

审计结论：

- 用户类消息（1–3）有明确 ingress owner 和事务/事件身份，可作为「最小基线可证明」的部分。
- 终态兜底转录（4–5）在旧 Turn 上**不能证明**与投影 checkpoint 原子 ⇒ 按方案 §12.2，不能证明的情况按 `syncing` 处理，不伪造 ready 快照。
- 阶段 C 落地时必须：拆出接收同一事务上下文的持久化适配；明确每类消息唯一 owner；baseline 截点与 accepted sequence 绑定；旧 Turn 提供 `partial/unavailable + 原因`，不在 GET 中补建/重放。

## 7 游标与失败语义（冻结）

### 7.1 三游标分离（不得混用）

| 名称 | 含义 | 允许用途 |
|---|---|---|
| `eventHead` H | 已提交事件最新位置 | 表达还有多少同步差额 |
| `snapshotCursor` C | 响应已覆盖的读模型位置 | 初次 SSE `afterSequence=C`；必须 `C <= H` |
| `lastAppliedSequence` A | 客户端已按顺序应用的位置 | 断线重连；必须与本地状态一起保存 |

- 不能先读消息再取 H 当快照游标；不能把「只保存游标、未保存状态」的缓存当完整基线。
- 服务端用**同一短 SQLite 读事务**读取 checkpoint、消息页、必要运行状态与对应 head；读事务在 DTO 取数后释放，不跨序列化/SSE。
- 旧 `SessionProjectionStore` 的 `Max(旧游标, canonical checkpoint)` 不得作为新读模型的覆盖证明；迁移时盘点旧消费者并退役旧首屏游标。

### 7.2 分页游标

- 历史：键集 `(createdAt, id)` 降序，`limit+1` 判 `hasMore`，不做 `COUNT(*)`；游标绑定 conversation、排序版本、页边界；跨会话/旧排序版本拒绝。
- 过程：canonical `sequence` 键集；绑定 conversation、可选 turn、`beforeSequence`、冻结的 `throughSequence`；空展示页也必须推进扫描边界。
- 失败原因枚举固定（不得共用模糊 `status/cursor`）：`empty_conversation`、`conversation_mismatch`、`empty_message_identity`、`sort_version_mismatch`、`turn_mismatch`、`negative_sequence`、`sequence_out_of_range`、`invalid_limit`。

### 7.3 条件请求与失败语义

- 条件请求升级为表示层版本校验：ETag 至少覆盖会话身份、主会话绑定版本、`readModelVersion`、摘要修订、请求窗口；不能只比较事件 head（投影可能无新事件追平）。
- 304 仅用于已有相同实体缓存的请求；无缓存收到 304 允许一次无条件补取，不进入空响应重试环；权限校验先于条件响应。
- 必须可区分的失败：`not_found`、`archived/unavailable`（证据被清理）、`syncing + retryAfter`（投影未就绪）、`invalid_cursor`、`snapshot_required`（差额超预算/保留缺口）、`unauthorized/forbidden`。
- completeness：`complete | partial | unavailable`；未知计数返回缺失+原因，不填零；`processSummary` 的局部覆盖必须显式 `hasMoreContent`/截断原因。

## 8 测试环境与性能预算校准（冻结）

固定条件：同一机器、同一构建、同一 SQLite/Provider 版本、同一 DataRoot 副本与 fixture；冷进程 ≠ OS 磁盘缓存已清空，需明确记录；WebView2 与无头 Edge 分开报告；Core Ready 时间与 Chat 可读时间分开计量。

| 指标 | 通过线（方案 §10.1） |
|---|---|

## 10 未证明项与阶段 C 前置

1. **索引单独无效**已被 fixture 证实；但生产库加索引后实际查询改写收益仍需在 `D:\data` 的 SQLite 在线备份副本上复核（阶段 C）。
2. 活库探针运行库 `sqlite_version=3.53.3`、fixture Python 3.53.1；Core 使用 `SQLitePCLRaw.bundle_e_sqlite3 2.1.13`，阶段 C 必须在 Core 同 provider 下重跑 EXPLAIN，不能假定计划器行为完全一致。
3. `ChatMessages(SessionId, CreatedAt)` 对 `(created_at, id)` 键集的覆盖需用真实 EXPLAIN 判定；`Id` 为 rowid 时可能无需新增索引。
4. 现有索引中存在 `ix_ce_*` 与 EF 同名索引的重复集合；清理前必须核对列/顺序/唯一性/替代索引与消费者，属于维护窗口动作。
5. 系统命令回复（owner #3）与兜底转录（#4/#5）能否构造一致最小基线尚未证明；阶段 C 必须实现事务适配或显式 `syncing`，不得把无法证明的旧 Turn 标成 ready。
6. fixture 当前为均匀 1,820 Turns；阶段 C 需扩展分布：单 Turn 十万事件、超大工具结果、同毫秒消息、数千子代理、失败无助手正文。
7. 生产库索引创建/统计更新耗时、磁盘增长、取消恢复只在副本测量后执行；不在运行库直接试跑。
