# Chat UI/UX 现代化：静态外观像素复核（2026-10-02）

对象：`Docs/11_design/Chat-UI-UX-Modernization-Spec-2026-10-01.md` 的 §13（IMG01–IMG12）与 §14（SCROLL-001）。
构建标识：页角版本徽标实测为 `v6.1.3 · 97fb4d2 · 2026-10-01 23:58`（对应提交 `97fb4d2`，前端 6.1.3）。
证据来源：**用户提供的运行截图**（2560×1344，sha256 `876156fc…`），以及改动前同布局的截图（sha256 `e58c5a08…`）。

## 1. 这次复核能证明什么、不能证明什么

**能证明**：静态外观里「颜色/底色/滚动条形态/文案」这类可直接测量的量，在**深色主题、该窗口尺寸与缩放下**的实际结果。

**不能证明**（因此下列项仍记为未验收）：浅色主题、主题切换过程、hover/focus/keyboard 反馈、拖拽与键盘微调手感、触屏点击区、动画与性能预算、可访问性细节（对比度的实际合成、屏幕阅读器）、WebView2 特有行为（焦点/IME/弹层叠层）、以及截图未入镜的界面区域。按 §13.1 的边界，截图也不构成「服务端能力可用」的证明。

采集条件不受控（非固定 DPI/窗口缩放/主题矩阵），所以本记录只作为**专项抽查**，不替代 §12 的验收表。

## 6. 第二批截图：浅色 + 工具区 + 窄标签表（2026-10-02）

用户提供了同一界面的**深色与浅色两张**截图（另含"更多"下拉与左栏顶部的裁剪）。这是本轮首次拿到**浅色证据**，也暴露了一处此前只有静态审阅、没有被指出来的缺口。

### 6.1 浅色主题首次核对：Web 侧合格

| 区域 | 浅色实测 | 判定 |
|---|---|---|
| Web 聊天区背景 | **`#f7f8fa`** | 与 §3 的浅色基准 `LightBackgroundArgb = 0xFFF7F8FA` **完全一致** |
| Web 左栏 / 顶栏 | `#fdfdfe` | §3 中性层级成立 |
| Web 输入区 | `#ffffff` | surface 成立 |

同时确认深色下这三处仍是 `#11151b` / `#191f28` / `#1a2029` —— 深浅两套都是 §3 的值，不是"只调了深色"。

### 6.2 新缺口（已修）：Web 主题开关没有标明作用范围

**实测**：浅色截图里 Web 全白，但 **Shell 工具区在深浅两张图里完全相同** —— 工具顶栏 `#27272b`、浏览器内容 `#121212`、底部状态条 `#1a2226`。即 Web 顶栏那个 ☀/🌙 开关**只改 Web**，不改 Shell。

而它当时的文案是"跟随系统（当前暗色），点击切换到手动模式"，可访问名称是"切换主题"——**没有任何地方说明范围**。这正是 §13.x 明令禁止的形态："如保留 Web 独立选择，必须标明'仅聊天区域'，不能出现两个看似全局但范围不明的开关"。

**修复**（前端 6.1.5，`95055f1`）：新增 `THEME_SCOPE_HINT` 与纯函数 `describeThemeToggle`，tooltip 变为"外观（仅 Web 工作台，右侧工具区由 Desktop 外观设置决定）：…"，`aria-label` 由"切换主题"改为"切换 Web 工作台主题"；并加 4 项测试把范围提示钉住（三模式 × 两明暗全覆盖 + 可访问名称不得回退）。

**已补齐（Shell 侧，`be0fca8`）**：Desktop 设置页的「外观」下拉下补一行说明——"影响窗口、工具区与底部状态条。Web 工作台（聊天页）顶部另有独立的外观开关，只改 Web。"，不改行为（三个选项与保存逻辑未动）。于是从任意一侧都能分清两个开关的范围。证据：Desktop 重定向链接构建 0 错误（XAML 编译通过）、Foundation 84/0、Desktop 259/0。

### 6.3 窄标签表：IMG07 的原始症状在这次拿到了验证场景

第二张深色截图里有一张 `项 | 结果` 表，首列正是**短标签**（心跳间隔 / 偏好固化 / 本轮动作）。放大实测：**三个标签各自占一行，没有被挤成多行**，结果列长文本正常换行——即 IMG07 抱怨的症状在这个真实场景下不存在。

**但归因要谨慎，并且暴露出我上一批的一处问题**：我上批给**所有**表格首列加了 `min-width: 7em`，而实测该列宽约 4em（< 7em）——说明这条规则在该表上**并没有生效**；让标签保持整行的是表格自身的 auto layout。此外规格 §13.5 明确写过这个类"**只用于具有短标签首列的规格/状态表，不能全局套在任意数据表**"，而我的实现恰恰是全局套用。

⇒ **已修正**（前端 6.1.6，`4ab177f`）：删除全局首列规则（既违反 §13.5 的限定，实测在 Chromium 自动表格布局下也不生效——真实该列约 4em < 7em，留着只会制造"已修好"的假象）；改为规格原文的 `chatLabelTable` 类作用域规则（`min-width: 7em` + `white-space: nowrap`），并由 `MarkdownBlock` 的纯函数 `isLabelTable` 按**表头词**（项/项目/字段/标签/键/属性）判定后套用——这样钩子有真实消费者而非死 CSS，判定不中的 LLM 数据表仍走默认（允许换行 + 容器横滚）。测试：新增 4 项判定测试；`img06img07` 的表格式断言改为**按真实类名**断言"规则挂在 chatLabelTable 作用域"，并加反向守卫（`markdownBody` 下不得再出现 first-child 定宽）。仍待真实会话截图确认新标签表的观感。

### 6.4 这一轮同时确认的既有改动

- **IMG03**：用户裁剪图显示"更多"下拉为 `自动朗读（已开启）` / `开发者模式（已关闭）` / 分隔线 / **`帮助（GitHub 仓库）`**，顶栏不再有孤立问号图标 —— 与 `1c97f57` 一致。

## 7. 第三批截图：6.1.6 生效 + 数据表未误伤 +「Esc 胶囊」结论（2026-10-02）

### 7.1 6.1.6 生效

页角徽标实测 `v6.1.6 · 4ab177f · 2026-10-02 09:02`，与部署核对一致。

### 7.2 IMG07 的**非误伤**证据（数据表）

截图里有一张 `名称 | 最后修改 (UTC)` 表：首列是 `agents/`、`data/`、`Docs/` 这类**数据**，表头是「名称」——不在 `isLabelTable` 的判定词（项/项目/字段/标签/键/属性）内，因此不套 `chatLabelTable`，走默认的"允许换行 + 容器横滚"。渲染正常（每行一行、时间列对齐）。这条补上了 §6.3 里缺的反面证据：判定**不误伤**数据表。

### 7.3 「Esc 胶囊」：证据表明它不是 Pudding 的 UI（结案）

此前多轮都没能解释聊天区里出现的小 `Esc` 胶囊。本轮用两组证据结案：

1. **同坐标对照**：把三张截图在**同一预览坐标**（x 770–860、y 298–338）裁出来对比——6.1.4 那张**深色**截图在该位置**完全空白**，浅色那张也是空白（浅底上白色键帽本就不易分辨），只有 6.1.6 这张多出一个**纯白键帽式**胶囊。即它是**浮在固定位置的独立叠加物**，不是随消息卡内容/滚动移动的元素。
2. **产物全量扫描**：对部署产物所有 chunk 的 `sourcesContent` 搜 `>Esc<` / `'Esc'` / `Esc+关闭|退出|取消|返回`，命中只有三处**注释**（`CommandPalette`、`useGlobalShortcuts`）、一个 workspace 抽屉页脚（`WorkspaceAgentSettingsDrawer` 的「Ctrl+S 保存 · Esc 关闭」，不在 chat 页）、以及 `MentionPalette` 的整句提示（`@ 指派给…（↑↓ 选择，Enter 确认，Esc 关闭）`，仅在该面板打开时出现）与 `@dnd-kit` 的键盘枚举。**chat 页面没有任何源渲染独立的 Esc 键帽。**

⇒ 该键帽**不属于应用**：它是纯白、不随主题（应用内同类元素都会走 caption/border token），且只在某一两张截图里出现。最可能是**截图/录制软件叠加的按键提示或标注**。结论登记在此，避免后续再重复排查；若它确实来自某款工具，确认一下即可。

（保留一句诚实的余地：截图是唯一证据来源，无法排除"某个只在特定交互后出现的应用元素"。如果你在实机里看到它、并能给出触发步骤，我按步骤复现后再定位。）

## 8. 第四批截图：浅色模式两处宿主表面缺陷（2026-10-02）

第四批截图（设置页 + 两处标注"颜色"）暴露了**两个真实缺陷，根因是同一个**：`ApplyWorkbenchAppearance()` 只作用在**主工作台那一个 WebView2** 上，标题栏按钮与工具区浏览器表面都没被覆盖。

### 8.1 缺陷一：浅色下标题栏按钮与白色高度相似、无法分辨（用户报告）

窗口使用 `ExtendsContentIntoTitleBar = true` + `SetTitleBar(TitleBar)`，此时最小化/最大化/关闭**不再自动跟随应用主题**；系统深色 + 应用浅色时就是白色字形画在浅色标题栏上。仓库里**从未设置过** `TitleBar.Button*Color`（全仓 grep 无命中）。

**修复**（`d106368`）：由外观落点显式给出两套值——字形 / 非激活字形 / hover 与按下背景（背景透明让 Mica 透出），取值来自 Foundation 新增的 `CaptionGlyphArgb`、`CaptionInactiveGlyphArgb`、`CaptionHoverBackgroundArgb`、`CaptionPressedBackgroundArgb`。测试断言：字形必须完全不透明、浅色方案用深字形且相对亮度 < 0.2、深色方案相反，**对比度 ≥ 7:1**；hover/按下背景必须半透明。

### 8.2 缺陷二：浅色下工具区浏览器是一片纯黑（上张截图标注"浅色模式下的颜色"）

实测同一张浅色截图里：Shell 工具首页 `#f6fafc`、工具工具栏 `#fdfdfe`，而**浏览器内容区 `#121212`** —— 那是 Chromium 在 UA 深色下的 `about:blank` 画布。工具区浏览器走 `WebView2BrowserRuntime` 的**独立** WebView2（`WinUiBrowserSurfaceHost`），从未拿到 `DefaultBackgroundColor` / `PreferredColorScheme`。

**修复**（`d106368`）：WinUI 版 `IBrowserSurfaceHost` 增加 `ApplyAppearance(argb, scheme)`（WPF/archive 版接口不动，`Tests/PuddingDesktop.Tests` 的替身不受影响）；`WinUiBrowserSurfaceHost` 记住最近一次设置、对**新建表面自动继承**（避免"先开浏览器再切主题"复现黑画布）；`MainWindow` 在浏览器就绪后立刻同步一次，并在每次外观变化时同步。

### 8.3 同一份判断

新增 Foundation `WorkbenchPreferredColorScheme` + `PreferredColorSchemeFor`（**System 必须映射为 UA `Auto`**，不能把宿主选择冒充成系统偏好），`MainWindow` 的 `ToColor` / `ToWebView2Scheme` 是唯一映射点，三处宿主表面（标题栏按钮、工具区浏览器、主工作台）共用同一份判断。
