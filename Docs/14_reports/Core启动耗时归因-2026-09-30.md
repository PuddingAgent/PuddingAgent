# Core「启动耗时 21.5 秒」归因

日期：2026-09-30；触发：用户就运行中心「启动耗时 21.5 秒 · 接口 127.0.0.1 · PID 26676 · 启动于 09-30 07:00:31」提问「为什么这么长，Core 启动都做了什么」。

前置：`Chat-Queue-Response-Fix-2026-09-30.md` 结尾明确「未将 21.5 秒启动时间归因为性能缺陷」。本报告接续该未决项。

> **本报告含一次自我更正**：初稿曾把「机器负载使启动从 6.5 s 涨到 12.4 s（甚至 111 s）」当作结论。后续查明那些"负载"主要来自**我自己被 `job_kill` 后残留的孤儿 Python 进程**（见 §6），已按干净重测数据重写 §4/§5。

## 1. 结论摘要

1. **21.5 秒是 Desktop 的测量口径**，不是 Core 自报：等于「子进程 spawn」到「stdout 收到 `PUDDING_DESKTOP_READY` **且** `/health/ready` 返回 2xx」。
2. 该次启动的 **17.46 秒（占 81%）没有产生任何一行日志**：进程创建于 07:00:31，而 `logs/system` 当日文件的**第一行**是 07:00:48.460。
3. 失明原因已定位并修复（§8）：初始化阶段的 `[Startup] ...` 全是 `Console.WriteLine`，只进 Desktop 的内存环形缓冲（运行中心面板），**不落文件**且**不带耗时**。
4. **排除**：DI 注册与容器构建。同一二进制、隔离 DataRoot、schema 已存在时，`[Startup] Host built`（含 `builder.Build()` 与 `ValidateOnBuild=true`）出现在进程启动后 **536–724 ms**。
5. **排除**：启动期索引重建。25 个 schema bootstrapper 涉及的索引在现网库中**全部已存在**（已逐条读 `sqlite_master`），`CREATE INDEX IF NOT EXISTS` 均为空操作。
6. **排除**：平台库的 192.4 MB 未检查点 WAL。实测把探针库的 WAL 灌到 **209 MB** 再启动：Platform 阶段 **1.83 s**，与同库无大 WAL 时的 **2.01 s** 无差异，且主库仍为 0 字节（根本没发生检查点）。见 §5。
7. **主因最可能是冷启动期的 CPU/磁盘争用，而不是某个数据相关步骤**：同一个二进制、同一条代码路径，实测跨度 **3.75 s → 12.4 s → 111.6 s**（后者由我自己的孤儿进程造成）。07:00:29 启动的 `PuddingDesktop.exe`（WebView2 + 自身程序集冷加载）与上一个 Core 的拆除，与 07:00:31 的 Core 冷启动完全重叠。
8. **未证明**那 ~15 秒的逐阶段归属。埋点已就位（§8），重启一次 Core 即可读到精确到每个 bootstrapper 的 `delta`。

## 2. 21.5 秒的定义位置

- `Source/PuddingDesktop.WpfArchive/Core/CoreProcessSupervisor.cs`（由 WinUI Desktop 链接编译）
  - `startedAt = DateTimeOffset.UtcNow`（`process.Start()` 之前）
  - `ReadyAt = DateTimeOffset.UtcNow`（收到 Ready 行 **且** `/health/ready` 通过之后）
- 展示：`Source/PuddingDesktop/MainWindow.xaml.cs:123`
  `启动耗时 {(ready - session.StartedAt).TotalSeconds:F1} 秒`
- Ready 行由 `Source/PuddingAgent/Program.cs` 在 `InitializeAsync` + `StartAsync` **之后**输出 ⇒ 该数字覆盖「进程创建 → 组合根 → 初始化 → 所有 HostedService 启动 → 监听就绪」。

## 3. 现场证据（只读）

- `D:\data\logs\system\pudding-20260930_002.log` 第一行：
  `2026-09-30 07:00:48.460 [INF] [ConnectorStreamSchema] Projection table ensured`
- 该行对应 `PuddingApplicationInitializer` 的第 9 个 bootstrapper；它**无条件打日志**，因此是「静默窗口」的右边界。
- 全 `D:\data\logs` 在 `07:00:30–48` 只命中 2 行，且都在 48.460 之后；最早的其他日志是 07:00:50.945（组件日志）。
- 48.460 之后剩余启动约 4 秒：48.899 EventStore、49.15–49.58 Controller DB schema 警告、50.105 KeyVault、50.190 ConnectorHost/P2P、50.675 `ConnectorHost Started with 5 connectors`。

## 4. 干净实测分阶段基线

装置：`temp/measure-core-startup.ps1`（隔离 DataRoot + 专用端口 + 逐行 stdout 时间戳）。
被测二进制与现网一致：`Source\PuddingAgent\bin\Debug\net10.0\PuddingAgent.exe`，`ASPNETCORE_ENVIRONMENT=Production`，`--desktop-child`。

| 阶段 | run1 空库首启 | walA2 schema 已存在 | walB 同库 + 209 MB WAL |
|---|---|---|---|
| → `[Startup] Host built` | 1077 ms | **724 ms** | **536 ms** |
| → `Ensuring Platform DB tables...` | 1365 ms | 988 ms | 808 ms |
| → `Platform DB tables ... ensured` | 3737 ms（+2372） | 2994 ms（**+2006**） | 2637 ms（**+1829**） |
| → `Conversation Event Store ... ensured` | 3763 ms | 3014 ms（+20） | 2657 ms（+20） |
| → `Memory DB tables ensured` | 5001 ms（+1238） | 3198 ms（**+184**） | 2847 ms（+190） |
| → `Workspace Catalog loaded` | 6135 ms（+1134） | 3725 ms（**+527**） | 3357 ms（+510） |
| → `jieba tokens backfill completed` | 6154 ms | 3753 ms（+28） | 3380 ms（+23） |
| → `PUDDING_DESKTOP_READY` | **6521 ms** | **4131 ms** | **3749 ms** |

要点：
- **无争用时同一二进制只要 3.7–6.5 秒**，其中组合根（MVC application parts + 全部 DI 注册 + `builder.Build()` 含 `ValidateOnBuild`）不足 1 秒。
- 现网那次是 21.5 秒；本表说明代码路径本身没有 15 秒级别的固有开销。
- 逐阶段最贵的是 Platform DB ensure（约 1.8–2.4 s）与 Memory DB / Workspace Catalog（首启各约 0.5–1.2 s）。

## 5. 已实测证伪的候选

| 候选 | 结论 | 证据 |
|---|---|---|
| DI 注册 / `ValidateOnBuild` | 证伪 | `Host built` 在 536–724 ms；`StartupConfig` 审计行到 `Host built` 仅约 306 ms |
| 启动期重建索引 | 证伪 | `sqlite_master` 逐条核对：`IX_TokenUsageEvents_*`(7)、`IX_llm_gateway_usage_events_*`(4)、`session_steering_messages`(5) 等全部已存在 |

| `MessageFabricSchemaBootstrapper` 的无条件全表 UPDATE | 量级不足 | 现网 `message_deliveries` 仅 6,230 行、`room_messages` 5,519 行（仍是应修的实现缺陷，见 §10） |

## 6. 重要测量教训：`job_kill` 不杀孙进程

本次先后有 3 个 Python 进程（`inspect-platform-db.py` ×2、`backup-dbs-for-probe.py`）在 `job_kill` 之后**继续存活**并持续读取 9.2 GiB 的 platform.db，把整机磁盘打满。表现：

- 空库启动实测 **111.6 s**（Platform 16.7 s、Memory 8.7 s、**Workspace Catalog 73.9 s**）。
- 逐文件复制 1,287 个文件耗时 **884,865 ms**（0.69 秒/文件）。
- 一度据此得出「启动耗时对机器负载极其敏感」的错误结论。

在杀掉这 3 个孤儿进程后，**同一 DataRoot、同一二进制**立刻回到 **4.13 s**。

⇒ 规则：**在 `job_kill` 之后必须用 `Get-CimInstance Win32_Process` 确认没有残留的孙进程**；任何"负载导致变慢"的结论，必须先证明当前负载不是自己造成的。另外，`sqlite3.Connection.backup()` 在本机对该 9.2 GiB 库 26 分钟 0 字节、仅 9 秒 CPU（挂住），不要用它做此库的复制；如需副本，改用停机窗口的文件级复制或 `VACUUM INTO`。

- `23a8e83`（本次）：该提交**收了 `phases` 却没有往下传**，整个初始化段仍只是一个 `initialized` 增量。现补：

  - 为 `PlatformDbEnsure` / `EventStoreEnsure` / `MemoryDbEnsure` / `WorkspaceCatalog` / `JiebaBackfill` 各打一点；
  - 为 **25 个 schema bootstrapper + `EnsureCreated`** 各打一点。
  - 零行为变更：只加打点，不改调用顺序、不吞异常、不改 DDL。
- 行格式（可 grep）：`[StartupPhase] schema-MessageFabricSchemaBootstrapper total=17500ms delta=3000ms`；**`delta` 才是刚结束那一步的耗时**。

## 9. 未决与确定性下一步

**未证明**：17.46 秒静默窗口中，组合根（实测 <1 s）与「Platform-ensure 的 `EnsureCreated` + #1–#8」各占多少。

**确定性手段**：重启一次 Core（运行中心「重启」），读 `logs/system/pudding-*.log` 中的 `[StartupPhase]` 行：

- 若 `host-built` / `middleware-mapped` 的 `delta` 很大 ⇒ 冷启动 CPU/程序集加载争用（与 §6 一致），优化方向是**降低冷启动成本**（Release/ReadyToRun 发布、减少启动期程序集与 `ValidateOnBuild` 面积），而不是改数据。
- 若某个 `schema-*` 的 `delta` 很大 ⇒ 直指该 bootstrapper，按 §10 修。

**该埋点目前的已知缺口**：`process-start` 实为「托管入口」而非「OS 进程创建」，**运行时与程序集加载的耗时仍落在第一个打点之前**。要覆盖它，需用 `Process.GetCurrentProcess().StartTime` 与首点时间取差额。

## 10. 顺带发现的确定性缺陷（未修）

- `Source/PuddingPlatform/Services/MessageFabric/MessageFabricSchemaBootstrapper.cs` 每次启动都：
  - 无条件执行 4 条 `UPDATE message_deliveries ...`，其中 `SET execution_state = CASE ... instr(lower(coalesce(last_error,'')),'busy') ...` **无 WHERE，重写整表**；另一条对 `room_messages` 每行做 3 次 `replace(lower(...))` 再 `LIKE`。属**每次启动重复执行的一次性脏数据整备**，应改为带版本标记的一次性迁移。
  - 8 条 `ALTER TABLE ... ADD COLUMN` 每次都靠「抛 `duplicate column name` 再捕获」跳过；应改用与同批其它 bootstrapper 一致的 `PRAGMA table_info` 前置判断。
- `Source/PuddingPlatform/Services/TokenUsageSchemaBootstrapper.cs` 每次启动做约 25 次 `PRAGMA table_info` 往返与 6 条 `CREATE INDEX IF NOT EXISTS`。

## 11. 边界

- 全程只对 `D:\data` 做**只读**查询（`mode=ro` + `PRAGMA query_only=ON`）；没有写入、没有改配置、没有重启生产 Core、没有改写运行状态。
- 隔离测量使用独立 DataRoot（仓库外路径）与独立端口（18080–18094），未与运行中的 Core 争用同一 DataRoot 或锁文件。
- 未在生产 Core 上重启验证埋点输出；§8 的验证只到编译与单测。埋点行要在下一次 Core 重启后才第一次出现。
- 临时产物已清理（探针目录、`temp/test-out` 下的测试 DataRoot）；`temp/measure-core-startup.ps1` 与三个只读核查脚本保留在 `temp/` 根（git 忽略）。
