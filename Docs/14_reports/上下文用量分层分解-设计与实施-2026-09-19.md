# 上下文用量分层分解 —— 设计与实施

日期：2026-09-19 ｜ 触发：用户诉求「给上下文进度条添加颜色，需要细分并统计不同 token 占比」

## 一、结论先行

进度条改为**分段彩色条**，条的总长 = **模型配置的上下文窗口**（1,000.0K），从 12 点方向分三类区段：

| 区段 | 含义 | 数据来源 |
|---|---|---|
| 5 段彩色 | 已使用 token 按**来源**拆分 | 请求组装点按消息类别分别计数 |
| 1 段中性灰蓝 | **系统预留**（输出预留） | `contextWindowTokens − effectiveWindowTokens` |
| 1 段浅灰 | **可用余量** | `remainingTokens` |

色段之和 = 已使用；`已用 + 预留 + 余量 = 窗口`，与标题百分比（分母 = 模型窗口）同口径。

## 二、分类口径

用户点名的分类是「压缩后记忆 / 会话消息 / 思维链 / tool 调用 / 系统预留」。落到**可测量**的粒度：

| # | 类别 | 判定键 | 可行性 |
|---|---|---|---|
| 1 | 系统提示词 | `Role == System` 且正文不含 `<compact_summary>` | ✅ 已有字段 + 排除摘要 |
| 2 | 工具定义 | 工具 schema 序列化 | ✅ 既有 `ToolDefinitionTokens` |
| 3 | 压缩后记忆 | 正文含 `<compact_summary>` 标记（**不按角色**，注入路径可能落在 System 或 User） | ✅ 标记识别 |
| 4 | 对话消息 | `Role == User/Assistant` 且非摘要，**扣除思维链部分** | ✅ |
| 5 | 思维链 | 消息 `ReasoningContent` 部分单独计量 | ✅ 请求侧的 `ChatMessage.ReasoningContent` |
| 6 | 工具结果 | `Role == Tool` 且非摘要 | ✅ |
| — | 系统预留 | `W − E` | ✅ 前端算，纯派生 |

**不变量**：1–6 之和恒等于 `MessageTokens`（各桶互斥且穷尽）。已由单测锁定。

**被否决的口径**：
- 「连接器及 MCP / 技能」（参考图 4 的另两项）：请求侧不按这两个维度组织，无对应消息类别，**不伪造**。
- 按 DB `ContentType` 分类：DB 侧只有 `text` / `compact_summary` 两类，无法区分思维链与工具结果 —— 所以分类落在**请求组装点**而非 DB。

## 三、后端设计（已实施）

落点：`ContextUsageSnapshotStore.CaptureLlmRequest` —— 请求组装时唯一能看到完整消息构成与工具列表的位置。

- `ContextUsageSnapshot` 新增：`SystemPromptTokens` / `CompactionSummaryTokens` / `ConversationTokens` / `ToolResultTokens` / `ReasoningTokens`
- `CaptureLlmRequest`：主循环按角色 + 摘要标记分桶；思维链用**独立二遍扫描**计量并从对话桶扣除（改动面最小、不触碰既有归类分支）
- `ContextHealthSnapshot` 新增同名 5 个可空字段（`init` 属性，不改位置参数签名 → 既有构造点与测试不受影响）
- `ContextCompactionService.GetHealthAsync` 透传
- REST 端点直接返回该 record（`Ok(health)`），**无需改 DTO**

## 四、前端设计（本轮实施）

- `api.ts`：类型补 5 个可选字段
- `ContextUsageRing`：进度条改分段渲染 + 图例列表；每行 `色点 · 名称 · 百分比`
- **归一化**：字典估算与 provider 报数（`usedTokens`）不同源，直接把估算段画到窗口刻度上会与标题百分比打架。故按 `usedTokens / Σ(五桶)` 缩放后再计算段宽，图例数值同步用缩放后的值 —— 保证「色段之和 = 标题已用」。
- **降级**：五桶全为 0（旧后端 / 未组装）时回落为现有单色条，不显示图例。
- 配色（沿用应用既有色板 + 参考图色序）：系统提示词 蓝 / 工具定义 绿 / 对话消息 橙 / 思维链 紫 / 工具结果 青；系统预留 中性灰蓝；可用余量 浅灰。

## 五、验收

1. `dotnet test PuddingCoreTests --filter ContextUsageSnapshotAttribution` → 3/3 通过（互斥性、标记识别、思维链扣除）
2. 前端构建过体积门禁
3. 部署后面板出现分段彩色条与图例；标题百分比 = 色段之和 ÷ 窗口
4. 压缩前后对比：压缩应使「压缩后记忆」段上升、其它段下降

## 六、遗留

- 「思维链」段实际是否有量，取决于历史消息是否回传 `ReasoningContent`；若为 0 则图例该项显示 0%，属真实情况而非缺陷。
- `ContextUsageSnapshot` 的 provider 覆盖路径（`RecordProviderUsage`）已同步携带新字段，避免被旧值覆盖为零。

## 七、重启后分层消失：修复 + 顺带发现的真实缺陷（2026-09-19 续作）

### 7.1 根因

分层六桶只在请求组装点算得出（`ContextUsageSnapshotStore` 是内存态、按会话、重启即失）；
`GetHealthAsync` 的 5 级回退中**只有第 1 级带分层**，第 2~4 级只填 `UsedTokens`/`MessageTokens`/`HistoryMessageTokens`。
于是重启后（或本进程内该会话尚未发请求）六桶全 0 → 前端 `segments` 为空 → 分段条与图例整块消失。

### 7.2 修复

1. `RequestContextAttribution` 补带 5 桶（请求冻结时捕获 → 随 usage 落账）；
2. `TokenUsageEvents` 新增 5 列（`TokenUsageSchemaBootstrapper` 幂等加列）；
3. `SessionTokenDiagnostics` 与仓储读取补齐 5 字段；
4. `ContextCompactionService` 的 DB 回退源（level 2）回填 5 桶，并加**完整性 fail-safe**：
   只有「新五桶齐备」的行才用于分层 —— 旧行只持久化了旧四字段，用它渲染会漏桶
   （例如「对话消息 0%」而会话显然有消息），正是用户投诉过的「显示错误的信息」；
   否则回落单色条 + 给出不可用说明；
5. `Source` 标为 `provider_usage_db_layers`，前端据此注明「分层口径：最近一次请求的落账值」。

### 7.3 顺带发现的真实缺陷（同一提交内修复）

新增回归用例首次**真正调用**仓储读取路径时暴露：

```
System.NotSupportedException: SQLite does not support expressions of type 'DateTimeOffset' in ORDER BY clauses.
```

`TokenUsageEventRepository` 的四个查询都对 `OccurredAtUtc`（DateTimeOffset）排序，SQLite 在**翻译期**即抛异常，
而调用方 `catch (Exception)` 只写 Debug 日志 → **DB 回退源（provider_usage_db / 分层诊断 / 熵诊断）自始就是静默失效的**。
排序改为按自增主键（插入序 = 记录序）并在代码内写明原因；新增
`TokenUsageRepository_AllReadPaths_AreTranslatableOnSqlite` 作为护栏。

**已知限制（未修）**：`GetFilteredAsync` 的 `from/to` 走 DateTimeOffset **比较**，SQLite 同样不可翻译
（实测 `could not be translated`）；该方法全仓无调用方（死路径），已在代码内标注，接线前必须先改为可翻译谓词。
