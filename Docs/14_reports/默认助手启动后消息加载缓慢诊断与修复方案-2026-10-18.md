# 默认助手启动后消息加载缓慢诊断与修复方案

## 结论与范围

用户截图中的骨架屏对应 `MessageList.tsx` 的 `historyLoading && turns.length === 0`。本次确认的主要瓶颈是运行中旧版 `/conversation` 的服务端查询，以及已提交优化没有部署到实际启动目录。不是仅凭截图推测前端渲染慢。

2026-10-18（北京时间）对当前实例进行正常登录后的 GET 测量、进程/静态资源核对、SQLite `mode=ro` + `query_only=ON` 查询与 EXPLAIN 对照。没有发送聊天、调用模型、重启 Desktop/Core、执行 DDL/DML、修改业务代码或部署产物。业务接口内部及既有后台 Worker 可能产生正常运行日志/事件；本次未启动额外 Core。

本次没有采集 WebView2 点击到首绘制/可交互的 trace，不能把 HTTP 耗时等同于完整用户等待时长，也不能声称已经修复或验收完成。

## 3. SQL 原因：结果只有 20 条，扫描范围仍是整个会话

数据库：`D:/data/databases/pudding_platform.db`，约 11.12 GB（十进制）。默认助手事件数在采样时从 1,824,517 增至 1,824,777；运行中的后台回合使数据继续变化。

旧版首屏逻辑对可见 messageId / turnId 使用 `IN (...)`，再按 `sequence` 排序。只读 SQL 对照模拟这两种查询形状；不是从运行中 EF 截获的逐条 SQL trace。实际计划均为：

```text
SEARCH conversation_events USING INDEX ix_ce_seq (conversation_id=?)
```

这只按会话收敛，仍需检查约 182 万事件。仅给响应加 `20 条` 上限不能限制前面的事件扫描成本。

对照改为源码已有的逐 messageId / turnId 等值查询，SQLite 使用：

```text
IX_conversation_events_conversation_id_message_id_sequence (conversation_id=? AND message_id=?)
IX_conversation_events_conversation_id_turn_id_sequence (conversation_id=? AND turn_id=?)
```

第二次完整对照（枚举值与生产合同一致）：

| 查询 | 旧查询 | 收敛查询合计 | 返回行数 |
|---|---:|---:|---:|
| 可见消息过程摘要输入 | **1628.03 ms** | **14.17 ms** | 两者均 7,641 |
| 可见 Turn 终态 | **1650.01 ms** | **7.73 ms** | 两者均 10 |

第一次过程查询对照为 2004.50 → 78.65 ms；两次都支持同一执行计划结论。结果行数相同不等于业务语义已全面回归；这里用于成本归因。两条新索引在现场库中**已经存在**，无需再通过重建索引解决本次问题，关键是运行新查询代码。

先前[临时 Core 验证报告](会话加载优化阶段D端到端验证-2026-10-18.md)记录旧入口优化后 p95 514.1 ms、新入口 p95 111.7 ms。那是此前临时环境的 30 样本结果，明确没有正式替换产品部署，不能冒充本次实例或 WebView2 的验收数字。

## 4. 会持续影响体验的附加问题

### 4.1 缓存读取与写入使用了不同 owner

现场旧 `/conversation` 返回 `ownerUserId=Administrator`；已部署 sourcemap 的 `selectAgent` 使用 `DEFAULT_AGENT_CHAT_OWNER_ID=single-user` 读取缓存，`saveConversation(fresh)` 则按响应的 owner 写入。

因此本次响应写入 `default::Administrator::<agent>`，下次选择读取 `default::single-user::<agent>`，不能复用该条缓存。该链路有代码和真实响应支持；本次未读取 WebView2 IndexedDB，不能断言用户库里不存在其他历史缓存。

当前源码已修正 Controller 使用 NameIdentifier，再将 admin 归一为 single-user；但前端 select 中常量 owner 与外层 owner 仍有混用：缓存读使用 single-user，`fetchConversationOnce` 却把初始化输入的 owner（登录 userid 可为 admin）传给快照适配器并写入返回视图。新快照路径也可能写到 admin key，不能认为只修 Controller 就解决缓存。需统一并锁定测试，同时覆盖活动回合 legacy 分支。

### 4.2 缓存 I/O 位于首屏门槛

`chatClientStore.ts` 先 `await cache.loadConversation` 才发网络请求；收到响应又 `await cache.saveConversation(fresh)` 才设置 `isOpening=false`。缓存慢会叠加等待；缓存读取在 try 之外，拒绝时可能直接跳过网络加载并留下打开状态。源码与已部署 sourcemap 均可见此结构。本次未测得缓存的独立耗时，因此将其列为确定的可靠性问题、尚未量化的延迟放大项。

### 4.3 新读模型已有陈旧运行态，不能只切接口

本次只读交叉核对：

- `conversation_read_state` 最后更新 **11:00:29**，revision=309，current turn 为 `7979dff27f5c470f9e47532024c5484e`，terminalState=0（未终态）。
- 同 Turn summary 的 lastSequence=1,820,442，terminalState=0。
- canonical 事件已在 **13:04:22**、sequence=1,821,473 写入该 Turn 的 **turn.completed**。
- 共用的 `conversation_projection_checkpoints` 却在 **18:29:49** 已到 1,824,777。

这证明新读模型与旧投影 checkpoint 已失配。结合旧 Core 继续运行、早前临时 Core 建表的记录，最符合证据的解释是旧投影继续推进共用 checkpoint，而未维护新摘要；需以构建/投影诊断进一步确认完整写入时间线。

新 API 将 snapshotCursor 取自共用 checkpoint，同时从陈旧 read_state/summary 返回 activeTurn。前端适配器遇到未终态 activeTurn 会 `await legacy(...)` 后才交付首屏。因此直接部署新前端仍可能持续走旧查询；已经越过终态事件的 SSE 起点也不能自动补回缺失的历史终态。

### 4.4 fallback 过宽，且阻塞打开

`conversationSnapshotAdapter.ts` 对新接口的任何异常均回退 legacy，包含取消、鉴权、服务端失败等；活动 Turn 也串行等待 legacy。它既掩盖配套部署失败，又让新入口无法稳定获得预算内首屏。既有源码仍有该过渡分支。

## 5. 建议修复顺序与具体落点

### P0：让已有查询修复进入真实产品构建

1. 从明确的已提交版本构建前端与 Core；前端以 `package.json` 为唯一版本真源，重新 `pnpm run build`，不要直接复制目前与源码版本不一致的 dist。只有新增前端代码修改时才按规则递增版本。
2. 使用 `temp/build/recovery` 隔离输出，先 restore/build；Desktop build/test/publish 串行。核对 Core 包中的 Platform DLL、`wwwroot/admin/index.html` 及 bundle 构建信息。
3. 由进程外控制器读取 Desktop 实际 Core 路径，完成停止、替换整套产物、启动和回读；保留可回滚制品。不能只把产物放进另一个临时目录，也不能让 dev-up 与 Desktop 同时占用 DataRoot。
4. 首先验收已优化旧 `/conversation` 的降耗。这一步不依赖新读模型完整性；即使新路径暂未启用，也应消除会话级两次扫描。无需删聊天记录、重置数据库或再次建已有索引。

### P1：修复读模型状态后再把新快照作为首屏唯一来源

1. 在 SQLite 在线备份副本上实现/验证显式维护流程：从 canonical 事件重建受影响会话的读模型，或对当前与可见 Turn 做有证据的有限修复并保持其余部分 `Partial`；压缩/子代理状态也必须满足覆盖口径。维护可分批、可取消、有进度，不进入 GET 热路径。
2. 不直接回退共用 checkpoint 触发全量消息重放，也不仅把 terminalState 手改为完成。若引入独立读模型覆盖位置，应定义其与消息 checkpoint 的关系，只有同一快照确实覆盖的 C 才能作为 SSE 恢复起点；这是正确性设计，不能靠版本号掩盖数据缺口。
3. 针对本次“旧 writer 推进 checkpoint、新摘要停留旧 Turn”的 fixture，必须证明重启后返回真实终态、不会复活运行态、不会遗漏 C 之前的终态事实。
4. 将有界 active preview、Turn/runtime 摘要直接映射到现有渲染合同，先展示最近消息与可编辑输入，再用 SSE 追平；过程明细/长正文按需展开。不要把 full legacy projection 放在 `await` 首屏链路中。
5. 在可控的配套交付中移除静默兼容 fallback；部署不匹配、鉴权和服务失败分别返回可诊断错误，AbortError 直接取消。若短期保留退路，必须显式策略、可观测原因且不串行阻塞已有快照。

### P2：修复缓存与加载状态

1. 所有入口按同一认证身份/服务端归一化合同生成 cache key；禁止用显示名作为身份。检查初次选择、活动 legacy、后台同步、退出重登与快速切换。
2. 网络请求与缓存读并行；缓存命中可先展示，但迟到缓存不得覆盖较新的网络结果。所有提交校验 scope/generation。
3. 网络成功后先提交视图、解除 opening，再异步写缓存；写入失败记录诊断，不隐藏已收到的消息。缓存读取失败应继续网络请求。
4. 缓存读写设置有界等待及失败降级；超时/取消不能无期限骨架屏。输入可编辑与“已具备正确会话身份/游标、允许发送”分开建模，发送仍遵守既有防串会话围栏。
5. 对照 `agent.select` 的 `cache.loadConversation / api.getConversation / cache.saveConversation / select.finish` 埋点与浏览器 resource/long-task，分别测服务端、传输、解析、首帧、可发送状态，不能只测合成渲染。

## 6. 验收门禁（目标，不是本次达成结果）

- 部署：新 PID、新 Core 文件哈希、实际 Core 路径、前端版本/commit/build time 对齐；正式交付无 `+dirty`；新接口返回 200，不再靠旧路径掩盖部署错误。
- 正确性：现场已终态 Turn 不得仍 active；读模型覆盖与 SSE 游标一致；旧库 Partial 有明确展示，不伪造完整；首次打开不触发全量回放或 GET 内补建。
- 性能：按既有方案，统一打开 API p95 ≤200 ms；本机健康环境点击到可见消息/可发送目标 p95 ≤1 s；缓存命中首帧目标 ≤200 ms。每种稳态场景至少 30 样本；冷进程、冷 WebView2 另列，活动/空闲分开。
- 场景：空闲长会话、活动长回合、首次无缓存、重启后缓存、缓存被阻塞/拒绝、快速 A→B、网络失败/取消；消息/正文/过程分页不重复、不丢失、滚动锚点稳定。
- 数据库：EXPLAIN 必须按 messageId / turnId 收敛，首屏禁止退回整会话事件扫描；百万级现场副本验证。
- 产品：外部控制器判定启动、重启、退出回收；进程内新会话证明功能已由新构建执行。现有临时 Core 结果不能替代 Desktop/WebView2 验收。

## 7 修复与复核（2026-10-18 19:20）

本轮已在源码实施并验证以下修复（提交见同日 changelog）：

- **缓存身份键/加载状态**：`chatClientStore.selectAgent` 不再用 `DEFAULT_AGENT_CHAT_OWNER_ID` 覆盖配置 owner；缓存读、网络请求、保存使用同一 `ownerUserId`。网络快照到达后先提交会话并解除 `isOpening/isRefreshing`，再 await IndexedDB 写入。
- **陈旧读模型自愈**：`ConversationProjectionWorker` 除 `head > checkpoint` 外，额外发现 checkpoint 已到 head 但 `read_state` 落后 >1 分钟的会话；`ConversationProjector` 用 Turn 摘要最大 `last_sequence` 作为恢复点补放尾部事件，同事务更新 read_state/summary/checkpoint。避免直接回退 checkpoint 全量重放。
- **构建/部署产物**：前端 6.9.5、Core（`Source/PuddingAgent/bin/Debug/net10.0`）、Desktop launcher（`temp/build/winui3/bin/PuddingDesktop/debug_win-x64`，core bundle 19:20/6.9.5）均已重构建；但当前工作树含并行 WIP，正式身份预检仍为 `+dirty`，需要外部停止旧 Desktop/Core 后启动新构建。
