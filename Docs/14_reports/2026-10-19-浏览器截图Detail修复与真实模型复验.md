# 2026-10-19 浏览器截图 Detail 修复与真实模型复验

## 结论与边界

原报告 B1 截图异常有源码缺陷，不能只靠重启解除；B2 角色定位已有源码修复，需要部署新 Core。两者在构建 `48a9c37` 的本地真实模型测试中得到验证。随后发现折叠工具区会让截图等待并阻塞 Bridge 收包，补充修复提交 `80d6910`。最终部署验证结果见末节。

用户授权使用默认助手和 D:\data 做本地测试。全程未访问京东、未加购、未下单；本地表单仅提交一次。测试 URL 为 `http://127.0.0.1:4717/ef2f253e/`，唯一提交标记 `CAPTURE-ef2f253e`。此结论不覆盖商业站点完整任务、截图坐标输入的真实安全性、生命周期全矩阵或启动性能。

## 根因与修复

| 问题 | 事实 | 修复 |
|---|---|---|
| B1 InvalidOperationException | 无参 CDP 的 nullable null 未匹配属性模式，`Nullable.Value` 抛异常，尚未调用 WebView2 | null / JSON null / Undefined 序列化为 `{}` |
| 截图格式、尺寸和坐标 | 旧路径没消费全部采集参数；回执尺寸不能证明实际图像尺寸；转换出的坐标未传给动作 | 纯组件生成 PNG/JPEG、缩放与 clip 参数；读取图片头校验；实际消费转换后的点击/移动/拖拽端点 |
| Detail 丢失 | `LlmImagePart` 第二参数收到 MIME `image/png` | 传入 low/high/original，MIME 由工件提供 |
| B2 Role 线名 | 仓库已有显式 wire 名映射，旧部署未加载 | 完整重建并部署 Core/Desktop，同源协议 v3 |
| 隐藏页面阻塞 | 同一构建、同一页面，折叠工具区截图超时、桥断开；打开后恢复且截图成功 | UI 可见性检查、CDP 可取消等待、独立有界命令队列，保留心跳/取消收包 |

按 [DeepSeek 图像理解文档](https://api-docs.deepseek.com/zh-cn/guides/vision/)：服务端 low 缩至 512×512；high 等价 original；auto 当前等价 original。Pudding 本地 low 使用等比例最长边 ≤512，high/original 保留采集设备尺寸；这两层处理须区分。网关已有 canonical original/high/auto → high、low → low 映射，本次通过 wire 测试确认，不改变供应商逻辑。

## 启动耗时仍需单独处理

第一次新包 Core 启动超过 60 秒超时，Desktop 保留重试入口；点击重试后 Core 就绪 **41.207 秒**。阶段耗时：服务注册 28.332 秒、构建 Host 0.147 秒、映射中间件 4.048 秒、数据库与初始化约 2.2 秒、至服务器启动约 6.4 秒。采样主线程栈落在 `RuntimeModule.GetTypes → AddPuddingToolsFromAssembly → AddRuntimeServices`。

这是服务注册/程序集扫描耗时的线索，不足以断言所有时间均由同一个函数或防病毒软件造成。本次没有关闭防护、扩大启动超时或声称启动性能问题已修好；没有运行完整崩溃恢复/退出回收矩阵。
