- 日期：2026-10-23
- 关联提交：`b23311c`（符号检索改走覆盖索引两阶段）
- 探针：`temp/idx-eval/`（gitignored，可复现）

## 1. 结论先行：上一轮汇报的 "950ms → 19ms" 不成立

上一轮的 `19ms` 是**合成 SQL 基准**（两阶段查询 + 50 次按主键点查），不含真实调用路径里
`SearchSymbolsFastAsync` 的阶段 2 LIKE 全扫与回表成本。

真实端到端（进程内调用 `SqliteCodeIndexStore.SearchSymbolsAsync`，warmup 后 5 次取中位数）：

| query | 命中 | 第 1 次运行 | 第 2 次运行 | 旧值（日志/tool_stats，旧镜像） |
|---|---|---|---|---|
| `Budget` | 50 | 4.3 ms | 4.1 ms | 936 ms |
| `Prepare` | 50 | 10.5 ms | 10.4 ms | 954 ms |
| `LlmRequestBudgetGuard` | 50 | 181.4 ms | 175.3 ms | 934 ms |
| `ToolResultContextPolicy` | 50 | 292.8 ms | 288.8 ms | 952 ms |
| `zzzz-no-such-symbol` | **0** | 368.6 ms | 365.8 ms | 958 ms |
| WIDE 回退（`Kind=Class`） | 7–50 | 307.6 ms | 304.2 ms | 950 ms |

**真实提速约 5 倍（936→181 ms），不是 50 倍。** 且**稀有词/零命中仍 290–370 ms**，
与旧值同一量级 —— 这部分没有被 `b23311c` 改善。

`InitializeAsync` = 5.9–6.1 ms（含 128 MB `cache_size` PRAGMA）。

## 2. 硬证据：为什么稀有词仍慢

### 2.1 索引清单（`sqlite_master`，纯读）

```
IX_CodeSymbols_File              (WorkspaceId, ProjectId, FilePath)
IX_CodeSymbols_Workspace_Name    (WorkspaceId, Name)
IX_CodeSymbols_Workspace_Project_Name (WorkspaceId, ProjectId, Name)
```

**没有任何索引包含 `SymbolId`。**

### 2.2 执行计划（`EXPLAIN QUERY PLAN`）

阶段 2 实际 SQL（`SqliteCodeIndexStore.cs` L608–615）：

```sql
SELECT ProjectId, SymbolId FROM CodeSymbols
WHERE WorkspaceId = $w AND Name LIKE $like ESCAPE '\' AND Name <> $q
ORDER BY Name, SymbolId, ProjectId
LIMIT $take;
```

```
-> SEARCH CodeSymbols USING INDEX IX_CodeSymbols_Workspace_Name (WorkspaceId=?)
-> USE TEMP B-TREE FOR LAST 2 TERMS OF ORDER BY
```

对照组（同一谓词，只取 `Name`）：

```
-> SEARCH CodeSymbols USING COVERING INDEX IX_CodeSymbols_Workspace_Name (WorkspaceId=?)
```

**诊断：谓词本身能用索引，慢在两处 —— ① `ProjectId`/`SymbolId` 不在索引里，必须回表；
② `ORDER BY` 后两个 term 无法由索引满足，需临时 B 树。**

## 3. 一次无效优化（已回滚）

尝试把阶段 2 的 `ORDER BY Name, SymbolId, ProjectId` 简化为 `ORDER BY Name`（目标是消掉
`USE TEMP B-TREE`）。实测：

| query | 改前（run2） | 改后（run3） | 变化 |
|---|---|---|---|
| FAST `LlmRequestBudgetGuard` | 175.3 ms | 190.5 ms | +8.7% |
| FAST `ToolResultContextPolicy` | 288.8 ms | 311.0 ms | +7.7% |
| FAST `zzzz-no-such-symbol` | 365.8 ms | 389.1 ms | +6.4% |
| **WIDE（本次未改动的对照）** | 304.2 ms | 326.7 ms | **+7.4%** |

**未改动的 WIDE 路径同比例变慢 ⇒ 差异属环境噪声。** `LIMIT 50` 时临时 B 树只有 50 行，
排序成本可忽略，因此该简化无可测收益。

已回滚：还原后源文件 SHA-256 = `94EFA70A9714368B7B9E225FD70CB1D7103C9482889E4B721C50025158448FF9`，
与改动前逐位一致，`git status --porcelain` 为空。

## 5. 方法论教训（可复用）

- **合成 SQL 基准不能代替真实调用路径**。上一轮的 19 ms 漏掉了阶段 2 的全扫与回表，
  导致对用户报告了 50 倍提速（实际 5 倍）。凡"提速 N 倍"的结论，必须以**被测入口函数**
  为测量点。
- **要证明"优化有效"必须有未受影响的对照组**。本次 `ORDER BY` 简化若只看 FAST 路径会
  误判为 -8%；把未改动的 WIDE 路径当对照组，才定性为噪声。
- **`EXPLAIN QUERY PLAN` 的 `COVERING` 关键字是最直接的覆盖索引判据**，比推断列集合可靠。
