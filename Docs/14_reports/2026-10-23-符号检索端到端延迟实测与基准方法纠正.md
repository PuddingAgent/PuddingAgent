# 符号检索端到端延迟实测与基准方法纠正

- 日期：2026-10-23
- 关联提交：`b23311c`（符号检索改走覆盖索引两阶段）
- 探针：`temp/idx-eval/`（gitignored，可复现，支持 `--db` / `--create-index` / `--drop-index`）
- 数据源：`D:\Data\databases\code-index\code_index.db`（2,836,717,568 B ≈ 2.64 GiB，`CodeSymbols` 195,533 行）

## 1. 结论先行：上一轮汇报的 "950ms → 19ms" 不成立

上一轮的 `19ms` 是**合成 SQL 基准**（两阶段查询 + 50 次按主键点查），不含真实调用路径里
`SearchSymbolsFastAsync` 的阶段 2 LIKE 全扫与回表成本。

真实端到端（进程内调用 `SqliteCodeIndexStore.SearchSymbolsAsync`，warmup 后 5 次取中位数）：

| query | 命中 | 第 1 次运行 | 第 2 次运行 | 旧值（日志/tool_stats，旧镜像） |
|---|---|---|---|---|
| `Budget` | 50 | 4.3 ms | 4.1 ms | 936 ms |
| `Prepare` | 50 | 10.5 ms | 10.4 ms | 954 ms |
| `LlmRequestBudgetGuard` | 50 | 181.4 ms | 175.3 ms | 934 ms |
| `ToolResultContextPolicy` | 50 | 292.8 ms | 288.8 ms | 952 ms |
| `zzzz-no-such-symbol` | **0** | 368.6 ms | 365.8 ms | 958 ms |
| WIDE 回退（`Kind=Class`） | 7–50 | 307.6 ms | 304.2 ms | 950 ms |

**真实提速约 5 倍（936→181 ms），不是 50 倍。** 且**稀有词/零命中仍 290–370 ms**，
与旧值同一量级 —— 这部分没有被 `b23311c` 改善。

`InitializeAsync` = 5.9–6.1 ms（含 128 MB `cache_size` PRAGMA）。

## 2. 硬证据：为什么稀有词仍慢

### 2.1 索引清单（`sqlite_master`，纯读）

```
IX_CodeSymbols_File              (WorkspaceId, ProjectId, FilePath)
IX_CodeSymbols_Workspace_Name    (WorkspaceId, Name)
IX_CodeSymbols_Workspace_Project_Name (WorkspaceId, ProjectId, Name)
```

**没有任何索引包含 `SymbolId`。**

### 2.2 执行计划（`EXPLAIN QUERY PLAN`）

阶段 2 实际 SQL（`SqliteCodeIndexStore.cs` L608–615）：

```sql
SELECT ProjectId, SymbolId FROM CodeSymbols
WHERE WorkspaceId = $w AND Name LIKE $like ESCAPE '\' AND Name <> $q
ORDER BY Name, SymbolId, ProjectId
LIMIT $take;
```

```
-> SEARCH CodeSymbols USING INDEX IX_CodeSymbols_Workspace_Name (WorkspaceId=?)
-> USE TEMP B-TREE FOR LAST 2 TERMS OF ORDER BY
```

对照组（同一谓词，只取 `Name`）：

```
-> SEARCH CodeSymbols USING COVERING INDEX IX_CodeSymbols_Workspace_Name (WorkspaceId=?)
```

**诊断：谓词本身能用索引，慢在两处 —— ① `ProjectId`/`SymbolId` 不在索引里，必须回表；
② `ORDER BY` 后两个 term 无法由索引满足，需临时 B 树。**

## 3. 一次无效优化（已回滚）

尝试把阶段 2 的 `ORDER BY Name, SymbolId, ProjectId` 简化为 `ORDER BY Name`（目标是消掉
`USE TEMP B-TREE`）。实测：

| query | 改前（run2） | 改后（run3） | 变化 |
|---|---|---|---|
| FAST `LlmRequestBudgetGuard` | 175.3 ms | 190.5 ms | +8.7% |
| FAST `ToolResultContextPolicy` | 288.8 ms | 311.0 ms | +7.7% |
| FAST `zzzz-no-such-symbol` | 365.8 ms | 389.1 ms | +6.4% |
| **WIDE（本次未改动的对照）** | 304.2 ms | 326.7 ms | **+7.4%** |

**未改动的 WIDE 路径同比例变慢 ⇒ 差异属环境噪声。** `LIMIT 50` 时临时 B 树只有 50 行，
排序成本可忽略，因此该简化无可测收益。

已回滚：还原后源文件 SHA-256 = `94EFA70A9714368B7B9E225FD70CB1D7103C9482889E4B721C50025158448FF9`，
与改动前逐位一致，`git status --porcelain` 为空。

## 4. 覆盖索引方案：A/B/A 对照实验（**已否证**）

在**生产库的完整字节副本**（`temp/idx-copy/`，2,836,717,568 B，与源逐字节相同）上做三组对照，
每组 warmup 后 5 次取中位数：

- A：副本原状（无覆盖索引）
- B：`CREATE INDEX IX_CodeSymbols_Workspace_Name_Covering ON CodeSymbols (WorkspaceId, Name, ProjectId, SymbolId)`
- A'：`DROP INDEX` 后重测（验证可逆）

| query | A 基线 | B 建索引后 | A' 删索引后 |
|---|---|---|---|
| FAST `LlmRequestBudgetGuard` | 189.8 ms | **245.4 ms** | 195.2 ms |
| FAST `ToolResultContextPolicy` | 304.5 ms | **355.3 ms** | 327.2 ms |
| FAST `Prepare` | 11.2 ms | **24.8 ms** | 11.8 ms |
| FAST `Budget` | 4.7 ms | **6.6 ms** | 4.6 ms |
| FAST `zzzz-no-such-symbol` | 394.5 ms | **430.6 ms** | 411.3 ms |
| WIDE `LlmRequestBudgetGuard`（不受该索引影响） | 321.5 ms | 319.8 ms | 331.2 ms |
| WIDE `Budget`（同上） | 322.5 ms | 322.6 ms | 341.4 ms |

**结果：覆盖索引使所有走快路径的查询变慢 9–121%，A' 回到基线量级（证明差异确实来自索引、可逆）。**

B 组执行计划确实变成：

```
-> SEARCH CodeSymbols USING COVERING INDEX IX_CodeSymbols_Workspace_Name_Covering (WorkspaceId=?)
-> USE TEMP B-TREE FOR LAST 2 TERMS OF ORDER BY
```

### 4.1 为什么"消除回表"反而更慢

1. `%关键词%` 前导通配符决定了**无论有没有覆盖索引，都必须全扫 195,533 条索引项** —— 扫描次数不变。
2. 覆盖索引多了 `ProjectId` 与 `SymbolId` 两个字符串列，**索引条目显著变宽**，每次全扫读取的字节数上升。
3. 原本的回表代价已被 OS 页缓存吸收，增益接近零。

⇒ **净效果为负。回表不是瓶颈，"全扫"才是。**

### 4.2 附带测得

| 操作 | 耗时 |
|---|---|
| `CREATE INDEX`（195,533 行 / 2.7 GB 库） | **1,075.3 ms** |
| `DROP INDEX` | 61.7 ms |

建索引代价远低于此前担忧（原先估计"数十秒、可能长时间阻塞 Core"），但既然无效，不再考虑。

## 5. 遗留与下一步

| 项 | 现状 | 方案 | 代价 |
|---|---|---|---|
| 稀有词 175–330 ms | 全扫 19.5 万条索引项 | **FTS5 trigram**（前一轮在 5 万去重符号名上实测 0 ms） | 建虚拟表 + 写入同步 + 全量重建 + 一致性测试 |
| 零命中 366–411 ms | 阶段 3 `Signature OR Container LIKE` 全表回表，**属正确性必需成本** | 需对 `Signature`/`Container` 也建 FTS 才能救 | 同上，范围更大 |
| 覆盖索引 | **否证，不再考虑** | — | — |
| `ORDER BY` 简化 | 无可测收益，已回滚 | — | — |

**下一刀应指向"减少扫描量"，而不是"减少回表次数"。**

## 6. 方法论教训（可复用）

- **合成 SQL 基准不能代替真实调用路径**。上一轮的 19 ms 漏掉了阶段 2 的全扫与回表，
  导致对用户报告了 50 倍提速（实际 5 倍）。凡"提速 N 倍"的结论，必须以**被测入口函数**为测量点。
- **要证明"优化有效"必须有未受影响的对照组**。两次实验（第 3 节的 ORDER BY 简化、第 4 节的
  覆盖索引）都靠 WIDE 路径作对照，才把"噪声"和"真实效应"分开。
- **A/B/A 三组比 A/B 两组可靠**。第三组回到基线，才能排除时间漂移与缓存变化。
- **执行计划里的 `COVERING` 只说明"不回表"，不代表"更快"**。必须实测。
- 在副本上做破坏性实验（建/删索引）的成本很低：复制 2.7 GB + 建索引 1.1 s。
