## 3. "走了索引" 为什么还是不快的理论澄清

`EXPLAIN QUERY PLAN` 输出：

```
-> SEARCH CodeSymbols USING INDEX IX_CodeSymbols_Workspace_Name (WorkspaceId=?)
-> USE TEMP B-TREE FOR LAST 2 TERMS OF ORDER BY
```

关键在于 `SEARCH ... (WorkspaceId=?)` **只用到了索引的第一列做等值裁剪**。
`Name LIKE '%x%'` 是**前导通配符**：B-tree 按字典序排列，无法确定匹配起点，
因此只能把整个 `WorkspaceId` 分区（195,616 条索引项）逐条取出评估谓词。

- `Name LIKE 'Foo%'`（前缀）→ 可做值域裁剪，真正缩小扫描量。
- `Name LIKE '%Foo%'`（任意位置）→ 只能做**分区裁剪**，对 `Name` 的过滤能力为 0。

**"走索引" ≠ "用索引缩小范围"。** 扫描量没变，只是载体从表页换成了索引页。
`COVERING` 又只消除回表，同样不减少扫描行数 —— 因此理论与实测并不冲突。

## 4. 覆盖索引：A/B/A 对照实验（已否证）

在生产库完整字节副本（`SAME=True`）上三组对照：

| query | A 基线 | B 建索引后 | A' 删索引后 |
|---|---|---|---|
| FAST `LlmRequestBudgetGuard` | 189.8 ms | **245.4 ms** | 195.2 ms |
| FAST `ToolResultContextPolicy` | 304.5 ms | **355.3 ms** | 327.2 ms |
| FAST `Prepare` | 11.2 ms | **24.8 ms** | 11.8 ms |
| FAST `Budget` | 4.7 ms | **6.6 ms** | 4.6 ms |
| FAST 零命中 | 394.5 ms | **430.6 ms** | 411.3 ms |
| WIDE（不受该索引影响） | 321.5 ms | 319.8 ms | 331.2 ms |

A' 回到基线 ⇒ 差异确实来自索引且可逆。归因：`%q%` 决定全扫量不变，覆盖索引多了
`ProjectId`+`SymbolId` 两列使**索引条目变宽**，每次全扫读取字节数上升；
回表本已被 OS 页缓存吸收，增益≈0。

`CREATE INDEX` 1,075.3 ms / `DROP INDEX` 61.7 ms（远低于先前"数十秒"的担忧，但既然无效不再考虑）。

## 5. FTS5 trigram 倒排索引（✓ 已验证有效）

在副本上建三列 trigram 倒排索引：

```sql
CREATE VIRTUAL TABLE sym_fts USING fts5(Name, Signature, Container, tokenize='trigram');
INSERT INTO sym_fts(rowid, Name, Signature, Container)
SELECT rowid, Name, COALESCE(Signature,''), COALESCE(Container,'')
FROM CodeSymbols WHERE WorkspaceId = 'default';
```

查询：`SELECT rowid FROM sym_fts WHERE sym_fts MATCH $phrase LIMIT 50`，再按 rowid 回表取详情。

| query | 现有实现 | FTS5 端到端 | 加速 | 召回 |
|---|---|---|---|---|
| `LlmRequestBudgetGuard` | 187.9 ms | **1.0 ms** | **188×** | n=50 |
| `ToolResultContextPolicy` | 305.2 ms | **5.7 ms** | **54×** | n=50 |
| `Prepare` | 11.1 ms | **0.2 ms** | 55× | n=50 |
| `Budget` | 4.6 ms | **0.1 ms** | 46× | n=50 |
| `zzzz-no-such-symbol` | 384.9 ms | **0.0 ms** | 全消 | n=0 |

**召回与现有实现一致（均打满 limit=50）。**

### 5.1 成本

| 项 | 实测 |
|---|---|
| `CREATE VIRTUAL TABLE` | 0.8 ms |
| 填充 195,616 行（三列） | **8,015.6 ms**（一次性；单列 `Name` 时 1,892–2,493 ms） |
| 索引实际占用 | **146.3 MB**（37,460 页 × 4096 B） |
| **额外磁盘占用** | **0** —— 全部由库里已有的 745.7 MB freelist 空洞吸收，文件大小不变（2,836,717,568 → 2,836,717,568） |

### 5.2 单列 vs 三列对照

只索引 `Name` 时：`LlmRequestBudgetGuard` 命中 5 条、`ToolResultContextPolicy` 命中 3 条
（0.9 / 1.3 ms），因为现有实现的 50 条里大部分来自阶段 3 的 `Signature`/`Container` 扩展。
**三列索引才能对齐召回**，且零命中查询从 385 ms 降到 0 ms。

### 5.3 尚未验证

- **写入同步**：`CodeSymbols` 增删改时必须同步 `sym_fts`（触发器或应用层双写），否则索引漂移。
  这是落地的关键工作量，尚未实现或测试。
- 与 `WorkspaceId` / `ProjectId` / `Kind` / 文件扩展名过滤的组合（需在 MATCH 之后回表过滤，
  或按 workspace 分表）。
- 3 字符以下的查询在 trigram 下会退化（trigram 需要 ≥3 字符）。

## 6. 方法论教训（可复用）

- **合成 SQL 基准不能代替真实调用路径**。凡"提速 N 倍"，必须以**被测入口函数**为测量点。
- **必须有未受影响的对照组**。两次实验都靠 WIDE 路径作对照，才把噪声与真实效应分开。
- **A/B/A 三组比 A/B 两组可靠**，第三组回到基线才能排除漂移与缓存变化。
- **`COVERING` 只证明"不回表"，不证明"更快"**。
- **文件大小不变 ≠ 没写入**。`sqlite_master` 的 B-tree 可能不在文件头部；
  应用**跨连接可见性**（新连接查 `count(*)`）判定提交，而不是看文件字节数。
- **`PRAGMA freelist_count` 是判断"新增结构是否真的占磁盘"的正确工具**。
