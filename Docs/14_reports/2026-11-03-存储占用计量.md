# 清理执行记录（2026-11-03 09:26–09:31）

## 结果

| 目录 | 清理前 | 清理后 | 回收 |
|---|---|---|---|
| `D:\Data` | 25.03 GB | **18.59 GB** | **6.44 GB** |
| 项目目录 | 174.95 GB | **125.51 GB** | **49.44 GB** |
| **合计** | 199.98 GB | **144.10 GB** | **55.88 GB** |

明细变化：

```
D:\Data\databases      21.14 → 14.71 GB    (compact.db 及 sidecar 已删)
项目\Source             41.72 →  7.51 GB    (全部 bin/obj，实际 356 项)
项目\temp              130.05 → 114.82 GB    (仅减 15 GB，见下)
```

三项操作全部先做 dry-run，再执行：

| 步骤 | 对象 | 数量 | 释放 | 失败 |
|---|---|---|---|---|
| 1 | `Source\PuddingCoreTests\TestResults\**\*.dmp` | 9 个 | **27.29 GB** | 0 |
| 2 | `temp/` 非保护产物 + `Source/**/bin`、`obj` | 363 项 | **22.15 GB** | 7 |
| 3 | `pudding_platform_compact.db` + sidecar | 3 个 | **6.44 GB** | 0 |

步骤 2 的 7 个失败是 `.playwright\package\bin` —— 父目录先被删除导致的"路径不存在"连锁，非真实失败。

## ⚠ 执行中发现的关键事实：`temp/build` 是宿主运行目录

原计划要清 `temp/` 的 130 GB，但执行前查到：

```
PuddingAgent                 pid 56056  → temp\build\winui3\bin\PuddingDesktop\Debug\...\core\PuddingAgent.exe
PuddingDesktop               pid  8884  → temp\build\...\PuddingDesktop.exe
PuddingDesktop.ExitObserver  pid 39800  → temp\build\...\observer\PuddingDesktop.ExitObserver.exe
PuddingDesktop.Guardian      pid 51796  → temp\build\...\guardian\PuddingDesktop.Guardian.exe
```

**四个进程正从 `temp/build` 运行，其中包含我自己（pid 56056）。**

删除的后果不是"立刻崩溃"（文件已加载进内存），而是：
**Guardian 一旦重启宿主，就再也找不到 exe，永久起不来。**

所以 `temp/build`（114 GB）被列入保护区，一个字节都没动。
**这也解释了为什么 `temp` 清理后仍有 114.82 GB。**

## 复现脚本

| 脚本 | 用途 |
|---|---|
| `temp/measure_storage.ps1` | 完整计量（一级目录 / 最大文件 / 扩展名） |
| `temp/remeasure.ps1` | 快速复测（只算总量与一级目录） |
| `temp/clean_dumps.ps1` | 删 `.dmp`（默认 dry-run，加 `-Execute` 才删） |
| `temp/clean_artifacts.ps1` | 删 temp 产物 + bin/obj（含 `build`/`runner`/`uia-probe`/`uia-verify` 保护区） |
| `temp/clean_compact.ps1` | 删 compact.db（删除前打印证据） |
| `temp/inspect_compact.ps1` | 只读核查：大小、时间戳、独占锁探测 |

**全部脚本默认 dry-run**，必须显式 `-Execute` 才动手。

## 一条教训

原始计划里「`temp/` 130 GB 可回收约 120 GB」是**基于路径名的推断，不是基于事实的核实**。
如果直接按计划执行，会把宿主和 Guardian 的运行目录一起删掉 —— 那一刻不会报错，
问题会在下一次宿主动重启时才爆发，而那时已经很难联想到是这次清理造成的。

**核实成本是三条 `Get-Process` 命令，不到一分钟。**
