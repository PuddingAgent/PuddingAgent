## W2、W4、W5 证据口径

- W2 的新入口标志和保留键过滤能在所测 handler 上生效。新增用例检查已落盘的键、resolver 错误及账户数为零，采用测试受理存储。fixture 没有运行 Coordinator 或计数 provider。现有“provider 0 次”应收窄为“resolver 拒绝且无账户”，端到端拒绝需由下一次复核实测。
- 两种请求构造均有 `BudgetAttempt` 赋值。现有测试直接调用转换 helper，另有一例手工组装请求调用 facade。需从真实 buffered 和 streaming 入口捕获各自实际传入的请求，再做移除一条传播就取红的对照。
- W5 在真实主路径关闭 facade 或预算 port，验证明确失败及直连计数 0。通过实际快照/序列化和派生执行入口检查受权绑定的暴露与继承范围。策略开启时缺少必需的 resolver，应能和策略明确关闭区分。
- 启用前另核对冻结报价能区分同名模型的 provider。当前 resolver 按 modelId 查询，目录实现取第一条同名记录。本次没有对多 provider 配置作运行时判定。

## 原型决策

**B 暂缓。** 两个叶单分别关闭了一个账本错误码问题和九个工程的引用边界问题。B 的必需链路还有两段缺少真实连接。[原型场景及 A1～A6](../12_features/基础设施服务生命周期与最小原型两阶段目标-2026-11-07.md)

| 门禁 | 本次判据 |
|---|---|
| A1 / A2 | 组件合同卡可用于施工。A2 的九个实现工程已补足正反引用证据；整体范围还包括 SDK/契约消费者的依赖边界。 |
| A3 / A4 | 预算账户的持久实现有回归证据。普通 Work 的来源、恢复与发送入口仍有上述阻断，单次发送的模型租约及在途取消尚待 06。 |
| A5 / A6 | 已有事件存储、`PluginEventDispatchWorker.RunOnceAsync` 和工具 Worker。对生产源码的检索只见 `IPluginEventDeliverySink`、`IEventDispatchWorkspaceSource` 的声明/依赖，扩展管线只见类型和 DI 登记。还需实际的工作区产物提交 → outbox → PluginManager/Worker → 零工具功能插件受权写入，以及重投、撤权和卸载后的效果断言。 |

**施工顺序**：先修三个红例并补 Coordinator、双分支与 W5，独立接受 05 后启动 06。同时可独立推进 A5/A6 的隔离组件验证，让一个零工具插件响应真实的工作区产物事件，重投两次只产生一条记录，卸载后无新副作用。按两阶段合同复核 A1～A6，再开始 B 的跨域组合。
