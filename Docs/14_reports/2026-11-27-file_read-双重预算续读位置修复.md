# file_read 双重预算：续读位置互相矛盾的修复

## 1. 症状（运行时一手样本）

探针文件写在仓库 `temp/`（gitignored），用完即删：

| 文件 | 规模 |
|---|---|
| `probe_small_0127.txt` | 1512 B / 28 行 |
| `probe_large_0127.txt` | 24598 B / 502 行 |

`file_read(max_chars=20000)` 读后者，回执同时出现两行：

```
... [TRUNCATED: lines 1..156 shown (7643 bytes, inline budget 7680). Use OffsetLines=156+LimitLines to continue from line 157.]
... (truncated at 20000 chars of this window; file has 24598 chars / 502 line(s); continue with OffsetLines=408+LimitLines)
```

**两个数字，同一件事。** 照第二条执行会从第 409 行开始，第 157–408 行共 252 行**从未交付也再不会被读到**——而且两条提示都写得很自信。

算术可交叉验证，证明两者确实来自不同截断点（每行 48 字符 + `\n` = 49 字节）：

- MaxChars 20000 字符 ÷ 49 ≈ 408.16 → 408 行 ⇒ `OffsetLines=408`
- inline 7680 字节 ÷ 49 ≈ 156.7 → 156 行 ⇒ `OffsetLines=156`

## 2. 根因

`FileReadTool` 的收尾顺序是「先 `BoundInlineBody` 截字节，再拼 MaxChars notice」，而 MaxChars notice 的偏移在 `BoundInlineBody` **之前**就算好了，基于尚未过字节闸门的 `content`：

```csharp
var body = $"{meta}\n{BoundInlineBody(content, windowStart, out _)}";   // 字节闸门在这里
if (maxCharsNotice is not null) body = $"{body}\n... {maxCharsNotice}"; // 偏移早已算完
```

小文件与大文件两条读取路径各有一份相同写法，所以两个分支都中。

## 3. 为什么现在才暴露——是我上一轮引入的

`96c64e2` 之前，护栏判据是「没有显式分页参数」：

```csharp
var hasExplicitSlice = HeadLines || TailLines || OffsetLines;   // 旧版：不含 MaxChars
```

对 502 行文件、`max_chars=20000`（无分页参数）来说，护栏会先命中并直接返回 400 行预览，**MaxChars 分支根本不可达**。`96c64e2` 让 `MaxChars` 也算显式预算（这是修上一处静默的必要改动），这条路才被打开，随即暴露本条。

⇒ 这条缺陷是**我自己的回归**，不是历史遗留。写在这里而不是写成「顺带发现的旧问题」。

## 4. 修法

一份判据：续读位置只按**实际交付**算。

- `BoundInlineBody` 增加 `out bool truncated`，把「字节闸门是否真的截了」暴露给调用方，不再靠外部重算。
- `DescribeMaxCharsTruncation` 增加可选 `int? deliveredLines`。传入时偏移改用交付行数，并把措辞改成「requested max_chars=… but the 7680-byte inline budget bound first」，明确是哪道预算先命中。
- 两条读取路径在 `BoundInlineBody` 之后判断 `byteBounded`，为真则重算 notice。

未传 `deliveredLines` 时（字节闸门未命中）文案与偏移**保持原样**——既有 4 条 MaxChars 用例零改动即通过，说明没有顺手改到不该改的地方。

## 5. 取红

两次变异各打红一条，且红点不同：

| 变异 | 改动 | 结果 |
|---|---|---|
| M1 | 小文件路径 `if (… && byteBoundedSmall && emittedSmall < 0)` | 30 例 **1 红**：`MaxChars_WithInlineByteBudgetBound_ReportsSingleContinuationOffset`；大文件用例仍绿 |
| M2 | 恢复小文件、大文件路径加同形不可能条件 | 30 例 **1 红**：`…OnLargeFilePath_WithInlineByteBudgetBound…`；小文件用例仍绿 |

M1 的失败明细指向 `StringAssert.Contains`（缺 `inline budget bound first`），M2 指向同名断言的另一条用例——**两条读取路径各自被守**，一处修复不能替另一处通过。

复原后 `git diff` 只含预期 hunk，`emittedSmall < 0` / `emittedLarge < 0` 变异残留 grep 为 0 命中；重跑 30/30。

未重放 M3（让 `DescribeMaxCharsTruncation` 忽略 `deliveredLines`）：那会把两条用例同时打红，属共用判据的证据，不是独立守护——不声称。

## 6. 部署验收

见 §7 待验收项。程序集层：提交后 build-restart，核 live DLL 时间与进程启动时刻（取 `Get-Process.Modules`）。行为层：对 502 行探针文件重跑 `max_chars=20000`，续读位置必须只有一个数字，且等于正文末行的下一行。

## 7. 不声称的

- 未验证 CJK 内容下的字符/字节换算（此处探针全 ASCII，1 字符 = 1 字节）。理论上 CJK 会让字节闸门更早命中，修复应同样生效，但**没有样本**。
- 未验证 `max_chars` 小于一行长度时的续读（例如 `max_chars=10` 落在首个换行前）。
- 回执里仍会出现两行提示（第一条来自字节闸门、第二条说明 MaxChars 被字节闸门抢先），只是两个数字现在一致。是否合并成一条属于回执格式调整，未做。

## 8. 记下的规则

1. **同一件事只能有一个计算源。** 两个 notice 各自算偏移，必然在某个组合下打架；把「交付了多少」作为唯一事实传下去，比让两处各自推演可靠。
2. **修复可能打开此前不可达的路径。** 上一轮把 `MaxChars` 变成显式预算，等于新开了一条通路；这种改动之后必须对新通路的**所有参数组合**取样，而不是只验被修的那一种。
3. **验收措辞要与语义对齐。** 本轮实测 `offset_lines=20` 从第 **21** 行开始（schema 明写 0-based）；上一轮我写「须从第 20 行起」是措辞错误，不是工具缺陷——记下来，免得下次当成 bug 去修。
