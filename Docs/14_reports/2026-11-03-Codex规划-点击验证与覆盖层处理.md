# Codex 规划：点击验证设计与覆盖层处理

> **更正（2026-11-03）：实施边界。** 中心命中结果已完全退出窗口评分，旧惩罚实现及专用测试已清理。
> 下文 Q2 的“同 PID 即放行”和 Q3 的“异 PID 中心命中强惩罚”是当时的规划建议，均不是当前实现，
> 不能据此恢复中心命中评分或宣称覆盖层输入已验收。实际点击仍按 `authorizedRoot` 检查落点归属；
> 扩展接收者授权集合及验证输入是否到达内容控件，需要单独完成。

## 为什么请 Codex

前一轮的困境：三种点击方式（`ClickAt` / `MoveCursorTo+ClickAt` / `SendInput` 绝对坐标）
全部返回成功，但窗口像素零变化；而看图确认点击位置正确。

我意识到「像素差测不出输入框获得焦点」，但**不知道该怎么验证**。
问题收束成一个明确的架构判断问题，具备升级 Codex 的条件。

## 调用方式（含上次失败教训）

上次调用失败：**prompt 没给硬预算**，Codex 用 2 小时扫全仓、输出 283 KB 日志、零结论。

本次 prompt 加了硬约束：

```
- Read AT MOST 3 files. Make AT MOST 8 tool calls TOTAL.
- Do NOT read CODE_MAP.md / README / AGENTS.md, or list directories.
- Do NOT run git grep / git log / find.
- Time target: 10 minutes.
```

结果：**52 KB 日志（上次 283 KB）**，约 45 分钟出结论（目标 10 分钟未达标，但收敛了）。

技术要点：prompt 走 **stdin**（`codex.ps1` wrapper 会按空格拆分长位置参数）。

## Codex 的三条结论

### Q1 —— `Clicked` 不等于「收到」

> Treat `Clicked` only as "input emitted"; prove receipt through a post-click focus
> transition plus UIA or temporal caret evidence, with a reversible character probe
> as fallback.

**判定为 `ReachedTarget` 的条件**（需先确认点击前输入框未聚焦）：

1. 前台/焦点进程是 PID 81092，**且**
2. UIA 报告新的焦点可编辑元素、其 bounds 与目标输入框重叠；**或**
3. 在输入 ROI 内以 10+ FPS 采样 2–3 秒，观察到一条**固定窄竖条**出现/消失 ≥2 次，
   且周边像素保持稳定，且点击前不存在该模式。

**关键约束**：
- 单次截图不足；
- 仅前台进程相同不足；
- **观察不到证据时应报 `Indeterminate`，不是 `Failed`**。

**回退方案**：保存输入框基线值 → 输入一个唯一无害字符 → 验证恰好出现一次 →
Backspace → 断言**完全恢复**。这是最强且可逆的实际证据。

### Q2 —— 分析面和输入接收者是两件事

> `0xE51328` is most plausibly an oversized Electron auxiliary tool/compositor/input
> window — not a DWM shadow: it is a real topmost, non-transparent hit-test window,
> and its DWM bounds equal its window bounds.

- **分析面 = `0xCF0FCC`**：矩形 95.6% 是应用内容（vs 59.8%），能产出有用的目标几何
- **输入接收者 = 实际点击坐标处 `WindowFromPoint` 返回的窗口**（这里是 `0xE51328`）

**关键洞察**：

> Physical mouse input is screen-routed, not addressed to the analysis HWND.

物理鼠标**按屏幕坐标路由**，不是发给分析 HWND 的。
所以应当**保留分析得到的屏幕坐标**，并把授权范围扩成
**「接收者集合/进程」而非单一分析根**：接受 `0xCF0FCC`、`0xE51328` 及其子窗口，
**只要 PID 是 81092**；其他进程一律拒绝。

**分析 `0xE51328` 是错的**：只会引入壁纸、扭曲搜索范围，而**不改变谁接收点击**。

### Q3 —— 替代评分（我上一轮那条判据是反的）

分析窗口评分应基于：

1. **内容占比/密度**（主信号；95.6% 决定性胜过 59.8%）
2. **主窗口先验**：优先非 `TOOLWINDOW`、非 `TOPMOST`
3. 有效内容区与检出的可交互结构；**原始矩形面积只作弱 tie-breaker**
4. 对已知焦点/搜索区域的覆盖度

**明确不要**把输入路由混进评分：

| 情形 | 处理 |
|---|---|
| 中心命中同 PID 的另一个窗口 | **不惩罚**，记录"覆盖层关系" |
| 中心命中其他 PID | 强惩罚或临时排除 |
| 中心命中为 null | 未知，不作为正负证据 |

**点击时**应在**实际落点**重新做命中测试——不是中心点——再套进程/授权集合的安全闸门。

## 实验清单（含判据）

| # | 实验 | 通过条件 |
|---|---|---|
| 1 | 时序光标：失焦→基线→合成点击→采样 3 秒 | 光标在输入 ROI 内**仅在点击后**切换 ≥2 次；否则 `Indeterminate` |
| 2 | UIA 焦点：点击前订阅 | 点击后出现焦点事件，标识 PID-81092 的可编辑元素且与输入框 ROI 重叠 |
| 3 | 可逆探针：输入 1 字符→校验→Backspace→校验恢复 | 字符精确插入 **且** 基线精确恢复；恢复失败即测试失败，需清理 |
| 4 | 覆盖层路由：`WindowFromPoint(clickPoint)` 解析到 PID 81092 | 其他 PID 安全失败；同进程 `0xE51328` 通过路由授权 |

## 最便宜的反证

先跑零副作用检查，再跑可逆探针。

**若 UIA/光标程序报告 `ReachedTarget`，但那个唯一字符并未出现在预期输入框中
⇒ Q1 的判定流程产生假阳性，被证伪。**
