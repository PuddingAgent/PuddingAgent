## 审查发现

### P1：无页面目标的浏览器能力被产品默认信任策略拒绝

`Source/PuddingDesktop/Hosting/DesktopApplicationCoordinator.Capability.cs` 的 `StartCapabilityChannelAsync` 调用组合器时没有传 `serviceOptions`。`Source/Pudding.DesktopService/DesktopCapabilityChannelComposition.cs` 创建的缺省服务把 `ShellCallerTrust` 设为 `Untrusted`。

`Source/Pudding.DesktopService/DesktopService.cs` 在 `BrowserContexts`、`BrowserContextCreate`、`BrowserContextClose` 请求上向 `RunOnUiAsync` 传 `target: null`，`ValidateAdmission` 因而使用 `ShellCallerTrust`。`DesktopCapabilityPolicy.cs` 对这些能力只允许 `AgentAuthorized`。结果是启用态即使握手成功，`browser_context list/create/close` 仍返回 Unauthorized；工具省略 contextId 后先列上下文的路径同样受影响。浏览器页面注册为 AgentAuthorized 不会改变无目标调用的信任级别。

建议建立浏览器上下文专属的授权准入来源，保留 Shell 对话框/剪贴板的独立策略；增加使用产品缺省装配的请求测试，不能只用显式放宽的测试选项证明可用。

### P1：人工接管和暂停没有同步到 gRPC 执行器

`Source/PuddingDesktop/MainWindow.xaml.cs` 的 `OnTakeover` 仅调用 `BrowserWorkspaceController.SetUserTakeoverAsync`。该控制器只更改自身 `_userTakeover` 和 ControlState。新通道的执行器有独立 `DesktopService.Interaction`，其 `ValidateAutomation` 只读取这个状态；当前 Shell 接线未调用 `NotifyUserTakeover/ClearUserTakeover`，也未把控制器暂停状态接到新执行器。

gRPC 表面直接操作 IBrowserRuntime，绕过旧 `BrowserBridgeCommandDispatcher` 的接管门禁。因此启用新通道后，UI 宣称人工接管并不能保证变更操作被拒绝。活动身份/执行状态 UI 当前也主要订阅旧 BridgeDispatcher，新通道状态投影需一起核查。

建议让两条传输共用控制权事实源，并验证接管期间 click/fill/navigate 被拒、只读观测按策略允许、恢复后可操作及排队请求竞态。

### P1：新通道标签生命周期绕过工作区控制器

`Source/Pudding.DesktopSurface.Browser/BrowserRuntimeDesktopSurface.cs` 的 `TabsAsync(New/Close)` 直接调用运行时 context 的 `NewPageAsync/ClosePageAsync`。右侧实例 Tab、控制器 `_pages`、Agent 目标由 `Source/PuddingDesktop.WpfArchive/Browser/BrowserWorkspaceController.cs` 自己维护。运行时没有页面创建/关闭事件把上述变化回流给该控制器。

`AttachBrowserTargets` 又只订阅控制器 `Tabs.CollectionChanged` 登记页面。这意味着新通道创建的页面不会进入右侧实例 Tab 和目标注册表；后续需要 registered page target 的能力可能报 InvalidTarget。新通道关闭页面则可能留下 UI Tab/目标残影。新建 context 同样没有注册生命周期回流。

建议提供统一页面生命周期入口或运行时事实事件，覆盖 Agent 建页/关页、人工建页/关页和上下文创建/关闭，验证 UI、运行时、两个注册表一致。

### P2：通道重启留下事件订阅，启动和停止也缺少共同互斥

`DesktopApplicationCoordinator.Capability.cs` 的 `AttachBrowserTargets` 用匿名 lambda 订阅长期存活的 workspace，未返回 IDisposable，也没有在 `StopCapabilityChannelAsync` 解除订阅。订阅在读取令牌和启动通道之前发生，失败也会残留。每次 Core 重启会再创建注册表和订阅，旧注册表仍被事件闭包保留。

启动使用 `_capabilityStartGate`，停止使用另一个 `_capabilityGate`；停止可能看到尚未赋值的 `_capabilityChannel` 而提前返回，迟到的启动随后写入已失效会话。建议统一生命周期同步与订阅释放，在 CoreReady→停止→迟到启动场景验证。

### P2：DOM 输入实现不足以证明复杂网页可用

`Source/PuddingBrowser.WebView2/WebView2DomClient.cs` 的 InteractScript 直接赋值 `el.value` 并派发合成事件；`type` 实际是整串追加，未逐字产生键盘事件，`press` 只派发 keydown/keyup 并特判 Enter 提交，不能提供 Backspace、Tab、快捷键等原生默认行为。`fill` 对 React 受控输入的变更识别存在风险，需真实页面验证。无效目标类型也可能走到无效赋值后返回成功。

建议至少测试 React 受控表单、contenteditable、按键默认行为和不匹配元素类型；明确 DOM 模拟支持边界，若要求真实按键则提供相应驱动。

多数测试使用替身并分别验证组件。`Source/PuddingBrowser.WinUITests` 仅链接 DOM 客户端的预算、ref 校验和通配匹配测试，不能验证真实网页输入行为。上述 228 项通过不覆盖本报告列出的产品启用态接线缺口。

截图展示的能力是产品内 WebView2 标签页，不能推断已能接管任意外部 Chrome/Edge 窗口。截图浏览器“可用”主要表示运行时入口就绪，不代表 Agent 授权、目标绑定和通道健康同时就绪。

`WebView2BrowserPage.cs` 中 screenshot、PDF、CDP、拖拽、上传仍明确不支持；跨域 iframe 与 frame 定位也有边界。这些属于尚未建设的能力，不应与七项工具完成度混算。

早期[外部验收单](Desktop-Capability-Channel-External-Acceptance-2026-10-01.md)仍写 Shell 装配未完成和工具迁移未开始，与当前代码及后续[映射施工结果](../12_features/Desktop-Surface-Browser-Mapping-2026-10-01.md)不一致。该旧报告应视为历史交接证据。

## 下一步优先级

先修复三个 P1 接线问题并增加使用产品默认装配的组合测试；再处理生命周期订阅与 DOM 输入语义。最后由外部控制器部署明确新构建，在用户指定的测试 Agent/DataRoot 下运行真实模型 TestSite 任务，验证人工接管、后台收起、跨 Tab 目标稳定、断连重连及退出回收，并记录实际传输用量。当前证据不足以批准默认开启新通道或退役旧 Bridge。
