# 历史消息搜索高磁盘占用诊断

用户截图中的历史消息搜索没有走全文或向量索引。当前源码实现存在可确认的高 I/O 查询路径，现有数据库的只读查询计划与之吻合。本次完成诊断和修复设计，尚未修改检索实现或部署新 Core。

## 1. 实际调用链

[`HistorySearchModal.tsx`](../../Source/PuddingPlatformAdmin/src/pages/chat/components/HistorySearchModal.tsx) → [`api.ts`](../../Source/PuddingPlatformAdmin/src/services/platform/api.ts) 的 `searchMessages` → `POST /api/messages/search` → [`MessageSearchController.Search`](../../Source/PuddingPlatform/Controllers/Api/MessageSearchController.cs) → [`RawSessionLogService.GrepMessagesAsync`](../../Source/PuddingPlatform/Services/RawSessionLogService.cs)。

1. `GetWorkspaceSessionIdsAsync` 在 `conversation_events` 上按 workspace 过滤，做 `DISTINCT conversation_id`，最多返回 10,000 个会话 ID。
2. `LoadMessageTranscriptAsync` 按会话 ID 集合查 `ChatMessages`，按 `CreatedAt` 降序取最多 10,000 条**完整实体**；正文、ThinkingJson、UsageJson、metadata 和 content parts 等列一起水合。
3. 加载之后才在内存中筛选日期。
4. `TextMessageMatches` 用 `IndexOf(..., OrdinalIgnoreCase)` 逐条做子串匹配。响应限制为 50 条，并不意味着数据库只读 50 条消息。
5. 每个匹配项还带 `FullContent`，点击详情前已经传输了完整正文。

Controller 的注释称复用 Lucene FTS，但执行代码调用的是 DB grep。此链路既没有 `_ftsEngine.SearchAsync`，也没有 embedding 或 vector 查询。

## 2. 现场只读证据

2026-10-08 对 `D:/data/databases/pudding_platform.db` 使用 Python 标准库 SQLite，连接设置 `mode=ro` 与 `PRAGMA query_only=ON`。仅读取文件大小、sqlite_master 和 `EXPLAIN QUERY PLAN`；没有执行完整业务搜索、读取消息正文、回填索引或修改数据库。表结构查询未发现消息相关 FTS 虚表。

平台数据库主文件为 **10,334,580,736 字节，约 9.6 GiB**。这不是本次搜索实际读取字节数。

与源码等价的 SQL 形状及计划如下（会话参数使用虚构值，查询计划不依赖加载真实消息）：

```sql
EXPLAIN QUERY PLAN
SELECT DISTINCT conversation_id FROM conversation_events
WHERE workspace_id = ? LIMIT 10000;
-- SCAN conversation_events USING INDEX ix_ce_seq

EXPLAIN QUERY PLAN
SELECT * FROM ChatMessages WHERE SessionId IN (?, ?)
ORDER BY CreatedAt DESC LIMIT 10000;
-- SEARCH ChatMessages USING INDEX IX_ChatMessages_SessionId (SessionId=?)
-- USE TEMP B-TREE FOR ORDER BY

EXPLAIN QUERY PLAN
SELECT conversation_id FROM conversation_catalog WHERE workspace_id = ?;
-- SEARCH conversation_catalog USING INDEX IX_conversation_catalog_workspace_id (workspace_id=?)

EXPLAIN QUERY PLAN
SELECT Id, SessionId, Content, CreatedAt FROM ChatMessages
WHERE WorkspaceId = ? AND AgentInstanceId = ? AND CreatedAt >= ? AND CreatedAt < ?
ORDER BY CreatedAt DESC LIMIT 51;
-- SEARCH ChatMessages USING INDEX
-- IX_ChatMessages_WorkspaceId_AgentInstanceId_CreatedAt
-- (WorkspaceId=? AND AgentInstanceId=? AND CreatedAt>? AND CreatedAt<?)
```

事件表的现有索引没有 workspace 前缀：会话发现采用索引扫描，并需读取 workspace 列判断归属。消息的多会话检索不能直接得到全局时间顺序，需要临时 B-tree 排序；临时排序是否实际落盘尚未测量。已有 catalog 的 workspace 索引可避免从事件大表发现会话，但单独替换该步骤仍不能解决正文扫描。

截图只显示整块磁盘活动时间，无法独立证明所有占用来自 Pudding。尚未采集搜索期间的进程 I/O、冷暖耗时、实际读取字节和运行制品哈希；因此结论是**源码与现场查询计划确认存在缺陷**，不是对截图每一个峰值的完整归因。

## 3. 放大因素与正确性问题

- [`MemorySnippetRelevanceCalculator`](../../Source/PuddingRuntime/Services/MemorySnippetRelevanceCalculator.cs) 复用同一个 `GrepMessagesAsync`，每个 snippet 分别查询最近三天。因日期后过滤，相同消息集合可能被重复加载三次；这属于代码层面的潜在放大，未证明它在截图时正在执行。
- 先取最近 10,000 条再过滤日期/关键词，会漏掉更早的匹配；没有读完的消息也未准确体现在 `HasMore` 中。
- 弹窗在 Enter/分类切换时提交查询，没有忙碌时去重或取消旧搜索。可出现重叠请求；它并非每输入一个字符自动搜索。
- 话题标题单独走 `Contains`，属于普通数据库子串匹配，规模增大后也需索引化。
- 前端把搜索异常吞掉，呈现为空结果。实施索引后必须区分“没有匹配”与“索引尚未就绪”。

## 4. 为什么不能直接换成现有 GrepFtsAsync

[`RawSessionLogService.Fts.cs`](../../Source/PuddingPlatform/Services/RawSessionLogService.Fts.cs) 面向 Agent 原始 Markdown 日志证据：要求 agent 身份、日期范围最多 31 天、每日最多 512 个文件、最多 20 条命中。

它在查询路径内按天枚举文件并调用 `BuildIndexAsync(directory, "*.md")` 刷新索引，再执行搜索。刷新可能是增量，但仍涉及查询时文件走查和可能的索引写入。它返回 Markdown 行证据，不是 ChatMessages 消息 ID/完整消息合同。不能仅替换方法名，就宣称弹窗已具备低 I/O 的消息索引检索。

## 5. 建议修复设计与验收门禁

关键词历史查找优先采用**持久化全文倒排索引**，语义向量召回作为明确的可选能力。新增消息检索端口，索引文档以稳定 MessageId 为身份，保存 workspace、agent、session、CreatedAt 和可检索正文；正文只取用户/助手可见消息，不索引隐藏思考和工具原始 payload。

索引供应与查询分开：消息提交/终态投影产生可重放增量任务，以 durable checkpoint/outbox 捕获更新和删除；批量维护索引，避免每个 token delta 提交索引。存量消息单独进行有界回填，支持中断续跑。索引未就绪时返回明确状态，不在搜索请求内回填或降级全量扫描。

搜索先在索引中按 workspace/agent/session/日期过滤，再取 top-k 和一条额外命中判断 `HasMore`；只按命中的消息 ID 回源。列表默认仅返回有界 snippet，全文由受 workspace/agent 权限限制的消息详情接口按需读取。日期无关键词模式直接走带日期边界的消息索引分页。

必须覆盖截图中的双字中文“索引”，以及单字、英文大小写、子串和标点语义。不能只使用仅支持三个及以上字符的 trigram 查询，也不能为了短词偷偷退回正文全扫。Lucene 分析器或 SQLite FTS5 的预分词方案需先通过这些合同测试，再确定实现；全文与向量索引都应独立于调用方，并按组件交付规程先完成独立验证再接入 Host。

验收至少包括：

1. 早于最近 10,000 条的匹配可找到；workspace/agent/session/日期隔离在 top-k 前生效。
2. 中文短词、英文和标点测试；新增/修改/删除后索引一致，重启和积压恢复不漏消息。
3. 查询期间索引缺失明确报状态；没有目录扫描、BuildIndex、事件表全扫描或正文全量水合。
4. 大规模合成数据/在线备份副本测冷暖延迟、进程读取字节和返回正文体积；在 `temp/test-out` 验证，不对生产库试跑旧实现。
5. 前端取消/去重重叠搜索，错误与无匹配分开；新前端递增版本并验证部署徽标。
6. 外部控制器加载明确新构建后，进行真实弹窗功能 smoke 和进程 I/O 采样。当前尚未实施这些修复或验收。
