# Guardian 全应用退出验收

## 改动与边界

原有托盘退出只把 Guardian 留在 stopped，不退出进程。新增持久 `exit` 队列，完成当前部署或回滚后，先停止 Core，再关闭 Desktop，最后 Guardian 保存 exited 并退出。仅停止 Core 不关闭 Guardian；普通关闭窗口遵守托盘策略。

首次 Desktop 创建控制端点后提交 `launch`，由 Guardian 创建正式 Desktop，后者直接创建 Core；正式子进程跳过交接。`core.autoStart=false` 仅验收 Shell，不擅自启动 Core。显式重新打开 Desktop 才用 `--resume` 清除上次全应用退出意图。

Guardian 仍无产品 ProjectReference，Shell 未引入 Host/Runtime；控制令牌沿用已迁移的启动凭据解析。不改数据、前端及 KeyVault 加密链路。

- 变异：删除健康探针发现用户退出的分支后，ManualCoreStopKeepsGuardianButTrayExitDrainsWholeApplication 取红；恢复源码后全部变绿。日志 `.work/guardian-exit/20261117/mutation-red.log`、`restored-green.log`。
- Desktop 隔离构建通过；构建输出 `.work/guardian-exit/20261117/desktop-ready.log`。

## 外部验证与限制

状态：**ready-for-external-deploy，尚未完成全应用退出验收**。

定向脚本 `TestScripts/test-pudding-guardian-exit.ps1` 创建独立 DataRoot/DesktopHome/端口，验证父关系、单独停止 Core、全应用退出顺序、重新打开和数据目录租约释放。真实托盘操作使用 computer-use 技能。

当前隔离 EXE 的 Desktop 控制端点和 Guardian 均在 HttpListener 初始化失败，Desktop 报 Win32 6（句柄无效），未进入 healthy；该失败不能当作生命周期通过。日志 `.work/guardian-exit/20261117/lifecycle.log` 及对应 smoke 目录。

同一 Guardian DLL 通过 dotnet 启动后可暴露隔离认证端点；通过它提交全应用退出，完成清理并保存 exited。EXE 与 DLL 的差异尚未定位，不能归因到某一安全设置。未修改 Windows 安全设置。测试创建的旧隔离实例已清理，当前业务实例保持 healthy。

真实 WinUI 控制端点测试还原受 NuGet SSL EOF / NU1301 阻塞，未计入通过数。独立 xUnit 的标准 testhost 也出现父进程句柄拒绝访问，因此通过直接反射执行实际 Fact/InlineData 方法；不跳过用例或修改断言。
