# R1 注释面不可用 · 根因诊断

> 来源：R0-02 生产端口探针暴露的缺口（`c2573a4`）。
> 门禁原文：施工计划 §1.1 R0-02「概念反例可复现」。本诊断只定位，不含修复。

## 1. 现象

`PuddingRetrievalEvalProbe --mode production` 在 `small-puddingcodeindex` 集上，
8 条 `Kind=Intent` 用例的 `recall@10 = 0.0000`；同一集在 2026-10-02 的 Lucene 沙盘基线是 `0.7500`。

## 2. 三组排除实验（每组都能取红）

### 2.1 排除「文字层面查不到」

```
search_grep "匹配上限" → Source/PuddingCodeIndex/Services/Retrieval/RetrievalPortV1.cs:231 ✅ 文件里确实有
```
⇒ 文件级真值成立，问题在检索侧，不在语料。

### 2.2 排除「中文分词坏掉」

```
workspace_search("索引", intent=auto) → totalCount=7
```
⇒ 中文能命中。命中的 `why` 全部是「查询词命中**声明文本**（签名/容器），不是符号名」。

**关键观察**：7 条命中全部来自 `.tsx/.ts` 的声明文本，**没有任何一条来自 .cs 注释**。

### 2.3 排除「全文索引没建 / 没覆盖代码」

```
D:\Data\fulltext-index\.maintenance\<hash>\checkpoint.v1.json
  scopeRoot   = D:\CodeProject\PuddingAgent\PuddingAgent     ← 就是代码仓库根
  generation  = 696
  watermarkUtc= 2026-10-30T09:51:29Z                          ← 当天 17:51，仍在维护
  120 MB Lucene 索引实体（_6.cfs = 12.8 MB）
```
⇒ 索引存在、覆盖仓库、且当天还在增量更新。

## 3. 决定性证据

```
workspace_search("匹配上限", intent=comment)
  → totalCount 0
  → emptyReason = NotIndexed
  → nextStep    = RebuildIndex
  → 正文        「文本数据面不可用：scope 'default' 下没有已建立的全文索引（候选目录 1 个）」
```

而磁盘上**只有一个**全文索引，其 `scopeRoot` 是代码仓库根。

⇒ `WorkspaceRootScopeDirectories.Resolve("default")` 返回的那 1 个候选目录，
**不是** `D:\CodeProject\PuddingAgent\PuddingAgent`，其下没有已建立的索引。

代码路径：`Source/PuddingRuntime/Services/Retrieval/FullTextRetrievalTextSource.cs`
```csharp
var roots = _directories.Resolve(scopeId);          // ← 这里
var indexedRoots = roots.Where(_engine.HasIndex).ToList();
if (indexedRoots.Count == 0)
    throw new RetrievalTextSourceUnavailableException(
        $"scope '{scopeId}' 下没有已建立的全文索引（候选目录 {roots.Count} 个）");
```
默认实现 `WorkspaceRootScopeDirectories` 把检索 scope（= workspaceId）映射为**工作区根目录**
（`IExecutionEnvironmentProvider.GetWorkspaceRoot(scopeId)`），而全文索引是按**代码仓库根**建的。

## 4. 根因（两条，互相独立）

**R1-A｜scope → 目录映射错位。** 检索 scope 认的是 workspaceId，全文索引认的是目录路径；
桥接层把 workspaceId 映射成工作区根（`D:\Data\workspaces\default`），而代码在
`D:\CodeProject\PuddingAgent\PuddingAgent`，且索引是后者上建的 ⇒ 注释面恒 `NotIndexed`。

**R1-B｜`auto` 意图不含注释面。** `RetrievalPortV1.RetrieveCommentsAsync` 只在
`RetrievalIntent.Comment` 时被调用（`RetrievalPortV1.cs:452`）。
`auto` 只会走符号/声明文本面，所以任何「答案在注释里」的自然语言查询在 `auto` 下必然 0 命中。

两条叠加的结果：`auto` 不查注释，显式 `comment` 又因 R1-A 不可用 ⇒ 注释永不可检索。

## 5. 影响

- 施工计划 §1.1 R0-02 的「概念反例可复现」目前**只能靠 claim 免责**（返回 `claim.kind=None`），
  但**不能声称注释面可用**。
- ADR-089 里「统一检索」的承诺在注释面上不成立。
- 这不是 R0-02 引入的缺陷；R0-02 把它测出来了。

## 6. 修复方向（未实施，需裁定）

| 方向 | 内容 | 代价 |
|---|---|---|
| A | 引入「代码项目 → 仓库根」映射，替换/补充 `WorkspaceRootScopeDirectories` 的工作区根语义 | 触及 Runtime 服务的一层，要定多项目/多仓库时的解析规则 |
| B | 建索引时就以工作区根为 scopeRoot（改供给侧） | 与现有 696 代索引不兼容，需重建 |
| C | 仅在 `auto` 中融合注释面（先解决 R1-B） | 小；但 R1-A 会让它恒 NotIndexed，收益为 0 |

建议顺序：**先 A 后 C**。C 单独做没有意义——A 不通，注释面永远查不了。

## 7. 复现命令（无成本）

```
workspace_search(query="匹配上限", intent="comment")   → 期望当前：NotIndexed，候选目录 1 个
search_grep("匹配上限", Source/PuddingCodeIndex)        → 期望：RetrievalPortV1.cs:231（正对照）
```
