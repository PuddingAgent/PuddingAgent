# Goal 多轮效率与缓存命中评估（2026-09-17）

## 结论

**用户目标尚未达成；平台 Completed 只证明一个覆盖不足的验收合同通过。** 当前主要问题是目标合同遗漏、执行/认领恢复和等待期间的重复工作；缓存命中较高，但没有解决这些效率问题。

本次为只读取证与评估，没有构建、测试、部署、改配置、改数据库或变更任务状态。用户截图是现场证据，其中的 A/B、reopen、文件操作要求不作为本轮授权。

## 取证范围与口径

- SQLite 快照：2026-09-17 **18:04:20 北京时间**（10:04:20 UTC），`D:/data/databases/pudding_platform.db`，`mode=ro`、`query_only=on`。Goal、检查、验收合同、Gateway 与归因表在同一读取事务中提取。
- Task 状态另经 External Task API v1 读取：G92-0 v21、G92-1 v26。API 与数据库不是跨源原子快照。
- 之后按 Gateway `source_id=runtime-activity:<activity_id>` → `runtime_activity.execution_id/trace_id` → `goal_iterations.run_id/trace_id` 唯一关联请求。活动行另行只读查询。缓存百分比采用 `sum(hit)/(sum(hit)+sum(miss))`，不平均逐请求百分比。
- Gateway 为本地服务商 usage 记录，**本轮未与新导出的服务商账单对账**。TokenUsageEvents 仅补充原因/调用类型，不与 Gateway 相加；当天 1,263 条 Gateway 均有 session/provider/model/input/output/hit/miss 七元组唯一对应的归因行，这种内容关联不等于共享 requestId。
- 中间脚本/快照在忽略目录 `temp/goal-efficiency-*`，最终可读结论在本报告。不把运行数据库或原始会话正文提交到 Git。

**这属于验收合同覆盖不足导致的业务误完成。** 非空合同只能防“空集通过”，不能防“验错了东西”。当前源码 `GoalAcceptanceContractPlanner` 在没有目标证据时只写 engineering-gates warning；`ConservativeGoalIterationVerifier` 在 `allRequiredPassed && goalScope` 时可完成独立 Goal。两者组合与实测吻合。

“0 步骤”不是独立 Goal 必然错误；本例错误在于目标明确指向任务，合同却缺失任务验收义务。不能用强制所有目标拆步骤来替代合同覆盖校验。也不能只加“产物文件存在”：存在不证明内容、行为或验收条件满足。

API 结构化状态还揭示文案失真：G92-1 description 仍写 InProgress/72%/历史 assignment，实际字段为 Blocked/70%/无 active assignment；G92-0 description 的父任务编号与结构化 parentTaskId=null 不一致。应明确区分历史叙述和当前状态。上一轮回复的逐行判定实际上为 **1 项通过、5 项部分、1 项未达成**，仍写“3/3/1”，应从结构化子项自动汇总。

## 4. 改进优先级与验收断言

1. **P0 目标合同覆盖**：显式 Task 目标在 admission 时解析权威任务并绑定；将验收条件及依赖版本冻结入合同。未覆盖的目标义务必须可见，纯回归门禁不能替代目标级证明。普通文字/文件目标也要支持相应后置条件。回归用例：build/test全绿但G92-1未通过或Task未完成，Goal不得宣称原目标完成。独立Goal可无步骤，但必须有充分目标条件。
2. **P0 先恢复依赖与认领链**：审批 profile 缺失是依赖不可用，不能通过削弱审查门禁来解决；核对实际 resolver 与现有受支持配置，完成最小修复。`execution_claim_orphaned` 要检查 Assignment/Run/Reservation/fence，由canonical恢复协议处理，不能仅改description或反复reopen。截图的A/B方案本轮未完成配置级验证，不替用户选择执行。
3. **P0 等待不反复调用模型**：将检查 pending/依赖不可用持久化，释放资源，以结果/租约/依赖变化事件唤醒；在 blocker、输入身份、证据版本均未变化时，不再产生相同续行和全文汇报。修复工作可继续，但每轮应说明新增证据或义务变化。验收：等待期间无周期性LLM调用；恢复后恰好一次有效续行。
4. **P1 输入身份与检查恢复**：按已定ADR-092内容指纹实施；相关变化使旧成功和旧失败失效。执行前后输入变化则旧报告不得完成当前目标。构建互斥落实到执行资源/产物目录，旧epoch leased与实际存活进程分别核对。故障恢复需新租约/fence并拒绝迟到结果。
5. **P1 缓存优化按miss贡献排序**：优先压缩全周期收益（摘要调用+首轮重建+未来若干轮）、稳定工具序列与恢复、system首变段；后台按变化批处理与幂等。保持任务、工具功能、权限和必要历史语义；不能为命中率保留无限无效上下文。最终请求应记录不含正文的分段hash/首变位置及调用身份，避免只凭原因标签猜测。
6. **P1 效率与状态可观测**：同屏展示“目标条件满足数/总数、Task状态、等待原因、最后有效证据时间”，15/32明确为预算。追踪每个已验证义务的输入/miss/输出/费用/耗时，单列无进展续行、恢复次数、人工介入和压缩成本；补齐Goal cost账本及分层估算校准。

完成判定应沿用：源码验证 → 明确新构建 → 产品功能smoke → 全部目标义务通过 → canonical Task/Goal终态。此报告不申请运行上述修复、不变更任务分派；建议在既有授权范围内按依赖推进并报告具体外部所需动作。
