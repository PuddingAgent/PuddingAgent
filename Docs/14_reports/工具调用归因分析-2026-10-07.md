# 工具调用归因分析报告（2026-10-07）

## 0. 结论摘要（TL;DR）

1. **`file_patch` 吞换行已字节级复现，根因锁定到具体代码行**：`ExpandLeadingWhitespace`（`FilePatchTool.cs:468`）
   在 `old_text` **以换行开头**时执行 `start -= 2` 吃掉上一行的 `\r\n`，**而匹配跨度末端不变**
   ⇒ 上一行与本行**并成一行**，并残留**孤立 `\r`**。工具**报成功、无告警**。
2. **两次事故同一根因**：① 行合并；② 我的修复脚本在**含孤立 `\r` 的合并行**上 `rfind("|")` 切错位置丢列
   —— 后者不是独立的脚本错误，而是①的下游后果。
3. **对照组已跑**：同文件同形态，`old_text` **不以换行开头**时，精确匹配与**强制空白容忍匹配**两条路径**全部正确**。
4. **指标盲区（本报告最重要的元结论）**：`file_patch` 诊断统计为 **3 calls / 3 success / 0 failure / 成功率 100%**，
   而它实际造成 **2 次静默损坏**。⇒ **成功率指标不可用于判断正确性**，必须用磁盘字节比对做独立验收。

## 3. `file_patch` 吞换行：根因（代码分析 + 复现 + 对照组）

### 3.1 代码分析

`Source/PuddingRuntime/Tools/BuiltIns/Files/FilePatchTool.cs`

```csharp
// 行 466-490（含作者意图注释）
// Extend the span left over the same-line indent run —
// plus one preceding newline when old_text starts with a newline — so the replacement swaps
// the whole region including its indentation.
private static List<TextMatch> ExpandLeadingWhitespace(string original, string oldText, List<TextMatch> matches)
{
    if (matches.Count == 0 || !char.IsWhiteSpace(oldText[0]))
        return matches;

    var includeNewline = oldText[0] == '\n'
        || (oldText[0] == '\r' && oldText.Length > 1 && oldText[1] == '\n');

    for (var i = 0; i < matches.Count; i++)
    {
        var match = matches[i];
        var start = match.Index;
        while (start > 0 && (original[start - 1] == ' ' || original[start - 1] == '\t'))
            start--;
        if (includeNewline)
        {
            if (start >= 2 && original[start - 1] == '\n' && original[start - 2] == '\r')
                start -= 2;                       // ← 吃掉上一行的 CRLF
            else if (start >= 1 && (original[start - 1] == '\n' || original[start - 1] == '\r'))
                start--;
        }
        if (start != match.Index)
            matches[i] = new TextMatch(start, match.Index + match.Length - start, match.Strategy);
        //                        ↑ 末端恒为 match.Index + match.Length，不随 start 变化
    }
    return matches;
}
```

配套证据（同文件）：`FindNormalizedMatches` 的跨度末端由
`source.OriginalIndexes[end] + 1`（**末个内容字符 +1**）推出 ⇒ **末端不含行尾换行**；
`NormalizeEolToHost` 只规范化 **`new_text`**，**不会修复**被吞掉的换行。

**失配链**：`old_text` 前导换行 ⇒ 跨度**左端**多吃 2 字符（`\r\n`）；跨度**右端**不变
⇒ 被替换区域 = **上一行的行尾换行 + 本行内容**。若 `new_text` 不以换行开头，上一行与本行就**粘连成一行**。

### 3.2 复现（treatment / control 差一变量）

复现文件：CRLF、无 BOM、ASCII Markdown 表格（`temp/fp-repro.md` / `temp/fp-repro2.md`）。

| 组 | `old_text` 形态 | `new_text` 形态 | 结果 |
|---|---|---|---|
**T（treatment）** | **以 `\n` 开头**：`"\n\| target \| two \|"` | 不以换行开头：`"\| target \| two \|\n\| ins1 \| x \|"` | 🔴 **并行** |
**C1（control）** | 不以换行开头：`"\| target \| two \|"`（精确） | 同上 | ✅ 正确 |
**C2（control）** | **强制空白容忍**：`"\|   target2 \| two2 \|"`（文件里是 4 空格） | 同上 | ✅ 正确且缩进被规范化 |

**T 组字节级证据（`temp/fp-repro2.md`，复现前后）**

```text
before: 74 B, crlf 5
  | a | b |\r\n|---|---|\r\n| keep | one |\r\n| target | two |\r\n| tail | three |\r\n

after : 87 B, crlf 5, lone_lf 0
  | a | b |\r\n|---|---|\r\n| keep | one |\r| target | two |\r\n| ins1 | x |\r\n| tail | three |\r\n
                                        ↑↑ 被吃掉的是 \r\n 中的 \n，残留孤立 \r
```

**T 组工具自报的 diff（原文）**

```text
temp\fp-repro2.md: patched (1 replacements)
- | keep | one |
+ | keep | one || target | two |
- | target | two |
+ | ins1 | x |
```

⇒ 两行并成一行；`crlf` 计数不变（吃 1 加 1，掩盖了损失）；工具**报成功且无告警**。

### 3.3 为什么"看不见"（仪表缺陷，同一文件另一处）

`file_patch` 打印的 diff **本身会错位**：在 **C1 组**（磁盘字节完全正确、`crlf 11→13`）中，
工具输出的 diff 却呈现**整体位移一行的级联**：

```text
- | tail | three |
+ | ins1 | x |
-
+ | tail | three |
- | c | d |
+ 
- |---|---|
+ | c | d |
```

⇒ **diff 渲染会把"正确写入"显示成"结构错乱"**，也会把"结构错乱"显示成普通增删。
**它既会误报，也不能作为验收证据。**

### 3.4 两次事故的归因

| 事故 | 现象 | 归因 |
|---|---|---|
① `code-map-规范-v2.md` §7 | `header-repeat` 行与新行合并 | **T 组形态**：`old_text` 以 `\n` 做锚点、`new_text` 不以 `\n` 开头 ⇒ 触发跨度前扩。**主要是我方 payload 模式踩中工具的隐式契约** |
② 同文件 §6 | `路线图` 行与新行合并，且修复脚本 `rfind("\|")` 切错位置**丢第三列** | **①的下游**：合并行内含**孤立 `\r`**，我的修复脚本假设"每行是干净一行"、用 `rfind("\|")` 定位行尾 ⇒ 切点落在错误位置。**我方脚本缺防守 + 上游污染** |

**结论**：②**不是**独立的脚本 bug；把①修好（或改用整文件重写）②即不复现。我已据此改为
"**改 Markdown 表格行一律不用 `file_patch`**，改用 Python 精确替换或整文件重写，改完 `file_read` 复核"——
本轮根 code_map 与 L2 的两行补登即按此执行（`anchor_hits=1 already_present=0 / RESULT=INSERTED`，零污染）。

## 更正（2026-10-07）：匹配路径与修复建议复核

六组当前源码方法级探针确认：§3 的 **87 B、孤立 CR** 来自精确匹配 `old_text` 的前导 LF 命中 CRLF 的后半段；精确候选立即返回，未进入 `ExpandLeadingWhitespace`。强制容忍匹配才会前扩删除完整 CRLF，结果为 **86 B、无孤立 CR、两行粘连**。前文将两条路径归为同一分支的解释不成立。

diff 级联错位主要来自按相同行序号比较、没有序列对齐，不能仅通过 CRLF 切行修复。显式删除完整换行可能是合法替换；不采用“自动补回换行”或“右端扩到行尾”的通用修复。`rfind` 脚本缺结构校验需独立修复；子代理缺 skill_id、并发写者等历史定责仍缺原始事件证据。运行构建日期也不能证明实际加载了历史修复。

## §9 归因更正（2026-10-07 心跳实测推翻 §3.1）

**§3.1 的第一版归因错误**：我原判「`ExpandLeadingWhitespace` 的 `includeNewline` 分支吞掉了上一行换行」。**已被红测试推翻。**

**真正的机制（TRX 红测试锁定）**：

- `old_text` 以**孤立 `\n`（LF）**开头时，**精确匹配路径** `FindLiteralMatches` 在 CRLF 文件里**命中的是 `\r\n` 中的 `\n` 那一半**；且该路径 **命中即 `return exact`，根本不进入 `ExpandLeadingWhitespace`**。
- 于是跨度从 `\n` 开始 ⇒ **把 CRLF 劈成两半**，上一行留下**孤立 `\r`**、失去行尾 ⇒ 与替换文本并成一行（并会在表格里表现为「两行合并」）。
- 伴生事实：`NormalizeEolToHost` 只规范化 `new_text`，**从不规范化 `old_text`** —— 这就是非对称的源头。

**我方失误模式 5（新登记）**：读了代码就下结论，却**没算出「精确匹配会先命中 `\n` 那一半」**；而 `file_patch` 自报的 diff 渲染又会**整体位移错乱**，进一步把方向带偏。**是编译器（`CS7036`）与 TRX 红测试把方向纠回来的，不是我的阅读。**

**修复（已落地，26/26 全绿）**：

1. **跨度层面的两条不变量**：换行**不得被劈开**（跨度起点落在 CRLF 的 `\n` 上 ⇒ 回扩覆盖整个 `\r\n`）；换行**不得被吞掉**（跨度以换行开头而 `new_text` 未自带换行 ⇒ 把被吃的那个换行**原样还回** `new_text`）。
2. `includeNewline` 加**对称门**：`old_text` 与 `new_text` 都需以换行开头才扩展跨度。
3. 非对称时输出**显式 warn**（工具仍成功，携 `N issue(s)`），提示调用方：若确实想消费该换行，请把它写进 `new_text`。
