# 运行中心内存口径修复与 Core 内存占用归因（2026-10-02）

对应现象：运行中心显示 `内存 · 工作集 1007 MiB`，任务管理器显示 `PuddingAgent 730.6 MB`；设计要求 Core 常驻内存较小。

## 0. 结论

1. **两个数字不是同一口径**：面板读 `Process.WorkingSet64`（**总工作集**，含共享映像页 / 映射文件页 / 共享 JIT 代码页），任务管理器「内存」列是**专用工作集（Private Working Set）**。同一时刻实测：空数据根 Core 总工作集 248 MiB、专用工作集 **113 MiB**；真实数据下总工作集 570–652 MiB、专用工作集 438–493 MiB。
2. **730 MB 不是"设计上要常驻的数据"**：空数据根冷启动只有 **113 MiB** 专用工作集（Jieba 词典、Lucene reader、ASP.NET、全部装配都在内）。真实数据下抬升的主因是**代码索引（Roslyn + MSBuildWorkspace 整仓索引）+ 会话分块回填 + TypeScript 抽取**的突发负载；对照实验（唯一变量：代码索引 scope）显示峰值私有提交 **734 MiB → 271 MiB**、稳态专用工作集 **438–493 MiB → 192–201 MiB**。
3. **主因是索引工作负载本身，不是 GC 参数**：把 `DOTNET_gcServer` 关掉做同条件对照，专用工作集只降约 50–100 MiB，峰值反而从 734 MiB 升到 767 MiB（§2.5）。因此修复方向应是**收敛索引范围/预算**（§3.2），GC 配置只能作为上限兜底。

## 2. 问题二：733 MB 里是什么

### 2.1 复现方法（不触碰 `D:\data`）

- 二进制：用户实际在跑的 **Debug** 产物 `Source\PuddingAgent\bin\Debug\net10.0\PuddingAgent.exe`（来自 `%LOCALAPPDATA%\Pudding\desktop.json` 的 `coreExecutablePath`）。
- 数据：`D:\data` 的完整副本（robocopy，13.8 GB / 20126 文件）位于系统 Temp；**LLM/连接器/飞书凭据已移出**（`config\_quarantine`），`taskAutoDispatch.Enabled=false`、`externalTaskApi.enabled=false`，避免任何外呼与自动派单副作用。
- 端口/数据根与原实例隔离；测量脚本 `temp/memprobe/measure-replay.ps1`、`temp/memprobe/measure-core.ps1`、`temp/memprobe/ab-index.ps1`。

### 2.2 测量结果（同一构建、同一数据副本、每 5 s 采样）

| 组 | 变量 | 峰值私有提交 | 稳态总工作集 | 稳态私有提交 | 稳态专用工作集 |
| --- | --- | --- | --- | --- | --- |
| 基线 | 空数据根，Server GC | ≤133 MiB（采样最大，未记录真峰值） | 248 MiB | 129 MiB | **113 MiB** |
| A | 真实数据 + 代码索引**关闭**，Server GC | **271 MiB** | 333–338 MiB | 219–228 MiB | **192–201 MiB** |
| B | 真实数据 + 代码索引**开启**，Server GC | **734 MiB** | 570–652 MiB | 643–730 MiB | **438–493 MiB** |
| C | 真实数据 + 代码索引**开启**，`DOTNET_gcServer=0` | **767 MiB** | 546–553 MiB | 621–627 MiB | **386–392 MiB** |

A/B 唯一变量是代码索引 scope，差值：**峰值私有提交 +463 MiB、稳态专用工作集 +245 MiB**。

### 2.3 触发源（Core 自身日志，同一时间轴）

```

09:26:26 [SessionChunkBackfill] progress batch=140 lastId=7000 indexed=1092 ...

   ...（连续数十个 csproj，绝大多数 "Failed to open project"）

```

- `CodeIndexMaintenanceHost: 0 registered scope(s)`（关闭组）时峰值只有 271 MiB；有 scope 时把 `D:\CodeProject\PuddingAgent\PuddingAgent` 整仓交给 **Roslyn `MSBuildWorkspace`**，逐个 `OpenProjectAsync`，并对 `dist-dev/*.js` 跑 **TypeScript 抽取脚本**（对 `vendors_1-async.js` 产生 4.6 万行 JSON 并在 `symbols[5192]` 处解析失败）。
- `system.json` 的 `FullTextIndex.Scopes` 同样指向整个仓库；`FullTextIndex.Enabled=true`。
- `Config: runtime.enableRuntimeDiagnostics=true`、`enableFrontendDebug=true`、`enableFakeLlm=true`。

### 2.4 保留机制（为什么空闲不归还）

- 产物 `PuddingAgent.runtimeconfig.json` 只写了一条 GC 配置：`"System.GC.Server": true`（Web SDK 默认）。`System.GC.HeapCount`、`System.GC.DynamicAdaptationMode`（DATAS）、`System.GC.RetainVM`、`System.GC.HeapHardLimit`、`System.GC.Concurrent` 均未设置。
- 本机 24 逻辑核 ⇒ Server GC 24 个堆，逐堆 gen0 预算/卡表/标记位图随核数放大；DATAS 未开时**峰值后不主动缩容**。
- 观测：真实数据组在 09:26:50 之后日志静默（突发结束），但 09:33–09:34 仍持有总工作集 570 MiB / 私有提交 643 MiB；09:34:47 采样显示 CPU 仍在忙（10.64 s/10 s，索引未结束）。基线组（空数据根）则长期稳定在 248 MiB WS / 113 MiB 专用工作集。

### 2.5 关闭 Server GC 的对照（C 组）

| 指标 | B 组：Server GC | C 组：`DOTNET_gcServer=0` | 差值 |
| --- | --- | --- | --- |
| 峰值私有提交 | 734 MiB | 767 MiB | **+33 MiB（工作站反而更高）** |
| 索引进行中 总工作集 | 570–652 MiB | 546–553 MiB | −20 ～ −100 MiB |
| 索引进行中 私有提交 | 643–730 MiB | 621–627 MiB | −16 ～ −105 MiB |
| 索引进行中 专用工作集 | 438–493 MiB | 386–392 MiB | **−50 ～ −100 MiB** |

**结论（与最初的 GC 假设相反，按实测修正）**：单独关闭 Server GC 只是有限改善（专用工作集约 −10%），峰值不降反升。说明这数百 MB 主要是**索引期间仍然存活的对象**（Roslyn 编译/语法树、MSBuild 加载的程序集与项目图、TypeScript 抽取结果），而不是"GC 没回收的余量"。GC 侧更适合作为**上限兜底**（`System.GC.HeapHardLimit` / `DynamicAdaptationMode`），不是主修复手段。

⚠️ 两组"稳态"都发生在**索引尚未结束**时（C 组日志 09:42:17 仍在 `Opening project`，停止时 CPU 仍在增长），因此上表读作"索引进行中"而非"索引完成后空闲"。索引结束后的空闲 footprint 见 §2.8。

这些体量本身不常驻；但在有 HTTP 请求时会成为"一次性物化"的风险面（§3.3）。本次复现**没有 Desktop/WebView 轮询、没有诊断页面请求**，仍达到峰值 734 MiB，说明代码索引一项就足以解释主因。

### 2.7 与用户实例的差异（不夸大）

用户实例：总工作集 1007 MiB、专用工作集 730.6 MB。本次复现：总工作集 570–652 MiB、专用工作集 438–493 MiB、峰值私有提交 734 MiB。缺口（约 +240 MiB 专用工作集）可能来自用户实例额外的 Desktop WebView 每秒轮询、诊断/遥测/统计接口的全量物化（§3.3）、以及更长的索引过程（本次索引在采样结束时仍未结束）。代码索引一项的因果性由 A/B 对照确证；其余增量尚未逐项实测。

### 2.8 索引结束后是否归还（idle 观测，18 分钟未到平台期）

方法：`temp/memprobe/measure-idle.ps1`——启动同一数据副本，每 15 s 采样，直到 CPU 连续 3 次空闲（忙比 < 0.05）或 18 分钟到时。

| 时刻 | 总工作集 | 私有提交 | 专用工作集 | CPU 忙比 |
| --- | --- | --- | --- | --- |
| 16 s（接近峰值） | 506–623 MiB | 447–654 MiB | 351–465 MiB | 0.39–1.16 |
| 9 min | 585–623 MiB | 615–654 MiB | 426–464 MiB | ~1.10 |
| 18 min（到时停止） | **439 MiB** | **462 MiB** | **278 MiB** | **1.12** |

- **18 分钟内没有出现空闲**：CPU 忙比全程 1.03–1.16（≈ 1 个逻辑核持续满载）。`SessionChunkBackfill` 在 09:47:01 完成后日志不再输出进度行，但进程继续满载计算——这说明索引/抽取循环在静默状态下仍在长时间运行。
- 内存不是"不归还"，而是**随索引推进缓慢下降**（专用工作集 465 → 278 MiB），18 分钟仍未到平台期。因此"索引完成后的空闲 footprint"本轮**未取得**；真正的空闲观测点是用户实例本身（4.4% CPU、1007 MiB 总工作集 / 730.6 MB 专用工作集），它说明空闲时内存仍停在数百 MB 量级。
- 由此新增一条待查项（本轮未定位）：**整仓索引的代价与结束条件**——日志可见 `Failed to open project` 之后仍 `escalating to a scope-level indexing run`，18 分钟无进度输出且持续满载，需要单独确认是首次全量索引耗时、还是失败重试/重复索引。

## 3. 建议

### 3.1 P1：GC 配置作为上限兜底（实测收益有限）

- 实测：`System.GC.Server=false` 只把索引期间的专用工作集降约 50–100 MiB，峰值不降（734 → 767 MiB）。因此**不要把它当作主修复**。
- 可选的兜底：设 `System.GC.HeapHardLimit`（例如 512 MB～1 GB）明确上限，或保留 Server GC 但开启 `System.GC.DynamicAdaptationMode=1`；二者尚未在本轮实测，接入前应按 §2 的方法做同条件 A/B。
- 24 逻辑核上 24 个 GC 堆对 100–700 MB 量级的进程收益有限，但这条不是本轮的主因。

### 3.2 P0：代码索引的触发与预算

- scope 不应默认覆盖整仓（含 `dist-dev`、`eval`、`Docs` 大文件与生成的 JS）；索引产品源码目录即可。
- Roslyn `MSBuildWorkspace` 逐个 `OpenProjectAsync` 大量失败（日志数十条 `Failed to open project`），失败重试与并发需要一个预算与退避，避免"失败但不释放"的峰值。
- TypeScript 抽取对 `dist-dev/vendors_1-async.js` 产出的 4.6 万行 JSON 解析失败，说明抽取脚本对超大打包产物既耗内存又无效：应在扫描阶段排除构建产物（`dist*`、`*.min.js`、`obj/bin`）。
- 结束条件与可观测性（§2.8）：整仓索引在复现中 18 分钟未结束、持续约 1 个逻辑核满载，且 `SessionChunkBackfill` 结束后**无进度日志**。需要给索引加"进度心跳 + 结束/失败事件 + 单轮时间与内存预算"，否则内存与 CPU 的异常既看不见也停不下来。

### 3.3 P1：三处"先全表物化、再在内存过滤/分页"的无界查询

| 位置 | 现象 | 建议 |
| --- | --- | --- |
| `Source/PuddingPlatform/Controllers/Api/TelemetryMetricsController.cs:48` | `AsNoTracking().ToListAsync()` 后 `:49-52` 才按 `sinceUtc` 过滤，`:54-68` 内存 GroupBy（2.37M 行 / 695 MB 字符串） | 时间过滤与 GroupBy 下推 SQL，强制默认时间窗/行数上限 |
| `Source/PuddingPlatform/Services/Diagnostics/RuntimeTimelineQueryService.cs:366-397` | 四个来源全量 `ToListAsync`，`:85-91` 内存排序后才 `Skip/Take` | 分页下推；`conversation_events` 只 `Select` 所需列，绝不物化 `payload` |
| `Source/PuddingPlatform/Controllers/Api/StatsApiController.cs:528-534` | 全表 `ToListAsync` 后内存按 from/to 过滤（带 `sessionId` 即走此分支） | 过滤/聚合下推 SQL |

### 3.4 P1：无淘汰的进程级字典

`Source/PuddingPlatform/Services/SessionStateManager.cs` 的 `_headNotificationChannels`/`_streamBatchBuffers`/`_sessionStates`/`_seqLocks`/`_sequenceStates` 全无 `TryRemove`；`Source/PuddingRuntime/Services/ContextPipeline.cs` 的 `_staticCache`/`_workspaceAgentsCache`/`_envCache` 按 session 缓存上下文正文且无容量上限。建议加 TTL/容量并暴露计数便于观测。

### 3.5 P2：启动期重活分帧

`SessionChunkBackfill`（本次 242 批）与 Jieba 回填都在启动路径附近集中执行；可改为空闲窗口分帧，避免与索引叠加成峰值。
