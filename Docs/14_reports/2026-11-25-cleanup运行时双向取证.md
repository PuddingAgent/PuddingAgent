# cleanup 运行时双向取证

## 为什么必须做双向

`f6cdaa4` 之前 cleanup 先销毁条目再清理，清理失败后唯一定位键没了；`d528c99` 之前复核读的是 `session_sub_agents` 投影，而 `CleanupAsync` 只删 `sub_agent_runs` 行与磁盘归档 —— 投影行本来就不删，于是断言恒真，每次清理都报「没清掉」，空闲条目也不销毁，命令彻底不可用。

这两处都只有单元测试。而单元测试的替身**不模拟投影的持久性**，所以那条恒真断言在测试里根本抓不到。

更关键的是：只验「无归档 → 报本来就不存在」是**单向**的 —— 一个「永远报本来就不存在」的实现同样能通过。判据必须是有归档的那一侧确实删掉了东西。

## 部署前置

| 项 | 现场 |
|---|---|
| 提交 | `d528c99` 19:52:26 |
| live DLL | `PuddingHost` 19:55:28 / `PuddingRuntime` 19:55:24 / `PuddingPlatform` 19:55:26 |
| 进程 | PID 101756 @ 19:56:10 |
| 模块路径 | 取自 `Get-Process.Modules`，指向 `temp\build\winui3\bin\PuddingDesktop\Debug\...\core\` |

三者有序且都晚于提交。**「重启 ≠ 部署」**，所以这一步不可省。

## 负向：无运行归档

建一条探针成员（`cleanup-probe-1125`，`pool_action="create"`，只预留不执行），独立通道确认 `agent_pool` 有行、`sub_agent_runs` 为 **0** 行。

调 `pool_action="cleanup"`，回执：

```
? 子代理 'cleanup-probe-1125' 已清理。 池条目已销毁。 运行归档本就不存在（此前已清理或从未落盘）。
```

事后核对：`agent_pool` 该行 `status='dead'`、`deleted_at=2026-11-25T11:59:05Z`；`sub_agent_runs` 仍 0 行；池列表回到原有 5 条。

## 正向：有运行归档

再建 `cleanup-probe-1125b` 并实跑一单（任务只有「只回复一个词：OK」），独立通道确认**清理前**三件事：

```
pool  [('cleanup-probe-1125b', 'sleeping', 'probe')]
runs  [('run_20261125_115930_1c300d22d626', 'completed', 'D:\Data\...\runs\run_20261125_115930_1c300d22d626')]
archivedir_exists=True
```

调 `cleanup`，回执：

```
? 子代理 'cleanup-probe-1125b' 已清理。 池条目已销毁。 已删除运行归档 1 条。
```

事后核对三件事全部翻转：

```
runs_after 0
pool_after [('cleanup-probe-1125b', 'dead', 1)]
archivedir_after=False
```

**两条分支各自被独立观测到，且计数变化方向相反**（0→报不存在；1→报删除 1 条且库行与磁盘目录同时消失）。这才排除「实现恒报一种结果」的退化可能。

## 顺带闭合一处遗留不对称

上一份验收报告（`2026-11-25-里程碑1验收-面板改角色热生效运行时取证.md`）末尾记了一条已知不对称：模型路由与模板的继承会向调用方公告，**角色继承发生在 Platform 层，工具看不到生效值，因此静默**；要补必须改接口契约，当时没做。

`57467c3` 补了 `SubAgentExecuteResult.RoleInPlan` 并由工具写进结果 JSON。本次正向用例的派活回执里直接读到：

```json
"subAgentId": "...-sub-fcd0ef11",
"runId": "run_20261125_115930_1c300d22d626",
"status": "completed",
"rawOutput": "OK",
"roleInPlan": "probe"
```

`roleInPlan` 是**生效值**而非入参（入参里确实带了 `pool_role="probe"`，但同一字段在「不传角色」时会回填条目声明角色 —— 那条路径由 `57467c3` 的单元测试覆盖）。这里能说的是：新字段确实出现在了运行时产物里，不再只是单元测试里的一个断言。

## 边界

- 两例都是**我自己建的探针成员**，不动用户既有的 5 条。探针销毁后 `agent_pool` 留下 `status='dead'` 墓碑行（软删除，池列表不可见），这是既有设计而非残留缺陷。
- 只覆盖 `cleanup` 单条路径。`cleanup-bulk` 仍按父会话批量，未在运行时验证。
- 「忙碌条目先销毁再清理」这条顺序分支**未在运行时取红** —— 要造出忙碌且清理失败的组合需要故障注入，本轮没做。
- `ResolveRunArchiveIdAsync` 的降级分支（快照查不到 → 退回 `SubSessionId` 占位值）仍无用例。

## 复用要点

- 破坏性命令的验收要「造对象 → 独立通道记前置状态 → 执行 → 独立通道核后置状态」，工具回执只当**待验主张**。
- 两侧相反方向的计数变化，比单侧「成功」文案更能排除退化实现。
- 探针成员一律用可识别命名（`cleanup-probe-<日期>`），事后按名字确认已不在池列表里。

## 追加（2026-11-25 20:4x）：验收时发现的第二个不收敛点——投影行

上文的双向取证只看 `sub_agent_runs` 与磁盘归档。取证收尾时顺手核了一件当时没列入判据的事：被清理的成员在 `session_sub_agents` 里还有没有行。

结果是有。

```
负向探针 cleanup-probe-1125   （从未执行）→ session_sub_agents 无行
正向探针 cleanup-probe-1125b  （执行过一单）→ 行仍在，Status='completed'
```

### 为什么这不只是数据残留

`session_sub_agents` 是「每个子会话的当前状态投影」，而它直接被 UI 消费：

```
SessionEventsController.cs:614   GET /api/sessions/{sessionId}/sub-agents  → _ssm.GetSubAgentsAsync
api.ts:2098                      getSessionSubAgents()
useSessionEventReplay.ts:119     const statuses = await getSessionSubAgents(selectedSessionId)
```

也就是说：成员销毁了、运行归档删了，**会话面板里仍挂着一个 completed 的子代理条目**，而 `cleanup` 是唯一声称「清理」的命令——它给出的成功回执与界面上的事实相反，且用户没有别的入口把那条去掉。

`CleanupAsync` 只删 run 行与磁盘归档（`SubAgentManager.cs` 旧实现），投影表此前**没有任何删除入口**（`ISessionStateManager` 只有 Track / Recover / 查询）。

### 修法

- `ISessionStateManager.RemoveSubAgentProjectionsAsync(parentSessionId, subSessionIds)` —— 首个删除入口。
  **父会话必须一起进 WHERE**：投影按父会话归属，只给子会话 id 时跨会话重名会删到别人的行。
- `SubAgentManager.CleanupAsync` 在删完 run 行后，对「归档确实不存在」的子会话删投影。
  判据不能只看 `DeleteRunAsync` 的返回值：`false` 是两义的（本来没有 / 删失败），
  删失败时投影是那条 run 的最后线索，一起抹掉就等于把可重试状态变成不可重试。
  因此新增 `IsRunArchiveAbsentAsync`：占位 RunId（快照在无 run 行时回退成 SubSessionId）直接判「不存在」，
  其余走 `GetRunArchiveAsync` 复核；探针本身抛错时一律当作「仍然存在」。
- 返回值语义**不变**：`CleanupAsync` 仍返回删掉的 run 行数（工具那句「已删除运行归档 N 条」说的是它），
  投影删除只进日志与接口返回。

### 这份修复的证据边界

- 编译绿、定向 214 例（Platform，`~SubAgent`）与 45 例（Runtime，`~SubAgentTool`）全通过、提交门禁 `OK: no new test failures`。
- **但没有新增守护用例**：`SubAgentManager.CleanupAsync` 至今没有直接单测（此前只有工具层的 mock），
  而给它补一个需要构造 7 个依赖并自建子代理状态替身。这一段属未覆盖，写在这里而不是留在脑子里。
- 计划中的运行时证据：部署后对那条已销毁成员的幽灵行调 `cleanup`（走 `sub_agent_id` 回退路径），
  预期回执成功且 `session_sub_agents` 该行消失。**未取得前不得声称已验证。**
