## 1. 诊断（实测）

| 项 | 值 |
|---|---|
| 文件大小 | 2,836,717,568 B（2.64 GiB） |
| `PRAGMA page_size` | 4096 |
| `PRAGMA page_count` | 692,558 |
| `PRAGMA freelist_count` | **194,231 页 = 758.7 MiB（26.8%）** |
| `PRAGMA auto_vacuum` | **0 = NONE** |

`CodeSourceAppliedVersions` 23,469；`CodeSourceManifest` 7,823；`CodeFiles` 5,407；
`CodeProjects` 4；`CodeIndexRuns` **0**。

**根因**：`auto_vacuum=NONE` ⇒ 页一旦释放就永久留在 freelist，文件只增不减。
不是"数据堆积"问题（无历史表膨胀）。

回收量比 freelist 多约 272 MiB，来自 B-tree 页重新装填（`VACUUM` 不只是清空洞）。

## 2. 模式选择：`INCREMENTAL`

| 模式 | 优点 | 代价 | 结论 |
|---|---|---|---|
| `NONE` | 无 pointer-map，写入开销最低 | 文件不缩小，只能反复做 73 秒全量 `VACUUM` | 不推荐 |
| `INCREMENTAL` | 按批回收，可限时/退避，不影响每次提交 | 约 0.12% pointer-map（本库约 2–3 MiB）；移动页产生额外 WAL | **推荐** |
| `FULL` | 每次提交后尽量缩小 | 每次提交移动页 + 更新指针 + 增 WAL，劣化尾延迟 | 不适合持续批量写 |

4096 B 页约每 820 页需要一个 pointer-map 页。WAL 模式下，移动/截断先入 WAL，
主文件物理缩小要等 checkpoint 完成。

**从 `NONE` 切换必须**（两句都不得放进显式事务）：

```sql
PRAGMA auto_vacuum=INCREMENTAL;
VACUUM;
```

## 3. 一次性整治（需维护窗口）

前置：停止 watcher 与索引写入，排空并关闭连接池。**不要在启动路径执行。**

第一连接（核对基线）：

```sql
PRAGMA busy_timeout=60000;
PRAGMA wal_checkpoint(TRUNCATE);   -- 返回首列必须为 0
PRAGMA integrity_check;            -- 必须仅返回 ok
PRAGMA foreign_key_check;          -- 必须零行
-- 七张表 count 全部记录，作为整治后比对基线
```

关闭连接后备份（SQLite Backup API，或确认 checkpoint 完成且句柄全关后复制主库）。
备份放另一卷。

唯一维护连接：

```sql
PRAGMA busy_timeout=60000;
PRAGMA auto_vacuum=INCREMENTAL;
VACUUM;
PRAGMA optimize;
PRAGMA wal_checkpoint(TRUNCATE);
-- 验收查询
PRAGMA integrity_check;
PRAGMA foreign_key_check;
PRAGMA auto_vacuum;      -- 必须为 2
PRAGMA journal_mode;     -- 必须为 wal
PRAGMA page_size;        -- 必须为 4096
PRAGMA page_count;
PRAGMA freelist_count;   -- 必须为 0
```

验收条件：`integrity_check=ok`；`foreign_key_check` 零行；七表计数不变；
`auto_vacuum=2` / `journal_mode=wal` / `page_size=4096`；`freelist_count=0`；
文件接近 1,756,123,136 B（因 pointer-map 与统计可能略大）；checkpoint 首列为 0。

## 4. 长期维护

每小时记录：`page_count`、`freelist_count`、`free_bytes = freelist_count × page_size`、
`free_ratio = freelist_count / page_count`、DB/WAL 文件大小、checkpoint 的 busy/log/checkpointed、
WAL 峰值、维护耗时、`SQLITE_BUSY` 次数、读写 P95/P99、最长读事务年龄。

触发条件（空闲时）：`free_bytes ≥ 128 MiB` 且 `free_ratio ≥ 10%`。
每 30–60 秒最多一批，每小时最多 16 批；降到 `< 64 MiB` 或 `< 5%` 即停。

```sql
PRAGMA busy_timeout=250;
PRAGMA incremental_vacuum(1024);   -- 最多回收 1024 页 = 4 MiB
PRAGMA wal_checkpoint(PASSIVE);
```

每批独立自动提交；遇 `SQLITE_BUSY` 直接退避，不密集重试。
每天在无读事务间隙尝试 `PRAGMA wal_checkpoint(TRUNCATE);`。
每周低负载 `PRAGMA quick_check; PRAGMA optimize;`；每月或异常关机后做完整 `PRAGMA integrity_check;`。

**为什么 `incremental_vacuum` 可能不缩文件**：① 模式仍是 `NONE` 时完全无效；
② 只回收 freelist 整页，不能压实 B-tree 页内空隙；③ WAL 结果未 checkpoint 前主文件不变。

## 5. 触发位置

| 动作 | 位置 |
|---|---|
| 模式切换 + 全量 `VACUUM` | **显式管理员命令 + 计划维护窗口** |
| 日常小批回收 | 应用内低优先级后台计时器，与索引写入调度器互斥 |
| 启动 | **只采集指标，绝不执行重维护** |
| 外部计划任务 | 不推荐（无法可靠协调连接池、watcher 与唯一写者） |

73 秒写锁放在启动会造成可用性风险与恢复风暴；后台偷偷执行同样不可接受。

## 6. 风险与缓解

| 风险 | 缓解 |
|---|---|
| 磁盘空间 | `VACUUM` 需要额外空闲空间（保守按 ≥ 原库大小准备）；同卷备份则需更多。本机 D: 当前 342 GB，充足 |
| 中断 | 原地 `VACUUM` 是事务性的，进程被杀应回滚或恢复；仍须保留已验证备份，**绝不手工删 `-wal/-shm`** |
| WAL 膨胀 | 长读事务导致 checkpoint starvation ⇒ 限制读事务寿命、小批回收、监控 backlog |
| 锁竞争 | SQLite 同时只有一个 writer ⇒ 维护与索引批次互斥，短超时 + 退避 |
| **ROWID 变化** | `VACUUM` 可能改变**没有显式 `INTEGER PRIMARY KEY`** 的表的 ROWID ⇒ 不得把隐式 ROWID 当外部标识（见 §7） |
| 回滚 | 验收失败时停所有连接，移开新库并恢复备份，不混用新旧 WAL |

## 7. 关键提醒：`CodeSymbols` 的隐式 ROWID 不可外依

`CodeSymbols` 的主键是 `(WorkspaceId, ProjectId, SymbolId)` 复合主键，**不是** `INTEGER PRIMARY KEY`，
因此其 `rowid` 是隐式的 —— SQLite 文档声明 `VACUUM` 可能改变这类表的 ROWID。

**这条直接影响此前拟用的 FTS5 方案**：该方案的设想是让倒排表 `rowid` 与 `CodeSymbols.rowid` 对齐，
`VACUUM` 之后这种对齐可能失效。⇒ 若落地 FTS5，倒排表必须**自带稳定业务键**
（`WorkspaceId`/`ProjectId`/`SymbolId`），不能依赖 rowid 关联。

**本库实测（2026-10-23，逐字节副本）**：VACUUM 前后按 `SymbolId` 比对全部 142,884 行
（`WorkspaceId='default'`）的 `rowid` 映射 ⚠️（口径有误，见 §11.3），结果 `ROWID_CHANGED=0`、`MISSING=0` —— **本次未变**。

但 SQLite 文档的措辞是"可能"而**非保证**，因此落地 FTS5 时倒排表**仍应自带稳定业务键**
（`WorkspaceId` / `ProjectId` / `SymbolId`），不要依赖 rowid 关联 —— 这是防御性设计，
不是当前阻塞项。（本次 VACUUM 耗时 37.8 秒，与先前 72.9 秒同量级，差异来自副本页缓存温度。）

## 8. 优先实施清单

1. 增加显式维护模式、连接排空与备份路径。
2. 在维护窗口切换 `INCREMENTAL` 并完整验收。
3. 落地容量 / WAL / 延迟指标采集。

## 10. 第二版评审（GPT-6 Astra）与差异裁决

来源：`fastrouter/gpt-6-astra`（1.05M context，纯推理，任务书禁止调用工具），单次窄范围裁决。

### 10.1 两版一致（结论已稳定）

- 选 `INCREMENTAL`；`NONE` 无法增量归还空间，`FULL` 会放大大批写入的尾延迟与锁竞争。
- 切换必须 `PRAGMA auto_vacuum=INCREMENTAL;` 再 `VACUUM`，**不得处于显式事务**。
- 全量 `VACUUM` 只走管理员计划窗口；**启动路径只采指标**。
- `incremental_vacuum` 不保证缩文件。
- 不得依赖隐式 rowid。

### 10.2 Astra 对第一版（codex）的修正 —— 已采纳

| 项 | 第一版说法 | Astra 修正 | 采纳 |
|---|---|---|---|
| **备份方式** | 确认 checkpoint 完成且句柄全关后复制主库 | **不要直接复制活跃 WAL 数据库**；用 `sqlite3_backup` 或 `VACUUM INTO` 到新文件，并对备份跑 `PRAGMA integrity_check` | ✅ 重要 |
| **`busy_timeout`** | 每批前 `PRAGMA busy_timeout=250` | 它是**连接级**参数，应在连接初始化时设置；忙时**跳过/退避**，不能靠忙等抢写锁 | ✅ |
| **`wal_checkpoint(PASSIVE)`** | 每批执行 | **不保证 WAL 截断**；不应无条件执行，按 WAL 指标与读者情况择机，且不把 PASSIVE 当截断保证 | ✅ |
| **30–60 秒一批 / 每小时 ≤16 批** | 当作执行节奏 | 是**限速上限**，不保证每批都跑；空闲写窗口、耗时、WAL 状态优先 | ✅ |
| **采样频率** | 每小时 | **每分钟** | ✅ |
| **验收门槛** | 文件接近 1,756,123,136 B | 生产值受写入时点影响，**不以逐字节相等为硬门槛** | ✅ |
| **阈值 128 MiB / 10%** | 直接采用 | 同意作初始值，但需以运行指标校准并配**低水位滞回**，避免阈值附近频繁启停 | ✅ |

### 10.3 Astra 强调的执行要点

1. 无条件执行 `PRAGMA incremental_vacuum(1024);` 之后**每批重新采样** —— 不能把"调用成功"当成"回收成功"。
2. 全量 `VACUUM` 期间**只暂停索引写入，不阻塞短读服务**；通知调用方并给任务设超时。
3. 批次连续无进展、耗时超预算、或影响到索引写入 ⇒ **暂停并告警**，升级管理员评估全量整理。
4. 避免外部计划任务与应用内维护器**并发操作同一库**。
5. 若生产无法接受写停顿，先做**副本演练**再选维护窗口（本文件 §1.1 已是该演练结果）。

### 10.4 结论

两版方案在方向上一致，Astra 的修正在**备份安全性**（不复制活跃 WAL）与 **PRAGMA 语义准确性**（连接级 busy_timeout、PASSIVE 非截断保证）两处是实质改进。
最终执行口径以 §10.2 修正后的版本为准。

## 11. 第三版评审（codex CLI + gpt-6-astra）与更正

来源：`codex exec -m gpt-6-astra`（CLI `0.163.0-alpha.11.2`，`sandbox=read-only`，reasoning `xhigh`，`--ephemeral`）。
⚠️ 工具指引里"配置中的 `gpt-6-astra` 会 400"的旧记录**已过时**：0.163.0 的 `models_cache.json` 已含该 slug（9 个模型），实测可正常运行。

### 11.1 与前两版的实质分歧（已采用 Astra）

| 议题 | 前两版 | Astra（第三版） | 采用 |
|---|---|---|---|
| 是否急需压缩 | 以"回收 38%"为主要动机 | **磁盘充足，没有紧急压缩理由**；先完成验证，再安排一次维护窗口 | ✅ |
| freelist 性质 | 表述为"26.8% 空间浪费" | **空闲页可被后续重索引复用，不是泄漏** | ✅ 更正措辞 |
| 进入阈值 | ≥128 MiB 且 ≥10% | **≥256 MiB 且 ≥20%，且持续 24 小时、趋势未显示快速复用** | ✅ |
| 退出阈值 | <64 MiB 或 <5% | **≤128 MiB 或 ≤10%**（滞回带更宽，留给下一轮重索引） | ✅ |
| 单批页数 | 直接用 1024 | **从 128 页试跑，按实测升到 1024；单批目标 ≤100 ms，超标减半** | ✅ |
| 采样频率 | 每小时 / 每分钟 | 启动 + **每 5 分钟** | ✅ |
| 验收断言 | 文件接近 1,756,123,136 B | **断言文件长度 == `page_count × 4096`**，不要断言等于副本实测值（pointer-map 会改变结果） | ✅ 更严谨 |
| 基线内容 | 仅八表行数 | **行数 + 按业务键排序的全列摘要**（防"行数对但内容变"） | ✅ |
| 备份方式 | `sqlite3_backup` 或 `VACUUM INTO` | 优先 **Backup API**（1024 页/步），明确"不要依次复制 db/wal/shm 冒充一致快照" | ✅ |
| checkpoint 断言 | 首列为 0 | **断言返回 `(0,0,0)`**；读 `(busy, log, checkpointed)`，不能只看第一列 | ✅ |

### 11.2 它指出前两版都遗漏的一点：SQLite 版本门禁

官方记录过多连接写入/检查点竞争导致数据库损坏的 WAL-reset 缺陷，要求 **3.51.3+** 或含修复的回移版本。

**本机实测（只读，2026-10-23）**：

```
SQLITE_VERSION=3.53.3
SQLITE_SOURCE_ID=2026-06-26 20:14:12 d4c0e51e4aeb96955b99185ab9cde75c339e2c29c3f3f12428d364a10d782c62
JOURNAL_MODE=wal  AUTO_VACUUM=0  PAGE_SIZE=4096  PAGE_COUNT=692558  FREELIST=194274
```

⇒ **3.53.3 高于 3.51.3，版本门禁通过。**

⚠️ 同时观察到：**`freelist_count` 从 194,231 变为 194,274（+43 页）**，说明生产库在此期间**有写入活动**（后台索引在跑）。⇒ 维护窗口开场必须先证明写入真的停了，不能只看"我以为停了"。

### 11.3 它指出的本报告数据缺陷（必须更正）

Astra 明确指出：**rowid 比对覆盖 142,884 行，少于题给的 195,641 行，必须解释差异。**

核查结果：**是本报告的探针有缺陷。** rowid 探针用 `Dictionary<string, long>` 且以 `SymbolId` 为键，而 `CodeSymbols` 主键是 `(WorkspaceId, ProjectId, SymbolId)` —— **`SymbolId` 在不同 project 间会重复**，后写覆盖前写。因此 142,884 是"去重后的唯一 SymbolId 数"，**不是行数**。

- §7 的"142,884 行"应读作 **"142,884 个唯一 SymbolId"**。
- **`ROWID_CHANGED=0` 这一结论仍然成立**（前后用同一键集合对比，是有效的等价性检验），但**覆盖少了 52,757 行**，不得声称"全部 195,641 行都验证过"。
- 若要完整覆盖，需改用 `(WorkspaceId, ProjectId, SymbolId)` 三元组为键重测。

### 11.4 它补充的两条运维要点

1. **同库的 maintenance ledger 也会被写锁阻塞** ⇒ 文件监听事件必须先进**独立持久队列**，维护结束后重放并做文件清单对账；不能只依赖 `FileSystemWatcher`（事件溢出时必须能重扫）。
2. 维护连接用 `PRAGMA synchronous=FULL`；进程终止时保留 db 及关联文件让 SQLite 自行恢复，**禁止用删 WAL 来"修复"**；成功提交的 `VACUUM` **不能靠 `ROLLBACK` 撤销**。

### 11.5 三版结论收敛

三版在模式选择与执行路径上一致（`INCREMENTAL` + 窗口内全量 VACUUM + 启动只采指标），
差异收敛为**参数与断言严格度**，以 §11.1 为准；**新增版本门禁（§11.2）与 rowid 口径更正（§11.3）**。

### 12.2 第一条代码改动：新建库启用 INCREMENTAL（完成）

`Source/PuddingCodeIndex/Storage/SqliteCodeIndexStore.cs` 的 `InitializeAsync` 顶部：

```sql
-- 新建库启用 INCREMENTAL（注释说明：仅建库时生效，存量库需一次 VACUUM）
PRAGMA auto_vacuum = INCREMENTAL;
PRAGMA journal_mode = WAL;
PRAGMA foreign_keys = ON;
```

**关键顺序：`auto_vacuum` 必须排在 `journal_mode` 之前。**
第一版写在 `journal_mode` 之后，测试当场取红 —— `Assert.AreEqual 失败。应为: <2>，实际为: <0>`；
原因是 `journal_mode=WAL` 会写入库文件头，此后 `auto_vacuum` 不再生效。

验证链：
1. 新增 `SqliteCodeIndexAutoVacuumTests`：断言新建库 `PRAGMA auto_vacuum == 2`，且重开初始化后仍为 2。
2. **变异取红**：注释掉该 PRAGMA ⇒ `失败: 1，通过: 0`；恢复后 SHA 与基线**逐位一致**（`B99A9D29…`），无 `MUTATION` 残留。

### 12.6 第三条改动：调度决策（纯逻辑，完成）

### 12.7 第四条改动：管理员维护入口（完成）

`SqliteCodeIndexStore.RunFullMaintenanceAsync(backupPath)` —— **显式调用、破坏性、不接启动路径也不接后台循环**。

**执行顺序（顺序本身被断言约束）**：

1. 采样 + **全表行数基线**（动态枚举 `sqlite_master`，不硬编码表名 ⇒ 新增表自动纳入）
2. **备份并校验**：Backup API 一致快照 → 对备份跑 `integrity_check` + 逐表行数比对 → 先删陈旧备份再写新备份
3. `busy_timeout=5000` + `synchronous=FULL`
4. `wal_checkpoint(TRUNCATE)` → **断言返回 `(0,0,0)`**；若不是 idle，**主动跳过 VACUUM** 并把原因记进失败列表
5. `auto_vacuum=INCREMENTAL` → `VACUUM` → `optimize` → checkpoint
6. 验收：模式 == 2、`freelist_count == 0`、逐表行数一致（含表集合一致）、**文件长度 == `page_count × page_size`**

**三个关键决策**：

- 报告里 `VerificationFailures` 为空才算成功；`"VACUUM 没抛异常"` 不算证据
- checkpoint 非 idle 时**不硬跑** —— 有读者/写者残留时重写要么失败，要么产出没人敢信的结果
- 文件长度断言用 `page_count × page_size`，**不用副本实测字节**（pointer-map 会改变它）

**补上的关键场景**：`Full_Maintenance_Switches_An_Existing_None_Mode_Database`
先造一个 `auto_vacuum=0` 的存量库（表先存在，`InitializeAsync` 的 PRAGMA 因此无效），再跑维护，断言模式变 2。
这正是生产库的真实处境 —— 新库场景根本验不出模式切换是否有效。

验证：5 个用例；变异（把 `PRAGMA auto_vacuum = INCREMENTAL;` 换成 `journal_mode`）⇒ 存量库用例红，
失败项正是 `auto_vacuum is 0, expected 2`；恢复后 SHA 逐位一致（`EA1CD23F…`）、无 `MUTATION` 残留；

### 12.11 「文件监听事件持久队列」经查证**不需要实现**

原待办来自第三次评审的担心：写锁期间监听事件可能丢失。**读代码后发现现有设计已用另一种方式解决，而且更简单。**

现有链路（全部在 `PuddingCodeIndex`）：

| 环节 | 位置 | 行为 |
|---|---|---|
| 队列 | `CodeIndexChangeQueue`（75 行） | **进程内** `Channel`，容量 8192，`FullMode.Wait`（通道本身永不静默丢弃） |
| 丢弃判定 | `CodeIndexWatcher.HandleChange` L272-278 | `TryPublish` 返回 false ⇒ `MarkNeedsReconcile(QueueOverflow)` + 计数 + 日志 |
| 监听错误 | `CodeIndexWatcher.HandleError` L293-305 | `InternalBufferOverflowException` ⇒ `MarkNeedsReconcile(WatcherError)` |
| 回调异常 | `CodeIndexWatcher.OnCallbackFault` L324-329 | ⇒ `MarkNeedsReconcile(CallbackFault)` |
| **无条件周期校准** | `CodeIndexMaintenanceService.IsCalibrationDue` **L1263** | `now - (LastCalibrationAt ?? AttachedAt) >= 15 min` ⇒ 逐路径对照文件系统 |
| 校准失败重试梯 | `CalibrationBackoffInterval` L1268+ | 60 s → 2 m → 4 → 8 → 16 → 30 min 上限 |

**关键点**：`NeedsReconcile` 的确是内存字段（`CodeIndexScopeState` L61，无持久化）。
但校准**不看这个字段** —— `IsCalibrationDue` 无条件按 15 分钟返回 true，而「从未校准过」的 anchor 是 **attach 时刻**。
⇒ 宿主重启 → 重新 attach → `LastCalibrationAtUtc = null` → **15 分钟内必跑一次全量校准**，把崩溃窗口内丢的事件补回来。

**因此不做持久队列。** 持久队列要自己处理存储失败、清理、重放顺序、去重与幂等，还会引入一个新故障面；
而周期对账只需一次文件系统扫描，且已有失败重试梯。加它就是重复造轮子。

**代价（如实记录）**：崩溃后最坏有 **15 分钟**的索引不一致窗口 —— ADR-089 §U3-C 已按此口径规定节奏，
这比「永不丢失但重放逻辑复杂」的故障面更小。

**取证方式**：读代码（行号如上）。这一项**没有代码改动**，也没有新增测试。
