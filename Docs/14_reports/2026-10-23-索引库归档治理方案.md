## 1. 诊断（实测）

| 项 | 值 |
|---|---|
| 文件大小 | 2,836,717,568 B（2.64 GiB） |
| `PRAGMA page_size` | 4096 |
| `PRAGMA page_count` | 692,558 |
| `PRAGMA freelist_count` | **194,231 页 = 758.7 MiB（26.8%）** |
| `PRAGMA auto_vacuum` | **0 = NONE** |
| `PRAGMA journal_mode` | wal |

行数：`CodeReferences` 756,514；`CodeRelations` 484,466；`CodeSymbols` 195,641；
`CodeSourceAppliedVersions` 23,469；`CodeSourceManifest` 7,823；`CodeFiles` 5,407；
`CodeProjects` 4；`CodeIndexRuns` **0**。

**根因**：`auto_vacuum=NONE` ⇒ 页一旦释放就永久留在 freelist，文件只增不减。
不是"数据堆积"问题（无历史表膨胀）。

### 1.1 副本 VACUUM 实测

| 项 | 值 |
|---|---|
| 前 | 2,836,717,568 B |
| 后 | 1,756,123,136 B |
| 回收 | **1,030.5 MiB（38.1%）** |
| 耗时 | **72,933 ms（72.9 秒）** |

| `integrity_check` | ok |
| 行数 | 七张表全部不变 |

回收量比 freelist 多约 272 MiB，来自 B-tree 页重新装填（`VACUUM` 不只是清空洞）。

## 2. 模式选择：`INCREMENTAL`

| 模式 | 优点 | 代价 | 结论 |
|---|---|---|---|
| `NONE` | 无 pointer-map，写入开销最低 | 文件不缩小，只能反复做 73 秒全量 `VACUUM` | 不推荐 |
| `INCREMENTAL` | 按批回收，可限时/退避，不影响每次提交 | 约 0.12% pointer-map（本库约 2–3 MiB）；移动页产生额外 WAL | **推荐** |
| `FULL` | 每次提交后尽量缩小 | 每次提交移动页 + 更新指针 + 增 WAL，劣化尾延迟 | 不适合持续批量写 |

4096 B 页约每 820 页需要一个 pointer-map 页。WAL 模式下，移动/截断先入 WAL，
主文件物理缩小要等 checkpoint 完成。

**从 `NONE` 切换必须**（两句都不得放进显式事务）：

```sql
PRAGMA auto_vacuum=INCREMENTAL;
VACUUM;
```

## 3. 一次性整治（需维护窗口）

前置：停止 watcher 与索引写入，排空并关闭连接池。**不要在启动路径执行。**

第一连接（核对基线）：

```sql
PRAGMA busy_timeout=60000;
PRAGMA wal_checkpoint(TRUNCATE);   -- 返回首列必须为 0
PRAGMA integrity_check;            -- 必须仅返回 ok
PRAGMA foreign_key_check;          -- 必须零行
-- 七张表 count 全部记录，作为整治后比对基线
```

关闭连接后备份（SQLite Backup API，或确认 checkpoint 完成且句柄全关后复制主库）。
备份放另一卷。

唯一维护连接：

```sql
PRAGMA busy_timeout=60000;
PRAGMA auto_vacuum=INCREMENTAL;
VACUUM;
PRAGMA optimize;
PRAGMA wal_checkpoint(TRUNCATE);
-- 验收查询
PRAGMA integrity_check;
PRAGMA foreign_key_check;
PRAGMA auto_vacuum;      -- 必须为 2
PRAGMA journal_mode;     -- 必须为 wal
PRAGMA page_size;        -- 必须为 4096
PRAGMA page_count;
PRAGMA freelist_count;   -- 必须为 0
```

验收条件：`integrity_check=ok`；`foreign_key_check` 零行；七表计数不变；
`auto_vacuum=2` / `journal_mode=wal` / `page_size=4096`；`freelist_count=0`；
文件接近 1,756,123,136 B（因 pointer-map 与统计可能略大）；checkpoint 首列为 0。

## 4. 长期维护

每小时记录：`page_count`、`freelist_count`、`free_bytes = freelist_count × page_size`、
`free_ratio = freelist_count / page_count`、DB/WAL 文件大小、checkpoint 的 busy/log/checkpointed、
WAL 峰值、维护耗时、`SQLITE_BUSY` 次数、读写 P95/P99、最长读事务年龄。

触发条件（空闲时）：`free_bytes ≥ 128 MiB` 且 `free_ratio ≥ 10%`。
每 30–60 秒最多一批，每小时最多 16 批；降到 `< 64 MiB` 或 `< 5%` 即停。

```sql
PRAGMA busy_timeout=250;
PRAGMA incremental_vacuum(1024);   -- 最多回收 1024 页 = 4 MiB
PRAGMA wal_checkpoint(PASSIVE);
```

每批独立自动提交；遇 `SQLITE_BUSY` 直接退避，不密集重试。
每天在无读事务间隙尝试 `PRAGMA wal_checkpoint(TRUNCATE);`。
每周低负载 `PRAGMA quick_check; PRAGMA optimize;`；每月或异常关机后做完整 `PRAGMA integrity_check;`。

**为什么 `incremental_vacuum` 可能不缩文件**：① 模式仍是 `NONE` 时完全无效；
② 只回收 freelist 整页，不能压实 B-tree 页内空隙；③ WAL 结果未 checkpoint 前主文件不变。

## 5. 触发位置

| 动作 | 位置 |
|---|---|
| 模式切换 + 全量 `VACUUM` | **显式管理员命令 + 计划维护窗口** |
| 日常小批回收 | 应用内低优先级后台计时器，与索引写入调度器互斥 |
| 启动 | **只采集指标，绝不执行重维护** |
| 外部计划任务 | 不推荐（无法可靠协调连接池、watcher 与唯一写者） |

73 秒写锁放在启动会造成可用性风险与恢复风暴；后台偷偷执行同样不可接受。

## 6. 风险与缓解

| 风险 | 缓解 |
|---|---|
| 磁盘空间 | `VACUUM` 需要额外空闲空间（保守按 ≥ 原库大小准备）；同卷备份则需更多。本机 D: 当前 342 GB，充足 |
| 中断 | 原地 `VACUUM` 是事务性的，进程被杀应回滚或恢复；仍须保留已验证备份，**绝不手工删 `-wal/-shm`** |
| WAL 膨胀 | 长读事务导致 checkpoint starvation ⇒ 限制读事务寿命、小批回收、监控 backlog |
| 锁竞争 | SQLite 同时只有一个 writer ⇒ 维护与索引批次互斥，短超时 + 退避 |
| **ROWID 变化** | `VACUUM` 可能改变**没有显式 `INTEGER PRIMARY KEY`** 的表的 ROWID ⇒ 不得把隐式 ROWID 当外部标识（见 §7） |
| 回滚 | 验收失败时停所有连接，移开新库并恢复备份，不混用新旧 WAL |

## 7. 关键提醒：`CodeSymbols` 的隐式 ROWID 不可外依

`CodeSymbols` 的主键是 `(WorkspaceId, ProjectId, SymbolId)` 复合主键，**不是** `INTEGER PRIMARY KEY`，
因此其 `rowid` 是隐式的 —— SQLite 文档声明 `VACUUM` 可能改变这类表的 ROWID。

**这条直接影响此前拟用的 FTS5 方案**：该方案的设想是让倒排表 `rowid` 与 `CodeSymbols.rowid` 对齐，
`VACUUM` 之后这种对齐可能失效。⇒ 若落地 FTS5，倒排表必须**自带稳定业务键**
（`WorkspaceId`/`ProjectId`/`SymbolId`），不能依赖 rowid 关联。

**本库实测（2026-10-23，逐字节副本）**：VACUUM 前后按 `SymbolId` 比对全部 142,884 行
（`WorkspaceId='default'`）的 `rowid` 映射，结果 `ROWID_CHANGED=0`、`MISSING=0` —— **本次未变**。

但 SQLite 文档的措辞是"可能"而**非保证**，因此落地 FTS5 时倒排表**仍应自带稳定业务键**
（`WorkspaceId` / `ProjectId` / `SymbolId`），不要依赖 rowid 关联 —— 这是防御性设计，
不是当前阻塞项。（本次 VACUUM 耗时 37.8 秒，与先前 72.9 秒同量级，差异来自副本页缓存温度。）

## 10. 第二版评审（GPT-6 Astra）与差异裁决

来源：`fastrouter/gpt-6-astra`（1.05M context，纯推理，任务书禁止调用工具），单次窄范围裁决。

### 10.1 两版一致（结论已稳定）

- 选 `INCREMENTAL`；`NONE` 无法增量归还空间，`FULL` 会放大大批写入的尾延迟与锁竞争。
- 切换必须 `PRAGMA auto_vacuum=INCREMENTAL;` 再 `VACUUM`，**不得处于显式事务**。
- 全量 `VACUUM` 只走管理员计划窗口；**启动路径只采指标**。
- `incremental_vacuum` 不保证缩文件。
- 不得依赖隐式 rowid。

### 10.2 Astra 对第一版（codex）的修正 —— 已采纳

| 项 | 第一版说法 | Astra 修正 | 采纳 |
|---|---|---|---|
| **备份方式** | 确认 checkpoint 完成且句柄全关后复制主库 | **不要直接复制活跃 WAL 数据库**；用 `sqlite3_backup` 或 `VACUUM INTO` 到新文件，并对备份跑 `PRAGMA integrity_check` | ✅ 重要 |
| **`busy_timeout`** | 每批前 `PRAGMA busy_timeout=250` | 它是**连接级**参数，应在连接初始化时设置；忙时**跳过/退避**，不能靠忙等抢写锁 | ✅ |
| **`wal_checkpoint(PASSIVE)`** | 每批执行 | **不保证 WAL 截断**；不应无条件执行，按 WAL 指标与读者情况择机，且不把 PASSIVE 当截断保证 | ✅ |
| **30–60 秒一批 / 每小时 ≤16 批** | 当作执行节奏 | 是**限速上限**，不保证每批都跑；空闲写窗口、耗时、WAL 状态优先 | ✅ |
| **采样频率** | 每小时 | **每分钟** | ✅ |
| **验收门槛** | 文件接近 1,756,123,136 B | 生产值受写入时点影响，**不以逐字节相等为硬门槛** | ✅ |
| **阈值 128 MiB / 10%** | 直接采用 | 同意作初始值，但需以运行指标校准并配**低水位滞回**，避免阈值附近频繁启停 | ✅ |

### 10.3 Astra 强调的执行要点

1. 无条件执行 `PRAGMA incremental_vacuum(1024);` 之后**每批重新采样** —— 不能把"调用成功"当成"回收成功"。
2. 全量 `VACUUM` 期间**只暂停索引写入，不阻塞短读服务**；通知调用方并给任务设超时。
3. 批次连续无进展、耗时超预算、或影响到索引写入 ⇒ **暂停并告警**，升级管理员评估全量整理。
4. 避免外部计划任务与应用内维护器**并发操作同一库**。
5. 若生产无法接受写停顿，先做**副本演练**再选维护窗口（本文件 §1.1 已是该演练结果）。

### 10.4 结论

两版方案在方向上一致，Astra 的修正在**备份安全性**（不复制活跃 WAL）与 **PRAGMA 语义准确性**（连接级 busy_timeout、PASSIVE 非截断保证）两处是实质改进。
最终执行口径以 §10.2 修正后的版本为准。
