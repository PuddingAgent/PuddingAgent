# 子代理运行失败归因普查

## 1. 方法与样本

- 数据源：`D:\Data\databases\pudding_platform.db`，表 `sub_agent_runs`，**只读**打开（`mode=ro`）。
- 样本：1860 行，时间跨度 `2026-07-18` → `2026-11-24`。
- 状态分布：`completed` 1299 · `failed` 397 · `interrupted` 79 · `budget_exhausted` 42 · `cancelled` 23 · `timed_out` 20。
- 动机：先确认「下一步该修什么」，而不是按计划顺序继续做。

## 2. 结论先行

### 2.1 「busy 悬挂」没有现场依据 ⇒ 租约方案降级

普查同时查了池表：

```
agent_pool  status 计数：idle 2 · sleeping 3 · busy 0
sub_agent_runs  非终态（running）计数：0
```

即：**当前没有任何一条卡在 `running` 的 run，也没有任何一条 `busy` 的池条目。**

原计划（心跳/租约判据）是为「进程活着、run 卡在 running」这一形态设计的。该形态在 4 个月、1860 次运行的真实数据里**一次都没留下痕迹**。按「不为未观测到的问题造框架」的纪律，它降级为观察项，不进入实现队列。

需要如实说明的反面可能：进程内的悬挂会在**下一次重启时**被启动期恢复顺手修掉，因此终态表上看不出来。这条局限无法用现有数据排除，所以是「降级」而非「删除」。

### 2.2 失败最多的一批已经终结于 8–9 月

| 类别 | n | 首次 | **最后一次** | 判定 |
|---|---|---|---|---|
| A `reasoning_text` 未回传 | 23 | 08-19 | **08-26** | 已修 |
| B `non_stream_not_allowed` | 5 | 09-18 | **09-22** | 已修 |
| D 轮次耗尽（10/20/30/5） | 52 | 07-18 | **08-10** | 已修（限额或收敛改进） |
| L 执行以 `state=Failed` 结束 | 12 | 07-18 | 09-26 | 已修 |
| I `shell` 命令超时 | 13 | 08-06 | 09-25 | 已修 |
| H 取消 | 10 | 07-19 | 09-21 | 行为正常 |
| J 审批闸门拦截 | 9 | 08-02 | 09-19 | 设计如此 |
| C 文件被占用 | 9 | 08-14 | 09-24 | 已修 |

**「最后一次发生时间」这一列是本次普查的关键**：只看 `n` 会把早已修复的类别排在待办第一位。

抽样核对了一条 C 类与一条工具类，都能在 git 历史里找到对应修复（例：`terminal_start` 的 `yield_time_ms` 越界在 `13b3b22`「stop common misuse from killing a whole agent turn」改为夹取，该提交时间 11-13 19:50，而对应失败发生在同日 17:10 —— 修复正是被这类失败推动的）。

### 2.3 现存最大的可改类别：子代理工具误用

失败的「其它」桶 200 条按错误前缀细分：

| 前缀 | n | 性质 |
|---|---|---|
| `LLM API call failed` | 42 | 环境（网络 / 配额 / SSL） |
| `file_read` | 26 | **工具误用**（路径不存在居多） |
| `search_grep` | 19 | **工具误用**（传文件当目录、枚举上限） |
| `file_search` | 11 | 工具误用 |
| `file_patch` | 9 | 工具误用（锚点歧义） |
| `list_dir` | 6 | 工具误用 |
| `code_outline` | 5 | 工具误用 |
| `Outbound LLM history is …` | 5 | 平台护栏（待定性） |
| `LLM request input is too …` | 4 | 输入超限 |
| `apply_patch` / `browser_context` / `agent_skill` / `terminal_start` | 各 3 | 工具误用 |

工具误用合计约 **88 条 / 397 ≈ 22%**，显著大于环境类的 42 条。

这类失败有个共同点：**都不是能力问题，而是「工具规则没在错误的当口被说出来」**。例如：

- `file_patch` 在 `patch_text` 模式下，目标取自 diff 头部，入参 `path` **不参与解析**——本次普查期间实测复现：给了合法 `path` + 相对头部名，得到 `File not found: rt_d_ok.txt`（按进程 cwd 解析）。模型完全无法从错误文本推断「是我给的另一个参数被忽略了」。

**一处已自我纠正（原稿写错）：** 本报告初稿曾称 `search_grep` 的 `directory` 传入文件路径时只说「not found」。回查原始行文后确认**不实**——实际输出是

```
search_grep: '<…>\SubAgentManager.cs' is a file, not a directory. 'directory' must be a folder;
pass the containing folder, or use 'pattern' to match its content.
```

即该工具的诊断语**已经合格**。它那 19 条属于「模型误用」，不是「诊断不足」——两者不该混为一谈：前者靠提示词与工具描述改善，后者靠改代码。初稿把二者归到同一桶，是抽样时只看 150 字符截断文本导致的误判。

## 3. 下一步优先级（据本节数据重排）

1. **工具诊断语（小、可立即做）**：把「参数被忽略」这类**代码事实**写进错误文本本身。已落地：`file_read` / `list_dir` / `patch_text` 未命中时补出解析后的绝对路径、最深的已存在祖先与缺失层数（`MissingPathDiagnostics`）。
2. **`Outbound LLM history is …` 与 `LLM request input is too …`（9 条）定性**：这是平台护栏，需要确认它是「正确拦截」还是「配置过紧」。
3. **观察项**：`busy` 悬挂。仅当现场再次出现 `busy` 且 `running` 长期不终结时，才启动租约设计。
4. 环境类（SSL / 配额）不修代码，按需换路由。

## 4. 方法与局限

- `error_message` 记录的是**最后一条错误**，不等于运行的终止原因。因此本报告只做「类别与时间窗」统计，不据此断言因果。
- 未读 `run.json` / `events.jsonl`（文件系统为主存储）。若要判定某条失败的真实终止原因，需按 `archive_path` 展开，本次未做。
- `interrupted` 79 条是启动期恢复写入的，属正常工作路径，未计入失败。
- 「已修」的判定依据是「最后一次发生时间 + 在 git 历史里找到对应修复」，不是重跑复现。严谨说法是「该类在修复后未再出现」。
