# 首 Token 等待与上下文指示器诊断

两条消息均在主模型流式请求之前同步执行 warm-prefix 历史压缩，压缩分别耗时 **20.760 秒、22.854 秒**。主模型自身的首个非空推理增量分别为 **4.250 秒、3.987 秒**。这是已经通过同一消息、命令、Turn 和日志关联确认的主因；截图的“等待执行反馈”不能等同于 Provider TTFT。

上下文指示器则混合展示了保守预算估算、模型总窗口占用率与有效输入窗口压力，并把容量压力称为“上下文服务异常”。新压缩摘要的标记与计量器标记不同，亦存在确定的分层归因缺口。

## 3. 源码根因

### 3.1 同步摘要挡在主模型前面

[Streaming](../../Source/PuddingRuntime/Services/AgentExecution/AgentExecutionService.Streaming.cs) 第 789 行附近在最终预算检查前 `await TryWarmPrefixCompactionAsync`。该方法位于 [AgentExecutionService](../../Source/PuddingRuntime/Services/AgentExecutionService.cs) 第 2116 行附近，调用 `LlmInvoker.InvokeAsync(... purpose: "compaction")` 等待完整摘要后才替换历史。

[WarmPrefixCompaction](../../Source/PuddingRuntime/Services/WarmPrefixCompaction.cs) 原样重放出站历史和工具头，附加摘要指令。这有前缀缓存收益，但摘要仍需生成；即使用户消息只有五字，也要处理长历史。本次每个请求带 99 个工具定义。工具范围是输入开销的次要优化对象，不能直接解释成这次 23 秒全由工具 schema 引起。

`warmPrefixCompactionAttempted` 是每次 dispatch 的局部标记，跨 Turn 不防重复；上一 Turn 执行 35 轮/54 次工具后历史再次增长，下一条继续触发。不能以“刚压缩过”为由跳过真实的硬输入边界。

### 3.2 压缩缺少可展示的生命周期和计时

warm-prefix 方法只返回 outcome 并记日志，未发布通用的 `context.compaction.started/completed/failed`。Streaming 在 context 帧之后进入同步摘要，摘要输出也不进入当前消息流。已有普通压缩生命周期与前端 `useCompaction` 没有覆盖这条路径。

因此压缩期间没有推理/正文/工具事件可以展示。当前源码的 canonical `TurnStatus` 能从 started 派生 connecting，但截图仍为 pending；具体是运行制品版本、消息 Turn 绑定、surface 水合还是 fallback facts 路径，缺少浏览器同次抓取证据，**尚未唯一定位**。补齐压缩生命周期是独立成立的修复。

`AgentTurnTimingCollector` 在 Runtime 内部建立，晚于命令受理、准入与部分启动工作；其文档称“submit”不够精确。`modelMs` 只包主流，不包前置同步摘要；`contextReadyMs` 也早于摘要。当前终态计时没有独立 `compactionMs`，不能仅用这个面板看到完整因果链。

## 4. 上下文指示器

### 4.1 数值数学上相容，语义和置信度有问题

截图：用量约 463.8K / 1000.0K = 46.38%；有效输入 606.8K，剩余约 143.0K；故有效输入压力约 **76.4%**。总窗口百分比和有效输入百分比的分母不同，不是减法错误。

同一 Turn 在 22:50:36.327 的 canonical `usage.recorded` 返回输入 **131,117**、输出 **966**、总量 **132,083** Tokens；随后是 22:50:36.379 的下一轮请求。截图采集时间 22:50:36，来源 `llm_request_calibrated`，用量约 463.8K，约为最近已完成请求输入的 **3.5 倍**。这些是相邻请求，不能直接宣称完全相同请求的精确估算误差；但它明确不是“模型实测占用了 464K”。

[LlmOptions](../../Source/PuddingCore/Platform/LlmOptions.cs) 的 `CaptureLlmRequest` 每次将预算估算覆盖到同一 session 快照；Provider usage 完成又覆盖为报数。[ContextCompactionService](../../Source/PuddingRuntime/Services/ContextCompactionService.cs) 优先返回最新内存快照。因此运行时面板会随“请求准备/请求完成”交替切换估算与报数。

校准系数按 session/model 保留历史最大值，不能回落；日志已有 `calibration=1.845`。它用于安全预算是保守设计，但把它直接用于可见占用、健康告警和软压缩触发会放大压力。原始计量与 Responses wire 是否同形、系数为何达到该值、是否存在请求归因错配，仍待独立请求身份验证，不能只删除校准。

**第四张截图确认的下降**：22:53:13 显示 164.7K / 1000K = 16.5%，来源明确为 Provider 报数。canonical sequence `1703138` 在 22:53:13.106 记录输入 **164,612**、输出 **63**、总量 **164,675**，与截图数值完全一致。这个下降来自估算快照换成实测报数，不能解释成这一时刻又压缩了一次。第二条 Turn 的压缩 checkpoint 在22:50:19；22:53:13附近没有新的 warm-prefix提交或硬预算裁剪日志，该 Turn 查询也没有通用 compaction 事件。

**另有真实裁剪，必须区分**：后续22:57:20日志在同一 run 的 round23显示 `Trimmed outbound history ... removed=91`、请求消息143→56；此后多个轮次仍报告removed=91。这是 `LlmRequestBudgetGuard.Prepare` 对各次出站历史副本的硬预算裁剪，不能冒充新增持久摘要或每轮从会话再次删除91条消息。Streaming当前仅记Warning，未发可见裁剪事件。因此后续数值确有可能因真实出站范围变化下降，修复不能把所有下降一概当成估算切换。

### 4.2 “上下文服务异常”实际上是容量压力

[ContextHealthEvaluator](../../Source/PuddingRuntime/Services/ContextHealthEvaluator.cs) 使用 effective input 为门禁分母，76.4% 会超过 75% 的 Unhealthy 阈值。[serviceStatus](../../Source/PuddingPlatformAdmin/src/pages/chat/components/serviceStatus.ts) 将 Unhealthy/Critical/Blocking 映射 `error`，面板称“上下文服务异常”。这不能证明网络/API/服务故障，应分别展示容量压力与采集可用性。46.4% 的总窗口环形指示仍呈低压力颜色，亦与容量告警使用不同分母。

### 4.3 压缩摘要桶遗漏

warm-prefix checkpoint 写入 `<compacted-summary>`；计量器只识别 `<compact_summary>`。因此摘要被归入 conversation，不能显示正确的“压缩后记忆”色段。截图没有该色段，与这条源码缺口吻合；尚未对运行程序集作相同标记断言。

### 4.4 “预留输出”推导不完整

[ComposerStatusDetails](../../Source/PuddingPlatformAdmin/src/pages/chat/components/ComposerStatusDetails.tsx) 用 `windowLimit - effectiveLimit` 推导预留输出；[ContextUsageRing](../../Source/PuddingPlatformAdmin/src/pages/chat/components/ContextUsageRing.tsx) 同样推导不可用区。有效输入还可能受 Provider 输入上限与安全余量约束，这个差值不能普遍等于输出预留。

截图 393.2K 很接近 393,216。需从运行请求的冻结容量和输出预算核实这是实际预算还是模型能力上限；本诊断未读取含密钥的 Provider 配置，也未擅自降低预算。UI 的 health 使用不带默认 1,024 安全缓冲的口径，出站硬预算则含该缓冲，截图有效输入约 606,784 与日志硬上限 605,760 的差值也需显式标注。

## 5. 结论与未验证部分

优先处理同步压缩的位置与生命周期；同步修复用量来源混用、容量故障文案和摘要桶归因。不要优先加长超时、关闭压缩或删除会话历史。

未修改生产代码，未构建部署，未做修复后实测。浏览器绘制延迟、pending 的具体消费路径、完整校准误差来源以及 393.2K 预算的运行配置来源仍待验证。施工与验收见[修复方案](../12_features/首Token等待与上下文指示器修复方案-2026-10-07.md)。
