# 长轮内压缩归因与架构边界

## 已观测事实

来自 trace `d0e4fbb552574d6790e722b56a67f728` 的只读 conversation_events：第 4 轮已成功压缩 86 条消息，请求 525781 → 122688 bytes，144907 → 39463 tokens。第 35 轮请求再次达到 525233 bytes，超过客户端 524288-byte 预算；候选只有 1 条旧 checkpoint，5496 tokens，摘要却为 5407 tokens，整请求只减少 28 tokens。

本次源身份全部解析成功，区别于此前 coveredmessagesnotfound。上传未开始，dispatch_count=0，不能据此归因 DeepSeek 或 TUN。512 KiB 是客户端运行预算，不是服务商声明的限制。

## 根因与职责调整

1. 旧候选算法把最后 User 及之后所有消息视为永久保护区。首次压缩后，长任务仍累积工具记录，候选却退化成反复改写旧摘要。
2. 候选按删除后的请求估算，摘要输出另用固定上限，二者没有共同约束最终请求。只超 945 bytes 也可能无法形成足够净收益。
3. 拒绝提交时清空 AppliedMessages，诊断又从它测量 after bytes，因此丢失真实测量。

纯策略组件统一决定可替换跨度及摘要预算；Runtime 负责完整载荷计量、模型调用和事务；持久层保留准确源行与原始执行记录。最终出站硬门禁仍保留。

## 不变量

- 当前用户输入和 System 不被摘要替换；近期 N 条是偏好，硬压力下近期区受请求预算四分之一约束，边界扩展到完整工具批次，至少保留最新完整单元。未收到所有结果、重复或不匹配 ID 的工具批次是不可跨越的边界。
- 历史完整轮和当前轮已完成执行单元均可压缩。候选使用明确 start/count，不能跨越用户输入或受保护批次；重复正文按冻结位置校验。
- 最终请求预算 = 固定提示/工具/信封 + 保留消息 + checkpoint 包装 + 摘要。token 和序列化文本 bytes 分别计量，二者都须通过；计划额度不是实际 after。
- 新 checkpoint 是 Assistant 背景，不伪造新的 User。不得把整个当前轮标为 covered，也不得预先覆盖尚未持久化的最终回复。
- 严格校验 generation/revision/route/tools 后，原始源归档、摘要、逐行 coverage、manifest、代次推进同事务；成功才替换内存。模型失败、截断、超额、陈旧候选都保留历史。
- 主路径只在硬预算超限时同步压缩；软维护仍可延期。所有摘要只读取选中跨度并分段、单独计费；超额最多从同一完整源重生成一次，不能用部分成功结果覆盖整段源。

## 验证边界

独立策略测试覆盖跨度与预算算术；运行时集成须另验证同一 User 多次压缩、原生工具批次、事务失败、重启水合及真实 after 诊断。脚本化模型只证明机制与数据完整性，不证明真实模型摘要质量。验证结果见同日修改日志。


## Responses 约束核对

[DeepSeek Responses 指南](https://api-docs.deepseek.com/zh-cn/guides/responses_api/)明确接口无状态，不支持 previous_response_id、conversation、context_management 与 truncation。客户端仍须管理可恢复历史与压缩。工具调用/结果必须按 call_id 完整配对。
[创建响应文档](https://api-docs.deepseek.com/zh-cn/api/create-response/)说明 max_output_tokens 包含思考 token；摘要子请求关闭 DeepSeek 思考以使用规划的正文额度，主请求设置独立。未调用付费模型，语义质量仍须真实业务验证。
