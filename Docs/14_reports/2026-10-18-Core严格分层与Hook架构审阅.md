# Pudding Core 严格分层与 Hook 架构审阅

**结论：产品 Core 有清楚的进程边界，也有若干做得较好的独立组件，但内部尚未达到严格分层。Hook 已部分实现并有生产注册；统一的、可阻断和可变换的 Hook 扩展机制尚未落地。当前流式与非流式循环的 Hook 覆盖甚至不一致。**

本次审阅基于 2026-10-18 工作树，起始 HEAD 为 `e96f24ef26ad3a9069f77f919c73f62b70883b8b`。工作树存在他方未提交 WIP，审阅期间仍有变化；本报告针对实际读到的源码，不把其他工作树改动视为已提交或已验收成果。本次只新增报告与日志，不修改业务代码，不启动产品或访问开发 DataRoot。

## 审阅判据与 Core 定义

必须区分两个对象：

- **产品 Core**：`PuddingAgent.exe --desktop-child` 所承载的整个后端进程，包含 Host、Platform、Runtime、MemoryEngine 等。
- **`PuddingCore` 程序集**：命名空间主要是 `PuddingCode`，当前被多个项目当作共享依赖；它并不等于一个已经独立的最小 Agent 内核。

本次严格分层判据是：层级与允许依赖明确，内层不依赖外层实现，跨组件使用所属边界的窄合同，存储与网络细节在适配器中，组合根统一装配，违规依赖能在构建门禁中失败。同层实现互调、业务增强直接写入 Loop、以可选参数绕过唯一执行入口，都不满足该目标。没有循环 ProjectReference 只能证明依赖图无环，不能证明职责隔离。

## 发现与优先级

### F1 流式主路径缺失轮次与工具 Hook

**P1，现存行为差异，应优先修复。** `TurnExecutorAdapter` 第 83 行调用 `DispatchStreamAsync`，`RuntimeAgentDispatcher` 第 84 行进入 `ExecuteStreamAsync`。因此流式路径是当前统一 Turn 入口的实际执行链。

对两个 partial 文件中 `FireHooksAsync` 的调用做静态枚举：Buffered 触发全部 12 种接口方法；Streaming 只触发 `OnLoopStartAsync`、`OnCompletedAsync`、`OnLoopCompleteAsync`、`OnCancelledAsync` 四种。Streaming 第 1587 行执行工具，却没有对应的 `OnToolCallAsync` / `OnToolResultAsync`；每轮也没有 `OnRoundStartAsync` / `OnRoundCompleteAsync`。

后果：同一个已注册增强，仅因入口选择流式或非流式就有不同表现。Logging 的工具/轮次回调在流式路径不会执行；EmbeddingGenerationHook 自己增加终态与取消补充触点来弥补路径差异，不能代替统一合同。`OnLoopCompleteAsync` 注释承诺任意原因收口，但流式实现只在 `terminalStreamStatus is null` 时调用；失败和取消没有统一终态回调。

建议：共享一套 Agent Loop 状态机与工具执行管线，流式只影响输出适配。先添加同一 fake LLM/tool 场景下两种入口的 Hook 顺序、次数、取消与失败一致性测试，再迁移执行逻辑。

证据：[Turn 入口](../../Source/PuddingRuntime/Services/TurnExecutorAdapter.cs)、[Dispatcher](../../Source/PuddingRuntime/Services/RuntimeAgentDispatcher.cs)、[Streaming](../../Source/PuddingRuntime/Services/AgentExecution/AgentExecutionService.Streaming.cs) 第 1587、1941、2071 行、[Buffered](../../Source/PuddingRuntime/Services/AgentExecution/AgentExecutionService.Buffered.cs) 第 616、1103、1462、1649、2375 行。

### F2 现有 Hook 不能治理当前操作

**P1，统一扩展机制的阻断项。** `IAgentLoopHook` 返回 `Task`，没有 Allow/Deny、上下文替换、结果替换或 continuation 合同。其上下文只暴露会话与用户输入等信息，没有正式的待发送消息变换端口。

`AgentExecutionService.FireHooksAsync` 第 1298 行依次 await 回调，捕获所有 Exception 后继续。它没有按 Hook 点声明的失败策略或独立 deadline；永不完成的回调会挂住当前调用，抛出的拒绝或取消异常则被记录后吞掉。即使底层数据对象可变，也不构成受约束、可审计的 Transform 合同。

因此这套接口适合尽力观察，不适合权限 Guard 或请求/结果变换。**这不表示当前工具没有权限保护**：`PuddingToolExecutionService` 第 665 行仍调用 `IAgentFirewall`。问题在于权限与增强尚未进入用户要求的统一 Hook 管线，不能直接把 Firewall 改挂到现有 fail-open 回调上。

建议：在独立合同组件定义 `BeforeModel`、`BeforeTool`、`AfterTool`、`BeforeTurnEnd` 等 typed Hook；明确 Guard/Transform 的结果、顺序、超时、取消和审计语义。安全 Guard 任意 Deny 都应保持拒绝，失败/超时默认拒绝；可选 enrichment 才能显式配置失败后继续。注册应有 owner、唯一 id、scope 和可释放生命周期。

证据：[Loop 合同](../../Source/PuddingRuntime/Services/AgentLoop/IAgentLoopHook.cs) 第 45 行、[调用器](../../Source/PuddingRuntime/Services/AgentExecutionService.cs) 第 1298 行、[现有 Firewall 调用](../../Source/PuddingRuntime/Tools/Platform/PuddingToolRegistry.cs) 第 665 行。

### F3 合同层包含基础设施与另一套 Agent 循环

**P1，严格分层的阻断项。** `PuddingCore` 一方面提供 `ILlmGateway`、`IToolRegistry` 等共享合同，另一方面编译 `OpenAiLlmGateway`、`ResponsesLlmGateway`、`AnthropicMessagesLlmGateway` 的 HTTP 实现，以及 `ShellTool`、`FileTool` 和 `Core/AgentOrchestrator`。

任何为引用合同而引用 PuddingCore 的模块，同时获得具体供应商、工具和另一套循环的编译可见性。旧 `IAgentHook` 只用于该 AgentOrchestrator；在本次检索的 Host/Runtime/Platform/Controller 产品源码中未发现其生产装配调用，不能拿它作为当前产品 Loop 的 Hook 能力证明。

建议：把运行时合同、最小内核、供应商适配、内置工具分成独立程序集；先确认旧循环的消费者，再删除或隔离。只移动 namespace 或分成 partial 文件不能建立编译边界。

证据：[Core 项目](../../Source/PuddingCore/PuddingCore.csproj)、[OpenAI HTTP 实现](../../Source/PuddingCore/Core/OpenAiLlmGateway.cs) 第 19、71 行、[ShellTool](../../Source/PuddingCore/Tools/ShellTool.cs) 第 12 行、[旧循环](../../Source/PuddingCore/Core/AgentOrchestrator.cs) 第 10、271 行。

### F4 Runtime 可以越过记忆服务直接访问数据库

**P1，严格分层的阻断项。** Runtime 直接引用 MemoryEngine。`ContextCompactionService` 持有 `IDbContextFactory<MemoryDbContext>`，`ContextWindowManager` 第 375 行创建该 DbContext 并同步转录、查询 Messages。EmbeddingGenerationHook 也直接操作 `MemoryLibraryDbContext`。

这让循环附近的上下文策略依赖实体、EF Core 和存储布局，存储所有权没有被组件边界封住。Runtime 同时是 Web SDK 项目并定义 HTTP Controller，测试最小循环也会带入网络入口和大量工具依赖。

建议：将转录读取、压缩提交、记忆更新等分别收敛为端口；事务和 DbContext 留在存储实现中。把 HTTP Controller 移入入口适配层。内核测试只使用 fake 模型、工具和转录端口，不加载 EF/Roslyn/ASP.NET Core。

证据：[Runtime csproj](../../Source/PuddingRuntime/PuddingRuntime.csproj) 第 1、32、43 行、[压缩服务](../../Source/PuddingRuntime/Services/ContextCompactionService.cs) 第 38、58 行、[窗口服务](../../Source/PuddingRuntime/Services/ContextWindowManager.cs) 第 375 行、[Embedding Hook](../../Source/PuddingRuntime/Services/EmbeddingGenerationHook.cs) 第 19 行。

### F5 增强功能直接耦合到主循环

**P1，扩展方式不满足要求。** `AgentExecutionService` 的三个 partial 文件合计 7547 行，构造函数有 54 个参数。该类直接持有 SkillEnforcer、MemoryLibraryConvenience、SessionArchiver、工具目录、上下文压缩和多种输出/审计服务，并用 `h is SubconsciousConsolidationHook` 检查具体增强类型。

Buffered 第 641 行注释称 `PreMessageHook`，实际是直接调用 `_skillEnforcer.EnforceAsync` 并修改 history；Streaming 没有这一调用。Streaming 第 1882 行还在主循环末尾直接将终端记录写成记忆经验，之后直接调度上下文维护和会话归档。这些增强增加时需要改动中央循环。

建议：技能加载与记忆召回经注册的 Context Transform/Contributor 接入；工具策略经统一工具管线接入；经验提取、归档、embedding 等提交后工作由事件订阅者负责。主循环仅决定请求模型、执行工具、接受 steering、继续或停止。将流式和非流式统一后再迁移增强，避免复制第三套机制。

证据：[中央类依赖及具体类型判断](../../Source/PuddingRuntime/Services/AgentExecutionService.cs) 第 47、133、213 行、[技能加载](../../Source/PuddingRuntime/Services/AgentExecution/AgentExecutionService.Buffered.cs) 第 641 行、[流式终态增强](../../Source/PuddingRuntime/Services/AgentExecution/AgentExecutionService.Streaming.cs) 第 1882 行。

### F6 生命周期通知到持久作业之间存在丢失窗口

**P1，可靠性缺口。** `IHookPublisher` 实际是生命周期事件发布器：HookPublisher 转发给 InternalEventBus，后者第 88 行起用不等待的 `Task.Run` 调用订阅者。`session.compressed` 的消费者再调用持久队列 EnqueueAsync；只有该调用成功后，作业才有持久性。

因此，在压缩完成后、订阅者成功入队前崩溃，或入队失败时，该链路没有保证重放。ContextCompactionService 的发布异常只记 Warning；EventIngressBridge 还显式跳过带 `hook_event` 的事件，不能指望它自动补齐。这里确认的是代码中的丢失窗口，并非已观测到生产数据丢失。

建议：在业务提交事务中写 outbox，或同事务创建必需的维护意图；由消费者按稳定幂等键投递作业并重试。保留已有 SubconsciousJobs，补齐“事实提交到作业入队”这一段。Task/Goal 已有专用 outbox，不应误认为全仓没有持久事件机制。

证据：[事件总线](../../Source/PuddingRuntime/Services/Events/InternalEventBus.cs) 第 88 行、[发布器](../../Source/PuddingRuntime/Services/Hooks/HookPublisher.cs) 第 40 行、[压缩发布](../../Source/PuddingRuntime/Services/ContextCompactionService.cs) 第 1423 行、[入队消费者](../../Source/PuddingRuntime/Services/Hooks/SessionCompressedMemoryMaintenanceHook.cs) 第 104 行、[跳过普通分发](../../Source/PuddingHost/Services/Events/EventIngressBridge.cs) 第 56 行。

### F7 插件目录和生产注册尚未组成统一扩展宿主

**P2，插件扩展能力不完整。** 内置 Hook 的 DI 注册已经存在：产品 Host 注册 LoggingAgentLoopHook、EmbeddingGenerationHook，旧 SubconsciousConsolidationHook 由显式配置开关注册；压缩订阅者也已注册为 hosted service。

但 `PluginManifestCatalog` 明确只读取描述符，不加载 DLL，状态为 ManifestOnly。不能把安装插件 ZIP 或显示工具目录当作插件代码和 Hook 已激活。生产代码检索没有找到 `IHookDispatcher`、`HookRegistration`、`HookPoint` 的实现。

另一个装配风险是：产品 Host 明确不调用 `AddPuddingRuntime`，存在两份 Runtime 注册清单；本次通过的 RuntimeServiceExtensionsTests 测的是后者，不能证明产品清单一致。例如 Embedding Hook 出现在 Host 注册中，Runtime 扩展入口未作相同注册。

建议：先统一内置模块的声明式注册和组合验证，再决定是否需要动态程序集激活。静态注册也可以实现干净分层，不必以热加载作为前置条件；测试必须覆盖真实产品组合根。

证据：[生产注册](../../Source/PuddingHost/Extensions/PuddingServiceCollectionExtensions.Runtime.cs) 第 316、324、349、375、419 行、[独立注册入口](../../Source/PuddingRuntime/DependencyInjection.cs) 第 98 行、[ManifestOnly](../../Source/PuddingRuntime/Services/Plugins/PluginManifestCatalog.cs) 第 38 行。

| 机制 | 已实现的内容 | 尚不能承担的职责 |
|---|---|---|
| IAgentHook | 旧 AgentOrchestrator 的工具和回复前后通知 | 当前产品统一 Loop 的扩展机制 |

`HookEventNames` 还声明 `AgentLoopCompleted` 与 `SessionCompactionFailed`；本次生产源码检索只找到声明/事件 schema，未找到对应的 HookPublisher 发布调用。常量存在不能等同事件已接线。

已有[参考设计](../19_references/deepseek_harness/deepseek-harness-pi-plugin-hook-event-architecture-2026-08-14.md)的 Typed Hook 合同和渐进迁移方向基本正确；[hooks 配置文档](../06_config/hooks.md)也明确把 IHookPublisher 归类为 lifecycle event publisher。落地状态必须以生产源码为准。

## Pi 对照与推荐边界

Pi 的可取之处是最小循环通过显式接缝接受扩展：`transformContext` 处理模型输入，`beforeToolCall` 返回阻断决定，`afterToolCall` 返回结果覆盖；AgentSession 将这些接缝绑定到 ExtensionRunner。模型调用和工具执行本身仍然是直接的强类型调用。参见 [Pi agent loop](https://github.com/earendil-works/pi/blob/main/packages/agent/src/agent-loop.ts)、[Hook 类型](https://github.com/earendil-works/pi/blob/main/packages/agent/src/types.ts)、[AgentSession](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/src/core/agent-session.ts) 与 [ExtensionRunner](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/src/core/extensions/runner.ts)。这是审阅日读取的 main，不将用户引用文章的行号当作当前版本定位。

**应要求增强通过注册的扩展点进入基础行为，但不宜禁止所有函数调用或构造注入。** DI 应装配合同实现与 Hook 注册；Kernel 调用 `IModelClient` / `IToolExecutor` 等基础端口是正常依赖。跨模块注入具体增强实现、绕过唯一管线，才是需要禁止的行为。

| 建议边界 | 负责 | 禁止 |
|---|---|---|
| Kernel Contracts | Turn/Message/Tool DTO、模型与工具端口、Hook 合同 | EF、HTTP 实现、业务插件类型、Web Controller |
| Agent Kernel | 统一循环、取消与预算、模型和工具调度、Hook 调用点 | Memory/Goal/Skill 的具体实现、数据库、UI 投影 |
| Application 与扩展组件 | 会话用例、技能、记忆、Goal、审批策略 | 相互引用具体实现；修改内核分支才能注册功能 |
| Infrastructure 与入口适配器 | 供应商协议、存储、HTTP/WS、文件与进程能力 | 向内泄露 DbContext/网络协议和容器查找 |
| Composition Root | 按允许依赖清单装配端口、注册扩展，启动前验证 | 夹带业务状态机与隐式可选降级 |

编译依赖统一指向各自需要的内层合同；外层实现通过端口和注册点参与运行，内核不反向引用它们。应为每个程序集设置明确 allowlist，不能用一个包含全部实现的“公共 Core”作为越层通道。

扩展机制也需区分：工具发现用 Registry，立即获取模型/存储结果用端口调用，改变当前操作用同步 Hook，已提交事实的后续工作用 Event/Job。把所有交互塞进无类型事件总线会隐藏依赖，并破坏错误和事务语义。

## 整改顺序与验收门禁

1. **先补主路径行为门禁**：同一场景下 Buffered/Streaming 的 Hook 事件序列一致，成功/失败/取消恰好一次终态。确认当前技能加载差异，再修复接线。
2. **冻结最小内核合同**：定义层级依赖 allowlist；抽出独立 Kernel Contracts 与 Agent Kernel，以 fake 模型、工具、转录端口完成构建和测试。此时不改宿主。
3. **独立实现 typed dispatcher**：测试注册重复、顺序冲突、Guard 拒绝单调性、超时、取消、Transform 边界与作用域释放；通过后再接入统一工具执行入口。
4. **逐项迁出增强与存储细节**：先技能加载和工具策略，再记忆上下文、归档及后台维护；内核删除具体类型判断与可选旁路，保留必要不可绕过的安全检查。
