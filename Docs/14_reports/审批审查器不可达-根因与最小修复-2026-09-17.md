# 审批审查器不可达（P0）— 结构性根因与最小修复方案

日期：2026-09-17 07:45 BJT ｜ 作者：默认助手（default.global_general-assistant.6a8）
状态：**根因定稿（file:line 齐备，非假说）**；修复未实施（涉及安全相关配置语义，待裁定）

## 一、现象

所有需要审批的高风险工具调用全部挂起为 typed 依赖等待 `approval_review_profile_not_configured`：

- `shell`（powershell 分支）
- `file_write` 写仓库外路径（含 Agent 私有目录 `D:\data\agents\**`）
- `request_tool_approval` **自身**

子代理侧同样不可用（`sub-*` 的 tool_failure_summary 多次出现同一符号）。

## 二、根因链（三段，每段有代码证据）

1. **生产注册**：`Reviewer=llm` → `LlmToolApprovalReviewer`
   `Source/PuddingRuntime/Tools/Platform/PuddingToolServiceCollectionExtensions.cs:107-115`
   同时 `Configure<ToolApprovalLlmOptions>(GetSection("ToolApproval:Llm"))`（:89-90）。

2. **严格解析器只有两条路径，其中一条是死代码**
   `Source/PuddingRuntime/Tools/Approval/LlmToolApprovalReviewer.cs:120-195`
   - **路径 A**：`ToolApproval:Llm:ProfileId` 非空 → `_llmConfigService.ResolveProfile(profileId)`
     → 必须命中 `llm.providers.json` 的 `profiles` 映射；失败即返回 null（**无回退**，ADR-091 故意如此）。
   - **路径 B**：**不可达**。它的准入守卫要求 `ProfileId` 非空，
     而它只有在 `ProfileId` **为空**时才被求值：

     ```csharp
     // 仅当上面的 if (!IsNullOrWhiteSpace(options.ProfileId)) 块未返回时到达
     if (string.IsNullOrWhiteSpace(options.ProviderId)
         || string.IsNullOrWhiteSpace(options.ProfileId)   // ← 自相矛盾：此处 ProfileId 必为空
         || string.IsNullOrWhiteSpace(options.ModelId))
     {
         return Task.FromResult<ToolApprovalLlmProfile?>(null);
     }
     ```

   ⇒ 生产环境下**唯一可行路径是 A**（B 被守卫短路，且 `_llmConfigService != null` 时另有短路）。

3. **路径 A 的依赖为空**：`D:\data\config\llm.providers.json:377` 是

   ```json
   "profiles": {},
   ```

   ⇒ `ResolveProfile` 恒返回 null ⇒ **当前不存在任何可满足该解析器的配置**。

## 三、结论（本轮决定性发现）

这不只是"运维忘了配"，而是**解析器的配置面不可满足**：

| 尝试 | 结果 |
|---|---|
| 走 `ProfileId` | 需要 `profiles` 条目；`profiles` 为空，且平台无生成/写入该条目的工具 |
| 走 `ProviderId + ModelId` | 路径 B 是死代码；生产 `_llmConfigService != null` 时被显式短路为 null |

并且**修复动作本身被同一缺陷拦住**：修改 `D:\data\config\llm.providers.json`
需要跨出仓库写入 ⇒ 触发审批 ⇒ 审批不可用（鸡生蛋）。

这正是审批审计员 10 次复核均报"硬阻塞仍冻结"的结构性原因。

## 四、最小修复（两个选项，各 1 处改动）

- **选项 A（配置，不改代码）**：在 `llm.providers.json` 的 `profiles` 下新增一个审查用 profile，
  并在 `Source/PuddingAgent/appsettings.json:104-106` 写 `ToolApproval:Llm:ProfileId`。
  前置：先确认 profiles 的 schema（未完成）。
- **选项 B（代码，1 处守卫）**：路径 B 不应要求 `ProfileId`，改为
  `ProviderId + ModelId` 且 `_llmConfigService.Resolve(providerId, modelId) != null` 即成立
  —— 该 `Resolve(providerId, modelId)` 校验语句**代码里已经存在**，
  说明路径 B 的原始意图本就不依赖 profiles。
  之后 `ToolApproval:Llm:{ "ProviderId":"deepseek", "ModelId":"deepseek-flash" }` 即可生效，
  **纯仓库内配置 + 一次部署，不需要动数据目录**。

倾向 **B**：把"配置面不可满足"变成"可满足"，且不再要求操作者手工生成一个当前无法生成的 profile；
代价是放宽了「生产必须用命名 profile」的严格性 ⇒ **需用户/ADR 裁定**。
