# 插件仓库化（apt 模型）

> 需求原文在「即使插件」处被截断。本文按已读到的四段需求理解：**注册（不加载）→ 检索/枚举 → 安装到上下文（显式卸载前保留）→ 自建插件热加载不重启 Core**。若截断处的补充改变了语义，§2 与 §3 需要相应修订。

## 1. 现状盘点

先说结论：**仓库 + 注册 + 内容寻址已经存在**，缺的是「检索、依赖、持久化安装、安全扫描」四件事。

| 能力 | 现状 | 证据 |
| --- | --- | --- |
| 仓库存储布局 `{id}/{version}/{hash}`、不可变 | **有** | `PluginPackageStore.cs:22` `ImportAsync` 落 `relative = $"{Id}/{Version}/{hash}"` |
| 上传 ZIP 注册（含结构校验） | **有** | 同上；限 64 MiB 上传 / 128 MiB 展开 / 512 文件，禁软链接与越界路径 |
| 内容哈希 | **有** | `HashDirectory`，作为不可变标识参与加载 |
| 枚举 | **部分** | `PluginPackageStore.Scan()`；工具层 `plugin_catalog` 返回包与激活 |
| 按关键字检索（apt search） | **无** | `Scan()` 只有全量列举 |
| 版本目录 | **有** | 每版本一目录 |
| 版本选择策略（latest / 兼容性） | **无** | 加载要求显式 `contentHash`，调用方自己选 |
| 依赖声明 | **无** | `PluginContracts.cs:12` `PluginManifest` 无 dependencies 字段 |
| 依赖解析与冲突检查 | **无** | 同上 |
| 安全扫描（PE 头/签名/危险 API） | **无** | 只有结构校验 `PluginValidation` |
| 从目录或单 DLL 注册 | **无** | `ImportAsync` 只接受 ZIP stream |
| 安装到上下文（可调用） | **有** | `plugin_load`（需 approval + contentHash + operationId） |
| 安装持久化（重启仍在） | **无** | `HostToolMounts` 是进程内存；今晚只让 `host-service` 声明包自动挂载，SDK 插件仍需手工 |
| 卸载 | **有** | `plugin_unload` 走 Draining → Unloaded |
| 从仓库删除（uninstall ≠ unload） | **无** | unload 只撤销激活，不删内容 |
| 自建 → 构建 → 打包 → 导入 → 加载 → 调用 → 卸载，Core 不重启 | **已实测走通** | 2026-11-10 隔离 Core 闭环：产品检查 40/40、定向回归 26/26，Core PID 全程不变 |

## 2. 需要新增的四件事

### 2.1 安装持久化（最影响日常体验）

当前「安装」= 进程内挂载。重启即失，所以每进程都要重来。今晚的自动挂载只覆盖了 `host-service` 声明包，SDK 插件没有覆盖。

方案：新增 `ToolInstallations` 持久层，键为 `(workspace, agent, pluginId)`，值为 `(version, contentHash, scope)`；`PluginManager` 启动时不加载，首次枚举时按记录 rehydrate（与 host-service 自动挂载同一时机、同一抑制语义：显式 unload 写入抑制位，显式 load 清除）。

必须记录 **contentHash 而非仅版本**：仓库是不可变的，hash 才能保证「装的就是当时审过的那个」。

### 2.2 依赖声明与解析

`PluginManifest` 增加：

```jsonc
"dependencies": [ { "id": "pudding.tool.git", "range": ">=1.2 <2.0" } ]
```

解析顺序：拓扑排序（依赖先装），环检测报 `plugin.dependency_cycle`。

冲突判据要明确：同一 `id` 被两个父依赖要求**不相交**的 range → 拒绝并给出两条依赖路径；若相交，取最高满足版本。

不做的事：不引入传递版本回溯求解（SAT）。先做「按拓扑顺序、每 id 取最高满足版本」，失败即报错，不猜。

### 2.3 检索（apt search 等价物）

`Scan()` 之上加索引：按 `id`、`name`、`description`、`requestedCapabilities` 做子串匹配，支持 `--installed` 过滤（只列已安装）。返回项要带 `installed` 与 `active` 两个布尔位，让调用方一眼分清「仓库里有」与「我上下文里有」。

### 2.4 安全扫描与冲突检查

分两级，先做静态级：

- 静态：PE 头合法性、是否强命名/签名、导入表中是否出现进程注入类 API（`CreateRemoteThread`、`WriteProcessMemory`、`SetWindowsHookEx` 等）
- 声明级：`requestedCapabilities` 超出宿主允许集合 → 注册成功但标记 `quarantined`，不可安装

冲突检查包含两项：与已安装插件的能力冲突（两个插件抢同一 workspace 事件订阅）、以及 manifest `SdkApi`/`CoreApi` 与当前宿主不兼容。

## 3. 分阶段建议

| 阶段 | 内容 | 完成判据 |
| --- | --- | --- |
| **P0** | 检索 + 安装持久化 | 重启 Core 后已安装插件自动可用；`plugin_search` 能按关键字列出并区分 installed/active |
| **P1** | 目录/单 DLL 注册；仓库 uninstall | 能给一个目录完成注册；uninstall 后不可再 install，已有激活不受影响 |
| **P2** | 依赖声明 + 拓扑解析 | 缺依赖时安装报 `plugin.dependency_missing` 并给出缺哪个；环报 cycle |
| **P3** | 静态安全扫描 + 隔离位 | 危险 API 的 DLL 注册后被标 quarantined 且 install 被拒 |
| **P4** | 版本选择策略与回滚 | 同 id 多版本共存；可指定版本安装；uninstall 后回退到上一版本 |

P0 的收益最大：它把今晚「每进程重挂」的问题彻底解决（不只是声明包）。P1 次之。P2/P3 是正确性要求，但需要先定冲突语义。

## 4. 需要裁定的问题

1. **安装持久化的作用域**：`(workspace, agent)` 还是 workspace 级共享？（当前挂载作用域是 `(workspace, agent)`，持久层建议保持一致）
2. **是否允许同 id 多版本并存安装**：仓库天然支持（hash 目录），但上下文里两个版本会争同一批工具名
3. **依赖解析失败**：整体回滚，还是装能装的、其余报缺？（倾向后者 + 显式告警）
4. **安全扫描的权威来源**：自研静态检查 vs 复用系统 Defender/签名验证 vs 两者都要
5. **注册是否需要审批**：当前 `plugin_load` 需要批准；注册（仅落盘、不执行）是否也需批准？我的倾向是**不需要**——注册不执行代码，风险在加载那一步

## 4.1 P0 实现前必须定的安全点（2026-11-12 03:45 补充）

安装持久化听起来只是「把记录存盘 + 启动时恢复」，但对 SDK 插件来说它会**绕过一道现有闸门**：

- 今天 `plugin_load` 要求 `approved: true` 才能挂载（`HostToolContributions.Load` 首行就检查），这是人工确认「这段本地代码可以在我这里跑」的时机。
- 若启动时自动 rehydrate，就等于**首次批准永久生效**：以后每次进程重启都会自动拉起 worker 进程，不再有人看一眼。
- 对 `host-service` 声明包没这个问题：它们只是 JSON，进程内不执行代码（这也是为什么昨晚的自动挂载可以不加审批）。

三条可选路线，需要裁定：

1. **区分对待**（我倾向）：`host-service` 自动 rehydrate；SDK 插件只恢复「已安装」状态但不自动挂载，首次使用时仍需一次批准（批准后同一 `contentHash` 在本进程内有效）
2. **信任库**：首次批准的 `contentHash` 写入信任集，以后自动挂载，但仓库内容变了（hash 变）就重新批准
3. **全自动**：装了就跑，不区分类型——最简单，也把审批闸门的价值降到只剩第一次

在路线未定前，P0 后半**不做实现**：它改的是「谁能在我不知情时启动本地代码」，不应由我单方面决定。
