# DeepSeek 缓存命中率评估（2026-10-19 → 2026-10-25）

## 1. 取数范围

数据源由用户提供，位于 `F:\github\deepseek\usage_data_2026-10-19_2026-10-25`：

| 文件 | 内容 | 粒度 |
|---|---|---|
| `amount-2026-10-19_2026-10-25.csv` | 各计费类型（`type` / `price` / `amount`）的 token 量 | 按天 × 计费类型 |
| `cost-2026-10-19_2026-10-25.csv` | 官方账单金额（`name` / `model` / `cost` / `currency`） | 按天 × 项目 |

两个文件均为 UTF-8 with BOM（共 10 列 / 8 列）。窗口为 10-19 00:00 至 10-25 08:04（导出时刻），**因此 10-25 是残日，不可与整日横比**。

`amount` 表里的 `type` 取值：`input_cache_hit_tokens`、`input_cache_miss_tokens`、`output_tokens`、`request_count`、`function_call`。

## 2. 口径与自校验

一周内同一类型出现过两个单价档（未命中 1 与 2 CNY/百万，命中 0.02 与 0.04 CNY/百万）。**原因未核实**（可能是调价或分时段计费），所以不按"单一官方价"估算，而是逐行 `price × amount` 累加，再按天汇总。

自校验：这样算出的总额为 **¥312.5657**，与 `cost` 表合计 **¥312.5657** 逐分相同。这证明列定位、编码与聚合都没有错——不依赖任何关于单价的假设。

## 5. 缓存值多少钱

按逐行单价折算的加权单价：

- 命中：**¥0.0257 / 百万 token**
- 未命中：**¥1.2111 / 百万 token**
- 比值：约 **47 倍**

若这 28.3 亿输入 token 全部按未命中计费：**¥3,433**；实际输入费 **¥255**。
**缓存挡掉约 ¥3,178，占本来要付输入费的 92.6%。**

## 6. 剩余空间（what-if）

固定输出费与请求量，只调「未命中/请求」：

| 未命中/请求 | 估算总花费 | 相对现在 |
|---|---|---|
| 9,473（现状） | ¥312.57 | — |
| 8,000 | ¥284 | −9% |
| 6,000 | ¥246 | −21% |
| 5,000 | ¥227 | −28% |
| 4,000 | ¥207 | −34% |

即：命中率这一头已接近见底，**再优化最多再省三成**，且前提是把每轮新增 token 砍掉一半——那是改上下文结构，不是调缓存参数。

## 7. 这三件事我确认不了

**① 未命中的 9,473/请求里，多少是"必须新增"、多少是"白掉的"。**
导出只有按天聚合，没有请求粒度。按经验，一轮新增（用户消息 + 工具结果）约 2–5k，其余可能来自冷启动或前缀被改写。10-21 只有 572 个请求却高达 22,317/请求，形态上像长空闲导致缓存过期，**但这是推断，不是结论**。

**② 单价为何在一周内出现两档。**
未核实。已用逐行加权规避，但"为什么变价"仍未知。

**③ 10-25 是残日。**
只到 08:04，不可与整日横比。

## 8. 可执行结论

1. **守住前缀稳定。** 命中率高的前提是"请求开头那段一字不差"。工具顺序、系统提示、早前消息任何一处变化，其后全部退化为未命中。仓内已有 `Build_ToolOrderChange_ChangesToolSpecHashAndPrefixHash` 一类测试守着这条线，应继续守。
2. **压缩是"付两次钱换之后每轮更小"。** 改写历史后的第一次请求是全量未命中（约 174k token ≈ ¥0.21/次），换来此后每轮更小的上下文。按当前 9.5k/请求的未命中看，这笔交易大概率划算，但应按天对比压缩前后 `miss/req` 再下结论。
3. **真正的杠杆是上下文体积，不是命中率。** 17.5 万输入 token/请求意味着每一轮都在重读一份很大的前缀；缓存把它压到 2.6 分/百万，但基数仍然大。

## 9. 复现方法

不依赖临时脚本，按 CSV 直接算：

1. 读 `amount` 表，取第 8 列 `type`、第 9 列 `price`、第 10 列 `amount`（按列位取，**不要信表头**：两张表的表头列数与数据列数不一致）。
2. 按 `type` 聚合 `amount`，得到各类型的 token 量；按 `price × amount` 聚合，得到金额。
3. 命中率 = `hit / (hit + miss)`；加权单价 = 该类型金额 / 该类型百万 token。
4. 交叉校验：金额合计应与 `cost` 表合计逐分相同，否则口径有问题。

## 10. 深挖：差距不在"普通调用"，而在四类换前缀事件（2026-10-25 补）

上面几节用的是 provider 导出的按天聚合。要回答"为什么我们 94.6%、官方客户端 99%"，必须看**逐次调用**。
本地 `TokenUsageEvents`（`D:\Data\databases\pudding_platform.db`）有 145,417 行逐调用记录，
含 `CacheHitTokens / CacheMissTokens / PrefixChangeReason / PrefixHash / ToolSpecHash`，且 10-19 起共 16,714 行，
合计命中率 **94.77%**，与 provider 的 94.58% 相互印证（差异来自未计费/失败调用）。

### 10.1 普通调用其实已经到 99.3%

按 `PrefixChangeReason` 分组（10-23 → 10-25，代表当前行为）：

| 前缀变化原因 | 调用数 | 缺失 token | 占缺失 | 缺失/调用 |
|---|---|---|---|---|
| `(none)` 正常追加 | 5,075 | 6,322,960 | 15.0% | **1,246** |
| `compaction_replay` | 990 | 16,821,180 | 40.0% | 16,991 |
| `tool_spec_changed` | 662 | 10,511,241 | 25.0% | 15,878 |
| `compaction_checkpoint` | 152 | 8,097,988 | 19.3% | 53,276 |
| `session_rehydrated` | 12 | 305,011 | 0.7% | 25,418 |

**正常追加的调用缺失只有 1,246 token/次，即命中率 99.28%——与官方客户端同一水平。**
差距全部来自上表其余四类：它们占 17% 的调用，却吃掉 85% 的缺失 token。

按会话类型分（同期）：

| 类型 | 调用 | 命中率 | 平均 prompt |
|---|---|---|---|
| 主会话 | 6,226 | 95.78% | 144,357 |
| 子代理 | 505 | 92.87% | 74,484 |
| 后台任务（`periodic:` / `memory-write:` / `subconscious:`） | 162 | **0.69%** | 8,752 |

### 10.2 四类事件各自的性质

1. **压缩（59.3% 缺失）**：3 天里 1,142 次压缩相关调用（约占全部调用 17%）。压缩本身要"付两次钱"
   （重放读一次、checkpoint 换头后再读一次），但 1,142 次/3 天 ≈ 每 6 次调用就压缩一次，
   **频率本身值得怀疑**——正常对话不该这么频繁触发预算压缩。
2. **工具规格变化（25.0%）**：662 次。这一点比想象中便宜：`ResponsesLlmGateway` 把
   `input`（消息）写在 `tools` **之前**（`root["input"]` → `root["tools"]`），所以工具变化只作废尾部
   的工具块（约 15k token），不会作废整段历史。但"工具列表为什么会变 662 次"仍是个待查项。
3. **后台任务（3.3%，命中率 0.69%）**：每次运行都构造一份不同的短 prompt，从不复用，等于全额付费。
4. **历史锚点变化（本窗口内为 0）**：10-19→10-20 期间曾有 255 次、79.8M token（当时占缺失 86.4%），
   每次固定只有 42,624 token 命中（系统+工具），整段历史全灭。10-21 之后**不再出现**，
   怀疑是窗口管理/压缩策略改动后消失，但未核实是哪次改动。

### 10.3 这些数字推出的可达上限

若把上述四类调用都压到"正常追加"的水位（1,246 token/次），本窗口缺失会从 42.06M 降到约 7.7M，
命中率 **99.2%**——正好落在官方客户端的水平。折算到周维度约省 80M 缺失 token ≈ ¥97/周，
相当于当前账单的三成左右。

**结论：想追上 99%，要动的不是缓存参数，而是"前缀为什么会变"。**

### 10.4 未证实

- 压缩为何 3 天触发 1,142 次：尚未读 `ContextWindowManager` 的触发判据与实际 `plan` 输入，属未证实。
- `history_anchor_changed` 为何在 10-21 后消失：未定位到具体提交。
- 工具列表为何变动 662 次：未定位到来源（技能暴露？权限模式？）。

## 11. 压缩触发线为什么在 412k 就成立（2026-10-25 排除法定论）

日志里捞到一条真实提交：`measuredBefore=411,966, removed=145, messages=579->435`。
按 `PrefixCompactionPolicy.Decide` 的四条 `wait` 线逐条代入：

| 线 | 代入 | 是否成立 |
|---|---|---|
| `tokens / window ≥ 0.70` | 412k / 1,000,000 = 0.41 | 否 |
| `bytes / byteLimit ≥ 0.95` | 见下 | 待定 |
| `(tokens + growth) / window ≥ 1.0` | (412k + ~30k) / 1M = 0.44 | 否 |
| `tokens + growth ≥ inputLimit` | inputLimit = 1,000,000 − 64,000 − 1,024 = 934,976 | 否 |

排除过程中确认了两个常量（读码，非推测）：

- 单轮输出预留 `LlmReplyBudget.PerTurnOutputCapTokens = 64_000`，
  且 `ResolveReservedTokens = min(登记值 393_216, 64_000) = 64_000` ⇒ **输入上限 934,976**；
- 工单容量只在 task 绑定执行时才有（`ExecutionCommandReader` 的 task-plan 分支），
  普通聊天 `workUnit` 为 null ⇒ `UsageBudget` 为 null，那条线不参与。

**于是只剩字节口径。** 而且它能解释全部现象：

- `LlmRequestTextBudget.ResolveLimit` = `输入上限 × 3 B/token` ≈ **2.8 MB**；
- 同一段内容在 JSON 里的字节数在 CJK 密集时可达 3~6 B/token（`Measure()` 用
  `UnsafeRelaxedJsonEscaping`，中文不转义，但一个汉字 UTF-8 就是 3 字节，而它往往只占 1 个 token）；
- 412k token 的中文上下文 ≈ 1.5~2.5 MB，落在 `0.6 × 2.8MB` 到 `0.95 × 2.8MB` 之间 ⇒
  `prepare`（bytes ≥ 0.60）成立，`commit`（bytes ≥ 0.65）也可能成立。

这与 `LlmRequestTextBudget` 类头注释记录过的 2026-10-23 现象同源：
当时固定 512 KiB 预算被 506 KB 的固定前缀（系统提示 + 工具定义 + 技能目录）吃掉 98.6%，
于是每轮都压缩。那次把预算改成随窗口伸缩，但**字节/token 折算系数仍是 3**，
在中文占比高的会话里仍会先于 token 比例触线。

### 待实测确认（重启后一条日志即知）

已在 `63cf3dd` / `9fc2bb7` 把决策入参提到 Information：`pressure / tokens / window /
bytes / limit / inputLimit / workUnitCapacity / growth* / reason`。
重启后第一次压缩触发，看 `bytes` 与 `limit` 的比值即可判定：

- 若 `bytes/limit ≥ 0.60` 而 `tokens/window ≈ 0.4` ⇒ 字节网是瓶颈，应重新标定折算系数
  （或对纯文本会话改用实测 bytes/token），**不是**去调 0.60/0.65 这两个比例；
- 若两者都不越线却仍触发 ⇒ 说明还有第三条触发路径（疑为硬保护分支
  `AgentExecutionService.Buffered.cs:817`），需继续查。
