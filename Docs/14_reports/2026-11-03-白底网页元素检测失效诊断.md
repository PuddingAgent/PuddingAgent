# 白底网页元素检测失效诊断

## 背景

`AnalyzeForProcess` 修复后（提交 `b5d549c`，只在授权窗口内检测），对 ChatGPT 窗口
得到**检出 0 个目标**。这不是过滤错，是检测器在副屏白底界面上确实什么都没找到。

本报告记录四级探针数据，目的是**避免下一轮重复探**，并明确排除几个看起来很像但不对的方向。

## 探针 #1：颜色分布

截整屏（5120×1440），取 ChatGPT 窗口 `(3292,106) 1600×1038` 的颜色直方图（每通道量化 16 级）：

```
(0,0) 整屏左上角   BGR=(243,243,243)      ← 当前实现用作 diff 背景
ChatGPT 窗口众数   BGR=(248,248,248)      占比 89.7%
                    BGR=(248,232,232)      1.5%
                    BGR=(232,232,232)      1.5%
                    BGR=(248,248,232)      1.3%
                    BGR=(24,24,24)         0.7%   ← 深色文字/图标
```

**观察**：整屏左上角本身就是浅色（243），与白底窗口（248）只差 5。

## 探针 #2：换背景色有没有用（假设检验）

`OpenCvElementDetector.Detect` 里写：

```csharp
// 背景色取左上角。整屏截图的左上角是桌面区域，比"窗口内的白色"更稳定。
var background = bgr.At<Vec3b>(0, 0);
```

看起来很像"背景色取错位置导致白底隐形"。**实测否掉了这个假设**：

```
diffThreshold = 30
用 (0,0) 左上角作背景   非背景像素 = 79304 (4.78%)
用窗口众数色作背景       非背景像素 = 81478 (4.91%)
```

两者几乎相同 —— 因为 243 与 248 都远低于阈值 30，无论用哪个作背景，
**白底都会被滤掉，深色文字都会被保留**。

⇒ **改背景色的取法不会解决问题。** 这条要先排除，否则会白改一轮。

## 探针 #3：ROI 单独跑时的轮廓行为

只取 ChatGPT 窗口区域，用众数色作背景跑完整链路：

```
轮廓总数 = 1
唯一轮廓 = (3292,106) 1600x1038  rectangularity=1.00
```

**这是一条关键线索**：`MorphologyEx(Close, 5×3)` 把散落的文字/图标**粘连成一整片**，
`RetrievalModes.External` 只返回最外层轮廓，于是得到一个覆盖全窗口的大框。

## 探针 #4：整屏跑生产的检测器（未经任何过滤）

```
原始检出 = 140 个
  完全在 ChatGPT 窗口内 = 0
  在主屏 (x<2560)       = 129
  其它                  = 11
与 ChatGPT 窗口相交      = 0        ← 一个都没有
```

前 20 个检出的坐标全部在 `x ∈ [378, 1241]`，即主屏的 Pudding 界面。

**结论**：整屏跑时，副屏区域**没有产生任何轮廓**。

## 已排除的假设

| 假设 | 判定 | 依据 |
|---|---|---|
| 背景色取整屏左上角是错的 | **否** | 探针 #2：换众数色后非背景像素 4.78% → 4.91%，无实质差别 |
| 尺寸上限 `width > w*0.95` 把窗口排除了 | **否** | `w=5120`，`0.95w=4864`，1600 宽的窗口远小于它 |
| 截图没抓到副屏内容 | **否** | 探针 #1 在副屏 ROI 内取到 89.7% 的 (248,248,248) |
| 过滤（`IsCenterInside`）把结果吃掉了 | **否** | 探针 #4 显示**原始**检出里就没有窗口内目标 |
| 主屏的大框通过 `SuppressOverlaps` 吞掉了副屏的 | **否** | IoU 需要重叠，两屏不重叠则 IoU=0 |

## 仍未解释的矛盾（下一步的靶子）

| 场景 | 轮廓情况 |
|---|---|
| 只裁 ChatGPT 窗口 ROI 单独跑 | 轮廓总数 = 1（整个窗口一块） |
| 整屏跑同一检测器 | 副屏 0 个轮廓 |

同一个检测器、同一批像素，**只在整屏时副屏消失**。ROI 跑有、整屏跑没有，
这个差异必须解释清楚才能动手改。

候选方向（按优先级，尚未验证）：

1. **`RetrievalModes.External` 在多区域 mask 上的行为**：整屏 mask 里主屏有大量连通区域，
   若副屏那块在层级上被归为某个更大区域的内部，`External` 不会单独返回它。
   验证方法：改用 `RetrievalModes.List` 重跑，比较副屏是否出现。
2. **形态学闭运算核尺寸**：`5×3` 在密集文字区会把整块窗口连成一片，
   在大图上这个"一片"可能与别处连通。
3. **内存/尺寸限制**：`FindContours` 在 5120×1440 上是否有内部截断（未见文档依据，但未排除）。

## 探针 #5：RetrievalModes 对比（本轮最后一探）

怀疑方向 1（`External` 在多区域 mask 上丢掉了副屏）。实测**部分成立，但不足以解释 0**：

```
Canny 后（生产同参数 40/120）副屏窗口区域
  非零像素 = 82,347 (4.96%)        ★ 边缘信号充足，不是 Canny 的问题
闭运算后 = 193,285 (11.64%)

RetrievalModes 对比（同一 mask，整屏）
  mode        总轮廓    副屏窗口内    副屏相交
  External    135       38           40
  List        458       131          133
  Tree        458       131          133
```

`External` 在副屏**确实有 38 个**轮廓，`List` 更多（131）。List 模式下的候选长这样：

```
(3679,498) 1156x166 center=(4257,581)  rect=0.99
(3679,964) 1156x164 center=(4257,1046) rect=0.99
(3679,735) 1156x119 center=(4257,794)  rect=0.99
```

尺寸、矩形度都完全满足生产过滤条件（`>14x10`、面积 `>400`、`rect>=0.30`、
宽度 `1156 < 0.95*5120=4864`、高度 `166 < 0.95*1440=1368`）。

## 矛盾收窄（下一轮的精确靶子）

**同一个 mask、同样的 Canny 参数、同样的闭运算（5×5, iterations=2），
`FindContours` 能给出副屏 38 个轮廓，而生产 `Detect()` 返回的 140 个里副屏是 0 个。**

这说明问题**不在**图像处理阶段，而在 `ExtractRects` 的过滤条件或 `SuppressOverlaps`。
这两处是下一轮唯二需要查的地方：

1. `ExtractRects` 的四道 `continue`（尺寸 / 面积 / 相对整屏的尺寸上限 / 矩形度）
2. `SuppressOverlaps` 的 IoU≥0.45 抑制（按面积降序，若存在跨屏大框可能连带吃掉）

**不要**再去调 `diffThreshold` / Canny 阈值 —— 探针 #2 与 #5 都证明了信号本身是够的。

## 一条方法论备注

本轮先后有两个假设被自己的数据否掉：
① 背景色取整屏左上角是错的（探针 #2 否）
② Canny 在副屏没有信号（探针 #5 否）

两次都是"看起来非常合理"的假设，且都能写出一段自洽的因果解释。
**否掉它们的不是推理，是紧接着补的那一次测量。**
这类假设如果直接进入修改，会得到一个"改完看起来好了一点、但真实原因还在"的结果。

## 探针 #5 是错的（2026-11-03 更正）

上面「探针 #5」写的「`FindContours(External)` → 副屏窗口内 38 个轮廓」**是我的探针写错了**。

错在坐标判断：

```csharp
int cx = win.X + r.X, cy = win.Y + r.Y;   // ← 错
```

`r.X` 已经是从截图原点到该元素的屏幕坐标（整屏截图 `SourceRect=(0,0)`），
再加一次 `win.X = 3292` 等于把所有主屏元素平移了 3292 像素，
于是它们被误判成"落在副屏窗口内"。

**正确结果是：`External` 在副屏窗口内 0 个。** 用 `List` 才是 116（edge）/ 656（diff）。

这个错误让我一度以为矛盾出在 `SuppressOverlaps`，白查了一段。
教训：**探针自己也要有对照**——同一个数字用两种独立算法（加偏移 / 不加偏移）
各算一遍，差 3292 就该立刻警觉。

## 真正的根因（2026-11-03 逐条计数定位）

复刻 `Detect` 全流程并对每道过滤计数：

```
=== edge 通道 ===
  轮廓总数 145   中心在副屏窗口内 0
  mask 最大轮廓 = (0,0) 5120x1440     ← 整个屏幕连成一块
=== diff 通道 ===
  轮廓总数 375   中心在副屏窗口内 1
    → 该候选 (2560,0) 2560x1381 被 size cap 淘汰
```

两件事叠在一起：

1. **`Canny` + 形态学闭运算把整个屏幕连成一个 5120×1440 的连通体**
   （edge mask 非零像素 537,752）。`RetrievalModes.External` 只返回这一个外轮廓，
   副屏所有元素都被裹在它内部 → 窗口内轮廓数 **0**。
2. **尺寸上限按整屏算**（`w*0.95 = 4864`），所以"包住全部内容的外壳"
   永远在限内、永远过不了滤也没意义。

### 修复

`Detect` 增加可选 `focusRect`，两处配合：

```csharp
var mode = focusRect is null ? RetrievalModes.External : RetrievalModes.List;
int capW = focusRect?.Width ?? w;
int capH = focusRect?.Height ?? h;
if (rect.Width > capW * 0.95 || rect.Height > capH * 0.95) continue;
```

实测效果：副屏目标数 **0 → 202**（提交 `af43623`）。

## 第三个根因：窗口选错了（比前两个更关键）

修复检测后又发现 202 个目标里有 **120 个落点不在授权窗口上**。
先按面积占比过滤，发现只去掉 2 个、匹配率几乎不动 ⇒ 大块不是主因。

再查「别处」到底是谁：

```
其它根构成： 120 个全部是 Chrome_WidgetWin_1 "ChatGPT" [pid 81092]
样本：落点(4302,650) 点中窗口 = 0xE51328
```

查 z-order：

```
z#1  0xE51328  (3943,0)   1183x1444    ← 在上面
z#2  0xCF0FCC  (3292,106) 1600x1038    ← 在下面
重叠带采样 (4000,200)/(4200,500)/(4300,650)/(4500,900) 全部返回 0xE51328
```

**`FindBest` 按「平均亮度最高」选中了 0xCF0FCC（mean 248，白底界面更亮），
但它在 z-order 底部、被完全遮挡，任何点击都会被 0xE51328 接走。**

这不是检测问题，是**选了一个点不到的窗口**。

### 修复

`FindBest` 打分增加可点性：在候选窗口中心调 `WindowFromPoint` 求根祖先，
若返回**别的窗口**则分数 ×0.2（返回 null 不惩罚——那可能是合成层）。

实测（提交 `6b2ce47`）：

```
选中窗口 = 0xE51328 (3943,0) 1183x1444
检出目标 = 126
落点归属：★授权 126 · 别处 0 · 无窗口 0  →  匹配率 100.0%
```

## 三个根因的层级关系

| # | 根因 | 表现 | 修好的现象 |
|---|---|---|---|
| 1 | 闭运算粘连 + External 只取外轮廓 | 副屏轮廓数 0 | 检出 0 → 202 |
| 2 | 尺寸上限按整屏 | 外壳永远不被排除 | 同上 |
| 3 | 窗口被遮挡仍被选中 | 落点 60% 落在别的窗口 | 匹配率 40.6% → 100% |

**三者互相掩盖**：修好 1 和 2 才看得见 3；只修 3 的话目标数还是 0，仍然是废的。

## 下一步方案（按代价从低到高）

1. 用 `RetrievalModes.List` 对比 `External`，确认是不是层级语义问题（只改一行，可回滚）
2. 若确认，改用 `List` 并加**相对窗口**的尺寸上限（而非相对整屏），
   同时补一条「白底界面至少检出 N 个目标」的回归测试
3. 若 `List` 产生过多嵌套噪声，再考虑按「与页面底色的相对差」+ 连通域分析的组合策略

**不建议**：继续在 `diffThreshold` / Canny 阈值上调参 —— 探针 #2 已经说明，
在纯白界面上这些阈值不是瓶颈，改它们只是让主屏结果变多变少。

## 新增的回归约束

`CenterInsideWindowTests`（提交 `b5d549c`）锁定了"按进程分析只保留窗口内目标"，
所以即使检测器以后改进，也不会再把同桌面上别的应用的元素混进来。
