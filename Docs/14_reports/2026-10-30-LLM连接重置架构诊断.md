# LLM 连接重置架构诊断

本次为只读诊断与规划。检查源码基线 `5f003ce`，读取本机已有日志；未调用模型、未修改 DataRoot、未重启产品。源码结论不能替代运行中程序集身份核对。设计与施工门禁见[实施规划](../12_features/LLM请求交付可靠性架构与实施规划-2026-10-30.md)。

## 1. 原始事故与复发证据

时间均为北京时间。会话 `206a9b48ec904ebb93e7541131fbb835`，原始 trace `67b3e8d34a564fb7a735eea9c6403a93`，error `llm-d20696be2ad64eeb9b3452dfae63a570`。

| 观察 | 已核对的事实 | 证据位置 |
|---|---|---|
| 原始请求 | Responses 协议，870 条消息、46 个工具，1,838,327 bytes；三个请求体 SHA-256 均为 `3172f05127de97cedc14c74846819cad20abc26d37e20ca065d420b5af43749c` | `<DataRoot>/logs/system/pudding-20261030_048.log` 第 4234、4556、4729 行 |
| 原始结果 | 三次上传 reset，均未收到响应头、未向上交付增量；单次约 63.5 / 22.1 / 35.5 秒，逻辑调用总耗时约 123.2 秒 | 用户诊断导出；同文件第 4991、5053 行 |
| 后续复发 | 21:14 的请求增长至 872 条、2,272,063 bytes；三次 SHA-256 均为 `ea988e33c169e210b22227812605806162452a82fbf89a1d6721fff52b672b62`；第一次分类为 response_read_reset，后两次为 request_upload_reset，总耗时约 214.1 秒 | 同文件第 6191、6241、6258、6383、6444、6569 行；trace `c239650b9acd4c98ba1f4acee8811ca2` |
| 再次复发 | 21:19 的请求为 2,276,832 bytes，仍三次同体重发，21:21:13 失败 | 同文件第 6845 行及 `pudding-20261030_049.log` 第 1、63、177、238、352 行 |
| 历史加载 | 21:08 从持久层读取 100 行，组装/筛选后 76 条；内存 868 条。日志以持久历史较短为由保留内存 | `pudding-20261030_048.log` 第 4202–4208 行 |
| 图片占比 | 原请求 1 张内联图、22,308 bytes；后续 2 张、449,500 bytes | 同文件第 4234、6191 行；`inlineImageWireBytes` |

`request_bytes` 是完整请求体长度，并非实测已上传量。`dispatch_count=1` 是单个 attempt 内的网关派发计数；原始事故共有三次 attempt，不能解释为只发送过一次。后续 `response_read_reset` 是既有分类器结论，尚未补齐每次 HTTP 头与传输事件，不能据此认定三个失败来自同一网络阶段。

## 2. 压缩并非完全没有工作

该会话前一天的压缩现场 `logs/diagnostics/compaction/20261029-b0281cb53a7527a543ff6ebf6a30173cedc9f32b5b7ab5d43eeef9518de0df0c.jsonl` 记载：

- `plan`：sourceGeneration=423；initialTextBytes=3,652,723；initialUsedTokens=576,185；maxRequestTextBytes=5,609,856；effectiveInputLimit=934,976；候选移除 276 条。
- `outcome`：applied=true、durableCheckpoint=true；measuredAfterTextBytes=2,728,099；afterTokens=428,926；messageCount=763；attempts=16。

这证明该会话至少曾成功提交压缩，不证明今天发送的历史一定采用最新 checkpoint；也不证明压缩后的请求能够稳定送达。上述 textBytes 是 Runtime 逻辑投影估算，不是 Responses 最终 UTF-8 报文字节，不能直接和 1,838,327 bytes 作前后收益比较。

## 3. 源码中可确认的结构问题

| 问题 | 当前实现 | 后果与证据边界 |
|---|---|---|
| 上传预算与模型容量耦合 | `LlmRequestTextBudget.ResolveLimit` 使用有效输入窗口 × 6，下限 512 KiB | 这是客户端策略；它没有使用当前链路的成功/失败证据，因此不能代表独立的传输安全边界 |
| 规划与发送不是同一份载荷 | Runtime 重新序列化消息投影计量；Gateway 再转换 Responses input / 原生续传 / 图片并序列化；最后捕获真实 body | 计量差异可见，但尚未形成冻结载荷的准入合同。原事故 localEstimatedTokens=856,824，bodyTokens=558,156，两者都不能冒充该次 provider usage |
| 重试未改变条件 | `DirectLlmClient.ChatStreamAsync` 首增量前对瞬态异常按固定间隔重试；同一个 messages/tools 再交给 Gateway | 原样重试可处理偶发故障，但本次连续三次的报文完全相同，没有降载或有效状态变化 |
| 流式与非流式治理不同 | `DirectLlmClient` 的 `_circuitBreakers` 使用点在 `ChatAsync`；`ChatStreamAsync` 有自己的重试/watchdog，未使用该字典 | 不能说系统完全没有熔断：Runtime 另有会话 fuse；但调用级治理并未统一 |
| 派发与传输阶段混用 | `CreateRequest` 就调用 MarkDispatch；`MarkHeaders` 前均可保持 RequestUpload | 组装完成、真正 SendAsync、写完本地 content、等待响应头缺少独立事实；本次有上传栈指纹，但其他样本可能只有推断 |
| 内部再派发独立发生 | Responses 的 file 引用过期在 Gateway 内重建并再发；外层另有 retry 与 provider 输入上限恢复 | 局部有界不等于一次逻辑请求的总物理发送有统一上限 |
| 历史新鲜度判断不充分 | `ContextWindowManager` 前缀协调失败后，使用消息条数决定保留更长内存 | 76 条也可能只是有限查询/投影，不能直接替换 868 条。缺的是携带代次、覆盖与完整性的协调合同，不能简单删除这个保护 |

## 4. 为什么多轮修补仍没有收口

[10 月 21 日记录](../00_changelog/2026Year/10/2026-10-21-Responses体积保护与分段会话压缩.md)引入 512 KiB 文本预算与分段摘要，并记录合成小请求成功、约 1.45 MB 请求失败；该记录自己也明确实验只能支持体积相关性，不能证明固定服务端上限，原会话验收另待执行。

[10 月 23 日记录](../00_changelog/2026Year/10/2026-10-23-文本上传预算随输入窗口伸缩.md)为解决固定前缀挤占与高频压缩，将预算改为 3 B/token；后续提交 `610f9bb` 改为 6 B/token。这些调整有各自依据，但同时改变了以前承担传输保护作用的门槛。没有贯通“固定前缀大小—实际报文—链路表现—缓存成本—原会话恢复”的共同验收，局部优化就可能彼此抵消。

## 5. 仍不能下的结论

不能仅凭 10054 指定 DeepSeek、代理、TLS 中间设备或本机网络中的责任方；没有 HTTP 413/429 也不能直接断言服务端体积限制或限流。不能从 `platform=1.0.0.0` 确认运行制品包含哪一次修复。

没有读取生产数据库、导出会话正文或检查 secret。本次未完成：运行构建 SHA/MVID 核对；今天的实际 compaction decision、校准比与配置来源闭环；内存/持久 checkpoint 同代性判定；同链路小/大报文对照；HTTP 协议与连接复用的受控实验。因此，网络根因仍待定位，现有请求交付与恢复机制的结构缺口则已有直接证据。

历史日志写过的“部署后不再出现”只代表其当时观察窗口，不作抹除。本报告记录新反例，后续验收需给出范围、样本量、分母及尚未验证项。
