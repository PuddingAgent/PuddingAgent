# 2026-11-24 用量账本在「同 Turn 多次派发同一池条目」时丢账

## 结论

`TokenUsageEvents` 的唯一键是 `UNIQUE (SourceType, SourceId)`，而 `agent_llm` 的
`SourceId` 取值为 `{SessionId}:{TraceId}:{round}`。子代理执行时 `TraceId` 继承自父 Turn，
因此**同一父 Turn 内对同一池条目派发第二次**得到的 `SourceId` 与第一次逐字相同，
第二次的用量事件无法写入。表现为成本与 token 被少记，且派发本身正常返回，无任何告警。

这不是理论推演：两轮独立复现都得到「派发 2 次、账本 1 行」。

## 复现步骤

1. 取池中任一条目（本例 `probe-model`，`model_id=deepseek/deepseek-flash`，会话 `…-sub-31461569`）。
2. 在同一父 Turn 内对它连续 `spawn_sub_agent` 两次，任务文本不同、均只要求回一行。
3. 查 `TokenUsageEvents` 中该子会话的事件数。

## 证据

第一轮（20:36 前后，同一父 Turn `77188d2c17ef4ef3a5f5144718ae3de2` 内派发 3 次）：

```
派发1 12:14:31  SourceId=…-sub-31461569:49bc211d0e9047408efb884d02d88549:1
派发2 12:36:05  SourceId=…-sub-31461569:77188d2c17ef4ef3a5f5144718ae3de2:1  ← 落库
派发3 12:36:46  同父 Turn、同 round ⇒ SourceId 与派发2 相同            ← 无记录
```

第二轮（20:54，父 Turn `2e33b4044883426790c315d12dc237c1` 内派发 2 次，task 分别为
`LEDGER-PROBE-A` / `LEDGER-PROBE-B`，runId 分别为 `run_20261124_125409_68ba70f0a3c4` /
`run_20261124_125414_1917148063ff`，两次都正常返回并各回一行）：

```
ROWS: 1
(202390, 12:54:11, …-sub-31461569:2e33b4044883426790c315d12dc237c1:1, 68375, 67968, 407, 0.994048, 0.00381272)
```

12:54:14 的第二次派发没有对应行。该子会话累计只有 3 行，正好对应 3 个不同父 Turn。

## 机制

- 落库点：`AgentExecutionService.Buffered.cs:1032` 与 `AgentExecutionService.Streaming.cs:1431`，
  两处均为 `sourceId: $"{request.SessionId}:{execTrace.TraceId}:{round + 1}"`。
- 唯一约束：`CREATE UNIQUE INDEX IX_TokenUsageEvents_SourceType_SourceId ON TokenUsageEvents (SourceType, SourceId)`。
- `AgentExecutionService.Compaction.cs:403` 的 warm-prefix 路径**已经**带上 `RunId`
  （`{SessionId}:{RunId}:{round+1}:warm-prefix`），Buffered / Streaming 两条主路径没有。

`TokenUsageRecorder.cs:339` 的冲突兜底在「查得到同 source 但 payload 不同」时应抛
`InvalidOperationException`。但两次复现里调用方均正常返回，说明该路径要么未被触发，
要么被上层按尽力记录吞掉——**这一点尚未定性**，不能据此断言是静默成功还是吞异常。

## 影响面

- 直接命中「一个 Turn 内多次咨询同一持久顾问」这一核心用法：只有第一笔进账。
- 任何按 `agent_llm` 明细做的成本核算、缓存命中率统计、按 run 归因，都会系统性偏低。
- 不含子会话的普通会话不受影响：同一 Turn 内 `round` 递增，`SourceId` 天然不同。

## 修复提案（未实施）

在 Buffered / Streaming 两处把 `RunId` 并入 `SourceId`，与 Compaction 路径保持一致：

```
$"{request.SessionId}:{execTrace.TraceId}:{request.ExecutionIdentity?.RunId ?? "no-run"}:{round + 1}"
```

该形态同时满足两个约束：同一 run 的重试 `SourceId` 不变（保留幂等），不同派发各自不同。

**未实施的原因**：以下两点必须先验证，否则改了也可能无效：

1. `request.ExecutionIdentity?.RunId` 在子代理执行路径上是否非空。若为空，两次派发都退化成
   `no-run`，冲突照旧。Compaction 用 `?? "no-run"` 兜底，说明该字段确实可能缺失。
2. `TokenUsageRebuildService.cs` 是否独立重建 `agent_llm` 的 `SourceId`。若两处公式不一致，
   重建会产生与实时写入不同的键，需要同批修改。

改账号本键格式会影响全体 Agent 的用量归因，须在具备「改后两次派发落两行」这一可取的红的
验证手段之后再动，不宜作为心跳轮次的顺手改动。

## 修复状态（已实施，验收待部署）

前提两条已核实：

1. `SubAgentManager.BuildChildExecutionIdentity`（`SubAgentManager.cs:1675`）中 `RunId = runId`，
   每次派发唯一且非空；同处 `TraceId = parent?.TraceId` 正是冲突来源。
2. `TokenUsageRebuildService` 的 `agent_llm` 事件用 `SourceId = persisted.EventId`，
   与本公式无耦合，无需同批修改。

改动：`AgentExecutionService.Buffered.cs` 与 `AgentExecutionService.Streaming.cs` 的 `sourceId`
各并入 `request.ExecutionIdentity?.RunId ?? "no-run"`，与 `Compaction.cs:403` 已有写法对齐。
`PuddingRuntime` 构建 0 error。

验收判据（尚未执行）：部署后在同一父 Turn 内对同一池条目连派两次，`TokenUsageEvents` 应落两行。
在拿到这条证据之前，本次修复只能算「已编译」，不算「已验证」。

不应混为一谈。
