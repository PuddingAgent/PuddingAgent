# git_log 截断建议必须与「实现能力」和「已用尽的手段」同源

## 1. 缺陷：同一条建议有两处做不到

`BuildNotice` 在截断时给调用方两条出路：`raise max_count` 与 `narrow the query with branch/file_path`。两条都可能指向死路。

### 1.1 上限判据用错了量

```csharp
var clampedAtCeiling = requested > applied;   // 旧判据
```

这个判据只在「请求被削过」时为真。请求恰好 `max_count=100` 时不触发夹取（`requested == applied == 100`），判据为假 ⇒ 走「可以 raise」分支。而 100 就是硬上限，raise 到 200 仍会被夹回 100。

`5a9f611`（第八处）修的是 `max_count=1000` 那个形态，因此这个形态被漏掉了 —— 同一段代码、同一句建议，只覆盖了其中一半。

### 1.2 narrow 建议不看调用方已经给了什么

若调用方已经同时给了 `branch` 和 `file_path`，再劝它「narrow the query with branch/file_path」等于让它换个问题，而不是取完当前问题。

## 2. 证据（2026-11-26 主库运行时实测）

| 入参 | 旧回执 | 问题 |
|---|---|---|
| `max_count=100` | `... raise max_count or narrow the query with branch/file_path` | raise 无效（100 是上限） |
| `max_count=1, branch=master, file_path=<单文件>` | `... raise max_count or narrow the query with branch/file_path` | 两个维度都已指定，narrow 无处可去 |
| `max_count=0` | `max_count=0 was clamped ... raise max_count or narrow ...` | 这一条是**对的**：applied=1，raise 真有效 |

第三条是负向对照：修复不能把「抬到下限时 raise 有效」这个正确建议一并删掉。

## 3. 改法：建议读三个事实

```csharp
var atCeiling = applied >= MaxCountCeiling;          // 看生效值，不看是否被削过
var unused = new List<string>(2);                     // 还没被用尽的收窄维度
if (!branchGiven) unused.Add("branch");
if (!filePathGiven) unused.Add("file_path");
```

四种组合各自的措辞：

| 已在上限 | 还有未用的维度 | 建议 |
|---|---|---|
| 是 | 有 | `narrow the query with <未用维度> (max_count is already at the 100 ceiling)` |
| 是 | 无 | `branch and file_path are already given and max_count is already at the 100 ceiling — this query cannot return older history in one call` |
| 否 | 有 | `raise max_count or narrow the query with <未用维度>` |
| 否 | 无 | `raise max_count` |

最后一格是本轮唯一需要判断的地方：三种手段（raise / 换分支 / 换文件）全部用尽时，唯一诚实的输出是「本次调用取不完」，而不是从两条做不到的建议里随便挑一条。

`queriedBranch is not null` 与 `filePath is not null` 作为「已给」判据 —— 用的是**实际生效**的查询维度，而不是入参原文（`NormalizeFilterPath` 可能把空串规整成 null）。

## 4. 取红：两个变异各红不同用例

```
基线 13/13
M1  applied >= MaxCountCeiling → applied > MaxCountCeiling
    → 红 3：TruncationAtCeiling_DoesNotAdviseRaisingMaxCount（第八处原用例）
            TruncationAtRequestedCeiling_DoesNotAdviseRaisingMaxCount
            TruncationAtCeilingWithAllFiltersGiven_StatesNoRouteRemains
M2  unused 收集忽略 given 标志（无条件加 branch/file_path）
    → 红 2：TruncationWithAllFiltersGiven_DoesNotAdviseNarrowing
            TruncationAtCeilingWithAllFiltersGiven_StatesNoRouteRemains
复原 SHA D8602B1E…E49B70 逐字节相同 → -t:Rebuild 后 13/13
```

| 用例 | M1 | M2 |
|---|---|---|
| `TruncationAtRequestedCeiling_…` | 红 | 绿 |
| `TruncationWithAllFiltersGiven_…` | 绿 | 红 |
| `TruncationAtCeilingWithAllFiltersGiven_…` | 红 | 红 |
| `TruncationAtCeiling_…`（第八处） | 红 | 绿 |
| `TruncationBelowCeiling_…`（正向对照） | 绿 | 绿 |

两个变异各有**独有**红点，说明两条修复各自被守护；共同红的那条是组合守护，如实记录不夸大成「独立双保险」。

## 6. 边界（不声称的部分）

- `code_map.md` 的 `GitLogTool` 行约束列原本 158/160 字符，为写入本轮的判据变化，把末句从 `撞 100 上限时只劝收窄` 压成 `上限看生效值；已给的不劝收窄`（159 字符）。压缩后的措辞比原来的粗，完整判据在源码 `BuildNotice` 的 XML 注释里。
- 未测 `max_count` 为负数（`-5`）的形态：与 `0` 同走 `Math.Clamp` 下界，属同一分支，本轮未单独取红。
- 未验证 `branch` 给空串 `""` 时的「已给」判定：`string.IsNullOrWhiteSpace` 会把它当作未给，因此建议里会出现 `narrow the query with branch` —— 这是**正确**语义（空串确实没有收窄），但没有运行时样本。

## 7. 部署与运行时验收（2026-11-26 21:2x）

组装层：

| 量 | 值 |
|---|---|
| HEAD | `14b7436` @ 21:20:27 |
| live `PuddingAgent.dll` | 21:21:59 |
| 进程 | PID 126396，`StartTime` 21:22:29 |

DLL 晚于提交 1 分 32 秒，进程又晚于 DLL 30 秒。程序集时间只是前置条件，下面是实际调用的回执。

六臂（同一构建、唯一变量是指令参数）：

| 臂 | 入参 | 关键回执 | 判据 |
|---|---|---|---|
| A1 | `max_count=100` | `…narrow the query with branch/file_path (max_count is already at the 100 ceiling)` | 含 ceiling、**不含** `raise max_count` ✓ |
| A2 | `max_count=1` + `branch` + `file_path` | `…— raise max_count` | **不含** `narrow` ✓ |
| A3 | `max_count=100` + `branch` + `file_path` | `count=11`、`truncated=false`、`notice=null` | 该文件只有 11 次提交 ⇒ 天花板未触及，不产出噪声 ✓ |
| A4 | `max_count=-5` | `max_count=-5 was clamped … (applied 1); … — raise max_count or narrow the query with branch/file_path` | 负数与 `0` 同走下界夹取；建议随**生效值**走 ✓ |
| A5 | `branch=""` + `max_count=2` | 回执 `branch="master"`；提示含 `narrow the query with branch/file_path` | 空串被 `IsNullOrWhiteSpace` 视为未给，建议里照旧提供 branch ✓ |
| A6 | `file_path`=单提交文档 + `max_count=-5` | `truncated=false`，`notice` 只含 clamp 句 | 夹取与截断是**两条独立** notice，不互相吞没 ✓ |

A1 与 A2 是第九处修复的两个方向（上限判据、已给维度），A3 是「不该出声时不出声」的正向对照，A4–A6 来自 §6 列出的未覆盖项。

## 8. 由本轮验收结清的未覆盖项

§6 原有两条「未测」，现在都有运行时样本：

- `max_count` 负数（`-5`）：被夹到 1，且 clamp 文案如实报出原值与生效值（A4、A6）。
- `branch=""` 的「已给」判定：空串按未给处理，回执报实际查询的 `master`，建议里仍提供 branch 这个维度（A5）。

新增一条能力边界的如实记录：`BuildNotice` 里「branch 与 file_path 都已给、且 `max_count` 已在天花板 ⇒ `this query cannot return older history in one call`」这一分支，**在本仓运行时不可达** —— 需要 `branch` + `file_path` 同时给出、且该文件在那一支上有超过 100 次提交；本仓最热的单文件是 `GitLogTool.cs`（11 次）。该分支目前只有单测覆盖（`TruncationAtCeilingWithAllFiltersGiven_StatesNoRouteRemains`），不声称有运行时样本。

## 9. 一次被阳性对照否掉的「缺陷」

A4 之前我先用了 `file_path`=某约定文档、`max_count=-5`，拿到 `count=1` 与 `truncated=true`，看着像「1 条全给了却说被截断」的假截断。

`git log --oneline -- <该文件>` 给出该文件实际有 **2** 次提交（`5127550`、`974b906`）⇒ `truncated=true` 正确，被截掉的正是 `974b906`。源码也早已是「多取一条判定」：

```csharp
var probe = query.Take(count + 1).ToList();
var truncated = probe.Count > count;
```

判据：**看到 `truncated=true` 先数被查对象的真实总量，再谈缺陷**。这次没有写进报告当成 bug，是因为先跑了这条阳性对照；省下的不是一次提交，是一次错误的「修复」（改成 `applied >= total` 会引入一次额外的全历史枚举）。
