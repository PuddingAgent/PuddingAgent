# R0-03 能力矩阵 · 现状核对

> 施工计划 §1.1 R0-03（P1 前置）：「capability 明确区分词面、syntax/static binding、vector；
> 建立项目/语言/provider 覆盖矩阵」。本核对只回答「已经有什么、还缺什么」，不含实现。

## 1. 已有：契约是完整的，而且已经防住了三个陷阱

`Source/PuddingCodeIndex/Contracts/Retrieval/LanguageCapability.cs`（137 行）已实现：

```
RetrievalCapabilityFace   TextSearch / SymbolExtraction / SymbolIndexing / RelationGraph / References / DocComments
RetrievalCapabilityLevel  None / Lexical / Semantic
LanguageCapability        {LanguageId, Face, Level, Alternative?, Note?}
ILanguageCapabilityMatrix Resolve(languageId, face) / Describe(languageId)
```

**两点结构性诚实**（这正是门禁要的东西，已经写在类型里而不是写在文档里）：

1. `Supported(..., level)` 拒绝 `Level.None` —— 「声明支持」与「级别为无」在构造期就不可能同时成立。
2. `Unsupported(..., alternative)` **强制**给出替代方案，空字符串直接抛。

⇒ 「静默返回空 / 假装支持」在这套类型下是**不可表示**的。这比事后靠 code review 检查强得多。

## 2. 缺的：一个生产实现都没有


**零生产实现**。契约注释自己也写着「本刀只冻结端口与条目的诚实性，**不实现**具体语言数据（那是 U4-4）」。

⇒ R0-03 的真实工作量不是「设计契约」，而是 **填数据 + 接线 + 覆盖矩阵输出**。

## 3. 门禁原文 ↔ 现状对照

| 门禁原文 | 现状 |
|---|---|
| 「字段名 Semantic 或 UnsupportedIntents 为空不能当向量已接入证据」 | 类型层已防住一半：`Semantic` 只是一个 `Level` 枚举值，本身不构成「已接入」的证明；但**没有任何地方把「已接入」定义为可验证事实**（缺实现） |
| 「缺字段/解析失败不产生不存在结论」 | `Unsupported` 必须给 `Alternative`，方向对；但**没有默认矩阵**，所以现在任何 `Resolve` 都无从谈起 |

## 4. 下一步规格要点（实施前需确定）

1. **矩阵填在哪**：编译期静态表（每种语言 × 每面一行）还是配置文件？
   倾向静态表 —— 能力随代码能力走，不随部署配置走；配置化会让「声明支持」与「实际能跑」脱钩。
2. **项目维度怎么表达**：`ILanguageCapabilityMatrix` 只有 language，没有 project。
   覆盖矩阵要求「项目/语言/provider」，所以要么扩展端口（`Resolve(projectId, languageId, face)`），
   要么在输出层做交叉（项目 → 其包含的语言 → 能力）。后者不动契约，优先。
3. **必须能取红的三条**：
   - 声明 `Semantic` 但索引器实际未产符号 ⇒ 测试必须红（防止「字段名当证据」）
   - 声明 `Unsupported` 却不给替代 ⇒ 构造期已抛（现成）
   - 未知语言 ⇒ `Resolve` 必须返回 `Unsupported` + 替代，不能返回 `Supported(None)`
4. **不做什么**：不在本轮接 vector；矩阵只声明**当前真实**能力；`Semantic` 只能由 C#（Roslyn）那条链路声明。

## 5. 结论

R0-03 的契约层已完成且质量高（两条不变量写在构造期）。剩下的是一条**纯实现 + 数据**的活，
不涉及协议变更、不涉及部署（`PuddingCodeIndex` 是组件，工具侧接线才需要部署）。

在动手前需要确认第 4 节第 2 条：项目维度走「输出层交叉」还是「扩展端口」。
