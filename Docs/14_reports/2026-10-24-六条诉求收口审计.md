## ① 压缩触发太频繁 —— 已修

**根因**：有效窗口按「模型最大输出」预留，而实际每轮输出远小于此。
`effectiveWindowTokens = contextWindowTokens − requestedOutputBudgetTokens − safetyBufferTokens`，
其中 `requestedOutputBudgetTokens` 曾取到 393,216（模型上限）而非本轮真实预算。

**修复**：`2634d15`（窗口预留改取本轮输出预算）、`eaefef0`（health reserve 按每轮输出预算封顶）。

**实测（2026-10-23 21:37 重启后原始返回）**：

| 字段 | 修复前 | 修复后 |
|---|---|---|
| `effectiveWindowTokens` | 605,760 | **934,976**（+54.4%） |
| `requestedOutputBudgetTokens` | 393,216 | **64,000** |
| `safetyBufferTokens` | — | 1,024 |
| `gateRatio` | 0.619 | **0.07199** |
| `state` | `warning` | **`Healthy`** |

恒等式自检：`1,000,000 − 64,000 − 1,024 = 934,976` ✅

## ② 压缩后空间小又立即触发 —— 已修

**根因**：校准系数只增不减。一次 provider「输入超限」失败把它抬到 1.6 后，即便之后每轮实测都只有原始估算的 0.62 倍，系数也永远停在 1.6 ⇒ `usedTokens` 被永久放大 1.6 倍、有效窗口却没变 ⇒ 压缩被提前触发。

**修复**：`fa8c17c` 引入回落规则 —— 实测更高立即抬高（防超窗）；实测更低则逐轮按 `CalibrationRelaxFactor = 0.7` 回落，**永不低于 1.0**（低于 1.0 会让请求超出 provider 输入上限）。

**实测**：估算/实测倍数 **1.615 → 1.187**，仍在收敛。

**回归守护**：`2526507` 补 `ContextUsageCalibrationRelaxationTests`（5 例）。变异（系数改 1.0，退回只增不减）⇒ 3/5 取红；复原逐位相同（SHA `410F7F97`）。
**注意**：`LlmOptions.GetPromptCalibrationRatio` / `RecordProviderInputLimitFailure` **本来就有测试**（`RequestAttributionIdentityTests`、`LlmInputBudgetRegressionTests:161`、`ContextCompactionServiceTests:315`）——早前「零覆盖」的说法是搜错工程导致的误判，已在 `Docs/14_reports/2026-10-23-上下文用量面板口径诊断与优化方案.md` §13 勘误。

## ③ 每次工具调用省 token —— 本就有机制，且更细

**机制**：`Source/PuddingRuntime/Services/AgentExecution/ToolResultContextPolicy.cs`

| 档 | 字符/字节上限 | 头尾比例 | 适用 |
|---|---|---|---|
| 默认 | `MaxInlineChars = 8*1024` | `DefaultHeadRatio = 0.75`（3:1） | 一般工具 |
| **终端** | `TerminalInlineChars = 2*1024` | `TerminalHeadRatio = 0.25`（**1:4**） | `shell` / `terminal_start` / `terminal_wait` / `terminal_read` / `terminal_execute` |

终端档比例反直觉但正确，注释里写了实测依据（`temp/tool-noise-profile.md`：真实 shell 结果行数中位 = 1，3:1 会先丢掉末尾报错）：**报错与结论几乎总在末尾**。

**超限处理不是硬切**：完整内容写 `.pudding/context-tool-results/` + `.artifact.json`（含 sha256、原始字符/字节/行数），模型收到有界 head/tail 预览 + `file_read` 续读指针。

**失败时仍然有界**：spill 失败走 `BuildUnmaterializedBound` 并带 `context_materialization_failed` 机器可读码 —— 注释明确写了「返回原始载荷（旧行为）会在 spill 基础设施坏掉时**恰好**放开这个界限，而那正是这个界限存在的理由」。这是对的工程判断。

**对比行业**：Hermes 是单一 75/25 分档；本实现**按工具类型分档**，粒度更细。

⇒ **此处没有需要新增的东西**。真正占 token 的是**历史累积**，那属于 ①② 的范畴。

## ④ 检索优化 —— 本就有机制

**`search_grep`**（`Source/PuddingRuntime/Tools/BuiltIns/Search/SearchGrepTool.cs`）：

- `MaxInlineResults = 100`，超出即**释放到临时文件**并提示 `file_read` + `OffsetLines` 分页读（`PaginationReportMessage`）
- `DefaultMaxTotalBytes = 16*1024` 超限走「请缩小范围」硬提示（`TotalCapMessage`）
- 覆盖声明是**强制**的：非完整结果必带 `(coverage: partial — scanned X/Y files …; complete=false; limit_reason=…)`，空输出**不得**伪装成"查无结果"
- 枚举上限 / 扫描预算 / 读取失败 / 大文件跳过 各有独立提示文案

**索引侧**：`CodeSymbolSearch` 走 Lucene trigram（146.3 MB），实测 54–188× 快于扫描。

⇒ **机制齐全**。真正的问题是**多轮**（今晚实测多次 `coverage: partial` 导致反复缩小范围），这属于「检索引擎语义」，不是预算问题；要改需先有可复现的多轮样本。

## ⑤ 低效/无效调用 —— 已修

**`http_fetch`**：失败率 51.7%（14/29，≈420 万 token 白烧）。根因**不是** flaky、也**不是** UA：
- `docs.claude.com` 200×4（瞬时 403）
- `github.com` SSL 3/3、`api.github.com` SSL ⇒ **本机代理阻断特定 IP 段**
- `raw.githubusercontent.com` 200、DNS 正常（`github.com`→20.205.243.166）

修复 `ea8338b`：`HttpFetchFailureClassifier` 把状态码/异常链映射成「分类 + 是否可重试 + 下一步」，替代裸 `ex.Message`。
验证：HttpFetch 21/21；变异（403 的 `Retryable:false→true`）取红、复原 SHA 逐位相同。

**`deepseek_fetch`**（`e31b04b`）：62.5%（5/8），3 次失败全是上游 404（消息本身已可操作，未动）。缺陷在**传输异常路径**：裸抛 Flurl 的 `see inner exception` 占位符，真实原因被埋且不告知能否重试。
修复复用同一分类器，但 **hint 本地重写** —— 分类器默认建议「改用 deepseek_fetch」，在该工具内会**自指矛盾**。
验证：DeepSeekFetch 10/10；变异（退回裸消息）取红、复原 SHA `4B06A4AD`。
