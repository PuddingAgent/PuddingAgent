# 上下文用量面板：口径诊断与优化方案

- 日期：2026-10-23
- 触发：用户反馈后台对话界面「上下文用量」面板数字看不准，附截图（采样时间 2026/10/23 19:38:38）
- 结论：**不是显示 bug，是预算模型漏改了一半**；面板口径混用是第二层问题
- 状态：诊断完成，待实施（后端改动需重启宿主才生效）

## 1. 用户看到的现象

| 「有效输入压力」 | **≈61.9%** | 375.1K（**估算**） | 605.8K |

| 「预留输出 + 安全余量」 | **39.4%** | 394.2K | 1000.0K |

但这一整行推导式本就不该出现在用户界面上（见 §4）。

## 2. 根因（后端）：预留输出取了模型理论最大值

`Source/PuddingRuntime/Services/ContextHealthEvaluator.cs` L31-39：

```csharp
var reservedOutput = Math.Max(0, maxOutputTokens);          // ← 直接当成预留
var contextDerivedInputLimit = Math.Max(1, modelWindow - reservedOutput - safetyBuffer);
var effectiveWindow = Math.Max(1, Math.Min(contextDerivedInputLimit, providerInputLimit));
```

代入资源池登记值（`list_llm_providers` 实测）：

| 项 | 值 |
|---|---|
| `deepseek/deepseek-flash` `maxContextTokens` | 1,000,000 |
| `deepseek/deepseek-flash` `maxOutputTokens` | **393,216** |

于是：

```
reservedOutput = 393,216
safetyBuffer   =   1,024
effectiveWindow = 1,000,000 − 393,216 − 1,024 = 605,760   ← 正是面板上的 605.8K
394,240 / 1,000,000 = 39.4%                                ← 正是面板上的 39.4%
```

**即：系统把「模型一次最多能输出多少」当成了「本轮必须给输出留多少」，白锁 39.4% 的上下文。**

### 2.1 修复其实已经写好了，只是漏接了窗口预留这一侧

`Source/PuddingRuntime/Services/LlmReplyBudget.cs` 已存在，注释直接点名这个问题：

> 2026-10-23：资源池登记的是「模型最大输出能力」（deepseek-flash = 393,216），此前直接把它当成预留全额扣减
> ⇒ 1,000,000 窗口只剩 605,760 可用输入，39% 被锁在输出侧白等

其口径：`PerTurnOutputCapTokens = 64_000`，`ResolveReservedTokens(393_216) = 64_000`。

### 2.2 影响面

- 有效输入窗口被压到 **60.6%**（605,760 / 1,000,000）
- 自动压缩门禁按 `effectiveWindow` 判定（`ContextHealthEvaluator` L57），所以**压缩触发点比设计意图早了 35%**
- 每轮可用输入少 **328,192 token**，等于用户更早被压缩、更快丢历史

### 2.3 附带观察（不是本次要改的）

`ContextHealthEvaluator` L54 与 L57 刻意用了两个分母：

- `usageRatio = usedTokens / modelWindow` —— 对外展示，与用户认知一致
- `gateRatio = usedTokens / effectiveWindow` —— 内部压缩门禁

这是**有意设计**，不是 bug。面板同时展示两个百分比本身合理，问题是没把「哪个是给我看的、哪个是内部阈值」说清楚。

## 3. 根因（前端）：四个分母平铺 + 主指标用估算值

`Source/PuddingPlatformAdmin/src/pages/chat/components/ContextUsageRing.tsx`：

1. **主指标用估算值**：大号数字取 `tUsed`（本地字典估算 375.1K），而 Provider 实测 `measuredPromptTokens`（232.3K）只作为明细行出现（L~470 附近）。
   估算高估 61%，用户看到的「已用 37.5%」实际约 23%。
2. **四个分母平铺**：1000K（占用/预留/余量）、605.8K（有效压力）、605.8K（底部剩余）混在同一面板，且「可用余量 23.1%」与「剩余 230.6/605.8」对不上（前者分母 1000K，后者分母 605.8K）。
3. **推导式当信息**：`394.2K（1000.0K − 605.8K）` 是把减法过程写给用户看，且出现 `Esc` 异常字形。
4. **结论缺失**：`压缩状态待确认` 没有给出「会不会被压缩 / 什么时候」。

## 4. 优化方案

### P0（后端，改 2 行，收益最大）

把窗口预留接上已有的 `LlmReplyBudget`：

```csharp
// AgentExecutionService.Buffered.cs:2357 / AgentExecutionService.Streaming.cs:1958
- maxOutputTokens: effectiveLlmConfig?.MaxOutputTokens,
+ maxOutputTokens: LlmReplyBudget.ResolveReservedTokens(effectiveLlmConfig?.MaxOutputTokens),
```

- `reservedOutput`: 393,216 → **64,000**
- `effectiveWindow`: 605,760 → **933,952**（+54%）
- 压缩门禁按设计意图回归；`providerInputLimit` 仍是硬约束（L39 取 `min`），不会超窗

⚠️ 需重启宿主才生效（`bootstrap_reboot`，破坏性）。

### P1（前端，口径统一）

1. **主指标换成「还能用多少」**：回答用户真正的问题，而不是让他自己做减法
   - 主数字：`剩余 62%`（= `remaining / effectiveWindow`）
   - 副标题：`剩余 373K / 有效窗口 934K`
2. **单一分母**：面板内所有百分比一律用 `effectiveWindow`；模型总窗口只在首次出现时说明一次
3. **实测优先**：`measuredPromptTokens` 存在时，用它作为「已用」；估算值降级为「下一轮预计」并标注偏差
4. **删除推导式**：去掉 `（1000.0K − 605.8K）`
5. **补结论行**：`再约 N 轮触发压缩`（按最近几轮平均增量估算）或明确「暂不压缩」

### P2（可选）

- 面板加一行「本窗口预留输出 64K（单轮上限）」——把预留讲清楚，而不是让用户猜
- `压缩状态待确认` → 后端给出明确状态枚举 + 原因

## 8. 子代理审计补充与**自我修正**（2026-10-23 19:46）

子代理完成只读取证（完整报告 `temp/ctx-usage-audit.md`，444 行），以下三条**纠正本文档前面的表述**，另补充两个本文档漏掉的 bug。

### 8.1 修正一：`Esc` 是截图误读，源码无此缺陷

`ContextUsageRing.tsx` L395-404 之间只有 `formatTokens(inputUnavailableTokens)` + **字面量 `−`（U+2212）** + 空格 + `formatTokens(tLimit)` + `formatTokens(tEffective)`；**全文件不存在 `Esc`**。
真实串就是 `394.2K（1000.0K − 605.8K）`。

⇒ 我 §1 写的「疑为字体回退或减号字形问题」可以收口为：**源码层无缺陷，`Esc` 是 `− 605` 的截图/OCR 误读**。
（仍保留一句：不排除某些字体下 U+2212 字形偏窄导致误读，但那不是代码问题。）

### 8.2 修正二：`可用余量 23.1%` 与底部「剩余 230.6k/605.8k」**不是数字打架**

- 「可用余量」分子 = `tEffective − tUsed` ≈ 230.6K，分母 = `tLimit` = 1000K ⇒ 23.1%
- 底部「剩余」分子 = `remainingTokens` = `effectiveWindow − used` ≈ 230.6K，分母 = `effectiveLimit` = 605.8K ⇒ 38.1%

**分子是同一个数，只是分母不同。** 我 §1 写「对不上」不准确。
**真正的问题是**：那一行**不标分母**，而 `37.5 + 39.4 + 23.1 = 100` 又恰好闭环，于是强化了「分母都是 1000K」的心智模型 —— 用户没法自己发现那是两个分母。

### 8.3 修正三：我最初摸的两个后端文件不在链路上

`ContextBudgetAllocator.cs`（`ReservedForReply = 4096`）与 `ContextBudgetManager.cs`（`MaxPromptTokens = 24000`）**都不在这条链路上**，只是名字像。
真实链路：`ContextCompactionService.cs:140` 传 `capacity.MaxOutputTokens ?? 2048` → `ContextHealthEvaluator.cs:31`。
配置源头也已核实：`D:\Data\config\llm.providers.json:181`（`maxContextTokens=1000000`）、`:183`（`maxOutputTokens=393216`）。

### 8.4 本文档漏掉的 bug A：校准系数**单向**，估算高估后永不回落

`LlmOptions.cs` L694 / L698 / L793 / L796-800：

```csharp
ratio = Math.Max(1.0, …);        // 下限锁死 1.0
ratio = Math.Max(current, …);    // 只增不减
used  = ceil(raw × ratio);
```

⇒ 一旦某次估算把 `ratio` 抬上去，之后**只能放大不能缩小**。
这就是「估算 375.1K vs 实测 232.3K（1.615 倍）」在架构上**不可自愈**的原因 —— 不是数据陈旧，是算法单调。

### 8.5 本文档漏掉的 bug B：「上下文服务 需注意」是**假警报**

`gateRatio = usedTokens / effectiveWindow`（`ContextHealthEvaluator.cs:57`）
→ `WarningRatio = 0.60`（`ContextCompactionContracts.cs:23`）
→ `serviceStatus.ts:104-105` → `ComposerStatusDetails.tsx:105` 显示「需注意」。

用**被高估的** `used` 算 `61.9%` > 60% ⇒ 触发 Warning。
换成 **Provider 实测** 232.3K：`232.3 / 605.8 = 38.4%` ⇒ 应为 **Healthy**。

⇒ 用户看到的「需注意」不是容量真的紧张，是估算污染了状态位。
**这是把「算错」升级成了「报警」，比单纯显示不准更严重。**

### 9.3 ⑤ 的修复（P0，有实测）

**证据**（`agent_diagnostics tool_stats`，500 次样本）：

| 工具 | 调用 | 成功率 |
|---|---|---|
| `file_read` | 154 | 100% |
| `search_grep` | 152 | 96.1% |
| `shell` | 69 | 92.8% |
| **`http_fetch`** | **29** | **51.7%** |
| **`deepseek_fetch`** | **4** | **25%** |
| `github_search` | 1 | 0% |

**代价**：14 次失败 × 每次整套上下文（当前 30–40 万 input）≈ **420 万 token 白烧**，未计重试。
（本会话实测失败源：GitHub SSL 握手失败、`developers.openai.com` 403、`medium.com` 403、`kenhuangus.substack.com` 404。）

**修复方向**（按代价从低到高）

1. **失败分类 + 同类不重试**：把 `SSL 失败 / 403 / 404` 记为「域名级不可达」，同一 Turn 内对该域名的后续调用直接短路，不再发请求。
2. **调用前探活**：对同一域名先发一次 HEAD 或小请求，失败则不进入大上下文抓取。
3. **失败结果不重复入上下文**：失败信息压缩成一行（`FETCH_FAILED domain=X reason=SSL`），而不是把整段错误 + 重试过程留在历史里。
4. **域名白名单**：把已知可抓的域名（`raw.githubusercontent.com`、`cefboud.com`、`deepinfra.com` 实测可用）与已知失败的域名分开记录，复用。

### 9.4 ③ 的测量方法（P1）

不要直接改，先建基线。可用信号：

- `agent_diagnostics token_breakdown` —— 看 input 里「工具定义 / 历史 / 工具结果」的占比
- 本会话已有观察：`http_fetch` 与 `shell` 的输出常达数千字符，且**同一文件被反复读取**（`file_read` 154 次）

**候选措施**（按收益/风险排序）

1. **同一 Turn 内相同参数的工具结果去重**（同一文件读两次只保留一次）
2. **工具输出分级**：默认只回前 N 行 + 总行数，模型需要时再按行号展开
3. **shell 输出落文件 + 只回摘要**（现已有此纪律，但未强制）

### 9.5 ④ 的测量方法（P1）

已有资产：`CodeSymbolSearch` trigram 索引（146.3 MB，实测 54–188× 快于全表扫）。
缺的是**检索结果的 token 预算**与**多轮检索合并**：
- 一次检索只回「命中文件 + 符号名 + 行号」，不回源码正文
- 需要正文时再按 (file, line-range) 精确取，避免整文件读入
- 多轮检索合并成一次（同一 Turn 内相同 query 去重）
