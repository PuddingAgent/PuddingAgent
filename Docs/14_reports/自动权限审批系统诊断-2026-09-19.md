# 自动权限审批系统诊断报告

- 诊断时间：2026-09-19
- 触发：用户指出「`/authorize` 是错误做法；自动权限审批是**隐式**的，无需单独申请，YOLO 模式下系统应自动审批 Shell 指令」
- 结论：**用户的设计意图正确，实现链存在断点**。已定位根因并现场自愈。

---

## 0. 一句话结论

**当前 Core 进程的 `RuntimeExecutionMode` 是 `Normal`，不是 `Yolo`。**
YOLO 是**进程内内存状态**，其恢复**唯一**依赖仓库根的 `yolo.signal` 文件；
而该文件当时**不存在**，且 `checkpoint.json` 中**没有 `auto_yolo` 字段**，
导致普通重启后 YOLO 必然丢失 ⇒ `AgentFirewall` Gate 4 对每次高风险调用都强制走审批票据链。

**已自愈**：写入 `yolo.signal`，文件已被 `YoloSignalService` 消费删除（删除发生在 `SetMode` 之后，代码顺序构成证据）。

## 1. 证据链（逐环可复查）

### 1.1 审批入口：AgentFirewall Gate 4

`Source/PuddingRuntime/Services/AgentFirewall.cs:171`
```csharp
private async Task<FirewallDecision> EvaluateAuthorizationGateAsync(...)
{
    // YOLO mode skips authorization checks
    if (ctx.RuntimeMode == RuntimeExecutionMode.Yolo)
        return FirewallDecision.Allow();
    ...
    var authorization = await _authzSvc.CheckAsync(authzCtx, descriptor, ct);
    if (authorization.IsAuthorized) return FirewallDecision.Allow();

    // Not explicitly authorized — try implicit approval
    if (_approvalSvc is not null)
    {
        var approval = await _approvalSvc.CheckAsync(new ToolApprovalExecutionRequest {...}, descriptor, ct);
        ...
    }
}
```
⇒ YOLO 在此**直接放行**；非 YOLO 则回退到票据/隐式审批链。

### 1.2 `terminal_start` 必然命中 Gate 4

`Source/PuddingRuntime/Tools/Platform/ToolPermissionPolicyService.cs:72-76`
```csharp
public bool RequiresRuntimeAuthorization(ToolDescriptor descriptor)
    => descriptor.PermissionLevel == ToolPermissionLevel.High
       || descriptor.Safety.HasFlag(ToolSafetyFlags.RequiresShell)
       || descriptor.Safety.HasFlag(ToolSafetyFlags.RequiresFileWrite)
       || descriptor.Safety.HasFlag(ToolSafetyFlags.Destructive);
```
⇒ `terminal_start`（Shell）命中 ⇒ Gate 4 必须放行或拒绝。

### 1.3 `ctx.RuntimeMode` 的来源正确，但值不对

`Source/PuddingRuntime/Tools/Platform/PuddingToolRegistry.cs:633-639`

var firewallCtx = FirewallContext.FromExecutionContext(

⇒ 传递链**正确**，问题在于 `_runtimeControl.Mode` 本身是 `Normal`。

### 1.5 审批链的实际行为（工单实证）

`list_tool_approvals` 显示两类终态：

| 时间 | 状态 | `decisionReason` |
|---|---|---|
| 2026-09-16T12:14 / 14:17 / 21:56 | `deferred_dependency` | **`No approval review model profile is configured (ToolApproval:Llm).`** |
| 2026-09-19T02:18~02:27 | `denied` / `pending` | 详细的 LLM 审查理由（「steps incomplete」「placeholder command」「targets not enumerated」） |

⇒ 两种模式**都让自动化失败**：
- 审查模型未配置 ⇒ **依赖等待**（所有高风险调用直接挂起）
- 审查模型已配置 ⇒ LLM 逐条审查 ⇒ 自动化脚本**几乎必被拒**（因为脚本天然没有"逐步 expectedEffect/stopCondition/rollback"）

⇒ **⇒ 自动化（含子代理）在 `Normal` 模式下不可能可靠工作**，这与用户"隐式自动审批"的设计预期**直接冲突**。

## 4. 环境方法论副作用（附记）

- **`git grep` 只搜索「已跟踪」文件**：对 `temp/`（gitignored）执行 `git grep -c "" temp/x.txt` 会 exit=1 且无输出。统计 temp 文件行数请用 `find /c /v ""`。本次诊断因此误判过一次。
- **cmd 无 `head`/`tail`/`grep`**；`findstr` 可用（`/n` 行号、`/c:` 字面量、`/s` 递归）。
- 用 `&` 串联 cmd 命令（不用 `&&`），否则前一条失败会短路后续诊断步骤（本次因此丢失过一轮证据）。
