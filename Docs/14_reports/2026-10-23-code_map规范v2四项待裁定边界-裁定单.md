## R1 · 清单型 F 阈值：「3 个以上」还是「≥3」

**现状（三处口径）**

| 位置 | 原文/取值 |
|---|---|
| 规范 §2 · `用途`（F）列备注 | 「**不是清单**（不得罗列 **3 个以上**并列动作）」 |
| 规范 §6 · 反模式表 | 「`用途` 单元格内 `、`/`,` 分隔的并列短语 **≥3** 个」 |
| 检查器 | `LIMITS["LIST_MIN_ITEMS"] = 3`，判定 `len(items) >= 3`（`code_map_check.py:717`） |

**实测证据**：33 条命中里 **14 条恰好 3 项**（占 42%）。两种口径的差别不是文字游戏，是「14 条算不算违规」。

**两种口径**

- **口径 A（现状 + 改文案）**：`≥3` 命中。把 §2 的「3 个以上」改写为「**≥3 个（含 3）**」，规范与检查器即刻自洽，**检查器零改动**。
- **口径 B（改常量）**：把「以上」按「严格大于」读 ⇒ `LIST_MIN_ITEMS = 4`，命中 33 → 19，释放 14 条。属 §8 的规范变更，需实测分布（已具备）与信息损失评估。

**影响面**：F 列硬上限仅 80 字符。3 个并列短语塞进 80 字符，已足以把「一条职责命题」挤成罗列 —— 这正是 §2 想禁的形态。

**建议：A**。改动 = 规范 §2 一句文案，检查器 0 行。

**裁定：** ☐ A ☐ B

## R2 · §6 中文词表：是否改按「意图」判定

**现状**：`prose_only()` 只剥离行内代码跨度与 Markdown 链接目标；**中文词仍按裸子串匹配**。规范 §6 检查器口径自己也写着「中文词的领域用法（`执行计划`、`本次运行`、架构断言里的 `单一真源`）**照旧命中** —— 是否改按意图判定属未裁定事项」。

**实测证据（决定性）**：路线图 26 条里 **25 条是同一个词 `计划`**。逐条读上下文后：

| 形态 | 条数 | 例 |
|---|---|---|
| 「计划 §N」= 设计文档**章节引用**（导航，合法） | 12 | `> **Core 侧能力 Broker**（计划 §3/§5）：…` |
| 领域名词（`截图计划` / `执行计划合同` / `记忆维护计划模型` / `压缩计划` / `传输计划` / `计划/账本`） | 13 | `ScreenshotPlan.cs`：按截图计划生成实际格式… |
| 真正的路线图陈述（「未来将支持」） | **0** | — |

即 `计划` 这一词的**精确率 ≈ 0/25**。真正抓到路线图语义的只有 `未来` 1 条。同类问题：过度宣称 4 条里 `单一真源` 3 条均是架构术语（规范自身正文也在用「唯一真源」）。

**两种口径**

- **口径 A（保持子串匹配）**：接受 ≥28/80 条恒为噪声，靠人工 review 忽略。代价不是算力，是**reviewer 麻木**——噪声率 35% 的报告没人会逐条看。
- **口径 B（引入意图判定）**：中文无词边界，需上下文模型/规则树，不可解释、**不可取红**，且违反 §7「不为变绿加复杂度」的精神。否决。
- **口径 C（词表治理，不动匹配算法）**：把**多义中文词**从词表移除、替换为不可歧义短语 —— `计划` 移除（保留 `将支持` / `下一版` / `未来`）；`单一真源` 移除（保留 `零缺陷` / `彻底解决` / `完全杜绝` / `100%` / `O(1)` / `保证不`）。

**影响面（口径 C 的量化预期）**：路线图 26 → 1，过度宣称 4 → 1，总 warn 85 → **约 57**，剩下的全部是真实命中。漏检风险是「单字 `计划` 形态的路线图陈述」，而实测分母 25、命中 0 说明该形态**在本仓不存在**。

**建议：C**。改动 = `ANTI_PATTERN_WORDS` 两处 + §6 词表两行 + selftest 两处逐词取红断言（`计划` 断言**不命中**，`将支持` 断言命中）。

**裁定：** ☐ A ☐ B ☐ C

## R3 · §5 触发条件 ②「语义变更数 ≥ 30」无规则 ID

**现状**：§5 正文仍写「满足任一即需 refresh —— ① 源指纹不符 ② 语义变更数 ≥ 30 ③ 检查器报 `stale`」，紧接的注解已诚实标注「② 不由机器判定」。即**正文在承诺机器契约、注解在撤回它**，同一段自相矛盾。

**实测**：`RULES` 11 条里无对应规则；检查器全程不访问 git（纯静态文件检查，可离线）。

**三种口径**

- **口径 A（措辞对齐，建议）**：§5 正文改为「①③ 由检查器判定；② 为**人工判据**，不进门禁」。零代码改动，消除自相矛盾。
- **口径 B（补机器规则 `semantic-changes-exceed`）**：用 `git log --since=<最近整理日期> -- <覆盖范围>` 的**提交数 ≥30** 作代理。代价：检查器从「纯静态」变成「依赖 git + 依赖 HEAD/工作树」，离线不可用、结果非确定性，且「提交数」≠「语义变更数」，是**用一个不准确量替换一个诚实的人工判断**。
- **口径 C（删除 ②）**：承认它从未被执行。但人工判据本身有价值（指纹不变 ≠ 语义没变）。

**建议：A**。改动 = §5 一句措辞。

**裁定：** ☐ A ☐ B ☐ C

## R4 · `PLACEHOLDER_ALLOWED ∩ PLACEHOLDER_RE = ∅` 的恒真 guard

**现状**（`code_map_check.py:708`，逐字）：

    if cell and PLACEHOLDER_RE.match(cell) and cell.lower() not in allowed_placeholders:

**实测（逐值枚举，12 个探针值）**

| 集合 | 值 |
|---|---|
| `PLACEHOLDER_ALLOWED` | `none` / `n/a` / `无` / `-` / `—` / `""` |
| `PLACEHOLDER_RE` | `^(?:暂无｜待补｜待定｜tbd｜todo｜--)$` |
| 交集 | **空**（能 match 的 6 个值全部不在 allowed；allowed 的 6 个值全部不 match） |

⇒ 第三个条件 **恒真**，短路后等于 `if cell and PLACEHOLDER_RE.match(cell)`。

**性质判定：这是防御性冗余，不是缺陷**。若将来把 `待定` 加进 `PLACEHOLDER_ALLOWED` 表示「该占位可接受」，第三个条件立刻生效 —— 它是为词表联动预留的安全网。真正的问题是**它没有被守住**：现有 selftest 的「`—` 不命中（对照）」只证明了 RE 不匹配，**没有**证明 allowed 列表参与判定；把 allowed 删空，自测依旧全绿。

**两种口径**

- **口径 A（保留 + 补取红自测，建议）**：新增一个 stage —— 临时把 `待定` 注入 `LIMITS["PLACEHOLDER_ALLOWED"]`，断言该行**不再命中**；复原后断言**重新命中**。把「恒真」变成「被测」，检查器逻辑 0 改动。
- **口径 B（删掉第三条件）**：代码更短，但丢掉未来词表联动的安全网，且属于「为整洁而删护栏」。

**建议：A**。改动 = selftest 一个 stage（约 15 行）。

**裁定：** ☐ A ☐ B
