# 「读→改→写」族拒绝损失性解码

## 1. 缺陷类

一个工具要实现局部修改，最省事的实现是「读整个文件 → 改 → 写回整个文件」。危险在于读的那一步用了**宽松**解码：

```csharp
Encoding.UTF8.GetString(bytes)   // 非法字节 → U+FFFD，不抛异常
```

于是「读」这一步就已经**改变了数据**，而「写回」把它固化。对使用者表现为：patch 成功、文件变长、内容里多出 `�`。

这不是某一个工具的 bug，是一族实现的共同形状。本仓共五处：

| # | 位置 | 提交 | 症状 |
|---|---|---|---|
| 1 | `GoalUpdateTool`（base64 内容落盘） | `e8dfd12` | goal.md 8180 字节 / BOM / 1747 处 U+FFFD |
| 2 | `file_write(append)` 与 `file_patch` operations 路径 | `56f3944` | 任意用户文件被静默改写 |
| 3 | `ImportantMemoryService`（L4-PINNED 记忆） | `f73e3dd` | 记忆读入即腐化，写回固化；且三条写路径写 BOM |
| 4 | `file_patch` 的 `patch_text` / `apply_patch` 统一 diff 路径 | `3bb521b` | 与 #2 同型，但在另一条路径上（我先漏了它） |
| 5 | `file_patch` 写回时丢 BOM | `ffb3b8a` | 严格解码修好后，剥掉的 BOM 不会再写回，等于改了编码形态 |

第 4 处值得单独记：我在 `56f3944` 里只修了 operations 路径，**同一工具的另一条路径仍然宽松**。修一族缺陷必须按「写入路径」枚举，不能按「用户报的那个入口」枚举。

## 2. 修法

统一收敛到一个入口，避免两个候选写法各错一半：

```csharp
internal static class StrictUtf8Text
{
    public static string ReadAllText(string path)
    {
        var text = Strict.GetString(File.ReadAllBytes(path));   // 拒绝非法字节
        return text.Length > 0 && text[0] == '\uFEFF' ? text[1..] : text;  // 剥 BOM
    }
}
```

- `Encoding.UTF8.GetString` 严格但**不剥 BOM** `⇒` 逐行比对会把 `"\uFEFFalpha"` 与 `"alpha"` 判为不同
- `File.ReadAllText` 剥 BOM 但**宽松**
- 两者各错一半，所以必须显式组合

写回侧记录 `HasBom`，临时文件继承目标文件的 BOM 形态（`ffb3b8a`）。

## 3. 运行时验收（2026-11-25 02:53）

单元测试只证明源码，不证明部署。部署判定：

| 项 | 实测 |
|---|---|
| HEAD | `ffb3b8a` @ 02:51:17 |
| live `PuddingHost.dll` | 02:52:57 |
| 运行进程 | PID 104440，StartTime 02:53:30 |
| 进程实际加载的模块 | 上述同一路径（`Get-Process.Modules` 核对） |

三者时间序 HEAD < DLL < 进程启动 ⇒ at-or-after-head。

### 3.1 判据设计

负对照必须**可能成功**才算负对照。因此非法字节样本里特意保留了可匹配的 `beta`：

```
alpha\nbeta\nbe\xffta\n     ← 含 0xFF，同时含 "beta"
```

若解码宽松，替换会成功并把 `0xFF` 改成 3 字节 `EF BF BD`；若严格，读取即失败。两者在字节层面可区分。

### 3.2 逐项结果

| 检查 | 路径 | 结果 |
|---|---|---|
| 正对照（合法无 BOM） | operations | 成功，11 → 12 字节 |
| 正对照（合法无 BOM） | patch_text | 成功，11 → 12 字节 |
| 负对照（含 0xFF） | operations | **拒绝**，`is not valid UTF-8` |
| 负对照（含 0xFF） | patch_text | **拒绝**，`is not valid UTF-8` |
| BOM 保持 | operations | 14 → 15，`bom=True` |
| BOM 保持 | patch_text | 14 → 15，`bom=True` |
| 无 BOM 不新增 | operations | 11 → 12，`bom=False` |

失败文本（两条路径一致）：

> Refusing to patch '…': the file is not valid UTF-8. A lossy decode followed by a whole-file rewrite would silently replace its bytes with U+FFFD. Convert the file to UTF-8 first.

### 3.3 逐字节复核（不采信工具回执）

两个被拒绝的文件在事后独立读回：

```
rt_invalid.txt   len=17  bom=False kept_ff=True  fffd=False
rt_d_bad.txt     len=17  bom=False kept_ff=True  fffd=False
```

`kept_ff=True` 且 `fffd=False` ⇒ 原始 `0xFF` 仍在、没有被替换。这是「拒绝」与「拒绝且无损」的区别，前者只要抛异常就能满足。

## 4. 一个工具契约事实（实测）

`file_patch` 的 `patch_text` 模式下，目标文件取自 **diff 头部**，入参 `path` 不参与解析：

```
--- rt_d_ok.txt          → Error: File not found: rt_d_ok.txt   （按进程 cwd 解析）
--- D:/…/temp/rt_d_ok.txt → 成功
```

所以 `patch_text` 必须给绝对路径（正斜杠可用）。这条写在这里，是因为它不容易从工具描述推断，只能现场试出来。

## 5. 未覆盖的部分

- `AgentContentSummaryService` 已审：**无截断放大器**，且文件只由本服务写。仅剩「外部造成的损坏会被整文件改写」这一弱风险，**未改**。
- 一处既有测试在「去掉剥 BOM」变异下仍然绿（`"alpha"` 是 `"\uFEFFalpha"` 的子串），属假门禁，已删除并在类注释中说明原因。
- 运行期泄漏（进程活着、run 卡在 running）与本次无关，仍无判据，见 goal 待办。

## 6. 可复用的判据

1. **修一族缺陷按写入路径枚举，不按上报入口枚举。** 第 4 处就是这么漏掉的。
2. **负对照必须能成功。** 样本里要保留一个本可匹配的锚点，否则「hunk 不匹配」与「解码拒绝」在结果上不可区分。
3. **拒绝 ≠ 无损。** 必须逐字节复核原始非法字节仍在、且未出现 U+FFFD。
4. **变异本身也要能取红。** `GetBytes` 不产生 BOM，改它属于等价变异，测试永远不会红；必须显式拼 `EF BB BF` 才能验证 BOM 判据。
