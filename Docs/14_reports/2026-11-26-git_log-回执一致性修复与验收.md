# git_log 回执一致性修复与部署验收

## 1. 修的是什么

同一段 20 行代码里并存三处静默错误行为：

| # | 旧行为 | 后果 |
|---|---|---|
| ① | `FilePath` 声明了参数、写进了工具描述，却**从未被读取** | 传了过滤条件仍返回整支分支历史，命数一模一样 |
| ② | 分支名不存在时 `Branches[...]` 返回 null，**静默回落到当前分支** | 回执里 `branch` 仍写着 HEAD，调用方以为查的是指定分支 |
| ③ | 数量被截断（或 `max_count` 被夹取）**没有任何信号** | 无法区分「到上限了」与「历史就这么长」 |

改法：`file_path` 走 `NormalizeFilterPath`；分支不存在 `Fail` 并指向 `git_branch_list`；多取一条判定 `truncated`，`notice` 只在「调用方要的和拿到的不是一回事」时出现。

## 3. 测试计数：一次自我更正

提交说明写的是「`-t:Rebuild` 后 13/13」。本轮复跑发现该数字**无法用任何已记录的 filter 复现**：

| 命令 | 结果 |
|---|---|
| `--filter "fullyqualifiedname~GitLogToolBehaviorTests"` | **7/7 通过**（该文件确有 7 个 `[TestMethod]`） |
| `--filter "fullyqualifiedname~Git"` | **31/31 通过**，但匹配是子串语义，含 `RuntimeIdentity_…`、`FullCompactAsync_…` 等无关类 |

也就是说：写成「13」时既没记 filter、也没记项目路径，后续无法重放。这与本次修的三处缺陷**同源** —— 回执里的数字必须能让读者还原出「它测的是哪一批」。

顺带一条：`~Git` 这种子串 filter 会把 git 相关的门禁测试一起卷进来，不能当作「git 相关测试全绿」的证据。

### 采纳的规则

1. 提交说明与报告里的测试计数，**必须与 filter 及项目路径同时出现**，否则不写计数。
2. `~` 是子串匹配，不被当作集合定义；要证明「某个类全绿」，filter 用类全名。
3. 复跑计数与历史记录不一致时，**改记录、不删记录**：保留原数字并标注「不可复现」。

## 7. 三个未覆盖臂补齐 —— 并在这过程中发现第四处同类缺陷

### 7.1 三臂结果

| 臂 | 入参 | 回执 | 判定 |
|---|---|---|---|
| `max_count` 越界 | `max_count=1000`（配一个 `file_path` 过滤，避免拉回 100 条提交） | `count=2`, `truncated=false`, `notice="max_count=1000 was clamped to the supported range 1..100 (applied 100)"` | 夹取与截断是**两条独立 notice**：夹取不依赖历史长度，`truncated=false` 时依然出声 |
| `file_path` 不存在 | `file_path="no-such-file-1126.txt"` | `count=0`, `truncated=false`, `notice=null`, `commits=[]` | **按设计，非缺陷**：`NormalizeFilterPath` 的注释写明「回执里 count=0 与 file_path 原值足以让调用方看出没匹配上」。`git log -- <不存在路径>` 本身也是静默空；若加「工作树不存在」提示，会与「文件已删除但仍有历史」互相混淆 |
| 分支名大小写 | `branch="MASTER"` | 成功，回执 `branch="master"` | LibGit2Sharp 在 Windows 上按大小写不敏感解析，回执给规范名 |

第二臂的结论是「不该改」。这一臂的价值不在回执，而在于它把「回执里哪些字段是回显、哪些是实测」这件事逼出来——于是有了下面这条。

### 7.2 第三臂暴露的第四处缺陷

臂 ③ 让我注意到：回执的 `branch` 字段取自 `repo.Head.FriendlyName`，**报的是 HEAD，不是被查询的分支**。用一个 tip 与 master 不同的分支实测：

```
入参  branch="feature/r1-xss-fix"      （git 实测该分支 tip = e59b9c0）
回执  branch="master"
内容  commits[0].sha = e59b9c0         ← 确实是该分支的提交
```

回执与内容互相矛盾。这正是 `8187843` 注释②里写的那句话（「回执里 branch 还写着 HEAD」）—— 当时修掉了「不存在时静默回落」，字段本身没跟着改。

### 7.3 修法与取红

`branch = queriedBranch ?? repo.Head.FriendlyName`，其中 `queriedBranch = branch.FriendlyName`（git 规范短名）。

| 变异 | 结果 | 失败的那条断言 |
|---|---|---|
| M1 退回 `repo.Head.FriendlyName` | 8 中 1 红 | 应为 `"feature-x"` 但却是 `"master"` |
| M2 `queriedBranch = args.Branch`（逐字回显） | 8 中 1 红 | 应为 `"feature-x"` 但却是 `"refs/heads/feature-x"` |

两次复原 `SHA 88266a1e439a4d5c` 逐字节相同；`-t:Rebuild` 后 8/8。

**M2 是特意加的**：若测试只有「短名入参」一条臂，一个把入参原样回显的实现能让 M1 的断言照样全绿——因为入参短名恰好等于规范名。所以新增 `branch="refs/heads/feature-x"` 这一臂，它同时把「回执给规范短名」立成契约。两个变异红的分别是两条不同断言，不是同一条被打两次。

### 7.4 本节边界

- 大小写臂（`MASTER`）只在 Windows 上有意义：LibGit2Sharp 依赖文件系统大小写不敏感解析，所以**没有**写进单测（Linux 上会红）。它作为带时点的运行时事实记录于此。
- 未覆盖：远端跟踪分支（`origin/xxx`）的回执形态；detached HEAD 下的 `branch` 字段（仍走 `repo.Head.FriendlyName`，未实测）。
