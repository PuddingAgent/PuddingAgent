# git_log 回执一致性修复与部署验收

## 1. 修的是什么

同一段 20 行代码里并存三处静默错误行为：

| # | 旧行为 | 后果 |
|---|---|---|
| ① | `FilePath` 声明了参数、写进了工具描述，却**从未被读取** | 传了过滤条件仍返回整支分支历史，命数一模一样 |
| ② | 分支名不存在时 `Branches[...]` 返回 null，**静默回落到当前分支** | 回执里 `branch` 仍写着 HEAD，调用方以为查的是指定分支 |
| ③ | 数量被截断（或 `max_count` 被夹取）**没有任何信号** | 无法区分「到上限了」与「历史就这么长」 |

改法：`file_path` 走 `NormalizeFilterPath`；分支不存在 `Fail` 并指向 `git_branch_list`；多取一条判定 `truncated`，`notice` 只在「调用方要的和拿到的不是一回事」时出现。

## 3. 测试计数：一次自我更正

提交说明写的是「`-t:Rebuild` 后 13/13」。本轮复跑发现该数字**无法用任何已记录的 filter 复现**：

| 命令 | 结果 |
|---|---|
| `--filter "fullyqualifiedname~GitLogToolBehaviorTests"` | **7/7 通过**（该文件确有 7 个 `[TestMethod]`） |
| `--filter "fullyqualifiedname~Git"` | **31/31 通过**，但匹配是子串语义，含 `RuntimeIdentity_…`、`FullCompactAsync_…` 等无关类 |

也就是说：写成「13」时既没记 filter、也没记项目路径，后续无法重放。这与本次修的三处缺陷**同源** —— 回执里的数字必须能让读者还原出「它测的是哪一批」。

顺带一条：`~Git` 这种子串 filter 会把 git 相关的门禁测试一起卷进来，不能当作「git 相关测试全绿」的证据。

### 采纳的规则

1. 提交说明与报告里的测试计数，**必须与 filter 及项目路径同时出现**，否则不写计数。
2. `~` 是子串匹配，不被当作集合定义；要证明「某个类全绿」，filter 用类全名。
3. 复跑计数与历史记录不一致时，**改记录、不删记录**：保留原数字并标注「不可复现」。

| ① 分支不存在 | `branch="no-such-branch-1126"` | **失败**：`Branch 'no-such-branch-1126' not found. Use git_branch_list to see the branches that exist.` |

### 6.3 顺带：`5127550` 的文案也在跑

`shell=cmd` 跑 `python --version` → `exit code 9009`，回执提示含

> A name that PATH does resolve can still fail this way: on Windows 'python' is normally a Microsoft Store App Execution Alias stub that reports 9009 — use the real launcher ('py') or the interpreter's absolute path.

旧文案只说「查 PATH」，而 PATH 本是对的。这是 `5127550` 的行为层证据，不靠程序集时间推断。
