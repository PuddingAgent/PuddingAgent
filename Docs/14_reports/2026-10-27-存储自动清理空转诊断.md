# 存储自动清理空转诊断

## 1. 现象

| 项 | 实测值（2026-10-27） |
|---|---|
| `pudding_platform.db` | 11.94 GB |
| 表数 | 89 |
| 总行数（四张大表） | 10,169,704 |
| 库创建时间 | 2026-09-30（27 天） |
| 日均增长 | ≈ 442 MB |
| `freelist_count` | 0（无碎片浪费，全是实数据） |

空间前四**全是观测数据**：

| 表 | 大小 | 全表占比 |
|---|---|---|
| `conversation_events` | 2,964.8 MB | 24.4% |
| `telemetry_metric_events` | 1,982.6 MB | 16.3% |
| `runtime_activity` | 1,097.5 MB | 9.0% |
| `context_layer_metric_events` | 803.2 MB | 6.6% |
| `ChatMessages`（用户对话） | 181.6 MB | 1.5% |

年龄分布显示这三张诊断表 **>3 天即占 95–98%**。

## 2. 关键线索

库内已存在专门的保留索引，说明按时间清理是被设计过的：

```
ix_retention_conversation_events_committed_at          165.0 MB
ix_retention_telemetry_metric_events_occurred_at_utc   124.2 MB
ix_retention_runtime_activity_started_at_utc            92.5 MB
ix_prune_conversation_events_committed_at              164.9 MB
ix_prune_runtime_activity_started_at_utc                92.4 MB
```

## 3. 根因

`StorageMaintenanceCoordinator : BackgroundService` 具备完整骨架：

- 双通道 `_manualQueue` / `_automaticQueue`（人工优先）
- `StorageCleanupExecutor` 串行执行（单 writer）
- DataRoot 级独占文件锁防并发
- 崩溃恢复：`StartAsync` 会把 `Queued` 状态作业重新入队

**但 `_automaticQueue.Writer` 全仓只有一处写入** —— `StartAsync` 第 80 行的重启恢复：

```csharp
foreach (var job in _jobStore.ListRecent(200))
    if (job.Status == StorageCleanupJobStatus.Queued)
        await channel.Writer.WriteAsync(job.JobId, cancellationToken);
```

**不存在任何按保留策略周期性生成自动作业的代码**（无定时器、无策略评估循环、无"到期扫描"）。

⇒ 自动通道只会搬运「重启前已经排好队」的作业；一旦没有人工提交过作业，它就永远是空的。
**自动清理自上线起从未触发过**，这与 27 天 1017 万行的实测一致。

补充：`StorageDataClassCatalog` 里 `TelemetryRaw` 与 `ContextLayerRaw` 均标了
`RequiresRollupBeforeAutomatic = true`（小时/日聚合未实现 → 自动关闭，属**有意设计**）；
但 `RuntimeActivity`（14 天、`AutomaticCleanupAllowed = true`、无 rollup 前置）同样积累到 200 万行
——这一条不属于"设计上关闭"，属于**缺生产者**。

## 4. 已执行的缓解（2026-10-27，人工一次性）

保留 14 天，分批 1 万行/事务，全程宿主存活（PID 未变）：

| 表 | 删除行数 | 耗时 |
|---|---|---|
| `runtime_activity` | 1,907,184 | 200 s |
| `telemetry_metric_events` | 2,436,490 | 269 s |
| `context_layer_metric_events` | 1,487,135 | 54 s |
| 合计 | **5,830,809** | ≈ 8.7 min |

结果：`freelist_count` 0 → 1,409,017 页（**5.37 GB 可复用**）；三表 `oldest` 精确停在
2026-10-13/14；`conversation_events` 与 `ChatMessages` **未动**。
主库文件仍 12,231.84 MB（`auto_vacuum=0` 不会自动缩），WAL 升至 541 MB 待 checkpoint。

按 442 MB/天算，5.37 GB 空闲页约提供 **12 天**余量。

## 5. 修复方案（未实施）

**S1 —— 补生产者（核心）**

在 `StorageMaintenanceCoordinator` 内增加周期评估（建议 6 小时）：

1. 遍历 `StorageDataClassCatalog.Definitions`；
2. 过滤：`AutomaticCleanupAllowed` 且非 `RequiresRollupBeforeAutomatic`；
3. 读取该 target 的生效保留天数（策略值优先，回落 `DefaultRetentionDays`）；
4. 用 `RetentionIndexes` 声明的索引做**廉价候选探测**（`COUNT(*) WHERE ts < cutoff`），为 0 则跳过；
5. 有候选才走既有的 preview→job 路径，`Trigger="automatic"` 写入 `_automaticQueue`；
6. 单轮只允许一个自动作业在跑（人工优先已由双通道保证）。

**S2 —— 让 DebugPayload 的字段清理先跑起来**
`DebugPayload`（7 天、清 `debug_json`/`metadata_json`、无 rollup 前置）只清大字段不删行，
风险最低，可作为 S1 的首个启用目标验证链路。

**S3 —— 缩文件需单独决策**
`auto_vacuum=0`，要真正缩小必须 `VACUUM`：需独占锁 + 约 7 GB 临时空间 + 停写窗口。

## 6. 验收标准

| 指标 | 目标 |
|---|---|
| `[StorageMaintenance]` 日志出现 `trigger=automatic` 的作业 | 每周期至少一次评估记录 |
| 无候选时 | 打一条评估日志（不产生空作业） |
| `runtime_activity` 行数 | 稳定在 14 天窗口量级（当前 131,300） |
| `telemetry_metric_events` | 不受 S1 影响（`RequiresRollupBeforeAutomatic` 仍关闭，需 S-rollup） |
| 文件增长 | 日增应被窗口吸收，`freelist_count` 不再归零 |

## 7. 未验证项

- `StorageMaintenanceJobStore` 的持久化位置（库内无 `storage_*` 表，疑为 DataRoot 下文件）：**未确认**；
- 自动评估从未运行是否有其它闸门（配置开关 / 宿主未注册该 BackgroundService）：**未排查**；
- `conversation_events` 的清理是否应由独立"证据保留策略"接管：**未查**（`SafetyLevel` 未在本报告确认）；
- VACUUM 在本机 12 GB 库上的实际耗时：**未测**。
