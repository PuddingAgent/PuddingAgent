# exit code 9009/127 归因分支在当前构建上不可达

## 1. 结论

| 命题 | 判定 |
|---|---|
| 历史数据里确有 `exit code 9009` / `127` | **真**（2026-11-13、2026-11-21，共 3 条，全部 `tool_runner` + `shell`） |
| 当前构建能制造出 `exit code 9009` | **假**（三次探针 + 1 次交叉确认，全部 `1`） |
| `7d25b56` 的归因分支在今天算「修复活跃缺陷」 | **假**，应改称「对不可达分支的加固」 |
| 当前活跃失败形态 | `exit code 1`，全表 124 条 |

所以上一轮留下的验收方法（「制造一次 9009 看新文案」）**不可执行**，原因是环境，不是代码。

## 2. 四次实验（原始输出）

```
nonexistent_cmd_probe_1126_1343 --version
→ ❌ FAILED (exit=1)   Error: exit code 1
   [stderr]: 'nonexistent_cmd_probe_1126_1343' �����ڲ����ⲿ���Ҳ���ǿ����еĳ���
```

### 2.2 `cd /d ... &` 前缀后仍同（排除「裸命令走了别的路径」）

```
cd /d D:\Data\workspaces\default\temp & nonexistent_cmd_probe_1126_1347
→ ❌ FAILED (exit=1)   Error: exit code 1
```

### 2.3 PowerShell 外壳内层调 cmd（`$LASTEXITCODE` 交叉确认）

```
shell=powershell:  cmd /d /s /c nonexistent_cmd_probe_1126_1356 ; "RC=$LASTEXITCODE"
→ ✅ exit=0   输出 RC=1
   [stderr]: 'nonexistent_cmd_probe_1126_1356' is not recognized as an internal or external command,
```

这一条是决定性的：**RC=1 是 cmd 自己的退出码**，不是平台把 9009 改写成 1。平台 `HostShellExecutor.cs:105` 只是照抄 `process.ExitCode`。

### 2.4 `chcp 65001>nul &` 前缀（试图让中文错误可读）

```
chcp 65001>nul & nonexistent_cmd_probe_1126_1405
→ ❌ FAILED (exit=1)   中文仍是 U+FFFD
```

**修法被证伪**：`chcp 65001` 不改变 cmd 自身诊断消息的编码。

## 3. 为什么历史有、今天没有

历史 3 条（11-13、11-21）与今天差 5 天以上。`HostShellExecutor` 的退出码是原样转发的，没有归一化代码，所以差异只能来自 `cmd.exe` 本身的行为或系统版本状态。

这条按「环境型归因」处理：**记时点、记原始探针、环境变化后复测**。当前能说的只有：

- 本机（`Microsoft Windows 10.0.26300`）在 2026-11-26 13:43–14:07 时段内，`cmd /d /s /c <不存在的命令>` 返回 `1`。
- 未查实 `cmd.exe` 何时/为何改变，也没有可靠办法在本次心跳内回溯。

## 4. 对 `7d25b56` 的重新定性

代码本身没有任何问题：

```csharp
private static bool IsCommandNotFound(string error)
{
    var trimmed = error.Trim();
    return trimmed.Equals("exit code 9009", StringComparison.OrdinalIgnoreCase)
        || trimmed.Equals("exit code 127", StringComparison.OrdinalIgnoreCase);
}
```

整串相等、不吃 `Contains`，`1271` 不会被误判——这些断言在单测层仍然有效且有价值。

但它的**定性**必须改：

- 不是「修了一个正在发生的错误归因」
- 是「给一个今日不可达、历史上出现过 3 次的分支补齐归因」
- 单测保护的是「实现不退化」，不是「线上行为改变」

不删。删了等于放弃对未来环境变化的覆盖，而那 3 条历史记录说明这个分支真会被触发过一次。

## 5. `exit code 1` 为什么不归因

全表 124 条 `exit code 1`，是绝对主力。但 `1` 的语义属于被调命令：`findstr` 无匹配、`dotnet build` 失败、`git diff --exit-code` 有差异、脚本 `exit 1`，全是 1。

既有测试特意用 `"exit code 1"` 作为「无法归因」的样例，钉住「逐字回落到通用建议」。这个设计是对的：**猜错比不猜更贵**——把 `git diff` 的差异当成 PATH 问题，会让人去查一个不存在的环境问题。

所以本轮**不动**归因逻辑。

## 6. 顺带记录：cmd 外壳的中文 stderr 不可读

`ConfigureUtf8Environment` 对所有 shell 统一设 `StandardOutputEncoding/StandardErrorEncoding = UTF8`；PowerShell 侧由 `WrapPowerShellCommand` 显式把子进程 `[Console]::OutputEncoding` 改成 UTF-8，所以两边一致。

**cmd 侧没有对应处理**：cmd.exe 用 OEM 代码页（本机 CP936）输出内置诊断消息，被按 UTF-8 解码 → `�����ڲ����ⲿ���`。实测 `chcp 65001>nul &` 前缀无效（§2.4）。

影响面比看上去小：`auto` 在 Windows 上解析为 pwsh 7 优先，只有**显式** `shell=cmd` 才会踩到。规避方式就一条：需要 CD 语法以外的命令时用 `auto` / `powershell`。

未做的修法（列出来是为了下次不用重新想）：

| 方案 | 收益 | 代价/风险 |
|---|---|---|
| cmd 分支设 `StandardErrorEncoding = Encoding.GetEncoding(936)` | cmd 诊断可读 | 用户程序写到 stderr 的 UTF-8 会反向乱码 |
| 强制 `chcp 65001` 前缀 | —— | **已实测无效** |
| 保持现状 + 文档化规避 | 零风险 | 中文错误继续不可读 |
