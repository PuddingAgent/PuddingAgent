## 3. 各项细节

### 3.1 `displays`：IntPtr 修复确认【已证实】

`d0212f2` 之前该调用整条失败：

```text
Serialization and deserialization of 'System.IntPtr' instances is not supported.
Path: $.windows.Handle.
```

修复后回执中 `handle` 为十六进制字符串（`"0x590242"`），16 个窗口全部返回。**线格式边界（`ScreenCaptureWire`）确实把领域模型的 `nint` 挡在了序列化之外。**

### 3.2 双屏几何【已证实】

```
virtualDesktop = (0,0) 5120×1440
DISPLAY1 (primary) = (0,0)     2560×1440
DISPLAY2           = (2560,0)  2560×1440
```

两屏为**左右并排、等高**布局，虚拟桌面宽度恰为两屏之和 ⇒ 坐标空间无重叠、无空档。

### 3.3 跨屏坐标连续性【已证实】

区域 `x=2500, width=120` 横跨主屏右缘（2500–2560）与副屏左缘（2560–2620）。返回图像**左段为白色（Pudding 主界面边缘）、右段为蓝色（副屏壁纸）**，颜色分界恰好落在 `x=2560`。⇒ 虚拟桌面坐标在跨屏处**连续且无偏移**，这是"多屏合成为一张画布"能力的直接证据。

### 3.4 窗口采集用 `PrintWindow` 而非屏幕裁剪【已证实】

`windowTitle="Notepad"` 返回 `1920×1023`，`capturedRect=(208,208,1920,1023)` 与 `displays` 报告的窗口 bounds **完全一致**，且图像**不含 Windows 任务栏**。若走屏幕区域裁剪，任务栏必然出现在底部。⇒ 窗口口径走的是 `PrintWindow`（可抓被遮挡窗口）。

### 3.5 越界裁剪是 fail-soft 而非静默变卦【已证实】

请求 `(2500,1400) 500×500`，虚拟桌面高度仅 1440 ⇒ 高度被钳到 40。回执：

```json
"capturedRect": {"x":2500,"y":1400,"width":500,"height":40},
"notes": ["region was clamped from 2500,1400 500x500 to 2500,1400 500x40 (virtual desktop 0,0 5120x1440)"]
```

调用方能从 `notes` + `capturedRect` 双重确认实际采集范围，不会被"返回了一张图"误导。

## 4. 语义边界（不是缺陷，但会误导调用方）

### 4.1 `isVisible=true` 不等于"此刻屏幕上可见"【未证实具体原因】

`displays` 报：

```json
{"handle":"0x21F0A9C","title":"ChatGPT","processName":"ChatGPT",
 "bounds":{"x":4008,"y":0,"width":1113,"height":1440},"isVisible":true}
```

该窗口落在副屏 `(4008,0)–(5121,1440)`。但 `displayIndex=1` 的截图**只有壁纸**，无该窗口。

最可能原因是 `IsWindowVisible` 不区分虚拟桌面：窗口在另一个虚拟桌面时该 API 仍返回 TRUE，而 `BitBlt` 只抓**当前虚拟桌面**的实际像素。

⇒ **判读规则**：`isVisible` 应理解为"窗口未被隐藏"（`WS_VISIBLE` 语义），**不是**"用户此刻看得见"。要判断真实可见性，必须用截图交叉验证，或另取 `DwmGetWindowAttribute`/虚拟桌面 API。**【未证实】** 本次未做单变量实验证明就是虚拟桌面差异，仅记录现象与最合理解释。

### 4.2 最小化窗口以 `-32000` 占位矩形出现【已证实】

```json
{"title":"任务管理器","bounds":{"x":-32000,"y":-32000,"width":160,"height":28},"isVisible":true}
{"title":"ChatGPT 和另外 3 个页面 - 个人 - Microsoft Edge","bounds":{"x":-32000,"y":-32000,"width":160,"height":28},"isVisible":true}
```

`-32000` 是 Win32 最小化窗口的标准占位坐标。列表未过滤这类窗口，也未在字段上标注"已最小化"。
⇒ 按 `windowTitle` 匹配时，若目标恰为最小化窗口，可能抓到 `160×28` 的占位图而非真实内容。

### 4.3 UI 版本串仍是陈旧投影【已证实】

桌面右下角显示 `v6.9.10 · b9b1460 · 2026-10-19 14:04`，而运行二进制含 `d0212f2`（15:41）的行为（`handle` 已能序列化）。
⇒ 与本日早前记录的「UI 版本串 ≠ 二进制内容」是同一缺陷，`15:48` 这次构建仍未修复。

## 6. 结论

1. **`screen_capture` 在双屏 5120×1440 环境下六项口径全部可用**，包含多屏、区域、窗口、跨屏与越界裁剪。
2. **`d0212f2` 的 IntPtr 修复已确认生效**（`handle` 序列化为十六进制字符串，`displays` 不再整条失败）。
3. **两处语义边界需在调用侧规避**：`isVisible` 不能当"此刻可见"；最小化窗口会以 `-32000` 占位矩形出现。
4. **一条既有缺陷复现**：UI 版本串陈旧，与实际二进制不符。
5. 本工具只做**采集**，不产生任何输入事件；测试过程中未点击坐标、未向任何窗口发送按键或鼠标消息。
