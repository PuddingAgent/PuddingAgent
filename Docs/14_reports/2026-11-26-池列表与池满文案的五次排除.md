# 池列表与池满文案的五次排除

## 起因

`pool_action="list"` 的输出顺序是：

```
probe-model(11-25 13:36) → scout(11-25 00:39) → reviewer(11-24 18:15)
→ advisor(11-24 17:54) → frontend-ui(11-21 12:26)
```

既不是名字顺序，也不是创建顺序。想到 `SubAgentPool` 的条目容器是 `ConcurrentDictionary`，而 .NET 的字符串哈希有每进程随机种子 —— 若按枚举顺序渲染，成员位置会在每次重启后重排。这条线索值得查。

## 五次排除

| # | 怀疑 | 实际 | 位置 |
|---|---|---|---|
| 1 | 列表按字典枚举序渲染，重启后重排 | `List()` 已 `OrderByDescending(e => e.LastUsedAt)` | `SubAgentPool.cs:1754` |
| 2 | `LastUsedAt` 同刻时顺序不稳定 | 团队**有意不承诺**：「LastUsedAt 同刻时顺序不属于契约」 | `SubAgentPoolTests.cs:905` |
| 3 | 空列表渲染成只有表头的空表 | 调用方已判 `agents.Count == 0` 并给出创建指引 | `SubAgentTool.cs:262` |
| 4 | 池满文案指向 `DestroyAsync`，模型看不懂 | 工具层 `DescribePoolFull` 重写成「先用 `pool_name="…" pool_action="destroy"` 销毁不用的条目」 | `SubAgentTool.cs:1943` |
| 5 | 40 字中文 role 会污染执行链 | `RoleInPlan` 全程 `string`，无枚举解析、无路径拼接 | 见下 |

第 5 条的取证方式是列出全部消费点（`SubAgentManager`、`FileSubAgentRunStore`、`AgentExecutionService`、`ContextAssemblyService` 等 20 余处）：全部是原样赋值或写入 JSON 字段，没有任何一处把它当枚举、当路径段、或做长度校验。所以 `frontend-ui` 那条把职责文本写进 `role` 列的历史数据只会让列表显示变长，**不会导致派发失败**。

## 副产物：一条被确认的设计意图

第 2 条原本是我打算修的点 —— 加 `ThenBy(e => e.Name)` 让顺序完全确定。但测试文件里的注释表明这**不是遗漏而是决定**：

```csharp
// 不断言具体淘汰了哪一个：LastUsedAt 同刻时顺序不属于契约。
```

在这种前提下加 tie-breaker 等于单方面引入新契约：既有用例不守护它，将来别人依赖它会以为那是承诺。**所以不加。**

## 本轮无代码改动

五条全部排除，没有任何一处需要修改。这类结论如果不落盘，下一次（或下一个会话）会从同一个起点重查一遍 —— 本轮的实际成本是十几次工具调用。

## 顺带记录的两条操作事实

- `search_grep` 传相对目录（如 `Source/PuddingRuntime/Tools/...`）会解析到**工作区根**而不是仓库根，报「no files scanned」。判断依据是仓库根，必须以绝对路径传 `directory`。
- `search_grep` 在 `Source/` 全仓搜常见符号（如 `RoleInPlan`）会同时触发 `max_enumerated_files` 与 `max_results` 上限，`coverage: partial`。此时应缩小到具体子目录，或改用索引工具。
