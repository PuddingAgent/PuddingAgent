# 浏览器截图 / 输入「桥路径不通」根因定位

**定位时间**：2026-10-13 20:20–20:35（+08:00）
**背景**：`Docs/14_reports/浏览器Agent目标打通验收-2026-10-13.md` 登记了三项未通能力。本报告给出**截图的完整根因链**，并**校正一条运行映像事实**。

---

## 一、结论（先给答案）

| 问题 | 裁定 |
|---|---|
截图为啥不可用 | **不是授权被拒、不是传输选错**，而是 **Desktop 侧根本没有截图执行器**：唯一实现由**能力通道会话**独占持有，通道关闭 ⇒ `CapabilityExecutor == null` ⇒ 桥上的 `page.screenshot` 命令**结构性无法执行**（代码里是显式 fail-closed，不是漏接） |
桥侧有没有截图代码 | **有**：`PuddingBrowser.Protocol` 定义了 `page.screenshot` 命令与 chunk 载荷，Core 侧 `BridgeBrowserCapabilitySurface.ScreenshotAsync` 也**具备**转发实现 ⇒ 断点在 **Desktop 端缺执行器**，不在协议、不在 Core |

## 二、根因链（逐跳 file:line）

```
① Core 工具层发截图请求
     → TransportRoutedBrowserCapabilitySurface.ScreenshotAsync
       （Source/PuddingHost/BrowserBridge/TransportRoutedBrowserCapabilitySurface.cs:195）
       路由：无活动通道会话 ⇒ LegacyBridge
     → BridgeBrowserCapabilitySurface.ScreenshotAsync
       （同目录 BridgeBrowserCapabilitySurface.cs:35-41）
       _runtime is RemoteBrowserRuntime ⇒ 通过（DI 只注册这一种：
        BrowserBridgeServiceCollectionExtensions.cs:87）
     → RemoteBrowserRuntime.ScreenshotAsync → 下发 page.screenshot 到 Desktop

② Desktop 桥命令分发
     → BrowserWorkspaceController.HandlePageScreenshotAsync
       （Source/PuddingDesktop.WpfArchive/Browser/BrowserWorkspaceController.cs:880-891）
       if (_capabilityExecutor?.Invoke() is not { } executor)
           return Error(..., BrowserOperationNotSupported,
               "screenshot is not available over the bridge transport in this host configuration");
       ⇒ **就是这一行吐出了那句报错**（不是 Core 侧的字符串）

③ 那个执行器从哪来（缺口所在）
     MainWindow.xaml.cs:965-969
       new BrowserWorkspaceController(..., () => _coordinator.CapabilityExecutor)
     DesktopApplicationCoordinator.Capability.cs:32
       internal IDesktopCapabilityExecutor? CapabilityExecutor => _capabilityChannel?.Service;
       ⇒ _capabilityChannel 为 null（capabilityChannel 配置未启用）
       ⇒ CapabilityExecutor 为 null
       ⇒ 桥上的截图必然走 ② 的 fail-closed 分支
```

**同一根因也解释「DOM 点击无观测效果 / 输入值不可回读」**：能落地的交互执行器同样挂在能力通道会话上；桥侧只有 `dom` 合成事件路径，`native` 未实现（工具自身文档即声明「显式失败而非静默回退」）。

## 三、⚠️ 运行映像校正（本轮实测，推翻我上一轮的部署假设）

我上一轮的部署脚本断言的是 `debug_win-x64\core\PuddingAgent.exe` 存在且新鲜。**实测证明那不是宿主真正跑的 Core**：

| 项 | 实测值 |
|---|---|
运行中 Core（pid 79380）`ExecutablePath` | `D:\CodeProject\PuddingAgent\PuddingAgent\Source\PuddingAgent\bin\Debug\net10.0\PuddingAgent.exe` |
其 `PuddingHost.dll` | mtime **17:50:05**，SHA-256 `E8C9BD8A…` |
部署目录 `debug_win-x64\core\PuddingHost.dll` | mtime **18:55:14**，SHA-256 `6988BFEB…`（**不同文件**；`core\` 非 junction，LinkType 为空） |

⇒ **宿主在开发态从「构建输出目录」启动 Core，而非部署目录的 `core\` 子目录**。部署目录里那份 `core\` 副本**未被使用**（疑似给正式打包/外测用）。
⇒ 后果：**本轮修复之所以生效，是因为它是 Desktop 侧改动**（`Pudding.DesktopService.dll` + Shell 被真替换）；**若下一刀切在 Core 侧，光靠这次的部署脚本不会生效** —— 必须构建 `PuddingAgent.csproj` 让 `Source\PuddingAgent\bin\Debug\net10.0\` 变新，并核对进程 `ExecutablePath` 与模块时间戳。
⇒ 另：Core 运行映像为 17:50 构建 ⇒ **包含 P1 环境轨迹修复**（`eb55dee`，提交/构建同为 17:50）。

## 四、两条可选修法（未实施，待裁定）

| 方案 | 做法 | 代价 / 风险 |
|---|---|---|
**A. 重新启用能力通道** | 恢复 `capabilityChannel` 配置 → 会话建立 ⇒ `_capabilityChannel != null` ⇒ `CapabilityExecutor` 可用 ⇒ 截图与真实输入一并恢复 | 需重启 Desktop（会中断当前会话）；上一轮实测通道曾因 **Core 侧身份门禁**（`AgentInstanceId` 空）不通，**而该门禁已由 P1（`eb55dee`）修在热路径上**，故本轮**值得复测**；路由有两传输二选一（通道不就绪即回落 Bridge），故**对现有可用的桥路径回归风险低** |
**B. 给桥配一个不依赖通道的执行器** | 在 Desktop 侧为桥路径提供独立截图/交互执行器 | 与「收敛为单一授权组件」（设计 §3、step 4）方向**相反**，可能造成第二条权威链；不建议在 step 4 之前做 |

**倾向**：先按 **A** 复测（一次重启即可判定，且可回滚），若身份门禁确已解决则截图与输入一并恢复，不必新增第二条路径。

## 五、可复现取证命令

```powershell

Get-CimInstance Win32_Process -Filter "ProcessId=<core-pid>" | Select-Object ExecutablePath,CommandLine
(Get-Process -Id <core-pid>).Modules | Where-Object { $_.ModuleName -like 'Pudding*' } | Select ModuleName,FileName
# 同一时刻对比两份 PuddingHost.dll
Get-FileHash "<A>\PuddingHost.dll"   # A = Source\PuddingAgent\bin\Debug\net10.0
Get-FileHash "<B>\PuddingHost.dll"   # B = temp\build\winui3\...\debug_win-x64\core
```
