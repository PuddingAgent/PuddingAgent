# 工具插件自举能力核查

> 目的：回答「Agent 能否自己开发工具，并在 Core 不重启的情况下加载」。
> 只记录实测，不含修复；修复方案见 §5。

## 1. 结论

| 环节 | 结论 | 依据 |
|---|---|---|
| ① 写代码 | 可用 | `file_write` 成功落盘 `.work/probe/20261110-2025/write-probe.txt` |
| ② 编译 DLL | **不可用** | 无 `terminal_start` |
| ③ 打包 ZIP | **不可用** | 同上；`file_write` 只写 UTF-8 文本，无法产出二进制 ZIP |
| ④ 导入 | **不可用** | `plugin_import` 返回 `A frozen workspace root is required.` |
| ⑤ 加载 | 可用 | `revision 0→1→2`，工具已发布，Core PID **64992 全程未变** |

⇒ **「不需要重启 Core 就能加载/卸载工具」成立**；
**「Agent 自举造工具」不成立**，且缺的是**两道独立的门**（②③ 与 ④），不是一道。

## 2. 环境（本机实测）

- Core PID：`64992`（核查前后一致）
- sessionId：`206a9b48ec904ebb93e7541131fbb835`
- 起始 `revision=0`、`catalog.Packages=[]`、`hostTools.activations=[]`
- 零包挂载状态下，8 个产品工具内核入口可用（`plugin_catalog` / `plugin_import` / `plugin_load` / `plugin_unload` / `plugin_diagnostics` / `search_tools` / `request_tool_approval` / `list_tool_approvals`）

## 3. 加载可用：实证

```
load pudding.files  → state=Active, revision=1, toolNames=[file_patch, file_read, file_search, file_write, read_office_document, search_grep]
load pudding.shell  → state=Active, revision=2, toolNames=[terminal_cancel, terminal_read, terminal_status, terminal_wait]
load pudding.goals  → state=Active, revision=3
load pudding.git    → state=Active, revision=4
```

**说明**：`revision` 是所有激活共享的全局计数器，每次 `load` / `unload` 递增。卸载时须读当前值，传旧值会被 `plugin.revision_conflict` 拒绝（乐观锁生效，非缺陷）。

## 4. 两处阻断的根因

### 4.1 shell：策略裁剪，不是缺陷

`Source/PuddingHost/ToolPackages/shell.json` 声明 **8 个导出**：

```
shell / terminal_execute / terminal_input / terminal_start
terminal_cancel / terminal_read / terminal_status / terminal_wait
```

实际发布 **4 个**（仅后四项无 `RequiresShell`）。

**定性**：挂载成功、导出被策略过滤——宿主按 `AllowShellExecution=false` 裁剪，属**设计意图**，符合 AUTHORING.md「Shell 即使已挂载，仍需工具授权和 `AllowShellExecution`」。

**因此 ②③ 不是 bug，是能力开关。**

### 4.2 导入：真实缺陷

`Source/PuddingRuntime/Tools/BuiltIns/Plugins/PluginTools.cs:30`：

```csharp
if (string.IsNullOrWhiteSpace(context.WorkingDirectory))
    throw new InvalidOperationException("A frozen workspace root is required.");
```

聊天轮次的 `context.WorkingDirectory` 为空 ⇒ 直接抛异常。

**同程序集内的不一致**：文件工具走带兜底的解析

```csharp
// FileTools.ResolveWorkspaceRoot
=> string.IsNullOrWhiteSpace(executionWorkingDirectory) ? WorkspaceRoot : executionWorkingDirectory;
```

⇒ **同一执行上下文里，`file_read/file_write` 可用、`plugin_import` 不可用**。这是行为不一致，不是安全边界。

## 5. 修复方向（未实施）

```csharp
// PluginTools.cs:30 位置
var root = FileTools.ResolveWorkspaceRoot(context.WorkingDirectory);
var path = PluginValidation.Inside(root, args.Path);
```

与既有的 `FileTools.ResolveWorkspaceRoot` + `PluginValidation.Inside` 对齐，避免新增第二套路径解析语义。

**注意**：④ 修好后，②③ 仍挡着——没有 ZIP 依然到不了 ④。两处必须同时解除才能验证自举闭环。

## 6. 未验证 / 不得据本文件声称

- 四步全部解除后，SDK 自举闭环是否真能跑通（**未测**）
- 产品包（host-service）能否纯 JSON 新增而无需宿主重建（**未测**，按 AUTHORING.md 其实现由宿主管理，更新需重新发布宿主）
- Agent 自写插件在真实任务中的稳定性与该不该授予 `allowShellExecution`（**策略问题，待用户裁定**）
