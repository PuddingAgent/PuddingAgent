# 插件能力抑制诊断 · 实施方案

> 动机：架构评审第 ① 条。首次提出时的原始痛点见 §1。
> 本文件只给落点与草案，**未编译、未测试**。

## 1. 现象（2026-11-10 实测）

`plugin_load(pudding.shell)` 回执：

```json
"toolNames": ["terminal_cancel","terminal_read","terminal_status","terminal_wait"]
```

而 `Source/PuddingHost/ToolPackages/shell.json` 声明 **8 个导出**。回执只说"发布了 4 个"，**没有说另外 4 个为什么不在**。

结论是 Agent 只能反问自己：是包坏了？是我没权限？还是设计如此？实际要读过 `shell.json`、再找到过滤代码，才能确定是 `AllowShellExecution=false` 的裁剪。

同样情形会发生在任何一个被策略裁剪的包上（`pudding.files` 的 `file_write` 亦受 `AllowFileWrite` 门控）。

## 2. 现有过滤点（精确落点）

`Source/PuddingRuntime/Services/Plugins/HostToolContributions.cs`

```csharp
// ~line 110 —— Load 里用 Visible() 过滤，但不记录原因
public PluginActivation Load(string hash, PluginScope scope, string operation, long? revision, bool approved, ToolExecutionContext? caller)
{
    ...
    return activation with { ToolNames = activation.State == "Active"
        ? package.Exports.Where(e => caller is null || Visible(e.Key, e.Value, caller)).Select(e => e.Key).ToArray()
        : [] };
}

// ~line 132
private bool Visible(string id, string type, ToolExecutionContext caller) =>
    Selected(id, caller) && _bindings.TryGetValue(type, out var binding) && Permitted(binding.Metadata.Value, caller);

// ~line 142 —— 四道门，任一不过即不可见，但信息在此丢失
private bool Permitted(ToolDescriptor tool, ToolExecutionContext context) =>
    Selected(tool.ToolId, context) && context.CapabilityPolicy is { } p
    && (!tool.Safety.HasFlag(ToolSafetyFlags.RequiresShell) || p.AllowShellExecution)
    && (!tool.Safety.HasFlag(ToolSafetyFlags.RequiresFileWrite) || p.AllowFileWrite)
    && _permissions.CanExposeToAgent(tool, p);
```

`Permitted` 是**布尔连乘**——四道门被压成一个 bit，任何一项失败都不可区分。这就是信息丢失的地方。

## 3. 方案

### 3.1 不改契约

**不动** `PluginActivation`（在 `Pudding.ToolPlugins.Contracts`，改字段会波及 Worker/Protocol/宿主多端）。

改为：在 `PluginLoadTool` 的**回执对象**上附加 `suppressed` 诊断数组。`PluginLoadTool` 已持有 `HostToolContributions? host`（`PluginTools.cs:38`），依赖现成。

### 3.2 新增诊断方法（HostToolContributions）

```csharp
/// <summary>
/// 解释某个包在<b>当前调用者策略</b>下，哪些导出不可见、各自被哪道门挡住。
/// 只读；不改变 Visible/Permitted 的判定语义。
/// </summary>
public IReadOnlyList<SuppressedExport> ExplainSuppressed(string hash, ToolExecutionContext caller)
{
    if (_packages.TryGetValue(hash, out var package) is false) return [];

    return package.Exports
        .Where(e => !Visible(e.Key, e.Value, caller))
        .Select(e => new SuppressedExport(
            e.Key,
            _bindings.TryGetValue(e.Value, out var binding)
                ? Reason(binding.Metadata.Value, caller)
                : "unbound"))
        .ToArray();
}

private (string Code, string Detail) Reason(ToolDescriptor tool, ToolExecutionContext c)
{
    if (c.CapabilityPolicy is not { } p) return ("no-capability-policy", "调用者没有能力策略");
    if (!Selected(tool.ToolId, c)) return ("not-selected", "不在 AllowedToolNames/有效工具集内");
    if (tool.Safety.HasFlag(ToolSafetyFlags.RequiresShell) && !p.AllowShellExecution)
        return ("allowShellExecution=false", "工具声明 RequiresShell，但当前策略未开放 Shell 执行");
    if (tool.Safety.HasFlag(ToolSafetyFlags.RequiresFileWrite) && !p.AllowFileWrite)
        return ("allowFileWrite=false", "工具声明 RequiresFileWrite，但当前策略未开放写文件");
    if (!_permissions.CanExposeToAgent(tool, p))
        return ("permission-denied", "权限策略判定不可暴露给 Agent");
    return ("unknown", "不可见但未匹配已知原因——出现即说明 Permitted 与 Reason 已漂移");
}
```

`SuppressedExport` 建议为 `record struct`（同文件内私有或 internal 均可）。

### 3.3 回执附加

`PluginLoadTool`：

```csharp
var activation = host?.Load(...) ?? plugins.Load(...);
var suppressed = host?.ExplainSuppressed(hash, context) ?? [];
return new { ..., activation, suppressed };
```

保留原有字段不动，仅追加。

## 4. 关键设计约束（防止二次漂移）

1. **`Reason` 必须与 `Permitted` 逐条对齐**。两处若漂移，`unknown` 分支是唯一的探测器——这也是它必须存在、且不许被吞掉的原因。
2. **`ExplainSuppressed` 只读**：不得复用为判定路径，避免诊断逻辑反过来影响授权。
3. **不得在回执里回显策略原文**（如整份 capability policy），只给门名与一句话原因。

## 5. 验收（可执行，未执行）

| # | 用例 | 期望 |
|---|---|---|
| 1 | `plugin_load(pudding.shell)`，`AllowShellExecution=false` | `toolNames` 4 项；`suppressed` 4 项，`code=allowShellExecution=false` |
| 2 | 同上但 `AllowShellExecution=true` | `toolNames` 8 项；`suppressed` 为空 |
| 3 | `plugin_load(pudding.files)`，`AllowFileWrite=false` | `file_write` 出现在 `suppressed`，`code=allowFileWrite=false` |
| 4 | 构造 `Reason` 漏掉某道门（变异） | 用例 1 或 3 变红 |

**取红方式**：把 `Reason` 里 Shell 分支的条件改成恒 false，用例 1 必须红；复原后须位级一致。
用例 1/3 可直接用今天已有的实测数据做基线（4 项 / 6 项）。

## 6. 未验证 / 不得据本文件声称

- 编译是否通过（**未构建**，本机 Agent 当前无 `terminal_start`）
- `_permissions.CanExposeToAgent` 的实际判定分布（未读实现，`unknown` 分支可能比预期更常命中）
- 其他产品包（browser/code/computer 等）是否存在除上述四道门之外的隐藏裁剪（未逐个核）
- 该回执字段是否会被前端/管理 API 的消费方忽略或误解析（未核 `/api/tool-plugins` 的模型）
