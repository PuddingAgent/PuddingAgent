# SSH 当前实现独立审阅（2026-10-18）

**结论：建议暂缓 S5 接入。** 当前 SSH 执行与单文件 SFTP 传输已经有独立实现，但仍存在三项 P1、两项 P2 缺陷。现有 289 项测试全部通过；新增的六个隔离反例全部复现。历史“双门禁通过”不能替代这些边界的修补与重新验证。

## 1. 范围与证据身份

- 审阅起点：`e96f24ef26ad3a9069f77f919c73f62b70883b8b`。SSH 组件、测试、探针在审阅开始时无未提交改动。其他模块已有他方 WIP，本次没有修改、暂存或验证这些 WIP。
- 核查范围：`Source/PuddingSsh/` 的契约、信任校验、执行与传输协调器、路径策略、SSH.NET 适配，以及组件测试、真实探针和已有报告。
- 检索确认：宿主仍未引用 `PuddingSsh`，解决方案未登记该组件，未发现五个 `ssh_hosts` / `ssh_test` / `ssh_execute` / `ssh_upload` / `ssh_download` 工具的产品实现。Agent 目前不能通过这些工具使用该能力；审批、主机目录、`hosts.json`、ACL/revision 和 DI 仍属 S5。
- 本次未重跑真实 OpenSSH 24 场景，也未部署或操作 `D:\data`。下面的反例使用组件真实代码、受控端口替身和本地临时文件，不应描述成真实服务器复现。
- [机器证据](2026-10-18-SSH审阅反例证据.json) 包含六个结果和被审源码摘要。反例程序见 [Program.cs](../../TestScripts/ssh-probe/review-counterexamples/Program.cs) 与 [工程入口](../../TestScripts/ssh-probe/review-counterexamples/ReviewCounterexamples.csproj)。

## 2. 发现

### F1 / P1：上传排他创建失败后，会删除并不属于本次操作的目标

位置：[SshSftpTransferSession.cs](../../Source/PuddingSsh/Transport/SshSftpTransferSession.cs)，271–279、434–445 行；底层排他创建在 [SshSftpChannel.cs](../../Source/PuddingSsh/Transport/SshSftpChannel.cs) 第 68 行。

触发：`overwrite=Fail` 的首次 `Exists` 返回 false；另一客户端随后创建目标；本次 `FileMode.CreateNew` 正确拒绝打开。异常处理仍无条件调用 `AbandonUpload`，后者认为目标必然由自己创建并删除它。结果是禁止覆盖的请求反而删除了其他操作的数据。

证据 R1：模拟上述次序，排他打开抛错，本次返回 `ssh.transfer_failed`，但 `DeletedPaths` 包含最终目标，其他客户端的数据消失。既有 `FakeSftpChannel.UploadAsync` 直接执行 `_files[remotePath] = []`，未模拟“排他创建失败”，因此现有测试没有覆盖此路径。

修补要求：由创建层返回可验证的创建/所有权事实；只有成功创建的本次文件才进入回滚删除。不能以路径存在或“进入了上传方法”为所有权证据。增加并发创建目标与本地源打开失败的回归测试。

### F2 / P1：下载只检查事前大小，流式传输未执行字节上限

位置：[SshSftpTransferSession.cs](../../Source/PuddingSsh/Transport/SshSftpTransferSession.cs)，324–348 行；[SshSftpChannel.cs](../../Source/PuddingSsh/Transport/SshSftpChannel.cs)，100–115 行。

`GetLength` 的检查无法约束随后读取的数据。下载通道没有 `maxBytes` 参数，写入流也没有预算包装；远端普通文件在 STAT 后增长时，会全部写入并发布，越过请求、主机配置乃至 256 MiB 硬上限。持续增长的文件还可能消耗大量本地磁盘。

证据 R2：STAT 报 1 字节，请求上限 1024 字节，实际读取 4096 字节；最终 `Completed`、`BytesTransferred=4096`，4096 字节文件已发布。

修补要求：在复制循环或有界目标流中逐次检查实际写入总量，超过预算立即中止、删除本次临时文件并返回 `ssh.transfer_too_large`。保留事前大小检查作为快速拒绝，但不能以它替代运行时限制。

### F3 / P1：结果阶段的能力探测绕过生命周期与有界 worker

位置：[SshOperationCoordinator.cs](../../Source/PuddingSsh/Execution/SshOperationCoordinator.cs)，1274 行；实际探测在 [SshSftpTransferSession.cs](../../Source/PuddingSsh/Transport/SshSftpTransferSession.cs)，83–154 行。

传输结束或已经超时后，协调器仍直接 `await session.GetCapabilitiesAsync(CancellationToken.None)`。此调用既不使用剩余预算，也不进入 worker/租约阶段记账。下载此前不会探测能力，所以这里会真实执行 SFTP scratch 创建、读取和重命名；网络卡住即可让业务等待越过 deadline 和清理宽限，妨碍后续关闭。探测抛出的普通异常也没有映射成结构化结果。

证据 R3：操作 deadline 150 ms、清理宽限 50 ms；400 ms 后调用仍未返回，`ActiveStageWorkers=0`；`StopAsync` 返回 `PendingOperations=1, TimedOut=true`。解除探测等待后，结果仍为 `Completed`。

证据 R4：真实下载会话通过假通道读到 `payload` 并发布本地文件；随后 scratch 写入被拒，协调器直接抛出 `UnauthorizedAccessException`，调用方收不到已完成的下载结果。旧报告已经声明“探测目录需可写”，本项新增缺陷重点是探测发生在发布后，且不受生命周期约束、异常外溢。

修补要求：上传必需的能力探测应作为提交前的有界阶段；结果只读取已有能力快照。下载不需要远端原子写能力，不能为了结果诊断额外执行远端写入。任何保留的探测都必须受 deadline、取消、worker 和错误分类合同约束。

### F4 / P2：取消后丢弃会话的残留文件证据

位置：[SshOperationCoordinator.cs](../../Source/PuddingSsh/Execution/SshOperationCoordinator.cs)，1251–1267、1299–1300 行。

取消赢得 `WaitStageAsync` 后，协调器创建一个默认 `TemporaryLeftBehind=false` 的结果；会话迟到返回的结果由 `onLateSuccess: static result => _ = result` 丢弃。即使会话在清理宽限内明确报告删除失败，最终结果也无法表达这个已知事实。连接关闭完成与文件清理完成是不同事实。

证据 R5：真实传输会话经受控通道写入 4 字节 `our-`，随后取消，删除被拒。最终回报 `Cancelled`、`CleanupState=Completed`、`TemporaryLeftBehind=false`、`TemporaryPath=null`，服务端替身上仍保留部分目标。

修补要求：在同一清理宽限内合并已完成传输任务的字节数和残留证据，同时保留本地 Cancelled/TimedOut 终态。若到期仍不知道文件是否残留，应明确表达“未知/待确认”，不能用默认 false 断言没有残留。

### F5 / P2：真实执行会话先用默认预算启动关闭，覆盖协调器收窄配置

位置：[SshOperationCoordinator.cs](../../Source/PuddingSsh/Execution/SshOperationCoordinator.cs)，897–911 行；[SshNetTransportSession.cs](../../Source/PuddingSsh/Transport/SshNetTransportSession.cs)，79–83、274–281 行。

协调器先调用 `RequestAbort()`，真实会话因此用默认 2 秒创建共享关闭任务；随后 `DisposeAsync(budget)` 复用这份任务，不能再采用传入的剩余额度。L4 的“预算已传入端口”测试使用假会话，未证明真实关闭状态机实际使用该预算。

证据 R6：使用真实 `SshNetTransportSession`，协调器配置 `CleanupGrace=50 ms`，正常 `TestAsync` 关闭后读到 `CloseBudget=2000 ms`。本例使用未连接客户端与内存生成的一次性私钥，只证明预算选取错误，不声称实测了 2 秒网络阻塞。协调器外层等待仍然有界，但后台关闭工作没有遵守配置的收窄额度。

修补要求：让中止请求与关闭预算共用一个入口，或让 `RequestAbort` 只登记意图，由带预算的关闭路径决定实际预算；需要直接针对真实适配器验证首次调用顺序。
