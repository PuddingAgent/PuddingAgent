# file_read 分页参数静默修复与部署验收

## 1. 修的是什么

同一个读取工具里并存三种静默，症状都是「回执看起来正常，但调用方无法判断自己给错了参数」：

| # | 旧行为 | 后果 |
|---|---|---|
| ① | `OffsetLines` ≥ 总行数时正文为空 | 与「文件真的是空的」不可区分 |
| ② | `LimitLines` ≤ 0 时正文为空 | 同上；而且回执里连 `[GUARDRAIL]` 都没有 |
| ③ | `OffsetLines` 为负时被静默按 0 处理 | 调用方要的是「负数 offset」，拿到的却是文件开头 |

**不算异常的一种**：`HeadLines` / `TailLines` 是「从一端取 N 行」的语义，N 超过总行数等于全取，这本来就不该报警——写成异常会让正常的「取前 1000 行」变成噪声。

## 2. 改法

新增一个纯判据，只看入参与总行数：

```csharp
internal static string? DescribePagingAnomaly(
    int? offsetLines, int? limitLines, int? headLines, int? tailLines, int totalLines)
```

回执里以 `... [PAGING: {notes}]` 追加，`notes` 为空则整行不出现。

关键在于**两条读取路径共用它**（`FileTools.cs:439` 小文件全读 / `:505` 大文件流式）。本类历史上同一个字段出现两种口径，成因就是分头实现——第十处 `META size` 把字节数写进 `chars` 字段也是同一模式。所以这次不是「在两处各加一段」，而是「一个判据两处调用」。

## 3. 取红

**本轮一手重放 M1**（修复轮记录的是 M1→2 红 / M2→1 红 / M3→1 红；本轮只重放 M1，M2/M3 仍为修复轮记录）：

| 项 | 实测 |
|---|---|
| 基线 SHA | `4F84B9C08DE093D2405C693A1F651BEEFE8FAB83BB7E7831039806A8A773D304` |
| 变异 | `else if (offsetLines.Value >= totalLines)` → 追加 `&& totalLines < 0`（分支恒假） |
| 字节变化 | +18，`CR_COUNT=898` 不变（CRLF 未被改动） |
| 结果 | 24 例中 **Failed=2 / Passed=22** |
| 红点① | `OffsetBeyondEnd_ReportsPagingNotice` — 字符串不含 `[PAGING:` |
| 红点② | `OffsetBeyondEnd_ReportsPagingNotice_OnLargeFilePath` — 同上 |
| 恢复 | SHA 与基线逐字节相同，touch mtime 后 `-t:Rebuild` → **24/24** |

两条红点分别落在小文件路径与大文件路径上，其余 22 条（含负 offset、`LimitLines<=0`、以及正向对照）全绿。这正是「共用判据」的证据：一个分支被关掉，两条路径同时失声，而不是只关掉其中一条的一半。

`Copy-Item` 会保留 mtime，msbuild 因此跳过重编译 —— 恢复后必须 `-t:Rebuild`，否则跑的仍是变异版，看上去「全绿」。

## 5. 行为层验收（真实调用，非推断）

被测文件为本 Agent 的 `goal.md`：**28 行 / 1767 字符 / 2857 字节**（META 自报，与第十处修复后的口径一致）。

| # | 入参 | 回执 |
|---|---|---|
| ① | `offset_lines=100000` `limit_lines=10` | `[PAGING: OffsetLines=100000 is at or beyond the end of the file (28 line(s), valid offset 0..27), so no line was returned.]` |
| ② | `offset_lines=0` `limit_lines=0` | `[PAGING: LimitLines=0 requests no line (must be >= 1), so the body is empty.]` |
| ③ | `offset_lines=-5` `limit_lines=3` | 正文首行 `# goal · 索引（正文见 Docs/**）` + `[PAGING: OffsetLines=-5 is negative and was applied as 0, so the window starts at the first line.]` |
| ④ | `offset_lines=2` `limit_lines=3`（正向对照） | **无** `[PAGING:` 行 |
| ⑤ | `head_lines=100`（> 28 行，正向对照） | **无** `[PAGING:` 行 |

③ 同时成立两件事：正文确实从第 1 行开始（`-5` 被按 0 处理），而且这件事被说出来——旧行为只做到前一半。

④⑤ 是「不要变成噪声」的对照。没有它们，一个恒发提示的实现也能让 ①②③ 全绿。

## 6. 同类未修：MaxChars 分支整体绕过分页参数

同一轮顺着「同类静默」排查时,拿到运行时样本：

| 入参 | 回执 |
|---|---|
| `max_chars=200` + `offset_lines=20` | 正文从**第 1 行**开始；尾行 `... (truncated at 200 chars, total 1767 chars, 28 lines, encoding=utf-8)`；**无** `[PAGING:` |

源码依据：

- `FileTools.cs:406` 的 `MaxChars` 分支排在 `HeadLines` / `TailLines` / `OffsetLines` 三个分支**之前**并直接 `return`，`windowStart` 固定为 0 ⇒ 分页参数全部作废。
- `FileTools.cs:467` 大文件路径同样整篇读入后从字符 0 截断。
- 工具描述（`FileTools.cs:196`）写的是「无论用分页参数、`FullFile` 还是 `MaxChars`，超预算即按字节截断并给出可直接照抄的 `OffsetLines` 续读位置」——该分支既不给续读位置，也是按**字符**而非字节。

**本轮不修**：修它等于改变 `MaxChars` 与分页的叠加语义（是先截窗还是先截预算），需要一并定这两条路径的契约，不宜与验收报告混在一次提交里。已登记为下一个原子任务。

## 7. 不声称的部分

- `M2`（负 offset 分支）、`M3`（`LimitLines<=0` 分支）**本轮未重放**，仍是修复轮的记录。
- ⑤ 只证明 `HeadLines` 超总行数不提示，没证明 `TailLines` 同款；两者共用 `headLines.HasValue || tailLines.HasValue` 的提前返回，但那只在源码层成立。
- §6 只有一条运行时样本（小文件路径），大文件 `MaxChars` 分支的行为来自源码阅读。

## 8. 一条过程性事实
