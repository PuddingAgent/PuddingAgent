# L2 code_map 覆盖盘点（判据修正版）

## 1. 为什么要重盘

本次会话给 19 个工程补了 L2，过程中我两次用错判据：

1. 第一轮按「名字含 `Test`/`Probe`/`Smoke`/`Fixture`」判测试工程 —— 把两个探针 CLI
   （`Pudding.Rpc.IpcProbe`、`PuddingRetrievalEvalProbe`，都有 `Program.cs`）当成测试工程漏掉。
2. 第二轮改用 `OutputType` + `Program.cs` —— 仍然错：**.NET 测试工程本身就是 `Exe`**，
   而且本仓大量测试工程把框架声明在 **`Sdk=` 属性**（`Sdk="MSTest.Sdk/4.0.1"`），
   **不在 `PackageReference` 里**。只查 `PackageReference` 会把它们误判成 `LIB`。

因此此前提交信息里的「60 个无 L2 = 6 应用 + 54 测试」「6 个应用」两组数字**作废**，
以本文为准。

## 2. 判据

判定顺序（前者优先）：

1. `Sdk` 属性含 `MSTest.Sdk` / `Microsoft.NET.Sdk.Test` / `xunit` / `NUnit`
2. `<IsTestProject>true</IsTestProject>`
3. `PackageReference` 含 `Microsoft.NET.Test.Sdk` / `xunit` / `NUnit` / `MSTest*`
4. 以上皆无时：`Sdk` 含 `.Web` ⇒ 站点；`OutputType` 为 `Exe`/`WinExe` 或有 `Program.cs` ⇒ 应用；否则库

**反例留档**：`OutputType=Exe` 且无 `Program.cs` 仍可能是 MSTest 工程
（`Tests/PuddingToolPlugins.IntegrationTests`：`Sdk=MSTest.Sdk/4.0.1`、`OutputType=Exe`、无 `Program.cs`）。

## 3. 盘点结果

| 类别 | 全部工程 | 无 L2 |
|---|---|---|
| 库（LIB） | 103 | **0** |
| 测试（TEST） | 102 | **55** |
| 应用（APP） | 26 | **0** |
| 站点（APP web） | 7 | **0** |
| 合计 | **238** | **55** |

**结论一**：所有**非测试**工程（103 + 26 + 7 = 136）**全部有 `code_map.md`**。
「生产类项目缺 L2」这件事已彻底关闭。

**结论二**：55 个无 L2 的工程**全部是测试工程**；而 102 个测试工程里有 47 个**有** L2。
同一类工程一半有一半没有 —— 这是**规范口径未裁定**，不是漏做。

## 4. 待裁定

「测试工程是否必建 L2 / 是否进 L1 子项目索引」两端都有先例：
已有 47 个测试工程建了 L2，说明这条路走过；另有 55 个没建，说明没有强制。

裁定前不擅自批量创建 —— 47 个既有 L2 的写法与粒度也不统一，批量补会把不一致放大。

## 5. 复现

判据实现见脚本逻辑（会话内 `temp/classify3.py`，未入库）：

```
遍历 Source/ Tests/ Samples/ 下含 *.csproj 的目录
读 csproj：Sdk 属性、OutputType、IsTestProject、PackageReference
按 §2 顺序分类；与目录下是否存在 code_map.md 求差集
```

盘点当日基线：`code_map_check --report` → `files_scanned 186 / error 0 / warn 64 / gate PASS`。
