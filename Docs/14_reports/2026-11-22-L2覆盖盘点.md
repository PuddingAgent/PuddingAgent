# L2 code_map 覆盖盘点（判据修正版）

## 1. 为什么要重盘

本次会话给 19 个工程补了 L2，过程中我两次用错判据：

1. 第一轮按「名字含 `Test`/`Probe`/`Smoke`/`Fixture`」判测试工程 —— 把两个探针 CLI
   （`Pudding.Rpc.IpcProbe`、`PuddingRetrievalEvalProbe`，都有 `Program.cs`）当成测试工程漏掉。
2. 第二轮改用 `OutputType` + `Program.cs` —— 仍然错：**.NET 测试工程本身就是 `Exe`**，
   而且本仓大量测试工程把框架声明在 **`Sdk=` 属性**（`Sdk="MSTest.Sdk/4.0.1"`），
   **不在 `PackageReference` 里**。只查 `PackageReference` 会把它们误判成 `LIB`。

因此此前提交信息里的「60 个无 L2 = 6 应用 + 54 测试」「6 个应用」两组数字**作废**，
以本文为准。

## 2. 判据

判定顺序（前者优先）：

1. `Sdk` 属性含 `MSTest.Sdk` / `Microsoft.NET.Sdk.Test` / `xunit` / `NUnit`
2. `<IsTestProject>true</IsTestProject>`
3. `PackageReference` 含 `Microsoft.NET.Test.Sdk` / `xunit` / `NUnit` / `MSTest*`
4. 以上皆无时：`Sdk` 含 `.Web` ⇒ 站点；`OutputType` 为 `Exe`/`WinExe` 或有 `Program.cs` ⇒ 应用；否则库

**反例留档**：`OutputType=Exe` 且无 `Program.cs` 仍可能是 MSTest 工程
（`Tests/PuddingToolPlugins.IntegrationTests`：`Sdk=MSTest.Sdk/4.0.1`、`OutputType=Exe`、无 `Program.cs`）。

## 6. 测试工程的 L2 现状调查（47 个已有 L2 的实测）

「测试工程是否必建 L2」这个裁定，不能只看数量（102 个里 47 有 / 55 无），
还要看**已有那 47 个长什么样**。实测结果：**三种形态并存，且全部通过门禁**。

| 形态 | 数量 | 特征 |
|---|---|---|
| 规范五列表 | **36** | `文件 / 目录 \| 用途 \| 关键符号 \| 关联 \| 约束` |
| 纯散文（无表） | **9** | 每个 `.cs` 一段话说明「验证了什么」，`条目数: 0` |
| 两列表 | **2** | `文件 \| 用途` |

### 6.1 为什么会出现纯散文形态

以 `Source/PuddingSlackTests/code_map.md` 为例，它的形状是：

```
# PuddingSlackTests
> 源指纹: TestResults/**=2-79f0490cd4fa, *.cs=4-abdf1ec29b2e, *.csproj=1-81b04285fda1 · 条目数: 0 · 最近整理: 2026-11-09

只引用 PuddingSlack。`SlackTests.cs` 验证协议过滤、线程路由、持久化/ACK 顺序、崩溃恢复及发送结果分类；…
`SlackTokenRotationTests.cs` 验证轮换 Token 原样传输、到期前刷新、双 Token 持久化、并发互斥与不确定刷新防重试。
…
```

**这是有道理的**：测试工程的价值单位不是「文件做什么」，而是「这些用例守住什么行为」。
五列的 `关键符号 / 关联 / 约束` 在测试工程上常常填不出东西，硬填就是编造；
而「验证了哪些行为」恰恰是散文形式的强项。

### 6.2 `条目数` 字段的另两种用法

实测 22 个测试 L2 的 `条目数` 与实际表格行数不等，原因分三类：

1. `条目数: 0` —— 纯散文形态，明确表示「本文件不按条目计数」（9 个）
2. `条目数: N` 而表里 0 行 —— 声明的 N 指**被覆盖的源文件数**而非表格行数（历史遗留写法）
3. 表里有行但 `条目数` 与行数不等 —— 上两项的混合

⇒ 检查器**不校验** `条目数` 与行数是否相等（无对应规则 ID），所以三种写法都能 PASS。
这不是缺陷报告，而是「口径未定义」的证据。

## 7. 结论（供裁定）

- 「测试工程是否必建 L2」**不是二选一**：还要同时决定**形态**（五列 / 散文 / 两列）
- 现状 **36 : 9 : 2** 说明五列是主流但非唯一，且另两种形态各有理由
- 在裁定前**批量补 55 个**会做两件事：放大形态不一致、并给「散文形态」的工程强加五列空字段
- 可执行的中间路线（若被采纳）：测试工程用**散文形态 + `条目数: 0`**，正文逐文件写「守住了什么」；
  与 `PuddingSlackTests` 等 9 个既有写法一致，不需要新规范

### 三条可复用的教训

1. **「有 X 个」的自述必须用另一种枚举核实** —— `files=66` 与「覆盖 66 个」可能来自同一个错 glob
2. **「目录里没有」≠「工程里没有」** —— .NET 的工程定义在 csproj，不在文件树
3. **报「全部覆盖」前先问「分母怎么来的」** —— 分母是「扫过的目录」而非「仓库全部」时，分子再对也无意义
