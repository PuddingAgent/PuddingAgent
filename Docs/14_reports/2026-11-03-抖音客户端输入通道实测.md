# 抖音 Windows 客户端输入通道实测

目标应用：`douyin.exe`，主窗口 hwnd `4331090`，无边框（客户区原点与窗口原点相同，2304×1315）。
内容区子窗口 `Chrome_RenderWidgetHostHWND`（本次实测为 `0x101694`）。

## 结论

| 通道 | 是否到达页面 | 证据 |
|---|---|---|
| 窗口消息左键（WM_MOUSEMOVE/DOWN/UP） | **是** | 左侧导航切页；搜索框点击使推荐下拉打开 / 关闭 |
| SendInput 键盘 · VK（空格） | **否** | 发送 2 个事件被接受，视频未暂停 |
| SendInput 键盘 · Unicode（`abc7`） | **否** | 8 个事件被接受，搜索框文本无变化 |
| SendInput 键盘 · Ctrl+V | **否** | 4 个按键被接受，剪贴板内容未粘贴 |
| 窗口消息右键（WM_RBUTTONDOWN/UP） | **否** | 无上下文菜单出现 |

即：**鼠标点击可达，键盘与右键菜单不可达。**

## 三个容易误判的点

**① 第一次点击会被「激活窗口」吃掉。**
同一坐标第一次点击搜索框，界面无任何变化；先做一次窗口激活后再点同一位置，推荐下拉才打开。
所以「点了没反应」不能直接判成「点击无效」，必须先证明窗口已处于激活状态。

**② 原生焦点判据对 Chromium 无效。**
探针在抖音上跑完六阶段，`GetGUIThreadInfo` 的 `hwndFocus` 始终是顶层 `Chrome_WidgetWin_1`，从未下探到内容区；
而同一探针在自建窗口上，点击后 `hwndFocus` 立刻变成 `Edit`。
结论不是「抖音没取得焦点」，而是**Chromium 把 Win32 焦点留在顶层窗口、DOM 焦点在其内部状态里**，
因此 `hwndFocus` / `hwndCaret` 只能报 unknown，不能当作「编辑节点是否聚焦」的判据。这一点修正了方案里对探针指标的预期。

**③ 点击生效与文字进入必须分开观测。**
下拉打开证明点击到达；文字未变化证明输入未到达。把两者混成一个「点了搜索框没反应」的结论，
会同时掩盖正确的一半和错误的一半。

## 探针自身的两处错误（由自建窗口正对照抓出）

1. `WNDCLASS` 结构体按 ANSI 封送，与 Unicode 版 `RegisterClass` 不匹配，导致建窗返回 `root=0x0`；
2. 自建窗口的点击坐标落在 EDIT 上方 20 px，焦点从未进入控件。

这两处在正对照里表现为「所有通道全灭」，若直接拿目标应用试，会被读成「应用拒绝一切输入」。
