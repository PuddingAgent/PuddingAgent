# 抖音 Windows 客户端输入通道实测

目标应用：`douyin.exe`，主窗口 hwnd `4331090`，无边框（客户区原点与窗口原点相同，2304×1315）。
内容区子窗口 `Chrome_RenderWidgetHostHWND`（本次实测为 `0x101694`）。

## 结论

| 通道 | 是否到达页面 | 证据 |
|---|---|---|
| 窗口消息左键（WM_MOUSEMOVE/DOWN/UP） | **是** | 左侧导航切页；搜索框点击使推荐下拉打开 / 关闭 |
| SendInput 键盘 · VK（空格） | **否** | 发送 2 个事件被接受，视频未暂停 |
| SendInput 键盘 · Unicode（`abc7`） | **否** | 8 个事件被接受，搜索框文本无变化 |
| SendInput 键盘 · Ctrl+V | **否** | 4 个按键被接受，剪贴板内容未粘贴 |
| 窗口消息右键（WM_RBUTTONDOWN/UP） | **否** | 无上下文菜单出现 |

即：**鼠标点击可达，键盘与右键菜单不可达。**

## 三个容易误判的点

**① 第一次点击会被「激活窗口」吃掉。**
同一坐标第一次点击搜索框，界面无任何变化；先做一次窗口激活后再点同一位置，推荐下拉才打开。
所以「点了没反应」不能直接判成「点击无效」，必须先证明窗口已处于激活状态。

**② 原生焦点判据对 Chromium 无效。**
探针在抖音上跑完六阶段，`GetGUIThreadInfo` 的 `hwndFocus` 始终是顶层 `Chrome_WidgetWin_1`，从未下探到内容区；
而同一探针在自建窗口上，点击后 `hwndFocus` 立刻变成 `Edit`。
结论不是「抖音没取得焦点」，而是**Chromium 把 Win32 焦点留在顶层窗口、DOM 焦点在其内部状态里**，
因此 `hwndFocus` / `hwndCaret` 只能报 unknown，不能当作「编辑节点是否聚焦」的判据。这一点修正了方案里对探针指标的预期。

**③ 点击生效与文字进入必须分开观测。**
下拉打开证明点击到达；文字未变化证明输入未到达。把两者混成一个「点了搜索框没反应」的结论，
会同时掩盖正确的一半和错误的一半。

## 探针自身的两处错误（由自建窗口正对照抓出）

1. `WNDCLASS` 结构体按 ANSI 封送，与 Unicode 版 `RegisterClass` 不匹配，导致建窗返回 `root=0x0`；
2. 自建窗口的点击坐标落在 EDIT 上方 20 px，焦点从未进入控件。

这两处在正对照里表现为「所有通道全灭」，若直接拿目标应用试，会被读成「应用拒绝一切输入」。

## 未做

- 右键菜单未出现，因此方案里的「菜单粘贴」路径在本机尚不可用；需要先解释右键为何不可达（是否与键盘同源）。
- 未做无障碍探测（UIA Raw/Control View、MSAA `AccessibleObjectFromWindow`）；这是方案里的第 ② 步。
- 未评估 HID / 驱动路线。

## 无障碍通道（补测，同日 23:40）

之前的「只有两个空 Pane」是**看错视图**：Control View 里确实只有 42 个节点且不含输入框，
但 Raw View 在同一窗口枚举到 600+ 节点（8 秒预算内截断），搜索框区域命中 15 个，其中：

```
ct=ControlType.Edit  rect=616,382 516x38  offscreen=False
```

这正是搜索框。MSAA 侧 `AccessibleObjectFromWindow(..., OBJID_CLIENT)` 在顶层窗口与 render 子窗口上
都返回对象（`hr=0x00000000`），说明无障碍通道存在，此前判断「进程没有无障碍能力」无效。

**写值实测成功**：

```
PATTERNS value=True  READONLY=False  BEFORE_LEN=8
SetValue("中文探针X1") → AFTER_LEN=6  MATCH=True
```

比读回值更强的证据是**页面据此重算**：搜索框显示新内容，推荐词变成「中文金属 测仪 / 探针-15米套装 /
中文示波器平板 / 中文示波器屏幕尺寸」。若只是 provider 缓存回显，推荐词不会变。

因此「点进搜索框 → 输入中文关键词」这一段**已经打通**，走的是无障碍写值，不是键盘。

**提交仍未解决**：搜索按钮在无障碍树里没有名字，对其坐标发窗口消息点击不触发导航；
改为点击第一条推荐词时坐标落进视频区，误入直播间。提交路径待定。

当前能力阶梯：**写值 ✓ / 提交 ✗**。

## 通道能力盘点（2026-11-04 00:00 补测）

在直播间页面上逐项实测：

| 能力 | 结果 | 说明 |
|---|---|---|
| ESC 返回 | **无效** | `SendInput`（2/2 被接受）与 `WM_KEYDOWN/UP` 投递顶层窗口，页面均无变化 |
| 其它快捷键 | **无效** | 与此前空格、Unicode、Ctrl+V 结论一致：键盘整体不可达 |
| 点击返回箭头 | **无效** | 同一坐标连点两次（间隔 800ms），页面不变化 |
| 拖动 | **未验证** | 见下 |

无障碍侧同样没有入口：该页面 Raw/Control View 都只有 78 个节点，
**全部是 `ControlType.Custom` 且 `name_len=0`**，没有 Button、没有命名控件，
因此 `InvokePattern` 这条路在这个页面上也无从下手。

与推荐页对比（同一窗口、同一天）：

| 页面 | 合成点击 | 无障碍 Edit | 能否写值 |
|---|---|---|---|
| 推荐/搜索页 | 有效（切页、下拉开合） | 有（`ControlType.Edit`） | 能（`Verified`） |
| 直播间页 | 无效 | 无 | 无 |

所以「返回」不要靠 ESC，也不要在直播间页硬点：**应当避免进入直播间**（此前一次误点视频区就进了），
或在进入后用页面自身的返回控件从推荐页层面处理。

拖动未验证的原因：当前页面连点击都不响应，任何拖动结果都会被误读成「拖动不可用」；
需要一个先被证明可点击的区域作为拖拽起点，否则测不出结论。

## 接入 Runtime 的边界约束（2026-11-04 00:10）

试图把 `UiaValueWriter` 接进 `computer_input` 时撞到编译期硬约束，已回退，工作树干净：

1. `PuddingRuntime` 与 `PuddingHost` 的目标框架是 **net10.0**（平台中立），
   而 `PuddingComputer.UIAutomation` 必须是 **net10.0-windows**：
   FlaUI 5.0.0 只提供 .NET Framework 资产，改成 net10.0 直接 `NU1701` 还原失败。
   ⇒ Runtime **不能**引用 UIAutomation，`computer_input` 目前拿不到写值能力。

2. 宿主 `PuddingDesktop` 虽然是 net10.0-windows，但 csproj 里有 `_ForbiddenShellReference`
   白名单，只允许引用固定几个工程；新增引用等于改架构门禁，不该顺手做。

三条候选（留给规划裁决，不在实测里选）：

| 方案 | 内容 | 代价 |
|---|---|---|
| A | `Pudding.Contracts` 定义 `IUiaValueWriter` 契约，UIAutomation 实现，由组合根注册 | 需要改 `PuddingDesktop` 白名单或在 CapabilityHost 注册 |
| B | `PuddingRuntime` 多目标 `net10.0;net10.0-windows`，条件引用 | 影响面大，波及所有引用 Runtime 的工程 |
| C | 写值做成独立可执行/工具，`computer_input` 经子进程调用 | 不引入程序集依赖，但多一层进程管理与超时语义 |

`PuddingComputer.Windows`（P/Invoke）是 net10.0，说明"Windows 专有能力放 net10.0"在本仓库有先例；
但 FlaUI 的包资产决定了 UIAutomation 无法跟随这一先例。

## FlaUI 路线的判定（2026-11-04 00:25）

**FlaUI 作为依赖是错的**，证据是包资产本身：

```
FlaUI.UIA3 5.0.0            => net48, net6.0-windows7.0, net8.0-windows7.0
Interop.UIAutomationClient  => net35, net40, net45, netcoreapp3.0, netstandard2.0
```

FlaUI 没有 `net10.0` 资产，最新也只到 `-windows` ⇒ 引用它的工程被迫变成 `net10.0-windows`
⇒ `PuddingRuntime`（net10.0）无法引用 ⇒ 写值能力进不了工具层。这条墙是 **FlaUI 带来的**，
不是 UI Automation 本身带来的。

**但换成 COM 互操作尚未被证明等价。** 实测（`.work/uia-interop-probe`，net10.0 控制台，
引用 `Interop.UIAutomationClient 10.19041.0`）：

| 项 | 结果 |
|---|---|
| 编译/还原 | ✅ 无 `NU1701`，net10.0 直接可用 |
| `new CUIAutomation()` / `CUIAutomation8()` | ✅ 创建成功 |
| `ElementFromHandle` | ✅ 拿到根，`class=Chrome_WidgetWin_1` |
| 根节点属性读取 | ✅ `name_len=2` |
| `FindAll(TreeScope_Subtree, TrueCondition)` | ❌ 只返回 1 个节点 |
| `RawViewWalker.GetFirstChildElement` | ❌ 返回 null |
| `FindAll(TreeScope_Children, ...)` 逐层 | ❌ 每层 0 个子节点 |

同一窗口、同一时段，FlaUI 版探针枚举到 78~606 个节点。**说明差异不在权限、不在会话，
而在"用什么调用唤醒并取得这棵树的子节点"**，这一点尚未定位。

**因此：不要现在就拆掉 FlaUI。** 下一步是找出 FlaUI 具体哪个调用唤醒了 provider
（候选：`AutomationElement.FindAllChildren` 内部的条件构造、事务超时设置、或
`AutomationElement.FromHandle` 之后的首次握手），能在 COM 层复现之后再迁。
迁移完成后 `PuddingComputer.UIAutomation` 可回退到 `net10.0`，Runtime 的 TFM 墙随之消失。

## 对照实验：不是唤醒问题，是客户端差异（2026-11-04 00:38）

假设「Chromium 无障碍树惰性构建、需先唤醒」（来自 DeepSeek Harness 的 macOS `AXManualAccessibility` 经验）
**已被排除**。同一 shell 内连续执行：

```
STEP1  FlaUI 探针：UIA_CONTROL_VIEW nodes=78 / UIA_RAW_VIEW nodes=78
STEP2  裸 COM 探针：ROOT=ok  VISITED=1  EDIT=none
```

FlaUI 刚拿到 78 个节点，紧接着的裸 COM 调用**仍只看到根节点**。
若差异来自「树没被唤醒」，第二步就应当能看到子树 —— 实测没有。

**因此结论改为**：差异在**客户端侧**，即「怎么创建 UIA 客户端、怎么发起子元素查询」，
不在目标应用、不在权限、不在会话、也不在唤醒时序。

下一步的唯一决定性实验：**在同一进程内**先用 FlaUI 枚举成功、再用裸 COM 查询同一窗口，
两侧结果并列打印。若同进程内也是 FlaUI 成功 / COM 失败，则差异纯在 API 用法，
可据此定位 FlaUI 内部实际调用的 coclass 与查询方式；此时才谈得上移除 FlaUI。

在此之前，`PuddingComputer.UIAutomation` 保持 FlaUI 不变，TFM 墙维持原状。

## 撤回：FlaUI vs 裸 COM 的对比结论不成立（2026-11-04 01:05）

今晚对「为什么 FlaUI 能枚举、裸 COM 不能」做了一连串对照，结果是**互相矛盾**的，且矛盾随进程与时刻变化：

| 时刻 | 进程 | 方式 | 结果 |
|---|---|---|---|
| 00:38 | ComputerUseFocusProbe | FlaUI TreeWalker | **78** |
| 00:45 | UiaAbProbe | FlaUI FindAll / COM FindAll / COM walker | 0 / 0 / 0 |
| 00:52 | ComputerUseFocusProbe | FlaUI TreeWalker | **78** |
| 00:52 紧接 | UiaAbProbe | FlaUI FindAll + COM | 0 / 0 |
| 01:00 | UiaAbProbe | 四格（库×方式） | 1 / 0 / 1 / 0 |
| 01:03 | UiaAbProbe（15 秒轮询） | FlaUI walker + COM walker | 0 / 0 |
| 01:03 前后 | ComputerUseFocusProbe | FlaUI TreeWalker | **78** |

**结论：同一窗口、紧邻时刻、不同可执行体之间，枚举结果在 0 与 78 之间摆动。**
在这种不稳定下，任何「A 库行、B 库不行」的判断都不可靠 —— 包括我 00:25 那版「COM 不等价」
和 00:38 那版「差异在客户端侧」。**两版都撤回，作为未证实的观察保留。**

已被排除的（这几条证据是确定的反向结果）：
- 不是权限、不是会话、不是窗口句柄错误（`IsWindow=True`，`ElementFromHandle` 成功且能读到 `Chrome_WidgetWin_1`）
- 不是 `WM_GETOBJECT(OBJID_CLIENT)` 唤醒（发出后 `result=0x0`，树仍为 0）
- 不是简单的「重试不够」（15 秒轮询仍是 0，而另一进程 1 秒内就拿到 78）

**因此下一步不是继续换库，而是先把测量协议做稳**，否则每一次实验都在测噪声：

1. **单进程内交错**：同一进程里 A/B/A/B 交替各 5 轮，记录每轮计数与时间戳
2. **状态可判**：每轮先读一个已知稳定的锚点（如根节点 class），再读子节点计数
3. **同一可执行体**：先让一个进程内两种客户端都跑，排除「可执行体差异」这个当前最大的混淆变量
4. 只有在该协议下 A 稳定 >0 且 B 稳定 =0，才谈得上「FlaUI 可以移除」

在此之前，`PuddingComputer.UIAutomation` 保持 FlaUI 不变。**先修仪器，再下结论。**

## 更正 + 全部观测点：这个指标是非平稳的（2026-11-04 00:50）

### 先更正一句话

我此前反复说「FlaUI 探针能枚举到 78 个节点」。**这句是错的。**
`TestScripts/ComputerUseFocusProbe/Program.cs` 的 a11y 部分 `using System.Windows.Automation;`，
用的是 **WPF 自带的 UIA 客户端**，不是 FlaUI。**FlaUI 在这台机器、这个应用上从未被证明可用**。

### 全部观测点（同一窗口 hwnd 0x421652）

| 时间 | 可执行体 | 客户端 | 节点数 |
|---|---|---|---|
| 00:38 | ComputerUseFocusProbe | **WPF UIA** | 78 |
| 00:45 | UiaAbProbe | FlaUI / 裸 COM | 0 / 0 |
| 00:52 | ComputerUseFocusProbe | **WPF UIA** | 78 |
| 01:00 | UiaAbProbe | FlaUI / 裸 COM（四格） | 1 / 0 / 1 / 0 |
| 01:03 | UiaAbProbe | FlaUI / 裸 COM（各 15 秒轮询） | 0 / 0 |
| 00:50 | UiaWpfProbe（仅 WPF，无 FlaUI 无 COM） | **WPF UIA** | **4** |
| 更早 | ComputerUseFocusProbe | WPF UIA | 606（截断） |

**同一个客户端（WPF UIA）在不同时刻给出 606 / 78 / 4 —— 指标非平稳。**
差异来源至少有两个：目标应用当前页面内容不同（推荐页 vs 直播间页），以及 Chromium
无障碍树的按需使能状态。在这两个变量被固定之前，任何跨进程、跨时刻的对比都不成立。

### 因此

- 「FlaUI 行不行」这个问题**目前无数据可判**，需要同一进程、同一页面、连续 N 次采样。
- 我此前关于 FlaUI/COM 的两版结论（00:25、00:38）继续作废。
- 下一步（未做）：把测量协议做成工具 —— 单进程内连续采样 N 次，每次记录
  `时间戳 / 根节点 class / 客户端 / 节点数 / 耗时`，输出 min-max 与唯一值集合；
  只有该序列稳定，才允许用它做选型判断。

## 预热修复的端到端验证：未生效（2026-11-04 01:20）

`05d7d93` 加了有界预热后，走**生产路径**（`FlaUiInspector.Capture`）对同一窗口连续采集 3 次：

```
round=1 availability=Sparse nodes=1 actionable=0 ms=857
round=2 availability=Sparse nodes=1 actionable=0 ms=820
round=3 availability=Sparse nodes=1 actionable=0 ms=826
```

**每次都等满了约 800 ms，节点数仍是 1。预热没有解决问题。**

这与同一天的采样结果（三种客户端稳定 78）矛盾，可能的解释有两个，都未证：

1. **实例缓存**：`FlaUiInspector` 在整个生命周期复用同一个 `UIA3Automation`（构造时创建），
   而采样探针每次新建实例。若该实例在树尚未建好时已缓存了空的结果，后续探测都拿到空。
2. **树状态又变了**：目标应用当前页面与采样时不同（直播间页 vs 推荐页）。

下一轮要做的判别实验（未做）：在**同一个进程**里对**同一个窗口**交替调用
「新实例 Capture」与「复用实例 Capture」，各 3 次；若新实例能读到 >1 而复用实例恒为 1，
则问题在实例缓存，修复方向是「探测失败时重建 automation 实例」而不是继续等待。

**结论纪律**：本次修复按单元逻辑是自洽的（47/47 绿、变异取红），但**端到端未证明有效**，
不能记为「已解决」。

## 判别实验：唤醒者是 WPF 客户端，不是预热时长（2026-11-04 01:30）

实验：同一进程内交替「每次新建 `FlaUiInspector`」与「复用同一实例」各 3 次（**不加唤醒**）：

```
fresh  round=1 nodes=1 ms=859      reused round=1 nodes=1 ms=823
fresh  round=2 nodes=1 ms=821      reused round=2 nodes=1 ms=823
fresh  round=3 nodes=1 ms=823      reused round=3 nodes=1 ms=824
```

⇒ **不是实例缓存**：新实例与复用实例完全一样，恒为 1，且每次都等满 800ms。

再实验：**先用 WPF UIA 客户端碰一下窗口**（`System.Windows.Automation` 读根节点的兄弟数），
随后同样调用 `FlaUiInspector.Capture`：

```
wpf-wake sibling_count=3
fresh  round=1 nodes=4 ms=19       reused round=1 nodes=4 ms=3
fresh  round=2 nodes=4 ms=2        reused round=2 nodes=4 ms=3
```

两条结论：

1. **FlaUI（以及裸 COM）单独无法唤醒** Chromium 的无障碍树；**WPF UIA 客户端可以**。
   唤醒后同一套 `FlaUiInspector` 立刻能读到子节点（1 → 4）。
2. **预热逻辑本身是有效的**：一旦读到子节点就立刻返回，耗时从 820ms 降到 2~19ms。
   之前的“预热无效”是因为**树根本没被唤醒**，不是预热判据写错。
