# bulk 预演「候选构成」行的运行时验收

## 为什么值得单独验

`cleanup-bulk` 的候选范围是**整个父会话**、单次最多 100 条、不限池化成员、删除后不可恢复。而它的预演回执此前只说「命中 100 条」并列出 10 条明细 —— 读的人无法判断**这些是谁的**，而决定「要不要删」的关键问题恰好就是：删掉会不会动到我还在用的成员。

`3c42267` 加了「候选构成」一行。当轮只有单测，本轮把它补到运行时。

## 先算期望，再看回执

不看回执再编解释，先用独立通道（只读 SQLite）复刻 `SelectForCleanup` 的选择规则，把期望值算出来：

```
选择规则（Source/PuddingPlatform/Services/SubAgentQueryFiltering.cs:76）
  跳过 running → 按 spawned_at 升序 → Take(100)
```

| 量 | 值 |
|---|---|
| 本会话投影总行 | 104 |
| 其中 running | 0 |
| 候选（最旧 100 条） | **100** |
| 候选里属于当前 5 个池化成员 | **1**（只 `frontend-ui`） |
| 候选里是历史记录 | **99** |
| 被 `MaxCount` 截掉的 4 条 | 含 `scout`、`probe-model` 两个**池成员** |

最后一行是这次设计的要点：`scout` 与 `probe-model` 的投影属于池成员，但因为它们**最新**而被 100 条上限截掉。所以「构成」必须按**候选集**算，不能按全会话算 —— 按全会话算会报 3 条池成员，而实际会被删的只有 1 条。

## 回执（真调、`dry_run=true`）

```
🔍 批量清理预演：命中 100 条（不限状态），**未删除任何内容**。
范围：本会话全部非运行中的子代理，单次最多 100 条，不限于池化成员。

候选（按最旧优先，最多列 10 条）：
- (未命名) | …-sub-534f8673 | 2026-11-14 13:42 | failed
- (未命名) | …-sub-ed451fcc | 2026-11-14 15:26 | completed
… 共 10 条
- …另有 90 条未列出
构成：其中 1 条属于当前池化成员（frontend-ui），另有 99 条是已不在池中的历史记录。
      删除的是运行归档，成员本身仍留在池中。
```

逐项对账：

| 项 | 期望 | 回执 |
|---|---|---|
| 命中数 | 100 | 100 ✅ |
| 池成员条数 | 1 | 1 ✅ |
| 池成员名 | `frontend-ui` | `frontend-ui` ✅ |
| 历史条数 | 99 | 99 ✅ |
| 明细首条时刻 | 05:42 UTC → 本地 13:42 | `2026-11-14 13:42` ✅ |
| 未列出数 | 90 | 90 ✅ |

首条时刻顺带验了 UTC→本地渲染（源值 `2026-11-14T05:42:15Z`，回执 `13:42`）。

## 事后：四项计数不变

| 指标 | 调用前 | 调用后 |
|---|---|---|
| `session_sub_agents` | 1670 | 1670 |
| `sub_agent_runs` | 1861 | 1861 |
| `agent_pool` active | 5 | 5 |
| `agent_pool` 软删 | 4 | 4 |

这是 `dry_run` 参数绑定的**第二次**独立验证（上一次在 01:26，也是 100 条满候选、计数不变）。必要性在于：`DryRun` 是 `bool?`，未绑定就取默认 `false` ⇒ **直接真删**。本会话此刻的候选是 100 条中的 99 条历史归档，误删不可恢复。

调用前先把本会话 104 行投影（`Id`/`sub_session_id`/`status`/`spawned_at`/`display_name`）落盘到 `temp/bulk_pre_dump.json`，用于事后比对；本报告只用到计数，dump 为异常时的定位依据。

## 边界（不声称已覆盖）

- **池未就绪分支未在运行时验证**：让 `ISubAgentPool` 在预演期间不可用需要人为破坏 DI，代价大于收益。该分支由单测 `Composition_PoolUnavailable…` 守护（变异 M1 可打红）。
- **真删路径仍只有预演层证据**。要取红必须真的删掉 ≤100 条运行归档（含磁盘目录、不可恢复），且候选集由父会话决定、无法缩小到一次性探针 —— 因此这一条需要显式授权才能做，不作为自主推进项。
- 回执的「另有 N 条未列出」是把 `candidates.Count - PreviewLimit` 直接相减；候选 ≤10 时不出现该行 —— 已由下文「补验」臂 3（5 条候选）在运行时覆盖。
- 候选**全部**属于池成员的分支（措辞「全部 N 条都属于当前池化成员」）仍只有单测：造出它需要候选集恰好等于池成员投影集合，现有筛选维度（状态 + 时间窗）做不到。

## 结论

`3c42267` 的构成行在运行时成立，且数字与独立算出的期望逐项吻合。原先「bulk 预演构成只有单测」从待办里销掉。

剩余未覆盖不变：`cleanup-bulk` 真删、忙碌条目清理顺序、zhihu 时区独立真值、`IndexEntry` 同名换对象分支。

## 补验：筛选分支与小样本截断（同日 06:58）

上一版把「候选 ≤10 时不出现『另有 N 条未列出』」标为未覆盖。本轮补三臂，仍全部 `dry_run=true`，期望值同样先由只读 SQL 算出（复刻「状态筛选 → 时间窗 → `spawned_at` 升序 → `Take(100)`」）：

| 臂 | 入参 | 期望（独立通道） | 回执 |
|---|---|---|---|
| 1 | `status=all` + `older_than_days=10` | 16 条 / 池成员 0 | 16 条，「另有 6 条未列出」 |
| 2 | `status=failed` | 32 条 / 池成员 0 | 32 条，「另有 22 条未列出」 |
| 3 | `status=failed` + `older_than_days=10` | 5 条 / 池成员 0 | 5 条，**无**「另有」行 |

三点成立：

1. `HasStatusFilter` 与 `OlderThanDays` 在运行时都生效。臂 3 = 臂 2（32）∩ 臂 1（16）的结果为 5；单看任一臂都证明不了组合，三者一起才闭环。
2. 小样本分支（≤10）确实不输出「另有」行 —— 上一版的未覆盖项销掉。
3. 构成行这次走的是 **owned=0** 分支，措辞「全部不属于现存池化成员，都是历史记录。」—— 与上一轮 1/99 那条是不同分支，两种措辞现有各自运行时样本。

事后计数不变：`session_sub_agents 1670`、`sub_agent_runs 1861`、`agent_pool active 5 / 软删 4`。这是 `dry_run` 绑定的第三次验证，但**不作为独立证据计数** —— 同一构建、同一代码路径，重复验证不增加可信度，它只说明这次也没出事。

仍未覆盖：候选**全部**属于池成员那条措辞分支（需要候选集恰好等于池成员投影集合，现有筛选维度造不出）；池未就绪分支（需人为破坏 DI）。
