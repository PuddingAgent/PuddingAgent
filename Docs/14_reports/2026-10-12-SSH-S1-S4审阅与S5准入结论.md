## 2. 发现（按优先级）

### F1 / P1：cd 失败后复合命令仍执行

位置：[SshPosixCommand.cs](../../Source/PuddingSsh/Validation/SshPosixCommand.cs:77)。Compose 生成 `cd -- '<cwd>' && <command>`，只有 command 的第一段受 `&&` 限制。

不存在的 cwd 为 `/__pudding_ssh_review_missing_directory__`。以下三个命令的真实 `/bin/sh` 结果均为 **stdout=SECOND，exit=0**：

```sh
printf FIRST; printf SECOND
printf FIRST
printf SECOND
printf FIRST || printf SECOND
```

上述代码块第二/三行是一个带换行的独立案例，其他两行分别为分号和 OR 案例。第一段被 cd 失败跳过，后续段仍执行并覆盖失败退出码；实际部署命令可能在账号默认目录写文件。

这是原设计与实现共享的缺陷，不能只责令实现“遵守原设计”。ADR-096 D1 改为先执行 `cd ... || exit $?` 的独立行。

在临时 harness 中用建议格式重复同三例，真实 `/bin/sh` 均为 **stdout 为空、exit=2**；该观察验证设计方向，生产 Compose 尚未修改。

### F2 / P1：取消/截止没有挡住后续副作用

位置：[SshOperationCoordinator.cs](../../Source/PuddingSsh/Execution/SshOperationCoordinator.cs:316)，身份与建连为直接 await；准入快路径没有检查已取消 token，建连返回后也未复检。

| 反例 | 实际结果 | 应有结果 |
|---|---|---|
| token 在调用 ExecuteAsync 前已 Cancel，使用既有 FakeIdentity/FakeTransport/FakeSession | `Completed / Exited`；身份读取 1、连接 1、执行 1 | `Cancelled / NotSubmitted`，三个调用数为 0 |
| Connect 返回未完成 TCS，忽略 token；host deadline=100 ms | 350 ms 时操作仍未返回、in-flight=1 | 在 deadline + 清理预算内返回，不能无限 await |
| 上述 TCS 在 350 ms 后交还 FakeSession | `Completed / Exited`；执行次数=1 | 只回收迟到连接；执行次数=0 |
| IdentityProvider 返回未完成 ValueTask，忽略 token；同样 100 ms deadline | 350 ms 时仍未返回；交还 identity 后 `ssh_test` 连接 1 次并 Completed | 只销毁迟到材料；不得启动连接 |

已有 `ConnectDeadline_IsBounded` 使用 `Task.Delay(infinite, ct)`，只验证合作的实现，所以没有检出这些反例。真实适配器中仍有同步阶段，不能把“传 token”当作阶段围栏。

### F3 / P1：排空宽限之后仍无条件等待

位置：[SshNetTransportSession.cs](../../Source/PuddingSsh/Transport/SshNetTransportSession.cs:247)。`Task.WhenAny(drains, Delay(2s))` 后立即 `await drains`，没有分支处理超时。

将一个 drain 设置为不完成的 TCS，另一个为 CompletedTask，反射调用**实际** DrainWithGraceAsync；等待 2250 ms 后仍 `IsCompleted=false`。最后解除 TCS 才结束观察。

正常 exec 完成后，外层操作 timer 仍可能一直等待到 60/600 秒，之后只能放弃会话任务；这不是 2 秒排空宽限。外层 Dispose 超时也不能证明线程/连接实际回收。修补需要单一资源回收期限、Abort 与迟到任务所有权，不能只在此处删一行 await。

### F4 / P2：输出读取错误伪装为正常 EOF

位置：[SshBoundedOutputCollector.cs](../../Source/PuddingSsh/Execution/SshBoundedOutputCollector.cs:101)。读异常被 catch 后 break，没有错误或不完整标记。

自定义 Stream 首次返回 `hello`，第二次抛 IOException；实际 drain **成功完成**、输出 `hello`、`IsTruncated=false`。若主执行任务有 exit=0，现有结果无法表达输出丢失。应独立报告 output_complete 与原因，并保留已知退出码。

### F5 / P2：声明的硬限额未被强制

位置：[SshOperationCoordinator.cs](../../Source/PuddingSsh/Execution/SshOperationCoordinator.cs:52)、[SshLimits.cs](../../Source/PuddingSsh/Contracts/SshLimits.cs:46)。

实际构造 `CoreMaxConcurrentOperations=9 / MaxWaitQueueLength=33 / CleanupGrace=1 day` 被接受；`MaxOperationTimeoutSeconds=601` 的解析结果为 601 秒。组件只能收窄的公开约束与代码不一致；不能依赖尚未实现的 Runtime 配置校验补救。

## 3. 其他需随修补覆盖的代码路径

- Transport 在 `sshCommand.ExecuteAsync` 返回 Task **之后**才标记 submitted；开始提交窗口的异常需保守处理。本次没有注入真实“发送后同步抛错”，不得将其写成已发生的协议事故。
- Transport 的 Diagnostic 直接包含 `ex.Message`；known_hosts 解析诊断包含整行。这违反公开诊断的有界/不透传载荷合同，应使用稳定原因与行号，并用哨兵字符串回归。
- 测试 SDK 另把 coverage 写入源码 `Source/PuddingSshTests/TestResults`；本次已把生成文件移到审阅的 temp/test-out 范围。后续测试配置应显式指定 coverage 目录，避免仅指定 TRX 目录仍散落产物。
- 原 source code_map 含多段历史验收数字；本次不追加这些段落，新的审阅证据只在本文与 changelog 保存。

## 4. 下一步

先执行 R1–R5 组件内修补，每步独立测试与提交；再重跑修补扩展的真实协议矩阵。只有新的取消前置零副作用、cd 失败零后续执行、迟到资源不继续执行、有界排空与完整输出事实均成立，才给出 S5 准入结论。

Runtime 的路径/ACL/revision 与 A6 产品态验收仍是后续任务。此次不通过不撤销现有组件边界与已有正向用例的价值，也不表示已验证的 known_hosts/pin 路径全部失效。
