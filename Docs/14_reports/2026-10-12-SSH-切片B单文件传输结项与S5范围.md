# SSH 切片 B（单文件 SFTP 传输）组件内核结项与 S5 范围更新（2026-10-12）

> **结论**：切片 B 的**组件内核**完成（B1–B4，四步原子提交），单测与真实 OpenSSH 门禁通过；
> **仍未接入宿主**（`ssh_upload`/`ssh_download` 工具、审批与主机配置属 S5）。SCP 按设计不采用，文件传输即 SFTP。

## 1. 交付能力（组件内）

| 能力 | 契约/实现 | 门禁 |
|---|---|---|
| 单文件上传/下载 | `SshUploadRequest`/`SshDownloadRequest` + `ISshClient.UploadAsync/DownloadAsync`（协调器入口） | B3 10 例 + 真实 `transfer` 场景 |
| 字节限额 | 默认 64 MiB、硬上限 256 MiB；请求 0/负数 `ssh.request_invalid`、超硬上限 `ssh.transfer_too_large`；流式复制、超限立即中止 | B1 + B4（超限零残留） |
| 本地路径 | 执行快照工作区为根；**单一权威包含判定**（`GetRelativePath`，非字符串前缀）；逐段拒绝重解析点；拒绝目录/非普通文件；上传源前置大小校验 | B1 31 例 + 双向变异取红 |
| 远端路径 | POSIX 规范化、控制字符/目录标记拒绝、词法消解 `..`、允许根包含、父目录 **realpath** 根内（符号链接逃逸拒绝）；上传/下载根**分别建模** | B1 + B4（越界/跨根三类拒绝） |
| 发布语义 | 全部由**实测能力**支撑：`overwrite=false` 用排他创建（`SSH_FXF_EXCL`）原子占位，失败/取消删除我们创建的目标；`overwrite=true` 用临时文件 + posix-rename 原子替换；不支持即 `ssh.transfer_unsupported` | B2 16 例 + 三处变异取红 + B4 实测 |
| 取消与清理 | 本端终止后如实映射 Cancelled/TimedOut；删除本次目标/临时文件；清理失败明确报告 `TemporaryLeftBehind` + 路径；带预算释放**先等飞行中的传输清理再关通道** | B4 出带 sha256 抓到真缺陷并修复；新增门禁 + 变异取红 |
| 生命周期复用 | 与执行路径**共用**准入/前置围栏/操作 lifetime/资源租约/单一清理预算/隔离区/身份所有权；主机未配置传输限额 ⇒ `ssh.transfer_unavailable`关闭式失败 | B3（含未配置限额、预先取消、释放不收敛、迟到连接不传输） |

## 3. 过程中发现的真问题（都来自真实门禁）

1. **夹具不支持 SFTP**：自定义 `sshd_config` 不继承 `/etc/ssh/sshd_config` 的 `Subsystem` 行，
   缺 `Subsystem sftp` 时 `SftpClient.Connect()` 被拒（`phase=Connecting` + 裸 `SshException`）。
   已补 `Subsystem sftp internal-sftp`。**单元测试永远发现不了这一条**。
2. **关闭掐断飞行中传输的清理路径**：本地 deadline 触发后协调器立即关通道，仍在写入的传输来不及删除
   自己的目标，服务端留下**部分写入的 `big.bin`**——客户端自述 `left_behind=False`，
   只有**出带 sha256** 才暴露。已改为「先登记中止 → 有界等待飞行中的传输完成清理 → 再关通道」，
   并加门禁（变异取红证明该门禁真的敏感）。
3. **实测修正假设**：OpenSSH `internal-sftp` 的标准 SFTP RENAME **不覆盖**已有目标
   （`rename_no_overwrite=True`），与 B2 基于文档的推断相反。实现按实测能力选择语义，
   因此覆盖与否都不会用竞态冒充原子性。

## 4. 需要审阅人知晓的设计取舍（已按你的裁定固化）

方案 §11.1 字面是「先写临时文件，完成后发布」。真实能力显示「不覆盖发布」在 SFTP 上没有可靠
rename 原语，因此实现为：`overwrite=false` → **排他创建原子占位**（失败/取消删除本次目标）；
`overwrite=true` → 临时文件 + posix-rename 原子替换。你已裁定「保留当前实现」。

## 5. 残留限制（如实列出）

1. **传输限额尚无人配置入口**：`SshHostContext.Transfer` 由调用方给出，宿主侧 `hosts.json`（含上传/下载根）
   属 S5。
2. **远端路径检查不是沙箱**：SFTP 的检查与打开之间仍有服务端竞态，严格隔离必须远端 chroot/受限账号。
3. **本地发布**用 .NET `File.Move(overwrite:false)`；同一台机器上并发写同一目标仍有 TOCTOU（已声明）。
4. **无断点续传/不自动重试**（设计如此）；不声明"哈希已校验"，只在双方都实算同一份数据时给出哈希
   （探针的服务端 sha 是独立计算的真实证据）。
5. **能力探测会在允许根内创建并清理 scratch 文件**：要求该根可写（root 本身即写入目标目录）。
6. **迟到完成的传输可能留下完整目标**：本端终止事实与"目标是否存在"是两件事，门禁断言的是
   **不得留下部分目标**（存在则必须字节完整）。
7. **仅单文件**：无目录递归、无设备文件、无多文件批处理。
8. 未改宿主：`ssh_upload`/`ssh_download` 工具、`RequiresFileWrite` 声明与审批绑定均属 S5。

## 6. S5 范围更新

S5 现在包含**两个切片**的接入：

| 项 | 内容 |
|---|---|
| 工具 | `ssh_hosts`、`ssh_test`、`ssh_execute`（切片 A）+ `ssh_upload`、`ssh_download`（切片 B）= **5 个** |
| 审批 | 主机 ACL 与 pin 校验；上传声明远端写入语义；下载声明 `RequiresFileWrite` 并校验本地边界 |
| 配置 | `<DataRoot>/config/ssh/hosts.json`：主机授权、目录模式、identity 文件名、信任来源、执行限额，**以及分别的允许上传/下载根** |
| 隔离 | 跨平台 `.ssh` 与私有目录解析、路径/owner/ACL、revision 与可见性 |
| 组合 | DI 装配与宿主组合测试；缺配置仍可启动 |
| 外部 | A6：外部部署新构建 → 进程内功能 smoke（5 个工具）→ 外部控制器判定连接/资源回收 |

**边界不变**：S5 结论给出前不修改 Runtime/Host/DI/slnx/工具/审批。
