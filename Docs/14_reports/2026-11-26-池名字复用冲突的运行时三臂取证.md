# 池名字复用冲突的运行时三臂取证

## 为什么还要补这一轮

`dc26ea5` 把 `pool_action="cleanup"` 的「名字 ↔ `sub_agent_id` 冲突」从静默取名字改成了拒绝，理由是名字不是稳定键：

```
IX_agent_pool_name 是 WHERE deleted_at IS NULL 的部分唯一索引 ⇒ 销毁即释放名字
```

重试场景下调用方会同时带 `pool_name`（提示里抄来的旧名字）与 `sub_agent_id`（真实目标）。若名字已被新成员占用，旧实现让名字优先 ⇒ 清掉的是新成员的运行归档，随后销毁也落到新成员身上，而回执里写的是调用方拼的那个名字。

当轮只在单测层构造了这个场景，因为**运行时重放会真的删掉一条运行归档**。goal 把「名字复用冲突只有单测层」记为未覆盖项。本轮用一次性探针补齐。

## 三臂

| 臂 | 入参 | 期望 | 实测 |
|---|---|---|---|
| A 冲突 | `pool_name=probe-conflict-1126`（=B）＋ `sub_agent_id=…-sub-140f2441`（=A，已销毁） | 拒绝 | ✅ 拒绝，回执回显两个 id 并说明名字可被复用 |
| B 只给名字 | `pool_name=probe-conflict-1126` | 放行 | ✅ 已清理 + 池条目已销毁，未被误拒 |
| C 名字失效 + 旧 id | `pool_name=probe-notexist-1126` ＋ `sub_agent_id=…-sub-140f2441` | 放行回退 | ✅ 未拒绝，报「池条目不存在或已销毁」+「运行归档本就不存在」 |

臂 A 的拒绝回执原文（节选）：

```
子代理名 'probe-conflict-1126' 与 sub_agent_id 指向不同成员，已拒绝执行。
- 名字当前解析到：3f52368a35ef49ab834991e897e8715f-sub-901d1ad2
- sub_agent_id 给的是：3f52368a35ef49ab834991e897e8715f-sub-140f2441
```

## 臂 A 之后的存活核对

拒绝只是「没做」，还需要证明「没做错事」。冲突请求之后立即读库：

| 指标 | 冲突前 | 冲突后 |
|---|---|---|
| `agent_pool` active | 6（5 原有 + B） | 6 |
| `agent_pool` 软删 | 3（2 原有 + A） | 3 |
| `sub_agent_runs` | 1861 | 1861 |
| `session_sub_agents` | 1670 | 1670 |
| probe B 行 | `idle`, `deleted_at=NULL` | `idle`, `deleted_at=NULL` |

B 的 `sub_session_id`（`…-sub-901d1ad2`）与 A（`…-sub-140f2441`）不同，证明名字复用确实发生，被拒绝的请求没有落到 B 身上。

## 收尾与数据安全

三臂做完后的最终状态：

| 指标 | 基线 | 结束 |
|---|---|---|
| `agent_pool` active | 5 | **5** |
| `agent_pool` 软删 | 2 | 4（两条探针墓碑） |
| `sub_agent_runs` | 1861 | 1861 |
| `session_sub_agents` | 1670 | 1670 |

活跃成员仍是 `advisor` / `frontend-ui` / `probe-model` / `reviewer` / `scout`，内存 `pool_action="list"` 与库一致，`reviewer` 仍在（上一轮刚从软删恢复）。

全程只用一次性探针（`probe-conflict-1126` 创建两次、`probe-notexist-1126` 仅作为名字入参），**未对用户真实成员做任何写操作**。探针留下的两行 `dead` 墓碑属既有软删除设计，列表不可见。

## 一条被纠正的表述

此前把回退路径描述为「条目已销毁后用 `sub_agent_id` 重试」。实测 `cleanup` **强制要求 `pool_name` 非空**：

```
pool_action=cleanup 需要 pool_name。先用 pool_action=list 查看可用条目名。
```

所以「只给 `sub_agent_id`」不是合法形态。真实的重试形态是「名字仍给着但已解析不到 + 旧 id」。臂 C 证明这条路径没有被新加的拒绝逻辑误伤 —— 这正是变异 M2（无条件拒绝）在单测层打红的那条，现在运行时也成立。

## 边界（保持诚实）

- **未做运行时变异**：取红需要改代码再 build-restart，会中断当前回合。单测层已有 M1（去掉拒绝 → 1 红）与 M2（无条件拒绝 → 3 红）。
- 臂 B 只是「只给名字」的正常路径；`pool_name` 指向**忙碌**条目时的「先销毁再清理」顺序分支仍未在运行时验过。
- `cleanup-bulk` 的「真删」仍只有预演层证据。

## 结论

「名字复用冲突只有单测层」这条未覆盖项可以销掉：真实调用路径确实经过冲突判据，且拒绝之后目标成员与四项计数均未变动。

剩余未覆盖项不变：`cleanup-bulk` 真删、忙碌条目清理顺序、zhihu 时区独立真值、`IndexEntry` 同名换对象分支。
