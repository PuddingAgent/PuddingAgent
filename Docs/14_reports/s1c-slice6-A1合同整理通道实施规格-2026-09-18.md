## SUMMARY
【已批准】D1–D3：A1 是“Agent 回合提出结构化合同提议→平台验证→提交”，不新增 Agent Goal 工具；objective 由用户创作、迭代内不改。
【事实】现有合同生成仅由 `GoalSettlementWorker.cs:85-107` 触发，`GoalAcceptanceContractPlanner.cs:47-53` 对已有条件直接拒写；A1 尚无生产入口，以下为新增接线规格而非已实现声明。
【结论】应复用 canonical Goal Turn 的结构化 Runtime envelope（`AgentLoopResponse`），把 proposal 作为受控 metadata 事实随 `turn.completed` 持久化；不得把普通 reply、DONE、plan.proposal 或 Agent goal.md 当合同写入口。
【范围】本文件只写实现规格；本轮未改产品代码、未构建/测试、未做 git 写。
## A1_SHAPE
1. **提议载体**：仅 Goal-managed canonical Turn 允许 Runtime envelope 的 `meta.goal_contract_proposal`（复用 `AgentLoopResponse.Status/Message/Tool/Meta`：`Source/PuddingRuntime/Services/AgentLoop/AgentLoopResponse.cs:8-25,118-136`）；它是隐藏结构化 metadata，用户可见 `message` 保持自然语言/指定文本。禁止新增 `goal_create/goal_update` 工具，禁止把 `plan.proposal`（`Source/PuddingPlatform/Services/ConversationEventStore.cs:550-580,673-685`）误作 Goal 合同入口，禁止读取 goal.md。
2. **最小 payload**：`schemaVersion=1, kind="refine_acceptance_contract", expectedContractVersion, criteria[]`；每项只允许 `requirement`, `requirementRefs[]`（对 objective 的精确引用/覆盖说明）, `verification.kind`, `verification.definitionRef`, `verification.inputRefs[]`, `verification.expectedText?`。Agent 不得提交 `goalRunId/activationEpoch/turnId/criterionRevision/definitionHash/source/status/passed`；未知/额外字段 fail-closed。平台从可信 candidate/DB 派生这些字段。
3. **传播调用链**：`AgentLoopResponse.Parse` → Runtime terminal `done` payload → `TurnExecutorAdapter.ConvertFrame`/`TurnTerminalInfo`（`Source/PuddingRuntime/Services/TurnExecutorAdapter.cs:143-173`、`Source/PuddingCore/Runtime/ITurnExecutor.cs:140-167`）→ `ExecutionRunCoordinator.ExecuteLoopAsync`（`Source/PuddingPlatform/Services/AgentChat/ExecutionRunCoordinator.cs:580-628`）→ `SqliteExecutionJournal.BuildTerminalPayload`（`Source/PuddingPlatform/Services/Execution/SqliteExecutionJournal.cs:955-966`）→ `conversation_events.turn.completed` → `GoalSettlementStore.GetCandidatesAsync` 的 terminal/reply 读取（`:307-339`）→ `GoalSettlementWorker.SettleCandidateAsync`（`Source/PuddingPlatform/Services/Goals/GoalSettlementWorker.cs:79-107`）。proposal 必须独立于 reply 原文持久化；建议新增 Core `GoalContractProposal` 类型，并让 `TurnTerminalInfo` 携带可空 typed proposal，禁止从普通 reply 二次猜测。
4. **服务端验证**：在 `GoalSettlementWorker` 调用新 `GoalContractProposalValidator`（建议 `Source/PuddingPlatform/Services/Goals/GoalContractProposalValidator.cs`）后，交给新 `GoalContractRefinementStore`（同目录）在单 SQLite 事务中 CAS 提交。绑定来自 candidate 的 `(GoalRunId, ActivationEpoch, ObjectiveVersion, TurnId, AggregateVersion)`，不信 proposal 自报身份；proposal 仅接受该 canonical Turn 的 `turn.completed`、`EvidenceComplete=true`、当前 Goal Active、`ToolCalls`/预算事实与目标约束一致。
5. **版本/防伪**：读取当前合同 `source`, `ContractVersion`, `CriteriaJson`, `ChecksJson`, `PlanFingerprint`（`GoalAcceptanceContractStore.cs:18-31,35-95`）；要求 `existing.Source == bounded_planning`、`expectedContractVersion == existing.ContractVersion`，且 objective 原文/ObjectiveVersion、ActivationEpoch、candidate TurnId 与当前持久 Goal 逐项相等。平台拒绝 Agent 提交的 hash/revision/source，改由 Registry/Planner 计算（`GoalCheckDefinitionRegistry.cs:31-76`；`GoalAcceptanceContractPlanner.cs:66-105`）。文本断言必须使用已登记 `checks/text-assertion.md#equals` + `text-assertion`，ordinal exact；期望文本进 `DefinitionHash`。
6. **提交与幂等**：canonical operation key = `SHA-256(goalRunId|activationEpoch|objectiveVersion|turnId|canonicalProposalJson)`；服务端派生，不接受 Agent proposalId。合同写入采用 `UPDATE ... WHERE ContractVersion=expectedContractVersion AND Source='bounded_planning'`；0 行即 CAS 冲突，重新读取后：若已存在同 operation key 的 `goal.contract_refined` 事件返回 already-applied，否则拒绝 stale/concurrent。成功同事务追加 `goal.contract_refined` 审计事件，payload 只存 operation key、old/new ContractVersion、criterion IDs、hash 摘要，不存原始自然语言；该事件需登记到 `Source/PuddingCore/Goals/GoalEventTypes.cs:10-75`，并沿 `GoalRunStore` 现有 Goal 事件事务写入，不新增表/列。
7. **一次性闸**：成功后 source 改为受控非纯门禁值 `agent_refined`（新增 Core 词表常量，短于现 `source` 约束；现 `bounded_planning:objective_evidence` 已超过实体 `MaxLength(32)` 风险见 `GoalAcceptanceContractEntity.cs:42-47`，本片不扩大该修复）；同一 `(goal,epoch,objectiveVersion)` 再次只能返回 already-applied/needs_user，绝不二次覆盖。覆盖门本体不改：`ConservativeGoalIterationVerifier.cs:122-139` 仍只拦 `IsEngineeringGatesOnly`。
8. **并发语义**：两 Agent/重放提议竞争同一合同版本时仅一个 CAS 成功；另一方不得覆盖或追加第二份条件。不同提议均不自动合并；失败转 `contract_refinement_conflict`/needs_user，保留 objective 与既有合同。## WHY_IT_UNBLOCKS
1. UI 一行 objective 无 `证据:` 标记 → `GoalObjectiveEvidenceParser.Extract` 返回 `HasAny=false`（`GoalObjectiveEvidenceParser.cs:30-96`）。
2. 初始 planner 仍可生成 `bounded_planning` build/test 护栏（`GoalAcceptanceContractPlanner.cs:54-105`）；全绿后 S1-a 正确返回 `contract_coverage_insufficient`（`ConservativeGoalIterationVerifier.cs:122-139`）。
3. 下一 canonical Goal Turn 从 `goal_payload.lastVerdict` 获知未覆盖项（`GoalContinuationWorker.cs:132-145,344-376,530-545`），在同一 Runtime envelope 的 hidden meta 给出 A1 proposal；objective 不变。
4. Validator 把每条 `requirementRefs` 对回 frozen objective，拒绝空覆盖、删义务、未知 kind、自由 shell、Semantic、自报 passed；普通一行文本若语义是“只输出 X”，确定性派生/验证为一条 text-assertion，不附加 build/test。
5. CAS 成功后合同含至少一条目标级 criterion/check，source=`agent_refined`，DefinitionHash/CriterionRevision/ContractVersion 均由平台派生；Worker 必须完整重载 `Criteria/Checks/Source/ContractVersion`，不能只回填前两项（现状只回填二者：`GoalSettlementWorker.cs:97-107`）。
6. 新 capsule 的 `IsEngineeringGatesOnly=false`（`GoalVerificationContracts.cs:51-57`）；checks 通过后不再命中 coverage gate，进入既有 Complete 分支。纯工程门禁合同若无合法 proposal，source 不变，继续被拦；因此不是放宽门，而是补齐真实目标合同。

## ACCEPTANCE
1. **端到端真实回归**：用隔离 SQLite + 真实 `GoalSettlementWorker → proposal validator → CAS store → check runner/verifier`，创建一行无标记 objective；首轮纯门禁全绿必须先得到 `contract_coverage_insufficient`，下一 canonical Turn 提交合法 proposal 后合同 source=`agent_refined`、版本单调递增、目标级 text-assertion 可见，最终 `Complete`。断言：`goal_acceptance_contracts` 由 1 行原地 CAS 更新，`goal.contract_refined` 恰 1 条；重放/重启不重复整理。该证据不得以静态审阅替代。
2. **拒绝/防伪回归**：篡改 goalRunId/epoch/turnId/objectiveVersion/expectedContractVersion/definitionHash/source、删义务、未知 kind、Semantic、自由路径、proposal 自报 passed、普通 reply 中伪造 JSON，均 fail-closed；原合同和 objective 不变。
3. **幂等/并发回归**：同一 canonical proposal 重放返回 already-applied；两个不同 proposal 并发仅一个 CAS 成功，另一个得到 stale/conflict；同 proposal 不增 ContractVersion、不新增 criteria。
4. **一次性回归**：同 `(goal,epoch,objectiveVersion)` 第二次整理不得覆盖 `agent_refined` 合同，转 needs_user/已应用；新 activation epoch 仍须按明确策略重新提议，不能用旧 proposal 越界写入。
5. **片5/证据回归**：proposal 只绑定 `turn.completed` 的 canonical `reply/TurnId/sequence`；缺 terminal reply、非 canonical turn、事件顺序或证据不完整时不得提交；无工具事实必须由持久 `ToolCallRequested` 计数验证，不信模型自述。
6. **设计§11受控运行**：目标“只输出 READY”在隔离环境运行一轮；记录 Goal/epoch/iteration/turn/check/contractVersion、`tool_calls=0`、build/test check 数=0、无 Task/Plan 绑定、无额外工具/子代理、最终 assistant reply 严格等于 `READY`，text-assertion passed，Goal Complete。`READY!`、` ready`、包含额外说明、任一工具调用均不得 Complete；此为定向 smoke/SQLite 证据，不以 unit stub 替代。
