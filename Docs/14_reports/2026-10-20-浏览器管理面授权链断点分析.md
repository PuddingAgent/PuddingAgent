# 浏览器管理面授权链断点分析

## 现象

Agent 调用 `browser_tabs action=new` 恒失败：

```
no task-level management grant allows creating or closing browser targets for this caller
```

## 完整链路（逐跳实测）

```
BrowserTabsTool.NewAsync             PuddingBrowser.AgentTools/BrowserTabsTool.cs
  → surface.TabsAsync(...)           经能力通道到 Desktop
  → DesktopService 准入                Pudding.DesktopService/DesktopService.cs:1052
      var sessionAdmitted = !string.IsNullOrWhiteSpace(context.SessionPermitMarker);
      if (!sessionAdmitted) { Authority.Admit(...) }      ← 只有此处才判授权
  → BrowserAutomationAuthority.Admit  PuddingBrowser.Automation/BrowserAutomationAuthority.cs:118
      case Management: HasManagementGrant(req) ? Allow : Deny(...)
```

## 断点一：management grant 从未签发

`BrowserAutomationAuthority.IssueManagementGrant` 全仓调用点 10 处，**全部在 `*Tests`**，
生产代码 0 处。

签发器 `Pudding.DesktopService/BrowserGrantIssuer.cs` 只签 page grant ——
它需要 `DesktopPageTarget`，而管理面操作（建 context / 新建标签）**还没有页面可授权**，
所以从来没有对应入口。该类注释已承认过同类历史：

> 此前 `BrowserAutomationAuthority.IssueGrant` 没有任何生产调用方，
> "页面已授权"只能靠人记得。

## 断点二（更深）：`SessionPermitMarker` 在生产路径上不设置

`DesktopCallContext.SessionPermitMarker` 的全仓分布：

| 位置 | 性质 |
|---|---|
`Pudding.Contracts/DesktopCallContext.cs:44` | 定义 |
`Pudding.DesktopService/DesktopService.cs:1052` | **唯一读取点** |
`PuddingDesktop.WpfArchive/Browser/BrowserBridgeExecutorRoute.cs:98` | **唯一生产设置点，但在归档工程里** |
`PuddingDesktop/Hosting/DesktopApplicationCoordinator.Capability.cs:249` | 只有注释提到 |
其余 5 处 | 全部是测试 |

**含义**：当前生效的 WinUI Desktop 若不设置该字段，
`sessionAdmitted` 恒为 `false` ⇒ **每次调用都退回旧授权模型**
（`Authority.Admit`）⇒ 撞上断点一。

同时有一条守卫测试专门禁止该字段出现在 wire/protocol 映射里：

```
BrowserSessionPermitMarkerWireGuardTests.SessionPermitMarker_IsNeverReferencedByWireOrProtocolMapping
```

说明它是**宿主内部字段**，不能让模型经协议影响它 —— 这让"随手在工具参数里加一个"这条路直接封死。

## 两条修法与风险

### A. 在 WinUI 的 capability 路由里设置 `SessionPermitMarker`

照 `WpfArchive/BrowserBridgeExecutorRoute.cs` 的做法，在构造 `DesktopCallContext` 时
带一个非空标记（那里写死 `"bridge-session"`）。

**前提（必须先确认）**：会话权威（派发器）**确实做了准入**。
`DesktopService.cs:1049` 的注释说"会话权威已用目标绑定（v1 隐式绑定）表达了同一事实"，
但若该准入实际没跑，设置这个字段等于**对整个浏览器能力裸放行** —— 比现状危险得多。

**这是本轮没有直接动手的原因。**

### B. 在 `Admit` 前签发 management grant

`bb1f0ac` 已补签发端：

```
BrowserGrantIssuer.TryIssueManagement(caller, validity, parentHoldsManagement, out grant, out epoch, out reason)
```

接线位置：`DesktopService.cs:1065` 的 `Authority.Admit` 之前，判断
`automationOperation` 属于管理面（`RequiredGrantKind == Management`）且当前无有效授权时，
签一个**短时**（如 30 秒）grant。

**风险较低**：判据不变，只是把"允许本任务新建标签"这句话真正兑现。
**代价**：每次 `TabNew` 多一条短时 grant 记录（有过期清理）。

## 已否决的路

把 `TabNew` 降级为 `BrowserGrantKind.None`。**3 条测试红**，其中
`Management_Is_Refused_During_Takeover` 揭示：降级会连带取消
**「用户接管浏览器期间不得新建标签」**，因为接管拦截走的是 grant kind 分支：

```csharp
IsBlockedWhileUserControlling(op) => IsSideEffecting(op)
```

⇒ **改策略表会牵动接管语义，不能只改 `RequiredGrantKind`。** 已回滚（未提交）。

## 建议

先做 **B**（低风险、可测、判据不变），再单独评估 **A**（要连带审计会话权威是否真的在准入）。
两者不冲突：B 让旧模型下的调用可用，A 才是最终形态。
