# 提交门禁对「未基线化失败」存在盲区

## 1. 怎么发现的

提交 `7d25b56`（失败建议归因）时，门禁输出里有这么几行：

```
--- .\Tests\PuddingHost.Tests\PuddingHost.Tests.csproj  filter~AgentExecutionService
    unfiltered run reported problems (not blocking, filter never selected these):
    TRX ... did not report a complete run (outcome=Failed, exit=1, run errors=5, ...)
    executed 0 test(s)
=== OK: no new test failures
```

「run errors=5」与「OK」同时出现。若直接采信最后那行，就等于把 5 个失败当成不存在。

## 2. 这 5 个失败是什么

从该 TRX 里读出来的失败用例（461 例中 456 通过）：

| 用例 | 失败消息摘要 |
|---|---|
| `DeepSeekWebToolsCompositionTests.DesktopChild_CompositionRoot_RegistersDeepSeekWebTools_AsAutoAllowedTools` | `Assert.Single()`：集合为空 |
| `ComputerUseCompositionTests.DesktopChild_ObserveAndInputShareSession_AndAreRegisteredExactlyOnce` | 集合里没有匹配项（实际含 `ListToolApprovalsTool` 等） |
| `BrowserBridgeServiceCollectionExtensionsTests.DesktopChild_RegistersRemoteRuntimeAndAllBrowserTools` | 集合不等：实际多出 `ClearPanelTool`、`ListPanelsTool` 等 |
| `BiyingFinanceToolsCompositionTests.DesktopChild_ResolvesFinanceToolsWithSharedRuntime_WithoutProviderConfiguration` | 集合里没有匹配项 |
| `PuddingDataRootSecurityBootstrapTests.BootstrappedSecurityJson_IsTheJwtConfigurationSource` | 抛异常：`Jwt:Key` 是未展开的凭据引用 `{{vault:…}}` |

前四条是**断言与真实注册集不一致**（面板类工具已在同一 plugin 里注册，组合根用例仍断言旧集合）；
第五条是**本机配置**问题（`<DataRoot>/config/security.json` 的 `jwt.key` 没有写成真实密钥）。

## 3. 它们不是本次提交引入的（可复核）

扫 `.work/staged-test-gate/**/unfiltered/*.trx` 共 35 份历史全量 TRX，按用例名匹配失败记录：

| 用例 | 失败出现次数 | 最早失败时间 |
|---|---|---|
| DeepSeekWebToolsComposition | 6 | 2026-11-24T21:26:10 |
| BootstrappedSecurityJson | 6 | 2026-11-24T21:26:06 |
| ComputerUseComposition | 6 | 2026-11-24T21:26:10 |
| BrowserBridgeServiceCollection | 6 | 2026-11-24T21:26:06 |
| BiyingFinanceToolsComposition | 6 | 2026-11-24T21:26:10 |

最早一次比 `7d25b56`（2026-11-26 13:21）早两天，且 6 次全量运行每次都失败 ⇒ 稳定的既有失败，不是偶发。

## 4. 盲区在哪

两件事叠加：

1. 门禁把 unfiltered 全量运行的异常标成 **not blocking**（注释原话：`filter never selected these`）——
   本次提交只改了 `AgentExecutionService`，过滤器确实碰不到这些用例，于是一律放行。
2. `TestScripts/staged-test-baseline.json` 里**只有** `BrowserBridgeServiceCollectionExtensionsTests`
   一条（第 70 行），另外 4 条从未入基线。

结果是：**既有失败既不阻塞，也不在基线里**。没人会看到它们，除非有人主动跑 `PuddingHost.Tests` 全量。
这与「known-failure baseline」这个机制想达成的目标（已知问题显式登记、新增问题必须阻塞）相反。

## 5. 建议（待裁定，本轮未动）

- 前四条：属**真实缺陷候选**——很可能是加面板工具时没同步更新组合根断言。修断言比入基线好，
  否则会把「注册集漂移」永久合法化。
- 第五条：属**环境问题**，应在基线里显式登记为「本机 security.json 未填真实 jwt.key」，并注明复现条件。
- 门禁侧：unfiltered 失败目前只打印一行提示。建议至少把它计入「本次提交需解释的清单」，
  而不是留在 `OK` 旁边（本报告即是对这句话的人工补位）。

## 6. 边界

本轮只做取证与登记，未改任何测试、基线或门禁脚本。「前四条是加面板工具导致的漂移」这一句
是根据失败消息里的实际集合推断的，**未逐一读那些断言源码核对**。

## 7. 修复结果（2026-11-26 14:09–14:25，已取红）

复读源码后，§2 的推断**不完整**。逐条真实原因：

### 7.1 真因：测试输出目录没有 host-packages（三条用例共同根因）

产品组合根的 `HostToolContributions` 从 `AppContext.BaseDirectory/tools/host-packages` 读
声明式包清单（`HostToolPackage.ReadInstalled`），非 Kernel 工具只能经它暴露。
该清单由 `Source/PuddingHost/Build/PuddingHostContent.props:34` 复制到输出，
但 **Content 项不会随 ProjectReference 流到引用方**——`Tests/PuddingHost.Tests` 的输出目录
因此从来没有这份清单。实测：

| 目录 | `tools/host-packages/finance.json` |
|---|---|
| `temp/build/winui3/.../core/`（live 部署） | **存在** |
| `Source/PuddingHost/bin/Debug/net10.0/` | 不存在 |
| `Tests/PuddingHost.Tests/bin/Debug/net10.0/` | 不存在 |

所以生产正常、测试失明：`_packages` 为空 ⇒ `ListTools` 永远返回空 ⇒ 三条组合根用例
自 11-24 起红。

### 7.2 断言入口也漂了（非 Kernel 工具不以 IPuddingTool 登记）

`HostToolContributions.RegisterBinding` 只在 `Kernel.Contains(type)` 时额外登记 `IPuddingTool`；
其余工具仅 `TryAdd(type→type)` + 记 `Binding`。因此 `GetServices<IPuddingTool>()` 只剩
Kernel 十个（`SearchTools` / `RequestToolApproval` / `ListToolApprovals` / `Plugin*`）——
这正是原失败消息里那个集合的内容。

而 `PuddingToolRegistry.BuildToolSnapshot` **只在传了 caller context 时才合并 contextual source**，
且 `HostToolContributions.ListTools` 第一行是 `if (context.CapabilityPolicy is null) return [];`。
⇒ 正确入口是「带 CapabilityPolicy 的 context + registry」。

### 7.3 但 registry 返回的是包装，不是原类型

`registry.GetTool(id, context)` 返回 `HostToolContributions+MountedTool`（`Descriptor.SourceKind=Plugin`）。
所以断言必须**拆成两半**：可见性用 registry，实例身份与共享依赖用 DI 的具体类型登记。

### 7.4 改动清单

| 文件 | 改动 |
|---|---|
| `Tests/PuddingHost.Tests/PuddingHost.Tests.csproj` | 补 `ToolPackages\*.json → tools/host-packages/` 复制（与产品 props 同目标路径；不整体导入 props——它还带 worker 项目引用与前端资产复制） |
| `BiyingFinanceToolsCompositionTests` | 断言改「registry(带 policy) 可见 + DI 取真实例 + 共享 runtime」 |
| `ComputerUseCompositionTests` | 同上 |
| `DeepSeekWebToolsCompositionTests` | 同上（并避开与既有 `policy` 局部变量重名） |
| `BrowserBridgeServiceCollectionExtensionsTests` | 集合相等 → `Browser*` 前缀收窄后双向相等 |
| `TestScripts/staged-test-baseline.json` | 移除该用例的 `knownFailures` 条目（已修，不再算已知失败） |

## 8. 全量复跑与基线登记（2026-11-26 14:47–14:52）

`dotnet test Tests/PuddingHost.Tests/PuddingHost.Tests.csproj`（无 filter，461 例）：

```
失败!  - 失败: 1，通过: 460，已跳过: 0，总计: 461
[xUnit.net]  ...PuddingDataRootSecurityBootstrapTests.BootstrappedSecurityJson_IsTheJwtConfigurationSource [FAIL]
```

即：原先 5 条红，现在 4 条已修、**1 条仍是环境型**。该条失败信息本身写明了判据：

> 登录态 JWT 签名密钥是一个未展开的凭据引用（配置键 Jwt:Key，形如 `{{vault:...}}`）…
> 请把 `<DataRoot>/config/security.json` 的 jwt.key 写成真实密钥后重试

这是 `PuddingJwtSettings.FromConfiguration` 的 **fail-closed 守护**（否则 HS256 密钥等于
一个公开可见字符串），属正确行为，不是缺陷。

登记方式遵从 `staged-test-baseline.json` 自己的 ratchet 规则
（`note`: *entries may only be REMOVED (when fixed), never added without a dated reason*）：

| 字段 | 变更 |
|---|---|
| `reasonGroups.environmentJwtKeyPlaceholder` | 新增组，含 2026-11-26 的 dated reason 与 affected |
| `knownFailures` | 加 1 条（同一条用例全名） |
| `measuredTotals.PuddingHost.Tests` | `396/391/5` → **`461/460/1`**（旧值停在 2026-10-27，已过期 30 天） |
| `measuredAtUtc` / `measuredAtCommit` | → `2026-11-26T06:47:54Z` / `de7b69d` |

### 8.1 一次必须记下的操作失误

第一次改 `knownFailures` 时，我把 `old_text` 写成「`"knownFailures": [` + 相邻那一行」，
`new_text` 只写了新条目 —— 结果是**替换而非并列插入**，当场删掉了
`BrowserBridge.ConfiguredAgentBrowserSnapshotPolicyExecutionTests...` 那条。

发现后立即恢复，并用三条独立断言核对最终状态：

```
IN  jwt       True     # 新登记条目在
IN  bb-snap   True     # 被误删的条目已回
OUT bb-comp   True     # 上轮修好的那条确实不在
TOTAL 20              # 20 - 1(修好移除) + 1(新登记) = 20
```

教训：**数组插入不能拿相邻元素当锚点**，要么锚点含两个元素、要么先插入再验证长度。
