# 提交门禁对「未基线化失败」存在盲区

## 1. 怎么发现的

提交 `7d25b56`（失败建议归因）时，门禁输出里有这么几行：

```
--- .\Tests\PuddingHost.Tests\PuddingHost.Tests.csproj  filter~AgentExecutionService
    unfiltered run reported problems (not blocking, filter never selected these):
    TRX ... did not report a complete run (outcome=Failed, exit=1, run errors=5, ...)
    executed 0 test(s)
=== OK: no new test failures
```

「run errors=5」与「OK」同时出现。若直接采信最后那行，就等于把 5 个失败当成不存在。

## 2. 这 5 个失败是什么

从该 TRX 里读出来的失败用例（461 例中 456 通过）：

| 用例 | 失败消息摘要 |
|---|---|
| `DeepSeekWebToolsCompositionTests.DesktopChild_CompositionRoot_RegistersDeepSeekWebTools_AsAutoAllowedTools` | `Assert.Single()`：集合为空 |
| `ComputerUseCompositionTests.DesktopChild_ObserveAndInputShareSession_AndAreRegisteredExactlyOnce` | 集合里没有匹配项（实际含 `ListToolApprovalsTool` 等） |
| `BrowserBridgeServiceCollectionExtensionsTests.DesktopChild_RegistersRemoteRuntimeAndAllBrowserTools` | 集合不等：实际多出 `ClearPanelTool`、`ListPanelsTool` 等 |
| `BiyingFinanceToolsCompositionTests.DesktopChild_ResolvesFinanceToolsWithSharedRuntime_WithoutProviderConfiguration` | 集合里没有匹配项 |
| `PuddingDataRootSecurityBootstrapTests.BootstrappedSecurityJson_IsTheJwtConfigurationSource` | 抛异常：`Jwt:Key` 是未展开的凭据引用 `{{vault:…}}` |

前四条是**断言与真实注册集不一致**（面板类工具已在同一 plugin 里注册，组合根用例仍断言旧集合）；
第五条是**本机配置**问题（`<DataRoot>/config/security.json` 的 `jwt.key` 没有写成真实密钥）。

## 3. 它们不是本次提交引入的（可复核）

扫 `.work/staged-test-gate/**/unfiltered/*.trx` 共 35 份历史全量 TRX，按用例名匹配失败记录：

| 用例 | 失败出现次数 | 最早失败时间 |
|---|---|---|
| DeepSeekWebToolsComposition | 6 | 2026-11-24T21:26:10 |
| BootstrappedSecurityJson | 6 | 2026-11-24T21:26:06 |
| ComputerUseComposition | 6 | 2026-11-24T21:26:10 |
| BrowserBridgeServiceCollection | 6 | 2026-11-24T21:26:06 |
| BiyingFinanceToolsComposition | 6 | 2026-11-24T21:26:10 |

最早一次比 `7d25b56`（2026-11-26 13:21）早两天，且 6 次全量运行每次都失败 ⇒ 稳定的既有失败，不是偶发。

## 4. 盲区在哪

两件事叠加：

1. 门禁把 unfiltered 全量运行的异常标成 **not blocking**（注释原话：`filter never selected these`）——
   本次提交只改了 `AgentExecutionService`，过滤器确实碰不到这些用例，于是一律放行。
2. `TestScripts/staged-test-baseline.json` 里**只有** `BrowserBridgeServiceCollectionExtensionsTests`
   一条（第 70 行），另外 4 条从未入基线。

结果是：**既有失败既不阻塞，也不在基线里**。没人会看到它们，除非有人主动跑 `PuddingHost.Tests` 全量。
这与「known-failure baseline」这个机制想达成的目标（已知问题显式登记、新增问题必须阻塞）相反。

## 5. 建议（待裁定，本轮未动）

- 前四条：属**真实缺陷候选**——很可能是加面板工具时没同步更新组合根断言。修断言比入基线好，
  否则会把「注册集漂移」永久合法化。
- 第五条：属**环境问题**，应在基线里显式登记为「本机 security.json 未填真实 jwt.key」，并注明复现条件。
- 门禁侧：unfiltered 失败目前只打印一行提示。建议至少把它计入「本次提交需解释的清单」，
  而不是留在 `OK` 旁边（本报告即是对这句话的人工补位）。

## 6. 边界

本轮只做取证与登记，未改任何测试、基线或门禁脚本。「前四条是加面板工具导致的漂移」这一句
是根据失败消息里的实际集合推断的，**未逐一读那些断言源码核对**。
