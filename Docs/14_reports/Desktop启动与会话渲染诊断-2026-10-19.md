# Desktop 启动与会话渲染诊断

## 1 范围和证据

用户反馈前端 `6.9.6+dirty / 20158a0` 启动超过 30 秒；发送后看到旧消息，04:38 心跳以原始 JSON 出现在用户气泡。核对当前 Desktop/Core 进程、`D:/data/logs/system/pudding-20261019*.log` 的 09:25–09:26 启动片段，以及默认助手的 `conversation-open` 响应。原始会话仅保留在忽略目录 `temp/chat-render-open-before.json`，不入库其私人正文。

## 2 启动耗时

| logging-ready | 4,760 | 189 |

| jieba-backfill / initialized | 20,038 | 888 |
| server-started | 24,709 | 4,671 |
| ready | 24,710 | 1 |

Core 内部计时为 **24.710 秒**，图片的 27.2 秒还包括进程启动到计时入口等开销；它不等于 WebView 工作台可见耗时。进程创建时间为 Desktop 09:25:22、Core 09:25:35，前面还有约 13 秒，现有日志未细分这段，不能全部归因于 Core。

最大可定位区间是 logging-ready 到 services-registered 的 **10.629 秒**；覆盖 WebApplication builder、配置、认证和依赖注册。现有日志没有逐服务计时，不能断言某一个服务独占该区间。host 初始化后到 server-started 还有 4.671 秒；附近有本机 MCP 连接失败，但不能仅凭共时性将整段归因于 MCP。未绑定飞书渠道等错误也存在，不是心跳 JSON 渲染错误的原因。

本次修复针对会话展示，不改变启动服务次序。后续启动优化应先增加 builder/注册组/hosted service 与 Desktop 启动子阶段计时，分别测冷启动和热启动，再移动有证据的非必要阻塞工作；不能把所有服务盲目改成后台执行。

## 3 渲染根因与修复

1. **页顺序丢失。** 服务端按 `(CreatedAt DESC, Id DESC)` 返回最近 20 条；客户端原样交给从旧到新的列表。实测响应从 09:22 排到 04:38，正好解释截图底部停在旧心跳。打开与历史页统一反转副本，保留同时间戳稳定顺序。
2. **先截断信封，再丢掉发送者。** 新查询直接截取 ChatMessages.Content；心跳的 `pudding-message` JSON 在闭合前截断，adapter 又补成 user 来源。改为 SQLite 内先提取正文与身份，再截断；保持 user/agent/system 与 llmRole 独立，保留有界图片引用。正文分段同样读取解包后的正文，长度统一 UTF-8 字节。
3. **展开入口塞进纯文本。** 用户气泡不解释 Markdown，因而 `[展开全文](...)` 直接显示。改为消息行真实链接，由现有按需分段读取处理。
4. **翻页覆盖新状态。** `loadOlder` 使用 await 前快照写回；请求期间收到的消息和 activeRun 可能被覆盖。改为以返回时的当前会话为基础合并并去重。
5. **旧派生缓存保留错误投影。** IndexedDB schema 升到 2，仅清理 conversations 缓存；不删除服务端消息。语义 fingerprint/memo 增加身份与展开状态。

实测旧版本 `conversation-open` 用时 13 ms，C=H=1,835,935；说明这次画错消息不需要以“大事件表读取慢”解释。所读日志和快照没有证明用户截图前最近一次输入已被服务端接受，因此“消息未提交”和“已提交但位置/投影错误”仍须通过新消息验收区分。

实现合同已补入[首屏与渐进加载设计 §5](../12_features/会话首屏与渐进加载架构优化方案-2026-10-18.md#5-首屏与分页合同)。
