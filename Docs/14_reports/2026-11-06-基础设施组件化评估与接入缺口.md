# 基础设施组件化评估与接入缺口

**结论：独立组件和若干可用门面已经建立，但“上层不感知内部实现即可使用整套 Agent 基础设施”的目标尚未完成。当前最需要的是接通并收敛真实执行路径、身份和生命周期，而不是继续增加接口数量。**

本次优先评估基础设施，Goal 自动评审仅作为基础设施的消费者检查。源码基线为 HEAD `a385cff` 加当前未提交工作树；HEAD 不能单独复现这份工作树。本次没有修改生产源码或既有测试，没有 commit/push、部署、重启、读取真实凭据或调用真实模型。08B/08C 仍 NotRun。

## 1 评估口径

分别回答六个问题，不把它们合并成一个“完成”：

1. **契约**：是否清楚表达输入、权限、效果、失败和版本冲突？
2. **独立性**：实现是否脱离 Host/Runtime/存储重依赖，反向依赖是否在构建阶段失败？
3. **适配**：是否已有连接现有配置、存储、模型和执行链的真实适配器？
4. **消费**：现有产品调用是否确实经过新组件，还是只有测试/DI 注册？
5. **生命周期**：谁持有工作、取消源、预算、并发槽、租约，何时释放？
6. **上层可用性**：SDK/插件能否取得受权门面并完成调用，无需自己构造内部身份或解析配置文件？

“独立组件测试通过”证明局部行为；“登记解决方案/DI”证明可以装配；二者都不能替代真实调用链验收。这里的生产消费者判断来自静态源码搜索及关键调用点阅读，**不是运行中程序集加载或功能验收**。

## 3 编译边界：已经有效，但不是完整接入证明

静态检查的 13 个组件工程均有 ProjectReference 白名单及构建 Error 门禁；拟议 ExecutionKernel 工程不存在。本次没有对全部工程重跑完整独立测试。

另外对 Agents、Context、Tools 做了独立反向依赖探针：不修改 csproj，通过 `.work` 下的 MSBuild import 注入 Runtime 引用，显式运行各自边界 target。

| 工程 | 正常 target | 注入 Runtime 引用 | 实际错误 |
|---|---|---|---|
| PuddingAgents | exit 0 | exit 1 | Agents may only reference its ports and the public API contracts. |
| PuddingContext | exit 0 | exit 1 | Context may only reference its ports. |
| PuddingTools | exit 0 | exit 1 | Tool facade may only reference its ports. |

这证明三项抽查的构建门禁能取红；不宣称所有依赖形式或所有组件都经过负向测试。

## 4 优先修复的基础设施问题

### 4.1 查询身份被错误地绑到运行身份

[AgentBinding](../../Source/PuddingAgents.Contracts/AgentPorts.cs) 的有效性同时要求 Workspace、Agent、Actor、OwnerWork、RootBudget。目录服务经 [EnsureWorkspace](../../Source/PuddingAgents/AgentOwnershipPolicy.cs) 强制检查完整 binding。

结果是：一个仅想枚举工作区 Agent 的上层模块，尚未开始任何 Work，也必须已有 Work/预算身份。这不符合无副作用读取的目标。应分离宿主认证的调用方/工作区作用域与执行作用域；**不能用虚构 WorkId 或万能根预算填空**。

HTTP 管理、插件当前调用、持久后台 Job 都需要各自可信的工厂入口。AgentId 是目标，不是 actor。公开字符串 DTO 便于序列化，但构造 DTO 不能视为取得权限。

### 4.2 P2 目前仍是可选调用参数，尚未成为生产硬门禁

[LlmInvocationService](../../Source/PuddingRuntime/Services/LlmInvocationService.cs) 只有 `BudgetAttempt != null && budgetPort != null` 才进入 gate；带预算身份但缺端口时照常调用 provider。本次 buffered/streaming 两条红探针都观察到 provider 被调用一次。

此外，静态搜索未见 `IModelAttemptBudgetPort` 的生产 DI 注册；[主调用方](../../Source/PuddingRuntime/Services/AgentExecution/AgentExecutionLlmInvoker.cs) 未填 `BudgetAttempt`，并保留绕过门面的直接客户端分支。因此“流式路径已经增加门禁代码”成立，“主执行链已经受持久账本控制”不成立。

预算绑定与调用 Workspace/Agent/Session 也没有在门面处比对；本次不一致 Workspace 探针仍调用了 fake provider。这里证明的是不变量缺失，**不是证明外部攻击者已经能伪造宿主身份**。

### 4.3 流式资源保护范围和结算状态存在缺口

同一文件的三类红探针：

- `settled=true` 在 await 结算成功之前设置；结算前抛异常时不再进入 Unknown 清理。
- stream 对象构造在保护范围外；构造抛异常后已取得的预算没有本地 Unknown 处理。
- `GetAsyncEnumerator` 同样在保护范围外。

修正必须设计幂等终结：结算可能“已提交但回执丢失”，此时不能无条件覆盖成 Unknown。应查询/调和同一 attempt，保留已派发的不确定消费，不退款。持久调和仍是崩溃兜底，但不能代替正常异常路径的可靠清理。

### 4.4 模型调用、预算和租约的实际边界不统一

[内存 ModelResourcePool](../../Source/PuddingExecutionResources/ModelResourcePool.cs) 连接父取消与调用取消，支持超时，并对不合作 provider 排空后释放槽位。相对地，[DurableModelResourcePool](../../Source/PuddingPlatform/Services/Reviews/DurableModelResourcePool.cs) 只校验 timeout 数值，直接传入调用方 ct，没有复用父取消连接、超时等待和排空逻辑。其成功路径还将缺失 usage 转为零值 receipt，虽会另记 Unknown，公共回执不能据此被理解为“零成本已确认”。这些属于源码静态核对，本轮未做该资源池完整生命周期探针。

[ReviewEvaluationBinder](../../Source/PuddingPlatform/Services/Reviews/ReviewEvaluationBinder.cs) 创建资源 scope 后只返回 `IModelEvaluationApi`；未看到负责释放该 scope 的所有者。需要明确持有执行资源的绑定对象与只借用服务的门面，不能靠名称 `Lease` 代替所有权契约。

主调用和 Review 最终使用的 [DirectLlmClient](../../Source/PuddingRuntime/Services/DirectLlmClient.cs) 含内部重试；外侧一次 Begin 不能代表每个实际 provider attempt 都预留了预算。现有模型算子 binder 则直接使用单次 gateway，路径并不相同。

另一个边界丢失发生在 [HostRuntimeLlmChatClient](../../Source/PuddingHost/Services/HostRuntimeLlmChatClient.cs)：请求携带 MaxOutputTokens，但传给下游的是原配置，没有应用该上限。Review 的“有界调用”注释不能作为上限真的生效的证据。

应先共享“单次派发 + 预算账本端口 + 全局并发槽 + 取消/排空”机制，再让主 Agent、子代理、算子和 Review 使用它。不要简单注册新 port 后再叠加多层预留。

### 4.5 Review 提交暴露的是通用幂等与身份基础设施问题

[GoalReviewSubmissionService](../../Source/PuddingPlatform/Services/Goals/GoalReviewSubmissionService.cs) 的所有提交 `AcceptedSequence=0`，而 [ReviewJobStore](../../Source/PuddingPlatform/Services/Reviews/ReviewJobStore.cs) 的 Latest 查询按该序号、再按哈希 JobId 排序。真实 SQLite 探针证明：新 artifact 提交成功后，Latest 仍可能返回旧 Job。

同 operation 重复请求只检查逻辑 key，改变 actor/预算账户后仍返回旧记录。探针证明是内容冲突校验缺失，不证明当前生产入口接受任意 actor。应冻结并比较有授权意义的完整创建指纹；无需把 actor 加进 Job ID 从而绕过冲突。

另需明确 TaskId 到 ParentWorkId 的映射，不能因都是字符串就视为同一身份；请求期限应使用同一个注入时钟验证。这些应在完成候选事务接入之前处理。

## 5 本轮验证与证据边界

隔离工程链接了原有预算/取消/提交测试源文件，未改既有测试；新增探针只在 `.work/r26-review/20261106/probes/`。使用 fake provider 和内存 SQLite，没有启动产品。

| 验证 | 结果 |
|---|---|
| 隔离工程构建 | exit 0，0 error，119 warning |
| 原有选定测试 | 16/16 通过 |
| 新增契约边界探针 | 8/8 失败，暴露缺口；测试命令 exit 2 |
| 合计 | 24 项，16 通过、8 失败、0 跳过 |
| 构建依赖门禁抽查 | 3 个正常 target 通过，3 个反向引用注入按预期拒绝 |

八条红探针分别是：预算端口缺失 buffered/streaming、结算失败、stream 构造失败、enumerator 构造失败、跨 Workspace 预算身份、Review Latest 顺序、重复 operation 改变 actor/账户。

这组结果不否定此前 274/151 等记录；它说明原用例覆盖与这些边界不重合。本轮没有重跑全解决方案、全部组件或完整 Platform suite，不把历史数字列为本轮通过证据。

- `.work/r26-review/20261106/probes/`、`build.log`、`test.log`：隔离测试源码、实际输出。
- `.work/r26-review/20261106/*-baseline.log` / `*-forbidden.log`：三个工程的构建门禁正反验证。
- `.work/r26-review/20261106/source-fingerprints.json`：关键输入文件指纹。临时探针不是已集成的永久回归测试；后续修复须将针对性用例迁入所属测试工程。
