# 主循环工具活动流缺失

## 1. 现象

`agent_diagnostics tool_stats` 连续两天的「样本窗口」停在 11-24：

```
sample_oldest_utc: 2026-11-22T07:06:59Z
sample_newest_utc: 2026-11-24T06:36:54Z
query_component:   tool_runner
```

同期我每分钟都在调工具，因此「窗口停在两天前」不可能是「最近没用工具」。

## 2. 取证（全部只读，`mode=ro`）

### 2.1 不是全部组件停写

`runtime_activity` 按组件看 `MAX(started_at_utc)`：

| 组件 | 最后写入 |
|---|---|
| llm_gateway / agent_execution / context_pipeline / event_dispatcher | **2026-11-26T03:18Z**（当时刻） |
| tool_runner | 2026-11-24T06:36:54Z |

⇒ 写库管道本身是活的，只有 `tool_runner` 这一路断了。

### 2.2 主会话从来没写过这一路

```
SELECT COUNT(*) FROM runtime_activity
 WHERE component='tool_runner' AND session_id NOT LIKE '%-sub-%';
-- 0
```

按天拆也一样：**每一天的 `tool_runner` 行全部来自 `-sub-` 会话**（10-13 至 11-24 共 22 天，非子代理列恒为 0）。

同一条主会话（`3f52368a…`）的其他组件行数：`agent_execution` 72181 · `llm_gateway` 47142，时间到当时刻。

⇒ 不是「两天前坏了」，而是**主循环从未接入这条流**；11-24 停的是最后一次子代理运行。

### 2.3 组件日志独立印证

`D:\Data\logs\components\tool_runner\tool_runner-20261124_001.log`（7440 字节）最后一条正好是 `2026-11-24 14:36:54`，会话 `…-sub-a797a6ee`。文件列表里 11-25 / 11-26 没有新文件。

日志与库给出同一条时间线 ⇒ 不是写库失败，而是**根本没发生这次调用**。

### 2.4 写点是 8 处，但流式路径不在其中

`RecordActivityAsync(component: ToolRunner)` 的全部出现位置：

- `AgentExecutionService.Buffered.cs`：6 处（子代理循环 + CONTINUE 路径）
- `AgentExecutionService.cs`：2 处（`approve_tool`，高危审批）

而生产主循环走的是 `AgentExecutionService.Streaming.cs`：那里对每次工具调用只调 `RecordToolMetricAsync`（写 `telemetry_metric_events`），**没有任何 `RecordActivityAsync`**。

数据侧对得上：`telemetry_metric_events` 的 `tool.execution` 今天 514 条、到当时刻仍在增长（含本轮我自己调的工具）。**指标流是完整的，活动流缺了主循环。** 而 `tool_stats` 读的是活动流。

## 3. 修法

在流式路径的工具调用收尾处，按 Buffered 路径**同一形状**补写活动：成功 / 失败两个分支各一条，元数据沿用 `tool_name` / `tool_args_hash` / `tool_args_length` / `tool_duration_ms` / `tool_output_length`（失败另加 `error_code` / `error_message`）与 `session_id`。

不新建读路径、不引新抽象：真正的缺陷是两条执行路径不对称，补齐不对称处比给诊断工具加第二个数据源更小、更可解释。

## 4. 验证（三态）

新增用例 `StreamingToolCall_RecordsToolRunnerActivity`：以真实工具调用驱动 `ExecuteStreamAsync`，注入记录型 `IRuntimeActivitySink`，断言恰好 1 条 `tool_runner/execute_tool`、`status=succeeded`、元数据带 `tool_name` 与 `session_id`。

| 态 | 结果 |
|---|---|
| **生产代码复原到修复前**（`git checkout` 该文件）+ 新用例 | **失败 1 / 通过 0**，消息：「Assert.HasCount 失败。大小 1 的预期集合。实际： 0」 |
| 复原修复（字节 SHA `350c83ccf6b84829` 与备份一致）+ `-t:Rebuild` | **9/9 通过**（该类原 8 例 + 新 1 例） |
| 定向类 `ToolCallPresentationEmissionTests` | 424 ms，失败 0 |

复原一条是取红的关键：它直接证明「删掉这次活动写入，用例必红」，而不是只证明「代码在时用例会绿」。

## 5. 局限与未覆盖

- 用例住在 `ToolCallPresentationEmissionTests.cs`：那是仓库里唯一以真实工具调用驱动 `ExecuteStreamAsync` 的夹具。为此给它的私有 `CreateService` 加了可选 `activitySink` 参数（默认 null，既有调用不受影响）。属于「借夹具」，不是它本来该管的领域。
- 只验了成功分支的取红；失败分支（`status=failed` + `error_message`）没有单独用例。
- 未在旧产物上重跑「修复前的运行时形态」：进程已重启，回不去。因此「旧实现会漏」这一条是源码 + 数据的推断，运行时的取红由上面的单测承担。
- 本条修复只补「写」，不改 `tool_stats` 的输出形状；`sample_*_utc` 那对键是上一轮加的。
