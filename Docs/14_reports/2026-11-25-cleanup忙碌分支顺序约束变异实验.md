# cleanup 忙碌分支的顺序约束：能不能取红

## 1. 要证的问题

`cleanup` 对忙碌条目与空闲条目用两种相反的顺序（`SubAgentTool.cs`）：

- 忙碌：先 `DestroyAsync`（级联取消在跑的那一单）再清理 —— 清理会跳过「运行中」的记录，先清只会清 0 条。
- 空闲：先清理、复核通过再销毁 —— 否则清理失败时条目已没，唯一稳定定位键也一起没了。

此前 goal 记着一条未覆盖：「『状态查询先于清理』只有调用顺序断言，无反事实用例」。
问题就是：把顺序改错，测试真的会红吗？

## 2. 做法（单点变异）

| 步骤 | 动作 |
|---|---|
| 基线 | `SubAgentTool.cs` SHA-256 = `51DC5773…958834D4`，116560 字节 |
| 变异 | 单锚点替换 `var wasBusy = poolAgent?.Status == PooledSubAgentStatus.Busy;` → `var wasBusy = false;`，锚点命中数断言 = 1 |
| 构建 | `dotnet build … -t:Rebuild`：0 错误 / 976 警告 |
| 测试 | `--filter FullyQualifiedName~Cleanup`，TRX 逐例统计 |
| 恢复 | 回写备份，SHA 逐字节比对；再 `-t:Rebuild` 并重跑同一过滤 |

## 3. 结果

变异态：**Passed 13 / Failed 1**，红的是
`Cleanup_BusyEntry_DestroysFirstSoRunningRunCanBeCleaned`：

```
CollectionAssert.AreEqual 失败。忙碌条目必须先销毁（级联取消）再清理；
归档已删时不重复销毁：status,cleanup,destroy。索引 0 处的元素不匹配。
```

失败信息里的 `status,cleanup,destroy` 就是变异后的真实调用顺序，期望值是 `destroy,status,cleanup`。

恢复态：`backup_sha == restored_sha == 51DC5773…958834D4`，`git diff --numstat` 为空；
重编译后同一过滤 **Passed 14 / total 14**。

## 4. 结论与边界

- 该顺序约束**已被守住，且守护能取红**：顺序断言不是「只能在代码正确时通过」的弱断言，它记录了期望顺序并逐元素比较。
- goal 里「无反事实用例」的说法**不成立**，已更正；该项从前述未覆盖清单里移除。
- 「状态查询先于清理」这一半是**结构性强制**的：`targetSubSessionId` 与 `wasBusy` 都要从 `GetAsync` 的结果取，取不到 id 连清理目标都没有。所以能变异的空间只在「拿到状态后是否先销毁」。
- 变异只覆盖 `wasBusy` 分支，不覆盖空闲分支「先清理后销毁」的相反顺序；那条由另一个用例与运行时取证（`Docs/14_reports/` 前序报告）分别覆盖。
- 本轮**不改产品代码**：源码恢复后与 HEAD 逐字节一致，故此轮无需部署。
