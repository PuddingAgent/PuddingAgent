# 办公文档处理能力 · 现状盘点（PuddingAgent）

> 日期：2026-09-21 ｜ 作者：dsh(0e0) ｜ 性质：**只读盘点**（未改任何代码）
> 目的：为「办公工具」方向的研究提供**可核验的基线**，回答「现在能不能读/写 Office 文档、缺什么」。
> 取证方式：静态全仓检索（`smart_explore` 委派 Explorer 子代理）+ **父级独立复核关键项**（见 §五 标记 ▲）

---

## 一、结论先行

**PuddingAgent 当前的办公文档能力是一条「纯只读」单链：**

```
LLM tool_call(read_office_document)
  → PuddingToolRegistry（[Tool] 特性扫描注册）
  → ReadOfficeDocumentTool.ExecuteCoreAsync
  → 按扩展名分派：ReadDocx / ReadExcel / ReadPdf / File.ReadAllText
  → ApplyAction(auto/toc/pages/chapter/search) → 截断 200,000 字符 → 返回 Markdown 文本
```

- ✅ **能读**：`.docx` / `.xlsx` / `.xls` / `.pdf` / `.txt` / `.md`（转 Markdown 纯文本）
- ❌ **不能写/生成**：全仓**不存在**任何生成型依赖（OpenXML / ClosedXML / EPPlus / Aspose / PdfSharp / iText / MiniExcel / CsvHelper / Markdig / QuestPDF / Spire 全部零命中）
- ❌ **明确不支持**：`.doc`（提示转 .docx）、`.pptx`（源码注释称「将在下一版本添加」）、`.csv`、`.odt`
- ❌ **无文档制品链路**：制品存储只有**图像**（Vision）与**音频**（Audio），**没有文档类制品**
- ❌ **前端无文档能力**：聊天附件仅支持图片；无文档上传/预览/下载组件；仅 `react-markdown` 渲染
- ❌ **知识库是空壳**：`KnowledgeBaseApiController` 有 `DocumentCount` 字段却**无文档摄取/上传/解析端点**（创建时恒为 0）

## 六、缺口清单与关键决策点

### 6.1 缺口（按业务价值排序）
1. **无写入/生成能力**（最致命）：Agent 无法交付 .docx/.xlsx/.pdf 产物，只能给文本。
2. **无文档制品链路**：即便生成了文件，也没有 vision/audio 那样的「制品存储 + 引用 + 前端下发」通道。
3. **`.pptx` 读缺失**：源码自称"下一版本添加"，属已知待补项。
4. **前端零文档支持**：不能上传、不能预览；人类无法在界面上把文档交给 Agent。
5. **知识库空壳**：有 `DocumentCount` 无摄取；"文档知识库"目前只是名字。
6. **无 OCR**：扫描件 PDF 只能拿到空文本（PdfPig 仅取文本层）。
7. **`.csv`/`.odt`/`.doc` 未覆盖**：办公场景高频格式中的空缺。

### 6.2 关键决策点（供研究阶段拍板）
1. **写入栈选型**：OpenXML SDK（MIT，docx/xlsx/pptx 官方）｜ClosedXML（xlsx 读写友好）｜**复用已有 NPOI 2.8（零新增依赖即可写 docx/xlsx）**｜MiniExcel（轻量大表）。
   → 是否坚持「已有依赖优先」以避免新增许可证审查？
2. **格式优先级**：先补 `.pptx` **只读**，还是先补 docx/xlsx **生成**？（两者面向完全不同的用户故事：读既有资料 vs 交付产物）
3. **PDF 生成与 OCR**：生成用 QuestPDF（社区许可）/PdfSharp/无头渲染；OCR 是否引入 Tesseract/PaddleOCR（新增原生依赖 + 体积），还是把扫描件外包给外部 MCP/视觉模型（已有 `VisionArtifactStorageService` 可复用）？
4. **制品类型扩展**：是否把 Vision/Audio 的制品模式复制成 **Document artifact**（含 MIME、大小、hash、引用、前端下发）？
5. **前端面**：文档上传走聊天附件（扩 `modality`）还是独立「文档库」页？预览是否需要 docx-preview/pdf.js（新增前端依赖）？
