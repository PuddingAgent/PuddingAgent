# 浏览器能力通道启用实测（配置已生效 · 闸门前移到身份）

**实测时间**：2026-10-13 16:41–16:45（+08:00）

## 四、为什么"只靠配置"到此为止（三处硬证据）

1. **授权器是硬编码注册的，无配置开关**：`PuddingApplicationHost.cs:315` 直接 `new`，附近无分支；宽松实现 `AllowAllDesktopCapabilities`（`Source/Pudding.CapabilityBroker/ICoreDesktopChannel.cs:44`）**只存在于类库里、无组合根引用**。
2. **该状态是作者有意为之的未完成增量**：`PuddingApplicationHost.cs` 在启用通道处直接打印
   `"[CapabilityChannel] 已启用：显式重绑 REST 与能力通道；授权器=默认拒绝（待切片 D 接入 Tool Runtime 准入）"`；
   同文件注释与授权器 XML 文档均写明「把 Tool Runtime 的权限/审批链也接进来属**切片 D** 的调用点迁移」。
3. **启用通道 ≠ 可用**：即便规则 ② 被满足，变更类（interact/tabs/context.create）还要过规则 ③（`ExecutionId` + `AgentInstanceId`），这属于同一切片。

⇒ 因此**"配置已到头"是取证结论，不是推测**。

## 七、根因定位（17:20 追加）：**Agent 身份从未被发布到 Ambient 轨迹**

**结论**：`AgentInstanceId` 为空**不是偶发**，而是结构性缺陷 —— **承载 Agent 身份的轨迹从未被压栈到 Ambient（AsyncLocal）上下文**，因此授权器规则 ② 对"由 Agent 执行的工具调用"而言**在设计上不可达**。

### 证据（全部一手读码）

1. **Ambient 的写入点全仓只有 3 处，全部来自事件分发链、且全部不含 Agent 身份**：
   - `Source/PuddingRuntime/Services/Events/EventDispatcher.cs:120` → `_traceAccessor.Current = internalEvent.Trace ?? trace;`
   - `Source/PuddingRuntime/Services/Events/EventDispatcher.cs:282` → `ResolveTrace()` 内 `_traceAccessor.Current = trace;`，其中 `trace = qe.Trace ?? _traceAccessor.Current ?? CreateNew(sessionId: qe.SessionId, workspaceId: qe.WorkspaceId, eventId: qe.Id)`
   - `Source/PuddingRuntime/Services/Events/InternalEventBus.cs:169`
2. **`CreateNew` 的签名根本没有 `agentInstanceId` 参数**（`Source/PuddingCore/Observability/RuntimeTraceContext.cs:20-43`），Agent 身份只能靠 `WithAgent(...)` 后补，而上述三处均未补。
3. **承载 Agent 身份的轨迹只作数据、不作上下文**：`AgentExecutionService.CreateExecutionTrace`（`Source/PuddingRuntime/Services/AgentExecutionService.cs:1061-1084`）**确实**调用了 `.WithAgent(request.AgentInstanceId, request.AgentTemplateId)`；返回的轨迹在两条执行路径被大量使用（`AgentExecutionService.Buffered.cs` 27 处、`AgentExecutionService.Streaming.cs` 22 处），但**全部是数据传递**（`Trace = execTrace`、日志参数、`sourceId` 拼接），**没有任何一处把它发布为 Ambient**。
4. **`Scope(...)` 在生产代码中零使用**：`Source/PuddingCore`（仅 `TraceContextEnricher.cs:10` 读取 `.Current`）与 `Source/PuddingHost`（仅身份提供方读取 `.Current`）均无发布点；`Source` 级检索未命中（诚实标注：该次 Source 级检索覆盖 923/2000 文件，非全量枚举；但两个最相关工程已单独闭合核对）。
5. **运行时侧吻合**：授权器看到 `SessionId` 有值（来自事件轨迹）而 `AgentInstanceId` 为空（事件轨迹从未带 agent）⇒ 命中规则 ②。
6. **顺带印证一条旧现象**：Core 日志行长期呈现 `[trace:]` 为空而 `[session:...]` 有值 —— 说明**对外可见的轨迹作用域与会话作用域不是同一条**。

### 因果链

```
message.deliver 事件
  → EventDispatcher.ResolveTrace() 发布【会话级】轨迹到 Ambient
  → 处理器内启动 Agent 执行
  → 执行侧构建【带 Agent 身份】的 execTrace（仅作为数据向下传）
  → 工具在 Ambient（会话级）中执行
  → 浏览器工具发起能力调用
  → TrustedCallerDesktopCapabilityAuthorizer 读 Ambient
  → 有 SessionId、无 AgentInstanceId  ⇒ 规则 ② 拒绝
```

### 文档与实现不符（须一并修正）

`Source/PuddingHost/Hosting/RuntimeTraceContextCallerIdentityProvider.cs:9` 的注释断言：
> 「Runtime 在执行 Agent / 工具时用 `RuntimeTraceContextAccessor`（AsyncLocal）压栈」

**实际不成立**：压栈方是**事件分发器**（会话级），Agent 执行侧**从未压栈**。这条注释正是规则 ② 被误判为"可用"的认知来源。

### 推荐修法（**未实施**，按爆炸半径排序）

| 方案 | 落点 | 爆炸半径 | 评估 |
|---|---|---|---|
| **P1（推荐）** | **工具执行边界**：以工具请求携带的 `Trace` 开 `using var scope = RuntimeTraceContextAccessor.Scope(trace);` | 仅工具执行期 | 语义精确（"此刻的调用方就是这次工具调用"），风险最小 |
| P2 | Agent 执行边界（`Buffered.cs:75` / `Streaming.cs:87` 之后）发布 `execTrace` | 整个 Agent 执行期（含 LLM、事件、日志相关性） | 会改变嵌套事件的轨迹归属，须全量回归 |
| P3 | 授权器侧放宽 | `TrustedCallerDesktopCapabilityAuthorizer.cs` | ⛔ 削弱闸门，与拒收报告 F1 冲突，**不做** |

### 取红验收（能失败才算验收）

- **修前**：`browser_context(list)` 报规则 ②（原始返回已存档于本报告 §三）；
- **修后**：**不再报规则 ②**；若改报规则 ③（变更类需 `ExecutionId`）属**预期推进**，不得据此判失败；
- **反向对照**：未设 Agent 目标页时**仍必须被拒**（证明是补身份、不是放开闸门）；
- **变量隔离**：必须核对同一二进制的前后 A/B，禁止用"重新编译了"混淆变量。
