# 浏览器能力通道启用实测（配置已生效 · 闸门前移到身份）

**实测时间**：2026-10-13 16:41–16:45（+08:00）
**目的**：执行用户指令「先把功能打通」——把 Agent 浏览器从「完全不可用」推进到可用。
**结论一句话**：**配置这一步已经生效并改变了行为**；但**只靠配置无法打通**，当前唯一阻断点已从「无签发者」前移为 **Core 侧身份门禁**（`AgentInstanceId` 为空）。

## 一、已执行的配置改动（两处，均为本机配置，非仓库文件）

| # | 文件 | 改动 | 校验 |
|---|---|---|---|
| ① | `D:\Data\config\system.json` → `desktop.capabilityChannel` | `enabled: true` · `transport: named-pipe` · `desktopId: default` · **`grantable` 显式列全 19 条能力线名** | 脚本 dry-run→apply；写前备份 `system.json.bak-20261013-141134`；写后读回 `written_ok=True`；复查 `SYS_HAS_CHANNEL=True / SYS_HAS_GRANTABLE=True`（size 2322，mtime 14:11:34） |
| ② | `%LOCALAPPDATA%\Pudding\desktop.json` → `desktop` | `capabilityChannel: { enabled: true, desktopId: default, controlTokenHeader: x-pudding-control-token, handshakeTimeoutSeconds: 15 }` | 备份 `.bak-20261013-141134`；复查 `DESK_HAS_CHANNEL=True`（size 823） |

**为什么必须显式列 `grantable`**：握手授予 = `Core 策略上限 ∩ Desktop 声明`，而 `CapabilityChannelConfiguration.DefaultGrantable` **不含** `browser.binding.apply/revoke`、`browser.context.create/close`。只写 `enabled: true` 会得到「通道健康、但关键能力永不授予」的**静默不可用**。线名逐字取自 `Source/Pudding.Contracts/Capabilities.cs` 的 Catalog（唯一真源）。

**回滚**：还原两个 `.bak` 文件 + 重启一次即可回到 2026-10-13 之前的状态。

## 四、为什么"只靠配置"到此为止（三处硬证据）

1. **授权器是硬编码注册的，无配置开关**：`PuddingApplicationHost.cs:315` 直接 `new`，附近无分支；宽松实现 `AllowAllDesktopCapabilities`（`Source/Pudding.CapabilityBroker/ICoreDesktopChannel.cs:44`）**只存在于类库里、无组合根引用**。
2. **该状态是作者有意为之的未完成增量**：`PuddingApplicationHost.cs` 在启用通道处直接打印
   `"[CapabilityChannel] 已启用：显式重绑 REST 与能力通道；授权器=默认拒绝（待切片 D 接入 Tool Runtime 准入）"`；
   同文件注释与授权器 XML 文档均写明「把 Tool Runtime 的权限/审批链也接进来属**切片 D** 的调用点迁移」。
3. **启用通道 ≠ 可用**：即便规则 ② 被满足，变更类（interact/tabs/context.create）还要过规则 ③（`ExecutionId` + `AgentInstanceId`），这属于同一切片。

⇒ 因此**"配置已到头"是取证结论，不是推测**。
