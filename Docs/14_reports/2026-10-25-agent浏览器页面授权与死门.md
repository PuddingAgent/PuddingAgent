# agent 浏览器：页面授权为何拒绝，以及一道未接线的管理门

## 1. 现象

agent 浏览器上下文里**已经打开**着 `https://platform.deepseek.com/usage`
（`contextId=58ae2c7e…`，`pageId=e0c9fb28…`，pageVersion=3）。但四个读操作全部被拒：

| 操作 | 结果 |
|---|---|
| `browser_snapshot`（outline/text） | `no page grant covers '<ctx>/<page>' for this caller` |
| `browser_navigate`（reload） | 同上 |
| `browser_screenshot` | 同上 |
| `browser_tabs`（activate） | 同上 |
| `browser_tabs`（new） | `no task-level management grant allows creating or closing browser targets` |
| `browser_context`（create） | `Capability 'browser.context.create' is not supported` |

`test_tool browser_snapshot` 报告 `registered=true, available=true, actual_permission=Low`——
**卡点是页面授权，不是权限级别或审批。**

## 2. 结论一：页面授权只能由「任务-页面绑定」签发（设计如此）

`Source/Pudding.DesktopService/BrowserTaskBindingService.cs:110`：

```csharp
if (!_issuer.TryIssue(new BrowserGrantIssuanceRequest(...), out var grant, out var epoch, out var reason))
    return new BrowserBindingAcceptance(false, reason, default);
```

其拒绝文案（同文件）明确指出：

> the selected page is already bound to another task; an unrelated task needs its own explicit user selection

这条路径在**生产里是活的**：`Source/PuddingDesktop/Hosting/DesktopApplicationCoordinator.Capability.cs:214`
创建 `BrowserTaskBindingComposition`，`Source/Pudding.DesktopSurface.Browser/BrowserWorkspaceTargetBridge.cs`
持有 `_taskBindings` 并在目标切换时撤销绑定。

⇒ **不是缺陷**。agent 要读某个页面，前提是有人把该页面显式选给这个任务。
在没有绑定之前，任何读取都被 fail-closed 拒绝，这是正确的安全行为。

## 3. 结论二：Management 授权是一道未接线的门（缺陷）

`TabNew` / `ContextCreate` 在策略表里归入 `BrowserGrantKind.Management`
（`Source/Pudding.Common/Desktop/BrowserControlContracts.cs:291` 附近）。而这类授权的唯一签发器是
`Source/Pudding.DesktopService/BrowserGrantIssuer.cs:161` 的 `TryIssueManagement`。

全仓检索 `TryIssueManagement` 的命中共 **7 处**：

| 位置 | 性质 |
|---|---|
| `BrowserGrantIssuer.cs:161` | 定义 |
| `Pudding.DesktopServiceTests/BrowserGrantIssuerTests.cs` ×6 | 测试 |

**没有任何生产调用者。** 该方法自己的注释也写着「生产代码从未签发过这类授权」，
并声明「本方法把那条路补上」——但补完没有接线。

后果：agent 无法自己新建标签页。这既是能力缺口，也让 §2 的唯一补救路径变得不自然
（用户必须事先在某个已存在的标签上完成绑定）。

**边界说明**：把 `TryIssueManagement` 接到 `browser_tabs new` / `context create` 上属于
**扩大 agent 的浏览器权限**，不应由实现自行决定。而且即使接通，新标签也没有用户的登录态，
仍需用户先在该标签里登录目标站点——所以它的价值主要是「能自己开空白页」，不是「绕过登录」。

## 4. 待办（按不扩大权限优先）

1. **用户侧**：在 agent 浏览器里把目标页面绑定给当前任务（若界面提供），即可读 DOM / 翻页 / 触发导出。
2. **产品侧**：明确 `TryIssueManagement` 是要接线还是删除。
   - 接线：`TabNew` / `ContextCreate` 走管理授权，拒绝面与 page grant 同构（行动者不可信、有效期超限、子代理不得自取）。
   - 删除：把策略表里的 `Management` 类型一起删掉，避免留一道「看起来能开、实际永远拒」的门。
3. **不建议**：通过放宽 `BrowserOperationPolicy` 让 `TabNew` 归 `None`——那等于把管理面完全放开。

## 5. 取证方式

均为现场命令与读码，未采信任何自述：

- 工具调用：上表六次调用返回码与文案原文；
- `test_tool browser_snapshot` 的 `actual_permission=Low`；
- `findstr`/`Select-String` 全仓检索 `TryIssueManagement`、`BrowserTaskBindingService`、
  `BrowserGrantKind.` 三组符号并逐处读上下文。
