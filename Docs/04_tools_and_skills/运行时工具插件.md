# 运行时工具插件

插件闭环是：Agent 写代码 → 独立编译 → 打包 ZIP → 导入 → 授权加载 → 下一次模型调用使用新工具 → 卸载。Core 不加载插件 DLL；DLL 位于独立 Worker。首次安装这套基础设施需要部署新版 Core，之后插件的增加、修改与卸载不需要重启 Core。

## 产品工具内核

产品直接注册八个工具。发现入口为 `search_tools`，审批入口为 `request_tool_approval` 和 `list_tool_approvals`，生命周期入口为 `plugin_catalog`、`plugin_import`、`plugin_load`、`plugin_unload`、`plugin_diagnostics`。Agent 能使用哪些入口仍由模板、会话策略和执行审批决定。

文件、Shell、子代理等第一方工具按领域随产品安装。安装清单在 [ToolPackages](../../Source/PuddingHost/ToolPackages/)，每项声明现有工具 ID 和宿主已注册的服务类型。Core 按工作区、实际执行 Agent 和会话挂载导出；类型化工具的配置元数据从工具声明生成，调用时才取得实现；旧式 Skill 和手写描述符需要读取实例元数据。卸载撤销导出、通知在途调用取消并等待退出。领域服务和它的程序集由宿主管理，更新其实现需要重新发布宿主。独立开发和替换的 DLL 使用下节的 SDK 和 Worker。

配置端通过 `GET /api/tools` 取得已安装工具的描述符，状态为 `Installed`，默认选择清单排除这些工具；模型请求只接收已挂载且当前策略允许的定义。Task 角色本身不提供 Shell 授权。

管理员通过 `GET /api/tool-plugins` 查看 `hostTools.packages`、导出名称和内容哈希。选择产品包后，向现有 `load` 接口提交该哈希、作用域、操作 ID 和加载授权，`approvedCapabilities` 传空数组，`enableHooks` 传 false。乐观并发使用 `hostTools.revision`；SDK 包使用顶层 `revision`。Agent 侧 `plugin_catalog` 只列其策略允许的产品工具。Shell 即使已挂载，仍需工具授权和 `AllowShellExecution`；实际调用再次经过执行防火墙。

Windows 上运行 `pwsh -File TestScripts/test-product-tool-plugins.ps1` 可从源码发布测试 Core、使用随包 SDK 构建示例并验证真实调用。脚本将全新的数据根、模型替身、包和证据隔离在本次运行内。[启动脚本](../../TestScripts/test-product-tool-plugins.ps1) · [产品验收断言](../../TestScripts/test_product_tool_plugins.py)

## Agent 使用

编写并运行 DLL 的 Agent 需按需启用 `plugin_import`、`plugin_load` 和相应的文件与进程执行权限。产品声明包只需获准加载，实际操作受原工具策略约束。已加载工具的曝光权限以宿主指定的 `plugin_load` 为锚点；这样无需提前把随机代号写进模板。常规权限模式下，撤销该入口的工具授权会使模型不能再调用这些工具；显式角色白名单始终适用。已批准 Hook 与实例同寿命，需卸载实例以撤销。单个插件工具的副作用仍按实际函数名审批，并检查文件写入、网络、Shell 资源权限。

1. 调用 `plugin_catalog`，获取当前执行身份、SDK 目录、`authoringGuide`、`exampleDirectory`、包目录与实例状态。
2. 用文件工具把示例复制到当前工作目录，再修改源码和 `plugin.json`。不要修改产品 SDK 或现有包目录。
3. 编译示例项目时传 `-p:PuddingPluginSdkDirectory=<目录>`。只引用 `Pudding.ToolPlugins.Contracts.dll` 和 `Pudding.ToolPlugins.Sdk.dll`，`Private=false`；不引用 Core/Host/Runtime。
4. 包根为 `plugin.json`，入口 DLL 放在清单声明的 `bin/` 路径。将自己的托管依赖和 `.deps.json` 同时打包；不要打包 SDK/Contracts 或任何 `Pudding*.dll`。首次支持 Windows x64、net10.0、托管插件；原生 DLL 依赖不在本版合同中。
5. `plugin_import({"path":"plugin.zip"})` 从本轮冻结的绝对工作目录读取 ZIP。宿主提供了显式工作目录时沿用该目录（例如委派 worktree）。普通本机执行从宿主环境取得工作区根，默认位于配置的 DataRoot 下的 `workspaces/<workspaceId>`。文件写入、Shell 默认工作目录与插件导入共享这次绑定。导入返回已验证包内容的 `contentHash`。启动原生 SDK Worker 还需要该次执行具备 `AllowShellExecution` 并通过 `plugin_load` 的审批。
6. `plugin_load({"contentHash":"<hash>","operationId":"<本次唯一ID>","approvedCapabilities":["workspace.read"],"enableHooks":true})`。此操作按原有高风险工具审批执行本地代码；参数必须明确涵盖清单的服务与 Hook。批准包执行不取消后续工具调用的权限边界。
7. 只有回执 `state=Active` 才表示初始化完成、工具已发布。使用回执 `toolNames` 中的真实函数名；下一次模型调用会刷新清单。若曝光预算淘汰了工具，用 `search_tools` 再发现。
8. `plugin_unload({"activationId":"<id>"})`。工具/Hook 先撤销，再回收 Worker；`Unloaded` 表示已观察到退出且宿主回调已排空，`StopFailed` 表示至少一项未确认。包留在目录，可再次加载。相同 operationId 重试幂等；卸载后重新加载必须换 operationId。

固定函数名和旧代调用不能混用。每次加载的函数名包含实例代号；旧模型请求不会错误地调用新版本。替换版本时先导入新包，再卸载旧实例、加载新实例。不会覆盖正在运行的文件，也不会自动把旧调用重放到新版本。

默认实例按 `workspace + 实际执行 Agent + session` 绑定；不使用配置所属 Agent 替代子代理身份。其他 Agent 或会话看不到也不能调用；显式角色工具白名单仍有效，插件不能绕过它。默认不跨会话自动加载、不在 Core 重启后自动恢复实例。使用完显式卸载；Core 退出时回收，Windows Job 关闭时一并回收子进程。当前限制每个 Agent 最多 4 个、整个 Core 最多 16 个活动实例。

## 编写工具和扩展

继承 `Pudding.ToolPlugins.Sdk.ToolPlugin`，实现 `ToolIds` 与 `ExecuteAsync`。可实现 `InitializeAsync`、`ShutdownAsync`；实现的工具/Hook ID 必须和清单完全相符，否则整体加载失败，不发布一半工具。

`PluginCall` 包含冻结的执行身份、callId、截止时间和 JSON 参数。工具返回 `PluginResult.Ok(value)` 或 `Fail(error)`；输入输出都接受清单 schema 校验。支持 object、array、string、integer、number、boolean、properties、required、additionalProperties、items、enum、长度/数值范围；不支持 `$ref`、oneOf 等完整 JSON Schema 特性。

首批扩展点是 `tool.result.advice`：实现 `HookIds` 与 `OnToolResultAsync`，返回 `PluginHookResult(AppendText)`。宿主经现有 `IAgentLoopHook` 注册调用，按 order/pluginId/hookId 排序。最多追加 2048 字符建议，保留原始输出、Success 和 ExitCode。Hook 异常只记录诊断，不阻断原任务；不提供绕过权限、替换系统提示或修改 Core 服务对象的接口。

Core 服务从 `Context.Core` 获取：

| 权限 | SDK 方法 | 边界 |
|---|---|---|
| `workspace.read` | `ReadWorkspaceTextAsync` | 当前调用冻结的工作目录，UTF-8，最多 256 KiB |
| `assets.read` | `ReadAssetTextAsync` | 仅清单声明的包内文本资产，最多 256 KiB |
| `state.read` | `ReadStateAsync` | 当前 workspace/Agent/plugin 私有状态 |
| `state.write` | `WriteStateAsync` | 单值 64 KiB，64 个键，总量 256 KiB；跨本 Agent 的会话保留 |

Core 回调仅在当前 execute 租约和截止时间内可用，且必须同时被清单请求与加载授权；Initialize/Shutdown/Hook 内不允许。禁止相对路径逃逸、重解析点、ADS 和设备名。此约束是 Core 服务合同，**不是限制插件直接调用操作系统的安全沙箱**。

## 隔离和诊断

### Core API 1.1：Agent 配置

引用 `Pudding.ToolPlugins.AgentSdk` 与公共 SDK/Contracts（均由 Worker 随包提供，不重复装进插件包），使用 `using Pudding.ToolPlugins.AgentSdk;`。清单设 `coreApi: "1.1"`，按需请求并批准 `agent.configuration.read/update/changes`；这里三个完整名称分别为 `agent.configuration.read`、`agent.configuration.update`、`agent.configuration.changes`。写工具须声明 effect `agent.configuration.write`，仍经过既有高风险审批。

```csharp
var configuration = Context.AgentConfiguration();
var current = await configuration.GetAsync(ct);
var receipt = await configuration.UpdateAsync(
    new() { DisplayName = "新名称" },
    new(current.Revision, operationId), ct); // operationId 来自明确的一次业务操作
```

仅当前持久执行 Agent 的名称/描述可写；不能指定其他 Agent、管理身份或凭据。每次工具执行最多 16 次配置调用，不超过原工具截止时间。配置读取、更新、变更页复用同一公共 API；回执证明配置源落盘，不等于 UI/活动 Run 已同步。版本冲突不会自动合并；写回执丢失为 `unknown`，以原 ID/原请求核对，不自动重新执行。

配置能力只在 execute 回调中可用；Hook/初始化不可使用。卸载撤销新准入并等待宿主回调，超时返回 `StopFailed/unknown`。首次使用此 API 需部署带 Core API 1.1 的基础设施，之后插件热加载无需重启。工作提交、算子调用和任意服务查找尚未开放；[设计与下一切片](../12_features/插件Agent配置租约与算子开放设计-2026-11-05.md)列出具体边界。

### 进程与协议

Worker 使用同用户命名管道、随机管道名、客户端 PID 核对、版本化帧、requestId/activationId 关联。帧上限 1 MiB；单次 execute 默认 30 秒、最大 60 秒；Hook 3 秒；每次执行最多 32 次 Core 回调。单实例串行，停止可以打断阻塞调用。Windows Job 限制内存与子进程数量；不继承宿主环境中的凭据。stdout/stderr 不作为协议，诊断使用结构化回执。

Worker 以当前 Windows 用户权限运行；只能装载信任的代码。Job 和进程边界用于故障回收，不阻止恶意代码访问同用户资源。[.NET 插件加载说明](https://learn.microsoft.com/en-us/dotnet/core/tutorials/creating-app-with-plugin-support)和 [Windows Job Object 文档](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects)说明了这些边界。

`plugin_diagnostics` 和 Web「工具管理 → 可运行插件」显示状态、PID、内容指纹、作用域与最近失败。诊断含 `code/stage/errorId/effectOutcome`；失败和不确定副作用不能算执行成功。内存诊断最多 256 条，随 Core 重启清空；工具调用本身仍走现有执行审计链。

管理 API 为管理员认证路由 `/api/tool-plugins`：GET 目录、GET diagnostics、POST import、POST load、POST unload。load 必须明确 `executeApproved`，管理操作可带 `expectedRevision` 防止覆盖过期视图。202/已派发或进程存在均不是 `Active` 的替代判据。

旧 `pudding-plugin/v1` 包只保留元数据读取，不能作为模型工具。需按 v2 重新打包；不自动执行旧目录。渠道、前端组件和服务替换尚不是可注册贡献类型；本版交付工具与建议 Hook。

## 开发验收

仓库脚本 `TestScripts/test-pudding-tool-plugins.ps1` 构建独立组件、测试 Fixture、运行器与宿主测试，并把产物和日志放到 `.work/plugins/`。测试覆盖包和权限拒绝、初始化失败、作用域隔离、过期代调用、阻塞/崩溃/输出超限/子进程回收，以及 Buffered/Streaming 两条真实 Agent 循环中的加载→调用→卸载。不依赖外部 LLM 或生产数据。

配置 API 的专门验收入口是 `TestScripts/test-plugin-agent-api.ps1`，包括真实 Worker → 原子配置 writer、变更页、授权、CAS、跨重载去重与撤销排空。

编译闭包由各 csproj 的引用白名单门禁保证：Contracts 叶子；作者 SDK/Protocol/Runtime 只向 Contracts；Agent SDK 只向插件 Contracts 与公共 SDK/Contracts；Windows 适配器向 Protocol；Worker 只向这些 SDK/Protocol/Contracts；宿主适配在 PuddingRuntime/Platform。`.NET AssemblyLoadContext` 仅在 Worker 内处理托管依赖，不作为可卸载的 Core 内插件容器。
