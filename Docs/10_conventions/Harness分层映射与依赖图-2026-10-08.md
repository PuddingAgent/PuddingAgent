# Harness 分层映射与依赖图（实测）

> **上游**：`Docs/10_conventions/质量门禁与Harness架构标准-2026-09-24.md` §5.1（分层与依赖方向）与 §11 附录 A 的 **A1-3「工程 → 层 显式映射表」**。
> **本文件解决什么**：§5.1 的可检查化**缺一个前置件**——如果不知道"哪个工程属于哪一层"，那么"依赖只指向更小编号"就无法断言。本文件给出：①**实测依赖图** ②**L0–L5 提议映射** ③**必须先排除的非生产工程** ④**待人工裁决项** ⑤**复现命令**。
> **状态**：`draft` —— **层归属属提议，未经人工终裁前不得据此写门禁断言**（与标准 §2 范式 E「人工终裁」一致）。

---

## 1. 实测方法与口径（可复现）

**复现命令**（PowerShell 5.1 / 仓库根执行；从 `*.csproj` 的 `ProjectReference` 解析出有向图，按"从叶子起最长路径"算深度，并用访问栈检测环）：

```powershell
$root=(Get-Location).Path
$files=Get-ChildItem -LiteralPath $root -Recurse -File -Filter *.csproj |
  Where-Object { $_.FullName -notmatch '\\(bin|obj|node_modules|temp|\.vs|\.git)\\' }
$map=@{}
foreach($f in $files){
  $n=[IO.Path]::GetFileNameWithoutExtension($f.Name)
  $refs=@(); foreach($m in [regex]::Matches([IO.File]::ReadAllText($f.FullName),'<ProjectReference\s+[^>]*Include="([^"]+)"')){
    $refs += [IO.Path]::GetFileNameWithoutExtension(($m.Groups[1].Value -replace '\\','/')) }
  $map[$n]=@($refs | Sort-Object -Unique)
}
$depth=@{}; $visiting=@{}
function D($n){ if($visiting.ContainsKey($n)){return -1}; if($depth.ContainsKey($n)){return $depth[$n]}
  $visiting[$n]=$true; $d=0
  foreach($r in $map[$n]){ $v=D $r; if($v -lt 0){$d=-1;break}; if(($v+1) -gt $d){$d=$v+1} }
  $visiting.Remove($n); $depth[$n]=$d; return $d }
foreach($n in @($map.Keys)){ [void](D $n) }
$map.Keys | Sort-Object { $depth[$_] },{ $_ } | ForEach-Object { '{0,3} | {1,-42} | deps={2}' -f $depth[$_],$_,($map[$_] -join ',') }
```

| 口径 | 值 |
|---|---|
扫描对象 | 仓库内全部 `*.csproj`（排除 `bin/obj/node_modules/temp/.vs/.git`） |
工程总数 | **81** |
深度定义 | `depth = 0`（无工程引用）；否则 `1 + max(depth(依赖))` |
外部/未扫描引用 | 按 `depth = 0` 计（**不影响**本仓内部的相对比较） |
环检测 | 访问栈回边 ⇒ 该节点深度记为 `-1` |

**⚠️ 统计陷阱（本轮实测踩到）**：`Get-ChildItem -LiteralPath … -Include *.csproj` 中 **`-Include` 不生效**（`-LiteralPath` 下被忽略），会把非目标文件一并枚举。本节命令使用 **`-Filter *.csproj` + 目录排除**双保险。

## 2. 结论摘要（实测）

1. **环：0 个**（负深度节点数 **0**；81 工程全量、全路径检测）⇒ 标准 §5.1.1 中"**可见子集内无环（⚠️ 未全量证明）**"这一保留，**本轮升级为「全量已证」**。
2. **真正的叶子契约候选**：`Pudding.Contracts` · `Pudding.Rpc.Protocol` · `PuddingBrowser.Protocol`（三者 `depth=0`，无工程引用）。
3. **`PuddingCore` 的 `depth = 1`**，自身**只依赖 `PuddingDiagnostics`**。⇒ 它与 §5.1.1「混合内核」的判断一致，但注意：**它并不是依赖图的顶端**（被大量工程引用 ≠ 它依赖别人）。**§5.1 的阻塞点是"它内部混装契约与实现"，不是"它的依赖太多"。**
4. ⭐ **`depth ≠ 层`**：`PuddingPathFiltering` / `PuddingIndexChunking` / `PuddingVectorIndex` / `PuddingRetrievalEval` / `PuddingCodexService` **都是 `depth=0`**，但按角色它们属 **L2 能力实现**。⇒ **层号必须"显式声明"，不能从依赖深度自动推导**；能自动化的只有"**声明层号之后的一致性断言**"。
5. **必须先划生产范围**：81 个工程里有 **≥11 个非生产工程**（探针/基准/冒烟/归档/测试站点/内嵌库）——若不排除，任何"层方向/边界"断言都会被它们污染（与附录 A 的教训同源：**作用域未定义 ⇒ 数字不可定性**）。

## 5. 待人工裁决项（**这是本文件的核心产出**）

| ID | 待裁决 | 为什么不能由自动化决定 | 影响 |
|---|---|---|---|
**D-1** | L0 是否包含 `PuddingBrowser.Protocol` / `PuddingDesktop.Foundation`；L0 是否**必须零第三方包** | 依赖图只能证明"无工程引用"，**不能证明"仅依赖 BCL"**（本项目 L0 的实际判据是"无包引用 + 无 I/O 符号"）；且 `PuddingDesktop.Foundation` 命名像基础库、实际内容未核 | L0 是否可断言 |
**D-2** | `PuddingDiagnostics`（与 `github.hyfree.GM`）算 L0 还是"**横切关注点**"独立一层 | 它对所有层开放（谁都能用），若强行塞进 L0 会让"L0 只依赖 BCL"失真 | 层数定义（是否引入 L-X 横切层） |
**D-3** | `HarnessAgent.Core`（**第二套 harness 实现**、休眠、却被 `PuddingHost` 引用）归 L3、冻结，还是删除 | 属**产品决策**（历史包袱 vs 在用能力） | L3 范围 |
**D-4** | `PuddingDesktop` 既是组合根（L4）又是 WPF shell（L5）；`PuddingDesktop.CapabilityHost` 虽 `depth=1` 却可能扮演宿主角色；`PuddingAgent` 是 L4 还是 L5 | 标准 §5.1 的 L4/L5 划分在"桌面端单进程"下**天然重叠**，需要人为定一条规则（例："凡含 `Main`/WPF `App.xaml` 者归 L5"） | 桌面侧断言 |
**D-5** | `github.hyfree.GM`（**内嵌第三方库**，package 名样式）是否纳入层级体系 | 它是"外部依赖"还是"本仓工程"，取决于是否允许本地源码引用的治理口径 | 边界治理 |
**D-6** | `PuddingDesktop.WpfArchive` / `MiniProject` / `PuddingWsTest` / `Mcp.Cli` 是否**冻结/删除** | 归档与夹具是否长期保留，属维护策略 | 非生产清单是否长期有效 |

**建议裁决顺序**：**D-4 → D-2 → D-1**（先定 L4/L5 边界，再定横切层，最后定 L0 纯度判据），因为前两者决定层数**数量**，D-1 只是在既定层上填内容。
