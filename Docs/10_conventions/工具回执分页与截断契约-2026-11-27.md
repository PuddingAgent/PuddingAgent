# 工具回执的分页与截断契约

任何"按窗口返回内容"的工具（`file_read` 是当前最复杂的一例）都要同时处理三件事：
**选窗口**（护栏 / Head / Tail / Offset+Limit）、**截预算**（`max_chars`、inline 字节预算）、
**告诉调用方下一步怎么读**。三者顺序错一次，回执就会自相矛盾。

本文的每条断言都来自 2026-11-26 ~ 11-27 的运行时实测与变异取红，不采信代码阅读的直觉。

## 1. 五条不变量

| 编号 | 不变量 | 违反后的具体症状（实测） |
|---|---|---|
| **I1** | **先定窗口，再截预算** | `max_chars` 提前 `return` ⇒ `offset_lines=20` 被丢弃，从第 1 行开始返回；同一调用把预算调大后 offset 又"生效"，结果取决于预算是否够 |
| **I2** | **续读位只能描述已交付内容** | 首行被切到中间却给 `continue from line 2` ⇒ 首行剩余部分永远取不到；更糟的是 `OffsetLines=0` ⇒ 照做得到逐字相同的回执，形成死循环 |
| **I3** | **建议必须可兑现** | 首行 20000 B > 7680 B inline 预算，仍劝 `Raise max_chars` ⇒ 调用方把预算提到行长（20000）也取不到，同一段回执里前一行刚说过 `not addressable` |
| **I4** | **每处裁切都要出声** | 单行 20002 B 只交付 7680 B 且 `truncated = emittedLines < lines.Length` 恒假 ⇒ 12322 B 静默丢失；`max_entries=0` 被夹到 1 却只在上限侧提示 |
| **I5** | **两条提示若同时出现，数字必须相等** | 字节闸门说 `OffsetLines=210`、`max_chars` 说 `OffsetLines=8` ⇒ 两个数字都对不上正文末行，调用方只能猜 |

## 2. 三条互斥情形与判定顺序

判定只看两件事：**首行有没有超过 inline 字节预算**、**本次窗口有没有交付完整行**。

| 情形 | 判据 | 该给什么 | 不该给什么 |
|---|---|---|---|
| **A 不可寻址** | 首行字节数 > inline 预算 | 说明"第 1 行只剩前 N 字节，该行剩余部分不可寻址" | 任何行偏移；`Raise max_chars` |
| **B 预算不够** | 首行 ≤ 预算，但窗口内 0 完整行 | 劝提高 `max_chars`，并可给出可行值 | 行偏移（`OffsetLines=0` 是死循环） |
| **C 正常截断** | 窗口内有完整行但被截 | `OffsetLines = 已读行数 + 窗口起点`，绝对行号 | 相对行号；与另一条提示不同的数字 |

**A 与 B 的实现陷阱**：两者的"已消费行数"都是 0，若调用点统一传 `FirstLineTruncated ? 0 : EmittedLines`，
就丢掉了"为 0 的原因"，而原因正是建议真假的判据。传 `bool` 比传 `0` 更安全。

## 3. 单位纪律：`max_chars` 计字符，inline 预算计字节

CJK 3 字节/字符 ⇒ 同一次调用可能给出看起来矛盾、实际自洽的结论。实测（单行文件）：

| 臂 | 内容 | `max_chars` | 回执 |
|---|---|---|---|
| F | 3000 字 = 9000 B | 3000 | `no max_chars value can deliver it`（可寻址性由 9000 > 7680 决定） |
| G | 2000 字 = 6000 B | 1000 | 劝提高预算 |
| G2 | 同上 | 2000 | 完整交付 6000 B |

F 不是缺陷：两个数字量的不是同一件事。**写验收断言时不要用"字符数 == 字节数"的 ASCII 样本推断 CJK 行为。**

多行 CJK 的偏移推进同样成立：每行 121 B、`max_chars=8000` ⇒ `lines 1..63 shown (7622 bytes)`，
`7622 = 63×121 − 1`，且加 `offset_lines=100` 后变成 `lines 101..163`、`OffsetLines=163`
（绝对行号，不是相对行号）。

## 4. 参数组合的静默丢弃：设计还是缺陷

判据一句话：**结果正确但与调用方意图不同、且调用方无法察觉 ⇒ 缺陷**；结果正确且与文档一致 ⇒ 设计。

| 现象 | 判定 |
|---|---|
| `tail_lines=100` 对 10 行文件返回全部 10 行、无提示 | **设计**（"从一端取 N 行"，N 超总行数等于全取） |
| `offset_lines=8` + `tail_lines=3` 返回末 3 行（忽略 offset），无提示 | **缺陷**（要的是"第 9 行起的末 3 行"） |
| `head_lines=5` + `limit_lines=2` 返回 5 行，无提示 | **缺陷** |
| `file_path` 指向不存在文件 → `count=0`、无提示 | **设计**（`count=0` 已足以表达"没匹配上"；加提示会与"文件已删除但仍有历史"混淆） |

出声即可，不必改行为：分支优先级（Head → Tail → Offset）保持不变，只在提示里写明"哪个参数被忽略、由谁选定窗口"；
三个都不给时不出声，正常路径必须安静。

## 5. 变异取红纪律

| 要求 | 反例（实测） |
|---|---|
| 每条分支独立打红**不同**用例 | M1/M2 只打红同一个用例 ⇒ 说明两条断言其实守的是同一处，另一条是多余的 |
| 必须有**正向对照** | 没有"窗口装得下时不发提示"这条，一个恒发提示的实现也能让全部截断用例通过 |
| 删除新分支后旧用例仍绿 | 证明新分支没有偷走旧用例的职责（M3 实测：37 绿 / 2 红） |
| 恢复要**逐字节** | `SHA` 相同 + `-t:Rebuild` 才算恢复；`Copy-Item` 保留 mtime，msbuild 会跳过重编译 |
| 锚点断言先于写盘 | 缩进推错（16 vs 20 空格）时 `count=0`，脚本必须在 `WriteAllBytes` 之前失败 |

## 6. 未决（等用户裁定，勿单方面改）

1. `lines 101..163`（1-based 行区间）与 `OffsetLines=163`（0-based 偏移）并存 ⇒ 同一段里"163"出现两次、含义不同，易读成"重读第 163 行"。
2. `head_lines` + `offset_lines` 同时给出的语义：现在是"从头取 N 行并提示 offset 被忽略"，是否改为"从 offset 起取 N 行"。

## 7. 沉淀下来的三个反例

- **`truncated=true` 先数被查对象的实际总数，再谈缺陷**：`git_log` + `file_path` 一度"看起来所有提交都给了却报截断"，实测该文件真有 2 次提交（`Take(count + 1)` 判定），按"假截断"去改会引入一次额外的全量历史枚举。
- **判 EOL 不能用文本模式**：`py open()` 文本读把 `\r` 归一化掉，误报"整文 LF 化"；`ReadAllBytes` 才是判据。
- **`file_patch` / `file_write append` 会把整文 LF 化**：仓库期望 CRLF 的文件改完要核 `BARE_LF=0` 再提交。
