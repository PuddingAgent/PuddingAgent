# shell 工具的退出码归因与 cmd 外壳编码约定

## 1. 三条结论

| 事项 | 事实（2026-11-26 本机实测） |
|---|---|
| 退出码从哪来 | `HostShellExecutor.cs:105`：`Error = process.ExitCode == 0 ? null : $"exit code {process.ExitCode}"`，**原样转发，无归一化** |
| cmd 对「命令不存在」返回什么 | **1**（不是 9009）。`shell=cmd` 与 `shell=powershell` 内层调 `cmd /d /s /c` 两种形态都是 1 |
| cmd 内置中文诊断消息编码 | OEM 码页（本机 CP936），被按 UTF-8 解码 → `'x' �����ڲ����ⲿ���…`（U+FFFD） |

## 2. 退出码归因：只归因「shell 自己定义的」码

`AgentExecutionService.BuildFailureSuggestion` 的现有分配：

| 错误形态 | 归因 | 依据 |
|---|---|---|
| `timed out` | 超时建议（改 `terminal_start`+`terminal_wait` 或调大 `timeout_seconds`） | 与命令语义无关 |
| `is a file, not a directory` | 目录参数误用建议 | 明确 |
| `exit code 9009` / `exit code 127` | 「shell 找不到命令」 | 9009 由 cmd、127 由 sh/bash 定义，**不是被调命令的退出码** |
| 其他 `exit code N`（含 1/2/255） | 通用建议（不猜） | `1` 同时意味着 `findstr` 无匹配、`dotnet build` 失败、`git diff --exit-code` 有差异、脚本 `exit 1` |

**为什么不给 `exit code 1` 加归因**：猜错比不猜更贵。把 `git diff` 的差异当成 PATH 问题，会让人去查一个不存在的环境问题。既有测试特意用 `"exit code 1"` 作为「无法归因」的样例钉住这一行为。

### 2.1 9009/127 分支在当前构建上不可达

历史数据里确有 3 条（2026-11-13、2026-11-21，全部 `tool_runner` + `shell`），但本机造不出来：

```
shell=cmd:              nonexistent_cmd --version            → exit code 1
shell=cmd:              cd /d <dir> & nonexistent_cmd        → exit code 1
shell=powershell:       cmd /c nonexistent_cmd               → exit code 1
shell=powershell:       cmd /d /s /c nonexistent_cmd ; "RC=$LASTEXITCODE"   → RC=1
shell=cmd:              chcp 65001>nul & nonexistent_cmd     → exit code 1（中文仍 U+FFFD）
```

第四条是决定性的：**RC=1 是 cmd 自己的退出码**，不是平台改写。所以那条归因分支保留（历史真触发过、单测守着实现不退化），但在当前环境**不产生线上行为**。详见 `Docs/14_reports/2026-11-26-exit-9009归因分支在当前构建不可达.md`。

### 2.2 更正（2026-11-26 17:44 实测）：9009 可达，条件是「名字能解析但无法执行」

§2.1 的结论只说对了一半：`cmd` 对**不存在的名字**返回 `1`，但对**能解析到、却不能执行的条目**返回 `9009`。本机 `python` 正是后者 —— `%LOCALAPPDATA%\Microsoft\WindowsApps\python.exe` 是 Microsoft Store 的 App Execution Alias 桩。

原始探针（`shell` 工具，`shell=cmd`，17:44 平台时间）：

```text
python --version
→ Tool FAILED (exit=9009)
   Error: exit code 9009
   [stderr]: Python was not found; run without arguments to install from the Microsoft Store,
             or disable this shortcut from Settings > Apps > Advanced app settings > App execution aliases.
   💡 Suggestion: exit code 9009 (cmd) / 127 (sh) means the shell could not find the command itself.
                  Check the command name and PATH, and pick the shell= ...
```

三件事同时被这一条回执钉住：

1. **9009 在当前构建可达**，不必等环境变化。历史那 3 条（2026-11-13 / 11-21）大概率就是这个成因。
2. **旧建议会误伤**：stderr 已经写明「名字找到了，是别名桩」，而建议只说「查命令名和 PATH」—— PATH 本来就是对的。
3. 因此 §2.1 的「不产生线上行为」作废；该归因分支是**有效**的，且建议文案需要区分两种成因。

旧建议 → 新建议（本轮改动）：

```text
旧：… means the shell could not find the command itself. Check the command name and PATH, …
新：… means the shell could not execute the command. Check the command name and PATH, …
    A name that PATH does resolve can still fail this way: on Windows 'python' is normally a
    Microsoft Store App Execution Alias stub that reports 9009 — use the real launcher ('py')
    or the interpreter's absolute path.
```

实证：本机 `py -V` → `Python 3.14.7`（退出码 0），`python -V` → `Python was not found`（9009）。

## 3. cmd 外壳的编码

`HostShellResolver.ConfigureUtf8Environment` 对所有 shell 统一设：

```csharp
psi.StandardOutputEncoding = Encoding.UTF8;
psi.StandardErrorEncoding = Encoding.UTF8;
```

- **PowerShell 侧**有配套：`WrapPowerShellCommand` 先把子进程 `[Console]::OutputEncoding` 改成 UTF-8，两边一致。
- **cmd 侧没有配套**。`cmd.exe` 及其内置错误消息按 OEM 码页（CP936）输出字节，平台按 UTF-8 解码 → 中文变 U+FFFD。模型读到的是一条读不懂的错误。

实测 `chcp 65001>nul &` 前缀**无效**——cmd 内置诊断消息不受它影响。

### 3.1 使用约定（规避，不需要改代码）

1. **默认用 `auto`**：Windows 上解析为 pwsh 7 优先，错误消息是英文可读。
2. 需要 PowerShell/Unix 语义时显式 `shell=powershell` / `wsl` / `bash`。
3. **只有确实需要 CMD 专有语法**（`%VAR%`、`&` 链、`cd /d`）时才 `shell=cmd`，并预期**中文诊断不可读**；此时把工作目录交给 `working_directory` 参数，不要写 `cd /d` 前缀（平台还有 `shell_syntax_mismatch` 拦截）。

## 4. 未采纳的修法与代价

| 方案 | 收益 | 未采纳原因 |
|---|---|---|
| cmd 分支单独设 `StandardErrorEncoding = Encoding.GetEncoding(936)` | cmd 诊断可读 | 用户程序写到 stderr 的 UTF-8 会**反向乱码**；影响所有 `shell=cmd` 调用，需要按流（stdout/stderr）与按 shell 分别论证 |
| 强制 `chcp 65001` 前缀 | —— | **已实测无效**（§2.1 第五行） |
| 规范化为 `exit code 1` 之外的语义 | —— | 归一化会掩盖真实退出码，且 9009 在当前环境本就不可达 |

保持现状 + 本文档化规避，是当前取舍。

## 5. 复现命令

```cmd
:: ① 退出码：应看到 exit code 1（不是 9009）
shell=cmd:  nonexistent_cmd_probe --version

:: ② cmd 真实退出码：应看到 RC=1
shell=powershell:  cmd /d /s /c nonexistent_cmd_probe ; "RC=$LASTEXITCODE"

:: ③ 编码：应看到中文被 U+FFFD 替换，且加 chcp 也无效
shell=cmd:  chcp 65001>nul & nonexistent_cmd_probe
```

## 7. `if` 后面的 `&` 整段被吞（2026-11-26 逐臂实测）

一条长期记在 `AGENTS.md` 里的归因是「cwd 落在 Agent 私有目录时 `cd /d <dir> && <cmd>` 会整链静默跳过」。今天为查一次「备份命令退 0 却没生成文件」逐臂实测，**推翻了这个归因**。

### 7.1 六条臂

| # | 命令形状 | 结果 |
|---|---|---|
| 1 | `cd /d <私有目录> && copy /Y goal.md archives\…\a.md` | **成功**：回执「已复制 1 个文件」，文件存在 |
| 2 | `cd /d <私有目录> && echo … > <仓库 temp>\d.txt` | **成功**：文件存在 |
| 3 | `cd /d <私有目录> && if not exist <存在的目录> mkdir <该目录> & copy … > nul & powershell …` | **静默跳过**：无任何输出、退出码 0、目标文件不存在 |
| 4 | `if not exist <存在的目录> mkdir <该目录> & echo TAIL_RAN` | **无输出** |
| 5 | `if not exist <不存在的目录> mkdir <该目录> & echo TAIL_RAN` | 输出 `TAIL_RAN` |
| 6 | `cwd` 参数指到 <私有目录> + `echo` | **成功**：输出 `CWD_PARAM_RAN` |

臂 1、2、6 否掉了「私有目录」这个归因；臂 4 与臂 5 用同一命令、只差条件真假，把原因钉在 cmd 的 `if` 上。

### 7.2 机制

`if <cond> cmd1 & cmd2` 里，`&` 之后的部分属于 **if 语句自身的命令行**。条件为假时 `cmd1` 与 `cmd2` 一起被跳过，**退出码仍是 0，也没有任何提示**。

这次的实际后果：备份目录本来就在 ⇒ `if not exist` 为假 ⇒ 紧跟其后的 `copy` 与 `powershell` 都没跑，回执是「exit 0 + 空输出」，而 goal 备份根本没生成。

### 7.3 规避

1. 「不存在则创建」与后续动作**分开**：单独一次调用，或用括号把 if 体闭合，不要用 `&` 把后续命令接在同一条 `if` 后面。
2. `&&` 前置判断是安全的（`cd /d X && cmd` 不属于 if 的命令行）；危险的是 `if … & …` 这个组合。
3. 备份/复制这类有副作用的动作，以「**目标文件存在 + 字节/SHA 与源一致**」验收。这次退出码与回执都干净，只有核对文件才看得出没执行。

### 7.4 复现

    :: 应无任何输出（目录已存在）
    shell=cmd:  if not exist <存在的目录> mkdir <该目录> & echo TAIL_RAN

    :: 应输出 TAIL_RAN（目录不存在）
    shell=cmd:  if not exist <不存在的目录> mkdir <该目录> & echo TAIL_RAN

### 7.5 对旧条文的处理

`AGENTS.md` 那句按「改记录不删记录」就地加注了本次复测结论与正确归因，原文保留 —— 它描述的症状（退出 0、无输出、命令没生效）是真的，只是被归错了原因。
