# 工作区产物清理规程

## 1. 问题（实测）

2026-11-11 盘点本机仓库：

| 位置 | 体积 | 说明 |
|---|---|---|
| `.work/` | **233 GB** | 约 170 个历史任务目录 |
| `bin`/`obj`（`.work` 外） | 14 GB | 583 个目录 |
| `temp\build\guardian` | 15.45 GB | 旧独立构建 |

单任务示例：`commit-scope` 19.8 GB、`first-round` 19.3 GB、`agent-work-api` 17.4 GB、`ds-pa03-a` 15.1 GB。

每个任务的体积主要来自 `.../solution-artifacts/bin`、`.../gate-build/bin`——**一整套 Debug 构建产物**。

## 2. 根因

交付流程需要一份"干净、可复现"的构建产物来验证，做法是复制整套输出到 `.work/<任务>/`。这个做法本身合理，问题在于：**没有任何一步负责回收**。

产物一旦落地就永久留存，而每次交付又必然产生新的一份。

## 3. 约定

1. **任务收尾时删除自己的 `.work/<任务>/` 子目录。**
   交付完成、证据入库（commit / 报告）之后，那份产物副本就不再需要。
2. **`.work/` 只放当前进行中的任务。**
   跨会话仍需保留的证据应写进 `Docs/`，不要指望 `.work/` 长期保存。
3. **定期执行清理工具**（见 §4），处理遗漏项。

## 4. 工具

```powershell
# 默认 dry-run：只打印将删除的目录与总大小
pwsh -NoProfile -File TestScripts/clean-work-artifacts.ps1

# 实际删除 2 天前的任务目录 + 陈旧 bin/obj
pwsh -NoProfile -File TestScripts/clean-work-artifacts.ps1 -Apply

# 只看 .work，不动 bin/obj
pwsh -NoProfile -File TestScripts/clean-work-artifacts.ps1 -SkipBinObj
```

参数：

| 参数 | 默认 | 含义 |
|---|---|---|
| `-MinAgeDays` | 2 | 只处理最后写入早于 N 天的目录 |
| `-Apply` | 关 | 不加就是 dry-run |
| `-RepoRoot` | `D:\CodeProject\PuddingAgent\PuddingAgent` | 仓库根 |
| `-SkipBinObj` | 关 | 跳过 `.work` 外的 `bin`/`obj` |

## 5. 保护清单（脚本内置，不可关闭）

- 路径含 `\temp\build\winui3` 的一律跳过：**运行中的 Core / Desktop / Guardian 从那里加载程序集**。
- 脚本只扫描仓库根之下的路径，不触碰 `D:\Data\databases`。
- 删除使用 `cmd rmdir /s /q`，以便处理超过 `MAX_PATH` 的路径；删除失败会逐条列出，不静默忽略。

## 6. 局限

- **不处理 `.work` 之外的其它膨胀源**：`D:\Data\browser`（WebView 缓存）、`D:\Data\logs`、`fulltext-index` 各有独立生命周期，需要单独判断。
- **删除 `bin`/`obj` 会导致下次构建全量重建**（数分钟）。这是预期代价，不是缺陷。
- **`-MinAgeDays` 依据目录 mtime**：若某任务目录被后续操作触碰过，其 mtime 会被刷新而跳过清理。需要强制清理时用 `-MinAgeDays 0` 并人工确认清单。
- 脚本未经"删除中进程占用"场景的自动化测试；遇到锁文件时以 `FAILED` 列表如实报告，不重试。

## 7. 实测记录

2026-11-11 首次执行（人工，分三批）：

| 动作 | 释放 |
|---|---|
| 删除 11-11 之前的 168 个 `.work` 任务目录 | 166.6 GB |
| 删除 583 个 `bin`/`obj`（`.work` 外） | 14.0 GB |
| `temp\build\guardian` + `recovery` | 16.5 GB |
| `D:\Data\browser\agent-browser` + `contexts` | 1.5 GB |
| `D:\Data\logs` 7 天前（8186 个文件） | 280 MB |

结果：`D:` used 332 GB → 132.8 GB。四个 Pudding 进程全程存活。

清理后 `.work` 保留 9.7 GB（当日进行中任务）。

## 6. 实测冲突：`.work/` 事实上已是证据仓库（2026-11-13）

本规程 §3.2 要求「证据写进 `Docs/`，不要指望 `.work/`」。但 2026-11-13 实测：

```
findstr /s /m /c:".work/" Docs\*.md   ->  169 个文件
```

**169 份文档**（changelog、reports 为主）把 `.work/` 下的路径当作证据位置引用。典型：

| 被引用的 `.work` 目录 | 体积 | 引用处 |
|---|---|---|
| `agent-tool-ownership/20261111` | 9.27 GB | `00_changelog/2026Year/11/2026-11-11-Agent工具挂载归属.md` |
| `dingtalk-routing/20261112` | 0.52 GB | `00_changelog/2026Year/11/2026-11-12-钉钉已绑定成员执行路由.md`（`health.json`） |
| `winforms-uia-probe` | 0.41 GB | `14_reports/2026-11-11-UIA观察层可读性核查-actionable恒0定案.md`（`UIA_ASM_LOC`） |

### 由此得出的操作约定

1. **`bin`/`obj` 清理是安全的**，随时可做——它们不被任何文档引用（本次释放 15.03 GB）。
2. **`.work/<任务>` 的删除必须逐一核对引用**，不能只按 `-MinAgeDays` 批量删。
   批量删会让 169 份文档中的一部分指针变成死链，而删除动作本身不会报错。
3. **交付时应把被引用的小件搬进 `Docs/`**（如 `health.json` 这类 KB 级产物），
   大件（构建产物、日志全集）不必搬，但引用处应写明「产物已清理，结论见本节」，
   而不是留一个指向已删除路径的链接。
4. §3.2 的理想不改，但要承认现状与理想有 169 份文档的差距——**清理前先查引用**。
