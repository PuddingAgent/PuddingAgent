# 记忆维护规程（人工期 v1）

- 日期：2026-10-27
- 状态：**人工执行**（PuddingAgent 侧自动化尚未实现，见 §6）
- 适用对象：`save_memory` / `grep_memory` / `query_session_logs` / goal.md / `memory/*.md` / `archives/*`

## 0. 为什么需要它

召回是**被动触发**的：靠关键词搜、靠会话新建时的记忆管线注入。
Agent 在"不知道自己忘了一件事"时不会去搜 —— 2026-10-27 实测过一次：早前 standing order
「部署验收脚本 + 回滚路径」的产物 `Docs/15_tasks/2026-10-21-Desktop部署与回滚.md` 一直存在，
但被当成"待办"挂着，直到用户提醒才召回。

⇒ 记忆的价值不在写进去，在**过期、核对、更新**这三件事有没有人做。

## 1. 过期机制

给每条记忆一个**可判定的寿命**，到期不是删除，是**降级为"待复核"**。

| 记忆类型 | 寿命 | 到期动作 |
|---|---|---|
| 路径 / 目录 / 文件名 / 端口 | **7 天** | 必须现场 `Test-Path` / 实测后才可引用 |
| 版本号 / 提交号 / 行号 / 字节数 | **3 天** | 引用前重新取，或改写成"当时为 X（YYYY-MM-DD）" |
| 实测数字（大小 / 行数 / 耗时 / 成本） | **7 天** | 注明时点；再次使用前复测或标注"未复核" |
| 开关默认值 / 配置值 | **14 天** | 采信前读源码或配置文件确认 |
| 决策 / 架构结论 / 用户偏好 | **长期** | 不作废，但被推翻时必须标 `superseded` |
| 一次性事故 / 环境型失败 | **长期** | 必须带时点与探针输出；环境变化后**复测再下结论** |

**禁止**：把"当时的结论"写成"现在的事实"。写法上区分：

- ✅ `2026-10-27 实测：platform.db 11.95 GB`
- ❌ `platform.db 是 11.95 GB`

## 2. 核对机制

**凡召回命中涉及"存在性 / 路径 / 默认值 / 数量"的结论，采信前必须核盘。**
召回给的是**线索**，不是事实。

必须核盘的断言类型：

1. 「某文件/目录存在」→ `Test-Path`（并核对大小/时间戳）
2. 「某个默认值/开关是 X」→ 读源码或配置文件
3. 「已修复 / 已部署」→ `git log` + 进程镜像/文件 mtime（**部署 ≠ 重启**）
4. 「某功能没有测试」→ 先跑**正对照**（同法搜一个已知存在的符号），否则空结果可能是范围错
5. 「某文档说的是对的」→ 文档是**陈旧投影**的高发区，以磁盘为准

**反例纪律**：如果核对结果与记忆不符，**改记录，不删记录** —— 保留"曾经这么认为"这个事实，
追加一条带时点的更正。

## 3. 更新机制

- **幂等覆盖**：同一 key 用 `save_memory` 覆盖，不追加同义条目。
- **失效不删除**：旧条目加 `superseded`（被哪条取代、取代时间），保留可追溯链。
- **大段内容外置**：`save_memory` 只存摘要 + 路径指针；正文写 `memory/*.md` 并登记 `INDEX.md`。
- **写完自检**：落盘后读回校验（字节数 / 关键串存在），不采信写工具的回显。

## 4. 触发时机（人工期由我执行）

| 时机 | 动作 |
|---|---|
| 会话开始、召回命中后 | 对命中的路径/数字类结论做一次核盘；不符则当场更正 |
| 每次提交前 | 检查本次是否产生"会过期的事实"，是则写入并带时点 |
| 心跳空闲 | 抽查 1 条最老的路径类/数字类记忆，核盘并更新 |
| 发现记忆与磁盘冲突 | 立即更正并记录冲突本身（这是召回质量的信号） |

## 5. 已知缺口（如实记录，不粉饰）

1. 召回靠关键词；**"不知道自己忘了"这件事无法自愈**，只能靠周期性抽查。
2. 记忆会过期，但**过期不会自动提示** —— 目前靠人记得去看 §1 的寿命表。
3. `save_memory` 无强制时点字段，时点只能写在正文里，**无法被机器过滤**。

## 6. 后期应交给 PuddingAgent 的部分（未实现）

- 记忆条目带结构化 `observedAt` / `ttlDays` / `supersededBy` 字段，到期自动降级为"待复核"。
- 涉及 `path` / `defaultValue` 类型的记忆，写入时自动挂"需要核盘"标记，召回时提示。
- 定期（如每日）自动抽查 N 条最老条目，跑一遍存在性核对，产出差异报告而非静默更新。
- 召回结果与磁盘冲突时，落一条 conflict 事件（这是召回质量的度量，不只是数据修正）。

## 1.1 状态类记忆必须拆「结论」与「数字」两段（2026-10-27 首例实证）

**事故形态：同一条记忆里一半过期、一半有效。**

实测例证：某条 2026-10-21 的状态记忆写着「HEAD=64b2682，27 项待部署，Desktop 跑旧产物」。

- 「HEAD=64b2682 / 27 项」→ 数字段。10-27 核盘时 HEAD 已到 `765101d`，**数字死了**
- 「Desktop 仍跑旧产物、尚未部署」→ 结论段。核盘后**依然成立**

按 §1 字面执行，这条会被整体判为「过期」而作废 —— **但它最重要的结论是对的**。
这是记忆过期最坑的形态：不是全错，是半对。

**规定写法**（状态类记忆一律两段）：

```
结论：Desktop 仍在跑旧产物，尚未部署。                          <- 长期，直到被证伪
数字：HEAD=765101d；待部署提交 5 个（2026-10-27 23:50 实测）。   <- 3 天寿命，过期即作废
```

**核对纪律**：核盘时**分段判定** —— 只作废过期的数字段；结论段必须另行证伪才可推翻。
禁止「因为数字不对就把整条记忆丢掉」。

**后续自动化（交给 PuddingAgent）**：结论段与数字段存为两个字段（如 `claim` / `measured`），
`measured` 带 `observedAt` + `ttlDays`，到期只降级 `measured`，`claim` 不受影响。

## 6. 分层落位表（2026-10-28 补）

记忆不是一层，是**五层加一个归档**。每层解决不同的失效模式：写入成本、检索能力、可读性、留存期限。

| 层 | 载体 | 放什么 | 不放什么 | 检索方式 | 当前状态 |
|---|---|---|---|---|---|
| **L4 原始** | `query_session_logs` | 每轮对话原文 | —（自动产生） | FTS | ⚠️ **2026-10-28 实测不可用**（阳性对照也 `no_match`） |
| **L3 正文** | `Docs/**`（git 追踪） | 分析过程、实验数字、设计、判决、规程 | 待办状态、临时路径 | `search_grep` / 文件名 | ✅ 可靠，且可 code review |
| **L2 图书馆** | `grep_memory`（memory.db） | 关键事实、决策、偏好、可检索结论 | 大段过程 | FTS5 | ✅ 2026-10-28 验证可用 |
| **L1 记忆** | `save_memory` | 摘要 + **路径指针**（≤200 字） | 正文 | FTS | ✅ 可用 |
| **L0 索引** | `goal.md`（**≤4 KB**） | 当前状态、指针、待办**标题** | 任何内容 | 每次会话必读 | ✅ 2026-10-28 重构为索引 |
| **归档** | `memory/archives/**` | 旧版快照、超限正文 | 活动内容 | 不检索 | append-only，逐位 + SHA 记账 |

### 6.1 两条方向

- **写：自下而上摘要。** 过程进 L3 → 结论进 L2 → 摘要+指针进 L1 → 状态与标题进 L0。
- **读：自上而下展开。** 先读 L0 → 按需 L1 → 再 L2 → 最后才 L3。**不允许**会话一开始就把 L3 全读进上下文。

### 6.2 每层必须有指针，否则等于没有

L1 条目不带路径指针 = 只记住"有这么回事"，找不回正文。L0 待办不带指针 = 忘了当初为什么这么写。

**强制**：L1 的 `content` 必须含至少一个可定位路径（`Docs/...`、`memory/...`、`Source/...`）。

### 6.3 L4 不可用时的替代（2026-10-28 起生效）

`query_session_logs` 的 FTS 当前取不到数。**后果**：只写在对话里、没落 L2/L3 的结论，跨会话即丢失。

⇒ 因此当前的有效载体只有 **L2 / L3**。凡属"下次还要用"的东西，**必须落库，不能只在对话里说**。

⚠️ 同时记住判断口径：**阳性对照失败 ⇒ 只能报"检索不可用"，不得报"历史里没有"**。

### 6.4 L0 的硬约束（2026-10-28 用户裁定）

`goal.md` **只是索引，不是笔记本**：

- 平台硬限 16 KiB（超限只返回尾部），**自设上限 4 KiB**。
- 写进去的只有：当前状态、正文指针、待办标题（一行一条）、归档记录。
- **不写**：分析过程、实验数字、代码片段、长篇结论 → 一律 L3。
- 单次 append 前自检：这是「索引」还是「内容」？**超过 1 KB 多半是内容。**

### 6.5 落盘纪律（均为实测踩过的坑）

1. **写盘后必须独立读回复核**，不采信写工具的回显（实测 `file_patch` 回显 `ref refusals` 而落盘为 `refusals`）。
2. **PowerShell 单引号字符串不解释 `\n`** —— 用它拼多行会得到一行字面量。用数组 + `[Environment]::NewLine`。
3. **归档必须逐位**：`ReadAllBytes` / `WriteAllBytes` + 双端 SHA-256 相等，再写 INDEX 记账。
4. **路径必须现场实测**：`global_general`（下划线）写成 `global-general`（连字符）会直接 `NOT_FOUND`。
5. **`goal_update` 返回的 size 不可信**：2026-10-28 实测报 `new_size=17508` 而磁盘 `27846`（偏差约 10 KB）；只信 `MTIME` 与 `Get-Item`。

## 7. 改动的量化纪律（2026-10-28 补）

**任何以「精简 / 优化 / 压缩」为目标的改动，动手前必须记基线数值，改完必须报差值。**

理由不是洁癖，是实测翻车：2026-10-28 我在「优化提示词」这件事上**连续两次把优化做成了增重** ——
`MEMORY.md` 1,805 → 2,023（+218 字符）、`TOOLS.md` 第一版 4,121 → 4,427（+306 字符）。
两次我都用「内容更准了」说服自己，直到量了字符数才发现方向反了；
第三次按「先量再改」执行，才真正从 4,121 降到 3,374（−747，−18%）。

有效手法（按收益排序）：

1. **把会过期的环境状态压成一行**（Codex 段 600 → 200 字符，因为本机已卸载）。
2. **合并重复提醒**（同一条警告原在【文件】和【代码智能】两段各写一遍）。
3. **删重复条目**（`agent_diagnostics` 同时出现在【诊断】与【其他】）。
4. **长段落压成半行，但保留判据关键词**（如「`< NUL` 必需，否则永久阻塞」不可删）。

判据：

- 改动**前**：记 `Get-Item` 的**字节数**与**字符数**（两者都要 —— 中文 UTF-8 是 3 字节/字，
  只看一个数会误判。实测 `agent_state` 报的 `length` 是字符数：SOUL 2,766 字符 / 7,565 字节）。
- 改动**后**：报「原 → 新」与差值。**不能只说「改好了」**。
- 若目标含「精简」而结果是增重，**必须说明为什么这次增重是必要的**（例如修正了失效指引），
  否则按失败记 —— 今天的 `MEMORY.md` 就属于这种情况（+218，但替换掉了两个失效工具名）。

同一纪律适用于文档、代码与配置：**没有基线数字的「优化」不可验收。**
