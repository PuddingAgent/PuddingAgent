## 怎么跑（血泪换来的四条）

1. **先 `dotnet build`，再 `dotnet test --no-build`** —— 否则构建时间会淹没测试时间（实测一次白等 20 分钟）。
2. **挂住不要人工二分**：`--blame-hang --blame-hang-timeout 120s` 会点名挂住的用例，
   再用 `dotnet-dump analyze <dmp> -c "clrstack -all"` 直接拿到调用栈（实测 2 分钟出结论）。
3. **cmd 里的 `&` 是串行**，不要用它「并行」跑多个工程 —— 会排队，而且看不出在排队。
4. 输出重定向到文件再读，终端是 GBK，长输出会乱码。

## WebApi 4 条失败：已修 2 条，剩 2 条（2026-11-01 14:20）

### 诊断由 Codex 提供，我独立复核后落地

`codex exec -m gpt-5.6-sol -s read-only` 给出的结论（原文存 `temp/codex-webapi-fix.md`）：

**已证实：**

1. `compaction.preparation_failed` 是**错误码掩盖了真实原因** —— 真正的异常是
   `SQLite Error 1: cannot start a transaction within a transaction`；
2. 根因：测试工厂把所有 `DbContext` 都接到**同一个 `SqliteConnection` 实例**上
   （`CustomWebApplicationFactory.cs:98-107`），
   于是后台事件写入（`ConversationEventStore.AppendAsync` 的 `BEGIN IMMEDIATE`）与请求内写入
   挤在同一条物理连接 → 嵌套事务；
3. Goal 测试同理：`does not support nested transactions`，栈在 `GoalRunStore.CreateAsync`；
4. `062a838` 的新代码**不在**这些测试的执行路径上（空会话候选为 0，早在
   `ContextCompactionService.cs:855` 就返回，压根到不了 summary generator）。

**我的独立复核（不采信自述）：**

- 在 TRX 里实测：`cannot start a transaction within a transaction` ×2、
  `does not support nested transactions` ×1 —— **命中**；
- 读 `CustomWebApplicationFactory.cs:98-107` —— 确为单一连接共享 —— **命中**。

### 已落地的修法（测试侧，不动产品代码）

内存库改为**共享缓存 + 每 DbContext 独立连接**，保留一个 keep-alive 连接防止库被回收：

```csharp
var platformConnectionString = $"Data Source=file:pudding-webapi-{Guid.NewGuid():N}?mode=memory&cache=shared";
_platformConnection = new SqliteConnection(platformConnectionString);
_platformConnection.Open();
services.AddSingleton(_platformConnection);
services.AddDbContextFactory<PlatformDbContext>(options => options.UseSqlite(platformConnectionString), ...);
```
