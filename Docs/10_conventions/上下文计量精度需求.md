# 上下文计量精度需求（判据）

## 一、目标不是"数字准"，是"决策不翻转"

上下文计量唯一的下游用途是**发送前决定压不压缩**。provider 在发送后才告诉我们真值，
所以发送前只能预测。因此判据不是 `|估算 - 真值| < ε`，而是：

> 在任何一个真实占用下，估算都不应让闸门跨过它本该停在的阈值。

## 二、为什么"差不多"不行

四个边界（运行中 `context_health.gateThresholds` 实测）：`warning 0.6`、`unhealthy 0.75`、
`trigger 0.8`、`blocking 0.92`。分母为有效窗口 `934,976`。

- **高估** → 提前压缩：一次压缩是一次真实 LLM 调用，外加不可逆的上下文信息损失。
- **低估** → 该拦不拦：撞真实窗口，请求在 provider 侧失败。

两者都直接计入「单位成功任务成本 × pass^k」——也就是 RSI 的度量本身。计量误差不是显示问题，
是**度量基准的误差**。

## 三、精度反推（算式，不用猜）

设 `e = 估算 ÷ 真值`。

**高估侧**：真实占用 `r` 被误判为触发，当 `r × e ≥ 0.8`，即 `r ≥ 0.8 / e`。
故误触发带宽 = `0.8 - 0.8/e`：

| e | 误触发起点 | 带宽（比例） | 带宽（tokens @934,976） |
|---|---|---|---|
| 1.385（重启前） | 0.578 | 0.222 | **约 20.8 万** |
| 1.138（校准后，当前） | 0.703 | 0.097 | **约 9.1 万** |
| 1.02（目标上限） | 0.784 | 0.016 | 约 1.5 万 |

**低估侧**：blocking 触发条件是 `r × e ≥ 0.92`。当 `e < 0.92`（低估超过 8%）时，
即使真实占用打满有效窗口也永远到不了 0.92 ⇒ **blocking 结构性失效**，闸门退化为事后失败。

**结论**：可接受区间约为 `e ∈ [0.97, 1.02]`，即 **±2~3%**；红线是不要低估超过 8%。
当前 `e = 1.138`，超出上限约 12 个百分点。

## 四、达成路径：换误差结构，不是调参

要求 ±2% 意味着"估算器再准一点"这条路是死的：分词器与服务端词表的差异是客观存在的，
不可能被消除到 2% 以内。正确做法是让误差乘上一个远小于 1 的系数。

**anchoring**（参照 deepseek-harness）：

```
projected = pressureTokens + heuristic(自上次实测以来的增量)
```

其中 `pressureTokens` 是 provider 上一次报告的真实 prompt 规模（真值，无误差），
只有**增量**使用估算。

于是总误差 `E = p × e_增量`，`p` 为增量占总量比例。取 `p = 0.15`、要求 `E ≤ 2%`，
则所需增量精度仅 `e_增量 ≤ 13.3%` —— **恰是当前估算器的水平**。

更重要的是 `p` 是自适应的：接近 0.8 阈值时上下文必然很大，`p` 必然小。**anchoring
恰好在需要精度的区间才最准**，远离阈值时误差变大也不影响任何决策。

而现在的"从零估算整个请求 + 一个全局校准系数"做不到这一点：误差是结构性的
（中文、英文、工具定义 JSON、消息信封各自比例不同），单一系数只能对齐平均，
无法逐段对齐，因此 1.138 很难再往下压。

## 五、怎么判定达标（可执行）

1. **不翻转检验**：给定真实占用序列，估算应使 `state` 的变化点与真实变化点一致；
   允许误差但不允许在 0.75–0.8 之间、0.8–0.92 之间出现反号翻转。
2. **带宽度量**：直接报告 `0.8 - 0.8/e` 折算的 token 数，作为单一健康指标（目标 ≤ 1.5 万）。
3. **方向分账**：高估与低估分开统计，不能用一个平均误差掩盖（二者后果不同）。

## 六、当前状态

- `e = 1.138`（raw 57,776 ÷ provider 50,777），带宽约 9.1 万 tokens，距上限 12 个点。
- 未决项：「报文在估算后被改写」与「估算/计费口径不同」二者未区分，需同一报文的
  `bodyTokens` 断言，该仪器目前被进程环境块不可变阻塞。
- 结论：**不要在判清根因前再调系数**（全局系数压不到 ±2%，只会掩盖结构性误差）。

## 七、显示与行为必须同源（用户不变量 2026-10-24）

> 不得出现「面板只显示 20%，系统已经开始执行压缩」（用户或 Agent 主动触发除外）。

这条不变量的实质不是「压缩太早」，而是**三条路径各有自己的分子与分母**：

| 路径 | 判据 | 分母 | 折算到面板口径 |
|---|---|---|---|
| 自动压缩触发 | `ContextMaintenanceOptions.CommitRatio = .65` | 模型窗口（`maxTokenBudget`） | **69.5%** |
| 面板「该压缩」状态 | `ContextHealthGateThresholds.TriggerRatio = .80` | 有效输入窗口（`effectiveInputLimit`） | 80% |
| 面板显示的分子 | `measuredPromptTokens`（provider 实测） | 有效输入窗口 | 真值 |

三处代码位置：

- `Source/PuddingCore/Runtime/SubAgentInvocationContracts.cs` — `ContextMaintenanceOptions`，注释明确
  「Ratios are applied to the registered model window」。
- `Source/PuddingRuntime/Services/ContextWindowManager.cs:1147-1150` — `ShouldAutoCompact` 被**覆盖**为
  `health.UsedTokens >= maxTokenBudget * autoTriggerRatio`（默认 .65），与 `ContextHealthEvaluator`
  算出的 0.80 口径无关。
- `Source/PuddingRuntime/Services/AgentExecution/{Buffered,Streaming}.cs` — 传参处用 `CommitRatio`。

于是有两个叠加偏移：**阈值差 15 个百分点**（.65 vs .80）+ **分子差**（估算 `UsedTokens` vs 实测
`measuredPromptTokens`）。任一个都足以让面板数字低于决策数字；两者同时存在时，面板 20% 而决策已到
65% 是可复现的（历史实测估算可达 provider 报数的数倍）。

### 修法方向（未实施）

不能只把 `.65` 改成 `.80`：`BlockingRatio = .70` 也按模型窗口算，直接改会出现「先被阻断、后想压缩」
的顺序倒置。必须整组一起动，或者——更小的改动——**让决策从一个锚定值出发**：

```
decisionTokens = 最近一次 provider 实测 + (当前估算 - 该次实测对应的原始估算)
```

这既是 anchoring 的最小版本，也直接满足本不变量：面板与决策共用一个真值锚，只差一个通常很小的增量。

### 验收方式

构造一组 `UsedTokens` 远大于 `ProviderPromptTokens` 的健康快照，断言 `ShouldAutoCompact` 不得为 true。
该测试**预期取红，尚未实际跑过**（本条为待执行的验收步骤，不是已证实的结论）。
在跑红之前不得改压缩参数——否则改的是行为，不是矛盾。

## 实施结论（2026-10-24 追加）

上面「修法方向（未实施）」一节已由**另一条更小的路径**落地：不改阈值、不做 anchoring，
而是把**分母统一**，并把显示口径收到后端唯一投影。

1. `Source/PuddingCore/Runtime/ContextUsageDisplay.cs` — `ContextUsageDisplayProjection.Project(snapshot)`：
   面板主指标 = `UsedTokens ÷ EffectiveWindowTokens`，与 `ContextHealthEvaluator` 的 `GateRatio` 同一算式。
2. `ContextHealthSnapshot.Display` — 由快照自身字段派生的只读投影，**结构上不可能**与门禁分母漂移。
3. `ContextHealthSnapshot.ExceedsAutoCompactRatio(ratio)` — 判定分母固定为有效输入窗口；
   `ContextWindowManager.cs` 的覆盖改为调用它，`maxTokenBudget * autoTriggerRatio` 已删除。

结果：`CommitRatio = .65` 现在作用于**有效输入窗口**，即面板显示 65% 时触发，与面板完全同源。
阈值本身未改动，因此没有引入「先阻断、后压缩」的顺序倒置（`BlockingRatio = .92` 仍按有效窗口判定）。

验收：`Source/PuddingRuntimeTests/Services/ContextUsageDisplayProjectionTests.cs`。

- `Project_PercentEqualsGateRatio_ForTheSameSnapshot`：断言 `Display.Percent == GateRatio * 100`（逐位相等）。
- `ExceedsAutoCompactRatio_UsesEffectiveWindow_NotModelWindow`：判别点 620,000 / 模型窗口 1,000,000 /
  有效窗口 935,000 / 比率 0.65 —— 模型窗口口径下不达标、有效窗口口径下达标，只有取后者才会通过。
- 变异取红：两个分母各改成 `ContextWindowTokens` → 7 失败 / 4 通过；逐位复原后 11/11 通过。

原「验收方式」一节的预期测试（`UsedTokens` 远大于 `ProviderPromptTokens` ⇒ `ShouldAutoCompact == false`）
**不再需要**：现在 `ShouldAutoCompact` 根本不看 provider 实测，它只看估算与有效窗口。
面板显示的是同一个数，因此「面板 20% 而系统已在压缩」在结构上不可表达。
