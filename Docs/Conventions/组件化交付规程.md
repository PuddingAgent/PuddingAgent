# 组件化交付规程（先独立测试，再接入 PuddingAgent）

> 落定：2026-09-23 ｜ 依据：用户裁定
> 「所有的组件，完成测试之后，再加入到 PuddingAgent，这样可以**在不重启的情况下进行测试和开发**，同时也保护了接入之后的质量，以及架构上不胡乱依赖 —— 因为一个组件是一个独立的组件，具有明显的边界。通过多个组件的组合，加入到 PuddingAgent。**我们的工具体系也逐渐朝着这个目标**。」
>
> 与 `AGENTS.md`「架构第一原则：架构整洁性」配套；组件边界判据见
> `Docs/Features/ADR-089-索引组件拆分设计-2026-09-23.md` §2。

# 第一部分：原则

## 1.1 一句话

**组件先在自己的边界内完成构建与测试，通过门禁后才登记进 PuddingAgent 的解决方案与依赖注入。**

顺序不可颠倒：**先独立可测，再接入宿主**。不是"先接进去再补测试"。

## 1.2 四条收益（对应用户的四点理由）

| # | 收益 | 机制 |
|---|---|---|
| R1 | **不重启宿主即可开发调试** | 组件是独立程序集，`dotnet build` / `dotnet test` 只碰它自己的输出，**不需要停止运行中的 Core** |
| R2 | **保护接入后的质量** | 接入前测试已全绿；接入动作只剩"登记 + 装配"，引入的变量最小 |
| R3 | **架构上不胡乱依赖** | 组件是有明显边界的独立单元，**不得反向引用调用方**；边界由编译期强制 |
| R4 | **PuddingAgent = 组件的组合** | 宿主只做装配与生命周期；能力以组件为单位增量长大 |

## 1.3 实测证据（R1 不是理论）

本机长期存在：运行中的 host 进程（`PuddingAgent.exe`）**锁定** `Source/PuddingAgent/bin/Debug/net10.0/*.dll`
⇒ `PuddingAgent.csproj` 的 **Debug 构建恒 exit 1**（`MSB3027`/`MSB3021`，`error CS` 命中 0），
**基线即如此**。而独立组件（如 `PuddingCodeIndex`）可以随时 `build` + `test`，
完全不与运行中的宿主抢文件锁 —— 这就是"不重启即可开发"的具体兑现。

# 第二部分：什么该是独立组件

## 2.1 判据（满足任一条即应拆）

1. 有**独立的关注点**（例：维护索引产物 vs 语言解析）。
2. 有**独立的测试需求**，且测试时**不需要**宿主或更上层组件在场。
3. 依赖**重且带全局副作用**（例：Roslyn / `Microsoft.Build.Locator` 必须**进程级一次性注册**，
   是并行测试宿主的经典脆弱点）—— 拆出去可让相邻测试进程**完全不加载**它。
4. 会被**多个消费方**使用，或会被单独打包（例：CLI）。

## 2.2 边界硬规则

1. **新组件不得反向引用其调用方。** 判据是**编译期失败**（不是文档约定）。
2. **归属存疑的文件留在引用方一侧**（宁可少拆），并逐条记录回退原因。
3. **不确定就少拆**；反向引用一旦形成就会锁死架构。
4. 抽取时**禁止顺手重构**：纯搬迁才能用"基线数字不变"当判据。

# 第三部分：交付门禁（五步，逐步可验）

| 步 | 动作 | 判据 |
|---|---|---|
| **S1** | 建独立工程（`Source/<Component>/<Component>.csproj`） | 叶工程或只依赖更低层；**本项目内 `ProjectReference` 从 0 开始** |
| **S2** | 建**独立测试工程**（`Source/<Component>Tests/`） | 测试工程**只引用该组件**（+ 通用测试框架）；**不得**引用宿主、其他组件或上层 |
| **S3** | 无宿主验证 | 组件与组件测试**可以在宿主运行中**构建并跑绿；测试进程**不加载**被刻意隔离的重依赖（如 Roslyn/MSBuild） |
| **S4** | 边界断言（机器可验） | 新组件内检索调用方程序集名 ⇒ **0 命中**；csproj 无禁用包；`ProjectReference` 清单符合预期 |
| **S5** | **接入**（此时才做） | ① 登记到 `PuddingAgentNetwork.slnx`；② 在消费方 csproj 加引用；③ 在 DI 组合根装配；④ 跑宿主侧组合测试（如 `PuddingApplicationHostCompositionTests`） |

**S5 之前的任何一步都不得改动宿主。**

## 3.1 接入前的自检清单（逐条勾）

- [ ] 独立工程能单独 `dotnet build`（exit 0）。
- [ ] **独立测试工程**全绿，且它**不引用宿主 / 不引用其他组件**。
- [ ] 跑测试**不需要**启动 Core、Desktop 或任何后台服务。
- [ ] 组件内 `search_grep` 调用方程序集名 = **0 命中**。
- [ ] 组件 csproj：`ProjectReference` 与包引用符合设计（无 Roslyn/MSBuild 等禁用项）。
- [ ] 已写/更新 `Source/<Component>/code_map.md`。
- [ ] 接入后测试：宿主组合测试通过（防 `TryAddSingleton<IFace, Impl>()` 构造参数未注册导致
      `ValidateOnBuild` 在 Build 期失败、Core 起不来 —— 本项目真实发生过的事故）。

## 3.2 什么**不算**遵守本规程（反例）

| 反例 | 为什么不算 |
|---|---|
组件测试仍放在**引用了宿主/其他组件**的测试工程里 | S2/S3 不成立：测它就得把无关的重依赖一起加载，且受宿主状态影响 |
"先接进 slnx 和 DI，再慢慢补测试" | 顺序颠倒，接入后质量无保护 |
为新组件反向开放 `InternalsVisibleTo` 给上层程序集 | 实质是**反向依赖**，边界被击穿 |
组件内为实现便利引用 `PuddingHost` / `PuddingRuntime` | R3 失效，边界不复存在 |
把"能编译"当成"已测试" | 没有能取红的断言，等于没测 |

## 4.2 新门禁：搬迁后必须做「全解决方案构建」（2026-09-23 教训）

**背景（真实事故）**：Slice 1（`eff21d4a`）把 `ICodeIndexScheduler` 等契约用 `git mv` 迁入
`PuddingCodeIndex.Contracts`，并更新了**它自己看到的**引用。但 `Tests/PuddingHost.Tests` 的两个
Storage 测试文件仍只 `using PuddingCodeIntelligence.Contracts;`，于是**该测试工程从此编译不过**
（`CS0246`）。而父代理当时只跑了 `PuddingCodeIntelligenceTests` 与 `PuddingRuntimeTests`（都绿），
外加 `PuddingAgent -c Release`（也绿 —— 因为该测试工程**不在** `PuddingAgent` 的构建图里），
**完全没发现**。断点一直留到 U3-B2a 才被顺带修掉（命名空间归属对照：`ICodeIndexScheduler` 在
`PuddingCodeIntelligence.Contracts` 命中 **0**、在 `PuddingCodeIndex.Contracts` 命中 **2** ⇒ 确凿）。

**新门禁（独立于 S1~S5 的一条）**：任何 `git mv` / 命名空间根变更 / 工程拆分之后，
**必须做一次覆盖全部工程的构建**（`dotnet build PuddingAgentNetwork.slnx`，或逐工程枚举全部 `*.csproj`），
并以「**构建失败工程数 = 0**」作为该步的验收判据。

**理由**：搬迁的影响面不只是"调用了被迁类型的生产代码"，还包括**仅靠 `using` 指令间接引用该契约的
测试工程** —— 而这类工程通常不在主产物的构建图里，因此"主产物构建成功"与"我跑的那几套测试都绿"
**都无法覆盖它**。测试通过只覆盖"我选择跑的"；构建失败属于"我没选择的"。

**S5 首次真实使用**：`PuddingCodeIndex` 的 S1/S2 完成后，U3-B2a 用它走完了 **S5（接入宿主）** ——
`ICodeIndexMaintenance` 注册进组合根，`PuddingHost` 新增**唯一生命周期驱动**
（`CodeIndexMaintenanceHostedService`：Host 只驱动，索引逻辑仍留组件内），并带宿主组合测试
（含"闭合性"与"变异取红"）。⇒ 上表可在 S1/S2 之外再增一列 S5 状态。
