# 2026-10-23 软压缩增加「微小回收」守卫

## 背景：触发只看阈值，不看「能收回多少」

自动软维护压缩的触发条件是「当前用量越过阈值比例」，与本次预案**实际能回收多少 token** 无关。
2026-10-22 的宿主日志统计（`D:\Data` 下当日 core 日志，人工汇总）：

| 指标 | 数值 |
|---|---|
| 自动压缩次数 | 179 次 |
| 压缩 LLM 调用 | 510 次 / 7.3M prompt token / 合计 6,010 s（单次 40.65 s） |
| 回收 ≤5k token 的自动压缩 | 40 / 181 ≈ **22%** |

而同日 `cache_health` 显示压缩调用的前缀缓存命中率仅 **1.2% / 0%**（正常轮次 96.0–99.6%），
即这些「小收益压缩」同时付出两项成本：

1. 压缩摘要请求本身按**全价 cache miss** 计费（deepseek-flash 缓存命中 ¥0.04/M vs 未命中 ¥2/M）；
2. 摘要写入会改写历史尾部 ⇒ **整段 warm prefix 缓存作废**，下一轮主请求回到全价。

净效果：为了回收几 k token，付出数十倍的 token 费用。

## 改动

- 新增 `Source/PuddingRuntime/Services/WarmPrefixSoftReclaimAdmission.cs`（纯函数，无状态）：
  - `ResolveFloor(initialUsedTokens)` = `max(2000, initialUsedTokens * 5%)`；
  - `ShouldSkip(removedTokenEstimate, initialUsedTokens, requiresSynchronousProtection, forcePreparation)`：
    硬保护（`RequiresSynchronousProtection=true`）或强制准备时**永不跳过**；其余情况当
    `removedTokenEstimate < ResolveFloor(...)` 时跳过。
- `Source/PuddingRuntime/Services/AgentExecution/AgentExecutionService.Compaction.cs`：
  `TryCreatePlan` 成功后、真正发起准备/摘要前调用守卫；命中跳过时输出
  `[AgentExec:Compaction] Skip trivial soft reclaim session=… round=… plannedReclaim=… floor=… usedTokens=…`，
  调用 `EndPreparedCompaction` 清掉预置状态，随后返回 `WarmPrefixCompactionOutcome.NotNeeded`。
  **不生成摘要、不写压缩记录、不动 `UsedBudget` 语义。**

## 验证

- 新增 `Source/PuddingRuntimeTests/Services/WarmPrefixSoftReclaimAdmissionTests.cs`（5 用例：下限取大值、边界恰好等于下限、
  低于下限跳过、硬保护跳过禁用、强制准备跳过禁用）。
- 绿：`--filter FullyQualifiedName~WarmPrefixSoftReclaimAdmission` → 失败 0 / 通过 5。
- 变异取红：把守卫核心行改为 `return false;` → 失败 1 / 通过 4（证明用例真的锁住行为）；复原后源码无变异残留。
- 回归：`--filter "FullyQualifiedName~WarmPrefixSoftReclaimAdmission|FullyQualifiedName~WarmPrefix"` → 失败 0 / 通过 88。

## 影响面与风险

- 只影响**自动软维护**分支；硬保护压缩（字节级上传预算超限时的同步保护）与手动压缩路径行为不变。
- 生效条件：源码变更，需重新构建并重启 Core 才是运行态事实（本轮未重启，避免破坏 warm prefix）。
- 覆盖率诚实说明：该接线点本身**没有端到端用例**，只有上面 5 个准入判定的单元用例。

## 后续（未做）
