# 适配器审计（第二批）：交互受影响元素 + 等待语义与 Desktop 对齐

## 目标 / 背景

延续上一轮的逐字段审计，本轮过**结果与错误语义**维度：把每个操作「Desktop 侧返回什么」
与「Bridge 侧返回什么」并排看。又查出两处分叉。

## 查出并修复的两处分叉

### 1. `browser.interact` 丢掉了受影响元素

- 契约 `DesktopInteractionResult(target, page, element)` **有** `Element`；
- Desktop 侧确实填它（先解析句柄 → 动作 → 用句柄映射成引用）；
- 我的适配器返回 `new DesktopInteractionResult(request.Target, state)` ⇒ **element 恒为 null**。

**修复**：动作**之前**解析句柄（产品规则明确禁止"交互提交后重查旧 Locator"，
后续状态只能靠 Wait 或新 Snapshot），动作之后用新增的 `ToElementRef(handle, state.Version)`
映射成引用；版本取**交互之后**的事实（旧 Ref 由此作废），而非句柄里的旧版本。

### 2. `browser.wait_for` 把「诊断信息」升级成了失败

- 契约 `DesktopWaitResult(target, condition, timedOut, page, error)` 有 `error`；
- Desktop 侧语义：**超时用 `TimedOut` 表达**，运行时诊断信息作为附加说明随**成功结果**返回；
- 我的适配器：`result.Error is not null` ⇒ 直接返回**失败**。

**修复**：与 Desktop 侧对齐——始终返回成功，`TimedOut` 表达超时，`error` 透传为诊断说明。
我此前"不透传错误文本以免泄露"的理由在本例**站不住**：该文本来自同一个 WebView2 运行时，
Desktop 路径本来就会把它发到线缆上，且接收方正是发起调用的一方 ⇒ 一致性优先。

## 改动

- `Source/PuddingHost/BrowserBridge/BridgeBrowserCapabilitySurface.cs`：
  交互前解析句柄 + 新增 `ToElementRef`；等待改为成功语义并透传 `error`。
- `Tests/PuddingHost.Tests/BrowserBridge/BridgeBrowserCapabilitySurfaceTests.cs`：
  假页面 `QueryAsync` 可配置；新增"报告受影响元素"用例；
  原"诊断即失败"用例改为"诊断随成功结果返回"（记录这次语义更正）。

## 验证

- `PuddingHost.Tests` **225/225**。
- 未验证：真实通道端到端（需 Desktop 侧启用能力通道 + 外部重启窗口）。
