# 修复外部审查 P1-1：无页面目标的浏览器能力不再继承 Shell 的调用方信任

## 缺陷（审查报告 `030e5b7` 的原文口径）

`DesktopApplicationCoordinator.Capability.cs` 启动组合器时不传 `serviceOptions` ⇒ 缺省服务 `ShellCallerTrust = Untrusted`；
而 `DesktopService` 对 `browser.contexts` / `create` / `close` 传 `target: null` ⇒ 准入拿不到 `pageState.Trust`，
沿用 Shell 信任；策略表对这些能力只允许 `AgentAuthorized` ⇒ **通道握手成功，但 `browser_context` 的
list/create/close 全部 Unauthorized**；工具省略 `contextId` 时"先列上下文"的路径同样失败。
页面注册为 AgentAuthorized 并不能改变**无目标调用**的信任级别。

## 修复（把两份调用方信任分开，并把"哪些能力属于浏览器上下文作用域"变成单一定义）

| 文件 | 改动 |
|---|---|
| `Source/Pudding.DesktopService/DesktopServiceOptions.cs` | 新增 `BrowserContextCallerTrust`（默认 **AgentAuthorized**），与 `ShellCallerTrust` 分开：这些能力只可能来自 Core 的 Agent 浏览器工具层，且**没有页面目标**，拿不到 `pageState.Trust` |
| `Source/Pudding.DesktopService/DesktopCapabilityPolicy.cs` | 新增 `IsBrowserContextScoped(capability)` —— **单一定义**（策略表/准入/测试共用，避免三处各写一份后漂移） |
| `Source/Pudding.DesktopService/DesktopService.cs` | 准入按作用域选取信任来源：浏览器上下文作用域 ⇒ `BrowserContextCallerTrust`；Shell 自身能力 ⇒ `ShellCallerTrust`（**保持 fail closed**）；有页面目标的能力仍由 `pageState.Trust` 覆盖 |
| `Source/Pudding.DesktopService/DesktopCapabilityChannelComposition.cs` | `CreateDefaultServiceOptions` 同时携带两份来源（**产品缺省装配**因此正确） |
| `Source/Pudding.DesktopServiceTests/TestInfrastructure.cs` | 夹具新增可选 `options` 参数：用例可以拿**产品缺省装配**来验证准入，而不是只能靠测试自己放宽过的选项（这是审查明确提出的要求：显式放宽的选项会掩盖产品默认装配下的拒绝） |
| `Source/Pudding.DesktopServiceTests/BrowserContextScopeAdmissionTests.cs`（新） | 4 条（含一个 8 行 Theory）：产品缺省装配下两份信任取值；`IsBrowserContextScoped` 的定义（三个上下文能力为真、Shell 面全为假）；**用产品缺省装配**跑 `BrowserContexts` 不再因信任被拒；显式放宽 Shell 信任只影响 Shell 面、不影响浏览器上下文来源 |

## 验证

- `Pudding.DesktopServiceTests` 构建 **0 错误**；**181/181 通过**（原 170 + 本轮 11：4 条用例含 8 行 Theory）；
- 未放宽任何别的面：Shell 对话框/Picker/剪贴板仍按 `ShellCallerTrust`（默认 Untrusted）拒绝，并有断言钉住。

## 仍未修（审查的三个 P1 里剩下的两个 + 两个 P2）

| 项 | 根因（审查原文 + 我的核对） | 状态 |
|---|---|---|
| **P1-2 人工接管未同步** | `MainWindow.OnTakeover` 只调 `BrowserWorkspaceController.SetUserTakeoverAsync`；新通道执行器有独立的 `DesktopService.Interaction`，`ValidateAutomation` 只读它自己的状态 ⇒ 未调 `NotifyUserTakeover/ClearUserTakeover`；gRPC 表面直接操作 `IBrowserRuntime`，绕过旧 `BrowserBridgeCommandDispatcher` 的接管门禁 | ⬜ 需把两条传输接到**同一份控制权事实源** |
| **P1-3 标签生命周期未同步** | `BrowserRuntimeDesktopSurface.TabsAsync(New/Close)` 直接调运行时 `NewPageAsync/ClosePageAsync`；右侧实例 Tab / 控制器 `_pages` / Agent 目标由 `BrowserWorkspaceController` 自己维护，运行时无页面创建/关闭事件回流 ⇒ 新通道建的页面不进 UI Tab 与目标注册表（后续能力可能 InvalidTarget），关的页面留残影；新建 context 同样无回流 | ⬜ 需统一页面生命周期入口或运行时事实事件 |
| **P2 订阅未释放 + 启停缺共同互斥** | `AttachBrowserTargets` 的匿名 lambda 订阅长期存活的 workspace，不返回 IDisposable、`StopCapabilityChannelAsync` 不解绑；启动用 `_capabilityStartGate`、停止用 `_capabilityGate` ⇒ 停止可能看到未赋值的 `_capabilityChannel` 提前返回，迟到的启动写入已失效会话 | ⬜ |
| **P2 DOM 输入语义** | `WebView2DomClient.InteractScript` 直接赋值 `el.value` + 合成事件；`type` 是整串追加、`press` 只派发 keydown/keyup 并特判 Enter，无 Backspace/Tab/快捷键默认行为；`fill` 对 React 受控输入有风险；无效目标类型可能"赋值失败但返回成功" | ⬜ |

## 立场（与审查一致）

**在三个 P1 修完并有产品默认装配的组合测试之前，不默认开启新通道、不退役旧 Browser Bridge**；
真实模型 smoke 与 Desktop 生命周期验收由外部控制器在明确新构建下执行。
