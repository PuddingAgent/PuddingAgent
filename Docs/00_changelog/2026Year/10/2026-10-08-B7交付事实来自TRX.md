# 2026-10-08 B7 交付事实来自 TRX：测试计数不再靠人工填

## 目标 / 背景

上一轮登记了交付链缺的"事实采集"：生成器接受事实，但没人去产出事实。其中最容易被伪造的一环是
**测试计数** —— 「通过 276 条、失败 0 条」如果靠人手写，就是一条无法复核的声明。本轮把它接到
**测试框架自己写的文件**上。

## 改动

`Pudding.DesktopService/TrxTestResultParser.cs`（新增）：

- 从 TRX 里按 `LocalName` 找 `Counters`（TRX 有命名空间、版本间略有差异），读 `passed`/`failed`；
  套件名由调用方给出（TRX 里没有稳定的套件名）。
- **保守解析**：内容缺失 / XML 非法 / 没有 `Counters` / 缺 `passed`/`failed` 属性 ⇒ **失败**，
  并给出具体原因（不猜 0、不返回"通过了"）。
- `TryParseAll`：多个套件**全有或全无** —— 任一读不出来就整体失败（不拿"读不全的检查"去交付）；
  一个都没给也算失败（空检查列表不是交付）。
- `0/0` 如实返回（那是"跑了但没有用例"），是否合格交给清单校验判断 —— 解析器不替它下结论。

## 验证

| 套件 | 结果 |
|---|---|
| `Pudding.DesktopServiceTests` | **265 / 265**（原 260 ＋ 5） |
| `Automation` · `Contracts` · `AgentTools` · `DesktopSurface.Browser` · `PuddingDesktop` · `Host` | 276/276 · 153/153 · 64/64 · 66/66 · 320/320 · 258/258 |

新增门禁：从样例 TRX 读出 2 passed / 1 failed；null / 非法 XML / 无 `Counters` / 缺计数字段 / 空套件名
各自被拒且原因具体；`0/0` 如实报告；`TryParseAll` 的全有或全无（含"一个都没给"）；
**端到端小步**：TRX → checks → `DeliveryManifestBuilder` 产出清单（累计 534 条通过），
且换成"257 通过 / 1 失败"时**清单生成器拒绝产出**。

**取红实测**：把"缺计数字段"改成静默返回 `0/0` 成功 ⇒
`MissingOrMalformedResultsAreRefusedInsteadOfGuessed` **恰好变红**；复原后 265/265 复绿。

## 已知边界（诚实登记）

- **还没有"采集入口"**：没有一条命令去**跑**测试（生成 TRX）、列发布产物、读日志并调用生成器 ——
  那需要一个脚本或可执行入口。本轮的解析器是它的零件之一（另一件是上一轮的日志提取器）。
- **不解析 TRX 的逐用例细节**：只取汇总计数（交付清单需要的是"跑了多少、失败多少"，
  逐用例明细属于测试报告）。
- **TRX 结构随测试框架版本变化**：按 `LocalName` 容错，但若框架大改结构，解析会**失败**（而不是给出错数字）——
  这正是想要的行为。
- 真机无关（纯解析）。

## 影响与回滚

- **无对外行为变化**：新增组件尚无生产调用方。
- 回滚：删除 `TrxTestResultParser.cs` 与其测试。
