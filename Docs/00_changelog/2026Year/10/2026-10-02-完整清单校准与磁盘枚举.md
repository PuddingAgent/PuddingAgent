# 2026-10-02 完整清单校准与磁盘枚举（D 第二阶段校准）

## 改动

按修订版 D 节建议顺序，把「完整清单校准」落地成可独立验证的组件能力：

- 新增 `Source/PuddingCodeIndex/Contracts/CodeSourceScanningContracts.cs`：
  - `CodeSourceDiskEntry`（**只含元数据**，stat 读不到就是 null）+ 稳定原因串 `CodeSourceScanReasons`；
  - `ICodeSourceIgnoreRules`：路径忽略规则的**注入端口**。组件不反向引用 `PuddingPathFiltering`——
    `PuddingCodeIndex` 必须保持 `ProjectReference = 0` 的叶子，忽略真源由宿主适配后注入，组件内不另建白名单；
  - `ICodeSourceScanner` + `CodeSourceScanOutcome`（`Entries` / `RootUsable` / `Complete` / 原因）；
  - `CodeSourceScanRun`（变更集 + **捕获版本** + 扫描开始时刻 + 能力缺失标记）与 `CodeSourceScanOptions`。
- 新增 `Source/PuddingCodeIndex/Services/CodeIndex/FileSystemCodeSourceScanner.cs`（默认实现，只读元数据）：
  根先探测（缺失/不可读 ⇒ `RootUsable=false`）；**目录被忽略即整棵子树不枚举**；子树读不到只把 `Complete`
  置 false 并给原因（不会假装「那里没有文件」）；条目上限触顶同样只报不完整（避免把未枚举路径当删除）；
  忽略规则抛错时按「不忽略」处理（多一个候选只是核验一次，误忽略才是真漏文件）；枚举顺序按组件路径身份确定。
- 新增 `Source/PuddingCodeIndex/Services/CodeIndex/CodeSourceScanService.cs`（校准）：
  读取持久状态（`ICodeSourceMaintenanceStore`，缺失时降级为 `CapabilityMissing` 且只产出磁盘事实）→
  枚举磁盘 → 用上一阶段的判定器产出真实变更集 → 在账本里登记**捕获版本**并持久化。
  明确不做三件事：**不读正文/不算 hash**（需要核验的候选返回 `RequiresContentHash=true` 交给执行层）、
  **不写索引**（删除/替换由执行层经存储接缝完成）、**不推进扫描水位**（水位只在执行层回报提交时前进）。
  没有任何需要动作的路径时不递增版本、不写库。
- `CodeSourceMaintenanceLedger` 两处补强：新增 `FromState`（从持久快照恢复账本，保留 `DirtyAgain`），
  `RecordObservedChanges` 递增期望版本时同时标记「还有工作」（进程中途退出不会被当成已完成）。
- 新增测试：`FileSystemCodeSourceScannerTests`（8 条）与 `CodeSourceScanServiceTests`（9 条）。

## 验证

- `dotnet test Source\PuddingCodeIndexTests\PuddingCodeIndexTests.csproj` → **236 通过 0 失败**
  （本次 +17：扫描器 8 + 校准 9）。
- 关键用例：完整扫描对「新增 / 改动 / 消失」分别给出 `ReindexContent`（两条）与 `Delete`（一条）；
  扫描只登记期望版本、**水位保持原位**；无变化时既不递增版本也不写库；根不可用与扫描不完整
  **都不产出删除**（只把路径计为未解决/Deferred）；被忽略规则排除的旧索引路径在完整扫描下成为删除候选
  （对应 D3「排除规则变更 ⇒ 按新旧覆盖集合差异移除记录」）；存储没有该能力时仍能产出磁盘事实并标记；
  深度核验与 watcher 提示原样透传到判定器；扫描开始时刻可注入供执行层回报提交。
- `PuddingCodeIndexTests` 的组件边界断言（`ComponentBoundaryTests`）保持通过：新实现只引用本组件契约
  与 BCL，`ProjectReference` 仍为空。

## 未完成与影响

- **仍未接入维护链路**：`CodeSourceScanService` 与磁盘扫描器目前没有调用方（`CodeIndexMaintenanceService`
  仍走旧的 watcher→逐文件/升级路径），`CodeIndexCalibrationService` 也仍是原来的「已索引路径 mark-and-sweep」。
  因此对运行中实例仍是零行为变化，不构成任何性能结论。
- **仍未做原子替换**：`ReplaceFilesAsync`（索引结果 + 已应用指纹同事务）未实施；在它落地之前，
  「扫描出删除」与「删除生效」之间没有事务保证，本服务也刻意不执行删除。
- **未接宿主忽略规则**：把 `PuddingPathFiltering` 适配成 `ICodeSourceIgnoreRules` 属于接入阶段（由宿主完成）。
- 后续阶段：原子替换 → 语言批量/依赖影响计划 → 既有维护链路接入。
