# 2026-10-08 I2 第一步：授权签发的生产路径

## 为什么这是 I2 的起点

方案 §4.1 要求"Core 提出受范围约束的 grant 申请；Desktop 检查本地用户目标事实、实例/连接世代和任务 binding，
调用**唯一 authority** 的 `IssueGrant`"。而在此之前 **`IssueGrant` 没有任何生产调用方** ⇒ 授权只能靠人记得。

## 交付

`Source/Pudding.DesktopService/BrowserGrantIssuer.cs`：

| 拒绝面 | 原因 |
|---|---|
| 行动者不可信 | 复用 `BrowserCallerRequirement`（缺身份 / 冒充 User / 无运行身份） |
| 有效期 ≤0 | "grant validity must be positive" |
| 有效期 > Desktop 上限 | 显式拒绝（**不**静默截断成上限）——调用方不能把授权拉长 |
| 范围为空 | 不签发"没有能力的授权" |
| 子代理范围非父授权子集 / 未给父范围 | 子代理不得扩大父授权 |
| 目标未登记 | 禁止对隐式目标（"当前激活 Tab"）或未选页面签发 |
| 连接世代不活 | 先签了也无法在后续校验中被承认 |

成功路径把 `BrowserPageGrantBinding`（Desktop 实例 + 进程实例 + **连接世代**）与 `Source`（用户目标绑定标识）一起记录。

## 验证

| 项 | 结果 |
|---|---|
| `Pudding.DesktopServiceTests` | **346 / 346**（＋7 条签发用例） |
| 纵深防御（实测发现） | authority **自身**要求活世代（否则抛 `no live connection generation…`）；子代理签发还会核对**真实父授权**（`not a subset of its parent task's grant (no_grant)`）⇒ 我的参数检查之外还有一道 |
| 全量链 | **本轮未再跑**（改动仅 DesktopService 与其测试；提交门禁跑的正是该套件） |

## 诚实边界（诚实登记）

- **只做了"签发"**：`Admit`/`Revalidate`/租约回收的**接线**（§4.2 的共用准入适配器与执行前复检）仍未做。
- **用户目标绑定是入参**：本轮 `Source` 只作为记录字段；**从可信 Core 元数据解析绑定**、以及在 UI 上显示归属（§4.1 前半）尚未实现。
- **`BrowserPageLifecycle.Authority` 是 public**：签发路径直接用它（同一实例 ✓），但方案提醒过"直接暴露 Authority 会迫使消费方引用 Automation 组件"——后续可加窄端口收敛。
- **全量链未跑**（如上）。
- **未真机验证**。
