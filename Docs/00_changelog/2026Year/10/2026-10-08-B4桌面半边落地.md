# 2026-10-08 B4 桌面半边落地（并更正一处我说错的话）

## 更正：决定①其实**文档已经答了**

我此前多轮把 B4 说成"卡在 artifact 字节归属，等你拍板 A/B/C"。重读权威文档
[设计方案 §8.1](../../../12_features/浏览器自动化可靠性与渐进阅读设计方案-2026-10-08.md) 后：

> Desktop 返回有界媒体载荷/分块和元数据，Core 校验 MIME、像素/字节上限、截屏身份后写入既有 Vision Artifact；
> 模型结果只收 artifact 引用和类型化图片部分，不收 base64 长字符串。**跨进程不得以 Desktop 临时文件路径假定 Core 可读。**
> 初始截图输入上限拟为 **8 MiB/张**，超限明确返回限制原因。默认 **detail=low（最长边不超过 512px）**……

⇒ 分工是**文档规定**的（Desktop 半边负责有界载荷+元数据；Core 半边负责校验与落库），不是三选一。
**我的"卡住"叙述有误**：真正超出我当前边界的是 **Core/Host 侧的落库与模型输出接线**（属 S5 接入，需 Host/Runtime 所有者同意），
而不是"要先挑 A/B/C"。这也解释了上一轮我为什么会被 S-09 的 512px 绊住：那是**文档要求**，不是空头承诺
（但当时仓库里确实**没有**实现它的代码 —— 这一点判断没错）。

## 本轮交付：B4 的桌面半边

新增 `Source/PuddingBrowser.Automation/BrowserScreenshotTransfer.cs`：

| 约束（来自 §8.1） | 落地方式 |
|---|---|
| 单张 **8 MiB** 上限、超限明确说明原因 | `MaxImageBytes` + `OverLimit` + 可操作原因（截视口/降画质/裁剪区域） |
| 默认 `detail=low`，最长边 **≤512px** | `LowDetailLongestEdge` + `DetailViolation`（承诺没做到就是**假**：会让调用方按错尺寸算坐标） |
| 只认位图 MIME | 白名单 `image/png`/`image/jpeg`，其余明确拒绝 |
| 截屏**身份** | 必须带 `ObservationId`（§8.2 坐标要用它），缺失即拒 |
| 报告源/输出尺寸、设备缩放、CSS viewport、scroll offset、裁剪变换、三代修订号 | `BrowserScreenshotMetadata`；**未上报用可空表达并拒绝**，绝不补 0 |
| 跨进程传载荷、不得假定共享路径 | `Split` / `TryAssemble`：**无缺口/无重复/尾片标 last/总量相符**，否则明确失败 |

**明确不做**（诚实登记）：不落库、不调模型、不写 Core 侧 artifact、不假定任意路径可读。

## 顺带修回 S-09（上一轮我删掉的数字，本轮以**真源**形态写回）

S-09 期望现为：`detail=low 最长边 ≤{LowDetailLongestEdge}px、单张 ≤{MaxImageBytes/(1024*1024)} MiB，超限明确说明原因`
—— **插值自代码常量**，并新增"元数据含源/输出尺寸…三代修订号"。数字溯源门禁同步加两条：
`detail=low → LowDetailLongestEdge = 512`、`MiB → MaxImageBytes = 8 * 1024 * 1024`。

## 诚实边界（诚实登记）

- **这不是 B4 完成**：仅桌面半边的**契约与校验**；CapturePreviewAsync 采集、Core 侧落库、模型图片路由、Canvas/图表理解**都还没做**。
- **`low` 的缩放本身上限尚未在采集侧强制执行**：本类只校验"声称的输出尺寸"是否守约（采集侧接线属 S5）。
- **分块载荷的字节内容未加密/未压缩**：`Split` 只做切片与校验（通道层职责）。
- **`MaxImageBytes` 是"拟"值**：文档用"拟为 8 MiB"，若产品要改，改常量即可（门禁会提醒改文档）。
- **未真机验证**；决定②（可信调用身份）仍待你确认。
