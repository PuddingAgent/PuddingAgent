# 2026-10-08 修 flake 根因（一）：配置加载用例

## 根因（测试问题，不是生产问题）

```csharp
Assert.True(thread.Join(TimeSpan.FromSeconds(5)), "…deadlocked.");   // ← 判据是墙钟
```

- 生产 `PuddingFileConfigLoader` **处处** `ConfigureAwait(false)`（5 处，已核对）；
- 但"没死锁"的证据是一个 **5 秒墙钟**：套件并行、机器繁忙时就会假失败 ⇒ 登记在册的时序 flake。

## 修法（符合方案 §6.2：不用 sleep、不扩 timeout）

| 项 | 内容 |
|---|---|
| **确定性判据** | 加载完成后断言 `NonPumpingSynchronizationContext.PostCount == 0` —— 捕获了桌面上下文才会投递；投递到不泵消息的线程上就永久排队，**那就是死锁本身** |
| **watchdog** | 线程等待降级为 **60s 探针**，只用于在真挂住时给出可诊断失败（方案允许"明确的探针 watchdog"，但不得作为验收判据） |
| **去抖动** | 临时目录删除改为可重试（句柄未释放不再把清理失败算进用例结论） |

## 验证

| 项 | 结果 |
|---|---|
| **取红** | 生产 5 处 `ConfigureAwait(false)` → `true` ⇒ 用例**失败**（watchdog 约 60s 触发）⇒ 判据真的看得见死锁 |
| **稳定门禁（单项）** | 修复后连跑 **20 / 20 通过**（单次约 26s，含 `dotnet test` 启动） |
| `Pudding.DesktopServiceTests`（注册表守卫） | **339 / 339** |
| 注册表 | 该用例**已移出条目**（改为 `FIXED` 注释：写明修复方式、取红证据、20/20 与"不要再无证据加回"） |
| 守卫更新 | 断言"仍在册的两条在册 **且** 已修的这条**不是条目**、注册表含 `FIXED` 记录" |

## 诚实边界（诚实登记）

- **只修了三条中的第一条**：握手 flake 与 WebView2 隐藏表面 flake **仍未修**（方案要求各自独立切片 + 同样的 20 次门禁）。
- **"串行整链 20 次"门禁未跑**：单次全链约 10 分钟，20 次超出本轮预算（登记为待办；单项 20 次已完成）。
- **watchdog 仍是时间**：它只决定"多久算挂住"，**不**决定成败判据；若将来到处都是慢机器，它可能仍需调整（已注明是探针）。
- **未真机验证**。
