# 2026-10-18 浏览器工具验证阻滞：Bridge 协议修订不匹配

## 结论

按用户要求验证 `browser_context` / `browser_tabs` / 页面级工具，三条业务预期（打开 jd.com 看购物车、读取正文并以图片方式理解、搜索比价加购）**全部停在入口**，均未开始。

阻滞点单一且可复现：**Core 与 Desktop 不是同一配套构建**，Bridge 协议修订不等，Hello 在反序列化阶段即被拒绝。

按 [部署手册](../../../13_runbooks/浏览器Bridge配套构建与部署-2026-10-18.md) §3 的 R4 门禁（两侧 `PuddingBrowser.Protocol.dll` SHA-256 必须相同、修订均为 3），当前环境**不满足**。

## 现场证据（2026-10-18 14:53–15:56）

### 1. 工具回执

| 调用 | 结果 |
|---|---|
| `browser_context(list)` | `exit=1`，`browser_not_connected`「No Desktop is connected for browser capabilities」 |
| `browser_tabs(list)` | 同上，逐字相同 |

14:53 与 15:56 两次取样一致；两进程仍在运行（PuddingAgent 14:52:47、PuddingDesktop 14:52:41），期间未重启。

### 2. 两侧共享程序集不一致

| 侧 | 目录 | 大小 | mtime | SHA-256 前缀 |
|---|---|---|---|---|
| Core | `Source/PuddingAgent/bin/Debug/net10.0/` | 274 944 B | 10-18 **07:54:08** | `E16E04CD3C05DB9F` |
| Desktop | `temp/build/winui3/…/win-x64/` | 292 352 B | 10-18 **14:51:43** | `5AC9E1724CCB911C` |

Core 目录内 `PuddingAgent.dll` / `PuddingHost.dll` / `PuddingPlatform.dll` / `PuddingRuntime.dll` / `PuddingBrowser.AgentTools.dll` 等**全部** mtime 为 07:54，**没有任何 14:52 的新产物**。即 14:52 那次启动复用了 07:54 的整套二进制。

### 3. 握手日志形态

```
14:53:14.518  Browser Bridge connection attached: "…" gen=1
14:53:14.555  Browser Bridge Hello failed: "…" gen=1        ← 37 ms
14:53:14.569  Browser Bridge connection closed: "…" gen=1
```

`gen` 递增至 7，每次均为「attached → failed → closed」三行，**间隔 0–37 ms**，不是 5 秒 Hello 超时。
日志中**不存在** `Browser Bridge Hello: desktop=… protocol=… build=…` 这一行——该行由 `AwaitHelloAsync` 在校验之前打印，缺失说明失败发生在其之前。

## 根因链

1. `766f9b3`（10-18 **13:54**）把 `BrowserBridgeProtocol.CurrentVersion` 由 **2 改为 3**，注释明确「两端必须严格相等；不提供旧新载荷兼容」。
2. `e821e6d`（14:11）在 Hello/Ack 增加构建身份字段。
3. Desktop 于 **14:51:43** 重新构建，携带修订 3。
4. Core 加载的是 **07:54** 的 `PuddingBrowser.Protocol.dll`，其修订常量为 2。
5. Desktop 发出 `ProtocolVersion=3` 的 Hello → `BrowserBridgeSerializer.Deserialize` 比较本地常量 2 → 抛 `BrowserBridgeProtocolException(BrowserProtocolMismatch, "Unsupported protocol version: 3")`。
6. `DesktopBrowserBridgeWebSocketEndpoint.AwaitHelloAsync` 的 `catch (BrowserBridgeProtocolException) { return false; }` 丢弃原因，仅上层打印 `Hello failed` → 关闭 → Desktop 按退避重连，形成无限循环。

## 未执行的重建前置条件

修复需要两端同源重建并同时重启（`bootstrap_reboot` 的 desktop-build 路径）。本轮**未执行**，原因：

- 用户明确「本次为验证使用过程，不需要 fix 错误」；
- 重启会关闭正在运行的 PuddingDesktop 工作区并终止当前 Turn。

执行前请先确认维护窗口。当前无在飞子代理（`query_sub_agents(running)` 返回空），但 Desktop 为用户交互界面，仍属破坏性操作。

## 一条命令复核

```powershell
$a='Source/PuddingAgent/bin/Debug/net10.0/PuddingBrowser.Protocol.dll'
$b='temp/build/winui3/bin/PuddingDesktop/Debug/net10.0-windows10.0.19041.0/win-x64/PuddingBrowser.Protocol.dll'
Get-FileHash $a,$b -Algorithm SHA256 | Select-Object Path,Hash
```

两侧哈希相同 ⇒ R4 门禁通过；不同 ⇒ 本阻滞点仍在。日志侧对照：`Browser Bridge Hello: desktop=` 出现表示已越过解析校验，缺失则表示仍在解析阶段被拒。

## 附带的可观测性缺口

版本不匹配这条**唯一能指明病因**的信息（错误码 + 期望/实际修订）被 catch 吞掉，运维只看到 `Hello failed`。建议在该 catch 内至少记录 `ex.ErrorCode` 与 `ex.Message`；本轮未改动源码。

## 边界

- 未验证 `browser_context(create)` 在此状态下的具体回执；
- 未读 Desktop 启动器的部署脚本，「14:52 只重启未重编」由目录 mtime 推断，未取得脚本级证据；
- Desktop 侧自有日志不在 `D:\Data\logs`，未取得对端断开原因；
- 三条业务预期所需的分层验收（transport / protocol / discovery / handover / tools / business）本轮只推进到第 1–2 层。

## 量化补证（16:57 取样，按日志 tag 过滤）

当前会话 `pudding-20261018_021.log` 内 Browser Bridge 事件计数：

| 事件 | 条数 |
|---|---|
| `connection attached` | 745 |
| `Hello failed` | 746 |
| 握手成功（`Browser Bridge Hello: `） | **0** |

即自 14:52 启动以来每一次连接都在握手阶段失败，无一次成功（两数相差 1 条可由日志切换边界解释）。

### 口径变化告知（不得直接与历史日志比计数）

`Browser Bridge Hello: desktop=…` 这行 INFO 由 `e821e6d`（10-18 **14:11**）才引入；`Hello failed` 由 `5a5cf13` 引入。
⇒ 历史日志里该行计数为 0 属**预期**，不能据此断言「历史上从未握手成功」。跨版本比较日志计数前，必须先确认该日志语句的引入时点（`git log -S '<日志原文>' -- <文件>`）。

### 一个会让结论反转的 grep 陷阱

`HostShellTool` 会把**整条命令行**写进同一份 system 日志。用 `Select-String -Pattern 'Browser Bridge Hello: '` 这类**含待查文本的模式**检索日志时，**自己的命令会被自己命中**：本轮实测 1 条「命中」全部来自自己的命令行，若不按 `tag:HostShellTool` 排除，会得出「曾有握手成功」的错误结论。

## 解除阻滞前的第二个门禁风险：字节级可复现性不成立

部署手册 §3 要求「两侧 `PuddingBrowser.Protocol.dll` SHA-256 相同」。受控实验（17:5x）显示该判据在“分别构建”时**不可能满足**。

**实验**：同一工作树、同一命令，仅 `--artifacts-path` 不同（`temp/build/repro-a` / `repro-b`），各构建一次。

| 构建 | 退出码 | 大小 | SHA-256 |
|---|---|---|---|
| repro-a | 0 | 292 352 B | `A17563F9…38FCF7149C4` |
| repro-b | 0 | 292 352 B | `23B1C4CB…D5656C973B` |

结果：**IDENTICAL = False**。与之对照，`temp/build/browser-companion` 内 4 份拷贝同属一个 artifacts-path，SHA 完全一致（`198CFAEB…`）；而 14:51 另行构建的 Desktop 副本为 `5AC9E172…`。

### 含义

1. 同一源码、不同输出目录 ⇒ **字节不同**；同一 artifacts-path 内的各拷贝 ⇒ 字节相同。
2. 因此 §3 只有在“两侧取**同一次**构建产物”时才可通过；若 Desktop 因自定义 `OutputPath` 另行编译（手册 §2 已提示该风险），门禁**必然失败**。
3. 失败形态与真正的协议偏斜**完全相同**（哈希不等），极易被误读为“还没同步”。**哈希不等不得单独作为协议版本不一致的证据**；版本一致性应以握手日志 `protocol=3` 与 Hello 是否被接受为准。

### 本阻滞点的证据边界（自限）

前文判定版本偏斜的依据是：Core 侧程序集**大小不同**（274 944 vs 292 352）、mtime 早于 `766f9b3` 的版本提升 6 小时、以及握手日志缺失 `Hello: desktop=` 行；**不**以哈希不等单独定论。

### 建议（未实施）

§3 二选一：(a) 两侧都从单一 artifacts-path 拷贝同一份 `PuddingBrowser.Protocol.dll`；(b) 引入确定性构建参数（`Deterministic` / `ContinuousIntegrationBuild` / `PathMap`）后再比较 SHA。
