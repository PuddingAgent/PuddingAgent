# 2026-10-02 源指纹与真实变更判定（D 第一阶段）

## 改动

按用户 2026-10-02 修订后的 D 节（撤销「扩展名分类 → Ignore / Incremental / 全仓 Reconcile」补丁）实施
**建议施工顺序的第一步：源 manifest / 变更判定纯逻辑**。

- 新增 `Source/PuddingCodeIndex/Contracts/CodeSourceManifestContracts.cs`：
  - `SourceFingerprint(LastWriteTimeUtc, Length, ContentHash)`：**hash 必须来自实际参与提取/解析的那份内容**；
    提供 `HasSameStat` / `HasSameContent` 两个不同口径的比较。
  - `AppliedFileVersion(ProviderId, ParserPolicyFingerprint, SemanticInputFingerprint, AppliedVersion)`：
    全文与各语言 provider **分别**推进自己的水位，一个成功标记不能替代所有消费者。
  - `CodeSourceEntry` / `CodeSourceObservation` / `CodeConsumerInputFingerprint`：
    持久 manifest 行、磁盘 stat 观察（**读不到就是 null，不得用扫描时刻顶替**）、消费者当前输入指纹。
  - `CodeSourceAction`（`Reuse` / `RefreshFingerprintOnly` / `RebindConsumers` / `ReindexContent` / `Delete` /
    `Deferred`）、`[Flags] CodeSourceChangeSource`（Watcher / MTimeScan / IntegrityCheck / Configuration）、
    稳定原因串 `CodeSourceChangeReasons`、`CodeSourceChange` / `CodeSourceScanRequest` / `CodeSourceChangeSet`。
- 新增 `Source/PuddingCodeIndex/Services/CodeIndex/CodeSourceChangeDetector.cs`：**纯逻辑**（不读文件、不访问
  数据库、不看时钟；全部事实由调用方提供，因此可用最小夹具精确锁定每条不变量）。落地的 D2 不变量：
  1. watcher 只是提示：同路径重复提示与重复观察合并，处理时以磁盘事实为准。
  2. manifest 里没有的路径**即使 mtime 很旧也必须处理**；已知路径比较 mtime+length；mtime 落在
     `ScanStartedUtc - RacyOverlap`（默认 2s）之内也是候选，不能只按「大于上次索引时间」跳过。
  3. stat 未变 + 无提示 + 消费者输入未变 + 不在窗口/深度核验 ⇒ **直接复用**（不读正文）。
  4. mtime 不是绝对证明：提示、深度核验、stat 读不到都必须核验内容；`RequiresContentHash=true` 时调用方
     不得跳过 hash 推进水位。
  5. **稳定读取校验**：提供的 hash 若与本次观察的 stat 不一致（读取与写入竞争）⇒ `Deferred` +
     `unstable_read`，绝不提交。
  6. 内容一致但解析器策略/语义输入变了 ⇒ `RebindConsumers`（重新绑定，不重新提取正文）。
  7. **删除必须由完整且根可用的扫描得出**；不完整扫描、根不可用、watcher-only 批次（没有枚举磁盘）、
     扫描期间又变化的路径一律 `Deferred` 并计入 `UnresolvedMissingCount`，**绝不删除**。
  8. **水位不掩盖失败**：只有「完整 + 根可用 + 确实扫描过」的轮次才把水位推进到 `ScanStartedUtc`；
     watcher-only 批次与不完整轮次保持旧水位（宁可重放，不可漏掉）。
- 新增 `Source/PuddingCodeIndexTests/Services/CodeIndex/CodeSourceChangeDetectorTests.cs`（25 条）：新文件旧 mtime、
  同 stat 复用不 hash、stat/length 变化、stat 读不到、watcher 提示有/无 hash、racy 窗口内外对照、深度核验、
  策略/语义输入变化只重绑、消费者从未提交、内容变化重索引、不稳定读取被拒、完整扫描确认删除、
  不完整扫描/根不可用/watcher-only 不删除、扫描期间变化一律 Deferred、水位推进规则、重复观察合并、
  不完整 manifest 行重核验、路径大小写身份。

**本次不含**被撤销的分类补丁（`ICodeIndexChangeClassifier` 及其测试、`CompositeCodeIndexer` 与
`CodeIndexMaintenanceService` 的分类改动已在实施前回退，未进入任何提交）。

  → 25/25 通过。

  `PuddingCodeIndex` 不反向依赖 `PuddingCodeIntelligence`（`ComponentBoundaryTests` 在运行期三重断言）。

## 未完成与影响

D 的后续阶段尚未实施（按报告建议顺序）：

1. **完整清单校准与持久待办**：把 `CodeIndexCalibrationService` 扩展为「磁盘清单 vs manifest 差异扫描」，
   并由持久账本保存 epoch / desiredVersion / 待重试路径 / 成功扫描水位（本阶段只定义合同，没有持久化表）。
2. **store 原子替换**：`ReplaceFilesAsync` 事务接缝（文件记录 + 符号 + 引用/关系 + 该消费者已应用指纹），
   失败保留旧完整产物并标 stale。
3. **语言批量/依赖影响计划**：语言侧按项目/配置版本复用有界 workspace；`NotApplicable` 作为能力路由结果；
   签名变化使依赖方失效。
4. **既有维护链路接入**：watcher/防抖/调用方把本阶段的判定器接上去，替换「无 owner 即全仓」路径。

本阶段只发布纯逻辑与合同，**未接入任何宿主、未改数据库 schema、未部署**；因此对运行中实例零行为变化，
也不构成对「高读取已消除」的性能结论。
