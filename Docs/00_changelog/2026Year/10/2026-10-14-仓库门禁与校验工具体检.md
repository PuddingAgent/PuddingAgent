# 2026-10-14 仓库门禁与校验工具体检（探针 + 对照法）

## 目标 / 背景

本日做 code_map 全仓治理时，**多次被"静默漏检/假绿"坑到**：一个校验器"绿"并不等于被检查的对象真的没问题。
于是把仓库自带校验工具逐个体检一遍，把结论沉淀成基线，避免后来者重复探查或误信。

方法固定为三步，缺一不可：

1. **做坏一个探针**（故意写一个必然违规的输入，且放进**不会被剪枝**的目录）；
2. **对照**（同一检索/校验方式在**已知有问题**的对象上必须报红）；
3. **清理**（探针用完即删，并复核工作树无残留）。

> 反面教材（本日实测）：把探针放在 `temp/` 下 —— 该目录在多数扫描器里**被剪枝**，
> 于是"扫描 0 个文件"被误读成"没有违规"。**探针位置本身就是变量。**

## 本日修掉的两类工具缺陷（都要"取红"才认）

1. **`front_matter.py` 的静默漏检**（`aa675fc`）
   - 重复给出 `--paths A --paths B` 时**只保留最后一个**（`nargs='*'` 的 store 语义）⇒ 前一个文件的违规**完全不报**；
   - 显式给的路径匹配不到任何文件时，仍输出「不合规 0 个」且 `exit 0` ⇒ **假绿**。
   - 修法：路径参数改 `action='extend'`（累加）+ 新增 fail-closed（显式 paths 匹配 0 个 `.md` ⇒ 非零退出）。
2. **两个守恒门禁的输出编码缺陷**（`521c996`）
   - 会打印**文档内容片段**，若调用方 stdout 是 GBK/cp936 ⇒ `print` 抛 `UnicodeEncodeError`，
     **在打印 VERDICT 行之前崩溃**（退出码仍 1），消费者会误判成"工具坏了"而不是"校验失败"。
   - 修法：启动时 `reconfigure(errors="replace")`（只改 `errors`、不动 `encoding`）。
   - 诚实记录：该缺陷**依赖执行环境**，默认 utf-8 环境下**首次复现失败**，靠"强制 GBK"的对照实验才复现；
     修复后用**同一变异件**做端到端闭环验证（两个门禁都能完整打印 VERDICT）。
