# 2026-10-18 阶段E1回填断点持久化与恢复保护

## 改动

- `IChatMessageBackfillSource` 新增 `GetMaxIdAsync`（冻结本次回填高水位 H）与 `GetDatasetIdentityAsync`（platform 库路径身份）；`BackfillChatMessageSource` 实现两者。
- `SessionChunkBackfillOptions` 新增：
  - `CheckpointFilePath`（默认 `<DataRoot>/runtime/backfill/session-chunk-checkpoint.json`）；
  - `IndexConfigVersion`（分块/embedding 配置版本，变化即失效重建）；
  - `StartupDelayMs`（Ready 保护窗口，默认 60s）。
- `SessionChunkBackfillService` 重写主流程：
  - 启动等待保护窗口 → 冻结 `H = MAX(ChatMessages.Id)` → 读取并校验 checkpoint；
  - checkpoint 绑定 `datasetIdentity + IndexConfigVersion`；**恢复旧库**（checkpoint 水位 > 当前 maxId）、换库、索引配置版本变化时旧断点失效，从 0 重建；
  - 只扫描 `(lastId,H]`，每批成功后才推进 `lastId` 并**原子写 checkpoint**（tmp + File.Move）；
  - checkpoint 损坏/写失败只降级为全扫或继续索引，不阻断回填；取消时未完成批会被重扫（索引器幂等）；
  - 生产默认仍 `Enabled=false`，不改现有宿主行为。
- 测试新增：
  - 重启恢复只扫描 H 以内新增消息（不重扫已完成区间）；
  - IndexConfigVersion 变化从 0 重建；
  - 模拟恢复旧库（checkpoint 水位高于当前 maxId）必须重建。
- Runtime code_map 更新。

## 验证

- `SessionChunkBackfillServiceTests`：**8/8 通过**（5 个既有 + 3 个断点场景）。
- `PuddingRuntime`、`PuddingPlatform`、`PuddingAgent` 构建均 0 error。
- 未修改 `D:\data`、未部署、未启动 Core/Desktop。

## 未完成与影响

- **失败项持久记录未做**：`ISessionChunkIndexer` 内部吞异常（既有幂等契约），服务目前只能保证“批未成功不推进”，无法列出永久失败消息；需后续给索引器增加可观察失败结果或回读校验。
- Ready 保护窗口目前是固定延迟（默认 60s），尚未接入真实 Ready/负载信号；SQLite busy 退避仍是固定 `DelayMs`，未按忙时自适应。
- 数据集身份仅用数据库路径（不含量化内容指纹）；恢复同一路径下的不同库副本时依赖“maxId 降低”检测，若新库 maxId 更大则不会失效（需显式清 checkpoint 或后续增强）。
- 生产 `SessionChunkBackfill:Enabled` 默认 false，E 的负载/争抢门禁尚未在真实开启回填的场景下测量。
