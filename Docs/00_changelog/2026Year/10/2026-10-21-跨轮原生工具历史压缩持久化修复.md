# 跨轮原生工具历史压缩持久化修复

## 根因与范围

用户报告 trace `90d5d78a49c94f789d099dfc2a41ac66`：526099 字节超过 524288 字节保护预算；选中 94 条历史生成摘要成功，但 `durable_commit_coveredmessagesnotfound` 阻止提交。前一轮有 9 组原生工具调用，18 条工具协议消息保留在运行中历史，未投影为 canonical ChatMessages。旧提交路径只要一条身份未知就对整段退回角色/正文匹配，既无法覆盖工具消息，也丢弃了已解析的精确身份。

更正（2026-10-21）：前次“压缩持久身份与近期跨度修复”的冷水合验证没有覆盖跨轮原生工具历史，不能证明本场景已解决。本次用连续两轮真实执行循环复现，修复前流式/非流式均失败。

## 改动

- `Source/PuddingCore/Runtime/ContextCompactionContracts.cs`：用完整、有序的 `WarmPrefixSourceMessage` 替代全段内容键回退，每条来源独立保留持久 ID。
- `Source/PuddingCore/Models/ChatMessage.cs`、`Source/PuddingRuntime/Services/AgentExecutionService.cs`：入站消息 ID 在运行期信封渲染后保留，不发送给 provider；原有精确身份不会因其他消息未解析而被丢弃。
- `Source/PuddingRuntime/Services/ContextCompactionService.cs`：原生工具消息及未投影运行期原文以 `warm_prefix_source` 完整 JSON 归档，包含空正文工具调用、参数、结果、推理、continuation 和内容部件；归档行、摘要、覆盖清单、覆盖标注和代次在同一事务写入。已知 ID 缺失、歧义映射、代次/覆盖冲突仍拒绝，不改内存。清单 ID/hash 顺序一致。
- `Source/PuddingRuntime/Services/ContextWindowManager.cs`：捕获逐条来源，已登记消息和待归档消息保持区分。
- 执行循环、`WarmPrefixCompaction.cs`、`LlmRequestTextBudget.cs`：失败报告附 `compaction_id`、选中数量、未解析数量、问题位置/角色/原因、摘要后字节测量；不输出用户正文。生命周期事件和系统日志保留归档数量与提交状态。
- 更新根与 Core/Runtime 代码地图、诊断手册。未提高上传预算，未改代理/TUN，未修改前端。

## 验证

- Runtime 定向回归 179/179；事务、覆盖过滤与诊断补充测试 31 项通过，新增诊断用例修正故障注入目标为实际选中首行后 1/1 通过；去重共 **203 项通过**。
- 跨两轮原生工具回归：修复前 2/2 失败，修复后流式/非流式均通过；当前轮保真、旧轮归档、重启加载摘要均断言。
- SQLite 故障注入：原文和摘要已插入后，在归档覆盖更新处故意失败，原文、摘要、已写覆盖标注、清单、代次全部回滚。
- 真实会话 SQLite 在线备份副本 + 前一轮 18 条工具事件本地重放（不执行工具、不调用模型）：576355 → 255617 字节；102 条来源提交，包含全部 18 条工具原文；副本代次 91 → 92。重启水合摘要仍在，含合成工具定义总量 413104 字节，持久身份全部可解析。使用模拟摘要，仅证明持久化与恢复链路，未验证语义摘要质量或原业务任务成功。
- 证据位于忽略的 `temp/test-out/compaction-native/`、`temp/compaction-native-*.log`；真实数据只写入在线备份副本，不把模拟摘要写入生产库。
