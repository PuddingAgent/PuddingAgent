# 加宽第 11 项实为 Bridge 侧等待超时缺陷；并发现应做「适配器逐字段审计」

## 更正（2026-10-02）：第 11 项不是契约缺口，是 Bridge 适配器丢掉调用方预算

先按纪律实读定性，结论是**我自己写的适配器有缺陷**：

| 位置 | 事实 |
|---|---|
| 契约 | `BrowserWaitForRequest.TimeoutMs` **本来就有**（含 `DefaultTimeoutMs`/`MaxTimeoutMs` 校验与 `Timeout` 便捷属性） |
| 线缆 | `WaitForCommand.timeout_ms = 5` 早就在 |
| Core→proto | `Pudding.CapabilityBroker/WireMapping.cs:142` 写 `TimeoutMs = waitFor.TimeoutMs` |
| proto→DTO | `Pudding.DesktopConnection/Mapping.cs:407` 读，并做"0 ⇒ 默认值"回退 |
| Desktop 侧 | `BrowserRuntimeDesktopSurface.cs:481` 塞进运行时 `WaitCondition.TimeoutMs` |
| **Bridge 侧** | **`ToRuntimeWaitCondition` 只映射条件、不带超时** ⇒ 调用方要 5 分钟，实际按运行时默认 30 秒等待 |

**后果**：这是"能力通道路径尊重预算、Bridge 路径静默忽略预算"的行为分叉——
与第 8 项（`DeltaX`）**完全同类**。修复：`ToRuntimeWaitCondition` 改为接收整个请求并逐分支带上
`TimeoutMs = request.TimeoutMs`；新增测试 `WaitFor_PassesTheRequestedBudgetToTheRuntime`
（断言 1 234 ms 真的到达运行时）。

## 值得注意的规律（本轮最重要的产出）

加宽清单 11 项里，**已有 2 项（第 8、11）实为适配器自身缺陷**，而不是契约缺口：

- 第 8 项：`Scroll` 只传 `DeltaY`，丢掉 `DeltaX`；
- 第 11 项：等待不传 `TimeoutMs`，调用方预算被运行时默认值覆盖。

两项都是**可选参数**在"按形状手写映射"时被漏掉，且都只在 Bridge 路径上发作——正是本系列最忌讳的
"两条传输行为分叉"。因此**下一步应先做一次适配器逐字段审计**：把
`BridgeBrowserCapabilitySurface` 的九个映射分别与「契约 DTO 的全部字段」和
「`BrowserRuntimeDesktopSurface` 的对应实现」逐字段对照，而不是继续按清单往下猜。
这比再改一个 proto 字段更值钱——它能把同类缺陷一次清干净。
