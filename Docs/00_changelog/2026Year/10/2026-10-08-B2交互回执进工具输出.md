# 2026-10-08 B2：交互回执进工具输出，一次 fill 即可确认写入（G7）

## 目标 / 背景

设计把「一次 `fill` 调用即可确认写入成功」列为**最直接的省 token 手段**（G7：
「一次 fill 回执足以确认非敏感值，无二次 snapshot」）。前两轮分别备好了
**回执判定**（B0 的 `BrowserReceiptJudge`/`BrowserActionAssertion`）与**表单值回读**
（上一轮 `value`/`selectedValues` 端到端），本轮把两者合流并接到工具输出。

## 改动

### 判定（纯逻辑，`PuddingBrowser.Automation`）

- `Source/PuddingBrowser.Automation/BrowserInteractionReceipt.cs` — 新增。
  `BrowserInteractionEvidence`（调用方声明 + 驱动观测）+ `BrowserInteractionReceipt.Build(...)`：
  - **① 不按动作名推断成功**：只有声明了期望才有断言——显式 `expect_value`，或 select 的
    `values`、check/uncheck 的 `checked` 这类**调用方自己给的目标值**；没有期望就如实报
    `dispatched`（`ok=true` 但标注 `requiresFollowUp`），不假装 verified；
  - **② 表单值一律不回显**：value/selectedValues 只给 `matched` 与长度；
    `checked` 是布尔，可以回显；
  - **③ 期望存在但拿不到观测**（元素消失/重渲染）⇒ `unverified`，**不是** failed；
  - `ExecutionFor(error)` 由错误目录的 `Retryable`/`MayHaveSideEffects` 推导执行阶段
    （未开始 / 已派发 / 结果不明），不引入新知识。

### 接线（工具层，两条传输因此天然同形）

- `Source/PuddingBrowser.AgentTools/BrowserInteractTool.cs` — 新增 `expect_value` 入参；
  成功路径把证据交给共享判定器，输出新增 `ok`/`completion`/`assertions`/`mayHaveSideEffects`/`safeToRetry`。
- `Source/PuddingBrowser.AgentTools/BrowserToolContracts.cs` — `BrowserInteractionToolValue` 新增上述字段，
  并新增 `BrowserAssertionToolValue`（`kind`/`matched`/`length`/`actual`）。
- `Source/PuddingBrowser.AgentTools/PuddingBrowser.AgentTools.csproj` — 新增对
  `PuddingBrowser.Automation` 的引用（纯逻辑组件，只依赖 Contracts）。

**为什么判定放在工具层**：工具同时位于两条传输之上，只判定一次 ⇒ 桥接路径与能力通道路径
不可能各自验出相反结论（设计「映射层不能各自再验出相反结论」）。放在这里还避免了改
proto/线缆 DTO 的必要。

## 验证

| 套件 | 结果 |

| `PuddingBrowser.AgentTools.Tests` | **20 / 20**（原 18 ＋ 2） |

| `build` Automation · AgentTools | 0 错误 |

新增门禁（关键几条）：

- `Interact_FillWithExpectValue_ConfirmsTheWriteInOneCall`（工具层，G7 验收）：
  `expect_value` 命中 ⇒ `completion=verified`、`ok=true`、断言 matched；
  不命中 ⇒ `completion=failed`、`ok=false`；**不给期望 ⇒ `dispatched`**（不假装成功）。
- `Interact_Receipt_NeverEchoesTheFormValue`（工具层）：断言 `actual` 为 **null**、
  `length` 等于真实长度，且整个输出**不含**输入内容。
- `BrowserInteractionReceiptTests`（17 条，纯逻辑）：表单值零回显、无期望不判失败、
  有期望无观测报 unverified、select 的集合比较与 check 的 no-op 成功、
  执行阶段由错误目录推导、只有「未开始 + 可重试 + 无副作用」才 `safeToRetry`。

**取红实测**：把工具里的 `ExpectedValue: args.ExpectValue` 改成 `null`（断开期望传递）⇒
`Interact_` 两条**恰好变红**，其余 18 条仍绿；复原后 20/20 复绿。

## 已知边界（诚实登记）

- **失败路径暂无回执**：`browser_interact` 失败时仍走 `BrowserCapabilityFailure.From(...)`
  （只有 code/message），因此「超时且输入已提交 ⇒ unknown + 已派发事实」尚未体现在工具输出里。
  这需要失败结果也能携带结构化载荷，属后续切片；本轮只覆盖成功路径。
- **重渲染稳定的验证未做**：判定用的是驱动**同一轮脚本内**的回读值。受控组件（React 等）
  可能在一次重渲染后回滚值，设计要求的「重渲染后仍满足期望」需要在脚本里等一帧再回读，
  属驱动侧后续（本轮未改脚本行为，也无法在本环境运行时验证）。
- **located 的 `value` 仍可能回显明文**：上一轮加的 `include_value` 目前原样返回；本轮的
  零回显策略只覆盖**交互回执**。两者策略不一致，已在后续切片处理。
- `expect_value` 目前只判「等于」；URL/文本出现/元素状态等其它 expect 属后续。

## 与本次改动无关的两处既有失败（已核实）

`PuddingPlatformTests` 有 2 条失败，**与本次改动无关**，且**不可能相关**：

- `DefaultSeedCases_ShouldNotLeakBenchmarkOrSystemHints`：`Docs/14_reports/测试套件健康与缺陷类诊断-2026-09-17.md:312`
  已登记为**假失败**——该用例经 `AppContext.BaseDirectory` 上溯 4 层定位仓库数据，
  在 `--artifacts-path` 下深度变化 ⇒ 找不到种子数据；
- `RefreshWorkspace_Starts_Stdio_Server_And_Preserves_Codex_Thread_Result`：同属
  `Docs/00_changelog/2026-10-06-登录JWT有效期七天与security-json密钥来源.md:85`
  记录的既有失败，与 stdio 子进程/文件锁相关。

**决定性依据**：`Source/PuddingPlatformTests/PuddingPlatformTests.csproj` 只引用
`PuddingPlatform`/`PuddingCore`/`PuddingRuntime`/`PuddingTaskRecall.Cli`/`Mcp.Cli`，
而这三个生产工程**都不引用** `PuddingBrowser.AgentTools` 或 `PuddingBrowser.Automation`
（已检索确认）⇒ 本轮改动根本无法进入该测试程序集。

另：为尝试「不加 `--artifacts-path` 复跑」留下了一个 testhost 进程锁住 Debug 产物；
该进程（PID 80940，路径属本次运行的 `PuddingPlatformTests\bin\Debug`）已由我停止。

## 影响与回滚

- **行为变化（Agent 可见）**：`browser_interact` 输出新增 5 个字段；不带 `expect_value` 时
  `completion=dispatched`。既有调用方少读字段不会出错，但**新字段是设计要求的语义**，不应被忽略。
- 无数据/配置影响；线缆 DTO（proto/能力通道）未改动。
- 回滚：删除 `BrowserInteractionReceipt.cs` 与 `BrowserInteractionReceiptTests.cs`，
  还原工具/契约/csproj/测试与三处 code_map。
