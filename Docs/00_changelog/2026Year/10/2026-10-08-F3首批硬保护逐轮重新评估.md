# 2026-10-08 F3 首批：硬保护逐轮重新评估（软维护延期不得让它失效）

> 范围：`Source/PuddingRuntime/Services/WarmPrefixMaintenanceAdmission.cs`（新增）、
> `Source/PuddingRuntime/Services/AgentExecution/AgentExecutionService.Streaming.cs`、
> `Source/PuddingRuntime/Services/AgentExecution/AgentExecutionService.Buffered.cs`、
> `Source/PuddingRuntime/Services/WarmPrefixCompaction.cs`、`Source/PuddingRuntimeTests/Services/WarmPrefixMaintenanceAdmissionTests.cs`
> 依据：[ADR-095](../../../07_architecture/109ADR-095会话上下文维护与首增量延迟治理ADR.md) D1/D2、[修复方案](../../../12_features/首Token等待与上下文指示器修复方案-2026-10-07.md) §3
> 触发：用户点名的验收用例「第一轮软维护被延期，后续工具结果使请求越过硬阈值仍须硬保护」，
> 以及[分类回放](2026-10-08-软硬分类回放与393216容量来源核对.md) §5.2 的实证缺陷

## 1. 问题

`warmPrefixCompactionAttempted` 是 **Turn 级一次性**标记，同时管住软维护与硬保护。而 F3 首批
（2026-10-08）把软维护改成「请求仍安全就延期」之后，这个语义就出问题了：

- 第 0 轮判**软** ⇒ 只发 `context.compaction.skipped`，不改历史，**标记置位**；
- Turn 内工具结果持续增长 ⇒ 第 N 轮 `Prepare` 发现未裁剪请求越过有效上限；
- 但标记已置位 ⇒ 不再评估压缩 ⇒ 只能每轮裁剪**请求副本**（诊断 §5.2：事故第一条样本的 Turn 内
  round 34 `removed=1`、round 35 `removed=76`），记忆连续性下降；若不可裁剪地板（system + 工具 schema
  + 受保护尾部）本身超限，还会直接抛 `LlmInputBudgetExceededException`。

⇒ 延期修复等于用「更早、更多的请求副本裁剪」换首块时间。这正是用户要求补用例的那条路径。

## 2. 改动

### 2.1 两条封顶拆开（`WarmPrefixMaintenanceAdmission`，纯判定，可单测）

| 维护类型 | 封顶口径 | 理由 |
|---|---|---|
| 软维护 | **每 dispatch 一次** | 同一 dispatch 内重复评估不会有新的可压缩内容（候选级准入；真正的去重/退避由持久候选指纹承担，本轮未落地） |
| 硬保护 | **逐轮重新评估** | 延期不得让后续轮次失去硬保护；同一 dispatch 内至多尝试一次，避免每轮昂贵测量 |

判定**不做 I/O、不需要额外计量**：调用方用本轮 `LlmRequestBudgetGuard.Prepare` 的结果作为
「未裁剪请求已越界」的证据 —— `RemovedMessageCount > 0`（裁掉才装得下）或
`LlmInputBudgetExceededException`（连裁剪都不够）。

### 2.2 两条执行路径都接线（Streaming 与 Buffered）

1. **软维护**：条件从 `history.Count > 12 && !warmPrefixCompactionAttempted` 改为
   `WarmPrefixMaintenanceAdmission.ShouldAttemptSoft(...)`（语义不变，口径集中）。
2. **硬保护（正常路径）**：`Prepare` 前留存 `untrimmedOutbound`；若 `RemovedMessageCount > 0`
   且硬保护尚未尝试 ⇒ 用**未裁剪**的 outbound 做一次同步压缩，成功后重建并**重新** `Prepare`，
   日志记 `remainingTrim`。
3. **硬保护（异常路径）**：`Prepare` 抛 `LlmInputBudgetExceededException` 时，在 fail-closed 之前
   先做一次确定性同步压缩；压缩不可用才继续抛（保持既有失败语义）。
4. `Prepare` 只返回新列表、不改动输入，因此 `untrimmedOutbound` 与压缩请求的
   `exactOutboundHistory` 语义一致（原样重放压缩前的出站）。

### 2.3 顺手修掉 `after` 的最后一处残留

`WarmPrefixCompactionOutcome` 新增 `AppliedAfterUsedTokens`（只有提交成功才是非 null），
Buffered 的 `subagent.context.compacted` 事件改用 `measured_tokens_after`，
并把计划估算移到 `plan_estimate_excluding_summary_tokens`。上一批只修了主 `completed` 事件，
这条子代理事件仍把「未含摘要的计划估算」当 after。

| 项 | 状态与原因 |

| **可选维护调度到 canonical 终态提交 + 前台租约释放之后** | **未交付**。`TrimHistoryAsync` 仍在 `done` 之前、且在整个 Turn 的前台租约内（Streaming 1790 / Buffered 2195）。要真正移出去需要：① 前台租约释放后的调度点；② 与持久 checkpoint 同一事务的维护；③ 用户抢占信号。而本仓库**没有任何驱动流式/缓冲执行的测试宿主**（`ExecuteStreamingAsync` 在测试里 0 引用），也就是说这类生命周期改动**当前无法验证** —— 在缺少证据的情况下改「谁在什么时候写历史」会引入数据一致性风险，故本轮不动。 |

## 6. 更正（同批）：删掉异常路径上不可达的 rescue 分支

本批最初的实现对 `LlmInputBudgetExceededException` 做了一次「先压缩再重试」的救援。随后核对发现
**该分支不可能生效，属死代码**，已在 Streaming 与 Buffered 两个路径移除，改为记一条明确诊断后直接
`throw`（保持 fail-closed）：

| 事实 | 依据 |
|---|---|
| 两条路径共用**同一个受保护尾部地板** | `LlmRequestBudgetGuard.RemoveOldestConversationUnit`（第 291 行）与 `PrepareSoftCompaction` 都调用同一个 `ComputeProtectedTailStart`（第 320 行，`ProtectedTailMessages = 8` + 当前 User 围栏） |
| `Prepare` 的裁剪能力**更强**（token 更少） | `Prepare` 在裁剪之后还会做一次 `EvictOversizedToolPayloads`（第 162 行），warm-prefix 候选没有 |
| ⇒ 结论 | 凡 `Prepare` 抛超限，压缩后的整请求 = 地板 + 摘要 ≥ 裁剪后 > 上限 ⇒ `VerifyApplication` 必然以 `after_summary_exceeds_hard_limit` 拒绝。保留该分支只会在注定失败的请求上多花一次约 20 秒的摘要调用 |

**回归案例**（把这条不变量固定下来，防止分支被加回）：
`WarmPrefixMaintenanceAdmissionTests.ExceptionPath_WarmPrefixCannotRescue_WhenUntrimmableFloorExceedsLimit`
—— 构造「巨大 system + 可裁剪中间段 + 受保护尾部 + 极小上限」：断言 `Prepare` 抛
`LlmInputBudgetExceededException`、候选仍能形成且 `RequiresSynchronousProtection == true`，
而 `VerifyApplication` **拒绝**并给出 `after_summary_exceeds_hard_limit`。

**更正后复跑**：`dotnet build` exit 0；`PuddingRuntimeTests` 全量 **失败 0 / 通过 2008 / 跳过 6（2014）**；
`WarmPrefixMaintenanceAdmissionTests` **8/8**。（§3.1 里「异常路径 rescue」的表述随之作废：
该路径已不存在，主循环改动只剩「顺序调整 + mid-turn 硬保护插入」。）
