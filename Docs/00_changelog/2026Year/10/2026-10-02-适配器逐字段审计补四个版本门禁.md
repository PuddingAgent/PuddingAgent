# 适配器逐字段审计：补齐 4 个缺失的版本门禁（3/7 → 7/7）

## 目标 / 背景

上一轮提出「先做适配器逐字段审计」：把 `BridgeBrowserCapabilitySurface` 的九个映射与
契约 DTO 全字段、以及 `BrowserRuntimeDesktopSurface` 的对应实现逐字段对照。
本轮执行，**第一次对照就发现成片缺陷**。

## 审计方法与结果

先数「可钉版本的操作」有几处、各在哪一层做门禁：

| 操作 | Desktop 侧门禁 | 本适配器（修复前） |
|---|---|---|
| `browser.contexts` | — （无版本约束） | — |
| `webview.page_state` | — （无版本约束） | — |
| `browser.tabs` | ✅（第 167 行，**无条件**：请求构造即要求必填版本） | ❌ **缺失** |
| `browser.locate` | ✅（259，`IsKnown` 守卫） | ✅ |
| `browser.snapshot` | ✅（394，`IsKnown` 守卫） | ✅ |
| `browser.wait_for` | ✅（449，`IsKnown` 守卫） | ❌ **缺失** |
| `browser.interact` | ✅（516，无条件） | ✅ |
| `webview.navigate` | ✅（623，`IsKnown` 守卫） | ❌ **缺失** |
| `webview.execute_javascript` | ✅（673，`IsKnown` 守卫） | ❌ **缺失** |

⇒ **Desktop 侧 7/7，本适配器只有 3/7**。缺的四个里最严重的是 **`tabs`**：
切换/关闭是变更类操作，调用方明确钉了版本、而页面其实已经变过，
旧行为会**照旧去切换/关闭那个页面**——动的可能根本不是调用方以为的页面。

## 改动

- `Source/PuddingHost/BrowserBridge/BridgeBrowserCapabilitySurface.cs`：
  - 新增共享门禁 `VersionGate(targetKey, actual, expected, required)`：
    `required: true` 时无条件核对（tabs/interact，其请求构造保证版本必填）；
    否则 `expected.IsKnown` 为假即跳过。错误形状与 Desktop 侧一致
    （`page_version_mismatch` + `page 'x' is at vN, request pinned vM` + `retryable: true`）。
  - `NavigateAsync` / `TabsAsync` / `WaitForAsync` / `ExecuteJavascriptAsync` 各加门禁，
    且**都在动作之前**。
- `Tests/PuddingHost.Tests/BrowserBridge/BridgeBrowserCapabilitySurfaceTests.cs`：新增 4 项
  「陈旧版本钉 ⇒ 拒绝且**一次都没动**」的用例。

## 验证

- `PuddingHost.Tests` **224/224**（新增 4 项）。
- 未验证：真实通道端到端（需 Desktop 侧启用能力通道 + 外部重启窗口）。

## 过程教训（两条，都是工具层）

1. **不要用 PowerShell 脚本写含中文的补丁**：本机 `pwsh` 里的 Windows PowerShell 会按 ANSI
   解码 UTF-8 脚本，中文字符串被拆坏导致解析失败——改用 Python（源码默认 UTF-8）即通过。
2. **脚本插入语句必须锚定在「语句边界」**：`execute_javascript` 的门禁最初被插进
   `var value = await page` 与 `.EvaluateAsync(...)` 之间（跨行表达式中间），编译立刻失败；
   移到表达式之前即修复。编译期就暴露，未造成隐性损坏。
