# 2026-10-08 开闸门

## 改动（一处）

```csharp
var service = new DesktopService(
    dispatcher, surface, pageTargets,
    serviceOptions ?? CreateDefaultServiceOptions(), authority,
    connectionGeneration: () => authority.ConnectionGeneration,  // ← 新增：闸门生效
    taskBindings: taskBindings);
```

**语义变化**：浏览器能力在生产路径上**必须**有有效授予（`Admit` 会判身份/世代/授予/租约/接管）；无授予 ⇒ **拒绝**（fail-closed），而不是放行。

## 为什么现在才开（顺序回顾）

1. round-197：结论是"**先有生产路径的签发，再开闸门**"，否则会 ship 出"fail-closed 但完全不可用"的浏览器功能；
2. rounds 199–252：控制面全线（契约/身份/载荷/ack/线缆/编解码/Desktop 策略与分支/Core 生产者/幂等/端到端）；
3. rounds 256–265：**触发点接线**（运行时缝 → 门实现 → 门用例 → 运行时证据 → 组合根实现 → **DI 注册**）；
4. **本轮**：开闸门。

## 诚实边界

- **能力通道默认关闭** ⇒ 那条路径上"无会话 ⇒ 门 no-op"；但**闸门本身已开**：一旦 Desktop 侧启用能力通道，浏览器能力就必须有授予。
- **没有真机验证**：本轮的证据是测试层的；真机行为（含 250ms 扫描、外部生命周期）仍需外部验收。
- 若全量链暴露出"被拒但本不该拒"的路径，应**回退开闸门并记录**，而**不是**放宽判据。
