# 2026-10-24 上下文用量口径收敛到后端单一投影

## 问题

用户反馈：**面板显示只有一个很低的百分比，系统却已经开始压缩上下文。**

复现后确认这不是显示 bug，而是三套算式并存：

| 位置 | 分子 | 分母 |
|---|---|---|
| 面板标题 | Provider 实测 | 有效输入窗口 |
| 面板分项/环弧 | 本地估算 | 模型窗口 |
| 压缩判定（`RequestAutoCompactionAsync` 覆盖） | 本地估算 | 模型窗口 × `CommitRatio` |

三者互不相干，任何一次改动只能对齐其中两套。叠加本地估算偏高后，「20% 已在压缩」是必然结果。

## 决定

用户裁定（2026-10-24）：**前端指示器与后端估算必须同参数、同 Service、同函数。**

落地为一条不变量：

> 面板主指标 = `UsedTokens ÷ EffectiveWindowTokens`；
> 它与压缩门禁使用**同一个分子、同一个分母**，由同一个纯函数产出。

Provider 实测降为**次级参考**（`measuredPercent`），用于评估真实节省，不参与任何门禁判定。
这是一个明确的口径切换：此前实测优先是为了让数字尽量真，但真数字若与系统行为不一致，
用户会失去唯一可对照的基准。现在主数字就是系统用来做决定的那个数。

## 实现

1. 新增 `Source/PuddingCore/Runtime/ContextUsageDisplay.cs`：
   `ContextUsageDisplay` + `ContextUsageSegment` + `ContextUsageDisplayProjection.Project(snapshot)` 纯函数。
   全部派生值（percent / remainingPercent / inputUnavailablePercent / segments）都在这一处算。
2. `ContextHealthSnapshot` 增加派生属性 `Display => ContextUsageDisplayProjection.Project(this)`。
   因为是**从快照自身字段派生**，结构上不可能与 `UsedTokens`/`EffectiveWindowTokens` 漂移。
3. `ContextHealthSnapshot.ExceedsAutoCompactRatio(ratio)`：判定分母固定为有效输入窗口；
   `ContextWindowManager` 改用该方法，删除 `maxTokenBudget * autoTriggerRatio` 的模型窗口分母。
4. 前端 `ContextUsageRing` 优先渲染 `display.*`，不再做任何除法；旧算式仅在 `display` 缺失（老后端）时回退。
   `api.ts` 增加 `ContextUsageDisplay` / `ContextUsageSegment` 契约与对照注释。

## 验证

- 新增 `ContextUsageDisplayProjectionTests`（9 条）：分母必须是有效窗口、`Percent == GateRatio*100`、
  实测不驱动主指标、分段之和等于标题、退化快照不除零、比率判定用有效窗口且边界含等号。
- **变异取红**：把投影分母改成 `ContextWindowTokens`、把判定分母改成 `ContextWindowTokens`
  → `失败 7 / 通过 4`；逐位复原（SHA-256 两个文件均相同）后 `-t:Rebuild` → `11/11` 通过。
- 前端新增 2 条用例：本地估算 99.9% 与后端口径 20% 分歧时，圆环 aria-label 与面板标题都必须是 20.0%。
  **变异取红**：把 `displayPct` 的来源改回 `pct` → `1 failed / 16 passed`；逐位复原 → `17/17`。
- 回归面：`PuddingRuntimeTests` 全量 **2300 通过 / 0 失败 / 7 跳过**；前端 `tsc --noEmit` 0 错误。

## 已知边界

- `PuddingWebApiTests` 的 `Compact_*` 用例在本机偶发失败，原始输出为
  `[Startup] 无法取得 DataRoot 独占租约 …（等待 30 秒后仍无法取得独占租约）`，
  属于测试宿主共享临时数据根的环境冲突，**未归因于本次改动**；本轮未复跑基线对照，故如实记为未归因。
- 前端回退分支仍在：后端未提供 `display` 时沿用旧算式。后端与前端随同一次重启部署，
  正常情况下该分支不会执行；它存在的唯一理由是防止滚动升级期间面板空白。
