# 2026-10-08 T5 首批：可选维护移出终态关键路径（含去重/抢占/取消）

> 新增：`Source/PuddingRuntime/Services/PostTurnMaintenanceScheduler.cs`、
> `Source/PuddingRuntimeTests/Services/PostTurnMaintenanceSchedulerTests.cs`（6 例）；
> 改动：`AgentExecutionService`（+2 行装配）、`AgentExecutionService.Streaming.cs`、`AgentExecutionService.Buffered.cs`；
> `WarmPrefixMidTurnHardProtectionE2ETests` +1 例顺序断言
> 依据：[ADR-095](../../../07_architecture/109ADR-095会话上下文维护与首增量延迟治理ADR.md) D1/D2、
> [修复方案](../../../12_features/首Token等待与上下文指示器修复方案-2026-10-07.md) §3
> 前序：[更正二](../../2026Year/10/2026-10-08-软压缩移出主请求关键路径与压缩生命周期归因.md)（曾更正「普通压缩仍在 done 之前且占前台租约」）

## 1. 问题

自动压缩（`TrimHistoryAsync`，含持久摘要 + 覆盖标注 + 代际）原本**同步出现在 done 帧与
`ExecuteAsync` 返回之前**，而且整个 Turn 持有 `SessionExecutionGate` 租约
（Streaming 旧 1882 行 / Buffered 旧 2279 行）。后果：

- 用户看到的终态时刻被维护耗时直接抬高（事故里最坏 20.760 s / 22.854 s 就发生在终态前的同步压缩上）；
- 维护与首增量延迟治理（ADR-095 D1/D2）的目标相冲突：它既不在终态之后，也不属于「安全新消息」该等的事。

## 2. 改动

### 2.1 `PostTurnMaintenanceScheduler`（新组件，复用既有 gate + logger，零 DI 变更）

| 语义 | 实现 |
|---|---|
| **终态之后**才开始 | 任务先 `EnterAsync(sessionId, "post_turn_maintenance", token)` 探一次门：Turn 持有租约**到方法返回**，因此这一步等价于「等本轮前台租约释放」 |
| **不长期占锁**（D2） | 探到门后**立刻释放**再干活 —— 维护不会把新消息挡在外面；真正与其它压缩互斥由 `ContextCompactionService` 的 per-session 单飞锁承担 |
| **去重 + 抢占** | 同一会话只保留一个在途请求；更新的请求**协作取消**旧的（新请求代表更新的历史状态，旧结果必然过期） |
| **失败有界** | 维护抛错只记 Warning，绝不冒泡影响已提交的 Turn 结果 |
| **可观测/可测** | `InFlightCount` + `DrainAsync()`（测试等待在途任务） |

### 2.2 两条执行路径接线

- `Streaming`：`await _contextManager.TrimHistoryAsync(...)` ⇒ `_postTurnMaintenance.Schedule(...)`；
- `Buffered`：同样替换（`ExecuteAsync` 返回即终态）；
- **历史快照在 Turn 内同步取**（`history.ToList()`）：避免维护与后续 Turn 并发遍历同一个 `List<T>`；
- 维护自己的 `CancellationToken` 由调度器提供（被抢占时取消），不再沿用 Turn 的 `postLoopCt`。

**遗留的取舍（已记录）**：维护现在可能与**下一个** Turn 并发（它不再独占租约）。这是 D2 的直接后果 ——
「不阻塞新消息」与「独占租约」不可兼得；一致性由既有机制保证（压缩单飞锁 + `InvalidateHistory`
+ 覆盖清单/代际 CAS + `CurrentTurnCompactionGuard`）。

## 3. 验证（本机真实执行）

| 命令 | 结果 |
|---|---|
| `dotnet build Source\PuddingRuntime\PuddingRuntime.csproj` | **exit 0**，0 错误 |
| `dotnet test … --filter "…PostTurnMaintenanceSchedulerTests"` | **exit 0**，失败 0 / 通过 **6**（连跑 3 次均 6/6，无 flake） |
| `dotnet test … --filter "…WarmPrefixMidTurnHardProtectionE2ETests"` | **exit 0**，失败 0 / 通过 **3** |
| 全量 `PuddingRuntimeTests` / `PuddingPlatformTests` | 见 §3.1 |

调度语义单测：

1. `Work_StartsOnlyAfterTheGateIsReleased`：Turn 持有租约期间维护**不得开始**；释放后必须开始。
2. `Work_DoesNotHoldTheGateWhileRunning`：维护运行期间新的会话级获取**必须立刻成功**（D2 的直接断言）。
3. `NewerRequest_PreemptsEarlierOne`：被抢占的维护**不得正常完成**、最新请求必须执行、留抢占日志。
   （断言口径刻意不依赖取消落在门探测还是执行体 —— 两者都算抢占成功；首版依赖「执行体内观察到取消」
   在门探测抢先时会偶发失败，已改为稳健口径并连跑 3 次验证。）
4. `DifferentSessions_RunIndependently` / `WorkFailure_IsSwallowedAndLogged` / `Schedule_ValidatesArguments`。

端到端顺序断言（`PostTurnMaintenance_CompletesOnlyAfterExecuteAsyncReturned`）：
捕获服务日志，`ExecuteAsync` 返回后立刻插入 `TERMINAL_RETURNED` 标记，轮询等
`[PostTurnMaintenance]` 出现，断言**标记下标 < 维护日志下标** ⇒ 终态确实先返回，
且维护没有因移出关键路径而消失。

### 3.1 全量回归

| 套件 | 结果 |
|---|---|
| `PuddingRuntimeTests`（含新增 6 例调度单测 + 3 例 E2E） | **exit 0**，失败 **0** / 通过 **2044** / 跳过 6（总计 2050） |
| `PuddingPlatformTests` | **exit 0**，失败 **0** / 通过 **1435** |

**顺序断言的第一版是错的（已更正，留痕）**：最初用「测试在 `ExecuteAsync` 返回后插标记，
断言标记下标 < 维护日志下标」。定向跑 3/3 通过，**全量跑却失败**（`terminal@8` 必须 < `maintenance@7`）。

根因：`ExecuteAsync` 的 `await using` 租约在**方法返回前**释放，因此后台维护可以在
「方法返回」与「调用方执行下一行 `Mark(...)`」之间就把 `Completed` 写进日志 —— 这个断言本身在竞态，
不是产品缺陷（全量负载下后台任务更容易抢到窗口）。

已改为**确定性**口径：

1. 回到调用方时立刻 `gate.EnterAsync(...)` 并断言**立刻成功** ⇒ Turn 租约确已释放；
2. 维护仍然会被执行（轮询到 `[PostTurnMaintenance]` 出现，证明它没有因移出关键路径而消失）；
3. 「维护只能在租约释放之后开始」由单测 `Work_StartsOnlyAfterTheGateIsReleased`（显式持租约断言不得开始）
   确定性证明 —— 2 与 3 组合起来才是「终态之后」的完整证据。
