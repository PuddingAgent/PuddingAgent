# 2026-10-08 软压缩移出主请求关键路径与压缩生命周期归因

> ⚠️ **本记录已被更正（2026-10-08）**：文中「两条样本的压缩请求输入只有 193K/197K，远低于当时约 606K 的有效输入上限」是**错误的量纲对比**——193K/197K 是**摘要请求的 Provider 实测输入**，而判据用的是校准后的 `InitialUsedTokens`，两条样本分别是 **583,691 / 625,824**。按 605,760 的有效上限代入，**只有第一条**会被判为软（可延期），**第二条仍是硬保护**。回放证据、更正后的结论与由此发现的两个新问题见文末「更正（2026-10-08）」节。

> 范围：`Source/PuddingRuntime/Services/`（`AgentExecutionService.cs`、`WarmPrefixCompaction.cs`、`AgentExecution/AgentExecutionService.Streaming.cs`、`AgentExecution/AgentExecutionService.Buffered.cs`、`AgentExecution/AgentTurnTimingCollector.cs`、`ContextWindowManager.cs`、`LlmRequestBudgetGuard.cs`）、`Source/PuddingCore/`（`Runtime/ContextSummaryMarkers.cs` 新增、`Platform/LlmOptions.cs`、`Platform/SseEventTypes.cs`、`Platform/ConversationContracts.cs`）、`Source/PuddingRuntimeTests/`、`Source/PuddingCoreTests/`
> 依据：[ADR-095](../../../07_architecture/109ADR-095会话上下文维护与首增量延迟治理ADR.md) D2/D7、[修复方案](../../../12_features/首Token等待与上下文指示器修复方案-2026-10-07.md) §1/§3、[诊断报告](../../../14_reports/首Token等待与上下文指示器诊断-2026-10-07.md) §3.1/§3.2/§4.3
> 阶段：ADR-095 施工顺序里的 **F3 核心（软维护时机）+ F4（生命周期与计时）+ F1 摘要标记合同**；**F2（唯一提交边界/持久 checkpoint 与 generation CAS）与独立组件 `PuddingContextPolicy` 未实施**，见文末「未完成」。

## 问题（改动前）

1. **软压缩挡在主模型前面**。Streaming/Buffered 在第 0 轮、最终预算检查之前 `await TryWarmPrefixCompactionAsync(...)`，而该方法内部 `await LlmInvoker.InvokeAsync(... purpose: "compaction")` 等完整摘要返回。长历史下这给每条新消息附加同步等待；诊断报告实测两条样本分别为 **20.760 秒 / 22.854 秒**（占「受理→首推理增量」的 77% / 81%），而主模型自身 TTFT 只有 4.250 / 3.987 秒。触发条件是软阈值（`triggerRatio`，默认 0.80），**不是**硬输入越界——这两条样本的压缩请求输入只有 193K/197K，远低于当时约 606K 的有效输入上限。
   > **更正（2026-10-08）**：末句量纲错了。193K/197K 是**摘要请求的 Provider 报数**（`promptTokens`），不是判据输入；判据输入是校准后的 `InitialUsedTokens` = **583,691 / 625,824**。按 605,760 的有效上限，**第一条才是软（+22,069），第二条是硬（−20,064）**，即第二条仍会同步压缩。详见文末更正节。
2. **这条路径没有可展示的生命周期**。warm-prefix 只返回 outcome 并记日志，不发布 `context.compaction.*`，因此压缩期间前端没有任何事实可显示；`AgentTurnTimingCollector` 也没有独立的压缩耗时，终态面板无法解释约 23 秒的前置等待。
3. **摘要标记两套，计量只认一套**。`ContextUsageSnapshotStore` 只按 `<compact_summary>` 识别摘要，而 warm-prefix checkpoint 写的是 `<compacted-summary>`；后者被误计入「对话消息」桶，表现为摘要桶恒为 0（诊断 §4.3）。

## 改动

### 1. 软维护准入门槛（ADR-095 D2，核心修复）

`WarmPrefixCompactionPlan` 新增判据 `RequiresSynchronousProtection => InitialUsedTokens > EffectiveInputLimit` 与 `HardHeadroomTokens`，两侧口径同源（模型窗口 − 实际输出预算 − 安全余量，再取 Provider 输入上限与 WorkUnit 容量的较小值）：

- **判为软**（候选只来自软阈值、请求仍能安全容纳）：`TryWarmPrefixCompactionAsync` **不调用摘要模型、不改动历史**，只发一条 `context.compaction.skipped`（`stage=deferred`、`reason=soft_threshold_request_still_safe`、`applied=false`、前后估算、`candidateRemoved*`、`hardHeadroomTokens`、`durableCheckpoint=false`）+ `[AgentExec:Compaction] Warm-prefix soft maintenance deferred` 日志，然后返回 `Disposition=DeferredSoft`。真正的整理交给 canonical 终态提交后已有的持久压缩路径（`ContextWindowManager.TrimHistoryAsync` → `ContextCompactionService`），与方案 §3「轮内只评估、终态后整理」一致。
- **判为硬**（估算输入已越过有效输入上限）：保持原语义同步生成摘要，只是补齐 `started`（真实开始前）与 `completed(applied=true)` / `failed` / `no_gain` 终态，且失败/无收益时历史保持原样（`historyPreserved=true`）。

`warmPrefixCompactionAttempted` 的「本轮一次」上限语义未变（同一 dispatch 内不再重复尝试），变的是**软候选不再产生同步等待**。

方案明确不承诺的部分也照旧：活跃 Turn 内的**并行**候选生成没有做（方案 §3 末段与 ADR-095 D1 都把它列为后续扩展），初版只在安全点评估、终态后整理。

### 2. 生命周期事件与计时归因（F4）

- `SseEventTypes` / `ConversationEventTypes` 新增 `ContextCompactionSkipped = "context.compaction.skipped"`。它映射到会话目录投影的 `_ => null` 分支（保持原状态），不像 `completed` 那样投影为 `frozen`——延期不是「已压缩」。
- `ContextWindowManager` 新增 `internal EmitWarmPrefixCompactionLifecycleAsync(...)`，复用既有 `ISessionCompactionEventEmitter` canonical 管道（不新增第二套事件库、不新增轮询）；emitter 缺失/写入失败按既有策略记 metric 并告警，不抛。
- `AgentTurnTimingCollector` 新增 `CompactionMs`（**未被观察时为 null，不用 0 掩盖**）、`CompactionAttempts`、`DeferredSoftCompactions`、`AppliedCompactions`，四个键进入终态 `done` 帧的 `timings` 载荷；`RegisterCompactionAttempt` 的注释明确：压缩耗时**不计入** `ModelMs`（主模型耗时），两者是独立归因。
- 埋点约定没有引入摘要原文/Prompt/密钥；事件只带数量、估算与 id。

### 3. 压缩摘要标记收敛为共享合同（F1 的标记部分）

新增 `Source/PuddingCore/Runtime/ContextSummaryMarkers.cs`：`Canonical = "<compact_summary>"`、`WarmPrefixCheckpoint = "<compacted-summary>"`、`All`、`ContainsMarker(string?)`。`ContextUsageSnapshotStore.CaptureLlmRequest` 的分层归因与思维链扣除、`WarmPrefixCompaction.TryCreateCheckpoint` 的写入都改走该合同。合同放在 PuddingCore 是因为计量在 Core、压缩写入在 Runtime，依赖方向不得反转；新增摘要标记路径必须在此登记，禁止各自比较字面量。

### 4. 软阈值分母与出站硬门禁同源

`LlmRequestBudgetGuard.PrepareSoftCompaction` 新增末位可选参数 `workUnitInputCapacity`，并传给 `ResolveEffectiveInputLimit`；`WarmPrefixCompaction.TryCreatePlan` 同样新增该末位可选参数，由 `AgentExecutionService` 传入 `request.UsageBudget?.MaxInputTokens`。改动前软阈值用的是比真实硬边界更宽的分母（忽略 WorkUnit 容量），会把「其实已经越界」的请求误判成软候选。两个参数都在末位且有默认值 ⇒ 既有调用与测试零改动。

## 已知取舍与风险

- **降级路径仍存在**：延期后同一 dispatch 内不再重试软压缩，若后续轮次因工具结果增长越过硬边界，出站只能靠 `LlmRequestBudgetGuard.Prepare` 的**请求副本**硬裁剪（会把 `removed=N` 记成 Warning）。这正是方案 §2 要求单独展示的「本次请求裁剪了旧上下文」，本轮只保留了既有 Warning 日志，**尚未**发独立 canonical 事实、也未在前端显示。
- **`completed` 事件的既有副作用**：`context.compaction.completed` 会被 `ConversationCatalogWriter` 投影为会话目录状态 `frozen`。这条映射改动前就存在于自动压缩路径（`ContextWindowManager` 同样发这个事件），本轮没有改变它；`skipped` 走 `_ => null` 分支不受影响。若认为该映射本身有误，属独立问题，不在本轮范围。
- **成本方向**：延期意味着在软阈值与硬上限之间（80%–100%）的请求仍按高水位发出，直到终态后的持久压缩收缩历史。本提交没有做 token 成本对比；方案 §6.3 要求的「摘要 Token/费用、缓存冷 miss」聚合指标也未实现。

## 更正（2026-10-08）

本条记录与同批次提交信息中的一句结论作废：

> 原文：「这两条样本的压缩请求输入只有 193K/197K，远低于当时约 606K 的有效输入上限。」

**错在量纲**：193K/197K 是**摘要请求的 Provider 实测输入**（promptTokens），不是判据输入。判据用的是校准后的 plan.InitialUsedTokens，两条样本分别是 **583,691 / 625,824**（pudding-20261007_023.log 行 1547 / 2781），有效输入上限是 **605,760**（同日志 21 处 inputLimit=）。

| 样本 | 判据输入 | 硬余量 | 结论 |
|---|---|---|---|
| 第一条 22:43:39 | 583,691 | **+22,069** | 软 → 延期（省 20,760 ms）|
| 第二条 22:50:19 | 625,824 | **−20,064** | **硬 → 仍同步保护**（22,854 ms 保留）|

⇒ 「两条样本都能省掉前置压缩」**不成立**；本次修复只覆盖第一条。回放证据、393,216 来源结案，以及由此发现的**压缩请求归因指向压缩后形状**与**Turn 级一次封顶会让硬保护失效**两个新问题，完整记录见 [2026-10-08-软硬分类回放与393216容量来源核对.md](2026-10-08-软硬分类回放与393216容量来源核对.md)。原始文本与结论一律保留在上文，不回改。

### 更正二：普通压缩**没有**移到终态之后

同批改动里还有一句被更正的表述：

> 原文：「真正的整理交给 canonical 终态提交后已有的持久压缩路径（`ContextWindowManager.TrimHistoryAsync` → `ContextCompactionService`）」

**事实：`TrimHistoryAsync` 现在跑在终态之前，并且仍在 Turn 的准入租约覆盖期内。**

| 位置 | 行号 | 与终态的关系 |
|---|---|---|
| `Source/PuddingRuntime/Services/AgentExecution/AgentExecutionService.Streaming.cs` | `TrimHistoryAsync` = **1790** | `turnTimings.MarkCompleted()` = **1882**、`done` 帧构造 = **1895**、`Append` = **1929**、`yield return doneFrame` = **1936** ⇒ 压缩在 `done` 之前 |
| `Source/PuddingRuntime/Services/AgentExecution/AgentExecutionService.Buffered.cs` | `TrimHistoryAsync` = **2195** | 同样在其终态之前 |
| `Source/PuddingRuntime/Services/Messaging/AgentExecutionAdmissionCoordinator.cs` | `AcquireForeground`（第 26 行） | 前台租约按**整个 Turn**持有 ⇒ 该阶段仍会推迟回复完成与下一条消息的准入 |

⇒ 本批修复只做到「软维护不再进入第 0 轮的关键路径」；**「整理移到终态提交之后」尚未实施**，属 T5。
因此「延期 + 终态后整理」目前只是**一半**：延期生效了，但被延期的整理落在了 `done` 之前且仍占前台租约。
