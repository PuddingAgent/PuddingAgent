# 2026-10-02 提示驱动的按路径观测

## 为什么这一刀是必需的

上一轮把驱动切到 `Coordinator` 后，**每一次「保存一个文件」都会触发一次全树枚举**
（协调器每轮跑完整清单校准）。对几万个文件的仓库，这比旧的逐文件路径**更费磁盘** ——
正好与被修复的放大同款。也就是说：上一轮的开关在性能意义上是不能打开的，先修这个。

## 改动

- 新增 `Source/PuddingCodeIndex/Contracts/ICodeSourcePathProbe.cs`：**按路径观测**的可选能力端口
  （只给一批已知路径取元数据，不遍历整棵树）。与 `ICodeSourceScanner` 分开是刻意的：
  给共享端口加成员会破坏每一个实现者（含组件外替身），而这里只需要「能按路径观测」的实现。
- `FileSystemCodeSourceScanner` 实现该端口：
  - 文件提示 ⇒ 只读该路径的元数据（不存在也如实给出「元数据为 null」，读不到不得用别的值顶替）；
  - 目录提示 ⇒ 枚举其子树（目录变更可能影响批次从未提到的文件），目录本身不作为文件候选；
  - **结果永远 `Complete=false`**：没被问到的路径这一轮没有事实 ⇒ **永远不能据此删除任何记录**。
- `CodeSourceScanOptions` / `CodeSourceMaintenanceRunOptions` 增加 `Targeted`；
  `CodeSourceScanService.ObserveAsync` 在「`Targeted` + 有提示 + 扫描器具备该能力」时走按路径观测，
  否则退回完整枚举（正确性优先于省读盘）。
- `CodeIndexMaintenanceService` 在 `Coordinator` 模式下按「有提示」置 `Targeted`：
  提示驱动的批次只做按路径观测；没有提示（例如重组/reconcile）仍走完整扫描。
- `CodeSourceMaintenanceMode` 文档登记**启用前的硬前提**（见下）。

## 验证

- `dotnet test Source\PuddingCodeIndexTests` → **318 通过 0 失败**（本次 +7）。
- `dotnet test Source\PuddingCodeIntelligenceTests` → **132 通过 0 失败**。
- 用例覆盖：提示驱动**不调用全树枚举**、只调一次按路径观测且路径就是提示集合；
  **提示驱动的轮次绝不确认删除**（文件消失 + 提示 ⇒ `DeletedCount == 0` 且旧 manifest 记录保留）；
  没有 `Targeted` 时仍完整枚举且 `ScanComplete=true`；扫描器没有该能力时退回完整枚举；
  真实扫描器只观测给定路径（元数据真实）、缺失路径给出 null 元数据、目录提示展开子树。

## 未完成与影响 —— 启用 Coordinator 前的硬前提

1. **周期性校准尚未接到协调器**：常规校准钟（默认 15 分钟）仍由旧的 `CodeIndexCalibrationService`
   直接扫 store 删陈旧行，而新链路的 manifest/账本由协调器维护 ⇒ 两者同时存在会让
   「索引」与「manifest」对同一路径给出不同结论。**启用前必须把常规校准钟接到协调器的完整扫描**
   （提示驱动的批次不产生删除，丢失的删除只能靠周期性完整扫描兜住）。
2. **Watcher 事件到提示的节流/合并**仍未接（提示目前来自旧 watcher 的批次路径）。
3. 默认仍是 `Legacy` ⇒ **运行中实例行为未变**，本轮不需要重启，也不构成性能结论（真实磁盘读数的
   四场景复核必须在打开开关并由进程外控制器重启之后进行）。
