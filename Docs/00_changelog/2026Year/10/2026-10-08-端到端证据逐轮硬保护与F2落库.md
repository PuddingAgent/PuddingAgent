# 2026-10-08 端到端证据：逐轮硬保护与 F2 落库在真实 Turn 内成立

## 1. 更正（重要）：不是「没有执行宿主」

前几轮我反复写「本仓库对 `ExecuteStreamingAsync` 零引用、没有驱动执行的测试宿主」。这句**不准确**：

- `AgentExecutionService.ExecuteAsync`（缓冲路径）与 `ExecuteStreamAsync`（流式）都是可测入口；
- `AgentExecutionWakeupActiveTaskPreservationTests` 早已**自己装配 `AgentExecutionService` 并驱动
  `ExecuteAsync` 跑到终态**，还带一个支持 **tool call** 的脚本化 LLM；
- `TaskE2EHarness` 也装配了同一个服务（`ScriptedLlmClient` 是 public）。

准确的说法是：**缺的是面向压缩叙事的串联用例**，而不是缺宿主。本提交把它补上了。

## 2. 新增用例（真实 Turn，`ExecuteAsync` 驱动）

### 2.1 主用例：软延期 → 增长越界 → 逐轮硬保护 → 落库

装配：内存 SQLite（36 条消息，**首条为 system**）+ `ContextUsageSnapshotStore` +
`ContextCompactionService` + 支持 tool call 的脚本化 LLM；`MaxContextTokens=30_000`、
`MaxOutputTokens=1_000` ⇒ 有效上限 27,976。

剧本：第 0 轮返回 `CONTINUE` + `task_update`（正文 44,000 字符）→ 第 1 轮返回 `DONE`。

断言（全部通过）：

| 断言 | 含义 |
|---|---|
| 前提自检：第 0 轮 `22,381 ≤ used ≤ 27,976` | 真正落在「已过软触发、仍在限内」的定义域（防止分词器/配置漂移让用例失去意义） |
| **摘要调用恰好 1 次** | 第 0 轮软维护**只延期、不调模型**；越界后**逐轮硬保护**触发一次同步压缩 |
| 内存库出现 `compact_summary` 行且 `Source=warm_prefix_checkpoint` | F2 **真的落库**，不是只改内存 |
| 被覆盖行逐行 `CompactedBy == 摘要行 id` | 覆盖标注精确到行 |
| `Session.CompactionGeneration == 1` | 持久代际推进 |
| 覆盖清单存在且 `Generator=warm_prefix_checkpoint` | 与摘要/打标同事务 |

### 2.2 对照用例：软延期的第 0 轮若无增长 ⇒ 零落库

同一个 Turn 形态但不越界（第 0 轮即 `DONE`）：历史未被压缩 ⇒ 不写摘要行、不打标、代际不变。

## 3. E2E 揭示的两条真实前置（写进用例注释，避免后人重踩）

1. **warm-prefix 候选要求 durable history 以 system 开头**：`TryCreatePlan` 里
   `leadingSystemCount == 0` 就 `return false` —— 而且这条路径**不打任何日志**，
   表现只是「压缩没发生、只剩请求副本裁剪」。用例最初正是这样失败的：种子历史首条是 user ⇒
   `Prepare` 在 round 2/3 反复 `Trimmed outbound history removed=10`，却没有一次压缩。
   生产环境由 Turn 内装配的 system prompt 提供该前导消息。
2. **水合会过滤 DB 里的 system 行**（system prompt 由上下文管线在 Turn 内装配）。因此
   「从库里种一条 system 行」并不能让水合后的历史以 system 开头 —— 用例改为水合后显式补一条
   前导 system（它**不在被替换跨度内**，不影响跨度身份解析）。

另外记录一条度量事实：重复单字符（`aaaa…`）的 token 压缩率极高（实测约 **7.7 字符/token**），
按字符数估 token 会严重失准；用例改用词表拼接（≈4~5 字符/token）并**自检前提**而不是硬编码断言。
