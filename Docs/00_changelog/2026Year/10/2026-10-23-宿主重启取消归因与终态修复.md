# 宿主重启取消归因与终态修复

现场 Turn `82da15383b7648fb9d817566d1e97891`、run `44df268c9f8b4b97906fafb8a1bf853e`：用户在部署待办之后发送 `approve`，Agent 于 16:48:40 调用 `bootstrap_reboot`，16:48:42 写入 `turn.cancelled`，不存在 CancelRequested 控制消息。部署结果记录 16:49:25 成功重启 Core。飞书格式化器因取消附带 errorCode，先进入失败分支，输出了错误的配置检查建议。

Desktop/Core 后续于 16:50:37 退出。Windows AppX 同秒以 `ForceTargetApplicationShutdownOption` 更新 Codex；没有发现对应 Pudding 崩溃记录。它是独立于成功 Core 重启的外部退出线索，尚无直接证据确认 Desktop 的终止来源。已按用户要求在 17:06 启动 Desktop（PID 29612），由其拉起 Core（PID 68884），状态 Ready。

改动：

- `ExecutionRunCoordinator.cs`：Runtime 返回取消/完成终态帧、抛取消异常或直接结束流后，宿主停止均走恢复路径；刷出已有输出，不提交终态，释放租约并记录带 run/turn/command 的 `reason=host_shutdown`。真正取消不重新入队。
- `ConversationTerminalMessageFormatter.cs`：Cancelled 优先于 errorCode/errorMessage 判失败；保留部分回复并明确标记停止，避免误报失败、完成或“未生成回复”。
- 补充相应测试、平台代码地图与[诊断手册](../../../08_how_debuge/14-案例-调度与Token内核.md)。

验证：Platform 定向测试 31/31 通过，包含真实内存 SQLite 下的三行状态一致性、已生成输出保留、原 command/turn 重新领取，以及真实取消不重放；覆盖 4 种宿主停机流结尾形态和 4 种取消回信正文形态。测试输出在 `temp/test-out/cancellation/cancellation.trx`，日志在 `temp/cancellation-tests.log`。现场只读记录留在 `temp/cancellation-incident.json` 和 `temp/cancellation-desktop-appx-events.json`，不入库。

未完成：待干净 Core 构建部署。此次未重写历史取消终态、未重新发送飞书消息、未重放旧部署命令；Desktop 外部退出因果仍有证据缺口。
