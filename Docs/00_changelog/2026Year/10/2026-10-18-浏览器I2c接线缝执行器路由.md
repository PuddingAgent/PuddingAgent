# 2026-10-18 I2-c 接线缝：派发器执行器路由

## 改动

按 I2-c 决议 D1/D2 在派发器建立**可替换接线缝**（Shell 组合根后续注入真实执行器路由，WpfArchive 不直接依赖执行器实现）：

- `BrowserCommandExecutorRoute` 委托：`(command, ct) → BrowserBridgeCommandResult?`
  - 非 null = 已由执行器路由处理（结果必须真实反映执行事实）；
  - null = 不在执行器覆盖面内，回退 `IBrowserCommandHandler`（迁移期）；
  - 抛异常 = 结果未知，**不得**静默回退（防双执行/绕过门禁）。
- `BrowserBridgeCommandDispatcher.SetExecutorRoute(...)` / `HasExecutorRoute`；
- `DispatchCoreAsync` 在会话准入 + 复检之后优先尝试路由；路由失败结果不触发 handler 回退。
- 测试 3 条：路由优先且 handler 0 调用；路由返回 null 时回退 handler；路由抛异常时返回失败且 handler 0 调用（不双执行）。

## 验证

- `dotnet test Tests/PuddingDesktop.Tests` ⇒ **373/373 通过**（新增 3 条 + 既有全量）；
- 全量 CLI、产品与模型均未运行；派发器默认未设置路由，生产行为不变（仍走 controller）。

## 未完成与影响

- **Shell 侧真实路由实现**未做：需构造 `DesktopCallContext`（含 `SessionPermitMarker` 与从 `command.Caller` 映射的 `BrowserCallerIdentity`）、调用工作区执行器、用 `BrowserBridgeCommandAdapter`/`BrowserBridgeResultAdapter` 做请求/结果双向映射，并把能力错误映射为稳定 Bridge 错误码；
- 路由覆盖面先限定在已有结果反投影的命令（context.list/getInfo、page.list、page.getInfo）；其余命令待结果适配完成后加入；
- controller 收缩与删除旧执行路径未做；
- 回滚 = revert 本提交（新增委托/字段/测试，无生产行为变化）。
