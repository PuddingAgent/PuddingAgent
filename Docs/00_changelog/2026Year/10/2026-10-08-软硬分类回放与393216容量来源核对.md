# 2026-10-08 软/硬分类回放与 393,216 容量来源核对（更正事故样本结论）

> 范围：只读复核 + `Source/PuddingRuntimeTests/Services/LlmRequestBudgetGuardTests.cs` 新增回放用例 + 更正 [上一批 changelog](2026-10-08-软压缩移出主请求关键路径与压缩生命周期归因.md)

## 1. 结论先行

1. **原结论作废**：上一批 changelog 与提交信息里「两条样本的压缩输入 193K/197K，远低于约 606K 硬上限」是**量纲错误**。193K/197K 是**摘要请求**的 Provider 实测输入；判据输入是校准后的 `InitialUsedTokens`。
2. **回放结果**：第一条（583,691）判**软 → 延期**；第二条（625,824）判**硬 → 仍同步保护**。「两条都能省掉前置压缩」不成立。
3. **`393,216` 结案**：它是资源池模型 `deepseek-flash` 的 `maxOutputTokens`（384K 精确值），是当前唯一可用的输出预算；算式 `1,000,000 − 393,216 − 1,024 = 605,760` 与日志硬上限完全一致。
4. **新增两个必须修的问题**：压缩请求的持久归因指向**压缩后**的形状（污染校准样本，F1/T3）；`warmPrefixCompactionAttempted` 是 Turn 级一次性标记，会让**硬保护在同一 Turn 后续轮次失效**（F3/T5）。

## 4. `393,216` 来源核对（原「未完成」项结案）

`393,216` **不是**误解析的能力上限，也不是 Agent 级请求预算：它是**资源池里 `deepseek-flash` 模型的 `maxOutputTokens`**（DeepSeek API 文档 384K 的精确值），而 Agent 级 `maxReplyTokens` 已废弃，因此该能力上限就是当前唯一喂给有效输入公式的输出预算。

- `1,000,000 − 393,216 − 1,024 = 605,760` —— 与日志 `inputLimit=` 完全一致。
- `1,000,000 − 393,216 = 606,784` —— 与修复前 `healthCheck effective=` 完全一致（缺 1,024 安全余量），正是诊断 §4.4 指出、上一批已统一的口径分裂。

⇒ 方案 §2.6 应改写为**容量策略取舍**而非解析缺陷：当前把模型 384K 的全量输出能力当作「预留输出」，占掉 1M 窗口的 **39.3%** 输入容量。是否改成「按实际 Agent 请求预算预留、并为推理/续轮留足空间」需要容量算术独立成组件（T2）后带回归门禁另行决策；**本轮不改**，也不下调到固定值。

## 5. 新增发现

### 5.1 压缩请求的持久归因指向**压缩后**的形状（F1 缺陷 → T3 必修）

DB `TokenUsageEvents` 两条 `agent_compaction_llm` 记录的形状估算（`MessageTokens + ToolDefinitionTokens`）为 **176,873** 与 **233,331**：

- 它们 ÷ 1.845 = 326,330 / 430,450，与同日志**压缩后**的 `EstimatedRetainedSnapshot.UsedTokens`（326,392 / 430,576）在 0.02% 内吻合；
- 与判据输入（583,691 / 625,824）相差 3.3× / 2.7×，且两者隐含的校准系数（3.30 / 2.68）**互相不一致**，也与会话全局唯一的 1.845 矛盾。

⇒ 压缩请求的「冻结请求上下文」捕获的是**历史已被 checkpoint 替换之后**的快照。后果：

1. 摘要请求的 `RecordProviderUsage` 用 193,218 去比一个错误的 raw（176,873），观测比 1.0925 —— 校准样本被污染（本次因取 max 未上升而无可见危害，机制是错的）；
2. 现有持久字段**不能**当作「该请求的 raw estimate」使用，这正是方案 §2.1/§6.3 要求分离 `currentPreparedRequest` / `lastMeasuredRequest` 并按 invocation/attempt 配对的原因。

### 5.2 Turn 级一次封顶会让**硬保护**在同一 Turn 后续轮次失效（F3 缺陷 → T5 必修）

第一条样本的 Turn 内，出站估算再次越过硬上限、退回请求副本裁剪：

| 时刻 | round | removed | 裁剪后 estimated | raw | 上限 |
|---|---|---|---|---|---|
| 22:49:18.485 | 34 | 1 | 605,649 | 328,204 | 605,760 |
| 22:49:25.773 | 35 | 76 | 422,669 | 229,046 | 605,760 |

compaction 在第 1 轮把 583,691 压到 326,392，买到约 33 轮余量。**按新判据延期后**，第 1 轮只比上限低 22,069，Turn 内工具结果增长会更早越过上限；而 `warmPrefixCompactionAttempted` 是 **Turn 级一次性**标记，后续轮次不再评估 ⇒ 只能靠请求副本裁剪，甚至当不可裁剪地板（system + 工具 schema + 受保护尾部）本身超限时抛 `LlmInputBudgetExceededException`。

⇒ T5 必须把**硬保护**从 Turn 级一次封顶改为**逐轮重新评估**（软维护仍保持候选级准入与去重），并补「第一轮软维护被延期、后续工具结果越过硬阈值仍须硬保护」的用例。否则本次延期修复等于用「更早、更多的请求副本裁剪」换 20.8 秒。

### 5.3 普通压缩仍在终态之前、且仍占前台租约（T5 必修）

源码核对（2026-10-08）确认上一批的表述有误 —— 「整理交给 canonical 终态提交后的持久压缩路径」**不成立**：

| 位置 | 行号 | 与终态的关系 |
|---|---|---|
| `Source/PuddingRuntime/Services/AgentExecution/AgentExecutionService.Streaming.cs` | `TrimHistoryAsync` = **1790** | `MarkCompleted()` = 1882、`done` 帧 = 1895 / `Append` = 1929 / `yield return` = 1936 |
| `Source/PuddingRuntime/Services/AgentExecution/AgentExecutionService.Buffered.cs` | `TrimHistoryAsync` = **2195** | 同样在其终态之前 |
| `Source/PuddingRuntime/Services/Messaging/AgentExecutionAdmissionCoordinator.cs` | `AcquireForeground`（第 26 行） | 前台租约按**整个 Turn**持有 |

⇒ 「延期 + 终态后整理」当前只实现了一半：软维护的**摘要生成**确实不再阻塞第 0 轮主请求；但被延期的整理落在 `done` 之前，且仍在 Turn 的前台租约内，因此仍可能推迟**回复完成**与**下一条消息的准入**。T5 需要把可选维护调度到 canonical 终态提交 + 前台租约释放之后，并保持用户优先的抢占与取消语义。
