# 2026-10-07 · Stage 4-a：终态投影与「复制现场」导出（后端）

## 背景 / 动机

用户明确要求：**界面只显示一眼能懂的标题与大概原因，同时要有「复制」功能把准确、全面的现场交出来**
（含日期、`traceId`、`errorId`），以便在茫茫日志里定位。叶子组件已备好呈现目录与复制载荷渲染，
但终态链路还没接上——界面仍然只回显 `LLM 调用失败: Error while copying content to a stream.`。

## 改动

| 文件 | 内容 |
|---|---|
| `Source/PuddingRuntime/Services/Diagnostics/TerminalDiagnosticExport.cs`（新，internal） | 投影与导出的**可单测纯投影**：异常 + 现场 + 身份/轮次 → ①界面呈现（标题/大概原因/建议动作/严重度/可重试）；②复制载荷（`ReportText` 人读 / `ReportJson` 机器读 / `EvidenceJson`）；③事故视图（复用 `IncidentProjector`）。此前投影逻辑藏在 `AgentExecutionService` 的私有嵌套 DTO 里，**无法构造就无法单测** |
| `LlmFailureDiagnostics.Attach/TryGet` | 因果结论随异常穿过边界（`Exception.Data`）。不新造异常类型：终态判定要读 `HttpRequestException.StatusCode` 与 `VisionPipelineException.Code`，包装会打断既有语义；`throw;` 不丢 |
| `DirectLlmClient` | 在唯一出口 `RecordActivityAsync` 挂载因果结论（覆盖所有失败/重试路径）；看门狗空闲超时抛出的**新** `TimeoutException` 也显式带上结论，避免上层丢失阶段事实 |
| `AgentExecutionService` 终态 DTO | 新增 `CauseCode / CauseTitle / CauseShortCause / RemediationHint / Severity / Retryable / CausePhase / ReportVersion / EvidenceJson / ReportText / ReportJson` |
| 终态 markdown | 首行仍是 `## 请求失败`（前端既有子串识别不破），随后是**粗体标题 + 大概原因**；诊断信息块新增「因果码 / 失败阶段 / 可重试 / 处置建议」 |
| `AgentExecutionService.Streaming` `done` 帧 | 增扁平键 `causeCode / causeTitle / causeShortCause / remediationHint / retryable / causePhase / errorReportVersion / errorEvidence`（`error` 对象内含 `reportText` / `reportJson`） |

## 验证（实测）

```
dotnet test ...PuddingRuntimeTests --filter TerminalDiagnosticExportTests        → 3/3 通过
dotnet test ...PuddingRuntimeTests --filter (AgentExecution|LlmStream|TerminalDiagnostic|TurnExecutor)
                                                                                → 62/62 通过
dotnet test ...PuddingRuntimeTests            （全量）                          → 1946 个中 3 失败（见下，均与代码无关）
dotnet build Source\PuddingRuntime\...        → 0 错误
```

新门禁 `TerminalDiagnosticExportTests`：

1. **友善呈现 + 可复制载荷**：`transport.request_upload_reset`、阶段 `request_upload`、标题「模型服务连接中断」；
   标题与大概原因**不含** `Exception` / `Error while copying`；复制文本含 schema 版本、本地时间、`traceId`、`errorId`、
   因果码、「上传请求体」、`1048576`、`10054`、`logs/error/pudding-error*` 与 `session-timeline`；`ReportJson` 可解析且含
   `Schema/CauseCode/Evidence.phase/Attempts`。
2. **未挂载结论时**仍给出稳定码（用现场重新分类）。
3. **结论穿过 `throw;`**（`Exception.Data` 往返）。

### 全量套件的 3 个失败（已逐条归因，均非本刀引入）

| 失败 | 归因 | 证据 |
|---|---|---|
| `PuddingRuntime_MustNot_Reference_PuddingPlatform` · `PuddingRuntime_MustNot_Contain_UsingPuddingPlatform` | **我选的构建参数导致的假红** | 守卫测试用 `AppContext.BaseDirectory` 向上**固定 5 级**找 `Source/PuddingRuntime/PuddingRuntime.csproj`；我用 `--artifacts-path temp/build/...` 改变了输出层级。改用默认输出路径复跑：**2/2 通过** |
| `HostShellExecutor_WslMode_UsesWindowsWorkingDirectoryMapping` | 既有环境问题（本机 WSL 未配置） | 默认路径下同样失败；本刀未触碰 host shell 执行路径 |

⇒ 教训：仓库里存在**依赖固定输出层级**的测试，用 `--artifacts-path` 跑全量套件会产生假红；判读失败前先看它是否依赖路径层级。

## 未完成（Stage 4-b / 4-c）

- **前端**：错误卡按 `causeCode` 映射（未知码显示原码）+「复制诊断信息 / 下载 JSON」按钮（用 `error.reportText` / `error.reportJson`）；
  历史消息保留同一载荷。前端改动须递增 `package.json` 版本并重新构建部署 `wwwroot/admin`。
- **`providerId`**：终态 DTO 仍拿不到（需把 LLM 路由快照的 provider 传到终态构造点）——不猜、留空并已登记。
- **尝试明细**：复制载荷目前是「终态一次尝试」+ 证据（`attempt`/`dispatch_count` 在证据里）；完整多次尝试需把 DirectLlmClient 的每次尝试事实回传。
- **可索引列**：`cause_code/phase/attempt/request_bytes/turn_id` 仍在 `metadata_json`；`ChatAsync`（非流式）仍无作用域。
