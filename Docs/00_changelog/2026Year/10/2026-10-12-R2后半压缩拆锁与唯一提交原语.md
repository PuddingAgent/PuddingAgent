# 2026-10-12 R2（后半）：普通压缩拆锁与唯一提交原语

> 依据：[复核与验收判定](../14_reports/上下文治理实施复核与验收判定-2026-10-12.md) §3（R2，P1）
> 修改方案第 2/3 条。前半（调度与前后台准入接线）见
> [R2 前半](2026-10-12-R2前半维护接入前后台准入.md)。

## 1. 缺陷

- `CompactAsync` 从入口到写库**整段**持有 `CompactionCoordinator` 的 per-session 单飞锁，
  远端摘要生成也在锁内 ⇒ 下一 Turn 的水合/硬保护（同样要取这把锁）被排队 ——
  即使后台不持 `SessionExecutionGate`，等待仍会通过压缩锁转移给下一条消息。
- 写库是「先读 `session.CompactionGeneration` 再赋值 + 单次 `SaveChanges`」，
  非条件更新；生成期间若有别的提交推进代次，本次会把过期候选写进去。

## 2. 修复

### 2.1 生成阶段不持提交锁（复核 §3 方案 3）

`CompactAsync` 冻结阶段结束时**显式释放** `CompactionCoordinator` 租约，再做远端摘要生成；
生成结束后重新取锁进入提交阶段。`CompactionLease.DisposeAsync` 以 `Interlocked.Exchange`
实现释放**幂等**，因此方法退出时 `await using` 的再次释放无副作用（已核对实现）。

### 2.2 提交前重验（复核 §3 方案 2）

重新取锁后、写库前逐项重验，任一不符即**零写入**返回：

| 重验项 | 不符时的终态 |
|---|---|
| ① 代次（`TryGetCompactionGenerationAsync` 与冻结值比较） | `SkippedStaleCandidate` |
| ② revision（候选窗口指纹：代际 + MessageId + 正文 hash） | `SkippedStaleCandidate` |
| ③ 覆盖行仍未被覆盖（`CompactedBy IS NULL`） | `SkippedStaleCandidate` |
| ④ 后台压缩 + 已出现前台需求 | `SkippedForegroundDemand` |

`ContextCompactionOutcome` 新增 `SkippedStaleCandidate`、`SkippedForegroundDemand`
（无穷尽 switch，纯增量）。`ContextCompactionRequest` 新增 `IsBackground`（init 属性，纯增量）；
终态后维护链路 `TrimHistoryAsync(..., isBackground: true)` → `TryAutoCompactAsync` → 请求标记
已串通（Streaming/Buffered 的维护调用传 `isBackground: true`）。

### 2.3 唯一提交原语（复核 §3 方案 2 末句）

把「显式事务 + 先插摘要行与清单 + 条件推进代次 + 逐行条件覆盖标注 + 提交」抽成
`WriteCheckpointAtomicallyAsync(db, sessionId, compactionId, expectedGeneration, targetGeneration,
summaryMessage, manifestEntity, rows, ct)`：warm-prefix/hard-protection 与**普通压缩**共用它。
普通路径写库前先把将被覆盖的跟踪实体 `Detached`，避免 `SaveChanges` 用陈旧值回写
（覆盖标注由原语用原始 SQL 完成）。任一受影响行数不为 1 即整体回滚。

### 3.1 新增门禁（`ContextCompactionCommitRevalidationTests`）

1. **生成阶段不持压缩锁**：摘要生成被人工屏障卡住时，同 session 的
   `CompactionCoordinator.AcquireAsync` 必须在 2 秒内成功（否则下一条消息会被排队）；
   屏障释放后压缩仍 `Applied`。
2. **代次冲突零写入**：生成期间把 session 代次 0→1 ⇒ 结果 `SkippedStaleCandidate`，
   无摘要行、无覆盖标注、无覆盖清单，代次仍为 1（未被推到 2）。
3. **后台遇前台需求零写入**：`IsBackground = true` 且生成期间
   `ReserveSessionForeground` ⇒ `SkippedForegroundDemand`，库中零写入。
4. **对照**：无并发变化 ⇒ `Applied`，代次 1、摘要行 1（证明拒绝不是"一律拒绝"）。

### 3.2 环境失败与并行写入方

- `PuddingMemoryEngineTests` 3 个失败、`PuddingRuntimeTests` 4 个失败均与上批同名同因
  （ContextPipeline 环境依赖；终端/宿主 Shell 用例的 PATH 上 `python` 是 Windows Store 别名桩，
  exit 9009），与本批无因果。
- 施工期间遇到**他方并行 WIP**（浏览器委派契约）导致 Runtime 一度构建失败；
  等待其自洽后恢复正常，未触碰其文件。
