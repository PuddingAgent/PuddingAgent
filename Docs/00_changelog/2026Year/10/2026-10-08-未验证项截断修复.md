# 2026-10-08 交付链：修掉"未验证项被静默截断"

## 缺陷（真实，且正好踩在"绝不报告假事实"上）

维护巡检时注意到一个可疑的巧合：交付清单的 `knownUnverified` **连续很多轮都正好是 20 条**，
而我这些轮次里加了大量"真机未验证/无法自证"的记录。查代码：

```csharp
if (items.Count >= MaxItems)      // MaxItems = 20
{
    return items;                 // 提前返回 —— 没有任何"被截断"的标记
}
```

实测：用抽取器自己的标记统计，changelog 里有 **27 条**互不相同的未验证声明（宽口径行数 43）。
⇒ 清单一直报"20 条"，读者会以为"一共 20 条"。**这是报告缺陷，不是数据缺失。**

## 修法

| 层 | 改动 |
|---|---|
| 抽取器 | 新增 `KnownUnverifiedExtraction(Items, TotalDistinct)` 与 `ExtractDetailed(...)`；不再提前 return，而是**继续计数**、只把展示列表限到 20；`Extract(...)` 保持兼容（返回 `Items`） |
| 清单模型 | 新增**必填**整数 `knownUnverifiedTotal` + 派生属性 `KnownUnverifiedIsTruncated`；反序列化缺该字段即**显式失败**（`ReadInt32`） |
| 校验 | `knownUnverifiedTotal` 必须 ≥ 列出条数（否则两个字段自相矛盾） |
| 生成器 | 从 `ExtractDetailed` 取总数；人工补充的条目也计入总数 |
| 报告 | 标题与表格都写成"**显示 20 条 / 共 27 条（已截断）**"；未截断时写"（全部列出）" |

## 验证

| 项 | 结果 |
|---|---|
| `Pudding.DesktopServiceTests` | **321 / 321**（＋4：抽取器总数、真实语料确实超上限、报告截断措辞、校验拒绝总数偏小） |
| **端到端（真实全量链）** | **1543 / 0**；JSON `knownUnverifiedTotal=27`、列表 20 条；报告行：`| 未验证项 | **显示 20 条 / 共 27 条（已截断）** |` |
| 留痕清单 | [交付清单 truncation-124](../../../14_reports/2026-10-09-浏览器自动化交付清单-truncation124.md) |
| fail-closed 再次实战 | 第一次跑全量链时 Host 的已知 flake（handshake）失败 ⇒ **清单拒绝产出**；重跑通过后才产出 |

## 一次"险些误报"（诚实登记）

带了 `-RetryFailedSuites 1` 的那次运行日志里出现了 `--- retrying suites whose TRX shows failures`，
我一度以为**重试路径终于被实战验证**。核对 TRX 后发现：那次 Host 的 `failed="0"`（本来就通过），
重试块只是打印了表头、**内层循环一次都没进**（`continue` 生效）。
⇒ **重试的实际重跑与 `-retried` 改名路径仍未验证**（沿用 round-95/96 的登记）。
**教训**：`retrying…` 这种表头不能当"发生了重试"的证据；要看 TRX 计数与 `-retried` 文件是否存在。

## 诚实边界（诚实登记）

- **27 是当前语料的值**：会随日志增长；用例只断言"确实超过上限"，不断言具体数字。
- **仍非"全部未验证项"**：抽取器只认**保守词表**里的明确说法（"宁可少提取"），所以 27 条也不是全集 ⇒
  清单的语义是"自动提取到的、有界的"，这一点在报告里已用"已截断/人工可补"表述。
- **公开面有增量**：清单多一个必填字段（对**反序列化**是破坏性的：旧 JSON 缺该字段会显式失败）——
  这是刻意的 fail-closed，但确实要求任何外部消费方同步。
- **重试重跑路径仍未验证**（见上）。
- **未真机验证**；两项待决取舍未触碰。
