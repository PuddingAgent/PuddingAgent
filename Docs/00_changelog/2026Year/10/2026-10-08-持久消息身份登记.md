# 2026-10-08 持久消息身份登记（F2 持久化尾款的前置基础设施）

> 范围：`Source/PuddingRuntime/Services/ContextWindowManager.cs`、
> `Source/PuddingRuntimeTests/Services/DurableMessageIdentityTests.cs`（新增，7 例）
> 依据：[ADR-095](../../../07_architecture/109ADR-095会话上下文维护与首增量延迟治理ADR.md) D5（持久 checkpoint/代际是权威）、
> [修复方案](../../../12_features/首Token等待与上下文指示器修复方案-2026-10-07.md) §3（事务 checkpoint/generation）
> 前序：[F2 首批](2026-10-08-F2首批warm-prefix唯一应用边界与真实after.md)、[提交单飞租约](2026-10-08-warm-prefix接入压缩提交单飞租约.md)

## 1. 为什么先做这一步

F2 的持久化尾款（warm-prefix 的 checkpoint 与自动/手动压缩一样落库：summary 行 +
`CompactionCoverageManifest` + `MessageEntity.CompactedBy` + `Session.CompactionGeneration`，
全在一次 `SaveChangesAsync` 里）**卡在一个具体障碍上**：

- 覆盖标注必须精确到 `MessageEntity` 行，而内存历史 `List<ChatMessage>` **不携带持久消息 id**；
- 用「内容哈希 + 顺序」模糊对齐会**标错行**，而 `CompactedBy` 的语义是「这行已被摘要覆盖、
  不再参与水合」—— 标错等于**静默隐藏真实消息**；
- 给 `ChatMessage`（`record`）加字段不可接受：record 的值相等会把身份并入比较语义
  （现有 `SourceContentHash` 就是这样一个字段），影响既有去重/比较与全量回归。

⇒ 先建立**不改变 record 语义**的身份来源，持久化尾款才有安全的地基。

## 2. 改动

### 2.1 引用相等的旁路登记表

`ContextWindowManager` 新增 `_durableMessageIds`：`sessionId → (ChatMessage 对象 → MessageId)`，
内层用 `ReferenceEqualityComparer.Instance`。

- **登记点**：`BuildContextFromDbAsync` 的 DB 行投影（Streaming 水合与 `TrimHistoryAsync` 的
  合并路径都走它）。原 LINQ `Select` 改成 `foreach` 物化，逐条登记 `entity.MessageId`。
- **发布语义是整体替换**（`PublishDurableMessageIds`），与调用方随后的
  `history.Clear() + AddRange(...)` 一致；既保证语义镜像，也避免旧消息对象被永久引用而泄漏。
- **未登记 = 没有持久行**（本 Turn 新追加、尚未落库的消息），因此不可被覆盖。
- `InvalidateHistory` 一并丢弃登记（内存历史已被丢弃，登记不得继续引用旧对象）。
- 空表时移除该会话条目（不为空会话留垃圾）。

### 2.2 对外只暴露一个判定

```csharp
internal DurableSpanResolution ResolveDurableSpan(string sessionId, IReadOnlyList<ChatMessage> span)
```

返回 `AllResolved` / `MessageIds` / `UnresolvedCount`。**`AllResolved == false` 时调用方必须放弃
写 `CompactedBy`/覆盖清单**，不得只标注解析出来的那部分去「凑齐」—— 这是防静默隐藏的关键约束，
已写进类型注释。

## 3. 验证（本机真实执行）

| 命令 | 结果 |
|---|---|
| `dotnet build Source\PuddingRuntime\PuddingRuntime.csproj` | **exit 0**，0 错误 |
| `dotnet test … --filter "…DurableMessageIdentityTests"` | **exit 0**，失败 0 / 通过 **7** |
| 全量 `PuddingRuntimeTests` / `PuddingCoreTests` / `PuddingMemoryEngineTests` / `PuddingPlatformTests` | 见 §3.1 |

新增用例（`DurableMessageIdentityTests`）：

1. `HydratedMessages_ResolveToTheirDurableMessageIds`：库水合 3 条 ⇒ 解析出 `msg-1..3`。
2. `InTurnAppendedMessage_IsUnresolved_SoTheSpanMustNotBeMarked`：跨度里混入本 Turn 新追加消息 ⇒
   `AllResolved == false`、`UnresolvedCount == 1`（**这条就是防静默隐藏真实消息的回归**）。
3. `LookupIsByReference_NotByValueEquality`：`with { }` 生成的**同值不同引用**实例不得被当成同一行
   （先断言值相等成立，再断言解析失败）。
4. `DuplicateContents_ResolveToTheirOwnRows`：两条内容完全相同的消息各自解析到自己那一行。
5. `InvalidateHistory_DropsRegistrations`：失效后旧引用全部不可解析。
6. `Rehydration_ReplacesRegistrations`：重新水合的实例可解析、**旧实例随整体替换失效**（有界性）。
7. `EmptySpan_IsNotAllResolved`：空跨度不算「全部解析」，避免调用方写出空覆盖清单。

## 4. 未完成（下一步）

本提交**只交付身份地基，没有写库**。后续仍需要：

1. 在 `ContextCompactionService` 一侧提供「用显式消息 id 集合提交 checkpoint」的入口，
   与现有 `CompactedBy` + 覆盖清单 + `Session.CompactionGeneration` **同一事务**写入；
2. warm-prefix 提交前用 `ResolveDurableSpan` 解析被替换跨度：`AllResolved == false` 时
   **降级为内存-only**（维持现有 `durableCheckpoint=false`）并记录原因，绝不部分标注；
3. 代际 CAS：把 `Plan.SourceGeneration`（现恒为 0）接到 `Session.CompactionGeneration`；
4. 重启恢复与事务失败回滚测试（可用现有 `ContextCompactionCommitRollbackTests` 的
   in-memory SQLite 模式）。
5. 交付状态仍为 **ready-for-external-deploy**；无真实模型调用、无部署、无浏览器证据。
