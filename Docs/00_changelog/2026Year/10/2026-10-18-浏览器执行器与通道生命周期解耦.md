# 2026-10-18 浏览器执行器与能力通道生命周期解耦（F1 前置）

## 目标与结论

按 [ADR-097](../../../07_architecture/111ADR-097Agent浏览器控制一期闭环与单一执行链ADR.md) D2 的第一条要求：浏览器执行部分必须能从能力通道生命周期解耦。本轮落在 `Pudding.DesktopService` 内部，**不改 Shell、不改 Bridge、不宣称 F1 已修复**。

同时修复审阅报告未列出的一个实际缺陷：能力通道释放会调用 `DesktopService.Close()` → `Authority.Close()`（不可重开），而 Core 每次重启都会停通道 ⇒ 一旦启用过通道，Bridge 路径的准入会被**永久关死**。现在共享权威的关闭权明确归浏览器工作区执行器，通道执行器只借用。

## 改动

- 新增 `Source/Pudding.DesktopService/DesktopBrowserExecutorComposition.cs`：Shell 可见的 `IDesktopBrowserExecutor`（`IDesktopCapabilityExecutor` + `Interaction`/`Close`/`DisposeAsync`）与工厂 `Create`/`CreateService`；构造只接收 `BrowserPageLifecycle` 与 UI 缝隙，`authority`/`ConnectionGeneration` 等 Automation 类型不出现在 Shell 调用面（延续 `BrowserTaskBindingComposition` 的 CS0012 规避方式）。
- `Source/Pudding.DesktopService/DesktopService.cs`：构造函数末位新增 `closesAuthorityOnDispose = true`；`Close()` 仅在该开关为真时关闭共享权威，其余行为（拒绝新调用、取消在途 UI 调用）不变。
- `Source/Pudding.DesktopService/DesktopCapabilityChannelComposition.cs`：改用上述工厂构造通道执行器并传 `closesAuthorityOnDispose: false`；所有权语义写入注释。
- `Source/Pudding.DesktopService/code_map.md`：新增文件条目，更新通道组合根语义。
- 测试：新增 `Source/Pudding.DesktopServiceTests/DesktopBrowserExecutorCompositionTests.cs`（4 条：复用 lifecycle 注册表/权威、无通道可构造、借用不关权威、拥有则关权威）；`DesktopCapabilityChannelCompositionTests` 新增 `DisposingTheChannel_DoesNotCloseTheSharedAuthority`。

## 验证

- `dotnet test Source/Pudding.DesktopServiceTests`（含新增用例）⇒ **402 通过 / 0 失败**（2 s）。
- 未运行 PuddingDesktop/PuddingAgent、未调用模型、未重跑链级清单；本轮是组件级证据。

## 未完成与影响

- **F1 仍未闭合**：把默认 Bridge 截图切到该执行器后，`DesktopService.ValidateAdmission` 仍要求旧 authority 的页级 grant，而默认 Bridge 路径没有 `browser.binding.apply` 签发者 ⇒ 会判 `Unauthorized`。正确修复在 I2：以新的会话权威（用户交页 + 可信所有者 + 写世代）替换浏览器页级准入，再把 Bridge 全动作统一入场。本轮没有为了让截图"看起来成功"而放宽断言或增加旁路。
- 执行器尚未被 Shell 构造/使用；`CapabilityExecutor` 仍返回通道服务。下一步（I2 前置）在工作区初始化时构造该执行器并把 `AttachBrowserTargets` 上移（见审阅报告与侦察记录），然后切换准入。
- 回滚 = revert 本提交；通道停止语义恢复为"关闭共享权威"，无配置/数据变更。
- 工作树存在他方并行 WIP；本提交只含上述 5 个文件。
