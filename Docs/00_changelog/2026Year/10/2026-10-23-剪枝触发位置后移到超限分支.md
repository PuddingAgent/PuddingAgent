# 2026-10-23 确定性剪枝的触发位置后移到「超限分支」

## 背景：先算账，再决定跑在哪

上一轮把去重键修好之后，剩下一个没回答的问题：剪枝**该在什么时候跑**。
用只读探针读 `pudding_platform.db` 的 `TokenUsageEvents`（本会话最近 200 条），反推单价：

| 指标 | 实测 |
|---|---|
| 平均 prompt | 87,159 tokens |
| 平均 cache hit | 82,468 tokens（86.3%） |
| 平均 cache miss | 4,691 tokens |
| 反推 miss 单价 | ≈ 0.1076 元/M |
| 反推 hit 单价 | ≈ 0.0400 元/M |
| 价差 | 0.0676 元/M |

剪枝的经济学是单向的：

- **收益**：省下 R tokens，按 hit 价计 ⇒ `R × hit`；
- **代价**：改写历史 ⇒ 整段 warm prefix 失效一次 ⇒ `prompt × (miss − hit)`。

⇒ 盈亏平衡点 `R* = prompt × (miss − hit) / hit` = 87,159 × 1.69 ≈ **147,000 tokens**。

而剪枝单条 bounded 预览最多省 `8192 − 2133 ≈ 6,059` 字符 ≈ **1,515 tokens**，差 **97 倍**。
结论：**在 cacheHit 高的常态轮次上，任何「为省 token 而改写历史」都是净亏**——这解释了为什么
S5 接入后日志里一条 `[LlmRequestBudgetGuard:DeterministicPrune]` 都没有，而且**这是正确行为**。

真正划算的时机只有一个：**本轮已经超限**。那时本来就要删消息 / 驱逐载荷，前缀必然作废，
剪枝是零增量成本的「先救一次」。

## 改动

`Source/PuddingRuntime/Services/LlmRequestBudgetGuard.cs`：

| 项 | 改前 | 改后 |
|---|---|---|
| 位置 | `CaptureLlmRequest` **之前**无条件尝试 | 首次 `CaptureLlmRequest` **之后**、`while` 删消息 **之前** |
| 条件 | `deterministicPruneEnabled` | `deterministicPruneEnabled && snapshot.UsedTokens > effectiveInputLimit` |
| 剪枝后 | —— | **重新** `CaptureLlmRequest`（否则后续按旧快照判断，会白删消息） |
| 日志 | 无 `limit` | 追加 `limit={Limit}`，便于在日志里直接看到触发边界 |
| XML 注释 | 「发请求前是否先跑一次」 | 「输入**已超限**时是否先跑一次」+ 经济账注释 |

顺序由此变为：**测量 → 超限？→ 剪枝（无损）→ 重测 → 删消息（有损）→ 驱逐载荷 → fail-closed**。
先用无损手段救，再动有损手段。

## 测试改动

`Source/PuddingRuntimeTests/Services/LlmRequestBudgetGuardDeterministicPruneTests.cs`：

- 原用例 `Prepare_PrunesDuplicatedToolPayloads_AndKeepsProtectedTailVerbatim` 断言「未超限也会剪」，
  与新语义相反 ⇒ 替换为 `Prepare_LeavesHistoryByteIdentical_WhenUnderLimit`：
  逐条 `Assert.AreSame`，并用 `logger.Information.Count == 0` 锁住「一条日志都不能有」。
- 新增 `Prepare_PrunesOnlyWhenOverLimit_AndBeforeDroppingMessages`：
  先用两个独立 `ContextUsageSnapshotStore` 量出剪枝前/后的真实用量，把 `workUnitInputCapacity`
  卡在两者中点 ⇒ 必然超限、但剪枝足够 ⇒ 断言 `RemovedMessageCount == 0`（一条都没删）
  且尾部逐字保留。这条断言直接锁住「剪枝发生在删消息之前」。

## 验证

- 绿：`dotnet test --filter FullyQualifiedName~LlmRequestBudgetGuard` → **失败 0 / 通过 39**。
- 变异取红（三份原始输出）：
  1. **M3** 条件退回 `if (deterministicPruneEnabled)`（即每轮都剪）→ **失败 1 / 通过 38**，
     红在 `Prepare_LeavesHistoryByteIdentical_WhenUnderLimit`：「未超限时第 3 条必须按引用原样返回」。
  2. **M4（无效尝试，记录在此）** 在 `working = …` 后加 `snapshot = snapshot;` —— 那是自赋值，
     不改变任何行为，测试仍全绿 38+1。**该变异设计失败，不是缺陷**，因此重做为 M4b。
  3. **M4b** 把剪枝后的重测改为 `snapshot = snapshot; _ = usageStore.CaptureLlmRequest(…)`
     （丢弃重测结果）→ **失败 1 / 通过 38**，红在 `RemovedMessageCount` 期望 0、实际 **5**
     —— 证明「剪枝后必须重测」这条断言真的有效。
  4. 复原（`SHA256=87E76299748706A5…`，与备份逐字节相同）→ **失败 0 / 通过 39**。

## 影响面与风险

- 未超限轮次：**完全不动历史**（元素按引用原样返回），warm prefix 与 0.86–0.99 的缓存命中不受影响。
- 超限轮次：先用剪枝救；救不动再走原来的删消息 / 驱逐 / fail-closed，行为向后兼容。
- `deterministicPruneEnabled: false` 仍逐字回到接入前行为（原用例保留并继续通过）。
- 生效条件：源码变更，**需重启 Core** 才是运行态事实（本轮未重启）。

## 后续（未做）

- 剪枝的「准入地板」`MinReclaimTokens=2000 / MinReclaimRatio=5%` 沿用原值：在超限分支里不再需要它
  承担经济判断（位置已经保证只在划算时跑），它现在只起「别为几百 token 折腾」的噪声过滤作用。
- 上游 `ToolResultContextPolicy` 的 `MaxInlineChars=8192` 与剪枝阈值 `8000` 仍然错配；
  但按上面的账，**降阈值本身不划算**，真正该考虑的是直接把 inline 上限调小（少发字节，不必改写历史），
  这属于另一个决策，未在本轮触碰。
