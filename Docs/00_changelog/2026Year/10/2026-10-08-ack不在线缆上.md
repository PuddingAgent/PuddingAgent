# 2026-10-08 重要发现：ack 不在线缆上

## 证据

| 事实 | 位置 |
|---|---|
| ack 类型存在 | `Contracts/Desktop/BrowserControlPlaneRequests.cs:12` |
| Desktop 会构造它 | `DesktopService.cs:401` / `:417` ⇒ `FromBindingAck(...)`（round-209） |
| **结果 oneof 没有它** | `desktop_capability.proto` 的 `oneof outcome`：`navigate`(10) … `context_closed`(26) + `error`(13)，**无 `binding_ack`** |
| 全仓提及 | 只在 Contracts / DesktopService / 新写的生产者与测试里；**线缆两侧编码解码都没有** |

⇒ Desktop 的 ack 回不到 Core ⇒ 生产上生产者必然拿到 no ack 并判失败。

## 修正此前的说法

此前反复说『Desktop 侧已完全就绪』；准确说法是：**Desktop 内部**（受理/子集/期限/ack 构造/级联释放）已就绪且有用例，**a c k 上不了线**。

## 修复步骤（下一轮，落点齐全）

1. **proto**：`oneof outcome` 加 `BindingAckOutcome binding_ack = 27;` 与 `message BindingAckOutcome { bool accepted = 1; string grant_id = 2; uint64 epoch = 3; string reason = 4; }`；
2. **三条冻结 wire 守卫一次改全**（round-212 教训）：`PayloadOneof_IsClosedWhitelist` 里 `OperationResult` 的 outcome 计数 **17 → 18**；`CommandAndResultFieldNumbers_AreFrozen` 的结果元组与 `OutcomeOneofCase` 名单；**先完整读该用例再改**；
3. **结果编码器**（Desktop→Core）与**结果解码器**各加一个分支；
4. **端到端用例**：用 `CapabilityBrokerTests` 的 `BrokerHarness`（假流有 `Push(DesktopFrame)` 与 `Sent`）—— 生产者 → `session.SendAsync` → 假 Desktop 回带 ack 的 `OperationResult` → 生产者如实还原；另加拒绝 ack 分支；
5. 之后才是**真实触发点**与**开闸门**（round-197 顺序）。
