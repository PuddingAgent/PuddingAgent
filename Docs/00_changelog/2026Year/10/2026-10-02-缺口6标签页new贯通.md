# 缺口 #6 完成：标签页 `new` 贯通（无需新 oneof）——`browser_tabs` 因此完全解锁

## 改动（跨侧协议变更，两侧同提交）

| 层 | 文件 | 改动 |
|---|---|---|
| 线缆 | `desktop_capability.proto` | `TabsCommand` 新增 `context_id = 4`、`url = 5`、`activate = 6`；动作走**既有** `action` 字符串字段（`"new"`）⇒ **不需要新的 payload oneof** |
| 契约 | `Contracts/Desktop/TabsContracts.cs` | `DesktopTabAction` 新增 `New` + 冻结线名 `"new"`；新增静态工厂 `BrowserTabsRequest.New(contextId, url, activate)`；`Target` 变**可空**、新增 `ContextId`/`Url`/`Activate` |
| Core→proto | `CapabilityBroker/WireMapping.cs` | target 可缺省（新建时）、写入 context/url/activate；**幂等键补上 context/url/activate** |
| proto→DTO | `DesktopConnection/Mapping.cs` | **先解析动作**：`new` 不要求 target、版本必须为 0、url 若给出必须是绝对地址、context 必填 |
| Desktop 侧 | `DesktopSurface.Browser/BrowserRuntimeDesktopSurface.cs` | `new` 分支：按 context 建页 → 可选导航 → 可选置前 → 重算剩余清单 → 用**新建页的事实**构造状态 |
| Bridge 侧 | `Host/BrowserBridge/BridgeBrowserCapabilitySurface.cs` | 同一套语义 |
| 测试 | 契约冻结线名 / 线缆字段号 / 适配器新增用例 | 覆盖 `new` 的建页、是否关闭、活动页与计数 |

## 设计取舍（写下来，因为它决定了改动面）

- **不让公开构造函数变形**：全仓库有 **17 处** `new BrowserTabsRequest(...)` 调用，`new` 这种"没有目标页"
  的形态用**静态工厂**表达，既有调用点一行不用改 ⇒ 编译期把影响面钉在"读 `Target` 的地方"。
- **`new` 是唯一允许不钉版本的标签页动作**，而且是**被校验的**：请求里有 `Target` 或带了已知版本
  就直接抛异常，不给"变更类必须钉版本"这条不变量开天窗。
- 线缆上 `new` 复用 `action` 字符串 ⇒ 与交互 `type`（缺口 #7）同一模式，省掉一次 oneof 变更。

## 过程教训

- 我用**全局字符串替换**把 `request.Target` 改成 `tabsTarget`，结果**溢出到了另一个方法**
  （交互里也有一句 `BuildPageState(request.Target, page)`）⇒ 编译立刻报"名称不存在"。
  ⇒ 批量替换**必须限定作用域**（按方法边界或带上下文锚点），改完立刻编译。
- 两阶段施工（契约+线缆 / 映射+实现）本轮奏效：每次都在阶段末尾编译，问题没有跨阶段堆积。
