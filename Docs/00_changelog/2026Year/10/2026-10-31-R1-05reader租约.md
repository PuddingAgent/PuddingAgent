# 2026-10-31 R1-05 reader 生命周期：查询期间不再被缓存失效打断

## 缺陷（可控复现，非静态推测）

`SearchAsync` 从缓存取到 `IndexSearcher` 后直接查询，而 `InvalidateScope` / `GetOrRefreshSearcher` 会**立即释放**同一个 reader：

- `InvalidateScope`：`_readerCache.TryRemove(...)` 后 `reader.Dispose()`
- `GetOrRefreshSearcher`：刷新分支里 `existingReader.Dispose()`

两者都会把「正在被查询的 reader」直接释放。实测错误：

```
Search failed: this IndexReader is disposed. Object name: 'Lucene.Net.Index.StandardDirectoryReader'.
```

## 改动

- `Source/PuddingFullTextIndex/Infrastructure/Search/LuceneSearchEngine.cs`：
  - 新增测试接缝 `internal Action<string>? AfterSearcherAcquired`（生产为 null、零开销），把「拿到 searcher → 真正查询」这个时序固定下来，用来确定性模拟失效。
  - `SearchAsync`：取得 searcher 后 **先** `lease = searcher.IndexReader; lease.IncRef();`，再走接缝与查询；外层 `try` 增加 `finally { lease?.DecRef(); }`。
  - `InvalidateScope` 与刷新分支的 `Dispose()` 改为 `DecRef()`：只释放「缓存持有的那一份引用」，正在查询的调用方自己 IncRef 过，计数不归零就不会真正释放。
- `Source/PuddingFullTextIndexTests/ReaderLifecycleTests.cs`（新）：2 条门禁测试。

## 证据（实测）

- **修复前**：`InvalidateDuringQuery_DoesNotBreakTheInFlightSearch` **红**，错误正是 `this IndexReader is disposed`；正对照 `QueryAfterInvalidate_ReturnsFreshResults` 绿（失效后重新查询本来就没问题）。
- **变异取红**：注释掉 `lease.IncRef()` ⇒ **恰好 1 红**（该条），正对照仍绿。
- **还原**：按备份字节写回，SHA-256 位级一致 ⇒ 2/2 复绿。
- **全量回归**：`PuddingFullTextIndexTests` **329/329 通过**。

## 一处我自己先写错、被测试抓出来的时序错误

IncRef 最初放在接缝**之后**——即「先让失效把 reader 释放掉，再去取租约」，测试照样红且报同样的 disposed 错误。把 IncRef 前移到接缝之前才真正成立。这条不是靠读代码想出来的，是测试逼出来的。

## 未做 / 边界

- 未做多 scope 驱逐（eviction）与取消场景的独立回归；`DecRef` 的泄漏路径（异常时）由 `finally` 覆盖，但**没有**用文件句柄计数验证「不泄漏」。
- Windows 文件回收（未释放句柄阻止目录 Move/Delete）未单独验证。
