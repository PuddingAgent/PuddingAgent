# 2026-10-08 B1：补上对账表里风险最高的两条缺口

## 为什么先补这两条

入口对账表里"仅正向"的四个入口中，这两个**最可能绕过前几轮的修复**：

- 若 `RevokeAllGrants` 漏掉派生授权 ⇒ 第 110 轮的级联修复可以被"用另一个入口撤销"绕过；
- 若 `RevokeExecutionScope` 只收窄父任务授权 ⇒ 子代理仍能写 ⇒ 用户"收回执行权"的操作形同虚设。

## 观察方法（都是公开 API，不依赖内部字段）

难点是"怎么知道在途租约真的释放了"：清空/收窄之后**没人**有授权，无法用一次成功准入来观察。
本轮的技巧是：**事后重新签发一条授权，再看新写入者是否被 `PageBusy` 挡住** —— 挡住说明旧租约还在。

## 新增两条用例

| 用例 | 断言 |
|---|---|
| `RevokeAllGrantsClearsDerivedGrantsAndReleasesTheInFlightLease` | 父/子/孙三条授权 + 管理授权 + 子代理在途写租约；清空后 `ActiveGrants`/`ActiveManagementGrants` **空**、子代理不能再写；**重新签发后新写入者立刻可写**（旧租约确实释放） |
| `RevokeExecutionScopeNarrowsSubAgentGrantsAndReleasesTheirInFlightLease` | 撤执行权后：子代理**写被拒**、**读仍可**（保留只读）；重新签发后新写入者立刻可写（在途租约释放） |

## 验证

| 项 | 结果 |
|---|---|
| `PuddingBrowser.AutomationTests` | **343 / 343**（＋2） |
| **取红实测 ①** | `RevokeAllGrants` 去掉 `ReleaseLeaseInternal()` ⇒ 相应用例**变红** |
| **取红实测 ②** | `RevokeExecutionScope` 去掉 `ReleaseLeaseIfUnauthorized()` ⇒ 相应用例**变红** |
| 结论 | **两处产品行为本来就正确**（本轮**无产品代码改动**，补的是证据） |
| 对账表 | 两条判定 仅正向 → **已核对并取红**；缺口清单 #2/#3 标记"已补"（#2 的"管理授权是否受影响"仍留） |

## 诚实边界（诚实登记）

- **对账表里的删除线只在缺口清单里**：表行本身是就地改写（保留唯一事实），历史判断变化由本文与表内标记共同体现。
- **仍有 3 条缺口未补**：`RevokeManagementGrant` 的"不释放页面租约"语义、`ActiveManagementGrants` 的过期投影、`Capture` 的"读取无副作用"；**并发仍然全未验证**（最大未覆盖面）。
- **`RevokeExecutionScope` 对管理授权的影响仍未验证**（缺口 #2 的半条）。
- **未真机验证**；仍属组件层结论。
