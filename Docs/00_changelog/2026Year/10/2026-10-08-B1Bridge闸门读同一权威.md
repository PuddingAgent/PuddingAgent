# 2026-10-08 B1 收尾：Bridge 闸门读同一权威，控制权事实源覆盖默认路径

## 目标 / 背景

审计结论 #1 的原始形态是：进程内有三份互不相通的接管表示，而 **Bridge 路径**（默认路径）
的命令闸门读的是它**自己的字段** —— 于是用户在 UI 上点「人工接管」对 Agent 没有约束力。
第 3、9、11 段分别做了「唯一写入点」「能力通道侧状态收敛为投影」「统一生命周期端口」，
但**默认路径上的那份私有字段一直没动**；而且权威实例此前只在"能力通道启用"时才构造，
默认配置下根本不存在。本轮把它补上。

## 改动

| 文件 | 改动 |
|---|---|
| `Source/Pudding.DesktopService/BrowserPageLifecycle.cs` | 新增**控制面门面**：`IsPaused`/`IsUserTakeover`/`SetPaused`/`SetUserTakeover` —— 读写同一个权威实例。存在的理由：直接暴露 `Authority` 会迫使每个消费方（Bridge 闸门、窗口控制器）都引用 Automation 组件，而 Shell 本不该关心授权/租约/世代这些内部模型 |
| `Source/PuddingDesktop.WpfArchive/Browser/BrowserBridgeCommandDispatcher.cs` | **删掉自己的 `_paused`/`_userTakeover` 字段**：构造时只接受 `BrowserPageLifecycle`，读快照、写同一事实源。Bridge 命令的准入判定改用属性（`IsPaused`/`IsUserTakeover`），行为不变但来源变了 |
| `Source/PuddingDesktop.WpfArchive/Hosting/DesktopApplicationCoordinator.cs` | 组合根构造**一个** `BrowserPageLifecycle`（`default` + 进程实例 ID），交给 `BridgeDispatcher`，并暴露为 `BrowserAutomation` |
| `Source/PuddingDesktop/Hosting/DesktopApplicationCoordinator.cs` | 同上（WinUI 侧是独立文件，不链接归档版） |
| `Source/PuddingDesktop/Hosting/DesktopApplicationCoordinator.Capability.cs` | 能力通道路径**复用**协调器的那一个端口，不再自己 `Create` |
| `Source/PuddingDesktop.WpfArchive/PuddingDesktop.WpfArchive.csproj` | 新增对 `Pudding.DesktopService` 的引用（控制权/生命周期事实源） |

由此，"同一个实例"覆盖了两条传输：Bridge 闸门（默认）与能力通道准入（可选）读写同一个权威，
Shell 的接管开关经闸门集合推给两者 —— 结论 #1 的**读端**也闭合了。

## 验证

| 套件 | 结果 |
|---|---|
| `PuddingDesktop.Tests` | **305 / 305**（原 301 ＋ 4） |
| `Pudding.DesktopServiceTests` · `DesktopSurface.BrowserTests` · `PuddingHost.Tests` | 215 / 215 · 58 / 58 · 252 / 252 |
| `build` `PuddingDesktop.WpfArchive` · `PuddingDesktop`（WinUI） | 0 错误 |

新增门禁：

- `BridgeDispatcher_ReadsTheSharedAuthority_NotItsOwnFlag`：**不经调度器**直接写端口（Shell 的接管开关
  与生命周期清理点都会这么做），调度器必须立刻反映；
- `BridgeDispatcher_RejectsCommands_WhenTheSharedAuthorityIsTakenOver`：接管后 Bridge 命令
  以 `BrowserUserTakeover` 被拒（默认路径上的真实约束力）；
- `BridgeDispatcher_WritesTheSharedAuthority`：调度器的写落到同一实例，且"解除暂停不连带解除接管"；
- `Constructor_RejectsMissingLifecyclePort`：没有事实源就构造失败（fail closed）。

**取红实测**：把 `IsUserTakeover => _lifecycle.IsUserTakeover` 改成 `=> false`（退回"自己的字段"语义）⇒
**7 条**测试恰好变红（2 条新增 + 5 条既有的接管闸门用例），其余 298 条仍绿；复原后 305/305 复绿。

## 已知边界（诚实登记）

- **权威的 desktop id 用 `"default"`**：它与能力通道设置里的 `DesktopId` 未打通（后者缺省也是
  `default`）。授权绑定用到它，等 grant 真正签发时必须统一来源。
- **`Admit`/写租约仍未接入 Bridge 路径**：本轮只把**控制面**（暂停/接管）收敛到同一事实源；
  Bridge 命令级的授权判定（grant 范围、写租约互斥）需要可信调用方身份（`BrowserBridgeCommandOrigin`
  已有 workspace/agent/session/run/toolCall，但没有子代理父子标记），属后续切片。
- **WinUI 组合根的这几行没有自动化测试**：`Source/PuddingDesktop` 不被任何测试工程引用
  （内部 Agent 无法验收 Desktop 生命周期，AGENTS.md 已写明）。因此"两处都构造同一个端口"只有
  构建保证 + 归档侧（WpfArchive，有测试）的同源实现作对照。
- 创建侧（context/tab 新建）仍未走统一端口。

## 影响与回滚

- **行为变化**：`BrowserBridgeCommandDispatcher` 构造函数新增必填参数（测试统一走
  `BrowserTestState.CreateDispatcher()`）；控制状态写入会**推进控制世代**（原先只是改一个 bool），
  因此"接管瞬间的在途租约"会被撤销 —— 这正是设计要的语义。
- 归档 WPF 项目新增对 `Pudding.DesktopService` 的引用；WinUI 侧无需新增引用（走端口门面）。
- 回滚：还原上表 6 个文件与 4 个测试文件及 code_map。
