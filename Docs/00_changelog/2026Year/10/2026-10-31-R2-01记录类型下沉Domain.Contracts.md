# R2-01 记录类型下沉 PuddingDomain.Contracts

> 施工计划 R2-A 前置：`PuddingRetrieval`（实现）要独立，必须先让它的窄端口
> `IRetrievalSymbolSource` 能只依赖「共享值类型」而不依赖存储组件。

## 1. 为什么要做

`RetrievalPortV1` 内部已有窄端口 `IRetrievalSymbolSource`，签名用到 5 个 CodeIndex 记录类型
（`CodeProjectRecord` / `CodeSymbolRecord` / `CodeSymbolSearchRequest` / `CodeFileRecord` / `CodeRelationRecord`）。
这些类型留在 `PuddingCodeIndex.Contracts` 里，`PuddingRetrieval` 一旦独立就必须反向依赖存储组件 ——
正是 R2-01 依赖禁令要禁止的方向。

## 2. 改动

5 个文件、13 个类型从 `Source/PuddingCodeIndex/Contracts/` 移到 `Source/PuddingDomain.Contracts/`：

| 文件 | 类型 |
|---|---|
| `CodeFileRecord.cs` | `CodeFileRecord` |
| `CodeSymbolContracts.cs` | `CodeSymbolRecord` / `CodeSymbolMatchTarget` / `CodeSymbolSearchRequest` / `CodeSymbolDetail` |
| `CodeProjectContracts.cs` | `CodeProjectStatus` / `CodeProjectRecord` / `CodeProjectAddRequest` / `CodeProjectRemoveRequest` |
| `CodeRelationContracts.cs` | `CodeRelationRecord` |
| `CodeIndexScopeContracts.cs` | `ScopeSource` / `ScopeState` / `CodeIndexScope` |

**命名空间一律保持 `PuddingCodeIndex.Contracts` 不变** —— 与枚举下沉同一手法：只换程序集，
调用方 `using` 一行都不用改，也不存在「漏改某个文件」的可能。

`CodeIndexScopeContracts.cs` 是编译错误逼出来的：初始只按 `using` 判断依赖干净，
但该文件在同命名空间内引用了 `ScopeSource` / `ScopeState`（无需 using）——
**「零 using」不等于「零依赖」**。

## 4. 未做

- **命名空间整理**：13 个类型仍住在 `PuddingCodeIndex.Contracts` 下，程序集名与命名空间不一致。
  这是刻意的过渡状态，留作单独一步。
- **`PuddingRetrieval` 实现组件**：本轮只解决了它的前置（记录类型可被独立引用），未创建。
- **`Retrieval.Adapters`**：未创建。
- `CodeSymbolSearchRequest` 等记录类型**没有独立测试**（仅有枚举的数值稳定性测试）。
  下沉是程序集移动、无行为变化，故未新增断言；若后续要防「字段被误删」，需要另加。

## 5. 下一步

1. 建 `PuddingRetrieval`（S1）：把 `IRetrievalSymbolSource` / `IRetrievalTextSource` +
   编排逻辑（意图路由、去重、排序、预算、空原因裁决）从 `PuddingCodeIndex/Services/Retrieval/`
   搬入，依赖只允许 `Retrieval.Contracts` + `Domain.Contracts`。
2. 建 `PuddingRetrieval.Adapters`（S1）：把 `ICodeIndexStore` 适配成窄端口（现有
   `CodeIndexStoreSymbolSource` 是它的雏形）。
3. 两者过 S1–S4 后才进 slnx / DI（组件化交付规程：先独立测试，再接入宿主）。
