# 2026-10-08 B7 交付留痕自动化

## 目标 / 背景

上一轮的交付报告是我**手工誊写**的 —— 手工誊写必然漏项，而且我确实漏了：手写时把相对路径多写了一级，
产出了两条死链（门禁在下一轮才抓到）。本轮把报告生成自动化，并更正那两处错误。

## 改动

| 文件 | 改动 |
|---|---|
| `Source/Pudding.DesktopService/DeliveryManifestReport.cs`（新增） | 纯函数渲染：标准 12 项 Front Matter + 事实表 + 检查表（来自 TRX）+ 产物 + **逐字列出全部未验证项** + 外部步骤清单 + 「内部不能判定生命周期」的明确声明 |
| `Pudding.DeliveryManifest.Cli`（改） | 新增 `--report <file>`（可配 `--report-title` / `--report-slug`）：清单产出的同时渲染留痕报告 |
| `TestScripts/delivery-manifest.ps1`（改） | 新增 `-Report <path>` 参数（透传给 CLI）；**脚本保持纯 ASCII**（并写明原因） |

## 验证

- **端到端**：`& .\TestScripts\delivery-manifest.ps1 -SkipTests -BuildId round-64 -PublishDirectory … -Report "Docs/14_reports/2026-10-09-浏览器自动化交付清单-round64.md"`
  ⇒ `manifest emitted (stage: ready-for-external-deploy)` + `报告已写入 …`；生成的报告 Front Matter 齐全
  （`front_matter.py --check` 该文件 **0 不合规**），正文含 7 个套件 1409/0、24 个产物、20 条未验证项、四步外部清单。
- **拒绝路径**：publish 目录不存在时脚本按预期 `exit=2` 且**不产出**清单与报告。
- **更正自己造成的错误**：手工报告与渲染器都把 `Docs/14_reports/` → `Docs/` 的相对路径写成了两级
  （`../../12_features/…`、`../../../TestScripts/…`），实为一级；两处均已改正，`check_md_links.py --all-repo`
  在我这两个文件上**零失效目标**（剩余 1 条 `Docs/16_qa/Review.md` 是既有问题、非本次改动）。
- **测试**：`Pudding.DesktopServiceTests` **278 / 278**（＋6：Front Matter 齐全、未验证项逐字保留、
  无未验证项时显式声明、事实/阶段齐全、链接相对报告目录、空标题/空 slug 被拒）。
- **另一次踩坑（已写进脚本注释）**：往脚本里加中文默认标题 ⇒ Windows PowerShell 5.1 按 ANSI 读无 BOM 的
  `.ps1`，中文变乱码导致**解析失败**（round-62 踩过同样的坑）。现已保证脚本 0 个非 ASCII 字符。

## 已知边界（诚实登记）

- **报告日期用系统当天**（本次生成是 `2026-10-09`），而本会话 changelog 用 `2026-10-08`；文件名与
  Front Matter 的日期以生成为准，不做伪造或回填。
- **报告内容里 `checks` 仍是调用方提供的 TRX 事实**：本轮生成用的是 round-63 的 TRX（`-SkipTests`），
  因此 `buildId=round-64` 但 checks 与 round-63 相同 —— 这是**如实**的：报告只声明它读到的文件。
  正式交付应不加 `-SkipTests`。
- **报告会覆盖同名文件**：`--report` 直接写盘（无冲突检测）。
- **清单与报告的产物仍是「发布目录里的 exe/dll」**，未真正 `dotnet publish`（同上轮边界）。
- 手工报告（round-63）保留为历史记录，仅更正了其中的死链（属更正，不抹除）。

## 影响与回滚

- `--report` / `-Report` 为新增可选能力，不改变既有 JSON 输出路径与退出码语义（0 产出 / 2 拒绝）。
- 回滚：删除渲染器与其测试、移除 CLI 与脚本的 report 参数、还原两份报告的链接。
