# 平台库按数据类占用（选 A：dbstat 页计数，界面不标「估算」）

## 先核实到的现状（避免重复造）

| 用户要求 | 现状（实读） |
|---|---|
| "Pudding 平台数据库要按数据类型算占用" | ❌ **缺**：全仓库**没有任何 `dbstat`/按表统计**；图3 里 9.3 GB 只显示为单块 |
| 可清理数据类目录 | ✅ 已有 `StorageDataClassCatalog`（ADR-076）：数据类 → **物理表/列/日志根**白名单、安全等级（`Disposable/Derived/Evidence/UserData`）、保留天数区间、`ManualCleanupAllowed`、`ShowInManualSelector` |
| 存储页接口 | ✅ 已有 `/api/admin/storage/{overview,data-classes,protected-objects,inventory/*,retention-policy,cleanup/*}` |
| 保留策略面板 | ✅ 已有（截图里的"自动清理策略"就是它） |

⇒ 真正缺的就是**每张表占多少**这一层；数据类目录已经能告诉我"哪张表属于哪个数据类、能不能清"。

## 本轮改动（两个纯 Core 组件 + 测试）

| 文件 | 改动 |
|---|---|
| `Source/PuddingPlatform/Services/StorageManagement/DatabaseSpaceProbe.cs`（新） | 只读探针（`Mode=ReadOnly`，**绝不**建库/改库/加写锁）：① 文件级总量 = **主文件 + `-wal` + `-shm`**（只报主文件会让用户看到的总量明显偏小）；② 按表明细走 SQLite `dbstat`（毫秒级、不扫行）；③ **拿不到 dbstat 时如实置 `PerTableAvailable=false` 且不返回任何猜测明细**；④ 经 `sqlite_master.tbl_name` 把**索引占用归到它所属的表**（否则"索引特别多的表"会被明显低估） |
| `Source/PuddingPlatform/Services/StorageManagement/StorageDataClassSpaceMapper.cs`（新） | 把按表占用归入**既有目录**的语义数据类；不在目录里的表进"未归类"桶并**恒排最后**（它是"目录没覆盖"的信号，不该因体积大抢头条）；安全级别与"是否允许人工清理"**原样透传**目录值，不在这一层发明规则 |
| `Source/PuddingPlatformTests/Services/DatabaseSpaceProbeTests.cs`（新，5 条） | 库不存在 ⇒ `null`（与"空库"区分）；总量含 WAL/SHM；按表明细与页统计自洽；**索引归属正确**；归并（含"未归类排在最后即使最大"）；空输入 |

## 验证（含一条本轮**确立的事实**）

- `PuddingPlatformTests` 构建 **0 错误**；`dotnet vstest` 跑本轮用例 **5/5 通过**；
- **确立的事实：本仓库使用的 SQLite（Microsoft.Data.Sqlite）支持 `dbstat`** —— 我先写成"可用就用、不可用如实报"，
  再用一条**严格断言**去问（把能力钉住），它通过了 ⇒ 按表占比这条路完全可行，界面可以放心展示真实明细。

## 用户口述要求的记录（避免丢失）

- 数字是**快速估算**（`dbstat` 页计数，毫秒级、不干扰运行中的 Core）；
- **界面上不标注「估算」字样**。

## 未完成（本项剩下的两步）

1. **接口**：在 `/api/admin/storage/` 增加一个"按数据类占用"的只读出口（复用本轮两个组件 + 平台库/代码索引库路径），
   形状与既有 `data-classes` 一致，便于前端与 Shell 共用；
2. **界面**：存储页把"分类占比"换成**按数据类的真实占比**，并按数据类给出可勾选项（依据目录的安全级别与
   `ManualCleanupAllowed`）；不写「估算」。

## 我自己的失误（如实记录，都在编译/运行期被抓到）

① 补丁脚本里**内层引号未转义**导致 Python 语法错误，连中两次（本会话第三次踩同一个坑）——好在 all-or-nothing，
脚本两次都没写盘；② 猜错了枚举成员名（写成 `Protected`，实际是 `Disposable/Derived/Evidence/UserData`）；
③ 漏了 `using PuddingCode.Storage;`；④ 一次"通过"其实是**用了构建失败前的旧 dll**（vstest 报 3/3 而当时构建是红的），
已重新构建后取到真实结果 5/5。
