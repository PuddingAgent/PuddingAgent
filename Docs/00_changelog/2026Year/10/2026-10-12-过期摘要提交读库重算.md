# 2026-10-12 修复：过期摘要提交（提交时读库重算 + 事务内版本 CAS）

> 依据：用户转达的复核结论第 1 项（P1，已复现）。位置：`ContextCompactionService` 提交前重算指纹处、
> 事务内逐行覆盖标注处。

## 1. 缺陷（复核探针）

- 提交前重算指纹用的是**生成前**的内存 `messagesToCompact`（同一批对象，必然与冻结值相同）⇒ 该重验形同虚设。
- 事务内逐行更新只要求 `CompactedBy IS NULL`，不含内容/版本条件。
- 探针：摘要生成被屏障暂停 → 修改数据库原消息正文 → 释放屏障 ⇒ 实际返回 **`Applied`**。

## 2. 修复

1. **同一选择规则**：抽出 `SelectCandidateWindow(activeMessages)`，冻结与提交两处共用
   （`text`/`compact_summary` 过滤 + 非 system + 按 Sequence 排序 + 保留最近 6 条）。
2. **冻结版本期望**：`FrozenCoverageRow(MessageId, Sequence, Role, ContentHash)`；
   冻结时同时记录**被覆盖行**与**整个候选窗口（含保留尾部）**两组期望。
3. **提交前真正读库**：`LoadActiveMessagesAsync(..., asNoTracking: true)`。
   原因：同一 `DbContext` 的**变更跟踪实体会返回冻结时的旧值**，那样"读库重算"等于读内存副本
   —— 补充探针正是打穿这一点（首版修复后 3/5 用例仍失败，根因即此）。
4. **两道闸门**：读库重算后逐项比对（候选窗口不符 / 被覆盖跨度不符 ⇒ `SkippedStaleCandidate`），
   并且把版本条件写进事务：`WriteCheckpointAtomicallyAsync` 新增 `expectedRows`，给出期望时
   覆盖标注的条件更新额外要求 `Sequence` / `Role` / `Content` 全等，受影响行数必须为 1，否则整批回滚。
5. 普通压缩提交改用 `commitWindow.ToCompact` + `expectedRows: frozenCoverageRows`。
