# 2026-10-23 终端工具结果 inline 预算降为 2 KiB 并改尾优先

## 先纠正一条会误导决策的事实

事件流 `conversation_events` 里 `tool.call.completed` 记的是**工具原文**；
真正进模型历史的是 `ToolResultContextPolicy.MaterializeAsync` 的返回值（≤8192 字符）。
`AgentExecutionService.Buffered.cs:1526-1540` 可逐字核对。
交叉验证：`TokenUsageEvents.toolResultTokens` 实测均值 12,367 ≈ 6 条 × 2048，吻合。

⇒ 「再设一个 8000 字符上限」是空改；上限一直在。

## 数据（`temp/tool-noise-profile.md`）

| 档 | 样本 | 结果 |
|---|---|---|
| 按行裁剪 shell（头5 + 错误行 + 尾80） | 最长 120 条 | 仅 **11 条（9.2%）**适用，其余全是 `few_lines`；**原文行数中位 = 1**；适用时压到 48.6%，错误行 **100% 保留** |
| 剥 HTML `script/style/标签` | 60 条 | 只压 **12.9%**（`browser_snapshot` 本就是纯文本树）⇒ 放弃 |

⇒ 方向对、维度错：真实终端输出**行少行长**，该按**字符 + 尾部优先**，不是按行。

## 改动（`ToolResultContextPolicy.cs`）

| 项 | 改前 | 改后 |
|---|---|---|
| inline 预算 | 全局常量 8 KiB | `ResolveInlineBudget(toolName)`：终端档 **2 KiB**，其余 8 KiB |
| 头尾比例 | 固定 3:1（头 75%） | 终端档 **1:4（尾 75%）**，其余 3:1 |
| 终端工具集合 | —— | `shell` / `terminal_start` / `terminal_wait` / `terminal_read` / `terminal_execute`（大小写不敏感） |
| `BuildBoundedPreview` | 2 参 | 5 参（`maxInlineChars` / `maxInlineUtf8Bytes` / `headRatio` 均有默认值，**旧调用逐字兼容**） |
| UTF-16/UTF-8 双口径 | 都 8192 | 终端档都 2048 |

选择「尾优先」的依据：报错与结论几乎总在末尾；默认 3:1 会先把末尾截掉。
全文仍 spill 到 `.pudding/context-tool-results/`，notice 里的 `full_output_file` 指针不变，按需可索取。

## 测试（7 → 11 例）

| 新增用例 | 锁住什么 |
|---|---|
| `ResolveInlineBudget_Uses_Terminal_Tier_Only_For_Terminal_Tools` | 5 个终端名走 2 KiB / 1:4；`file_read` 与 `null` 走 8 KiB / 3:1 |
| `MaterializeAsync_Terminal_Result_Uses_Terminal_Budget_And_Keeps_The_Error_Tail` | 结果 ≤2048；**距末尾约 800 字符**处的 `ERROR:` 必须在 preview 里；notice 仍在 |
| `MaterializeAsync_NonTerminal_Result_Between_Budgets_Is_Untouched` | 6000 字符的 `file_read` 结果**逐字原样**（不被新预算误伤） |
| `MaterializeAsync_Terminal_Result_Under_Terminal_Budget_Is_Untouched` | 1000 字符的 shell 结果逐字原样 |

## 验证

- 绿：`--filter FullyQualifiedName~ToolResultContextPolicy` → **失败 0 / 通过 11**
- **M1**（`ResolveInlineBudget` 恒返回默认档）→ **失败 2 / 通过 9**：
  `Assert.AreEqual 应为 <2048> 实际为 <8192>`；`IsLessThanOrEqualTo 实际值 <8192> 不小于 2048`
- **M2 第一次无效**（`TerminalHeadRatio 0.25 → 0.75`）→ **全绿 11/11**。
  原因：用例把 `ERROR` 放在**最后一行**，尾 25%（≈430 字符）也能覆盖 ⇒ 该变异没有区分力。
  **这是变异设计失败，不是缺陷**，已把用例改为「报错后面还有 780 字符普通日志」。
- **M2b**（同一变异 + 新用例构造）→ **失败 1 / 通过 10**，红在 `StringAssert.Contains`（ERROR 不在 preview）
- **M1b**（新用例构造下重跑）→ **失败 2 / 通过 9**
- 复原（`SHA256=D41F4ABA8CA26FA11C04CE4ECCF7E61BB3C990669886025786A84772F256A2E0`）→ **失败 0 / 通过 11**

## 过程中踩到的一个坑（记档）

变异脚本原先的 restore 基线是「打补丁**之前**」的备份，导致 restore 会把文件回退到未打补丁状态，
下一次变异匹配不到锚点（`SOURCE_NOT_PATCHED` 才暴露）。
修法：restore 基线改为「打补丁之后」的 `policy-patched.bin`，补丁前基线保留用于证明补丁确实改了东西。

## 影响面

- 终端类工具结果：inline 上限 8192 → **2048**（省 75%），且尾部信息优先保留。
- 非终端工具：**逐字不变**（8 KiB / 3:1）。
- `deterministicPrune` 组件不受影响（它作用于消息历史，本改动作用于入历史之前的单条结果）。
- 生效条件：需重启 Core（本轮未重启）。回滚：把 `TerminalInlineChars/TerminalInlineUtf8Bytes` 调回 8 KiB 或从 `TerminalToolNames` 移除即可。
