# 2026-10-02 Desktop 能力通道：平台无关件、组合根与版本回写

## 目标 / 背景

切片 C-3 的 Desktop 侧接线是**唯一会改变产品行为**的一步，也是最容易出「看起来配好了、其实没起来」
的地方——同一天就抓到过一例（就绪端点描述不可解析）。因此把能在无 UI 环境下验证的部分全部下沉到
组件里测试，Shell 里只留「提供 UI 实现 + 调一次 + 退出时释放」。

## 改动

- `Source/Pudding.DesktopService/DesktopCapabilityChannelComposition.cs`（新增）—
  组合根：判定 → 构造 → 启动 → 停止收成一次可测试调用。三条语义：关闭 = 什么都不做
  （`Success(null)`，继续走旧 Bridge）；启用却起不来 = **明确失败**（不是只记日志）；
  不做跨传输回退。缺省服务策略 fail-closed（允许集合 = `DeclaredCapabilities`，
  `ShellCallerTrust = Untrusted`）。
- `Source/Pudding.DesktopService/DesktopService.cs` — **回写观察到的页面版本**：
  `ExecuteAsync` 拆出 `ExecuteCoreAsync`（原 switch 主体未动），在**唯一出口**记录结果里的版本。
  这是"通道整条不可用"级修复：准入按注册表版本判 `page_version_mismatch`，而此前没有任何代码回写，
  注册表会停在页面创建时的版本 ⇒ 第一个带版本的操作就被拒。
- `Source/Pudding.DesktopService/BrowserTargetRegistry.cs` — 新增 `SetAgentTarget`：
  `RegisterPage(isAgentTarget:false)` **只增不减**，导致用户接管/目标换页后旧页面永远是 Agent 目标
  （注册表替不该被驱动的页面继续背书）。
- `Source/Pudding.DesktopSurface.Browser/BrowserWorkspaceTargetBridge.cs`（新增）—
  把页面生命周期翻译成**两个**注册表；未登记上下文 `Untrusted`、先页面后上下文直接抛、版本只前进、
  版本事件不凭空造目标、关闭/清空不留悬空引用。
- `Source/Pudding.Contracts/Desktop/ShellHostFacilities.cs`（新增 `IDesktopShellHostFacilities`）+
  `Source/Pudding.DesktopService/DesktopShellSurface.cs`（扩到 5 项）+
  `Source/Pudding.DesktopSurface.Browser/DesktopSurfaceComposition.cs`（新增，14 项各归其位）+
  `Source/PuddingDesktop.CapabilityHost/WinUiShellHostFacilities.cs`（新增，委托式 WinUI 实现）。
- `Source/PuddingDesktop/PuddingDesktop.csproj` — `EnforceShellBoundary` 只放宽 5 个 Desktop 侧组件，
  `PuddingHost`/`PuddingRuntime`/`PuddingPlatform`/`PuddingAgent` 仍禁止。
- 测试：`DesktopCapabilityChannelCompositionTests`（10）、`RegistryVersionRecordingTests`（10）、
  `BrowserWorkspaceTargetBridgeTests`（14）、`DesktopSurfaceCompositionTests`（4）、
  `DesktopShellSurfaceTests`（+5）。

## 验证

- `Pudding.DesktopServiceTests` **170/170**；`Pudding.DesktopSurface.BrowserTests` **54/54**；
  `Pudding.ContractsTests` **96/96**；7 套件合计 **537**；真实端点探针 **53/53 exit 0**；
- `PuddingDesktop`（含新引用）与 `PuddingDesktop.CapabilityHost` 构建 **0 错误**
  （后者 0 警告，并核对产物时间戳确认真的编译了新代码）；
- **实测发现「能编译 ≠ 能运行」**：只加引用时 `--no-restore` 编译通过，但
  `Grpc.Net.Client.dll`/`Grpc.Core.Api.dll` **没有**进 Shell 输出（旧 `project.assets.json` 不认识新传递包）
  ⇒ 组合根一跑就是 `FileNotFoundException`。对 Shell 跑一次 `dotnet restore`（**可离线完成**）后逐个核对输出程序集；
- 顺带验证：指向不存在的命名管道时，`StartAsync` 不等待握手即返回、`DisposeAsync` 有界完成
  ⇒ 「Core 没起来时 Desktop 不挂住」；
- 测试纪律（新踩）：`CapabilityResult<T>` 是严格联合，失败态读 `.Value`、成功态读 `.Error` 都会抛
  ⇒ **断言消息里的表达式也会被求值**，失败信息必须放进确知状态的分支。
