# 2026-10-08 横向：负载敏感用例分析 + 交付脚本可选重试

## 一、分析（只读，未改他方代码）

三条中断用例的共同点：**只在全量链满载时失败，隔离运行稳定通过**（本轮 Host 全量连续 **3/3 全绿**）。
并给出一条**可核对的代码事实**：`DesktopBrowserBridgeHandshakeTests.SecondConnection_CannotReplaceAwaitingHelloConnection`
只给服务端 **2 秒**（`CancellationTokenSource(TimeSpan.FromSeconds(2))`）来"接受第二个连接并关闭它"——
而我历次看到的失败时长恰为 2 s / 5 s 量级，与"等待超时被取消"一致。

**结论（假设级）**：支持"测试侧时限假设过紧"；**未排除**真实竞态（没做线程/时序级分析）。
建议（**未实施**，属他方子系统）：改为宽松上界或等信号；让重试计数可见；按子系统分派排查。

报告：[负载敏感用例分析](../../../14_reports/2026-10-09-负载敏感用例分析.md)

## 二、我这边：交付脚本新增可选重试（默认关闭，且可见）

`TestScripts/delivery-manifest.ps1` 新增 `-RetryFailedSuites <n>`：

- 默认 **0 = 完全关闭**（行为与之前一致）；
- 只有 TRX 显示 `failed > 0` 的套件才重跑；
- 重跑成功后 **TRX 改名为 `<suite>-retried.trx`** ⇒ 清单里检查名带 `-retried`，**读清单的人一眼可见**；
- 重试仍失败 ⇒ 失败计数保留 ⇒ 清单照例**拒绝产出**。

**取舍（如实写下）**：这一步让"偶发失败"不再无条件阻塞交付，但**削弱了"第一次就必须全绿"的强度**；
因此默认关闭、必须显式传参；是否在外部验收里接受重试应由验收方决定——我不替你决定。

## 三、验证

| 项 | 结果 |
|---|---|
| 隔离运行 | Host 全量 3/3 全绿；handshake 用例单跑通过 |
| 脚本 | `-SkipTests` 快跑：参数解析与清单产出正常；**纯 ASCII**（0 非 ASCII 字符） |
| 默认行为 | 未传 `-RetryFailedSuites` ⇒ 与之前完全一致 |

## 四、已知边界（诚实登记）

- **未定位根因**；**未改他方测试**（仓库纪律）；**未量化 flake 概率**（未做满载 N 次统计）。
- **重试代码路径本轮未被真实触发**（没遇到失败）⇒ 登记为**未验证**；下次遇到失败应优先用它并记录结果。
- **`-retried` 后缀会出现在清单检查名里**：有意的可见性设计；下游若精确匹配检查名需知晓。
- 无产品行为变化（工具脚本 + 分析报告）。
