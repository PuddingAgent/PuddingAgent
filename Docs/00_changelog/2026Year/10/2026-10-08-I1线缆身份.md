# 2026-10-08 I1 第三步：能力通道带上类型化调用者身份

## 改了什么

| 件 | 变化 |
|---|---|
| `desktop_capability.proto` | 新增 `BrowserCallerIdentityMessage`（kind/caller_id/task_id/parent_task_id）；`CapabilityCommand` 用**未占用编号 7** 携带 `caller` |
| `Source/Pudding.Contracts/Desktop/BrowserCallerKindWire.cs`（新） | 线缆取值的**唯一真源**（Core/Desktop 共用）：`agent` / `sub_agent` / `user`；未知/空/大小写不符 ⇒ 解析失败 |
| `CoreCommandEncoder.Encode` | 携带 `DesktopCallContext.BrowserCaller`；**无身份则不写字段**（不得按 proto 默认值补身份） |
| 判据 | `IsBrowserCapability(descriptor) => descriptor.Kind == WebView`，取自能力目录本身，**不另建清单** |

**为什么 kind 用字符串而不是 proto enum**：proto3 enum 的默认值（0）会让"字段没填"与"填了第一个枚举值"无法区分，
而身份字段**必须**能区分 —— 否则"没填"会被悄悄当成某个类别，正是 §3.1/§3.2 要杜绝的"用默认值补身份"。

## 撤回的一处错误设计（诚实登记）

我起初在 `DesktopSession` 的调用路径上加了一道"浏览器能力必须携带 caller"的检查（返回 `Unauthorized`）。
随后发现生产侧**已经有** `TrustedCallerDesktopCapabilityAuthorizer` + `IDesktopCallerIdentityProvider`
承担同一职责（其拒绝文案就是"能力调用在当前执行上下文里没有可信调用者身份"）。保留两处会形成**第二份策略**
（设计 §1.1 明确反对"两条路径各自验出相反结论"）⇒ **已删除我的那道门禁**，职责归既有授权器。

⇒ 因此本轮的"缺身份拒绝"**发生在 Core 授权器**（已有），本轮新增的是**身份在能力通道上的携带与编解码真源**。

## 验证

| 项 | 结果 |
|---|---|
| `Pudding.ContractsTests` | **183 / 183**（＋10：线缆取值往返/未知拒绝/未注册枚举不可格式化） |
| `Pudding.CapabilityBrokerTests` | **93 / 93**（＋3：命令携带身份、无身份不造身份、浏览器/Shell 判据） |
| **全量链** | **1647 / 0**、**一次通过**（7 套件；Host 本轮首跑即绿，无重试） |
| 撤回验证 | 删除门禁后 `CapabilityBrokerTests` 由"46 失败/挂起风险"回到**全绿**；`IsBrowserCapability` 已无调用方残留 |

## 诚实边界（诚实登记）

- **身份尚未被消费**：proto 字段已携带，但 **Desktop 侧解码尚未读取它**（下一步），因此当前"带上了不等于被校验"。
- **协议版本仍是 v1**：我尝试把 `Current/Minimum` 升到 **v2**，但 v2 会让**旧端握手被拒**，导致 `CapabilityBrokerTests` **46 条**握手相关用例失败
  （测试替身硬编码 v1）。为避免"半升级"的脏树，本轮**回退为 v1**，把 v2 升级连同等价用例同步作为**独立一步**（这才是"同一切片一次性同步消费方"的正确粒度）。
- **未实现 Desktop 侧严格解码**：未知 kind/空必填/过长在**解码时**的拒绝还没写（下一步）。
- **未真机验证**。
