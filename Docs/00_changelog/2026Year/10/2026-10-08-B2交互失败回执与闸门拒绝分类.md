# 2026-10-08 B2 回执：交互失败不再丢失「已派发」事实，闸门拒绝与失败分开

## 目标 / 背景

设计 §4.1 的硬要求：「工具 `ok=true` 只用于 verified 或明确标注的 dispatched；
**unknown/blocked/failed 为 false，但不能丢失已经派发的事实**」，§4.3 又要求
「执行后断连无法证明结果时返回 unknown + mayHaveSideEffects=true + safeToRetry=false」。

上一轮的交互回执只覆盖**成功路径**：失败仍走 `code + message`，调用方看不到
「执行到哪一步、是否可能已经产生副作用、能不能重试」——最危险的后果是把
「超时且输入已提交」当成「没执行」然后重做一次副作用。本轮补上失败路径，
并把「闸门拒绝」与「普通失败」分开。

## 改动

| 文件 | 改动 |
|---|---|
| `Source/PuddingBrowser.Automation/BrowserInteractionReceipt.cs` | 新增 `IsGateDenial(error)`：**接管/暂停/授权**三种拒绝语义一致（未开始、无副作用、不得自动重试），判成 `blocked` 而不是普通 `failed`；`Build` 据此设置 `IsBlocked`。`BrowserInteractionEvidence` 增加 `IsBlocked` 入参 |
| `Source/PuddingBrowser.Automation/BrowserReceiptJudge.cs` | **修掉重试裁定的一处真空**：原来只按 `completion` 分派，于是「已跑过（dispatched/completed）但断言没过」落到 `_ =>` 分支，只得到 `not_retryable` 且**没有任何 detail**。现在这类情况判 `dispatched_observe_only`（先观察、勿重做）。仍只看执行阶段，不看 `mayHaveSideEffects` —— 后者与 `NotStarted` 同时出现是自相矛盾的回执，保守按不可重试处理，不谎称"已派发" |
| `Source/PuddingBrowser.AgentTools/BrowserToolContracts.cs` | 失败载荷支持 `value`（原先失败只有 code/message）；新增 `BrowserReceiptToolValue`（失败回执投影）；成功输出新增 `execution`/`verification`/`requiresFollowUp`/`retryDisposition`/`retryDetail` |
| `Source/PuddingBrowser.AgentTools/BrowserCapabilityFailure.cs` | `From(...)` 支持带 `value` 与 `warnings` |
| `Source/PuddingBrowser.AgentTools/BrowserInteractTool.cs` | 失败路径构造回执（`ExecutionFor(error)` + `IsGateDenial` + 请求上下文）并放进失败的 `value`；成功路径补 `execution`/`verification`/重试裁定。**重试裁定终于有生产消费方**（`BrowserRetryPolicy` 此前只在组件测试里被调用） |

## 验证

| 套件 | 结果 |
|---|---|
| `PuddingBrowser.AutomationTests` | **192 / 192**（原 187 ＋ 5） |
| `PuddingBrowser.AgentTools.Tests` | **30 / 30**（原 26 ＋ 4） |
| `PuddingHost.Tests` · `PuddingDesktop.Tests` · `DesktopServiceTests` · `ContractsTests` | 252/252 · 305/305 · 215/215 · 97/97 |

新增门禁：

- **纯逻辑层**：闸门拒绝（接管/暂停/授权）⇒ `blocked` 且重试裁定 `not_retryable`；
  普通失败（版本不符）⇒ `failed` 且 `safe_to_retry`；
  超时已派发 ⇒ `execution=dispatched`（**事实保留**）、`completion=failed`、
  裁定 `dispatched_observe_only` **且有 detail**；结果不明 ⇒ `unknown` + `unknown_outcome`；
- **工具层**：未知页面失败仍带结构化回执（`failed`/`not_started`/`not_retryable`）；
  闸门拒绝 ⇒ `completion=blocked` + `not_retryable`；连接不可用 ⇒ `safe_to_retry`；
  成功 click（无期望）⇒ `dispatched` + `dispatched_observe_only` + `requiresFollowUp`。

**取红实测**（两次）：

1. 让失败路径不带回执（`value: null`）⇒ `AgentTools.Tests` **3 条**恰好变红，其余 27 条仍绿；
2. 让 `IsGateDenial` 恒为 `false` ⇒ `AutomationTests` **1 条** + `AgentTools.Tests` **1 条**变红。
   两次复原后分别 30/30 与 192/192 复绿。

## 已知边界（诚实登记）

- **异常路径仍未带类型化回执**：`BrowserOperationException`（如驱动抛的 `stale_element_reference`）
  走 `BrowserToolResponse.FromException`，只有 code/message。它同样是"未开始"，但本轮只覆盖
  `CapabilityResult` 失败路径；统一两条路径属后续。
- **`BrowserReceiptToolValue.Operation` 用枚举名**（如 `Interact`），不是线名 —— 组件里没有
  operation 的线名助手，本轮不为一个字段新增公开类型。
- `retryDisposition` 的文案是英文短语（`retryDetail`），未做本地化。
- 设计 §4.3 的 `receipt_expired` 查询入口（过期重传）仍只有账本，没有工具面。

## 影响与回滚

- **行为变化（Agent 可见）**：交互失败现在返回带 `value` 的结构化载荷；成功输出新增 5 个字段；
  重试裁定的真空被填上（原先"已跑过 + 断言没过"给出无解释的不可重试）。
- 无数据/配置影响；线缆 DTO 与 proto 未改动。
- 回滚：还原上表 5 个生产文件与 2 个测试文件及 code_map。
