# 2026-10-02 切片 D 第①②步：窄端口 + 会话实现（零适配代码）

## 目标 / 背景

按 [`Desktop-Surface-Browser-Mapping`](../12_features/Desktop-Surface-Browser-Mapping-2026-10-01.md) §8.4 的结论，
切片 D **不能**靠替换 `IBrowserRuntime` 实现完成（`IBrowserPage` 约 35 个成员，能力通道只覆盖约 12 个）。
本轮落地其中的第①步（抽窄端口）与第②步（用会话的类型化调用实现），并把「端口真的接到线上」验证掉。

## 改动

- 新增 `Source/Pudding.Contracts/Desktop/BrowserCapabilitySurface.cs` —— `IDesktopBrowserCapabilitySurface`：
  能力通道**能覆盖**的九个浏览器操作（contexts / page_state / tabs / navigate / snapshot / locate /
  interact / wait_for / execute_javascript）。放 Contracts 的理由：它只依赖契约 DTO，
  正是"平台无关接口"该在的位置；工具层将来依赖它不必把 gRPC/协议拖进来。
  文件头写明为什么刻意窄：宽接口上做整替会让二十多个成员只能在**运行期**抛 `NotSupported`（编译期看不出来）。
- `Source/Pudding.CapabilityBroker/DesktopSession.cs` —— 类声明加一个接口：
  `DesktopSession : IAsyncDisposable, IDesktopBrowserCapabilitySurface`。**零适配代码**
  （九个方法的参数顺序与端口一致，编译通过即证明契约匹配）。
- `Source/Pudding.CapabilityBroker.AspNetCoreTests/TrustedCallerAuthorizerOverTheWireTests.cs`（+1 项）——
  把会话**当作端口**用，在真实 Named Pipe 通道上逐个操作断言其线名
  （`browser.contexts` / `webview.page_state` / `browser.tabs` / `webview.navigate` / `browser.snapshot` /
  `browser.locate` / `browser.interact`），钉住「端口 ↔ 能力目录」的一致性。

## 本轮由测试暴露的三条**真实契约**（不是测试瑕疵，值得记住）

1. **同 operation id + 不同 payload ⇒ 拒绝**（`InvalidRequest — duplicate operation id with a different payload`）：
   broker 的幂等语义。第一版测试九个操作共用一个 id，第 2 个就被拒——这是正确行为。
2. **单连接在途额度是 8**（`CapabilityChannelOptions.MaxInFlightPerConnection`）：
   连发 9 个"都不回结果"的操作，第 9 个会因超额度把会话打成 `Faulted`（后续操作全部 `NotConnected`）。
   ⇒ 测试里只能连发 ≤8；`webview.execute_javascript` 由既有 `CancelRequest_TravelsOverTheWire` 覆盖，
   `browser.wait_for` 由真实端点探针覆盖。
3. **可空重载的读取会取消整条流**：超时时它取消调用，服务端因此把会话判为 Faulted；
   要"看窗口内有没有帧"必须用会抛的重载并捕获异常。
