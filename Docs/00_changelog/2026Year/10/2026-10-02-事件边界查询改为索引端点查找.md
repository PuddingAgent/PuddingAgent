# 2026-10-02 事件边界查询改为索引端点查找

## 改动

- `Source/PuddingPlatform/Services/ConversationEventStore.cs`：`GetBoundsAsync` 的 SQL 由
  `SELECT MIN(sequence), MAX(sequence) … WHERE conversation_id = @cid` 改为**同一条语句内的两个索引端点查找**
  （`ORDER BY sequence ASC/DESC LIMIT 1` 标量子查询）。方法签名、参数化、`EnsureTableAsync` 与空会话
  `EventBounds(null, null)` 语义全部不变；不新增索引（复用既有 `(conversation_id, sequence)`），不引入迁移或
  兼容层，不改用 `conversation_heads` 作为 min。
- 两端保留在同一语句内：一条语句只有一个读取视图，并发追加/裁剪不会把 min 与 max 撕成不一致的一对。
- 新增 `Source/PuddingPlatformTests/Services/ConversationEventStoreBoundsTests.cs`：空会话、单事件、两会话隔离、
  稀疏序号、前缀裁剪后 min 前移、未提交写不可见、并发追加/裁剪下的合法快照对、查询计划回归底线，以及
  **工作量不随会话长度增长**的度量用例。

## 验证

- `dotnet test Source\PuddingPlatformTests\PuddingPlatformTests.csproj --filter "FullyQualifiedName~ConversationEventStoreBoundsTests"`
  → 9/9 通过（MSTest）。
- 度量口径是 VDBE 步数（`sqlite3_progress_handler`，每步回调一次），不是毫秒，因此与机器性能无关：
  夹具分别为 8,000 与 32,000 条事件的会话，断言 ① 旧聚合形式在 4 倍事件量下步数 ≥3 倍（放大确实存在）；
  ② 端点形式在 4 倍事件量下步数 ≤2 倍（恒定）；③ 32k 会话上端点形式比聚合形式少一个数量级以上。
- 查询计划对照：两种形式的计划都是 `SEARCH conversation_events USING COVERING INDEX …(conversation_id=?)`，
  所以测试只用计划锁定「会话约束仍进入索引、没有退化成全表扫描」，真正的工作量判据是上面的步数对照
  （诊断报告已说明「计划出现 SEARCH 本身不证明优化」）。
- 度量对象是这两种 SQL 形状在**同一产品 provider**（SQLitePCLRaw bundle_e_sqlite3）上的引擎工作量；
  `GetBoundsAsync` 自身的连接由 EF Core 持有，测试拿不到页级 I/O 计数器，该缺口在报告里已单列。
- 全量 `PuddingPlatformTests`：1,422 用例通过、0 失败（本次新增 18 条：A 9 + B 9）。

## 未完成与影响

- 没有在 `D:\data` 真实长会话上执行删除/写入验证；产品侧读取收敛需按报告「交付、部署与验收」由外部控制器
  部署新构建后复核（本任务未部署、未重启产品）。
- 既有两套同构索引的清理不与本修复混做（报告已明确另做任务）。
- 撤销本改动即回到 `MIN/MAX` 聚合；行为合同未变，因此撤销只影响读取成本，不影响语义。
