# 2026-10-08 横向：链外抽查做成脚本

## 为什么

上一轮我挑"相邻套件"靠的是在 `.csproj` 文本里搜 `Pudding.Contracts`，结果挑中一个**根本不加载**该程序集的套件
（它的 bin 里没有 `Pudding.Contracts.dll`），那 20 例全绿**不是证据**。这类判断必须是可复现的，而不是临场眼力。

## 新增 `TestScripts/check-dependent-suites.ps1`

- 从 `Source/**` 与 `Tests/**` 的 `*Tests.csproj` 出发，按 `<ProjectReference>` 做**传递闭包**；
- 判定标准是"引用图能否到达 `<Assembly>.csproj`"（默认 `Pudding.Contracts`）——**不是**文本匹配；
- 默认只**列出**选中项；加 `-Run` 才逐个 `dotnet test --no-restore` 并在任一失败时非零退出；
- **纯 ASCII**（PS 5.1 按 ANSI 读无 BOM 脚本）。

## 结果（比上一轮手工挑的更全）

| 项 | 数 |
|---|---|
| 扫描的测试项目 | 32 |
| **可达 `Pudding.Contracts`** | **12** |
| 其中在**我的交付链之外** | **5**（`WebApiTests` · `Agent.IntegrationTests` · `CapabilityBrokerTests` · `CapabilityBroker.AspNetCoreTests` · `DesktopConnectionTests`） |

**上一轮的疏漏被脚本纠正**：我手工只挑了 3 个，漏了 `PuddingWebApiTests` 与 `PuddingAgent.IntegrationTests`；
而 `Pudding.Rpc.ProtocolTests` 根本不在结果里（与上一轮的 bin 检查一致 ⇒ 两个方法互相印证）。

## 抽查链外 5 个

| 项目 | 结果 |
|---|---|
| `Pudding.CapabilityBrokerTests` | **90 / 90** |
| `Pudding.CapabilityBroker.AspNetCoreTests` | **43 / 43** |
| `Pudding.DesktopConnectionTests` | **80 / 80** |
| `PuddingWebApiTests` | **2–3 条失败**（运行间会变：先 3 后 2） |
| `PuddingAgent.IntegrationTests` | **未跑**（集成级，成本高；登记为未验证） |

**对 WebApi 失败的分析（未越界修改）**：

- 失败用例都在 **goal / compaction** 语义上（`GoalCommands_*`、`Compact*`），与本会话改的浏览器授权/租约无关；
- 这些用例所在文件里 **零** 浏览器/契约类型引用（`Browser|BrowserCallerIdentity|BrowserAutomationLease|IsSameActor|Grant` 命中 0）；
- 本会话对 `Pudding.Contracts` 的改动是**附加性**的（新增 `IsSameActor`），唯一的**行为**改动在浏览器租约与权威内部；
- 失败条数在两次运行间**变化**（3 → 2）⇒ 更像环境/时序敏感，而不是确定性的契约断裂；
- ⇒ **不归因于本次改动**，且**我不修**（他方子系统；仓库纪律禁代改）。

## 诚实边界（诚实登记）

- **脚本只回答"谁依赖谁"**：它**不**判断依赖方是否真的会执行到被改的代码路径（本轮靠人工看用例文件补上这一步）。
- **`PuddingAgent.IntegrationTests` 未跑**：属集成级、耗时长；本轮明确登记为未验证，不假装覆盖。
- **WebApi 的 2–3 条失败仍未被任何一方定位**：我只提供了"不可归因于我"的证据（文件无相关引用 + 附加性改动 + 计数可变），
  **没有**做根因分析，也**没有**修 —— 建议由该子系统 owner 处理。
- **未真机验证**；两项待决取舍仍未触碰。
- 无产品行为变化（工具脚本 + 记录）。
