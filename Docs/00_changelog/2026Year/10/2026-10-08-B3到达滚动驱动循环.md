# 2026-10-08 B3 到达滚动驱动循环

## 目标 / 背景

前两轮做了收敛策略与 seam（`PlanArrivalStep`）。本轮把它变成**行为**：原生 `to_top`/`to_bottom`
从「明确拒绝」变成「可用且能停」。

## 改动

| 文件 | 改动 |
|---|---|
| `WebView2BrowserPage`（驱动） | 新增 `ScrollToArrivalAsync`：每步**回读** `scrollY`/`scrollHeight`/`innerHeight`（`ExecuteScriptAsync`，读不到或解析不出 ⇒ **明确失败**："拿不到到没到就不猜"），问 `Policy.PlanArrivalStep` 是否继续，继续则按步送真实滚轮事件（复用 `Policy.PlanScroll`）；**本地硬上限 64 步兜底**（即使策略被换成有缺陷实现也不可能无限循环）。到达循环结束后仍走既有的"零位移回读"，如实返回前后位置/边界/内容变化 |
| 能力通道 | 解除对 `ToTop`/`ToBottom` 的原生拒绝；**`ToRef` 仍明确拒绝**（需先解析参考点位置），绝不悄悄退回 DOM |
| 测试 | `NativeScroll_CarriesTheMode_SupportsArrivalAndRefusesToRef`：`to_bottom`+native 现在**下传驱动**（断言 Target/InputMode），`to_ref`+native 仍失败且消息含 `to_ref` |
| 兼容 | 修掉 WinUI 投影编译问题：`ExecuteScriptAsync` 返回 `IAsyncOperation<string>`，改用 `async () => await …`（与此前 `CallDevToolsProtocolMethodAsync` 同一处理） |

## 已知边界（诚实登记）

- **真机未验证**：滚动循环的 CDP/脚本行为、以及"真实页面上 to_bottom 是否真的到得了底"，必须由外部进程内
  smoke 复核（本环境没有 WebView2）。**本轮全部证据是编译通过与映射层断言**，不含任何真实位移观测。
- **停止原因未回给调用方**：策略给出的 `StopReason`（到限/位置没变/步数封顶）目前只用于内部终止，
  尚未出现在 `ScrollOutcome` 里；调用方能看到的仍是前后位置/`atBoundary`/`contentChanged`。
  要如实报告"为什么停"，需要扩展 `ScrollOutcome`（登记为后续）。
- **只覆盖文档滚动元素**：回读几何用的是 `document.scrollingElement`；嵌套容器内的到达滚动尚未处理。
- **`to_ref` 仍未实现**（明确拒绝）。
- **每步之间不等渲染**：送轮后立即回读，快速滚动时可能读到中间状态；策略的"位置没变即停"会据此提前停止 ——
  这是**保守**方向的偏差（宁可早停也不空转），但需要在真机上观察是否过于保守。
- 步数上限两处（策略 `MaxSteps=40`、驱动兜底 64）：不一致是刻意的（策略负责语义上限，驱动负责绝不失控）。

## 影响与回滚

- **行为变化（Agent 可见）**：`browser_interact` 的 `scroll` 在 `input_mode=native` 且 `scroll_target=to_top/to_bottom`
  时**不再被拒绝**，改为真实滚轮循环；`to_ref` 与 DOM 模式行为不变。
- 回滚：还原驱动分支与辅助方法、恢复能力通道的拒绝、还原用例。
