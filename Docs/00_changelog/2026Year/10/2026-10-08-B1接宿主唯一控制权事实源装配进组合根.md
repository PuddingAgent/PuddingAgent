# 2026-10-08 B1 接宿主：进程内唯一控制权事实源装配进 Desktop 组合根

## 目标 / 背景

设计方案 §3.1：**Desktop 进程内只创建一个 `IBrowserAutomationAuthority` 实例**，
Bridge dispatcher、DesktopService、工作区控制器与 Shell 都读它，
「现有三份可写 takeover/paused 字段收敛为投影」。

B1 第三段（`b4e18b7`）只做到「唯一**写入**点 + fan-out」：Shell 一次写入被推给所有闸门，
但每个对象仍各自持有 bool，一致性靠推送维持。本段把事实源真正落地：**权威实例在 Desktop
组合根装配，状态对象变成它的读投影**，不再需要靠 fan-out 保证一致。

## 改动

| 文件 | 改动 |
|---|---|
| `Source/Pudding.DesktopService/DesktopCapabilityChannelComposition.cs` | **组合根在此装配**唯一的 `BrowserAutomationAuthority`（`settings.DesktopId` + 进程实例 ID）并注入 `DesktopService`；关闭态不构造服务，因此也不会留下没人读的权威实例 |
| `Source/Pudding.DesktopService/DesktopService.cs` | 构造参数新增 `BrowserAutomationAuthority authority`（**必填，fail closed**），暴露 `DesktopService.Authority`；`Interaction` 改为 `new DesktopInteractionState(Authority)`；`Close()` 同时 `Authority.Close("desktop window closed")`（窗口没了 ⇒ 自动化不再成立） |
| `Source/Pudding.DesktopService/DesktopInteractionState.cs` | `IsPaused`/`IsUserTakeover`/`Reason` 读**权威快照**；`Pause`/`Resume`/`NotifyUserTakeover`/`ClearUserTakeover`/`SetUserTakeover`/`SetPaused` 写**权威**。交互槽位（对话框/Picker 单窗口互斥）仍由本类持有 |

**一处刻意的细节**：权威只有一个 reason 槽位（"最近一次控制状态变更的原因"），而 UI 需要
「接管解除后仍显示暂停的原因」。因此本类保留两轴的**原因标签**（仅显示/诊断，不参与任何判定），
在解除一轴时把仍在保持的那一轴的原因回写给权威 —— 于是 `Reason` 恒为「当前仍在保持的那个原因」，
两轴都解除时为 `null`，与既有行为逐字一致。

## 验证

| 套件 | 结果 |
|---|---|
| `Pudding.DesktopServiceTests` | **203 / 203**（原 197 ＋ 6） |
| `PuddingDesktop.Tests` | **301 / 301** |
| `PuddingHost.Tests` · `PuddingBrowser.AutomationTests` | 252 / 252 · 187 / 187 |
| `build` `Pudding.DesktopService` · `PuddingDesktop` | 0 错误 |

新增门禁（`AuthorityProjectionTests`，5 条）：

- `State_Writes_Land_In_The_Single_Authority`：状态写入后从权威快照读得到，且**控制世代推进**
  （接管前的队列/租约不得复活，方案 G1）；
- `State_Reads_The_Authority_Not_A_Private_Flag`：**绕过状态对象直接写权威**（Shell/生命周期端口
  会这么做），状态立刻反映；解除接管**不**连带解除暂停；
- `Takeover_WrittenDirectlyToTheAuthority_StillBlocksMutatingCalls`（最强的一条）：
  直接写权威的接管**必须**让变更类能力被拒（`UserTakeover`）且**驱动调用数为 0**；
- `WindowClose_Closes_TheAuthority`：`Close()` 后权威 `IsClosed`；
- `Authority_IsRequired_FailClosed`：不传权威 ⇒ 构造即失败（不退化成"各自维护标志"）。

**取红实测**：把 `IsUserTakeover` 改成读本地标签（`_takeoverReason is not null`）而不是权威快照 ⇒
`State_Reads_TheAuthority_Not_A_Private_Flag` 与
`Takeover_WrittenDirectlyToTheAuthority_StillBlocksMutatingCalls` **恰好 2 条变红**，其余 201 条仍绿；
复原后 203/203 复绿。

## 已知边界（诚实登记）

- **`Admit`/`Revalidate` 与写租约尚未接入准入路径**：本轮只收敛了控制面（接管/暂停/关闭）。
  权威的 `Admit` 需要**可信调用方身份**，而 `DesktopCallContext` 明确不带身份
  （"身份与权限不由模型填写的字段决定"，由 Core 产生）⇒ 该字段的跨进程传递属后续切片。
  在此之前，桌面路径的两次校验（入队前 + 拿到 UI 线程后）仍由 `ValidateAdmission` 完成。
- **grant 时代价**：`BrowserPageGrant`/`BrowserGrantIssuancePolicy` 仍只在组件内被使用；
  页面级闸门目前仍用「Agent 目标页」判据（`DesktopTargetRegistry.IsAgentTarget`），
  与 grant 模型的合流同样等身份字段。
- **`IBrowserAutomationControl` 仍无 UI 侧驱动者**：Shell 的接管开关仍走
  `DelegateAutomationGate` → `DesktopInteractionState` → 权威；这条链路已经是同一个事实源，
  但"Shell 直接读权威做显示投影"未做。
- 本轮**未**把 Bridge dispatcher 自己的 `_paused`/`_userTakeover` 字段也改成读权威：
  它属 `PuddingDesktop.WpfArchive`，改它要动 Shell 进程的构造顺序，属后续切片。

## 影响与回滚

- **行为变化**：`DesktopService` 构造签名新增必填参数（3 处调用点已同步：组合根 + 2 处测试）；
  `Close()` 额外把权威置为关闭。产品行为中「接管/暂停」的判定结果不变。
- 无数据/配置影响；线缆 DTO 与 proto 未改动。
- 回滚：还原上表 4 个生产/测试文件与 3 处 code_map。
