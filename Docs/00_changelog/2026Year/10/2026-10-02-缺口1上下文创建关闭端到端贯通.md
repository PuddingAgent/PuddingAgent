# 缺口 #1 完成：上下文 create/close 端到端贯通（两个新能力）

## 结果

按 `a20d62a` 核验过的 14 点清单**一次性**施工，**首次构建即 0 错误**，九个套件全绿
（20+97+90+43+80+170+54+231+15 = **800** 用例）。两个新能力从目录到 Desktop 实现全通：

`browser.context.create` / `browser.context.close`（均为 `Mutating | HasSideEffects | RequiresTrustedContext`，
**无** `RequiresPageTarget` —— 上下文作用域）。

## 改动（14 点，逐层）

| 层 | 文件 | 改动 |
|---|---|---|
| 1 目录 | `Contracts/Capabilities.cs` | 新增两个能力名 + 两条目录项（**新名字**：目录注释明确要求改变同名能力语义时必须换名或升版本） |
| 2 线缆 | `Protos/desktop_capability.proto` | `ContextCreateCommand`/`ContextCloseCommand`；payload oneof 24/25；`ContextCreatedOutcome`/`ContextClosedOutcome`；outcome oneof 25/26 |
| 3 映射（Core） | `CapabilityBroker/WireMapping.cs` | 命令 switch 两例；能力↔结果匹配表两行；结果解码两段（含可信级别解析与 `Persistent`） |
| 4 映射（Desktop） | `DesktopConnection/Mapping.cs` | 解码 switch 两例（新建允许不设 target、要求 `context_id`）；结果写出 switch 两例 |
| 5 接缝 | `Contracts/Desktop/UiSeams.cs` | `IDesktopUiSurface` 新增两个成员（**发现**：能力分发端口是它，不是浏览器 surface 本身） |
| 6 组装 | `DesktopSurface.Browser/DesktopSurfaceComposition.cs` | 两个成员归属浏览器实现（组装类无逻辑，只归位） |
| 7 替身 | `DesktopServiceTests/TestInfrastructure.cs` | `RecordingUiSurface` 补两个桩（接口一改，替身立刻要求） |
| 8 Desktop 实现 | `DesktopSurface.Browser/BrowserRuntimeDesktopSurface.cs` | 实现 `IDesktopContextCapabilitySurface`：`_runtime.CreateContextAsync/CloseContextAsync`；可信级别取自目标注册表 |
| 9 会话 | `CapabilityBroker/DesktopSession.cs` | 实现第二个窄端口，两方法走既有 `InvokeAsync`（发命令 + 解码） |
| 10 Bridge | `Host/BridgeBrowserCapabilitySurface.cs` | 同上；Bridge 侧不知道可信级别 ⇒ 保守 `Untrusted`（既有不对称，已登记） |
| 11 路由 | `Host/TransportRoutedBrowserCapabilitySurface.cs` | 实现第二个端口并按同一套 `DesktopTransportRouting` 决策（组合根传入的两个实现都实现了它） |
| 12 策略 | `DesktopService/DesktopCapabilityPolicy.cs` | 策略表两行：仅 `AgentAuthorized`（与 `BrowserTabs` 同口径） |
| 13 声明 | `DesktopService/DesktopCapabilityChannelSettings.cs` | `DeclaredCapabilities` 加两项（**与实现同批**，否则就是假声明） |
| 14 测试 | 三处冻结快照 + 线缆快照 | 目录快照、可信上下文名单、策略表快照、payload/outcome 名单与计数、四个新消息的字段号 |

## 验证

- 构建：`Pudding.Contracts` / `Pudding.Rpc.Protocol` / `Pudding.CapabilityBroker` /
  `Pudding.DesktopConnection` / `Pudding.DesktopService` / `Pudding.DesktopSurface.Browser` /
  `PuddingHost` 全部 **0 错误**；
- 测试（九套件全绿，共 **800** 用例）：`Rpc.ProtocolTests` **20/20**、`ContractsTests` **97/97**、
  `CapabilityBrokerTests` **90/90**、`CapabilityBroker.AspNetCoreTests` **43/43**、
  `DesktopConnectionTests` **80/80**、`DesktopServiceTests` **170/170**、
  `DesktopSurface.BrowserTests` **54/54**、`PuddingHost.Tests` **231/231**、
  `AgentTools.Tests` **15/15**；
- 三处冻结快照（目录、可信名单、策略表）在**新增能力时必须更新**——它们正是本轮之前两次半程尝试被打回的原因；
- **未验证**：真实 Desktop 会话端到端（需启用能力通道 + 外部重启窗口）；两个新能力此刻还没有
  工具调用方（`browser_context` 工具迁移在下一轮）。

## 与前面两次失败尝试的对比（方法论）

- 第 106/107 轮：先做「契约层」再补实现 ⇒ 被护栏打回（能力一注册，策略表与声明集合就必须同步）；
- 本轮：按核验过的 14 点清单**整批**做，一次编译通过、九套件全绿。
  ⇒ 结论：**这类跨层变更的"分批"边界不能按"层"切，要按"护栏一致性"切**。

## 未完成 / 留白

- `browser_context` 工具迁移（第七个工具，也是最后一个）：现在可以**完全对齐**语义
  （`create` 不再需要 `createIfMissing`，`close` 走新能力）；
- Tool Runtime 权限链；切片 F（默认传输切换、退役 Bridge）；外部重启窗口 8 步验收。
