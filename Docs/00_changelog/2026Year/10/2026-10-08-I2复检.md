# 2026-10-08 触碰页面前的 Revalidate

## 为什么

只在**入队前**判一次准入是不够的：排队期间授权可能被撤销、用户可能接管、页面可能关闭。
方案 §4.2 要求"真正触碰页面前复检"，与"结束后释放租约"合起来才是完整的租约生命周期。

## 实现要点

| 点 | 说明 |
|---|---|
| 位置 | `RunOnUiAsync` 内、`_dispatcher.InvokeAsync(...)` **之前**，且**在 `try` 内** |
| 拒绝 | 返回 `revalidated.Error ?? Unauthorized(Denial)` ⇒ **驱动调用数为 0** |
| 租约 | 无论拒绝/继续/异常，`finally` 都会 `ReleaseLease`（放在 `try` 外会在拒绝路径泄漏） |
| 请求重建 | 用 `DesktopCapabilityOperations` 唯一映射 + `context.TryGetBrowserCaller` 重建，**不动 `ValidateAdmission` 签名** |
| 条件 | 仅当本操作**有租约**（变更类）且世代/身份/映射齐备时才复检 |

## 验证

| 项 | 结果 |
|---|---|
| `Pudding.DesktopServiceTests`（**TRX 判定**） | **361 / 361** ✅（含既有租约生命周期用例） |
| 全量链 | **未跑** |

## 诚实边界

- **本轮的 Revalidate 尚无定向用例/取红**：要证明"排队期间被撤权 ⇒ 驱动调用数=0"，需要在**准入之后、执行之前**确定性地撤销授权 —— 这需要编排（例如用 `RecordingUiSurface.Gate`/自定义调度器在派发时撤权），下轮实现并取红（去掉 Revalidate ⇒ 该用例必须变红）。
