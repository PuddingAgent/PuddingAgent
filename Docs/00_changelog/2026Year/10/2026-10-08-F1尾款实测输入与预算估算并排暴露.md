# 2026-10-08 F1 尾款：实测输入与预算估算两个口径并排暴露（前端 6.4.4）

> 范围：`Source/PuddingCore/Runtime/ContextCompactionContracts.cs`、
> `Source/PuddingRuntime/Services/ContextCompactionService.cs`、
> `Source/PuddingMemoryEngineTests/ContextCompactionServiceTests.cs`、
> `Source/PuddingPlatformAdmin/`（`ContextUsageRing.tsx` + `.test.tsx`、`IntentConsole.tsx`、`services/platform/api.ts`、`package.json` 6.4.3 → **6.4.4**）
> 依据：[修复方案](../../../12_features/首Token等待与上下文指示器修复方案-2026-10-07.md) §2.1、
> [诊断报告](../../../14_reports/首Token等待与上下文指示器诊断-2026-10-07.md) §4.1
> 前序：[F1 请求归因](2026-10-08-F1请求归因准备实测分离与用途落账.md)（后端槽位分离）

## 1. 问题

诊断 §4.1 记录的现象：界面上的「已使用」在 **463.8K** 与 **164.7K** 之间跳变 —— 因为估算与
Provider 实测共用同一个数值槽位（后到的实测会覆盖估算，反之亦然），用户无法判断看到的数
到底是「这次要发出去的请求有多大」还是「上次请求实际报了多少」。

后端的两个槽位在 [F1 请求归因](2026-10-08-F1请求归因准备实测分离与用途落账.md) 里已经分开，
但**前端只拿到其中一个**（`usedTokens` + 来源），因此无法并排展示。

## 2. 改动

### 2.1 后端：健康快照暴露「上一主请求实测」四元组

`ContextHealthSnapshot` 新增（均为 init 属性，JSON 直接序列化，**无需改 DTO 映射**）：

| 字段 | 含义 |
|---|---|
| `LastMeasuredPromptTokens` | **上一次主请求**的 Provider 实测输入（prompt tokens） |
| `LastMeasuredRawEstimatedTokens` | 该请求的原始（校准前）估算，用于解释校准系数 |
| `LastMeasuredInvocationId` | 调用身份（`session:trace:round:purpose`），可与日志/事件对表 |
| `LastMeasuredAtUtc` | 记录时刻（ISO-8601） |

取值来源是 `ContextUsageSnapshotStore.TryGetLastMeasuredRequest`（**主调用专用槽位**）——
压缩/审批等辅助调用走 `TryGetLastAuxiliaryMeasurement`，因此**不会污染**这个口径。
`UsedTokens`/`UsageSource` 保持原义（可能是「当前已准备好、尚未发出」请求的预算估算）。

### 2.2 前端：新增独立一行，不覆盖

`ContextUsageRing` 新增 `measuredPromptTokens`/`measuredRawTokens` 两个 prop 与一行
`data-testid="context-usage-last-measured"`：

```
上次请求实测输入    131.1K（原始估算 71.0K）
```

- 与主数值（`已使用 463.8K`，来源由既有的「数据来源」行标注）**并排**，互不覆盖；
- **未采集 ⇒ 整行不渲染**（不用 0 冒充，延续本面板「未采集 ≠ 0」的既有纪律）；
- `IntentConsole` 直接把 `contextHealth.lastMeasuredPromptTokens` /
  `lastMeasuredRawEstimatedTokens` 传下去。

## 3. 验证（本机真实执行）

| 命令 | 结果 |
|---|---|
| `dotnet build Source\PuddingRuntime\PuddingRuntime.csproj` | **exit 0**，0 错误 |
| `dotnet test … --filter "…GetHealthAsync"`（MemoryEngine） | **exit 0**，失败 0 / 通过 **6** |
| `pnpm run jest -- --ci src/pages/chat/components/ContextUsageRing.test.tsx` | **exit 0**，失败 0 / 通过 **10** |
| `pnpm run jest -- --ci`（全量）/ `pnpm run build` / `pnpm run tsc` | 见 §3.1 |

新增/扩展用例：

- `GetHealthAsync_ExposesLastMeasuredMainRequest_SeparatelyFromPreparedEstimate`：
  准备快照 + 主请求实测同时存在时，`LastMeasuredPromptTokens = PromptTokens`、
  `LastMeasuredRawEstimatedTokens = 原始估算`、`InvocationId` 与时刻齐备，且
  **Total（含 completion）不得被当成实测输入**。
- `GetHealthAsync_AuxiliaryMeasurement_DoesNotPopulateMeasuredInput`：只有压缩目的实测时
  `LastMeasuredPromptTokens` 必须为 **null**（「摘要与主请求隔离」在健康 DTO 上的体现）。
- 环面板：两个口径**并存**（实测行 + 主数值 463.8K 同时渲染），未采集 ⇒ 该行不存在。

> 一次测试自纠：断言最初写 `原始估算 71K`，实际渲染为 `71.0K` —— 是**断言**错，不是实现错，
> 已按真实渲染修正（面板 `formatTokens` 保留一位小数）。

**全量前端 4 个失败的定性**：3 个是既有基线失败（`InputArea.test.tsx` + `IntentConsole.test.tsx`），

全量负载下 26.9 s 才失败，属**负载/超时型 flake**，与本次改动（上下文用量面板）无关，已如实登记而不掩盖。
