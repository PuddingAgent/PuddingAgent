# 桌面设计令牌层与 XAML 字面量门禁（S1+S2）

## 1. 问题（实测，不是感觉）

`Source/PuddingDesktop/MainWindow.xaml`（759 行）：

| 类别 | 实测 |
|------|------|
| 裸 `FontSize` 数字 | **65 处 / 13 档**（29×12、11×6、18×6、15×5、10×3、13×3、24×3、28×3、9×3、8/16/19/21×1） |
| 裸 `CornerRadius` | **20 处 / 4 档**（8×14、10×4、15×1、16×1） |
| 裸 `#hex`（Background/Foreground/BorderBrush/Fill/Stroke） | **9 处** |
| 引用字号令牌 | **0 处** |

`App.xaml` 只有 5 个语义画刷（ThemeDictionaries），`MainWindow.xaml` 另有一组内联画刷，
主壳层则**整段绕过两者直接写字面量** ⇒ 同一视觉事实有两份真源，改一处不改另一处不会报错。
所以「视觉重量倒挂」的根因不是某个值选错，而是**没有词汇表**：13 档字号里
12/13/15/16/18/19/21 彼此相差 1–2px，无法用肉眼判断谁更重要。

## 2. 做了什么（本次提交，不含宿主改动）

新增 `Source/PuddingDesktop.Foundation/Design/`（Foundation 是 BCL-only 叶子，不引 WinUI，可脱宿主测试）：

- `DesignTokens.cs`：唯一字号 **6 档**（11/12/15/18/24/28）+ 圆角 **2 档**（8/12），
  按**角色**命名（`FontSizeBody` / `RadiusCard`），不按数值命名 ⇒ 未来调值是改一处；
  另给 `MapFontSize` / `MapCornerRadius`（把历史字面量映射到档位，迁移脚本与门禁共用同一套判断）。
- `XamlLiteralLint.cs`：纯文本扫描，三条规则 `PDT-TOKEN-001`（裸 FontSize）/ `002`（裸 CornerRadius）/
  `003`（用量属性上的裸色值）。`{StaticResource …}` / `{ThemeResource …}` / `Auto` / `*` / `Transparent` 放行；
  `<SolidColorBrush Color="#…">` 属**定义处**，刻意合法——否则令牌文件自己都过不了自己的门禁。
- `DesignTokenXaml.cs`：由上述表**生成** `Source/PuddingDesktop/Themes/DesignTokens.xaml`，
  字节确定、禁止手改 ⇒ ResourceDictionary 与常量不可能漂移。

`Source/PuddingDesktop.FoundationTests/DesignTokenTests.cs` 新增 22 个用例，其中：
- 迁移完备性：MainWindow 里出现过的 13 档字号逐档断言归宿（少一档 = 迁移会漏）；
- lint **红样本**：喂 `FontSize="13"` / `CornerRadius="0,12,0,12"` / `Background="#FF00AA"` 必须报，行号必须对；
- 生成物可被 `XDocument` 解析、覆盖全部 key、两次输出逐字节相同、自身零违规；
- **现状基线（characterization）**：真实 `MainWindow.xaml` 的违规数钉死为 65 / 20 / 9，`App.xaml` 为 0。
  迁移时这些数字只许单调下调；任何人新写一个 `FontSize="14"` 会立刻变红。

## 3. 验证

- `dotnet test Source/PuddingDesktop.FoundationTests` → **499 通过 / 0 失败**。
- 变异取红：把 `MapFontSize` 阈值 13.5 改成 12.5 → **2 个用例变红**
  （`MapFontSize_CoversEveryLiteralObservedInMainWindow(literal: 13)` 与 `Lint_FlagsRawFontSize`），
  复原后字节级 `-ceq` 相同并复跑全绿 ⇒ 门禁确实能失败，不是"永远绿"。
- 交叉验证：基线数字与独立的 PowerShell 正则统计（65 / 20 / 9）一致 ⇒ lint 的正则与预期口径相符。
- 宿主 `PuddingDesktop.exe` 全程未重启、未构建、未改一个字节；本次改动全部落在 `temp\build\winui3`。

## 4. 留白（下一步，均未开始）

1. **S5 接入**：生成 `Themes/DesignTokens.xaml` 并合并进 `App.xaml`（会动宿主 XAML，需单独提交）。
2. **机械迁移**：65 + 20 处字面量 → 令牌引用，视觉零变化（第三档：`8/9/10/11→Micro`、`12/13→Caption`、
   `15/16→Body`、`18/19/21→Subtitle`、`24→Title`、`28→Display`；`19/21→18` 会略微变小，需同屏比对）。
3. **颜色令牌**：9 处用量色 + 39 个 `Color=` 定义值要收敛成按语义命名的画刷，且必须三套 ThemeDictionaries
   （浅色/深色/高对比）齐备，工作量远大于字号，单独一轮。
4. **间距**：`Padding` / `Margin` 尚未盘点，本次刻意没写规则（避免伪门禁）。
5. **代码侧**：`MainWindow.xaml.cs` 里 `FontSize = …` 之类赋值尚未纳入 lint（纯文本扫描只覆盖 XAML）。

## 5. 门禁补洞：样式 Setter 写法（追加提交 `2a`）

上一版 lint 只认元素属性 `FontSize="13"`，而 WinUI 的视觉值绝大多数住在样式里：
`<Setter Property="FontSize" Value="13"/>`。这意味着**门禁漏了将近一半的真实存量**，
而基线把满眼绿当成“已经数清了”。实测证据：补上 Setter 解析后，同一份 `MainWindow.xaml` 的违规数从
65 / 20 变成 **78 / 33**（字号 +13、圆角 +13）；连一直显示“零违规”的 `App.xaml` 也露出 **1 处**
（`ContentDialog` 样式的 `CornerRadius="8"`）。

改动：

- `XamlLiteralLint.Scan` 新增 `<Setter>` 元素体解析（`Property` / `Value` 顺序与换行不敏感），
  两条路径共用同一套规则与消息，结果按文档位置排序 ⇒ 行号仍可信。
- 基线重钉：`MainWindow.xaml` = **78 / 33 / 9**，`App.xaml` = **0 / 1 / 0**（不再是“断言为空”）。
  `App.xaml` 那一处是 Stage 3 把令牌提升到 App 级资源字典时才迁的最后一处，在此之前只许降不许升。
- 新增 3 个用例：Setter 里的裸字号、Setter 里的裸圆角（**属性顺序反过来也抓**）、
  Setter 里引用令牌必须放行。

验证：

- `dotnet test Source/PuddingDesktop.FoundationTests` → **502 通过 / 0 失败**（覆盖 83.43%）。
- 变异取红：把扫描用的 `<Setter` 改成 `<SetterX`（等于回到上一版的行为）→
  **4 个用例变红**，其中基线报 `Expected: 78 / Actual: 65`、`Expected: 1 / Actual: 0`；
  用备份恢复（`=== RESTORED byte-identical: True ===`）后需 `dotnet build -t:Rebuild`
  才是真复原——`Copy-Item` 保留旧 mtime，msbuild 会跳过重编译，跑的还是变异体（这个坑当场又踩了一次）。
- 已知短板：`Lint_AcceptsTokenReferenceInsideAStyleSetter` 是“断言为空”的正样本，
  变异后仍为绿——它只能挡住把合法写法误报，挡不住漏报；漏报由上面两条红样本堵住。

## 6. 机械迁移：把「正好等于档位」的 74 处换成令牌（追加提交 `2b`）

S1 的令牌表原本靠一个生成器 `DesignTokenXaml.cs` 产出 `Themes/DesignTokens.xaml`，但那个文件**从未落过盘**，
只有测试在调它——等于为一个不存在的文件养一份生成逻辑。本轮改成实打实的做法：
令牌定义**直接写进 `MainWindow.xaml` 自己的 `Grid.Resources`**，生成器连同它的 2 个用例一起删掉。

为什么放这里而不是 `App.xaml`：同一份 `ResourceDictionary` 里已经有这些样式的宿主，
令牌块插在 `<ResourceDictionary.ThemeDictionaries>` **之前**即可被后面所有 `<Style>` 解析到
（`StaticResource` 是自上而下解析的，这是唯一不需要动宿主的落点）；
`App.xaml` 合并属 S5，仍待单独授权。

### 6.1 迁移口径：只做「等值替换」，不猜

只替换**值正好等于某一档**的站点，不做任何 12→13、19→18 这类判断——那些会改变像素，
必须由人逐条签核（见 §6.3）。多圆角写法（`CornerRadius="8,8,0,0"`）一律不动。

| 令牌 | 迁移站点 |
|------|----------|
| `FontSizeMicro` (11) | 8 |
| `FontSizeCaption` (12) | 32 |
| `FontSizeBody` (15) | 5 |
| `FontSizeSubtitle` (18) | 6 |
| `FontSizeTitle` (24) | 3 |
| `FontSizeDisplay` (28) | 3 |
| `RadiusControl` (8) | 16 |
| `RadiusCard` (12) | 1 |
| **合计** | **74** |

（引用数由独立正则复核：字号 8+32+5+6+3+3 = **57**，圆角 16+1 = **17**。）

用的是脚本（`temp/migrate-2b.ps1`，一次性、不入库），三道防线：

1. **按值计数断言**：每个 `(属性, 值)` 的预期条数写死在脚本里，多一处少一处直接 `throw` 且**不落盘**；
2. **注释区间保护**：任何替换落在 `<!-- … -->` 内即拒绝执行（否则会把说明文字改成资源引用）；
3. **区间不重叠 + 倒序应用**：Setter 体解析与元素属性解析共用同一份编辑清单，按位置排序后从后往前改，
   避免索引漂移。

写入保留原换行风格（该文件是 LF，不是 CRLF；脚本先探测，一旦发现混合换行就拒绝写）。

### 6.2 迁移后的实测

| 文件 | 裸 `FontSize` | 裸 `CornerRadius` | 裸色值 | 令牌引用 |
|------|--------------|-------------------|--------|----------|
| `MainWindow.xaml`（迁移前） | 78 | 33 | 9 | 0 |
| `MainWindow.xaml`（迁移后） | **21** | **16** | 9 | 字号 57 / 圆角 17 |
| `App.xaml` | 0 | 1 | 0 | 0（未动） |

- 基线按**门禁自己量出来的数**重钉（先只改字号预期 78→21，让圆角那条报出 `Expected: 33 / Actual: 16`，
  再把 16 写进去并转绿）——数字不是我算的，是断言吐出来的。
- 结构未被破坏：`XDocument.Parse` 通过，`Window` / `Application` 根节点正常；
  迁完的样式形如 `<Setter Property="FontSize" Value="{StaticResource FontSizeCaption}"/>`。

### 6.3 剩余裸值（Stage 3 的待办清单，本轮刻意不动）

字号 21 处（属性 13 + Setter 8）：`13×8`、`9×3`、`10×3`、`8×2`、`14×2`、`16×1`、`19×1`、`21×1`。
圆角 16 处（属性 6 + Setter 10）：`17×4`、`10×4`、`9×3`、`4.5×2`、`6×1`、`15×1`、`16×1`。

其中三类**不能机械替换**，必须签字：

- `CornerRadius="17"` ×4 用在 34×34 的圆形按钮上——`17` 是**推导出来的几何量**（半径 = 边长/2），
  改成 `RadiusCard`(12) 就不再是圆；
- `8 / 9 / 10 → Micro` 是**向上**收口（字变大），`19 / 21 → Subtitle` 是**向下**收口（字变小），
  两者都会让人眼看到差别；
- `4.5 / 6 → RadiusControl` 同理变圆变大。

### 6.4 新增的 3 道门禁（都能取红）

1. `MainWindowXaml_DeclaresEveryDesignTokenWithMatchingValue`
   —— Foundation 的 `DesignTokens` 是数值真源，XAML 里那份是拷贝；两侧任一侧改了值而另一侧没跟上就红，
   也挡住「自己新加一个 `FontSizeGiant`」这种绕过词汇表的写法。
2. `MainWindowXaml_ResidualLiterals_MatchDocumentedDelta`
   —— 把上面 §6.3 那份残留清单（含每个值的条数）钉死。多一个散值、少一处残留、
   或有人把某档静默改小都会红；它同时是 Stage 3 的机器可校验清单。
3. `MainWindowXaml_ParsesAndEveryTokenReferenceResolves`
   —— lint 是纯文本扫描，看不见 XML 是否还被结构地解析得动：`{StaticResource FontSizeBodyy}`
   这类**写错名字**的引用 lint 全绿但应用启动就会崩。这条把文件解析 + 每个令牌引用必须指向已声明 key 一起查。

顺带补一条正样本 `Lint_IgnoresValuesThatAreNotVisualTokens`：`Width` / `MinWidth` / `Height` / `Margin` /
`Padding` / `Opacity` 上的数字绝不能被误报（否则门禁会被当成噪音静音掉）。

## 7. 追加（同日）：颜色从 9 处裸值收到 0

字号/圆角之后对颜色做了一次实测盘点，结论与预期不同：**语义层早就存在**（`ThemeDictionaries`
里的 brush 键），三套字典键集合已经完全齐平（`MainWindow.xaml` 23/23/23、`App.xaml` 5/5/5），
`HighContrast` 分支也已改用系统色。真正的缺口是 **9 处使用点绕过该层直接写死颜色**，
与 lint 基线 9 逐条吻合。设计与边界见 `Docs/11_design/桌面颜色令牌层提案-2026-10-22.md`。

本轮只做其中零视觉变化的一步（提案里的 A1）：

| 项 | 前 | 后 |
|----|----|----|
| `MainWindow.xaml` 使用点裸色（`RawColorRule`） | 9 | **0** |
| `Default` / `Light` 字典 brush 键 | 23 / 23 | **30 / 30** |
| `{ThemeResource}` 引用 | 96 | 105 |
| 文件字节 | 56860 | 58741 |

`StatusWarningBrush` `StatusInfoBrush` `StatusAccentAltBrush` `StatusSuccessBrush`），
`Default` 与 `Light` 值逐字节等于迁移前的裸值，`HighContrast` **故意不声明**（按 `ThemeDictionaries`

**未做**：`HighContrast` 自适配（只在 HC 模式可见，需签字）；`#E2A33C` vs `#E7B877`、

## 8. 追加（同日）：`{ThemeResource}` 必须有定义 —— 门禁落地

§7 末尾留着的那条口子本轮补上。缺口是真实的：WinUI 在**运行期**才解析 `{ThemeResource}`，
键名拼错编译照过、启动才崩，而 §5/§6/§7 的三条 lint 都只看字面量、不看键能不能解析。

新增 `Source/PuddingDesktop.Foundation/Design/ThemeResourceAudit.cs`（BCL-only，只用 `System.Xml.Linq`），
三道判定：

| 判定 | 语义 |
|------|------|
| `FindUnresolvedReferences` | 每个引用必须在「本文件声明的键 ∪ `App.xaml` 声明的键 ∪ 平台白名单」里；未解析引用带 1 基行号 |
| `FindBrushKeySetDrift` | `Default` 与 `Light` 的 brush **键集**必须一致 |
| `PlatformResources` | WinUI 内建键的**显式**白名单（11 个，`Ordinal`），写死在源码里而不是临时脚本里 |

`HighContrast` 不参与键集比较 —— 按 `ThemeDictionaries` 规则它允许缺键（缺了回落 `Default`）。

**一条被实测纠回来的规则**：第一版 `FindAsymmetricBrushKeys` 把「键集 + 取值」一起比，
真文件一跑就有 8 个键红着（`ListViewItemBackgroundPointerOver` 之类 `#14FFFFFF` vs 浅色值、
`App.xaml` 的 `CardBackground`/`DividerBrush`/`NavigationBackground`/`SoftBackground`）。
这不是缺陷，是**设计**：同一批令牌在深色/浅色下取值本来就不同。
于是方法改名为 `FindBrushKeySetDrift`，**只比键集**，并专门加一条用例
`FindBrushKeySetDrift_AllowsDifferentValuesForTheSameKey` 把语义钉住，防止以后有人“顺手修回”成比值。

实测（`513` 个 Foundation 用例全绿）：`MainWindow.xaml` 的 105 个 `{ThemeResource}` 引用
全部可解析（42 个指向本文件外的键：`App.xaml` 8 个 + 平台/字体族/built-in 白名单），
`MainWindow.xaml` 与 `App.xaml` 的 `Default`/`Light` 键集均已齐平（30/30、5/5）。

取红证据（变异两处、其余字节不变，`SHA-256 4474288A…571D`）：

1. `{ThemeResource BrandAccentBrush}` → `…BrandAccentBrushTypo`（2 处）
   ⇒ `MainWindowXaml_EveryThemeResourceReferenceResolves` 失败；
2. 从第二套主题字典删掉 `<SolidColorBrush x:Key="StatusSuccessBrush" Color="#4CB782"/>`
   ⇒ `MainWindowXaml_DefaultAndLightThemeBrushKeySetsMatch` 失败。

同一次运行里**只有这两条**失败（`失败: 2，通过: 511`）—— §7 的 `RawColorRule` 基线用例仍绿，
证明它看不见这类问题，新门禁确实补的是空白而不是重复。
从字节级备份复原（`SHA-256 28F4F865…82A5`、`58741` 字节，逐位相同）后重跑 **513/513 全绿**。

**仍未做**：`HighContrast` 补键（A2，只在 HC 模式可见，需签字）、两组同义色漂移收敛（B，需艺术裁决）。
