# 2026-10-08 横向：S-13 的期望写实并与代码常量绑死

## 起因（我自己登记过的含糊）

round-97 加 S-13 时，期望只写了"`pageEvents` **如实列出**（有界、含 ×N 合并）"。**这不是可判定的期望**：
外部一方看到 3 条事件时，无法知道"是不是被截断了、总共有多少、重复怎么表示"。

## 改动

| 项 | 内容 |
|---|---|
| `BrowserSmokePlan` S-13 期望 | 改为写实：**最多保留最近 `{PageEventLog.DefaultCapacity}` 条**（=8，按**条数**截断、**不截断文本**）、连续重复**合并为 `(xN)`**、**总次数另计**、且**不用于继续交互** |
| 用例 | 新增 `TheEventReportingCheckStatesTheRealBoundFromTheCode`：断言 S-13 期望里出现**由 `PageEventLog.DefaultCapacity` 推出的数字**、`(xN)` 与 `pageEvents` —— 容量改了而清单没改 ⇒ **立刻变红** |
| 文档清单 | `Docs/14_reports/2026-10-09-浏览器自动化外部smoke清单.md` 的 S-13 行同步写实（8 条 / (xN) / 总次数另计） |

## 验证

| 项 | 结果 |
|---|---|
| `Pudding.DesktopServiceTests` | **314 / 314**（＋1） |
| **取红实测** | 把清单里的上界改成 `9 条`（模拟容量改了没同步）⇒ 新用例**变红**；还原 ⇒ 314/314 全绿 |
| 漂移门禁 | 脚本镜像与文档清单的既有漂移用例仍全绿（本轮只改期望文字，不动 Id/Gate/Area） |

## 顺带记录：本轮审计的两处"没有缺口"

为对账 G3/S-03 我依次查了两处，结论是**已覆盖**（不重复加用例）：

1. **operationId 账本**（`BrowserOperationLedger`）：15 条用例已覆盖"同 ID 不同请求拒绝、在途重传不重跑、
   终态重放、过期终态回 `receipt_expired`、**容量耗尽绝不淘汰在途项**、`Prune` 只清单终态"等；
   我特意核对 `ReclaimExpiredUnsafe` 只回收 `!IsRunning` 的条目 ✓ 与用例陈述一致。
2. **截图超预算的报错信息**（`ScreenshotPlan.DescribeBudget`）已包含**实测字节数 + 预算 + 可行做法**
   （降质/只截视口/提高预算），不是一句"资源耗尽"。

## 已知边界（诚实登记）

- **期望写实 ≠ 已验证**：S-13 仍需真机执行；本轮只是让"怎样算过"可判定。
- **8 是他方实现常数**：我按当前代码写实；若将来容量变化，本条与用例会一起提醒同步（这正是绑死的目的）。
- **`(xN)` 的合并只对**连续**重复生效**（不相邻的相同事件各占一条）——清单里未逐字强调这一点，
  属细小含糊，登记为可改进项。
- 无产品行为变化（清单文字 + 用例）。
