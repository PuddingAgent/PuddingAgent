# R3 审计：撤销三重机制

| 机制 | 证据 |
|---|---|
| **① `epoch` 前进（隐式失效）** | `SetUserTakeover`（`BrowserPageLifecycle.cs:124`）⇒ 接管/恢复/连接代际变化推进 epoch ⇒ `Revalidate` 判陈旧并拒（`DesktopService.cs:827` 文案："the admitted control or grant epoch is stale (takeover/resume/disconnect/revoke since admission)"）⇒ **接管/连接丢失无需逐条撤销即失效** ✓（外部复核 P0 的修法） |
| **② 显式撤销（能力驱动）** | `RevokeAllForCaller`（`BrowserTaskBindingService.cs:161`）**生产无内部调用点**（仅测试）⇒ 生产走能力：`DesktopService.cs:426` `_taskBindings.Revoke(revoke.Target, revoke.Task)` ✓ |
| **③ 结构性撤销** | `RevokePageAuthorization`（L237/L268）· `RevokeContextWideAuthorization`（L274→L319）· `RevokeExecutionScope`（L209，**保留只读**、与页面关闭区别对待）✓ |

## 关键闭环（R3 ↔ R4 真正连成链）

我在 R4 实现的 **`HostBrowserDelegationLifecycle.RevokeForRunAsync`** 正是**显式撤销请求的生产发起方**（发送 `ForBindingRevoke(binding.Task, binding.Target)`）⇒ **子运行收尾 ⇒ 端口发撤销 ⇒ DesktopService 受理 ⇒ 绑定服务撤销** ✓✓

**⇒ 没有"既不失效也不撤销"的触发类别** ✓
