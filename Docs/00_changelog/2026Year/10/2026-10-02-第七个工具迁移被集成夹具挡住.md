# 第七个工具迁移尝试：`browser_context` —— 被集成夹具挡住（已撤回，工作树绿）

## 本轮做了什么（未提交，已撤回）

1. 把 `BrowserContextTool` 迁到**两个**窄端口（`IDesktopBrowserCapabilitySurface` 读清单 +
   新端口 `IDesktopContextCapabilitySurface` 做 create/close）+ 上下文工厂；
2. 修好自己的一个语言坑：`CapabilityResult<T>` 是**非空值类型**，`is not { } x` 不可用
   ⇒ 改为 `read.IsFailure` 分支（编译期直接报 CS0165/CS0037）；
3. DI：把**同一个**路由实例注册为两个接口（否则用量计数分裂、退役判据不准）。

**通过的部分**：工具自身单测 **15/15**；构建 0 错误；`DesktopServiceTests` **170/170**。

## 被什么挡住（精确原因）

`PuddingHost.Tests` 里的**真实 WebSocket Bridge 集成测试**
（`BrowserAgentToolBridgeIntegrationTests.BrowserContextTool_TraversesAuthenticatedBridgeAndReturnsDesktopResult`）
失败于 `Assert.True(result.Success)`。

根因**不是生产缺陷**，而是夹具深度：

- 迁移后 `list` 走窄端口 ⇒ `BridgeBrowserCapabilitySurface.GetContextsAsync` 为了与 Desktop 侧
  **同形**会逐层解析实体：`context.list` → 每个上下文 `context.getInfo` → `page.list` →
  每个页面 `page.getInfo`（拿**活版本**与真实前进/后退标志）；
- 该夹具只应答第一条 `context.list`（所以测试能观察到 `BridgeCommandNames.ContextList` ✓），
  后续命令无人应答 ⇒ 适配器拿不到实体 ⇒ 工具如实失败；
- 迁移**前**该工具直接调 `runtime.ListContextsAsync`（一条命令就够）⇒ 夹具原样可用。
  ⇒ 迁移带来的往返增加是**刻意的**（同形 > 少往返），但夹具必须跟着升级。

## 下一步（可直接执行）

在 `Tests/PuddingHost.Tests/BrowserBridge/BrowserAgentToolBridgeIntegrationTests.cs` 的该用例里：

1. 把 `ContextList` 应答里的 `PageCount = 2` 改成 `PageCount = 0`（少两条 `page.getInfo`）；
2. 在 `var result = await invocation;` **之前**补两轮后续应答：
   - `context.getInfo` ⇒ `BrowserContextDescriptor`（`ContextId/UserDataDirectory`，`PageCount = 0`）；
   - `page.list` ⇒ `BrowserPageListDescriptor { Pages = [] }`；
   两者的 `CorrelationId` 都用收到的命令的 `OperationId`。

> 本轮我写好了这段补丁，但**锚点没匹配**（脚本因此在写盘前断言退出，什么都没改）——
> 失败原因是字面锚点 `        var result = await invocation;` 缩进与实际不符。
> ⇒ 下次先用 `Select-String -Context` 打印**待改行的原始缩进**再写补丁（本会话已多次栽在缩进/锚点上）。
