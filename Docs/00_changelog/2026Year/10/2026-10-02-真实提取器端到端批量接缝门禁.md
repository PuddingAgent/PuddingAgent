# 2026-10-02 真实提取器端到端批量接缝门禁

## 为什么补这一组

批量接缝此前只有**桩提取器**（TS/Python）与**内存 AdhocWorkspace**（C#）的用例 —— 它们锁定的是
接缝语义，不能证明「真工具链上产出的 payload 是对的」。而新链路**已在产品宿主启用**，
生产里跑的就是真实提取器，这段证据缺口必须补上。

## 改动

- 新增 `Source/PuddingCodeIntelligenceTests/Services/CodeSourceRealExtractorBatchTests.cs`（2 条）：
  用组件资产里的**真实** `Scripts/extract-ts-symbols.js` 与 `Scripts/extract-py-symbols.py`
  （测试输出目录已带 `Scripts/` 与 `node_modules`）跑真实源码：
  - 一个临时工程里两个真实文件（TS：`export class Alpha`、`export function betaHelper`；
    Python：`class Alpha`、`def beta_helper`）；
  - 一次 `UpdateFilesAsync` 调用 ⇒ 两个文件各自 `Applied`，payload 里的符号名与源码一致；
  - TS 侧断言 **`SessionKey` 非空**（真实提取器的项目模式确实可用 ⇒ 一批一次提取）；
  - 两边都断言 **store 没有被写**（批量接缝只回 payload）。
  - 资产/工具链缺失时用 `Assert.Inconclusive` 跳过，不让环境差异变成噪声。

## 验证

- `dotnet test Source\PuddingCodeIntelligenceTests` → **134 通过 0 失败**（本次 +2，无跳过）。
- `dotnet test Source\PuddingCodeIndexTests` → **332 通过 0 失败**。
- 结果说明：真实 TS 提取器的项目模式可用（`SessionKey` 非空），真实 Python 提取器按文件产出；
  两者都只在内存里产出 payload，落库仍由调用方的 `ReplaceFilesAsync` 负责。

## 未完成与影响

- 仅覆盖 TS/Python；C# 的真实 MSBuild 工作区端到端（`RoslynWorkspaceBootstrapper` 打开真实
  `.csproj`）仍只有内存 `AdhocWorkspace` 级证据 —— 需要 MSBuild 注册，属独立小刀。
- 已登记的剩余项：`ChangedDuringScan` 的生产来源（watcher 在合并批次时记录二次观测）；
  跨批次工程快照缓存。
- 仍待**进程外控制器重启 + 四场景受控复核**（这一次重启才会真正跑上本文件所验证的路径）。
