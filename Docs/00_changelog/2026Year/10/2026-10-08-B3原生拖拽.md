# 2026-10-08 B3 原生拖拽：分步移动 + 按下必抬起，DOM 模式明确拒绝

## 目标 / 背景

`drag` 一直是桩（`DragAsync => throw NotSupportedException`）。它是 B3 里最后一块 P1 输入能力，
而上一轮打通的 `DriverCall` 计划通道正好让它可以直接落地。

## 改动

| 层 | 改动 |
|---|---|
| Automation | `NativeInputSequence.PlanDrag(from, to, steps = 8)`：移动到起点 → 按下 → **分步**移动到终点（全程 `buttons=1`）→ 抬起；步数有上下限（`MaxDragSteps=64`，防调用方给出离谱步数把一次拖拽变成几千次 CDP 调用） |
| Abstractions | `IBrowserDriverPolicy.PlanDrag(...)`；`NullBrowserDriverPolicy` 返回 `null` ⇒ 不支持（驱动 fail closed） |
| 契约 | `DesktopInteractionAction.Drag` + `BrowserInteractRequest.ToLocator`；`ValidateShape` 强制**两端都给**（只有一个端点无法表达「拖到哪儿」）；线名 `"drag"` 入冻结清单 |
| 能力通道 | `Drag` 加入原生支持清单并映射到 `page.DragAsync(source, target, new DragOptions { InputMode })` |
| 驱动 | 原生实现：取两端包围盒中心 → `Policy.PlanDrag` → 逐条发 CDP；**DOM 模式抛 `browser_input_mode_not_supported`**（用脚本伪造拖拽在真实页面经常不生效，假装成功比拒绝更糟）；跨界面缺策略时同样明确 unsupported |
| 工具 | 新增 `to_locator` 参数；`action=drag` 缺目标时**明确报参数错**；`drag` 加入 `MapAction` 与原生支持清单 |

**为什么必须分步**：很多拖拽实现（HTML5 drag&drop、画布、滑块）依赖中间的 `mousemove` 序列，
只发一次跳跃移动会被忽略或落错位置；而**按下必然抬起**是这条链上最硬的约束。

## 验证

| 套件 | 结果 |
|---|---|
| `PuddingBrowser.AutomationTests` | **272 / 272**（＋2：拖拽序列与步数上限） |
| `DesktopSurface.BrowserTests` | **66 / 66**（＋1：两端与模式下传） |
| `AgentTools` · `Contracts` · `DesktopService` · `PuddingDesktop` · `Host` | 64/64 · 152/152 · 231/231 · 320/320 · 258/258 |
| 构建 | `WebView2` · `WinUI` · `WpfArchive` · `DesktopService` · `AgentTools` 全部**已成功生成** |

新增门禁：拖拽序列为 移动→按下→(N 步移动，全程 `buttons=1`)→抬起，坐标单调走向终点、首尾坐标正确；
步数 0 与超上限**拒绝**；能力通道把 `InputMode=Native` 与两个端点送进驱动（fake 记为 `drag:native`）；
契约的动作线名冻结清单更新为含 `"drag"`。

**取红实测**：把分步移动的 `buttons` 从 1 改成 0（＝拖动过程中不按住，等价于"没有真的拖"）⇒
`DragPressesAtTheSourceMovesInStepsAndReleasesAtTheTarget` **恰好变红**；复原后 272/272 复绿。

**顺带修掉一个真实隐患**：`MapAction` 原本没有 `"drag"` 分支 ⇒ 传 `action=drag` 会**落到 check/uncheck 的默认分支**
（把拖拽当成勾选执行）。这类"未知动作被默认分支吞掉"是危险的，现已显式映射。

## 已知边界（诚实登记）

- **真机未验证**：CDP 序列有纯函数测试，但"分步拖拽在真实页面（HTML5 拖放 / 画布 / 滑块）能否生效"
  必须由外部进程内 smoke 复核（本环境无 WebView2）。
- **DOM 模式不支持拖拽**（明确拒绝）：没有"脚本合成 drag 事件"的回退路径——那类合成事件在多数站点上不可靠。
- **不含模态键拖拽**（如 Shift+拖拽多选）：接口没有修饰键参数，需要时再加（`PlanPress` 已有修饰键位掩码逻辑可复用）。
- **拖拽不使用 `InputMode` 的 DOM 分支**，因此 `DragOptions.InputMode` 只有 `Native` 是有意义的取值。
- 工具层与能力层各自维护"支持哪些动作"清单（重复仍在，已多次登记）。
- `PuddingDesktop` 整体产物未重新生成（本机运行中的 Shell 占用输出文件）。

## 影响与回滚

- **行为变化（Agent 可见）**：`browser_interact` 新增 `action=drag`（要求 `input_mode=native` 与 `to_locator`）。
  其它动作不受影响；`drag` 在 DOM 模式下明确失败。
- 回滚：还原契约动作/字段、策略 `PlanDrag`、驱动实现、工具接线与四处测试/冻结清单。
