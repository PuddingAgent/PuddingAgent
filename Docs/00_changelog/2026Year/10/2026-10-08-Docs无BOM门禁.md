# 2026-10-08 横向：把"Docs 下 markdown 不得带 BOM"变成提交前就会红的检查

## 目标 / 背景

本会话被同一类**编码假设**咬了三次：

1. round-83：PowerShell 改写 fixture ⇒ 写入 BOM，被 fixture 编码用例抓到；
2. round-84：往 `.ps1` 加中文 ⇒ Windows PowerShell 按 ANSI 读无 BOM 脚本，**解析失败**；
3. round-85/86：`Set-Content -Encoding UTF8` 改 changelog 相对链接 ⇒ **写入 BOM**，
   Front Matter 门禁报"缺少 Front Matter"（BOM 让 YAML 不再从字节 0 开始）。

第三条此前只能靠 python 门禁**间接**发现，而且是在**下一个任务**里才发现（我已经提交了坏文件）。
本轮把它变成提交前就红的检查。

## 改动

`Source/Pudding.DesktopServiceTests/DocsMarkdownEncodingTests.cs`（新增，1 条用例）：

- 扫描 `Docs/**/*.md`（当前 **906** 个文件），断言：① **无 UTF-8 BOM**；② 以 `---`（Front Matter）开头；
- 失败信息**直接给出修法**（`UTF8Encoding($false)` 重写 / 用编辑工具 / 别用 `Set-Content -Encoding UTF8`）
  与**违规文件清单**，避免下一个接手人只看到一句断言失败；
- 附带扫描健全性检查（文件数 > 100），防止"路径写错导致扫了个空目录也全绿"。

## 验证

| 项 | 结果 |
|---|---|
| `Pudding.DesktopServiceTests` | **311 / 311**（＋1） |
| 当前合规性 | `Docs/**/*.md`：**0** 个带 BOM、**0** 个缺 Front Matter |
| **取红实测** | 故意给一个 Docs 文件写入 BOM ⇒ 用例**恰好变红**并列出该文件与修法；复原后 311/311 复绿 |
| python 门禁 | `front_matter --check Docs/00_changelog` 0 不合规（与仓库内检查互补） |

## 已知边界（诚实登记）

- **只管 BOM 与"是否以 `---` 开头"**：Front Matter 的 **12 项字段**是否齐全仍由 python 工具负责
  （仓库内检查不做字段校验，避免与工具重复实现）。
- **只管 `Docs/**`**：仓库其它位置的 markdown（如 `.pudding/skills/**`）不在本检查范围（按 `Agents.md`，它们另有规范）。
- **检查是"全仓库"的**：若他人后续提交带 BOM 的 Docs 文件，这条用例会红 —— 这是**有意**的（规则来自 `Agents.md`），
  且修法就在失败信息里。
- **不检查 CRLF/LF**：行尾风格在本仓库不构成门禁，本轮不动。

## 影响与回滚

- **无产品行为变化**（新增测试）。
- 回滚：删除 `DocsMarkdownEncodingTests.cs`。
