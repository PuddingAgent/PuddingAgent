# 2026-10-07 · Stage 5 治理：埋点约束升级为机器门禁

## 背景 / 动机

`Docs/08_how_debuge/02-日志位置与埋点约束.md` §9 早就规定了失败日志的必填字段，但那是**人读约束**：
删掉一个字段不会有任何机制报红。2026-10-07 事故难查的根因正是"失败路径只记了一句话"。
设计文档 §7 Stage 5 要求把可机械验证的部分变成断言——本刀落地。

同时补上**此前漏跑的消费者回归**：Stage 3 改了三个协议网关（`PuddingCore`），当时只跑了
`PuddingRuntimeTests`；`PuddingCoreTests` 才是这三个网关的直接回归面。

## 改动

| 文件 | 内容 |
|---|---|
| `Source/PuddingRuntimeTests/Diagnostics/DiagnosticContractGateTests.cs`（新，5 例） | ① 探测器**正/负控制**；② `[DirectLlm] STREAM ERROR/RETRY` 日志字段；③ 失败活动 `ErrorCode = cause?.Code`（带旧写法正控制）；④ 三个网关都有 `MarkDispatch` + `MarkHeaders`；⑤ 终态 DTO 带界面呈现与 `ReportText/ReportJson/EvidenceJson`，markdown 保留 §9 可定位字段 |
| `Docs/12_features/可诊断基础设施设计-2026-10-07.md` | 新增 §15：门禁内容、取红证据、未机械化部分的诚实登记 |

仓库根定位改用「向上找 `PuddingAgentNetwork.slnx`」，而不是 `AppContext.BaseDirectory` 固定上溯若干级——
上一刀的教训（用 `--artifacts-path` 跑全量时，固定层级的守卫测试产生假红）在这里被主动规避。

## 验证（实测）

```
dotnet test ...PuddingCoreTests                      → 已通过! 1059/1059（40s）——三个网关改动的直接回归面
dotnet test ...PuddingRuntimeTests --filter DiagnosticContractGateTests → 已通过! 5/5
```

**取红证据（变异测试）**：临时从 `OpenAiLlmGateway.ChatStreamAsync` 删掉一行 `MarkHeaders()` ⇒
`EveryGateway_RecordsRequestBytesAndPhase` **变红**，报告 `OpenAiLlmGateway.cs: 缺 MarkHeaders（阶段翻转）`；
恢复后复跑全绿，且 `git diff` 为空（逐字节还原）。
⇒ 门禁不是"永远绿"的摆设。

## 未机械化（诚实登记）

- §9 的 `conversationId/commandId/runId/eventSequence/projectionCheckpoint` 属命令链路（Conversation/Event 层），
  不在本刀范围，应由各自链路的守卫覆盖。
- 「每条 catch 都传了原始异常」无法用文本断言可靠验证（需要分析器），暂以评审 + 字段断言兜底。
- 关联 ID 的落库列（`turn_id/attempt`）仍属 Stage 4-c。

## 未完成（沿用上一刀清单）

- **前端**（Stage 4-b）：错误卡按 `causeCode` 映射 +「复制诊断信息 / 下载 JSON」按钮 + 历史同载荷；
  改动须递增 `package.json` 版本并重新构建部署 `wwwroot/admin`。
- **Stage 4-c**：`cause_code/phase/attempt/request_bytes/turn_id` 落索引列 + 一次查询事故面；`ChatAsync` 作用域；
  `providerId` 与多次尝试明细。
