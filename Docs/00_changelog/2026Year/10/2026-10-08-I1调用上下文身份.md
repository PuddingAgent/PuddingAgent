# 2026-10-08 I1 第二步：Desktop 调用上下文携带类型化 caller

## 改了什么

| 件 | 变化 |
|---|---|
| `Source/Pudding.Contracts/DesktopCallContext.cs` | 新增 `BrowserCaller`（`BrowserCallerIdentity?`，构造器**可选**参数，兼容既有调用点）＋ `TryGetBrowserCaller(out caller, out reason)` |
| `Source/Pudding.ContractsTests/Desktop/DesktopCallContextCallerTests.cs`（新，7 条） | 覆盖：可省略（非浏览器）、Agent 可准入、SubAgent 保留父任务、缺身份拒绝、**User 冒充拒绝**、无运行身份拒绝、类型层拒绝非法标识 |

`TryGetBrowserCaller` 的三条拒绝理由（互不混淆，便于外部观察）：

1. `the Desktop call carried no trusted browser caller identity` —— 没有身份；
2. `a browser automation operation cannot be admitted as a User caller` —— **§3.2 明写**：浏览器工具不能构造 User kind 绕过闸门（用户原生操作走独立可信入口）；
3. `the browser caller carries no run identity; the authorization cannot be bound to a task` —— 授权要绑定到一次具体运行（才可撤销/回收）。

## 为什么先做契约

计划要求「两传输同步升级」，而两传输（能力通道 gRPC / Bridge WebSocket）都要携带**同一个**类型化身份。
先把"通用 Desktop 上下文可携带、浏览器操作必须校验"这一层定下来并测住，下一步的 proto/Bridge 字段、版本升 v2
与两侧映射才有唯一真源；否则两个传输会各自演化出不同的身份语义——正是设计 §1.1 要避免的"两条传输各自验出相反结论"。

## 验证

| 项 | 结果 |
|---|---|
| `Pudding.ContractsTests` | **173 / 173**（＋7） |
| 类型层非法标识 | 空/空白、超 `MaxLength`、未注册枚举、**子代理缺父任务** 一律构造即失败 |
| **全量链** | **1637 / 0**、**经重跑**：Host 首次失败是**已登记的时序 flake**（`LlmConfigurationLoad_DoesNotDeadlock…`，脚本判定 'all of them are on the known-flaky registry'，累计第 2 次），重跑转绿；其余 6 套件首跑即绿 |
| code_map | `DesktopCallContext.cs` 条目已更新（只写"现在是什么"） |

## 诚实边界（诚实登记）

- **尚未上线缆**：`CapabilityCommand` / Bridge envelope 还没带 caller，两协议版本仍是 v1 —— 也就是说**当前真实请求里 `BrowserCaller` 仍是 null**，本条只是契约前置。
- **尚未有准入调用方**：`Admit` 仍未在活路径被调用（I2 的授权闭环未施工）。
- **`DesktopCallContext` 是通用类型**：非浏览器调用可省略 caller；"浏览器操作必须带"这一约束由**准入点**落实（下一批），本类型只提供判据。
- **未真机验证**；② 250ms、③ flake、④ 指纹仍按方案的独立切片处理。
