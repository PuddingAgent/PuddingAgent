# 2026-10-22 画布标注回读运行时验收

## 背景

`bf89a62` 交付「画布标注经只读快照交给 Agent」：Desktop 每 2 秒把 `puddingAnnotation.take()` 的原文写进
`{DataRoot}/panels/panel-{id}.annotations.json`，Core 侧 `read_panel` 读同一文件并把标注原样返回。
此前只有单元测试（Core 12 例 + Foundation 8 例 + 变异取红），**运行时链路从未验收**。
`77ce380` 已部署并启动（Desktop PID 31128 / Core PID 104868，构建耗时点 13:30，启动 13:32），
故本轮在真实进程上补做验收。

## 验收方法

用户尚未在面板上落笔，`D:\Data\panels` 只有 `panel-acceptance.json` 与 `panel-main.json`，
**没有** `*.annotations.json` —— 这是「还没有笔迹」的正常状态，不能当作缺陷证据。
因此改用**合成快照 + 一正一负对照**，直接打到运行中的 Core：

1. 手写 `panel-acceptance.annotations.json`（`schemaVersion=1`、`panelId=acceptance`、`updatedAt`、
   `payload` 用 `take()` 的真实形状：`src/width/height/naturalWidth/naturalHeight/items[]`），
   UTF-8 无 BOM 写入并断言写入字节数与逐字回读一致；
2. 调用 `read_panel(panel_id=acceptance)`；
3. 删除该文件后再调用一次（负对照）；
4. 对部署产物做字面量探针，确认 Desktop 侧写链路确实编进了在跑的二进制。

## 结果

| 项目 | 结果 |
|---|---|
| 合成快照写入 | 344 B，`ROUNDTRIP_OK=True` |
| 正对照 `read_panel` | `annotations` 逐字回显（含两条 item），`annotationsUpdatedAt=2026-10-22T06:40:00+00:00`，`annotationsTruncated=false`，`annotationsNote` 给出像素→0..999 换算说明 |
| 负对照 `read_panel` | 删除文件后 `annotations=null`、`annotationsUpdatedAt=null`、`annotationsNote=null`，工具本身仍成功返回面板内容（`exists=true`、`revision=2`） |
| 探针：Foundation 字面量 `.annotations.json`（UTF-16LE） | True |
| 探针：Desktop 字面量 `puddingAnnotation.take()`（UTF-16LE） | True |
| 探针：Desktop 方法名 `PublishPanelAnnotationsAsync`（UTF-8 #Strings） | True |
| 探针：阳性对照 `pudding-image`（UTF-16LE） | True |
| 探针：负对照 `.annotations.jsonXYZ` | False |

结论：**标注回读（Core 读 + DI + 工具 + 提示文案）在部署实例上成立**，且失败路径是「降级为无标注」而不是让
`read_panel` 失败；写链路已编入在跑的 Desktop，但真实落盘仍需用户画一笔（2 秒轮询 + 非空原文才会写）。

## 仪器教训

第一版探针用 UTF-8 解两个 DLL 找字面量，得到 `False`；同一调用里 `pudding-image` 这个**已知存在**的
字面量也是 `False` —— 对照组先红，说明是**仪器坏了**而不是结论变了：.NET 的用户字符串字面量在 `#US` 堆里
是 UTF-16LE，只有方法名在 `#Strings` 堆里是 UTF-8。改用 `Encoding.Unicode` 后四项全 True、负对照 False。
往后探测「某字面量是否编进程序集」一律：**字面量按 UTF-16LE、方法名按 UTF-8**，且必须带已知存在的阳性对照。

## 新发现：清空与恢复的语义冲突（未修，待设计裁定）

快照写入刻意**拒绝空原文**（空串会盖掉用户上一轮真实笔迹）。一旦后续做「面板重绘后把笔迹灌回去」的恢复机制，
冲突就出现了：用户点「清空」后 `take()` 返回 `items: []`（非空原文，但无笔迹），若清空也照写，恢复会把已删的
笔迹画回来；若清空不写，磁盘上仍是旧笔迹，恢复同样会画回来。⇒ 恢复机制上线前必须先定义
「清空」的可持久标记（例如快照里带 `clearedAt` 或 `items:[]` 视为显式清空并参与去重），否则恢复=踩用户。
