# 浏览器定位 kind 线名不匹配

## 现象（本机实测，逐字回执）

授权验收流程走到“指向元素”这一步时全部失败，而同一时刻**建页、导航、快照都正常**：

```text
browser_tabs(new)     → ok=true, pageId=aa7e3e2e…, pageVersion=1
browser_navigate      → ok=true, statusCode=200, title="Pudding 本地浏览器验收", pageVersion=2
browser_snapshot      → ok=true, 读到 textbox「测试标记」/button「验证提交」/status「尚未提交」
browser_locate(role)  → ok=false browser_invalid_command: locator kind 'Role' is not registered (no guessing, no fallback)
browser_locate(css)   → 同上（Css）
browser_interact(fill) → 同上（Ref）
```

`Ref` / `Css` / `Role` 三种都被拒 ⇒ **不是个别策略选错，而是十种定位全部失效**。

## 根因

线缆上 `BrowserLocatorDescriptor.Kind` 是**字符串**，两端对它的解释不同：

| 端 | 位置 | 行为 |
|---|---|---|
| 发送（宿主） | `Source/PuddingHost/BrowserBridge/RemoteBrowserPage.cs` `ToDescriptor` | `Kind = locator.Kind.ToString()` ⇒ 送出**枚举名** `"Role"` / `"AltText"` / `"TestId"` |
| 接收（Desktop） | `Source/PuddingDesktop.WpfArchive/Browser/BrowserBridgeCommandAdapter.cs:661` `TryMapLocator` | `DesktopLocatorKindWire.TryParse(wireLocator.Kind, …)` ⇒ 只认**线名** `role` / `alt-text` / `test-id` |

`DesktopLocatorKindWire`（`Source/Pudding.Contracts/Desktop/LocateContracts.cs`）是线名的唯一真源，
且 `TryParse` 使用 `StringComparison.Ordinal` **严格解析、不猜测、不回退**（这是刻意设计，避免歧义线名被猜成别的策略）。
两套命名空间不相交，因此每一次定位请求都在参数校验阶段被拒，执行器根本没被调用。

注意 `Ref` / `Css` 的线名也不是枚举名（`ref` / `css`），所以这不是“个别 kind 命名不一致”，而是**发送端整体用错了命名空间**。

## 修复（`d38b6cd`）

发送端改为经真源输出线名，并把映射收敛为一个可测的私有方法：

```csharp
private static BrowserLocatorDescriptor ToDescriptor(Locator locator) => new()
{
    Kind = LocatorWireName(locator.Kind),   // 原来是 locator.Kind.ToString()
    …
};

internal static string LocatorWireName(LocatorKind kind)
{
    if (!Enum.TryParse<DesktopLocatorKind>(kind.ToString(), ignoreCase: false, out var desktopKind))
        throw new BrowserOperationException(…, $"locator kind '{kind}' has no wire equivalent");
    return DesktopLocatorKindWire.NameOf(desktopKind);
}
```

- 两套枚举的成员名**一一对应**（`DesktopLocatorKind` 注释即声明“与 `PuddingBrowser.Abstractions.LocatorKind` 等价，取值为线名真源”），因此按成员名过渡一次即可；
- 若两套枚举将来发生漂移，`TryParse` 失败 ⇒ **响亮抛错**，不静默退化成语义不同的策略；
- 只动发送端一行语义，未触及接收端的严格解析（保持 fail closed）。

## 验证

- `dotnet build Source/PuddingHost/PuddingHost.csproj` → **0 个错误**（141 个警告，均为既有警告）。
- 回归测试 `Tests/PuddingHost.Tests/BrowserBridge/RemoteBrowserPageLocatorWireTests.cs` 已写好：
  用**接收端的真实解析器** `DesktopLocatorKindWire.TryParse` 断言十种 kind 的输出可被解析且解析回同一策略，
  另有一条“取红哨兵”断言 `kind.ToString()`（旧实现）**不是**合法线名。

  本机曾同时存在 24 个 `dotnet.exe` 与 1.3 GB `VBCSCompiler`），已取消作业；
  因此本提交只含生产代码，测试文件待构建空闲窗跑通后再提交。

## 生效条件与验收方法

修复在 **Core 进程**（`PuddingHost`）内，须重启 Core 才生效。重启后的判据是**错误码变化**，不看“是否重启过”：

1. `browser_locate` 用 `role` + `name="测试标记"` 应返回 1 个命中（而不是 `browser_invalid_command`）；
2. `browser_interact(fill)` 返回 `verification=verified`，且回读值等于写入值；
3. 继续“单击验证提交 → 快照读回执编号 → 截图报 observationId”。

## 方法与教训

1. **“能导航”不等于“能交互”**：发现面（contexts/tabs）、导航面、元素面是三条不同的链，逐条验证，不要用前一步的成功推断后一步。
2. **错误文案先找唯一来源行**：`is not registered (no guessing, no fallback)` 在仓库中只有一处产生点，直接定位到行即可，胜过猜三层调用。
3. **部分覆盖的 0 命中不是阴性**：本轮 `search_grep` 在 `Source` 根撞到 2000 文件枚举上限（`coverage: partial`），
   真正命中的文件在未被扫描的 WPF 工程目录里；必须缩小目录或换索引工具重查。
4. **终端工具本身就可能是坏仪器**：本轮 `shell` 在本机持续 `exit=1` 且无任何输出（连 `dir` 亦然），改用 `terminal_start` / `terminal_wait` 才拿到真实回执。

## 边界

- 未改接收端的严格解析策略，未放宽任何 fail-closed 检查。
- 未验证站点侧行为（反爬、登录态、截图），它们与本次缺陷无关。
- 未重启 Core；本轮只交付“源码修复 + 编译通过 + 待执行回归测试”。
