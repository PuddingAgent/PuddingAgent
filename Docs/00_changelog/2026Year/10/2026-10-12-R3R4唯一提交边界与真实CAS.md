# 2026-10-12 R3+R4 修复：唯一提交边界与真实 CAS

> 依据：[复核与验收判定](../../../14_reports/上下文治理实施复核与验收判定-2026-10-12.md) §4（R3）、§5（R4），两项均为 P1。

## 1. 缺陷

**R3（提交顺序）**：`AgentExecutionService.TryWarmPrefixCompactionAsync` 先在临界区内
`durableHistory.Clear(); AddRange(AppliedMessages)`，**再**尝试 `CommitWarmPrefixCheckpointAsync`；
落库失败时只记 `durableSkipReason` 而**不回滚内存** —— 等于「内存-only 成功」，DB 仍是旧历史。
`ContextCompactionService` 侧只用一次 `SaveChangesAsync`（隐式事务）且代次推进是
`session.CompactionGeneration = target`（先读后写，非条件更新），并发写入不会撞车。

**R4（CAS 输入）**：`VerifyApplication` 构造 `CurrentContextDescriptor` 时把
`Generation/RouteVersion/ToolSpecVersion` 直接取 `plan` 的冻结值 ⇒ 这三项**永远相等**，
CAS 变成同义反复（复核探针：路由 A→B 之后仍 `CanApply=true`）。
另外：路由版本只看 `ModelId`（同名模型换 Provider/Endpoint/协议不失效）；
消息身份不含**工具调用参数**、思维链与有序内容部件（「同一 tool 换参数」被判为未变）。

## 2. 修复

### 2.1 R4：提交时真实当前值

- `WarmPrefixCompaction.VerifyApplication` 新增 `CurrentContextValues? currentValues` 参数
  （generation/route/tool 版本）；**为 null 一律拒绝**（`current_context_unavailable`）——
  从接口上消除「拿冻结值自比较」的可能。
- 调用方在**锁内**重新读取代次（`GetCompactionGenerationAsync`）、按当前 config 重算路由、
  按当前工具清单重算 tool spec，再构造描述符。
- `ResolveRouteVersion` 纳入 **Provider（由调用方给出）、Endpoint 主机、模型、协议、容量三元组**；
  `ResolveToolSpecVersion` 提升为 `internal` 以便调用方在提交时重算。
- `ComputeMessageIdentity` 覆盖**思维链 + 工具调用参数 JSON + 有序内容部件**（文本用正文，
  非文本用规范 JSON）。
- `TryCreatePlan` 透传 `providerId`，使冻结与提交两处用同一路由身份算法。

### 2.2 R3：唯一提交边界 + 事务内真实 CAS

`ContextCompactionService.CommitWarmPrefixCheckpointAsync`：

1. `BeginTransactionAsync`；
2. **先插摘要行与覆盖清单**并 `SaveChangesAsync`（覆盖标注的外键指向摘要行，必须先存在）；
3. **条件推进代次**：`UPDATE Sessions SET CompactionGeneration = target
   WHERE SessionId = @id AND CompactionGeneration = @expected`，受影响行数必须为 1，
   否则回滚并返回 `GenerationMismatch`；
4. **逐行条件覆盖标注**：`UPDATE Messages SET CompactedBy = @summary, CanonicalContentHash =
   COALESCE(...) WHERE MessageId = @id AND SessionId = @sid AND CompactedBy IS NULL`，
   每行受影响行数必须为 1，否则回滚并返回 `AlreadyCovered`；
5. `CommitAsync`。

`AgentExecutionService`：先提交，**只有 `Committed` 才替换内存**并登记完成；否则显式保留原历史
（`durableApplied=false`），拒绝原因如实写进日志/`context.compaction.failed` 事件
（`compaction_service_unavailable` / `durable_commit_*` / `durable_commit_failed`）。
落库抛异常时降级为拒绝（维护是可选能力，不得中断安全消息），取消则照常向上传播。

### 3.1 新增用例（逐项取红语义）

**R4（`WarmPrefixCompactionApplyTests`，6 条）**：
① 不提供当前值 ⇒ `current_context_unavailable`（防同义反复）；
② 代次变化 ⇒ `generation_changed` 且不给 `AppliedMessages`/`AfterSnapshot`；
③ 路由变化（换 Endpoint/协议/容量）⇒ `route_changed`；
④ 工具清单变化 ⇒ `tool_spec_changed`；
⑤ **只改工具调用参数** ⇒ 消息身份必须变化且 `history_revision_changed`；
⑥ 对照：什么都不变 ⇒ 仍 `applied`（证明不是"一律拒绝"）。

**R3（`WarmPrefixMidTurnHardProtectionE2ETests`，2 条，走真实 `ExecuteAsync`）**：
① 持久服务不可用（`contextCompactionService: null`）⇒ Turn 仍到终态，但**内存历史不含 checkpoint
前导语**、DB 零写入（无摘要/无标注/无清单/代际仍 0）、日志有拒绝且无"已提交"；
② **摘要调用期间**另一个持久压缩把代次推到 1（真实并发窗口：候选在摘要前冻结、提交在摘要后）⇒
拒绝、代际仍是 1（未推进到 2）、内存未被替换、DB 零写入、日志原因含 `generation_changed`。

### 3.2 全量回归

- `PuddingRuntimeTests`：失败 4 / 通过 2054 / 跳过 6。4 个失败**全部**是终端/宿主 Shell 用例
  （`HostShellExecutor_Sets_Utf8_Python_Output_Environment`、`TerminalWait_*` ×3），单独跑同样失败，
  根因是 PATH 上的 `python` 是 Windows Store 别名桩（exit 9009 "Python was not found"、
  `Get-Command python` → `WindowsApps\python.exe` Version 0.0.0.0）⇒ **环境性**、与本批无因果，
  按复核要求如实登记且不冒充「相同基线」。
- `PuddingMemoryEngineTests`：失败 3（既有环境依赖 ContextPipeline 用例，与上批同名同因）。
- `PuddingPlatformTests`：0 失败。

本批**没有**取到「字面的红→绿」证据：R4 的 6 条门禁与 R3 的 2 条端到端用例都是在实现完成后编写的，
其中 R4 ① 与 R3 ② 直接对应复核探针的两条结论（同义反复 CAS、代次冲突仍应用）；
旧实现的因果链是改动前逐行读源码确认的（`plan` 复制 + 先内存后落库），未在旧提交上重跑这 8 例。
