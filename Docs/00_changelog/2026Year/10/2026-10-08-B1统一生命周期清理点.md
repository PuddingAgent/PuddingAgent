# 2026-10-08 B1 生命周期：统一清理点 BrowserPageLifecycle，关闭时授权与租约一起清

## 目标 / 背景

设计方案 §3.3：新增统一生命周期端口，「人工 UI 和两种传输均通过该端口创建/关闭 context/tab」，
且**关闭后同时清掉 UI、两个注册表、grant、ref/cursor 和租约**。

此前关闭路径分散在两处（`BrowserWorkspaceTargetBridge.OnPageClosed/OnContextClosed` 自己清两个注册表），
而"授权与租约"根本没有归属 —— 权威实例直到本轮之前都只被控制面读，没人负责在关闭时清理它。
审计（2026-10-08 结论 #1/#2）里那类"两处状态不一致"的缺陷，正是这种归属缺失的产物。

## 改动

| 文件 | 改动 |
|---|---|
| `Source/Pudding.DesktopService/BrowserPageLifecycle.cs` | **新增**：页面/上下文生命周期的唯一清理点。`ClosePage`/`CloseContext` 一次做完四件事 —— 从**两个**注册表移除、撤销该页**全部**授权（连只读一起撤）、释放它的写租约；结果按项报告（`WasRegistered`/`PagesCleared`/`GrantsRevoked`/`LeaseReleased`/`ExecutionScopeRevoked`/`GrantEpoch`），因此"清没清干净"可判定。`Create(desktopId, processInstanceId)` 构造进程唯一的端口（内含权威与两个注册表），使 Shell 组合根**不必引用 Automation 组件**，也不可能把另一份注册表配错进来 |
| `Source/Pudding.DesktopService/DesktopTargetRegistry.cs` | 新增 `PagesInContext(contextId)`：关闭上下文前必须先取页面清单（注册表移除后就查不到，而授权是按页绑定的） |
| `Source/Pudding.DesktopService/DesktopCapabilityChannelComposition.cs` | `StartAsync` 的 `pageTargets` + `authority` 两个参数**合并成一个** `BrowserPageLifecycle`：分开传就允许"注册表来自 A、权威来自 B"，那等于又出现两份控制权状态（§3.1） |
| `Source/Pudding.DesktopSurface.Browser/BrowserWorkspaceTargetBridge.cs` | 构造函数只接受 `BrowserPageLifecycle`；`OnPageClosed`/`OnContextClosed` 把清理交给它（不再自己拼步骤），两个注册表从端口取 |
| `Source/PuddingDesktop/Hosting/DesktopApplicationCoordinator.Capability.cs` | 组合根改为**一个** `BrowserPageLifecycle.Create(...)`，桥接与能力通道共用它（原先各自 `new` 三个对象） |

**两处刻意的设计选择**：

1. **关闭与"切换 Agent 目标"的区别显式区分**：切换用 `RevokeExecutionScope`（**保留**只读授权，
   用户还想看），关闭撤销**全部**授权 —— 页面都不存在了，"还能读"没有意义。
2. **先放租约、后撤授权**：撤销授权时权威会顺带释放已失效租约，若反过来做，
   "租约到底是不是这次释放的"就无法如实报告（第一版实现就是这样，被测试抓出回执撒谎）。

## 验证

| 套件 | 结果 |
|---|---|
| `Pudding.DesktopServiceTests` | **215 / 215**（原 208 ＋ 7） |
| `Pudding.DesktopSurface.BrowserTests` | **58 / 58**（原 57 ＋ 1） |
| `PuddingDesktop.Tests` · `PuddingHost.Tests` · `PuddingBrowser.AutomationTests` · `ContractsTests` | 301/301 · 252/252 · 187/187 · 97/97 |
| `build` `Pudding.DesktopService` · `Pudding.DesktopSurface.Browser` · `PuddingDesktop` | 0 错误 |

新增门禁（关键几条）：

- `ClosePage_ClearsBothRegistries_AndRevokesTheGrant`：两个注册表都清、授权**全清**（含只读）；
- `ClosingAPageRevokesMoreThanSwitchingTheAgentTarget`：把"关闭 vs 切换目标"的差别钉死
  （切换后只读授权仍在）；
- `ClosePage_ReleasesTheWriteLeaseHeldForIt`：先用真租约（`Admit` 一个写操作）再关闭，
  断言 `ActiveLease` 变 null **且回执如实说 `LeaseReleased`**；
- `ClosePage_IsIdempotent_AndStillRevokesStaleAuthorization`：重复关闭时注册表已无该页，
  但新签发的陈旧授权**仍被撤销**（失败安全）；
- `CloseContext_ClearsEveryPageAndItsAuthorization` / `CloseContext_DoesNotTouchAnotherContext`；
- `StartAsync_UsesTheProvidedLifecycle_InsteadOfCreatingItsOwn`：组合根用的就是传入的实例
  （`Assert.Same` 权威与页面注册表）；
- `ClosingAPage_AlsoRevokesItsAuthorization`（桥接层）：关闭事件确实走到了清理点。

**取红实测**：把 `ClosePage` 里的 `RevokePageAuthorization(target)` 换成 `(0, false)`（不再撤授权、放租约）⇒
`Pudding.DesktopServiceTests` **4 条**、`DesktopSurface.BrowserTests` **1 条**恰好变红，其余全绿；
复原后 215/215 与 58/58 复绿。

## 已知边界（诚实登记）

- **权威与注册表仍只在「能力通道启用」时构造**：`StartCapabilityChannelAsync` 在关闭态
  （默认配置，走 WebSocket Bridge）会提前返回，因此那时**没有**权威实例、注册表与生命周期端口，
  Bridge 路径也没有消费它们。把创建上提到进程启动、并让 Bridge dispatcher 读同一权威，
  仍属后续切片（本轮把"唯一所有者"这个前提做出来了，但它目前只在启用态存在）。
- **UI 与 ref/cursor 的清理未纳入**：§3.3 要求的"关闭后清 UI、ref/cursor"里，UI 归 Shell 事件、
  ref 登记表尚未接入驱动（`BrowserRefRegistry` 仍未被生产代码消费），本轮只覆盖两个注册表 +
  授权 + 租约。
- **创建侧未迁移**：设计要求"创建/关闭都走统一端口"，本轮只做了关闭侧；页面创建仍由
  `BrowserWorkspaceTargetBridge.OnPageCreated` 直接登记。
- 桥接路径的授权闭环（`Admit`/租约）仍等可信调用方身份跨进程传递（见 code_map 已知缺口）。

## 影响与回滚

- **行为变化**：`DesktopCapabilityChannelComposition.StartAsync` 的参数由
  `pageTargets + authority` 变为 `lifecycle`；`BrowserWorkspaceTargetBridge` 构造函数由两个注册表
  变为一个生命周期端口。关闭页面/上下文现在会**额外撤销授权并释放租约**（原先不会）。
- 无数据/配置影响；线缆 DTO 与 proto 未改动。
- 回滚：删除 `BrowserPageLifecycle.cs` 与其测试，还原桥接/组合根/协调器/注册表与 code_map。
