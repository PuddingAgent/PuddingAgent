# 2026-10-08 B2 定位：locate 输出按设计收敛，动作拒绝三态各给正确重试建议

## 目标 / 背景

设计 §6.2 对定位结果定了四条输出规则与一条安全规则：

- 输出：`includeHidden=false`、`limit=10`；结果默认 ref/role/name/必要状态，
  **省略与 name 相同的 text**；**bbox 展示保留最多一位小数**（驱动内部保留精度，
  且不把展示四舍五入值用于实际点击）；`value`/`selectedValues`/`checked` **可显式请求**；
- 安全：**匹配歧义必须明确拒绝，不静默选第一个**；隐藏/禁用/遮挡目标不按成功处理。

调研发现：驱动侧的安全规则**已经实现**（交互脚本对 `matches.length > 1` 返回
`browser_locator_ambiguous`，并对不可见/禁用目标拒绝），但**工具侧的输出规则一条都没做**，
而且这些拒绝在新接入的回执链路上被当成 `internal_error`（= 可能已产生副作用 ⇒ "先观察"），
把调用方**指向了错误的修复方向**。

## 改动

| 文件 | 改动 |
|---|---|
| `Source/PuddingBrowser.AgentTools/BrowserToolContracts.cs` | 新增**元素展示投影的唯一实现** `Element(DesktopElementRef, includeValue, includeChecked)`：text 与 name 相同则省略、bbox 保留一位小数（负零归一成 0）、checked/value 显式请求。两个工具共用 ⇒ 规则不会各写一份 |
| `Source/PuddingBrowser.AgentTools/BrowserLocateTool.cs` | 新增 `limit`（**默认 10**，1..100，越界返回参数错误而不是抛异常）与 `include_checked`；改用共享投影 |
| `Source/PuddingBrowser.AgentTools/BrowserInteractTool.cs` | 改用共享投影（保留 `checked`：交互后"到底勾上没有"是直接证据；表单值仍不回显） |
| `Source/PuddingBrowser.AgentTools/BrowserOperationFailure.cs` | §6.2 的动作拒绝三态各自映射：`browser_locator_ambiguous` ⇒ 不可重试 + 「用 nth 或更具体的定位」；`browser_element_not_visible` ⇒ 不可重试 + 「滚入可见或换目标」；`browser_element_disabled` ⇒ 不可重试 + 「等它可用」；`browser_element_not_found` ⇒ **可重试** + 「等待或重新观察」（零命中不等于"定位方式全坏"） |

## 验证

| 套件 | 结果 |
|---|---|
| `PuddingBrowser.AgentTools.Tests` | **36 / 36**（原 31 ＋ 5） |
| `PuddingHost.Tests` · `PuddingDesktop.Tests` · `PuddingBrowser.AutomationTests` · `DesktopServiceTests` | 252/252 · 305/305 · 194/194 · 215/215 |

新增门禁：

- `Locate_AppliesTheDesignOutputRules_AndTheDefaultLimit`：默认 `limit=10` 确实传到能力层；
  `text == name` 时 `text` 为 null；`checked` 默认为 null、显式请求时给出；
  bbox 由驱动的 `10.25 / 20.5 / 80.04 / 30.75` 展示为 `10.3 / 20.5 / 80.0 / 30.8`；
- `Interact_DriverRejections_MapToTheRightRetryAdvice`（4 个 Theory 用例）：四种驱动拒绝都报
  `not_started` + `mayHaveSideEffects=false`，重试建议与提示片段分别正确，且**一次驱动动作都没发生**。

**顺带修替身缺陷**：`FakeCapabilitySurface.LocateAsync` 原先不映射 `BoundingBox`
（导致定位输出永远没有几何），`FakeBrowserPage` 也没有"按驱动语义抛拒绝异常"的开关。
两处都补上——否则上面两条测试根本无法成立。

**取红实测**（两次）：

1. 去掉 `browser_locator_ambiguous` 的映射（退回 `internal_error`）⇒ 该 Theory 用例**恰好变红**；
2. 恢复"总是返回 text"（不再省略与 name 相同的 text）⇒ 定位输出规则用例**恰好变红**。
   两次复原后 36/36 复绿。

## 已知边界（诚实登记）

- **`includeHidden` / `cursor` / `inViewportOnly` / `fields` 未实现**：它们需要
  `BrowserLocateRequest` → `Locator`（Abstractions）→ 驱动脚本的整条链路改动，
  属下一批（驱动脚本的真机行为在本环境无法验证）。
- **`visible` 与 `inViewport` 未分离**：目前只有 `visible`（含"有尺寸"），没有独立的视口内标记；
  §6.2 要求的「屏外但有尺寸的元素仍可定位；写操作先滚入可见区域并复检」因此只有驱动侧的一半
  （不可见即拒绝），没有"先滚入再复检"。
- **驱动侧几何/隐藏过滤的运行时行为未验证**：本环境无法跑真实 WebView2，
  所有脚本行为仍只有脚本文本断言与替身近似。
- **`text` 定位的重复文本消歧与"最小可见匹配节点"**（§6.2 第一段）仍依赖驱动脚本现状，
  未做确定性测试；歧义拒绝只覆盖交互路径，定位路径仍返回多条（这是**诚实列举**，不是静默选第一个）。

## 影响与回滚

- **行为变化（Agent 可见）**：`browser_locate` 默认只返回 10 条（原 20，输出侧截断 100 不变）；
  `text` 与 `name` 相同时不再重复返回；`checked` 默认不返回（需 `include_checked=true`）；
  bbox 变为一位小数；`browser_interact` 的 `browser_locator_ambiguous` 等拒绝现在给出正确的
  重试建议（此前会误导成"先观察、勿重做"）。
- 无数据/配置影响；线缆 DTO 与 proto 未改动。
- 回滚：还原上表 4 个生产文件与测试文件及 code_map。
