# 2026-10-08 全文索引新增 per-scope 新鲜度只读探针（A23，组件侧 S1–S4）

> 范围：`Source/PuddingFullTextIndex/Contracts/`（新增 2 契约）、`Source/PuddingFullTextIndex/Infrastructure/Search/LuceneSearchEngine.cs`、`Source/PuddingFullTextIndexTests/FullTextIndexFreshnessProbeTests.cs`（新增 3 例）

## 问题（改动前）

`search_grep` 的 `backend=index` 路径已经在报 `complete` / `limit_reason`（其中 `stale_index_paths` 表示「索引命中的路径已不存在」），但它**读不到索引本身有多旧**：

- 命中 0 条时，调用方无法区分「索引里真的没有」与「索引是三天前建的、源文件昨天才改」；
- 后一种情况下那句 `(no matches)` 会被读成「语料里不存在这个模式」—— 正是 ADR-089 §8 硬约束 6 明禁的**假否定**；
- 而这两个事实的原料其实**已经在磁盘上**：每个作用域的索引目录里有 `.last_indexed`（`{"t":…,"p":…}`，引擎自用于增量构建比较），以及该目录自身的 mtime（既有的 per-scope 新鲜度判定口径 `IFullTextIndexSupplyComposition.LiveIndexLastWriteUtc`）。缺的是**把原料读出来的只读接缝**。

## 改动

1. **新增契约**（`Contracts/`）
   - `FullTextIndexFreshnessState`：`Missing`（索引目录不存在）/ `StampUnreadable`（目录在但 `.last_indexed` 缺失或损坏 ⇒ **读不出**）/ `Available`。
   - `FullTextIndexFreshness`：`State` + `LastIndexedAtUtc`（`.last_indexed.t`，语义 = 上次索引**扫描**时刻）+ `PatternFingerprint`（12 位）+ `IndexDirectoryLastWriteUtc`（**该 scope 自己的** live 索引目录 mtime）+ `StampAgeAt(nowUtc)`。只上报事实，**不含**「该不该重建」的判定策略（那是 `IndexPrebuildFreshness.ShouldRebuild` 的职责）。
   - `IFullTextIndexFreshnessProbe`：`ProbeFreshness(corpusRootPath)`。
2. **为什么不给 `IFullTextSearchEngine` / `IFullTextIndexRootedEngine` 加成员**：这两个接口被 CLI 工程与多处替身/桩（`FileSearchToolTests`、`SearchGrepToolTests` ×2、`RawSessionLogFtsTests`、`LuceneFullTextProbe` 等）共同实现，**加成员会破坏它们的编译** —— A19（命名哈希单一真源）与 A2a（rooted engine）已按同一理由以「新增独立接缝」扩展，本次沿用该模式。
3. **`LuceneSearchEngine` 实现该探针**：路径一律经 `GetIndexDirectoryPath`（命名哈希单一真源）；**不打开 Lucene reader**（不占文件句柄、不影响 Windows 下目录 Move/Delete），只读 `.last_indexed` 与目录 mtime。三态严格区分：「读不出」返回 `StampUnreadable` 且时间字段为 `null` —— 不得用目录 mtime 冒充 stamp 时刻（两个口径不可混用），也不得伪报 `Available`。
4. **`.last_indexed` 解析抽出为单一真源** `TryParseLastIndexed`：异步增量路径与新的同步探针共用同一处，避免同一份 JSON 形状出现两处解析（分叉后「读到的新鲜度」与「引擎实际用的增量基准」会悄悄不一致）。与抽出前行为逐字等价（原实现同样把解析块整体包在 `catch` 里返回 `null`）。

## 证据（三段原始输出，命令与结果）

| 段 | 命令 | 结果 |
|---|---|---|
| 基线 | `dotnet test Source\PuddingFullTextIndexTests\PuddingFullTextIndexTests.csproj --filter "FullyQualifiedName~FullTextIndexFreshnessProbeTests"` | 失败 0 / 通过 3（exit 0） |
| 变异取红 | 把「stamp 缺失」分支的 `StampUnreadable` 改报 `Available` 后跑同一命令 | **失败 1 / 通过 2**，失败精确命中 `ProbeFreshness_StampMissing_ReportsUnreadableAndNeverFabricatesTime`，消息 `应为 <StampUnreadable>，实际为 <Available>` |
| 复原 | `Copy-Item` 逐位恢复后 `dotnet build … -t:Rebuild` + 同一命令 | 失败 0 / 通过 3（704 ms）；`RESTORED_SHA == 变异前 SHA == EC3540E84AADDCF7DA7AFDB313AF4B4BB1D5EF09BC002867F2D281C35C6F7EAB` |

用例自带**对照组**：`Available` 用例先断言 `BuildIndexAsync` 成功且 `IndexedFileCount > 0`（否则「有索引」可能只是「空索引也算建成」）；`StampUnreadable` 用例先断言 stamp 文件确实存在再删除（否则无法证明「缺失会被区分」）。

### 顺带实测到的一条陷阱（与本次改动无关，但对验证流程重要）

`Copy-Item` 复原文件会**保留源文件的 LastWriteTime** ⇒ 复原后源码 mtime 可能**早于**上次编译产物 ⇒ `dotnet test` 的增量构建**跳过重编译**，跑的还是变异版二进制（本轮实际发生过一次：hash 已证明内容复原，但测试仍红）。⇒ **复原源码后必须 `dotnet build -t:Rebuild`**；且 `dotnet test -t:Rebuild` 不被支持（MSB1008「只能指定一个项目」），要写成两步。
