## B 步 4（只读，当日 15:10 补）：**§1 顺序已核 —— 机制存在，但“记忆意图”不在其中**

### 1）Turn 终止确实是**单事务**提交（且带围栏校验）

`ExecutionRunCoordinator.ExecuteAsync`（`Source/PuddingPlatform/Services/AgentChat/ExecutionRunCoordinator.cs:35`）主路径：

terminalPending = loopResult.Pending;

`SqliteExecutionJournal.CommitTerminalAsync`（`:166`）在**一个事务**里写 terminal 事件 + Turn/Run/Command 行更新，
并做**受影响行数校验**（日志里有 `Fence may be lost` / `Terminal fence rejected`），`tx.CommitAsync` 在 `:296`。

⇒ **“terminal 与额外意图在同一 canonical 事务提交”的机制本来就存在**（`pendingEvents` 参数就是入口）。

### 2）但 `pendingEvents` 里**没有记忆意图**

`ExecuteLoopAsync`（`:580`）返回值构造得很清楚：

```
terminalPending = batch;              // 来自 chunker.Feed —— terminal 事件那一批的 pending 输出

```

`TurnOutputChunker` 产出的是**会话输出事件**（助手消息分块类）⇒ **`pendingEvents` 纯是会话输出**，
**无任何 memory/outbox 意图**。（方法内其余逻辑只有 `AppendOutputAsync` 与 terminal 提取。）

> **AC §1（“先在 canonical transaction 中提交 Turn terminal 与 memory-outbox intent”）在当前设计里“无对象”**：

> 记忆工作改走 **压缩事件 → durable 队列**（B 步 1），本身就是“terminal 先成事实、记忆后异步跑、不占 lease”。
