## B 步 1（只读，当日 06:15 补）：**目标架构已部分在位**（重要反转）

上文「要定论需要什么」的第 1 步做到一半，已得到**足以改变结论**的发现。

### 1）`ISubconsciousJobQueue` 的生产消费方（全仓扫描，按文件）

| 文件 | 角色 |
|------|------|
| `Source/PuddingMemoryEngine/Services/SubconsciousJobQueue.cs` | **接口实现**——类注释即 “**SQLite-backed durable queue** for subconscious maintenance jobs” |
| `Source/PuddingRuntime/Services/Background/SubconsciousJobScheduler.cs` | 调度（入队） |
| `Source/PuddingRuntime/Services/Background/SubconsciousRuntimeControlService.cs` | 运行时控制 |
| `Source/PuddingRuntime/Services/Background/SubconsciousWorkerService.cs` | **worker**（卡内指定入口） |
| **`Source/PuddingRuntime/Services/Hooks/SessionCompressedMemoryMaintenanceHook.cs`** | ⭐ **“会话压缩记忆维护钩子”——就是卡里说的 memory hook 的对位物** |
| `Source/PuddingPlatform/Controllers/Api/SubconsciousDebugApiController.cs` | 调试 API |

### 2）该钩子**已完成的正是 P0 的目标形态**

`SessionCompressedMemoryMaintenanceHook`（134 行，`BackgroundService`）订阅 `session.compressed`，
在事件到达时：
- **入队**（`_jobQueue.EnqueueAsync`）而不是**内联调 LLM**；
- 带**幂等键** `MemoryConsolidateSession:{workspaceId}:{sessionId}:{compactionId}`（`BuildIdempotencyKey`）；
- 日志文案即 “Enqueued **durable** memory maintenance job …”；
- 且注释写明：模板 ID 缺失时“**降级入队** …… （**修复自动压缩静默丢失整合任务的问题**）”。

### 3）队列本身已具备验收标准 §2 要求的性质

`SubconsciousJobQueue.cs`（793 行）实测具备：
- **SQLite 持久化**（`IDbContextFactory<MemoryDbContext>`，表 `SubconsciousJobs`，类注释自称 durable）；
- **幂等**：`EnqueueAsync` 先按 `IdempotencyKey` 查重，非 `completed`/`dead_letter` 则**直接返回既有作业**；
- **重试**：`MaxRetries = 3`，并有 `dead_letter` 终态；
- **lease**：`SemaphoreSlim _leaseLock`。

⇒ **验收标准 §2（独立 execution identity/预算/**lease**/幂等键，重启重放最多一个有效结果）**
**已在队列层大体落地**；§4 要求的两个埋点字段则**确实不存在**（上文第 3 节已证）。

### 4）仍然**未核**的部分（不下结论）

- **§1/§3 的关键顺序**：**Turn terminal commit** 与 **memory 入队触发点**的先后 ——
  本步只证了“**存在入队机制**”，**没有**证“入队在 terminal 之后（或同一 canonical 事务里）”；
- 该钩子订阅的是 **`session.compressed`（压缩事件）**，而卡描述的故障发生在 **一次性 Turn 的 post-turn memory hook**
  —— 两者**是否同一条路径**未核；
- §4 埋点字段缺失，导致**没有现成数据**能直接量测 “main answer ready → terminal” 的延迟。

### 5）结论修正（相对本文件首版）

首版只能说“具名产物不存在”；现在可以补一句更准的：

> **P0 卡所要求的“durable 记忆作业队列 + 独立 worker + 幂等 + lease”这层架构确实已经存在并在被使用，**
> **因此该卡很可能已**部分/基本**完成；但**§1 的 terminal 顺序**与**§4 的埋点**仍无证据。**

⇒ **建议优先级调整**：把“是否重写架构”降级，改为先花小的只读代价核实 **§1 顺序**（读 Turn 终止路径），
若顺序已正确，则本卡可收缩为“补 §4 埋点 + 回归样本验证”而非重做架构。

## B 步 2（只读，当日 07:50 补）：**卡描述的 post-turn 记忆钩子今天已不存在**

### 3）结论（B 步 2）

> **按当前代码拓扑，该 P0 卡描述的故障机制（post-turn 记忆钩子在 terminal 提交前跑 LLM 并占住 lease）已不存在** ——
> 因为**那个钩子本身已不在**；唯一的记忆维护触发点是**压缩事件**，且**只做 durable 入队**。

⇒ 结合 B 步 1（队列已具备 durable/幂等/lease）与首次核实的第 3 节（§4 埋点字段确实不存在），
本卡很可能已**基本完成**，剩余可办的事集中在：
1. **§4 埋点**（`main_answer_ready_at` / `terminal_committed_at` / `tail_latency_ms`）确实没做；
2. **用卡内固定回归样本**（`run 26566c…`）做一次**时序验收**（需运行环境，非只读）。

### 4）诚实边界（**不得**当成“已修”证据）

- 本次**未**通审整条 Turn 流水线，**未**证明“任何可能的记忆 LLM 调用都发生在 terminal 提交之后”；
  特别是压缩期服务（如 `PreCompactionFlushService`）在**上下文满**时可能落在 Turn 中间，
  它对 terminal 延迟的影响**本次未测**；
- §1 要求的“**terminal 与 memory-outbox intent 在同一 canonical 事务提交**”**未核**（本步只证了触发点拓扑）；
