# 2026-10-08 I1 第四步：Desktop 侧严格解码

## 改了什么

| 件 | 变化 |
|---|---|
| `Source/Pudding.DesktopConnection/Mapping.cs` | 解码 `command.Caller`：`BrowserCallerKindWire.TryParse` 失败 ⇒ `caller.kind '…' is not a registered caller kind`；构造身份抛错（空/超长/子代理缺父任务）⇒ `caller identity is invalid: …`；**WebView 系能力**必须能通过 `TryGetBrowserCaller`（缺身份/User 冒充/无运行身份分别有具体原因） |
| 顺序 | 身份校验**先于** payload 校验：身份问题永远给出身份原因（不因"payload 也不对"而改变拒绝语义） |
| 测试替身 | `TestInfrastructure.cs` 的 4 处命令构造统一带 `TrustedCaller`（agent/agent-1/run-1），并保留显式构造"无 caller"命令的能力 |
| 新用例 | `CallerIdentityDecodeTests`（7 条）：可信 Agent 身份落到上下文、浏览器能力缺身份被拒、未知 kind 被拒、User 冒充被拒、缺运行身份被拒、子代理缺父任务被拒、**Shell 能力无需 caller 仍可用** |

**判据只有一份**：Desktop 侧门禁不重写规则，直接消费契约里的 `DesktopCallContext.TryGetBrowserCaller`。

## 验证

| 项 | 结果 |
|---|---|
| `Pudding.DesktopConnectionTests` | **87 / 87**（原 80 全绿 + 7 新） |
| 消费方同步 | 同步替身构造前 **29 条失败**（浏览器命令缺身份）⇒ 同步后全绿；这是"同一切片一次性同步消费方"的又一实例 |
| **全量链** | **1647 / 0**、一次通过、无重试（7 套件） |
| 能力通道集成用例 | **18 / 18**（`PuddingAgent.IntegrationTests`） |

## 诚实边界（诚实登记）

- **协议仍是 v1**：字段是新增的，v1 端不会发送它 ⇒ 由 v2 升级负责"旧新配对明确拒绝"（独立一步，未做）。
- **Bridge（WebSocket）传输尚未携带身份**：本轮只做了 gRPC 能力通道；Bridge 侧的 envelope 身份是下一步。
- **尚未接入准入执行**：Desktop 侧校验发生在**解码**这一步；`Admit`/`Revalidate`/租约（I2）仍未接。
- **`PermissionEvidenceSummary` 未被当作身份**：字符串 `allowed` 依旧不能获得授权（本轮没有放宽它）。
- **未真机验证**。
