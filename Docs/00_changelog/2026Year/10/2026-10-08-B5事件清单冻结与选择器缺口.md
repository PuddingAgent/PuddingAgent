# 2026-10-08 B5 收尾：冻结事件接管清单 + 核实文件选择器缺口

## 目标 / 背景

B5 剩的是"外围能力"（剪贴板 / 文件选择器）。本轮先**核查现状**再动手：

| 项 | 核查结果 |
|---|---|
| 剪贴板读取 | **契约已存在且设界**：`ClipboardReadRequest(maxCharacters)` 限制在 `[1, 1_000_000]`（默认 64,000），结果 `DesktopClipboardContent(text, truncated)` 还刻意处理了"截断了但没内容"的自相矛盾 |
| 文件选择器（Shell 侧） | **契约已存在**：标题 ≤128、扩展名 ≤16 项，结果区分取消与路径 |
| 准入 | `DesktopCapabilityPolicy` 已把 对话框/Picker/剪贴板 限为 `Workbench`（`Workbench` 永不脚本注入） |
| 页面侧事件接管 | 已接管 9 个事件（导航/标题/来源/进程失败/脚本对话框/权限/新窗口/下载） |

既然契约侧已设界，本轮转向**真正的缺口**：**页面自己弹出文件选择器时我们接管不了**。

## 核实（不是猜测）

在 `Microsoft.Web.WebView2.Core.dll`（SDK **1.0.4078.44**）里检索 `FilePicker` 与 `FileChooser`：
**均为 0 处**。⇒ 该 SDK **没有**对应事件/API，因此"页面脚本点击 `input[type=file]` 弹出的选择器"
**不在自动化可控范围**。

## 改动

| 文件 | 改动 |
|---|---|
| `WebView2BrowserPage.cs` | 在事件订阅处加**说明块**：清单为什么冻结；**文件选择器缺口**（SDK 无 API ⇒ 接管不了 ⇒ **不假装**）；对策只有两条（① 上传走 `DOM.setFileInputFiles`；② 明确不支持"页面自行弹选择器"）；若将来 SDK 升级，这里是唯一该加订阅的地方 |
| `DriverEventHandlingTests.cs`（新增，3 条） | ① **冻结订阅清单**（9 个事件，按源码顺序，用 `\b` 精确匹配避免把 `_coreWebView.X` 算进来）；② 代码里**必须写明**缺口与对策（"文件选择器无法接管" + `FilePicker` + `DOM.setFileInputFiles`）；③ **三条安全侧默认**仍在（`CoreWebView2PermissionState.Deny`、`e.Cancel = true;`、`Handled = true;`） |

## 已知边界（诚实登记）

- **缺口无法在本轮修好**：SDK 没有 API。因此这条是**记录 + 冻结**，不是修复；真机上遇到页面自弹选择器时，
  只能由外部观察并记为"不支持"。
- **未把该缺口写进 smoke 清单/手册**：`BrowserSmokePlan` 的门禁是 G1–G11（设计如此），
  选择器缺口不属任一门禁；本轮只写进代码注释与本文（若要进清单需扩门禁集）。
- **剪贴板/Picker 的 Shell 侧链路未做端到端验证**：契约与准入核查过，但没有真机（无产品 Shell）——
  这属 B7 的外部验收范围。
- **冻结清单是源码文本断言**：它检查的是"订阅了哪些事件"，不检查处理逻辑是否正确（那要靠真机观察）。
