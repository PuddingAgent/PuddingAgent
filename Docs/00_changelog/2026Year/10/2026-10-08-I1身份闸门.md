# 2026-10-08 I1 第一步：身份闸门 + 消费方同步

## 改了什么

| 件 | 变化 |
|---|---|
| `Source/PuddingBrowser.AgentTools/BrowserCallerIdentityScope.cs`（新） | **调用级身份作用域**：`BrowserCallerIdentityScope`（AsyncLocal，`Push` 返回**无条件还原**句柄）+ `IBrowserCallerIdentityAccessor` / `BrowserCallerIdentityAccessor`（Host 侧读取，**不缓存**）。投影失败时保留具体原因 |
| `BrowserAgentToolBase.cs` | 每次调用推入**三个**作用域（审计 Origin、权限证据、**调用者身份**）；`ExecuteCoreAsync` 改为 `sealed` **闸门**：无 `Current` ⇒ `ToolExecutionResult.Fail("browser tool refused: …")`，**不执行**；新增抽象 `ExecuteBrowserCoreAsync` |
| 七个工具（Context/Interact/Locate/Navigate/Snapshot/Tabs/WaitFor） | 入口改名 `ExecuteBrowserCoreAsync`（编译期强制同步） |
| `BrowserCallerIdentityAdmissionTests.cs`（新，6 条） | 缺身份拒绝且**驱动调用数=0**、子代理缺父运行拒绝、身份调用内可见且调用后清空、异常路径也还原、**并发不串用**、访问器不缓存 |

身份来源仍是 `BrowserCallerIdentitySource.TryProject(ExecutionIdentity, agent 实例标识)`（round-167/168 已落地），**不接收任何工具参数**。

## 过程中发现并修复的真实破坏（重要）

新闸门让**既有消费方**暴露出来：`Tests/PuddingHost.Tests/BrowserBridge/BrowserAgentToolBridgeIntegrationTests.cs`
与 `ConfiguredAgentBrowserSnapshotPolicyExecutionTests.cs` 构造 `ToolExecutionContext` 时**没有** `ExecutionIdentity` ⇒
工具被拒绝 ⇒ 测试继续等待**永不到来的桥命令** ⇒ **挂起**（不是快速失败）：

- 现象：Host 套件隔离运行 8 分钟不结束；`--blame-hang` 90s 后只跑到 **245/258** 并留下 hangdump；
- 归因：这三条用例**确实**执行浏览器工具（`BrowserContextTool`/`BrowserSnapshotTool`），且它们的上下文无身份；
- 修复：按方案「同一切片一次性同步消费方」给这两处的上下文补上可信 `ExecutionIdentity`；
- 复验：三条用例 **3/3 通过、555 ms**（不再挂起）。

⇒ 这条也证明了闸门**真的生效**（工具不再可能静默走桥）。

## 诚实边界（诚实登记）

- **只完成 I1 的 AgentTools 一侧**：`DesktopCallContext` 的类型化 caller、gRPC `CapabilityCommand` caller message、Bridge envelope 身份、两协议版本升 v2、`CoreCommandEncoder.Fingerprint` 纳入身份（§3.2/§3.3）**尚未施工**。
- **Host 侧尚未从 accessor 取身份**（§3.1 后半）：本轮只保证"工具有身份"，Host 调用上下文工厂的接线是下一步。
- **身份现在是硬前置**：任何新的浏览器工具调用方都必须提供 `ExecutionIdentity`；否则**拒绝**（这是设计意图，但属破坏性变化，已在日志登记）。
- **`Profiles`/其它未跑套件**：本轮只在 7 套件链 + Host 三条定向用例上验证；链外依赖套件（CapabilityBroker/DesktopConnection/WebApi 等）**尚未重跑**。
- **未真机验证**；② 250ms、③ flake、④ 指纹仍按方案的独立切片处理（方案已裁定：允许在必要路径修 flake 根因）。
