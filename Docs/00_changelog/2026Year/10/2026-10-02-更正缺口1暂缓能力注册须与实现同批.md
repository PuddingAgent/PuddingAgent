# 更正（2026-10-02）：缺口 #1 暂缓——能力注册必须与实现同批落地

## 更正（2026-10-02）

上一轮（`a33576c`）我在**只做契约层**时就往能力目录里加了两个能力名（`browser.context.create` /
`browser.context.close`）。这**破坏了两条既有测试**，而我当时只构建了 Contracts 与 CapabilityBroker、
没有跑 DesktopServiceTests ⇒ **把红色测试留在了工作树里**（本轮才发现）。两条测试正是仓库的护栏：

| 测试 | 它断言什么 |
|---|---|
| `PolicyTable_CoversEveryRegisteredCapability` | 策略表必须覆盖**每一个已注册能力** |
| `DeclaredCapabilities_AllHaveAnAdmissionRule` | 声明的能力集合必须与准入规则集合一致 |

⇒ 结论（也是本轮最有价值的产出）：**能力注册不能在"只有契约"的半程落地**——
注册即声明"Desktop 实现了它"，因此必须与 **proto payload/outcome + 两侧映射 + Desktop 实现 +
DesktopSession/Bridge/路由三个端口实现 + 声明与准入规则 + 测试** 同批提交。
这与我此前按"先契约、再实现"分阶段的习惯相反，是**这套护栏刻意要求**的。

## 本轮动作（恢复绿色）

- 撤回 `Capabilities.cs` 里的两个能力名与两条目录项（`git checkout` 撤回尚未提交的 proto/映射改动）；
- **保留**已提交的契约齿轮：`BrowserContextCreateRequest` / `BrowserContextCloseRequest` /
  `DesktopContextClosed` / 新窄端口 `IDesktopContextCapabilitySurface` / 联合的两个分支与工厂
  （它们不引用被撤回的目录项，编译与测试均通过，作为**待接线**的脚手架）。

## 验证

- `Pudding.DesktopServiceTests` **170/170**、`Pudding.ContractsTests` **96/96**、
  `Pudding.Rpc.ProtocolTests` **20/20**、`Pudding.Contracts` 构建 **0 错误**；
- 工作树无红色测试。

## 过程教训（纪律层，比技术细节更重要）

**改了能力目录就必须跑 DesktopServiceTests（策略表 + 声明集合）**。本轮我把"契约层可编译"
当成了"这一步安全"，漏掉了跨组件的目录一致性护栏 ⇒ 红色测试停留了一轮。
已写入本日志作为固定动作：**触碰 `Capabilities.cs` 后，必跑 DesktopServiceTests**。

## 未完成 / 留白（缺口 #1 的完整清单，需一次性窗口）

1. 能力目录（2 个新能力名 + 特征）；
2. proto：2 个 payload 消息 + 2 个 oneof 分支（24/25）+ 2 个 outcome（25/26）+ 线缆快照断言；
3. 两侧映射（Core→proto 命令、Desktop 解码、Desktop→proto 结果、Core 结果解码）；
4. Desktop 实现（`BrowserRuntimeDesktopSurface` 实现新端口）；
5. `DesktopSession` / `BridgeBrowserCapabilitySurface` / `TransportRoutedBrowserCapabilitySurface`
   三者实现（或转发）新端口；
6. 声明集合 + `DesktopCapabilityPolicy` 规则表 + `DesktopService` 分发；
7. 测试（契约冻结线名、线缆字段号、端口实现、路由）+ 探针；
8. 之后才是 `browser_context` 工具迁移。

另有：Tool Runtime 权限链；切片 F（默认传输切换、退役 Bridge）；外部重启窗口 8 步验收；索引登记。
