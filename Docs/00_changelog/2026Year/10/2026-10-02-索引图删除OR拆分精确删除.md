# 2026-10-02 索引图删除 OR 拆分精确删除

## 改动

- `Source/PuddingCodeIndex/Storage/SqliteCodeIndexStore.cs` 的 `RemoveSymbolGraphForFileAsync`：对每个符号，
  把原来「每个表一条 `(SourceSymbolId = $s OR TargetSymbolId = $s)`」的删除拆成**四条精确删除**
  （CodeReferences 的 Source/Target、CodeRelations 的 Source/Target），全部仍在**调用方传入的同一事务**里，
  取消或异常整体回滚；自引用在 Source 删除后已消失，Target 删除是安全 no-op；其它 workspace/project 不受影响。
- 保留既有 Source/Target 索引，不改 pooling、PRAGMA、事务粒度或全量重建算法。
- 扩展现有 `Source/PuddingCodeIndexTests/Storage/SqliteCodeIndexStoreRemoveFilesTests.cs`：跨文件入边、出边、
  自引用、同 ID 不同 workspace/project、无符号文件的文件记录与残留图行、无关图保留。
- 新增 `Source/PuddingCodeIndexTests/Storage/SqliteCodeIndexStoreRemoveGraphWorkTests.cs`：四条精确删除的查询计划
  与**代价不随作用域图规模增长**的度量用例。

## 验证

- `dotnet test Source\PuddingCodeIndexTests\PuddingCodeIndexTests.csproj` → 全绿（本次 C 新增 7 条用例）。
- 计划对照（产品 provider，Microsoft.Data.Sqlite）：四条精确删除计划为
  `SEARCH CodeReferences USING INDEX IX_CodeReferences_Source (WorkspaceId=? AND ProjectId=? AND SourceSymbolId=?)`
  这类**完整三列约束**；`EXPLAIN QUERY PLAN` 只对第一条语句出计划，因此用例逐条取计划后再断言。
- 工作量度量（VDBE 步数，与机器性能无关）在 2,000 / 8,000 行两个作用域分区上执行**真实 DELETE**（包在显式事务里
  执行后 `ROLLBACK`，可重复且不改夹具）：四条精确删除的步数恒定，两条 OR 删除的步数随分区线性放大
  （4 倍数据下 ≥3 倍），8k 分区上精确形式比 OR 形式少一个数量级以上。
- 重要口径修正：**不能用「相同 WHERE 的 SELECT」代替 DELETE 度量** —— SELECT 的取列会改变索引覆盖性，
  实测 `TargetSymbolId` 的 SELECT 会退化成作用域前缀扫描，而同谓词的 DELETE 使用 `IX_…_Target` 查找。
  因此度量直接跑删除语句本身（该结论已写入测试注释）。
- 未在生产库或真实索引上执行删除；真实数据对照按报告要求只在 `temp/test-out` 的 SQLite 在线备份副本上做
  （本任务尚未执行该对照）。
