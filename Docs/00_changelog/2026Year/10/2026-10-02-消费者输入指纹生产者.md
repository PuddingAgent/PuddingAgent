# 2026-10-02 消费者输入指纹生产者

## 改动

- 新增 `Source/PuddingCodeIndex/Services/CodeIndex/LanguageCodeSourceConsumerInputProvider.cs`（含端口
  `ICodeSourceConsumerInputProvider`）：补齐维护链此前**没有生产者**的一环 —— 「本 scope 有哪些消费者、
  它们的输入指纹是什么」。没有它就无法区分「配置/工具链变了 ⇒ 只需重新绑定」与「内容变了 ⇒ 必须重读」，
  也无法在提交时按消费者分别推进水位。
  - 一个注册的语言实现 = 一个消费者（`ProviderId = ILanguageCodeIndexer.Language`，顺序稳定排序，
    否则指纹字符串会抖）。
  - **解析器/策略指纹** = 实现所在程序集版本 + `PolicyVersion` 常量：工具链（Roslyn / 提取器脚本）随程序集升级
    ⇒ 该语言的路径需要重新提取。
  - **语义输入指纹** = scope 根那一层的工程/配置文件（`.csproj`/`.sln`/`tsconfig.json`/`package.json`/
    `pyproject.toml`/`Directory.Build.props` …）的「长度 + 内容 hash」排序合成。
    **源码正文变化不算语义输入变化** —— 否则改一个 `.cs` 就会把整个 scope 判成需要重新绑定（白读盘）。
    读不到的语义输入文件被记成 `unreadable`（确定性，且不会把一次瞬时失败静默当成「没变」）。
  - 没有任何工程文件时返回确定性标记 `no-semantic-inputs`（**不用随机值**，否则每轮都会判成变化）。
  - 默认实现经 `ICodeProjectRegistry` 取 scope 根；也可注入自定义指纹函数。
- `Source/PuddingCodeIntelligence/DependencyInjection.cs`：登记 `ICodeSourceConsumerInputProvider`
  （消费者 = 已注册的 `ILanguageCodeIndexer` 集合，根路径来自 `ICodeProjectRegistry`）。
  仍是**登记装配、不驱动**。

## 验证

- `dotnet test Source\PuddingCodeIndexTests` → **307 通过 0 失败**（本次 +6）。
- `dotnet test Source\PuddingCodeIntelligenceTests` → **132 通过 0 失败**。
- `dotnet test Tests\PuddingHost.Tests --filter CodeIndexMaintenanceHostCompositionTests` → **4 通过 0 失败**
  （含新增登记后宿主容器仍可解析、`ValidateOnBuild` 通过）。
- 用例覆盖：消费者数量/顺序/策略指纹非空；**工程文件变化 ⇒ 指纹变化、源码正文变化 ⇒ 指纹不变**；
  没有语义输入时返回确定性标记；语义输入文件识别（含 `Directory.Build.props`）；经工程注册表取根且两次调用一致；
  没有注册语言时没有消费者。

## 未完成与影响

- **驱动仍未切换**：`ICodeSourceConsumerInputProvider` 只是把「切换所需输入」补齐，
  `CodeIndexMaintenanceService`（旧逐文件路径）仍是唯一维护驱动 ⇒ **运行中实例零行为变化**。
- 下一步（会产生用户可见变化）：在组件维护驱动里按开关调起协调器（消费者输入取自本提供者，
  watcher 事件接到 `WatcherHints`），并替换「无 owner ⇒ 整仓」旧路径；随后按规程交付
  `ready-for-external-deploy`，由**进程外控制器重启到明确的新构建**再跑四场景受控复核。
