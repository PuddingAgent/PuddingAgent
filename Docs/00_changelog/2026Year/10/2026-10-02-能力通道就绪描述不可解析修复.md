# 2026-10-02 能力通道就绪端点描述不可解析（启用后通道永不启动）

## 目标 / 背景

执行 `Desktop-Contracts-Grpc-Capability-Plan-2026-10-01.md` 切片 C-3 收尾时，实读 Core 侧就绪输出发现：
`PuddingApplicationHost.CaptureBoundAddresses` 把端点描述打成 `kind:address|v1|core-x`，
而 Desktop 侧的严格解析器要求第二段是**整数**（`int.TryParse(parts[1], NumberStyles.None)`）。

后果链：解析失败 → `DesktopChannelTransportResolver.ResolveFromText` 失败 →
`DesktopCapabilityChannelPreflight` 判「描述缺失/不可用」→ Desktop 只记一条日志并保持旧 Bridge。
即 **`Enabled=true` 时能力通道永远不启动**，而**默认关闭的路径永远绿**，表现像「配置没生效」。

## 改动

- 新增 `Source/Pudding.CapabilityBroker.AspNetCore/CapabilityChannelReadySignal.cs` —
  产出 `kind:address|protocolVersion|serverInstanceId`，并用**同一个**严格解析器自检
  （不可解析即启动期抛异常，不留静默失败）；`DescribeLogLine` 让人读日志与就绪信号共用同一份文本；
  `FieldName = "capabilityEndpoint"`。
- `Source/PuddingHost/Hosting/PuddingApplicationHost.cs` — 日志行改用 `DescribeLogLine`；新增
  `GetCapabilityEndpointDescription(IServiceProvider)`（关闭时返回 `null`，入口点无须触碰内部 DI 类型）。
- `Source/PuddingAgent/Program.cs` — `PUDDING_DESKTOP_READY` 改由 `JsonSerializer` 产出并新增
  `capabilityEndpoint` 字段；`DefaultIgnoreCondition = WhenWritingNull` ⇒ **关闭态那一行与今天逐字一致**。
  改为序列化器而非手写 JSON：正是手写造成了这次漂移。
- `Source/PuddingDesktop.WpfArchive/Core/CoreReadyMessage.cs` + `CoreReadyMessageParser.cs` —
  新增 `CapabilityEndpoint`，只做逐字搬运（可用性由预检单一入口判定）；空白视同缺席。
- 测试：新增 `Source/Pudding.CapabilityBroker.AspNetCoreTests/CapabilityChannelReadySignalTests.cs`（8 项）；
  `Tests/PuddingDesktop.Tests/Core/CoreReadyMessageParserTests.cs` 增 5 项。

## 验证

- `Pudding.CapabilityBroker.AspNetCoreTests` **39/39**（往返解析、版本段必须是整数、`v` 前缀必须被拒、
  日志与信号一致、无凭据、字段名）；
- `PuddingDesktop.Tests` **266/266**（缺席/空白 ⇒ null、原文逐字搬运、未知字段向前兼容）；
- `PuddingAgent`（含 `PuddingHost`、适配器）Release 构建 0 错误，产物时间戳确认已重编译。

## 未完成 / 留白

- 探针 `--dry-run` **验证不了这条链路**：它自己构造端点描述，走的是解析器而不是 Core 的 stdout 产出路径。
  因此接线手册第 6 节第 3 步（Desktop 能解析出端点）仍是**必经**的窗口期验收动作。
- 本次未在真实重启窗口内验证启用态（属外部控制器）。

## 影响与回滚

关闭态输出逐字不变（`WhenWritingNull`）；回滚 = `Enabled=false` 重启。
