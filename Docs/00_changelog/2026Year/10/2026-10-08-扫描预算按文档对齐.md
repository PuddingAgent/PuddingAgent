# 2026-10-08 按文档对齐扫描预算

## 判断口径的改变（并说明理由）

上一轮我把 §6.1 的三处预算偏差登记为"待拍板"。本轮重新读文档后改变口径：

- 本次任务的原始指令是「**请根据文档，执行 fix**」⇒ **文档是权威**；
- 文档里 **节点 10,000 / 深度 64** 是明确的"内部扫描预算初值"；
- 只有**扫描时间门限**那一句写明"实现前通过真实驱动样本校准" ⇒ 只有 **250ms** 属于"需样本才能定"。

⇒ 因此：**节点/深度按文档对齐**（本轮做），**250ms 与 full 模式输出预算仍登记为偏差**（不改行为，因为它们要么需要样本、要么会改变显式调试模式行为）。

## 改动（九处默认值）

| 位置 | 改动 |
|---|---|
| `SnapshotContracts.DefaultMaxNodes` | 5,000 → **10,000** |
| `SnapshotContracts` 构造默认 `maxDepth` | 24 → **64** |
| `ScriptAndSnapshot`（Abstractions） | MaxNodes 5,000→10,000、MaxDepth 24→64 |
| `BrowserBridgeCommandPayloads`（Protocol） | 同上 |
| `BrowserSnapshotTool`（AgentTools） | 同上（MaxNodes/MaxDepth） |
| `Mapping.cs`（DesktopConnection） | 另一处硬编码深度 24 → **64** |

**旁证（为什么 64 才是设计值）**：`BrowserReadingFormat.ScanMaxDepth` 本来就是 **64**，
驱动侧也写着 `Math.Clamp(options.MaxDepth, 1, 64)` ⇒ 快照路径里的 **24 是离群值**，对齐后各层一致。

## 验证

| 项 | 结果 |
|---|---|
| `Pudding.DesktopServiceTests` | **337 / 337**（偏差门禁已改为断言"已对齐 + 记录仍在"） |
| **全量链** | **1595 / 0**、无重试 |
| 回归确认 | 第一次跑链时 Host 的**已知 flake**（`SecondConnection_CannotReplaceAwaitingHelloConnection`）失败 ⇒ 我核对 TRX 确认**不是**本次改动引起（该用例与快照预算无关），重跑即绿 |
| 偏差记录 | 对账表里节点/深度两行由 ❌ 改为 ✅（写明"已按文档对齐"及旁证），250ms 与 full 模式两行**保留为偏差**，门禁同时钉住这三件事 |

## 诚实边界（诚实登记）

- **这是一次"默认值扩大"**：最大扫描量从 5,000/深度 24 提到 10,000/深度 64 ⇒ 极端大页面上**扫描成本更高**。
  文档把这组值当作初值并允许用真实样本校准；我在**没有样本**的情况下按文档对齐，是**遵从权威**而非实测最优。
- **250ms 时间门限仍未实现**（缺样本，无法诚实设定）。
- **full 模式仍无 16 KiB/64 KiB 输出预算**（改它会改变显式调试模式行为，保留为偏差）。
- **未真机验证**：这些默认值在真实页面上的扫描耗时/内存**未经观测**。
- 决定（B1 可信调用身份）仍未拍板。
