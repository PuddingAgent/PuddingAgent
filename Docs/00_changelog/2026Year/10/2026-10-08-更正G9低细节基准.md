# 2026-10-08 更正：G9 的「低细节基准 512px/40 KiB」是硬要求

## 更正（我此前的误判）

| 轮次 | 我当时的判断 | 事实 |
|---|---|---|
| round-136 | 「≤40 KiB **查无出处**」⇒ 从 smoke 清单 S-09 删掉，并把 S-09 改写成"按调用方上限判定" | **错**：设计文档 §11 G9 与说明段**都写了 40 KiB** |
| round-142 | 据上述判断，把对外清单文档里的 40 KiB 也同步删掉，并新增门禁"数字必须有出处" | **错上加错**：门禁本身没问题，但被我用在了**错误的删除**上 |

**误判原因**：我当时只读了 §8.1（那里写的是 **8 MiB 输入上限**与 **512px 默认**），**没有通读 §11 验收矩阵**。
两者是**两件事**：`8 MiB` 是单张**输入**上限，`40 KiB` 是**低细节基准的输出预算**。

**教训**：把"我没找到"当成"文档没要求"，是最容易犯也最伤的一种判断；正确做法是**通读验收矩阵**再下结论
（这也正是"要求对账"该做的事 —— 本轮正是靠对账才发现）。

## 恢复与落地

| 位置 | 内容 |
|---|---|
| `BrowserScreenshotTransfer` | 新增 `LowDetailBaselineBytes = 40 * 1024`（注释直接引用 §11 G9 与说明段）；新增拒绝原因 `LowDetailBudgetExceeded`，原因文案含 **budget_exceeded** 与"改为局部截图"的指引，并明确"不得无限压缩后仍称可读" |
| `BrowserScreenshotPlanner` | 规划结果新增 `ByteBudget`：`detail=low` ⇒ 40 KiB 基准；其余保真度 ⇒ 8 MiB 输入上限 |
| S-09 期望（代码真源） | 改为 `detail=low 基准 ≤512px/40 KiB（超预算明确 budget_exceeded 或要求局部截图…）；单张输入 ≤8 MiB`，数字全部**插值自常量** |
| 对外清单文档 | 与代码真源逐字同步（严格门禁要求） |
| 数字溯源门禁 | 新增 `KiB → LowDetailBaselineBytes = 40 * 1024`；文档对表用例新增"设计文档里应写明 40 KiB" |
| S-09 覆盖声明 | 仍指向坐标/载荷/规划器三组用例（覆盖门禁验证类真实存在） |

## 验证

| 项 | 结果 |
|---|---|
| `PuddingBrowser.AutomationTests` | **389 / 389**（＋2：低细节超 40 KiB 必须报 budget_exceeded；高保真可超 40 KiB 但受 8 MiB 约束） |
| `Pudding.DesktopServiceTests` | **335 / 335**（S-09 与文档改回真源后仍绿） |
| **全量链** | **1592 / 0**、无重试（第一次跑遇 Host 已知 flake ⇒ 清单**拒绝产出**，重跑才绿） |
| 三方一致 | 设计文档（§11 G9/说明段）↔ 代码常量 ↔ 清单与文档措辞，全部由门禁钉住 |

## 诚实边界（诚实登记）

- **"40 KiB 基准"仍是目标值**：真实 JPEG 编码后能否达到，**没有真机实测**（也没有对应实现）——本轮只把**要求**与**拒绝语义**落到代码里。
- **低细节压缩策略未实现**：`detail=low` 目前只校验收到的载荷是否守约，**没有**"逐步降质量直到 ≤40 KiB"的编码器逻辑
  （那属采集侧/S5）。因此本轮的产物是"**越界就明确拒绝**"，不是"自动压到预算内"。
- **`ByteBudget` 是新增字段**（规划结果结构变化）：消费方需同步（目前只有测试与将来的工具面）。
- **更正不抹除历史**：round-136/142 的 changelog 保留原文，本页是追加式更正（符合仓库日志约定）。
- **未真机验证**；决定②仍待确认。
