# 2026-10-02 指纹先判与磁盘 I/O 画像

## 改动

- `Source/PuddingCodeIndex/Services/CodeIndex/CodeSourceMaintenanceCoordinator.cs`：
  **顺序改为「指纹先判、再动手」** —— 先对候选路径做稳定读算出指纹，只有在内容与「上次已提交」
  不一致时才调用语言批量接缝：
  - 一致（长度 + 内容 hash 相同、记录 `Complete`、消费者已登记）⇒ 记入 `ReusedFileCount`，
    **跳过提取**，只把消费者视图推进到捕获版本（`SaveSourceManifestAsync`）；
  - 不一致 ⇒ 照常提取并原子替换（指纹用第①步读到的那一份，绝不重新读、也绝不凭空构造）；
  - 没有可提交指纹（读取不稳定 / 找不到对应指纹）⇒ 记退避，**绝不写索引**。
  - 结果新增 `ReusedFileCount`。
  动机：提示只说明「这个路径可能变了」。一次 Roslyn / ts-morph / Node 装载的代价远高于一次读盘，
  而编辑器抖动、重复事件、`git checkout` 之后的提示常常内容并未变化。
  **读盘本身仍要做**：那正是「提示 ⇒ 必须核验内容」这条不变量的代价。
- 新增 `Source/PuddingCodeIndexTests/Services/CodeIndex/CodeSourceMaintenanceIoProfileTests.cs`（4 条）：
  用**可计数装饰器**（全树枚举次数 / 按路径观测次数 / 内容读取次数）把新链路的读盘画像固化成用例 ——
  诊断报告关心的就是这个，不能只靠「应该很快」的断言。

## 验证

- `dotnet test Source\PuddingCodeIndexTests` → **324 通过 0 失败**（本次 +4）。
- 画像用例断言（真实临时文件 + 真实扫描器 + 真实稳定读，只把语言侧换成脚本化替身）：
  1. 单文件改动 + 提示 ⇒ **零次全树枚举**、一次按路径观测、只读那一个文件的内容；
  2. 周期性完整校准 + 指纹全未变 ⇒ 一次完整枚举、**零次正文读取**；
  3. 完整校准 + 只改一个文件 ⇒ **只读那一个文件**的正文；
  4. 重复提示 ⇒ 仍是零次全树枚举、一次核验读盘、**零次提取**（`ReusedFileCount == 1`）。
- `dotnet test Tests\PuddingHost.Tests`（全套 240 条）→ 239 通过；唯一失败
  `DesktopBrowserBridgeHandshakeTests.SecondConnection_CannotReplaceAwaitingHelloConnection`
  是浏览器桥的 WebSocket 超时（与代码索引无关），**单独重跑该用例 4/4 通过**，判定为全量并发下的时序抖动，
  非本笔引入。

## 未完成与影响

- 默认仍是 `Legacy` ⇒ 运行中实例行为未变；上述画像描述的是**启用 Coordinator 后**的行为，且是在
  测试替身语言侧上的计数，真实仓库的四场景读数仍需外部重启后测量。
- 残余窗口（已知、未在本笔处理）：指纹在「读取」时被验证，提取发生在其后；若两次之间文件又被改写，
  下一次提示/周期扫描会重新核验并纠正，但这一次提交的索引可能对应稍旧的字节。
  彻底闭合需要在提取后再校验一次 stat（代价极低），列为后续小刀。
