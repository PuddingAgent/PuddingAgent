# 2026-10-02 授权端到端验证（拒绝发生在发送之前）+ 切片 D 的关键发现

## 目标 / 背景

上一轮把产品授权器从 `DenyAll` 换成可信身份门禁（`56e31b2`），但只有单测证明。
本轮补**真实通道**上的验证，并顺带把切片 D 的可行性摸清——结果发现原计划的实现路径不可行，
必须改法（见下）。

## 改动

- 新增 `Source/Pudding.CapabilityBroker.AspNetCoreTests/TrustedCallerAuthorizerOverTheWireTests.cs`（3 项）：
  在**真实 Named Pipe 通道**上（`CapabilityHostHarness`，与产品组合根同形态）验证：
  ① 无身份 ⇒ 能力被拒为 `unauthorized`，**且 Desktop 侧收不到任何命令帧**
  （授权必须发生在发送之前——否则"拒绝"只是让桌面白挨一次命令，这只有端到端才看得见）；
  ② 有可信身份（会话+Agent+执行+用户齐备）⇒ 命令正常下发、结果正常回填；
  ③ 身份在但缺"可识别的 Agent 执行" ⇒ 变更类能力仍被拒，同样不下发。

## 切片 D 的关键发现（改变下一步的实现方式）

原计划把切片 D 理解为「把七个工具从 Bridge 迁到能力通道」。本轮实读后确认：
**不能靠替换 `IBrowserRuntime` 实现来完成**——`IBrowserPage` 有约 **35** 个成员
（CDP、截图、PDF、DevTools、订阅、拖拽、选择、上传、cookie、权限……），
而能力通道只覆盖其中约 **12** 个（九个浏览器能力对应的操作）。任何"直接实现 `IBrowserRuntime`"的
适配器都会瞬间产生二十多个必须抛 `NotSupported` 的成员，等于把工具在运行期打成半残。

⇒ 正确做法是**按操作迁移**：为七个工具实际用到的操作提供**窄端口**（或按能力逐个替换调用点），
而不是在宽接口上做整体替换。这条已写入映射规格 §8.4，避免下一轮再走一遍死路。
