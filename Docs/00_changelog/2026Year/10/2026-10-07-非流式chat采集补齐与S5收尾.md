# 2026-10-07 · 补齐非流式 chat 路径的采集 + S5 收尾

## 背景 / 动机

2026-10-07 事故里失败的不只是主链路：**子代理委派走的是非流式 `ChatAsync`**，同一族错误（写请求体阶段被重置）。
Stage 3 只给流式路径建了诊断作用域，因此非流式失败虽有稳定因果码，**却没有请求体字节数**——
而"请求体多大"正是判断「是不是大上下文把连接压垮」的关键事实。

## 改动

| 文件 | 内容 |
|---|---|
| `Source/PuddingRuntime/Services/DirectLlmClient.cs` | `ChatAsync` 每次尝试 `Begin()` 一个诊断作用域（provider/model/host/attempt/maxRetries）；超时分支置 `FirstChunkTimeout`（非流式用首块预算 CTS），外部取消置 `UserCancelled`。分类与异常挂载仍走唯一出口 `RecordActivityAsync`，不新增调用点 |
| `Source/PuddingRuntimeTests/Services/LlmStreamObservabilityTests.cs` | 新增门禁 `ChatAsync_WhenRequestUploadReset_RecordsCauseAndRequestBytes`（同一真实异常链） |
| `Docs/12_features/可诊断基础设施设计-2026-10-07.md` | 新增 §16：非流式补齐、S5 收尾、实测汇总、仍然未做（含"事实表加列会让已有库缺列，必须配幂等启动期升级"的明确警示） |

## 验证（实测）

```
dotnet test ...PuddingRuntimeTests --filter (LlmStreamObservability|DiagnosticContractGate) → 已通过! 23/23
dotnet test Tests\PuddingHost.Tests --filter PuddingApplicationHostCompositionTests → 已通过! 2/2   （S5 第④步）
```

新门禁断言 `chat` 活动：`ErrorCode=transport.request_upload_reset`、`cause_phase=request_upload`、
`socket_error_code=10054`、`attempt=1`、**`request_bytes>0`**。

S5 收尾说明：本刀未新增 DI 注册（诊断作用域与分类器都是无状态纯计算，不需要容器），
宿主组合测试通过即证明新增工程引用没有扰动 `ValidateOnBuild`。

## 未完成

- **前端**（Stage 4-b）：错误卡按 `causeCode` 映射 +「复制诊断信息 / 下载 JSON」按钮（后端已给出
  `error.reportText` / `error.reportJson`）；改动须递增前端版本并重新构建部署 `wwwroot/admin`。
- **查询面与索引列**（Stage 4-c）：`runtime_activity` / `telemetry_metric_events` **没有 EF 迁移链路**
  （建表走 `EnsureCreatedAsync`），直接加列会让已存在的库缺列并导致运行期 SQLite 报错；
  必须先做一个幂等的启动期 schema 升级（`PRAGMA table_info` 探测 + `ALTER TABLE ADD COLUMN`）
  或明确重置策略，并有针对性验证后再动。
- `providerId`（需把 LLM 路由快照的 provider 传到终态构造点）与多次尝试明细。
