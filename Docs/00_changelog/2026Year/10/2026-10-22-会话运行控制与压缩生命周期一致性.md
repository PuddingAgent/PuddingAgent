# 会话运行控制与压缩生命周期一致性

归因：服务端仍持续执行工具且压缩提交成功，浏览器却显示无活动回复。只读 API 和浏览器组件状态对照发现，心跳输入的成功状态/提示正文被合并为助手终态，实际 running 快照被隐藏；Composer 同时读取旧本地 loading 与 messageId 映射，刷新后无法停止或插嘴。压缩生命周期经过主会话投影过滤后没有接入其唯一处理者，空正文终态又被列表丢弃。这不是网络上传失败或压缩提交锁死。

改动：

- `conversationExecution.ts` 按作用域派生运行态与 canonical Turn ID；`useChatState`、`useMessageInteractionQueue`、`index.tsx` 共同使用同一快照。终态清除控制目标，runId 和独立压缩卡不能作为取消/插嘴目标。
- `MessageList.tsx` 分开心跳输入与执行回复，在当前消息流边缘显示真实运行卡；列表合并和 `types.ts` 消息块生成保留没有正文的压缩记录。
- `useSessionEventProjection.ts` 在主消息所有权过滤前将四类压缩事件交给 `useCompaction`，保留去重与 replay 语义。`skipped` 进入未改动终态，历史重放不复活。
- 前端版本 `6.10.1` → `6.10.2`；补充代码地图和[排查手册](../../../08_how_debuge/13-案例-浏览器Bridge与Chat.md)。

验证：9 个定向 Jest 套件 178/178 通过，TypeScript 检查通过。覆盖真实故障形状：心跳输入和活动 run 共用 Turn、没有本地追踪表的刷新、压缩终态路由/去重、空正文终态卡、跨会话身份隔离。Jest 使用 `--forceExit` 处理既有异步句柄；日志位于 `temp/chat-stall-tests.log` 和 `temp/chat-stall-tsc.log`。

现场：会话 `206a9b48ec904ebb93e7541131fbb835`，执行 `1931a6b47ee94f138437950842afd9dd`，Turn `832708f097424068b904c64e0657dbac`。只读快照、渲染状态与截图保留在忽略目录 `temp/chat-stall-*`；未复制密钥、改写会话数据库或重新发送排队消息。

文档验证：变更文档 Front Matter 通过，子项目代码地图门禁 0 error；全仓文档链接检查为 26 个既有失效目标、0 个失效锚点，本次没有新增失效链接。

未完成：本提交尚待干净构建、Desktop 静态前端热部署与在线浏览器回验；后续追加实际产物身份及验证结果。后端队列策略未更改，长任务期间普通消息继续排队；停止和插嘴由用户通过恢复的运行控制选择。

## 补充（2026-10-22）：历史维护卡排序

`6.10.2` 干净构建后已通过 Desktop 的前端加载接口部署，在线资源与 273 个产物文件哈希一致，Desktop 页角显示 `6.10.2 · 1828b18`，Core 进程保持运行。只读浏览器验证运行卡和停止控制恢复；实机回验同时发现，恢复的历史压缩卡被追加到末尾，且旧排队输入的活动回复留在较早的位置，遮挡了最新工作进展。

修正 `MessageList.tsx`：按事件时间插入历史压缩卡，保持原消息顺序；旧排队输入仍在原位，活动回复显示到消息流末端。前端版本递增为 `6.10.3`。列表与消息投影 2 个套件 56/56 通过，TypeScript 检查通过；日志为 `temp/chat-stall-order-tests.log`、`temp/chat-stall-order-tsc.log`。本次仍待新版本构建部署与回验。
