# 2026-10-08 页面事件事实上报 Agent + 修复 WinUI 面自 round 36 起的编译中断

## 一、页面事件事实终于到 Agent 手里

前两轮做了五类页面事件的确定性接管（脚本对话框/权限请求/新窗口/下载），但**事实只留在驱动内部**：
"页面不卡了"却没人知道为什么 —— 只完成了一半价值。本轮补齐另一半。

| 层 | 改动 |
|---|---|
| Automation | `PageEventLog.cs`（新增）：有界日志（默认 8 条）、**连续重复合并为计数**、`TotalCount` 如实（含被容量挤掉的）、空摘要不计入 |
| 驱动 | 用 `PageEventLog` 记录五类事件；`PageSnapshot.PageEvents` 带出（无事件 ⇒ `null`，**不填「一切正常」**） |
| 契约/运行时 | `DesktopSnapshot.PageEvents` / `SnapshotOptions`→`PageSnapshot.PageEvents` |
| 能力通道 + 桥接 | 内进程面与桥接面都映射；桥协议 `BrowserSnapshotDescriptor.PageEvents`；宿主处理端同步 |
| 工具 | 输出 `pageEvents`（最多最近 4 条）**并并入 `warnings`**（`page_event: …`）——Agent 常常只看 warnings |

验证：`AutomationTests` **270/270**（＋6）、`AgentTools.Tests` **63/63**（＋1）、其余套件不变（见下表）。
取红实测：把 `PageEvents = PageEventsOf(...)` 改成 `null` ⇒ `Snapshot_ReportsPageEvents_…` **恰好变红**；复原后 63/63 复绿。

## 二、（更重要）WinUI 面的编译中断：从 round 36 起就坏了，我此前没发现

排障时构建 `PuddingBrowser.WinUI` 才发现：

```
WebView2BrowserPage.cs(4,22): error CS0234: 命名空间"PuddingBrowser"中不存在类型或命名空间名"Automation"
```

**原因**：`PuddingBrowser.WinUI.csproj` **链接**驱动源码
（`WebView2BrowserRuntime/Context/Page/DomClient/ElementHandle`），并用 `EnforceBrowserBoundary` 目标
**强制只允许引用 `PuddingBrowser.Abstractions`**。而我从 round 36 起在**共享源码**里使用了
Automation 类型（`NativeInputSequence`、`ScreenshotPlan`、`ScriptDialogPolicy`、`PageEventPolicy`、
`PageEventLog`），并在 `PuddingBrowser.WebView2.csproj` 里加了 Automation 引用 —— 那只修好了
**WebView2 项目自己的编译**，链接同一文件的 WinUI 面则一直编不过。

**验证这是"自 round 36 起"而非本轮引入**：把本轮未提交的该文件改动 stash 后构建 WinUI，**HEAD 同样报错** ✓。

**修法**（在共享源码里用 `#if`，与文件里既有的 `#if WINUI_BROWSER`（导航完成事件）保持一致）：
- `using PuddingBrowser.Automation;` 与页面事件日志、五类事件订阅/处理器：`#if !WINUI_BROWSER`；
- 原生输入、原生滚动：`#else` 分支**显式抛 `browser_input_mode_not_supported`**（提示用 `input_mode=dom`），
  **绝不静默回落**；
- 截图：`#else` 抛 `NotSupportedException`（回到本轮之前的诚实状态）；
- 另外修掉一个 WinUI 侧投影差异：`CallDevToolsProtocolMethodAsync` 在 WinRT 投影下返回
  `IAsyncOperation<string>`，原来的 `() => …` lambda 无法隐式当 `Task` 用，改成 `async () => await …`（两种投影都能编译）。

结果：**`PuddingBrowser.WinUI` 重新可以编译**（`已成功生成`）。

## 已知边界（诚实登记）

- **WinUI 面（产品 Shell 链接的那一份）缺少本轮及 round 36–47 的能力**：原生输入/原生滚动/截图不可用
  （显式 unsupported）、五类页面事件未接管。要补齐必须**把策略注入进来**（Abstractions 定义 seam，
  Desktop 侧注入 Automation 实现），而不是让共享源码直接引用 Automation —— 这是下一轮的首要任务，
  已写进 code_map 的边界说明。
- **验证方法上的教训（真实问题）**：我此前每轮只构建"受影响的项目"，因此链接同一份源码的
  **WinUI 面坏了 11 轮没人发现**。后续凡改动共享驱动源码，必须**同时构建 `PuddingBrowser.WinUI`**。
- `PuddingDesktop` 的最终产物未能重新生成（文件被占用），因此**没有**在本轮验证桌面产品的整体构建；
  这是环境限制，不是"已验证通过"。
- 页面事件摘要仍可能包含页面可控文本（截断到 80/120 字符并去掉控制字符，但**没有做内容脱敏**）：
  如果将来发现敏感信息经此路径外泄，需要在写入日志前增加过滤。

## 影响与回滚

- **行为变化（Agent 可见）**：`browser_snapshot` 输出新增 `pageEvents`（最多 4 条）并在有事件时把它们并入
  `warnings`（`page_event: …`）。没有事件时字段为 `null`（不编造）。
- **行为变化（WinUI 面）**：恢复"可编译但无这些能力"的状态（显式 unsupported），与 round 36 之前一致。
- 回滚：还原 `PageEventLog.cs`、驱动的事件日志/`#if` 守卫、契约/协议/工具映射、其测试与冻结列表、code_map。
