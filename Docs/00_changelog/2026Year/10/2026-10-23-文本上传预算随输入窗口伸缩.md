# 2026-10-23 文本上传预算随输入窗口伸缩

## 背景：固定 512 KiB 与 1M 窗口不相容

`LlmRequestTextBudget` 原本对所有 DeepSeek Responses 请求硬编码 `DeepSeekResponsesLimit = 512 KiB`。
在 `deepseek-flash` 的 1,000,000 token 输入窗口（资源池登记 `maxContextTokens`，1M 按十进制 10^6 计）下，**固定前缀**（系统提示 + 工具定义 + 技能索引）
实测约 **506 KB**（≈ 该预算的 98.6%，见「工具曝光有界化」与「技能索引层瘦身」两次削减后的残余），
历史正文只剩约 6 KB 余量 ⇒ 几乎每轮都判定「文本体积越界」并强制压缩，而压缩调用缓存命中率≈0
且会作废整段 warm prefix 缓存。净效果与前一条「微小回收守卫」同因：**花大钱换小回收**。

## 改动

- `Source/PuddingRuntime/Services/LlmRequestTextBudget.cs`
  - 常量改名并降级为**下限**：`DeepSeekResponsesLimit` → `MinimumTextBudgetBytes = 512 KiB`（语义不变，不再是唯一取值）。
  - 新增 `ConservativeBytesPerToken = 3`：CJK 约 3 B/token 是最坏折算，用它可保证字节预算不会反推出超窗请求；
    英文/代码约 4~4.5 B/token，天然留富余。
  - `ResolveLimit` 改为 `Clamp(3 × 有效输入窗口, 512 KiB, int.MaxValue)`，窗口取自
    `LlmRequestBudgetGuard.ResolveEffectiveInputLimit`（与压缩判定同源，含 reply 预留与 safety buffer）；
    窗口未知（≤0 或 `int.MaxValue`）时回落到下限。非 DeepSeek 路由仍返回 0（不参与该预算）。
- `Source/PuddingRuntime/Services/AgentExecution/AgentExecutionService.Compaction.cs`
  - 维护边界决策处补 `LogDebug("[AgentExec:Compaction] Boundary decision …")`：一行内同时给出
    `prepare/commit/wait/pressure/tokens/window/bytes/limit/growthTokens/growthBytes/hasCandidate/ready`。
    动机：`Text upload budget triggered` 只在**派发前体积校验**里打，流式路径压缩成功时不会走到该行，
    排障时无法区分「token 触发」与「字节触发」；有了这一行，两条压力口径当场可读（也是 E2E 的取证点）。

## 测试

- `Source/PuddingRuntimeTests/Services/LlmRequestTextBudgetTests.cs`：新增/改写契约，覆盖
  1M 窗口按 3 B/token 放大、小窗口被 512 KiB 下限兜住、窗口未知回落下限、非 DeepSeek 返回 0。
- `Source/PuddingRuntimeTests/Services/WarmPrefixMidTurnHardProtectionE2ETests.cs`：夹具从「常量预算」
  改为「按模型窗口算预算」，并且不再「碰运气」越线——`MegabyteHistory_…` 在派发前用实测体积补足最后一条消息，
  **补足后立刻断言** `Measure(history) > ResolveLimit(request)`（前提有牙齿），再做原有用例断言。
  「触发原因是字节压力」的断言改成取证式：命中 `Text upload budget triggered`（非流式）
  **或** `Boundary decision` 行里 `bytes/limit ≥ 0.95`（流式）。
  变异取红：把该阈值改成 2.0 后，恰好只有两条流式大窗口行转红（`(False,True,True)`、`(True,True,True)`），
  说明新分支是承重的，不是空转。

### 计量口径（2026-10-23 校正）

窗口一律取资源池登记值：`deepseek/deepseek-flash` 的 `maxContextTokens = 1,000,000`（1M = 10^6，
**不是** 2^20 = 1,048,576）。有效输入窗口与字节预算按同一公式换算：

- 有效输入 tokens = 窗口 − reply 预留（`LlmConfig.MaxOutputTokens`）− safety buffer（1,024）；
- 字节预算 = 3 × 有效输入 tokens，下限 512 KiB；
- 夹具（window = `1_000_000`、output = `1_000`）⇒ 有效输入 997,976 tokens ⇒ 预算 **2,993,928 B**。

单测与 E2E 里的窗口字面量已由 `1_048_576` 改为 `1_000_000`，避免「拿 2 的幂冒充 1M」导致的口径漂移。

## 遗留

- 预算缩放目前只对 DeepSeek（responses 协议）生效；openai / anthropic 路由仍返回 0（不设该预算），
  如需统一口径应另起一次改动并配红测试。
- 固定前缀 ≈ 506 KB 仍是 1M 窗口下的主要成本项；本改动只是让**预算**不再误判，前缀本身的削减（工具曝光、技能索引）仍可继续。
- **reply 预留取的是登记值 `maxOutputTokens = 393,216`（链路已核实）**：`config/llm.providers.json`
  → `PuddingFileLlmConfigService.ToLlmConfig` → `LlmConfig.MaxOutputTokens` → `LlmRequestBudgetGuard`。
  故运行时有效输入只有 605,760 tokens（1,000,000 − 393,216 − 1,024）、文本预算 ≈ **1,817,280 B（≈1.73 MiB）**，
  比夹具口径（997,976 tokens / 2,993,928 B）低约 39%。缺的只是运行进程的 Debug 级 `Boundary decision`
  实测日志（默认 INF 级不落盘），不是链路不明。
- 建议下一轮改造：reply 预留改为 `min(登记 maxOutputTokens, 单一回复上限配置)`，或优先采用登记的
  `maxInputTokens`；否则「模型硬上限」被当作「本回合会用到的输出」，白扣 39% 窗口。


## 追加（同日）：reply 预留收敛到单轮上限 64,000

上节遗留第 3 条（「登记的 `maxOutputTokens` 被当成这一回合会用的输出」）已修。

### 改动

| 文件 | 变更 |
|---|---|
| `Source/PuddingRuntime/Services/LlmReplyBudget.cs`（新增） | 单轮回复口径的唯一出口：`PerTurnOutputCapTokens = 64_000`；`ResolveRequestTokens(int?)` = `min(登记, 上限)`（`null` / `0` 原样透传）；`ResolveReservedTokens(int?)` = `min(max(0, 登记), 上限)`（脏数据不得变成负预留） |
| `Source/PuddingRuntime/Services/LlmRequestBudgetGuard.cs` | 窗口预留改用 `ResolveReservedTokens`，不再直取登记值 |
| `Source/PuddingRuntime/Services/DirectLlmClient.cs` | 网关请求 `max_tokens` 改用 `ResolveRequestTokens`，**发出的值恒等于预留值**（下游 `MaxTokens` / metadata / 日志同源） |
| `AgentExecutionService.Buffered.cs` / `.Streaming.cs` | 在 `effectiveLlmConfig` 源头收敛 `MaxOutputTokens`，使 `TrimHistoryAsync`、`ContextHealthEvaluator` 与摘要 allowance 共用同一每轮值；边界处修复退化为幂等兜底 |
| `Source/PuddingRuntimeTests/Services/LlmReplyBudgetTests.cs`（新增） | 3 用例：登记 393,216 / `int.MaxValue` → 64,000；8,192 与 0 透传；`null` → 0 预留且 `-5` 不为负 |

### 口径

- 预留 = `min(393,216, 64,000)` = **64,000** tokens（窗口 6.4%，原为 39.3%）。
- 有效输入窗口 = 1,000,000 − 64,000 − 1,024 = **934,976** tokens（原 605,760，多出 329,216）。
- 文本预算 = 3 × 934,976 ≈ **2,804,928 B（≈2.67 MiB）**（原 1,817,280 B）。
- 未登记 `maxOutputTokens` 时**不预留**：保持「登记了什么就用什么」，不臆造上限。
