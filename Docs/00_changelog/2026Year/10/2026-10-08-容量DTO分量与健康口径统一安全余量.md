# 2026-10-08 容量 DTO 分量与来源、健康口径与出站硬门禁统一安全余量

> 范围：`Source/PuddingCore/Runtime/ContextCompactionContracts.cs`、`Source/PuddingRuntime/Services/ContextHealthEvaluator.cs`、`Source/PuddingRuntime/Services/ContextCompactionService.cs`、`Source/PuddingRuntimeTests/Services/ContextHealthEvaluatorTests.cs`、`Source/PuddingMemoryEngineTests/ContextCompactionServiceTests.cs`、`Source/PuddingPlatformAdmin/`（`services/platform/api.ts`、`chat/components/inputUnavailable.ts`、`ContextUsageRing.tsx`、`ComposerStatusDetails.tsx`、`IntentConsole.tsx`、`serviceStatus.ts` 及 `.test` 文件）
> 依据：[修复方案](../../../12_features/首Token等待与上下文指示器修复方案-2026-10-07.md) §1 第 5 行 + §2.5、[ADR-095](../../../07_architecture/109ADR-095会话上下文维护与首增量延迟治理ADR.md) D7、[诊断报告](../../../14_reports/首Token等待与上下文指示器诊断-2026-10-07.md) §4.4
> 承接：[上一增量](2026-10-08-上下文指示器区分容量压力与服务故障.md) 留下的「容量 DTO 分量缺失 ⇒ 只能显示来源未知」

## 问题（改动前）

1. **差值被当成「预留输出」**。UI 用 `contextWindowTokens − effectiveWindowTokens` 命名不可用区，但该差值可能来自实际输出预算、Provider 输入上限、安全余量或三者叠加。截图里的 `393.2K` 究竟是运行请求输出预算还是注册模型上限，诊断 §4.4 明确「未核实」，改动前也没有任何字段可供判断。
2. **健康口径与出站硬门禁不共享安全余量**。`LlmRequestBudgetGuard.ResolveEffectiveInputLimit` 的子式是 `模型窗口 − 实际输出预算 − 安全余量`（默认 1,024），而 `ContextCompactionService.GetHealthAsync` 调 `Evaluate` 时没有传安全余量。于是同一次请求在健康面板与日志硬上限上会出现两个数（诊断 §4.4：约 `606,784` 对 `605,760`），而两者本应同源。
3. **回退值冒充预算**。容量没有给出输出预算时，`GetHealthAsync` 传入回退值 `2,048` 让门禁照常工作；这个值此前没有任何出口，会被读成「用户配置了 2,048 的输出预算」。

## 改动

### 1. 契约：容量分量与来源（`ContextCompactionContracts.cs`）

新增 `ContextEffectiveWindowSources` 常量（`output_reserve` / `provider_input_limit` / `safety_margin` / `output_reserve_and_safety_margin` / `fallback_output_reserve` / `model_window` / `unknown`），并给 `ContextHealthSnapshot` 增加四个 init 属性：

- `ProviderInputLimitTokens`（null = 未配置，不伪造）
- `RequestedOutputBudgetTokens`（**容量侧真实预算**；null = 容量没给，门禁用了回退值）
- `SafetyBufferTokens`
- `EffectiveWindowSource`（有效输入上限为什么比模型窗口小）

### 2. 评估器：如实标注来源（`ContextHealthEvaluator.cs`）

`Evaluate` 新增末位可选参数 `requestedOutputBudgetTokens` 与 `outputBudgetIsFallback`（C# 无法区分「省略」与「显式传 null」，故用独立开关而非哨兵值，注释里写明）。来源判定顺序：Provider 输入上限优先（它一定来自真实配置）→ 输出预算与安全余量的组合 → 只有安全余量 → 只有回退预留（记为 `fallback_output_reserve`，**不冒充用户预算**）→ 无预留（`model_window`）。既有调用者语义不变（省略参数时按 `maxOutputTokens` 为真实预算）。

### 3. 服务：健康分母与出站硬门禁同源（`ContextCompactionService.cs`）

`GetHealthAsync` 改为传 `safetyBufferTokens: LlmRequestBudgetGuard.DefaultSafetyBufferTokens`，并把回退值提为命名常量 `DefaultOutputReserveTokens = 2_048` 且标记 `outputBudgetIsFallback` —— 门禁数学不变（未放宽硬保护），只是把「实际预算」与「回退值」在输出上分开。

### 4. 前端：按来源命名，不再猜（`PuddingPlatformAdmin`）

- `inputUnavailable.ts`：取值与后端 `ContextEffectiveWindowSources` **逐字对齐**（原先前端自造了 `reserved_output` 这个名字），新增 `toInputUnavailableReason(source)` 把后端字符串映射为已知来源，未知取值 ⇒ `undefined`（不猜）；`fallback_output_reserve` 的文案是「内置回退预留（未配置输出预算）」。
- `api.ts`：`ContextHealthSnapshot` 补上四个字段。
- `IntentConsole.tsx`：把 `effectiveWindowSource` 一路传给圆环（`tUnavailableReason`）与 composer 摘要（`token.unavailableReason`）。
- `ContextUsageRing.tsx` / `ComposerStatusDetails.tsx`：不可用区名称改为来自来源；缺失时仍是「不可用于输入（来源未知）」。

新增/扩展用例：

- `ContextHealthEvaluatorTests`（+4）：真实输出预算 + 安全余量 ⇒ 来源 `output_reserve_and_safety_margin` 且四个分量各自正确；Provider 输入上限取小时来源指向它并上报该上限；**回退预留不得被报告成用户预算**（`RequestedOutputBudgetTokens == null` 且来源为 `fallback_output_reserve`）；无预留 ⇒ `model_window`、只有安全余量 ⇒ `safety_margin`。
- `ContextCompactionServiceTests`：三处原先硬编码的整数改为**与出站硬门禁同源**的表达式（`… − LlmRequestBudgetGuard.DefaultSafetyBufferTokens`），并新增断言 `health.SafetyBufferTokens == DefaultSafetyBufferTokens`、`health.EffectiveWindowSource == OutputReserveAndSafetyMargin`、`health.RequestedOutputBudgetTokens == 384_000`。改的是口径而不是为了变绿放宽断言。
- 前端：`serviceStatus.test.ts` 断言五种来源文案 + `toInputUnavailableReason` 只映射已知来源（`model_window`/未知字符串 ⇒ `undefined`）；`ContextUsageRing.test.tsx` 的来源取值改为与后端对齐。

### 关于 `PuddingMemoryEngineTests` 的 3 个失败

失败用例是 `ContextPipeline_ShouldAssembleAll7Layers`、`EnvironmentLayer_ShouldBePresentInAssemblyResult`、`ContextPipeline_ShouldTriggerGentleCompaction`，断言的是「环境信息 / 近期历史」分层是否出现。判定与本改动**无关**，依据有三条：

1. **代码路径零接触**：`ContextPipeline*.cs` 与 `ContextAssemblyService.cs` 对 `ContextHealth` / `EffectiveWindow` / `GetHealthAsync` / `ContextCompactionService` **零引用**（按文件全文检索确认），而本改动唯一触及的服务入口 `ContextCompactionService.GetHealthAsync` 不在这条路径上。
2. **干净基线复现**：在 HEAD（`6e978cb`，即本增量之前）用 `git worktree add temp/wt-head HEAD` 检出干净工作树，跑 `--filter "FullyQualifiedName~MemoryLibraryTests"` 得到 **失败 4 / 通过 53**，其中就包含这 3 个用例（外加同类的 `TerminalProcess_ShouldStartAndReturnPid`，也是环境依赖）。即这 3 个失败在改动前就存在。
3. **失败数单调下降**：本增量把该项目失败数从 6 降到 3，减少的正是受安全余量口径影响的 3 个 `GetHealthAsync_*` 用例（已同步更新为与出站硬门禁同源的表达式）。

这 4 个用例依赖运行环境的「环境信息 / 终端进程」能力，属既有环境依赖问题，需单独排查，不在本轮范围。
