# 2026-10-08 请求副本裁剪成为独立事实（计时 + canonical 事件 + 前端展示）

> 范围：`Source/PuddingCore/Platform/SseEventTypes.cs`、`Source/PuddingCore/Platform/ConversationContracts.cs`、
> `Source/PuddingRuntime/Services/AgentExecution/AgentTurnTimingCollector.cs`、
> `Source/PuddingRuntime/Services/ContextWindowManager.cs`、
> `Source/PuddingRuntime/Services/AgentExecution/AgentExecutionService.Streaming.cs`、
> `Source/PuddingRuntime/Services/AgentExecution/AgentExecutionService.Buffered.cs`、
> `Source/PuddingPlatformAdmin/`（`TurnTimingPanel.tsx` + `.test.tsx`、`services/platform/api.ts`、`package.json` 6.4.2 → **6.4.3**）
> 依据：[修复方案](../../../12_features/首Token等待与上下文指示器修复方案-2026-10-07.md) §2（「请求副本裁剪另发有界 canonical 请求准备事实…文案为『本次请求裁剪了旧上下文』」）、§1 第 2 行（计时归因）、[ADR-095](../../../07_architecture/109ADR-095会话上下文维护与首增量延迟治理ADR.md) D7
> 来源：[诊断报告](../../../14_reports/首Token等待与上下文指示器诊断-2026-10-07.md) §4.1 记录的「后续 22:57:20 同一 run 的 round23 Trimmed outbound history removed=91…不能冒充新增持久摘要」

## 1. 问题

出站硬预算裁剪（`LlmRequestBudgetGuard.Prepare` 的 `RemovedMessageCount > 0`）此前**只有一条 Warning 日志**：

- 用户/诊断侧无法区分「这次请求少带了旧上下文」与「会话历史真的被压缩了」——两者在界面上都可能被读成
  「上下文被删/被压缩」；
- 计时面板也没有这块事实：`TurnTimings` 契约里连 `compactionMs` 都还没有（后端 T4 已下发，前端类型未补），
  更没有裁剪条数/轮数；
- 诊断 §4.1 明确要求：请求副本裁剪必须作为**与持久摘要压缩不同**的操作单独展示，且完整会话记录仍在。

## 2. 改动

### 2.1 canonical 事实：`context.request.trimmed`

- `SseEventTypes` / `ConversationEventTypes` 新增 `ContextRequestTrimmed = "context.request.trimmed"`。
  注释明确：**不得复用** `context.compaction.*` 的语义，前端不得据此显示「已压缩」。
- `ContextWindowManager` 新增 `EmitRequestCopyTrimmedAsync(...)`，复用同一个 canonical 事件管道
  （不新增事件库、不新增轮询）。
- payload（有界、无正文）：`round`、`invocationId`、`removedMessages`、`estimatedAfterTokens`、
  `rawEstimatedTokens`、`effectiveInputLimit`、`calibration`，以及两个显式区分字段
  **`durableCompaction = false`**、**`completeSessionHistoryRetained = true`**。
- **每 dispatch 只发一次**：后续轮次的裁剪计入计时聚合，不重复发事件
  （诊断里出现过同一 run 连续 10+ 轮 `removed=91`，逐轮发事件只会制造噪声）。
- 目录投影安全：`ConversationCatalogWriter` 对未知事件走 `_ => null`，保持会话原状态，
  不会像 `context.compaction.completed` 那样投影成 `frozen`。

### 2.2 计时归因

`AgentTurnTimingCollector` 新增（与压缩计数**分开**）：

| 字段 | 含义 |
|---|---|
| `RequestTrimmedRounds` | 本 dispatch 内发生请求副本裁剪的轮数（0 = 未裁剪） |
| `RequestTrimmedMessages` | 被裁掉的消息总条数（各轮累加） |
| `FirstRequestTrimMs` | 首次裁剪时刻（相对提交）；从未裁剪为 **null**（不用 0 冒充已测量） |

`RegisterRequestTrim(<=0)` 不构成事实（直接忽略）。三个键进入 `done` 帧的 `timings` 载荷。

### 2.3 前端

- `TurnTimings` 契约补齐：`compactionMs`、`compactionAttempts`、`deferredSoftCompactions`、
  `appliedCompactions`、`requestTrimmedMessages`、`requestTrimmedRounds`、`firstRequestTrimMs`
  （前四项后端 T4 已下发但前端类型缺失 ⇒ 面板一直读不到）。
- `TurnTimingPanel` 新增两行：**「同步压缩耗时」**（`compactionMs`）与
  **「本次请求裁剪旧上下文」**。
- 新增纯函数 `formatRequestTrim` 保持本面板的**三态纪律**：
  - 未采集 ⇒ 「未采集」；
  - 采到 **0** ⇒ 「0 条」（真的没裁剪是好事实，不许折叠成未采集）；
  - 采到 >0 ⇒ `N 条（M 轮 · 完整会话记录仍保留）`。
- `package.json` 版本 6.4.2 → **6.4.3**（展示类改动，修订号递增）。

**过程中的一次自伤与修复**（留痕）：版本号递增第一次用 PowerShell `Set-Content -Encoding utf8` 写入了 BOM，
导致 `package.json` 解析失败、`pnpm` 的 `postinstall(max setup)` 连带 46 个 esbuild 报错。
已用无 BOM 的 UTF-8 重写并 `json.load` 校验通过（`version = 6.4.3`），`git diff` 对该文件只剩 1 行改动。
教训：**改 JSON 不能用 PS5.1 的 `-Encoding utf8`**（它写 BOM）。


## 4. 未完成

- F2 持久化尾款（事务 checkpoint/generation、重启恢复、事件幂等补投）**未实施**：见
  [F2 首批](2026-10-08-F2首批warm-prefix唯一应用边界与真实after.md) §3 的原因 —— 内存历史
  （`List<ChatMessage>`）**不携带持久消息 id**，无法把「被替换跨度」映射回 `MessageEntity` 行，
  因此不能安全地写 `CompactedBy`/覆盖清单；这需要在 hydration 边界引入稳定身份，属独立设计。
- 前端消费新 canonical 事件本身（例如在消息流里插一条「本次请求裁剪旧上下文」事实卡）**未做**：
  本轮先把事实落进终态 timing 载荷并由面板展示（现有链路，零新增订阅）；事件已入库可供后续消费。
- Session 单飞/去重/抢占与「终态后调度」仍未交付（见 [F3 首批](2026-10-08-F3首批硬保护逐轮重新评估.md) §4）。
- 交付状态仍为 **ready-for-external-deploy**；无真实模型调用、无部署、无浏览器证据。
