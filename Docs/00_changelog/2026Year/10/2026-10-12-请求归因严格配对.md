# 2026-10-12 修复：请求归因严格配对

> 依据：用户转达的复核结论第 2 项（P1，已复现）。位置：`LlmOptions.TryGetPreparedRequest`（原 attempt→invocation 回退）。

## 1. 缺陷（复核探针）

明确传入 `attempt-never-prepared` 时，`TryGetPreparedRequest` 先试 attempt 键、失败后继续试 invocation 键
⇒ 匹配到 `attempt-known`。后果：未知或已被淘汰的 attempt 的 usage 会借用**另一次请求**的 raw 参与校准，
把「按身份配对」重新变成概率匹配。

## 2. 修复

`TryGetPreparedRequest` 重写为两条明确规则：

| 输入 | 规则 |
|---|---|
| **给了 attempt** | 必须精确命中 `attempt:<id>` 键；命中记录的 `InvocationId` 还必须与传入的 invocation 一致（给了才算），否则视为身份冲突 ⇒ 未配对。**不再回退 invocation** |
| **未给 attempt、给了 invocation** | 仅当该 invocation 对应**唯一**一次冻结请求时才允许这一明确约定的降级匹配；同一 invocation 有多次 attempt（重试）⇒ 歧义 ⇒ 未配对 |

配套：
- 新增 `_preparedByInvocation` 索引（invocation → 各 attempt 的序号集合）用于「唯一性」判据，并随主注册表一同按序号有界淘汰。
- `RecordProviderUsage` 两条路径都核验 **purpose 类别**：辅助 usage 不得借主请求记录（raw 记 0）、
  主 usage 不得借辅助记录（进未配对账本）。
- 实测记录改记**配对到的那次冻结请求**的 invocation/attempt，而不是调用方传入值
  （降级匹配时调用方可能没给 attempt，展示与诊断因此不会有歧义）。

## 3. 验证（本机真实执行）

`PuddingCoreTests` 新增 `RequestAttributionStrictPairingTests` 5 条：

1. `UnknownAttempt_DoesNotFallBackToKnownAttempt` —— **复核探针等价场景**：未知 attempt ⇒ 未配对
   （校准保持 1.0、不进投影、准备槽位原对象不变、留证于未配对账本）。
2. `AttemptWithMismatchedInvocation_IsUnpaired` —— attempt 命中但 invocation 对不上 ⇒ 身份冲突，不配对。
3. `InvocationOnlyFallback_RequiresUniqueness` —— 唯一时降级匹配成功并记录真实 attempt；
   出现第二次 attempt 后同 invocation 的降级匹配必须失败（投影保持原值、校准不再抬高）。
4. `AuxiliaryUsage_DoesNotBorrowMainPreparedRecord` —— 辅助 usage 借主记录 ⇒ 视为未配对（raw=0）。
5. `RetriedAttempts_PairPerAttempt` —— 多次重试各自配对，按请求序号推进投影。

结果：`--filter RequestAttribution` **19/19**；`PuddingCoreTests` 全量 **1079 通过 / 0 失败**
（上批 1074 + 新增 5）。
