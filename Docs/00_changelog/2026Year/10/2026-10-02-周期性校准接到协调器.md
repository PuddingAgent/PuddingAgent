# 2026-10-02 周期性校准接到协调器

## 为什么这一刀是启用前的硬前提

上一轮已把「提示驱动的批次」改成按路径观测（不再全树枚举）。但**周期性校准钟**（默认 15 分钟）
仍由旧的 `CodeIndexCalibrationService` 直接扫 store、直接删陈旧行，而新链路的 manifest/账本由协调器维护。
两条链路并存时，「索引」与「manifest」会对同一路径给出不同结论 —— 这是启用 `Coordinator` 之前必须消除的分叉。

## 改动

- `Source/PuddingCodeIndex/Services/CodeIndex/CodeIndexMaintenanceService.cs`：
  `CalibrateDueScopesAsync` 在 `Coordinator` 模式下改走新增的
  `CalibrateViaSourceMaintenanceAsync`（协调器 **完整**扫描，`Targeted: false`，无提示），
  并把结果映射回**与旧路径完全相同的簿记语义**：
  - 根不可用 ⇒ 标位 `CalibrationRootUnavailable` + `RejectedCalibrationRunCount++` + 走退避阶梯，
    一个文件都不删（**绝不把「读不到」当成「没有陈旧行」**）；
  - 扫描不完整 ⇒ 标位 `CalibrationTruncated` + 复位退避档位（它读到了根：剩余轮次按基础间隔推进）；
  - 完整且根可用 ⇒ 清除标位 + 复位退避档位，`SweptFileCount += 本轮确认删除数`。
  - 到期判据（`IsCalibrationDue` / 退避阶梯 / 只按上次完成计时）**一字未改**，两条模式共用同一套节拍。
- `CodeSourceScanRun` / `CodeSourceMaintenanceRunResult` 增加 `RootUsable`：
  **空结果路径也必须带上它**（否则「根不可用但这一轮没有任何变更」会被误报成可用 —— 实测正是这个缺陷
  让「根被拒」只能退化成「扫描不完整」，从而少了退避档位的推进）。
- `CodeSourceMaintenanceMode` 文档更新：周期性校准已接线；并登记「scope 级全量重索引不更新新 manifest，
  会让指纹暂时陈旧（随后由协调器重新提取而自愈）」。

## 验证

- `dotnet test Source\PuddingCodeIndexTests` → **320 通过 0 失败**（本次 +2）。
- `dotnet test Source\PuddingCodeIntelligenceTests` → **132 通过 0 失败**。
- `dotnet test Tests\PuddingHost.Tests --filter CodeIndexMaintenanceHostCompositionTests` → **4 通过 0 失败**。
- 新增用例：**陈旧行经协调器清理**（索引行与 manifest 记录一起消失、`SweptFileCount ≥ 1`、标位被清除）；
  **根不可用保持标位**（`NeedsReconcile` 为真、`RejectedCalibrationRunCount ≥ 1`、`SweptFileCount == 0`）。
- 既有 15 分钟常规钟、退避阶梯、截断/拒绝语义的用例（`CodeIndexRoutineCalibrationTests`、
  `CodeIndexCalibrationBackoffTests` 等）在 Legacy 模式下全部保持通过 ⇒ 节拍语义未变。

## 未完成与影响

- 默认仍是 `Legacy` ⇒ **运行中实例行为未变**，本轮不需要重启，也不构成性能结论。
- 剩余启用前提：**watcher 事件到提示的节流/合并**（延迟优化，不影响正确性）→ 然后由
  **进程外控制器重启到明确的新构建**，跑四场景受控复核（无变更时是否仍读盘 / 单文件改动的读盘量 /
  删除只由完整扫描确认 / 根不可用不误删）。
