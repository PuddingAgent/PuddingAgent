# Agent 浏览器 V1 授权的三道门与零页面死锁修复

## 裁定

用户 2026-10-18 明确：**PuddingDesktop 提供的浏览器不需要用户授权**，V1 之前不做限制；并指出「授权给 Agent」这一逻辑本身不正确。本节记录按此裁定逐层拆除旧授权模型闸门的过程，每处都有实测现象与回归用例。

## 三道门

### 门一：页面必须由用户交接（`agent_target_required`）

- **现象**：`browser_navigate` / `browser_snapshot` / `browser_locate` / `browser_tabs` 全部返回 `agent_target_required`；Desktop 状态栏显示 `Agent target: (session confirmed)` 但页面仍未授权。
- **机制**：`AgentTargetSessionAuthority.Authorize` 在无目标会话时直接拒绝；目标只能由 Desktop UI 的「设为 Agent 目标」建立。
- **修复**（`636e678`）：新增 `EnsureImplicitTargetUnsafe` —— 用宿主注入的可信控制句柄把目标**隐式绑定**到它请求的页面；同 owner 换页自动跟随；owner 不同仍报 `browser_owner_mismatch`；用户显式「撤销」后置 `_implicitBindingSuspended`，隐式绑定停止。同时 `BrowserBridgeCommandDispatcher` 对无 `PageId` 的管理类命令（`page.create` / `context.*`）不再要求既有目标。
- **验证**：`PuddingBrowser.AuthorizationTests` 49/49、`PuddingDesktop.Tests`(Browser) 160/160、`Pudding.DesktopServiceTests` Browser 子集 124/124；变异取红 6 例。

### 门二：零页面时不能创建第一个页面（`browser_page_not_found`）

- **现象**：Desktop 重启后上下文 `pageCount=0`，`browser_tabs(new)` 返回 `browser_page_not_found`「browser.tabs requires an explicit page target」。
- **机制**：`DesktopService.ValidateAdmission` 用**能力级** trait（`DesktopCapabilityPolicy.RequiresPageTarget`）判断是否需要页面目标；`BrowserTabs` 的 trait 是能力内**最严动作**的并集，而 `new` 动作按 `BrowserOperationPolicy` 属 `Management` 类、不需要页面目标。`activate` / `close` 的目标由请求构造器强制，因此唯一能创建页面的动作反被「必须先有页面」挡住。
- **修复**（`06ca3e6`）：改为**动作级**判定 —— 动作不需要页面目标时跳过目标解析，并按上下文作用域取 `BrowserContextCallerTrust`；`ExecuteOnUiAsync` 的复检同步转发 `operationOverride`，否则能力级回退映射会在 UI 线程把已放行动作再拒一次。
- **验证**：新增 `TabNew_IsAdmittedWithoutAnExistingPage`；变异取红 1/1；复原后文件 SHA-256 与变异前一致。

### 门三：会话已准入后又被页级闸门二次拒绝

- **机制**：门一的隐式绑定只写 `AgentTargetSession`（会话层），**不**写 `DesktopTargetRegistry.IsAgentTarget`（注册表层）；而 `ValidateAdmission` 的页级闸门（审计 2026-10-08 结论 #2）仍要求 `pageState.IsAgentTarget` ⇒ `snapshot` / `locate` / `interact` 会在会话放行后再次被拒。
- **修复**（`2e4766a`）：把 `sessionAdmitted`（`SessionPermitMarker` 非空）提到闸门之外，页级闸门加 `!sessionAdmitted`。语义：**会话权威是浏览器自动化的单一准入来源**；旧页级闸门只在能力通道（无会话票据）路径继续生效。保留：页面存在性、context 信任级、自动化状态、页面版本检查。
- **验证**：新增 `SessionAdmitted_CallSkipsTheLegacyPageGate`；`Pudding.DesktopServiceTests` 422/422；变异取红 1/1；复原后 SHA-256 一致。

## 复现与复核方法

1. 现场判据：`browser_context(list)` 看 `pageCount`；`browser_tabs(list)` 看页面清单；`browser_tabs(new, context_id, url)` 看错误码。
2. 版本判据：部署的 `Pudding.DesktopService.dll` mtime 与 `PuddingDesktop` 进程启动时刻对比 —— **两者早于修复提交即未生效**，不要凭「重启过」推断已生效。
3. 回归：`dotnet test Source\Pudding.DesktopServiceTests\Pudding.DesktopServiceTests.csproj`。
4. 集成预检（不触碰运行中的 Desktop）：`dotnet build Source\PuddingDesktop\PuddingDesktop.csproj --artifacts-path temp\build\winui3-check`。

## 生效条件与待验矩阵

浏览器执行器在 **Desktop 进程**内，须重编并重启 Desktop：

```text
dotnet build Source\PuddingDesktop\PuddingDesktop.csproj --artifacts-path temp/build/winui3
```

重启后按序验收：`tabs new` → `navigate` → `snapshot` → `screenshot` → `locate` → `interact`。

## 重启前的静态预检（2026-10-19 00:3x）

重启之前先确认“还有没有第四道门”，避免再来一轮。结论：**预期没有**，依据如下。

1. **page grant 不在桥路径上**：`DesktopBrowserExecutorComposition.cs:85` 把 `HasSufficientPageGrant` 作为 `readOnlyPageBaselineAdmission` 注入，而它只在 `Authority.Admit` 拒绝时作为迁移期例外被调用；带 `SessionPermitMarker` 的桥调用整段跳过 `Authority.Admit`，因而也不会碰 grant。`PuddingBrowser.Authorization` 内没有 grant 概念（只有 permit）。
2. **新建页面的版本会回填**：`RecordObservedPageVersion` 对 `response.Tabs` 取 `tabs.Target` + `tabs.Page.Version`；`tab new` 的结果 `DesktopTabsResult.Page` 是新页状态，因此下一次带版本的操作不会误判 `page_version_mismatch`（该失败模式在源码注释里被点名过：“握手成功却什么也做不了”）。
3. 其余闸门（页面存在性、信任级、自动化状态、版本）在修复后仍保留，且均为 V1 允许的行为。

仍属运行期未知：WebView2 截图能力本身、站点反爬与登录态。这些只能在重启后实测。

## 边界

- 未改 `page grant`（任务绑定签发）旧路径；若重启后出现 `no page grant covers …`，那是**第四道门**，按同样方式定位。
- 三道门均为**授权模型**问题，未涉及页面读取、DOM 快照与截图实现本身。
- 上述验证均为单元/集成层；真机浏览器行为（WebView2、站点反爬、登录态）尚未在本轮验证。
