# 权限证据链：设计文档对齐现状 + 两处**有意暂缓**的判定

## 为什么这一轮先改文档

链条的前四步（地基 → 生产者 → 携带者 → 观察者）与第二阶段闸门已经落地，但**设计文档还停留在"待施工"**。
文档与代码不一致会让接手者按过期前提动手，因此先对齐；同时把两个我判定**不该做**的步骤写清理由，
避免后来者"为了阶段完整"而做无用功或引入误伤。

## 设计文档新增：施工现状表

| 阶段 | 状态 | 落点 |
|---|---|---|
| 证据类型 + 可选携带位 | ✅ | `ToolPermissionEvidence`；`ToolExecutionContext.PermissionEvidence`；`DesktopCallContext.PermissionEvidenceSummary`（**进程内**，不上线缆） |
| 生产者 | ✅ | `ToolInvocationService.EvaluatePermissionEvidence`（`allowed` / `denied` / 未配置 guard ⇒ `not-required` + `Source=no-guard-configured`） |
| 携带者 | ✅ | 工具每次调用作用域（AsyncLocal）+ 工厂带证据重载 + 七个工具 11 处调用点 |
| 观察者 | ✅ | `MissingEvidenceCalls` + 只读状态面 `missingEvidenceCalls` |
| 第二阶段闸门 | ✅ | 路由端口 `RejectWithoutEvidence<T>`：副作用类缺证据/`denied` ⇒ `Unauthorized`；只读不受影响 |
| 第三阶段全量 + 会话层闸门 | ⬜ **有意暂缓** | 理由见下 |

## 两处有意暂缓（附理由，不是遗漏）

1. **会话层闸门**（在 `DesktopSession` 上再判一遍）：能多拦的只有"进程内代码绕过组合根直接解析 broker 会话"
   这一路径 —— 而进程内代码同样可以直接调 UI 侧接缝，**闸门无法穷尽**，已超出本设计的威胁模型。
   实测代价：仓库里已有 **7 处测试直接调用会话的副作用方法**（`CapabilityChannelHostTests`、
   `TrustedCallerAuthorizerOverTheWireTests`），全部要改夹具。⇒ **收益低、噪音大，暂缓**；
   将来若出现真实调用方，按同一判定补上。
2. **第三阶段全量**（把只读能力也纳入）：只读能力不改变状态，拦住它们的价值远低于误伤风险
   （例如运维/诊断代码直接读页状态）。当前闸门已覆盖**全部六条副作用入口**。
   ⇒ **在出现明确需求前不做**。

## 运行手册同步

新增第 6 步「权限证据观测」：读 `missingEvidenceCalls`，**干净窗口应为 0**；不为 0 即说明有调用方绕过工具层
（第二阶段闸门会拒绝并计数，而 `denied` 被拒时**不**计数 —— 有证据只是不允许，不属于"缺失"）。
原退役判据顺延为 6b。

## 顺带记录：上一轮坦白的一个缺口已经闭合
