# 2026-10-08 B7 两段式验收判定：把「内部 Agent 不能验收自身生命周期」变成可执行规则

## 目标 / 背景

项目强制规定（`AGENTS.md`「验证边界（两段式验收，强制）」）：

- 运行在产品内部的 Agent 能测**已经加载**的成品，但**不能**证明刚改的代码已被当前进程加载；
- 也**不能**独立验收承载自身的 Desktop/Core 生命周期（单实例会把第二次启动转发给旧进程；退出后无法观察子进程回收）；
- 因此流程是：内部交付 `ready-for-external-deploy` → 外部控制器重启到新构建 → 产品内 smoke 交付
  `in-product-functional-complete` → **启动/重启/崩溃恢复/退出回收仍由外部控制器判定**。

这条规则此前**只写在文档里**。而它恰恰最容易被「看起来验证过了」绕过（我在本会话中就多次需要提醒自己
"真机未验证"）。本轮把它落成**可执行判定**。

## 改动

`Pudding.DesktopService/DesktopAcceptance.cs`（新增，纯判定）：

| 阶段 | 允许谁声明 | 必备证据 |
|---|---|---|
| `ready-for-external-deploy` | 内部 Agent | 构建标识 + 至少一条记录的检查 |
| `in-product-functional-complete` | 内部 Agent | 构建标识 + **确实在新启动的构建上**（`RanOnANewBuild`）+ 至少一条检查 |
| `external-lifecycle-verified` | **仅外部控制器** | 构建标识 + **确实执行了生命周期**（`ExercisesLifecycle`） |

两条**拒绝**是核心：

1. 在**可能仍在运行旧代码**的进程上声称"产品内功能完成" ⇒ 拒绝（附具体理由）；
2. 内部 Agent 声称生命周期已验证 ⇒ 拒绝（理由：单实例转发 / 退出后无法观察子进程）。
3. 没有构建标识的结论一律拒绝 —— "测的是哪一版"必须能被指出来。

## 验证

| 套件 | 结果 |
|---|---|
| `Pudding.DesktopServiceTests` | **237 / 237**（原 231 ＋ 6） |
| `Automation` · `Contracts` · `AgentTools` · `DesktopSurface.Browser` · `PuddingDesktop` · `Host` | 276/276 · 153/153 · 64/64 · 66/66 · 320/320 · 258/258 |

新增门禁：每阶段的必备证据逐一钉住；**内部 Agent 的生命周期声明被拒**；**旧构建上的功能完成声明被拒**；
缺构建标识被拒；未登记的阶段/声明者被拒；阶段线名与交付用语一致。

**取红实测**：把「必须在新构建上验证」的条件取反 ⇒
`InProductFunctionalComplete_RequiresANewBuild` **恰好变红**；复原后 237/237 复绿。

（第一次尝试用 `if (false)` 做变异 ⇒ 编译器以 **CS0162 不可达代码**报错，说明这条判定无法被"短路掉"还能编译
—— 这本身是个不错的信号。）

## 已知边界（诚实登记）

- **这是判定组件，不是执行器**：它回答"这个声明允不允许作出"，**不**去部署、重启或观察进程。
  真正的外部控制器与验收脚本（G1–G11 清单、隔离 DesktopHome/DataRoot/端口）仍未落地 —— B7 的下一半。
- **证据靠调用方如实提供**：组件无法验证 `RanOnANewBuild` 是否真的为真（那需要外部控制器的构建标识与
  进程启动事实）。它能做的是**要求**这些字段存在，并拒绝在没有它们时给出结论。
- **没有持久化验收记录**：目前没有把"谁在哪个构建上声明了什么"存下来的地方（审计留痕属于后续）。
- 真机无关（纯判定）。

## 影响与回滚

- **无对外行为变化**：新增组件尚无生产调用方（下一步是外部验收脚本/控制器调用它）。
- 回滚：删除 `DesktopAcceptance.cs` 与其测试。
