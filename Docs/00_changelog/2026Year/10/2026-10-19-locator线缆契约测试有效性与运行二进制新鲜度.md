## 二、关键发现：**原测试对真实回归变异不取红**

按“变异必须能取红”的纪律，把发送端改回历史缺陷形态：

```csharp
// 还原历史写法
Kind = locator.Kind.ToString(),   // 原修复：Kind = LocatorWireName(locator.Kind)
```

结果 **21/21 仍然全部通过** —— 变异**完全没有被捕获**。

注意这不是“用例空转”，而是更隐蔽的一类：

| 变异绿的两类含义 | 判据 |
|---|---|
| ① 用例空转 | 断言与变异点无因果关系 |
| ② **变异点不在被测路径上** | 测试调的是辅助方法（`LocatorWireName`），而真实调用点（`ToDescriptor`）另有一行可独立退化 |

原测试直接调用 `RemoteBrowserPage.LocatorWireName(kind)`，因此它只能防住“`LocatorWireName` 实现写错”，
**防不住“有人把 `ToDescriptor` 改回 `locator.Kind.ToString()`”** —— 而这恰恰是历史上真实发生过的缺陷形态。

## 三、修法：让断言锚定**真实发送路径**

`ToDescriptor` 就是写进线上 `BrowserLocatorDescriptor.Kind` 的那一处，把它开放给测试：

```csharp
// Source/PuddingHost/BrowserBridge/RemoteBrowserPage.cs
internal static BrowserLocatorDescriptor ToDescriptor(Locator locator) => new()
{
    Kind = LocatorWireName(locator.Kind),
    …
};
```

> `PuddingHost` 已有 `[assembly: InternalsVisibleTo("PuddingHost.Tests")]`（`Properties/AssemblyInfo.cs:3`），
> 因此无需新增可见性入口，也没有放宽任何对外契约。

新增用例（10 个 `Theory`，覆盖全部 `LocatorKind`）：

```csharp
[Theory]
[MemberData(nameof(AllLocatorKinds))]
public void DescriptorSentOverTheWireCarriesTheWireName(LocatorKind kind)
{
    var descriptor = RemoteBrowserPage.ToDescriptor(new Locator { Kind = kind, Value = "probe" });

    Assert.True(DesktopLocatorKindWire.TryParse(descriptor.Kind, out var parsed),
        $"receiver rejects wire name '{descriptor.Kind}' for {kind}");
    Assert.Equal(kind.ToString(), parsed.ToString());
}
```

断言使用**接收端真实解析器** `DesktopLocatorKindWire.TryParse`，而不是另写一份期望表 —— 否则契约漂移时双向都错。

## 五、运行二进制新鲜度：**不能按 `Source/.../bin` 判断**

本轮核实「修复是否已在 Core 中生效」时，两次踩到同名 DLL 的陷阱：

| 路径 | 是什么 |
|---|---|
| `Source/PuddingAgent/bin/Debug/net10.0/PuddingHost.dll` | **不是**运行目录（易误判） |
| `temp/build/winui3/bin/PuddingDesktop/Debug/net10.0-windows10.0.19041.0/win-x64/core/` | **实际运行目录**（`Get-Process PuddingAgent).Path` 的父目录） |

实测：

```text
PuddingAgent  Id=29300  StartTime=2026/10/19 11:05:59
core/PuddingHost.dll   LastWriteTime=2026/10/19 09:50:10
修复提交 d38b6cd        committed=2026/10/19 10:25:23
```

⇒ **进程虽然“刚重启过”，加载的 DLL 却比修复旧 35 分钟**。
判据必须两段一起看：**进程 `StartTime`** 与 **进程实际 Path 所在目录里该 DLL 的 `LastWriteTime`**；
只看“重启过”或只看 `Source/.../bin` 都会得出错误结论。

## 六、推送通道阻塞（环境型，带时点）

| 探测 | 结果 |
|---|---|
| `git push origin master`（11:14 / 11:15 / 11:46 三次） | `Connection closed by 198.18.0.27 port 22` → `fatal: Could not read from remote repository` |
| `Test-NetConnection 198.18.0.27 -Port 22` | `TcpTestSucceeded : True` |

三层证据合起来才可定性：**TCP 可建连、SSH 协议层被中断** ⇒ 不是凭据问题（凭据失败会报 `Permission denied (publickey)`），
而是本机到远端的传输通道（代理/隧道）在 SSH banner 阶段掉线。

## 方法与教训

1. **测试要锚定“会退化的那一行”**：改完修复要问“如果把这行改回去，我的测试会红吗”，并真的去变异一次。
2. **变异绿必须先分类**：①用例空转 ②变异点不在被测路径。两者修法不同：①补断言 ②把测试挪到真实路径（必要时开放可见性，但只对测试程序集）。
3. **可见性放开不是放宽契约**：`internal` + 既有 `InternalsVisibleTo` 不改变任何对外行为。
4. **“重启过” ≠ “修复生效”**：取进程实际 Path 的父目录，比对 DLL 的 `LastWriteTime` 与修复提交时间。
5. **网络失败要看协议层**：TCP True + banner 超时 + connection closed 是通道问题；`Permission denied` 才是凭据问题。
