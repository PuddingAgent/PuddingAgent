# 2026-10-12 修复：LIVE 预检绑定实例身份与字节校验

> 依据：用户转达的复核结论第 4 项（P1）。位置：`verify-external-deploy-identity.ps1` 的 LIVE 阶段。

## 1. 缺陷

- LIVE 阶段**选第一个同名进程**再读其目录里的 DLL：既没绑定 `BaseUri` 对应的进程，也没证明
  **实际加载**的程序集身份；且只校验入口 DLL，覆盖不到本次主要修改的 Runtime/Core。
- HTTP 部分只比首页哈希；JS 只解析身份字段，**不校验脚本字节** ⇒ "身份字段相同但脚本不同"能蒙混过关。

## 2. 修复

### 2.1 产品侧：只读匿名身份端点

新增 `GET /api/system/build-identity`（`BuildIdentityApiController`，`[AllowAnonymous]`，只读）：

```json
{ "processId": 1234, "processStartedAtUtc": "…", "entryFileName": "PuddingAgent.exe",
  "baseDirectory": "…", "contentRoot": "…", "runtimeVersion": "10.0.0",
  "assemblies": [ { "name": "PuddingRuntime", "loaded": true,
                    "mvid": "…", "informationalVersion": "…", "fileSha256": "…", "fileName": "PuddingRuntime.dll" } ] }
```

- 覆盖**入口 + 本次修复触及的关键链**：`PuddingAgent`/`PuddingCore`/`PuddingRuntime`/`PuddingMemoryEngine`/`PuddingPlatform`。
- 未加载的程序集显式 `loaded=false`（脚本据此判 unknown，绝不猜）。
- **不返回**密钥、配置值、令牌、用户数据或完整路径（程序集只回文件名）——由测试断言。

### 2.2 脚本侧：绑定 + 逐项比对

- 按端点返回的 `processId` 取进程并核对**启动标识**（±2 秒）⇒ 完成「端口 → 进程」绑定；
  取不到即 unknown。
- 逐程序集比对：在构件根里**唯一**命中同名 DLL，比较在线 `fileSha256` 与构件文件哈希，
  并强制要求报告 MVID；多命中（多实例/多配置）⇒ 显式拒绝，不按时间猜。
- 逐个拉取 `index.html` 引用的 **JS/CSS**，比较字节 SHA256 与构件同名文件 ⇒ 拦截
  「身份字段相同但脚本不同」；一个都没校验到 ⇒ unknown。
- 附带加固：git 事实读取改为容错 —— `-RepoRoot` 不是 git 工作树时**显式记问题**
  （无法 pin 提交 ⇒ artifact 阶段不得通过），而不是抛异常中断。

## 3. 验证（本机真实执行）

**端点单测**（`PuddingPlatformTests`）3 条：报告 PID == `Environment.ProcessId` 与可解析启动标识；
关键程序集齐全且给出 MVID 与 64 位 SHA256；负载不含 `apikey/token/secret/...` 且程序集只回文件名。
结果 **3/3**；`PuddingPlatformTests` 全量 **1438 通过 / 0 失败**（上批 1435 + 新增 3）。

**脚本端到端桩验证**（合成 repo + 合成构件 + 真实进程 PID + python HTTP 桩，本机执行）：

| 用例 | 结果 |
|---|---|
| 一致（身份端点哈希与构件相同、JS/CSS 字节相同） | **LIVE 阶段：PASSED**（artifact 阶段因合成根非 git 工作树而拒绝，信息明确） |
| 旧进程 + 新磁盘文件（端点报告的程序集哈希 ≠ 构件） | 拒绝：`在线 PuddingRuntime 的文件 SHA256 ≠ 构件根（旧进程仍在运行）` |
| 身份字段相同但脚本不同（只改服务端 `umi.js` 字节） | 拒绝：`在线 JS/CSS 与构件字节不一致（身份字段可能相同）：umi.js` |
| 多实例/多配置（构件根出现第二个同名 DLL） | 拒绝：`构件根里有 2 个 PuddingRuntime.dll（多实例/多配置）：不得按时间猜测` |

**真实仓库冒烟**：`git 可判定: True`，artifact 阶段按事实拒绝（工作树脏 + dist 带 dirty + commit 不符），
LIVE 显式 `SKIPPED`（未提供 `-BaseUri`）—— 与预期一致，无崩溃。

**未取得**：完整 `PREFLIGHT OK`（需要**干净检出**的构件 + 真实运行实例；本工作区长期混有他方 WIP，
且本机没有运行中的 Core）。这一点如实保留，不做替代性声明。

## 追加（2026-10-12，端点真实宿主 E2E）

新增 `Source/PuddingWebApiTests/BuildIdentityApiE2ETests.cs`：用既有 `CustomWebApplicationFactory`
**进程内启动完整 ASP.NET Core 宿主**（不触碰任何产品进程、不占用真实端口、隔离 DataRoot），
再以真实 HTTP 管线请求 `/api/system/build-identity`。断言：

- 端点**匿名可达**（200）——否则部署预检的 live 阶段永远 unknown；
- `processId` == 宿主进程 PID；`processStartedAtUtc` 可解析（供预检绑定端口 → 进程）；
- 关键程序集 `PuddingRuntime` 的 `loaded=true` 且给出 **MVID 与 64 位文件 SHA256**；
- 载荷不含 `keyVault`/`apiKey`/`controlToken` 等敏感字段。

结果：`--filter BuildIdentityApiE2ETests` **1/1 通过**（13 秒）。

**边界说明**：本用例验证的是**端点机制**（路由 + 匿名可达 + 载荷形状）；
「脚本按真实端口绑定进程」与「在线字节与构件逐项比对」已通过桩环境验证（四例），
而**真实部署实例上的 LIVE PASSED** 仍须由外部控制器在部署后执行 —— 本次未部署、未重启。

**权衡记录（为什么不自己起一个 Core 来跑完整 LIVE）**：本机没有运行中的 Core；自动起一个隔离实例虽可行，
但它验证的是"机制"，不是"外部控制器部署到运行实例"这一事实——两段式验收要求后者由进程外控制器判定；
且启动/生命周期结论按规定不归本 Agent。故本轮止于端点真实宿主 E2E + 桩环境 LIVE 机制验证。
