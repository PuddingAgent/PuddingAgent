# Chat发送按钮与输入法草稿修复

- 定位：输入法组合期间叶子有可见文字且 hasText=true，父级 inputValue 仍为空或滞后；旧 `onSend()` 在 ChatPage 读取父级值并静默返回。当前 6.9.8 的受控浏览器复现中，普通输入点击触发请求，组合态点击为 0 请求。探针拦截所有 API POST，没有给 Agent 发送测试消息。该机制吻合用户症状，但没有抓取用户原始操作的原生 IME 事件，不能断言每次无响应均是同一原因。
- 修改：`IntentConsole.tsx` 从叶子读取草稿，清空叶子后调用 `onSend(draft)`；`ChatLayout.tsx`、`ChatMain.tsx` 透传合同，`index.tsx` 使用显式草稿。保留运行中服务端排队和失败草稿恢复。`ComposerTextInput.tsx` 更新合同注释；前端修订号 `6.9.8→6.9.9`。
- 回归：新增空闲/运行中两例，父级为空且输入法仍组合时，按钮提交完整文字一次、清空输入，迟到的 compositionEnd 不恢复旧内容。既有语音测试仍指向已移除的会话面板，更新为当前内联录音→转写→发送路径，并替身实际使用的 adapter 工厂；未修改语音产品实现。
- 验证：前端关联 5 套件共 71 项通过（4 套件 51 项及最后单独复核 IntentConsole 20 项）；TypeScript `tsc --noEmit` 通过。Jest 仍有既有 open handles 提示。更新 Admin 代码地图和平台会话诊断手册。
- 未完成：新前端构建、部署和部署后浏览器回归待执行，不能将单元测试等同实机验收。部署将另行追加记录；本次无需修改 Core/Desktop 合同。

`73b55ba / 6.9.9` 前端构建及 bundle budget 门禁通过。Desktop/Core 已在 10:58 退出；离线备份旧静态目录后，将新前端部署至配置指向的 Core `wwwroot/admin`，159 个文件哈希一致，HTTP index SHA256 与构建一致。随后启动 Desktop，实际聊天页徽标为 `v6.9.9+dirty · 73b55ba · 2026-10-19 11:04`；Bridge Hello protocol=3，Core ready=4326ms（单次温启动观测，不代表本补丁优化了启动性能）。

部署后受控浏览器验证普通输入、输入法组合态各发出一次 canonical turn 请求，正文与输入完全相同；模拟 HTTP 400 后原文正确恢复，JS 异常 0。所有写请求均被拦截，没有提交给默认助手，也没有触发截图中的京东任务。完整摘要见[部署证据](../../../14_reports/Chat发送按钮修复部署验证-2026-10-19.json)。

## 更正与后续诊断（2026-10-19）

上述受控浏览器验证覆盖了输入法草稿缺陷，但没有覆盖实际 Desktop 已有 Agent 投影快照的发送路径，因此不能代表实机发送已恢复。用户再次反馈后，在真实 Desktop 断点确认另一个阻塞：投影适配器只返回游标数值、未发布 ready 状态，发送在 POST 前被 `cursor-not-ready` 拒绝。补充修复与验证见[投影游标准备与发送反馈修复](2026-10-19-Chat投影游标准备与发送反馈修复.md)。
