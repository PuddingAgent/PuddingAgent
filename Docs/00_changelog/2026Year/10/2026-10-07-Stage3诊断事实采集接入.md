# 2026-10-07 · Stage 3 接入：诊断事实采集

## 背景 / 动机

前两刀交付了叶子组件的设计、契约与纯计算（因果分类、有界证据、事故投影、复制载荷），但**产品里还看不到它**。
2026-10-07 事故暴露的核心缺口是：故障时**只有异常字符串**，没有「请求体多大、发了几次、卡在哪一步」。
本刀把这三类事实真正采集进活动元数据，并按 `组件化交付规程` S5 接入宿主。

新增门禁 `ChatStreamAsync_WhenRequestUploadReset_RecordsStableCauseAndRequestBytes`：注入 2026-10-07 的真实异常链
（`HttpRequestException("Error while copying content to a stream.") ← IOException ← SocketException(10054)`）后断言
`chat_stream` 失败活动携带 `cause_code=transport.request_upload_reset`、`cause_phase=request_upload`、
`cause_retryable=true`、`attempt=2`、`socket_error_code=10054`、`request_bytes>0`、`dispatch_count≥1`，
且 `ErrorCode` **已是稳定因果码而不是 CLR 类型名**；重试活动（`attempt=1`）同样带因果码。

## 结构变更门禁（`组件化交付规程` §4.2）：第一次是红的

全解决方案构建第一次失败，**原因是本刀引入的真破坏**：

```
Source/PuddingHost/Extensions/PuddingServiceCollectionExtensions.Platform.cs(341): error CS0104:
"DiagnosticRedactor" 在 PuddingCode.Diagnostics.DiagnosticRedactor 与 PuddingPlatform.Services.Diagnostics.DiagnosticRedactor 之间不明确
```

根因：叶子组件的命名空间 `PuddingCode.Diagnostics` **已被 PuddingCore 的 DTO 占用**，而该文件同时 import 两个命名空间；
新增 `PuddingCore → PuddingDiagnostics` 后二义性显现。处置：改名 `DiagnosticEvidenceRedactor`（语义也更准）。
⇒ 只跑"我引用的那几个工程"会漏掉「仅靠 `using` 间接看到该类型」的消费方，这正是 §4.2 判据的价值。

改名后复跑：**唯一剩余失败是 `Source/Pudding.Rpc.IpcProbe/ProbeExecutor.cs` 3 处 `CS8604`**（该工程 `TreatWarningsAsErrors=true`），
已核实与本刀无关（只引用 Contracts/CapabilityBroker/Protocol/DesktopConnection/DesktopService、工作树未修改、最后改动为无关提交 `d27fe3d`）
⇒ **全解决方案构建在本刀前即为红**，修复它属另一件事。

## 诚实标注：两次自己的失误

1. **工具失误（已恢复）**：我用 PowerShell 批量正则改写源文件做重命名，`Get-Content`/`Set-Content` 编码不一致，
   把 5 个文件的 UTF-8 中文写成乱码。已 `git checkout` 从 HEAD 逐文件恢复并核对中文与结构，改用 UTF-8 安全的编辑工具重做。
   ⇒ 源码批量改写不要走 shell 文本替换。
2. **设计缺口（本刀内补上）**：第一版分类只认「堆栈帧指纹」，而合成的异常链没有框架帧，于是集成测试只能测出
   `transport.unclassified_failure`。补上「网关阶段记账」这条判据后，真实链路上的定性才既准确又稳（异常被重建也不丢）。
