# 2026-10-08 上下文指示器区分容量压力与服务故障、明确两个分母（前端 6.4.1）

> 范围：`Source/PuddingPlatformAdmin/`（`src/pages/chat/components/serviceStatus.ts`、`src/pages/chat/components/inputUnavailable.ts` 新增、`src/pages/chat/components/ContextUsageRing.tsx`、`src/pages/chat/components/ComposerStatusDetails.tsx` 及对应 `.test` 文件、`package.json` 版本 6.4.0 → **6.4.1**）
> 依据：[修复方案](../../../12_features/首Token等待与上下文指示器修复方案-2026-10-07.md) §1 第 4/5 行、[ADR-095](../../../07_architecture/109ADR-095会话上下文维护与首增量延迟治理ADR.md) D7、[诊断报告](../../../14_reports/首Token等待与上下文指示器诊断-2026-10-07.md) §4.1/§4.2/§4.4

## 问题（改动前）

诊断报告截图样本：总窗口 `463.8K / 1000.0K = 46.4%`，有效输入窗口 `606.8K`、剩余约 `143.0K` ⇒ 有效输入压力 `76.4%`。改动前：

1. `serviceStatus.ts` 的 `mapContextHealthState` 把 `Unhealthy`/`Critical`/`Blocking` 一律映射为 `'error'`，`ComposerStatusDetails` 的 `SERVICE_LABEL.error` 是「异常」，面板把它显示成**上下文服务异常**。76.4% 只是容量压力，它没有证明网络/API/上下文服务出错——用户会去排查一个并没有坏的服务（诊断 §4.2）。
2. 圆环只给一个百分比，分母是**模型总窗口**；而容量告警用的分母是**有效输入窗口**。两个数字（46.4% / 76.4%）在界面上不可区分其分母，读数无法互相解释（诊断 §4.1）。
3. `ComposerStatusDetails` 用 `windowLimit − effectiveLimit` 直接推导「预留输出」，`ContextUsageRing` 用同一个差值推导不可用区。该差值还可能来自 **Provider 输入上限**或**安全余量**，把它叫做「预留输出」是猜测（诊断 §4.4；截图 `393.2K`、以及健康口径不含默认 1,024 缓冲导致的有效输入约 `606,784` 与日志硬上限 `605,760` 的差值都属这一类）。

## 改动

### 1. 容量压力 ≠ 服务故障

`ContextServiceStatus` 新增 `'capacity'` 取值（`'error'` 保留在联合类型里——索引/模型服务等信号仍有真实失败证据）。`mapContextHealthState`：`Unhealthy`/`Critical`/`Blocking` → `'capacity'`，`Healthy` → `'available'`，`Warning` → `'warning'`，缺失/未知 → `'unknown'`。上下文健康度这条链路现在**不可能**返回 `'error'`；采集失败（含 409 `context_window_unresolved`）保持 `'unknown'`——「没采到」既不证明故障也不证明有压力。`ComposerStatusDetails` 的 `SERVICE_COLOR.capacity` 用「需注意」橙色（**不用故障红**）、`SERVICE_LABEL.capacity = '建议整理上下文'`。

### 2. 两个分母各自标注

`ContextUsageRing` 标题改为「模型窗口占用 `used/contextWindowTokens`」，并新增独立一行「有效输入压力 ≈y%（分母 `effectiveWindowTokens`）」，`y = used / effectiveWindow`。分母缺失/非正 ⇒ 整行不渲染，**不拿总窗口顶替**。圆环弧长与色阶口径未变（仍是总窗口占用率），悬浮 aria-label 同时带两个分母。两处新增 `data-testid`（`context-usage-window-occupancy` / `context-usage-effective-pressure`）供断言。

### 3. 「不可用于输入」按来源命名，来源未知就写未知

新增叶子模块 `inputUnavailable.ts`：`InputUnavailableReason`（`reserved_output` / `provider_input_limit` / `safety_margin`）+ `describeInputUnavailableReason()`，未标注来源时返回「不可用于输入（来源未知）」。`ComposerStatusDetails` 与 `ContextUsageRing` 都改用它；`ContextUsageRing` 新增可选 `tUnavailableReason`，`serviceStatus.ts` 重新导出该模块以保持既有引用不破。**只有来源确实是输出预算时才叫「预留输出」。**

### 4. 顺带修掉本次引入的模块依赖回归（重要）

第一版实现让 `ContextUsageRing.tsx` 直接从 `serviceStatus.ts` 引用该文案函数。`serviceStatus.ts` 为了推导服务信号会 import `@/pages/index-status/health` → `@/pages/index-status/api`，于是把整条 umi 应用链（`src/app.tsx` → `@ant-design/v5-patch-for-react-19`）拉进圆环的模块图，`ContextUsageRing.test.tsx` 整套在 import 阶段就失败。修法是把纯文案映射移到**叶子模块** `inputUnavailable.ts`，圆环只依赖叶子模块（见 `Source/PuddingPlatformAdmin/code_map.md` 对应条目）。基线对照证据见下节。

> 文案注记：`code_map.md` 有一条纪律「`status=thinking` 不得再用『整理上下文』」，理由是它与压缩共用同一批词。本次容量压力行按方案 §1 使用「建议整理上下文」，它是**容量信号**不是运行态文案；若复核认为仍会混淆，只需改 `SERVICE_LABEL.capacity` 一处。
