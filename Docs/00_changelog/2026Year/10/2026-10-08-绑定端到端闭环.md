# 2026-10-08 控制面端到端闭环

## 交付

| 件 | 内容 |
|---|---|
| `DesktopCapabilitySender` | 首参由 `DesktopCapabilityDescriptor` 改为 **`DesktopCapability`（枚举）** —— 与 `DesktopSession.SendAsync` 同形；生产者内部传 `_capability.Capability` |
| `BindingIssuanceEndToEndTests`（新） | 夹具**声明**控制面能力（`HarnessOptions.Declared/Grantable |= BrowserBindingApply|Revoke`）后跑真实会话往返 |
| 方法组适配 | `session.SendAsync` 的末参 `CancellationToken` 是**可选**的 ⇒ 方法组不能直接转委托，改用 lambda 显式适配（CS1503） |

## 验证（TRX 判定 100/100）

| 用例 | 判据 |
|---|---|
| 接受 | 命令上线（`browser.binding.apply`、`Caller.TaskId=run-1`）⇒ 生产者 `Issued=true`、`GrantId=grant-1`、`Reason=null` |
| 拒绝 | 生产者 `Issued=false`、无 grant、原因如实带出（`not the page the user currently selected`） |

⇒ **控制面在线缆、编解码、生产者三处全部闭环**；round-250 的阻断缺口彻底消除。

## 失败面一路缩小的记录（可复用）

1. round-250：ack **不在 proto 结果 oneof**（上不了线）；
2. rounds 251–252：补契约 + 三条冻结守卫 + **两侧编解码**；
3. round-253：生产者**对接签名不匹配**（描述符 vs 枚举）+ 方法组可选参数；
4. round-254：夹具**未声明**控制面能力 ⇒ 命令被挡在发送前（**这一条也纠正了 round-213 我改错方向的判断**：那份"握手名单"是夹具声明的镜像，该改的是声明而非断言）。

## 诚实边界

- **`epoch` 仍按 0 往返**（语义未定，两侧有注释）；
- **真实触发点仍未接**：谁发起这次绑定申请（目标事实来自 Bridge `IsAgentTarget` + 当前任务身份）尚未接；
- **生产开闸门**（给 `DesktopService` 注入世代）必须在其后（round-197 顺序）；**未跑全量链**；**未真机验证**。
