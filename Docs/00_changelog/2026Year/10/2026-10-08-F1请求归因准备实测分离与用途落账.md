# 2026-10-08 F1 请求归因：准备/实测分离、按用途落账并修掉压缩归因取错快照

> 范围：`Source/PuddingCore/Platform/LlmOptions.cs`、`Source/PuddingRuntime/Services/LlmRequestBudgetGuard.cs`、`Source/PuddingRuntime/Services/WarmPrefixCompaction.cs`、`Source/PuddingRuntime/Services/AgentExecutionService.cs`、`Source/PuddingRuntime/Services/AgentExecution/AgentExecutionLlmInvoker.cs`、`Source/PuddingCoreTests/`、`Source/PuddingRuntimeTests/`
> 依据：[ADR-095](../../../07_architecture/109ADR-095会话上下文维护与首增量延迟治理ADR.md) D6、[修复方案](../../../12_features/首Token等待与上下文指示器修复方案-2026-10-07.md) §2.1/§2.2/§6.3
> 前置：[分类回放](2026-10-08-软硬分类回放与393216容量来源核对.md) §5.1 记录的归因缺陷

## 1. 问题（改动前）

1. **准备估算与实测共用一个可变快照**。`ContextUsageSnapshotStore` 只有「每个 session 最新一条快照」：
   `CaptureLlmRequest` 写入估算，`RecordProviderUsage` 又用 Provider 报数覆盖同一条。于是界面/Runtime
   在「估算」和「实测」之间交替跳变，来源变化被误读成占用跳变（诊断 §4.1 的 463.8K ↔ 164.7K）。
2. **辅助/摘要调用与主请求共用同一落账路径**。`AgentExecutionLlmInvoker` 对任何 `purpose` 都调用
   `RecordProviderUsage(sessionId, usage)`：摘要调用的 Provider 报数会改写主请求的准备快照，
   并且用「摘要的 provider prompt ÷ 当前快照的 raw」去更新**出站硬门禁**使用的保守校准系数。
3. **候选测量污染准备快照**（诊断 §5.1 的实证缺陷）。`PrepareSoftCompaction` 在挑选候选时会对
   「移除后的保留列表」反复 `CaptureLlmRequest`，而该方法**顺带发布**。结果是软压缩跑完后
   session 快照停在**压缩后**的形状上，紧接着 `FreezeRequestContext` 冻结到的就是这个错形状：
   DB 实测该记录 `MessageTokens + ToolDefinitionTokens = 176,873`，÷1.845 = 326,330，
   与压缩后的 `EstimatedRetainedSnapshot`（326,392）吻合，而判据输入是 **583,691**；
   摘要 usage 也就拿 193,218 去比这个错误的 raw（观测比 1.0925）。

## 2. 改动

### 2.1 计量与发布分离（`ContextUsageSnapshotStore`）

- 新增 `MeasureLlmRequest(...)`：与 `CaptureLlmRequest` 同口径，但**不发布**。
- `CaptureLlmRequest(...)` = `MeasureLlmRequest` + `Set(...)`，既有调用者语义不变。
- `LlmRequestBudgetGuard.PrepareSoftCompaction` 的全部候选测量改用 `MeasureLlmRequest`：
  挑选候选不再产生任何 session 副作用。

### 2.2 准备 / 实测分成两个槽位

- 新增 `MeasuredRequestUsage`（`SessionId`/`Purpose`/`InvocationId`/`AttemptId`/`ProviderPromptTokens`/
  `ProviderCompletionTokens`/`ProviderTotalTokens`/`RawEstimatedTokens`/`RecordedAtUtc`）与两个槽位：
  `_lastMeasuredRequests`（最近一次**主请求**实测）与 `_lastAuxiliaryMeasurements`（最近一次辅助/摘要实测）。
- 新增 `TryGetLastMeasuredRequest` / `TryGetLastAuxiliaryMeasurement`。
  `Total` 与 `Prompt` 分开保存，`Total` 不命名为「实测输入」。

### 2.3 按用途落账（`LlmCallPurposes`）

`RecordProviderUsage(sessionId, usage, purpose = Agent, invocationId = null, attemptId = null)`：

| 用途 | 改写 `currentPreparedRequest` | 参与安全校准 | 写实测槽位 |
|---|---|---|---|
| `agent`（主请求，缺省） | ✅ | ✅ | `lastMeasuredRequest` |
| `compaction` / `approval` / 其它 | ❌ | ❌ | `lastAuxiliaryMeasurement` |

`AgentExecutionLlmInvoker` 把已有的 `purpose` 透传给 `RecordProviderUsage`；缺 usage 时不发布、
也不写任何实测槽位（既有「缺 usage 保持估算与置信度」语义保留）。

### 2.4 修掉压缩归因取错快照

- `LlmSoftCompactionResult` 与 `WarmPrefixCompactionPlan` 都带出**压缩前**的完整测量
  `InitialSnapshot`（`Snapshot` 仍是「移除后、未加摘要」的计划测量，明确标注**不是**提交后的值）。
- `TryWarmPrefixCompactionAsync` 在冻结归因之前显式 `Set(plan.InitialSnapshot)`，
  使压缩请求的请求级归因与该次 Provider 报数配对到同一 raw。

## 4. 未完成 / 边界

- **迟到的主请求 usage 覆盖更晚准备快照**：当前单写者流程里主请求 usage 在同一轮的 `Prepare` 之后、
  下一轮 `Prepare` 之前落账，因此该情形**目前不可达**；真正可达的是辅助/摘要 usage（已修）。
  快照上的 `InvocationId`/`AttemptId` 与 CAS 式拒绝要等 T4 引入终态后/后台维护（那时才有跨轮的
  并发作者）再落，避免现在加一个没有写入者的字段。
- **校准误差本身未查清**（方案 §7 实施调查项）：本提交只保证「辅助调用不参与校准」「同一请求配对到
  自己的 raw」，**没有**变更校准算法，也没有降低安全上界。
- 请求副本裁剪的独立 canonical 事实、`lastMeasuredRequest` 的前端展示、容量 DTO 的实测/估算并排显示
  仍未实施。
- 交付状态仍为 **ready-for-external-deploy**；无真实模型调用、无部署、无浏览器证据。
