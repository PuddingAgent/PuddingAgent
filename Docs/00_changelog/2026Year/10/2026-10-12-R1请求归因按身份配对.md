# 2026-10-12 R1 修复：请求归因按 invocation/attempt 配对，usage 不再改写准备槽位

> 依据：[复核与验收判定](../14_reports/上下文治理实施复核与验收判定-2026-10-12.md) §2（R1，P1）
> 范围：Core 归因存储与契约、Runtime 预算守卫/调用层/两条执行路径/健康 DTO、Core 与 MemoryEngine 测试、
> `PuddingContextPolicy/code_map.md`（复核指出的陈旧条目）

## 1. 缺陷（复核 §2 复现）

旧实现三处叠加构成同一缺陷：

1. `RecordProviderUsage` 取 `TryGet(sessionId)` 的**当前最新**准备快照，用它的 `RawEstimatedTokens` 与
   `ModelId` 算校准；
2. 再用 Provider 报数 `Set(snapshot)` **覆盖准备槽位**；
3. `lastMeasuredRequest` 按**到达时间**写入。

复核最小探针实测：A 准备（model-A、raw=2504）→ B 准备（model-B、raw=6）→ A 的实测迟到 ⇒
A 的实测输入被 B 的 raw 除，得到 **417.33 倍**并写进 **model-B** 的校准键，同时 B 的准备快照被改成
Provider Total。后果：展示错乱、安全上界被抬高，重新制造硬压缩与裁剪等待。

## 2. 修复

### 2.1 冻结不可变准备记录（Core）

新增 `PreparedRequestRecord(SessionId, Purpose, InvocationId, AttemptId, RequestSequence, ModelId,
RawEstimatedTokens, CalibratedUpperBoundTokens, PreparedAtUtc)`：

- `PublishPreparedRequest(...)`：登记记录 + 发布准备槽位（**准备路径独占该槽位**）；
- `FreezePreparedRequest(...)`：只登记身份（用于「已发布过、只需补身份」的场景，如压缩请求）；
- `TryGetPreparedRequest(sessionId, invocationId, attemptId)`：attempt 优先、invocation 兜底；
- 会话内单调请求序号；每会话保留最近若干条（有界）。

### 2.2 按身份配对（`RecordProviderUsage`）

| 情形 | 行为 |
|---|---|
| 主请求 + 身份配对成功 | 用**该记录自己的** raw 与 model 校准（路由天然隔离）；写 `lastMeasuredRequest`（带该记录的请求序号）；**不 Set** 准备槽位 |
| 主请求 + 身份配不到 | 只进未配对账本（`TryGetUnpairedMeasurement`）：不校准、不投影、不改写准备槽位 |
| 辅助（压缩/审批） | 只写辅助槽位；其 raw 取**它自己**的冻结记录（不再借主槽位） |
| Provider 完全没报数 | 不产生实测（不得用 0 伪造） |

「最近主实测」投影按**请求序号单调**推进：迟到的旧实测不得把它拉回去。

`Total` 缺失时按 `prompt+completion` 推导 —— 该推导只进**实测槽位**，不再进准备槽位。

### 2.3 生产路径真正传身份

- `LlmRequestBudgetGuard.Prepare(...)` 新增 `purpose/invocationId/attemptId`，三处 `CaptureLlmRequest`
  （首测、裁剪循环、载荷驱逐后重测）都带同一身份；
- Streaming / Buffered：把本轮身份（`BuildLlmInvocationId(request, round, "agent")` + attempt）
  **提前**到轮次作用域，供 Prepare、主调用与流式 usage 落账共用；
- 主调用：`AgentExecutionLlmInvoker.InvokeAsync(..., invocationId, attemptId)` 转发到落账；
  流式路径的 `RecordProviderContextUsageSnapshot(...)` 同样带上身份；
- 压缩调用：发布 `plan.InitialSnapshot` 时补冻结身份（`purpose=Compaction`），调用也带同一身份。

### 2.4 健康 DTO

准备槽位不再携带 Provider 报数，因此 `ContextHealthSnapshot` 的 Provider 三项改为取**实测槽位**
（已配对）；`UsedTokens/UsageSource` 仍描述当前准备请求 —— 两个口径各自独立来源，不再随到达顺序互相覆盖。

### 3.1 新增门禁用例（`RequestAttributionIdentityTests`，8 例）

1. **`LateUsageForEarlierRequest_...`（复核探针的等价场景）**：A/B 两次准备后 A 的实测迟到 ⇒
   断言 B 的**对象与数值未被改写**、B 的校准**不被污染**、A 的校准用 A 自己的 raw、最近实测 = A 且 raw 配 A。
2. 身份未知的 usage ⇒ 只进未配对账本，不校准、不改写、不投影。
3. 最近实测按请求序号单调：先到的旧请求不能覆盖后到的新请求（迟到不得倒退）。
4. 同 attempt 重复上报幂等（不重复抬校准、不改变序号）。
5. 同 invocation 不同 attempt 各自配对（失败重试不串槽）。
6. 辅助 usage 不参与主校准、不进主投影，且其 raw 来自自己的冻结请求。
7. 缺 Provider 报数 ⇒ 不产生实测。
8. 校准按 model 路由隔离。

**诚实说明（取红证据的边界）**：这批用例的语义直接来自复核报告 §2 的最小探针（417.33 倍），
但我**没有**在本机把旧实现单独跑一遍来留下「红」的字面证据（旧实现已被同一批修改替换）；
旧行为的因果链（取 session 最新 raw + 覆盖准备槽位 + 按到达时间投影）是在改动前的源码里逐条读出来的。
如需字面取红证据，可在旧提交上单独跑这 8 例。

### 3.2 `PuddingRuntimeTests` 的 4 个失败：**环境性**，非本批引入

失败全部是终端/宿主 Shell 用例（`HostShellExecutor_Sets_Utf8_Python_Output_Environment`、
`TerminalWait_*` ×3），单独跑同样失败，报错一致：

```
python … → "Python was not found; run without arguments to install from the Microsoft Store …" exit_code 9009
Get-Command python → C:\Users\hyfree\AppData\Local\Microsoft\WindowsApps\python.exe  (Version 0.0.0.0 = Store 别名桩)
```

⇒ 这些用例依赖 PATH 上的 `python`，本机 PATH 上是 Windows Store 桩（不是解释器）。
**这是新出现的环境漂移**（本会话早前这些用例是绿的），与 R1 无因果关系；
按复核要求如实登记，不当作「相同基线」（基线是原先 0 失败）。
建议由环境侧把真实 Python 放上 PATH 后再判这些用例。
