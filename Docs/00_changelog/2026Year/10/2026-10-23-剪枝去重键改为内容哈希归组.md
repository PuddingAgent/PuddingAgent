# 2026-10-23 剪枝去重键改为「内容哈希 + 去 notice 正文」

## 背景：线上零触发，三处阈值错配

S5 接入后完整扫描 `D:\Data\logs` 当日 94 个日志文件，`[LlmRequestBudgetGuard:DeterministicPrune]` **0 条**。
逐层核对（证据：`temp/prune-eval/eval.txt`，只读探针读 `pudding_platform.db`）：

| 事实 | 实测值 | 来源 |
|---|---|---|
| 真实请求的装配规模 | `prefixMsgs` 均值 56.5 / 最高 104，`prompt` 79k–95k | `TokenUsageEvents` 近 200 条 |
| 上游 bounded 后的工具结果长度 | `inlineChars` 7076–8192，均值 **8175.6** | 日志 `[AgentExec:ToolResultContext] Spilled`，3 天 69 次 |
| 剪枝摘要阈值 | `MinToolResultChars = 8000` | `DeterministicPruneOptions` |
| 单条最多可回收 | `8192 − (1600+400+marker)` ≈ 6059 字符 ≈ **1515 tokens** | 组件语义 |
| 准入地板 | `≥2000 tokens` **且** `≥5%`（`prompt≈80k` 时 5% = 4000 tokens） | `DeterministicPruneOptions` |

⇒ 单轮最多省 1515 tokens，恒低于地板，`Changed=false`，故无日志。
**这不是接线错误**：`AgentExecutionService.Buffered.cs:743` 确实传了 `logger`，`Prepare` 也确在
`CaptureLlmRequest` 之前执行。之所以「不触发」在经济上是正确的——当前 `cacheHitRate` 0.88–0.998，
为省 1.5k token 重写 80k 前缀会让整段缓存作废。

但其中**有一处是真实缺陷**：去重策略恒为 0 命中。

## 缺陷：逐字比较被 bounded notice 污染

`ToolResultContextPolicy.BuildBoundedPreview` 生成的预览形如

```
head + "\n\n" + "[TOOL RESULT BOUNDED: ... content_sha256=sha256:<64hex>;
                     full_output_file=.pudding/.../<toolCallId>-read_file.txt; ...]" + "\n\n" + tail
```

notice 内嵌 **每次调用都不同** 的 `toolCallId` 与 spill 路径，于是「原文完全相同」的两条结果
逐字必然不同，`(ToolName, Content)` 分组永不重合 ⇒ `DeduplicatedToolResults` 恒为 0。

## 改动

`Source/PuddingContextPruning/DeterministicPayloadCompaction.cs`：

- 分组键类型 `(string ToolName, string Content)` → `(string ToolName, string Fingerprint)`，
  键由新增的 `ResolveDuplicateFingerprint(content)` 计算。
- 新增 `TryParseBoundedNotice(content)`：
  - 定位 `[TOOL RESULT BOUNDED: ` … `]`，要求其中存在 `content_sha256=sha256:` 且紧随 **连续 64 个 ASCII 十六进制字符**；
  - 解析成功 ⇒ 指纹 = `content_sha256=sha256:<小写哈希>` + `\u0001` + **去掉 notice 段后的正文**；
  - 任一条件不满足（notice 缺失、无哈希、长度不足、含非十六进制）⇒ 返回 `null`，**退回逐字比较**。
- 双条件（哈希 + 正文）而非单用哈希：即使 notice 被伪造，也需同时伪造出相同正文才会归组。
- `ToolCallId` / `ToolName` / `Role` 在替换时仍原样保留（配对不断），改写文案与替换语义未变。

不改 DSL、不改配置项、不改宿主调用点——组件内部实现修正。

## 验证

- 新增 3 个用例（`Source/PuddingContextPruningTests/DeterministicPayloadCompactionTests.cs`）：
  `Bounded_Previews_With_Different_Call_Ids_But_Same_Sha256_Are_Deduplicated`、
  `Bounded_Previews_With_Different_Sha256_Are_Never_Deduplicated`、
  `Bounded_Notice_Without_A_Valid_Sha256_Falls_Back_To_Verbatim_Comparison`。
- 绿：`dotnet test --no-build` → **失败 0 / 通过 32**（原 29 + 3）。
- 变异取红（三份原始输出）：
  1. M1 键退回 `content`（即修复前的行为）→ **失败 1 / 通过 31**，失败断言 `Assert.IsTrue(outcome.Changed)`；
  2. 复原（`SHA256=7F3DF21D…`，与备份逐字节相同）→ **失败 0 / 通过 32**；
  3. M2 把 `Sha256HexLength` 改为 `0`（哈希不再被校验）→ **失败 2 / 通过 30**，
     分别打穿「不同哈希不得合并」与「非法 notice 必须保守」；复原后再次 **失败 0 / 通过 32**。
- 端到端探针（`temp/prune-eval`）用 4000 条真实工具事件重跑：默认参数
  `before=2,936,506 → after=1,339,237`（回收 **1,597,269**，54.39%），两次运行 `outHash` 一致。
  该输入的 `dedup=0` 属**预期**：`conversation_events` 存的是未 bounded 的原始载荷，不含 notice，
  新逻辑不会被触发——去重的收益只在真实请求的 bounded 预览上体现。

## 影响面与风险

- 只改一个私有分组键 + 两个私有方法；`TryApply` 签名、返回类型、准入地板、尾部保护均未变。
- 无 API / DI / `.slnx` / 宿主改动，故不需要 S5 重接线；但**运行态要重启**才生效（当前进程仍是 12:38 的镜像）。
- 风险：若 notice 格式未来变更（哈希字段改名/长度变化）⇒ 解析失败自动退回逐字比较，即**退化为修复前行为**，不会误合并。

## 后续（未做）

- 摘要阈值与准入地板**尚未**对齐上游 bounded 上限（8000 vs 8192）。降阈值能提高命中，但会打穿 warm prefix
  缓存，需先做一轮 A/B（`cacheHit` 与总成本）再决定，本轮未动。
- `ToolName` 仍参与分组，跨工具（`file_read` vs `shell`）读同一文件不会去重；是否放开需单独论证。
