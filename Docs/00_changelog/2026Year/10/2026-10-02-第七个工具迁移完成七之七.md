# 第七个工具迁移完成：`browser_context` 走两个窄端口 ⇒ 工具迁移 7/7

## 结果

七个 Browser Agent Tools **全部**迁到能力通道的窄端口（不再依赖进程内 `IBrowserRuntime`）。
本轮完成最后一个 `browser_context`，并让它的集成夹具跟上"同形"要求。

`PuddingHost.Tests` **231/231**（含真实 WebSocket Bridge 的集成用例）、
`PuddingBrowser.AgentTools.Tests` **15/15**。

## 改动

| 文件 | 改动 |
|---|---|
| `BrowserContextTool.cs` | 四个动作走两个窄端口：`create`/`close` → `IDesktopContextCapabilitySurface`（缺口 #1 新能力）；`list`/`get` → `IDesktopBrowserCapabilitySurface.GetContextsAsync`。`create` 仍固定 `Persistent = true`；`get` 省略 id 时沿用"用第一个可用上下文"；不给 id 时命中失败 ⇒ `browser_context_not_found`；未连接 ⇒ `browser_not_connected`（与"读取失败"分开） |
| `BrowserAgentToolsTests.cs` | 替身端口同时实现第二个窄端口（create/close 委托给既有假运行时）；4 处构造点更新 |
| `BrowserBridgeServiceCollectionExtensions.cs` | 把 `TransportRoutedBrowserCapabilitySurface` 注册为**具体类型**，两个接口都指向**同一个**实例（否则用量计数分裂、退役 Bridge 的判据不准） |
| `BrowserAgentToolBridgeIntegrationTests.cs` | 夹具升级：`list` 走窄端口后，适配器为与 Desktop 侧同形会逐层解析（`context.getInfo` → `page.list` → 每页 `page.getInfo`）⇒ 应答列表改为 0 页并补两轮后续应答 |

## 语义保持

- `close` 的可见形状仍是 `{ closed = true }` + context id；`create` 仍返回上下文摘要；
- 与迁移前**唯一的差别**是 `create` 不再需要 `createIfMissing`（缺口 #1 之后创建能力由能力通道承载）；
- 未连接 Desktop 时如实报 `browser_not_connected`（迁移前会在进程内直接抛运行时错误）。

## 过程教训（本轮解决了上一轮的两个卡点）

1. 上一轮锚点没匹配的真因找到：字面锚点 `        var result = await invocation;` 在**同文件其他用例里也出现**
   ⇒ 计数断言失败。修法：锚点延长到**跨多行的唯一片段**（含紧随其后的 `Assert.Equal("ctx-visible",`）。
2. `CapabilityResult<T>` 是**非空值类型** ⇒ `is not { } x` 不可用；取值路径要写成
   `read is null`（未连接）/ `read.Value.IsFailure`（失败）/ `read.Value.Value`（成功）三段。
3. 写补丁前先 `Select-String -Context` 打印**原始缩进**（本轮一次通过）。
