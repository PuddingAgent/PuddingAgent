# 2026-10-19 启动失败三模式修复：DataRoot 租约重试、启动租约前移、重复启动幂等

> 用户连续两次贴出「Core 启动失败 / 自动恢复已暂停」，要求「fix 一下，然后总结出错的模式」。本文记录三种失败模式的证据、根因、修复与验证。

## 1. 出错的模式（三件事叠在同一个 60 秒窗口里）

| # | 模式 | 触发条件 | 证据 | 旧行为 |
|---|---|---|---|---|
| **A** | **DataRoot 租约冲突 → 新 Core 未处理异常崩溃** | Desktop 重启 / 进程内 `bootstrap_reboot(desktop-build)` 在旧 Core 尚未退出时就拉起新 Core；或重复 Start 拉起第二个 Core | Windows 事件日志 `.NET Runtime` 1026 + `Application Error` 1000（CLR20r3）：`System.IO.IOException: The process cannot access the file 'D:\Data\.pudding-host.lock' because it is being used by another process.`；15:44:36、15:45:45、17:48:51、17:48:59、17:50:11 多次 | `PuddingDataRootLease` 构造函数立即抛出 `IOException` 且无人捕获 ⇒ Core 进程直接 CLR 崩溃（无清晰错误、无退出码语义） |
| **B** | **冷启动超过 60s 启动看门狗 → 被误杀** | 全量重编后首次启动（250+ 产物文件被重写，本机 Defender 首次扫描/首次加载极慢） | 实测 `StartupPhase`：`data-root-bootstrapped` 24–44s、`services-registered` 单阶段 **65s**、进程→Ready **118.9s / 145.8s**；而 `desktop.core.startupTimeoutSeconds=60` | Core 的 `PUDDING_DESKTOP_STARTING` 租约循环在 `Build()` **之后**才启动，慢启动阶段没有任何续期 ⇒ Desktop 判定「60s 内未 Ready 也未续租」并杀掉 Core，重试同样慢，3 次即熔断 |
| **C** | **状态机与真实进程失配 → 失败面板卡死，重试反而再拉一个 Core** | 自动恢复 / 重建流程 / 用户点「重试」的 Start 相互重叠 | Desktop 诊断：`coreState=Failed` 但 Core 实际健康运行（`/health/ready` 200）；`lastError=Core is already running or changing state.`；随后重试又触发模式 A | supervisor 对「Ready 且存活」的重复 Start 直接抛 `already running` ⇒ orchestrator 把状态标成 `Failed`；接着重试再起第二个 Core 抢 `.pudding-host.lock`，放大成 A |

**为什么最近反复出现**：开发期大量通过进程内 `bootstrap_reboot`（用户对产品内 Agent 说「重启」）触发「停 Core → 全量编译 → 部署 → 重启」。每次全量重编都会重写产物（B 冷启动变慢 → 超时被杀 → 自动恢复重试），而重试/重建与旧 Core 退出重叠（A 抢锁崩溃），失败状态又让 UI 落进 C 的失配死循环。

## 2. 修复

| 文件 | 改动 |
|---|---|
| `Source/PuddingHost/Hosting/PuddingDataRootLease.cs` | 租约获取改为**有界重试**（默认 30s、每 200ms 一次；新增 `(dataRoot, acquireTimeout)` 重载与 `LockFileName`/`DefaultAcquireTimeout`/`RetryInterval` 常量）。超时抛出带处置说明的 `IOException`（含锁路径与等待秒数），不再让瞬时占用变成崩溃。适配重启窗口内旧 Core 的 15s 优雅退出。 |
| `Source/PuddingAgent/Program.cs` | ① DesktopChild 的启动租约循环**提前到进程一开始**（args 解析后、CreateBuilder 之前），全量重编后的慢启动全程有续期，60s 看门狗不再误杀；② DataRoot 租约获取包 try/catch：失败时打印 `[Startup] 无法取得 DataRoot 独占租约…` 并 **return 2**（明确退出码，不再抛未处理异常/Crash 报告）。 |
| `Source/PuddingDesktop.WpfArchive/Core/CoreProcessSupervisor.cs` | ① 重复 Start 幂等：状态 `Ready` 且会话/进程存活时**复用现有会话**（新增可测的 `ShouldReuseRunningCore`）；② 启动前若发现状态机之外的**存活旧 Core**，先 `TerminateAndCleanupAsync` 再起新进程，杜绝「旧 Core 持锁 + 新 Core 抢锁」；③ 错误信息从 `already running or changing state` 细化为 starting/stopping。 |
| `Source/PuddingDesktop.WpfArchive/Runtime/DesktopRuntimeOrchestrator.cs` | `StartUnderLockAsync` 的失败分支先核对 supervisor：若实际已 `Ready` 且会话存活，发布 `Ready`（清空 LastError），不再把健康实例标成 `Failed`。 |

测试：`Tests/PuddingHost.Tests/Hosting/PuddingDataRootLeaseTests.cs`（竞争失败信息、释放后重试成功、超时说明）；`Tests/PuddingDesktop.Tests/.../CoreProcessSupervisorTests.cs`（`ShouldReuseRunningCore` 6 组）；`.../DesktopRuntimeOrchestratorTests.cs`（重复 Start 竞争时采纳 Ready）。

## 3. 验证

**单元测试**（过滤集，全部 exit 0）

- `PuddingDataRootLeaseTests`：**3/3 通过**（含 `AcquireWaitsForReleasingInstance`：租约被占用时等待 500ms 后旧实例释放、新实例成功获得）。
- `CoreProcessSupervisorTests` + `DesktopRuntimeOrchestratorTests`：**29/29 通过**（含 `StartAsync_WhenDuplicateStartRacesButCoreIsReady_AdoptsReadyInsteadOfFailing`）。

**集成验证（真实进程）**

1. **模式 A**：产品 Core 持锁时，用新构建再起第二个 Console Core → 它等待 30s 后向 stderr 输出
   `[Startup] 无法取得 DataRoot 独占租约，Core 不会启动：DataRoot 已被另一个 Pudding Core 实例占用：D:\Data\.pudding-host.lock（等待 30 秒后…）`，
   进程正常退出；**期间/之后 Windows 事件日志无任何 CLR20r3 崩溃**。
2. **模式 B**：清空旧实例后启动新 Desktop（冷启动，Core 于 18:01:42 起）——
   `PUDDING_DESKTOP_STARTING` 从 **sequence 1（elapsed=0ms）** 开始每 5s 续期，共 27 次；`server-started total=145840ms`、Ready 于 18:04:23；Desktop 全程保持 `CoreStarting` → `WorkbenchReady/Ready`，**`restartAttemptsInWindow=0`、`lastError=null`、0 崩溃**。修复前同样的 146s 冷启动必然在 60s 被杀。
3. **模式 C**：Core 已 Ready 时 `POST /desktop/bootstrap/core/start`（模拟重复/重叠启动）→ `success=true`，PID 仍为 **12224**（未新起进程），状态 `Ready`、`lastError` 为空。
4. **在线身份**：`/api/system/build-identity` 的 5 个关键程序集 `fileSha256` 与新产物逐一相等；`PuddingHost.dll` 含租约重试文案、`PuddingDesktop.dll` 含 `reusing the existing session` / `Terminating stale Core process` 文案（编译产物证据）。

- 未对进程内 `bootstrap_reboot(desktop-build)` 做端到端实测（它现在受益于 A+B+C：新 Core 等待旧实例释放、冷启动有续期、重复启动幂等）；建议下次开发期触发重启时观察一次。
