# 2026-10-02 独立复核发现的处置（D4）

## 复核方式

用一个**新鲜上下文**的只读对抗性 subagent 审 D 系列新增代码，给它 8 条必须攻击的不变量，要求给出
file:line 级反例与分级。结论：**无 BLOCKER**（原子性、payload 不写库、不顶替读不到的值等都不变量成立），
但有 **4 条 MAJOR**（都属顺序/调度/活性）与 4 条 MINOR。下面逐条处置。

## 处置（全部落在 `CodeSourceMaintenanceCoordinator`）

1. **MAJOR-1 已修**：被检测器判 Deferred 的路径此前既不入索引、也不入重试表，且不阻塞水位 ——
   唯一的下一触发器只剩「再来一次提示」或 15 分钟周期扫描（真·静默丢失窗口）。
   现在：`RetryLater` 的计划项一律计入 `UnresolvedPathCount`（水位停住），
   且**首次**出现时记入持久待办（已在待办里的不重复记 —— 否则每次 `RecordFailure` 都会把下次尝试
   时刻往后推，永不到期）。
2. **MAJOR-2 已修**：清理退避此前只在「提取成功 / 确认删除」两条分支；一个从此走
   `RebindOnly` / `NotApplicable` / 指纹一致复用 的路径会永远挂着待重试 ⇒ 永久冻结水位。
   现在**本轮确实处理过**的路径一律清退避（提取、删除、复用、只重绑、无消费者认领）。
   复核提到的「水位冻结导致每次校准都全树枚举」是**设计如此**：周期性校准本来就必须完整枚举
   （提示驱动的轮次不产生删除，丢失的删除只能靠它兜住）；水位只影响诊断与 racy 窗口判定，
   冻结只会让核验更保守，不会漏变更。
3. **MAJOR-3 已修**：删除会连带删掉**其他文件**指向被删符号的入边（`RemoveFilesAsync` 不做依赖方计算），
   而协调器此前只把依赖方收集进返回值、从不排期。现在删除前先用
   `ICodeGraphDependencyQuery` 查出依赖方，删完把它们**记进持久待办**并报进
   `InvalidatedDependentFilePaths`（下一轮按待办重新提取，补上被删掉的入边）。
4. **MAJOR-4 已修**：`RebindOnly` 分支此前用「提取之前的 manifest 快照」给**任何**重绑路径写
   「消费者已应用到版本 V」，包括反向依赖扩展出来、这一轮根本没看盘的依赖方。
   现在只刷新**变更集里真的观测过**的路径（未观测的不写 manifest，留给下一轮看盘）。
5. **MINOR-2 已修**：`IsUnchangedSinceLastCommit` 里对可空 `Fingerprint` 的取值加了守卫
   （当前写入方不会产生空指纹，但这是 fail-open 路径上的一处 NRE 风险）。
6. **MINOR-1 已闭合**：消费者输入变化的路径即便内容一致也会进 `reusedPaths`，而 `reusedPaths`
   现在会被并入重绑集合写回 manifest（刷新消费者视图）⇒ 不会再「既不提取也不重绑」。
7. **MINOR-3 记录**：`ChangedDuringScan` 在生产路径上确实无人设置（只有测试覆盖）——
   watcher 批次不携带「扫描期间又变了」这一事实。生产上的等效保护是 racy 窗口 + stat/hash 比对；
   要真正用上它，需要 watcher 在合并批次时记录二次观测，属独立小刀。
8. **MINOR-4 记录（启用前注意事项）**：忽略规则在两条链路上不对称（扫描器用工作区 `.gitignore` 栈，
   旧语言索引器只用名单级噪声）⇒ **旧链路时代被索引、但被 `.gitignore` 忽略的文件没有 manifest 记录**，
   新链路既不枚举它、也就不会清理它（孤儿行）；反之「先索引后被 gitignore」的文件会被新链路删掉。
   本笔不引入迁移代码；启用 Coordinator 前的操作步骤里应包含「先跑一次旧校准清理孤儿行（或重置索引）」。

## 顺带完成的一刀

- 提交前**复核 stat**：提取可能耗时，期间文件被改写时「索引内容」与「指纹」会错配
  （指纹来自读取时刻、索引来自提取时刻）。现在提交前再确认一次 `Length + LastWriteTimeUtc`，
   不一致就弃用本轮结果并记退避（不写索引、不写指纹）。

## 验证

- `dotnet test Source\PuddingCodeIndexTests` → **328 通过 0 失败**（本次 +4）。
- `dotnet test Source\PuddingCodeIntelligenceTests` → **132 通过 0 失败**；
  `Tests\PuddingHost.Tests --filter CodeIndexMaintenanceHostCompositionTests` → **4 通过 0 失败**。
- 新增用例逐条对应复核发现：提示命中的文件消失 ⇒ 不删、计未解决、水位停住、**记进待办**（MAJOR-1）；
  走过 `NotApplicable` 的路径**清掉**退避（MAJOR-2）；删除 Owner ⇒ 依赖方出现在
  `InvalidatedDependentFilePaths` 且进入待办（MAJOR-3）；提取期间文件被改写 ⇒ 不写索引也不写指纹（stat 复核）。

## 未完成与影响

- 默认仍是 `Legacy` ⇒ 运行中实例行为未变。
- 启用清单（更新）：① 先跑一次旧校准清理孤儿行（或重置索引，MINOR-4）；② 宿主登记
  `CodeIndexMaintenanceOptions(Coordinator)`；③ 进程外控制器重启到明确新构建；
  ④ 四场景受控复核（无变更时的周期扫描读数 / 单文件改动读数 / 删除只由完整扫描确认 /
  根不可用不误删）。
