# 2026-10-23 符号检索提速：覆盖索引两阶段，950ms → 19ms

## 现场数据（`temp/prune-eval/symbol-search-latency.txt`）

| 指标 | 值 |
|---|---|
| 索引库 | `D:\Data\databases\code-index\code_index.db` = **2.64 GB**（692,558 页 × 4 KB） |
| `CodeSymbols` 行数 | **195,533** |
| 去重后不同 `Name` | **50,854** |
| page cache | **2 MB**（SQLite 默认） |
| 现有索引 | `(WorkspaceId, Name)`、`(WorkspaceId, ProjectId, Name)`、`(WorkspaceId, ProjectId, FilePath)` |

实测旧查询（match_target=all、limit 50）：

| query | 耗时 |
|---|---|
| `LlmRequestBudgetGuard` | 934 ms |
| `ToolResultContextPolicy` | 952 ms |
| `Prepare` | 954 ms |
| `zzzz-no-such-symbol`（必然零命中） | **958 ms** |
| 首轮（冷） | **4,227 ms** |

**零命中也要 958 ms** ⇒ 与命中数量无关，就是全量扫描。

## 根因（三条叠加，`EXPLAIN QUERY PLAN` 直证）

```
SEARCH CodeSymbols USING INDEX IX_CodeSymbols_Workspace_Name (WorkspaceId=?)
USE TEMP B-TREE FOR ORDER BY
```

1. **`%关键词%` 无法用 B-tree 索引**：索引只吃到 `WorkspaceId=?` 等值，之后在 19.5 万行逐行 LIKE。
2. **`ORDER BY CASE WHEN Name = $query THEN 0 ELSE 1 END, ...` 是表达式**：索引顺序无法满足，必须把所有匹配行塞进临时 B 树排序，`LIMIT 50` **无法提前终止**。
3. **`Signature` / `Container` 不在索引里**：三字段 LIKE 必须回表读宽列。
4. 2 MB cache vs 2.64 GB 库 ⇒ 冷查 4.2 s、热查 0.95 s。

**注意：这不是「索引没建好」。** 只查 `Name` 时 SQLite 自己就走 `USING COVERING INDEX`，实测 **1 ms**。

## 改动（`SqliteCodeIndexStore`）

`SearchSymbolsAsync` 增加快路径准入，命中则走 `SearchSymbolsFastAsync`：

| 阶段 | SQL 形态 | 实测 |
|---|---|---|
| 1 精确匹配 | `WHERE WorkspaceId=$w{ AND ProjectId=$p} AND Name=$q ORDER BY SymbolId, ProjectId LIMIT n` | 走 `(WorkspaceId[, ProjectId], Name)` 索引 |
| 2 Name 子串 | 同上 + `Name LIKE $like AND Name <> $q` | 覆盖索引，只回表取 ProjectId/SymbolId |
| 3 Signature/Container | 仅在 1+2 不足 limit 且 match_target 允许时才走 | 慢路径，按需 |
| 详情 | 同一连接逐条 `WHERE WorkspaceId/ProjectId/SymbolId` 点查 | 50 次 ≈ 18 ms |

**准入条件**（不满足则回退原宽表 SQL，语义逐字不变）：`skip == 0 && Kind == null && 文件扩展名过滤为空 && Query 非空`。
kind 与 FilePath 都不在索引里，skip 需要稳定分页语义 —— 任一项出现就回退。

两处 `PRAGMA cache_size = -131072`（128 MB，连接级）：快路径与宽表回退路径各一处。

**projectId 必须写成等值条件**：`($p IS NULL OR ProjectId = $p)` 会让 SQLite 放弃索引；改用 `{ AND ProjectId = $p }` 动态拼接。

**语义保持**：精确匹配单独用一次单值查询先取，因此不会被 `LIMIT` 截掉；其余按 `Name, SymbolId, ProjectId` 稳定排序，与原 `ORDER BY CASE…, Name, …` 等价。

## 过程中被现有测试抓住的一次回归

第一版快路径**漏了 `ProjectId` 过滤**，跨项目结果污染；`Symbol_Search_Can_Be_Narrowed_To_Project`
（既有测试）立刻取红：期望 1 条、实际 2 条。已修，并用 M2 证明该断言对 projectClause 有区分力。

## 评估过的另两条路线（本轮不做）

| 路线 | 实测 | 结论 |
|---|---|---|
| **FTS5 trigram** | 5 万去重名灌进临时表：任意子串 `LIKE` **0 ms**；建表 219 ms；临时库 8.2 MB（含两份） | 备选。当前量级 plain 表全扫已 0–4 ms，收益边际；**符号数 >50 万时再上** |
| **Lucene.Net** | 仓库已有（`search_grep backend=index`），但已承担三条“分词假阳性/零候选/语法字符”防护测试 | 不做。符号搜索要的是结构化 + 子串，Lucene 的打分与分词在这里是负担 |

「FTS5 向量检索」是两种东西：FTS5 是关键词全文索引，向量检索是 embedding 语义召回 —— 符号名搜索**不需要向量**。

## 未做

- 宽表回退路径（带 kind/文件扩展名过滤）仍有 ~330 ms（加 cache 后），未进一步优化。
- 索引库 2.64 GB 本身未做分区/归档治理。
- 需重启 Core 才进运行镜像。
