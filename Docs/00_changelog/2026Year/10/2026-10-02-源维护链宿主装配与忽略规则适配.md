# 2026-10-02 源维护链宿主装配与忽略规则适配

## 改动

- 新增 `Source/PuddingCodeIndex/Services/CodeIndex/WorkspaceCodeSourceIgnoreRules.cs`：
  把路径忽略的**唯一真源**（叶子组件 `PuddingPathFiltering`：名字级噪声名单 + 与 `git check-ignore`
  对齐的 .gitignore 语义）适配成 `ICodeSourceIgnoreRules`；忽略栈**按仓库根缓存**并按有效期
  （默认 5 分钟）重建 —— 用户新写的 `.gitignore` 不必重启就生效，同一仓库的多个 scope 不重复读盘。
  - **修掉一个真实缺陷**（写用例时暴露）：名字级噪声必须用
    `IndexExcludePatterns.IsNoisePathBelow(repositoryRoot, path)` **相对仓库根**判定。用绝对路径判定时，
    工作区自己的祖先目录名（`…\Temp\…`、`…\build\…`、`…\Debug\…`）会被当成噪声，**整棵工作区被排除**
    （索引悄悄变空）。已加专门用例锁定（测试根就在系统 Temp 下，正是这条风险的真实场景）。
  - 更正 `ICodeSourceIgnoreRules` 的旧注释（原写「组件不反向引用 PuddingPathFiltering」，与事实不符：
    组件已把它作为允许的叶子依赖引用），因此默认实现放在组件内；宿主要换规则就替换该端口。
- `Source/PuddingCodeIntelligence/DependencyInjection.cs`（组合根 = 组件化交付规程的 S5「登记 + 装配」）：
  注册 `ICodeSourceIgnoreRules` · `ICodeSourceScanner`（`FileSystemCodeSourceScanner`）·
  `CodeSourceScanService` · `CodeSourceFingerprintReader` ·
  能力端口 `ICodeSourceMaintenanceStore` / `ICodeGraphDependencyQuery` / `ICodeIndexFileBatchUpdater`
  （三者都 **fail-closed** 并要求解析到**同一个** `ICodeIndexStore` / `ICodeIndexer` 实例 ——
  两个 store 就是两个写者，与既有 scheduler/pump 同一实例约束同理）· `CodeSourceMaintenanceCoordinator`。
  - **只登记装配、暂不驱动**：驱动权仍在旧路径 `ICodeIndexMaintenance` 手里，因此这一笔对运行中实例
    是**零行为变化**，不需要重启。把驱动切到协调器是独立的一步。
- `Tests/PuddingHost.Tests/Hosting/CodeIndexMaintenanceHostCompositionTests.cs` 新增宿主组合用例：
  新链在**真实宿主容器**（`ValidateOnBuild` 开启）里可解析、能力端口与批量接缝都指向同一实例，
  并断言维护驱动仍是旧的 `CodeIndexMaintenanceService`（本笔未改变运行行为的证据）。

## 验证

- `dotnet test Tests\PuddingHost.Tests --filter CodeIndexMaintenanceHostCompositionTests` → **4 通过 0 失败**
  （含新增用例；该套件在 Build 阶段就会因无法解析的注册而失败，正是它守护的事故类型）。
- `dotnet test Source\PuddingCodeIndexTests` → **301 通过 0 失败**（新增忽略规则用例 6 条）。
- `dotnet test Source\PuddingCodeIntelligenceTests` → **132 通过 0 失败**（组合根改动未破坏既有 DI 用例）。
- 用例覆盖：噪声目录任意层级被忽略；`.gitignore` 的目录/通配文件被忽略；普通源文件不被忽略；
  **仓库自身位于噪声名祖先之下时不得被排除**；忽略栈缓存期内不重读、过期后重建生效、同仓库只缓存一份；
  空路径与非法有效期；以及宿主容器内的一致性装配。

## 未完成与影响

- **驱动权尚未切换**：`CodeSourceMaintenanceCoordinator` 已在容器里，但没有任何调用方驱动它，
  `CodeIndexMaintenanceService`（旧逐文件路径）仍然是唯一的维护驱动 ⇒ **运行中实例零行为变化**。
- watcher 事件到 `CodeSourceScanOptions.WatcherHints` 的接线、以及「无 owner ⇒ 整仓」旧路径的替换，
  与驱动切换放在同一步（那一步会产生用户可见的运行时变化）。
- 该步落地后按仓库规程交付 `ready-for-external-deploy`：**必须由进程外控制器重启到明确的新构建**，
  再跑四场景受控性能复核；本 Agent 不能证明新代码已被当前进程加载，也不能独立验收进程生命周期。
