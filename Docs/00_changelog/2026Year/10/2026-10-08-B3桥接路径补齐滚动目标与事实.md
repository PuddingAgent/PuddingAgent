# 2026-10-08 B3 桥接路径补齐滚动目标模型与结果事实

## 目标 / 背景

上一轮（见 [B3 滚动目标模型与结果事实](2026-10-08-B3滚动目标模型与结果事实.md)）把 §7 的滚动目标模型与
结果事实做到了**能力通道路径**，桥接路径当时明确返回 `unreported` 并登记为**传输不对称**。
本轮把它补上 —— 否则同一个 `browser_interact` 在两种传输下给出的事实完全不同。

## 改动

| 文件 | 改动 |
|---|---|
| `Source/PuddingBrowser.Protocol/BrowserBridgeCommandPayloads.cs` | `PageInteractArguments.ScrollTarget`（目标模型线名）；`BrowserInteractionResultDescriptor.Scroll` + 新增 `BrowserScrollReportDescriptor`（容器/前后位置/消耗位移/边界/内容变化）；未报告时为 `null` |
| `Source/PuddingBrowser.Protocol/BrowserBridgeJsonSerializerContext.cs` | 登记 `BrowserScrollReportDescriptor`（源生成序列化必须显式登记） |
| `Source/PuddingDesktop.WpfArchive/Browser/BrowserWorkspaceController.cs` | 宿主侧 `page.interact` 的 `scroll`：解析目标（显式线名优先，否则按 locator/位移推导，**未登记线名抛 `browser_invalid_command` 而不猜测**）、把 locator 一起下传、把驱动的 `ScrollOutcome` 回填进响应 |
| `Source/PuddingHost/BrowserBridge/RemoteBrowserPage.cs` | `ScrollAsync` 直接发 `PageInteract`（携带目标线名与 ref 定位）并把响应读回成 `ScrollOutcome`；宿主**未报告**时才标 `unreported`（不再无条件 `unreported`） |

## 验证

| 套件 | 结果 |
|---|---|
| `PuddingHost.Tests` | **256 / 256**（原 254 ＋ 2） |
| `PuddingDesktop.Tests` | **312 / 312**（原 310 ＋ 2） |
| `AgentTools.Tests` · `DesktopSurface.BrowserTests` · `ContractsTests` · `DesktopServiceTests` · `AutomationTests` | 45/45 · 61/61 · 101/101 · 220/220 · 194/194 |

新增门禁：

- Core 侧 `RemotePage_ScrollCarriesTheTargetModel_AndReadsBackTheFacts`：宿主报告
  「到底了 + 0 位移 + 无新内容」⇒ `ScrollOutcome` 如实带回（不是 `unreported`、也不是编造的位移），
  并断言**线缆上的真实字段名**（`action`/`scrollTarget`/`deltaY`）；
- Core 侧 `RemotePage_ScrollWithoutHostFacts_IsMarkedUnreported`：宿主没报告事实 ⇒ `unreported` + 位移 0
  （"没有事实" ≠ "滚了 0 像素"）；
- 宿主侧 `PageInteract_ScrollCarriesTargetAndReturnsFactsOverTheBridge`：`to_bottom` 到达驱动，
  响应里的 `scroll` 事实与驱动报告一致；
- 宿主侧 `PageInteract_UnknownScrollTargetIsRejectedInsteadOfGuessed`：`wheel` ⇒ 命令失败、
  **驱动一次都没被调用**。

**取红实测**：把 `RemoteBrowserPage` 发送的 `ScrollTarget` 置空 ⇒
`RemotePage_ScrollCarriesTheTargetModel_AndReadsBackTheFacts` **恰好变红**，其余 8 条仍绿；
复原后 256/256 复绿。

## 已知边界（诚实登记）

- **宿主侧映射现在有两份**：能力通道（`DesktopScrollTarget` → `ScrollTarget`）与桥接
  （线名 → `ScrollTarget`）。两处逻辑等价但**各写了一遍**（字面量在 Protocol/Core/Desktop 之间重复），
  未来若加目标必须同时改三处 —— 已按"未登记即拒绝"保证不会静默漂移，但**没有单一真源**。
- **驱动侧的真机滚动行为仍未验证**（本环境跑不了真实 WebView2），只验证了事实在两条传输上的
  传递与不编造。
- 桥接的 `to_ref`/`element` 目标需要 **ref** 定位：与能力通道一致（脚本按宿主 ref 匹配）；
  用非 ref 定位描述符会被宿主下传后在驱动层拒绝。
- `atBoundary` 判据仍是"请求了位移但方向不对/没动"，不区分"到底了"与"被浮层挡住"。

## 影响与回滚

- **行为变化（Agent 可见）**：走 WebSocket Bridge 的 `browser_interact` 现在也会返回 `scroll` 事实，
  且 `scroll_target` 会被尊重；桥接行为与能力通道**同形**（此前桥接静默忽略目标、只回 `unreported`）。
- 线缆新增可选字段（向后兼容：旧宿主不回 `scroll` ⇒ 消费方得到 `unreported`）。
- 回滚：还原上表 4 个生产文件与 2 个测试文件及 code_map。
