# 2026-11-17 飞书兜底收件人统一走 open_id

## 缺陷

派发器的显式收件人分支（`send_message` 传 `user:ou_xxx`）会把 `open_id` 写进
`metadata["open_id"]`，并**主动删掉** `chat_id` / `message_id`。而连接器侧四条发送路径
各写了一遍兜底逻辑，只有文本那条读 `open_id`：

| 路径 | 原行为 |
|---|---|
| 文本 | 有 `open_id` 按用户发 |
| 语音 / 图片 / 文件 | 一律 `receive_id_type = "chat_id"` |

于是给显式收件人发图片或文件时，**open_id 被当成 chat_id 提交**。`SendFileTool`
的说明本身写着 never provide a recipient，依赖的正是这条兜底路径。

## 改动

- 新增 `Source/HarnessAgent.Core/Connectors/Feishu/FeishuRecipientResolver.cs`：
  纯函数 `Resolve(metadata, target)` —— 显式 `open_id` 优先，否则 `target` 视为
  `chat_id`，两者都没有则抛 `ArgumentException`（不猜）。
- `FeishuConnector` 四条路径（文本 / 语音 / 图片 / 文件）改为调用它，
  各自那份判定与注释删除；新增发送路径无法再各写一份而漏读。
- 顺带把「有 open_id 但为空串」的边界钉住：空串不得遮蔽真正的 chat 目标。

## 验证

- `dotnet build Source/PuddingHost`（含 HarnessAgent.Core）：0 error。
- `HarnessAgent.Core.Tests` Feishu 全量：**通过 92 / 跳过 1 / 总计 93，失败 0**。
- 变异（把 `open_id` 分支的 `receive_id_type` 改回 `chat_id`，即原缺陷形状）：
  构建 0 error、测试**失败 1 / 通过 7**，红的正是
  `Explicit_Open_Id_Wins_Over_Chat_Target`（`FeishuRecipientResolverTests.cs:35`）。
- 逐字节复原：`ORIG_SHA == RESTORED_SHA == C7D87031…`，`BIT_IDENTICAL=True`；
  `-t:Rebuild` 后复跑 8/8 通过。

## 局限（不要当成已验证）

`FeishuConnector` 本身**没有连接器级集成测试**，`clientFactory` 测试缝至今无人使用。
因此「连接器确实调用了这个解析器」是由编译与代码阅读保证的，**不由测试保证**。
要真正闭合，需要注入带假 HTTP handler 的 `FeishuClient`，断言请求 URL 里的
`receive_id_type`——该测试缝已存在，但仍是待办。
