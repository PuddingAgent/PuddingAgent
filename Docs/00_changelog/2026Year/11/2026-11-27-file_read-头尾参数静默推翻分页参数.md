# 2026-11-27 file_read 头尾参数静默推翻分页参数

## 现象

用 10 行文件（`L1`..`L10`）实测：

| 入参 | 正文 | 提示 |
|---|---|---|
| `offset_lines=8`、`tail_lines=3` | `L8 L9 L10` | 无 |
| `head_lines=5`、`limit_lines=2` | `L1`..`L5` | 无 |
| `head_lines=2`、`tail_lines=3` | `L1 L2` | 无 |

第一行：调用方要的是「从第 9 行起的末 3 行」，拿到的是**整个文件**的末 3 行。
第二行：要 2 行，拿到 5 行。
第三行：两个都给，只认 head。

三者都没有任何提示。根因是 `DescribePagingAnomaly` 的第一行：

```csharp
if (headLines.HasValue || tailLines.HasValue)
    return null;
```

它不只丢弃这两个参数——连 `OffsetLines` 越界、`LimitLines <= 0` 这些本来会出声的分页异常也一并静音了。

## 哪部分是设计，哪部分不是

`HeadLines`/`TailLines` 是「从一端取 N 行」的语义，N 超过总行数等于全取 —— 这**是**设计。实测确认：`tail_lines=100` 对 10 行文件返回全部 10 行、无提示，结果正确，不该报异常。

但「同时给了 offset/limit 就静默丢弃」不是同一件事：它没有文档、没有提示，结果与调用方意图不同且不可察觉。

## 改法

只出声、不改行为（分支优先级 Head → Tail → Offset 保持原样）：

- 有 head/tail 时，若同时给了 offset 或 limit，各出一条 `[PAGING:]` 说明被忽略、以及由谁选定窗口；
- head 与 tail 同时给，说明 tail 因 head 优先被忽略；
- 三个都不给时仍返回 null —— 正常路径不出声。

## 取红

| 变异 | 结果 | 红点 |
|---|---|---|
| M1 新分支恒 `return null` | 45 例 **3 红** | 三条新用例全红，正向对照绿 |
| M2 只删 limit 那段 | 45 例 **1 红** | `LimitLines_WithHeadLines_ReportsIgnored` |

M1 打红的集合严格包含 M2，说明三条断言各管一个参数、不是同一处分派被数了三遍。

正向对照 `HeadLines_Alone_HasNoPagingNotice` 两轮全绿 —— 没有它，一个恒发提示的实现也能让前三条全过。

恢复后 `SHA EFE0967117C2AC0E` 与修复后基线逐字节相同，`dotnet build -t:Rebuild` 后 45/45。

## 运行时验收

**未验收。** 部署后需实调三条：`offset_lines=8 + tail_lines=3` 应出现「OffsetLines=8 was ignored」；`head_lines=5 + limit_lines=2` 应出现「LimitLines=2 was ignored」；`head_lines=2` 单独应无 `[PAGING:`。

## 局限

- 新用例只走小文件路径。大文件流式路径共用同一 `DescribePagingAnomaly`，但三个变异都打在单一实现上，没有单独打红大文件路径。
- `head_lines` 与 `offset_lines` 组合的**语义**（是否该改成「从 offset 起的 N 行」）没有裁定。本轮保持现状、只补提示——改语义会影响现有调用方，需要单独决策。
