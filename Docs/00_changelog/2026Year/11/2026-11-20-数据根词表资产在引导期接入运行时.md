# 2026-11-20 数据根词表资产在引导期接入运行时

## 目标 / 背景

精确分词在该机器上一直没生效（`runtime_identity` 报 `isExact=false` / `AssetMissing`）。
排查结论是：`PUDDING_TOKENIZER_ASSETS` 已在 User 级登记（注册表有值），但运行中的 Core
看不到——Windows 的环境块在进程创建时从父进程继承，Core 是 Desktop 的长寿子进程，因此
只重启 Core 不会重读 User 级变量。三方对照取证：`USER_REG` 有值 / `PROCESS_ENV` 空 /
部署目录 `tokenizers` 零文件。

资产本来就被安装在 `{DataRoot}/models/tokenizers`（安装脚本的默认落点），而引导期已经算出
数据根，所以不需要新增配置项，也不需要把 6.4 MB 词表复制进构建产物。

## 改动

- `Source/PuddingTokenization/TokenizerAssetDirectory.cs` — `ContainsAnyAsset` 由私有改为
  公开：「什么样的目录算配好资产」必须只有一份定义，解析策略与引导期共用它；并新增
  `DataRootAssetDirectory(dataRoot)`，把「词表在数据根的哪里」与「资产叫什么、怎么算配好了」
  放在同一个组件里。数据根本身仍由宿主解析，组件不读环境变量也不猜路径。
- `Source/PuddingHost/Hosting/PuddingDataRootBootstrapper.cs` — 新增
  `EnsureTokenizerAssetsVisible`，在 `Bootstrap` 中于 `EnsureRuntimeDirectories` 之后调用：
  仅当 `PUDDING_TOKENIZER_ASSETS` 为空**且** `{DataRoot}/models/tokenizers` 确有资产时，
  把**进程级**变量指向该目录；不写回 User/Machine，不覆盖显式配置。
- `Tests/PuddingHost.Tests/Hosting/PuddingDataRootTokenizerAssetsTests.cs` — 4 条用例。

## 验证

- 新增用例 4/4 通过：有资产则接入、无资产不接入、**空目录不算有资产**、显式配置不被覆盖。
- 变异取红：把判据改成 `Directory.Exists` → 恰好 `Bootstrap_DoesNotTreatAnEmptyDirectoryAsConfigured`
  一条变红；复原后重新 4/4 绿。
- 全量 `Tests/PuddingHost.Tests`：**461 总计 / 456 通过 / 5 失败**；基线（改动 stash 后同一命令）
  **457 总计 / 452 通过 / 5 失败**，失败集合完全相同（逐名比对）⇒ 零回归，新增 4 条全绿。
- 5 条既有失败中 `BootstrappedSecurityJson_IsTheJwtConfigurationSource` 与本改动无关但值得记：
  引导期把 `security.json` 的 `jwt.key` 写成 `{{vault:...}}` 引用，而
  `PuddingJwtSettings.FromConfiguration` 明确拒绝未展开的 vault 引用。另 4 条是
  `DesktopChild_*` 组合根用例，基线同样失败。

## 影响与回滚

- 影响范围：只在进程内设置环境变量，不落盘、不改用户配置；对没有词表资产的机器完全无副作用。
- 生效时机：下次 Core 启动即可，**不需要重启整条 Desktop 进程树**。
- 回滚：`git revert` 本提交；即使不回滚，把数据根下的词表目录移走即恢复原行为。
