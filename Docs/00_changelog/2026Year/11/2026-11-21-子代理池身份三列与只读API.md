# 子代理池身份三列 + 只读池列表 API

## 目标与边界

前端要做「子代理」管理视图，而池条目只存在于 `agent_pool` 表，Web 侧没有任何端点能读到它。
本切片补两件事：

1. 补齐前端要展示但表里没有的三列：`model_id`、`avatar_key`、`responsibility`；
2. 新增**只读** `GET /api/admin/sub-agent-pool`，返回池条目列表。

**只读**：创建 / 唤醒 / 销毁留给后续切片。控制器里没有任何写动词方法，
这条约束由测试用特性反射断言锁住（出现 `HttpPost/Put/Patch/Delete` 即失败）。

## 为什么补列只能走 bootstrapper，不能走 EF migration

全仓 `Migrate()` / `MigrateAsync()` **零调用**，运行时只有 `EnsureCreated`，而
`EnsureCreated` 对「已经存在的库」什么都不做——存量平台库早已有几十上百张表，
`agent_pool` 的列变更永远不会被它补上。因此：

| 场景 | 谁负责 |
|---|---|
| 全新库 | EF `EnsureCreated` 依实体声明建 21 列 |
| 存量库（18 列） | `AgentPoolSchemaBootstrapper`：`PRAGMA table_info` 查列 → 缺才 `ALTER TABLE ADD COLUMN` |

SQLite **不支持 `ALTER TABLE ADD COLUMN IF NOT EXISTS`**，所以守卫不是防御性代码而是必需条件：
去掉守卫，第二次启动就直接 `SQLite Error 1: 'duplicate column name: model_id'`。
变异实验（见「验证」）就是把这个守卫删掉，结果 5 条用例全红。

三列一律 `TEXT NULL`，不写 `TEXT(64)`：SQLite 不执行长度约束，写长度只会让
「EF 新库」与「存量库 ALTER」的 `PRAGMA type` 不同（`text(64)` vs `TEXT`），
给两路一致性测试制造永久噪声。长度上限仍由实体上的 `MaxLength` 表达。

新列追加在实体声明**末尾**，使 EF 建表的物理列序与存量库 ALTER 追加的顺序一致；
两路比对本就用集合相等，但序一致可以让 `SELECT *` 类诊断脚本不会看到两种排法。

## 为什么空池必须 200 + `[]`

对界面来说「一个条目都没有」和「这个端点不存在」是两件完全不同的事：前者要显示空状态
与创建引导，后者是部署 / 路由故障。用 404 表达空列表，会把后者伪装成前者。
因此 `GET` 无论有没有条目，都返回 `200`。变异实验：把空池分支改成 `NotFound()`，
「空池必须 200」的用例立刻变红（失败 1 / 通过 2）。

## 为什么直接查库，不注入 `SubAgentPool`

`SubAgentPool` 是内存池，带四态就绪门：未 Ready 时 `List()` 抛 `PoolNotReadyException`。
若本端点复用它，「Core 刚启动、池还在预热」就会表现为一个读接口报错——而此时库里的条目
是完全可读的。本端点直接经 `IDbContextFactory<PlatformDbContext>` 短生命周期 context 查库，
于是启动早期界面也能如实显示库里有什么。

## 响应契约

`GET /api/admin/sub-agent-pool` → `200` + `SubAgentPoolEntryDto[]`（camelCase）：

`poolId, name, role, responsibility, avatarKey, modelId, templateId, status, taskCount,
lastUsedAt, lastSuccess, subSessionId, createdAt`

- 过滤 `deleted_at IS NULL`（软删墓碑不出现）；
- 排序 `last_used_at DESC`，空值（库列 NOT NULL，实际是空串）排最后；
- 时间列原样透出库里的 ISO-8601 文本，不转 `DateTime`：诊断时要看到「库里究竟存了什么」。

**与任务书的一处差异**：任务书 DTO 列了 `lastSuccessAt`，但实体只有布尔
`last_success`（三态：NULL 从未执行 / 0 上次失败 / 1 上次成功），**库里没有任何「最近成功时刻」的列**。
凭空造一个恒为 `null` 的时间字段，界面会一直显示「从未成功」——那是假数据。
因此这里如实透出 `lastSuccess`；若前端确实需要时间轴，应另开一列 `last_success_at`
并补写入方，属后续切片。

DTO 放在 Host 内、不塞 `Pudding.Api.Contracts`：后者是跨进程契约，
本端点只供 Web 前端读取，放进去会让无关进程被迫跟着版本化。

## 验证

| 步骤 | 结果 |
|---|---|
| `PuddingPlatform` `-t:Rebuild` | 0 error / 56 warning（全部为既有告警，本次新增文件 0 告警） |
| `PuddingHost` `-t:Rebuild` | 0 error / 216 warning（同上） |
| `AgentPoolSchemaBootstrapperTests` + `SchemaBootstrapperFreshDatabaseColumnTests` | 失败 0，通过 5，总计 5 |
| `SubAgentPoolAdminControllerTests`（控制器层） | 失败 0，通过 3，总计 3 |
| `SubAgentPoolAdminEndpointTests`（真实宿主 HTTP） | 失败 0，通过 3，总计 3：无 JWT ⇒ 401、带 JWT ⇒ 200 + JSON 数组、预置行逐字段 camelCase 映射且 `lastSuccessAt` **不存在** |
| 影响面（`AgentPool*` + `*SchemaBootstrapper*`） | 失败 0，通过 103，总计 103 |
| 变异①：删掉 `PRAGMA table_info` 守卫（无条件 ALTER） | **失败 5 / 通过 0**，报 `duplicate column name: model_id` |
| 变异②：空池返回 `NotFound()` | **失败 1 / 通过 2**，断言落在 `Assert.IsInstanceOfType<OkObjectResult>` |
| 复原 | 两处均 SHA-256 逐位一致（`F4FA0FE2…68BF5766` / `01090256…53E6F85C`），`-t:Rebuild` 后重跑全绿 |

`Copy-Item` 复原保留原 mtime 会让 msbuild 判定「已是最新」而继续跑变异后的 DLL，
因此复原后对 `PuddingHost` 也是显式 `-t:Rebuild`（产物时间戳 03:19:55 晚于复原时刻，可核）。

## 已知限制

- 三列目前**没有写入方**：`AgentPoolInsertRequest` / `AgentPoolEntryStore` 未改，
  所以新建条目这三列为 NULL。谁写 `model_id`、谁写 `responsibility` 由后续切片决定
  （设计稿：派发者写，未给时回退 `task_summary` 首句）。
- `last_success_at` 不存在，见上「与任务书的一处差异」。并行推进的前端 WIP
  （`Source/PuddingPlatformAdmin/src/pages/chat/components/subagent-pool/api.ts`）已按同一结论
  把 `lastSuccessAt` 声明为可选、`lastSuccess` 为三态，前后端契约一致。
- `Tools/Docs/front_matter.py` 需要 python，本机无 python，故本文 front matter 未过校验器，
  字段集合照抄同目录 `2026-11-21-agent_pool表schema.md`。
