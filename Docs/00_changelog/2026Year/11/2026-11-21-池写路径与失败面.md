# 池的写路径与失败面（S5a–S5d）

四个提交修的是同一条线：**池从「内存真相」变成「数据库真相」之后，所有依赖旧假设的地方都要跟着改**。

| 提交 | 内容 |
|---|---|
| `62d4af3` | Execute / Finish / Sleep / Destroy 写库 |
| `9aef9b5` | LRU 淘汰写库 |
| `269fba5` | 重启后恢复 stale busy |
| `5a507c1` | 工具层五类失败可区分 |

## S5a：DB 为准，缓存跟随

此前只有 `CreateAsync` 写库，条目能落库但执行结果不回写——重启后库里仍是 `status='idle'`、`task_count=0`。

统一为：先打 DB 条件更新，**成功（≥1 行）才改内存**；返回 0 行记 warning 并丢弃该次内存变更，不静默改缓存。

`PoolEntry` 新增 `PoolId`。**注意**：`pool_id` 与 `sub_session_id` 是两列，前者定位行、后者只是 `TryCompleteAsync` 的复用键校验。`pool_id` 只在创建处生成一次，恢复路径从快照带回、绝不重生成——两处各生成一个会让内存 id 永远指向不存在的行，每次条件写都静默 0 行。

`ExecuteAsync` 的**自动创建**路径也必须先 `TryInsertAsync`：真实工具层的 `execute` 默认走自动创建，不先插一行的话抢占必然 0 行。

## S5b：淘汰写库，否则重启复活

`EvictLeastRecentlyUsedAsync` 原先只改内存（置 Dead + `TryRemove`）。库里那行仍是 `sleeping`、`deleted_at IS NULL`，于是重启后 `EnsureReadyAsync` 把它原样加载回来——**淘汰等于没发生**。

两处配合：

- `TryEvictOldestSleepingAsync` 返回类型 `int` → `Task<string?>`，返回被淘汰的 `pool_id`。只返回行数时，池知道「淘汰成功」也不知道该从内存移除哪个
- 池拿到 `pool_id` 后才按 `PoolId` 从内存移除。**不按名字**——名字可被 destroy→create 换掉，只有 `PoolId` 与库行一一对应

实现用事务内「SELECT LIMIT 1 + 条件 UPDATE（带 status 守卫）」，**不用 `RETURNING`**：EF 的 `ExecuteSqlInterpolatedAsync` 拿不到结果集。

## S5c：busy 恢复——把顺序依赖换成状态依赖

崩溃或重启会留下 `status='busy'` 的池条目，池加载后它们永远派不了活（`TryAcquireAsync` 要求 `idle`/`sleeping`）。

`ResetStaleBusyAsync` 早就存在，但没调用方，且判据只有 `WHERE status='busy'`——**接上去会误杀正在跑的条目**。

关键判断：不能靠「让它跑得够晚」。`BackgroundService.StartAsync` 不 await `ExecuteAsync` 主体，注册顺序只保证「更晚开始」，不保证「恢复已完成」（S4 已确认）。

所以判据改成查数据：

```csharp
.Where(p => !db.SubAgentRuns.Any(r =>
    r.SubSessionId == p.SubSessionId && activeStatuses.Contains(r.Status)))
```

只有「库里显示 busy、但 run 表里没有任何非终态 run」的条目才复位。执行早了也不会误杀。

配套做了一件事：把 `FileSubAgentRunStore.IsTerminalStatus` 里硬编码的 6 个终态字面量提取为 `SubAgentRunEntity.TerminalStatuses`，新增 `NonTerminalStatuses` 供池使用。两处各写一份的话，「本类认为已结束」与「池认为还在跑」会同时成立——那正是僵尸 busy 与误杀 busy 两种缺陷的共同源头。

另有一个边界：词表若被改坏成空集合，`Contains` 恒 false，判据会退化成「所有 busy 都是 stale」，一次把整个池重置。所以词表为空时**拒绝重置并 LogError**——误杀代价远大于不救。

## S5d：五类失败要分开说

`pool_action` 原先用一个宽泛 catch，五种失败显示成同一句话。更糟的一种不是「不够详细」而是**说了假话**：未就绪时 `list` 若走空集合分支会输出「池为空」，用户会以为子代理都没了。

- `PoolFailureKind` + `ClassifyPoolFailure`：先按异常类型判 `PoolNotReadyException` / `PoolOwnershipMismatchException`，再按抛出方的**稳定文案前缀**判「忙」与「池满」。前缀被改写只会退化成 Unknown → 通用文案，**不会错报到另一个类别**（安全方向失败）
- 未就绪文案带 `readiness` 分档：`Loading`/`NotStarted` 是暂时状态、`Failed` 是终态且**重试无效**；带 `InnerException` 底层原因；显式声明「还不知道 ≠ 没有」
- 归属文案按 `ReasonCode` 给中文维度，并说明「在创建 run 之前拒绝、未污染池计数」

测试的关键不是「有报错」，而是「可区分」：

- `PoolFailures_ArePairwiseDistinct`：收齐五条文案后 `Distinct` 计数必须仍为 5
- 归属 / 忙 / 池满三条互相断言：各自标志词存在，**另两个标志词不存在**

## 验证

| 提交 | 测试 | 父代理亲自做的变异 |
|---|---|---|
| S5a | 44/44 | 关掉 Sleep/Destroy 的 store 分支 → 失败 2 |
| S5b | 51/51 | 池跳过 store 淘汰 → 失败 3（含「重启不复活」核心回归） |
| S5c | 63/63 | 删掉 `!SubAgentRuns.Any` 判据 → 命中「在跑的 run 被误判 stale」 |
| S5d | 26/26 | 在未就绪文案插「池为空」→ 命中「未就绪被误报成空池」 |

每处复原后 SHA-256 均与应用变异前逐位一致，`-t:Rebuild` 后重跑全绿。

## 两个流程观察

**一、子代理报 failed 不等于没交付。** S5b 与 S5c 的子代理都在最后一步工具调用出错而报 failed，但代码已经完整落盘。按「工作树有已完成未提交的改动，先验收再提交」的纪律核盘后都救回来了——没有重做。

**二、子代理改禁止改的文件时，看它是「改变语义」还是「提取单一真源」。** S5c 改了 `FileSubAgentRunStore`，但改的是把 6 个硬编码终态提取成共享常量，**值逐字一致**。这恰恰是任务书要求的「不许另写一份」，所以接受。
