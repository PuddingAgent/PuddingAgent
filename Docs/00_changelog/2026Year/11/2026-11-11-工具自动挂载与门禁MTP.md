# 工具自动挂载与门禁 MTP 修复

## 现象

每次 Core 重启后，Agent 的可用工具集从 8 个内核工具重新开始，必须手工把 `pudding.goals`、`pudding.files`、`pudding.git`、`pudding.shell`、`pudding.general` 逐个 `plugin_load`，每次还要读一次递增的 `hostTools.revision`。

## 根因

- `HostToolMounts` 的挂载表是**进程内内存**，Core 重启即清零。
- `PluginManager.MountOwner` 已经把 `SessionId` 清空（注释：`Agent tool mounts span conversations`），所以激活本来**跨会话**——重挂的触发点是进程重启，不是新对话。

2026-11-11 23:26 的部署重启后，`activations` 为空即由此而来。

## 改动

`HostToolContributions.ListTools` 在枚举前执行 `AutoMount(context)`：

1. 只考虑尚未挂载、且未被显式卸载钉住的包；
2. 包的导出项中只要有一项同时满足 `Selected`（能力策略选中）与 `Permitted`（含 `CanExposeToAgent`、shell/文件写权限位），就为该 `(workspace, agent)` 作用域挂载；
3. `UnloadAsync` 记入 `_autoSuppressed` 钉住，`Load` 解除。

安全边界不变：`host-service` 包是 JSON 声明，导出名指向产品已注册的宿主操作，进程内不执行任何代码（`ProcessId = null`）；每次调用仍逐个通过 `Permitted()`。

## 门禁修复

`dotnet test --logger trx` 对 Microsoft.Testing.Platform 项目在 .NET 10 上直接报错「VSTest target is no longer supported」。原逻辑把这条错误归入「过滤器零命中」，打印 `skipped` 后仍输出 `OK: no new test failures`——**零测试执行却报绿**。

现在检测到该错误后改为运行构建产物 `dotnet <dll> --filter ... --report-trx`，产出的 TRX 与 VSTest 结构一致，直接复用原解析；确实无法运行时打印 `SKIPPED (runner): reason` 并在结论前单列 `NOT VERIFIED` 清单。

启用后又暴露出 7 条 `RealWorkerTests`：它们用 `Environment.GetEnvironmentVariable("PUDDING_PLUGIN_WORKER")!` 直接拼路径，缺变量时以 `ArgumentNullException` 崩掉；同目录的 `FoundationPrototypeTests` / `PluginWorkspaceEventDemoTests` 早就用 `Assert.Inconclusive` 跳过。已给 `RealWorkerTests` 加 `[TestInitialize]` 守卫，与既有约定对齐：缺验收环境时 `13 tests / 3 passed / 10 skipped / 0 failed`。

### 盲区有多大

真正拒绝 VSTest 的标记不是 `MSTest.Sdk`，而是 csproj 里的 `<UseVSTest>false</UseVSTest>`（配合 `OutputType=Exe`）。实测统计：99 个测试工程中 **37 个**是该配置 —— 它们在本次修复前，无论是否被选中，**都没有被执行过一次**。

抽样：`GoalDecisionPresenter.Tests` 经新路径运行 `9/9 通过`，证明新路径不只对单个工程有效。其余 36 个未跑，不能因为抽样绿就声称它们健康。

## 验证

| 项 | 证据 |
| --- | --- |
| 自动挂载用例 | 2/2 通过（首次枚举即得工具、卸载钉住、加载解除、策略拒绝不挂载） |
| 变异取红 | 删掉 `AutoMount(context);` 后失败：`Assert.HasCount 期望 1 实际 0`；复原 `-t:Rebuild` 后通过，文件 SHA 位级一致 |

## 门禁选择面（同日补充）

上一节修复的是「选中了却静默跳过」。还有一个更早的失效点：选择面本身。

门禁按**类型名**构造过滤器（`FullyQualifiedName~<类型名>`），可测试类不一定要用被测类型命名。`SlackGatewayTests` 只是**构造** `MessageGatewayIngress`，类名里没有它——工程被选中，过滤器却匹配零个测试类，于是一个用例都没跑。2026-11-11 的单会话改造就是这样漏掉的。

现在扫描命中文件时，同时收集 `[TestClass]` 属性紧邻的类名并入过滤器（上限 40 个，防过滤面爆炸）。

实测同一改动（暂存 `MessageGatewayIngress.cs` 注释）：

| | 过滤器 | 结果 |
| --- | --- | --- |
| 修复前 | `~MessageGatewayIngress` | 零测试类命中 |
| 修复后 | `~FakeFeishuRoundTripTests\|FeishuCommandInterceptionTests\|MessageGatewayIngress\|SlackGatewayTests` | `ran 2`，通过 |

## 未验证与局限

- 自动挂载**尚未在生产生效**：Core（PID 63324）运行的是改动前的产物，需要重启。
- `--report-trx` 若某个 MTP 项目不支持，会退化为 `SKIPPED` 并显式显示，不会静默。
- 多目标框架项目取 `bin` 下最新产物，未处理并行多 TFM 同时构建的情形。
- 门禁仍然是「按改动选测试」，选中范围之外的测试不会被跑；本次修正的是「选中了却静默跳过」，不是选择策略本身。
