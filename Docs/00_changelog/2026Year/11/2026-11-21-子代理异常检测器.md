# 子代理异常检测器（P0-a）

## 为什么

一次性子代理有固定计数器（轮次 600 / 工具 2400）。子代理持久化并可取消之后，这个上限两头都错：

1. **误杀正常长任务** —— 计数器量的是「做了多少步」，而长任务的正常步数可以远超 600。实测某子代理停在 `轮次 92/600`，那不是异常。
2. **挡不住真正的病态** —— LLM 复读时缓存命中率极高（实测同会话可达 98.7%），复读一轮只要几厘钱，600 轮复读的成本**低于**一次正常长任务。计数器在这里完全失效。

所以真正要检测的是「原地打转」，而不是「做了多少步」。

现状：`AgentExecutionGuardrails` 已有三项检测（`MaxSameToolRepeat=3` / `MaxNoProgressRounds=3` / `MaxConsecutiveToolDiscoveryCalls=8`），**前两项只注入引导消息、不停**。取消轮次上限后它们就是新的失控口 —— 因此本检测器是取消上限的**前置条件**。

## 做了什么

新增两个文件，**不改任何既有文件、不改 DI、不改状态词表**：

| 文件 | 字节 | 内容 |
|---|---|---|
| `Source/PuddingRuntime/Services/AgentLoop/RunAnomalyDetector.cs` | 15,487 | 纯函数检测器（无 ILogger / 无 IDbContext / 无时钟） |

契约形状按设计文档 §六 固定：`RunAnomalyObservation`(readonly record struct) / `RunAnomalySignal` / `RunAnomalyAction` / `RunAnomalyVerdict` / `RunAnomalyDetectorOptions` / `RunAnomalyDetector`(`Observe` / `Reset` / `SnapshotWindow`)。

三类信号：

| 信号 | 判据 |
|---|---|
| S1 `RepeatedAssistantOutput` | 同一条 Assistant 观测的归一化文本 hash 在窗口内 ≥ RepeatThreshold 次 |
| S2 `RepeatedToolAction` | 同一 Tool 的「工具名 + 归一化参数」hash ≥ RepeatThreshold 次 |
| S3 `FrequencySpike` | 当前窗口 events/min > 前两窗均值 × 5，且连续两窗 |

## 三个决定成败的实现细节

**一、复位规则（防误杀核心）**

```csharp
if (!_currentWindowHit) _consecutiveHitWindows = 0;
```

一个窗口结束时若没有任何命中，连续命中计数归零。没有这一行，长任务里偶发一两次相同调用会被累加成 Pause —— 误杀正常任务比漏检病态更糟。

**二、归一化必须剥掉时间戳与 ≥8 位 hex**

复读的每一轮都带新的时间戳和新的 trace id。不剥离，同一句话每轮 hash 都不同，检测器**永远不会命中** —— 这是最危险的失败模式：它静默地什么都不做，而所有「能检测到复读」的用例仍然全绿。

**三、hash 用 SHA256，禁用 `string.GetHashCode()`**

后者带进程级随机种子，同一段文本在测试进程与生产进程得到不同值，检测结果无法复现。

另有两处刻意的语义选择：

- **同一窗口只升一次阶梯**。否则窗口内第 4 条重复就把阶梯顶穿，等于变相「一命中即杀」。
- **S3 的 `durationMs <= 0` 返回 0 而不是无穷大**：同一毫秒内灌进来的样本不构成频率证据，不能当成「无限快」。

## 验证

```
dotnet build Source\PuddingRuntime\PuddingRuntime.csproj -t:Rebuild      → 0 错误
dotnet build Source\PuddingRuntimeTests\PuddingRuntimeTests.csproj -t:Rebuild → 0 错误
dotnet test --filter "FullyQualifiedName~RunAnomalyDetector"              → 11/11 通过
```

三处变异取红（子代理两处 + 父代理独立一处）：

| 变异 | 结果 |
|---|---|
| A `PauseWindows = 2 → 1` | **失败 7 / 通过 4**（含判据 2「第三次重复只出 Notice」、判据 4「干净窗口复位」） |
| B 删掉复位规则那一行 | **失败 1 / 通过 10**，恰为判据 4 —— 证明该行唯一负责该行为 |
| C 删掉 hex 剥离（父代理） | **失败 1 / 通过 10**，恰为判据 7「仅时间戳与 hex 不同必须同 hash」 |

三处复原后 `SHA-256 = B493857A…45E075D` **逐位一致**，`-t:Rebuild` 后复绿 11/11。

## 判据里容易写歪的两条

- **对照组**：30 条互不相同的观测必须全部 `Action == None`。没有这条，检测器写歪了会误杀正常长任务，而所有「能检测到复读」的用例仍全绿 —— 那种测试只能证明它会停，证明不了它停得对。
- **复位**：命中 → 干净窗口 → 再命中，只能 `Notice` 不能 `Pause`。

## 遗留（P0-b 才做，已识别风险）

1. **检测器目前没有生产调用方**，行为变化为零。接线属 P0-b。
2. `paused` 是**字符串词表不是枚举**，散落至少 5 处：`SubAgentTransientDirectoryGcService.cs:30`（终态集合）、`SubAgentManager.cs:227/245`（事件映射与 resumable）、`SubAgentInvocationService.cs:399-412`（聚合）、`AgentExecutionService.Buffered.cs:2493`、前端 `SubAgentCardStatus`。漏一处就是「暂停了但界面显示失败」或「暂停了但恢复不了」。
3. `AgentExecutionService` 有 **Buffered / Streaming 两条并行路径**（`MaxSameToolRepeat` 在 `Buffered.cs:1172` 与 `:1929` 各一份），接线必须双路径覆盖。
4. **S3 的基线含尖峰窗口自身**（按设计字面「前两窗均值」）。因此连续两窗尖峰只在频率**继续上升**时成立；等幅稳态高频在数学上不可能触发（`R > 2.5(B+R)` 无解）。若将来希望稳态高频也触发，需改为「排除已判尖峰的窗口」—— 属设计变更。
5. **`HitCount` 在 S3 时记 0**（无样本 hash 可比）。接入方若要用它做报表，需另开 events/min 字段。
