# 子代理委派配置的读写出口（需求 3 前置）

## 为什么先做这一层，而不是先写界面

需求 4/5/6 的四个开关（`MaxDepth` / `MaxConcurrentSubAgents` / `AllowModelSelection` /
`DefaultModelRoute`）此前只能手改 `D:\Data\config\system.json`，前端完全读不到。
先写界面等于让前端去猜一个它看不见的后端文件。

所以本次只做服务端出口：`GET` / `PUT /api/admin/sub-agent-delegation`。

## 关键判断：这个改动不需要重启

三条证据拼起来才成立：

1. `system.json` 以 `AddJsonFile(..., reloadOnChange: true)` 接入配置链（`PuddingApplicationHost.cs:70`）；
2. 四个键由 `SubAgentTool` 在**每次派发时**实时 `IConfiguration[key]` 读取，不缓存、不 `IOptions` 快照；
3. 实测：新建带 `reloadOnChange: true` 的配置根 → 写入文件 → **260 ms 后**读到新值（`WrittenValue_IsObservedByAReloadOnChangeConfigurationRoot`）。

⇒ 界面不应提示「重启后生效」。这与 `llm.providers.json`（启动时一次性加载、改了必须重启）是两套语义，不能混用。

**但重载是异步的**：PUT 的响应体返回的是「已落盘的目标值」；紧接着的 GET 可能仍读到最后一次重载前的快照
（第一版测试就是在这里红了一次）。界面应以 PUT 响应为准，不要写完立刻回读再断言「没生效」。

## 设计要点

- **不改契约**：四个键与 `SubAgentTool` 逐字一致，没有新增配置项。
- **部分更新**：请求体为 null 的字段保持原样；`defaultModelRoute` 传空串表示删除该键。
- **只动目标段**：用 `JsonNode` 局部改 `SubAgentDelegation`，其余键（含 `{{vault:...}}` 占位符）原样保留。
- **原子替换**：先写 `.tmp` 再 `File.Move(overwrite)`；`reloadOnChange` 的 watcher 会短暂持句柄，
  Windows 下偶发 sharing violation，因此带 4 次重试。半截 JSON 会让整条配置链回退到旧快照，
  症状是「改了没生效且没有任何错误」——这是必须避免的失败模式。
- **写入口做联动校验**：`AllowModelSelection=false` 而 `DefaultModelRoute` 为空时，
  `SubAgentTool.ResolveChildLlmRouteAsync` 会在派发时抛异常，表现为「所有子代理都起不来」。
  这是配置可以单独写坏、但只有运行到才暴露的组合，因此在写入口 fail closed（400，一个字节都不写）。
- **来源标记**：快照里每个字段带 `*FromConfigFile`，用来区分「文件里没写、取的是代码默认」
  和「文件里写了这个值」。两者在界面上不能长得一样，否则用户无从判断自己改过没有。

## 验证

| 项 | 结果 |
|---|---|
| 构建 | 0 警告 0 错误 |
| 新增用例 | 5/5 通过 |
| 变异（忽略既有文件内容） | 失败 1 / 通过 0，报错点为「`environment` 键被抹掉」 |
| 复原 | SHA-256 与变异前比特一致 `B0B7B45C…A7F0F`，`MUTATION` 残留 0 处 |
| 复原后重跑 | 5/5 通过 |

用例覆盖：校验矩阵（含联动约束）、无关键保留、校验失败不落盘、`reloadOnChange` 取真、HTTP 端到端（GET 默认 → PUT → GET 新值 → 非法值 400 且状态不变）。

## 遗留

- **尚未部署**：`SubAgentDelegationSettingsStore` 与控制器只在源码里，需重启 Core 才可调用。
- 需求 3 的三个界面（子代理指示器 / 团队管理 / 配置界面）仍依赖持久子代理的
  `名称 / 备注 / 用途` 字段，`session_sub_agents` 表里还没有。
