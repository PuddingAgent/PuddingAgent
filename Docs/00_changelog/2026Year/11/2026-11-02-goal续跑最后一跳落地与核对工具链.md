# 2026-11-02 goal 续跑最后一跳落地

## 动机

11-01 结束时，goal 模式线有 13 个纯逻辑组件、113 条测试，但**没有一处能在执行循环里改变控制流** —— 决策再准也只能记日志。这一天要做的是把它接上，并且让人能自己核对它是否接上。

## 改动

### 主干接线（`2ebaf2c`）

在 `AgentExecutionService.Buffered.cs` 的 `CompletionVerdict.Completed` 分支、`break` 之前插入一次判定：

```csharp
if (GoalContinuationGate.TryContinue(request.SessionId, round, out var goalRound))
{
    stopReason = AgentLoopStopReason.Done;
    execState  = AgentExecutionState.Running;
    continue;   // 不 break，再来一轮
}
```

三重条件缺一不可：开关 `PUDDING_GOAL_CONTINUE=1` + 目标 active/armed + 账本可准入。准入走 `TryReserve` → `TryAdmit` 两步，**真的消耗一次额度**，不绕开既有 `maxRounds`。

### 只覆盖 Buffered，Streaming 未接（`698bf66`）

核对后确认两条路径结构不同：Buffered 有循环内裁决点，Streaming 的完成在流结束处（约 1998–2005），要续跑需**重新发起一轮流式执行**，属于新增控制流而非一处 `continue`。强行改会把接线变成两条路径的重新设计。

### 删除未接线队列（`055b9ee`）

`GoalContinuationQueue` 从没有生产路径入队 —— 留着就是「看起来有跨轮次能力、其实没人调用」的空壳。删除 174 行（实现 + 7 条测试），同步 code_map 与方案文档。

### 核对工具链（`de63d42` → `d5d3ba7` → `a7345a7`）

`TestScripts/verify-goal-continuation.ps1`：一条命令输出「进程/DLL 新鲜度 + User env 四值 + 最新 live 日志的决策行计数」。

**判定器两次假阳性，都出在同一类错误上 —— 把「提到这个词」当成「产生了这个词」**：

1. 裸 `[GoalLoop]` 命中了自己 `sleep` 的 work_summary（其中写着「日志 0 条」）；
2. 改成前缀匹配后，下一轮的 work_summary 又**用那句话描述了这次修复**，于是命中转述（自指）。

最终改为要求三个标记同现，并做阳性对照：真实格式行 → True，两次误报样本 → False。

### 接线测试（`c8ffac4`）

新增 `GoalContinuationWiringTests` 4 条。三个组件各自有测试，但「它们是否共享同一个注册表」只有串起来才暴露；若不共享，env 生效了也照样不续跑，且日志里看不出原因。

其中一条钉死了一个我记错的事实：**`MaxRounds=2` 实际放行 2 次续跑**，不是「最多多跑 1 轮」。

## 未做

## 教训

1. **「不归本次改动引入」≠「不是缺陷」** —— 前者用 stash 对照就够，后者必须查根因。本日正是因为多查了一层，才发现 Python 索引长期失效（解释器候选只有商店占位符）。
2. **判定器本身要先自证不会说谎** —— 能取红的校验才算校验；阳性对照不是可选项。
3. **变异必须「先备份后变异」**，位级一致用 git blob hash 判断（文件 SHA 受 `core.autocrlf` 的 CRLF 归一化影响，会误报）。
4. **顺序依赖只能靠注释守住** —— 用户插话优先于 goal 续跑，靠的是 `TryInjectSteeringMessageAsync` 排在 gate 之前；一旦重排，所有测试仍全绿。
