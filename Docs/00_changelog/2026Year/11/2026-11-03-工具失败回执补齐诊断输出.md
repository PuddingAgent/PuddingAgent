# 2026-11-03 工具失败回执补齐诊断输出

## 缺陷

工具失败时，进入模型上下文的是：

```
❌ Tool 'search_grep' FAILED (exit=1)
   Error: exit code 1
   💡 Suggestion: Check the tool's parameter constraints. ...
```

`Error` 只有退出码，`Suggestion` 是通用话术，**真正的失败原因（stdout/stderr）没有被回传**。

对照：`HostShellExecutor` 已经执行 `MergeOutput(stdout, stderr)` 并把结果放进
`HostShellResult.Output`，也就是说内容在，只是没被使用——失败态比成功态少给信息，
而失败态恰恰更需要诊断信息。

## 代价

调用方为了看到原因，只能重跑一次命令并重定向到文件。这付两次钱：
第一次的会话上下文已被污染且不可回收，第二次的执行还有副作用风险
（脚本可能已经写了一半文件）。本会话中该模式反复出现。

## 修复

- `AppendFailureOutput(StringBuilder, string?)`：输出非空白时追加 `   Output:` 段；
  空输出不产出任何内容，避免给回执加噪声行。
- `BuildFailurePayloadWithoutFuse(string, SkillResult)`：抽出旧执行路径的失败回执，
  与 `BuildToolFailurePayload` 共享头三行，避免两条路径的失败信息再次分叉。
- 两条调用链（流式 / buffered）都在 `ToolResultContextPolicy.MaterializeAsync` 之后
  才进入历史，因此超大输出仍受既有 8 KiB / 终端 2 KiB 预算与落盘约束，本改动不放宽边界。

## 验证

```
基线与修复后：ToolFailurePayloadTests 4/4 通过
变异一（删除回执里的输出追加）      → 失败 1 / 通过 3
变异二（去掉空输出守卫）            → 失败 2 / 通过 2
还原（SHA 592F7DFD…DAEFFF92 位级一致）→ Rebuild 后 4/4 复绿
```

两次变异的红色集合不同，说明「输出确实出现」与「空输出不产出噪声」是两条独立断言。
