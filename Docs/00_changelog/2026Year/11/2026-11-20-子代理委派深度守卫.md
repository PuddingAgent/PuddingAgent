# 子代理委派深度守卫（需求 4）

## 背景：三个「写了但没生效」的地方

用户 2026-11-20 需求清单第 4 条要求「最大递归深度 = 1，仅允许主 Agent 创建子智能体」。
排查后发现三个参数都在，但**没有一个真正拦住任何东西**：

| 参数 | 实际行为 |
|---|---|
| `max_depth` | 只在任务规划路径生效。`SubAgentTool.CheckTaskPlanningPolicyAsync` 开头即 `if (!planning.HasTaskContext) return null;`，普通子代理不做任何深度检查。 |
| `allow_sub_delegation` | 全链路零执行点。从请求读入 → 写入子代理上下文 → 再写回孙代理，**没有任何一处据此拒绝**。 |
| `DelegationDepth` | 全来自模型传参。`SubAgentInvocationService` 原样透传 `request.DelegationDepth`，平台不注入 ⇒ 模型传 `depth=0` 即可绕过。 |

当天清理的 `sub_agent_runs` 里有一条嵌套到 5 层的历史运行记录，是这个缺口的现场证据。

## 为什么不能「加个参数检查」

前两个参数由模型提供，第三个参数也由模型提供。任何基于它们写出的判断，
都可以被同一模型用另一个入参绕过。守卫必须基于**平台自己记录的事实**。

## 实现：用会话归属做判据

平台在创建子代理运行时，一定会往 `sub_agent_runs` 写一行，`sub_session_id` 就是子代理自己的会话。
于是「当前 Agent 是不是子代理」等价于「当前会话是否作为 `sub_session_id` 出现过」。

- `ISubAgentRunStore.HasSubAgentAncestryAsync(sessionId)`
  —— 新增。**不限运行终态**：跑完一次不消除「曾被 spawn」这一事实，
  否则子代理完成任务后守卫就对它失效。
- `FileSubAgentRunStore` —— `AnyAsync(e => e.SubSessionId == key)`。
- `SubAgentTool.CheckDelegationDepthAsync` —— 调用点位于 `cancel` / `logs` 分支之后、
  所有创建路径（sync / async / pool / batch）之前。管理操作不受影响，只有创建被拦。
- 配置 `SubAgentDelegation:MaxDepth`，默认 **1**；`<= 0` 表示不限制（运维逃生口）。

## 失败模式选择

`ISubAgentRunStore` 未注册、或查询抛异常时，守卫 **fail-open 并记 Warning**。
理由：这是防误用而非安全边界，基础设施故障不应把整条派发能力掐断。
代价是这种情况下守卫静默失效——因此 Warning 是本条唯一的可观测线索，不可删除。

## 已知限制

- 只支持 `MaxDepth = 1`。配置大于 1 时守卫仍按「子代理不得再派发」执行，
  多层递归需要真实深度链，留待第二期（见 `Docs/07_architecture/持久子代理与团队协作规划-2026-11-20.md`）。
- 未覆盖需求 5（并行数量上限）与需求 6（子代理模型选择开关）。
