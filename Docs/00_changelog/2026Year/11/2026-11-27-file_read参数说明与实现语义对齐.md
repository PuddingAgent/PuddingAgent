# file_read 参数说明与实现语义对齐

## 现象

`6fb2f17` 把 `limit_lines` 单独传入的语义实现成了「从首行起前 N 行」，并补了 5 条用例。
但 `FileReadArgs` 上的 `[ToolParam]` 文案没跟上：

- `LimitLines` 仍写「Maximum lines to read. **Use with OffsetLines** for arbitrary window.」
- `OffsetLines` 仍写「0-based line offset to start reading from. **Use with LimitLines**.」

两句合起来等于告诉调用方「这两个参数必须成对」。模型读的是 schema 而不是我的提交说明，
于是新语义在契约层完全不可见——它会继续按「必须给 offset」的方式调用，或者干脆不用 `limit_lines`。

同块的 `LimitLines` 那行还是 8 空格缩进（块内其余为 4 空格）。

## 依据

- 全仓 `Source/` 内 `Use with OffsetLines|Maximum lines to read` 只有一处命中：`FileTools.cs:710`，
  即这两个说明没有任何别处的副本需要同步。
- 既有测试没有一条断言参数说明文本，所以文案漂移不会被任何用例发现。

## 改法

```
LimitLines:  Maximum lines to read. Alone it reads the first N lines; with OffsetLines it reads N lines from that offset.
OffsetLines: 0-based line offset to start reading from. Without LimitLines the read continues to the end of the file.
```

只改说明与缩进，不动参数解析与窗口计算逻辑：`FileTools.cs` 57482 → 57562 字节，CRLF=1075、BARE_LF=0、无 BOM（逐字节回写，未整文重排）。

## 取红

新增两条用例，分别守两句话——刻意拆成两个方法，好让两个变异各打红一条、互不代偿：

| 变异 | 结果 | 红点 |
|---|---|---|
| 基线 | 52/52 | —— |
| M1 `LimitLines` 说明改回 `Use with OffsetLines for arbitrary window.` | 1 红 / 51 绿 | `LimitLinesDescription_DocumentsStandaloneFirstLines`（`StringAssert.Contains` 缺 `first N lines`） |
| M2 `OffsetLines` 说明改回 `Use with LimitLines.` | 1 红 / 51 绿 | `OffsetLinesDescription_DoesNotImplyMandatoryPairing`（`Assert.IsFalse`：仍暗示必须成对） |
| 复原 | 52/52 | SHA `B0F17CDA…DA8` 与基线逐字节相同、变异残留 0、`-t:Rebuild` |

M1 下 M2 的用例保持绿、M2 下 M1 的用例保持绿，说明两条断言各自独立生效；
若把两句写进同一个测试方法，任一变异都会让同一个方法变红，就分不清是哪句失守了。

## 局限

- 这两条是**文案测试**：它们只能防「说明被改回去」，不能证明说明与实现的语义真的等价。
  语义由 `6fb2f17` 的行为用例与运行时六探针保证，不是这两条。
- 没有验证参数说明在 LLM 端实际呈现的形态（schema 序列化后的字符串未取样）。
- 没有第三方副本需要同步这一点，是靠一次全仓 `search_grep` 得出的；`search_grep` 在该次调用里报了
  `coverage: partial`（文件枚举达 2000 上限），所以严格说：「在已扫描范围内只有一处」。
  后续若新增 schema 快照文件，需要重新核一遍。
