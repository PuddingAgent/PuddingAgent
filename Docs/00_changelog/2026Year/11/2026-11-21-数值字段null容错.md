# 数值字段 null 容错（中断-run 恢复不再整轮失败）

- 日期：2026-11-21
- 提交：`c3e9a27`
- 范围：`PuddingCore/SubAgents/SubAgentLatencyAggregator.cs` 及其两个测试文件

## 现象

每次 Core 启动都会记一条 `[SubAgentProjection] Interrupted-run recovery failed`：

```
System.InvalidOperationException: The requested operation requires an element
of type 'Number', but the target element has type 'Null'.
```

全量扫描 `D:\Data\logs\system`（200 份日志）：该短语共出现 12 次，最早 **11-18 20:09**，此后每次启动一次。`sub_agent_runs` 里 `interrupted` 状态累积到 76 条。

## 根因

真实 run 的归档事件里存在 null 数值字段：

```
D:\Data\workspaces\default\agents\<id>\runs\run_20261118_104805_451006a28e5a\events.jsonl:7
D:\Data\workspaces\default\agents\<id>\runs\run_20261118_110150_a6c9583bfc21\events.jsonl:7
  eventType=subagent.llm.completed  payload.cache_hit_tokens = null
```

（扫描 225 份 jsonl，仅此 2 处 null 数值。）

聚合器读它时用的是 `JsonElement.TryGetInt64`。**这个方法对 null 元素不返回 false**，而是在内部经 `JsonDocument.TryGetValue` 走到 `ThrowJsonElementWrongTypeException` 抛 `InvalidOperationException`。方法名里的 `Try` 具有误导性。

`AddEventLine` 只 `catch (JsonException)`，`InvalidOperationException` 直接穿出去，被 `FileSubAgentRunStore.RecoverInterruptedRunsAsync` 的外层捕获 —— **一条坏行让整轮恢复中止**，后续 run 全部得不到终态。

## 改动

- 新增 `TryReadLong`：先判 `ValueKind == Number` 再取数，缺失 / null / 非数字一律按 0
- `ReadLong` 与 `ReadDurationMs`（payload 内与根级旧格式两处）统一走它
- `SubAgentLatencyAggregatorRealRunTests` 里那份**独立 oracle 有同一缺陷**，一并修
- 新增不依赖环境变量的回归 `Aggregator_TreatsNullNumericPayloadAsZero`

## 证据

| 步骤 | 结果 |
|---|---|
| 修复前，环境门控真实数据用例指向含 null 的 events.jsonl | **红**，异常与生产逐字一致 |
| 修复后同一用例 + 同族用例 | **9/9 绿** |
| 变异：删掉 `ValueKind` 守卫 | **失败 2 / 通过 7**，命中的正是真实用例与新回归 |
| 复原 | SHA-256 `A4927FA7…92C9C` 比特一致，残留 `MUTATION` 标记 0 |
| 复原后重跑 | 9/9 绿 |

## 遗留

1. **日志里的方法名对不上代码**：生产日志的栈帧写的是
   `SubAgentLatencyAggregator.ExtractTokens`，而该名字**从未存在于仓库历史**
   （`git log -S` 零命中），部署目录里所有 `Pudding*.dll` 与 PDB 也都搜不到该字符串
   （正对照 `AccumulateTokens` 命中 1）。
   行号 77 → 151 却与当前源码完全吻合（`AddEventLine` → `AccumulateTokens`）。
   本次修复未依赖该名字，故不阻塞；但**下次读这类日志时要留意方法名可能不可信**。
2. 76 条 `interrupted` 记录要等下次启动恢复才能转为终态，本轮未做数据订正。
3. `AddEventLine` 目前只 catch `JsonException`；是否要扩到 `InvalidOperationException`
   属于防御性加固，本次未改（真正的问题已在源头修掉）。
