# 2026-11-27 file_read 续读位置只按实际交付算

`FileReadTool` 的续读提示此前只保证「给了一个数字」，不保证这个数字能用。三处先后被实调取证：

| # | 入参 | 旧回执 | 后果 |
|---|------|--------|------|
| A | 40 行文件 `max_chars=10` | `continue with OffsetLines=0` | 起点就是 0；照做得到**逐字相同**的回执，自我循环 |
| B | 单行 20000 字节文件 + `max_chars=20000` | 无任何截断提示 | 正文只交付 7680 字节，12320 字节静默丢失 |
| C | 首行 20000 字节 + 后续 19 行 | `continue from line 2` | 行偏移跳不进一行中间，首行剩余 12320 字节永不交付 |

A 与 C 是两次真实调用（`temp/probe_fr_small_1127.txt`、`temp/probe_fr_longline_1127.txt`），B 是读源码时发现的同源分支：`truncated = emittedLines < lines.Length` 在单行文件上恒为假。

## 修法

一条判据：**续读位置只能描述已经交付的内容**。

- `TakeLinesWithinByteBudget` 增加 `out bool firstLineTruncated`，把「首行只剩前缀」这件事暴露给调用方。
- `BoundInlineBody` 改为返回 `record struct BoundedInlineBody(Body, EmittedLines, Truncated, FirstLineTruncated)`；`truncated` 改为 `firstLineTruncated || emittedLines < lines.Length`，并为首行被切单独出一条不提偏移的文案。
- `DescribeMaxCharsTruncation` 在「零完整行交付」时不再给偏移，直接说明该改预算。
- 两个调用点把 `deliveredLines` 传成 `FirstLineTruncated ? 0 : EmittedLines`——被切成半行不算交付。

## 取红

三个变异各打红一条，且红点不同：

| 变异 | 结果 |
|------|------|
| M1 去掉 `truncated` 里的 `firstLineTruncated` | 33 例 1 红：`SingleLineLongerThanInlineBudget_AnnouncesTruncation` |
| M2 恒用带偏移的旧尾串 | 1 红：`LongFirstLine_DoesNotAdviseOffsetPastUndeliveredRemainder` |
| M3 去掉零完整行分支 | 1 红：`MaxChars_ShorterThanFirstLine_DoesNotAdviseNonAdvancingOffset` |

每轮变异从同一份基线改写，恢复后逐字节相同（CRLF 982 / 无 bare LF），`-t:Rebuild` 后 33/33。

## 未验证

- 没有在生产流量里见到 B/C 两种形态的证据，只有构造样本与源码判读。
- 「一行到底该多长才算异常」没有定论——本轮只保证回执不说假话，不改交付量。
