# 子代理委派配置界面（需求 3 配置页）

## 落点

`/system-config/subagent-delegation` → `src/pages/subagent-team/index.tsx`。

**没有复用 `/system-config/team-management`**：那个页面管的是用户与团队 RBAC（成员、工作区权限），
与「子代理委派开关」不是同一回事。同名不同义的两个东西塞进一个页面，后面必然互相干扰。

## 页面承担的四个开关

| 控件 | 键 | 语义 |
|---|---|---|
| 最大递归深度 | `SubAgentDelegation:MaxDepth` | 1 = 仅主 Agent 可创建；0 = 不限制 |
| 并发上限 | `SubAgentDelegation:MaxConcurrentSubAgents` | 同一主 Agent 下所有层级存活总数；0 = 不限制 |
| 允许选择模型 | `SubAgentDelegation:AllowModelSelection` | 关闭后忽略 Agent 传的 model |
| 默认模型路由 | `SubAgentDelegation:DefaultModelRoute` | 选择关闭时使用；空 = 清除该键 |

## 三处刻意的设计

**① 每项都标来源。** 每个 Card 右侧有「来自配置文件」/「代码默认」标签。
两种状态在视觉上必须不同，否则用户无从判断自己到底改过没有——这与检查器里
`–` 既可能是「没取到」也可能是「确实没有」是同一类问题。

**② 前端也做联动校验。** 关闭模型选择而未填默认路由时，表单项直接拒绝提交。
后端已经 fail closed（400），前端再挡一次是为了在**提交前**说清原因，
而不是等用户点保存再吃一个错误。

**③ 保存后不回读 GET。** 配置重载是异步的，PUT 之后立刻 GET 可能仍是旧快照。
页面一律用 PUT 的响应体更新本地状态，避免把「已保存」误报成「没生效」。

页面上明确写着「保存后不需要重启」——这是实测结论（`system.json` 为
`reloadOnChange: true`，且 `SubAgentTool` 每次派发实时读配置），不是推测。
