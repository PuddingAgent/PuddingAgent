# 2026-11-27 file_read 小预算下的建议与首行超预算判定一致

## 现象（运行时取证）

文件：119100 字节 / 100 行，首行 20000 字节，其余 99 行各 1001 字节。

| 入参 | 回执末尾 |
|---|---|
| `max_chars=3000`（**小于**首行） | `... no complete line fits in that budget ... Raise max_chars to at least the length of one line.` |
| `max_chars=20000`（等于首行） | `... the first line of this window alone exceeds the 7680-byte inline budget: no max_chars value can deliver it ...` |

同一份文件、同一个函数，只因请求的预算不同就给出方向相反的两种建议。照第一行做（把 3000 提到 20001）会得到第二行的结论——**建议本身可以照做，但照做之后才发现它指不到可达状态**，白费一次往返。

## 根因

`DescribeMaxCharsTruncation` 的「预算比首行短」分支要靠 `firstLineTruncated` 判真假，而两处调用点只在**第二次**调用（`BoundInlineBody` 之后的重算）才把该标志传进去；第一次调用用的是默认值 `false`。

关键在判据的取样时点：`MaxChars` 先切片，`WindowFirstLineExceedsInlineBudget` 若取自切片后的内容，首行已被切短到 ≤ 预算，于是「首行超预算」为假——但它**底层那一行**并没有变短。实测 20001 字节首行被切成 3000 字节后，切片后的首行确实不超预算，而原始首行永远超。

## 改法

新增 `WindowFirstLineExceedsInlineBudget(string windowContent)`，判据与 `TakeLinesWithinByteBudget` 完全一致（首行 UTF-8 字节数 > `InlineBudgetBytes`）。两处调用点在**切片前**求值并传入第一次调用：

```csharp
var firstLineOverBudget = WindowFirstLineExceedsInlineBudget(content);   // 切片前
content = content[..args.MaxChars.Value];
maxCharsNotice = DescribeMaxCharsTruncation(
    args.MaxChars.Value, windowStart, content, totalChars, totalLines,
    firstLineTruncated: firstLineOverBudget);
```

第二次调用保持原样——它用 `BoundInlineBody` 的实测结果重算，两者在可达区间内一致：切片长度 ≤ 7680 时不会截断（不触发重算），> 7680 时 `FirstLineTruncated` 必为真。

## 取红（两次变异，红点不相交）

| 变异 | 结果 | 红点 |
|---|---|---|
| M1 小文件调用点传 `false` | 41 例中 **1 红 / 40 绿** | `MaxChars_BelowFirstLine_WithFirstLineOverBudget_SaysNoBudgetCanDeliver` |
| M2 大文件调用点传 `false` | 41 例中 **1 红 / 40 绿** | `MaxChars_BelowFirstLine_OnLargeFilePath_SaysNoBudgetCanDeliver` |

两条红点互为镜像（只修一处时另一处保持绿），变异后的失败消息逐字复现了旧文案：

- M1：`[META: size=20030 chars / 20033 bytes, lines=6]` … `Raise max_chars to at least the length of one line.`
- M2：`[META: size=111503 bytes, lines=1501]` … 同一句

正向对照 `MaxChars_ShorterThanFirstLine_DoesNotAdviseNonAdvancingOffset`（6 行文件、`max_chars=5`、首行 17 字节）两轮变异全程绿——它守的是「首行不超预算、只是预算不够」那一支，本轮没有偷走它的职责。

每轮变异前从修复后的基线复制，锚点断言 `count=1`；`finally` 复原后 `SHA C73DBC7523E207F3…` 逐字节相同，`dotnet build -t:Rebuild` 后 41/41。

## 局限

- 只断言「不再劝提预算」与「给出新结论」，不校验原因分支的分子；分派正确性靠 M1/M2 守住。
- 运行时取样只用 ASCII（1 字符 = 1 字节）；CJK 下字节 > 字符，绑定会更早发生，逻辑相同但未取样。
- 结论仍不告诉调用方「怎么取回那一行」——本工具确实没有「行内偏移」参数，给假方案比不给更糟。

## 关系

延续同一条不变量：**回执给出的下一步必须真的可达**。上一轮修的是「首行超预算时不再劝提预算」，本轮修的是「同一个结论不能因为请求的预算不同而翻面」——判据的取样时点一旦错位，建议就会在两次调用之间自相矛盾。
