# 子代理终态写入不再依赖进程内存

## 问题

2026-11-20 实测：`sub_agent_runs` 有 2 条运行卡在 `running` 达 46 小时，`session_sub_agents` 另有 10 条卡了 4 个月（最早 2026-07-23）。两者都是无产物的路由探针。

## 根因

`SubAgentManager` 有五处终结路径（异步完成、异常失败、同步失败、同步成功、取消）都用同一形态：

```csharp
if (_runIdMap.TryRemove(subSessionId, out var runId))
    await _runStore.CompleteRunAsync(runId, ...);   // 只有内存命中才写库
```

`_runIdMap` 是进程内存字典，只保存**本进程创建**的运行。进程重启后它为空，`TryRemove` 返回 `false`，写库被跳过，运行永远停在 `running`。

同时 `session_sub_agents` 从未纳入重启对账（`sub_agent_runs` 有 `RecoverInterruptedRunsAsync`，它没有），因此无人纠正。

## 改动

- `ISubAgentRunStore` 新增 `FindRunningRunIdAsync(subSessionId)`：按子会话查非终态运行。注释写明它只服务终结路径的回落，且返回 null 表示无可终结运行。
- `FileSubAgentRunStore` 实现该方法（EF 查询，与 `GetRunningCountByParentTurnAsync` 同口径）。
- `SubAgentManager` 新增 `TakeRunIdAndRevokeAsync`：内存命中则立即撤权并返回；未命中则回落查账本，查到也撤权。查询失败记 warning 并降级为「无可终结」，不阻断取消/失败处理。
- 五处终结路径改为调用该方法。

**取 runId 与撤权被刻意绑在一起**：仓库有一条源码不变量守卫（`SubAgentManagerRevokeCoverageGuardTests`）要求每个 `_runIdMap.TryRemove` 后 6 行内出现撤权调用。第一版把两者拆成两个调用点，守卫立刻取红——守卫是对的，拆开就意味着将来任何新终结路径都可能只做前者、漏掉后者（R4 授权泄漏缺陷的原始形态）。

## 验证与限制

- `PuddingPlatform` 构建 0 错误（56 个既有 warning）。
- 新增用例 `FileSubAgentRunStoreTests.FindRunningRunIdAsync_ReturnsOnlyNonTerminalRunOfThatSubSession`：运行中可命中、终态后不命中、空/空白/不存在返回 null。
- 变异：去掉非终态过滤 → 该用例 1 失败 / 0 通过；复原后文件 SHA-256 比特一致（`B456856D…37BAD24`）。
- 全量 `PuddingPlatformTests`：2012 总计 / 2011 通过 / **0 失败** / 1 跳过。
- 过程中曾引入一次回归：`EveryTerminalRunRemovalAlsoRevokesTheBrowserDelegation` 报 `unpaired.Count=1`，即上面那处拆开；已按守卫要求改为原子操作。

**未覆盖**：本组测试守住「回落查询正确」与「撤权配对」，但未端到端验证「重启后取消一个跨进程遗留的运行，两张表同时到终态」。该判据需要构造跨进程场景，留到第一期后续（启动对账扩展与池条目落库）一并验收。

另外本轮只清了数据（13 行 stale running），未部署；运行中的 Core 仍是旧产物。
