# 子代理并发上限与模型选择开关（需求 5 / 6）

## 需求 5：同一主 Agent 下所有递归层级的存活总数

用户口径是「同一主 Agent 下，**所有递归层级**同时存活的子智能体总数，主 Agent 不计入」。
平台原先只有会话粒度的 `GetRunningSubAgentCountAsync`，它只数**直接**子代理。

新增 `ISessionStateManager.GetRunningSubAgentDescendantCountAsync(rootSessionId)`：

- 从根会话出发逐层下钻（`ParentSessionId` → `SubSessionId`），只数 `running`；
- 深度上限 8：既是防环，也是防止脏数据把一次查询拖成 N 次；
- 用 `visited` 集合去重，同一会话被重复引用时不会双计。

**为什么不用递归 CTE**：委派层数本来就很浅，而递归 CTE 在 EF Core 里只能走裸 SQL，
会多出一段与实体不同源、需要单独维护的 schema。

既有方法刻意保持不变：它和新方法的口径差异正是测试里的对照组
（同一份数据：`descendants = 2`，`direct = 1`）。

配置：`SubAgentDelegation:MaxConcurrentSubAgents`，默认 **0 = 不限制**。
默认不限制是为了不改动既有行为；需要上限时显式配正数。

## 需求 6：是否允许 Agent 为子代理选模型

配置 `SubAgentDelegation:AllowModelSelection`，默认 `true`。
关闭后在 `ResolveChildLlmRouteAsync` 内忽略模型传参（**包括 fallback 路由**），
改用 `SubAgentDelegation:DefaultModelRoute`。

### 一个不能想当然的地方

最初的设计是「关闭时把 modelId 传 null，让解析器用平台默认」。
读 `ILlmResolver` 的契约后否掉了：

> modelRoute 与 requiredCapabilityTags 同时提供时…两者均为空时**拒绝解析，不存在平台默认路由**。

也就是说空路由是**明确拒绝**而不是降级到某个默认模型。所以必须把目标路由显式读出来。
未配置 `DefaultModelRoute` 时抛明确异常，而不是静默挑一个——静默挑模型会让
配置错误变成难查的行为差异。

## 失败模式

两个守卫在依赖服务（`ISubAgentRunStore` / `ISessionStateManager`）未注册或查询异常时
**fail-open + Warning**。理由与需求 4 一致：这类守卫防的是误用而非越权，
基础设施故障不应掐断整条派发能力。代价是这种情况下守卫静默失效，
因此 Warning 是唯一可观测线索，不可删除。

## 已知限制

- 需求 6 目前只支持「配置的默认模型」这一分支；「继承父 Agent 的模型」未实现——
  工具层拿不到父级的 `LlmInvocationProfile`（`LlmProfile` 当前由子路由自身生成）。
- 并发上限按「会话树」计，未按 workspace 或全局计。
- 两个新增配置项都尚未接入界面（需求 3 的团队配置界面）。
