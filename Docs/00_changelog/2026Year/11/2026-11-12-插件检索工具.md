# 插件检索工具 plugin_search

## 为什么

仓库已有注册与内容寻址（`PluginPackageStore` 落 `{id}/{version}/{hash}`），但只能全量列举：`plugin_catalog` 返回的是「全部包 + 当前激活」的一大坨。想把插件用起来，缺的是一步「按关键字找」。

## 做什么

`plugin_search(query?, limit?)`：

- 对 `id`、`version`、`name`、`description`、`requestedCapabilities` 做大小写不敏感子串匹配
- 每条返回 `id/version/contentHash/status/name/description/capabilities/active`
- `active` 是**上下文状态**：true 表示该 `contentHash` 在本次 Agent 上下文中已挂载
- `matched` 恒为真实命中数，`returned` 受 `limit`（1..200，默认 20）约束
- 只读，不加载任何东西

## 三处注册，缺一不可

| 位置 | 为什么 |
| --- | --- |
| `PuddingToolServiceCollectionExtensions` | 工具存在 |
| `HostToolContributions.Kernel` | 发现类工具不能依赖「先挂载某个包」，否则鸡生蛋 |
| `ToolExposurePlanner.CoreToolIds` | 不能被曝光预算淘汰，否则检索能力会自己消失 |

## 验证

测试用真实 ZIP 走 `ImportAsync` 建仓库（非伪造目录），覆盖五条断言：描述命中、能力命中、空查询列全、`limit` 生效但 `matched` 不变、无命中返回 0。

变异取红：把匹配函数首个判断改成恒 `true`，按描述检索得 2 条（期望 1）失败；复原并 `-t:Rebuild` 后通过，源文件 SHA 位级一致。

## 过程中修掉的真缺陷

匿名对象写 `item.Id` 会以 **PascalCase** 落盘——`ToolResultMaterializer` 用默认序列化选项，不套 Web 命名策略。消费方按 `"id"` 取会 `KeyNotFoundException`。已改为显式 `id = item.Id`。

## 已知限制

- 检索是**线性扫描** `Scan()` 结果，未建索引；包量大时的耗时未测。
- 只支持子串匹配，没有分词、排序权重或 `--installed` 专用过滤（用 `active` 位自行筛）。
- 安装持久化未做：`active` 只反映当前进程的挂载，重启后归零。
