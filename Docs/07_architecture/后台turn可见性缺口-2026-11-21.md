# 后台 turn 可见性缺口（2026-11-21）

## 现象

子代理结果消息送达后，主代理开始处理（后台 Turn），但会话界面**没有任何运行指示**：看不到墨球、看不到「正在执行 X」，只能看到一条子代理消息之后一片静默。

前台 Turn（用户发消息触发）不受影响——用户消息所在气泡承载运行指示。

## 已验证的事实

### F1. 运行指示器只能挂在已有 assistant 消息上

`AgentMessageBubble.tsx:863`：

```tsx
{shouldShowRunMonitor && (
  <div className="agentRunMonitor">
    {turnStatus && <TurnStatus status={turnStatus} ... />}
```

`shouldShowRunMonitor = isRunActive`（`:555`），而整段位于消息气泡内部。没有消息 → 没有承载者。

### F2. 「没有持久消息也能渲染运行行」的机制已存在

`MessageList.tsx:1046` `mergeActiveRunIntoTurns`：当 `activeRun` 找不到可归并的历史 turn 时，直接 `return [...turns, activeTurn]`——**追加一条合成 turn**。

`getTurnProjection(turnId)`（`chatStateTypes.ts:198`）本身就是 **turn 维度**索引，不是消息维度。

结论：C 方案（把运行指示挂到 turn 上）**不需要新造数据通路**，已有投影与合成 turn 两件基础件。

### F3. 服务端确实会为后台 turn 产出 activeRun —— 原假设被推翻

我曾假设「后台 turn 不写 `chat_execution_commands`，所以服务端选不到根 turn」。**实测否证**：

```
chat_execution_commands 行数        = 658
turn.started 去重 turn_id 数        = 658        （一一对应）
turn.started 事件总数               = 682        （部分 turn 有重试/恢复的重复事件）
```

最近 5 条 command 的时间戳（epoch ms 换算）与消息到达时刻吻合：

| command turn_id | 时间 | 对应事件 |
|---|---|---|
| 4383bcf3… | 15:32:40 | 用户消息 |
| 9821afdd… | 15:27:53 | **心跳** |
| d108df6a… | 15:19:55 | 用户消息 |
| 7cf124f4… | 15:14:41 | **子代理结果 `subresult:675ec8ab`** |

⇒ 后台 turn **有** command 行、**有** `turn.started`。服务端 `AgentConversationProjectionService` 按「最新 command → 其 turn.started → 是否终态」选根 run，对后台 turn 同样成立。

### F4. 前端维护 live activeRun，但它是「瘦」的

`chatClientStore.ts:930 ensureActiveRun()` 在 `turn.started` 事件上就地构造 activeRun。构造体**只含**：

```
runId / workspaceId / ownerUserId / agentId / mainSessionId
status / statusText / summary / eventCursor
outputSnapshot.{markdown, processItems, window}
startedAt / updatedAt / completedAt
```

**不含** `userMessage`、**不含** `commandClientId`、**不含** `outputSnapshot.userMessage`。

而 `MessageList.tsx` 的 `createActiveRunTurn` / `mergeActiveRunIntoTurns` 会读：

- `:926` `activeTurn.userMessage`
- `:1002` `activeRun.userMessage.timestamp`

## 已否证的假设

### H1（否证，2026-11-21 15:38）「瘦 activeRun 缺 userMessage 导致抛错」

原假设：SSE 构造的 activeRun 不含 `userMessage`，合成 turn 读 `userMessage.timestamp` 会抛错 → 完全静默。

**否证证据**：`MessageList.tsx:425 createActiveRunTurn` 自己合成占位用户消息，**从不读取服务端 `userMessage`**：

```ts
turnId: activeRun.outputSnapshot.window?.turnId || activeRun.runId,
userMessage: {
  id: `${activeRun.runId}:active-user-placeholder`,
  text: '',
  timestamp,          // 来自 toTimestamp(activeRun.startedAt || activeRun.updatedAt)
  status: 'success',
},
```

⇒ 无 undefined 解引用，无抛错可能。`MessageList.tsx:1002` 读的 `activeRun.userMessage.timestamp` 也是这个本地占位对象。

**补充事实**：合成 turn 追加分支不需要服务端 `userMessage`：

```ts
if (activeRun.outputSnapshot.window?.turnId) return [...turns, activeTurn];
```

## 待证假设（按可检验性排序）

### H2（否证，2026-11-21 15:40）「后台 turn 的快照刷新被性能短路跳过」

原假设：若 `status.activeRunId` 只对前台 turn 设置，则 `chatClientStore.ts:566` 的短路条件（`!matchingStatus.activeRunId && !existingConv.activeRun`）会跳过刷新 → activeRun 长期为 null。

**否证证据**：`AgentRunProjectionService.cs:82` 构造 status 时取：

```csharp
status == "running" ? latestLifecycleEvent?.RunId : null,
```

而 `MapStatus`（`:174`）的判据是 **最新生命周期事件是否终态 + 是否 < 5 分钟**，与「前台/后台」无关：

```csharp
if (IsTerminalEvent(latestLifecycleEvent.Type)) return "idle";
...
if (DateTimeOffset.UtcNow - ParseOccurredAt(latestLifecycleEvent.OccurredAt) > ActiveRunStaleAfter)
    return "idle";
return "running";
```

后台 turn 的 `turn.started` 是非终态事件 ⇒ `MapStatus` 返回 `running` ⇒ `ActiveRunId` 正常给出 ⇒ 短路不成立。

**检验方式**：单测直接喂一个合成 turn（`outputSnapshot.window.turnId` 有值、无 `userMessage`），断言 `shouldShowRunMonitor` 为 true。

## 设计纪律

- **同一屏只允许一颗动画墨球**。若子代理浮坞也在跑，后台 turn 指示用静态状态点 + 行扫光，把墨球留给前台 turn（`TurnStatusOrb.tsx` §3.2 既有纪律）
- **不得伪造用户消息**。后台 turn 没有用户输入，界面不能凭空造一条 user 气泡
- **合成 turn 必须可识别**：刷新后若该 turn 已持久化，合成行须与真实行合并而非并存（`mergeActiveRunIntoTurns` 已有归并逻辑，不得绕过）

## 复现与验收

- 复现：派一个短子代理，在其结果到达后立即观察主会话界面（父代理正在跑长 turn 时最明显）
- 验收判据：子代理结果到达后的 N 秒内，界面必须出现**与结果消息关联**的运行指示；且该指示在 turn 终态后消失
- 反向判据：前台 turn 的指示行为不得改变（同屏仍只有一颗墨球）
