# 子代理结果通知与父代理唤醒：现状缺陷与优化规划

日期：2026-11-21 ｜ 状态：调查结论 + 待实施规划
关联：`子代理生命周期护栏-2026-11-21.md`、`子代理界面重复性调查与重构建议-2026-11-21.md`
代码锚点：`SubAgentManager.cs:858 NotifyParentAgentAsync`、同一文件 `:938 BuildSubAgentResultEnvelope`

## 一、用户诉求（2026-11-21 14:45）

> 子代理之后，通知你、唤醒你的协作的步骤也需要优化。系统架构、规划、调研。

截图实测：子代理完成/失败后，主对话里出现的气泡只有两行 ——
`Sub Agent 发来的消息` / `shell: exit code 1`。**没有任何可行动信息。**

## 二、通道现状（读码所得，非推测）

`NotifyParentAgentAsync` 把结果投递为一条 `MessageEnvelope`：

| 字段 | 值 |
|---|---|
| `ContentType` | `application/vnd.pudding.agent-context-envelope+json` |
| `intent` | `subagent_result` |
| `requires_response` | `true` |
| `Priority` | `Important` |
| `MessageId` | `SubAgentResultIdentity.Compute(runId, status, parentSession)` —— 幂等去重键 |

Metadata 里**应有尽有**：`parent_session` / `run_id` / `child_run_id` / `result_id` /
`contract` / `contract_satisfied` / `contract_missing` /
`tool_failure_count` / `tool_output_truncated_count` / `tool_output_chars` / `tool_failure_summary`。

**问题不在字段缺失，在可见正文的取值：**

```csharp
var deliveredResult = completed || resumable;
var contextText = deliveredResult
    ? reply ?? string.Empty        // 成功/可续跑 → 回复正文
    : error ?? "unknown error";    // 其余一切 → 只给错误串
```

## 三、三个结构性缺陷

### 缺陷 1：失败时把 `reply` 丢弃，父代理只看到一条错误串

`status` 不是 completed 也不是可续跑终态时，正文 = `error`。
而我们的子代理**经常**在交付完成后、最后一步工具报错（`read` 工具不存在、`search_grep` 传了文件路径、`shell` exit 1），
于是父代理看到的是 `shell: exit code 1`，看不到它其实改了 14 个文件、跑绿了 22 个用例。

**实测（本会话，全部可核）**：连续 4 个子代理报 `failed`，4 次产物都完整落盘 ——
`sub-c1031084`（检查器两处修复）、`sub-f1b3030c`（名字/头像/短 ID）、`sub-13c9773b`（paused 词表 9 文件）、
`sub-e0b08674`（11 条判据 22 用例）。父代理每次都必须去磁盘复核，**否则会把已完成的交付当失败重做**。

这不是"子代理不听话"，是**通道把「最后一步工具报错」等同于「任务失败」**。

### 缺陷 2：`work_outcome` 与 `terminal_error` 被压成一个 `status`

现在的 `status` 一个字段同时承担两件事：

- 工作有没有产出（delivered / partial / nothing）
- 运行时/工具有没有报错（error string / exit code）

两者**正交**。压成一个值的结果：要么把有交付的报成失败（缺陷 1），要么把失败的报成成功（更危险）。

### 缺陷 3：唤醒时没有「行动简报」，父代理必须先考古

父代理被唤醒后要做四件事：核 diff 面 → 跑测试 → 做变异 → 提交。
现在这些都得手工重建。而 metadata 里其实已有 `tool_failure_summary`、`contract_satisfied`，
只是**没有产物面**：改了哪些文件、增删行数、测试 summary、门禁结果、变异 SHA。

## 四、关键架构主张：交付面由**运行时采集**，不采信子代理自述

已多次实测证伪子代理自述：路径全错、序列与 `tools.jsonl` 不符、报 100/196 实际 DONE、
报 failed 但代码完整。所以「让子代理自己写 SUMMARY」不能作为验收依据。

**应采集的三类事实（全部可由运行时确定，无需模型配合）**：

| 事实 | 来源 | 为什么可信 |
|---|---|---|
| 改动面 | 子代理工作区前后 `git status --porcelain` + `git diff --numstat` 快照 | git 自己算的，与模型无关 |
| 工具面 | `tools.jsonl` 计数（总调用 / 失败 / 截断 / 输出字节） | 事件流记账，已有 `tool_failure_count` 等 |
| 门禁面 | 子代理若跑了测试，捕获其 `dotnet test` 的 summary 行 | 原始输出行，不解释 |

⚠️ 前提：子代理与父代理**共享同一文件工作区**（实测如此），所以前后快照差分是可行的。
若将来改成隔离 worktree，这条要重设计。

## 五、建议的信封结构（v2）

```
work_outcome : delivered | partial | nothing        ← 采集所得
terminal_error : { kind, message, last_tool }       ← 附带，不覆盖 work_outcome
deltas : { files_changed, insertions, deletions, files[] }
tools  : { calls, failed, truncated, output_chars }
gate   : { ran, summary_line, trx_path } | null
contract : { declared, satisfied, missing[] }        ← 已有，保留
next_action_hint : string                            ← 给父代理的建议（可选）
```

三条硬规则：

1. **可见正文不再只由 `status` 决定**：正文 = 交付事实摘要 + 失败原因（若有），两者都出现
2. **`reply` 永不被丢弃**：失败时正文 = `reply`（若有）+ `terminal_error`（若有）
3. **`requires_response` 保持 true，但不等价于"唤醒成功"**：唤醒可靠性单独保证（见 §6）

## 六、唤醒链：必须单独核实的部分

已知事实（本会话实测）：

- 子代理结果消息偶有 **2.4–2.6 分钟**延迟送达
- 心跳 `created_at` 可**滞后数小时**，且平台会**批量投递**
- 有回执是"被心跳捎带"进来的（同一轮收到多条 subagent_result）

⇒ **无法从消息时间戳判断唤醒是否及时**，必须现场核对。

待核实（这是本规划的调研项，不是结论）：

1. `subagent_result` 消息是否**主动唤醒**空闲父代理，还是等下一次心跳/用户输入才被消费？
2. 父代理处于 `running` 时收到结果，是排队还是打断？排队上限多少？
3. 已登记的平台缺陷（`lease_lost`、重启后需用户再发"继续"、父 Turn completed 而子仍 running）是否仍存在？

**判据**：造一个 sleep 30 分钟的子代理完成场景，记录「子代理终态时刻 → 父代理首次消费时刻」，差值即唤醒延迟。
没有这个数，任何"优化唤醒"都是猜。

## 七、分期

```
W0  信封 v2：work_outcome / terminal_error 解耦 + reply 不再丢弃 + 运行时采集交付面
W0  判据：构造"交付完成但最后工具报错"的用例 → 正文必须同时出现产物清单与错误
W1  唤醒延迟实测（§6 三问）→ 有数再定优化方向
W1  行动简报：唤醒后父代理首屏可见「改了什么/测试如何/下一步建议」
W2  协作闭环产品化：一键 "验证并提交"（核 diff → 跑测试 → 门禁 → commit）
```

**W0 必须先做**：它是 W2 的前置——没有可信的交付面，一键提交就是把不可信的东西自动化。

## 八、明确不做

1. **不采信子代理自述作为验收依据**（已被实测证伪多次）
2. **不把 `contract_satisfied=false` 判成失败**（现有注释已写明原因：任务书允许覆盖默认格式，误杀正确遵从的执行）
3. **不在没有唤醒延迟数据前改唤醒策略**——否则只是把"猜"换个地方
4. **不新增第二条通知通道**：`IMessageSystem` + `InternalEvent` 两条已足够，问题在内容与唤醒，不在通道数量
5. **不做自动重试**：失败自动重派会把「假失败」变成「真双份工作」

## 九、一个必须承认的边界

父代理（我）现在对「子代理报 failed」的处置纪律是：**先去磁盘核对，再决定是否重做**。
这条纪律在 W0 落地前**不能放松**，因为通道不可信。W0 之后也仍要保留抽样复核——
把纪律换成对通道的信任，就等于把一次实测证伪过的东西重新当真。
