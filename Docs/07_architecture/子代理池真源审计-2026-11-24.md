# 子代理池真源审计：内存缓存还是数据库真源

## 结论

**单一真源在数据库。**

`agent_pool` 表（经 `AgentPoolEntryStore`）是所有池状态的唯一权威。内存 `_pool`（`ConcurrentDictionary`）是**启动时从库重建、写入时后于库更新的易失缓存**。

这一条是 `持久子代理与团队协作规划-2026-11-20.md` §2.3 那个既有负债（「状态写在内存里，重启即失」）是否真正解决的判据。结论是：**已解决**。

## 证据

### 启动回填链

| 位置 | 内容 |
|---|---|
| `SubAgentPool.cs:236` | `_readiness = PoolReadiness.Loading` |
| `SubAgentPool.cs:241` | `loaded = await _entryStore.LoadAllAsync(ct)` |
| `SubAgentPool.cs:281` | `await TryRecoverStaleBusyAsync(ct)`（复位遗留 busy） |
| `SubAgentPool.cs:283` | `_readiness = PoolReadiness.Ready` |
| `SubAgentPool.cs:268` | 回填时 `ownerSessionId: snapshot.OwnerSessionId`，`pool_id` 从库读出而非重新生成 |

`pool_id` 不重新生成这一点很关键：条件写库靠它定位行，换了 id 就会写到错的墓碑上。

### 写路径：库先行，拒则抛

`SubAgentPool.cs:733` 的源码注释：

> 标记为 Busy 之前先抢库里的那一行（S5a，**DB 是第一道真相**）。顺序不能倒：先改内存再写库时，若库拒绝……

实现（`AcquireInStoreAsync`，定义在 `:633`）：

```csharp
var affected = await _entryStore.TryAcquireAsync(...);
if (affected == 0)
{
    throw new InvalidOperationException(
        $"... Refusing to run a task the store has not handed to this execution.");
}
```

库拒绝即抛异常，**调用方永远到不了内存赋值那一行**。

### 终态三重校验

`SubAgentPool.cs:570-601` 的 `FinishAsync` 要求同时满足：

1. 内存条目引用相等（`ReferenceEquals(current, executedEntry)`，防 destroy→create 后落到新条目）
2. `ActiveExecutionId` 令牌相同（防迟到收尾）
3. 库 `TryCompleteAsync` 影响行数 > 0（库是最终裁决者）

任一不满足即 `LogWarning("Stale completion dropped")` 并返回，**不动任何计数**。

源码注释解释了为什么第三道不能省：内存令牌只在本进程内有效，条目可能被另一路径写成 sleeping，那时内存令牌仍相等但库里那行已不归这次执行。

### 接口契约层面的表述

`AgentPool/IAgentPoolEntryStore.cs:128`：

> 要么只改内存——后者会让条目在重启后被 `LoadAllAsync` 从库里**复活**。

即「只改内存不写库 = 重启后复活」，这是把「库为真源」写进接口文档的明证。

## 一条窄缺口：`OwnerSessionId` 为空时跳过库条件门

`AcquireInStoreAsync` 有两条提前 return：

```csharp
if (_entryStore is null) return;                    // 生产不会走（DI 已注册）
if (string.IsNullOrEmpty(entry.OwnerSessionId))
{
    _logger.LogDebug("... Skipping store acquire ... no owner session recorded");
    return;                                          // ← 第二条
}
```

第二条会让条目只靠内存锁保护，跨会话/跨进程的抢占互斥在该情形下失效，且日志是 `Debug` 级默认不可见。

**复核结果（代码 + 数据双侧）：当前不触发。**

代码侧，两条创建路径都会写入：

| 位置 | 内容 |
|---|---|
| `SubAgentPool.cs:480` | `CreateAsync` → `ownerSessionId: request.ParentSessionId` |
| `SubAgentPool.cs:495` | 内存 `PoolEntry` 同样写 |
| `SubAgentPool.cs:759` / `:780` | `ExecuteAsync` 自动创建条目时也写 |

数据侧（只读打开 `D:\Data\databases\pudding_platform.db`，`mode=ro`）：

```
agent_pool: total=1  alive=1  owner_null=0  cols=21  status=[('sleeping', 1)]
```

4 个库文件中只有该库含此表，唯一一条存量行 `owner_session_id` 非空。

**因此不改代码**：注释表明这是刻意设计（「无主则不阻塞执行」），改成 fail-closed 只会给正常路径加噪音。若将来真出现 owner 为空的条目，症状是跨会话抢占互斥退化为仅内存锁 —— 届时再改 `LogWarning` 或 fail-closed。

## 纠偏：`DestroyAsync` 已是级联取消

规划时曾判断「destroy 撞上正在跑的 run，需要在拒绝与级联之间做裁定」。实际读完整方法后确认：**服务层已经是级联取消**，无需新裁定。

`SubAgentPool.DestroyAsync` 的顺序：

1. 库先迁 `dead`（同时写 `deleted_at`）；`affected == 0` 时**保留内存条目并返回 false**
2. `_pool.TryRemove(name, out _)`
3. 若原本是 `Busy`，`_subAgentManager.CancelAsync(entry.SubSessionId, "Pooled sub-agent destroyed")`

源码注释给出了两个方向都不可行的理由：

> 先删内存再写库 → 库拒绝时库里还活着、内存没了，重启后它又「活」回来，而调用方已经收到「已销毁」；
> 库拒绝却删内存 → 同一个名字又能被 create 成新条目，但库里旧行还占着唯一索引（软删后同名才可被新条目占用），新条目会在插库时撞约束。

## 一个语义事实：「唤醒」在服务层不存在

`ISubAgentPool` 只有 `CreateAsync` / `ExecuteAsync` / `SleepAsync` / `DestroyAsync`。

池条目状态机是 `Idle / Busy / Sleeping / Dead`，`Sleeping → Busy` 的唯一入口是 **`ExecuteAsync`（必须带一个具体任务）**。

⇒ 管理界面不能做「点一下就醒」的开关，只能做「派任务」。UI 文案必须讲清这一点，否则用户会以为按钮坏了。
