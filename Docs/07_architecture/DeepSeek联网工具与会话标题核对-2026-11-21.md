## 二、联网工具（`deepseek_web_search` / `deepseek_read_url`）

**是什么**：两个**服务端工具**。声明在 `tools` 里，由模型自己决定是否搜索/读链接，搜索与抓取都在服务端完成，**客户端不执行任何工具**。

| 能力 | 开启方式 |
|---|---|
| 联网搜索 | 声明 `deepseek_web_search`，关思考 → 带引用作答 |
| 深度思考搜索 | 声明 `deepseek_web_search`，**开思考** → 多步推理中自主搜索、打开网页、页内查找 |
| 阅读链接 | 声明 `deepseek_read_url` → 自动识别用户消息里的链接并抓取 |

**协议支持**：Messages / Responses / Chat Completions 三套都可。要求 `deepseek-flash` —— 正是我们的主力模型。

**三条硬约束**：

1. `tool_choice` **不能**指定这两个名字，否则 `400`（是否搜由模型判断）。
2. `tool_choice=none` 会**连带关掉阅读链接**。
3. 搜索产生 `server_tool_use`(kind=search) + `web_search_tool_result` 块；回答用 `citations` 引用。
   图片搜索 `kind=image_search`，`queries` 为空，结果多一个 `image_url`（仅展示，可能不可达）。

**用量可观测**：`usage.server_tool_use = { web_search_requests, web_fetch_requests, tool_search, tool_fetch, tool_image_search }`。

### ⚠️ 一条决定采纳与否的原文

> 这两个工具为**对话场景**设计，用于构建 Chatbot。
> 如果要在 **Agent 或自己的程序**里搜索和抓取网页，请使用 **网页搜索与抓取** 接口。

PuddingAgent 是 Agent，不是 Chatbot。所以**正确路径不是直接挂这两个 server tool**，而是去看官方的「网页搜索与抓取」独立接口。
本节的 server tool 形态，对我们唯一确定的用途是：**深思考搜索**（在推理链内搜索，省掉一轮工具往返），这仍值得单独评估。

## 三、会话标题（`title: {"enabled": true}`）

| 项 | 事实 |
|---|---|
| 成本 | **不计费** |
| 额外请求 | **不需要** —— 模型回答时顺带生成 |
| 延迟 | 回答结束后最多再等 **5 秒** |
| 可靠性 | **不保证有**（被拒答或出错时没有），文档要求自行兜底（如取用户消息前若干字符） |
| 建议 | **只在会话第一次请求开启**，拿到标题后不再开启 |
| 位置（Messages） | 非流式顶层 `title`；流式 `message_delta.delta.title` |
| 位置（Responses） | 非流式顶层 `title`；流式结束事件 `response.title` |
| 位置（Chat Completions） | `message.title`；流式最后一个 chunk 的 `delta.title` |

## 四、对我们仓库的具体映射

| 能力 | 我们现在的做法 | 落点 |
|---|---|---|
| 联网搜索 | 客户端工具 `doubao_search` / `anysearch_search` + `http_fetch` 抓原文 | 各自一次工具往返，每轮重发上下文 |
| 读链接 | `http_fetch`（`output_format=markdown`，带 cursor 分页） | 同上 |
| 引用 | **没有**（`http_fetch` 只回正文，不产 citation） | — |
| 会话标题 | 自己实现（存在已知失败用例 `CompactSession_DoesNotStackCompactionPrefixInNewSessionTitle`） | 见 §5.2 |
| 思考开关 | `config.ThinkingMode`（`DirectLlmClient.cs:1026/1476`、`PuddingJsonConfig.cs:57`） | 已具备，可直接配合深度思考搜索 |
| 用量记账 | `TokenUsageEvents`（tokens / 缓存 / 成本三分项） | 缺 `server_tool_use` 五个计数 |

## 五、采纳建议

### 5.1 优先做：把 `server_tool_use` 五个计数纳入用量账

**理由**：无论是否采用 server tool，只要上了就必须能按次计费归因；而我们的报表已经按模型/子代理/天聚合。
**工作量**：小（扩 `TokenUsageEvents` 一列或一张子表 + 解析 usage）。
**判据**：一次带 `deepseek_web_search` 的请求，账上 `web_search_requests` 与响应对得上（能取红：把它置 0，断言失败）。

### 5.2 评估：用 provider 标题替换自研标题

**但要先说清一件容易混淆的事**：provider 标题与我们的「压缩前缀」不是同一层的东西。
provider 标题是**新会话首次回答**时顺带生成的一句话；我们的压缩逻辑是**在既有标题上加前缀**。
**两者不能互相替代**，只能取舍：若新会话一律由 provider 命名，则"压缩前缀堆叠"这个老问题在新会话上不再发生，但老会话仍然是旧逻辑。

**建议**：先做一个**只读对照实验**——同一句开场白，比 provider 标题与自研标题的质量/长度/中文自然度，再决定。
不要直接改代码，因为那条已知失败用例的语义会随方案变化，必须先定方案再改断言。

### 5.3 暂缓：server tool 联网搜索

**理由**：官方明说 Chatbot 向；Agent 应向「网页搜索与抓取」接口。硬上 server tool 会把搜索行为藏进模型内部，
我们的 `events.jsonl` 就看不到「搜了什么、抓到什么」，与「诊断信息无处可看」的整改方向**背道而驰**。

### 5.4 可考虑：深度思考搜索

若「网页搜索与抓取」接口的延迟/成本不合适，可回到 server tool 的深度思考搜索，但必须同时解决可观测性：
把 `server_tool_use` 块与 `web_search_tool_result` 落进事件流，否则等于把搜索变成黑盒。

## 六、不采纳

1. **不把 `tool_choice` 指向这两个工具**（协议直接 400）
2. **不把 provider 标题当成"修掉已知失败用例"的手段**——先定方案再改断言，详见 §5.2
3. **不在没有用量归因前启用任何 server tool**（会产生看不见的成本）

## 七、一条方法论

这两份文档最有价值的地方不是"能开新功能"，而是**它明确写了不适用的场景**（"为对话场景设计…Agent 请用另一个接口"）。
文档里的**限制条款**比能力清单更能决定要不要做——这次如果只看到"能联网搜索"就动手，就会走错入口。

## 八、更正（用户 2026-11-21 15:03：「我们现在已经支持 deepseek 搜索了」）

用户指正属实，本文 §4 的映射表**不完整**：我只写了 `doubao_search` / `anysearch_search` / `http_fetch`，
漏了仓库里**已经存在**的 DeepSeek 搜索与抓取工具。

### 8.1 已核实的存在性

| 工具 | 文件 | 参数 |
|---|---|---|
| `deepseek_search` | `Source/PuddingRuntime/Tools/BuiltIns/Search/DeepSeekSearchTool.cs:16` | `query` / `count`(1–50，默认 10) / `need_content` / `ori_question` / `localization` |
| `deepseek_fetch` | `Source/PuddingRuntime/Tools/BuiltIns/Search/DeepSeekFetchTool.cs:15` | `url` |

配套：
- 凭据与配置：`Source/PuddingRuntime/Services/DeepSeekWeb/DeepSeekWebSettingsProvider.cs`
  （`<DataRoot>/config/search.providers.json` 的 `deepseek_search` 节，回退到 `llm.providers.json` 的 `providerId="deepseek"`）
- 实网测试：`Source/PuddingRuntimeTests/Tools/DeepSeekWebLiveTests.cs`
- 工具描述里明确写了闭环：搜索返回摘要级内容，**关键事实必须再用 `deepseek_fetch` 或 `http_fetch` 打开原文核实**

**也就是说：我们走的正是官方文档推荐给 Agent 的那条「网页搜索与抓取」独立接口。**
§5.3「暂缓 server tool」的结论因此更站得住 —— 我们已经在正确路径上，不需要回头挂 Chatbot 向的服务端工具。

### 8.2 由此产生的**真问题**：这两个工具不进任何用量账

核实方式（两处 grep，范围已写明）：

- `Source/PuddingRuntime/Services/DeepSeekWeb/` 内 `Usage|charge|billing|cost` → **0 命中**
- `Source/PuddingRuntime/Tools/BuiltIns/Search/` 内 `DeepSeekSearchTool.cs` / `DeepSeekFetchTool.cs`
  → **无** `TelemetryMetricSink` / `TokenUsage` / `Metrics` 任何记账调用
  （同目录的 `SearchGrepTool.cs` 有 telemetry，两个 DeepSeek 工具没有）

结论：`deepseek_search` / `deepseek_fetch` 的调用**既不计入 `TokenUsageEvents`，也不发 telemetry 指标**。
而它们是**计费的付费 API**。

这与「用量报表」整改方向直接冲突：报表会把「搜索花了多少钱」整体漏掉，
而且漏得**不留痕迹**（连调用次数都看不到），使用者无法从任何界面发现这一块缺失。

### 8.3 修正后的采纳优先级

| 原建议 | 修正 |
|---|---|
| ① 把 `server_tool_use` 五计数纳入用量账 | **不适用**。那是 server tool 的 usage 字段；我们用的是独立 API，没有这个字段。 |
| 新 ① | **给 `deepseek_search` / `deepseek_fetch` 建账**：调用次数、耗时、失败分类，以及可得的计费口径（官方按次/按量，需查其计费页确认字段）。落点同既有 telemetry 模式（照抄 `SearchGrepTool.cs` 的做法，不要新造）。 |
| ② provider 标题对照实验 | 不变 |
| ③ 暂缓 server tool | **强化**：我们已在官方推荐路径上 |
| ④ 深度思考搜索 | 降级：只有在「独立接口 + 现有工具」无法满足多步检索时再评估 |

**判据（能取红）**：发一次 `deepseek_search` → 账上必须出现一条对应记录（工具名、耗时、结果状态）；
把埋点删掉，断言必须失败。

### 8.4 一条自省

我上一篇文档写「我们现在的做法」时，依据是**工具目录里看得见的那几个名字**，没有去仓库里核对是否已有更贴合的实现。
工具目录只展示**当前暴露**的工具，不展示**已实现但未加载**的能力 —— 用目录当全量清单，必然得出这种错误结论。
（同族错误在本会话已出现过一次：`search_grep` 覆盖 partial 被当成"没有"。）
