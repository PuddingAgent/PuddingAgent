# 子代理生命周期护栏：用滑动窗口 + 重复检测替代固定计数器

日期：2026-11-21 ｜ 状态：设计稿（用户裁定方向，未实施）
关联：`子代理可观测性与用量报表设计-2026-11-21.md`、`持久子代理与团队协作规划-2026-11-20.md`

## 一、用户裁定（2026-11-21 13:00）

> 可以使用滑动窗口和重复输出检查器来代替，而不应是一个固定计数器。
> 同时可以考虑事件机制和 HOOK：如果异常高频调用，比如 LLM 由于窗口异常开始变成复读机，
> 那么暂停，同时发布通知给主代理，让主代理判断要么恢复子代理要么停止或者销毁异常的子代理。

方向明确：**固定计数上限 → 滑动窗口异常检测 + 暂停 + 父代理裁决**。

## 二、为什么固定计数器是错的（两个方向都错）

实测数据：某子代理 `轮次 92/600`、`耗时 6m16s`、`工具 50/失败 2`。

1. **误杀正常长任务**：600 轮对齐的是「步数」，而长任务的正常步数可以远超它。
   被砍在 600 轮 = 工作白做。
2. **挡不住真正的病态**：LLM 复读时缓存命中率极高（实测同会话可达 98.7%），
   复读一轮可能只要几厘钱 —— 600 轮复读的成本**低于**一次正常长任务。
   计数器在这里完全失效。

> 结论：真正要检测的是「原地打转」，不是「做了多少步」。

## 三、现状盘点：已有检测，缺的是升级动作

`Source/PuddingRuntime/Services/AgentLoop/AgentExecutionGuardrails.cs` 已有三项：

| 护栏 | 默认 | 现在超限后的动作 |
|---|---|---|
| `MaxSameToolRepeat` | 3 | **只注入引导消息** |
| `MaxNoProgressRounds` | 3 | **只注入引导消息** |
| `MaxConsecutiveToolDiscoveryCalls` | 8 | 终止（`tool_discovery_stalled`） |

缺陷：前两项「只提醒、不停」。模型如果无视提醒继续重复，会无限提醒下去。
**取消轮次上限之后，这就是新的失控口** —— 所以本设计是取消上限的前置条件。

## 四、检测器设计（滑动窗口）

窗口：最近 **20** 个事件（`events.jsonl` 的 `round/llm/tool` 三类），按 run 维度维护。

三类信号：

| 信号 | 判据 | 说明 |
|---|---|---|
| S1 重复输出（assistant） | 归一化后消息 hash 相同 ≥ 3 次 | 复读机的直接证据 |
| S2 重复动作 | 同工具 + 同参数 hash ≥ 3 次 | 复用既有 `MaxSameToolRepeat` 语义 |
| S3 频率尖峰 | events/min > 该 run 前两窗口均值 × 5，且连续两窗 | 空转/忙等 |

归一化：去首尾空白、合并连续空白、剥离时间戳与随机 id（避免唯一噪声导致永不命中）。

## 五、动作阶梯（关键：pause 不是 kill）

```
notice  →  pause  →  通知父代理（+ 用户可见）
```

1. **第一窗口命中**：记 `subagent.budget.notice`（既有事件），不停，只在时间线留痕。
2. **连续两窗口命中同一信号**：置 `paused`，停止调度，保留上下文与预算。
3. **同时发布通知给父代理**：带 reason + 窗口统计（重复次数、样本 hash、频率）。
4. **父代理三选一**：`resume` / `sleep`（池化留用）/ `destroy`。
5. 用户也可在界面直接选同样三个动作。

### `paused` vs `sleeping`（必须区分）

| 状态 | 含义 | 上下文 | 恢复代价 |
|---|---|---|---|
| `paused` | 跑着跑着被检测器叫停，等人裁决 | **热** | 直接 resume |
| `sleeping` | 主动休眠，可能很久 | 冷 | 需重建/重放 |

因此 `paused` 挂在**运行**维度，`sleeping` 挂在**池条目**维度，两者不可合并。

## 六、需要新增的部件

| 部件 | 落点 | 说明 |
|---|---|---|
| `paused` 运行状态 | `SubAgentRunEntity.Status` + 前端 `SubAgentCardStatus` | 与 `budget_exhausted` 并列的可续态 |
| `subagent.run.paused` 事件 | `EventSchemaRegistry` 注册 | payload 带 `reason` / `signal` / `window_stats` |
| resume 动作 | 父代理工具 + 界面 | 复用既有 resume 通道 |
| 父代理通知 | **复用既有事件机制** | 不新造通道 |
| 窗口检测器 | `AgentExecutionService` 内或独立 `RunAnomalyDetector` | 纯函数优先，便于单测 |

## 七、实施顺序（不可颠倒）

```
P0  paused 状态 + 重复检测升级（notice→pause）+ 父代理通知 + resume
P1  取消轮次/工具固定上限（此时已有刹车）
P2  成本上限（可选，最后一道保险）
```

**理由**：先取消上限再补刹车 = 出现「既无上限又无刹车」的窗口。

## 八、验收判据（必须能取红）

1. 构造重复输出流（同消息 hash ×3）→ 命中 S1，第一窗口只 notice 不 pause
2. 连续两窗口命中 → 状态变 `paused`，且发出 `subagent.run.paused` 带窗口统计
3. `paused` 后无新 LLM 调用（断言 mock 调用计数不再增长）
4. 父代理 `resume` → 继续且上下文保留（断言消息数）
5. 父代理 `destroy` → 池条目变 `dead`，库与内存一致
6. 正常长任务（30 轮不同动作）**不得**被误判 → 这是防误杀的对照组
7. 变异：把「连续两窗口」改成「任意命中即 pause」→ 用例 1 必须红
