# 持久子代理与团队协作规划

> 本文只做规划，不含代码改动。所有「现状」条目均已对照磁盘源码核对。

## 1. 需求拆解

| # | 需求 | 本质 |
|---|---|---|
| 1 | 持久子代理：可复用、有名字与备注、有独立上下文与压缩、有持久生命周期 | 把「一次性委托」变成「有身份的长期协作者」 |
| 2 | 主↔子、子↔子通信 | 从「单向下发」变成「对话」 |
| 3 | 子代理指示器改造 + 团队管理界面 + 配置界面 | 从「看不到」变成「可管理」 |
| 4 | 最大递归深度 = 1（仅主 Agent 可创建） | 已有语义，需在 UI 明确 |
| 5 | 同主 Agent 下并行子代理总数上限（主不入计） | 已有语义，需在准入处强制 |
| 6 | 是否允许 Agent 为子代理选模型；关闭后继承父 | 已有开关，需定义回退链 |

动机是成本：新建子代理必须重新探索，而探索成本远高于执行。

## 2. 现状盘点（含代码证据）

### 2.1 已有的

| 能力 | 位置 | 说明 |
|---|---|---|
| 内存池 + 命名 | `SubAgentPool.cs:18` | `reserve` / `execute` / `sleep` / `destroy` / `list`，`SubAgentPool:MaxCapacity` 配置，LRU 驱逐（`:431`） |
| 状态投影表 | `session_sub_agents`（`SessionSubAgentEntity.cs:12`） | 每 SubSessionId 一行，含 `Status` / `template_id` / `model_id` / `task_summary` / `full_result_json` |
| 运行账本 | `sub_agent_runs` | run 级记录，含 `parent_turn_id` / `total_rounds` / `total_tool_calls`，重启对账写 `interrupted` |
| 主→子单向消息 | `pool_action=steer`（`SubAgentTool.cs`） | `SessionSteeringService.EnqueueAsync` + `SubAgentSteerPlanner` |
| 递归深度/并行/模型开关 | 管理端「子智能体」配置页 | 已有 UI，语义如需求 4–6 所述 |
| 浏览器委派授权 | `TryRequestBrowserDelegationAsync` | 子运行级授权，失败即 fail-closed |

### 2.2 缺的

| 缺口 | 证据 |
|---|---|
| **池是进程内内存** | `SubAgentPool` 的 `_maxCapacity`、LRU、条目状态全在内存；重启即清空 |
| **无身份字段** | `SessionSubAgentEntity` 只有 `TaskSummary`，没有 `display_name` / `notes` / `purpose` / 所属项目 |
| **无重启对账** | 今晚实测：`session_sub_agents` 积了 10 条 4 个月前的 `running`，而 `sub_agent_runs` 有对账 |
| **终态写入依赖内存** | `SubAgentManager.CancelOneAsync:558` 用 `_runIdMap.TryRemove` 判断是否写库；重启后 map 为空 ⇒ `sub_agent_runs` 永不终结 |
| **子→子无通道** | 只有父会话 `steer` 一条链路；没有同级寻址、收件箱、授权模型 |
| **复用无上下文策略** | 池化复用重置为 `running`，但没有「保留哪些上下文、压缩到什么程度」的定义 |

### 2.3 一个必须正视的既有负债

「持久」的前置条件不是加字段，而是**把真源从内存搬到数据库**。今晚两起事故（幽灵运行、`_runIdMap` 丢失）都是同一个根因：**状态写在内存里，重启即失**。持久子代理若不先解决这一点，等于在流沙上盖楼。

## 3. 外部调研

| 来源 | 要点 | 对本规划的约束 |
|---|---|---|
| *Thread-Scoped Context Isolation*（doi:10.5281/zenodo.19769211） | 多主题会话会导致编排者「上下文塌缩」；解法是按任务域隔离上下文，环境信息走独立轻量记忆 | 持久子代理的上下文**必须按职责隔离**，不能让子代理共享一块大历史 |
| *Architectural Design Decisions in AI Agent Harnesses*（arxiv:2604.18071，70 个项目实证） | 五个反复出现的设计维度，首项即 subagent 委派；设计模式可由项目语料归纳 | 我们不需要发明模式，按已验证维度对齐即可 |
| *When Parallelism Pays Off*（arxiv:2606.00953） | 多 agent 引入**跨 agent 通信开销**，可能抵消并行收益；本质是图划分的通信/计算权衡 | 子→子通信**默认应关闭**，按需授权开启；否则通信成本会吃掉复用省下的钱 |
| *Agent Brain and Trust Architecture*（doi:10.5281/zenodo.19457253） | 把 LLM 推理与记忆存储分离，用显式 token 预算模型管理上下文 | 持久子代理需要**显式上下文预算**，而不是「历史全留」 |

**结论**：持久化的价值在「省掉重复探索」，风险在「上下文膨胀 + 通信开销」。这两条决定了方案必须带预算和准入门槛。

## 4. 方案（分三期，每期可独立交付）

### 第一期：把真源搬到数据库（不新增用户可见功能）

- `sub_agent_runs` 终态写入：内存 map 未命中时按 `sub_session_id` 回落查库（修 `CancelOneAsync:558`）
- 启动对账扩展到 `session_sub_agents`（陈旧 `running` → `interrupted`）
- `SubAgentPool` 条目持久化：新增 `agent_pool` 表（工作区、名称、备注、用途、模板、模型、状态、最后活跃时间、累计成本）
- **完成判据**：重启后 `pool_action=list` 仍能列出此前条目；两张表 `running` 归零

### 第二期：身份与复用

- 字段：`display_name`（工作区级唯一）、`notes`（可改）、`purpose`（用途/项目）、`owner_project`
- 创建与修改入口：`pool_action=create|update`，名称冲突时明确报错而非静默改名
- 复用时的上下文策略（**已决定：完整上下文**，见 §5 第 1 条）。因此第二期的核心不是裁剪历史，而是：
  - 保证子会话历史能被完整重新装载（恢复链）
  - 子代理拥有**自己的压缩链路**（独立阈值、独立摘要、独立预算）
  - 复用前先判定上下文水位，超限则先压缩再执行

### 第三期：通信与界面

- 主↔子：现有 `steer` 补齐「子→主」回执
- 子↔子：**默认禁止**，需显式授权；实现为消息投递（发件箱/收件箱），不做共享内存
- 界面：
  - 子代理指示器：显示名称、备注、状态、当前任务、上下文占用
  - 团队管理页：按父 Agent 分组，支持新建/改名/改备注/休眠/销毁
  - 配置页：现有三项语义补充说明（需求 4–6）

## 5. 待决策（需要用户裁定后才能进入第二期）

1. ~~复用时的上下文粒度~~ **已决定（用户 2026-11-20 18:11，18:14 补充）**：**完整上下文**。子代理被视为完整 Agent——拥有自己的会话历史、独立会话压缩、完整生命周期。并且**复用主代理已有的实现**（会话管理、上下文装配、会话压缩、生命周期、工具链），不为子代理另写一套专用实现。不采用「摘要+台账」的降级方案。

   > 架构含义：子代理不再是一次性委托对象，而是**可恢复的 Agent 实例**。复用 = 恢复同一会话，不是新建。
   > 实现含义（用户 18:14 更正）：是「代码层面复用已有能力」，**不是**子代理与主代理共享同一个文件工作区。
   > 成本含义：复用条目的每轮 token 量级等于一个完整 Agent，**必须依赖会话压缩**控制，且需独立预算（不能与父会话共享额度）。
2. **子↔子通信默认开关**：默认关闭、按团队开启？（文献建议默认关闭）
3. **名称唯一性范围**：工作区级 vs 父 Agent 级？（建议工作区级，便于跨会话定位）
4. **持久条目的成本归属**：复用子代理的历史是否需要独立预算上限？超限时休眠还是拒绝？
5. **递归深度 = 1 的强制点**：在准入处拒绝，还是在参数校验处拒绝并给可读原因？

## 6. 风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| 上下文膨胀 | 复用的子代理带着旧历史，每轮重发 | 显式预算 + 压缩策略（第二期） |
| 通信成本抵消收益 | 文献量化过 | 子↔子默认关闭 |
| 状态双写不一致 | 今晚已实测两张表分叉 | 单一真源 + 对账（第一期） |
| 内存态残留 | `SubAgentPool` 全部在内存 | 第一期必须先做 |
| 命名冲突 | 用户重命名后旧引用失效 | 稳定 id 为主键，名称为可变显示属性 |

## 7. 下一步

第一期不涉及界面与语义变更，风险最低，且能独立验收（重启后条目仍在、`running` 归零）。建议先做第一期，再就是否进入第二期做一次决策。

### 实施顺序（前两步是已经就绪的依赖）

1. **配置项已就绪**（`6d31441` + `f79302a`）：`SubAgentDelegation:MaxDepth` /
   `MaxConcurrentSubAgents` / `AllowModelSelection` / `DefaultModelRoute` 已能读，
   但**还没有任何 API 暴露给前端**。配置界面必须先把这四个键做成可读写的配置端点，
   否则前端只能改一个前端看不懂的后端配置文件。
2. **身份字段缺失**：持久子代理要求「名称 + 备注 + 用途」，而 `session_sub_agents`
   目前没有这些列。团队管理界面的列表主体就是它们，缺列时界面只能显示会话 id。
   ⇒ 界面二期应排在第一期「身份」之后。
3. 检查器改造可以先做：它的数据源（`sub_agent_runs` + 事件归档）已经完整，
   改造内容是把模型、轮次、耗时、Token 的**空值状态**（截图中显示为 `–`）
   换成真实读数或明确的「不可用」原因。当前 `–` 既可能是「没取到」也可能是「真的没有」，
   界面没有区分，这本身是可观测性缺陷。

### 一个必须先定的判据

「指示灯」要显示什么状态？现有 `SubAgentCardStatus` 的取值决定了改造面。
若沿用现有枚举，只需补渲染；若要加「睡眠/复用中」（持久子代理引入的新态），
则要同时改前端枚举、后端投影与事件契约——后者属于第二期，不能提前做。
