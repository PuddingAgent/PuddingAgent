## 一、DSH 怎么做（实测，非推测）

### 1. 子代理即「子会话」，不是独立对象

`GET /sessions` 返回 107 个会话，其中 **45 个带 `parentSessionId`**。会话行的字段是
`sessionId / title / updatedAt / cwd / running / blank / agentAvailable / archived / parentSessionId / origin`。

⇒ 子代理在数据层就是一条带 parent 的会话记录，UI 侧靠这棵树组织，不另建实体。

### 2. 两套名字：`subagent` 与 `subagent_fork`

- `subagent`：从**全新上下文**开始
- `subagent_fork`：**继承已完成轮次**
- 两者都立即返回一个**名字**（如 `reviewer`）用于寻址；名字在同一创建者的子级之间唯一，描述可重复
- 活跃子任务用 `send_message` 引导；完成后可继续其对话

⇒ 「名字」是 UI 里的主要标识，不是 `sessionId`。这点和我们 `agent_pool.name` + `pool_id` 的双标识一致。

### 3. 团队 = 持久化共享任务板

`@deepseek-ai/dsh-agent-team`（版本 0.2.2-rc.5）的定位原文：

> 为现有 subagent（子智能体）树添加持久化共享任务板。成员使用标准 subagent 工具发现和联系彼此。Team 提供比较并交换（CAS）的任务归属更新。成员共享同一检出目录。

- 「Lead / Teammate」是角色词：Lead 发起，Teammate 是被发起的子代理
- 任务归属更新用 **CAS**（比较并交换）—— 和我们池里 `rowsAffected == 1` 才改内存是同一个思路
- 开启方式：根 Session 的模型菜单里「使用智能体团队」；`defaultEnabled: true` 可默认开；关闭后**整棵树后续步骤**不再显示 Team 工具与提示词，**但保留任务与子代理**

### 4. 最重要的一条：UI 明确把「任务」和「成员」分开了

DSH 变更记录原文：

> **Web Team 面板仅显示任务；subagent 导航负责浏览成员。** 线上 `agentTeam.members` 字段与 `TeamMemberProjection` 被移除；持久化成员状态仍可解码。

这是踩过坑之后的收敛：**同一个面板既管任务又管成员，会同时做不好。** 任务板回答「还有什么没做」，成员导航回答「谁在跑、跑得怎么样」，两者刷新频率与交互完全不同。

### 5. 已知限制（DSH 自己承认的）

> **全量视图广播** —— 每次任务变更向已连…（后续被截断）

即每次任务变更向所有已连接的客户端广播全量视图。子代理一多，这是性能上的真问题，值得我们提前避开。

### 6. UI 包形态

DSH 拆成独立包：`dsh-client-ui-agent-team`（团队面板）、`dsh-client-ui-settings-subagent`（设置，含 `SubagentCard` / `SubagentLimitsCard`）。前端按「面板」与「设置」分包，不塞进主界面。

## 二、本项目落点建议

### 位置：顶部导航第三项，紧邻「任务看板」

现状（`Source/PuddingPlatformAdmin/src/pages/chat/components/ChatMain.tsx`）：

- `:593` `aria-label="任务看板"` 的按钮
- `:325` 注释「任务看板模态窗口（原独立路由改为弹窗）」
- `:822`（`workspace-tasks/index.tsx`）「任务看板模态窗口：约占窗口 80% 宽高，内容区可滚动，关闭即卸载并重新加载数据」

⇒ 新增「子代理」按钮挂在同一行，复用同一模态壳（80% 宽高、关闭卸载重载）。**不要新开路由**——与既有取舍保持一致。

### 形态：左树 + 右详情（两栏）

```
┌─ 子代理 ──────────────────────────────── [×] ┐
│ 搜索 / 状态筛选 / [只显示运行中]              │
├──────────────┬──────────────────────────────┤
│ 树（左，320px）│ 详情（右，自适应）             │
│ ● planner     │ [概览][运行][日志][用量]       │
│  ├ ● 运行中    │  名字 / 模板 / 角色           │
│  └ ○ 空闲      │  状态 + readiness             │
│ ● reviewer    │  task_count / last_success    │
│  └ ✕ 已销毁    │  归属：owner_session/workspace│
└──────────────┴──────────────────────────────┘
```

要点：

1. **左树按 parentSessionId 组织**，与 DSH 一致；池条目已有 `owner_session_id`，可派生
2. **状态徽标用池的四态**（`NotStarted/Loading/Ready/Failed`）+ 条目态（`idle/busy/sleeping/dead`），**不要合成一个模糊的「健康」**
3. **用量页签直接读 `llm_gateway_usage_events`**——本会话已证明子代理面板的 token 统计**不累加续跑轮次**，所以详情页必须显示真账，不能显示面板汇总
4. **任务不进这个面板**（照 DSH 的教训），任务留在「任务看板」；两个面板互相跳转即可

### 不建议做（有证据的坑）

- **不要全量广播**：DSH 已把它列为已知限制。池变更走增量事件（已有 `agent_pool.status` 索引），面板按需拉取
- **不要按名字做主键**：名字可被 destroy→create 替换，`pool_id` 才是稳定标识（S5b 已因此把驱逐改成返回 `pool_id`）
- **不要显示「池为空」当未就绪**：S5d 已把这条写进文案判据，UI 层必须继承同一判据

## 三、分期建议

| 期 | 内容 | 依赖 | 验收 |
|---|---|---|---|
| P1 | 只读列表 + 详情（树、状态、归属、用量） | `agent_pool` 表（已有） | 打开面板能看到当前池条目；未就绪时显示「未就绪」而非空 |
| P2 | 操作：唤醒 / 睡眠 / 销毁 / 改名 | `ISubAgentPool` 已有方法 | 每个操作后条目状态与库一致；失败文案走 S5d 五类映射 |
| P3 | 运行中会话跳转（点条目看它的对话） | 子会话与主会话共用会话存储 | 能从条目跳到对应会话历史 |
| P4 | 团队任务板（仅在需要多子代理协作时） | 需先有跨会话任务归属 | 同 DSH 的 CAS 归属语义 |

P1 只读，风险最低，建议先做。
