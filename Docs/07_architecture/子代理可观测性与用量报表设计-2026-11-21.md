# 子代理可观测性：历史轨迹 · 诊断数据 · 用量报表（设计）

日期：2026-11-21 ｜ 状态：设计稿，未实施 ｜ 关联：`子代理管理视图调研与设计建议-2026-11-21.md`

## 一、先说结论

需求分四块，**数据底座差异极大**：

| 需求 | 数据是否已有 | 结论 |
|---|---|---|
| 操作轨迹（工具调用/轮次/失败） | **有**，`runs/*/events.jsonl` 实测 13 类事件 | 可直接做，只读 |
| 诊断数据（模型/缓存/成本/tokens） | **有**，`TokenUsageEvents` 58,120 行，字段极全 | 可直接做，只读 |
| 思维链轨迹 | **字段就绪、内容为空** | 需先补采集，再做界面 |
| 历史对话上下文 | **DB 里几乎没有** | 需先定位数据源 |

所以：**先做前两块（1～2 周内可交付），后两块必须先解决数据缺口再谈界面。**
把界面画在没有数据的字段上，是这轮唯一必须避免的错误。

### 2.3 思维链：字段就绪，内容为空

`reasoning_available / reasoning_chars / reasoning_preview / reasoning_truncated` **四个字段已经在事件里**，但该 run 实测是 `false / 0 / ""`。

两个可能，**尚未区分**（下一轮必须先测）：
1. deepseek 侧没返回 reasoning 正文（只回了 reasoning tokens 计数）；
2. 返回了但采集开关没开。

在区分之前，任何“思维链视图”都是空转。

## 三、视图设计

### 3.1 子代理详情：四个页签

```
[概览] [轨迹] [用量] [产物]
```

**概览**（已有骨架，补字段）：
名字 / 头像 / 状态徽标（池四态）/ 角色 / 模板 / 模型 / 创建时间 / 最近使用 / 最近成功（三态：从未执行 / 成功 / 失败）/ 任务数 / 所属父会话。

**轨迹**（新增，核心）：

时间线按 run 分组，一行一个事件，可折叠：

```
run_...  03:09:34  已完成  968 事件 · 39 分钟 · 失败
├ 03:09:35  round 1   开始
│  ├ LLM  1.68s  51,028→62 tok  缓存 0%   工具调用 1
│  ├ tool  file_read  8ms  ✓  3,702 字符
│  ├ tool  search_grep  120ms ✗  no_match
│  └ …
├ 03:12:01  progress  计划：先读任务书 → 再改 store
└ 03:48:17  run 失败  budget_exhausted
```

要点：
- **只有预览**（`output_preview` 3702 字符上限、`message_preview` 截断标志）；点开“完整输出”需要额外读 `tools.jsonl`
- 失败项默认展开，成功项默认折叠（信噪比）
- 支持按类型过滤（只看工具 / 只看失败 / 只看 LLM）

**用量**：

本 run / 本子代理累计：
- 请求数、prompt / completion / total tokens
- **缓存命中率**（含 miss 明细：`PrefixChangeReason`、`SystemPromptHash` 是否变、`ToolSpecHash` 是否变）
- 成本（区分「已登记」与「未知」）
- 按轮次的 tokens 曲线（上下文增长趋势 —— 这是诊断“上下文被谁撑大”的关键）
- 上下文窗口用量 = `ConversationTokens` / 模型上限（**需要一个模型上限表，目前没有**）

**产物**：`output.md` 正文 + `input.json` 任务书 + `errors.jsonl`。

### 3.2 报表（跨子代理 / 跨会话）

必做四张：

1. **按日趋势**：tokens、请求数、成本、命中率（折线）
2. **按模型**：请求数 / tokens / 成本 / 平均命中率（柱状 + 表）
3. **按子代理**：谁最贵、谁命中率最低
4. **命中率诊断**：把 `CacheHitRate < 0.5` 的请求按 `PrefixChangeReason` 归类 —— **这张是唯一能直接省钱的报表**

数据来源：直接对 `TokenUsageEvents` 现算 SQL。**不要等 `llm_usage_daily_aggregates`**（只有 3 行，且不知是否还在跑）。

## 四、优先级：必须 / 应该 / 暂缓 / 不做

### 必须（P0，先做，风险低）

| # | 事项 | 理由 |
|---|---|---|
| 1 | 轨迹页签（读 `events.jsonl`，只读） | 数据已在，纯前端 + 只读 API |
| 2 | 用量页签（读 `TokenUsageEvents`） | 数据已在，58,120 行可直接查 |
| 3 | 四张报表（SQL 现算） | 命中率诊断能直接省钱 |
| 4 | **数据源决策：轨迹读文件还是读表** | 表里只有 1 行；不先定，界面必空 |
| 5 | 成本显示区分「未知 / 零」 | 否则会把“没登记”看成“免费” |

### 应该（P1）

| # | 事项 | 理由 |
|---|---|---|
| 6 | 上下文窗口用量（需模型上限表） | 需求明确要求；缺一张小配置表 |
| 7 | 思维链采集开关 + 抽样验证 provider 是否返回正文 | 需求明确要求；必须先测再谈界面 |
| 8 | 全文落盘策略（preview → full，带容量上限） | 现在只有预览；全文有存储成本，要定预算 |
| 9 | 主会话历史定位 | 现在 DB 与 `D:\Data\sessions` 都是空的 |

### 暂缓（P2）

- 跨会话全文检索（FTS）
- 实时推送（先轮询即可；DSH 的全量广播已被它自己列为反模式）
- 轨迹的图形化（泳道/拓扑）—— 先把时间线文本跑通
- 引用/因果链可视化（`correlation_id` 已有，但先不做图）

### 不做

- **脱敏**（用户明示不需要）
- **另建一套 trace 存储**（`events.jsonl` 已是真源，重造等于双写两份真相）
- 拓扑图（已在前一份调研否决）

## 六、三个必须先回答的问题

1. **reasoning 到底能不能拿到？** 需要一次开 reasoning 的实测：看 provider 原始响应的 reasoning 字段是否非空。拿不到就必须如实告诉用户“思维链不可得”，而不是做一个永远空的页签。
2. **主会话历史在哪？** DB 里 `conversation_events`=1、`conversation_turns`=6，`D:\Data\sessions` 空。主代理自己的对话轨迹存哪儿，必须在做“历史对话”界面之前定位。
3. **`sub_agent_runs` 为什么只有 1 行？** 是投影任务没跑，还是只有池化路径写？界面依赖它就必然空。

以上三条都属于「数据结构问题」，不是 UI 问题。按项目纪律（先独立测试再接入），**先补证据、再动手**。
