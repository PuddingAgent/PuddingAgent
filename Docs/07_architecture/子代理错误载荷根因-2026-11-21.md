# 子代理错误载荷根因

## 1. 用户看到的现象

子代理任务完成后，父代理收到的消息正文（旧格式）只有一行：

```
shell: exit code 1
```

既没有子代理的交付内容，也没有任何诊断信息。而实际磁盘上往往已经写好了完整代码。

## 2. 完整产生链（逐行核对，file:line 为 2026-11-21 HEAD `42484ce` 实测）

```
① PuddingRuntime/Tools/BuiltIns/Shell/HostShellExecutor.cs:108
     Error = process.ExitCode == 0 ? null : $"exit code {process.ExitCode}"
        ↑ 裸退出码。stderr 其实已被读出并 MergeOutput 进 Output（同文件 :104-105）

② PuddingRuntime/Services/AgentExecutionService.cs:1755
     firstToolFailureSummary ??= BuildToolFailureSummary(toolName, error, output);
        ↑ 注意：output 已经传进来了（含 stdout+stderr+执行元数据）

③ PuddingRuntime/Services/AgentExecutionService.cs:1762-1770
     private static string BuildToolFailureSummary(string? toolName, string? error, string? output)
     {
         var reason = !string.IsNullOrWhiteSpace(error) ? error! : ... ;
         return $"{toolName ?? "tool"}: {Truncate(reason, 512)}";
     }
        ↑★ 缺陷所在：error 优先，且 output 被完全丢弃

④ RuntimeDispatchResult.ToolFailureSummary → SubAgentManager.cs:197 → :274
     → BuildSubAgentResultEnvelope（A 期已改为三段式，正文不再被错误串占据）
```

## 3. 根因一句话

**信息不缺，是选错了那个。** `error` 只有退出码，`output` 里有完整 stderr —— 而摘要构造时优先取了贫瘠的那个，且直接把另一个丢掉了。

`SystemPromptBuilder.cs:196` 甚至已经写明「非零退出码不是文件或任务失败的充分证据」，但错误摘要本身就是这个退出码。

## 4. 为什么不在信封层修

A 期（`4d90041`）已把正文改成三段式，错误降级为附注行 —— 那解决的是「正文被错误串占据」。
但附注行里仍然只有 `exit code 1`，因为摘要源头就没带诊断。**信封层再加工也变不出它没有的信息。**

## 5. 修复方案（已实施）

只改 ③，一处：

```csharp
private static string BuildToolFailureSummary(string? toolName, string? error, string? output)
{
    var name = toolName ?? "tool";
    var reason = !string.IsNullOrWhiteSpace(error) ? error! : "unknown tool failure";
    if (string.IsNullOrWhiteSpace(output))
        return $"{name}: {reason}";
    return Truncate($"{name}: {reason} | 输出尾部: {Tail(output!, 400)}", 512);
}
```

要点：

- `error` 仍然在前（保留「失败原因」的语义），`output` 作为诊断附在后面
- 取**尾部**而不是头部：shell 的错误信息通常在末尾
- 保留既有 `Truncate(…, 512)` 总长约束
- `output` 为空时输出与现状**逐字相同**（零行为变化）

## 6. 影响面与风险

| 风险 | 评估 |
|---|---|
| 影响所有工具（不只 shell） | 是。但只在 `output` 非空时追加，且带明确分隔符 ` \| 输出尾部:` |
| 消息体变大 | 单条上限 512 字符，与现状同一量级 |
| 既有单测 | `BuildToolFailureSummary` 是 **private static、全仓仅一处调用、无直接测试**（已 grep 确认） |
| `ToolFailurePayloadTests.cs:51` 断言的 `"   Error: exit code 1"` | 那是**另一处**渲染（工具失败载荷），不走本方法，需实测确认不受影响 |
| 摘要可能含敏感内容 | output 已是模型可见的工具输出，摘要不引入新的暴露面 |

## 7. 判据（必须能取红）

1. `error="exit code 1"`、`output="line1\nERR: 文件不存在\n"` → 摘要**同时**含 `exit code 1` 与 `文件不存在`
2. `error="exit code 1"`、`output=""` → 摘要**逐字等于** `shell: exit code 1`（证明零变化分支）
3. `error=null`、`output="boom"` → 仍走 `unknown tool failure` 或不含空 error 占位
4. 长度断言：摘要长度 ≤ 513（`Truncate` 截断后会追加一个省略号，旧实现同样如此；不要在测试里断言 512）
5. **变异**：把 `Tail(output, 400)` 改成 `""` → 判据 1 必须失败

## 8. 未做（明确边界）

- **没有**把 `exception_type` / 真实堆栈放进载荷：`BuildToolFailureSummary` 手里只有 `error` 字符串和 `output`，没有异常对象。伪造堆栈比没有更坏。
- **没有**改 `HostShellExecutor.Error` 的语义：它是**退出码**，语义正确；给上下文是摘要层的职责。
- **没有**端到端验证「消息真的到达父代理并渲染」：需要一次真实子代理回执才能看到，属部署后观察项。
