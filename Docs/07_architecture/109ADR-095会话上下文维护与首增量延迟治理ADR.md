# ADR-095：会话上下文维护与首增量延迟治理

状态：Proposed。本文规定目标架构；不表示实现或产品验收已经完成。施工顺序与文件范围见[修复方案](../12_features/首Token等待与上下文指示器修复方案-2026-10-07.md)，运行证据只保留在[诊断报告](../14_reports/首Token等待与上下文指示器诊断-2026-10-07.md)。

## 1. 背景与适用范围

Session的历史随用户消息、模型回复和工具轮持续增长。压缩可以发生在Session的任意安全点；Session第一条消息和每个Turn的第一轮都不应成为默认压缩时机。仅在Turn内部用布尔标记限制一次尝试，会在长执行中积累容量压力，并在下一条消息重新开启同步摘要。

现有warm-prefix路径直接改内存历史，普通压缩路径管理覆盖清单与代次；二者的提交、事件、收益与恢复语义需要统一。预算估算和Provider实测当前共享可变session快照，还会把数据来源变化投影为占用跳变。

范围：主/子Agent的Streaming与Buffered、自动/手动压缩、重启水合、请求预算与WebUI。业务留在Core，Desktop仅承载Web；不新增Shell业务或独立模型协议。

## 2. 与已有决策的关系

- 保留[ADR-090](104ADR-090上下文压缩触发口径来源标注与收益准入收敛ADR.md)的预算分层、来源诚实、候选增量/收益准入、无收益退避与硬边界。本地保守上界不得成为软压缩唯一触发依据。
- 保留[ADR-084](98ADR-084稳定请求前缀与缓存99验收ADR.md)的稳定最终请求前缀、真实Token加权缓存统计和请求身份复用；必要压缩的摘要成本及checkpoint后冷miss均纳入评价。
- 保留[ADR-042](43ADR-042上下文自动压缩与主动Compact命令ADR.md)的手动入口与上下文连续性。手动请求可以立即申请，但仍须经过候选保护、收益验证和唯一提交边界。
- 对ADR-090否决完整计划器的选择作有限扩展：允许在已有协调器中保存Session级候选指纹、代次、单飞任务与终态结果，并以已有代次/请求身份验证异步候选。**不新增通用计划引擎、第二套事件库或第二套历史权威。** 扩展原因是后台生成期间前台继续推进，提交必须能拒绝旧候选；这不是为了统计引入全量多代次快照体系。

## 3. 决策

### D1. Session维护跨Turn，准入由容量与候选变化决定

维护键为 `(workspaceId, sessionId)`，绑定当前Agent/route配置。复用已有CompactionGeneration与覆盖清单；同一代次可有多个追加后的候选指纹，候选不变则合并重复请求。

每个完整模型/工具轮结束及Turn终态提交后重新评估。替换`warmPrefixCompactionAttempted`的Turn级封顶为候选级准入：没有新增可压缩内容不重做；新候选达到经济性门槛可再次维护。代次在成功应用checkpoint后递增，普通追加只推进历史revision/指纹。

初版在活跃Turn内只评估和标记维护需求；可选摘要在canonical终态提交、前台租约释放后生成。现有Agent准入按整个Turn持有前台租约，不允许通过普通后台注册绕过它。长Turn内遇到硬容量不足仍由当前执行者同步保护；“轮次评估”不等于每轮发摘要请求。活跃Turn内并行生成是后续扩展，须另证准入、费用和候选命中收益，不作为本次上线前提。

软维护须同时满足：同形请求的窗口压力证据、候选新增量、预计整请求回收收益。字段未知时明确为未知；退化估算可供观察，不能冒充实测。门槛复用已有配置并经回放校准，不在本ADR任意降低触发比例或设置“每条消息压一次”。

### D2. 软维护不阻塞安全的新消息，硬保护逐请求生效

软维护生成摘要可后台执行，用户消息受理/准入时优先取消同Session的可选工作。取消无需等待完整远端摘要；已计费使用仍记账，迟到结果不能进入前台输出或越过版本校验。

每次出站仍验证实际路由、工具/历史、输出预算与安全余量组成的输入边界。当前保守安全检查不允许发出请求时，先使用已验证候选；必要时显式同步压缩。不能在计量未校准前仅凭上一轮较小的Provider用量忽略当前安全上界。

同步压缩有独立取消/超时/输出预算，受当前Turn绝对deadline和剩余Token预算约束。失败不能以无声删除历史伪装成功；安全空间仍不足则提交明确的`context_budget_exceeded`结果。请求副本裁剪若作为已配置的降级策略保留，必须保持完整工具轮和当前Turn，发独立事实，不能称为持久摘要压缩。

### D3. 一个候选应用边界，生成与提交分开

摘要策略可保留warm-prefix原样重放，也可使用已有其他策略；最终提交都经同一应用边界，负责候选验证、脱敏、持久checkpoint/coverage/generation和内存更新。禁止warm-prefix再绕过它只`Clear/AddRange`共享List。

候选保存源generation、源revision、选中旧跨度的稳定身份/内容hash、保留尾部hash、工具与路由版本。初版采用严格校验：生成后任何相关历史/配置变化都丢弃候选并记录`stale_candidate`，不做复杂尾部拼接或自动rebase。被丢弃的候选不算“压缩完成”。

摘要可能看见重放的全前缀，但只能总结将被替换的旧跨度；受保护的当前Turn、未完成工具轮、保留尾部不得被重复写入摘要。摘要加入后重新计量整个请求，必须真实收缩、满足硬上限、语义保护和配置回收准入；计划阶段未含摘要的估算不能当作最终收益。

### D4. 锁序显式，模型调用不占维护提交锁

后台生成只读取冻结、脱敏的历史快照，不持Session执行锁或压缩提交锁跨网络调用。提交短临界区严格按 **SessionExecutionGate → CompactionCoordinator** 获取；严禁压缩锁→执行锁或持锁等待dispatch回执。

后台提交若遇到前台正在运行或等待准入就延期，不与前台竞争长租约；获取执行锁后、事务前再次验证foreground demand及源版本。必要的同步压缩由前台执行者在完整轮边界提交，已持执行锁时只获取压缩锁。Round内执行期间不得有后台writer改变共享history。

generation比较与持久写入在事务/CAS中完成；跨进程使用已有执行fence/维护租约校验，进程内锁不作为跨进程证明。唯一锁序覆盖自动、手动、warm-prefix和后台四条入口，并以竞争/死锁测试作为门禁。

### D5. 提交与恢复以持久checkpoint为准

生成候选不是提交；提交成功后才推进generation。checkpoint必须保存可恢复的脱敏语义历史及所需协议continuation信息/引用，不能保存注入密钥后的完整Prompt；coverage引用稳定消息身份和hash。

事务提交后才更新内存；内存更新失败则显式失效并从新generation水合。事件发布失败不撤销已提交历史，以compactionId和持久清单补投并幂等投影。进程重启将未提交任务标为interrupted/过期，已提交checkpoint优先恢复；不得凭“DB消息少于内存”跳过更新的有效generation。

### D6. 请求估算、实测与压缩候选各自归因

复用现有invocationId/attemptId、路由及context generation，仅保存当前准备快照和最近已完成主请求实测。辅助/摘要请求单独归因，迟到usage不能改写另一请求的raw estimate或安全校准。

- `currentPreparedRequest`：本次请求原始估算、保守安全上界、计量依据/置信度、完整容量参数。
- `lastMeasuredRequest`：该主请求Provider PromptTokens；Completion/Total分别保留，Total不命名为“实测输入”。
- `candidateUsage`：可替换原文与固定成本；不得把工具schema和受保护尾部计入可压缩收益。

校准按同形的request/attempt配对，同一路由/模型/协议范围使用有界更新；异常样本、换路由及generation变化均有明确处理。历史最大保守系数可以用于安全隔离，但不能固化成可见占用或唯一经济性触发。具体统计方法需由配对回放证明，未经证明不降低安全上界。

### D7. 容量和前端事实统一

`effectiveInput = min(providerInputLimit, modelWindow - actualOutputBudget - safetyBuffer)`。缺失的上限/预算须标来源与未知，不把Provider能力上限自动当本次输出预算；上下文health与出站门禁共享同一公式和冻结参数。

UI分别显示最近实测输入、当前预算估算、模型总窗口占用、有效输入压力。容量状态与API采集状态独立；“压力偏高”不是“上下文服务异常”。摘要分层基于统一typed kind，普通摘要与warm-prefix用同一合同。

复用canonical Conversation事件：真实开始后才发`context.compaction.started`；成功/跳过/延期/失败结果明确，完成必须带applied标记；仅applied会显示“已压缩”。请求副本裁剪单独显示“本次请求裁剪旧上下文”。估算换实测只更新来源说明，不虚构压缩事件。前台状态由accepted→preparing→compacting（若有）→provider_wait→reasoning/content/tool事实派生，重放不重新激活旧动画。

## 4. 不变量与方案取舍

| 必须成立 | 取舍 |
|---|---|
| 新消息不等待可选摘要完成 | 丢弃过期候选可能浪费已发生的摘要费用，完整记账；同候选合并限制重复成本 |
| 成功提交后只出现一个新generation | 需要短事务与持久清单，不用进程内布尔标记代替 |
| 当前Turn和完整工具轮不丢失 | 硬超限且无法安全压缩时允许显式失败，不伪造可继续 |
| 实测与预算来源不相互覆盖 | 多显示一个估算数，但来源清楚 |
| 稳定前缀只在必要应用时改变 | 不能用保留重复历史、无任务预热或取消必要工具抬高缓存率 |

否决：Session只压缩一次；每条消息固定压缩；单纯延长冷却；仅移除保守校准；把当前`await`替换成`Task.Run`并发改List；后台持执行锁等待20秒摘要；仍以硬预算副本裁剪长期掩盖Session历史膨胀。

## 5. 实施与验收约束

先完成计量配对、生命周期和纯决策/候选验证测试，再接入Session维护与唯一提交边界。独立组件先S1–S4，后S5装配，详见修复方案；当前文件只登记设计，不新增程序集或DI。

验收至少覆盖：一个长Turn跨两次候选变化；同Session第二条短消息；后台摘要20秒时前台正常首增量；用户抢占、手动竞争、deadline、无收益、事件补投与重启；相同generation上的迟到usage；Responses continuation与工具轮完整性。理论上的首增量收益不是实测承诺；修复后的分布、压缩频次、摘要费用、冷miss和任务正确性均需报告。

上线按组件与请求阶段灰度，回退只能关闭可选后台调度，硬保护、准确用量来源和已提交checkpoint仍保留。不得回退到无法理解新checkpoint的旧代码访问真实开发库。变更、门禁和部署结论写changelog/report，不写入本ADR。
