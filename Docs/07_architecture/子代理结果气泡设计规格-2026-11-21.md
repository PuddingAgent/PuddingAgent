## 一、用户反馈（2026-11-21 14:50）

> 「是的，这个气泡设计有点问题。」

截图实测，气泡内容只有两行：

```
Sub Agent 发来的消息
shell: exit code 1
```

## 二、现状三个问题（按严重度）

| # | 问题 | 后果 |
|---|---|---|
| 1 | **正文就是错误串** | 用户/父代理看不到「它做了什么」。实际已交付 9 文件 +123/−32，气泡里一个字都没有 |
| 2 | **没有身份** | 永远显示 `Sub Agent`。它有 `display_name`（`dock-fix` / `paused-tests` / `paused-status`），气泡不显示 |
| 3 | **没有状态与动作** | 是成功、失败、还是"失败但有交付"？看不出来。也没有入口去看详情或重派 |

根因（已读码确认）：后端 `contextText = deliveredResult ? reply : error`。
失败时 `reply` 被整条丢弃，只剩 `error`。**气泡只是忠实渲染了这个错误取值。**

## 三、卡片形态

```
┌────────────────────────────────────────────────────────────┐
│ [头像] paused-tests                              [失败]     │
│        workspace-task-agent · 1m44s · 工具 37（失败 2）     │
├────────────────────────────────────────────────────────────┤
│ 已交付 9 个文件（+123/−32）· 测试 22/22 通过                │  ← 交付面（W0 上线后）
│ ⚠ 最后一次工具报错：shell: exit code 1                     │  ← 错误降级为附注
├────────────────────────────────────────────────────────────┤
│ [查看运行详情]  [重派]  [标为已处理]                        │
└────────────────────────────────────────────────────────────┘
```

## 四、四种状态（互斥，各有一句主文案）

| 状态 | 触发条件 | 主文案 | 副行 |
|---|---|---|---|
| **已交付** | 有产物且无终态错误 | 已交付 N 个文件（+a/−b） | 测试 22/22 通过 · 耗时 1m44s |
| **已交付但有报错** | 有产物 + 最后一次工具报错 | 已交付 N 个文件（+a/−b） | ⚠ 最后一次工具报错：<原文> |
| **无产物** | 无产物 + 报错 | 没有产生改动 | 错误：<原文> |
| **未知** | 无产物 + 无报错 | 未采集到交付信息 | 查看运行详情 |

**「已交付但有报错」是本设计存在的理由。** 本会话 4 个子代理都属这一档，
现状把这一档渲染成和「无产物」一模一样。

## 五、字段映射（分两期）

**A 期（不改后端，用现有 envelope metadata）**

| 卡片元素 | 来源 |
|---|---|
| 名字 + 头像 | `display_name`（`session_sub_agents`）/ `avatar_key`，空则回退「模板名-短 ID」 |
| 状态徽标 | envelope `status` |
| 工具计数 | `tool_failure_count` / `tool_output_chars`（已在 metadata） |
| 契约披露 | `contract` / `contract_satisfied` / `contract_missing`（已在 metadata） |
| 正文 | `reply`（**有就显示，无论 status**） |
| 错误附注 | 现有的 `error` 串，降级为附注行 |
| 详情入口 | `run_id` / `child_run_id` → 运行检查器 |

A 期**不需要后端改任何字段**：`reply` 已经在 envelope 里，只是被 `contextText` 的取值逻辑丢了。
需改的是 `BuildSubAgentResultEnvelope` 里 `contextText` 的拼法 + 前端渲染。

**B 期（依赖信封 v2）**

交付面（`files_changed` / `insertions` / `deletions`）、门禁 summary、`work_outcome` 三态。

## 六、渲染纪律

1. **正文必有主文案**，不允许"整条气泡只有一个错误串"。错误只能出现在附注行。
2. **截断必须标注**：正文超过 8 行折叠，显示「展开全文（共 N 字符）」。
3. **缺失 ≠ 零**：无交付面时显示「未采集到交付信息」，不显示「0 个文件」。
4. **不把气泡做成日志查看器**：时间线、思维链、原始 JSON 一律进「查看运行详情」。
5. **动作不做成默认破坏性**：「重派」需二次确认；「标为已处理」只影响气泡状态不改 run。

## 七、验收判据（能取红）

1. 构造 `status=failed` 且 `reply` 非空的 envelope → 气泡正文**必须**显示 `reply` 的内容，
   且同时出现「最后一次工具报错」附注行。（现状会红：正文只有错误串）
2. 构造 `status=failed` 且 `reply` 为空 → 显示「没有产生改动」，不得显示空白气泡。
3. 名字取自 `display_name`，不得硬编码 `Sub Agent`（断言气泡里不出现该字面量，或用具体名字断言）。
4. 无交付面字段时不显示「0 个文件」。
5. 正文超长折叠时，折叠提示必须含总字符数。

## 八、不做

1. 不在气泡里放时间线 / 思维链（性能与噪音）
2. 不做「自动重派」——失败自动重派会把「假失败」变成「真双份工作」
3. 不改 `MessageId` 幂等语义（`SubAgentResultIdentity.Compute` 去重是崩溃重投的保护）
4. 不为气泡新增第二条通知通道

## 九、错误载荷规格（用户 2026-11-21 14:53 追加要求）

> 「即使需要返回一个错误文本，也应该是一个比较正式的错误文本，告知错误诊断信息和错误堆栈，
> 方便后续的主代理或者我去诊断。」

### 9.1 现状：`shell: exit code 1` 不是错误文本

它是**工具退出码**，属于"未加工的信号"。它丢失了全部可诊断信息：

- 哪个工具（哪个命令、什么参数）
- 退出码之外，stderr 说了什么
- 有没有异常类型与堆栈
- 发生在哪一轮、哪个 run、哪个工具调用
- 是工具失败，还是运行时异常，还是取消

把它当作错误文本投递，等于让接收方从零开始考古。

### 9.2 正式错误载荷的字段

```
error:
  category      : tool_failure | runtime_exception | provider_error | timeout | cancelled | unknown
  tool_name     : string?            # category=tool_failure 时有值
  exit_code     : int?
  stderr_tail   : string?            # 尾部 N 字符，无输出时显式写 "(无输出)"
  exception_type: string?            # 例 System.InvalidOperationException
  stack_trace   : string?
  message       : string             # 人类可读一句话
  round         : int?
  tool_call_id  : string?
  occurred_at   : ISO-8601
```

**硬规则**：

1. **`category` 必填**。不允许只有一句自由文本——没有类别的错误，无法被自动化处置。
2. **`stderr_tail` 无内容时写 `"(无输出)"`，不是空**。空与"没有输出"必须可区分（缺失≠零）。
3. **`stack_trace` 拿不到时显式写 `"无堆栈（工具退出码路径）"`**，不得留空让人以为是漏填。
4. **`message` 必须是完整句子**，包含工具名与退出码，例如：
   `工具 shell 以退出码 1 结束（第 11 轮，调用 call_01_…），stderr 末 4 行见诊断。`
   不允许 `exit code 1` 这类片段直接充当 `message`。
5. **堆栈只在 category=runtime_exception 时有意义**；工具退出码路径本就没有堆栈，不要伪造。

### 9.3 三段呈现

| 位置 | 内容 |
|---|---|
| 气泡正文 | **交付结果**（`reply`）。永不显示原始错误串 |
| 气泡附注行 | `error.message` 一行（完整句子，可含工具名与退出码） |
| 「展开诊断」 | 完整 `error` 载荷（category / stderr_tail / 堆栈 / round / 调用 id） |

### 9.4 判据（能取红）

1. 构造 `category=tool_failure, exit_code=1, stderr_tail=""` → 附注行必须是完整句子且含工具名与退出码；
   展开诊断里 `stderr_tail` 必须显示 `(无输出)`。
2. 构造 `category=runtime_exception` 带堆栈 → 展开诊断必须显示异常类型与前若干行堆栈。
3. 构造 `category=runtime_exception` 无堆栈 → 必须显示 `无堆栈` 字样，不得空白。
4. 任何情况下气泡正文**不得**等于 `error.message`（正文只放交付结果；无交付时正文写「没有产生改动」）。

### 9.5 与信封 v2 的关系

本节是 `子代理结果通知与父代理唤醒优化规划` §5 里 `terminal_error` 的具体化。
`work_outcome`（有无交付）与 `error`（错误载荷）仍然正交：**有交付 + 有错误** 是最常见的一档
（本会话 4 例全部如此），必须能同时表达。

## 十、"主代理在做什么"没有可见信号（用户 2026-11-21 15:25）

> 「界面上，我看不到你处理『Sub Agent 发来的消息』的气泡，所以，我并不知道主代理（也就是你）在做什么。
> 是否应该同步触发一个主代理的气泡，让我可以看到？」

### 10.1 现象核对

截图：我的上一条回复 → `Sub Agent 发来的消息` 气泡 → 输入框。**中间没有任何"主代理正在处理"的指示**。

不是我没在干活（那一轮正是我在读码、跑测试、提交），是**界面没有承载它的位置**。

### 10.2 根因：运行指示器只能挂在"已存在的 assistant 消息"上

`AgentMessageBubble.tsx:862-881`：

```tsx
{shouldShowRunMonitor && (
  <div className="agentRunMonitor">
    {turnStatus && processActivity?.variant !== 'compaction' && (
      <TurnStatus status={turnStatus} turnStartedAt={...} agentName={agentName} />
    )}
```

`TurnStatus`（含那颗墨球与「正在生成回答 · 已运行 Nm」）是**消息气泡内部**的一段。

于是：子代理结果唤醒父代理 → 父代理开始一个**后台 Turn** → 此时**还没有任何 assistant 消息产生** →
没有任何气泡可以承载 TurnStatus → 用户看到的只有子代理那条消息，然后是一片静默。

### 10.3 为什么这是"设计缺口"而不是"渲染 bug"

后台 Turn（子代理结果触发）与前台 Turn（用户消息触发）在界面上**没有区别对待**：
前台总有一个"用户消息"作为时间轴锚点，后台**没有锚点**。

`MessageDeliveryDispatcher.cs:415` 把子代理结果排除在 `claimedIsForeground` 之外 —— 在调度层是正确选择（不打断），
但**界面层没有配套**：不打断的代价是"看不见"。

### 10.4 三个候选方案

| 方案 | 做法 | 优点 | 风险 |
|---|---|---|---|
| A 服务端占位消息 | 受理 canonical turn 时写一条空 assistant 消息，TurnStatus 挂上去 | 简单、与现有一致 | 产生空壳消息；turn 失败会留下一条永远空的消息 |
| **B 前端虚拟占位气泡** | 前端看到"已受理但无产出的 turn"就渲染一个占位气泡 | 不产生消息实体；turn 结束自动消失 | 需要一份**不依赖消息**的 turn 投影 |
| **C 挂在子代理结果消息下方** | 把 TurnStatus 作为该 `subagent_result` 消息的子元素 | 语义最准：「我正在处理这条结果」 | 需要把该消息与 turn 关联 |

**建议 C 为主、B 为兜底**：C 表达的是真正的因果关系（处理的是这一条），B 覆盖"当前没有任何可挂消息"的极端情形。

### 10.5 待核实的可行性前提

1. **前端是否已有"不挂在消息上"的 turn 投影？**
   现有 `turnStatus` 来自 `deriveTurnStatusFromProjection(executionFlowProjection)` 或 `deriveTurnStatusFromFacts(...)`，
   两者都在 `AgentMessageBubble` 内部，即以消息为锚。要落地 B/C，需要一个**会话级**的"当前 turn 正在运行"事实。
   → 未核实，需查 `executionFlowProjection` 的产生方式与作用域。
2. **子代理结果消息与它触发的 turn 之间有没有可关联的 id？**
   消息侧有 `result_id` / `child_run_id`；turn 侧应有 canonical turn 的幂等键（`ResolveCanonicalTurnIdentityAsync`）。
   → 若无共同键，C 方案需要后端补一个关联字段。

### 10.6 最小可见形态（不依赖上述核实）

即便 B/C 都暂时做不了，也有一个**零风险**的兜底可立刻做：

> 在 `subagent_result` 消息气泡的页脚显示一行：`主代理已受理，正在处理…`（前端本地状态 + 超时置灰）

它不精确（不显示在干什么），但**消除了"静默"**。伪造"正在做的事"不行，说"已受理"是事实。

### 10.7 判据（能取红）

1. 子代理结果到达后 3 秒内，界面必须出现一条**主代理侧**的可见指示（任何形态）。
2. 该指示必须能区分「已受理」与「正在执行某工具」——不得把"已受理"写成"正在执行 X"。
3. turn 结束后指示必须消失，不得残留成"永远在处理"。

### 10.8 与既有纪律的关系

同一屏只允许一颗动画墨球（见 `TurnStatusOrb` §3.2）。若子代理浮坞也在跑，**必须让位**：
建议 subagent_result 触发的后台 turn 指示用**静态**状态点 + 行扫光，把墨球留给前台 turn。
