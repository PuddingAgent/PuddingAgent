# 子代理界面重复性调查与重构建议

日期：2026-11-21 ｜ 状态：调查结论 + 待裁定方案（未实施）
关联：`子代理生命周期护栏-2026-11-21.md`、`子代理可观测性与用量报表设计-2026-11-21.md`、`子代理管理视图调研与设计建议-2026-11-21.md`

## 一、起因（用户 2026-11-21 14:20 实测反馈）

1. 正在运行的子代理 `paused-tests`（`…sub-e0b08674`）**没有出现在「子代理」管理面板里**；
2. 质疑「子代理界面可能是重复的」。

两张截图对照后现象确认：

| 界面 | `paused-tests` 是否可见 |
|---|---|
| 浮坞 / 运行检查器 | **可见**（运行中 · 44 请求 · 3.8M tokens · 命中 97.6%） |
| 子代理管理面板 | **不可见**（只有 `frontend-ui`，共 1 个） |

## 二、根因：三个数据源，两个界面，一个名字

这不是渲染缺陷，是**数据源不同**：

| 界面 | 组件 | 数据源 | 覆盖面 |
|---|---|---|---|
| 浮坞 + 运行检查器 | `SubAgentActivityDock.tsx`（同一文件两种呈现） | ①会话事件流（`subagent.*` 实时）②`/api/sub-agents/runs/{runId}/…`（run.json + events.jsonl） | **本次会话内所有子代理**（含未池化） |
| 子代理管理面板 | `subagent-pool/SubAgentPoolPanel.tsx` | `/api/admin/sub-agent-pool` → **`agent_pool` 表** | **只有池条目**（当前 1 行） |

`paused-tests` 是一次性 `spawn_sub_agent`，从未进入 `agent_pool`，因此管理面板看不到它 —— 面板**按设计**只列持久池条目。

但用户预期是「管理界面能看到所有子代理」，这说明**命名与信息架构错了，不是数据错了**。

另一条并存的三号源容易混淆：`getSessionSubAgents()` → `/api/sessions/{id}/sub-agents` → `session_sub_agents` 投影表
（按会话列全部子代理，含历史 1600+ 行）。它**目前没有独立界面**，只在会话上下文里被消费。

## 三、哪些是真重复，哪些不是

**真重复：两个列表看起来都在回答「有哪些子代理」**

- 运行检查器的列表：按 run 维度，有状态、模型、轮次、工具数、耗时
- 池管理面板的列表：按条目维度，有名字、头像、角色、任务数

两个列表视觉语言相近（卡片 + 状态徽标 + 名字），但一个回答「谁在跑」、一个回答「谁可以被复用」。
用户无法从界面区分，于是看起来像重复功能。

**不是重复的三样（必须保留，别在重构中合并掉）**

1. **浮坞**：对话进行中的即时反馈，回答「现在有没有东西在替我干活」。它不是列表，是状态指示器。
2. **运行检查器的时间线**：run 级工具调用与失败证据，是排障入口。列表替代不了。
3. **池条目的可复用语义**：`sub_session_id` 可 resume、`task_count`、`last_success`、`sleeping/idle` —— 这些字段在 run 维度不存在。

## 四、真正缺的那一块

缺的不是「合并两个列表」，而是**从运行到复用的桥**：

- 一个正在跑、跑得好的子代理，现在**没有入口**把它「收养」成池条目（用户只能靠父代理显式 `pool_action=create`）
- 反过来，池条目被 resume 后产生的新 run，在运行检查器里看不出它来自哪个池条目

没有这条桥，两套东西永远是各管一段，用户只能记住「哪边看什么」。

## 五、建议方案：一个入口、两个页签、一条桥

### 5.1 信息架构

「子代理」入口（现有导航按钮）打开一个面板，两个页签：

```
┌─ 子代理 ─────────────────────────────────┐
│ [ 运行中与最近 ]  [ 持久池 ]      搜索     │
├──────────────────────────────────────────┤
│ 运行中与最近                              │
│  ● paused-tests   运行中  44 请求  1m44s  │
│     └ 查看时间线 / 收养为池条目            │
│  ✓ anomaly-detector 已完成  11/11 全绿    │
│  ✗ paused-status    失败    search_grep…  │
├──────────────────────────────────────────┤
│ 持久池                                    │
│  ● frontend-ui    空闲  任务1  最近 12:26 │
│     └ 唤醒 / 休眠 / 销毁 / 改名            │
└──────────────────────────────────────────┘
```

- **页签一「运行中与最近」** = 现在的运行检查器列表（数据源不变：run store + 事件流）
- **页签二「持久池」** = 现在 `agent_pool` 面板（数据源不变：池 API）
- 点任一条目 → 右侧详情（时间线 / 条目详情），复用现有两种详情视图

**不做的事**：不合并数据源。两个源语义不同，合并成一个 API 只会把「run」和「池条目」两种实体糊成一种。

### 5.2 那条桥：`收养为池条目`（P1）

运行详情里加一个动作：把本次 run 的 `sub_session_id` 注册成池条目
（调既有 `pool_action=create` 的语义，不新增服务）。约束：

- 只有**可续跑终态或运行中**的 run 允许收养（`failed` 不允许，除非显式覆盖）
- 收养后池条目 `name` 默认取 run 的 `display_name`，重名按既有 `-2/-3` 规则加序号
- 必须留 `owner_session_id` / `owner_agent_id`（归属 fail-closed 已经实现）

### 5.3 反向可见性（P2）

池条目的 run 在运行检查器里带一个徽标「来自池 `frontend-ui`」。数据已有（`agent_pool.sub_session_id` ↔ run 的 `sub_session_id`），只需联表。

## 六、实施顺序

```
P0  合并入口为两页签（纯前端重排，数据源与后端均不动）
P0  修文案：管理面板标题改「持久池」，消除「子代理面板看不到子代理」的歧义
P1  「收养为池条目」动作
P2  池条目 ↔ run 双向徽标
```

P0 是**纯前端**改动、可独立回滚，且立刻消除用户当前的困惑。

## 七、风险与不可做

1. **不要把 `session_sub_agents` 的 1600+ 历史行直接塞进页签一**。那是投影表，含大量已结束记录；页签一的语义是「运行中与最近」，必须有时间窗（复用现有「近 7 天」过滤）。
2. **不要让池面板回退成「所有子代理」**。池条目的核心价值是可复用与可寻址（`pool_name`）；把一次性 run 混进去会让 `pool_action=execute` 的寻址语义崩掉。
3. **不要在列表里显示完整 `sub_session_id`**。已有短 ID（后 6 位）+ 复制入口，足够定位。
4. 浮坞不要与面板合并。浮坞是**运行中**的状态指示器，面板是**管理**界面，刷新频率与交互模型不同（此结论来自 DSH 的教训：同一面板既管任务又管成员会两边都做不好）。

## 八、待用户裁定

1. 是否接受「一个入口 + 两页签」，而不是保留两个独立入口？
2. 页签一的时间窗默认多久（建议「运行中 + 近 7 天」，与现有过滤器一致）？
3. 「收养为池条目」是否允许对**运行中**的 run 操作（建议允许，但要求先 pause，避免同一 sub_session 被两个调度方持有）？

## 九、v2 修订（用户 2026-11-21 14:21 二次裁定）

> 「而且功能上重复，并且都不完善。」

这条纠正把问题从「两个列表长得像」提升到更根本的层次。

### 9.1 重新定位：错在锚点，不在布局

现在的两个界面**分别锚定在两种存储实体上**：

- 运行检查器锚定 `run`（一次执行）
- 池面板锚定 `pool_entry`（一条可复用注册）

但用户脑子里的实体是**一个子代理**。子代理的身份是 **`sub_session_id`**：

| 数据源 | 与 `sub_session_id` 的关系 | 回答什么 |
|---|---|---|
| `session_sub_agents` | 主键 | 它是谁（名字/头像/职责/模板/状态） |
| `runs/*` + `subagent_runs` | 一对多（每次执行一条） | 它干过什么、现在在不在跑 |
| events / `TokenUsageEvents` | 挂在 run 上 | 它怎么干的、花了多少 |
| `agent_pool` | 一对一（可选用，唯一索引 `IX_agent_pool_sub_session`） | 它能不能被复用、能不能被寻址 |

**所以正确形态不是「两页签」，而是一个以 `sub_session_id` 为锚点的工作台**：
列表按子代理聚合（一次执行只是它的一条记录），详情里再分页签。
「两页签」只是把两个半成品并排，问题原样保留。

### 9.2 「都不完善」的具体缺口（逐条有据）

**运行检查器（锚定 run）缺**

| # | 缺口 | 现状 |
|---|---|---|
| 1 | 无任何动作入口 | 不能 resume / pause / destroy / 收养；只能看 |
| 2 | Token 无口径 | 显示 `1.72M` 累计值，既不标"累计"，也不给当前上下文占比 |
| 3 | 无成本、无缓存命中率 | 界面只有模型/轮次/Token/工具；`TokenUsageEvents` 里两者都有 |
| 4 | 轮次仍显示 `24/600` | 固定计数器未移除（P1 未做） |
| 5 | 思维链只存 4,096 字符 | 实测单轮最长 118,795 字符（P1 未做） |
| 6 | 无法跳到该 run 在对话中的位置 | — |
| 7 | 按 run 平铺，同一子代理多次执行各占一行 | 看不出「这个子代理一共跑过几次、成功率多少」 |

**池面板（锚定 pool_entry）缺**

| # | 缺口 | 现状 |
|---|---|---|
| 1 | 全部只读 | 不能创建 / 唤醒 / 休眠 / 销毁 / 改名 |
| 2 | 详情没有它的 run 列表 | 「任务数 1」是个数字，点不进去看是哪一次 |
| 3 | 头像/职责不可编辑 | `avatar_key` 为空时只能回退生成 |
| 4 | 模型显示 `–` | `model_id` 为空（列刚加，历史条目没值） |
| 5 | 看不到不可复用的子代理 | 一次性 spawn 完全缺席 |

**两者共缺**：父子链（`owner_session_id` / `owner_agent_id` 有数据、无展示）、历史成功率与耗时趋势、成本报表（汇总 API 已有、前端未接）。

### 9.3 建议形态：子代理工作台

```
┌─ 子代理工作台 ────────────────────────────────────────────┐
│ [全部] [运行中] [可复用] [异常]         搜索名字/职责       │
├──────────────────┬──────────────────────────────────────┤
│ ● paused-tests   │ [概览] [运行历史] [轨迹] [用量] [动作]│
│   运行中 · 1m44s │  头像  paused-tests        [运行中]   │
│ ✓ anomaly-detect │  模板  workspace-task-agent           │
│   已完成 · 11/11 │  职责  为 paused 状态词表补测试…      │
│ ⚠ paused-status  │  归属  parent=鲸鲸 · run_20261121_…   │
│   失败 · 44 请求 │  ── 用量 ──────────────────────────    │
│ ● frontend-ui    │  累计 3.80M · 上下文 8.2% · 命中97.6% │
│   空闲 · 可复用  │  成本 $0.52 · 11 次工具 · 2 失败      │
└──────────────────┴──────────────────────────────────────┘
```

关键差异（与 v1 建议相比）：

1. **左列按子代理聚合**，同一 `sub_session_id` 的多次 run 合并成一条，显示最近一次状态 + 总次数/成功率
2. **「可复用」是一个维度，不是另一个界面**：池条目在列表里就是一个徽标 + 一个动作，不再单独开面板
3. **动作页签是必须品**：resume / pause / destroy / 收养为池条目 / 改名 / 设置职责 —— 没有动作，界面就只是日志查看器
4. **用量页签一次做全**：累计 tokens、当前上下文占比（`ConversationTokens / maxContextTokens`，上限已有）、缓存命中率、成本（含「未登记」态）、按 run 的趋势

### 9.4 最小可交付（避免又做成半成品）

**P0 — 只做「聚合 + 只读完整」**（纯前端 + 一个聚合 API）

- 新 `GET /api/admin/sub-agents?window=…`：按 `sub_session_id` 聚合，联 `session_sub_agents` + `agent_pool`，挂最近 run 摘要
- 工作台左列 + 概览页签 + 用量页签（接已上线的 `usage/summary`）
- 池面板**不再单独存在**，降级为列表上的「可复用」徽标
- **判据**：`paused-tests` 必须出现在左列（它现在不在任何管理界面）

**P1 — 动作**

- resume / pause / destroy（复用既有通道）、收养为池条目、改名与设置职责
- **判据**：每个动作都有失败面文案（未就绪/归属不匹配/不存在），复用 S5d 的五类映射

**P2 — 轨迹与成本报表**

- 轨迹页签（复用现有 run 事件 API + 思维链容量策略）
- 成本报表与阈值告警

### 9.5 明确不做

1. 不做「两页签并列」—— 那只是把两个半成品并排
2. 不合并数据源为一个表 —— run 与 pool entry 语义不同，联表聚合即可
3. 不把 `session_sub_agents` 的 1,600+ 历史行无过滤塞进列表（必须有时间窗与状态过滤）
4. 不删运行检查器的**时间线**视图 —— 它是排障唯一入口，搬进「轨迹」页签即可
5. 不在 P0 就动固定计数器与思维链落盘 —— 那需要 P0-b 的 `paused` 刹车先上线（护栏顺序不可颠）

### 9.6 与在飞工作的关系

`paused` 状态词表（P0-b1）与检测器接线（P0-b2）**不受本重构影响**，继续推进：
工作台的「动作」页签正是 `paused` 的消费方，两者在 P1 汇合。
