# 子代理池生命周期护栏设计：卡在 busy 的条目怎么救

## 范围

只回答一个问题：**一个条目被写进 `busy` 之后，如果驱动它的那次执行再也收不了尾，谁能把它救回来。**

不含：容量淘汰、LRU、软删（已有实现）、子↔子通信（另立一篇）。本文**不动代码**，只定设计。

## 现状（全部现场核对）

### 复位判据是状态驱动的，不是顺序驱动的

`AgentPoolEntryStore.ResetStaleBusyAsync` 只把满足下列条件的行从 `busy` 改成 `sleeping`：

```
status = 'busy' AND deleted_at IS NULL
AND NOT EXISTS (SELECT 1 FROM sub_agent_runs
                WHERE sub_session_id = p.sub_session_id
                  AND status IN (<非终态集合>))
```

非终态集合取自 `SubAgentRunEntity.NonTerminalStatuses`，而它的实际内容只有一项：`running`。

这让复位**不会误杀真正在跑的条目** —— 即使复位跑得比 run 恢复更早，那些还有 `running` run 的条目也不会被碰。

### 复位只有一个调用点，而且是一次性的

生产代码里 `ResetStaleBusyAsync` 唯一调用者是 `SubAgentPool.TryRecoverStaleBusyAsync`，它在池初始化末尾执行一次（`SubAgentPool.cs:281`）。之后**没有任何重试、没有周期巡检**。

### 单次调用的后果：可能整轮空转

宿主启动时两条链是并发的：

- `SubAgentPool` 初始化 → 一次性复位
- `SubAgentConversationProjectionWorker.ExecuteAsync` → `RecoverInterruptedRunsAsync` 把上一进程遗留的 `running` 标成 `interrupted`（终态）

若池的复位先落地，此刻 run 仍是 `running` ⇒ 复位返回 0、什么也不改；等 worker 把 run 收成终态时，复位这一次机会已经用掉了。**条目停到下次重启为止。**

源码注释把这条写成了自觉的取舍：

> 而反过来只是少救一条，下次重启还有机会。

也就是说：安全性（不误杀）是刻意保住的一侧，活性（能救回来）是刻意让出的一侧。这不是未发现的缺陷，是**已接受的代价**。本文的任务是在不退让安全性的前提下把这一侧补回来。

### 卡住之后的两条真实后果

1. **该条目再也驱动不了。** `TryAcquireAsync` 的守卫是 `status IN (idle, sleeping)`，`busy` 直接被拒。
2. **本进程也收不了尾。** 收尾走 `FinishAsync` 的三重校验，其中一项要求内存里的 `ActiveExecutionId` 令牌与执行时一致；上一进程的令牌本进程根本不存在 ⇒ 判定为 stale completion 丢弃，状态不动。

所以「等它自己好」这条路不存在。

### 现有逃生口

管理面「销毁 → 重建」（`58d4413`）能解，代价是丢掉 `sub_session_id` 与 KV 缓存身份 —— 也就是丢掉了持久顾问最值钱的那部分。

管理面 PATCH **不提供改状态**（只允许 `responsibility` / `avatarKey` / `modelId` / `role`），这是刻意的：状态必须经池的令牌路径写，否则会与内存缓存分叉。

## 风险分级：为什么不是 P0

- 触发条件是「进程在 busy 窗口内崩溃」或「运行期 run 记录被外部改坏」，不是常规路径。
- 只挡**驱动**，不挡**读**：列表、详情、改备注、改模型照常。
- 有逃生口（销毁重建）。

**但它不是可以无限期搁置的小事**，因为它污染了一个人用来做判断的信号：面板上的「忙碌」再也不能区分「真在跑」与「僵尸」。管理视图的可信度一旦破了，用户就得自己去查库。

## 方案

三条方案的**判据完全相同**（仍以 `sub_agent_runs` 有无非终态行为准），差别只在**什么时候再试一次**。这一点很重要：判据是安全性的来源，不动它就不会引入误杀。

### A. 有限重试

池 Ready 之后，带退避重试若干次（例如 3 次，间隔 2s / 5s / 10s）。

- 优点：改动最小，只碰池内部。
- 缺点：只是把窗口撑大，没有消除顺序依赖；崩溃发生在**运行期**（不是启动期）时依然救不回来。

### B. 顺序显式化

让跑完 interrupted-run 恢复的那一方**回调**池做一次复位，把「先恢复 run、再复位池」从时序巧合变成显式契约。

- 优点：直接消灭启动期的竞态根因，不靠等待。
- 缺点：引入一条 projection worker → 池的依赖边，要先确认不成环。

### C. 周期巡检

池暴露一个幂等的 `SweepStaleBusyAsync`，由既有维护类 worker 周期调用（例如每 10 分钟），判据不变。

- 优点：这是唯一能覆盖**运行期**成僵尸的形态（进程好好的，run 记录却被写成非终态且无人收尾）。幂等，可反复调用。
- 缺点：需要定周期；最坏情况下条目在窗口内最多多卡一个周期。

### 推荐：B + C

B 消除启动期竞态，C 覆盖运行期。A 只在 B 因依赖方向不可行时作为兜底。

**不动判据、不动收尾三重校验、不给管理面开改状态的 PATCH** —— 这三样是当前「库为真源」结论的支点，动它们换来的便利不值得。

## 不采纳

| 方案 | 否决理由 |
|---|---|
| 按 `last_used_at` / `updated_at` 超时直接杀 busy | 会杀掉「慢但真在跑」的条目；而且等于给「还在跑」再立一套时间口径，与 run 表这个唯一真源冲突 |
| 管理面 PATCH 直接改 status | 绕过池的执行令牌，与内存缓存分叉；重启后被 `LoadAllAsync` 从库复活成另一个状态 |
| 启动时把所有 busy 一律复位 | 多进程共享同一 SQLite 时会把另一个进程正在驱动的条目重置，导致两个执行驱动同一子会话 —— 正是现判据要防的事故 |

## 验收判据（实现时逐条取红）

1. **不误杀**：fixture 置条目 `busy` + 对应 run 为 `running`；跑复位；断言状态仍是 `busy`。
2. **能救**：同 fixture 把 run 改成 `interrupted`；再跑复位；断言转 `sleeping`。
3. **顺序无关**（这条只有 B/C 才过、A 的短重试窗口内也可能过但不可靠）：先让复位在 run 仍 `running` 时跑一次（断言 no-op）→ 再把 run 收成终态 → 触发 B/C 的复位 → 断言转 `sleeping`。

第 3 条是本次设计的核心判据：**去掉 B/C 的后一次触发，它必然失败**。没有这条，方案 A 和 B/C 在测试上无法区分。

## 待定

1. **C 的周期与阈值**：建议周期 10 分钟；是否需要额外「busy 持续超过 N 分钟」的二次门槛（当前判据不含时长，纯状态驱动，加时长会引入第二套口径 —— 我倾向不加）。
2. **B 的依赖方向**：`SubAgentConversationProjectionWorker` 目前只依赖 `ISubAgentRunStore` 与 `ISessionStateManager`。若它要回调池，需确认 `ISubAgentPool` 的注册不反向依赖 run store（成环则改用 C 单方案，或让池订阅一个「run 恢复完成」的轻量通知接口）。

## 与既有结论的关系

`子代理池真源审计-2026-11-24.md` 的结论是「单一真源在库、内存是易失缓存」。本文是它的**推论**：既然库是唯一权威，那么「库里有行、但没有任何活着的执行者认领它」就必须有一个常规的回收通道，否则权威表里会长期积累无人认领的 `busy`。护栏不是给内存打补丁，是给这条权威链补上收尾。
