## 二、根因（三源取证，互相独立）

### R1 直接原因：运行中的宿主进程**从未加载过 SKILL Hub 后端**

| 证据 | 值 |
|---|---|
| 进程 | `PuddingAgent.exe` PID **40992**，启动于 **2026-09-21 10:40:39** |
| 该进程实际加载的 `PuddingPlatform.dll` | `Source\PuddingAgent\bin\Debug\net10.0\` → **修改时间 09:47:07** |
| `SkillHubController.cs` 源码时间 | **16:09:51**（晚于 DLL 近 6.5 小时）|
| 字符串探测（部署 DLL） | `skill-hub` / `SkillHubController` / `SkillHubService` / `SkillHubSchemaBootstrapper` **全部 `False`** |
| 字符串探测（源码构建产物，19:28:26） | 同样四项 **全部 `True`** |

⇒ B1/B1.1/B2/B3 全部在这台宿主启动**之后**才落地。**`/api/skill-hub/*` 15 个端点从未上线**。

### R2 放大器：未命中的 `/api/*` 被 SPA 回退成 **200 + HTML**

`Source/PuddingHost/Extensions/PuddingWebApplicationExtensions.cs`（修复前）：

```csharp
// ── Chat SPA fallback ──────
var chatIndexPath = Path.Combine(outputWwwRoot, "index.html");
if (File.Exists(chatIndexPath))
{
    app.MapFallback(() => Results.File(chatIndexPath, "text/html; charset=utf-8"));
}
```

无约束的 `MapFallback()` 会兜住**所有**未命中路由，**包括 `/api/*`**。

**活体对照实验**（`Invoke-WebRequest`，未带 Token）：

| 请求 | 结果 | 判定 |
|---|---|---|
| `/api/skill-packages`（确实存在的路由） | **401** | 路由命中 → `[Authorize]` 拦截 |
| `/api/skill-hub/stats` | **200 `text/html`**，体为 `<!DOCTYPE html>...` | **路由未命中** → 回退成 `index.html` |
| `/api/skill-hub/skills?pageSize=5` | **200 `text/html`**，同上 | 同上 |
| `/api/skill-hub/installs?pageSize=5` | **200 `text/html`**，同上 | 同上 |
| `/api/definitely-not-a-route-xyz`（对照组） | **200 `text/html`**，同上 | 与上面三者**完全同款** |

⇒ 前端 `request()` 正常 resolve 出一个 **HTML 字符串**，无异常、无 4xx、无 5xx。

### R3 前端：响应形状不做校验，非数组直接进数组槽位

`Source/PuddingPlatformAdmin/src/pages/skill-management/SkillsTab.tsx`：

```ts
const data = await listHubSkills({ ... });
setItems(data ?? []);        // ← data 是 HTML 字符串时，?? 不生效（字符串非 nullish）
...
{items.map((item) => (       // ← :339 崩溃点
```

`?? []` 只兜 `null`/`undefined`，**兜不住类型错误**。四个 Tab 均有此模式：

| 文件 | 行 | 写法 |
|---|---|---|
| `SkillsTab.tsx` | 79 | `setItems(data ?? [])` |
| `EventsTab.tsx` | 40 | `setEvents(data ?? [])` |
| `EvoMapTab.tsx` | 44 | `setSkills(data ?? [])` |
| `OverviewTab.tsx` | 24 | `setStats(data ?? null)` |

### R4 事故链

```
后端路由未部署（R1）
  → 请求未命中
  → SPA 回退返回 200 + HTML（R2）        ← 放大器：把「404」伪装成「成功」
  → 前端 resolve 出字符串
  → setItems(字符串)
  → 渲染期 items.map 抛 TypeError（R3）   ← 白屏，且错误信息指向无用的栈
```

**R2 是本次最危险的一环**：它让「端点不存在」这条本应一目了然的错误，变成了一次**静默的类型污染**。

## 三、修复（已推送）

### F1 平台侧：`/api/*` 未命中一律 404（JSON），不得进入 SPA 回退

`Source/PuddingHost/Extensions/PuddingWebApplicationExtensions.cs`

```csharp
app.MapFallback((HttpContext context) =>
{
    if (context.Request.Path.StartsWithSegments(
            "/api", StringComparison.OrdinalIgnoreCase))
    {
        return (IResult)Results.Problem(
            statusCode: StatusCodes.Status404NotFound,
            title: "API endpoint not found",
            detail: $"No endpoint matches {context.Request.Method} {context.Request.Path}.");
    }

    return (IResult)Results.File(chatIndexPath, "text/html; charset=utf-8");
});
```

- 保持 `/admin/{*path:nonfile}` 回退不变（该模式已限定前缀，不与 `/api` 冲突）
- 前端页面路由（非 `/api`）回退行为**零变化**

### F2 前端侧：API 边界增加响应形状断言

`Source/PuddingPlatformAdmin/src/services/platform/api.ts`（Skill Hub 段，10 个函数）

新增私有守卫 `requireArray<T>` / `requireObject<T>` + `describeShape`：

```ts
async function requireArray<T>(pending: Promise<unknown>, label: string): Promise<T[]> {
  const data = await pending;
  if (!Array.isArray(data)) {
    throw new Error(`${label}：服务端返回的不是数组，实际为 ${describeShape(data)}。${SHAPE_HINT}`);
  }
  return data as T[];
}
```

效果：把「静默错值 + 白屏」升级为「**可读异常 + 空态 + `message.error`**」。
`describeShape` 会明确指出 *HTML 文本（N 字符，疑似 SPA 静态回退页）*。

**冻结签名（设计文档 §7.2）未变**，仅在边界加断言。

## 五、遗留：生效需要一次宿主重启（未自行执行）

`outputWwwRoot = AppContext.BaseDirectory/wwwroot`，而 `PuddingHostContent.props` 负责 `dist → wwwroot/admin`。
因此「后端路由 + 前端加固」两者都必须经**重建宿主 + 重启进程**才生效；且运行中的进程**锁定**了 `bin\Debug\net10.0\*.dll`，构建阶段即会撞 `MSB3027`。

**未自行重启的原因**（不是遗漏）：

1. 重启会终止**本 Agent 自身所在宿主**的当前回合；
2. 会打断同宿主内 6a8 / 258 的在途工作；
3. 协作协议 v1.2 §11 将「重启节奏」归 6a8 排期，且我已就本特性申请过窗口。

**待办**：在协调窗口执行「停止 → `dotnet build Source\PuddingAgent\PuddingAgent.csproj` → 启动」，随后按设计文档 §9 做端到端联调（11 个 action + 六 Tab 真数据）。

## 六、防复发

| 措施 | 说明 |
|---|---|

### 本次暴露的部署陷阱（建议纳入发布清单）

> **`wwwroot/admin` 与 `bin/*.dll` 会各自独立更新。**
> 本次现场：前端产物刷新于 19:22，后端 DLL 停留在 09:47。
> 发布后必须同时核对两者时间戳，否则会出现「界面是新的、接口是不存在的」这种最难排查的组合。
