## 七、Iteration 3：受控检查读输出头部 ⇒ Test 类检查恒报 test_count_unknown（平台缺陷修复）

**现象**：Iteration 1/2 的 `lastVerdict` 恒为
`blocked / criterion_failed / test:Source/PuddingPlatformTests/PuddingPlatformTests.csproj: test_count_unknown`；
且 Iteration 2 已把会话侧证据修正为英文可解析摘要后**仍然复现**（verdict 时间 14:09:42Z 晚于该修复）
⇒ 说明验证器取的不是我会话的输出，假设被推翻。

**定位过程（读代码，不靠猜）**：
1. `search_grep test_count_unknown` → `GoalCheckFailureCodes.TestCountUnknown`（`GoalCheckDefinitionRegistry.cs:168`）、
   `GoalCheckEvidencePolicy.cs:23`、抛错点 `GoalCheckRunner.cs:269`。
2. 关键发现：测试证据**不是**取会话输出，而是由平台**自己执行受控检查**并采集输出 ——
   `GoalCheckRunner`（经 `ITerminalProcessManager`，与 terminal 工具同一后端）→ `GoalCheckOutputParser.ParseTestSummary`。
3. 检查命令来自版本化注册表 `GoalCheckDefinitionRegistry`：
   - Build = `dotnet build {0} --no-restore --nologo`
   - Test  = `dotnet test {0} --no-restore --nologo`（**全量、无 filter**）
4. Parser 已同时支持英文与 zh-CN 干净摘要（`Failed: N, Passed: N` / `失败: N，通过: N`）⇒ **locale 不是本次病因**。
5. **真因**：`GoalCheckRunner` 中
   ```csharp
   private const int MaxCapturedLines = 400;
   var snapshot = await processManager.ReadOutputAsync(process.ProcessId, 0, MaxCapturedLines, null, ct);
   ```
   `offset` 契约为 0-based 行号 ⇒ 只读**前 400 行**；而全量 `dotnet test` 在本仓输出远超 400 行
   （实测本次 473 行；`dotnet build` 光警告就 928 行），**VSTest 汇总行在末尾必然被截掉** ⇒
   `ParseTestSummary` 返回 null ⇒ exitCode=0 走 fail-closed 报 `TestCountUnknown`。

**修复**（commit `46b9aa76`）：
- `GoalCheckRunner.cs`：先 `probe = ReadOutputAsync(pid, 0, 1, null)` 取 `TotalLines`，再以
  `readOffset = max(0, TotalLines - MaxCapturedLines)` 读**尾部** 400 行；probe 失败回退 offset=0（旧行为）；
  fail-closed 分支与 `lines` / `exitCode` / `unfinished` 语义零改动。
- `GoalCheckRunnerTests.cs`：`StubProcessManager.ReadOutputAsync` 改为**真实切片**（正确填
  `Offset/NextOffset/TotalLines/Truncated`）—— 此前恒返全量会把「只读头部」这类缺陷完全掩盖；
  新增回归锁 `Run_LongOutputWithTailSummary_StillParsesSummaryAndPasses`（500 行 NU1903 噪声 + 末尾汇总行）。

**验证证据**（父级 `terminal_start` 真实执行；英文可解析摘要）：
```
Results File: E:\github\AgentNetworkPlan\PuddingAgent\.tmp-test-out\goal-check.trx

Passed!  - Failed:     0, Passed:    19, Skipped:     0, Total:    19, Duration: 6 s - PuddingPlatformTests.dll (net10.0)
TEST_EXIT_CODE=0
```
**活证据**：该次运行输出共 **473 行**，汇总行位于**第 473 行（末尾）** —— 旧逻辑读取前 400 行恰好把它截掉，
即 `test_count_unknown` 的现场复现。

**影响面**：所有走 Test 类受控检查的 Goal 目标 —— 只要仓库输出量超过 400 行，Test 检查**永远无法通过**
（Goal 目标因此被无限 blocked）。本修复同时惠及 Build 类检查（`Build succeeded` 标记同在输出末尾）。

## §12 · Iteration 12：真根因（第三层）—— Exited 时 Dispose 丢弃末尾输出（2026-09-17）

### 12.1 现场证据：末尾行从未进入缓冲
`D:\data\logs\components\terminal\d9fc5f167933.log`（**epoch7 那次 test 检查**的终端日志）：
共 **141 行**，末尾 14 行全部是 MSBuild 警告（`…warning MSTEST0037: …`），
**没有 VSTest 汇总行**（`Passed! - Failed: N, Passed: N`）。
⇒ 证明是「行没到缓冲」，而非「读了但没读到」。

### 12.2 代码根因
`TerminalProcessManager.StartAsync` 的 `process.Exited` 处理器：
```csharp
tp.ExitCode = process.ExitCode;
…
await logWriter.DisposeAsync();
process.Dispose();        // ★ 早于异步输出投递完成
```
.NET 明确：启用输出重定向时，`Exited` 可能在 stdout/stderr 的异步处理完成**之前**触发；
立即 Dispose 会关闭底层流并丢弃尚未投递的末尾行。

⇒ 这解释了为何前两轮修复都无效：
| 层 | 修复 | 为何不足 |
|---|---|---|
| 行窗口 | `46b9aa76` 改读尾部 | 行在缓冲里，但字符预算把窗口截断 |
| 字符预算 | `fde428d7` 显式 200 000 | **行根本不在缓冲里** |
| **输出排空** | **本次 `bca022c8`** | — |

### 12.3 修复
`Exited` 处理器在 Dispose 前先 `await Task.Run(() => process.WaitForExit())`
（无参语义 = 等待重定向输出的异步事件**全部处理完毕**），
`Task.WhenAny(drain, Task.Delay(5000))` 作上限（超时只记警告，不阻塞清理）。
无死锁依据：channel 为 `CreateUnbounded`（handler 的 `WriteAsync` 不背压），
handler 为 `async void`（不阻塞 async 读取线程）。

### 12.4 验证
新增 `TerminalProcessManagerOutputDrainTests`（MSTest）：2000 行输出 + 末行 marker，
按 `TotalLines` 断言（**与读窗口无关，直接检验「行是否在缓冲中」**）。
```
dotnet test Source/PuddingRuntimeTests/PuddingRuntimeTests.csproj \
  --filter "FullyQualifiedName~TerminalProcessManagerOutputDrainTests"
→ EXIT=0
```

### 12.5 排查中发现的测试写法坑（已固化到记忆）
- `ReadOutputAsync(pid, 0, null, null)` 的 `maxLines=null` 默认 **200 行**（不是全部）——
  首版测试因此误判（`captured 2091 chars` ≈ 200 行）。
- 命令经 `ProcessStartInfo.ArgumentList` + `cmd /d /s /c` 传递时**内嵌引号会被转义错乱**
  （`call "path"` 退化成 cmd 报错），测试须用**无引号**的内联命令。

### 12.6 影响面
所有经 `ITerminalProcessManager` 读取**已退出进程**输出的场景（受控检查、terminal 工具回读路径）
都受益；「进程运行中实时订阅」（`SubscribeAsync`）不受影响。
