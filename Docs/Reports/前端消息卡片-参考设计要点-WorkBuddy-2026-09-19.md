## 一、用户红字批注（原文，最高优先级）

1. **「详细的命令行会折叠」** —— 指向步骤行 `List workspace folders and files`。
2. **「点击之后展开」** —— 指向同一行，展开后显示 `bash` 代码块（真实命令全文）+ 底部 `✓ 运行成功`。
3. **「整体的配色和字体很好」** —— 明确正向认可配色与字体。
4. **「这里会显示最新的状态」** —— 指向底部状态行中的 `正在准备执行命令`。

## 二、从截图提取的结构（自上而下）

### 1) 消息头（Header meta）
```
WorkBuddy   预计消耗 ◇0.62 ~ 12.25
已处理 4m
```
- Agent 名称 + **成本预估区间**（`预计消耗 ◇min ~ max`）
- **实时**耗时（`已处理 19s` / `50s` / `3m30s` / `4m`）—— 会随执行推进刷新

### 2) 过程区（步骤行统一样式）
每行 = **小图标 + 灰色弱化动作标签 + 内容 + 可选折叠箭头 `⌄`**：

| 观察到的行 | 语义 |
|---|---|
| `⌘ 运行命令 ⌄` | 命令分组标题 |
| `⌘ List workspace folders and files ⌄` | 具体命令（折叠态只显示人类可读摘要） |
| `⌘ 运行校验、修改：collect_pkg_info.py` | 脚本类操作 |
| `⌘ 运行 数据采集完成（559` | 执行结果摘要 |
| `⌘ 处理、查看文件：tencent-docs-routing` | 文件/技能处理 |
| `✎ 编辑 C:\Users\...\build.py  +13 -5` | 编辑操作，**带 +/- 行数** |
| `深度思考` | 推理块标签（灰） |

### 3) 推理块（深度思考）
- 标签为**灰色弱化**文字
- 正文用**左侧竖线（quote bar）**包裹，内容为原始推理，内部可滚动（右侧可见滚动条）

### 4) 折叠/展开交互
- 默认**折叠**：只显示命令的人类可读摘要
- 点击行 → 展开为**带语言标签的代码块**（示例中标签为 `bash`），显示完整命令/脚本
- 代码块底部有**结果态**：`✓ 运行成功`

### 5) 底部实时状态行
```
正在准备执行命令   ｜  已消耗 ◇4.9   ｜  想少看字多得料？设置-个性化里选"高效务实"，信息密度拉满
```
- **左侧 = 当前最新状态**（用户批注重点，需实时刷新）
- 中间 = 已消耗
- 右侧 = 弱化的提示/轮播文案

### 6) 流式过程中的最小态
- 起始：`准备中`
- 生成中：`✎ 生成中  +19 -0`
- 写入：`正在写入文件 ｜ 已消耗 ◇0.62 ｜ <模型说明>`

### 7) 叙述文本
助手自然语言说明**内联在步骤之间**（例：「工作区当前没有子文件夹，只有 6 个文件（上面列表）。接下来我用 ADB 收集全部应用的包信息，然后生成表格文件。」），**不另起独立气泡**。

## 三、配色与字体观感（定性）
- 整体为**中性灰阶**基底，正文高对比，标签/辅助信息**明显弱化**
- 卡片为**浅色、大圆角**，用户气泡右对齐
- 代码块为**浅灰底 + 等宽字体 + 语言标签**
- 状态/结果用极小号图标 + 文字（`✓` / `⌘` / `✎`）
- 无强烈彩色强调，仅图标与状态点缀

## 七、实施切片建议（父级规划，2026-09-19）

为便于并行/回滚，本卡拆为 4 个**原子切片**，每个切片独立提交、独立可验证。**不要一次性全做**。

### S1 — 步骤行归一两态 + 展开代码块 + 结果态（对应批注 1、2）
- 把现有各步骤行（运行命令 / 运行脚本 / 处理查看文件 / 编辑）统一为**同一组件与样式族**：`小图标 + 弱化灰色标签 + 人类可读摘要 + 展开箭头`
- 默认**折叠**只显示摘要；点击展开 → **带语言标签的代码块**（`bash` 等）+ 块底**结果态**（成功/失败）
- 判定完成：组件测试同时覆盖「折叠」与「展开」两条分支；无样式分叉
- 风险点：既有 `ActivityGroup`（默认展示最近 6 项）的折叠语义要**保持不变**，只改行内呈现

### S2 — 底部实时状态行（对应批注 4）
- 显示**当前最新活动**文案，随执行推进实时更新；空闲/完成态有确定性文案
- 判定完成：有一次真实的「状态随活动变化」的证据（前后两次取值不同）
- 风险点：不得停留在过期状态（需确认数据源是实时流而非一次性快照）

### S3 — 消息头元信息 + 流式最小态（对应模式 1、5）
- 消息头补齐 `预计消耗 <min> ~ <max>` 与**实时** `已处理 <时长>`（需真实递增）
- 流式最小态：`准备中` → `生成中 +N -M` → `正在写入文件`，**禁止空白卡片**
- 依赖：需确认后端/前端是否已提供耗时与成本数据源（见差距分析 C 问）

### S4 — 观感对齐（对应批注 3）
- 标签与辅助信息**弱化配色**；推理块改用**左侧竖线（quote bar）** 容器
- 整体保持中性灰阶；正文与代码块对比度符合可读性
- 判定完成：无新增固定 px 宽度；未复活任何已清理死样式键

### 通用要求（每个切片都适用）
- 切片提交信息须写明对应批注编号（如 `refs annotation 1/2`），便于回溯用户诉求
- 每切片完成后**必须** `pnpm run build`（含 `check-chat-bundle-budget.cjs`）

  `dist/index.html` 与 `Source/PuddingAgent/bin/Debug/net10.0/wwwroot/admin/index.html` 必须一致

## 九、交互模型修正（用户 2026-09-19 补充，覆盖 §二 的简化理解）

### 用户原话（权威）
> 「实际上 workbuddy 的做法是给可以展开的元素使用不同的样式，当鼠标悬停的时候，显示 `>`，点击的时候，展开下一级的元素，**这个过程是可以多级的**。」

配 2 张对照图：同一行 `运行校验、修改：collect_pkg_info.py` —— 图 1（非悬停）**无箭头**，图 2（悬停）出现 **`›`**。

### 修正前的错误理解
我在 §二 §4 把「折叠/展开」简化成了**单级的显隐切换**（折叠显示摘要 ⇄ 展开显示详情）。**这是错的**。真实模型是：

**渐进披露（progressive disclosure）三要素**
1. **可展开元素用不同样式**（与不可展开元素视觉可区分）
2. **悬停才显现折叠箭头**（`›` 折叠 / `⌄` 展开），非悬停时保持占位不跳动
3. **点击展开下一级，且可多级嵌套**（层级递归，不是单级切换）

### 我方现状核实（逐条对照，证据已实读）

| # | 用户要求 | 现状 | 证据 |
|---|---|---|---|
1 | 可展开元素用**不同样式** | ✅ **已有** | `styles/execution-flow.styles.ts:26` `rowClickable`（`cursor` + `&:hover` + `:focus-visible` 焦点环 + 最小可点区 32px）vs `:12` 注释「**非可展开行无 hover/焦点反馈**」 |
2 | **多级**展开 | ✅ **已有** | `components/execution-flow/ToolCallTree.tsx` 头注释：「工具调用**递归树**（CU-07）；基于 `ToolNode.children`（父子嵌套调用，投影器 `buildToolTree` 已按 `parentToolCallId` 建树）：**父行 + 缩进子列表递归渲染**」；`ToolCallTreeBranch` 为递归分支 |
3 | **悬停才**显示箭头 | ❌ **差距** | `execution-flow.styles.ts:107` `chevron` 仅定义 `flexShrink / width 16 / height 28 / fontSize 10 / color var(--pudding-chat-text-caption) / transition transform 150ms` —— **无 opacity / visibility 的 hover 门控**；`:119` `chevronPlaceholder { visibility: hidden }` 仅用于**不可展开行**的占位对齐。⇒ 可展开行**常驻显示**箭头 |

**结论：三点里两点已具备，唯一真实差距是「悬停显现箭头」。**

### 新增切片 S1c（严格串行，排在 S1b 之后）

**S1c — 箭头渐进披露**
- 可展开行：**非悬停/未聚焦时箭头不可见**（`opacity: 0`，**保留占位尺寸**以免行首跳动）；**悬停或键盘聚焦时显现**（`opacity: 1`）
- 折叠态箭头 `›`（右向）→ 展开态旋转为 `⌄`（下向）；`transition` 沿用既有 150ms
- **可访问性硬要求**：不得只靠 hover —— 必须同时响应 `:focus-visible`，否则键盘用户无法发现可展开性；箭头需保留可被辅助技术识别的语义（如既有 `aria-expanded`）
- **不得**改动 `ToolCallTree` 的递归结构与 `ActivityGroup`「默认只展示最近 6 项」语义
- 测试：覆盖「非悬停不可见」「hover 可见」「focus-visible 可见」「展开态箭头方向翻转」四分支

### 附带发现：turn 级可折叠头（新增，建议并入 S3）
图 1 顶部为 `已完成 8m52s ⌄` ⇒ **整个 turn 也是可折叠的**，折叠态显示「终态 + 总时长」+ 箭头。
这与 §七 S3「消息头元信息」相关但**不等价**：S3 原计划是"补齐实时耗时"，本项是"**turn 容器本身可折叠**，且折叠态以时长作为标题"。建议在 S3 一并评估，或单列 S3b。

### 10.4 硬约束（源自 gap analysis 风险项，实现时逐条遵守）

1. **tick 必须封装在叶子组件内**（建议新增 `TurnElapsedLabel` 之类的叶子组件）。若把 `useState`/`useEffect` 放在 `AgentMessageBubble` 本体，会**每秒 reconcile 整卡**（含 `TurnContentStream` 大 DOM）。
2. **必须支持注入 `now` prop** 供测试（照抄 `TurnStatus` 的 `nowProp` 约定）；测试**禁止快照**，用确定性注入时间断言。
3. **只在 `isRunActive` 时渲染**。
4. 计时**不得**在 render 内直接调用 `Date.now()` —— 一律经 `now` prop 或叶子组件 state，否则测试不可控。
5. 文案格式与既有 `TurnStatus` **保持一致**（`已处理 <Xs|Xm>`），**不新增第二套时长格式**。
6. `AgentMessageBubble.test.tsx` 对头部有断言 ⇒ 新增展示项**不得破坏既有断言**。

### 11.3 规则

**任何内容块高度超出其上限时 → 限高并转为内部滚动区域，而不是无限撑高卡片。**

1. 推理块展开体（`reasoningFullRow` 等）
2. 工具调用展开体（`turnContentStream` / 命令输出 / 代码块）

### 11.4 硬约束

1. ⚠️ **块级，不是卡级**：不得把整张 `AgentMessageBubble` 变成滚动容器
2. ⚠️ **与既有「清除固定像素上限」清理不冲突，但不得混淆**：此前清理的是**宽度方向**的 `min(720px, 100%)` 类固定上限；本规则需要的是**高度上限**，属必要度量。**不得以「要过体积门禁」为理由省略必要的限高**
3. ⚠️ `currentActivityPanel` 带 `contain: paint` → 会裁剪溢出，须确认与滚动容器不冲突
4. ⚠️ `message.styles.ts:178` 注释记录历史坑：「操作按钮 abs 悬浮与 `TurnStatsLine` 重叠」—— 引入滚动容器后须复核
5. ⚠️ 无障碍：滚动区域须**可键盘访问**（可聚焦 / 内部可聚焦元素可滚到），不得仅依赖鼠标滚轮；不得破坏 `TurnStatus` 的 `aria-live="polite"`（全卡唯一）
