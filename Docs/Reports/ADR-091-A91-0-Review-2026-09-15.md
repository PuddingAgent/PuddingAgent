## 3. 必须修正的代码问题

### F01 / P1：隐式自动审查仍把依赖等待变成拒绝，调用端继续索要授权

位置：`Source/PuddingRuntime/Tools/Approval/InMemoryToolApprovalService.cs:829` 及 `:910`；`Source/PuddingRuntime/Services/AgentFirewall.cs:213`、`:222`。新增分支只覆盖 SubmitAsync；普通工具调用走 CheckAsync/隐式审查，仍仅用 `review.Decision == Approved` 二分。

复现：使用返回 DeferredDependency 的 reviewer，CheckAsync 检查 `python png2jpg.py --help`。结果包含 `Implicit audit denied`、`request_tool_approval` 和 `/authorize shell 10m`；内部还写 ImplicitDenied / Failed。AgentFirewall 更进一步丢弃 approval 的原因，只使用 authorization.Message 并追加审批提示。用户最关心的自动路径仍会空转。

修复：

1. 给 ToolApprovalCheckResult 增加 typed disposition 和 ReasonCode，所有返回分支穷尽映射；不只增加字符串 Message。
2. 隐式 DeferredDependency 输出独立事件与 Deferred 指标，不写 ImplicitDenied、Failed，不建议人工批准；真正 NeedHuman 与 Deny 分开。
3. 通过 FirewallDecision → PuddingToolExecutionService → ToolInvocationService 保留该类型。依赖等待不能增加 RuntimeErrorKind.Tool 的错误/熔断计数，不能被通用拒绝提示改写。
4. 当前 A91-0 修正分类与传播；durable wait 去重/恢复仍按 A91-3 完成，报告中不得提前声称系统已自动恢复。

验收：覆盖显式 Submit、隐式 Check、真正工具执行入口三个层次；缺模型/故障不能返回审批诱导或污染 Agent 工具失败指标；硬拒绝仍拒绝、人工决定仍保持人工路径。

### F02 / P1：AllowFakeReviewer 是生产可绑定的开关，不是测试隔离

位置：`Source/PuddingRuntime/Tools/Approval/LlmToolApprovalReviewer.cs:83`；`Source/PuddingRuntime/Tools/Platform/PuddingToolServiceCollectionExtensions.cs:112`。

复现：生产注册方法 AddPuddingToolRegistry，配置 Reviewer=fake、AllowFakeReviewer=true 即可获得 FakeToolApprovalReviewer，无测试宿主限制。该 reviewer 的默认批准仍能进入执行链。因此“默认关闭”不满足 ADR 的“生产没有 fake 放行路径”。

修复：生产配置不支持 fake，删除 AllowFakeReviewer 及生产 fake 分支。Fake/Stub 通过测试程序集的明确 DI 注册注入；复用测试专用 helper，而不是恢复默认 fake 使测试变绿。默认 llm 的组合测试注入 RecordingToolApprovalLlmClient，验证解析到真实 LlmToolApprovalReviewer；实际 Host 组合另做测试。

验收：普通生产注册，即使传入旧 Reviewer=fake/AllowFakeReviewer=true 配置，也不能解析为 fake；测试可显式注入受控 reviewer。修改夹具时按新的配置契约替换已删除属性，但不能删掉该行为断言。

### F03 / P1：所谓严格 JSON 校验仍可抛异常或接受矛盾的批准

位置：`Source/PuddingRuntime/Tools/Approval/ToolApprovalReviewParser.cs:16–44`。

实测：`null`、`[]`、`1`、字符串根节点触发 InvalidOperationException，而当前只捕获 JsonException；`{"decision":"approved"}` 缺 reason 仍批准；approved + requiresHumanAuthorization=true 仍批准；deferred_dependency + requiresHumanAuthorization=true 仍被标记要人工授权。新增空响应/坏 JSON 测试没有覆盖“语法合法但 schema 不合格”。

修复：在读取属性前校验 root.Object；明确必需字段、非空 reason、字段类型、枚举值和合理数值范围；验证 decision 与授权字段的语义一致性。拒绝/等待结果不得携带生效的批准 scope/allowlist。用稳定 reasonCode 产生协议故障，不依赖大范围 catch 吞掉编程错误。只有已验证合法的 Approved 才进入授权/allowlist 创建。

验收：回归夹具四种非对象根、三种缺字段/矛盾字段；补 approved/denied/need_human/deferred 的正向用例。不能用放宽 parser 或删除正向授权边界使测试通过。

### F04 / P1：reasonCode 在 JSON→契约边界丢失，wire 状态未统一

位置：`LlmToolApprovalReviewer.cs:330` 生成 reasonCode；`ToolApprovalReviewParser.cs:27` 不读取；`PuddingCore/Tools/ToolApproval.cs` 的 ReviewResult、TicketRecord、TicketResult、CheckResult 均无对应字段。

实测：review JSON 有 `approval_review_profile_not_configured`，解析后的类型中不存在 ReasonCode。后续无法稳定区分缺配置、服务不可达、超时、协议错误。RequestToolApprovalTool/ListToolApprovalsTool 使用 ToLowerInvariant 将新状态输出为 `deferreddependency`，而新审查协议使用 `deferred_dependency`；Admin 事件映射也没有专门条目。

修复：为类型契约、存储、事件/指标及工具/API DTO 串通 ReasonCode；服务端产生的 code 和模型文本分开。引入一个共享 wire formatter/parser，明确 `deferred_dependency` 等输出名，覆盖查询过滤和事件展示。不能只在推荐文案里塞 code。

验收：从真实 IToolApprovalLlmClient → parser → service → store → tool/API 的 round-trip 保持原因与状态；重启/列表读取后仍能区分原因。依赖状态缺少 durable 恢复的事实继续明确标注。

### F05 / P1：16 项现有测试回归需要真正修复

位置：`Source/PuddingRuntimeTests/Tools/PuddingToolInfrastructureTests.cs`，失败名称与错误完整列表见证据 JSON。

* 14 项因默认 reviewer 从 fake 改 llm 后，测试组合缺 ILlmInvocationService 而失败。覆盖注册/扫描/工具暴露、Memory/Message 工具及 request_tool_approval 参数校验；不能只检查直接 `new FakeToolApprovalReviewer()` 的用例。
* `InvocationToolApprovalLlmClient_Returns_NeedHuman_Without_Approval_Profile` 仍断言 NeedHuman/人工授权，与新增用例互相矛盾。合并或修订为 DeferredDependency，并断言模型调用次数为零。
* `RequestToolApprovalTool_Uses_Configured_Review_Profile_And_Allows_Exact_High_Risk_Call` 的 AgentInstanceId 断言被改成 null，但 client 实际使用发起 Agent 的身份。按明确的请求归因契约断言调用者 identity 和显式 review profile，不能只删断言，也不能为了旧断言丢失身份隔离。

修复组合 helper 后保留这些测试的原本意图，不能批量 Skip、削弱断言或将产品默认改回 fake。修复必须包含本报告新边界测试与真实消费者集成测试；code_outline 无语法错误不是 DI 或行为验证。

### F06 / P1：实际审查超时/取消边界尚未建立

位置：`InvocationToolApprovalLlmClient.ReviewAsync` 直接用调用者 ct 调 ILlmInvocationService，未建立审查专属 deadline；“timeout 用例”只是 fake 返回 Success=false、Error="provider timeout"。

这是已核实的实现/验收缺口，尚未进行真实慢服务超时实验。建议配置 ReviewTimeoutSeconds，用独立 deadline 与调用者 token 链接；审查自己的 deadline 到期转 DeferredDependency/approval_review_timeout，用户取消保持 OperationCanceled，不建待恢复操作、不继续调用模型。迟到结果必须按输入代际和取消状态失效。

验收：可取消的延迟 fake、真正等待到审核 deadline、用户先取消、返回竞争、普通成功等场景。不要用字符串包含 timeout 来推断取消来源，也不要 catch 所有 OperationCanceledException 后吞掉用户停止。

### N01 / P2：交接中的枚举声明不准确

交接单称三个 enum 都“末尾追加、不改变既有值”，但 ToolApprovalAuditEventType 的新成员插在 TicketNeedHuman 后，TicketMatched 从 4 变成 5，后续成员一起偏移。当前 FileToolApprovalStores 使用 JsonStringEnumConverter，**本轮没有发现旧文件因此被误读**，不得把它写成已发生数据损坏。

仍应将新成员移到末尾或明确旧值，修正交接证据，避免未来数值序列化/外部消费者产生歧义；这是小型一致性修正，不需要增加数据库兼容层。
