## 一、对照 Harness 四层模型：PuddingAgent 的「实然」映射

| Harness 层 | Harness 的做法 | PuddingAgent 对应的东西 | 偏差判定 |
| --- | --- | --- | --- |
| ① 启动组合层 | `dsh CLI → Profile: web → dsh-base → web-app` + **声明式 `cordis.patch.yml`** | `PuddingAgent`（仅 `Program.cs`，107 行）→ `PuddingHost`（`Hosting/` + `Extensions/` + `Connectors/` + `BrowserBridge/`） | ⚠️ **有组合根，但无声明层**：全部靠**命令式 DI 代码**（`PuddingHost` 内 `AddSingleton/AddScoped/AddTransient` 出现 **420** 次、`AddHostedService` **34** 次）；没有 Harness 那种 patch 声明式补丁 |
| ② Cordis Runtime | 单一**共享 ctx** + `ctx.agents / ctx.agentLoop / ctx.sessions / ctx.tools / ctx.systemPrompt` + **typed events** | `PuddingRuntime`（`AgentExecutionService*`、`ContextPipeline*`、`MessageDeliveryDispatcher`）+ `PuddingPlatform`（`Services/AgentChat`、会话/命令存储）+ `PuddingCore`（`Core/`、`Runtime/`、`Orchestration/`）**三处共同承担** | ❌ **运行时被切成三块**；无统一 `ctx` 对象（实为 `IServiceProvider` + 大量单例 + 静态），typed events 分散 |
| ③ Capability seams | `LLM Adapter · Shell·FS·LSP · Sandbox·Approval · Skill·SubAgent · Jobs·Workflow` 各**一条缝** | LLM：`PuddingCore/Core/ResponsesLlmGateway.cs` **+** `PuddingRuntime/Services/DirectLlmClient.cs`（**两套适配**）；工具：`PuddingRuntime/Tools/`（124 文件 29.3k 行）**+** `PuddingCore/Tools/`（14 文件）；审批：`InMemoryToolApprovalService`（1952 行）**+** 平台侧 `ToolApproval:Llm`（缺配）；SKill/SubAgent：`PuddingCore/Skills` **+** `Runtime/Tools/Agents/SubAgentTool.cs` **+** `Platform/Services/SubAgentManager.cs` | ❌ **每条缝都有 2–3 份实现**（本报告最主要的「大泥球」来源） |
| ④ Surface/Output | `Web Host/API · Browser plugins · Session JSONL · ACP/JSON-RPC` | `PuddingPlatform/Controllers`（74 个 Controller 类）**+** `PuddingController/Controllers`（14）**+** `PuddingHost/Controllers`（8）**+** `PuddingGateway` **+** `PuddingDesktop`（WinExe）+ `PuddingBrowser.*` + `PuddingCodexService` | ❌ **两套控制器栈并挂同一宿主**（`PuddingHost.csproj:34,35` 同时引用 `PuddingPlatform` 与 `PuddingController`） |

**一句话诊断**：Harness 的「一棵插件树、每层一条缝」在 PuddingAgent 里变成了**「三层各长一棵树，每条缝长 2~3 个头」**——没有双向引用（无环）是优点，但**职责横向重复**与**组合层命令式膨胀**是主要混乱源。

## 四、六类系统性病灶（跨模块，按危害排序）

1. **「Core」不是 Core**：`PuddingCore` 承载 8 个子域实现 + 210 接口混杂契约与实现 ⇒ 依赖图上它是底座（无人可依赖它之外），语义上它是**第二个平台**。后果：任何「契约应与实现分离」的判断都失效，接口数量失真（18~210 悬殊）。
2. **组合层命令式膨胀**：`PuddingHost` 420 次 DI + 34 个 `AddHostedService`，却**没有声明式补丁层**（对比 Harness 的 `cordis.patch.yml`）⇒ 装配知识散落在代码里，**测试无法用配置裁剪宿主**（测试报告已证：夹具只能靠「删服务」硬编码，仍漏 15+ 个后台服务）。
3. **同职责多实现（本仓第一混乱源）**：
   - Store：**60** 个（Platform 34 / Core 9 / Runtime 8 / …），单一 Goal 域 6 个
   - SchemaBootstrapper：**23** 个**全部**在 Platform（同调度域 5 个）
   - Controller：**约 98** 个（Platform 74 / Controller 14 / Host 8 / Desktop 1 / Runtime 1），存在**跨项目同名**
   - BackgroundService：**28** 个，仅 1 个以 `HostedService` 命名（命名无序）
   - Worker **8** · Dispatcher **9** · LLM 适配 **2 套** · 审批实现 **2 套** · SubAgent 三处
4. **生成代码未隔离**：Migrations 20,508 行（均 621 行/文件）与手写代码同项目 ⇒ 指标被污染、评审噪音大。
5. **命名空间与项目名漂移**：`PuddingCore` 全为 `PuddingCode.*`（357/357）；`PuddingHost` 内 3 套根命名空间 + 同目录混用 2 套 Controllers 命名空间 ⇒ 靠 `using` 无法判断分层归属。
6. **测试侧结构同病**：`Source → Tests` 反向引用、测试引用 CLI 应用、阻塞式 `.Result` 89 处、夹具共享单例连接（导致套件级 flaky，详见 `Docs/Reports/测试套件待裁定项-决策备忘-2026-09-17.md` §6.1 系列）。

**✅ 值得肯定的两点**：① 工程级**无循环依赖**；② `PuddingCore` 是无入边的真底座（依赖方向总体自上而下，未出现「上层被底层反向引用」的经典泥球形态）。

## 五、改进路线（分优先级；含「不要做什么」）

**P0（低风险、高收益，1–3 天）**
1. **修 slnx 漂移**：把 6 个缺失项目登记进 `PuddingAgentNetwork.slnx`（当前 18+7 与实际 29+9 不符）——纯配置，零代码风险。
2. **清残留**：删 5 字节空文件 `ContextCompactionService.TokenEstimation.cs`、根目录一次性 `split_*.ps1`、孤儿目录 `PuddingPlatformAdmin`（确认归属后归档）。
3. **命名空间对齐**：新文件按项目名命名空间；为 `PuddingCore` 制定 `PuddingCode.* → PuddingCore.*` 的**渐进映射表**（先文档，后批量）。

**P1（1–2 周，需设计评审）**
4. **给组合层加「声明式裁剪」**：把 `PuddingHost` 的 34 个 HostedService 与关键单例改为**配置开关驱动**（可参考已存在的 `GoalRuns:Enabled` / `TaskAutoDispatch:Enabled` 模式），使测试/嵌入场景能**按配置裁剪宿主**——这同时能根治 WebApi 夹具的 15+ 后台服务问题。
5. **对「同职责多实现」做归并清单**：60 Store / 23 SchemaBootstrapper / 9 Dispatcher 逐一标注「保留 / 合并 / 下沉」，优先合并 `Scheduling` 域 5 Store 与 `Goal` 域 6 Store。
6. **分层边界落地**：`PuddingController` 与 `PuddingPlatform` 二选一（建议：Platform 为唯一 API 层，Controller 退化为兼容垫片或下线）；`PuddingRuntime` 与 `PuddingPlatform` 保持**兄弟关系**（现状正确，勿引入交叉引用）。

**P2（结构性，需 ADR）**
7. **`PuddingCore` 瘦身**：`Platform/`、`Runtime/`、`Tasks`、`Goals`、`Swarm`、`Tools`、`Skills` 的**实现**迁往对应层，Core 只留契约与模型（对齐 Harness 的「seam 只有一条缝」）。
8. **生成代码隔离**：Migrations 移入独立目录/项目并以 `*.Designer.cs` 白名单从质量指标中排除。
9. **能力接缝收敛**：LLM 适配、审批、SubAgent 各保留单一入口（其余降级为内部实现或删除）。

**不要做什么（防止「治理本身变成新泥球」）**
- ❌ 不要为了「对齐 Harness」而**新建第四套分层目录**——现状已有 3 套源根（`Source/`、`src/`、`external/`），再加一层只会加剧查找成本。
- ❌ 不要在未锁定唯一 API 层前**同时重构 `PuddingPlatform` 与 `PuddingController`**——两套控制器栈并存期间的重构极易产生双份不兼容契约。
- ❌ 不要把 `PuddingRuntime` 的 `Microsoft.NET.Sdk.Web` **直接换成普通 SDK**——它可能依赖 Web SDK 的隐式引用（需先编译验证，本次未验证）。
