# Core「启动耗时 21.5 秒」归因

日期：2026-09-30；触发：用户就运行中心「启动耗时 21.5 秒 · 接口 127.0.0.1 · PID 26676 · 启动于 09-30 07:00:31」提问「为什么这么长，Core 启动都做了什么」。

前置：`Chat-Queue-Response-Fix-2026-09-30.md` 结尾明确「未将 21.5 秒启动时间归因为性能缺陷」。本报告接续该未决项。

## 1. 结论摘要

1. **21.5 秒是 Desktop 的测量口径**，不是 Core 自报。它等于「子进程 spawn」到「stdout 收到 `PUDDING_DESKTOP_READY` **且** `/health/ready` 返回 2xx」。
2. 该次启动的 **17.46 秒（占 81%）没有产生任何一行日志**：进程创建于 07:00:31，而 `logs/system` 当日文件的**第一行**是 07:00:48.460。全日志树在 07:00:30–48 之间只有 2 行，且都在 48.460 之后。
3. 失明原因已定位并修复（见 §6）：初始化阶段的 `[Startup] ...` 全部是 `Console.WriteLine`，只进 Desktop 的内存环形缓冲（运行中心日志面板），**不落文件**，而且**不带耗时**。
4. 实测排除：**DI 注册与容器构建不是瓶颈**。同一 Debug 二进制、隔离 DataRoot 下，`[Startup] Host built`（含 `builder.Build()` 与 `ValidateOnBuild=true`）出现在进程启动后 **1077 ms**，其中 `[StartupConfig]` 审计行（在 `AddPuddingApplicationServices` 之前）到 `Host built` 只占 **306 ms**。
5. 实测排除：**启动期没有重建任何索引**。25 个 schema bootstrapper 涉及的索引在现网库中全部已存在，`CREATE INDEX IF NOT EXISTS` 均为空操作。
6. 实测确认：**启动耗时对机器负载极其敏感**。同一二进制、同一隔离 DataRoot：机器空闲 **6.5 秒**；Core 正在忙 **12.4 秒**（连尚未碰数据库的组合根都从 1077 ms 涨到 3856 ms）。
7. **未证明** 21.5 秒中那 15 秒的具体归属，`§7` 列出候选与下一步的确定性手段。

## 2. 21.5 秒的定义位置

- `Source/PuddingDesktop.WpfArchive/Core/CoreProcessSupervisor.cs`（由 WinUI Desktop 链接编译）
  - `startedAt = DateTimeOffset.UtcNow`（`process.Start()` 之前，约 87 行）
  - `ReadyAt = DateTimeOffset.UtcNow`（收到 Ready 行 **且** `/health/ready` 通过之后，约 134 行）

- Ready 行由 `Source/PuddingAgent/Program.cs` 在 `InitializeAsync` + `StartAsync` **之后**输出 ⇒ 该数字覆盖「进程创建 → 组合根 → 初始化 → 所有 HostedService 启动 → 监听就绪」。

## 7. 未决与下一步

**未证明**：17.46 秒静默窗口中，组合根（约 1.4 s 量级）与「首次访问 9.2 GiB 平台库」各占多少。候选：
- (a) `PlatformDbContext` 首次建连 + WAL 恢复/检查点：`-wal` 有 **192.4 MB**，远高于自动检查点阈值（1000 页 ≈ 4 MB）。若上一个 Core 是被 `Kill` 结束（`StopUnderLockAsync` 在 15 秒优雅关闭超时后 `Kill(entireProcessTree)`），WAL 可能未被检查点，新进程首次写会触发大检查点。
- (b) `EnsureCreatedAsync` 在 9.2 GiB 库上的元数据开销。
- (c) 重启瞬间的机器争用（旧 Core 退出刷盘 / Desktop 自身启动）——由 §4 的 6.5 s → 12.4 s 放大效应支持。

**确定性手段**：重启一次 Core（运行中心「重启」），读 `logs/system/pudding-*.log` 中的 `[StartupPhase]` 行；`schema-*` 各行的 `delta` 会直接指出是哪一步吃掉了十几秒。注意 `process-start` 目前是「托管入口」而非「OS 进程创建」，**运行时与程序集加载的耗时仍落在第一个打点之前**，这是该埋点目前仍未覆盖的缺口。

**顺带发现的确定性缺陷（未修）**：
- `MessageFabricSchemaBootstrapper`（`Source/PuddingPlatform/Services/MessageFabric/MessageFabricSchemaBootstrapper.cs`）每次启动都会：
  - 无条件执行 4 条 `UPDATE message_deliveries ...`，其中 `SET execution_state = CASE ... instr(lower(coalesce(last_error,'')),'busy') ...` **无 WHERE，重写整表**；另一条对 `room_messages` 每行做 3 次 `replace(lower(...))` 再 `LIKE`。当前表很小（6,230 / 5,519 行）故代价有限，但属于**每次启动都做的一次性脏数据整备**，应改为一次性迁移（版本标记）。
  - 8 条 `ALTER TABLE ... ADD COLUMN` 每次都靠「抛 `duplicate column name` 再捕获」跳过，应改用同文件外的 `PRAGMA table_info` 前置判断。
- `TokenUsageSchemaBootstrapper` 每次启动做约 25 次 `PRAGMA table_info` 往返与 6 条 `CREATE INDEX IF NOT EXISTS`。
