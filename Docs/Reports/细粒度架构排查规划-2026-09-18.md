## 一、目标与非目标

**目标**：把「哪个模块乱」推进到「**模块内部哪一处乱、边界在哪、证据是什么、改法与代价**」，产出可执行的重构/加固清单（含风险与依赖顺序）。

**非目标（本阶段不做）**：
- ❌ 不做批量重命名/搬迁（先出清单与 ADR，再动手）
- ❌ 不动 `PuddingCore` 的命名空间（体量最大、风险最高，排在最后）
- ❌ 不做与排查无关的功能开发

**产出物（每批固定四件）**：
1. **模块卡**（见 §七模板）：边界四问 + 度量 + 重复实现清单
2. **证据表**：每条结论带 `文件:行号`（静态证据）+ `DI 注册点/调用点`（装配证据）
3. **问题清单**：分「契约缺陷 / 越层直调 / 重复实现 / 数据所有权 / 装配耦合 / 死代码」六类，每项标注危害与最小修法
4. **裁决请求**：需要所有者拍板的项（不擅自改他人模块）

## 二、粒度定义（四级 + 一套「边界四问」）

| 级别 | 单位 | 观察对象 | 现有手段 |
| --- | --- | --- | --- |
| **L0** | 域 | LLM / 记忆 / 上下文 / 执行内核 / 平台服务 / 组合根 | 已完成（Top10 审计）|
| **L1** | 模块（≈命名空间或目录） | 类清单、内聚度、对外接口数量 | `code_outline`、目录聚合脚本 |
| **L2** | 类 | 职责数、字段依赖数、方法数、行数、是否实现接口 | `code_symbol_search`、`code_explore`、逐文件读 |
| **L3** | 方法 | 参数个数、是否跨层取数、是否直用具体类 | `code_callers`/`code_callees`、grep 调用点 |

**「边界四问」**（每个模块必答，这是本阶段的核心方法）：

1. **入边**：谁调用我？经过接口还是具体类？（`code_callers` + DI 注册点）
2. **出边**：我调用谁？是否越过自己的下一层直达底bottom（跳层）？
3. **数据所有权**：我依赖的表/文件/内存结构，是否也被别人直接读写？（EF 实体/DbContext 类型出现处）
4. **装配点**：我在哪里被 new/注册？生命周期（Singleton/Scoped/Transient）是否与状态一致？

## 三、六类「混乱判据」（可脚本化，逐条可判真假）

| 判据 | 检测手法 | 已发现的实例（示例） |
| --- | --- | --- |
| **① 空壳/失真契约** | 接口方法数 vs 实现公开方法数 | `ILlmResourcePoolService` **仅 11 行 1 个方法**（`LoadAsync`），实现 `LlmProviderFileService` **806 行**，暴露 CRUD/价格/余额/KeyVault 全套 ⇒ 契约对 95% 行为**无约束力** |
| **② 同名跨层/跨项目** | 类名 `Group-Object` 后按命名空间比对 | `LlmProfileResolver` **两份**：`PuddingCode.Configuration`（静态，L12-90）vs `PuddingRuntime.Services`（实例，L13-92），**返回值类型不同、不共享接口** |
| **③ 越层直调具体类** | 控制器/上层构造函数是否注入 `XxxService/XxxStore` 具体类型 | `BootstrapApiController.cs:34` 直接注入 `LlmProviderFileService`，`:383` 调用 `UpsertProviderWithModelsAsync`；`LlmModelApiController.cs:15`、`LlmProviderApiController.cs:15` 同 |
| **④ 重复实现（逐项对齐）** | 同族文件做方法清单 diff | `SessionMemoryStore`（Write/Recall/Clear/ToEntity/ToEntry）与 `WorkspaceMemoryStore` **逐项对齐，仅 scope 常量不同** |
| **⑤ 数据所有权外泄** | 下层 DbContext/实体被上层直接使用 | `ContextWindowManager._memoryDbFactory IDbContextFactory<MemoryDbContext>`（L33）；`ContextCompactionService._dbFactory`（L31）⇒ 上下文层**直接写记忆库** |
| **⑥ 装配耦合/兼容残留** | DI 注释与「兼容旧接口」注册 | `PuddingServiceCollectionExtensions.Connectors.cs:211-216` 明确注释「ILlmConfigService 已注册，**同时注册 ILlmResolver 兼容旧接口**」⇒ 双契约并存 |

**补充度量**（每模块卡固定填）：
- 文件数 / raw LOC / 最大文件行数 / 平均方法行数
- 接口数、实现数、**同名类数**
- 扇入（被引用次数）/ 扇出（引用类型数）/ **跨层边数**
- `catch (Exception)` 数、`async void` 数、`.Result/.Wait` 数、`#pragma warning disable` 数
- **测试可达入口数**（有多少测试直接构造该模块）

## 九、风险、纪律与工具上限

**纪律**
1. **只读优先**：排查阶段不改任何文件；需要改动时先出提案（参照 `Docs/Reports/提案-WebApi测试夹具连接隔离-2026-09-18.md` 的做法）。
2. **不擅动他人模块**：涉及 `PuddingCore`/`PuddingPlatform` 改动 → 出裁决请求。
3. **双源交叉**：静态 + 装配/运行期，单源结论标注「未验证」。
4. **不扩大范围**：每批只查本批清单，发现新域先记账。

**已知工具上限（必须写进报告局限）**
- `search_grep` 全 `Source/` 会触发 2000 文件/64MB 预算 → 返回空或部分；应**先按目录/文件名收窄**
- `code_symbol_search` 存在**重复 project_id 索引**（同一文件多份索引），可能漏符号
- `code_outline` 行数可能与物理行数差数行（取的是 namespace 结束行）
- 运行期证据依赖 TRX/日志，需注意「测试路径 ≠ 生产路径」

**排期建议（粗略）**：B1 ≈ 2–3 小时；B2/B3 各 ≈ 3–4 小时；B4 ≈ 3 小时；B5 需拆 2–3 子批；B6 依赖前面结论。**每批结束产出模块卡 + 问题清单 + 裁决请求，不跨批混改。**
