## 1. B 项 —— 产品缺陷：无效 swarm 目录应「降级完成」而非「抛异常中断」

### 1.1 现象（实测原文）

```
失败 ProcessSwarmAsync_WithInvalidSwarmDirectory_HandlesError [92 ms]
错误消息: Assert.Fail 失败。Should not throw exception:
  git worktree list failed: fatal: not a git repository (or any of the parent directories): .git
堆栈: ... SwarmOrchestratorTests.ProcessSwarmAsync_WithInvalidSwarmDirectory_HandlesError()
      in Source/PuddingCoreTests/Swarm/SwarmOrchestratorTests.cs:line 403
```

### 1.2 契约（用例自己写明的两条硬约束）

`Source/PuddingCoreTests/Swarm/SwarmOrchestratorTests.cs`（约 `:386-404`）：

```csharp
catch (Exception ex) { thrownException = ex; }

// Assert: Should either succeed or handle error gracefully
if (thrownException != null)
    Assert.Fail($"Should not throw exception: {thrownException.Message}");
Assert.IsTrue(events.Any(e => e is SwarmCompletedEvent), "Should complete workflow");
```

⇒ 契约 = ①**不得抛异常**；②**最终必须产出 `SwarmCompletedEvent`**。实测两者都被违反（`:403` 即那条 `Assert.Fail`）。

### 1.3 产品违反点

| 位置 | 行为 |
| --- | --- |
| `Source/PuddingCore/Swarm/WorkerManager.cs:206-222` `RunGitAsync` | git 退出码非 0 且 stderr 非 `already exists` / `nothing to commit` ⇒ `throw new InvalidOperationException($"git {args} failed: {stderr}")` |
| 同上 `CreateWorktreeAsync:137` | 调用 `worktree list` **无任何防护** ⇒ 异常向上穿透到编排层 |
| 同上 `CleanupExistingWorktreeAsync:105-127` | **同文件已有 try/catch 容错先例** ⇒ 缺失处属实现不一致，而非「有意设计」 |

抛出消息 `git worktree list failed: …` 与实测**逐字吻合** ⇒ 归因确定。

### 1.4 提案（两选，**推荐 ①**）

**① 编排层容错（推荐）**：在 `SwarmOrchestrator.ProcessSwarmAsync` 捕获单个 worker 创建失败 ⇒ 通过既有 `ErrorEvent` 通道（`:193` / `:231` 已存在）告知 ⇒ 继续推进直至 `SwarmCompletedEvent`。
- 与用例注释「handle error gracefully」完全一致；对「一个 worker 失败不应让整轮 swarm 消失」的语义也更符合直觉。

**② 局部容错**：`worktree list` 改为与 `CleanupExistingWorktreeAsync` 一致的 try/catch（返回空列表 + 记日志）。
- 改动更小，但只覆盖 git 未初始化这一种起因。

### 1.5 风险与验证

- **风险**：属**产品行为变更**（「失败」是否仍算「完成」需要产品口径确认）⇒ 故未擅自动。若口径要求「失败必须显式失败」，则应在完成事件里带上 `Success=false` 语义，而不是抛异常。
- **验证**：`dotnet test Source/PuddingCoreTests/PuddingCoreTests.csproj --filter "FullyQualifiedName~SwarmOrchestratorTests"` ⇒ 目标 18/18。
- **顺带**：该用例**方法名**（`...HandlesError`）与**内部注释**（`Create orchestrator with valid paths`）互相矛盾，注释疑为陈旧，建议一并校正，避免后续读者误判用例意图。

1. 检测并复用现有事务：`var tx = db.Database.CurrentTransaction; if (tx is null) { … BeginTransaction … }`；
2. 或整体包进 `db.Database.CreateExecutionStrategy().ExecuteAsync(...)`（EF Core 推荐做法，可兼容重试策略）。

**影响面**：凡「某次 turn 触发 Goal 命令创建」的路径都可能命中（不止测试）。

  "recommendedNextStep": "Waiting for the approval review dependency to recover (configure or fix the ToolApproval:Llm review profile/model) …" }

而 `Source/PuddingAgent/appsettings.json:105-107` 只声明了 `"ToolApproval": { "Reviewer": "llm" }`，**没有 `Llm` 子节点**。

### 6.3 运行期影响（不只是测试问题）

本 Agent 心跳期间，`shell` / `terminal_start` / `file_write` / `file_patch` 会**间歇**报同一 `reasonCode`；
且 **`request_tool_approval` 自身也被同一门禁拦下**（实测 2026-09-17 05:4x）：

```
{ "ticketId": "tap_dd83…", "status": "deferred_dependency",
  "reasonCode": "approval_review_profile_not_configured",
  "recommendedNextStep": "Waiting for the approval review dependency to recover …" }
```

⇒ 门禁消息推荐的「去调 `request_tool_approval`」在**缺配场景下自身不可用**（**恢复路径自指**），
使用者只能靠人工 `/authorize <tool> 10m|once|session|permanent` 解锁。

**建议（按代价排序）**：
1. **补配置**：在 `ToolApproval` 下增加 `Llm` 子节点（形状见 `ToolApprovalLlmOptions`）⇒ 一并修好测试与运行期。
2. **降级设计**：缺配时 `request_tool_approval` **不应**同样 fail-closed 到同一条依赖，而应直接创建「人工授权工单」（无需 LLM）。
3. **放行只读/构建类工具**：`dotnet build/test`、只读检索等低风险调用不必经 LLM 审查。
4. **错误可辨识**：把「缺配置」与「模型暂不可用」区分开，并给出**真正可执行**的指引。

## 8. 附录：验证与排障速查

```bash
# 单套件（默认 bin 布局；路径类测试的失败必须在此布局下复核）
dotnet test Source/<Proj>/<Proj>.csproj --logger "console;verbosity=minimal" > temp/x.log 2>&1

# 类级过滤 / 点名挂起测试
dotnet test Source/<Proj>/<Proj>.csproj --filter "FullyQualifiedName~<ClassName>"
dotnet test Source/<Proj>/<Proj>.csproj --blame-hang --blame-hang-timeout 300s

# 需要绕开残留 testhost 对 bin 的 DLL 锁时（⚠️ 会让「按 bin 相对路径取数据」的测试假失败）
dotnet test Source/<Proj>/<Proj>.csproj --no-build --artifacts-path temp/hbk-artifacts2
```

**三条本环境硬经验**（详见诊断报告 §七）：
1. `--artifacts-path` 下的**任何**失败清单都必须先用默认布局复核，否则会把工具假失败当缺陷（本会话已证伪 3 例 + 1 个夹具族共 76 处）。
2. `exit code 1` ≠ 被门禁拒绝 —— 先读重定向日志，有内容就说明命令跑过了。
3. 门禁是**逐调用间歇**：`shell` 与 `terminal_start` 互为等价工具；不可用时改为产出无需命令的交付物，不要空转或盲目重试。
