## 三、缺陷类 A：断言参数写反（本会话主轴，覆盖 5 个测试文件）

MSTest 签名为「边界在前、被测值在后」：

```csharp
Assert.IsGreaterThanOrEqualTo(lowerBound, value);   // 断言 value >= lowerBound
Assert.IsLessThan(upperBound, value);               // 断言 value <  upperBound
Assert.IsLessThanOrEqualTo(upperBound, value);      // 断言 value <= upperBound
```

若把「被测实际值」写成边界，断言方向即反转、必然失败。已修清单：

| 文件 | 位置 | 修法 | 判定依据 |
| --- | --- | --- | --- |
| `Core/GitSnapshotServiceTests.cs` | 71 | 参数交换 | 断言与上下文相反 |
| `Core/WorkerManagerTests.cs` | 300 | 参数交换 | 同上 |
| `Swarm/SwarmOrchestratorTests.cs` | 273–277（5 处） | `IsGreaterThanOrEqualTo(xxxIdx, 0)` → `(0, xxxIdx)` | `events.FindIndex(...)` 找不到返回 **-1**，故「索引 ≥ 0」=「事件存在」，**并非恒真断言** |
| 同上 | 284 / 287（2 处） | `IsLessThan` 参数交换 | 断言**与自己的消息文字直接矛盾**：`IsLessThan(thinkingEventIndex, contractDefinedIndex, "Thinking should come before contract defined")` 实际断言 `contractDefinedIndex < thinkingEventIndex`；实测 `upperBound:<thinkingEventIndex=0>` / `value:<contractDefinedIndex=5>`，即现实确为 thinking(0) 先于 contract(5)、与消息一致，只错参数序 |
| `Swarm/Integration/ContractFirstWorkflowTests.cs` | 119–120 | 参数交换 | 消息已明示边界："at least one file" / "multiple symbols" |
| `Core/DefaultDistillerTests.cs` | 88 | `IsLessThan(result.RetainedLines, 50)` → `(50, result.RetainedLines)` | 测试造 50 行并断言发生截断；实测 `RetainedLines = 15`，原写法断言「50 < RetainedLines」 |
| 同上 | 412 | `IsLessThanOrEqualTo(Summary.Length, 4500)` → `(4500, Summary.Length)` | 注释 "MaxLlmChars + truncation marker"；实测 `Summary.Length = 1691`，原写法断言「4500 <= Summary.Length」 |

两条机制性教训：

1. **「修好一项才暴露下一项」**：`SwarmOrchestratorTests` 中 line 272 的写反断言先行失败，使执行根本推进不到 line 282；修好第一层后，同族的 `IsLessThan` 写反才现形。因此「只修可见错误」会漏掉后续层。
2. **从失败消息反推参数序**：MSTest 失败消息按「value … upperBound」排列，并打印 `upperBound:` / `value:` 的**表达式原文**。若 `upperBound:` 指向的是被测值（如 `result.RetainedLines`），应优先怀疑参数顺序，而非产品行为。
   —— 本会话曾把 `DefaultDistillerTests` 两项误判为「期望值与产品行为不一致，需所有者确认」，后由 commit `81f73da9` 显式更正。

### B. `SwarmOrchestratorTests.ProcessSwarmAsync_WithInvalidSwarmDirectory_HandlesError`（:403）

断言 `Assert.Fail("Should not throw exception: git worktree list failed: fatal: not a git repository …")`。

已核实夹具（`SwarmOrchestratorTests` 构造函数）：

```csharp
_testDir      = Path.Combine(Path.GetTempPath(), $"swarm-orchestrator-test-{Guid.NewGuid():N}");
_testSwarmDir = Path.Combine(_testDir, ".pudding", "swarm");
_testRepoDir  = Path.Combine(_testDir, "repo");
```

即测试目录在**系统临时目录**下（与 bin 布局无关），故本项**不受 `--artifacts-path` 影响**。
关键在于：该用例**唯独没有调用 `InitializeTestGitRepoAsync()`**（同文件其余用例都调用了），
因此 `_testRepoDir` 不是 git 仓库 → 产品内部 `git worktree list` 失败并向上抛 → 命中断言的 `Assert.Fail`。

两种设计解释需所有者裁定：
1. 产品应在 git 环境不可用时**优雅处理**（捕获并发错误事件）—— 这正是用例名 `HandlesError`
   与断言文字「Should not throw exception」所表达的契约 → 属产品健壮性缺口；
2. 用例应补 `InitializeTestGitRepoAsync()`，让「无效」只体现在 swarm 目录而非 git 仓库缺失。

**不可机械改成 `Assert.Throws`** —— 那会掩盖 "HandlesError" 的契约语义。

#### ★ 方法论结论（本报告最重要的一条）

`--artifacts-path` 改变的不只是 bin 位置，而是**布局形状**：

```
默认：            <项目>/bin/<配置>/<tfm>/
--artifacts-path： <dir>/bin/<项目名>/<配置>/
```

因此**凡按 `AppContext.BaseDirectory` 的相对层级或父目录名推断路径的测试都会假失败**。
推论：**任何在 `--artifacts-path` 下得到的失败清单，都必须先用默认布局复核才能定性**；
反之，若某用例在默认布局下失败，它才是真失败。本次 Platform 3 项「失败」中已有 **2 项**被此机制证伪。

**Platform 最终修正**：真实失败 **1 项**（`GoalCheckRunnerTests`，他方 Goals 在途）+ 1 项 flaky；
另 2 项为工具假失败（1 项已实测确认，1 项待实测确认）。

## 七、工具与排查手册（本环境实测）

### 测试运行

```bash
# 取失败清单：日志仅数十行，只含失败用例名 + 错误消息 + 堆栈，file_read 尾部即可读完
dotnet test <proj>.csproj --no-build --artifacts-path temp/hbk-artifacts2 \
  --logger "console;verbosity=minimal" > temp/x.log 2>&1

# 区分「慢」与「卡死」：需要逐条输出
dotnet test <proj>.csproj --logger "console;verbosity=normal"

# 定位挂起：点名阻塞测试并落盘 hangdump
dotnet test <proj>.csproj --blame-hang --blame-hang-timeout 300s
```

- `--artifacts-path temp/hbk-artifacts2`：绕开残留 testhost 对 `bin` 下 DLL 的锁（否则构建阶段报 MSB3021/MSB3027）。
- `--no-build`：复用已构建产物，零构建开销（Core 全量仅 56 秒）。
- `-v:q` 的零输出**不能**作为挂起判据。
- ⚠️ **`--artifacts-path` 的副作用（必读）**：它把 bin 移到 `temp/...`，从而改变 `AppContext.BaseDirectory`
  的层级 —— **凡以 bin 相对路径定位仓库数据的测试都会假失败**（实例与对照实验见 §6.C 的更正）。
  即该绕过手段与「路径类测试的可信度」之间存在取舍：验证路径类测试时应改用默认 bin 布局，
  但需先确认没有残留 testhost 占用；判断失败原因时，优先做「换布局重跑」的对照实验，
  以先排除「失败由自己的运行参数引起」。

### 检索与取证

- **`findstr` 不可用于日志检索**：对 UTF-8 无 BOM 文件，中文与部分 ASCII（实测 `Exception`、`Assert`）均 NoMatch。
- **`search_grep` 在 `temp/` 会超时**（文件数过多，`scanned 0/2000`，`coverage: partial`）：须先把目标复制到干净小目录再检索；**partial 结果不得当全集**。
- `terminal` 走 cmd：PowerShell 专属 cmdlet（`Select-String`）与多 `/C:` 模式（含空格）均失败。
- `shell` 工具对**非零退出码不回传 stdout**（仅报 `exit code 1`）→ 一律 `> temp/x.log 2>&1` 重定向后 `file_read` 取结果。
- 平台门禁已知缺陷：`terminal_start` / `shell` / `file_patch` 会间歇报 `approval_review_profile_not_configured`
  （**依赖等待，非人工授权**）。不要盲目重试，改用等价手段或稍后再试。
- `git_log` 的 `file_path` 过滤在本环境未生效（返回分支最近提交，未按路径过滤），需注意勿据此下结论。

### 提交纪律（共享工作目录）

- 永远**显式文件清单**暂存，禁止 `git add -A`、禁止 amend/改写历史；错话用后续提交显式更正。
- 改他方文件前先 `git_diff` 确认工作区干净；不代为提交他方在途改动。
- 临时产物一律写 gitignored 的 `temp/`。
