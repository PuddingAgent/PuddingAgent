## 七、侦察补全：去重机制完整因果链（只读代码侦察，file:line 齐备）

### 7.1 去重键的唯一构造点

`GoalVerificationPersistence.BuildScopedDedupKey`（`GoalVerificationPersistence.cs:43-50`）产出：

```
{goalRunId}|{epoch}|{scope}|{criterionRevision}|{definitionHash}|{inputFingerprint}
```

逐段对照实测键 `7ef90f2c…|1|work_unit|1|sha256:4357c6fa09c…|epoch:1:objective:1`：

| 段 | 取值来源 |
|---|---|
| `scope` | **常量** `GoalVerificationScopes.WorkUnit = "work_unit"`（`GoalVerificationContracts.cs:148-151`）⇒ 键内**无 WorkUnit 身份** |
| `criterionRevision` | 规划器硬编码 `1`（`GoalAcceptanceContractPlanner.cs:170-217`） |
| `definitionHash` | `{DefinitionRef}|{Kind}|{CommandTemplate}` 的 SHA256（`GoalCheckDefinitionRegistry.cs:52-60`）⇒ **runner 采集逻辑的修复不改此值** |
| `inputFingerprint` | 无绑定 Plan 时退化为 `epoch:{e}:objective:{v}`（`GoalAcceptanceContractPlanner.cs:150-156`） |

唯一索引 `UX_goal_check_records_dedup(dedup_key)`（`GoalSchemaBootstrapper.cs:208`）。

### 7.2 迭代 2/3/4 为何没有记录却仍有裁决

`GoalCheckRecordStore.EnqueueAsync`（`GoalCheckRecordStore.cs:44-76`）是**跨迭代幂等**的：先按含 `iterationNo` 的 `CheckRecordId` 查（`:52-61`），未命中再**按 `DedupKey` 全表查**，命中即 `continue`（不建行、不执行）（`:69-76`）。执行侧认领只接受 `pending/leased`（`:126-146`、`:164-168`），而 iter1 两行已 `finished` ⇒ **后续轮一次都不启动**。

裁决侧却照常推进：`GoalCheckRunner.RunAsync` 末尾以「`persisted ∪ produced`」为准（`GoalCheckRunner.cs:104-119`），结算按 `(goalRunId, epoch)` **不按 iterationNo** 全量读取（`GoalSettlementStore.cs:170-173`、`GoalSettlementWorker.cs:107-141`）⇒ iter2/3/4 各用 iter1 的失败证据产出 `criterion_failed`。

### 7.3 `activation_epoch` 1→2 的真实来源（修正上一节推断）

**不是某次 resume，而是熔断本身**：`GoalSettlementStore.cs:1203-1223` 在“不可恢复”分支同事务内 `Status=Blocked` **且** `ActivationEpoch++`（`:1223`）；熔断置码在同文件 `:1157-1180`，事件 `goal.circuit_opened` 在 `:1182-1195`。

记录侧一律取 `iteration.ActivationEpoch`（`GoalSettlementStore.cs:164-173`、`:260`），而 iter1–4 创建/结算时该值仍是 1 ⇒ 全部记录停在 epoch 1。

### 7.4 为什么 resume 后检查必然真实重跑

当前无 epoch=2 记录的原因是：熔断后 Goal=Blocked，而**受理新迭代要求 Active**（`GoalStateMachine.cs:78-80`）⇒ 未创建 iter5 ⇒ 从未以 epoch 2 调用 `EnqueueAsync`。一旦 resume：

1. 契约按 `(goalRunId, 2, objectiveVersion)` 查无行 ⇒ 重建（`GoalSettlementWorker.cs:77-106`、`GoalAcceptanceContractPlanner.cs:47-52`）；
2. `inputFingerprint` 变为 `epoch:2:objective:1`；
3. 新 `CheckRecordId`（`iterationNo=5`）与 `|2|` 前缀的 `dedup_key` **均无冲突** ⇒ 检查真实重跑。

⇒ `46b9aa76` 的尾部读取修复将在该轮生效（该轮全量实测输出 451–473 行、汇总行在末行、`Passed: 1125`）。

### 7.5 侦察暴露的三个**新**缺陷（本轮新增，均附证据）

**A. 无绑定 Plan 的 Goal：检查结果指纹退化，同 epoch 内永久复用**
`inputFingerprint` 的设计意图是绑定 `planFingerprint`（注释原文「工作树/计划变化即失效」），但无绑定 Plan 时退化为 `epoch:objective` ⇒ **完全失去内容变化检测**。后果：同一 epoch 内即使代码已改，同名检查也不会重跑，直至熔断。这与既有缺陷 `2b60040d`（Task-bound Goal 未注入 ActiveTask 元数据）构成**同一条因果链的下游后果**。

**B. 查询侧与结算侧 epoch 口径不一致 ⇒ 查询面看不到检查记录**
结算侧用 `iteration.ActivationEpoch`（=1）；查询侧 `GoalQueryService.cs:184-185` 用 `goal.ActivationEpoch`（=2）。二者不一致时，**按 Goal 查询不到任何 epoch-1 的检查记录**。属可复现的查询/面板缺陷（口径事实，非推断）。

**C. 去重键不含 WorkUnit 身份**
`scope` 恒为常量 `"work_unit"`（`GoalVerificationContracts.cs:148-151`）⇒ 同一 epoch 内不同工作单元、不同迭代的同名检查（如 `bounded:test:{project}`）共享同一 `dedup_key`，结论互相顶替。是否为有意设计需 ADR 裁决。

### 7.6 明确「未证实」项（不得当作结论）

- epoch 1→2 的归因系排除法 + 字段吻合，未直接读事件审计行点名校验；
- 「修复后仍恒失败是否**仅**由去重冻结造成、抑或叠加 locale/编码因素」未做运行时验证（侦察被约束为只读）；
- “该 GoalRun 无 `task_goal_bindings` 行”系由 `Status=Blocked(3)`（task-bound 时应为 `Failed(7)`）与 fingerprint 退化推断，未直接查库确认。

### 9.3 归因：Agent 自身操作与受控检查并发（高置信，且有自认）

时间线重叠：

```
15:26:42  Agent 在会话内启动 dotnet test（temp/verify-goal-check.py）  ← 本 Agent
15:29:17  平台创建 epoch=3 的 build / test 受控检查
15:29:31  build 检查 passed（exit 0，14s）
15:31:04  test  检查 failed（exit 1，107s）  ← 报 non_zero_exit_code
~15:30    Agent 的 dotnet test 仍在运行（其后才返回 exit 0 / 1126 全绿）
```

两个 `dotnet test` 进程**同时操作同一 `PuddingPlatformTests.csproj` 的 obj/bin 与测试宿主**。Agent 那次 exit 0、受控那次 exit 1 ⇒ **受控检查是失败的一方**。

⇒ 高置信结论：**iter5 的 `non_zero_exit_code` 是 Agent 自身并发运行构建/测试造成的，而非产品缺陷**。这是一次**操作污染验证结果**的案例，如实记录在此。

**纪律（已写入记忆）**：Goal 处于活跃迭代（或任何可能触发受控检查）期间，Agent **不得**在该仓库运行 `dotnet build` / `dotnet test`；需要复现时改用 `--no-build` 只读复跑，或先确认 Goal 非 Active。

### 9.4 预测：Iteration 6 将因去重复用而立即二次熔断

iter6 与 iter5 的 `dedup_key` 完全相同：

```
{goalRunId}|3|work_unit|1|{definitionHash:4357c6fa09c…}|epoch:3:objective:1
```

`GoalCheckRecordStore.EnqueueAsync` 命中 `DedupKey` 即 `continue`（不建行、不执行）⇒ iter6 **不会重跑检查**，直接复用 iter5 的 `non_zero_exit_code` 失败 ⇒ `ConsecutiveSameBlocker` 由 3 增至 4（阈值 3）⇒ **立即二次熔断（Blocked）**。

⇒ 这是缺陷 A（卡 `e53f22c1`：无绑定 Plan 时 `inputFingerprint` 退化为 `epoch:objective`）的一个**可复现现场**：同一 epoch 内一旦出现基础设施失败，**无法自愈**，只能靠再次 resume（epoch+1）强制改变 fingerprint。

### 9.5 出路（按代价排序）

1. **再次 resume**（epoch 3→4）：最直接，但需人工权能；`goal_resume` 工具波次（`sub-6cb5d351`）完成后可免人工。
2. **使该 Goal 绑定 Task/Plan**：`inputFingerprint` 将由退化的 `epoch:objective` 升级为 `planFingerprint`（工作树/计划变化即失效），从根上消除“同 epoch 永久复用”。与缺陷 `2b60040d` 同源。
3. **让基础设施失败不参与去重缓存**（设计议题）：执行环境失败（无任何测试计数）不应作为可复用的“结论”。
