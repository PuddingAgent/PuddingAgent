# 心跳持久调度与登记开销修复（2026-09-20）

## 问题与边界

现场已存在“全量登记合格 Agent”的修复，但每个空闲 tick 都重新列出目录，重启仅恢复间隔并从启动时间重新计时。审计员实例提示词为“本 agent 不参与心跳调度。”，调度配置却未关闭；提示词与平台追加的执行契约相矛盾。

本次只修心跳调度、配置开关与状态报告。Task/Goal 自主续行仍属于其各自的持久调度链路，不借心跳替代。冻结、停用、无主会话、忙碌、持久可用性和 pending delivery 检查继续保留。

## 实现

- `AgentWakeQueue` 把每个 Agent 的入队时间、最早/最晚到期时间、间隔原子写入 `<DataRoot>/agents/<id>/state/heartbeat-wake.json`。写入完成后才发布内存条目；重启恢复原时间，不从启动重新累计一小时。文件缺失时才初始化新周期；首次升级没有旧持久文件，无法恢复过去进程已经丢失的内存倒计时。
- 出队保留磁盘到期条目，进程在发送前中断后可以恢复。发送成功显式安排下一周期，且不覆盖并发 `sleep`；忙碌或已有 pending 心跳时延后 30 秒重新检查，避免每次忙碌都延后整个小时。用户消息抢占、显式清理或停用会删除旧注册。到期条目每个进程只出队一次，不展开停机期间的历史周期；消息投递仍遵循既有 Message Fabric/pending 检查，并非跨文件与消息库的 exactly-once 事务。
- `HeartbeatOrchestrator` 启动登记所有合格 Agent，此后最多每分钟核对一次目录。5 秒 tick 只检查内存到期队列；读取队列状态不再出队再回填。空目录时仍 ReArm，以便后续发现新 Agent；已删除/停用/冻结的 Agent 被移除。发送前重新检查实例状态和开关。
- `heartbeat.json` 增加 `enabled`，默认 true；false 仅关闭心跳，不停用 Agent 或普通消息/任务。配置不可解析时拒绝本次登记/发送，不回退为启用。单个 Agent 的错误不阻断其他 Agent 登记。`sleep` 不允许重新启用明确关闭的心跳，`agent_status` 报告该开关。
- 重试入队替换同 Agent 的既有条目，修复重复注册；耗尽快速重试后恢复正常周期。删除已无用途的单默认 Agent 选择逻辑。
