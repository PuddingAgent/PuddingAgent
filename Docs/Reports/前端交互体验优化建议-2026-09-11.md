## 0. 第一批实施记录（2026-09-11）

§4"第一批"五件事已按本文建议落码，并附带以下边界说明：

- **鼠标排队与键盘一致**：`IntentConsole.tsx` 移除"忙碌时发送按钮=停止"的挪用；运行中有草稿时主按钮变为"加入队列"胶囊（icon+文字），与 Enter 走同一提交链。运行中无草稿时按钮禁用。
- **补充给当前任务**：运行中有文本草稿时，发送区出现 ⚡"补充给当前任务"下拉菜单（`chat-steer-menu`），与 Ctrl/Cmd+Enter 调用同一 `submitSteeringInteraction`；受理才清空草稿，失败回填输入框（不覆盖用户新输入）。图片不能插嘴，故该入口仅对文本草稿出现。
- **独立停止（并升级为真实服务端取消）**：新增常驻"停止当前执行"按钮（`chat-stop`，位置稳定、危险色调）。实施中发现服务端已有 `POST /api/v1/conversations/{conversationId}/turns/{turnId}/cancel`（ADR-059 协作式取消）但前端从未接线——本次补齐：`cancelConversationTurn` API 封装 + `useMessageInteractionQueue.requestActiveTurnCancel`（对每个活跃 canonical Turn 请求取消，已结束/未受理按竞态静默）；`index.tsx` 的 `handleStop` 现在先中断本地在途提交，再请求服务端取消，"停止"由名不符实的本地 abort 升级为真实的中断请求。队列下拉的"中止当前"更名"取消全部"，语义=停止当前执行+清除未注入本地补充。
- **失败保留草稿**：`useMessageSend` 新增 `restoreDraft` 端口——提交未被服务端受理（网络失败等）时把原文回填输入框（输入框为空才回填），失败轮保留在时间线作为记录；与 Steering 失败恢复同一规则。图片上传失败保留文字与暂存图片的行为此前已有，未改动。
- **清楚的操作回执**：忙碌期间提交的消息在服务端 202 受理后明确提示"已加入队列，将在当前回复完成后自动投递"（`useMessageSend` 按 `localBusy` 判定，鼠标/键盘/窗口事件三条链一致）；空闲提交的回执即消息卡本身，不额外弹 Toast。停止请求受理提示"停止请求已受理，当前执行将尽快中断"。
- **键盘可达（第一批验收项）**：状态胶囊补 Enter/Space 激活；ChatMain 余额徽标从 `span onClick` 改为语义 `<button>`（新增 `headerTextButton` 复位样式，含 focus-visible）。
- **样式**：`composerSendButton` 支持 `data-queued` 胶囊形态；新增 `composerStopButton`（`--pudding-danger`，含 focus-visible 与禁用态）。

**验证**：`npx tsc --noEmit` 通过；chat 目录 jest 950 通过/9 失败，其中本批新增 10 项测试全绿，并顺带修复了 2 项队列文案的既有断言漂移；9 项失败全部为既有漂移（语音工作台入口已不可达、推理披露行、TurnStatus 投影、DevPanel 基准），与本批无关。`npm run build` 通过且 bundle 预算达标（sync 1375KB ≤ 1536KB、chat 473KB ≤ 480KB）。改动文件 biome 无新增违规。

**未完成**：浏览器/实机走查仍未进行（本轮浏览器工具不可用）；"停止当前执行"的服务端真实中断效果、排队回执的观感、Windows 缩放与焦点路径，仍需按 §4 场景在运行产品中验收后方可宣称体验验收通过。服务端队列项的取消/重排/重试仍缺后端端点（MessageQueueDropdown 中相关按钮为占位禁用）。

## 1. 结论与证据边界

建议按“操作意图清楚 → 执行状态可信 → 工作上下文连续 → 结果便于使用 → 视觉一致”的顺序优化。首批集中在 Chat 的发送、停止、排队、状态反馈和长会话阅读，随后打通会话、任务和交付物。

本次检查当前工作树的 Chat、任务卡、管理壳、相关设计文档，并对照本地 `E:\github\deepseek\deepseek-harness` 的侧栏、输入宿主和长会话交互测试。仓库已有未提交改动，本文以读取时的文件为基线。浏览器工具连接失败，未进行当前运行版本的视觉走查、真实交互测试或性能测量。源码存在不等于产品验收通过。

本文是体验评估补充。消息交错顺序和披露规则继续遵循 [ADR-079](../07架构/93ADR-079Agent消息交错内容流与最新行为组披露ADR.md) 与[完整实施方案](../Features/Agent消息交错内容流与最新行为组披露完整实施方案.md)，不另建一套轨迹或执行状态机。

## 3. 优化方向

### P0-A：明确发送、排队、补充和停止

- 空闲时主按钮为“发送”；运行中有草稿时为“加入队列”，相邻菜单提供“补充给当前任务”。“停止当前执行”单独显示且位置稳定。
- 持续说明文字会作用于哪里，不只依赖 placeholder 和快捷键。鼠标和键盘调用相同动作。
- 区分“已提交补充”与服务端“已接收/已应用”。如果实际语义是中断后续跑，应如实说明。
- 队列复用服务端投影，显示等待次序及可用的编辑、撤回动作。已领取或运行的项转入时间线，避免两处重复。
- 停止当前与取消全部明确分开；操作后显示当前执行和待发消息的各自状态。
- 图片上传失败保留文字和暂存图片，提供逐项原因与重试。中文选词回车不得误发。

落点：`IntentConsole.tsx`、`ComposerTextInput.tsx`、`MessageQueueDropdown.tsx`、`useMessageInteractionQueue.ts`、既有发送链。

### P0-B：看懂执行状态并能处理问题

- 优先显示“正在读取 3 个文件”“等待子任务返回”等具体动作，来自服务端事件；缺少事实时显示“状态待同步”，不推测百分比。
- 正文与行为组继续严格交错。保留最新组展开和用户手动披露偏好，在计数旁增加有依据的活动摘要；原始参数和日志仍为二级详情。
- 断线分别表达“界面连接中断”和“任务状态待同步”，不能据此宣告任务停止或失败。重连回放不重复、不倒退。
- 错误说明“发生了什么、影响范围、下一步动作”。自动重试就地更新，需要用户处理才突出显示真实可用的修复入口。
- 看板、Agent 列表、聊天使用一致术语：已分配不等于正在执行，工具退出不等于任务完成。恢复动作依服务端合同确定。
- 状态变化可被辅助技术感知，但不逐 token 播报，也不为高频工具事件反复弹 Toast。

落点：`ChatMain.tsx`、`TurnContentStream.tsx`、`ActivityGroup.tsx`、`ComposerStatusDetails.tsx`、`TaskCard.tsx` 与现有投影层。

### P0-C：保护阅读位置、选择内容和草稿

- 阅读历史时新消息只增加“有新内容”提示；主动回到底部后才恢复跟随。
- 展开工具、图片加载、分页和行为组折叠时保留锚点；流式更新不能破坏正在复制的文本选区。
- 按既有会话/Agent 身份边界保存草稿、阅读位置和披露偏好；切回来恢复，不能把 A 的草稿发给 B。
- 搜索、查看任务或交付物后返回聊天，保留位置和未发送内容。
- 延续虚拟视口、增量渲染与异步加载设计，先测量再定位，不增加第二个滚动控制器。

落点：`useMessageViewportRuntime.ts`、`MessageList.tsx`、`ComposerTextInput.tsx`、会话状态和披露注册表。

### P1-A：收敛导航与搜索

- 工作区围绕“会话、任务、成果”组织；Agent 用于会话内筛选和切换，模型、技能、存储进入设置区域。
- 先调整现有顶部与侧栏分组。Checkpoint、朗读、诊断等低频能力进更多菜单，启用状态仍可见；常用入口保留文字。
- 将标题筛选和历史全文搜索汇合为一个入口，明确“当前会话/当前工作空间”范围。结果显示归属和摘要，可定位原消息并返回。
- 新建、归档、查看详情保留工作空间和 Agent 上下文；可恢复归档提供撤销，永久删除明确影响。

落点：`SessionSidebar.tsx`、`ChatMain.tsx`、`HistorySearchModal.tsx`、`WorkspaceNavigationHeader`、`AdminLayout`。

### P1-B：让交付物便于继续使用

- 报告、代码变更、图片和文件用紧凑结果卡表达：名称、类型、生成时间、来源任务/会话、预览及可用动作。
- 聊天正文保留结论与引用；详细内容宽屏侧边预览、窄屏抽屉查看，关闭后保留阅读位置。
- 任务详情直达对应会话和交付物，交付物可返回来源。依托真实 Artifact 引用与服务端授权，不根据模型文本自行声称文件存在。
- 明确重新生成是否覆盖旧结果；先盘点既有端点和版本合同，缺少支持时先完成可靠的只读预览与跳转。

落点：现有 presentation renderer、任务详情和 Artifact 数据合同，不复制存储或执行状态机。

### P1-C：统一视觉规则和可访问操作

- 保留 Pudding 品牌，统一字号层级、内容宽度、间距、灰阶、圆角、焦点和状态色；先覆盖 Chat、任务卡、设置表单。
- 正文、当前行为、历史过程、诊断参数分层；减少多个角落同时发光，尊重减少动态效果偏好。
- 硬编码颜色归入语义 token；上下文占用升高不自动等同于故障，系统自动处理和需要用户处理应区别表达。
- 图标操作有可访问名称、键盘焦点和足够热区。重要操作不只在 hover 时可达。建议桌面常用按钮热区 32–36px、触控 44px，这是产品目标；WCAG 2.2 AA 的最低要求为 24×24 CSS px，存在间距等例外。
- 检查 Windows 125%/150% 缩放、深浅主题、键盘操作、窄窗口；不能为了统一壳层把管理依赖重新装入 Chat 首包。

落点：全局 token、`PuddingPageHeader`、`PuddingToolbar`、`PuddingStatusBadge` 等组件及调用点。

### P2：有上下文的首次使用引导

- 保留现有四态，根据真实缺项提供“选择 Agent”“完成模型配置”等动作。
- 按当前工作空间和 Agent 能力给出 2–3 个示例；点击先填草稿，避免尚未看清就执行。
- 设置入口按用户问题组织，同时保留搜索和直接导航。

## 4. 实施顺序与验收

| 批次 | 可独立交付的范围 | 验收场景 |
|---|---|---|
| 第一批 | 鼠标排队/补充、独立停止、回执反馈、失败保留草稿、键盘可达 | 空闲发送、忙碌排队、当前补充、停止当前、中文选词、图片上传失败 |
| 第二批 | 活动摘要、错误反馈、长会话连续性 | 断线重连、子任务等待、历史阅读时新消息到达、展开工具与加载历史、切会话再返回 |
| 第三批 | 导航/搜索衔接、成果预览、三类高频页面视觉统一 | 搜索定位再返回、聊天→任务→交付物、Windows 缩放与深浅主题 |
| 后续 | 上下文引导和低频管理流程 | 新工作空间从空状态完成第一项实际工作 |

先记录当前版本基线，再按同设备、构建模式和夹具比较。以下为拟定目标，不是本次测量值：

- 本地按钮和输入反馈 p95 以 100ms 内为初始目标，与模型首 token 延迟分开统计。
- 用至少 100 回合、包含长 Markdown、图片、工具详情和子代理的会话，验证滚动、选区、搜索定位和切换恢复。
- 固定脚本验证中文输入不误发、失败草稿不丢失、队列不重复提交、停止范围明确、重连后事实不重复/倒退。
- 邀请少量实际用户完成“发任务→补充要求→看进度→打开结果”，观察误操作、返回路径和求助次数；时间类指标先测基线再定提升目标。
- 定向测试验证交互语义，浏览器与 Desktop 实机验收验证焦点、滚动、缩放和成品行为；后者未完成不能宣称体验验收通过。
