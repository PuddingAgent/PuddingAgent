## 2. 审计发现

### R1 / P1：Steering 成功回执会清掉用户后来输入的内容

位置：`Source/PuddingPlatformAdmin/src/pages/chat/index.tsx:631`，尤其第 637 行。

复现：提交草稿 A，在请求尚未返回时继续输入 B，服务端确认 A 已受理。`handleSteerCurrent` 无条件 `setInputValue('')`，B 被清空。旧设计已明确要求 compare-and-clear，当前仅失败分支保护新输入，成功分支没有保护。

独立反例 A7 从当前源码 AST 提取并执行真实回调，预期 B 保留，实际为空。修复应冻结提交时的草稿版本、会话和 Agent 身份；只有同一身份且草稿未改变才清空，不能只比较 trim 后的文本。

### R2 / P1：直接 Steering 没有在途锁，重复点击会重复受理

位置：`components/IntentConsole.tsx:541,772,1115`、`hooks/useMessageInteractionQueue.ts:390,441`（以下未写前缀者均位于 `Source/PuddingPlatformAdmin/src/pages/chat/`）。

菜单请求期间没有禁用；Hook 的单飞保护仅在 `sourceQueueItemId` 非空时生效，Composer 直接调用不传此字段。反例 A3 连续提交同一草稿，实际产生 2 个 API 调用。后端 `SessionSteeringService.cs:47-73` 同样仅在来源键存在时查重，否则生成不同 SteeringId，不能依赖后端自动合并。

修复：Composer 操作单飞锁、稳定 operation id、模糊网络重试复用同一标识；重试同一操作不能生成新的执行事实。必要的服务端幂等字段进入既有 admission 合同，不新建并行通道。

### R3 / P1：已有排队消息时，“补充当前任务”可能选中排队 Turn

位置：`hooks/useMessageInteractionQueue.ts:397-405`；受理跟踪见 `hooks/useMessageSend.ts:523-533`。

复现：T1 执行中，T2 已受理等待执行，再点击补充。Hook 从后往前找 `isActiveAssistantTurn || trackedTurnIds.has(turnId)`，而已受理 T2 也在 tracked 集合，且乐观 assistant 初始为 thinking。反例 A4 预期 T1，实际选择 T2。结果是向错误目标请求 Steering，通常被服务端非 Running 门禁拒绝，而不是补充当前工作。

修复：停止和 Steering 共享基于 canonical active run/Turn 的目标解析，严格区分 accepted/queued 与 executing；目标不明确时禁用并说明状态待同步，不按数组最新项猜测。

### R4 / P1：带图片时仍能插嘴，只发送了文字意图

位置：`components/IntentConsole.tsx:772-773,1115`。

可用性条件只检查 loading、composerHasText、回调存在，没有排除 pendingImages 或 imageUploading。反例 A8 暂存图片并输入说明后，插嘴按钮仍可用。回调只取文字，图片不会随 Steering 提交；成功后文字被清空而图片继续暂存，打散了用户原本的图文意图。

修复：与旧设计一致，待发图片或上传中禁用插嘴，显示原因，图文都保留，普通发送/排队继续可用；Ctrl/Cmd+Enter 与鼠标遵守相同门禁。

### R5 / P1：受理后的本地错误被当成未发送，恢复草稿可能导致重复执行

位置：`hooks/useMessageSend.ts:463,721`；新发送生成新 clientRequestId 见第 355 行。

复现：Turn POST 返回 202，随后 `dequeueCommand` 的 IndexedDB 操作失败。整个 try 块进入同一 catch，新加的 restoreDraft 无条件执行。反例 A6 证实，已持久受理的内容再次出现在可发送草稿中；用户重发会创建新的请求身份，与旧 Outbox 重放构成重复执行风险。

修复：按 admission 阶段区分明确未受理、受理不确定、已受理、本地投影失败；已受理只能对账或修复本地状态，不能伪装为未发送。失败草稿绑定发起时会话/Agent，不能回填到切换后的另一会话。重试复用 operation id；网络错误本身不能证明后端未受理。

### R6 / P1：停止依赖本地 POST 跟踪，恢复场景可能无请求；“取消全部”范围也未落实

位置：`hooks/useMessageInteractionQueue.ts:552-600`、`hooks/useSessionSelection.ts:182,299`、`components/MessageQueueDropdown.tsx:273-284`。

停止只从 activeMessageIds→messageIdToTurnId 映射取目标。会话切换清空映射，历史/快照可以先恢复活动卡片和 loading，metadata 重放尚未补齐时映射为空。反例 A1 的真实 Hook 输入中已有活动 Turn、loading=true，但点击停止发出 0 个取消请求，返回 0。

此外，“取消全部”仅停止当前并移除本地 steering_pending 投影，不取消服务端排队消息，也不撤销已受理 Steering。后端当前取消 handler 只接受 Running，所以不能把遍历本地 tracked 集合称为取消全部。请求失败也只记 perf 并吞掉，调用方没有结构化恢复状态。全局 request handler 可能弹通用错误，因此本审计不宣称所有错误必定无 Toast。

修复：复用 R3 的权威目标解析，显示“请求中→已受理→终态确认”及可重试失败；补已终态竞态、断网/503 和刷新恢复测试。在有真正的服务端队列撤销合同前，把“取消全部”改为符合实际范围的动作，不通过清掉本地显示来声称取消成功。

### R7 / P2：Composer 直接 Steering 仍增加“待发消息”计数

位置：`hooks/useMessageInteractionQueue.ts:331,418-435,669`。

反例 A5 直接提交 Steering 后，interactionQueue 从 0 变为 1。虽然没有因此创建普通 Turn，但 UI 将直接补充与普通待发消息合并展示，违背旧任务的独立回执合同。

修复：直接补充的 accepted/injected/failed 回执独立于普通待发数量；已有队列项转换为 Steering 的路径仍按其原合同呈现，不删除其历史。
