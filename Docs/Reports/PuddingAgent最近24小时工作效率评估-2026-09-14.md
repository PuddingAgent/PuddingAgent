统计窗口：**2026-09-13 19:55 至 2026-09-14 19:55，Asia/Shanghai**，左闭右开。对象为默认助手 `default.global_general-assistant.6a8`、主会话 `206a9b48ec904ebb93e7541131fbb835`、其 7 个子代理 Run，以及账本中相关后台模型调用。

## 1. 结论

**研发与局部自纠错能力已得到实际证明，但最近一天的交付效率偏低，连续无人值守能力不达标。**

- 有效产出不是零：通过主代理 git_commit 工具回执与本地 Git 双重核对，确认 **7 个属于 PuddingAgent 的提交，其中 2 批源码修复、5 批诊断/设计文档**。它能发现自身平台缺陷、登记问题、修改源代码并执行测试。
- 工作没有稳定转化为任务闭环：窗口内看板 **0 条 task.completed 事件、0 条验收评价**；2 次自动 Task-bound Goal 都以预算错误失败，同一 P0 卡又回到 Blocked。代码交付不能等同整张任务验收。
- 17 次明确标记为 heartbeat 的运行，**10 次 succeeded、7 次 failed**。成功的 10 次中，3 次没有任何工具动作，只输出压缩交接摘要；另 7 次有诊断、修改或委派动作，不等于 7 个任务完成。
- 最昂贵的失败子代理用掉 **1,325.39 万输入 token、118 轮、约 81.7 分钟**，最终未完成；缓存命中率却为 **98.39%**。高命中不能证明高效率。
- 12:52 的带图消息执行失败后，随后 6 次心跳和一次飞书文本再次报相同错误。至采样截止没有新的成功主会话终态；这段约 7 小时的能力中断，比压缩次数或单次模型速度更影响全天产出。

本轮只读运行数据/看板并形成报告；未向 Agent 发指令，未更新任务状态，未部署或重启。当前工作树中的心跳/图片/状态投影修复由其他任务进行，不纳入上述 PuddingAgent 产出。

## 4. 效率损失最大的地方

### P0：模型调用前的确定性故障，导致后续整条会话不可工作

commands 1997–2004 的 canonical `turn.failed` 都是：`Visual inputs require a workspace and a vision-capable route.`。六次心跳分别在 13:51、14:52、15:52、16:53、17:54、19:22；每次仅约 1.9–3.7 秒就失败，0 工具动作。这不是 Agent 主观不愿工作，也不是“省 token”的成果，而是模型调用链不可用。

同日其他任务的修复记录指出历史图片进入旧制品的 Responses 文本路由，并正在处理部署与无回复失败状态投影。本审计用 canonical 终态独立确认了故障串；尚未验收该在途修复。不能把其他任务的修复归作 PuddingAgent 自愈。

建议：明确“能带图推理”和“文本任务可继续”的能力合同；正确的视觉模型带图，不能静默丢图后声称理解。对同一确定性失败指纹去重、阻止无变化的自动重试，并使外部主管/运行中心可观察到故障和恢复条件。模型本身无法启动时，需要进程外恢复路径，不能依赖它再发一条自救提示。

### P0：600 轮已放宽，累计输入预算仍提前终止任务

7 个子代理 run.json 的 maxRounds 均为 600。本窗口没有跑到该轮数上限；两次自动 Goal 却分别报 `1011283/1000000` 和 `1020083/1000000` 的输入预算耗尽，所派子代理分别在 **21 轮、16 轮** 就终止，对应子预算 `909904/898621`、`879555/859472`。

累计重复输入与一次请求峰值是两个维度。有缓存的长上下文每轮重传会迅速用光累计 token cap；继续把轮数调大不会解决它。即使累计费用预算是业务需要，也必须明确按费用/累计账本约束，而不是复用 MaxInputTokens 名字暗示模型单次输入容量。

建议：统一区分单次输入窗口、累计调用费用、输出预算、轮数、运行期限和无进展条件；按主子聚合扣费时避免重复计账。预算耗尽应持久化检查点与可续跑状态；恢复性失败不应因释放 assignment 让原 Agent 永远失去 canonical 上报权限。先修 `3bd2a4b0`、`e2c35d6e`、`dc0ac9a8` 所涉及的闭环，再连续运行小批真实任务验证。

### P1：审批、探针与长等待耗掉大量时间

最明显的是 `run_20260913_233113_2c12ed4609a2` / `sub-450cb047`：

- 118 轮、165 工具、20 个工具失败状态；其中 shell 审批拒绝 11 次。
- shell 40 次、file_read 48 次、search_grep 38 次；最终 Run 错误仍是 shell 需要审批。
- tools.jsonl 累计工具耗时约 **3,306.6 秒**，LLM completed 累计约 **1,554.3 秒**。工具等待是主要耗时；这些分项含调度/嵌套等待，不能作为 CPU 精确分解。
- 同一 terminal job 两次 `terminal_wait(wait_seconds=600)`；后续 node probe7/probe8 分别发生约 600 秒、540 秒 shell 超时。参数在改变，精确 argsHash 重复额外次数只有 2，却没有形成任务结果。
- 消耗 13,253,899 输入 token，占全天 **25.17%**；这一个 Run 的高缓存率为 98.39%，无法抵消任务未完成。

另有主代理 command 1996 的 `file_search` 从 requested 到 completed **751.6 秒**，搜索范围 Source、pattern=`AgentExecutionWakeup*`、provider=`BuiltInRecursiveFileSearch`，最后只返回一个已有测试路径。这是确认的端到端延迟，尚未细分真正扫描、排队、审批/系统负载，不能直接定罪为递归算法耗时。

建议：委派前核对工具能力与审批条件；审批等待交给持久等待句柄，未授权时不可换工具/参数绕过。只读证据用经过授权的结构化查询和限时、小结果探针；同一目标连续无进展时，按目标/证据版本识别停滞，避免只按完全相同参数拦截。等待由事件唤醒，长命令要有可观测进度和超时后的止损。文件查找优先精确路径/索引，并补队列与实际执行时延拆分。

### P1：压缩交接与记忆整理挤占工作轮次

3 个成功 heartbeat（1984、1989、1993）各只有一次主模型账本调用，0 工具，共输入 **456,600 token**；结果都是工作纪要，没有本轮新的文件/工具/看板动作。可以认定为交接维护轮，不能当任务推进轮。其余有工具的成功心跳也可能只是诊断，不扩大为任务验收。

command 1996 的 goal_read 返回明确的 `truncated=true`：goal.md 已 **26.1 KB**、工具读取上限 **16 KB**。更早的回复已反复建议归档，却仍继续增长。这与长程记忆应该简洁、能定位下一步的目标相悖。

建议：工作状态只保留当前目标、下一条可执行动作、阻塞条件、检查点与引用；历史推理/交付证据进入有标题与索引的 Memory/报告。交接消息作为内部状态产物，与正常工作完成回复分开；心跳先由确定性状态判断是否有可执行事项，不能一再读取/重写整份纪要。接受摘要维护有价值，但单独计量其产出和成本。
