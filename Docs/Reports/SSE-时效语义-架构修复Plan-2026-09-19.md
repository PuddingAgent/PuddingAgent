# SSE 时效语义架构修复 Plan（2026-09-19）

现场触发：重启后 UI 仍显示「正在压缩上下文… 已运行 11466m 23s」，而上下文面板占用仅 10.9%。
第一次止血见 commit `d54b683`（前端按事件时间判定陈旧）。本文处理**根因**：实时通道失去时效语义。

## 一、被破坏的三条不变量

| # | 不变量 | 现状 | 证据 |
|---|---|---|---|
| I1 | **时效性**：live 流上的帧意味着「此刻发生」 | 无游标连接会把**多天前**的事件当实时帧下发，且帧上无法区分 | `SessionEventsController.cs:215/255` → `after = afterSequence ?? 0`；`SessionEventStreamService.FollowAsync` Phase 1 `while (nextAfter < head)` 无界回放 |
| I2 | **游标权威**：客户端游标是「我已应用到哪里」的唯一来源 | 两个独立游标源（`bootstrap.snapshotCursor` 与 SSE `Last-Event-ID`），不一致时静默退化为全量重放 | `useChatState.ts:1209` 注释已记录此坑，但只在常规会话切换处设防；`:883→:906`（压缩后继会话切换）与 `:1261→:1273`（checkpoint fork）先置 `lastSequenceNumRef=0` 再立刻开流 |
| I3 | **回放有界**：重放必须是显式且有界的 | `cursor=0` 绕过 410 快照校验（校验条件是 `cursor > 0`），随后全量回放 | `SessionEventsController.cs:215-236` |

后果不只是压缩卡：任何**依赖时效**的新事件类型都会踩同一个坑（「这不是现在发生的事」在协议层不可表达）。

## 二、消费侧的联系（为什么仅靠前端门控不够）

- 前端 SSE 消费：`useSessionEventConnection.ts:350` → `applySessionEvent(ev)`（**不带** replay 语义）
- 压缩 started 有两个渲染汇点，都会因「伪实时」而点亮：
  1. `useCompaction.handleCompactionLifecycleEvent` → 建专用压缩卡
  2. `useSessionEventProjection.mapEventToTurn` 的 `context.compaction.started` 分支 → 把普通 turn 翻成运行态
- 而按 compactionId 的判活门控只在 `replay === true` 时生效 → **对 live 通道完全无效**

## 三、方案对比

| 方案 | 做法 | 优点 | 代价/风险 |
|---|---|---|---|
| **A 协议层标记** | 帧上显式携带 `replay`（Phase 1 追赶 vs 实时） | 一次解决整类问题；消费端不再猜 | 帧字段新增（向后兼容，旧客户端忽略） |
| **B 无游标 = live-only** | 缺游标时不回放，从 head 起 | 危险默认消失 | **语义破坏**：`TestScripts/chat_e2e_test.py:222` 依赖「无游标=从头」；前端压缩后继会话切换也依赖该重放拿 compaction-origin 事件 |
| **C 回放加界** | 按条数/时效窗截断 + 相位标记 | 保留追赶能力 | 需要定「界」的语义与过期策略（410 已有部分机制） |
| **D 纯前端** | 总是显式传游标 | 不动后端 | 不解决结构问题；未来客户端可再踩 |

## 四、决策：A 先行（协议层建立不变量），B/C 分阶段，D 补齐

原则：**先在协议层让「回放 vs 实时」可表达**（A），消费端改用该信号；把语义破坏性的 B 放到最后，且只在我们自有调用方全部改为显式传游标之后。

### S1/S2 的验收

- 后端：`FollowAsync` Phase 1 的帧 `IsReplay=true`，Phase 2 实时帧 `IsReplay=false`；SSE 帧 JSON 含 `replay`；Core 日志出现 `SSE subscribed ... cursor=<n> phase=replay-from-zero|replay-after`
- 前端：`jest chatStateUtils + useCompaction` 全通过；新增用例覆盖「replay 帧上的新鲜 started 仍点亮」「replay 帧上无时间戳的 started 不点亮」「live 帧上的陈旧 started 不点亮」
- 端到端：重启后打开会话，不再出现历史压缩卡的运行态

### 风险与回滚

- 风险 1：`replay` 字段被旧客户端忽略 → 行为退回今天（安全）。
- 风险 2：把「短暂断线期间真的在运行的压缩」判成 replay 而漏显示 → 已用「确定新鲜即点亮」消除（原按 id 的门控反而会误杀）。
- 回滚：S1 是新增字段、S2 是消费侧分支，均可单独 revert；无数据迁移。

## 五、实施顺序的经验（原「S3/S4 之前不建议做的事」，已由本切片处置）

- 「不要直接改『无游标 → live-only』」**成立但可解**：关键在于先让客户端能**显式表达**自己的位置。做法是先修协议可表达性（客户端任何游标含 0 都下发 `Last-Event-ID`），再改服务端默认。顺序颠倒才会静默丢事件。
- 「不要拿 `lastSequenceNumRef` 清零当重放意图」——本切片按此执行：两处调用点改为**显式** `cursor: 0` + `reason`，清零动作本身不再承载语义。

## 六、S3 实施中的一处「偏离 Plan」及依据

Plan 原文要求两处 `=0` 调用点「改为先取 head」。实施时核实后**改为显式 `cursor: 0`**，理由：

1. `switchToCompactedSessionPreservingTurns`（`useChatState.ts:849`）**保留**上一会话的 turns（`turnsRef` 不动），只切 sessionId，因此后继会话的**早段事件是必需的**——包括压缩来源事件与承接中的 turn。若「先取 head」会跳过它们，属于功能性回归。
2. 该会话是**压缩当场新建**的，事件日志必然很短 → 全量回放有界，不存在 Plan 所针对的「把多天前的事件当实时帧」风险。
3. `forkCheckpointToNewSession` 同理（分支会话新建，需保证新会话低位事件不丢）。

因此「有界性」由**调用点语义**保证（只在新会话上用显式 0），而非由「取 head」保证。若将来出现「在旧会话上显式 0」的调用，必须重新评估。

## 七、S4 剩余项（已处置，2026-09-19 续作）

原先有意未做，因为前置条件不成立：`useSessionEventConnection` 对**任何** 410 都走 `handleSessionNotFound`（会话被标为终态），放开 `cursor=0` 会把「重取快照」误判成「会话没了」。

前置条件已先落地：

1. `api.ts` 从错误响应体读出结构化 `code` 并透出（解析失败不影响错误分类）；
2. `useSessionEventConnection` 按 `code` 分流 —— `snapshot_required` 走**恢复**路径（端口 `syncCompletedHistoryEventCursor(sessionId, signal, {resetCursor: true})` 重取快照并**强制**把游标置为快照位置，然后重连），其余 404/410 仍为终态；
3. `connectionManager`（ADR-057 新运行时的 dead code）同步分流。

随后才放开后端校验，而且**不是**简单地把 `cursor > 0` 去掉 —— 见 §八。

## 八、`cursor=0` 校验为什么不等于「去掉 cursor>0 判断」

若直接把 `cursor < min` 套到 `cursor=0`，会因为**序号原点就是 1**（`conversation_heads.head_sequence` 从 0 递增后分配）而让**每一次**合法的「显式 0 全量回放」都返回 410 —— 而那正是 compaction 后继会话与 checkpoint fork 依赖的路径。

所以判据改为**缺口**语义（`Services/SnapshotRequiredCheck.cs`）：

    HasMissingEvents(cursor, min) => min.HasValue && cursor + 1 < min.Value

- `cursor=0, min=1` → false：号段连续，全量回放合法，**不再 410**；
- `cursor=0, min=51` → true：1..50 已不可读，确有缺口，要求重取快照；
- 顺带修掉旧判据的假阳性：`cursor == min - 1`（客户端已持有 min 之前的全部事件）本无缺失，旧判据却报 410。

**诚实限定**：当前代码库**没有任何裁剪 `conversation_events` 的路径**（全仓无 `DELETE FROM conversation_events`），因此 `min > 1` 在实践中不会出现，`snapshot_required` 分支目前**不可达**；前端恢复路径也因此无法端到端验证。本次交付的是「机制正确 + 单测锁定」，不是「已在生产触发过」。

### 9.2 新增两条集成用例（`Source/PuddingWebApiTests/SessionEventsControllerTests.cs`）

| 用例 | 断言 |
|---|---|
| `EventsStream_WithExplicitZeroCursor_ReplaysHistoryAndMarksFramesAsReplay` | 显式 0 → 首帧 `sequence == 1`；**全部帧 `replay == true`**；序号严格递增 |
| `EventsStream_WithoutCursor_DoesNotReplayHistory` | 无游标 → 首帧 `replay == false` 且 **`sequence > 历史 head`**（即历史未被回放） |

B 案的构造要点：先写好 3 条历史事件，再发起无游标连接，然后在读取过程中**持续追加**新事件（追加会 signal 事件通知器）。这样无论服务端在哪一时刻读取 `head`，首帧都必然是「订阅之后产生的事件」——避免了「追加先于 head 计算」造成的竞态，断言不依赖时序运气。
