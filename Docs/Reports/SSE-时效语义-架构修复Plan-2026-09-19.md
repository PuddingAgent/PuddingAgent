# SSE 时效语义架构修复 Plan（2026-09-19）

现场触发：重启后 UI 仍显示「正在压缩上下文… 已运行 11466m 23s」，而上下文面板占用仅 10.9%。
第一次止血见 commit `d54b683`（前端按事件时间判定陈旧）。本文处理**根因**：实时通道失去时效语义。

---

## 一、被破坏的三条不变量

| # | 不变量 | 现状 | 证据 |
|---|---|---|---|
| I1 | **时效性**：live 流上的帧意味着「此刻发生」 | 无游标连接会把**多天前**的事件当实时帧下发，且帧上无法区分 | `SessionEventsController.cs:215/255` → `after = afterSequence ?? 0`；`SessionEventStreamService.FollowAsync` Phase 1 `while (nextAfter < head)` 无界回放 |
| I2 | **游标权威**：客户端游标是「我已应用到哪里」的唯一来源 | 两个独立游标源（`bootstrap.snapshotCursor` 与 SSE `Last-Event-ID`），不一致时静默退化为全量重放 | `useChatState.ts:1209` 注释已记录此坑，但只在常规会话切换处设防；`:883→:906`（压缩后继会话切换）与 `:1261→:1273`（checkpoint fork）先置 `lastSequenceNumRef=0` 再立刻开流 |
| I3 | **回放有界**：重放必须是显式且有界的 | `cursor=0` 绕过 410 快照校验（校验条件是 `cursor > 0`），随后全量回放 | `SessionEventsController.cs:215-236` |

后果不只是压缩卡：任何**依赖时效**的新事件类型都会踩同一个坑（「这不是现在发生的事」在协议层不可表达）。

## 二、消费侧的联系（为什么仅靠前端门控不够）

- 前端 SSE 消费：`useSessionEventConnection.ts:350` → `applySessionEvent(ev)`（**不带** replay 语义）
- 压缩 started 有两个渲染汇点，都会因「伪实时」而点亮：
  1. `useCompaction.handleCompactionLifecycleEvent` → 建专用压缩卡
  2. `useSessionEventProjection.mapEventToTurn` 的 `context.compaction.started` 分支 → 把普通 turn 翻成运行态
- 而按 compactionId 的判活门控只在 `replay === true` 时生效 → **对 live 通道完全无效**

## 三、方案对比

| 方案 | 做法 | 优点 | 代价/风险 |
|---|---|---|---|
| **A 协议层标记** | 帧上显式携带 `replay`（Phase 1 追赶 vs 实时） | 一次解决整类问题；消费端不再猜 | 帧字段新增（向后兼容，旧客户端忽略） |
| **B 无游标 = live-only** | 缺游标时不回放，从 head 起 | 危险默认消失 | **语义破坏**：`TestScripts/chat_e2e_test.py:222` 依赖「无游标=从头」；前端压缩后继会话切换也依赖该重放拿 compaction-origin 事件 |
| **C 回放加界** | 按条数/时效窗截断 + 相位标记 | 保留追赶能力 | 需要定「界」的语义与过期策略（410 已有部分机制） |
| **D 纯前端** | 总是显式传游标 | 不动后端 | 不解决结构问题；未来客户端可再踩 |

## 四、决策：A 先行（协议层建立不变量），B/C 分阶段，D 补齐

原则：**先在协议层让「回放 vs 实时」可表达**（A），消费端改用该信号；把语义破坏性的 B 放到最后，且只在我们自有调用方全部改为显式传游标之后。

### 切片

| 片 | 内容 | 状态 |
|---|---|---|
| **S1** | `SessionEventEnvelope.IsReplay` + `FollowAsync` Phase 1 打标 + SSE 帧输出 `replay` 字段 + 连接相位日志（cursor/phase） | ✅ 本次实施 |
| **S2** | 前端消费 `replay`：`applySessionEvent(ev, { replay })`；压缩 replay 门控细化为「有权限来源→按 id，无来源→要求确定新鲜」 | ✅ 本次实施 |
| **S3** | 前端**必须**显式传游标：两处 `=0` 后立刻开流的调用点改为先取 head；`lastSequenceNumRef===0` 时不再默认「回放全部」 | 待办（需先确认压缩后继会话切换的真实依赖） |
| **S4** | 后端：无游标 → live-only（fail-safe）；`cursor=0` 也走 410 快照校验；同步修 `chat_e2e_test.py` 显式传 `afterSequence=0` | 待办（语义变更，需用户裁决 + 全调用方改造后） |

### S1/S2 的验收

- 后端：`FollowAsync` Phase 1 的帧 `IsReplay=true`，Phase 2 实时帧 `IsReplay=false`；SSE 帧 JSON 含 `replay`；Core 日志出现 `SSE subscribed ... cursor=<n> phase=replay-from-zero|replay-after`
- 前端：`jest chatStateUtils + useCompaction` 全通过；新增用例覆盖「replay 帧上的新鲜 started 仍点亮」「replay 帧上无时间戳的 started 不点亮」「live 帧上的陈旧 started 不点亮」
- 端到端：重启后打开会话，不再出现历史压缩卡的运行态

### 风险与回滚

- 风险 1：`replay` 字段被旧客户端忽略 → 行为退回今天（安全）。
- 风险 2：把「短暂断线期间真的在运行的压缩」判成 replay 而漏显示 → 已用「确定新鲜即点亮」消除（原按 id 的门控反而会误杀）。
- 回滚：S1 是新增字段、S2 是消费侧分支，均可单独 revert；无数据迁移。

## 五、S3/S4 之前不建议做的事

- 不要直接改「无游标 → live-only」：会静默丢掉压缩后继会话的 compaction-origin 事件（`useChatState.ts:883` 注释明确该依赖）。
- 不要把前端 `lastSequenceNumRef` 的清零逻辑当作「重放意图」的表达——它是「会话切换」的副作用，两者必须解耦。
