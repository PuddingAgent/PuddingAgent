## 3. 代码原因

### P0：raw-token 上限实际检查整个请求

`Source/PuddingRuntime/Services/ContextCompactionOptions.cs` 的 `MaxActiveRawTokenBudget=131072`，注释定义为“未压缩活动原文”的绝对上限。

`ContextCompactionService.GetHealthAsync` 却用 `usage.UsedTokens > MaxActiveRawTokenBudget`，与相对窗口阈值构成 OR。`ResolveCurrentContextUsageAsync` 优先取最近请求/Provider 快照，不是待压缩 DB 原文的独立预算。

这意味着固定系统提示、工具定义及不属于压缩候选区的当前轮内容，都可能触发“历史原文过大”。本次仅工具定义和系统层的本地估算就有 58,434 token，已占绝对阈值的 44.6%。这不是要求关闭工具，而是应纠正预算对象。

### P0：保守估算与 Provider 实报混在一个字段

`Source/PuddingCore/Platform/LlmOptions.cs` 的 `ContextUsageSnapshotStore.RecordProviderUsage` 使用 `max(existing.UsedTokens, Provider.TotalTokens)`，却将 Source/Confidence 标记为 `provider_usage/provider_reported`。

同文件校准比例只允许大于等于 1，且通过 max 保留高值。本次本地估算比 Provider PromptTokens 高约 70%，仍主导压缩判断。保守上界可用于防超窗，但不能伪装为实报，也不应直接充当经济性压缩的唯一触发值。

### P1：缺少收益门槛和基于内容变化的抑制

`CompactionCoordinator` 只有成功后 30 秒冷却；没有“自上次压缩新增了多少可压缩原文”“这次预计能回收多少整请求空间”的准入条件。失败/no-op 不记录成功冷却。

9 月 12 日 23:27:05 的 `35b4e685c9f1438181e7b822878309a9`：已花 17.1 秒生成摘要，随后因摘要膨胀跳过写入。诊断 JSONL 记录摘要输入 2,102 → 3,845、count=0；canonical completed 则记录活动消息 17,255 → 17,255、`skippedDueToTokenIncrease=true`。当前“不增反升则跳过”保护确实有效，问题是事后才止损，且日志两处 before/after 语义不同。

### P1：展示和诊断会放大体感

`Source/PuddingPlatformAdmin/src/pages/chat/hooks/useCompaction.ts` 在同一个 started 事件中更新压缩卡片并创建顶部 loading toast；`useSessionEventProjection.ts` 也有 compacting 行为轨迹投影。截图中的 toast 与卡片不能计为两次压缩，本轮 canonical 事件按 compactionId 没有发现重复 started。

`ContextWindowManager.TryAutoCompactAsync` 在 flush、CompactAsync 的锁/冷却/候选检查之前发 started；无写入结果仍记录 succeeded/completed。因而“完成流程”不等于“成功回收上下文”，需要分开呈现。当前 requested 出现在 started 后，是不同层发事件的实际顺序，不应拿名称推导阶段先后。

## 4. 建议实施顺序

1. **先修预算合同，不先简单调大阈值。** 区分 Provider 实报输入、本地估算、保守安全上界、可压缩历史原文、当前轮、系统与工具固定成本。安全防超窗按最终整请求上界；自动历史压缩按可回收候选区与真实窗口压力。原文 cap 只约束它命名的对象。保持工具与任务能力不变。
2. **区分暖会话运行和冷启动水合。** `MaxHydrationTokenBudget=49152` 是源码中的冷启动回放预算，不是要求正在工作且有前缀缓存的会话频繁压缩到 49K。冷启动采用摘要、近期原文和检索补充；暖会话在有足够窗口时保留稳定前缀。新 Session 的初始占用单独分层计量。
3. **增加可复用的压缩计划与收益准入。** 在 summary/flush 前得到候选边界、可回收量、新增原文量、压缩代次和当前轮保护结果。低收益时 defer；确有安全压力则优先回收工具大载荷/历史，不能靠冷却阻止必要的防溢出处理。具体门槛需用历史请求回放调优，不在本轮拍定数字。
4. **用代次/请求身份管理快照。** 成功压缩或重新组装后旧 usage 不能继续代表新上下文；按 session、model、request、contextGeneration 关联快照。对同一候选集合的 no-op/膨胀失败记录有限退避，新数据或真实窗口压力到来后才重新评估。不得用延长时间限制掩盖统计错误。
5. **统一运行结果与 UI。** completed 结果显式区分 compacted、deferred、skipped、failed；记录 triggerReason、候选 token、最终请求前后 token、回收量、耗时。前端按同一 compactionId 展示单个主状态，自动压缩无需同时永久 toast 与大卡片；历史回放不再次弹 loading。
6. **再验收缓存和长程效果。** 固定任务/工具集合，对照压缩次数、每百次主模型调用压缩率、有效回收率、压缩用时、provider token 加权缓存命中率、任务完成速度和记忆检索正确率。不能靠减少模型调用或删任务来宣称缓存优化，也不能以不压缩换取最终超窗。

## 5. 必须覆盖的验证场景

- Provider 实报约 120K、本地估算约 205K、有效窗口 616K、可压缩历史仅约 17K：不得仅因固定工具/系统估算跨 raw cap 就强制压缩。
- 大窗口长期任务、短会话、小窗口、模型切换、工具 schema 变化、长工具结果、接近真实输入上限、冷启动检索回放分别验证。
- 连续请求在同一压缩代次内没有新增候选时，不重复生成无收益摘要；新内容到来后仍能重新评估，真正超窗时不能被退避拦住。
- 当前轮/工具调用配对与 canonical transcript 覆盖不回归；摘要变长必须返回 skipped，不伪装为成功回收。
- 同 compactionId 的 SSE 重放、断线重连和正常完成不制造重复提示或残留 loading。
