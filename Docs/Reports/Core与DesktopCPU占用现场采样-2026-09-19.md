此前 17:23:09–17:23:29 的四个窗口，Core 为 0.16%–0.51%、Desktop 为 1.64%–2.57%。另取 10 秒窗口核对 Desktop 所属的 6 个 WebView2 进程，CPU 增量均为计时精度内的零；同期 Core 0.195%、Desktop 2.597%。此结论限于该窗口，不能外推为网页永远不耗 CPU。

Desktop 线程 37760 在最初四个 5 秒窗口分别消耗 0.906、0.953、0.562、0.938 CPU 秒，占该进程大部分增量。通过只读 `NtQueryInformationThread(ThreadQuerySetWin32StartAddress)` 查询起始地址并映射已加载模块，属于 `Microsoft.WindowsDesktop.App/10.0.12/wpfgfx_cor3.dll`。托管栈中主 UI 线程停在 GetMessageW；仅抓托管栈会漏掉这个原生热点。

`Views/WorkbenchView.xaml.cs:104` 使用 `WebView2CompositionControl`，让网页参与 WPF 合成以解决窗口层叠问题。当前证据将持续消耗定位至 WPF 图形线程；是否由该控件持续捕获、窗口尺寸、重绘、阴影或图形驱动导致，仍需原生 CPU 调用栈和可见/隐藏对照，不能仅凭模块名称进一步定因。

Core 的一次托管栈捕获到 `FeishuStreamingProjectionWorker.ProjectBatchAsync` 查询 SQLite；源码空批次后等待 300 ms，工作批次后等待 100 ms。这说明存在常驻后台轮询，但当前 Core 占用很低，不能据此解释截图的 15.4%。
