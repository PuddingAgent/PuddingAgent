## 1. 判断与推荐顺序

当前最值得做的优化，是把已有运行事实、请求快照和前端投影的责任收敛，并消除几处明确的并发与无界工作量问题。现在不适合启动全仓重写、全面插件化或更换前端框架。

当前代码已经建立了 Desktop/Core 边界、canonical Conversation 事件、ExecutionLease、任务结算、上下文压缩覆盖检查、工具渐进发现、前缀指纹、消息虚拟化和部分有界查询。优化应复用这些基础，避免再次建立平行系统。

建议先交付以下六项：

1. F01：修复 Chat 明细水合并发上限与会话切换生命周期。
2. S01：修复 Token 月度聚合的并发更新，建立请求级不可变归因。
3. C01：把 Composition 的恢复与提交从遥测旁路中独立出来。
4. R01：归档补偿改为有界发现、增量读取，降低重复 IO 和分配。
5. F02：为 Chat 读模型建立可靠版本与增量投影，减少全量快照重建。
6. A01：清理入口项目遗留服务注册副本，明确唯一组合根与文档入口。

其中 F01、S01、C01 都能从当前源码直接定位，建议与较大的运行内核拆分分开提交。C02 的精确缓存观测可在完成请求身份合同后推进；不要等所有重构完成才开始采集七日基线。

### 1.1 优先级和证据口径

- P1：本轮最应优先实施，涉及正确性、运行稳定性或显著的重复工作。
- P2：重要的结构收敛或效率改造，需在核心合同和基线明确后实施。
- P3：根据测量决定是否值得做，不应阻塞前两类工作。
- “源码确认”表示存在相应实现或可推导的执行交错；不表示已经在线上复现。
- “需实验量化”表示风险有代码依据，但收益、发生频率或资源占比尚未测得。
- 本轮没有足够证据将某项标为正在发生的 P0 生产故障。

## 4. F01：Chat 明细水合并发与生命周期

### 当前代码与问题

主要文件：Source/PuddingPlatformAdmin/src/pages/chat/hooks/useTurnSurfaceStore.ts。

该 hook 过滤已完成、可见、未水合、未 in-flight 的消息后执行 slice(0, 2)。这限制的是“本次 effect 新启动的数量”，不是总并发数。旧请求仍 pending 时，conversationView 更新、可见项注册或另一请求结束均能触发 effect，继续新增两个不同请求。

可以确定性安排的交错：

~~~text
effect #1：m1、m2 开始，均未结束；inFlight=2
新的 projection 对象到达
effect #2：m1、m2 被过滤，m3、m4 开始；inFlight=4
~~~

另外：

- visibleTurnIdsRef 只有 add，没有离开视口的 unregister；会话 reset 未清空该集合。
- 会话切换只清空 in-flight Set，没有 AbortController 终止旧网络请求。
- then 做了 conversationId 检查，但 catch/finally 仍会修改共享 Set；A→B→A 时仅比较 conversationId 也不能区分两代 A 请求。
- failedMessageIds 在每个 conversationView 更新时清空，明细接口失败可随 1.2 秒快照轮询反复重试。
- 现有名为 keeps hydration concurrency bounded 的测试使用立即 resolve 的 mock，只检查总调用三次，没有检查同时未完成请求的峰值。

### 建议设计

抽取一个页面作用域 DetailHydrationScheduler，hook 只负责与 React 订阅衔接。维持 capacity=2、queue、activeRequests、generation 和 failureState；同时限制当前页面尚未结束的请求数。若 abort 不能立即结束旧请求，旧请求继续占物理槽位，避免快速切换反复叠加请求。

请求键至少包含 workspaceId、agentId、conversationId、messageId、detailsRevision。每次会话选择变更递增 generation；所有成功、失败、finally 回调均先检查 request token 是否仍为该键的 owner，旧 callback 不得删除新请求的锁或修改新会话失败状态。

最小补丁可先用 availableSlots=max(0, 2-activeRequests.size) 替换固定 2，但必须同时处理取消、切换和失败退避。仅改 slice 不能完成本卡。

visibleTurnIds 改为挂载/卸载引用计数或由 viewport 提交当前可见集合；离开视口后停止新预取，已取得的非活跃详情进入有字节上限的 LRU。最新活动回合、当前展开详情可 pin。不要因缓存淘汰删除 canonical 历史。

错误分类：401/403 等待认证变化；404 对该 details revision 终止；临时网络错误使用有界指数退避与 jitter。projection 更新不能重置同一失败的 retry budget；用户手动重试可以重新开启预算。

### 验收

用可手动 resolve 的 deferred promise 验证：8 条可见消息、连续 20 次重渲染，未完成请求始终 ≤2；释放一个槽位只补一个；最终全部需要的详情可取得。补 A→B→A、旧请求迟到成功/失败、unmount、401、404、持续失败、离开视口和同一详情新 revision 的测试。必须同时验证取消旧请求不会误清理新请求。

## 5. S01：可信的 usage 事实、并发聚合和请求归因

### 当前代码与问题

Source/PuddingPlatform/Services/TokenUsageRecorder.cs：

- 先 AnyAsync 检查 SourceType/SourceId，再添加事件。
- 读取 TokenUsageStats 后在 CLR 中执行 +=，最后 SaveChangesAsync。
- 月度聚合具有月份/Provider/Model 唯一索引，但未配置相应并发版本。
- ContextLayerMetric 读取按 sessionId 保存的“最近一次” ContextAssemblyStore / ContextUsageSnapshotStore。

两个独立 scope 处理不同请求时，可能同时读到 RequestCount=100，分别写回 101；两个事件均可成功落库，但聚合少一次。SQLite 串行执行写事务不等于能够保护事务外已读取的旧值。同一 source 并发还可能在第二次 SaveChanges 遇唯一约束异常；提前 AnyAsync 不是最终幂等保证。

如果归因投影延迟到下一轮之后处理，读取 session 最新快照可能把 A 请求归到 B 的 layer/hash/token estimate。ContextAssemblyStore 最多保留 10 个 session，此时还可能完全缺失归因。不能把调试缓存作为可延迟消费的事实源。

### 建议设计

先确定三类身份：

| 字段 | 含义 |
|---|---|
| invocationId | Agent 发起的一次逻辑模型调用 |
| attemptId | 实际向 Provider 发出的某一次网络请求；重试产生新 ID |
| providerRequestId | Provider 返回的请求 ID，可为空，不承担本地唯一性 |

父 Turn/Run/ToolCall、purpose、模型路由、compositionVersion、requestShapeId 在发送前冻结。usage 回来时与该 attempt 直接关联。保留既有 SourceId，明确新合同和已有字段的映射，避免全链路同时改名。

在同一个数据库事务中：

~~~text
INSERT usage_event ... ON CONFLICT(唯一 source) DO NOTHING
读取本次是否确实插入
仅 inserted=true 时：
  原子 UPSERT 月度聚合，counter = counter + excluded.counter
  写 attribution/outbox 或相同事务内的明确事实
COMMIT
~~~

金额计算保持既有 decimal 语义和单位；若 SQLite 表达式无法确保目标精度，应统一使用显式精度的定点单位或经过验证的转换，不能顺手改为 double。版本迁移单独定义，不要求为本卡重写整个金额体系。

唯一约束冲突只有在核实“同身份、同 payload”时作为幂等成功；相同 ID 不同 usage 记录为冲突，不能覆盖。新月份并发、不同模型并发、取消、busy 重试都必须覆盖。发生故障时重试本地提交，不得重发已经成功的 Provider 请求。

把 RequestUsageAttribution 作为不可变小对象随 invocation/outbox 传递，包含 layer metrics 的值或不可变快照 ID。调试缓存继续服务 UI，但不参与事实归因。诊断投递允许 best-effort；账本写入失败必须保留 pending 状态和 durable 重试证据。如果只设计内存队列，不算 durable。

网关账本与 attribution 的事务边界必须写清：可同库原子写则直接同事务；跨调用边界则由账本事务记录待归因 outbox，再由幂等消费者补齐。进程在 Provider 成功与本地持久化之间崩溃的窗口不能靠普通 outbox 消除：请求发送前记录 pending attempt，恢复后标记 outcome_unknown，并在 Provider 支持查询/幂等时核实，不能盲目重发或编造 usage。

已有 TokenUsageDailyAggregateService 应复用，但已关闭日的缓存要能被迟到 usage 失效或按 checkpoint 重建；不能假定昨天的所有 usage 永远准时到达。UTC 日统计不能直接冒充北京时间验收日。

### 验收

使用真实 SQLite 文件临时库与独立 DbContext，barrier 控制 50 个调用读写交错：事件数、聚合请求数、Token、金额完全对齐；重复 source 只加一次；同 ID 异内容被报告；失败事务不留下半个聚合。A 请求延迟归因且 B 已写调试缓存，A 仍关联 A 的 requestShape。次日补录前一天 usage 后，日报与原始账本重新对齐。

## 6. C01：Composition 是执行状态，不能依赖遥测

### 当前代码与问题

Source/PuddingRuntime/Services/DirectLlmClient.cs 的 RecordCompositionSnapshotAsync 在 _telemetrySink 为 null 时直接 return；Observe 在此检查之后执行。因此 Composition 的版本观察与持久化是否发生，依赖遥测 sink 是否注入。

PersistentCompositionVersionRegistry.Observe 用 fire-and-forget 写穿；未等待落盘就允许模型请求继续。RecoverFromStoreAsync 每次加载该 session 全部记录；Buffered 路径还用 CancellationToken.None 调恢复。没有“该 session 已恢复”的明确加载状态。

CompositionVersionRegistry 使用 hash → version 映射。同一权限指纹下依次观察 A、B、A，可返回 1、2、1。持久登记按“version 大于已持久最大值”判定是否写入，第三次 A 不会成为最新持久头。这里混淆了可复用的内容身份与单调的状态修订号。record 用 long，但 observation 和内部计数用 int，也存在合同不一致。

当前 PermissionFingerprint 来源是本次可见 toolIds；搜索加载新工具就可能被记成 permission_changed，而同一个工具的参数授权范围改变并不一定改变 ID 列表。此处主要是 epoch/诊断语义问题，不据此声称权限执行检查已失效。

恢复只保留工具 ID 与 hash，再用当前 availableTools 重建 schema。它能恢复工具名称，不能证明重启前后定义正文、顺序、提示版本和 Provider 转换结果相同。

### 建议设计

将 ObserveDiagnostic 与 CommitComposition 分离。执行路径必须能在没有遥测的情况下恢复和提交 Composition；telemetry 只订阅已发生的提交事实。

建议在现有合同上增加以下明确语义，而非新增平行快照系统：

~~~text
CompositionRevision : long  每次有效状态转换严格递增，包括 A→B→A
ShapeContentId       : hash 相同内容可复用，和 revision 是两个维度
PermissionEpoch      : long 来自实际授权配置的版本/指纹
ExposureRevision     : long 来自工具发现/显示集合变化
ContextGeneration   : 压缩/水合后的上下文代
ProviderRoute       : providerId/modelId/protocol/adapterVersion
ToolBindings        : 有序 (toolId, definitionVersion, schemaHash)
StableInputVersions : persona/skill/环境/配置的版本引用与内容 hash
~~~

同一个 revision 内工具描述与参数 schema 不可变。工具发现结果先进入 pending exposure，在下一轮边界批量提交；首个集合确定后追加新项，不对全量集合重新字母排序。当前 ToolExposurePlanner 每次全量按名字排序，新工具可能插到已有前缀中部。改变排序策略本身需要一次明确 epoch，不保证 Provider 一定缓存 top-level tools 的任何特定位置。

PermissionEpoch 变化由授权源发布，立即生效并强制校验；不得为缓存保留已撤销权限。工具是否可见与工具是否可执行分别判定。

提交顺序：

~~~text
获取现有 session execution gate
恢复 latest composition（每个 generation 一次，single-flight）
解析当前配置与权限版本，形成 proposed composition
在现有存储中 CAS append：expectedRevision → newRevision
提交成功后发布 immutable request snapshot，允许 Provider 调用
单独发送诊断事件
~~~

只在组成变化时做持久写，普通轮次复用已提交快照，因此不必为每个 delta 或普通请求增加数据库写。CAS 冲突重读并重新计算，不能由“MAX 后 INSERT”代替完整预期版本检查。

CompositionSnapshots 保持不保存 prompt/schema 正文的当前原则。为确保可重建，ToolBindings 应引用已有或拟补充的不可变工具定义版本目录/插件包，而不是只引用当前注册表；人格、Skill 等也引用可解析版本。若旧版本不可用，创建原因明确的新 revision 并使用当前有效配置，不谎称字节恢复。若未来确需保存组成正文，要单独更新对应 ADR 的保留与访问合同，不能混入遥测表。

存储短暂不可用：有已提交快照且权限仍有效时可以明确标记复用旧快照；需要新组成却不能提交时返回可重试的 composition_commit_unavailable，不能静默发出未提交形状。取消照常传播。原有“失败降级为纯内存”的接口注释和测试要同步修改，否则新旧语义冲突。

### 验收

无 telemetry sink 时仍提交；A→B→A 的 revision 为 1、2、3，contentId 为 A、B、A；重启恢复第三次 A。提交前崩溃不发模型请求；提交后崩溃能恢复；权限撤销不可因冻结工具而延迟。新 schema 发布、工具不可用、Skill 变化、纯温热复用、storage busy 和 cancellation 各有独立用例。

## 7. C02：在最终序列化边界建立可解释的缓存观测

### 当前代码与问题

CompositionSnapshot.ComputeToolSpecHash 与 PrefixCacheSnapshotBuilder.Build 使用不同的 system 范围和工具属性排序规则；后者增加了第一个非 system 历史消息的锚点，但仍无法定位后续历史中部的修改。SerializationVersion 是工程常量，不足以证明 Provider Adapter 的实际输出未变化。

本轮按 RequestShapeManifest、FirstChangedSegment、PrefixEpoch 符号检索未找到对应实现。已有 hash、HistoryAnchorHash、layer metrics 很有价值，但不等于完整请求形状归因。

### 建议设计

在每个 Provider Adapter 最终构造模型可见消息和工具的地方产出 PreparedProviderRequest：发送内容与诊断 manifest 共享同一份确定性构造结果。不要在 Runtime 另写一套“近似序列化”然后宣称其等同线上请求。

RequestShapeManifest 至少含：

| 字段 | 说明 |
|---|---|
| invocationId / attemptId / requestShapeId | 与账本一对一关联 |
| providerId / modelId / protocol / adapterVersion | 不同模型与协议分开比较 |
| compositionRevision / contextGeneration | 组成和历史变化归因 |
| modelVisibleEnvelopeHash | 最终模型可见载荷的确定性指纹 |
| transportEnvelopeHash | 可选，区分 stream 等传输参数；排除认证头和 secret |
| segments[] | 按实际请求顺序记录 kind、stableId、role、hash、UTF-8 bytes、估计 tokens |
| previousComparableRequestId | 同一路由/会话/序列化版本的上一可比较请求 |
| firstChangedSegment / commonPrefixBytes | 客户端能确定的首个变化及公共前缀 |
| declaredChangeReasons[] | configuration、permission、exposure、compaction、rehydration 等，可同时出现 |
| comparisonStatus | comparable / initial / unavailable / serialization_changed |

segments 应包含 system/developer、tools、逐条历史、typed image/tool output、当前输入；不能只覆盖 L0–L4。同一 content part 使用稳定 artifact hash/版本引用，不把可变的临时 URL 当唯一内容身份。

UTF-8 字节偏移不是 Provider tokenizer 的 token 偏移，Provider 内部缓存布局也不可见。commonPrefixBytes 只代表客户端载荷变化；估算 token 需带 tokenizer/version/confidence。不要从一个 hash 或 gzip 比例推出精确 miss token 数。

分两层给出原因：

1. 可确定的请求变化，例如第 14 条历史被替换、工具定义插入、system 内容改动。
2. Provider 原因尚不可观察：冷缓存、服务端淘汰、路由策略等记为 provider_unknown，而不是把所有 miss 归罪于本地 prompt。

内容不存入统计遥测。日常保留 hash、大小、ID；需要排障正文时从有访问控制的既有 transcript/artifact 读取。哈希与 token 估算按 immutable segment 复用，别为诊断再复制一份长历史。

### 优化与验收口径

以现有 Docs/Features/上下文Token效率缓存命中与分级压缩优化设计方案.md §15.3 为权威：

- 连续 7 个完整北京时间自然日，DeepSeek 直连按 Token 加权总命中率 >99%。
- 当日输入 ≥10M 的 Pro/Flash 分组分别 >99%；小样本明确展示，不能制造流量凑门槛。
- 同 Composition 预热稳定请求 ≥99.5%。
- main/sub-agent 分开；approval/compaction 控制面单列，不借混合分母掩盖问题。
- 预热后 system 与非预期 tool-spec 变化合计低于请求数 0.1%。
- 本地 usage 与 Provider 账单输入差异 <0.5%，否则该日不能作为最终验收日。

统计统一使用 sum(hit)/sum(hit+miss)，同时检查 prompt 与 hit+miss 的协议关系；缺失 cache 字段不能按 0 命中处理。当前脚本以 prompt 为分母，需要在一致性检查通过后才认为两种计算等价。删除脚本中把历史覆盖率约 99.8% 写成无日期当前事实的表述，改为每次报告实测覆盖。

新增目标：≥95% 的 miss Token 能关联可比较 manifest 和明确的观测分类；“provider_unknown”单独计算，不能仅打标签就算根因已解释。日报同时显示完整率、首请求、warm、重水合、工具变更、压缩、provider_unknown，以及每成功任务的实际输入/未命中/输出成本与延迟。

先用固定模型/工具/任务序列做离线载荷 diff 和真实小规模 A/B，再持续七日。减少空转轮次是收益，但不能删除必要任务、工具、当前输入、图片或覆盖历史来提高命中率。

还应报告缓存目标的可达性预算：如果一次工作负载的输入总量为 I，首次出现且此前不具备可复用缓存的输入至少为 U，则该次负载命中率上限至多为 1-U/I；服务端淘汰等还会进一步降低上限。U 的实际可缓存范围取决于 Provider，不能简单将“本地新增消息 Token”全当精确冷 miss。此分析用于解释新会话多、任务短时为何仍有冷启动成本，不用于下调现有门槛或通过增加无用历史放大分母。最终同时考察任务成功、总成本和延迟。

## 8. R01：归档恢复采用增量游标与有界发现

### 当前代码与问题

Source/PuddingPlatform/Services/FileSubAgentRunStore.cs：

- ReplayPendingConversationEventsAsync 每 30 秒仍在 WorkspacesRoot 下递归枚举所有 events.jsonl，再排序 ToArray。maxRuns 只限制发现后的处理。
- ProjectPendingConversationEventsCoreAsync 在 stamp 有变化时 ReadAllLinesSharedAsync 整个归档，然后从行号 cursor 开始投影。
- 每条投影事件都可能重写 cursor 文件。

因此已有 stamp 能减少静止文件的内容读取，却不能限制目录规模，也不能避免活跃大归档一变就重新读取全部内容。持有 per-run gate 时做这类读取/投影，还会延长该 Run 的 append 等待。源码能确认 IO/分配放大，不能据此断言当前 Private memory 增长都由它造成。

### 建议设计

保留 Run Archive 为权威源，先改 projector，不在本卡把事件整体迁入另一套库。

1. 用既有 sub_agent_runs 索引按单调键/时间+runId keyset 分页发现，维护需补偿的 Run 和投影进度。正常追加发轻量 dirty 信号；信号丢失由持久状态与低频分片扫描补偿。
2. cursor 升级为 version、fileIdentity/generation、byteOffset、lastEventId、lastSequence、processedCount。从 FileStream.Seek(byteOffset) 读取，仅在完整 UTF-8 行边界推进。
3. 每批限制 maxRuns、maxEvents、maxBytes、maxElapsed。建议初始值：32 runs、每 Run 256 events、总计 2 MiB、单批 50 ms；均为待压测参数，不是已证实最优值。
4. 同库 conversation 事件写入与 projector checkpoint 尽量同事务提交。若保留文件 checkpoint，必须先提交目标事件，再推进 cursor；崩溃重放由 eventId 幂等处理。
5. 不完整末行保留到下一批；完整但损坏的行产生明确 degraded 记录并停止该 Run，不得直接跳过损坏终态。文件截断/替换校验 generation 后安全回放，不能只比较长度。
6. 简短锁只负责读取一个稳定完整前缀与身份，释放后进行目标投影；所有权由单一 projector/checkpoint CAS 保护。不要在释放锁后继续消费会被改写的共享对象。

文件追加与数据库 dirty 标记不是一个事务。需明确崩溃恢复协议：归档完整行持久化后尝试标记 dirty；如果此时崩溃，重启恢复依靠 Run 索引比较归档长度/进度或分片发现补入。不能声称仅增加 outbox 就消除了跨文件/数据库原子性缺口。

对未索引孤儿目录保留低频分片扫描，持久保存工作区/Agent/Run 的遍历位置，并在发现阶段就检查预算与取消；不要每批重新从根排序全量目录。DB 索引与归档目录缺失要产生诊断，不能静默当完成。

### 验收

临时目录构造 10 万个 Run 和一个 100 MiB 归档；无新事件时不反复全树枚举；追加 10 行后读取量与新增内容同阶，而非重新读 100 MiB。测试 UTF-8 跨 buffer、半行、截断、同长度替换、sharing violation、cursor 写失败、投影成功后崩溃、取消、索引遗漏。目标事件无重复业务效果、无遗漏终态。用真实字节计数和 gate 等待时间报告收益。

## 9. F02：Chat 读模型版本和重复全量构建

### 当前代码与问题

Source/PuddingPlatform/Services/AgentChat/AgentConversationProjectionService.cs 的 GetConversationAsync 已对消息候选和 recentProcessEvents 设置数量上限；这值得保留。但每次请求仍读取所选消息相关的全部 process metadata，以及活跃 Run 全部正文增量和 process metadata，最后另读 eventCursor。

主页面默认 agent-client 路径按活跃 1.2 秒/空闲 5 秒轮询会话，另有 3 秒状态轮询。因此活跃长回合的工作量仍可能随历史事件总数增长。

前端 chatClientStore.isConversationSame 只比较 eventCursor、message 数、activeRun.runId、mainSessionId。同 cursor、同数量但正文/状态/详情修正的响应可能被当作未变化。后端多次独立查询后再返回最新 eventCursor，也存在“内容较旧、游标较新”的交错风险。本轮未在线上复现该竞争，需做事务与投影延迟注入验证。

### 建议设计

先定义三个不同值：

- headSequence：事件日志目前已提交到哪里。
- projectionCheckpoint：这个读模型确实消费到哪里。
- viewRevision：影响用户可见内容的单调版本，包括消息修正、详情摘要与状态变化。

快照必须携带 projectionCheckpoint 和 viewRevision，不能把 headSequence 用作其追平证明。短期可在单个短生命周期数据库读取快照中生成一致视图；但若 ChatMessages 本身由异步 projector 更新，单个 read transaction 仍不能让它自动追平，所以仍需明确 projector checkpoint。

中期复用现有 Conversation projector 增量维护 AgentConversationSummary / TurnProcessSummary。不要新增第二份 canonical 事件日志。每个事件幂等更新摘要和 checkpoint；长正文存为可增量取得的输出/消息内容，明细使用 before/after sequence 分页并携带 hasMore 和 coveredRange。

初次打开加载 bounded snapshot；后续按 projection revision 请求 delta 或用既有 SSE/Watch 获知变化。SSE 是传输优化，不取代快照恢复。事件长期空闲时降频、页面不可见时暂停非必要 refresh；网络失败分类退避。

客户端以 viewRevision/ETag 判断整个视图不变，以 messageRevision/detailsRevision 判断局部不变。sameCursorSameCount 只能作辅助信号。服务端“投影处理中”要能展示，不能无限轮询猜测末尾 user 是否补齐。

### 验收

快照读取中途追加事件、先提交终态后延迟消息投影、同消息数正文修正、同 Run 状态变化均可恢复。Snapshot+增量 replay 与完整 replay 结果一致。10 万历史事件时一次活跃刷新读取行数受窗口约束；无变化返回小响应；计数不因 64 条明细窗口而少算。

## 10. T01：工具参数闭合、真实结果和记忆读写闭环

### 当前代码与问题

SaveMemoryTool.ExecuteCoreAsync 只专门分支 delete、set_important、get_important，其余 action 都进入 upsert。SaveMemoryArgs.Action 是任意 string，描述只写 upsert/delete；typed 基类负责反序列化，未在此闭合 action 值。

因此 action 拼错或传入 read/get，且内容足以写入时，可能误走写入分支。多个参数错误和 catch 返回 ToolExecutionResult.Ok(JSON status=error)。外层 ToolInvocationService 依赖 result.Success，可能把业务失败记为工具成功，影响失败熔断、重试决策和 Goodput。

另一个明确不一致是 set_important/get_important 代码要求 agent_instance_id，但 SaveMemoryArgs 未声明该字段。实施时应核查 BuildRoot 与 context 派生方式，不能继续维护不可达或不完整的工具分支。

### 建议设计

先做小范围正确性补丁：

- 对 action 使用唯一的 enum/判别值合同。缺省仍为 upsert；任何显式未知值返回 invalid_action，保证写入次数为 0。
- 参数组合在执行前验证，如 preference 的 key/value、delete 的准确目标、content 空值；帮助文本、schema、validator 和测试数据同源。
- 工具结果使用统一 Success + ErrorCode + Retryability + ResultData。正常无匹配可成功返回 empty/no_match；业务错误必须失败，取消必须传播。
- 保留工具原始完整输出的归档和 Artifact 读取能力。Token 优化只改变模型预览体积，不丢原始结果。

再补记忆闭环：沿用现有管理/检索工具，按 chapterId 精确读回并分页，不新造第五码同义工具。写入结果返回 bookId/chapterId/contentHash 或 version；检索必须传出可精确读回的 ID 和 scope；读回校验 workspace/Agent 边界。

默认只读查找不得自动触发大规模探索/写入；如产品确需搜索无结果后的扩展检索，使用明确的返回状态或显式选项，避免普通检索隐含启动额外 LLM 调用。全量行为范围实施前需沿调用链验证，不能只按方法名推断。

重要记忆若由独立工具管理，删除 SaveMemory 中冗余入口；若保留则显式按 context 派生当前 Agent，跨 Agent 写入仍按授权合同处理，不让模型任意指定身份绕过作用域。

### 验收

action=read/get/upsertt 等未知值零写入、Success=false；空字段不删除或写坏数据；取消未转为 Success。写入→返回 ID→精确读回正文/hash→检索命中→再次读回一致。save_memory 失败计入失败率且不会被当成任务完成证据。file_patch 既有修复不在本卡重做。

## 12. R02：统一 Session 缓存与锁的生命周期

### 当前代码与问题

### 建议设计

由现有 session 生命周期发布 Released/Archived/Deleted/Expired 事件，区分 live execution、warm cache 与 durable state。C01 保证可恢复后，工具 ID 不必永远驻留于进程内。

建立小型 SessionResourceRegistry 或显式 lifecycle subscriber 合同，每个资源声明 key、estimatedBytes、lastAccess、pinCount、generation、evictionPolicy。优先按现有组件扩展，不引入外部缓存服务器。

缓存使用容量+字节+TTL 三类预算；正在执行、压缩、等待审批的 session pin 住，结束后逐步释放。删除 session 时显式释放；过期只释放可重建副本。tokenizer 可按有限模型类型共享，不能与 session 缓存混为一谈。

keyed lock 不可在 Release 后简单 TryRemove 再 Dispose：旧 waiter 可能仍持引用，新 caller 会得到另一把锁，破坏互斥。采用引用计数的 acquire lease，计数覆盖持有者和等待者，只有零引用时才能原子摘除；也可对低争用且键规模可控处选固定分片锁，并说明额外串行化代价。

### 验收

连续创建/结束 1 万临时 session，活动数归零后，各 registry 项数和估算字节回到约定预算范围；重开旧 session 能恢复相同有效组成。用 barrier 测试 lock acquire/release/evict 竞争，不出现同一 key 同时两个 owner。记录 GC heap、allocation rate、Private、WS 和 cache entries；无需强制 GC 作为产品修复。

## 13. C03：把请求预算估算与高成本诊断分离

### 当前代码与问题

ContextUsageSnapshotStore.CaptureLlmRequest 每次遍历所有消息、计 Token、拼接 system/history 全文、序列化工具、计算 hash 和 gzip。LlmRequestBudgetGuard.PrepareSoftCompaction 在每移除一个旧会话单元后再次 CaptureLlmRequest；硬预算路径也可能重复调用。

对 N 个消息逐次移除 K 个单元时，会重复做接近 O(K×N) 的全历史工作；工具 gzip 指标在一次 capture 内也有重复计算的机会。该成本发生在请求准备阶段，容易与 Provider 延迟混淆。

### 建议设计

- BudgetEstimator 是必需的廉价路径：按 immutable message/contentPart hash + tokenizerVersion + model/protocol 估算，缓存单消息/工具 schema 结果。
- 对 conversation unit 维护 prefix sums 或累计贡献，一次确定候选裁剪范围；保留原有工具调用/结果成组、当前 Turn 围栏和图片预算保护。
- 裁剪后的最终请求仍用权威估算与既有 hard guard 复核，避免简单加法遗漏协议边界开销。缓存只优化过程，不能弱化输入上限。
- EntropySampler 是诊断路径：新 schema/新 stable segment 计算一次；长 history 使用按频率/预算采样，日常不在每次候选裁剪上压缩全文。
- 借 C02 的统一 RequestShape 复用序列化字节/hash，避免三套计算口径。usage calibration 按具体 route、request identity 和 context generation 学习；不得把旧轮次回报套到新请求。

### 验收

同一 immutable 100K/500K 级上下文重复估算时，cache 命中可观察；追加一个消息只计算新增段。裁剪 100 个 conversation units 不发生 100 次全历史 gzip。最终上限判定与参考完整估算保持约定误差和保守边界，current Turn/图片/工具组不丢失。用 Benchmark 或固定临时 fixture 报告时间与 allocated bytes，不用文本相似度替代完整性测试。

## 14. A02：Buffered 与 Streaming 共用 Agent Loop

### 当前代码与问题

AgentExecutionService 三个主要文件合计 6,410 行：主文件 2,268、Buffered 2,312、Streaming 1,830。主类有大量上下文、工具、事件、预算、归档和后台依赖。partial 分文件降低了单文件长度，但没有消除职责耦合。

两条路径均维护请求准备、当前输入保护、usage、工具结果、预算、失败恢复、压缩和终态。继续把每次 bug fix 手工复制到两份长循环，容易形成缓冲/流式语义差异。本轮不声称所有分支已证明不一致；这是高维护风险。

### 建议设计

以既有 AgentLoop/Guardrails/ToolInvocation 等类为基础，抽取执行内核，而不是再建第二个 Loop：

| 组件职责 | 输入与输出 | 不承担 |
|---|---|---|
| ExecutionSessionScope | 获取 session gate、身份、取消和资源 lease | Prompt 拼接与 UI |
| RoundRequestPreparer | 已提交 Composition + history + steering → immutable request | 调工具、记终态 |
| ModelRoundExecutor | request → 有序模型事件和 RoundResult | Task 状态转换 |
| ToolBatchExecutor | 完整 tool calls → 有序结果/证据 | 自行重新解析全局 workspace |
| RoundTransition | state + model/tool outcome → next action | 数据库与网络 IO |
| RunFinalizer | 单一 terminal intent → journal/usage/归档适配 | 任意重试模型 |

统一模型事件接口可覆盖两种模式：buffered response 转成一次完成事件；streaming adapter 持续产生 text/reasoning/完整 tool call/usage。RoundTransition 决定下一轮、工具执行、预算结束、等待、取消；UI 输出由 sink 消费同一规范事件。不要为统一接口强迫 buffered UI 按 token 模拟流式。

按四批施工：先抽取完全一致的 request preparation；再抽取预算/工具结果策略；再统一 terminal；最后才合并循环。每批都能保留既有入口 API。功能上未证明等价的部分先留下明确 adapter，不用条件布尔参数把两个旧循环塞入新大类。

### 验收

建立脚本化 fake Provider 场景集，两种入口比较规范化后的事件序列、最终 transcript、工具执行次数、usage、当前输入围栏和 terminal。覆盖：纯文本、reasoning+tool、多工具、invalid JSON、工具失败、图片、steering、预算、压缩、等待/续行、首包失败、首包后中断、用户取消和 lease 丢失。相同工具最多执行既有合同允许的次数；不能用“输出字符串相同”证明执行等价。

## 15. F03：Chat 单一状态所有权与按回合订阅

### 当前代码与问题

当前主入口同时组合 useChatState、useAgentChatClient 和 TurnSurfaceStore，通过 feature flag 决定主线所有权；另有 useConversation + 全局 conversationStore。引用检索未发现 useConversation 在产品页被调用，它更像尚未接入的迁移分支，不能直接将其宣称为正在运行的主线。

useChatState 仍有 1,551 行，useSessionEventProjection 1,747 行。useSessionEventBuffers 在 80/120ms 批处理时 map 整个 turns 数组；主入口以 surface revision 改变 getTurnProjection 函数身份使 MessageRow 更新。已做虚拟化，但列表级引用变化仍可能扩大计算范围。

### 建议设计

先以 F02 的服务端合同收敛唯一客户端运行态。对每类状态明确 owner：

- canonical entities：conversationId → ordered turnIds → turn/message/run entities。
- connection：transport generation、checkpoint、reconnect 状态。
- command outbox：乐观发送和 accepted 对应关系，不写 canonical terminal。
- UI ephemeral：草稿、滚动锚点、展开 owner、选择、TTS，只存在 UI 层。

以当前正在使用的 agent-client 主线改造；不要激活缺少切换保护的旧 useConversation 来完成“迁移”。审查无调用模块是否测试/动态导入/外部导出需要，确认后删除，并同步旧迁移注释。

为 store 提供 turnId 级选择器和稳定 snapshot。delta 只更新对应 entity 的 revision；可见 MessageRow 只订阅自身和必要的 latest-activity owner，减少全列表 map 和函数身份广播。按帧合并 UI 更新，但 canonical eventId、sequence、tool callId 原样保留。终态到达前先 flush 已接收文本，再单调应用终态。

历史正文、thinking、工具详情按用户阅读状态加载，保留最新行为组披露合同；收起后允许卸载重组件，重新打开可重建。不得把 reasoning 再隐藏为不可恢复摘要来降低渲染成本。

### 验收

在 1 万条逻辑消息、长 Markdown/代码/表格、连续 delta、多子代理、断线 replay 下记录 render count 和交互延迟。更新末尾一个回合不重新计算所有历史回合投影。滚动锚点、输入焦点、草稿、展开 owner、失败提示和重连恢复保持原语义；需要实际 WebView2 截图/操作验收，不仅 Jest。

## 16. R03：后台任务、取消与 Provider 重试边界

### 当前代码与问题

ChatExecutionWorker 已维护 running tasks 并观察异常，但 ProcessWithSessionLockAsync 在取得 lease 后、try 块之前等待 sessionLock。若等待锁时取消，方法可能未进入释放 lease 的分支，只能依赖超时恢复。_maxConcurrency 从配置读取，未见这里的正数验证。

DirectLlmClient 的 buffered provider 调用与成功后的 activity/required usage 写入位于同一个 try 范围；异步诊断与业务请求错误应有清晰区分。当前 transient 分类只把有 HTTP 状态的 5xx 判为可重试；429 不重试，半开 circuit 没有限定单个 probe。是否导致当前故障尚未测量。

其他 Host/子代理启动有 Task.Run 和 fire-and-forget。不能一律视为错误，也不能只把它们全部改成 await；长后台任务若直接 await 可能阻塞 Ready。

### 建议设计

1. worker 从 acquired lease 开始进入 try/finally；显式记录 lockAcquired、executionStarted、terminalCommitted。等待阶段取消也按当前 fencing 释放，避免 finally 重复提交终态。
2. 对并发配置做正数上限验证，错误配置给明确诊断；不要为了吞吐直接调大并发。
3. Provider 网络尝试与本地后处理分离。只有网络操作本身的失败进入 provider retry；本地账本/日志失败进入各自恢复。已有流式“首个有效 delta 后不自动重试”原则继续保留。
4. 分别配置排队超时、首包超时、流空闲超时、总执行 deadline；连接取消要传到网络枚举器。HTTP 429 可按 Retry-After、总 deadline 和预算有界重试；认证/参数错误直接返回；半开 circuit 使用单探针或小的明确 probe 限额。
5. 对关键后台工作建立 owner、Task handle、取消、drain deadline、错误结果；启动时启动后台 handle 并由宿主监督，不在 StartAsync 等外网完成。不可丢的完成通知使用既有 durable delivery/outbox；普通指标可丢但记录 dropped 数。

### 验收

lease 已取得但锁未取得时停止，不遗留长期 busy；停止中 watcher fault 不产生双 terminal；超过 drain deadline 有清晰报告。模拟首包前 503、429、认证失败、首包后断流、本地 usage 写失败、用户取消、半开并发。Provider 成功后本地写失败不能再次请求模型或再次执行工具。

## 17. S02：收敛调度状态解释，先复用已有修复

当前工作树已增加 LegacyTaskExecutionProbe，多个调用方共享其判定；本卡不重复修复旧报告中的“所有 claim 都 Healthy”。

建议把 Availability/Tracking/Settlement 的判定输入固化为只读 ExecutionEvidenceSnapshot，包含 taskVersion、assignmentAttempt、binding、delivery、command、latest execution attempt/fence、reservation、lastProgress。纯函数返回判定码与建议动作，修改方进入事务后重读并核对版本再执行。

Task、Goal、Run 三个状态机保留领域差异，不合并为万能 Status 枚举。task-bound execution 的成功需要 verifier/settlement，Delivery ACK 不表示完成。陈旧 terminal 不能释放当前 retry 的 reservation；不同作用域的 Run 不能成为回收证据。

Repair 只修有证明的不一致，无法判定时保留 blocked/inconsistent 与证据 ID；用统一的状态解释 DTO 同时服务看板、Agent tools 和调度诊断。减少在 UI、Tracker、Repair、Command Handler 各写一套 reason mapping。

定时触发继续遵守既有 ADR-072/074 的 occurrence 去重、outbox、fencing 和 admission。不要以此为由在本卡新建另一个 Cron 调度器或改变低峰策略。

验收矩阵：旧 attempt 终态/新 attempt pending、lease 过期但仍有新 owner、assignment 与 workspace 不符、delivery terminal 无 run、用户抢占、重启、取消、未知证据。每个动作带预期版本，无误释放；自动验收必须从已授权且可派的安全库存自然触发，不能用手动 run-now 伪装自动派发。七夜验收单独记录。

- 在没有 retained-object/分配证据时宣称泄漏，或以强制 GC、定时重启、清空 D:/data 作为修复。
- 同时重写模型调用、Agent Loop、上下文压缩与调度事务；这样很难判断回归来源。
- 把所有后台操作串到一个全局锁/队列；应按事实 owner 与资源竞争范围划分。
- 对历史 ADR 大规模重编号、全仓格式化、批量改类名，作为架构整洁的主要成果。
