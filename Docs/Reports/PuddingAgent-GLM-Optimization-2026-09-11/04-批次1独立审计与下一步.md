## 2. 必须优先补修的发现

### AU-F01-1 / P1：AbortController 没有到达 HTTP 请求

源码位置：

- `Source/PuddingPlatformAdmin/src/pages/chat/hooks/useTurnSurfaceStore.ts:105`：fetch 接收 `_signal` 后丢弃，调用 API 只有 workspace/agent/message 三个参数。
- `src/pages/chat/client/agentChatApi.ts:42`：明细方法没有 signal 参数，request 选项只有 GET。
- `src/pages/chat/runtime/detailHydrationScheduler.ts:132` 起：beginGeneration 调用 abort，旧请求进入 settling 并继续占槽。

触发：会话 A 的两个 HTTP 请求尚未结束，切换 B。调度器发出 abort，但 transport 没有收到，B 仍等待旧 HTTP 完成、失败或底层超时。当前机制确实限制了调度器内未完成请求总数，却没有兑现主动取消；如果 transport 一直不结束，新会话无法取得槽位。现有测试直接手动 resolve 旧 promise，覆盖不到这个接线问题。

审计用例 `passes a cancellation signal from scheduler into API adapter` 失败，实际 signal 为 undefined。此用例验证 hook→adapter 边界；源码检查进一步确认 adapter→request 也没有 signal。

实施方案：

1. 给 `getAgentMessageProcessItems` 增加明确的请求选项（如 `{ signal, timeoutMs }`），在最终 request 调用中传递取消信号；三个身份参数的含义保持不变。
2. 会话切换与卸载走同一个取消路径。AbortError/transport cancellation 不消耗 transient 重试预算，不向用户展示业务失败。
3. 设定明细请求的有界超时并实际终止 transport。不要只用 Promise.race 把仍运行的 HTTP 请求从并发计数中移除；那会重新造成物理请求叠加。
4. 加 API adapter 测试证明 signal 到 request，另加可取消 transport 的 hook 集成测试。A→B 后旧请求应以取消结算，B 自动补位；仍保留“不支持立即 abort 的 promise 在结算前占槽”的所有权防线。

### AU-F01-2 / P1：离开视口会删除失败状态，绕过重试预算

源码：`detailHydrationScheduler.ts:163–180`。sync 删除所有“不在 desired 且非 running”的 entry，包括 auth、gone、exhausted 和 backoff；同一 key 再进入视口会新建 attempts=0 的 queued entry。

复现顺序：`sync([request]) → 返回 401/404/503 → sync([]) → sync([同一 revision])`。三个审计用例均从预期请求 1 次变成实际 2 次。503 用 maxAttempts=1 直接验证预算已耗尽后仍重启。这不需要服务端数据变化，滚动即可触发。GLM 的“投影对象变化不重置预算”测试通过，但没有覆盖可见集合收缩与重新进入。

实施方案：

1. 分开维护请求队列与失败记忆。离开视口只取消 queued/backoff 的调度意图，不抹掉该 key 的 attempts、retryAfter、gone 或 auth 状态。
2. 401/403 增加认证作用域的暂停状态，由真实登录/认证版本变化解除；滚动不是认证恢复事件。404/410 对同一 detailsRevision 保持终止，只有版本变化才重新尝试。
3. transient 预算属于请求身份及 generation。重新可见时沿用原预算和剩余退避时间，耗尽后等待明确的用户重试。
4. 失败记忆也要有边界：按当前会话/消息修订管理，退出 generation 后释放；认证门禁独立于单条缓存淘汰，避免 LRU 淘汰变相解除认证暂停。不要为了限制内存而在每次滚出视口时清除失败预算。

### AU-F01-3 / P2：React StrictMode effect 重放后调度器永久 disposed

源码：`useTurnSurfaceStore.ts:102–131,145–151`。调度器只在 render 检查 ref 为 null 时创建；effect cleanup dispose 后，没有与新 setup 配套的创建/激活。StrictMode 的 setup→cleanup→setup 保留 ref，随后 sync 在 disposed 检查处直接返回。

使用 Testing Library 的 **root `reactStrictMode: true`** 复现：注册一个可水合 turn 后，预期 API 1 次，实际 0 次。此结论适用于启用了 StrictMode 的 React 根；未据此宣称当前生产入口必定启用 StrictMode。嵌套 wrapper 与 root StrictMode 不应混为同一种测试条件。

实施方案：让 effect 成为 scheduler 的创建和释放所有者，初始化 effect setup 创建当前实例，cleanup 仅释放自己创建的实例；调度 effect/回调读取当前 ref，避免捕获上一代已 disposed 实例。setup 后应从现有可见集合与快照恢复期望工作。不要只在 cleanup 把 ref 设 null，而其他闭包仍持有旧 scheduler。保留 root StrictMode、真实卸载、会话切换三组独立测试。

### AU-F01-4 / P2：认证恢复和手动重试仅存在于调度器内部

源码：scheduler 的 `notifyAuthRecovered` / `retryAll` 已实现，但 hook 不返回这些操作，`onFailure` 为空，调用方也没有连接。需要同时解决“持续可见时永远不恢复”和“滚出去再进来反而非法重试”两端行为。

将失败状态投影给 hook/明细 UI；接入真实认证恢复事件；对已耗尽请求提供一个明确、可访问的重试操作。UI 区分尚未加载、正在加载、已失败和明细不存在，不把它们全部显示成永久空轨迹。此项是静态接线审计，没有单独计入 10 个失败测试。

F01 本批仍未实现的 byte LRU 和 detailsRevision 接线应如实保留：目前 hydrated 集合只按 messageId，构造 desired 时未传 detailsRevision。它们与 F02 的服务端修订合同一起推进，不要宣称只是加了 optional 字段就完成了内容缓存失效。

### AU-S01-1 / P1：Gateway 同 source 的不同用量被静默接受

源码：`Source/PuddingPlatform/Services/LlmGatewayUsageRecorder.cs:34–35,83–93`。前置 AnyAsync 只判断 SourceId；catch 唯一异常同样直接返回成功。第二次相同 source 即使 completion 从 500 变成 9000，也没有冲突信号。

临时 SQLite 集成测试 `Gateway_ConflictingPayload_MustReject` 失败：Required 没有抛出预期冲突。普通重复来源幂等测试通过不能证明这一分支正确。前置 Any 的缺陷已存在，本批新增的 catch 也没有完成原 S01-A 要求的精确冲突处理。

实施方案：两本账本共用明确的结果语义 `Inserted / DuplicateSame / ConflictDifferent`。Gateway 读取已有 source 后比较规范化内容和不可变身份；相同才成功，异内容通过 Required 返回明确失败。唯一冲突后必须回滚、用干净 context 查询目标 source 并做相同比较；不存在目标 source 就不能报告幂等成功。将冲突指标与正常重复指标分开。

### AU-S01-2 / P1：RawUsageJson 相同不代表请求身份相同

源码：`TokenUsageRecorder.cs:255–272`。现有查重按 sourceType/sourceId，比较只含 RawUsageJson；workspace/session/provider/model 等身份不参与验证。

审计将同一 usage 和 source 先提交 workspace A，再提交 workspace B，第二次 Required 正常返回；`Token_IdenticalUsageButDifferentWorkspace_MustReject` 失败。同样的 token 数在不同请求中完全正常，不能成为身份等价依据。这里验证的是冲突防线缺失，不是宣称生产中已发生 workspace 串账。

先在 S01-A-R 明确 existing row 与请求的不可变字段比较；在 S01-B 引入一次生成的 RequestUsageAttribution，解决身份来源本身。比较字段至少包括账本身份、sourceType/sourceId、workspace/session、provider/model、operation，以及已确定的 invocation/attempt 绑定。CreatedAt、重试记录时间等本地写入时间不是业务幂等身份。不要简单把“读取最新 session 快照”加入 payload hash，那会使合法重投也被错误判冲突。

### AU-S01-3 / P1：任意 UNIQUE/PRIMARY KEY 失败都被当成 source 重复成功

源码：`UsageWriteConflict.cs:16–24` 只检查 SQLite 19/2067/1555；`TokenUsageRecorder.cs:328–336` 回滚后无条件返回。SaveChanges 还会写聚合和 context layer 数据，错误码无法说明到底哪个约束冲突。

故障注入：在临时数据库给事件表加 BEFORE INSERT trigger，使另一个具有 UNIQUE 的临时表冲突。业务 source 尚不存在，Required 却成功返回。审计 `Token_UnrelatedUniqueConstraint_MustNotBeAcceptedAsDuplicateSource` 失败。这个 trigger 只是验证通用 UNIQUE 错误被吞的隔离探针，未向生产库添加 trigger，也不代表生产本来就有该 trigger。

保留已有效的 BEGIN IMMEDIATE 事务，不必为了形式强行换掉 decimal CLR 聚合。当前目标是正确性：只有确认目标 source 已存在且内容相等，才走重复成功；其他 DbUpdateException 向 Required 传播，保证整笔事务零残留。测试需额外证明非 source 唯一失败、提交取消/IO 失败均不增加任何聚合。事务持锁期间的 context layer 查询耗时另做 P95/锁等待采样后再优化，不凭感觉改并发控制。

### AU-T01-1 / P2：preference value 必填声明与执行不一致

`MemoryToolArgs.cs:25` 声明 value Required，`SaveMemoryTool.cs:75–78` 却只校验 key，并明确提示 value 可选；随后 `:184` 附近拼接 `${key}: ${value}`。审计传入 preference 和 key、不传 value，预期零次写调用，实际调用 UpsertExperienceAsync 1 次。

应以现有 schema 为准统一要求非空 key/value。若产品确实需要清空偏好，单独定义明确的删除/清空操作，不以缺参偷偷创建空值。同步 schema、错误提示和测试。审计测试使用记录型库替身，只证明错误输入进入写路径，没有操作真实记忆库。

### AU-T01-2 / P2：type 校验忽略大小写，内容构造却区分大小写

`SaveMemoryTool.cs:75,80` 使用 OrdinalIgnoreCase，但 `type switch` 只有小写 preference。`type="Preference", key="locale", value="zh-CN"` 通过 key 校验并跳过 content 必填检查，之后却走 generic 分支，给写服务的 Content 是空字符串。

审计 `PreferenceTypeCase_MustNormalizeOrRejectBeforeWrite` 失败；断言允许“统一归一化后正确写入”或“明确拒绝且零写入”两种策略，当前两者都不满足。建议一次 normalize/parse type 为封闭值（fact/preference/summary/chapter），后续验证和构造只使用这个值；未知 type 明确失败。先补这两个小缺口，精确 chapterId 读取、分页、version/hash 回执另列 T01 后续切片。

### S01-B 的设计落点

在模型请求准备时构造不可变 `RequestUsageAttribution`，包含 invocationId、attemptId、run/turn/round、parent/subagent、provider/model、source、compositionRevision/contentId、manifestId。随请求传到成功/失败/用量回执，晚到 A 的记录不再读取 B 已覆盖的 session 最新缓存。

将 Provider 请求结果与本地账本提交分开：Provider 已成功时，本地 SQLite busy 或重试只能重投同一用量事实，不能再次调用模型。迟到记录按实际发生时间归属自然日，并使受影响日报/聚合失效后重算。缺失归因写成 unknown 并统计覆盖率，不能借用最新值填满报表。

### C01 的设计落点

现存 `DirectLlmClient.RecordCompositionSnapshotAsync:1076` 在 telemetry sink 缺失时直接返回；Observe 也在其中。`PersistentCompositionVersionRegistry:57` 仍 fire-and-forget 写穿；`CompositionSnapshot:288–297` 仍复用内容版本，A→B→A 可返回旧版本。它们是执行状态合同问题，优先于泛泛拆分大类。

拆出必需执行服务：Prepare/Recover → Commit → BindRequest。遥测只消费已提交结果。用 long 单调 revision 表示事件先后，用 contentId 表示可复用内容，CAS 维护当前 head；完整 schema 的稳定引用与 canonical prefix 必须可恢复，不能仅凭哈希重建出“看起来相同”的工具定义。恢复 single-flight、可取消、恢复失败明确状态；不要把取消吞成纯内存继续。

ToolExposureRevision 与 PermissionEpoch 分开。search_tools 合法发现和用户权限变更不是同一原因；撤销权限后调用鉴权立即生效，不能为了命中率继续暴露/执行已撤销能力。提交点放在明确的轮边界，当前请求绑定已提交版本。

C01-A 可以先单独提交无 telemetry 仍维护执行状态的修复；C01-B 再提交 revision/CAS/持久化引用与权限模型。旧 Completed 看板卡保留历史，在评论中链接新差距任务，避免把旧阶段验收解释成此次完整实现。

### C02 的设计落点

在 OpenAI-compatible、Responses、Anthropic 等实际 adapter 的最终序列化边界生成 RequestShapeManifest，与发出的同一份数据绑定。记录模型可见 segment 的有序 hash、UTF-8 bytes、token 估算与完整历史，区分 transport 字段；不要额外组装一份“近似请求”作为证据。普通报表不保存认证头或秘密配置。

离线固定用例：只追加尾部、修改第 20 条历史一个字符、第二条 system 改动、tool properties/required 顺序或内容变化、图片 artifact 版本变化、协议切换。记录 firstChangedSegment/offset/前后 hash/影响 tokens，区分“能关联到 manifest”与“能解释 miss 成因”。这些指标不能用高 hit rate 反向推定。

真实验收沿用原权威设计 §15.3：任务语义、工具名称/参数/顺序和权限边界不变；连续 7 个完整北京时间自然日按 token 加权；Pro/Flash 分开，逐日达到 10M input 的模型单独要求 >99%，小样本显式标识并保留累计统计，不能删掉；同 composition warm ≥99.5%；主/子执行与 approval/compaction 等控制流分开；预热后 system_prompt_changed 与非预期 tool_spec_changed 合计低于请求数 0.1%；本地 usage 与服务商账单的输入 Token 差异 <0.5%。保持总目标 >99%，不把样本门槛解释成自动豁免。任何指标缺数据即未验收。
