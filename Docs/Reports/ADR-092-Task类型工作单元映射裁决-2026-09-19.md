# ADR-092 增补裁决：`general` 类型的 Task-bound Goal 可达性与执行计划映射

- **状态**：Accepted（父级设计裁决，2026-09-19）
- **裁决人**：`default.global-general-assistant.6a8`（PuddingAgent 维护者）
- **触发卡**：`ef7d6378814e421482c41e42fcbf6e5b`（P0）—— 「Task-bound Goal 不可达：`task_type=general` 无执行计划（205/213 张卡）+ implementation 计划 16/16 Failed」
- **上位文档**：ADR-092（第二版）决策 5/9「独立 Goal 无需 Task/Plan 即可完成；Task 是可选适配器」
- **关联**：G92-1 标准 3「Task-bound Goal 可达 Complete」、缺陷卡 `2b60040d`（派发未注入 ActiveTask）

---

## 1. 背景（卡面已登记，此处仅固化取证结论）

### 1.1 缺陷 A：`general` 结构性不可达
`Source/PuddingPlatform/Services/Scheduling/TaskExecutionPlanCompiler.cs:78-98` 的 `TryResolveKinds`
是硬编码 switch，已知 5 组类型，兜底 `_ => []`：

```csharp
private static bool TryResolveKinds(string? taskType, out TaskWorkUnitKind[] kinds) =>
    (taskType ?? "").Trim().ToLowerInvariant() switch
    {
        "implementation" or "operations" or "deployment" => [Explore,Plan,Change,Test,Review],
        "test"          => [Explore,Plan,Test,Review],
        "research"      => [Explore,Plan,Review],
        "review"        => [Explore,Review],
        "documentation" => [Explore,Plan,Change,Review],
        _ => [],          // ← task_type=general 落入此处 ⇒ kinds 空 ⇒ TryCompile 返回 false
    };
```

`TaskExecutionPlanCompiler.cs:35-36` 命中后直接 `return false`，默认 `code = "execution_plan_unavailable"`。

**影响面（SQLite 实测 2026-09-18）**：`workspace_tasks.task_type` 分布 `general = 205 / implementation = 8`（合计 213）
⇒ **96.2% 的卡（含 G92-0/G92-1/G92-2/G92-3 全家族）在结构上无法启动 Task-bound Goal。**

**实测复现链**：Ready 卡 → `task_goal_start` → `{"code":"execution_plan_unavailable"}`；
决策账本 `task_scheduler_decisions`（唯一一条，2026-09-18T04:15:42Z）：
`decision=denied, decision_code=execution_plan_unavailable, reason="code=execution_plan_unavailable;task_type=general;dependency=satisfied"`。

### 1.2 缺陷 B：implementation 计划 16/16 Failed
8 张 implementation 卡共产生 16 次 `task_plan_runs`（`plan_kind=workspace-task-v1`），**status 全部 Failed**。

**真因（子代理静态定位，证据见 §4）**：
`task_plan_runs.status` **不是执行期状态机**，而是 **Goal 结算的派生投影**：
- 唯一的 `workspace-task-v1` 创建点 `TaskGoalDispatchTransactionStore.AddExecutionPlan:449-528`（`:465` 恒写 `Status=Active`）
- `Failed` **只**由 `GoalSettlementStore` 写入：`:1192`（`ApplyBoundPlanVerdict` Stop 分支）、`:1719`（`FailIncompleteBoundPlan` 本体），
  调用点 `:1348`（不可恢复终态）与 `:1427`（迭代预算耗尽）
- ⇒ **失败阶段 = Goal 结算 / 验收合同判定段**，不是编译器、不是 WorkUnit 状态机、不是派发、不是 budget

**因果链**：验收合同**恒为空** → 每轮裁决 `acceptance_contract_missing`（Repair）
→ 无进展熔断 `no_progress_circuit_open` + `needs_user` → 进入不可恢复分支
→ `FailIncompleteBoundPlan` 把 plan 连带置 `Failed`（`error_message = no_progress_circuit_open`），同时 Task 置 `Blocked`、释放 assignment。

**空合同原因**：`GoalRuns:CheckProjects` 未配置 + objective 无显式证据声明 + 续行 prompt 从不提示 agent 提交 `meta.goal_contract_proposal`。

## 2. 关键设计考古（裁决的事实基础）

| 事实 | 证据 | 对裁决的意义 |
|---|---|---|
| `TaskWorkUnitKind = {Explore,Plan,Change,Test,Review}` | `Source/PuddingCore/Scheduling/TaskExecutionPlanContracts.cs:4-12` | 注释明确定性：**"Deterministic execution phases emitted from a structured WorkspaceTask"** ⇒ **是「阶段」不是「权限」** |
| `TaskTypeRouteOptions` 仅含 `RequiredCapabilityIds` / `AllowedRoles` / `RequiredProviderId` / `RequiredModelId` | `TaskAutoDispatchEvaluator.cs:154-160` | 它是**路由**配置，**不承担** task_type→work units 映射职责；映射职责确实在 `TryResolveKinds` |
| kinds 与能力是**独立轴** | `TaskExecutionPlanCompilerTests.cs` 断言 `WorkUnits[0].RequiredCapabilityIds = ["cap-file-write","cap-shell"]` | 能力过滤发生在 **work unit 上**，不在 kind 上 ⇒ 改 kinds **不直接**改变权限判定 |
| `TaskExecutionPlanSnapshot.CurrentPlanVersion = 2`、`CurrentSchemaVersion = 1` | `TaskExecutionPlanContracts.cs:80-82` | 计划快照是版本化 + 内容寻址（fingerprint 64 hex），改动需保持确定性 |
| `PuddingCode` 是**命名空间**，实体目录是 `Source/PuddingCore` | `list_dir Source`（32 项，无 `PuddingCode` 目录） | 记录：上一轮调研子代理因臆造 `Source/PuddingCode` 目录而 3 次工具失败（供后续委派避坑） |

## 3. 选项分析与裁决

### 3.1 选项 (a)：为 `general` 定义工作单元集合
- **子选项 a1 — 同 `implementation`（全 5 阶段）**：205 张卡全部可达变更。
  **否决理由**：`general` 是**未分类默认值**。默认授予 Change 会使**任何忘记声明类型的卡**（含只读研究/审阅卡）
  自动获得变更阶段，Change 单元会请求 `cap-file-write` 一类能力 —— 对"只读意图"的卡构成**行为扩大**。
  这与验收 5「不降低边界」的精神相悖。
- **子选项 a2 — 保守集合 `[Explore, Plan, Review]`**：**采纳**（见裁决 1）。

### 3.2 选项 (b)：开放 `task_type` 契约 + 结构化拒绝
- **采纳**（见裁决 2）。理由：**意图应由创建者显式表达**才是正确方向；(a) 只是兼容性兜底。
- 当前 `execution_plan_unavailable` 是**笼统**失败码，无法区分「类型不支持」与「依赖未满足」等其他拒绝原因 ⇒ 不可诊断。

### 3.3 选项 (c)：先修 16/16 Failed
- **不单独选**，但**必须与 a/b 同批处理**：因为 16/16 Failed 揭示 `task_plan_runs.status` 被 Goal 结算**被动牵连**，
  若不修，任何 Goal 的 `needs_user`/熔断结局都会继续把 plan 置 Failed ⇒ 即使 kinds 修好，"计划 100% Failed" 依然复现（见裁决 3）。

### 3.4 ✅ 最终裁决：**(a2) + (b) + (c') 组合**

## 4. 裁决内容（可执行规格）

### 裁决 1 —— `general` 采用保守工作单元集合
`TryResolveKinds` 新增分支（**与 `research` 同集合**）：

```csharp
"general" or "research" => [Explore, Plan, Review],
```

- **语义**：`general` = 未分类通用任务 ⇒ 默认**只读 + 计划 + 审阅**，不默认授予变更/测试能力。
- **可达性收益**：205 张卡的 Task-bound Goal **结构性可达**（能编译计划、能过调度评估）。
- **意图表达**：需变更的卡须显式声明 `task_type=implementation`（由裁决 2 保证契约可写）。
- **确定性保持**：集合固定有序 ⇒ fingerprint 稳定，不破坏 `CurrentPlanVersion=2` 契约。

### 裁决 2 —— 空类型归一 + 结构性拒绝升级
1. **空/null `task_type` 归一到 `general`**（不再落入 `_ => []`）：默认值语义修复。
   ```csharp
   // 归一在 Trim/ToLowerInvariant 之后、switch 之前
   var normalized = string.IsNullOrWhiteSpace(taskType) ? "general" : taskType.Trim().ToLowerInvariant();
   ```
2. **未知非空类型**返回**专用拒绝码** `execution_plan_task_type_unsupported`（替代笼统 `execution_plan_unavailable`），
   拒绝正文须含：`task_type`、`supported_types`（列举全部受支持类型）、`suggestion`（可执行建议，如
   「若需变更能力，请以 `task_type=implementation` 重新提交」）。
3. **保留** `execution_plan_unavailable` 作为**其他**失败原因的码（不得复用为类型错误的兜底）。

### 裁决 3 —— `task_plan_runs` 终态语义修正（缺陷 B）
- **问题**：plan 状态被 Goal 结算**被动牵连** ⇒ `needs_user` / `no_progress_circuit_open` 这类
  「**尝试结束但计划本身未失效**」的结局也把 plan 置 `Failed` ⇒ 结构性 100% Failed。
- **修复**：`GoalSettlementStore.FailIncompleteBoundPlan`（`:1719`）对上述结局**保留 plan 非终态**（不置 Failed）。
- **可观测性**：`task_plan_runs` 新增结构化列 `failure_code` / `failed_stage`
  （当前只有自由文本 `error_message` ⇒ 每次都要靠 `goal_runs.blocked_code` 反推）。
- **验收 3 的取证方式**：修复后给出 **≥1 次 plan run 非 Failed** 的实测行
  （`status ∈ {Active, Draft}` 或新增的成功终态），并说明该行对应的 Goal 结局。

### 裁决 4 —— 验收合同供给（Task-bound Goal 可达的**必要条件**）
根因是**合同恒空**，与 kinds 无关。须至少落实一项：
- (i) 任务创建/更新契约与卡面**要求显式证据声明**（objective 内的可核验断言）；
- (ii) **续行 prompt 主动提示** agent 提交 `meta.goal_contract_proposal`（当前从不提示）；
- (iii) `GoalRuns:CheckProjects` 配置就绪。
- **不建议**：把 `acceptance_contract_missing` 从 Wait 改为 Repair-until-circuit
  （`GoalVerificationContracts.cs:240-257` 注释显示它被**刻意**排除出 Wait ⇒ 只能 Repair 到熔断）。
  应改为「同版本只做一次有界规划，其后 typed wait + 明确恢复条件」。

## 5. 边界不变性论证（验收 5）

| 边界 | 是否改变 | 论证 |
|---|---|---|
| 审批链 | **不变** | 裁决 1/2 只改 `TryResolveKinds` 与拒绝码字符串；审批由 `TaskWorkUnitAwaitKind.Approval` + 审批票据链控制，**不在本改动路径上** |
| 权限模式 | **不变** | 权限由 Agent 权限模式 + `permission_mode` 决定，与 kinds 无关 |
| 能力门控 | **不变** | `RequiredCapabilityIds` 仍在 work unit 层面过滤；裁决 1 取**保守**集合，反而**减少**默认授予面 |
| 测试预期 | **不修改预期** | 只**新增**回归用例；不修改既有断言 |
| `general` 卡行为 | **收紧**（非放宽） | 默认从「不可达」变为「只读可达」；变更须显式声明类型 |

## 7. 未决与风险

- **RISK-1**：裁决 1 的保守集合使 205 张卡中**实施类**卡仍需显式改 `task_type` 才能真正变更。
  ⇒ 需配套**存量卡类型迁移清单/API**（本裁决范围内只保证"可达"，不保证"可变更"）。若用户要求"存量卡直接可变更"，
  须重新裁决为子选项 a1。
- **RISK-2**：裁决 3 的"保留非终态"可能让 `task_plan_runs` 出现长期悬挂行 ⇒ 需配套收敛策略（超时归集或显式 cancel）。
- **RISK-3**：缺陷 B 的根因判断基于**静态代码推理 + 部署配置推断**，未在只读约束下查库确认 16 行的 `error_message`
  实际取值 ⇒ S2 实施前应**先查一次实际 `error_message`** 以确认同因（若不同因，须扩展裁决）。
- **RISK-4**：验收 4 的"真实检查证据"依赖裁决 4 的合同供给；若 (iii) `GoalRuns:CheckProjects` 属运维配置而非代码，
  须由用户侧确认后再声明达成。
