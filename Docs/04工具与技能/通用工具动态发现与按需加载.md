# 通用工具动态发现与按需加载

## 目标

当 Agent 可用工具较多时，减少每次 LLM 请求携带的工具 schema，同时保持 DeepSeek 等 OpenAI-compatible 模型可用。本阶段只使用通用 Chat Completions 能力：请求顶层的 `tools`、模型返回的标准 function call，以及下一轮重新提交工具定义。

## 执行流程

1. Runtime 先完成既有 CapabilityPolicy、Workspace 和工具配置过滤，得到当前执行真正可用的完整工具集合。
2. 工具数不超过 24 时，保持原行为并发送全部工具定义。
3. 工具数超过 24 时，首轮只发送 `search_tools` 和少量始终可用的核心工具。
4. 模型调用 `search_tools`，传入能力或动作关键词。
5. `search_tools` 只检索当前执行上下文有权看到的工具目录，返回 `loaded_tool_ids` 和简要说明。
6. Agent Loop 校验返回 id 确实属于本轮完整可用集合，然后在下一轮请求的顶层 `tools` 中加入命中的完整函数定义。

Buffered 与 Streaming 两条执行路径共用同一暴露规划器。已加载集合只在当前 Agent 执行内有效；新的用户 Turn 会重新从精简集合开始，避免旧任务无界累积 schema。

## 权限边界

工具发现不是授权：

- `search_tools` 通过 `ToolExecutionContext.CapabilityPolicy` 和 Workspace 查询过滤后的目录；
- Agent Loop 只接受当前可用工具集合中存在的 `loaded_tool_ids`；
- 工具真正执行时仍必须经过 ToolInvocationService、Registry 和 AgentFirewall 的原有检查。

因此，模型不能通过伪造搜索结果或工具名扩大能力范围。

## Provider 兼容性

这一实现不依赖 Kimi K3 的以下扩展：

- message-level `system.tools` 动态声明；
- K3 专用的动态工具缓存语义；
- 强制首轮检索的 Provider 特定行为。

DeepSeek、Qwen 和其他正确实现 OpenAI-compatible function calling 的 Provider 都走相同代码。K3 专属优化如需引入，应放在 Provider capability 分支内，不能改变这里的通用协议语义。

## 验证

重点测试覆盖：

- 小工具集保持完整暴露；
- 大工具集首轮收敛，并在搜索结果后加载命中工具；
- 未知或越权工具 id 不会被加载；
- `search_tools` 只返回 CapabilityPolicy 可见工具；
- Runtime 程序集扫描会自动注册 `search_tools`。
