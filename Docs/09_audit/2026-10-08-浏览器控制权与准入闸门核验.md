# 浏览器控制权与准入闸门核验（2026-10-08）

> 核验方法：**父级亲自读源码 + 活实例实测**，不采信子代理自述。
> 标记约定：**已证实**＝我本人读到代码原文或跑出实测结果；**待复验**＝仅有二手证据或检索覆盖不足。
> 本报告只记录事实与建议，**不含任何代码改动**。

## 一、结论摘要（三条，全部已证实）

### 1. 「人工接管」按钮对 Agent **没有约束力**：三处 Takeover 状态互不相通

存在三份独立的「接管」表示，而产品 Shell 只写其中最**不具执行权威**的一份：

| # | 状态对象 | 写入者（产物构建内） | 执行闸门是否读它 | 证据 |
|---|---|---|---|---|
A | `BrowserWorkspaceController._userTakeover` | ✅ 产品 Shell 写它 | ❌ 只喂 UI 状态机（`UserTakeover > Paused > AgentControlling > Idle`） | `PuddingDesktop/MainWindow.xaml.cs:1055`；`Source/PuddingDesktop.WpfArchive/Browser/BrowserWorkspaceController.cs:127、488-492、504` |
B | `BrowserBridgeCommandDispatcher._userTakeover` | ⛔ **产物内无写入者** | ✅ 读它：拒绝并返回 `BrowserUserTakeover` | `.../Browser/BrowserBridgeCommandDispatcher.cs:20、26、45、70、75、78` |
C | `DesktopInteractionState.IsUserTakeover` | ⛔ 产物内无写入者 | ✅ 读它：`ValidateAutomation` 对 Mutating 能力返回 `UserTakeover` | `Source/Pudding.DesktopService/DesktopService.cs:829-855` |

- 产品 Shell 的接管开关只调用 `_browser.SetUserTakeoverAsync(...)`（状态 A），**从不**调用 `_dispatcher.SetUserTakeover(...)`（状态 B）：`PuddingDesktop/MainWindow.xaml.cs:1055`。
- **唯一同时写 A 与 B 的代码在被排除的归档视图里**：`Source/PuddingDesktop.WpfArchive/Views/BrowserWorkspaceView.xaml.cs:208/209、223/224、231/233`（`_controller.SetUserTakeoverAsync(...)` + `_dispatcher?.SetUserTakeover(...)`）。
- 而 `Views/*.cs` **不在产物构建内**：`Source/PuddingDesktop/PuddingDesktop.csproj` 的 `<Compile Include=...>` 显式列出 `WpfArchive/{Core,Configuration,Browser,Bootstrap,Debug,Diagnostics,Runtime}/*.cs` 与 3 个具名文件，**不含 `Views/`**（我逐字符读过该 ItemGroup）。
- 活实例通道现状：`%LOCALAPPDATA%\Pudding\desktop.json` 的 `"desktop": null` ⇒ 当前生效的是 WebSocket Bridge 路径（待复验：该文件我未亲读，来自子代理；但它与"Bridge 路径可控制成功"的实测一致）。

⇒ **结论**：用户点「人工接管」只改变了状态 A，而两条路径的执行闸门（B、C）都读不到它。**已证实到检索覆盖范围内**：`Takeover` 在 `Source/PuddingHost` 下 0 命中（Bridge 路径根本没有接管概念，不是"没接线"）；`PuddingDesktop.WpfArchive` 与 `PuddingDesktop` 的全部命中逐条见上表。

### 2. 「设为 Agent 目标」与准入判据**不在同一层**，不可能充当页面级准入

- 目标标记是 **page 级**：`BrowserTargetRegistry.RegisterPage(contextId, pageId, isAgentTarget, isActive)` 中 `isAgentTarget` **只**写入 `_agentTargets` 集合（`Source/Pudding.DesktopService/BrowserTargetRegistry.cs:52-84`），另提供一等撤销 `SetAgentTarget`（`:127-152`，其注释自述"不撤销会让注册表替已不该驱动的页面继续背书"）。
- 准入用的是 **context 级 Trust**：`DesktopService.ValidateAdmission` 对有页面目标的能力执行 `trust = pageState.Trust`，随后 `DesktopCapabilityPolicy.IsAllowedForTrust(capability, trust)`（`Source/Pudding.DesktopService/DesktopService.cs:793-816`）；Trust 由 `BrowserTargetRegistry.TrustFor(contextId)` 从 `_trust` 字典按 **contextId** 取（`BrowserTargetRegistry.cs:160-167`），未登记则 fail-closed 到最保守级别。
- 浏览器八项能力的允许级别**只列 `AgentAuthorized`**：`DesktopCapabilityPolicy.cs:44-56`（Snapshot/Locate/Interact/WaitFor/Contexts/Tabs/ContextCreate/ContextClose）。
- UI 文案 `"No agent target"` 出自 `BrowserWorkspaceController.cs:174-176`（`AgentTargetSummary`，字段 `_agentTargetPageId` 为控制器局部状态；我亲读原文）。

⇒ **结论**：`RegisterPage` 没有任何 Trust 参数，目标标记与 Trust 分属不同层且不同粒度 ⇒ 在 AgentAuthorized 上下文里，**非目标页面同样可通过准入**。UI 上的"目标"语义与准入语义不一致，属**误导性设计**（要么把目标纳入准入，要么从 UI 撤掉该暗示）。

### 3. Bridge 的「版本必须严格推进」后置条件，会把**非导航变更判成失败**（附实测）

- 代码：`Source/PuddingHost/BrowserBridge/BridgeBrowserCapabilitySurface.cs:532-539`
  `if (!state.Version.IsKnown || state.Version.Value <= request.ExpectedPageVersion.Value) → "mutating capability returned a page version that did not advance"`；注释自述"Desktop 侧的同一条检查才是权威，这里是纵深防御"（⇒ **待复验：Desktop 侧那一份的位置未定位，修一处可能不够**）。
- 实测（活实例，同一 tab）：`click` 触发真实导航（`example.com → iana.org`），但返回该错误；事后查到版本 4 → 5，说明**报错时读到的是旧版本（竞态）**。`fill` 只改 input value：动作后 `pageVersion` 仍为 7，直到按 Enter 导航才变 8 ⇒ **`fill/type/select/check/hover/scroll` 类动作永远无法满足该后置条件**。
- 工具层确认 `scroll` **允许不带 locator**（`Source/PuddingBrowser.AgentTools/BrowserInteractTool.cs:75-77` 的 `action != "scroll" && locator is null` 才报参数错），但 `delta_y=1200` 实测**坐标零位移**（10 条结果的 y 值逐项完全相同）⇒ 底层 scroll 未生效，**属真缺陷**（与上面的报错是两件事）。

## 二、核验覆盖与受限说明

- 全仓 `search_grep` 多次触及 2000 文件枚举上限（`scanned 855/2000`、`13/2000` 等），凡"0 命中"一律改写到**具体工程目录**内复核后才下结论；`Source/PuddingHost` 的 `Takeover` 0 命中是在该目录内单独检索得到的。
- 未亲读（故标待复验）：`%LOCALAPPDATA%\Pudding\desktop.json`；`Pudding.DesktopService/DesktopInteractionState.cs` 写入者的完整枚举；Desktop 侧同名版本后置条件的位置；`PuddingDesktop.WpfArchive/Views` 是否有 Other 构建分支包含它。
- 未跑测试、未 build、未改任何受管文件（本报告为唯一新增文件）。

## 三、建议修复（按优先级；**本报告不实施**）

1. **P0｜接管必须真正断电**：让产品 Shell 的接管开关同时驱动执行闸门（B/C），或直接让闸门读同一份状态。最小改动方向是把 `PuddingDesktop.WpfArchive/Views/BrowserWorkspaceView.xaml.cs:208/209` 的那对调用搬进产物内的 Shell 接线。
2. **P0｜修版本后置条件**：导航类动作（`click/press`）改为**带超时轮询**等待版本推进；非导航 DOM 变更（`fill/type/select/check/hover/scroll`）改为 **DOM 断言**（值/勾选/滚动位移），不要求版本推进；并同步 Desktop 侧同一判据。
3. **P0｜目标语义对齐**：`IsAgentTarget` 纳入准入判据（page 级闸门），或从 UI 移除"Agent 目标"这一暗示，避免"看起来有边界其实没有"。
4. **P1｜读取面瘦身**：`browser_snapshot` 祖先 `name` 不重复整页文本、支持 interactivity-only 与分页；`browser_locate` 去重 `name/text`、bbox 取整、默认过滤不可见节点（实测 `role=textbox` 13 个里 9 个是 0×0 隐藏节点）。
5. **P2｜补能力**：截图注入（`WebView2BrowserPage.cs:335-337` 为桩，待复验）以打通视觉通道；`click(x,y)`、修饰键、拖拽、上传；修 `scroll` 底层。
