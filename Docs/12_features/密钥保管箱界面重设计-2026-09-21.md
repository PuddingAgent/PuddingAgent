## 二、重设计目标

1. **可信**：界面上每个控件都必须真实生效（禁止"看起来能揭示"）；看不到明文的理由要**写在界面上**，而不是靠用户猜。
2. **可运维**：密钥页的主任务不是 CRUD，而是**回答"这个密钥被谁用、能不能安全轮换/删除"**。
3. **一致**：全面使用 antd 主题令牌，不出现"深色孤岛"；与 09-20/09-21 的新页面（`tool-approval`、`skill-management`）保持同一视觉语言。
4. **安全默认**：遮蔽为默认；任何明文动作（创建/轮换输入）必须显式、短暂、且可审计。

---

## 三、目标信息架构

```
密钥保管箱
├─ 概览条（新增）：密钥总数 / 30 天内未轮换 / 无引用（孤儿）/ 即将过期
├─ 工具条：搜索（名称·标签）+ 分类筛选 + 标签筛选 + 状态筛选
├─ 列表（列重排）
│   名称(等宽) │ 分类 │ 状态(启用/即将过期/已过期) │ 引用数(可点开) │ 最后轮换 │ 标签 │ 操作
└─ 引用抽屉：{{vault:name}} 的使用方清单（LLM 资源池 / connectors / 系统配置 …）
```

**操作列语义收紧**（当前 4 个 icon 无标签，靠 tooltip）：
- 「编辑元数据」= 仅 name/description/category/tags（**不含** value）
- 「轮换」= 改 value，弹**带二次确认 + 输入新值 + 显示影响面**的对话框（不是"进入编辑"）
- 「删除」= 保留现有二次确认，**但先把引用数展示出来**（有引用时禁止直接删除，或要求勾选"我知道会破坏 N 处配置"）

## 六、遗留给决策的点

1. **S3 的权限与审计口径**：明文可查看的授权范围（仅超管？是否需二次确认？审计事件字段与保留期）。属安全域，须蜜糖/HITL 定。
2. **删除策略**：有引用时是"硬禁止"还是"警告 + 显式勾选"？倾向前者（密钥删除导致线上配置静默失效，代价高）。
3. **是否引入"轮换历史/多版本"**：`IKeyVaultService` 当前**无版本概念**（单值覆盖），做历史需改后端数据模型 —— 建议先不做，仅在 UI 提示"轮换即覆盖"。
