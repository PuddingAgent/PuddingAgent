# ADR：SKILL Hub 工具对 Agent「无感」——本地/远程由平台内部裁决

- 日期：2026-09-21
- 状态：**已定稿（用户裁定），两条实现并行实施**
- 关系：**修订**《SKILL-Hub技能中心与EVO-MAP设计方案》§6 中"agent 工具走 HTTP + `X-Admin-Api-Key`"的约定
- 裁定链（留档以免反复）：
  1. 「开发一个 SKILL Hub 工具给你，这样你不需要密钥就可以上传、下载、更新」→ 本地路径 = 进程内直连。
  2. 「这两条路都可以并行，后续需要多个 PuddingAgent 平台互联，API Key 仍然需要，就像 MPM」→ 远程路径保留。
  3. **「允许连接到远程，但具体配置应该由 PuddingAgent 负责配置，Agent 自己的工具应该无感。具体的密钥管理和远程联机由 PuddingAgent 负责」→ 最终形态：工具契约与本地/远程无关；路由、凭据、联机全部下沉到平台。**

---

## 1. 问题

把"同进程内的平台能力"与"跨平台互联能力"混进**同一个工具契约**（工具自己解析 `BaseUrl`、自己带 `ApiKey`、自己选传输），导致：
- 工具承担了不该它承担的**拓扑与凭据**职责；
- 配置缺失时静默回退到错误端口（`:5000`），现场表现为"工具坏了"，实际是架构错位；
- 密钥被迫流经工具层，扩大了暴露面。

实测证据（2026-09-21）：宿主侧无 `X-Admin-Api-Key` 接收端（二进制扫描：仅 `PuddingRuntime.dll` 含该串）；工具默认 `:5000` 而宿主在 `:80`；人类 JWT 无法用于工具；External Token 被 policy 挡（仅 `/api/external/v1`）⇒ 双死因。

## 2. 决定（核心原则）

> **Agent 侧工具只依赖一个平台接口；"数据从哪来（本进程 / 远端平台）"是平台的事。**
> **密钥管理与远程联机由 PuddingAgent（平台）负责，工具与调用方均无感。**

由此**撤销**上一版草案中的 `skill_hub target=local|remote` 参数 —— 它把平台复杂度泄漏给了 Agent，违背"无感"。
**工具契约零变化**：工具 id `skill_hub`、11 个 action 名与参数**全部保持原样**，不新增任何拓扑相关参数。

## 3. 架构：一个契约 + 两个实现 + 组合根裁决

```
PuddingCore（契约层）
  PuddingCode.Skills/ISkillHubService.cs      ← 工具唯一依赖（15 个语义方法）
  PuddingCode.Skills/SkillHubDtos.cs          ← 迁移自 PuddingPlatform/Data/Dtos
  PuddingCode.Skills/SkillHubFeatureOptions.cs← Enabled 开关

PuddingPlatform（实现层 —— 两种拓扑，二者选一由组合根注册）
  Services/SkillHubService.cs        : ISkillHubService   ← ① 本地：EF/SQLite 直连（同进程，无凭据）
  Services/RemoteSkillHubService.cs  : ISkillHubService   ← ② 远程：HttpClient 调远端平台 Hub
                                                              （凭据由平台注入；工具看不到密钥）

PuddingHost（组合根 —— 唯一的裁决点）
  读配置：SkillHub:RemoteBaseUrl 有值 ⇒ 注册 RemoteSkillHubService
          否则                        ⇒ 注册 SkillHubService（本地，零配置默认）
  密钥：SkillHub:ApiKey / 远程凭据 → 由宿主注入 HttpClient（defaultRequestHeaders），
        **绝不进入工具、绝不进入工具 schema、绝不写日志**

PuddingRuntime（工具层 —— 彻底无感）
  Services/SkillHubTools/SkillHubTool.cs  ← 只注入 ISkillHubService
  删除：HTTP 传输层、命名 HttpClient 注册、BaseUrl 解析、ApiKey 读取、错误映射
```

**收益**：工具变薄且稳定；拓扑切换零代码改动（只改配置）；密钥不再流经 LLM 可见的工具层；本地/远程语义一致（同一接口）。

## 4. 边界与安全

| 项 | 要求 |
|---|---|
工具层 | 不得读取/记录任何密钥；不得出现 `BaseUrl`、`ApiKey`、`X-Admin-*` 字样；不得因未配置而静默回退 |
配置缺失 | 由**组合根**在启动时判定：既不静默回退到错误地址，也不影响本地默认可用性 |
宿主接收端（被其他平台调用时）| 新增 scheme（`X-Admin-Api-Key`）+ **仅限 SkillHub 端点**的命名策略；fail-closed；常量时间比较；不授 admin 角色；默认策略与其它端点零影响 |
远程出站（本平台调他人）| 凭据由平台持有并注入；建议随请求携带平台身份头（如 `X-Platform-Id`）以便对端审计 |
身份归属 | 由平台决定与校验（跨平台发布时 `PublishedBy*` 由平台填充/校验，不由调用方自由声明）|

## 5. 不变的部分（避免误伤）

| 项 | 保持不变 |
|---|---|
控制器 API 与 `[Authorize]` | 15 个 HTTP 端点、JWT 鉴权、DTO 形状**全部不变**（人类 UI 与外部脚本继续可用）|
`SkillHubService` 语义 | 校验规则（SkillId 正则、动作白名单、ContentHash = SHA256 前 16 字节小写 hex、版本比较）不变 |
数据库 | 4 张 `Hub*` 表 + `SkillHubSchemaBootstrapper` 接线不变 |
工具对外契约 | 工具 id + 11 个 action 与参数**零变化**（Agent 侧完全无感）|

## 7. 验收

1. 构建：`PuddingCore` / `PuddingPlatform` / `PuddingHost` / `PuddingRuntime` 均 0 错误；既有 `SkillHubServiceTests` 保持绿。
2. 本地默认路径：重启后 `skill_hub action=stats|publish|list|get|lineage|install` 全通，并发布 `ppt-master` 为首例。
3. 远程路径：配 `SkillHub:RemoteBaseUrl` 后工具行为**完全不变**（无感切换）；远端凭据不出现在工具日志/工具 schema 中。
4. 接收端隔离：带正确 `X-Admin-Api-Key` 访问 `/api/skill-hub/stats` → 200；错误/缺失 → 401；**同一头访问其它管理端点仍必须 401**。
5. 人类路径回归：管理界面六 Tab 正常。

## 8. 回滚

纯代码改动，`git revert` 对应提交；两条实现可分别回滚（组合根默认回本地）。数据库无需回滚。

## 9. 后续（不在本批范围）

跨平台**配对与密钥生命周期**（平台间注册/轮换/吊销，MPM 式 registry 账号体系）——本批只做"出站调远端 + 入站收凭据"两条腿，配对流程另行立项。凭据形态（沿用 `X-Admin-Api-Key` vs 复用 `ExternalAccessToken` + 新 scope 如 `skills.publish`）由平台侧决定，本批先用前者以最小改动打通。
