# PA-07A 事件流语义设计决策请求

**裁定入口（2026-11-06）**：[S5 架构裁定与接线门禁](Agent组件化S5架构裁定与接线门禁-2026-11-06.md)选择插件 Workspace 流与内部 UoW，并规定过滤游标、保留边界、租约和 Review 原子完成。本文件后文保留原方案分析；“等待选择”和“不改冻结端口”不再是阻止必要核心修订的条件，施工以裁定为准。

状态：**等待架构师选择**。已落地的 `SubscriptionStore`/`EventDeliveryStore` 按 SQLite 表与“订阅/事件去重/checkpoint 同事务”实现，但 `EventReadRequest.StreamId` 与 `SubscriptionGrant(WorkspaceId, Kinds)` 不匹配，且 `IEventOutboxWriter` 未定义业务事实与事件如何进入同一事务，因此分发 Worker 尚未实现。

## 1 问题

1. **流身份**：`ICommittedEventLog.ReadAsync(EventReadRequest(StreamId, AfterSequence, MaxCount))` 要求单一流游标；`SubscriptionGrant` 只有 WorkspaceId + Kinds，没有 StreamId。
2. **outbox 事务边界**：`IEventOutboxWriter.BeginAsync()` 返回仅有 `AppendAsync/CommitAsync` 的事务对象，没有暴露可挂业务写入的 DbContext/事务句柄；调用方无法保证“事实+事件”原子提交。
3. **保留与快照**：`EventPage.SnapshotRequired` 要求保留窗口外的 cursor 能触发新快照，需要定义哪个表保存流保留边界。
4. **Kinds 过滤**：订阅按 kinds 过滤；同一 workspace 多个订阅需要各自 cursor/checkpoint，而流游标是单一的。

## 2 方案对比

| 方案 | 语义 | 优点 | 代价/风险 |
|---|---|---|---|
| A. Workspace 为流（StreamId=WorkspaceId） | 每个 workspace 一条 canonical 事件流；订阅按 kinds 过滤并各自持有 cursor | 与现有 grant 一致；checkpoint/去重表无需改；插件天然按 workspace 授权 | 会话级精确顺序需要事件携带 conversationId；高并发 workspace 单流写放大 |
| B. Conversation 为流（StreamId=ConversationId） | 每条会话一条流；订阅需携带会话集合或改为会话级 | 与会话事件顺序天然一致；前端/SSE 复用 | grant 与订阅表需加 conversation scope；workspace 级插件订阅要维护 N 个游标；checkpoint 语义复杂 |
| C. 混合：workspace 主订阅流 + conversation 辅助流 | 插件订阅走 workspace 流；UI/SSE 走 conversation 流 | 每种消费者语义最优 | 两条流需保证同一事实不重复计费/重复投递语义；实现与测试面最大 |

**推荐：A（Workspace 为流）**，理由是与已冻结的 `SubscriptionGrant`、已落地表结构、以及插件按 Workspace 授权的边界一致；conversation 事件只是流内带 `conversationId` 的事实。

## 3 推荐设计要点（若选 A）

1. **流表**：`event_streams(stream_id, oldest_available_sequence, next_sequence, updated_at)`；`stream_id` = workspace_id。事件落库时分配 sequence（与 `conversation_events` 的 sequence 不同层，需明确二者关系：建议 canonical workspace 流引用 conversation event id，不复制正文）。
2. **订阅读取**：`EventReadRequest.StreamId = subscription.Grant.WorkspaceId`；`AfterSequence = subscription.CursorSequence`；读取后按 `Kinds` 过滤再进入 delivery 去重（`(subscription_id, event_id)` 已唯一）。
3. **checkpoint**：沿用 `SubscriptionStore.AckAndAdvanceAsync`（删除 delivery + 推进 cursor 同事务）；`SnapshotRequired` 时禁止推进 cursor，返回 `event.snapshot_required` 并要求重新建订阅/快照。
4. **outbox 事务**：新增**Platform 内部**端口 `IOutboxUnitOfWork`：
   ```csharp
   public interface IOutboxUnitOfWork {
       Task<T> ExecuteAsync<T>(Func<PlatformDbContext, IEventOutboxWriter, Task<T>> work, CancellationToken ct);
   }
   ```
   业务 Store 在传入的 `PlatformDbContext` 上写事实，并用 writer 在**同一 DbContext/事务**中 Append；Commit 由 UoW 统一完成。冻结的 `IEventOutboxWriter` 契约不变（仍由 UoW 适配器实现）。
5. **分发 Worker**：按 `subscriptions.workspace_id` 分组低频扫描 → `ICommittedEventLog.ReadAsync` → `IEventDeliveryStore.EnqueueAndClaimAsync` → 插件回调（超时/取消）→ 成功则 `AckAndAdvanceAsync`；失败 `FailAsync`（重试/死信）。退避同上，正确性不依赖 tick。
6. **保留/快照**：更正（2026-11-06）：连续提交序号下，`cursor + 1 < oldest_available_sequence` 才表示请求早于保留范围；原“小于订阅 cursor”方向错误。宿主负责受权快照恢复，不允许静默跳过；含序号空洞时用明确保留边界，见上述裁定。
7. **幂等**：`(subscription_id,event_id)` 唯一；ACK 丢失重投由消费方按 EventId 去重。

## 4 需要架构师确认

1. 选 A/B/C 中哪一个（推荐 A）。
2. canonical workspace 流与现有 `conversation_events` 的关系：引用其 eventId（推荐）还是独立复制 payload？
3. outbox 事务是否接受新增 Platform 内部 `IOutboxUnitOfWork`（不修改 07A 冻结端口）。
4. 保留窗口/快照重建的责任方（Host 启动任务 vs 订阅创建时）。

## 5 不做的部分

在决策前不实现分发 Worker、不改 `SubscriptionGrant`、不新增流表；已落地的订阅/投递/checkpoint 表保持现状（不与任何 Worker 绑定）。
