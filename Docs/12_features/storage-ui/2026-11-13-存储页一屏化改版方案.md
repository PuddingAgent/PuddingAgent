# 存储页「一屏化」改版方案

## 1. 现状与问题（逐条，基于 2026-11-13 实拍）

页面结构（`index.tsx` 30 KB + `DatabaseSpacePanel.tsx` + `StorageOverviewCharts.tsx`）：

1. 首屏左：`存储空间总览` 卡 —— 一句「Pudding 数据约 15.2 GB」+ 四行说明文字 + 5 行数据库表（大小 / 可复用页）。
2. 首屏右：`分类占比（估算）` 环形图 —— **当前只有一个分类「会话事件证据 ≈2.0 GB（100%）」**。
3. 首屏下：`近 30 天存储趋势（堆叠面积）` —— 占满整行高度，**只有 10-14 与 11-13 两个数据点**。
4. 第二屏起：`数据库占用（按数据类）` —— 横向进度条，四个数据库各自展开。

### 具体问题

| # | 问题 | 证据 |
|---|---|---|
| P1 | **真正的占用拆分在第二屏**。首屏只有 5 行「数据库大小」，看不到「哪个库里的什么占了空间」 | `数据库占用（按数据类）` 整体位于折叠线以下 |
| P2 | **环形图零信息量**。只有一个分类，占比 100%，图形不携带任何比较信息，却占约 1/3 首屏宽度 | 截图右上 |
| P3 | **趋势图面积与信息量严重不匹配**。整行高度换两个数据点 | 截图下方 |
| P4 | **说明文字喧宾夺主**。四行解释（WAL 口径、可复用页、可清理估算…）紧贴主数字，视觉权重高于数字本身 | 「更新于 … | 状态：空闲 | revision 30693」等四行 |
| P5 | **缺少可执行维度**。「能回收多少、点哪里回收」散落在文字与第二屏，首屏看不到 | 「可清理估算合计 ≈2.0 GB」是纯文字 |
| P6 | **空闲页 4.0 GB 与「占用」混在一起**。它是可回收空间，不是数据；但当前与占用同列 | 平台库 `可复用页 4.0 GB` |

## 2. 调研结论：图表选型

检索到的共识（来源见 §7）：

- **环形/饼图不适合比较面积**：人眼比较扇形面积与弧长精度低，类别多时更差；只适合「总量 + 少数类别」的定性展示。
- **矩形树图（treemap）适用于「类别多、需要在一屏内紧凑比较全部类别」**，且天然支持层级。
- 仪表盘应优先用**长度/位置**这类前注意属性编码，精确数字交给 tooltip 或表格。

**因此**：

| 用途 | 选型 | 理由 |
|---|---|---|
| 数据库 → 数据类 → 表 的层级占用 | **矩形树图** | 一屏内比较全部类别，面积=字节，支持下钻 |
| 单个数据库内部构成 | **100% 堆叠横条**（每库一条） | 长度编码精度高，适合读占比 |
| 可回收空间 | **独立三段条形**（VACUUM / 冗余索引 / 保留策略） | 三个不同性质的「可省」，需分开表达 |
| 趋势 | **KPI 卡内嵌 sparkline** | 数据点少时不让它独占一行 |

环形图**移除**——它承担的语义（分类占比）由堆叠横条更准确地完成。

## 3. 目标与验收标准

**一句话目标**：在 1440×900 的浏览器视口内，**不滚动**即可看到：每个数据库的总量、该库内 Top3 数据类及占比、以及可回收空间合计。

可判定的验收项：

1. 视口 1440×900 下，页面纵向滚动条不出现（`document.scrollingElement.scrollHeight <= clientHeight`）。
2. 五个数据库（平台 / 代码索引 / 记忆 / 控制面 / 全文索引）**全部可见**，无需展开。
3. 每个数据库旁展示其 Top3 数据类名称 + 百分比。
4. 「可回收合计」在首屏可见，且可拆解为三项（VACUUM / 冗余索引 / 保留策略）。
5. 任一数据块 hover 给出精确字节数（不牺牲精度）。
6. 数据类数为 0 或仅有 1 类时，图形**降级为文字**而不是画一个 100% 的单色块。

## 4. 布局规格

内容区宽度基准 1440 px（截图为 1920 宽视口、侧栏约 220 px，余 1700；1440 为保守基准）。

```
┌──────────────────────────────────────────────────────────────┐
│ [总占用 15.2GB] [数据库 14.9GB] [非库 393MB] [可回收 4.9GB]  │  行1  h=104  KPI×4
├───────────────────────────────────┬──────────────────────────┤
│ 矩形树图（DB→数据类→表）           │ 各库构成 100% 堆叠横条    │  行2  h=340
│ 面积=字节，颜色按库分组             │ 5 条，每条标 GB + Top3    │
├───────────────────────────────────┴──────────────────────────┤
│ 可回收：░░░░ VACUUM 4.0GB  ▒▒ 冗余索引 853MB  ▓ 保留策略 2.0GB │  行3  h=96
└──────────────────────────────────────────────────────────────┘
合计高度 ≈ 104 + 16 + 340 + 16 + 96 = 572 px（留出标题与说明 ≈ 180 px）
```

- **行1 KPI 卡**：主数字 28 px，单位 14 px；副行只放**一个**口径说明（如「含 WAL」），完整口径说明下沉到页面底部或 tooltip——解决 P4。
- **行2 左 treemap**：三层。默认展开到「数据类」层；点击某个库下钻到「表」层，面包屑返回。面积按字节，最小块低于总面积 0.5% 的合并为「其他（N 项）」，避免不可点击的碎片——与现有「未归类 96 张表」的处理一致。
- **行2 右 堆叠横条**：每个数据库一条，条内按数据类分段，段内不写字（宽度不足时省略），右侧固定列写 `12.0 GB · 会话事件 18% / Debug 5.3% / 空闲 34%`。
- **行3 可回收**：三段并列，各带一个按钮直达对应清理流程（`PreviewCleanup`）。三段颜色区分「结构性可回收（VACUUM）」「冗余可删（索引）」「策略可清（保留期）」。
- **趋势**：降级为「总占用」KPI 卡右侧的内嵌 sparkline（高 32 px），数据点 < 3 时显示「数据不足」而非画折线。

### 1280 宽降级

内容区 < 1280 px 时，行2 改为**纵向两段**（treemap 上、横条下），行3 保持单行；此时允许出现一次滚动，但首屏必须仍包含行1 与行2 的全部库名。

## 5. 数据契约

前端现有：`types.ts`、`usageBreakdown.ts`（占比计算）、`DatabaseSpacePanel.tsx`（按库面板）。

需要确认/补齐的服务端字段：

| 字段 | 用途 | 现状 |
|---|---|---|
| 每库 `mainBytes` / `walBytes` / `shmBytes` | KPI 卡精确总量 | 已有（`DatabaseSpaceReport`） |
| 每库 `freeListBytes` | 「可回收」第一段 | **已有**（`可复用页` 列已渲染） |
| 每表 `Bytes` + `OwnerTable` | treemap 叶子层 | 已有（`dbstat` 逐 B 树） |
| **表 → 数据类 映射** | treemap 中间层与横条分段 | 服务端 `StorageDataClassCatalog` 有 targetId→tables；**需在分析响应里一并给出，避免前端硬编码** |
| **受保护对象标记** | treemap 中标出不可清理项 | `ProtectedObjects` 目前只有中文描述串，**需要可判定的结构化清单** |
| 可清理估算（分三类） | 行3 三段 | 部分有（`可清理估算合计`），需拆成 VACUUM / 冗余索引 / 保留策略三项 |

> `ProtectedObjects` 目前是给人读的字符串数组（如「TokenUsageEvents（会话/角色/上下文归因账本）」）。要做「treemap 中标记不可清理」，需要一份 `表名 → 保护原因` 的结构化映射。这是本方案唯一的服务端改动，且是纯增量。

## 6. 边界与不做的事

- **不新增数据采集**。全部基于现有 `dbstat` + 目录映射；估算类数字沿用现有口径，不另造一套。
- **不做自动清理**。行3 的按钮只跳转到既有的 `PreviewCleanup`（预览确认），不引入新的自动动作。
- **不合并「空闲页」进占比**。空闲页是可回收空间，必须在视觉上与「占用」区分，否则用户会误以为数据在增长（P6）。
- **不保留环形图**。若产品另有页面用环形图表达「总量 + 少数类别」，可保留；本页的分类占比改用堆叠横条。

## 7. 参考

- Datylon《80 types of charts》——treemap 适用于「类别多、需一屏紧凑展示全部类别」。
- Nielsen Norman Group《Dashboards: Making Charts and Graphs Easier to Understand》——仪表盘应依赖前注意属性（长度、位置）编码。
- Domo / Chartbrew 关于 donut 的最佳实践——环形图适合少量类别的定性比较，不适合精确面积比较。
