# Super-agent 架构 vs 本仓 goal 模式

> 对标对象：DeepSeek Harness 团队的 Super-agent 架构（[原型](https://github.com/deepseek-ai/dsh-superagent-prototype)），
> 中文图解见 `Docs/19_references/动态图解-DeepSeek-Super-agent架构-2026-11-01.md`；
> goal 实现细节见 `Docs/19_references/deepseek-harness-goal-mode-解剖-2026-11-01.md`。

## 1. 目标形态先说清楚

用户 2026-11-01 的表述，和 Super-agent 的四特征是同一件事：

```
PuddingAgent = 24 小时常驻、事件驱动的 agent
goal 模式    = 持续做完「一件事」，而不是做完一个小步骤就停、等用户发「继续」
硬约束      = 做完必须自己停，不许一直烧 token
```

这三条**互相拉扯**：第一条要求常驻、第二条要求不停、第三条要求停得住。
只做前两条 → 空转烧钱；只做第三条 → 任务半途而废。

## 2. Super-agent 五模块 vs 我们的现状

| 模块 | 它解决什么 | 我们有什么 | 差距 |
|---|---|---|---|
| **双层架构**（Router + Worker） | 连续交互 vs 高效并发不必二选一；会话藏到底下 | 单一 Session 模型，`spawn_sub_agent` 是临时派活 | **没有常驻 Router**；多任务靠人肉切会话 |
| **事件驱动** | 主动响应环境事件，没人 @ 也能干活 | 心跳（定时轮询）+ Hook（进程内事件） | 只有**定时**与**进程内**事件，缺**外部事件入站**（IM / GitHub / 邮件） |
| **异步多信道交互** | 结果按渠道格式化：群里 100 词内、PR 写结构化 | `send_message` 单渠道（飞书） | 缺渠道适配层 |
| **存算分离** | 状态不绑在单机进程，换设备连续 | 状态在 SQLite + 文件，**与进程同机** | 换机即断；没有状态服务化 |
| **外部 Watchdog** | 异常自愈、长期在线 | `PuddingGuardian` 存在（部署回滚） | 覆盖部署，不覆盖"Agent 卡死/空转" |

## 3. goal 三件套已对齐的部分

本轮已落地并验证（都在 `Source/PuddingRuntime/Services/AgentLoop/`）：

| 组件 | 对齐的点 | 测试 |
|---|---|---|
| `GoalLifecycle` | phase（持久）与 activation（进程本地、永不落盘）分离 ⇒ **重启后不自动续跑** | 11 条 |
| `GoalRoundLedger` | 只有**真正进入模型历史**的 round 才计额度；轮号必须 == 已用+1 | 14 条 |
| `ContinuationPolicy` | 续跑三条件：有未完成 + 有余量 + 上轮有推进 | 11 条 |
| `RepeatedActionGuard` | 同一动作连续重复即判空转（该停就停） | 7 条 |

注意 `RepeatedActionGuard` 的语义是**连续重复**而非"窗口内出现次数"——
后者会把「读 A → 改 B → 再读 A」这种正常节奏误判成空转（实测踩过）。

## 4. 还缺的三件（按影响排序）

### 4.1 常驻 Router（双层架构的那一层）

现状：一个 Session 一件事，多任务靠人切换。
缺的：**一个只派活的常驻实体**，把"哪件事该由谁来推进"从人脑移到系统。

最小可行版本不需要重写会话模型：
```
Router 读事件队列 → 判定归属（新建 / 续接哪个 Session）→ 派给 Worker
Worker = 现有的 Agent Loop，不变
```

### 4.2 外部事件入站

现状：心跳是唯一的外部唤醒源，且是**定时**的。
缺的：IM 消息 / GitHub 事件 / 文件变更作为**一等事件**进来，而不是靠人转述。

这条决定「主动」是真的还是演的：没有入站事件，"主动"只能靠定时轮询猜。

### 4.3 完成判定的证据链

现状：`ContinuationPolicy` 用 `OpenItems == 0` 判完成 —— 等于**让模型自己宣布自己做完了**。
缺的：完成要带可核验证据（例如 goal 里声明验收命令，跑通才算完），否则只能标 `blocked`。

这条与「做完必须自己停」直接相关：**模型最容易在"我觉得好了"的时候停错。**

## 5. 建议顺序

```
① 完成证据链（最小、最硬、立刻能挡假完成）
② 常驻 Router（把多任务从人脑挪到系统）
③ 外部事件入站（让"主动"成立）
④ 存算分离 / Watchdog（长期在线的基础设施，最后做）
```

理由：① 是纯逻辑，能单测、能取红；② 是结构改动，需要先有 ① 才不会"派出去的活没人验收"；
③④ 依赖部署形态，短期收益不如前两条。

## 6. 明确的取舍

- **不照搬它的插件体系**（Cordis）：我们已有 DI + `IAgentLoopHook`，两套生命周期会割裂；
- **不做 fork/Ralph 式独立尝试**：它自己也标注属另一插件层；
- **不做 evaluator 认证**：列为 deferred，我们更没依据先做。

短期只拿它**最能证伪的三条**：activation 不持久化、轮次准入记账、完成要证据。
