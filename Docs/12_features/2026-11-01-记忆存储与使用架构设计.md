# 记忆存储与使用架构设计

> 目标一句话：**记忆不是一次性加载的文本，而是一个可遍历、可衰减、可维护的图**，
> 主代理只按预算看「索引 → 摘要 → 正文」的渐进切片，深度维护交给后台子代理（autodream）。

## 0. 先把已有的数清楚（不要再造一套）

现有实现（`Source/PuddingMemoryEngine`）：

| 能力 | 位置 | 现状 |
|---|---|---|
| 事实存储 | `Services/FactMemoryService.cs`（`MemoryFactRecord`、`CreateFactRequest/Evidence/Freshness/EntityMention/Association`） | 已有 fact + evidence + entity mention + **association** |
| 新鲜度 | `FactFreshnessCalculator.Compute` | 已有半衰期式打分输入结构 |
| 上下文匹配 | `FactContextMatcher.Match`（`FactContextMatchOptions.WeightedKeys`） | 已有按权重键匹配 |
| 召回 | `Services/MemoryRecallService.cs` | 已有召回服务 |
| 维护 | `Services/MemoryLibrarian.cs` | 已有整理入口（待确认触发方式） |
| 注入管道 | `PuddingRuntime/Services/ContextPipeline*.cs`（L4-PINNED / L9-USER-PREFERENCES 等层） | 已有分层注入与预算 |
| 扩展点 | `PuddingRuntime/Services/AgentLoop/IAgentLoopHook.cs`（12 个生命周期点 + `OnToolResultTransformingAsync`） | 已有插件式 Hook |

**结论：不需要从零设计存储。缺口有三处：**

1. **遍历**：有 association 表，但没有「从某个节点出发、按预算展开 k 跳」的查询面；
2. **渐进加载**：注入管道是「把整层拼进去」，没有「同一记忆的 L0/L1/L2 三档」概念；
3. **后台维护**：`MemoryLibrarian` 有整理能力，但没有**无人值守的触发与调度**（autodream）。

## 1. 存储：节点、边、版本

### 1.1 节点（Node）

在既有 fact 之上抽一层**统一视图**（不合并表，避免 god-table）：

```text
MemoryNode
  NodeId        : string (稳定业务 ID，幂等键)
  Kind          : Fact | Note | Procedure | Preference | Artifact
  Title         : string(≤120)      // L0 索引用，也是人读的唯一入口
  Summary       : string(≤600)      // L1 摘要
  Body          : string(不限)      // L2 正文
  Scope         : Workspace | Agent | Session
  Tags          : string[]          // 检索主键之一
  Salience      : float 0..1        // 重要性（人工/引用次数共同决定）
  Freshness     : float 0..1        // 由半衰期公式算出，不手写
  LastAccessedAt: DateTimeOffset
  AccessCount   : int               // 用于 salience 与冷存归档
  Provenance    : { SessionId, TurnId, MessageId } // 可追溯到原始对话
  Rev           : int               // 当前版本号（见 1.3）
  Tombstoned    : bool              // 软删
```

**为什么 Title/Summary/Body 三档是硬要求**：这是「渐进加载」能否成立的唯一前提。
没有 L0/L1，主代理只能整篇加载，1M 上下文也撑不住。

### 1.2 边（Edge）

现有 `CreateFactAssociationRequest` 已有雏形，建议显式化类型：

```text
MemoryEdge
  FromNodeId, ToNodeId
  Relation : About | Refines | Contradicts | DerivedFrom | Supersedes | RelatedTo
  Weight   : float 0..1     // 随共现/引用强化，随新鲜度衰减
  Confidence: float 0..1
  CreatedAt, UpdatedAt
```

- `Contradicts` 与 `Supersedes` 是**关键**：记忆最常见的坏味道不是缺失，而是**旧结论还在**。
- `About(entity)` 复用已有 entity mention，让「某公司/某项目/某文件」成为可遍历的锚点。

### 1.3 历史（Revision，append-only）

```text
MemoryNodeRevision
  NodeId, Rev, Title, Summary, Body, ChangedAt, ChangeKind(create|update|merge|archive), Actor(agent|human|dream)
```

当前节点行只存 head；所有变更写 revision。**删除是 tombstone，不是 DELETE** ——
否则「为什么这条记忆没了」永远查不出来。

## 2. 三个性质怎么落地

| 性质 | 落地方式 | 判据（可测试） |
|---|---|---|
| **关联性** | Edge + k 跳展开（默认 1 跳，最多 2 跳）+ Weight 排序 | 给定节点，展开结果里应出现人工构造的邻居 |
| **新鲜度** | `FactFreshnessCalculator` 半衰期；Kind 决定半衰期（Preference 长、Note 短） | 同一节点跨时间点评分单调下降；刷新后回升 |
| **语义相关性** | 复用 `FactContextMatcher.Match(WeightedKeys)`；向量检索作为**可选**加权项，不作为主路径 | 换上下文键，命中集合应变化 |

排序建议（可直接实现）：

```
score = 0.45*contextMatch + 0.25*freshness + 0.20*salience + 0.10*edgeProximity
```

权重不做成魔法常数，**放进配置**（`memory.ranking.*`），便于按真实数据调。

## 3. 使用：渐进加载（主代理侧）

### 3.1 三档 + 预算

```
预留给记忆的总预算 M（默认 = 输入预算的 8%，硬上限 8000 tokens）

L0 索引  每次最多 N0 条，每条 ≤ 40 tokens   ← 永远给
L1 摘要  仅对 L0 中被「点名」的节点展开，每条 ≤ 200 tokens
L2 正文  仅当代理显式读取（工具调用），每次 ≤ 1 条
```

**核心规则：L0 之外的展开必须是代理主动的行为**（`memory.open(nodeId)`），
而不是管道替它猜。猜错的代价是上下文被无关记忆占满。

### 3.2 注入格式（带来源，防"记忆当事实"）

```
--- LAYER: MEMORY-INDEX (n=12, budget=480/8000) ---
[F-8a31] 用户偏好：回答用中文  (pref, fresh .91)
[F-2c07] PuddingAgent 仓库根 = D:\CodeProject\PuddingAgent\PuddingAgent (fact, .88, 2026-11-01)
...
```

每条必须带 **NodeId + Kind + 新鲜度**：没有这些，模型无法判断该不该信、要不要复核。

### 3.3 写回

- 主代理显式写：工具 `memory.write(node)`（已有 save_memory 的升级形态）；
- 主代理隐式写：**不自动落库**。隐式写入会让记忆库变成日志，噪声淹没真结论。

## 4. Autodream：后台子代理维护（主代理无感）

### 4.1 触发（Hook）

```csharp
// 只加一个「低频」触发点，不碰工具结果热路径
public Task OnLoopCompleteAsync(ctx, finalMessage, stopReason, ct)
{
    if (_dreamScheduler.ShouldDream(ctx, stopReason))   // 去抖 + 配额 + 空闲判定
        _ = _dreamScheduler.RunAsync(ctx.SessionId);     // fire-and-forget，失败静默
    return Task.CompletedTask;
}
```

**为什么不用 `OnToolResultTransformingAsync`**：那是每次工具调用都走的路径，
在上面起后台任务会被调用频率放大，且会和用法引导/交接摘要抢同一条链路。

### 4.2 四类维护任务（各自幂等，各自可单测）

| 任务 | 做什么 | 幂等键 |
|---|---|---|
| `consolidate` | 合并重复/近重复节点，保留最高 salience + 证据并集 | (nodeKind, normalizedTitle) |
| `reconcile` | 检测 `Contradicts`/`Supersedes`，把旧节点标 superseeded 而不是删 | (fromNodeId, toNodeId, relation) |
| `decay` | 按半衰期更新 Freshness；低于阈值的归档（不进 L0） | (nodeId, dayBucket) |
| `link` | 给孤立节点补边（共现 + 实体重叠） | (fromNodeId, toNodeId) |

### 4.3 硬约束（"无感"的前提）

1. **不阻塞**：主链路只做一次入队判定，实际工作全在后台；
2. **有预算**：单次 dream 有 token/时长/写条数上限，超限即停并记录原因；
3. **可拒绝**：dream 产生的变更默认 `ChangeKind=dream`，高价值节点（`Salience >= 0.9`）
   只提 `Contradicts` 建议，**不自动改写**；
4. **可回滚**：全部走 revision，能按 `dreamRunId` 一次性回退；
5. **失败静默**：异常只进诊断日志，不影响主流程（与 Hook 契约一致）。

### 4.4 与「交接摘要」的关系

`context_handoff`（`062a838`）解决的是**会话内的短期接续**；
autodream 解决的是**跨会话的长期沉淀**。两者共用 Hook 基建，但职责不重叠：

```
会话内  → context_handoff（主代理自己写，短、贵精）
跨会话  → autodream（子代理整理，长、可批量）
```

## 5. 分阶段落地（按组件化交付规程 S1–S5）

| 阶段 | 内容 | 门禁 |
|---|---|---|
| **S1** | 新组件 `PuddingMemoryGraph`：节点/边/版本/预算查询（纯查询 + 纯函数排序） | 零 `Pudding*` 依赖，只依赖 BCL + 抽象契约 |
| **S2** | 独立测试工程，覆盖：k 跳展开、预算裁剪、衰减单调性、tombstone 不可见 | 表驱动正反例 |
| **S3** | 无宿主验证：拿真实记忆库副本跑只读查询，对比人工期望 | 只读 |
| **S4** | 边界断言：csproj 零 ProjectReference、程序集只引用允许项 | 编译期 |
| **S5** | 接入：`MemoryRecallService` 改为走 graph；`DreamScheduler` 注册为 `IAgentLoopHook` | 宿主改动仅 DI + 一处调用 |

**先做 S1 的理由**：`MemoryLibrarian` 已经有整理能力，缺的是「可遍历 + 可裁剪」的查询面。
把查询面独立成组件，才能在不重启宿主的前提下把排序算法调对。

## 6. 未决问题（需要裁定）

1. **存储后端**：继续用 `MemoryLibraryDbContext`（EF + SQLite），还是为新组件单独库？
   —— 我倾向**同一个库、不同表**，避免双写与一致性问题。
2. **衰减参数默认值**：Preference/Fact/Note 的半衰期分别取多少？
   —— 建议先取 180d / 60d / 14d，用真实访问数据回归。
3. **autodream 配额**：每次最多整理多少节点、多久跑一次？
   —— 建议「每会话结束最多 1 次，单次 ≤ 50 节点 / ≤ 30 秒」。
4. **向量检索是否进主路径**：我倾向**不进**，先做确定性排序；向量只用于「同义补召回」。
5. **L0 常驻条目数**：N0 取值直接决定每轮固定开销 —— 建议 12 条起，实测再调。
