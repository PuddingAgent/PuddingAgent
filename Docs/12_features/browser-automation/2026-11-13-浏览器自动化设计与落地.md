# 浏览器自动化设计与落地

## 0. 结论先行

现有工具**不是缺功能，是缺「动作可行性判定」**。七条实测缺陷里有五条同源：
**在动作发出前，没有确认「目标现在真的可以被点/被输入」**。

三条设计原则：

1. **先判定，再动作**。每次交互前跑一组可行性检查（可见 / 稳定 / 可接收事件 / 未禁用 / 可编辑），
   不满足就自动等待并重试，而不是把失败当结果返回。
2. **用语义身份，不用坐标**。坐标是快照，语义身份（role + name + 结构路径）可以重新解析。
3. **默认走可信输入**。合成事件（`dispatchEvent`）在真实站点上等于没发生。

## 1. 实测缺陷 → 设计规则（2026-11-13，抖音/B站/知乎实机）

| 实测现象 | 证据 | 对应规则 |
|---|---|---|
| `snapshot mode=text` 在三个 SPA 上恒返回空 | `nodeCount` 1822~3278，`content: null`、`returnedLines: 0` | R6 文本抽取改走可工作路径 |
| `locate` 的 `inViewport` 恒 `null`（显式请求亦然） | `fields:["inViewport"]` 仍 null | R1 可行性判定必须可观测 |
| 截图 1325×1135 vs locate 1060×908，DPR=1.25 未标注 | 同页两次调用 | R4 坐标系必须显式 |
| 自动播放后同一元素 `y=1471 → y=592`，`pointer_click` 报 `stale_element_reference` | 抖音 feed | R2 + R3 |
| `press` 的 DOM 路径用 `el.dispatchEvent(new KeyboardEvent(...))` | `WebView2DomClient.cs:793` | R5 可信输入 |
| `press` 无法无目标发按键 | `locator is required`，`PressAsync(Locator l, ...)` | R5 |
| 同名元素一次返回 5 个，无区分依据 | 5 个 `feed-comment-icon` | R3 |

## 2. 业界对标（2026-11 检索）

- **Playwright 的 actionability checks** 是这一层的标准答案：
  每次动作前检查 *visible / stable / receives events / enabled / editable*，全部通过才动手，
  否则自动等待重试。它明确把「元素稳定」（连续两帧包围盒不变）作为一个独立判据——
  这正是我们被自动播放打断的那一类。
- **Stagehand（为 agent 而生的浏览器驱动）** 的关键取舍是**把运行时放进浏览器**（扩展形态）：
  同等任务比 Playwright 快约 2 倍、token 少约 80%（官方对比表），并提供
  *self-healing actions*、深层 iframe / closed shadow DOM 定位、域名白名单、OTel。
  值得借鉴的是**减少往返**，而不是它的具体实现。
- **Playwright MCP** 用**无障碍快照 + ref**，不需要视觉模型——与我们现有 `outline` 模式同源。
  它的固有代价是 **ref 来自「上一次快照」**，所以 stale 是设计内生的，必须靠"重定位"而不是"防过期"。
- **Browser Use** 走 DOM + 截图双通道、默认开视觉。适合未知路径的探索，成本高。

结论：**我们要补的是 Playwright 的判定层 + Stagehand 的往返合并，而不是换成另一个框架。**

## 3. 目标架构

```
Agent
  │  browser_act(spec)            ← 会话级批处理：一个 spec = 一串步骤
  ▼
动作层（判定 + 重试 + 回执）
  │  resolve(identity) → 可行性检查 → 动作 → 复检
  │    ├─ identity：role+name+结构路径（可重定位）
  │    └─ 不满足 → 等待并重试（预算内），超时给出「卡在哪一条判据」
  ▼
驱动层
  │  native（CDP Input.*，唯一可信输入）
  │  dom（仅在 native 不适用时，且必须显式声明）
  ▼
页面
```

## 4. 五条改造（按 ROI）

### R1 动作可行性判定（P0，收益最大）

新增 `ActionabilityCheck`：`visible` / `stable`（两次采样包围盒一致）/ `receivesEvents`
（`document.elementFromPoint` 命中自身或后代）/ `enabled` / `editable`。
**不满足不报错，先等**；超出预算才失败，且回执必须写明“卡在第几条判据、等了多久”。

这条同时修掉：`stale_element_reference`、点偏、点在遮罩上、输入框还没渲染。

### R2 语义身份取代裸 ref（P0）

`ref` 只保留为**会话内句柄**；对外暴露可重定位的 `identity`：
`{role, name, nth, framePath, pathHash}`。动作前用 identity 重新解析，解析失败才回落到 ref。

Playwright MCP 的教训：ref 来自上一次快照，天然会过期；把"防过期"改成"能重新找到"。

### R3 补全观测事实（P0，且成本最低）

`locate` / `snapshot` 的返回体里**无条件**带：
`viewport {width, height, devicePixelRatio}`、每个元素的 `inViewport`、
以及明确的坐标空间声明（`coordinateSpace: "css-viewport"`）。

没有这三个数，调用方无法判断“要不要滚”“点哪里”。这是今晚所有坐标问题的根源。

### R4 文本抽取走可工作路径（P1）

`snapshot mode=text` 在 SPA 上失效，但 `locate {kind:css, value:body}` 的 `name` 字段
能拿到整页 innerText（实测）。新增 `browser_read`：
优先返回**语义内容块**（正文/评论/列表），回退到 body innerText，
并如实标注 `source: "content-blocks" | "body-inner-text"`。

### R5 输入一律可信（P0，已部分完成）

- 已改：`press` 默认 `input_mode=native`（`d731c23`）。
- 待改：`press` 允许无 locator（打到当前焦点），需要四层改动：
  契约 `RequiresLocator` → DesktopSurface → `WebView2BrowserPage.PressAsync` 无目标重载 → 工具门禁。
- 待改：DOM 路径用于 `fill/type` 时，必须用 `beforeinput/input` 事件序列，
  且不能只写 `value`（React/Draft.js 不认）。今晚实测 Draft.js 只有走真实输入才激活。

### R6 往返合并（P2）

`browser_act(spec)`：一个调用里跑 `scroll → click → waitFor(selector) → read`，
逐步返回回执。抖音“打开视频→读评论”目前要 5~6 次工具调用；合并后 1 次。
这是 Stagehand 用运行时内置换来的收益，我们用批处理近似。

## 5. 验收标准（可判定）

1. **能取红**：对每个判定项注入变异（例如把 `stable` 恒置 true），必须让对应用例红。
2. 抖音 feed 自动播放场景下，`click(identity=评论图标)` 连续 10 次成功率 ≥ 9/10。
3. 任何交互失败的回执必须包含：`failedCheck`、`attempts`、`waitedMs`、`hint`。
4. `locate` 返回必含 `viewport` 与 `inViewport`，缺一项即测试红。
5. `press` 不传 locator 时打到焦点元素（用真实站点快捷键验证，而非只验参数）。

## 6. 明确不做

- 不引入 Playwright/Puppeteer 作为运行时依赖：登录态在 WebView2 里，换引擎等于丢用户现场。
- 不做视觉坐标点击作为主路径：DOM 语义定位在 SPA 上更稳；视觉是 `pointer_*` 的兜底。
- 不追 self-healing 的模型侧策略：先把确定性的判定层补齐，再谈学习式修复。
