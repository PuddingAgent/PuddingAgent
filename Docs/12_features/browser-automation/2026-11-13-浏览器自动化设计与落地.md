# 浏览器自动化设计与落地

## 0. 结论先行

现有工具**不是缺功能，是缺「动作可行性判定」**。七条实测缺陷里有五条同源：
**在动作发出前，没有确认「目标现在真的可以被点/被输入」**。

三条设计原则：

1. **先判定，再动作**。每次交互前跑一组可行性检查（可见 / 稳定 / 可接收事件 / 未禁用 / 可编辑），
   不满足就自动等待并重试，而不是把失败当结果返回。
2. **用语义身份，不用坐标**。坐标是快照，语义身份（role + name + 结构路径）可以重新解析。
3. **默认走可信输入**。合成事件（`dispatchEvent`）在真实站点上等于没发生。

## 1. 实测缺陷 → 设计规则（2026-11-13，抖音/B站/知乎实机）

| 实测现象 | 证据 | 对应规则 |
|---|---|---|

| `locate` 的 `inViewport` 恒 `null`（显式请求亦然） | `fields:["inViewport"]` 仍 null | R1 可行性判定必须可观测 |
| 截图 1325×1135 vs locate 1060×908，DPR=1.25 未标注 | 同页两次调用 | R4 坐标系必须显式 |
| 自动播放后同一元素 `y=1471 → y=592`，`pointer_click` 报 `stale_element_reference` | 抖音 feed | R2 + R3 |
| `press` 的 DOM 路径用 `el.dispatchEvent(new KeyboardEvent(...))` | `WebView2DomClient.cs:793` | R5 可信输入 |

## 2. 业界对标（2026-11 检索）

- **Playwright 的 actionability checks** 是这一层的标准答案：
  每次动作前检查 *visible / stable / receives events / enabled / editable*，全部通过才动手，
  否则自动等待重试。它明确把「元素稳定」（连续两帧包围盒不变）作为一个独立判据——
  这正是我们被自动播放打断的那一类。
- **Stagehand（为 agent 而生的浏览器驱动）** 的关键取舍是**把运行时放进浏览器**（扩展形态）：
  同等任务比 Playwright 快约 2 倍、token 少约 80%（官方对比表），并提供
  *self-healing actions*、深层 iframe / closed shadow DOM 定位、域名白名单、OTel。
  值得借鉴的是**减少往返**，而不是它的具体实现。
- **Playwright MCP** 用**无障碍快照 + ref**，不需要视觉模型——与我们现有 `outline` 模式同源。
  它的固有代价是 **ref 来自「上一次快照」**，所以 stale 是设计内生的，必须靠"重定位"而不是"防过期"。
- **Browser Use** 走 DOM + 截图双通道、默认开视觉。适合未知路径的探索，成本高。

结论：**我们要补的是 Playwright 的判定层 + Stagehand 的往返合并，而不是换成另一个框架。**

## 3. 目标架构

```
Agent
  │  browser_act(spec)            ← 会话级批处理：一个 spec = 一串步骤
  ▼
动作层（判定 + 重试 + 回执）
  │  resolve(identity) → 可行性检查 → 动作 → 复检
  │    ├─ identity：role+name+结构路径（可重定位）
  │    └─ 不满足 → 等待并重试（预算内），超时给出「卡在哪一条判据」
  ▼
驱动层
  │  native（CDP Input.*，唯一可信输入）
  │  dom（仅在 native 不适用时，且必须显式声明）
  ▼
页面
```

## 4. 五条改造（按 ROI）

### R1 动作可行性判定（P0，收益最大）

新增 `ActionabilityCheck`：`visible` / `stable`（两次采样包围盒一致）/ `receivesEvents`
（`document.elementFromPoint` 命中自身或后代）/ `enabled` / `editable`。
**不满足不报错，先等**；超出预算才失败，且回执必须写明“卡在第几条判据、等了多久”。

这条同时修掉：`stale_element_reference`、点偏、点在遮罩上、输入框还没渲染。

### R2 语义身份取代裸 ref（P0）

`ref` 只保留为**会话内句柄**；对外暴露可重定位的 `identity`：
`{role, name, nth, framePath, pathHash}`。动作前用 identity 重新解析，解析失败才回落到 ref。

Playwright MCP 的教训：ref 来自上一次快照，天然会过期；把"防过期"改成"能重新找到"。

### R3 补全观测事实（P0，且成本最低）

`locate` / `snapshot` 的返回体里**无条件**带：
`viewport {width, height, devicePixelRatio}`、每个元素的 `inViewport`、
以及明确的坐标空间声明（`coordinateSpace: "css-viewport"`）。

没有这三个数，调用方无法判断“要不要滚”“点哪里”。这是今晚所有坐标问题的根源。

### R4 文本抽取走可工作路径（P1）

`snapshot mode=text` 在 SPA 上失效，但 `locate {kind:css, value:body}` 的 `name` 字段
能拿到整页 innerText（实测）。新增 `browser_read`：
优先返回**语义内容块**（正文/评论/列表），回退到 body innerText，
并如实标注 `source: "content-blocks" | "body-inner-text"`。

### R5 输入一律可信（P0，已部分完成）

- 已改：`press` 默认 `input_mode=native`（`d731c23`）。
- 待改：`press` 允许无 locator（打到当前焦点），需要四层改动：
  契约 `RequiresLocator` → DesktopSurface → `WebView2BrowserPage.PressAsync` 无目标重载 → 工具门禁。
- 待改：DOM 路径用于 `fill/type` 时，必须用 `beforeinput/input` 事件序列，
  且不能只写 `value`（React/Draft.js 不认）。今晚实测 Draft.js 只有走真实输入才激活。

### R6 往返合并（P2）

`browser_act(spec)`：一个调用里跑 `scroll → click → waitFor(selector) → read`，
逐步返回回执。抖音“打开视频→读评论”目前要 5~6 次工具调用；合并后 1 次。
这是 Stagehand 用运行时内置换来的收益，我们用批处理近似。

## 5. 验收标准（可判定）

1. **能取红**：对每个判定项注入变异（例如把 `stable` 恒置 true），必须让对应用例红。
2. 抖音 feed 自动播放场景下，`click(identity=评论图标)` 连续 10 次成功率 ≥ 9/10。
3. 任何交互失败的回执必须包含：`failedCheck`、`attempts`、`waitedMs`、`hint`。
4. `locate` 返回必含 `viewport` 与 `inViewport`，缺一项即测试红。
5. `press` 不传 locator 时打到焦点元素（用真实站点快捷键验证，而非只验参数）。

## 6. 明确不做

- 不引入 Playwright/Puppeteer 作为运行时依赖：登录态在 WebView2 里，换引擎等于丢用户现场。
- 不做视觉坐标点击作为主路径：DOM 语义定位在 SPA 上更稳；视觉是 `pointer_*` 的兜底。
- 不追 self-healing 的模型侧策略：先把确定性的判定层补齐，再谈学习式修复。
## 7. 已修根因（2026-11-13 晚）

### 7.1 输入侧：两个筛选参数从未到达 DOM 脚本

`WebView2DomClient.ToPayload` 只发 `kind/value/name/exact/nth/hasText`，
脚本读的 `locator.includeHidden` 与 `locator.inViewportOnly` 恒为 `undefined`。
另有两处同类漏传：`BrowserRuntimeDesktopSurface.ToRuntimeLocator` 丢 `InViewportOnly`；
桥接线上 `BrowserLocatorDescriptor` 两个字段都缺。

- 实测：`in_viewport_only=true` 在 908px 视口返回 `y=-346.6` 与 `y=1471.4`。
- 修复：`19574ae`（三处边界全部补通）；回归测试 `92aed3d`。

### 7.2 输出侧：结果描述符漏掉三个字段

`BrowserWorkspaceController.ToElementDescriptor` 只映射 10 个字段，
漏 `Value` / `SelectedValues` / `InViewport`。
桥接路径早已修过同一处（`BridgeBrowserCapabilitySurface.cs` 的注释写着「只是这里漏传」），
Desktop 路径没有同步。

- 后果：`expect_value` 永远只能报 `unverified`；`inViewport` 恒 `null`。
  上层于是只能另开 CDP 通道自验输入，这正是本文件 §1 中多条缺陷的共同来源。
- 修复：`0b570b6`。

### 7.3 教训

**同一份事实有两份映射，只修一份等于没修。** 输入侧三处、输出侧两处，
每一处单独看都是"少写一行"，合起来让整个可见性/输入回执链路失效。
新增字段时，两端的映射必须同时改，并且要有能取红的用例钉住。

## 8. 真正的边界是 protobuf（2026-11-13 22:32）

§7 修的是 JSON 桥接线与一个归档项目，都不是活路径。活着的链是：

```
BrowserLocateTool
  → CapabilityBroker.WireMapping.Encode  → Proto.LocatorSpec
  → DesktopConnection.Mapping.Decode     → DesktopLocator
  → BrowserRuntimeDesktopSurface → WebView2DomClient.ToPayload → 页面脚本
```

`LocatorSpec` 原本只有 6 个字段，`include_hidden`/`in_viewport_only` 根本没有定义；
`ElementRef` 缺 `value`/`selected_values`/`in_viewport`。缺字段与显式 false 无法区分，
所以失效是静默的。

- 修复：`3b77643`（两侧同时补，`value`/`in_viewport` 用 proto3 `optional` 表达 presence）
- 守护测试：`f5fdc9d`（含负对照——不写字段时必须为 false，避免断言恒真）

**教训**：定位"改了没生效"时，先确认改的是不是**活的那条边界**。
本项目同一事实有四套映射（DOM 脚本 / JSON 桥 / protobuf / 归档项目），
只有 protobuf 那条在运行时被加载。

## 10. 新发现：未知参数被静默忽略

`include_hidden` / `in_viewport_only` 是 **`locator` 对象的属性**，不是工具顶层参数。
作为顶层参数传入时被宿主静默丢弃，既不报错也不告警，于是再次表现为"代码没修好"。

这与本文件记录的其它缺陷同源：**失败必须可见**。
建议后续在工具参数绑定层做 fail-closed——未知参数直接拒绝，
或在回执里列出被忽略的参数名。

## 11. C4 精确根因：两处丢弃交互后观测（2026-11-13 23:30 核实）

`WebView2BrowserPage.ExecuteInteractionAsync`（`Source/PuddingBrowser.WebView2/WebView2BrowserPage.cs:1267`）
的签名是 `Task`，且内部显式丢弃返回值：

```csharp
_ = await _dispatcher.InvokeAsync(
    () => WebView2DomClient.InteractAsync(webView, PageVersion, _refScopeToken, action, locator, value, deltaX, deltaY, ct), ct);
```

`WebView2DomClient.InteractAsync` 本可返回 `BrowserElementInfo?`（含 value / checked / selectedValues），
驱动层用 `_ =` 把它丢掉了。原生路径 `ExecuteNativeAsync` 同文件 1301 行同样是 `Task`，
动作后不重新 `QueryAsync`，因此也没有回读值。

后果链条：
1. 驱动拿不到动作后的元素状态 →
2. surface 只能回传动作**之前**解析的元素（`IsPreActionObservation` 标记）或空 →
3. `BrowserInteractTool` 的 `ObservedValue` 恒为 null →
4. `expect_value` 永远判不出 verified（`35c7329` 只把它从「误报 failed」改成「如实报 unverified」）

修法（修正 2026-11-13 23:40：上一版说“改 ExecuteInteractionAsync 签名”，那会牵动 IBrowserPage 接口；实际有更小的改法）。

问题不在驱动是否返回元素，而在 surface 用的是**动作前**解析的句柄：

```csharp
// BrowserRuntimeDesktopSurface.InteractCoreAsync（约 1040 行）
handle = await browserPage.QueryAsync(locator, cancellationToken);   // ← 动作前
...
var scrollOutcome = await PerformAsync(...);                         // ← 动作
...
element = MapHandle(handle).Value;                                   // ← 仍是动作前的观察
```

`DesktopElementRef.IsPreActionObservation` 默认 false，而 surface 从不置 true，
所以上层把旧观察当成新观察——`BrowserInteractTool` 里那句
`element is { IsPreActionObservation: false }` 的判断本来就是为这种情况准备的，只是没人去设置它。

**最小改法（单文件约 15 行，不动任何接口）**：在 `PerformAsync` 之后重新解析一次：

```csharp
var observationIsPreAction = false;
if (locator is not null)
{
    var afterHandle = await browserPage.QueryAsync(locator, cancellationToken).ConfigureAwait(false);
    if (afterHandle is not null) handle = afterHandle;
    else observationIsPreAction = true;   // 元素被替换/移除：如实报“不可观测”
}
element = mapped.Value with { IsPreActionObservation = observationIsPreAction };
```

收益：`ObservedValue` 有真值 → `ValueObservable=true` → `expect_value` 首次可达 verified。
重新解析失败时 `IsPreActionObservation=true` → 上层判 unverified（不是用旧值假失败）。

验收判据：type "cd"（初值 ab）后传 `expect_value=abcd`，回执应为 verified；
故意使用会改变 DOM 结构的动作，应得到 unverified 而不是 failed。

**未做**：代码未动，需重启后验收。

## 13. R1 剩余三件：实施方案与前置风险（2026-11-14 00:16）

### 13.1 前置探针（必须先做，否则改动可能全盘失效）

`InteractScript` 是**同步 IIFE**：`(() => { ... })()`，直接返回结果对象。
`stable` 要等两帧，只能改成 `(async () => { ... })()` 并 `await`。

风险：WebView2 的 `ExecuteScriptAsync` 对 Promise 的处理依赖运行时版本 ——
若不 await，会拿到 `{}`，**所有交互都会静默失效**。这种"改了之后全线坏掉"的失败
在深夜无法验证时不能冒险。

因此第一步是一个**只读探针**（不动产品代码）：

```
1. navigate 到 about:blank
2. 执行 (async () => 42)()
3. 期望拿到 42 而不是 {}
```

拿到 42 才继续；拿到 `{}` 就说明只能走别的路（例如在 C# 侧做两次 locate 比较 bbox，
用 Task.Delay 隔帧，完全不碰 JS）。

### 13.2 三条缺口的实现

| 缺口 | 改法 | 是否需 async |
|---|---|---|
| `editable` | 写操作前判 `el.isContentEditable \|\| (!el.disabled && !el.readOnly && ['INPUT','TEXTAREA','SELECT'].includes(el.tagName))`，不满足报 `browser_element_not_editable` | 否，同步可加 |
| `stable` | 连续两帧 `getBoundingClientRect()` 完全相等；不等则等到相等或超时 | **是**（或改在 C# 侧用两次 locate 实现） |
| 自动重试 | 建议放在 **C# 侧**（`WebView2BrowserPage.InteractAsync` 外层），不在 JS 内循环：重试次数/间隔可配、可统一记 `attempts`/`waitedMs`，且不把页面脚本变成状态机 | 否 |

`stable` 的备选实现（不碰 JS）：C# 侧连续两次 `QueryAsync` 取 bbox，间隔 16–32ms，
两次相同才派发。代价是多一次往返，但**零 JS 风险**，且与 13.1 的探针结果解耦。
优先推荐这条。

### 13.3 验收判据（都能取红）

1. `editable`：对 `<div>` 执行 fill → 必须报 `browser_element_not_editable`（当前会静默无效）
2. `stable`：对正在播放动画的元素点击 → 要么等到稳定后成功，要么报 `browser_element_unstable`，**不得**点到漂移后的位置
3. 重试：失败回执必须含 `attempts` 与 `waitedMs`；把重试次数设为 0 时断言行为退回"立即失败"

### 13.4 本轮未做

代码未动。原因是 13.1 的探针需要真实 WebView2 页面，而当前没有重启时机；
在未验证 Promise 支持的情况下改脚本，风险收益不成立。
