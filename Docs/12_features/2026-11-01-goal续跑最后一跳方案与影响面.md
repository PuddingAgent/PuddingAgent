# 续跑最后一跳：把队列里的请求变成「真的再跑一轮」

> 前置阅读：`Docs/12_features/2026-11-01-Super-agent架构与goal模式差距对照.md` §8（Codex 裁定选方案 3，并给出进入 2 的四条判据）。

## 1. 现状：断在哪

```
✓ GoalRegistry         按会话存目标状态与账本
✓ GoalLoopDecider      统一决策（Continue/Complete/Yield/Stop/Block）
✓ GoalLoopDecisionHook 挂在 OnLoopCompleteAsync，观测期只记日志
✓ GoalOpenItemsReader  真实待办数（ITodoStore → CompletedAtUtc 计数）
✓ RepeatedActionGuard  真实空转信号（toolName+argsJson 连续重复）
✓ GoalContinuationQueue 决策说继续 → 入队
✗ 消费者               没人把请求取出来再跑一轮
```

共 10 个组件、101 条测试，全部是纯逻辑。**缺的是一个宿主侧的接线点。**

## 2. 可用的锚点（已现场核实）

`OnLoopCompleteAsync` 由执行服务在两处分发：

| 文件 | 行 | 场景 |
|---|---:|---|
| `Source/PuddingRuntime/Services/AgentExecution/AgentExecutionService.Buffered.cs` | 2452 | 缓冲模式 |
| `Source/PuddingRuntime/Services/AgentExecution/AgentExecutionService.Streaming.cs` | 2004 | 流式模式 |

两者都在循环结束后 `await FireHooksAsync(h => h.OnLoopCompleteAsync(loopCtx, reply, reason, ct))`。
**注意：这是两条独立路径**，任何改动都必须两边一致，否则两种模式行为分叉。

## 3. 三个候选实现点

### A. 在钩子内直接重入（否决）

钩子拿到 `AgentLoopContext` 后自己再调一次执行入口。

**否决理由**：钩子是「观测 + 轻量改写」的扩展点，让它驱动执行会让「谁在驱动这个会话」
无法归因；且 `AgentLoopContext` 不携带执行所需的完整输入（模型、工具集、取消令牌链），
硬凑会绕过既有的取消与配额路径。

### B. 在执行服务内消费队列（推荐，但要你点头）

循环结束、所有 hook 跑完之后，加一处：

```
if (stopReason == Done && queue.TryTake(sessionId) is { } request)
    → 发起下一轮（复用既有的「再来一轮」路径，如果存在）
```

**影响面**：

| 项 | 说明 |
|---|---|
| 改动文件 | `AgentExecutionService.Buffered.cs` + `.Streaming.cs`（两处，逻辑一致） |
| 新增依赖 | `GoalContinuationQueue`（单例），需在 DI 注册 |
| 行为变化 | **仅在队列非空时**发生；无目标/无请求时完全等价于现状 |
| 风险 | 死循环（决策持续说继续）→ 由 `GoalRoundLedger` 轮次上限 + `RepeatedActionGuard` 兜底 |
| 可回滚 | 单一开关 `PUDDING_GOAL_CONTINUE=1`，默认关；关掉即恢复原状 |

**必须先确认的一件事**：执行服务里是否已存在「再来一轮」的内部入口（例如递归调用自身或
一个 `RunTurnAsync`）。如果不成立，B 就退化成「在服务里新造一个循环」——那是重写，不是接线，
必须重新评估。

### C. 由宿主的心跳/调度器消费（次选）

不动执行循环，由外层调度在会话空闲时 `TryTake` 并触发一次新执行。

**代价**：需要心跳能定位到「该跑哪个会话」，这层能力当前不由本 Agent 掌握；
且延迟从「立刻」变成「下个调度周期」。

## 4. 我的建议

**先做一件事：确认 B 的前提是否成立**（执行服务内部有没有可复用的「再来一轮」入口）。

- 成立 → 走 B，改动小、语义清楚、可回滚。
- 不成立 → 停在 C，或退回「观测期」继续攒数据，**不硬造循环**。

## 5. 验证与回滚

```
① 单测：队列消费逻辑与「无请求时行为不变」的等价性
② 集成：起一个真实会话，目标设 2 轮上限，观察是否恰好续跑 1 次后停止
③ 变异：把 TryTake 改成常返回 null → 必须回到「只跑一轮」的旧行为
④ 回滚：关开关 + 重启，逐项核对 grep 与测试
```

**③ 是这次最关键的一条**：它同时验证「新路径生效」与「关闭后完全等价」，
缺任何一个都不能说这跳接好了。

## 6. 需要你点头的部分

- 动 `AgentExecutionService`（主干）—— 即使有开关，也是主干改动；
- 改完必须重启宿主才生效（`bootstrap_reboot`，破坏性）。

在你说「改」之前，我只做 §4 的第一步（只读确认），不动代码。

## 7. §4 第一步的实测结果（2026-11-01 22:50，只读确认）

**结论：B 的前提成立 —— 执行服务内部已有一个按轮次推进的循环，不需要新造。**

证据（`AgentExecutionService.Buffered.cs`，共 2557 行）：

| 行 | 内容 | 含义 |
|---:|---|---|
| 46 | `public async Task<RuntimeDispatchResult> ExecuteAsync(` | 唯一对外入口 |
| 1647 | `if (round < maxRounds - 1)` | **循环内已有 round 推进** |
| 2247–2253 | `// 最后一轮 CONTINUE → MaxRoundsReached` | 已存在「本轮要求继续但轮次用尽」的分支 |
| 1850 / 2255 / 2432 | `FireHooksAsync(h => h.OnMaxRoundsReachedAsync(...))` | 轮次耗尽另有专门钩子 |

⇒ 续跑不需要「在服务里新造循环」，只需要在**已有的停止判定点**上多问一句：

```
原本：没有工具调用 / 模型说完成 → 结束
改后：结束前问一次 GoalLoopDecider
      Continue → 不结束，继续下一轮（并把轮次计入 GoalRoundLedger）
      其他     → 按原逻辑结束
```

### 这改变了风险评级

| | 原评估（新造循环） | 实测后（复用既有循环） |
|---|---|---|
| 改动量 | 大（重写控制流） | 小（一个判定点 + 一行 `continue`） |
| 风险 | 高 | 中：仍需保证「关闭开关后与现状逐字等价」 |
| 验证方式 | 难 | 易：比对开关开关两种状态下的 round 数与 stopReason |

### 仍需注意的两点

1. **两条执行路径**（Buffered 2452 / Streaming 2004）都要看，否则模式间行为分叉；
2. 既有分支 `round == maxRounds - 1` 已经会强制 `MaxRoundsReached` ——
   续跑必须走 `GoalRoundLedger` 的额度，**不能绕过它**，否则两套上限会打架。

## 8. 下一步（等你点头）

改动收敛成一句话：**在既有停止判定点插入 `GoalLoopDecider`，Continue 时 `continue` 而非 `break`。**
