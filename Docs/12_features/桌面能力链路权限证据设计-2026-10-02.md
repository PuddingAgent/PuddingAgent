# 桌面能力链路的**权限证据**设计（审计发现 → 可施工方案）

## 审计发现（本次能力通道工作的副产物）

能力调用链路今天有四道门，但**审批证据不在其中**：

| 门 | 位置 | 校验什么 |
|---|---|---|
| ① 协商 | 握手（`DesktopCapabilityNegotiation.Validate`） | Desktop 是否**声明**了该能力、版本是否匹配 |
| ② 准入 | `DesktopService.ValidateAdmission` + `DesktopCapabilityPolicy` | 调用方信任级别是否允许该能力、目标页是否已注册 |
| ③ 目标/版本 | Desktop 侧 | 页面目标是否存在、`PageVersion` 是否固定且未过期 |
| ④ 工具声明 | `[Tool(permission: ToolPermissionLevel.Low)]` | **仅声明**，由 Tool Runtime 在执行前决定是否要审批 |

**缺口**：第 ④ 道门的**审批结论**（是否批准、由谁批准、批的是哪一次调用）**不进入能力链路**。
能力接缝（窄端口 / `IDesktopUiSurface`）只认 `DesktopCallContext`（实例 ID + OperationId + 期限），
因此**任何能拿到接缝的进程内代码**都可以发起一次 `Mutating | HasSideEffects` 的能力调用，
而不需要任何审批证据。

## 真实暴露面（诚实定性）

**今天是潜在暴露，不是活跃漏洞**：

- 生产里唯一调用方是七个 Browser 工具，它们本身受 Tool Runtime 的审批链约束；
- 接缝是**进程内 DI 接缝**，不对外暴露网络入口；
- 也就是说：这一项是**纵深防御 / 加固**，价值在于"将来新增调用方时不会悄悄绕过审批"，
  而不是"现在有人在攻击"。

⇒ 因此方案必须**可分级落地**，且第一级不能改变任何现有行为。

## 为什么不把校验放到 Desktop 侧

Desktop 看不到 Core 内部的审批结论。在 Desktop 侧唯一能做的是继续收紧"哪个信任级别允许哪个能力"（已有），
把 Core 的审批信息**放上线缆**则意味着：① 线缆上出现凭据类字段（违反"无凭据字段"的既有约束，
见 `CapabilityEndpoint` 的设计说明）；② Desktop 无法验证 Core 内部审批的真伪（等于自证）。
⇒ 结论：**证据留在进程内、在 Core 侧接缝处校验**。

## 候选方案

| 方案 | 结论 |
|---|---|
| A. 线缆携带审批 token | ✗ 不采纳：线缆引入凭据语义，且接收方无法验证签发方内部状态 |
| B. **Core 侧接缝校验**（`DesktopCallContext` 带权限证据；路由端口在派发前校验） | ✅ 推荐：进程内、零线缆改动、可与既有准入叠加 |
| C. 收紧 Desktop 策略表 | ✗ 不同维度（信任级别 ≠ 某次调用是否获批），且会误伤合法调用 |

## 推荐方案 B 的三阶段落地

**第一阶段（观察期，零行为变化）**

1. Tool Runtime 在进入工具前，把本次调用的审批结论写进执行上下文
   （`ToolExecutionContext` 已有**调用身份 id**，但**没有**审批字段 —— 需新增）；
2. 工具把这些信息交给 `IDesktopCapabilityCallContextFactory`，由它写入 `DesktopCallContext`
   的**进程内字段**（明确标注：**不上线缆**）；
3. 路由端口在派发前**只记录不拒绝**：缺证据时打一条遥测/日志；
4. 门禁：既有 800 用例全绿 + 新增"缺证据仍可调用"的观察期用例。

**第二阶段（对副作用类强制）**

5. 对 `HasSideEffects | RequiresTrustedContext` 的能力：缺证据或证据与本次调用不匹配 ⇒
   **fail closed**（返回 `Unauthorized` 类错误，不派发）；
6. 门禁：新增"缺证据被拒""证据不匹配被拒""证据齐备通过"三类用例；
   集成用例覆盖七个工具的真实路径（它们必须带上证据）。

**第三阶段（全量）**

7. 只读能力也要求证据；把"无证据"从"允许 + 遥测"改为"拒绝"；
8. 门禁：把第一阶段的观察期用例改为拒绝用例（**同一条用例的期望值翻转**，可追溯）。

## 施工现状（2026-10-02 更新，供接手者直接对齐）

| 阶段 | 状态 | 落点 |
|---|---|---|
| 证据类型 + 可选携带位 | ✅ | `ToolPermissionEvidence`；`ToolExecutionContext.PermissionEvidence`；`DesktopCallContext.PermissionEvidenceSummary`（**进程内**，不上线缆） |
| 生产者 | ✅ | `ToolInvocationService.EvaluatePermissionEvidence`：guard 允许 ⇒ `allowed`；拒绝 ⇒ `denied`；**未配置 guard ⇒ `not-required` + `Source=no-guard-configured`** |
| 携带者 | ✅ | `BrowserAgentToolBase` 的每次调用作用域（AsyncLocal）+ 工厂的带证据重载 + 七个工具 11 处调用点 |
| 观察者 | ✅ | 路由端口的 `MissingEvidenceCalls` 计数 + `GET /api/admin/transport/status` 的 `missingEvidenceCalls` 字段 |
| **第二阶段闸门** | ✅ | 路由端口的 `RejectWithoutEvidence<T>`：副作用类能力在证据缺失/`denied` 时返回 `Unauthorized`；只读能力不受影响 |
| 第三阶段（全量 + 会话层） | ⬜ **有意暂缓** | 见下 |

### 为什么"会话层闸门"与"第三阶段全量"被有意暂缓

- **会话层闸门**（在 `DesktopSession` 上也判一遍）：能多拦的只有"进程内代码绕过组合根直接解析 broker 会话"
  这一路径 —— 而那已超出本设计的威胁模型（进程内代码同样可以直接调 UI 侧接缝，闸门无法穷尽）。
  实测代价却不小：仓库里已有 **7 处测试直接调用会话的副作用方法**（`CapabilityChannelHostTests`、
  `TrustedCallerAuthorizerOverTheWireTests`），全部要改夹具。⇒ 判定：**收益低、噪音大，暂缓**；
  若将来出现真实调用方，再按同一判定补上。
- **第三阶段全量**：把只读能力也纳入。只读能力不改变状态，拦住它们的价值远低于其带来的误伤风险
  （例如运维/诊断代码直接读页状态）；且当前闸门已覆盖全部六条副作用入口。
  ⇒ 判定：**在出现明确需求前不做**，而不是为了"阶段完整"而做。

### 缺证据计数的用法

`missingEvidenceCalls > 0` 即表示"有调用方在没有工具层证据的情况下派发了副作用能力"。
干净窗口应为 0；外部验收时它同时是**闸门是否被触发**的观测点（被拒时计数 +1，
`denied` 被拒时**不**计数 —— 有证据只是不允许，不属于"缺失"）。

## 非目标

- 不改线缆/proto（`DesktopCallContext` 的新字段**不上线缆**，映射测试应断言它不在其中）；
- 不替代 Desktop 侧的目标/版本校验（③ 仍在）；
- 不改变七个工具对外可见的行为（它们的审批路径不变）；
- 不引入"绕过审批的后门开关"。

## 未决问题（施工前需读代码确认）

1. 审批结论的确切存放位置与形状：需读 `ToolApprovalService` / `ApprovalController` / `ToolInvocationService`
   （已知存在 `ApprovalId` 与审批记录，但"某次工具调用是否已获批"的查询面尚未核实）；
2. 七个工具当前 `permission: ToolPermissionLevel.Low` ⇒ 是否本来就不需要人工审批
   （若 Low 免审批，则证据是"免审批"这一结论本身，仍需可验证地携带）；
3. 子代理/委派调用（`ConfigurationAgentInstanceId` ≠ `AgentInstanceId`）时证据应绑定哪一个身份。

## 验证方式（每阶段独立）

- 单元：证据缺失/不匹配/齐备三种情形；
- 集成：七个工具经真实组合根路由的路径（`PuddingHost.Tests` 已有该类用例）；
- 遥测：第一阶段的"缺证据"计数（可复用 `GET /api/admin/transport/status` 的形态，
  新增一个同级的只读出口，而不是塞进那个端点）；
- 回归：全量九套件（当前基线 **800 用例**）。
