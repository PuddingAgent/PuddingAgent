# Harness 层行为校准：让工具自己提醒「你用法错了」

## 0. 一句话

模型自己复盘自己的低级错误是不可靠的（同一晚我把 `cmd` 的 `&` 当并行、把 `tail` 用在 cmd 里、
用 `python` 结果撞到商店占位符）。这些错误**在 Harness 层是可判定的**：命令字面量 + 平台 + 结果，
不需要模型觉悟。所以把判据下沉成规则，在工具返回处贴一行提示。

## 1. 实证：今晚真的发生过什么

| 现象 | 代价 | Harness 本可以怎么拦 |
|---|---|---|
| `(A) & (B) & (C)` 以为并行 | 30 分钟串行空跑 | 检测 `shell=cmd` + 多个 `&` 分隔的 `dotnet test` ⇒ 一行提示 |
| `dotnet test` 未带 `--no-build` | 20 分钟耗在构建 | 检测同项目刚构建过 ⇒ 提示加 `--no-build` |
| `python -c` / `python3` | 撞商店占位符 | 字面量即判定 ⇒ 提示 `py -3` |
| `findstr` 搜中文返回空 | 误判「实现里没有」 | 检测 CJK 字面量 ⇒ 提示 findstr 对 UTF-8 无 BOM 恒不命中 |
| `git add -A Source` | 把临时 `.tail.txt` 暂存 | 检测 `-A` + 目标目录内有未跟踪的非源码文件 ⇒ 提示改显式路径 |
| 测试挂住无从下手 | 20 分钟没有任何输出 | 连续超时 ⇒ 提示 `--blame-hang --blame-hang-timeout` |

共同点：**全部是「工具用法」而不是「领域知识」**。领域判断该模型自己扛，用法判断该 Harness 兜。

## 2. 注入点（已读代码核实，不是设想）

| 位置 | 性质 | 适合什么 |
|---|---|---|
| `PuddingToolBase<TArgs>.ExecuteAsync`（`PuddingCore/Tools/PuddingToolContracts.cs:388`） | **所有强类型 tool 的唯一执行入口**，内部已 try/catch 并统一返回 `ToolExecutionResult` | 单次调用后的**后置提示**（首选） |
| `PuddingToolBase<TArgs,TResult>` | 另一条特化基类 | 同上 |
| `IPuddingToolExecutionService.ExecuteAsync` | 更上层统一入口（含策略判定） | **跨 tool / 序列级**判断（重复失败、循环检测） |
| `ToolExecutionResult`（同文件 249 行） | `record`，字段 `Success/Output/Error/ExitCode/Status` | 用 `with { Output = ... }` **纯函数式追加**，不动语义 |

关键约束：追加提示**不得**改 `Success`、不得改 `ExitCode`、不得吞输出。它只是末尾多一行 `NOTE:`。

## 3. 规则目录（按「可判定性」排序，先做能确定判的）

### A. Shell 方言误用
- `tail` / `head` / `grep` / `sed` / `awk` / `wc` 在 `shell=cmd` 下出现
- Bash 变量语法（`$var`、`export X=`）出现在 cmd / pwsh
- PowerShell cmdlet（`Remove-Item`、`Get-ChildItem`、`Select-String`）出现在 cmd
- 一条命令里多个 `&` 串联多个耗时子命令 ⇒ 提示「cmd 的 `&` 是串行，不是并行」

### B. 编码陷阱
- `findstr` + 含 CJK 的字面量 ⇒ 「对 UTF-8 无 BOM 恒不命中；用 python/.NET 直读」
- `Get-Content` 读无 BOM 的 UTF-8 ⇒ 「默认 GBK 解码，用 `[IO.File]::ReadAllLines(..., UTF8)`」

### C. 二进制/别名
- `python` / `python3` ⇒ 「商店占位符，用 `py -3`」

### D. 构建/测试效率
- `dotnet test` 缺 `--no-build` 且该工程刚构建过 ⇒ 提示跳过构建
- 同一测试工程连续 2 次超时 ⇒ 提示 `--blame-hang --blame-hang-timeout <n>s`（今晚实测一次命中挂死测试）

### E. 危险/易错操作
- `git add -A <dir>` 且目录内存在未跟踪的临时产物 ⇒ 提示改显式路径
- `git stash push` 与后续命令挂在同一条 `&&` 链 ⇒ 提示「链断则 pop 不执行，改动会被锁在 stash 里」（今晚真实踩过）

### F. 低效循环（需要短期记忆，属第二档）
- 同一 `(toolId, 参数指纹)` 在窗口内连续失败 ≥3 次 ⇒ 提示「换观测手段」，并给出候选手法
- 同一文件在窗口内被同一 tool 反复读写 ≥N 次 ⇒ 提示可能陷入局部最优

## 4. 三档形态（按实现成本递增）

1. **即时提示**：单次调用后追加一行。零状态、零风险，覆盖 A–E。
2. **重复检测**：进程内环形缓冲记录 `(toolId, argsHash, 成功?, 时长)`，命中 F。需要定义窗口与上限。
3. **周期性统计**：`agent_diagnostics tool_stats` 已有成功率/慢工具数据，Harness 可主动推一条
   「你这个会话里 X 工具失败了 N 次」——把统计变成行动建议，而不是等模型自己去看。

## 5. 边界与风险（必须先定，否则会变成噪声）

- **可关闭**：默认开，但要能一键关（否则某类任务会被无关提示干扰）
- **有配额**：每轮最多 3 条；同一条规则每会话最多提示 3 次（防止刷屏挤占上下文）
- **不改语义**：只追加文本；`Success`/`ExitCode`/`Status` 一律不动
- **必须能取红**：每条规则配「不该提示」的反例；正例反例都要有测试
- **组件独立**：`PuddingToolGuidance` 做成 BCL-only 叶子组件，S1 独立工程 → S2 独立测试 → S3 无宿主验证 → S4 边界断言 → **S5 才接宿主**

## 6. 其他可以顺手做的方向（用户问的「推广开」）

| 方向 | 做法 | 收益 |
|---|---|---|
| **前置而非事后** | 把「方言限制」写进 shell 工具的 descriptor 文本 | 省掉整整一轮错误 |
| **失败可分类** | `ToolExecutionResult.Status` 增 `wrong_dialect` / `encoding_trap` 等约定值 | 模型能区分「我写错了」和「环境坏了」，不再白试 |
| **大输出自动落盘** | 超过 X KB 的 Output 自动写文件 + 只回路径 + 摘要 | 今晚我手工做了十几次 |
| **低效循环告警** | 用已有 `tool_stats` 数据判「同一工具反复失败」 | 直接打断局部最优 |
| **规则命中统计** | 记录每条规则命中次数 | 用数据决定下一条该写哪条规则，而不是凭感觉 |

## 7. 第一步（下一轮实施）

1. S1：新建 `Source/PuddingToolGuidance`（BCL-only），核心是纯函数
   `Evaluate(GuidanceInput) → GuidanceAdvice?`，先实现 A/B/C 三组 5 条规则；
2. S2：`Source/PuddingToolGuidanceTests`，表驱动：每条规则一组「应提示」与「不应提示」；
3. S3：控制台探针跑一遍真实命令字面量，打印判定结果；
4. S4：边界断言（程序集零依赖、无 `Pudding*` 引用）；
5. S5：接入 `PuddingToolBase.ExecuteAsync`，`with { Output = output + note }`，并跑受影响的测试套件。

## 8. 不确定 / 待裁定

- 提示文案用中文还是英文（当前系统提示词中英混排，工具输出多为中文）
- 配额默认值（每轮 3 条是否合适）
- 是否要把规则做成可配置（JSON），还是编译进组件（先编译进，改起来简单）

### 接入方式（最终形态）

没有改 `PuddingToolBase`，也没有在任何工具里加分支 —— 走的是既有 Hook 事件：

```
IAgentLoopHook.OnToolResultTransformingAsync(context, round, toolName, argsJson, result, ct)
```

- **为什么带 `argsJson`**：只看结果判不出「用法错在哪」（cmd 里的 `tail` 命令本身可能已经报错不算成功，
  而 `findstr` 搜中文会安静返回空），必须同时看到调用参数；
- **为什么是新增默认方法**：`OnToolResultAsync` 返回值被丢弃（只读通知），无法追加文本；
  新方法默认实现原样返回，现有 3 个 Hook 零改动；
- **组合与容错**：`FireToolResultTransformersAsync` 按注册顺序串行，后一个看到前一个的输出；
  抛异常或返回 null 只跳过它并保留当前结果 —— Hook 是建议层不是控制层。

### 默认方言必须按工具分流

| 工具 | 默认方言 | 依据 |
|---|---|---|
| `shell`（`shell=auto`） | PowerShell | Windows 上 auto 即 pwsh |
| `terminal_start` / `terminal_execute` | cmd | 终端工具默认 cmd.exe |

默认值搞反会让规则**系统性误报**，比不提示更糟。`shell=auto` 已显式归一化为平台默认。

### 验证（三态）

还原    SHA EE517587… SAME=True → 6/6 复绿
```

## 10. 第二条落地：低效循环检测（2026-11-01）

规则目录里的 F 组（需要短期记忆）已实现：

```
ConsecutiveFailureTracker   线程安全；键含 sessionId；成功即清零；超窗（默认 10 min）视为 0；容量上限 512
RepeatedFailureRule         连续失败 ≥ 3 次 ⇒ 提示「停止微调参数，换观测手段」
```

设计取舍：

- **状态放在组件里、规则保持纯函数**：`GuidanceInput` 增加 `ConsecutiveFailureCount`，
  规则只看这一个数，不自己维护状态 —— 这样规则仍可单测，计数器也可用假时钟单测；
- **键含 sessionId**：跨会话不得串；同一个工具在别的会话里失败不该影响当前会话；
- **成功即清零、过期即清零**：十小时前的失败不该拖累现在，否则「连续」二字失去意义；
- **容量上限 + 惰性淘汰**：长会话不会无限增长。

阈值 3 的理由：1 次是偶然，2 次是巧合，第 3 次就该停手 —— 读实现／打印对象／查文档，
都比第 4 次重试便宜。这条规则直接来自 2026-10-31 夜间「同一个测试连猜两轮」的教训。

验证：组件测试 40/40；变异（阈值 3→4）恰好 1 条红且红的正是阈值边界那条；还原 SHA 一致。
Hook 侧 8/8，其中包含「第 1/2 次不提示、第 3 次提示、成功后重新计数」三态断言。

## 11. P1 落地：Git 安全与本机工具链别名（2026-11-01）

这三条的共同点是「**不会报错，只会静默做错**」——比失败更危险：

| 规则 | 触发条件 | 文案要点 |
|---|---|---|
| `git.add_all_may_include_temp_artifacts` | 命令含 `git add -A` / `--all` / `git add .` | 会连带暂存未跟踪临时产物；改显式路径或先 `git status --porcelain` |
| `git.stash_recovery_on_same_chain` | 含 `git stash` **且** 同一行含 `&&` | pop 别挂在同一条链上，链断则改动被锁在 stash 里；分两次调用 |
| `host.python_alias_is_store_stub` | 命令位置出现 `python` / `python3` | 本机是商店占位符，改用 `py -3` 并设 `PYTHONIOENCODING=utf-8` |

两个刻意的「不触发」：

- **单独一条 `git stash` 不提示** —— 那是正确用法，只在和别的动作串成 `&&` 链时才有风险；
- **只是提到名字不提示** —— `findstr /c:"python"`、`echo python` 不算调用。

规则集现在按组组合（`DefaultRules`）：方言 → 构建效率 → Git 安全 → 本机工具链。
新加一组只动一个新文件，不必回头改名字已经对不上的旧类。

验证：组件 71/71（新增 14 条）；变异（去掉 `&&` 守卫）恰好 1 条红且正是那条负例；还原 SHA 一致。

### 一条关于「环境绑定规则」的纪律

`host.python_alias_is_store_stub` 的判据来自本机实测，不是通用真理。文案里写明了「本机」，
并且这类规则应当随环境变化删除 —— 规则库里混进过期环境假设，比没有规则更糟。

## 12. P2 落地：结果质量 —— 把「没搜到」和「没搜全」分开（2026-11-01）

这组治的是**假阴性**，比误报更危险：工具返回空，人和 Agent 的第一反应都是「不存在」。

| 规则 | 判据（工具输出原文） | 提示 |
|---|---|---|
| `search.coverage_incomplete_is_not_absence` | `coverage: partial` / `complete=false` / `scanned 0/` / `limit_reason=` / 「文件枚举已达上限」 | **不等于「不存在」**；缩小 directory、改用索引工具 |
| `test.filter_matched_nothing` | `No test matches the given testcase filter` 等 | 检查 FullyQualifiedName 是否写全；先用 `--list-tests` 确认名字 |

关键设计：判据取自**工具自己的输出文本**，而不是猜调用参数 —— 因此对任何 Agent 都生效，
无论它有没有读过这个工具的文档。

反例刻意包括「干净的空结果」（`no matches`）：那才是真正的「没有」，不该加任何提示。

验证：组件 80/80（+9）；变异（`Contains`→`StartsWith`）恰好 2 条红，都是标记出现在文本中段的用例；还原 SHA 一致。

  构建(2)  重复测试 → --no-build；连续超时 → blame-hang

```
