# 依赖方向编译期强制 · 现状核实与门禁方案

> 动机：用户裁定的第一原则「依赖方向由编译期强制」。本文先核实它现在的实际落地程度，
> 再给出一个可 opt-in、能取红的门禁。
> **本文未编译、未取红**，所有「应当如此」的表述都标在 §5。

## 1. 核实到的现状（两个文件，两句话，都不算错）

`Directory.Build.targets` 全文 42 行：只有测试项目属性、`Moq` / `coverlet` 的包引用、
以及一份 Jieba 资源传递导入。**没有任何依赖方向校验 target。**

而源码里对同一件事有两种表述：

```csharp
// Source/PuddingSshTests/ComponentBoundaryTests.cs:10
/// Pudding 上层程序集、EF Core、ASP.NET Core 或 Roslyn/MSBuild。边界由编译期强制，这里做运行期复核。

// Source/PuddingComputer.UIAutomationTests/BoundaryTests.cs:9
/// 规程要求"依赖方向由编译期强制"，但本项目没有 analyzer 插件，
/// 所以次级手段是运行时反射断言
```

**两句话都对，但说的不是同一件事。** 这正是需要说清的地方。

## 2. 缺的是「声明的强制」，不是「使用的强制」

把「编译期强制」拆成两件事，就清楚了：

| 层 | 含义 | 现状 |
|---|---|---|
| A. 使用的强制 | 项目只引用了允许的程序集 ⇒ 代码里 `using` 一个越界类型**根本编译不过** | **已成立** |
| B. 声明的强制 | 不许人随手往 csproj 里加一条越界 `<ProjectReference>` | **无人把关** |

A 是 B 的结果：只要 csproj 图是对的，越界使用就编不过。所以 `PuddingSshTests` 那句注释是准确的。

B 没有守。任何人都可以在某个组件的 csproj 里加一行 `<ProjectReference Include="..\..\PuddingRuntime\..." />`，
它**能编译、能跑、能部署**，只有等到有人去跑那 36 个反射边界测试才会红——而测试可以不跑。

`BoundaryTests.cs:9` 那句注释描述的正是这个缺口：没有 analyzer，所以只能在运行期事后复核。

**结论**：第一原则不是「名不副实」，而是**只覆盖了 A，没覆盖 B**。这个区分很重要——
它决定了修法不是「造一个 analyzer」，而是「让声明这件事本身会编译失败」。

## 3. 方案：opt-in 的 MSBuild 门禁

### 3.1 约定

需要受约束的项目在自己的 csproj 里声明白名单：

```xml
<PropertyGroup>
  <AllowedProjectReferences>PuddingCore;PuddingToolPlugins.Contracts</AllowedProjectReferences>
</PropertyGroup>
```

**不声明 = 不检查**。这让门禁可以逐组件落地，不需要一次性给 160 个工程写清单。

### 3.2 门禁 target（放进 `Directory.Build.targets`）

```xml
<!--
  依赖方向门禁：仅在项目显式声明 AllowedProjectReferences 时生效。
  目的：让「加一条越界 ProjectReference」在编译期失败，而不是等运行期反射断言。
-->
<Target Name="EnforceReferenceDirection"
        BeforeTargets="Build;Rebuild"
        Condition="'$(AllowedProjectReferences)' != ''">
  <ItemGroup>
    <_PuddingDeclaredRef Include="@(ProjectReference->'%(Filename)')" />
    <_PuddingAllowedRef Include="$(AllowedProjectReferences.Split(';'))" />
    <_PuddingViolation Include="@(_PuddingDeclaredRef)" Exclude="@(_PuddingAllowedRef)" />
  </ItemGroup>
  <Error Condition="'@(_PuddingViolation)' != ''"
         Code="PUDDING001"
         Text="依赖方向违规：$(MSBuildProjectName) 引用了未在 AllowedProjectReferences 声明的项目 [@(_PuddingViolation->'%(Identity)', ', ')]。" />
</Target>
```

三个要点：

1. **`BeforeTargets="Build;Rebuild"`**：构建入口就拦，不依赖测试是否被跑。
2. **`Code="PUDDING001"`**：错误码可被 grep，便于 CI 分类统计。
3. **`%(Filename)` 而非完整路径**：白名单写项目名，跨机器与目录重组不失效。

### 3.3 与现有反射断言的关系

**互补，不替代。**

- 编译期门禁守「声明」：越界引用进不了构建
- 运行期反射断言守「使用」的漏网：例如通过反射、DI 容器、动态加载间接用到禁止层的类型

两边都留，各自覆盖对方的盲区。

## 4. 怎么证明这条门禁能取红

不能只写「已实现」。三步：

1. **基线绿**：选一个已声明白名单的项目，正常 `dotnet build`，应为 0 错误。
2. **注入违规**：在该 csproj 里加一条**确实不该有**的 `<ProjectReference>`（选一个不在白名单的既有项目）。
   预期：构建失败，报 `PUDDING001` 并列出越界项目名。
3. **复原**：删掉那条引用，`dotnet build -t:Rebuild` 复绿，确认 `git diff` 为空。

**第 3 步必须用 `-t:Rebuild`**：`Copy-Item` / 手工删改会保留 mtime，增量构建会跳过重编译，
跑的还是变异版——本仓已有这个教训。

补充一条更便宜的常驻校验：在测试里扫全部 csproj，断言「凡是出现在白名单登记表里的组件，
其 csproj 都必须声明 `AllowedProjectReferences`」——防止有人删掉声明来绕过门禁。

## 5. 未验证 / 不得据本文件声称

- 表达式 `$(AllowedProjectReferences.Split(';'))` 在 `ItemGroup` 的 `Include` 里展开为多值——
  **未在本仓 MSBuild 版本上实测**。若不稳定，退路是改用 `<CreateItem>` 或写一个 `UsingTask`。
- `Exclude` 的匹配在 Windows 上是否大小写不敏感，未核实；白名单按**原样大小写**书写最稳妥。
- ~~未确认仓内是否已有项目使用同名属性或 target~~ → **已核实（2026-11-11 03:30）**：
  `Source/**/*.csproj` 对 `AllowedProjectReferences|EnforceReferenceDirection` 为零命中；
  同目录同配置搜 `ProjectReference Include` 立得 3 条作阳性对照，故零命中是真阴性。
  根 `Directory.Build.props` 也没使用这两个名字，无冲突。
- 根 `Directory.Build.props` 的实际内容：`TargetFramework=net10.0`、`LangVersion=latest`、
  `ImplicitUsings`/`Nullable` 开启，并把 `**/temp/**` `**/tmp/**` 加进 `DefaultItemExcludes`。
  它**没有任何依赖方向相关属性**，因此新增 `AllowedProjectReferences` 不会与既有语义撞车。
- 「加一条越界 ProjectReference 能编译通过」是**读 CSProj 机制得出的结论**，
  未拿一个真实组件做注入实验。
- 本门禁**只约束 `ProjectReference`**；`PackageReference` / `Reference` / 动态加载均不在覆盖范围内。
- 落地成本未评估：160 个工程逐个写白名单的工作量与顺序，未规划。

### 5.1 取红实测结果（2026-11-11 10:42，已落地）

试点组件：`PuddingComputer.UIAutomation`（只声明 `Pudding.Contracts`，文件末尾注释已明确禁止引用 `PuddingComputer.Windows`）。

| 步骤 | 证据 |
|---|---|
| 基线绿 | `-t:Rebuild` → 0 警告 0 错误，两个 DLL 产出，2.74s |
| 注入越界 | 加一条 `..\PuddingComputer.Windows\…csproj` 引用 → `error PUDDING001: 依赖方向违规：PuddingComputer.UIAutomation 引用了未在 AllowedProjectReferences 声明的项目 [PuddingComputer.Windows]` |
| 复原绿 | 删掉该引用，`-t:Rebuild` 重构建 → `PUDDING001=False` / `: error ` 计数 0 / DLL 产出 |

**新增发现（本方案原定的盲区，已修正实现）**：

首次注入时报了**两个**违规项 `[PuddingComputer.Windows, PuddingComputer.Automation]`，但 csproj 只声明了 `Contracts` 一条，`dotnet msbuild -getItem:ProjectReference` 也只返回 **2** 项。
加临时 `Message` 探针实测 target 内的真实集合：

```
REFGATE-DECL=[Pudding.Contracts;PuddingComputer.Windows;PuddingComputer.Automation]
```

即 **Build 阶段 `@(ProjectReference)` 包含传递项**（`PuddingComputer.Windows` 自己引用了 `Automation`）。
机制未查明（设计时评估不含，只在 target 执行时出现）；曾假设是 `Rebuild` 重复触发，改为只挂 `BeforeTargets="Build"` 后**仍然 3 项，假设被证伪**。

修法：用 `ProjectReference` 的 `DefiningProjectFullPath` 元数据限定为本项目声明的项：

```xml
<_PuddingDirectRef Include="@(ProjectReference->WithMetadataValue('DefiningProjectFullPath', '$(MSBuildProjectFullPath)'))" />
<_PuddingDeclaredRef Include="@(_PuddingDirectRef->'%(Filename)')" />
```

修正后 `DECL=[Pudding.Contracts;PuddingComputer.Windows]`、`VIOLATION=[PuddingComputer.Windows]`。

**语义后果（需后续裁定）**：门禁目前**不拦间接越界**——A 引用 B、B 引用禁层 C 时，A 不报错。
若需要连间接依赖一起拦，应另设一个独立的严格模式，而不是把两种语义混在一个 target 里。

### 5.2 第二例试点与一个推翻推广策略的发现（2026-11-11 16:34）

原计划给契约层（`Pudding.Contracts` / `Pudding.ToolPlugins.Contracts` /
`Pudding.Api.Contracts`）加 `AllowedProjectReferences`。**核实后发现这是多余的**：

| 组件 | 已有的自定义边界 target | 强度 |
|---|---|---|
| `Pudding.Contracts` | `EnforceContractsBoundary` | 禁止**任何** `ProjectReference` **和** `PackageReference`（BCL only） |
| `Pudding.ToolPlugins.Contracts` | `EnforceLeafBoundary` | 禁止任何 `ProjectReference` |
| `Pudding.Api.Contracts` | `EnforcePublicContractBoundary` | 禁止 `ProjectReference`/`PackageReference`，只允许 `Microsoft.NETCore.App` |

即：**“依赖方向由编译期强制”在契约层早已落地，而且比白名单更严**（白名单是有选择的禁止，
它们是全禁）。给它们写白名单会与现有规则重叠且语义矛盾。

**推广策略因此修正**：PUDDING001 的价值区间是**中间层**——那些允许引用若干项目、
需要把集合钉死的组件；契约层不需要它。

### 5.3 第二例：`PuddingComputer.Automation`（纯规则层）

选它的理由：csproj 注释写着“刻意不知道 UIA、窗口、输入、IPC、DI、数据库”，
但**这句意图此前没有编译期强制**。声明 `<AllowedProjectReferences>Pudding.Contracts</AllowedProjectReferences>`。

三步取红（`-t:Rebuild`）：

| 步骤 | 证据 |
|---|---|
| 基线绿 | `PUDDING001` 不出现，`: error` 计数 0，`PuddingComputer.Automation.dll` 产出 |
| 注入 `..\Pudding.Rpc.Protocol\...`（不在白名单） | `error PUDDING001: 依赖方向违规：PuddingComputer.Automation 引用了未在 AllowedProjectReferences 声明的项目 [Pudding.Rpc.Protocol]` |
| 复原后重建 | `PUDDING001=False`，`: error` 计数 0，DLL 产出 |

至此 PUDDING001 在两个语义不同的组件上都取得了红：`PuddingComputer.UIAutomation`
（引用含 UIA 包）与 `PuddingComputer.Automation`（纯规则、无包引用）。

**未做**：其余中间层组件的白名单（逐个需先核实其真实引用面）。

### 5.4 常驻登记校验（同日 17:20，补上了 §4 里那条“更便宜”的检查）

opt-in 门禁有一个天然漏洞：**把某组件的声明删掉，门禁就悄悄失效了，仓库不会报错**。
新增 `TestScripts/test-reference-direction-gate.ps1`，两条断言：

**A. 声明集合必须等于登记表**
扫描 `Source/**/*.csproj`，含 `<AllowedProjectReferences>` 的项目集合必须等于脚本内
`$Expected`。两面都抓：删声明 → 红；**新增声明未登记 → 也红**（强制走一次 review）。

**B. 契约层自定义边界 target 必须仍在**
`Pudding.Contracts` / `Pudding.ToolPlugins.Contracts` / `Pudding.Api.Contracts` 各自那条
比白名单更严的全禁规则，一旦被人删掉，契约层就失去编译期保护。

取红验证：

| 状态 | 结果 |
|---|---|
| 正常 | `RESULT: OK (2/2)` |
| 变异（删掉 Automation 的声明） | **A 失败**：`登记表里的项目缺少 AllowedProjectReferences 声明 -> PuddingComputer.Automation` |
| 复原 | `2/2`，且 `findstr MUTANT` 无残留 |

与 PUDDING001 的关系：门禁管「构建时」，本校验管「配置是否还存在」。
前者防越界，后者防**静默失效**。

### 5.5 第三例：`PuddingComputer.Windows`（CU 平台层，2026-11-11 18:12）

它的 csproj 注释写着「依赖方向由 ProjectReference 强制：Windows → Automation → Contracts」，
但**此前没有编译期约束**。声明：

```xml
<AllowedProjectReferences>Pudding.Contracts;PuddingComputer.Automation</AllowedProjectReferences>
```

三步取红：

| 步骤 | 证据 |
|---|---|
| 基线 | `PUDDING001` 不出现，`: error` 计数 0，`PuddingComputer.Windows.dll` 产出 |
| 注入 `..\Pudding.Rpc.Protocol\...` | `PUDDING001=True`，`: error` 计数 2 |
| 复原重建 | `PUDDING001=False`，`: error` 计数 0，DLL 产出 |

**顺带把 §5 里一条“未实测”变成了实测**：
“`$(AllowedProjectReferences.Split(';'))` 在 `ItemGroup` 的 `Include` 里展开为多值”——
本次白名单写两项，构建通过（若展开失败，第二项 `PuddingComputer.Automation` 会被
误判为越界而报红）。多个试点中这是第一个真用上多项的场景。

### 5.6 登记校验的“强制 review”被实操验证了一次

加完 `PuddingComputer.Windows` 的声明后，`TestScripts/test-reference-direction-gate.ps1`
的 A 断言确实会红（未登记却声明）——把 `$Expected` 补上后才转绿。
这说明那条校验不只防“删声明”，也真的拦住了“新加声明不登记”。

当前登记表：`PuddingComputer.Automation` / `PuddingComputer.UIAutomation` /
`PuddingComputer.Windows`（3 项）。

### 5.8 已接入 commit gate（同日 19:04）

`.git/hooks/pre-commit` 只是一个 shim，写着“edit TestScripts/”——真正入口是
`TestScripts/check-staged-tests.ps1`，所以接入可以入库。

新增一段：当暂存变更含 `*.csproj` / `*.props` / `*.targets` / `test-reference-direction-gate.ps1` 时，
先跑登记校验，失败则 `exit 1` 阻断提交。

**位置比内容更要紧**：首次实现放在 `# --- run ---` 之前，结果**纯 csproj 提交根本不触发**——
因为脚本在 `# --- select ---` 就因“no changed C# files” `exit 0` 了。
移到那个提前退出**之前**才行。这条写进代码注释了。

验证：

| 场景 | 结果 |
|---|---|
| 暂存一个 csproj | 输出 `=== reference-direction gate: 1 build config file(s) staged` + `PASS A/B` + `RESULT: OK (2/2)`，然后才走原来的 `no changed C# files` 分支 |
| 临时让登记表与现状不符 | 输出 `FAILURES: A: 发现未登记却声明的项目 -> PuddingComputer.Windows` + `WARNING: BLOCKED: reference-direction gate failed` |
| 真实退出码 | `Start-Process ... -PassThru` 取到 **`REAL_EXIT=1`** |

**仪器注意**：用 `& echo %ERRORLEVEL%` 拿到的是 `0`——cmd 在**解析期**就展开了它。
必须用 `Start-Process -PassThru` 的 `ExitCode`（或分开两行）才能拿到真实退出码。
这条如果没验，就会误以为“block 没生效”。

复原后：`git status` 对两个被变异文件无输出，索引 0 项。





## 6. 建议的落地顺序

1. 先只给 **2~3 个最关键的契约层项目**加声明（如 `PuddingCore` 的下游组件），跑通取红三步
2. 稳定后扩展到「已被 36 个反射断言覆盖」的组件
3. 最后把「新增组件必须声明白名单」写进交付规程，用一条测试兜住
