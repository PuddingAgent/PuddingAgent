# Core 事件驱动基础设施施工与代码设计

## 1. 交付范围与读法

以 [ADR-098](../07_architecture/112ADR-098Core事件驱动与严格分层基础设施ADR.md) 为决策依据，交付 Pudding 内部“持久受理 → 注册路由 → 独立投递 → 工作受理 → 执行 → 领域事件”的完整链。测试宿主不注册 Agent 心跳，使用内部生产者；不以外部客户端、真实平台接入、动态 DLL 加载或新前端作为前置条件。

下文新项目、文件、C# 接口和 SQL 都是**待实现设计**。现有接口均显式标记为复用；目标代码块用于冻结语义，不宣称已经可编译或已经接入。所有阶段均需留下代码、测试和修改日志，证据进入 `Docs/14_reports/` 或 `Docs/16_qa/`。

E0–E4 只新增独立组件及其测试，不改既有 Host、Runtime、Platform、解决方案或生产 DI。E5 起才进入这些组件的 S5 接入。E8 的 Agent Kernel 再独立经历 S1–S4 后接入。不能把文档完成、单测通过、DI 能解析、产品闭环混为同一个完成状态。

## 4. 核心合同

### 4.1 事件受理

```csharp
public enum EventAcceptKind { Accepted, Duplicate, Rejected, RetryLater }
public sealed record EventIdentity(string WorkspaceId, string ProducerId, string SourceKey);
public sealed record EventSubmission(
    string Type, int SchemaVersion, DateTimeOffset OccurredAt,
    string PayloadJson, string? CorrelationId, string? CausationId);
public sealed record EventReceipt(
    string ReceiptId, EventIdentity Identity, long Sequence,
    string RegistryRevision, int DeliveryCount, string RouteStatus);
public sealed record EventAcceptResult(
    EventAcceptKind Kind, EventReceipt? Receipt, string? ReasonCode,
    DateTimeOffset? RetryAfter);
public interface IEventIngress
{
    ValueTask<EventAcceptResult> AcceptAsync(
        EventIdentity identity, EventSubmission submission, CancellationToken ct);
}
```

Identity 来自持有对应生产权限的内层调用者或入口适配器，不从 PayloadJson 提取。SourceKey 是生产者持久保存的稳定键，重试复用。Hash 使用带长度前缀的身份、Type、SchemaVersion、OccurredAt、关联字段及**原始 PayloadJson UTF-8**，不包含接收时间、重试次数或注册版本；同键换空白/字段顺序也视为不同输入，生产者必须重用同一快照。不要用含歧义的字符串拼接散列。

Accepted/Duplicate 必须有 Receipt；Rejected/RetryLater 不得携带虚构成功收据。数据库提交成功后即使调用方取消或唤醒失败，记录仍存在；重试可查询原收据。已受理但无订阅时返回 Accepted + `RouteStatus=unmatched`，不伪称业务执行成功。

### 4.2 注册与映射

`SubscriptionDefinition` 必需字段：SubscriptionId、OwnerId、WorkspaceId、EventTypePattern、Min/MaxSchema、FilterAst、Target、InputMapping、PartitionRule、RetryPolicy、DeadlinePolicy、RequiredForSettlement、DefinitionHash。事件模式第一期只支持精确名称和尾部 `.*`；过滤仅支持声明字段上的 eq/in/数值比较/and，限制树深、节点数和字符串长度，不执行 regex/脚本。

`WorkTarget` 包含 CapabilityId、ContractVersion/Hash、TargetKind、目标 Agent/Graph/Job 标识。Graph 固定 RevisionId，不读执行时最新 Head；Agent 固定明确会话归属策略；信号固定 RunId/WaitToken。映射只可取已验证字段和常量，不能从事件任意改写 workspace、owner、权限或目标能力。

工作命令在路由时生成并冻结，而不是每次重试重新计算。CommandId 使用 `evt-` 加 `(ReceiptId, SubscriptionId, DefinitionHash)` 的完整 SHA-256；输入 hash 包括目标、映射结果与权限/预算快照。ContractHash 不匹配时 Suspend 并诊断，不自动绑定新版本。

内置贡献使用代码注册；长期用户配置位于 `<DataRoot>/config/event-subscriptions.json`，包含 WorkspaceId。文件采用原子替换；注册服务依次执行“校验全部 → 写期望配置 → 数据库激活不可变 snapshot/head”。Eventing 只调 ISubscriptionConfigurationStore 端口，文件 I/O 在 Hosting 的 FileSubscriptionConfigurationStore 实现。响应有 DesiredRevision、ActiveRevision、ActivationStatus；崩溃后重启协调，不因文件已保存就报 Active。敏感配置不写入快照。RegistrySnapshot 同时保存 HookSnapshotHash；新 head 只有在该 Hook 快照及所有目标能力就绪后才激活，重启时校验可重建相同快照，缺失则暂停关联投递。

### 4.3 存储与执行端口

```csharp
public sealed record DeliveryLease(
    string DeliveryId, string OwnerId, long Fence, DateTimeOffset LeaseUntil);
public sealed record WorkCommand(
    string CommandId, string WorkspaceId, string CapabilityId,
    string ContractHash, string TargetKind, string InputJson, string InputHash);
public enum WorkAcceptKind { Accepted, Existing, Deferred, Rejected, CancelledBeforeAccept }
public sealed record WorkReceipt(
    string CommandId, string WorkKind, string WorkId, string InputHash);
public sealed record WorkAcceptResult(
    WorkAcceptKind Kind, WorkReceipt? Receipt, string? ReasonCode,
    DateTimeOffset? RetryAfter);
public interface IWorkAcceptor
{
    ValueTask<WorkAcceptResult> AcceptAsync(WorkCommand command, CancellationToken ct);
}
public interface IEventStore
{
    ValueTask<EventAcceptResult> CommitPreparedAsync(PreparedEvent item, CancellationToken ct);
    ValueTask<ClaimedDelivery?> ClaimAsync(ClaimRequest request, CancellationToken ct);
    ValueTask<bool> RenewAsync(DeliveryLease lease, DateTimeOffset until, CancellationToken ct);
    ValueTask<bool> CompleteAsync(DeliveryLease lease, DeliveryCompletion result, CancellationToken ct);
    ValueTask<int> RecoverExpiredAsync(DateTimeOffset now, int limit, CancellationToken ct);
}
```

配套类型必须一并交付：PreparedEvent 含 raw hash、ReceiptId、期望 RegistryRevision、冻结 RoutePlan/Command 和配额成本；ClaimRequest 含 owner、workspace/partition、now、租期；ClaimedDelivery 含命令、lease、失败次数、deadline；DeliveryCompletion 是 Accepted/Deferred/Retry/Rejected/Cancelled/DeadLetter/Suspended 的封闭结果类型。不存在“直接写任意 status 字符串”的公开接口。

`IWorkReceiptReader` 按 `(WorkspaceId, CommandId)` 查询接受事实；`IWorkCancellationAcceptor` 持久记录按 CommandId 的取消，支持先取消后受理的 tombstone。CancellationToken 只取消当前传输等待，不代表业务取消。实现若不具备某种持久取消能力，必须在 capability 描述中标明，不能用返回成功掩盖仍可能发生的工作。

## 5. SQLite 模型与事务

### 5.1 核心表

下面是第一期可执行的建表基线。UTC 时间均为 Unix 毫秒；状态枚举与迁移工具从同一个目录定义生成，不维护两份字符串清单。应用查询始终携带 workspace。

```sql
PRAGMA foreign_keys = ON;
CREATE TABLE event_registry_revisions (
  workspace_id TEXT NOT NULL, revision TEXT NOT NULL,
  definition_hash TEXT NOT NULL, definition_json TEXT NOT NULL,
  created_at INTEGER NOT NULL,
  PRIMARY KEY (workspace_id, revision)
);
CREATE TABLE event_registry_heads (
  workspace_id TEXT PRIMARY KEY, revision TEXT NOT NULL,
  FOREIGN KEY (workspace_id, revision)
    REFERENCES event_registry_revisions(workspace_id, revision)
);
CREATE TABLE event_quota_usage (
  workspace_id TEXT PRIMARY KEY, retained_count INTEGER NOT NULL CHECK(retained_count>=0),
  retained_bytes INTEGER NOT NULL CHECK(retained_bytes>=0),
  open_deliveries INTEGER NOT NULL CHECK(open_deliveries>=0)
);
CREATE TABLE event_inbox (
  sequence INTEGER PRIMARY KEY AUTOINCREMENT,
  receipt_id TEXT NOT NULL UNIQUE, workspace_id TEXT NOT NULL,
  producer_id TEXT NOT NULL, source_key TEXT NOT NULL, input_hash TEXT NOT NULL,
  event_type TEXT NOT NULL, schema_version INTEGER NOT NULL CHECK(schema_version>0),
  occurred_at INTEGER NOT NULL, received_at INTEGER NOT NULL,
  correlation_id TEXT, causation_id TEXT, original_receipt_id TEXT,
  payload_json TEXT NOT NULL, registry_revision TEXT NOT NULL,
  route_status TEXT NOT NULL CHECK(route_status IN ('routed','unmatched')),
  route_plan_json TEXT NOT NULL,
  UNIQUE (workspace_id, producer_id, source_key),
  UNIQUE (workspace_id, receipt_id),
  FOREIGN KEY (workspace_id, registry_revision)
    REFERENCES event_registry_revisions(workspace_id, revision)
);
CREATE TABLE event_deliveries (
  delivery_id TEXT PRIMARY KEY, workspace_id TEXT NOT NULL, receipt_id TEXT NOT NULL,
  subscription_id TEXT NOT NULL, definition_hash TEXT NOT NULL,
  partition_key TEXT NOT NULL, partition_sequence INTEGER NOT NULL,
  command_id TEXT NOT NULL, command_json TEXT NOT NULL, command_hash TEXT NOT NULL,
  status TEXT NOT NULL CHECK(status IN
    ('pending','claimed','deferred','retrying','accepted','rejected','cancelled','dead_letter','suspended')),
  priority INTEGER NOT NULL, available_at INTEGER NOT NULL, deadline_at INTEGER,
  failure_count INTEGER NOT NULL DEFAULT 0, claim_count INTEGER NOT NULL DEFAULT 0,
  owner_id TEXT, fence INTEGER NOT NULL DEFAULT 0, lease_until INTEGER,
  cancel_requested INTEGER NOT NULL DEFAULT 0 CHECK(cancel_requested IN (0,1)),
  work_kind TEXT, work_id TEXT, result_code TEXT,
  created_at INTEGER NOT NULL, updated_at INTEGER NOT NULL,
  UNIQUE (workspace_id, receipt_id, subscription_id, definition_hash),
  UNIQUE (workspace_id, command_id),
  UNIQUE (workspace_id, partition_key, partition_sequence),
  FOREIGN KEY (workspace_id, receipt_id) REFERENCES event_inbox(workspace_id, receipt_id)
);
CREATE TABLE event_partitions (
  workspace_id TEXT NOT NULL, partition_key TEXT NOT NULL,
  last_sequence INTEGER NOT NULL DEFAULT 0,
  PRIMARY KEY (workspace_id, partition_key)
);
CREATE TABLE event_cancellation_requests (
  workspace_id TEXT NOT NULL, command_id TEXT NOT NULL, request_id TEXT NOT NULL,
  status TEXT NOT NULL CHECK(status IN ('pending','forwarded','confirmed','unsupported')),
  requested_at INTEGER NOT NULL, result_json TEXT,
  PRIMARY KEY (workspace_id, command_id), UNIQUE (workspace_id, request_id),
  FOREIGN KEY (workspace_id, command_id) REFERENCES event_deliveries(workspace_id, command_id)
);
CREATE INDEX ix_event_claim ON event_deliveries(workspace_id,status,available_at,priority);
CREATE INDEX ix_event_partition ON event_deliveries(workspace_id,partition_key,partition_sequence,status);
CREATE INDEX ix_event_expired ON event_deliveries(status,lease_until);
CREATE INDEX ix_event_trace ON event_inbox(workspace_id,correlation_id,sequence);
```

连接启用 foreign_keys、WAL 和有界 busy timeout；写入操作使用短事务，禁止共享并发 SqliteConnection。约束冲突必须重新读原记录核对 hash，不能笼统吞掉唯一索引错误。schema bootstrap 在独立组件中幂等执行，版本不支持时明确拒绝启动。

配额来自配置文件，usage 表只是运行计数；事务更新计数时同时校验上限，不能 `COUNT` 后跨事务插入。第一期保留去重 tombstone，不自动删除旧幂等键；达到 retained 上限后背压并提示维护。载荷归档不删除未结投递、工作关联或必要去重信息。后续若采用有限去重期限，必须增加明确的来源过期拒绝协议，不能静默削弱重投语义。

### 5.2 受理算法

1. 校验类型、大小、身份与来源权限，计算 raw input hash；查询幂等键。命中同 hash 返回原回执，异 hash 返回 `event.identity_conflict`。
2. 读取 active RegistryRevision，运行该版本的准入 Hook 和纯路由/映射，验证所有目标合同。无 LLM、无业务副作用；fan-out/命令字节超限在提交前拒绝。
3. `BEGIN IMMEDIATE` 后再次检查幂等键；核对 registry head 未变化；校验并更新 workspace 配额。对各分区分配单调 sequence，插入 Inbox、RoutePlan、Delivery，最后 commit。事务内无用户代码。
4. commit 后返回 Receipt，并用有界信号通知 Worker。信号失败只降级延迟，不能撤销已受理事实。Head 冲突重新准备，最多 3 次；数据库忙返回 RetryLater，不吞异常伪报 Duplicate。

RoutePlan 已包含实际 SubscriptionId、DefinitionHash、CommandId 和映射输入；重放诊断可直接说明“当时为什么投递给它”，无需重新执行现在的注册规则。

`IEventReplayService.ReplayAsync(ReplayRequest, ct)` 是独立控制面端口。请求含 WorkspaceId、OriginalReceiptId、稳定 ReplayId、明确的目标 RegistryRevision 与操作者身份；第一期只允许当前 active revision，调用前须展示将使用新注册路由。它以 `replay:{ReplayId}` 为新来源键、保存 OriginalReceiptId 并重新受理，重试同 ReplayId 返回同一回执；不修改原 Inbox/Delivery。普通 ingress 不接受调用者伪造 replay 标记。

### 5.3 领取、续租与终态

一个分区同一时刻最多有一个尚未完成交接的 claimed Delivery。候选必须到期、未被取消，并且没有更早的非终态分区记录；Deferred/Retrying/Suspended 默认保留分区顺序，其他分区继续。需要允许跳过的业务必须显式采用其他分区，不能自动越过失败记录。

在同一 `BEGIN IMMEDIATE` 事务内选候选并条件更新：status=claimed、owner、fence=fence+1、lease_until、claim_count+1。每次领取返回新 fence。续租和完成的必要谓词为：

```sql
WHERE delivery_id = @id AND workspace_id = @workspace
  AND status = 'claimed' AND owner_id = @owner AND fence = @fence
  AND lease_until > @now
```

影响行数为 0 表示失去所有权，旧 Worker 不能再次写状态。恢复过期领取时更新 fence、清理 owner/lease 并返回可领取状态；不增加业务 failure_count。永久错误进入 Rejected/DeadLetter；瞬时错误增加 failure_count 并指数退避；Busy 进入 Deferred，只增加诊断次数。正常重投永不重置终态。

### 5.4 取消竞争

未领取投递可在取消事务中直接 Cancelled 并释放 open_deliveries 配额。claimed 或已目标受理的投递必须写入 `event_cancellation_requests`；目标取消端口以 CommandId 写其所属数据库的取消 tombstone/请求。若取消先于受理提交，后续受理返回 CancelledBeforeAccept；若受理先提交，返回原 WorkId 并请求目标取消，等待其实际结果。

目标结果未知时保留请求并恢复查询；不把断开调用方等待当作取消成功。停止宿主时取消 pump、停止领取、有限等待已开始的受理调用，剩余工作由租约与 CommandId 去重恢复。

## 6. 工作执行适配与等待恢复

### 6.1 目标接受必须原子

每个目标域新增或复用 `work_acceptance_receipts`：唯一 `(workspace_id,command_id)`，含 input_hash、work_kind、work_id、accept_status、accepted_at、cancel_requested。收据与目标命令/Run/Job 在**同一个原生事务**写入，不能由 Eventing 先写“成功收据”再调用目标。

目标已提交但进程在 Eventing Ack 前退出：再次 Accept 同 CommandId 返回同 WorkReceipt，再完成 Delivery。CommandId 相同但 input_hash 不同必须拒绝。租约只保护队列写回，不代替目标幂等。

| 目标 | 新增适配文件及确切交接 |
|---|---|
| Agent Turn | `Source/PuddingPlatform/Services/Eventing/AgentTurnWorkAcceptor.cs`：验证 workspace/Agent/会话归属 → ISubmitTurnHandler → IConversationAcceptanceStore；从 CommandId 派生 ClientRequestId/ClientMessageId，返回真实 TurnId |
| Graph Start | `.../Eventing/OrchestrationWorkAcceptor.cs`：复用 QueryStore/Store，固定 RevisionId、InputsHash、RunId；Create 后 Draft 状态必须幂等 Activate，Active/终态返回原回执 |
| 后台 Job | `.../Eventing/BackgroundJobWorkAcceptor.cs`：通过 Core 中既有 Job 队列端口与稳定 IdempotencyKey 受理；不得在适配器中执行模型或维护任务 |

`...` 均指 `Source/PuddingPlatform/Services`。若具体 Job 的存储归属 MemoryEngine，其收据与原子修改留在 MemoryEngine；Platform 适配器只调用合同。可复用 [ManualRunService](../../Source/PuddingPlatform/Services/Orchestration/AgentOrchestrationManualRunService.cs) 的确定性创建/激活方法，但不能把事件伪装成 `manual:` 身份。

当前 `ConversationAcceptanceStore` 幂等命中直接返回批次，尚不能证明异输入冲突已被拒绝。E5 必须增加 AcceptanceBatch 输入 hash，并在原事务中写目标收据；事件身份上下文独立于 `IsTrustedGatewayIngress` / `IsTrustedMessageFabricIngress`。HTTP Controller 不映射该受信字段。事件内容作为来源数据渲染，不提升为 system 指令。

### 6.2 持久等待和提前到达的信号

现有 `IAgentOrchestrationStore` 的 Create/Activate 并不等于已具备通用 Resume API。本期新增 `IAgentOrchestrationSignalStore` 与 `OrchestrationWaitContracts.cs`，归属既有编排域。

- `RegisterWaitAsync(runId,nodeRunId,waitToken,expectedRunVersion,condition)`：同事务写等待节点与 `orchestration_waits`。WaitToken 每一轮重新生成，发出相应 Effect 之前必须持久化。
- `AcceptSignalAsync(commandId,inputHash,runId,waitToken,payload)`：同事务保存 `orchestration_signals` 与受理回执；唯一 `(workspace,commandId)`。允许合法信号先于消费进程观察到 wait，但不允许唤醒不同 epoch 的节点。
- `TryResolveWaitAsync`：在目标 Run 的 CAS/fence 下匹配 pending signal，原子标记 wait 已满足、signal 已消费、节点可运行，并写 Run event/outbox。超时、取消和 signal 同时发生时，仅一个状态转换提交。

`orchestration_waits` 主键 `(run_id,wait_token)`，记录 node_run_id、condition_hash、status、deadline/version；`orchestration_signals` 记录 signal_id、command_id、input_hash、run_id、wait_token、payload、consumed_at。过期 token 返回明确 StaleWait；未知合法 token 的提前信号限额持久保存，等待登记时合并检查。未建立此合同的节点不能宣称支持事件恢复。

## 7. 领域 Outbox 与必需消费者

新建 `Source/PuddingEventing.Hosting/SourceOutboxPump.cs`，通过各源域提供的 `ISourceOutbox` 读取，不持有任何域的 DbContext。通用源表最低字段：OutboxId、WorkspaceId、ProducerId、SourceKey、Type、SchemaVersion、Payload、OccurredAt、状态、owner/fence、NextAttemptAt。它必须和业务状态在原数据库同事务提交。

桥工作步骤：claim → IEventIngress.AcceptAsync → Accepted/Duplicate 后按源 fence ack。Crash 于受理后、源 ack 前只会再次得到 Duplicate。Rejected 必须留下隔离记录与原因；RetryLater 按回执延后。源 outbox 到事件库的所有运行循环都使用有界 batch，不一次读全部历史。

第一条真实内部业务链选“会话压缩提交 → 记忆维护作业受理”。当前权威写入位于 `ContextCompactionService.WriteCheckpointAtomicallyAsync`：它直接使用 MemoryDbContext，同事务写 summary、coverage manifest、Session generation CAS 和逐行覆盖标记；后面的 `PublishSessionCompressedHookAsync` 不在该事务内。E6 的具体改法为：

| 文件 | 目标改动 |
|---|---|
| `Source/PuddingCore/Abstractions/ICompactionCheckpointStore.cs`（新增） | 定义不含 EF 实体的 CommitRequest/Result 窄合同；涵盖 generation、冻结行版本、summary、coverage 与可选维护意图 |
| `Source/PuddingMemoryEngine/Services/CompactionCheckpointStore.cs`（新增） | 先原样迁入原子提交算法并回归，再在同一 MemoryDbContext 事务写维护 outbox；Runtime 不再持有该提交的 SQL |
| `Source/PuddingMemoryEngine/Entities/CompactionOutboxEntity.cs`（新增） | 稳定唯一键 `(WorkspaceId,CompactionId,EventType)`，保存完整发布输入与源租约 |
| `Source/PuddingMemoryEngine/Services/Events/MemoryCompactionOutboxReader.cs`（新增） | 实现源域读取/ack 合同；不访问 PlatformDbContext |
| `Source/PuddingRuntime/Services/ContextCompactionService.cs` | 调窄提交端口；提交前构造冻结维护 payload，成功后仅发唤醒；删除可靠义务对旧 Publish 的依赖 |

上述 Core 合同属于现有集成边界，不能被新 Eventing 叶组件反向引用。共享 checkpoint 原语同时服务 warm-prefix；必须明确 `CommitKind`，只有声明为业务压缩且带有效维护意图的提交生成该领域事件，不能让纯前缀 checkpoint 意外触发维护。映射复用现有 CompactionId 幂等键；切换时移除旧 SessionCompressedMemoryMaintenanceHook 的内存订阅 owner。独立的 Conversation Event 投影仍可异步追赶，不能取代 Memory 数据库中的原子事实。

Task/Goal 专用 outbox 不在本期强制全量改造。每迁移一种领域义务，都需列明源提交、原消费者、新消费者、旧路径禁用和 crash 证据；没有对应证据，不宣称该领域已进入可靠 Eventing。

## 8. Hook 代码与唯一注册入口

复用既定 `PuddingAgentKernel.Contracts` / `PuddingInvocationPipeline` 名称与职责，不在 Eventing 内复制 HookCallBoundary 或吞异常策略。新增通用端口摘录：

```csharp
public readonly record struct HookPoint<TContext,TResult>(string Id, int Version);
public readonly record struct HookSnapshotId(string Value);
public interface IHookPipeline
{
    ValueTask<TResult> InvokeAsync<TContext,TResult>(
        HookPoint<TContext,TResult> point, HookSnapshotId snapshot, TContext context,
        Func<CancellationToken,ValueTask<TResult>> terminal, CancellationToken ct);
}
```

每个点在 Catalog 固定输入/输出类型、允许的阶段、是否允许短路及失败策略。调用者传入 terminal，扩展只能由 Pipeline 提供的 OnceNextGate 继续；注册者不能持有可写 store 或原始 terminal。PointId 相同但合同类型/hash 不同在启动时拒绝。

| PointId | 阶段与允许行为 | 失败处理 |
|---|---|---|
| event.accept.v1 | Guard；受理前，无副作用，不能改身份和幂等键 | Deny/异常/超时阻止新受理；Duplicate 不重跑 |
| event.route.v1 | 纯 Transform；只生成消费者视图与映射输入，原始事件不变 | 变换后重验 schema、目标与预算；失败拒绝新受理 |
| event.deliver.v1 | Guard/Around；仅包裹持久工作受理，不能直接执行 LLM | 暂时失效 Deferred；永久拒绝 Rejected；结果未知按原 CommandId 重试 |
| event.accepted.v1 | 可选 Observer；提交后在线诊断 | 错误隔离，不能回滚已提交事实 |
| agent.context / tool.invoke / agent.terminal | 复用生命周期目录的类型化扩展点 | Guard fail-closed，取消传播，终态恰好一次 |

Guard 的拒绝不可被后续 Hook 重新允许。Transform 返回不可变新值。注册顺序按显式 Order、Before/After 拓扑与稳定 ID 决定；环、重复 ID、作用域不合法都在激活时失败。受理与投递使用冻结 RegistryRevision 所对应的 HookSnapshot；不得在一次调用中切换版本。

所有 Hook 有 deadline。超时无法强行终止任意托管代码，因此准入 Hook 限制为可信、无副作用代码；Around 取消后需等待已启动 terminal 得出结果或记为未知，并保留恢复义务。不能在 `Task.WhenAny` 超时后立即释放仍被代码使用的资源，也不能启动第二次副作用调用“碰碰运气”。动态不可信插件隔离另行建设。

S5 新增 `Source/PuddingHost/Composition/EventingComposition.cs`，声明内置订阅和 Hook，调用各组件已验证工厂；服务实现留在组件。注册示意如下，Builder API 由 E1/E5 交付：

```csharp
registry.RegisterConsumer(SessionCompressedMaintenanceContribution.Definition);
registry.RegisterConsumer(InternalTurnRequestContribution.Definition);
hooks.Register(EventHookPoints.Accept, EventPolicyGuard.Registration);
workAcceptors.Register("pudding.agent.turn", agentTurnAcceptor);
workAcceptors.Register("pudding.orchestration.start", graphStartAcceptor);
workAcceptors.Register("pudding.orchestration.signal", graphSignalAcceptor);
```

`event_subscribe` 只调用 `IEventSubscriptionService`，不能把 AgentId 任意扩展到其他工作区；更新/删除需要 expected revision。启动检查每个 Active subscription 的 target、schema、映射和 Hook owner 完整，不允许可选 DI 参数静默 null。

## 9. Worker、配置和诊断

`DeliveryPump.DrainOnceAsync` 是可独立测试的协调方法；Hosting 负责唤醒、计时和生命周期。内存信号 Channel 有界且允许合并，payload 只含 workspace/partition 提示；每次醒来读取数据库真源。启动扫描未完成投递，常态信号触发立即 drain，到期 timer 处理重试和过期租约。

第一期建议默认值如下，均为待性能验收的初始配置，不是既有实测能力：

| 配置 | 初始值及约束 |
|---|---|
| MaxPayloadBytes / MaxFanOut | 256 KiB / 64；超限在提交前拒绝 |
| MaxOpenDeliveriesPerWorkspace | 10,000；同时限制 retained 记录和字节，默认 100,000 / 512 MiB |
| MaxConcurrentHandoffs | 4；每分区 1，目标执行并发由其 owner 控制 |
| ClaimBatchSize / WakeCapacity | 32 / 256；唤醒满时合并，已持久工作不丢 |
| LeaseDuration / RenewInterval | 60 s / 5 s；续租不得超过 handoff deadline |
| HandoffTimeout / RecoveryInterval | 15 s / 5 s；正常事件不等待恢复 timer |
| MaxFailures / RetryBase / RetryMax | 5 / 1 s / 60 s；指数退避加可测 jitter，Busy 不计失败 |
| AdmissionHookTimeout | 100 ms；任何数据库/网络工作移出纯准入 Hook |

配置放 `<DataRoot>/config/system.json` 的 `eventing` 节。路径通过现有路径服务注入，不在组件写 `D:\data` 常量。启动期验证上下限与续租关系，非法配置明确失败。公平调度按 workspace 轮转，优先级采用有低优先级保留份额的加权轮转；同分区顺序优先于优先级。

`IEventQuery` 提供按 ReceiptId/CommandId/CorrelationId 查询、按状态分页、积压计数/最老年龄、未匹配/死信原因。HTTP 诊断只在 S5 由现有 EventDiagnosticsController 适配，不要求新前端。日志记录身份、状态、耗时、失败码与 WorkId，不输出原始载荷、凭据或完整消息内容。

至少定义错误码：`event.identity_conflict`、`event.quota_exceeded`、`event.fanout_exceeded`、`event.registry_changed`、`event.unmatched`、`delivery.lease_lost`、`delivery.target_unavailable`、`work.input_conflict`、`work.stale_wait`。取消、busy、重试和死信分别统计。

| T06 | 配额边界同时入队、fan-out 超限 | 不超额、不半受理；Rejected/RetryLater 无成功回执 |
| T07 | 长任务与短任务、Busy 后空闲 | 交接不等 LLM 完成；其他分区前进；Busy 不消耗 failure budget |
| T08 | 激活期间受理、重启、删除/更新订阅 | Receipt 指向唯一快照；原 Delivery 不换目标；旧能力缺失 Suspended |
| T09 | 唤醒全部丢失、Worker 重启、重试到期 | 5 秒恢复周期配置下可最终处理；不调用模型寻找待办 |
| T10 | Cancel 在领取前、受理前后、回执未知时竞争 | tombstone 或真实目标取消请求可查；不虚报副作用撤回 |
| T11 | signal 提前到达、旧 WaitToken、timeout 竞争 | 持久保留/拒绝陈旧；等待只解锁一次；Orchestration tests |
| T12 | Hook 拒绝/超时/取消/double-next、订阅扇出 | 不越权执行、不漏终态；任务型消费者不用可丢 mailbox |
| T13 | Buffered/Streaming 同一 fake 模型与工具脚本 | 规范化后的 Hook 序列、次数、输入/结果、终态一致 |
| T14 | 未匹配、目标能力卸载、死信、显式重放 | 各状态/原因可查；replay 新身份关联原收据，原账本不重置 |
| T15 | Host 重复 DI、缺依赖、非法程序集引用 | 组合启动/构建门禁明确失败；探测器变异取红 |

## 14. 切换、回退与完成定义

1. 隔离数据副本验证旧队列导入：稳定映射旧 EventId→新 SourceKey，记录导入收据；旧 completed 不重放，dead_letter 保留死信，未完成记录逐条导入或隔离并说明原因。无合法工作区/目标的旧记录不猜测补齐。
2. 停止旧生产者受理，等待旧在途工作结算或保留恢复证据；备份相关数据库。新旧路径不得同时执行同一义务。
3. 发布具备新存储读取能力的构建，初始化并激活注册，再启动消费者，最后开放可靠受理。核对实际构建标识和注册清单。
4. 内部事件/消息 smoke、信号丢失恢复和一次真实进程重启通过后，确认单 owner。回退时先关闭新受理与领取，保留 Inbox/Delivery/目标收据；只能运行理解该 schema 的已验证构建，禁止回到旧 PriorityEventQueue 重放。

完成本期要求 E0–E8 的适用门禁及 T01–T15 全部给出证据；若仅交付 E0–E4，应明确标记“独立组件完成，尚未接入”。事件基础设施 E7 可单独验收，但在 E8 未完成时不能宣称整个 Core 已达到严格分层或 Hook 全覆盖。所有状态、提交号和测试数字写修改日志/验收报告，不写 ADR 决策正文。
