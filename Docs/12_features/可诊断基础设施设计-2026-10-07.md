# 可诊断基础设施设计

> 触发动机：2026-10-07 长会话（`206a9b48…`，deepseek-flash / protocol=responses，msgCount 95→216、toolCount 99、prompt 18 万–22 万 token）
> 出现 `LLM 调用失败: Error while copying content to a stream.`。定位结论（请求体上传阶段被对端 RST，内因 `SocketException(10054)`）
> **只能靠人工 grep 三份日志 + 读堆栈**得出，且平台当时**没有记录请求体字节数、尝试序号、失败阶段与 socket 错误码**。
> 本文要解决的不是这一次报错，而是「这类问题下次能不能一次问清」。

---

## 1. 目标与非目标

### 1.1 目标

对一个失败调用，能用**一次查询**回答下面五个问题，且答案来自机器记录而不是人的推断：

| # | 问题 | 现状 |
|---|------|------|
| Q1 | 谁失败了（组件/稳定身份/阶段） | 部分有（`RuntimeActivity` + 组件日志），但阶段粒度不到「写请求体 vs 等响应头 vs 读流」 |
| Q2 | 为什么失败（稳定因果码，而非异常字符串） | ❌ 只有 `llmException.Message` 原样上浮；唯一例外是视觉链路的 `VisionErrorCodes` |
| Q3 | 当时带着什么（请求体字节数、消息数、工具数、尝试序号、耗时、连接/响应头状态） | ❌ 绝大部分没有 |
| Q4 | 是否可以重试、重试了几次、为什么最终放弃 | 部分有（`retried` 指标），但失败终态不携带尝试明细 |
| Q5 | 下次怎么避免/复现（处置建议 + 可在组件边界内红-绿复现的故障场景） | ❌ 靠经验与文档；故障注入散落在具体测试用例里，没有「场景 → 期望结论」对照资产 |

### 1.2 非目标（明确不做，避免过度设计）

- **不引入分布式 tracing 基础设施**（不加 OpenTelemetry/Jaeger/Collector），不新增任何 NuGet：新组件是叶子，`PackageReference = 0`。
- **不记录完整 Prompt / 响应正文 / 密钥**：只记录长度、计数、摘要（hash）与结构统计（沿用 `02-日志位置与埋点约束.md` §9 禁令）。
- **不改重试策略本身**：重试安全边界仍以 `Docs/08_how_debuge/06-延迟问题定位.md` §7.9（仅在未产出任何 delta 前重试传输错误）为准；本设计只让失败**变得可解释**。
- **不新建第二套事实通道**：事实仍走既有 `RuntimeActivity` / `TelemetryMetric` / 组件日志，本设计只补「因果与证据」并统一投影。

## 2. 设计原则（可诊断性四要素）

| 代号 | 原则 | 落地判据 |
|---|---|---|
| **D1 事实** | 任何跨边界调用都留下结构化事实，**失败路径记录得比成功路径更多** | 失败终态必须带 `CauseCode + Phase + Evidence`；成功路径允许只有计数 |
| **D2 因果** | 错误收敛为**稳定错误码 + 可重试性 + 用户可读消息 + 处置建议**，由**纯函数分类器**产出；原始异常只作证据，不作语义 | 分类器是纯函数：输入异常+上下文 → 输出 `DiagnosticCause`，无需宿主即可测试 |
| **D3 关联** | 所有事实携带同一组关联 ID，使一次事故能还原为一条时间线 | `traceId / sessionId / turnId / executionId / parentExecutionId / attempt / phase` |
| **D4 可复现** | 诊断结论必须能用**受控故障注入**在组件边界内复现并断言（红-绿），否则只是猜测 | 「场景 → 注入的异常链 → 期望 CauseCode/可重试性」对照表随组件一起测试 |

**关键架构判断**：D2 与 D4 决定了分类器与场景表必须待在**不含宿主依赖的叶子组件**里。
放在 `PuddingRuntime` 里的话，测一条分类规则要加载 Agent Loop、EF Core、Serilog、ASP.NET——正是 `组件化交付规程` 要避免的（R1/R2/R3）。

## 3. 现状盘点（2026-10-07，只列与诊断直接相关的）

| 已有资产 | 位置 | 诊断能力 | 缺口 |
|---|---|---|---|
| `RuntimeActivity` / `IRuntimeActivitySink` | `Source/PuddingCore/Observability/RuntimeActivity.cs` | 事实信封：component/op/status/时长/`Metadata`/`ErrorCode`/`ErrorMessage` | `ErrorCode` 是自由字符串；无 phase/attempt 维度；`QueryAsync` 只按 trace/session/execution/component |
| `RuntimeTraceContext` | `Source/PuddingCore/Observability/RuntimeTraceContext.cs` | trace/session/execution/parent/subAgent/event/connector | 无 `turnId`、无 `attempt`；执行维度靠 `executionId` 传递 |
| `TelemetryMetric` + sink | `Source/PuddingCore/Observability/TelemetryMetric.cs`、`Source/PuddingPlatform/Services/TelemetryMetricSink.cs` | 指标维度：`llm.chat_stream` 的 started/succeeded/failed/retried | 无字节数维度；失败指标无 cause 维度 |
| 流式诊断累加器 | `Source/PuddingRuntime/Services/DirectLlmClient.cs`（`LlmStreamDiagnosticsAccumulator`）、`Services/AgentExecution/StreamPipelineDiagnosticsAccumulator.cs` | 读耗时/间隔/解析耗时/首块等待/usage | 只在成功路径成型；失败时多数维度为空 |
| 终态错误契约 | `StreamErrorDiagnostic`（`Source/PuddingRuntime/Services/AgentExecutionService.cs`） | `ErrorId/Location/ErrorCode/ExceptionType/HttpStatusCode/Round/...` | `ErrorCode` 取值 `HttpRequestException` 这类**CLR 类型名**，前端只能回显英文原文 |
| 类型化错误样板 | `Source/PuddingCore/Core/VisionErrorCodes.cs` + `VisionPipelineException` | 稳定码 + `UserMessage` + 可重试性注释 | 只覆盖视觉链路，未泛化 |
| 日志路由 | `<dataRoot>/logs/{system,error,components/*,audit}` + `SerilogComponentFilterExtensions` | 按组件分流、按级别分流 | 失败详情分散；跨文件关联靠人 |
| 埋点约束 | `Docs/08_how_debuge/02-日志位置与埋点约束.md` §9（12 个必填字段 + 错误日志五项） | 人读规范 | **无机器门禁**：违反不会变红，只能靠 review |
| 故障注入 | `Source/PuddingRuntimeTests/Services/LlmStreamObservabilityTests.cs`（`FailOnceThenSseHandler`、`FailAfterFirstDeltaHandler`、`ScheduledSseHandler`、`RecordingTelemetrySink`） | 已有真实形状的注入先例 | 用例局部、不可复用、无「期望诊断结论」对照 |

**一句话差距**：事实有了、因果没有；记录有了、证据不够；规范有了、门禁没有；注入有了、资产没有。

## 4. 架构：一个叶子组件 + 单向适配

```
                    ┌───────────────────────────────────────────────┐
                    │  PuddingDiagnostics  （叶子 · ProjectReference=0）│
                    │                                               │
                    │  ① 契约      CauseCode / Cause / Phase /       │
                    │              Evidence / Fact / Classifier 接口  │
                    │  ② 分类      *FailureClassifier（纯函数）       │
                    │  ③ 证据      EvidenceBudget / 摘要 / 计数        │
                    │  ④ 脱敏      DiagnosticRedactor                │
                    │  ⑤ 投影      IncidentProjector（事实→事故视图） │
                    │  ⑥ 场景      FaultScenario 表 + 注入器（测试资产）│
                    └───────────────────────────────────────────────┘
                          ▲                    ▲                ▲
             单向引用（编译期强制，调用方不得被反向引用）
                          │                    │                │
        ┌─────────────────┴──┐   ┌─────────────┴───┐   ┌────────┴─────────┐
        │ PuddingCore 网关族  │   │ PuddingRuntime   │   │ PuddingPlatform   │
        │ OpenAi/Responses/   │   │ DirectLlmClient  │   │ Sink/投影/API     │
        │ Anthropic           │   │ AgentExecution   │   │ 诊断包            │
        └────────────────────┘   └──────────────────┘   └───────────────────┘
```

### 4.1 边界硬规则（编译期 + 机器断言）

1. `PuddingDiagnostics`：`ProjectReference = 0`、`PackageReference = 0`。**唯一允许的程序集是 BCL**（含 `System.Net.Http`/`System.Net.Sockets`——分类器必须能识别 `HttpRequestException` 与 `SocketException`，故**不**像 `PuddingVectorIndex` 那样移除 `System.Net.Http` implicit using）。
2. 组件内检索消费方程序集名（`PuddingCore`/`PuddingRuntime`/`PuddingPlatform`/`PuddingHost`/`PuddingAgent`）⇒ **0 命中**；不得出现 `Serilog`、`Microsoft.EntityFrameworkCore`、`Microsoft.AspNetCore`。
3. 消费方**只做适配**：把自己的事实形状映射为组件的 `DiagnosticFact`，不得要求组件反向理解宿主类型。
4. 组件不持有配置、不读文件、不写日志 sink：它只做**纯计算**（分类/预算/脱敏/投影）。

### 4.2 为什么是「叶子 + 适配」而不是「往 Runtime 里加日志」

- 加日志的实现方式无法被断言：没有能取红的用例，规则会在后续重构里静默失效（`组件化交付规程` §3.2「把能编译当成已测试」）。
- 分类规则与场景表是**跨层知识**（HTTP/传输/协议/取消/限流），放在任一消费方都会让另一个消费方重复实现或反向依赖。
- 叶子组件可以在**宿主运行中**构建与测试（R1），诊断规则迭代不需要重启 Core——这正是本次事故里最缺的能力。

## 5. 契约（字段级，Stage 1 落地）

### 5.1 稳定因果码 `DiagnosticCauseCode`（string 常量，落库/日志/前端共用同一字符串）

| 组 | 码 | 含义 | 可重试 |
|---|---|---|---|
| 传输 | `transport.request_upload_reset` | 写请求体时连接被对端重置/关闭（本次事故） | 是（未产出 delta 前） |
| 传输 | `transport.response_read_reset` | 读响应体时被重置 / `ResponseEnded` | 是（未产出 delta 前） |
| 传输 | `transport.connect_failed` | TCP 连接建立失败 | 是 |
| 传输 | `transport.dns_failed` | 域名解析失败 | 视策略 |
| 传输 | `transport.tls_failed` | TLS 握手/证书失败 | 否（多为配置） |
| 传输 | `transport.first_chunk_timeout` | 首块看门狗超时 | 是 |
| 传输 | `transport.stream_idle_timeout` | 流中空闲看门狗超时 | 否（已产出内容即不可重试） |
| 传输 | `transport.http_client_timeout` | `HttpClient.Timeout` / 传输层取消 | 是（未产出 delta 前） |
| 服务商 | `provider.http_401_403` | 鉴权/权限 | 否 |
| 服务商 | `provider.http_400` | 请求被拒（含协议/参数错误） | 否 |
| 服务商 | `provider.http_404` | 端点/模型不存在 | 否 |
| 服务商 | `provider.http_429` | 限流 | 是（退避） |
| 服务商 | `provider.http_5xx` | 服务商故障 | 是 |
| 服务商 | `provider.protocol_invalid` | SSE/JSON 解析失败、协议与路由不符 | 否 |
| 服务商 | `provider.request_too_large` | 请求体超限（本地 48 MiB 闸或服务商限制） | 否 |
| 本地 | `local.cancelled` | 外部取消（用户/父 Run） | 否 |
| 本地 | `local.circuit_open` | 熔断器打开 | 是（恢复窗后） |
| 本地 | `local.rate_limit_wait_cancelled` | 并发槽位等待被取消 | 否 |
| 视觉 | `vision.*` | 直接沿用 `VisionErrorCodes` 既有码 | 按既有裁定 |

> 码表是**契约**：新增码必须同时补「场景 → 期望码」用例与用户消息，否则测试取红。

### 5.2 `DiagnosticCause`

```csharp
public sealed record DiagnosticCause
{
    public required string Code { get; init; }            // DiagnosticCauseCode
    public required string Category { get; init; }        // transport|provider|local|vision
    public required bool Retryable { get; init; }
    public required DiagnosticPhaseKind Phase { get; init; }
    public required string UserMessage { get; init; }     // 中文、可直接进聊天终态
    public required string RemediationHint { get; init; } // 处置建议（网络/代理/重试/降上下文）
    public required IReadOnlyDictionary<string, string> Evidence { get; init; }
}
```

### 5.3 阶段 `DiagnosticPhaseKind` 与「怎么知道是写请求体」

`Build → Serialize → RequestUpload → AwaitResponseHeaders → ReadResponseStream → Persist → Unknown`。
客户端**能**区分的关键信号（全部机器可判，且各有一条用例）：

| 观测 | phase 判定 |
|---|---|
| 异常链中出现 `HttpContent.CopyToAsync` / `SendRequestContentAsync` 帧 | `RequestUpload`（本次事故的确凿指纹） |
| 异常发生在 `SendAsync` 且无上述帧、且 `responseHeadersReceived == false` | `AwaitResponseHeaders` |
| 异常发生在首个 delta 之后或响应头已到 | `ReadResponseStream` |
| 异常来自 SSE 解析（`JsonException` 等） | `protocol_invalid` + `ReadResponseStream` |

> 这是**启发式但可断言**：场景表把「真实观测到的异常链」原样注入，断言分类结果；不是靠读代码猜。

### 5.4 证据 `Evidence`（有界、可脱敏）

必填（失败路径）：`provider_id`、`model_id`、`endpoint_host`、`attempt`、`max_attempts`、`phase`、`failure_after_ms`、`since_dispatch_ms`、`response_headers_received`、`request_bytes`、`message_count`、`tool_count`、`exception_chain`（每层 `Type:Message`）、`socket_error_code`（若有）。
预算：单值 ≤ 512 字符、键数 ≤ 32、总量 ≤ 8 KiB，超出标 `evidence_truncated=true`（`EvidenceBudget`）。
脱敏：`DiagnosticRedactor` 对 `apiKey/authorization/token/secret/prompt/content/body` 类键直接掩码，且 URL 去 query。

### 5.5 事故视图 `IncidentView`（Q1–Q5 的答案形状）

```csharp
public sealed record IncidentView
{
    public required string TurnId { get; init; }
    public required string TerminalStatus { get; init; }
    public DiagnosticCause? RootCause { get; init; }
    public required IReadOnlyList<IncidentAttempt> Attempts { get; init; } // attempt/phase/cause/durationMs/requestBytes
    public required string Conclusion { get; init; }   // 一句话中文结论（含数字）
    public required IReadOnlyList<string> EvidenceLinks { get; init; } // errorId / 日志文件 / 事实行 id
}
```

## 6. 可复现：故障场景资产（D4 的载体）

组件内提供 `FaultScenario` 表（BCL-only）与注入器：每个场景 = 名称 + 注入的异常/响应 + **期望 CauseCode + 期望可重试性 + 期望 phase**。

首批场景（覆盖本次事故与相邻故障）：

| 场景 | 注入 | 期望码 |
|---|---|---|
| `reset_during_request_upload` | `HttpRequestException("Error while copying content to a stream.", IOException(SocketException(10054)))`，链中含 `HttpContent.CopyToAsync` | `transport.request_upload_reset` / RequestUpload / 可重试 |
| `reset_during_response_read` | `HttpIOException(ResponseEnded)` | `transport.response_read_reset` / ReadResponseStream |
| `tls_handshake_failure` | `AuthenticationException` 内因 | `transport.tls_failed` |
| `dns_failure` | `SocketException(11001)` | `transport.dns_failed` |
| `http_401` / `http_429` / `http_503` | `HttpRequestException(inner:null, StatusCode)` | 对应 provider 码（401 不可重试，429/503 可重试） |
| `sse_parse_failure` | `JsonException` 在首个 delta 前 | `provider.protocol_invalid` |
| `first_chunk_timeout` / `idle_timeout` | `TimeoutException`/`OperationCanceledException` + 上下文标志 | 对应传输码 |
| `external_cancellation` | `OperationCanceledException` + `userCancelled=true` | `local.cancelled` / 不可重试 |
| `circuit_open` | 熔断异常 | `local.circuit_open` |

**取红要求**：每条场景至少一条用例；新增码缺场景 ⇒ 红。场景表同时是 `Docs/08_how_debuge` 的**可执行版本**（文档负责「怎么判读」，场景表负责「判读规则是错的会红」）。

## 8. 验收判据（本次事故的「可诊断」定义）

以 2026-10-07 `206a9b48…` 那一轮为基准，改造后必须能用**一次查询**输出：

1. 终态：`turn.failed`，`errorId`，`round=2`，`consecutiveLlmFailures=1`；
2. 三次尝试明细：`attempt=1/2/3`、`phase=RequestUpload`、`durationMs≈20310/54290/20093`、`request_bytes`、`max_attempts=2`；
3. 根因：`transport.request_upload_reset`（`socket_error_code=10054`），结论句含「请求体 X MiB 上传阶段被对端重置，重试耗尽」；
4. 处置建议：网络/代理 A/B、上下文与工具集瘦身（本次上下文 18 万–22 万 token、99 个工具）；
5. 证据链接：`errorId`、日志文件与时间戳、`runtime_activity` 行 id。

并且在组件测试内，`reset_during_request_upload` 场景可**离线复现**同一结论（无需网络、无需 Core）。

## 11. 二次勘察补充（2026-10-07，本文档发布后的加深事实）

> 来源：三路只读勘察（事实采集链路 / LLM 调用链 / 诊断消费面与约定），全部带 `file:line`。
> 本节把新发现**并入裁定**；与前面章节冲突时以本节为准。

### 11.1 新增稳定码（补齐诚实兜底）

| 码 | 含义 | 可重试 |
|---|---|---|
| `transport.unclassified_failure` | 传输失败但现有信号不足以定性（例如有 RST 却无阶段指纹、也无响应头） | 是（未产出增量前） |
| `local.unclassified_failure` | 本地失败且无既有语义码可用 | 否 |

新增阶段 `queued`（等待并发槽位）：限流等待发生在请求构造之前，此前没有对应阶段，导致
`local.rate_limit_wait_cancelled` 无法归位。

### 11.2 查询面：把「静默截断」变成显式事实（新增强制项）

实测缺口：`RuntimeActivityQuery` 只支持四个字段精确相等、无时间窗 / 无 status 与 operation 过滤 /
无 offset 与升序；`RuntimeActivitySink.QueryAsync` 把 `Limit` 硬 clamp 到 500，而
`AgentDiagnosticsTool` 索要 500/2000 并在内存里分组，`diagnose` 还把截断后的数据当时间窗结论。

⇒ 裁定：诊断查询必须走 `DiagnosticFactQuery` / `DiagnosticFactPage` 形状（过滤维度 + 分页 +
**`Truncated` 标记**），且时间窗过滤下推到存储层。**禁止**再出现「先全量物化再内存过滤时间」
（`TelemetryMetricsController` 现状）与「截断后当全量解释」。

### 11.3 写入路径必须脱敏 + 有界（新增强制项）

实测缺口：既有 `DiagnosticRedactor` 只在**一个控制器的响应期**生效；`RuntimeActivitySink`、
`TelemetryMetricSink`、`SessionTimelineRecorder` 写入时完全不脱敏；其敏感键判据是**键名整串相等**，
`llm.apiKey` / `authorization_header` / `myToken` 会穿透；`metadata_json` / `dimensions_json`
在库里是**无长度约束的 TEXT**（实测已到数百 MB 量级），只有 `debug_json` 有 16 KiB 上限。

⇒ 裁定：所有证据值产生时即过本组件的 `DiagnosticEvidenceBuilder`（脱敏 + 预算 + 截断标记），
不允许任何写入路径「先落库、后脱敏」。`metadata_json` / `dimensions_json` 需要服务端上限。

### 11.4 事实通道的可靠性：诊断不得反噬业务（新增强制项）

实测缺口：`RuntimeActivitySink` / `TelemetryMetricSink` 写失败即 **rethrow**，而约 29 处业务路径直接
`await`（例如 `PriorityEventQueue.Enqueue`），`SafeRecorder` 只有 1 个调用方；另有 3 处 fire-and-forget
静默丢异常，且无丢弃计数；`TelemetryMetricSink` 的类注释声称「只记 warning 不阻断」与实现相反。

⇒ 裁定：事实写入是**旁路**。默认语义改为「记错误 + 计数 + 不抛出」（可显式选择 fail-closed 的关键
事实除外，且必须在其调用点写明理由）；补齐 `diagnostics.facts_dropped` 计数与注释/实现一致性。
原则：**一个会拖垮业务链路的诊断层，比没有诊断层更糟。**

### 11.5 关联维度与索引（新增裁定）

- `RuntimeTraceContext` 缺 `turnId`，事实表无 `attempt`；实体未落 `AgentInstanceId/AgentTemplateId`
  （查询侧永远拿不到）；`RuntimeActivityExecutionLifecycleRecorder` 把父 ActivityId 塞进
  `CorrelationId`，与 trace 语义冲突。
- ⇒ 新增可查询维度：`turn_id`、`attempt`、`cause_code`、`phase`、`request_bytes`（落列并建索引，
  与 `runtime_activity` 既有 14 天 / metadata 7 天的保留口径一致，遵循 ADR-076 的语义类型 ID）；
  父指针用独立列，不复用 `CorrelationId`。

### 11.6 消费面（新增裁定）

- **后端是唯一文案来源**：前端 `chatDiagnostics` 优先回显后端 markdown（`looksLikePersistedErrorDiagnostic`
  是原始子串匹配），`execution_stalled` / `execution_timeout` 在 `src/` **零命中** ⇒ §7.8 要求的
  「前端错误码映射」实为空缺。⇒ 终态 DTO 增 `CauseCode` / `RemediationHint` / 有界 `Evidence`，
  前后端都按码映射；未知码必须显示原码（沿用 `GOAL_BLOCKER_CODES` 的既有纪律）。
- **诊断包**：Desktop 包只有 `runtime.json` + 500 行 Core stdout + 配置键名，且 WinUI 产品里**无入口**；
  `Tools/Diagnostics/export_session_bundle.py` **完全未脱敏**，与「生成诊断包前再次检查脱敏」的文档规则相悖。
  ⇒ Stage 4 纳入 LLM 传输事实（长度 / 阶段 / 因果 / 尝试），并给 Python 导出补脱敏与 manifest 校验。
- **在制品工具文案**：`AgentDiagnosticsTool` 仍称活动库「可能是内存存储」，与 SQLite 落库实现相反，
  会同误导诊方向 ⇒ 一并更正。
- **对齐既有纯分类器**：`RuntimeDiagnosisEngine`（PuddingRuntime）已经是「纯函数 + 稳定 `DiagnosisCodes`
  + 证据不足报 unknown 而非 healthy」的既成范式。本组件的因果层是它的**单次调用粒度**输入，
  命名与「unknown ≠ healthy」纪律必须一致，不另立第二套语义。

## 12. 界面呈现与「一键复制现场」（用户诉求，Stage 4 的交付定义）

### 12.1 问题（截图实证）

界面上的失败只有一行 **原始英文异常文本**（`LLM 调用失败: Error while copying content to a stream.`）+ 一个「重试」：
用户看不懂「这是什么错」，维护者也拿不到能定位的东西；要复现就得让人去 grep 日志，而这正是本设计要消灭的成本。

### 12.2 两层契约（简略给人看，完整给机器读）

| 层 | 类型 | 内容 | 谁消费 |
|---|---|---|---|
| 简略 | `ErrorPresentation`（`Presentation/ErrorPresentation.cs`） | **错误标题**（一眼可识别类别）、大概原因（一句话）、严重度、是否可重试、建议动作、稳定因果码、类别 | 聊天错误卡片、看板、徽标 |
| 完整 | `DiagnosticReportDocument`（`Presentation/DiagnosticReportDocument.cs`） | 版本化 schema、**捕获时间(UTC)**、`errorId` / `traceId` / `turnId` / `sessionId` / `executionId` / workspace / agent、因果码 + 类别 + 失败阶段、尝试明细（attempt/phase/durationMs/requestBytes）、证据（含**异常链**）、**日志定位提示**、处置建议 | 「复制诊断信息」/「下载 JSON」；维护者与 AI |

渲染：`RenderText()` 供人读与直接粘贴（确定性输出），`RenderJson()` 供机器读（缩进、枚举字符串、证据键序稳定）。
上限 64 KiB，**超出即显式标注「报告已截断」**（不允许悄悄变短）；所有值在进入证据时已经过脱敏。

### 12.3 硬规则（由用例锁住）

1. **标题与简略原因不得出现异常类型名或英文原文**（`Exception` / `HttpRequestException` / `Error while copying` … 一律禁止）。
2. **未知码必须原样显示**（`vision_provider_file_expired`、`something.brand_new` 都要看得见），沿用 `GOAL_BLOCKER_CODES`
   「unknown 不得折叠成已知」的既有纪律。
3. **复制内容必须自带定位四件套**：捕获时间(UTC) + `errorId` + `traceId` + 稳定因果码；缺任何一项则无法从海量日志定位。
4. **必须给日志定位提示**（按真实目录）：`logs/error/pudding-error-*.log` 搜 `errorId=`、
   `logs/components/llm_gateway/` 搜 `traceId=`、`logs/diagnostics/session-timeline/` 按 `sessionId` 取当日 JSONL、
   `conversation_events` 按 `turn_id` 取终态事件。
5. **UI 只做两件事**：展示标题 + 大概原因 + 动作（重试/检查配置），并提供「复制诊断信息」与「下载 JSON」；
   技术堆栈不铺在界面上，放在复制载荷里。

### 12.4 后端 → 前端的数据流（Stage 4 施工清单）

1. `StreamErrorDiagnostic` 扩展：`CauseCode`、`Title`、`ShortCause`、`RemediationHint`、`ReportVersion`
   （现有字段保留；`ProviderId` 硬编码为 null 的缺陷一并修）。
2. 终态 SSE（`error` 帧与 `done` 帧的扁平键）带上上述字段 + `EvidenceJson`（有界）。
3. 前端不再「回显原始 message」：`chatDiagnostics` 从**文本子串匹配**改为**按码映射**（未知码显示原码），
   错误卡片 = 标题 + 大概原因 + 重试 + 复制/下载；历史消息保留同一载荷以便随时复取。
4. 复制到剪贴板 = `RenderText()`；下载 = `RenderJson()`（文件名含 `errorId` 与时间，便于归档）。
5. 相关既有缺口一并处理：Desktop 诊断包纳入同一载荷；`Tools/Diagnostics/export_session_bundle.py` 补脱敏。

> 纯计算部分（呈现目录、报告渲染、脱敏与预算、截断标注）**已在本轮组件内实现并有 6 条用例**；
> 上述 1–5 的接线属 Stage 4，需改宿主与前端（前端改动须递增 `package.json` 版本并重新构建部署）。

## 13. Stage 3 落地记录：诊断事实采集接线（2026-10-07）

### 13.1 接线形状（为什么是「作用域」而不是「到处传参」）

事实的产生方与持有方是分开的：**请求体字节数、真实 HTTP 派发次数、是否已收到响应头、失败阶段**只有网关知道；
而**异常与重试语义**只有 `DirectLlmClient` 持有。为此在 `PuddingCore` 增加一个**同一调用内**的事实容器：

- `Source/PuddingCore/Observability/LlmCallDiagnosticsScope.cs`（`AsyncLocal`，`IDisposable` 嵌套恢复，可变字段 + 计数器）：
  调用方 `Begin()` → 网关侧 `MarkDispatch(bytes)` / `MarkHeaders()` / `MarkReadStream()` 写入 → 调用方分类时 `ToContext()` 读取。
- 边界：它**只是事实容器**（不含分类、不做 IO、不写日志）；依赖方向 `PuddingCore → PuddingDiagnostics`（仍然向下），
  因此网关能使用叶子组件的 `DiagnosticPhaseKind` / `DiagnosticCauseCode`，而不是另造一套字符串。

### 13.2 网关写入点（三个协议都覆盖流式路径）

| 网关 | 写入点 |
|---|---|
| `ResponsesLlmGateway` | `CreateRequest` 计算字节数并 `MarkDispatch`（体积闸门命中时置 `RequestTooLarge` 覆盖码）；重发路径再次 `MarkDispatch`（**静默重发现在可见**，`dispatch_count` 会变成 2）；两处 `SendAsync` 之后 `MarkHeaders` |
| `OpenAiLlmGateway` | `ChatStreamAsync` 构造请求体后 `MarkDispatch`；`SendAsync` 之后 `MarkHeaders` + `MarkReadStream` |
| `AnthropicMessagesLlmGateway` | 同上 |

### 13.3 分类与落库

- `Source/PuddingRuntime/Services/LlmFailureDiagnostics.cs`：把作用域折成分类器输入、调用叶子分类器、
  把结论摊平成活动元数据键（`cause_code` / `cause_category` / `cause_phase` / `cause_retryable` / `cause_rule` /
  `cause_message` / `cause_remediation` / `request_bytes` / `attempt` / `max_retries` / `dispatch_count` /
  `response_headers_received` / `socket_error_code`）。
- `DirectLlmClient`：
  ① 每次流式尝试 `Begin()` 一个作用域，写入 provider/model/host/attempt/maxRetries；
  ② 在取消/首块超时/HTTP 超时/产出增量的分支上设置对应标志（保证分类不会把看门狗超时误判成用户取消）；
  ③ **在唯一出口 `RecordActivityAsync` 做分类**：失败活动与指标的元数据都被合并、
     `ErrorCode` 由「CLR 类型名」改为**稳定因果码**（不写因果码的调用点因此天然被覆盖）；
  ④ `[DirectLlm] STREAM ERROR` / `STREAM RETRY` 日志行带上 `cause/phase/retryable/requestBytes/dispatchCount/attempt`。
- 分类判据新增一条**比堆栈指纹更可靠**的生产路径：`MarkDispatch`（紧接请求体交给 HttpClient 前）与
  `MarkHeaders`（仅在收到响应头后）由网关自己记账，因此「阶段=上传请求体 且 连接被重置」直接定性为
  `transport.request_upload_reset`（规则名 `phase_hint:request_upload`）；堆栈帧指纹继续作为第二条判据。

### 13.4 验收证据（本轮实测）

### 13.5 尚未接线（诚实登记，Stage 4 继续）

- `ChatAsync`（非流式 `chat`）路径尚未 `Begin()` 作用域：其失败仍会得到稳定因果码，但**没有请求体字节数**。

  因此「按因果码查一轮事故」目前仍需元数据扫描；列与索引随 Stage 4 的查询面一起做。

### 15.1 为什么需要
