# CORE-I1-06 单次模型发送与租约结算

**核心单由主代理执行。** 开工依赖为 CORE-I1-05 的受管 Work、限额、模型绑定和可信作用域合同通过评审。范围是普通 Work 的 buffered/streaming 传输。集成验收要求一次实际模型推理发送对应一个独立 attempt，provider 调用、持久账本和并发槽的生命周期可以逐条对应。

## 代码范围及接口责任

| 位置 | 主代理的工作 |
|---|---|
| `Source/PuddingRuntime/Services/LlmInvocationService.cs`、`IRuntimeLlmClient.cs`、`DirectLlmClient.cs` | 盘点 facade 当前 Begin/Settle/Unknown 与客户端缓冲重试、流首 delta 前重试，明确每条受管路径的单一计费者 |
| `Source/PuddingCore/Core/OpenAiLlmGateway.cs`、`AnthropicMessagesLlmGateway.cs`、`ResponsesLlmGateway.cs` | 定位真正的推理 SendAsync。特别覆盖 `ResponsesLlmGateway.SendWithFileRebuildAsync` 的首次与重建后发送；文件上传等非推理请求单列。复用原 HTTP 管线前检查其隐式重试配置 |
| `Source/PuddingExecutionResources.Contracts/ModelAttemptBudgetPort.cs`、`Services/ExecutionBudgets/ModelAttemptBudgetGate.cs`、`PlatformModelAttemptBudgetPort.cs` | 按需补足预留与派发间撤销、真实代际验证、缺 usage/结算回执丢失调和。账本已有 Reserve、MarkDispatched、Release、Settle、MarkUnknown 语义，复用其唯一状态 |
| `Source/PuddingModels/ModelLeaseRegistry.cs`、Host 组合根与内部窄适配 | 受权配置拥有模型 generation，使用真实池取得/释放并发槽。显式 busy/排队策略沿既有语义，等待期间响应父取消；避免对单次活动同时占用两个同职责槽 |

表中不带 Source 的预算适配器归属 `Source/PuddingPlatform/Services/ExecutionBudgets/`。主代理先列出选定传输接缝、各协议/HTTP 重发点、其他客户端调用者及精确文件单。叶任务不可增改端口。现有 Review 走 `HostRuntimeLlmChatClient` 且有自己的预算路径，回归其语义并防止重复扣账。

## 单次发送合同

1. Work 与逻辑 Invocation 在重试期间稳定，每次新的模型推理发送使用新的 AttemptId。接收同一 attempt 的重放/结算回执必须幂等；有已派发或不确定记录时不能用同一许可重发。
2. 获取并发槽后，检查父取消、deadline、owner epoch 与模型代际。取得实际时点、版本、币种吻合的报价，冻结费率并以最终请求的输入界限和实际输出上限预留。现有 gate 用请求的 PriceVersion 记账，须核对 `quote.PricingRuleVersion`，并核对实际模型、窗口与币种。若模型配置允许更多输出，应在发送请求中收紧到所预留上限。跨窗口重试重新报价。
3. 持久派发许可紧邻传输。已证实未派发的 reservation 可 Release；持久派发与网络提交之间进程中断且无法证明未发送时，恢复为 Unknown。没有分布式事务可以同时提交本地账本与远端发送，审计应保留这个不确定窗口。
4. 成功以本次 usage 与冻结报价结算；缺 usage 或已发但效果不明，保留 Unknown。事务已提交但响应丢失时按同一 attempt 查询/幂等恢复；不得再次派发、重复退款或把已结算结果改 Unknown。父取消/客户端提前停止读取后，清理使用独立、有界的 token，并在底层实际退出/证实终止后释放槽位。
5. 确定允许的自动重试条件，继承协议原有次数、首 delta 和文件恢复语义。需要下一次发送时必须重新过账本及租约；预算不足/已取消阻断第二次。对未知外部效果采用既有受权重试策略，记录原因；流已对外发布内容后不得重放旧前缀。记录 provider 忽略取消时仍占用的资源。只记账一次的位置不能同时在 facade 和传输层重复准入。

## 离线集成矩阵

真实 mapper、SQLite 账本、gate、租约组件、Runtime 和被测重试/网关均参与。替换位于最末端的 provider 或 HTTP handler，不在重试循环上方用“重试成功”的 fake 代替。以屏障/可控时钟安排竞争，记录 handler 发送计数、每条 ID/报价/状态、根/叶账目和活跃槽。

| 场景 | 可取红的结果 |
|---|---|
| T1 正常，含流式 usage | 推理发送 1、派发许可 1、结算 1；设备/文件准备过程不产生推理计费记录 |
| T2 可重试错误及额度耗尽 | 允许两次时共发 2，两个不同 attempt、同一逻辑调用，账户反映两次；根 MaxCalls=1 时仅发 1 |
| T3 两个隐藏重试点 | 分别实际触发流首 delta 前重试、Responses 文件过期重建；逐次授权，裁掉第二次准入则测试红；首 delta 后不重复输出 |
| T4 取消竞争 | 等待槽、预留至派发间取消时发送 0，确认未发送的预留释放；真实发送后取消且 provider 暂不退出，槽仍占用，退出后归还一次 |
| T5 真实报价 | 错币种、revision/priceVersion 不匹配、过期报价时禁止以旧价发送；显式免费模型可用；账本的版本/费用对应实际采用报价 |
| T6 故障恢复 | 缺 usage、消费端提前退出、结算提交前失败/提交后回执丢失、进程中断重开同库，均可区分已结算与未知，零重复派发 |
| T7 降级与代际 | 旧模型代际、失效 owner epoch、缺端口、受管路径落入直连分支的故意变异均被发现；未迁移 Review/旧路径有回归 |

验收记录应把 `Handler.SendAsync` 的**模型推理**次数与 attempt 行逐条相连，同时给出最终 usage、Unknown/Reserved 和槽数；恢复故障案例单列不确定记录。任一受支持的受管协议仍能绕开限制时，记录具体入口并保持该入口未启用。由独立复核者使用独立构建和测试目录按[批次规程](A阶段第二批施工任务书-2026-11-07.md)复跑。后续阶段 B 或产品验证沿用两阶段计划。
