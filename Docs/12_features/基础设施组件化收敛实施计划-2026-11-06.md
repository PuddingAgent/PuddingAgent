# 基础设施组件化收敛实施计划

本计划以[源码评估](../14_reports/2026-11-06-基础设施组件化评估与接入缺口.md)为基线，优先补基础设施，暂不把 Goal 自动评审接入当作下一项主任务。这里的接口名称是施工建议，不是已发布契约；需要改动冻结契约时由主代理审阅调用者与测试后重签，不由叶任务自行改指纹。

**目标包含软件功能插件化，不限于 Agent 工具。** 工具、命令、事件消费者、业务策略、渠道与受控界面贡献使用同一插件生命周期和公共能力边界，按类型逐步交付。通用机制与扩展语义以[公共 API 规划](核心组件与插件公共API规划-2026-11-04.md) §1.1、§10 为准。基础设施与通用插件机制是 Goal 的前置；DS-I1-04 等已派发叶任务的白名单不因本计划扩大。

**阶段目标以[两阶段交付合同](基础设施服务生命周期与最小原型两阶段目标-2026-11-07.md)为准：先完成 A 基础设施，再组合 B 最小原型。** I0～I4 是 A 的组件工作包，须补齐组件/实例清单、合同卡、生命周期、事件/订阅和 Hook 的定义、实现与独立证据。B 使用真实组件完成公共 API → Work → 工具 → 产物事件 → 非工具功能插件的最小组合；I5 Goal 接入在 B 之后，不占用本轮基础目标。

## 1 目标与依赖边界

上层通过**受权环境与服务、可查询实例引用、可观察操作回执**使用基础设施；Agent 引用和 Work 是其中的领域对象，非 Agent 功能不必创建它们。Agent 配置读取/修改不暴露 JSON/数据库；枚举不启动推理；工作受理不等于完成；取消受理不等于底层调用已经停止。

依赖方向保持：

```text
插件 / 上层模块 → 公共契约、SDK → 宿主绑定的窄门面
                                     ↓
                              独立领域组件 → 自己的端口
                                     ↑
                      Platform / Runtime 适配现有业务权威
                      Host 只负责装配与可信入口
```

不能把 `IServiceProvider`、DbContext、凭据、Runtime Agent 对象或完整宿主上下文交给插件。新组件不反向引用适配层，已有公共契约和 SDK 保持无存储/宿主依赖。

推荐区分三种作用域，而不是创建一个包含所有系统的大 Context：

| 作用域 | 内容与用途 | 谁创建 |
|---|---|---|
| 调用方/工作区 | actor 来源、工作区、能力 grant、有效期、grant generation；目录/配置查询使用 | 管理认证入口、插件加载器或后台 Job 恢复入口 |
| 执行 | canonical Work/Run、父 Work、根预算、deadline、取消链；执行/委派/付费算子使用 | Work 受理及运行生命周期权威 |
| 模型 attempt | 冻结路由/配置/报价、attempt 身份、预留、并发槽、派发/终结状态 | 单次模型调用协调器 |

公开调用方可以指定要操作的对象和请求限制，不能自行决定可信 actor、预算根或授权范围。读取无需伪造执行作用域；执行根只能从受权 Work 创建路径获得。

## 2 优先级与施工包

### I0：先校正作用域与所有权契约

**主代理负责；是后续接入的前置，不单独扩张为平台重写。**

影响文件：`PuddingAgents.Contracts/AgentPorts.cs`、`Pudding.Api.Contracts/AgentDirectory.cs`、现有资源契约、相关调用方工厂。

- 将目录/配置所需的读取 binding 与执行/委派 binding 分开；复用现有 caller/grant 类型能表达的部分，不平行复制身份模型。
- 给 Work、Task、Turn、Run、Goal 的映射指定唯一适配位置；禁止字符串强行互换。
- 明确 Get/List 返回借用引用，Create 创建持久 Agent 实例但不自动启动模型，Submit 创建/复用 Work 回执，Acquire 返回须释放的资源租约。
- 配置继续由现有配置权威执行版本化 Patch；保留 revision 冲突、幂等操作回执及变更事件，不暴露任意配置文件写入。
- 运行中模型调用保留冻结配置；新配置只影响新的绑定/派发，不能改写已经执行的 attempt 账目。
- 持有计时器、取消源或槽位的绑定必须有明确释放者；不把生命周期藏在仅返回业务 API 的工厂里。

验收：无 Work/预算的受权调用可枚举 Agent；跨工作区和过期 grant 被拒；枚举/配置读取不触发 provider；保存的旧句柄不能在撤权或卸载后启动新工作。

### I1：收敛单次模型执行的预算、取消和租约

**最高代码优先级；主代理负责状态机、契约与主执行接线。**

主要位置：

- `PuddingRuntime/Services/LlmInvocationService.cs`
- `PuddingRuntime/Services/DirectLlmClient.cs`
- `PuddingRuntime/Services/AgentExecution/AgentExecutionLlmInvoker.cs`
- `PuddingExecutionResources/ModelResourcePool.cs` 及其 Contracts
- `PuddingPlatform/Services/ExecutionBudgets/PlatformModelAttemptBudgetPort.cs`
- `PuddingPlatform/Services/Reviews/DurableModelResourcePool.cs`、`ReviewEvaluationBinder.cs`
- `PuddingHost/Services/HostRuntimeLlmChatClient.cs` 与 DI 装配

步骤：

1. 先修复已复现的缺端口放行、流创建保护范围、过早标记 settled、身份不匹配问题。Enforced 绑定缺组件必须在 provider 前失败；非受管旧调用必须显式分类，不能靠 null 隐式豁免。
2. 建立一次真实传输 attempt 的协调机制：冻结输入 → 等待全局并发准入 → 原子预算预留及派发许可 → 派发 → 结算/Unknown → 实际退出后释放槽位。排队、预留、撤销间的失败均有明确终态；dispatch 前再次核对取消/租约代际。
3. 明确一个权威重试层。每次重试单独预算身份、重新准入；禁止外侧一次预留包住隐藏的多次 provider 请求。优先抽出单次 gateway 端口，由现有客户端的重试策略调用它，避免改变产品重试语义。
4. 内存/持久实现只替换预算存储策略，共享取消、timeout、并发和排空状态机；避免两个 pool 各实现一遍生命周期。先独立测试这部分，再接入 Runtime。
5. 绑定真实 Work 身份，接通主 Agent；随后子代理、工具内分类/验收和后台 Review 逐条迁移。每个调用路径只预留一次。迁移台账必须列出仍可直达 provider 的调用点。
6. 保留 Unknown 和真实 usage 的区别；结算失败或响应丢失按 attempt 幂等调和。Unknown 不返还已派发预留，不把零值 receipt 当已确认用量。
7. 正确传播 MaxOutputTokens、父 deadline 与取消；停止观察不释放仍在运行的 provider 槽。进程恢复后的账户 owner epoch/fencing 与租约恢复采用同一权威。

验收必须取红：缺 gate 的两种路径、stream/iterator 创建异常、结算提交前/提交后响应丢失、兄弟工作并发耗尽根预算、取消与派发竞争、provider 忽略取消、父退出、重试两次分别记账、配置代际变化、流消费者提前 break。静态扫描加测试计数证明所有目标入口均到达同一 attempt 端口。

### I2：交付可被上层直接使用的 Agent/子代理入口

影响位置：`PuddingAgents`、`PuddingPlatform/Services/AgentWork/`、`WorkspaceAgentFileService`、`SubAgentPool`、`Pudding.Api.Sdk`。

- 实现现有 `IAgentFactoryApi` 与 directory 的受权宿主适配，继续以现有配置服务为写入权威。
- Work Observe/Cancel 接 canonical 事件与取消入口；不能为 SDK 另起一套 Work 状态。
- 为 `IChildWorkSubmitter`、`ISubAgentLeasePool` 实现现有子代理系统适配；同一个池中原子 acquire/release，父归属、generation 和租约过期必须核对。
- 提供类型化工厂获取受权门面。SDK 的 Agent 对象只是稳定引用及便捷方法，不启动宿主、不自己创建数据库或 LLM 池。
- Borrowed Agent 引用不需要 Dispose；owned lease/scope 必须可显式释放；创建 Agent 与发起执行分开，避免构造函数产生隐式费用。

**I2 的组件消费验证**使用一个只引用 Contracts/SDK 的上层消费者，在隔离工作区读取/修改配置、取得 Agent、Submit、Observe、Cancel；使用真实适配、隔离存储和 fake provider，验证预算与取消到达调用边界，并补齐 factory 与父子委派。它是 A 的局部证据，不代表 A 完成或 B 最小原型通过；跨域原型需等待 I3/I4 的必要实现及生命周期门禁。

验收：未知结果不自动重试提交；同 operation 内容冲突拒绝；取消后无法再派发子工作；子工作不能扩大能力或预算；查询不改变任何运行状态。

### I3：让工具、授权、MCP、上下文和工作区真正接管行为

按调用链分小批迁移，不批量重写：

1. 工具查询接真实目录；工具执行端口进入现有 `ToolInvocationService`。将授权决策内核接在实际派发前，审批也复用同一权威。先独立测试，再装配，确保 deny 时真实工具调用计数为零。
2. MCP 以真实 transport 适配新连接协调器；工具注册、重连、卸载使用 generation fence，禁止旧连接重注册已撤销工具。
3. 上下文将可纯化的组装/验证部分接入 `ContextAssemblyService`；复用已有 Policy/Pruning/Handoff。存储读取与压缩 LLM 调用仍经各自端口，不能用简化新内核替换掉已有语义。
4. 工作区连接真实目录与文件服务；边界测试覆盖路径遍历、重解析点、原子写入和读取/写入间变化。宿主未能保证的操作返回明确不支持，不能假装安全检查通过。

每批验收同时保留旧行为测试和新组件测试，增加真实消费者测试。一个行为只有一个权威；迁移后删除失去调用者的实现及只保护废代码的测试，但要先证明没有其他消费者。

### I4：执行组件与通用功能插件基础

- 先选一个现有执行路径抽出独立 kernel，端口只包含上下文、模型 attempt、工具派发、事件与停止判定；canonical 持久化留在 Platform 适配层。
- 对照原行为测试后统一 buffered/streaming 的状态转换。禁止先写第二套循环再等待将来替换。
- 插件加载获得有期限/grant generation 的服务集合；卸载先阻止新调用、撤销订阅并请求取消，再排空 owned 调用。旧 delegate/句柄不得继续工作。
- 将 `ExtensionPipeline` 真正接入明确调用点，`PluginEventDispatchWorker` 接真实 PluginManager sink 与受权 workspace source；同一事件允许重投，效果靠幂等，不宣称全系统 exactly-once。
- Hook 建议异常仍按仓库约定隔离；权限、预算、租约、生命周期硬控制留在强制执行端口。不能把硬门禁放进允许忽略异常的 Hook。
- 插件注册区分“调用服务”和“贡献实现”。补充无工具贡献的 Feature/Action、Provider/Policy、Event/Job 类型；组件只消费声明端口，不按插件名称加分支。已有工具插件继续复用同一包、Worker、授权与生命周期，禁止另建一个互不相认的功能插件系统。
- 明确应用/工作区作用域的激活和授权；非 Agent 功能不伪造 Agent/Session/Work，付费或长任务另取执行作用域。消费 API 与注册/替换策略的权限分开。
- 先验证一个工作区功能插件：不声明任何工具、不创建 Agent 会话，订阅受权产物发布事实，通过应用服务登记归档/审计条目。业务写入与确认可恢复、重投幂等；另用类型化策略 fixture 证明声明行为可切换。它是目标验收例，实际端口和示例由主代理冻结后实施。
- 可靠事件负责已提交事实，短 Hook/策略负责有界干预，长工作交给 Job；同事务约束留在领域服务。不用任意全局事件模拟所有服务调用。
- 管理投影列出所有贡献类型、激活 scope、策略选择、Job 与失败；不依赖聊天消息作为唯一可见入口。UI 贡献后续在 Web 层实现，Shell 不承载业务。

验收：工具插件及零工具功能插件都能加载、执行、卸载；卸载后订阅/策略/命令和旧句柄全部失效；并发卸载与调用不泄漏，崩溃恢复不重复产生业务效果；增加同合同的第二个插件不改组件业务分支。使用真实 PluginManager/Worker 与隔离存储、假外部服务；不重启运行产品 Core 的结论另待授权产品验收。

### I5：最后把 Review/Goal 作为基础设施消费者收口

本阶段接入前，A 基础设施门禁和 B 最小组合原型必须通过，I0～I4 的必要公共能力、执行端口、通用插件注册/事件/生命周期有真实适配证据；不能以 Goal 特例回调代替插件基础设施。Goal 参考 deepseek-harness 的状态服务/工具/命令/driver 分工，复用 Pudding 现有持久状态权威。纯策略可提前独立测试，完整接线不得越过前置门禁。

- 修复 Review 提交顺序、完整幂等指纹、父 Work 映射与可控时钟；Latest 仅适合展示，完成判定查询精确版本 key。
- 完成候选/Required Review 的关系在事务或持久 outbox 中建立；不可先把 Goal 完成再补评审。
- Review 完成后按同一 activation/iteration/objective/artifact/policy 证据触发结算或 continuation；旧评审不得推动新一轮。
- 普通聊天不创建 Goal。是否启动持续目标由明确模式/策略决定；评审模型输出是建议，不能越过预算、授权或用户取消。

## 3 分工与防止局部完成冒充整体完成

主代理保留：作用域契约、资源状态机、attempt 粒度、核心循环、授权与 canonical 接线、事务/幂等、整体评审。

只有契约和测试先固定后，才下发叶任务：单个存储/目录适配、固定 DTO 映射、独立场景测试、SDK 消费示例、文档索引。每单明确文件白名单、禁止改动的契约和宿主、输入输出与取红用例。不得因适配困难擅自增加默认 actor、无界预算或另建状态库。

每项交付分别报告：独立测试、编译门禁、真实适配测试、产品消费者迁移、产品验收。A 以两阶段合同的 A1～A6 为放行条件，不能只有接口或 fake 适配；B 另交组合场景证据。已有产品消费者的迁移情况必须单列，未迁移不能称为“整个 Pudding 产品已组件化”。A/B 不以生产部署为前提，08B/08C 在本计划中不新增授权。

通用插件还须分别报告 ToolReady、FeatureReady、PolicyReady、LifecycleVerified 的实际证据；名称仅用于区分验收维度，不要求新增代码枚举。只有工具可调用，或只有 Goal 专用插件示例，不足以证明通用软件功能插件化完成。
