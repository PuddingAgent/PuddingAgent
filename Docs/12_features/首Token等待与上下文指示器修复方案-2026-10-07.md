# 首 Token 等待与上下文指示器修复方案

目标是消除长历史软压缩给每条新消息附加的约 21–23 秒串行等待，并让用户能区分“正在准备/压缩上下文”“等待模型首增量”“输入容量压力”。本方案尚未实现；依据见[诊断报告](../14_reports/首Token等待与上下文指示器诊断-2026-10-07.md)。

架构决策见[ADR-095](../07_architecture/109ADR-095会话上下文维护与首增量延迟治理ADR.md)。Session第一次压缩不会免除后续维护：第一条执行的回复与工具结果会再次扩展历史。要修复的是“软维护每到新Turn又同步执行”的时机和重复准入，而不是给Session设置永久`alreadyCompacted`。

预期行为：安全的新消息直接准备主请求；回复结束后在空闲期整理历史；新消息到达就抢占可选摘要。如果第二条到达时历史已实际超出硬上限，仍显示必要的同步整理，不能承诺所有第二条消息都省去压缩等待。

## 1. 先补可观测性和准确展示

| 改动 | 文件入口 | 验收 |
|---|---|---|
| warm-prefix 发布开始、完成、失败/跳过事件，携带同一 compactionId、Turn/run、触发原因、耗时和实际前后估算 | Runtime `AgentExecutionService.cs`、Streaming/Buffered；复用现有 canonical 生命周期管道 | 首块前即可显示“正在压缩上下文”，重放不重新激活历史压缩，失败保留历史 |
| 当前请求计时补 `compactionMs`、`llmPrepareMs`、受理/认领/准入边界；区分主流和摘要 LLM 调用 | `AgentTurnTimingCollector`、`ExecutionRunCoordinator`、`TurnExecutorAdapter`、TurnTimingPanel | 总耗时可归因；缺失为 null；终态面板能解释约 23 秒前置等待 |
| accepted/started 就创建和更新当前 Turn 状态 | MessageList → surface/index → AgentMessageBubble → TurnStatus | 尚无正文/推理/工具时也能显示真实已受理/准备态；用真实事件测试，不凭秒数推断阶段 |
| 拆分“上下文容量压力”和“状态采集/API 是否可用” | `serviceStatus.ts`、`ComposerStatusDetails.tsx` | 75% 输入压力称“建议整理上下文”，API 失败显示采集失败/未知；容量不标成服务故障 |
| 显示总窗口占用和有效输入压力的两个明确分母 | ContextUsageRing、ContextHealthSnapshot | 本截图示例为总窗口约46.4%、输入预算压力约76.4%；颜色依据压力或显式说明总窗口色阶 |

生命周期事件不得带摘要原文、Prompt、密钥。优先复用 canonical 管道，不增加第二套轮询。不要将 started 一律称为“连接模型”：主 HTTP 真正发出前应称“准备上下文”。

## 2. 统一上下文快照与预算口径

1. 快照拆出 `lastMeasuredRequest` 与 `currentPreparedRequest`：两者均携带 invocationId/attemptId、model/route、context generation、recordedAt、source/confidence。展示“上次请求实测输入 131.1K”与“当前请求预算估算 463.8K”，不在同一个已使用数值里交替覆盖。
2. 当前健康度按所需的当前请求预算判断，最近实测仅作对照；压缩改变 generation 后不可拿旧实测冒充新上下文。并发/迟到 usage 只能更新自己的请求，不覆盖更晚的准备快照；compaction、agent、辅助调用分开归因。
3. 冻结请求估算用于校准，逐请求配对 Provider prompt tokens；核对 Responses continuation/tool wire 与估算输入形状。安全校准与可见实测分离。验证后再引入按 route/model/shape/generation 的有界更新或失效策略，不能直接移除最大值保护导致真实越界。
4. 将摘要身份作为共享合同或 typed message metadata，由预算计量和 UI 同源识别；为 `<compacted-summary>` 新路径与现有摘要路径建立明确测试，不在前端猜测文本。分层合计要等于对应估算总量，若按实测总量缩放需标记“分层估算”。
5. 容量 DTO 分别输出模型窗口、Provider 输入上限、实际请求输出预算、安全余量、有效输入上限及各自来源。禁止由 `window-effective` 冒充全部“预留输出”；UI 与硬门禁统一安全余量。
6. 核对 393,216 是运行请求输出预算还是注册模型上限。如果只是能力上限，修正解析链把实际 Agent 请求预算用于有效输入容量；若确为用户预算则如实显示，不擅自降到固定4096。修改必须保留足够的推理/输出和续轮空间。

出站硬预算裁剪另发有界 canonical 请求准备事实，包含 invocationId、context generation、裁剪单位/消息数、前后用量和原因；文案为“本次请求裁剪了旧上下文”，明确完整会话记录仍保留。它与持久摘要压缩是不同操作。单纯估算→实测的变化则标明来源切换，不生成虚假的压缩事件。

## 3. 将可提前完成的软压缩移出发送关键路径

采用“安全点生成候选 → 验证 → 原子提交”的压缩生命周期，而非把现有 `await` 改成 `Task.Run` 继续并发改同一 List。

1. 主 Turn 达到软阈值且当前请求仍能安全容纳时，把软压缩安排到轮次/Turn 的安全点；优先在用户可见终态提交后由会话维护调度执行，避免拖延已完成回复。保持已有硬预算、当前用户 Turn 围栏和完整工具轮保护。
2. 压缩针对冻结历史生成候选，标记 history generation、head hash/消息边界和工具定义版本。沿用缓存前缀重放设计，但候选只替换选中的旧跨度，不吸收本轮受保护尾部或工具未完成状态。
3. commit 在已有 session 单写者/压缩协调边界内执行 CAS。用户新消息到达优先，取消正在生成的可选摘要。初版对源revision/generation和配置进行严格校验，变化即丢弃候选；不拼接新尾部或自动rebase，不能用旧摘要覆盖新消息。
4. 检测硬容量确实不足时仍需同步压缩/显式失败，并立即显示原因。不得用冷却期跳过硬保护，也不得为抢首块静默驱逐原历史。
5. 摘要加入后重新完整计量，验证实际收缩、当前 Turn 保留、工具轮完整及预算/目标。现有 `EstimatedRetainedSnapshot` 是未加入新摘要时的计划估算，不能当提交后的真实值。候选失败保持原历史且计费归因保留。
6. 持久化 checkpoint 与 coverage/generation，使进程重启后可恢复；按同一 generation 合并重复维护请求，记录不获益/失败结果，避免每条短消息反复生成相同摘要。后台与前台共享准入规则，不能让新的维护工作抢占用户消息。

初版在活跃Turn的完整轮边界只评估、合并维护需求；可选摘要在canonical终态提交、前台租约和执行锁释放后启动。不得把现有末尾的`TrimHistoryAsync`继续放在终态前等待。取消/失败Turn只在历史与工具状态完整、准入许可时整理，不无条件调度。

`AgentExecutionAdmissionCoordinator`当前按整个Turn持有前台租约，`TryRegisterBackground`会拒绝此时的后台工作。初版复用它的用户优先规则，不把活跃Turn内另发并行摘要包装成普通后台工作。长Turn若达到硬边界，由当前执行者同步保护；后续并行候选方案另行验证，不在本阶段承诺。

抽出独立纯策略组件，先按[组件化交付规程](../10_conventions/组件化交付规程.md)完成 S1–S4 的边界与独立测试，再 S5 接入宿主。候选选择、版本适用判断、收益验证、预算算术可独立测试；持久化、LLM、事件和租约适配留在引用方。Shell 不承接业务压缩逻辑。

## 4. 验证与交付

| 场景 | 必须证明 |
|---|---|
| 短历史、无压缩 | 不新增摘要 LLM 调用；首块计时准确 |
| 长历史、仅软阈值 | 新消息不必等待可选摘要完成；候选不覆盖消息；单一 session writer |
| 长历史、确实硬超限 | 首块前显示同步压缩原因；不越过输入边界；失败保持原历史 |
| 压缩中用户新消息/取消/重启 | 用户优先、CAS 不匹配拒绝、checkpoint 可恢复、终态不被旧事件复活 |
| Provider usage 迟到与交错 | 主请求、摘要、辅助调用归因不互相覆盖；上下文 generation 正确 |
| 指示器本例 | 46.4% 与76.4% 分母明确；131K实测与464K估算不混用；容量压力不称服务异常；摘要桶非零 |
| 用量下降 | 22:53:13的164,675 TotalTokens解释了原截图，但新“实测输入”使用164,612 PromptTokens；来源变化不伪造持久压缩，出站副本裁剪展示独立事件 |
| 新摘要不缩小/加入后超目标 | 拒绝无收益候选或明确记录未达目标，日志不能报告未包含摘要的“压缩后”值 |

使用隔离历史夹具和延迟可控的假摘要模型验证“等待被移出关键路径”，再由进程外部署新构建、核对前端徽标与 Core loaded identity，执行真实产品 smoke。测试产物只放 `temp/build`、`temp/test-out`；数据兼容验证用 SQLite 在线备份副本，不在开发 DataRoot 试跑旧代码。

真实观测分别记录服务端受理→首推理、首正文、Provider dispatch→首增量、压缩耗时以及浏览器提交→首绘制。没有浏览器本地观测时不报告首绘制数据。不承诺固定4秒 TTFT；对本样本，若成功提前完成压缩，理论可省约21–23秒，具体效果需修复后测量。

前端代码改动需递增版本、重新构建部署并核对徽标；文档方案不递增版本。最后交付部署前状态与产品功能验收，生命周期结论由进程外控制器给出。

## 5. 状态合同、所有权与原子提交

以下是拟定合同，字段映射优先复用现有对象；不建设新的通用计划器或第二套历史库。

| 合同 | 核心字段 | 所有权与用途 |
|---|---|---|
| Session维护状态 | workspace/session、agent/route、generation、historyRevision、candidateFingerprint、pendingReason、lastOutcome、nextEligibleAt | 现有压缩协调器承接单飞与无收益退避；成功应用才推进generation，追加推进revision |
| 冻结候选 | compactionId、sourceGeneration/revision、selectedSpan的消息身份/hash、protectedTail hash、tool/route版本、sourceEstimate、预计净回收 | 快照生成后不可变；选择的是完整旧轮，不包含当前用户围栏或未完成工具轮 |
| 候选结果 | summary、完整候选请求估算、实际净回收、usage/cost、validationOutcome | 未提交摘要仅为临时候选；迟到/取消/过期结果保留记账，不写入会话 |
| 压缩checkpoint | compactionId、generation、覆盖消息身份/hash、可恢复摘要和保留尾部/引用、协议continuation、应用时间 | 复用coverage manifest与存储事务；不保存密钥展开后的Prompt |
| 请求快照 | invocation/attempt、purpose、model/route/protocol、generation、preparedAt、rawEstimate、safeUpperBound、capacity、providerPrompt/Completion/Total | currentPrepared与lastMeasured分离；purpose区分主调用/摘要/辅助调用 |
| UI事实 | Turn/run或Session范围、compactionId、reason、stage、applied、before/after、duration、sequence | 复用canonical通道；背景维护显示Session活动，不激活已结束Turn的spinner |

提交协议：

1. 已持Session执行锁的调用方冻结候选；后台先取得可抢占的Agent后台准入，再在短执行锁内冻结。释放执行/压缩锁后调用摘要模型；需要同步保护的前台保留自身Turn执行租约，但不持压缩提交锁跨网络调用。
2. 模型提示明确标记“仅总结选中的旧跨度”。warm-prefix为缓存重放保留前缀与工具schema，但不把保留尾部重复概括进替代摘要。
3. 生成后按`SessionExecutionGate → CompactionCoordinator`顺序进入短提交区。后台再次检查前台需求/取消标记；严格比对源版本、受保护尾部与route/tool版本，任一不符返回`stale_candidate`。
4. 组装摘要后的整请求，再检查硬预算、实际收缩、配置净收益、当前Turn与工具轮完整性。验证失败不改变历史，after值不能复用未加摘要的`EstimatedRetainedSnapshot`。
5. 在同一持久事务内提交checkpoint、coverage和generation CAS；校验执行fence/维护租约。事务失败全回滚。成功后才替换内存；内存失败标记失效并按新generation重建。
6. 提交结果幂等发布。现有持久事件机制若不能同事务投递，使用带compactionId的清单待投标记和补投，不建立第二事件库。重启恢复已提交代次、终止未提交候选；“DB条数较少”不能挡住新代次水合。

软状态转换：`idle → pending → generating → validating → applied`；旁路终态为`deferred / cancelled / stale_candidate / no_gain / failed / interrupted`。同候选合并；退避键至少包含generation、候选跨度/hash、route/tool版本与策略版本。新候选达到新增量/收益条件可再评估，退避不能屏蔽硬预算保护。

## 6. 代码范围与分阶段施工

### 6.1 独立组件先行：S1–S4

拟新增`Source/PuddingContextPolicy/`及其独立测试项目，名称在施工前核对仓库是否冲突。只依赖BCL；不得引用PuddingCore、PuddingRuntime、MemoryEngine、Host或具体LLM SDK。组件负责容量算术、候选边界/指纹、严格适用校验、净收益准入和退避判定；不负责计时器、数据库、网络、Session锁或后台任务。输入采用最小不可变DTO，Runtime在边界转换现有模型。

按S1–S4完成需求/合同、独立实现、故障测试和编译期依赖门禁。禁止在这些步骤修改宿主/DI或提前登记解决方案装配；门禁通过后才进入S5。新增时维护真实的组件code_map与根项目登记。本轮仅登记设计入口，不登记未存在的组件。

### 6.2 S5接入后的原子任务

### 6.3 计时与指标合同

受理计时起点取服务器canonical accepted时间，不能把晚创建collector的时间命名为提交时间。记录claim/admission、执行锁等待、上下文加载/准备、摘要排队/生成/提交、主请求dispatch及首次reasoning/content；单次Provider调用明确attempt和purpose。后台摘要不加进前台模型耗时，抢占计时归到实际等待方。

时间线先保证守恒：串行阶段之和解释受理到首增量，重叠后台阶段独立展示；未观察到的阶段为null，不用0掩盖。聚合指标至少包括两种首增量延迟p50/p95、软/硬压缩次数、候选丢弃/无收益率、用户抢占等待、摘要Token/费用、缓存冷miss与真实输入安全失败数。

## 7. 必须通过的回归与故障门禁

| 用例 | 断言与现有测试入口 |
|---|---|
| A：安全输入，摘要假模型延迟20秒 | 前台主请求在人工释放摘要屏障前已dispatch/首增量；不以脆弱的固定秒数断言；准入测试与Streaming/Buffered集成各覆盖 |

## 8. 灰度、回退与交付边界

先启用准确计量/事件，再按Agent或Session灰度终态后软维护；保留硬预算保护。可选维护支持开关、单飞、并发上限、摘要deadline和成本上限；具体数值复用现有预算配置并由回放校准，不在文档指定未经验证的20秒超时或固定Token值。

回退仅关闭可选调度，继续理解已提交checkpoint并保留请求归因/硬保护。不对真实DataRoot试跑不能理解新checkpoint的旧版本；回退/兼容测试只在SQLite在线备份副本进行。

本方案与ADR交付后状态为“设计完成，待实施”。代码交付依次为`ready-for-external-deploy`、外部重启到明确新构建、新会话功能smoke的`in-product-functional-complete`。启动/退出/崩溃回收仍由外部控制器判定。不得把文档门禁通过、理论省时或未重启的内部测试写成生产修复完成。
