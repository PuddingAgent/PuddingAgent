# goal 模式自动续跑设计

## 0. 起因：一个被误读的数据

上一轮回放 3000 条真实 user turn，测「召回线索」，结果里最刺眼的一条是：

```
「继续」出现 1408 次（46.9% 的 turn）
```

我起初把它当成「召回线索」问题（「继续」暗示要想起过去）。**用户指出这读错了**：

> 因为大部分情况下，如果我不发送「继续」，会话必须等待你的心跳。

所以它不是语言习惯，是**架构症状**：任务没做完时 Loop 会停下，等人拍一下才动。
用户被迫当人肉心跳。

**推论（直接影响召回设计）**：「继续」不该是强召回线索 —— 它表示「你还没做完」，
不表示「你要想起过去」。把两者混为一谈，会让 46.9% 的 turn 触发一次无意义召回。

## 1. 根因：Loop 的结束条件太粗

现在的停止判据基本是「这一轮没有工具调用了 → 停」。
但「没有工具调用」有两种完全不同的含义：

| 含义 | 正确处置 |
|---|---|
| 任务真的做完了 | 停，收尾 |
| 我卡住了 / 我打算等你 | **不该停** —— 应该自己想办法继续 |

现有实现把两者混在一起，于是第二种情况变成了静默停下。

## 2. 设计：`ContinuationPolicy`（纯函数）

已落地：`Source/PuddingRuntime/Services/AgentLoop/ContinuationPolicy.cs`

```csharp
Decide(ContinuationObservation) -> Continue | Completed | BudgetExhausted | NoProgress | Halted
```

三条必须**同时**成立才续跑：

```
有未完成事项 (OpenItems > 0)
  且 还有预算 (RoundsUsed < MaxRounds)
  且 上一轮确实推进了 (LastRoundMadeProgress)
```

**为什么第三条不能省**：缺了它就会变成「空转续跑」——
每轮都不产出、但一直烧 token，而且掩盖「其实卡住了」这个事实。
那比停下来更糟。

### 两个刻意的保守

1. **失败不自动重试**（`Failed → Halted`）：重试属于上层策略，
   「失败即重跑」会把真故障刷成假绿。
2. **连续两轮无进展就停**（`MaxConsecutiveIdleRounds = 2`）：
   给一次重试机会，但不给无限次。停下时**写明原因**，而不是静默。

### 用户优先

`UserMessagePending = true` 时一律 `Halted`：
用户来了消息就处理用户，不要自顾自继续。

## 3. 与心跳的关系

两者不是替代关系：

```
心跳（外部定时器）：保证"没人管的时候它也会醒"
自动续跑（内部闭环）：保证"有人管的时候它别停下来等人"
```

正确顺序是：**先把单轮预算用完**（自动续跑），确实需要外部事件时才交还心跳。

现在的毛病是反的：单轮早早停下 → 等心跳 → 心跳又从头恢复上下文 → 白烧一轮。
