# 插件 Agent 配置租约与算子开放设计

## 1. 当前交付边界

插件通过 `Context.AgentConfiguration()` 读取、更新当前持久 Agent 的名称/描述，并读取配置变更页。调用方不接触 manifest、数据库、JWT、控制令牌或 Host 服务容器。该入口复用公共配置 API 的 CAS、操作去重和原子 writer。

本节至 §4 是配置 API 实现合同。确定性评分采用 Core API 1.2，实际接口见[确定性算子公共 API](确定性算子公共API-契约与接入-2026-11-05.md)；受父预算约束的分类和证据评审采用 Core API 1.3，见[父任务预算与模型算子 API](父任务预算与模型算子API-契约与接入-2026-11-05.md)。§5 的通用 handle 与算子替换仍为后续设计。管理入口的 `IAgentWorkApi` 不向插件开放：模型调用租约不等于跨 Work 的持久父子关联、预算和取消合同，不能把管理权限当作插件授权。

## 2. 组件与调用链

| 组件 | 责任与允许依赖 |
|---|---|
| `Pudding.ToolPlugins.Contracts/PluginAgentApi.cs` | 可选 Core API 1.1 传输端口、宿主租约工厂端口；仅 BCL |
| `Pudding.ToolPlugins.AgentSdk` | 公共 SDK 的插件传输适配；仅插件合同、公共 SDK/合同 |
| `PuddingAgentDelegation` | 配置 API 的范围、方法、调用数、时限、撤销；仅独立配置组件/端口/公共合同 |
| `PuddingPlatform/Services/Plugins/PluginAgentApiLeaseFactory.cs` | 宿主身份绑定和严格 JSON 路由，Store 使用既有 `WorkspaceAgentFileService` |
| `PuddingRuntime/Services/Plugins/ExecutablePluginService.cs` | 从真实工具调用生成租约；通过端口获取平台适配器，不反向引用 Platform |
| `Pudding.ToolPlugins.Runtime/PluginManager.cs` | 活跃代、请求/批准能力交集、当前工具 effects、截止时间和卸载排空 |
| `Pudding.ToolPlugins.Worker/Program.cs` | 唯一插件 DLL 装载进程；协议关联与公共 SDK 类型共享 |

链路：`Worker → Context.AgentConfiguration() → 当前调用的 Core callback → Manager 授权 → 平台租约 → 独立配置服务 → 既有原子 writer`。插件 SDK 和配置组件的依赖白名单由 csproj 拒绝非法引用；不开放 `IServiceProvider`、CLR 类型名解析或反射调用。

## 3. 授权与结果合同

- 配置清单显式 `coreApi: "1.1"`，也允许使用同时包含算子能力的 1.2。`sdkApi: "1.0"` 的工具作者接口不变；Core API 1.0 包不能请求配置能力。
- 能力名为 `agent.configuration.read`、`agent.configuration.update`、`agent.configuration.changes`。加载时逐项批准；每次回调重新检查当前代及批准集。批准集复制为不可变集合。
- 写入还要求当前工具声明 `agent.configuration.write` effect，并经过既有高风险工具审批。包有权限不能替代工具的副作用声明。
- 作用域由 Host 的实际 workspace、Agent、session 绑定。请求 JSON 不接收目标 Agent、身份或委托票据；未知字段拒绝。暂存子代理执行身份与配置父身份不同则拒绝，不能冒充父 Agent。
- 每工具调用最多 16 次配置 API；截止时间不超过原工具/父调用截止时间。独立租约组件另有 5 分钟/32 次上限，不能扩大工具已批准的期限。
- 初始化、关闭、建议 Hook 没有配置能力；保存 SDK handle 不能获得脱离当前执行的权限。Worker 用异步上下文绑定的请求租约隔离后台任务，原调用结束即撤销；旧后台任务不能借后续调用的 requestId 取得权限。
- 配置审计 actor 由 pluginId/workspace/Agent/session 的规范 JSON 哈希生成，不使用用户管理身份。actor 跨同作用域重新加载保持稳定，以便在重新授权后用原操作 ID 查询/重放未知写入；它不是授权凭证。
- `ExpectedRevision` 与 `OperationId` 由调用方显式传入。版本冲突不自动合并，丢失写回执不自动换 ID 或重试；仍使用原请求、原 ID 核对。无法确认副作用时保留 `unknown`。
- 写回执只说明 `configuration-source` 已应用，不代表 UI 已刷新或正在执行的 Run 已改配。

卸载首先撤销工具/Hook 与新回调准入，再停止 Worker，等待已准入宿主回调排空。排空最多等待 5 秒；超限返回 `StopFailed/unknown`，保留资源占用，不能报告 `Unloaded`。已提交写入不会因随后取消而回滚；撤销承诺的是不再准入和确认排空。

这些约束保护 Core API 的调用边界。Worker 仍以当前用户运行，不是恶意托管代码的系统资源沙箱。

## 4. 验收与可重跑入口

运行 `pwsh -NoProfile -File TestScripts/test-plugin-agent-api.ps1 -RunId <唯一运行标识>`。该脚本独立构建组件/SDK，测试调用授权与撤销，再运行真实 Worker 和旧插件故障回归，产物全部进入 `.work/plugin-agent-api/`。不启动产品 Core，不使用真实凭据或 LLM。

判据必须包括：跨 Agent 在 Store 前被拒；无写 effect 不落盘；加载后修改原批准集合不改变授权；写成功后的取消不伪装未写；卸载等待宿主回调而非只看 PID；排空超时仍计入实例上限；重载后旧工具失效但同操作回执不重复落盘；变更页只出现一次变更；既有 manifest 中其他字段保持不变。

组合根另由 `Tests/PuddingHost.Tests/Hosting/PluginAgentApiCompositionTests.cs` 验证工厂装配与既有配置 Store。公共配置 P0/P1 和单轮工作 API 的指纹门禁均继续适用，本切片不修改冻结合同。

## 5. 分类、打分、判断能力开放设计

确定性 `skill.value` 与受预算约束的分类/评审已有独立消费入口；以下泛化 handle 和算子替换继续作为后续设计，不应当作现有 API。

### 5.1 已有基础，复用而非重建

| 权威代码 | 现有语义 | 对外开放时的处理 |
|---|---|---|
| `Source/PuddingCore/Operators/OperatorPorts.cs` | `IScorer`、`IJudge`、`IClassifier` 三原语；模型适配另有 `IClassifierModel` | 对上层提供三种类型化结果；不直接交出模型端口 |
| `Source/PuddingCore/Operators/OperatorRegistry.cs` | 场景键 + 原语解析 | 授权后的目录快照和场景 handle；不暴露可变注册表 |
| `Source/PuddingCore/Operators/JudgementEnvelope.cs` | 输入指纹、算子/模型/指令版本、阈值、证据、分数量纲、置信种类和降级原因 | 公共结果保留这些字段；缺失为 null/unknown，禁止补造证据 |
| `Source/PuddingRuntime/Operators/OperatorBase.cs`、`OperatorEnvironment.cs` | 缓存、模型、时钟、超时、健康和审计旁挂 | 适配现有执行链；额外补齐公共调用预算，不宣称已有完整资源池预算合同 |
| `Source/PuddingRuntime/Services/Improvement/SkillValue/SkillValueScorer.cs` | 无 LLM 的确定性技能价值评分 | 适合作为第一个公共评分切片，不引入真实模型依赖 |
| `Source/PuddingRuntime/Operators/Adapters/ToolApprovalOperatorAdapter.cs` | 既有工具审批分类器的语义适配 | 分类结论可供观察；插件不能用自己的分类结果直接颁发执行授权 |

**语义不可压成一个 `Evaluate(): bool`**：分数与通过判据分离；`Abstain` 是有效弃权，`Unknown` 是没有有效判断；模型自报置信度不能标为概率。判定缓存命中与模型实际调用要分别可见；判断完成也不代表外部任务已验收完成。

### 5.2 对调用方的形状

以下名称是拟议 API，不可在当前插件清单中申请：

```csharp
var operators = context.Operators;
var catalog = await operators.ListAsync(ct); // 只枚举已授权、可调用的能力描述
var scorer = operators.Scorer("skill.value");
var score = await scorer.ScoreAsync(input, options, ct);
var classifier = operators.Classifier(sceneKey);
var classification = await classifier.ClassifyAsync(input, options, ct);
var judge = operators.Judge(sceneKey);
var judgement = await judge.JudgeAsync(input, options, ct);
```

三个 handle 使用独立方法和结果类型。目录描述包含场景键、原语、输入 schema ID/版本、输出 schema 版本、实现版本、是否可能调用模型、输入上限；返回授权过滤后的不可变快照。对已固定场景提供强类型 DTO；通用 JSON 仅留在 broker 传输边界，并由对应场景适配器校验。

公共 `options` 只允许提出更小的截止时间/预算和调用 ID，不能选择密钥、任意模型实例、越权工作区或伪造父 Run。宿主签发调用作用域，取父预算与请求的交集；模型调用前预留额度，完成后结算，响应丢失时不盲重试。缓存键至少隔离 scope、场景、输入 schema、输入指纹、实现/指令版本及影响结果的阈值版本，不能把跨租户缓存当优化。

授权失败、schema 不匹配、未知场景属于 API 调用失败；算子弃权/降级属于已返回的领域结果，保留原原因码与证据。消费端不得因“HTTP/RPC 成功”就把降级结果当作判断成功。

### 5.3 代码施工顺序

1. **主代理先做合同与独立边界**：`Pudding.Api.Contracts/OperatorEvaluation.cs` 提供公共目录/评分结果/调用选项，`Pudding.Api.Sdk/OperatorsClient.cs` 提供消费者 facade；不改已冻结配置/工作文件。独立 `PuddingOperatorAccess.Contracts` 与 `PuddingOperatorAccess` 只依赖公共合同和端口。每个项目先通过独立测试和引用白名单门禁。分类/判断结果随其实际实现再增加，避免发布不可调用的占位接口。
2. **首个切片只开放确定性评分**：在 Runtime 新建 `Operators/PublicApi/SkillValueAccessAdapter.cs`，将公开 DTO 映射到既有 `SkillValueOperatorContext`，调用原评分器；不重写公式、不增加隐式模型调用、不改变阈值。Host 仅在独立测试通过后登记。输入缺失、schema 版本不符、未注册场景、未授权、过期租约必须取红。
3. **接插件传输**：新增单独能力版本和目录/评分回调，复用本切片当前调用的作用域与撤销机制。不要把配置专用租约改成 `Invoke(method, object)` 的万能服务容器；抽取共享准入组件时需单独测试，保留已有配置合同。
4. **模型分类/判断**：先完成父调用预算/模型资源租约/取消的公共合同，再接 `IClassifierModel` 适配。测超时、预算不足、模型未配置、缓存隔离、降级和取消成本。不能以默认无限预算上线。
5. **注册和替换算子是另一种权限**：消费评分 API 不等于允许插件覆盖审批器、阈值或系统分类器。未来贡献类型采用不可变版本、显式宿主批准、停止新准入后排空旧版本；优先级及是否影响既有流程必须明确注册，不能依靠同名覆盖。
