# 交互面板：交互式编辑与制成品管理 · 设计方案

日期：2026-10-20　状态：**P1 与标注图元已施工，artifact 接入待定**

> **本版施工摘要（2026-10-20）**
>
> 已落地：标注图元从「框/点」两种扩展为**框、点、涂鸦、箭头、文字**（配撤销栈），
> 并实现**合成烧录**把笔迹写进像素；制成品可保存 / 继续编辑 / 删除，
> `_trash` 超 7 天自动清理；`generate_image` 水印默认改为 `false`。
>
> 尚未落地：把烧录图登记成 vision-artifact。因此形式 1 目前只能用**路径**引用，
> `generate_image` 的 `referenceArtifactIds` 还接不上（阻塞与两条候选路线见 §十）。
>
> 最重要的修正见 **§二·五**：官方支持**两种**交互形式。我最初只按坐标设计，
> 漏掉了「任意标记」—— 而它要求笔迹存在于像素里，这正是「烧录」存在的原因。

需求原话：

> 增加一个按钮，保存到制品库（对应的是制成品这个 Tab），用于保存制成品和再加工。
> 实际上，这个交互面板将负担一些比较重的功能和交互式编辑任务。
> 请在施工之前规划这个交互面板的交互 UI 应该如何设计，然后如何加载，用户如何执行
> 交互式编辑，以及你如何取回用户编辑的内容，然后重新生成新的。
> 同时，当用户执行多个图片修改的时候，是否支持多个不同的 tab 页签管理，
> 以及完善的制成品管理流程。

### 一个必须先解决的命名混淆

仓里有两个「右侧面板」，**不是同一个东西**：

- **前端 `SideArtifactPanel`**：Web 内右侧栏，tab = 交互面板 / 文档 / 制成品
- **Desktop 工具区**：原生 WinUI，tab = 首页 / 终端 / 制成品 / 输出 / 文档 / 画布 / 浏览器

用户截图里的工具栏按钮属于**后者**。本方案只改 Desktop 工具区，前端侧栏保持不动（它自己有一套 keep-alive 逻辑，动它风险大且本轮无收益）。

## 一、核心概念：把「生成结果」和「制成品」分开

这是整个设计的地基。

| | 生成结果（vision-artifact） | 制成品（craft） |
|---|---|---|
谁产生 | 机器，自动落盘 | **用户点「保存到制品库」** |
有无名字 | 无（只有 id） | 有（可改） |
有无血缘 | 无 | 有（parent） |
有无所用提示词 | 无 | 有 |
生命周期 | 可被清理 | 长期保留，可再加工 |
用户的感知 | "模型刚吐出来的" | "我挑中的那一版" |

**为什么必须分开**：如果每次生成都进制成品库，库里会被中间稿淹没；
反过来，如果制成品只是 vision-artifact 的别名，就没有"我确认要这一版"这个动作，
再加工也就没有起点。

## 二、数据模型

制成品存本地目录（`{DataRoot}/workspaces/{ws}/crafts/`），**不新增 Core API**。

理由见「七、关键取舍 T1」。

```jsonc
// crafts/craft-7f3a1b2c.json
{
  "artifactId": "craft-7f3a1b2c",
  "title": "金毛幼犬 · 戴针织帽",
  "kind": "image",                          // image | html
  "file": "craft-7f3a1b2c.jpg",
  "mimeType": "image/jpeg",
  "width": 2048,
  "height": 2048,
  "sha256": "…",
  "bytes": 342603,
  "createdAt": 1792492762000,
  "parent": "vision-7ced1b33…",             // 血缘：从哪来的
  "source": {
    "panelId": "edit-7ced1b33",
    "generator": "doubao-seedream-5-0-260128",
    "prompt": "图一 <bbox>320 180 680 520</bbox> 戴上米色针织帽",
    "annotations": [{ "kind": "box", "x1": 320, "y1": 180, "x2": 680, "y2": 520 }]
  },
  "note": ""                                 // 用户备注，可空
}
```

三条硬规则：

1. **文件按内容寻址存**（sha256 去重），JSON 引用它 —— 同一张图被保存两次不占两份空间
2. **`parent` 只存一个**。分支再加工会产生自然的多叉，但当前 UI 没有树形展示，先不引入
3. **JSON 是唯一真源**，目录扫描即索引，不维护额外清单文件（避免索引与磁盘不一致）

## 二·五、两种交互形式：坐标 vs 任意标记（本版最重要的修正）

第一版方案只抓到了**坐标**这一种形式，把涂鸦/箭头都当成「要转换成 bbox 的东西」。
这是不完整的。官方实际支持**两种并列**的形式：

| | 形式 1：任意标记 + 自然语言 | 形式 2：坐标精准定位 |
|---|---|---|
用户做什么 | 在图上手绘草图、涂鸦、圈选 | 框选 / 点选 |
prompt 里有什么 | **没有坐标**，纯自然语言 | `<point>` / `<bbox>` 标签 |
模型怎么理解 | 直接「看」图上的笔迹 | 按标签定位 |
表达力 | 更高：能表达形状、走向、「这一带」 | 更精确：区域边界确定 |

官方形式 1 的示例 prompt（原文）：

> 根据手绘草图对图像进行编辑。在左下角标记区域添加一叠真实的杂志或艺术画册，
> 并在右侧标记区域添加一个带杯碟的陶瓷杯咖啡。移除所有草图线条。
> 保持构图不变。让新添加的物体自然融入原有场景中。

注意两点：**一个坐标都没有**；而且明确写了「移除所有草图线条」——
说明模型会把标记当作待抹除的注记，而不是内容。

### 由此得到的硬约束：标记必须烧录进像素

形式 1 要求笔迹存在于**图片像素**里。而标注层一直是 DOM/CSS 覆盖
（`position:fixed` 的 div + SVG），`take()` 返回的 `src` 仍是**原图**。

**不烧录，用户画得再漂亮，模型收到的都是一张干净的原图。**

所以本轮真正的核心不是画笔，而是 `compose()`：

```js
原图 + 所有标记 → canvas → toDataURL('image/jpeg', 0.9) → 宿主落盘
```

### 图元降维规则（两种形式并用）

画布支持 5 种图元，但模型只认 `point` 与 `bbox`，所以每种图元要同时给出
**坐标（形式 2）** 与 **可烧录的原始几何（形式 1）**：

| 用户工具 | 存什么 | 喂给模型什么 | 为什么 |
|---|---|---|---|
框选 | `{kind:'box',x1,y1,x2,y2}` | `<bbox>x1 y1 x2 y2</bbox>` | 原生支持 |
点选 | `{kind:'point',x,y}` | `<point>x y</point>` | 原生支持 |
涂鸦 | `{kind:'scribble',points:[…]}` | `涂鸦 <bbox>外接框</bbox>` | 模型只需知道「落在哪片」；轨迹留给烧录 |
箭头/线段 | `{kind:'arrow',x1,y1,x2,y2}` | `箭头 <point>起</point> → <point>终</point>` | 协议没有「线」，方向用字面表达 |
文字标注 | `{kind:'text',label,x,y}` | `文字「…」 <point>x y</point>` | 文字本身是 prompt 的一部分 |
橡皮擦 | —— | 不产生图元 | 就是「撤销上一步」；独立做成擦会跟撤销抢职责 |

三条判断：

1. **箭头不做 min/max 排序。** 把两个端点「整理」成左上→右下，会把
   「从 A 指向 B」静默改成反向，而方向往往正是用户想说的那件事。
   有用例 `Arrow_preserves_the_draw_direction` 钉住。
2. **涂鸦不传轨迹给模型**，只给外接框。模型不需要知道画了几笔。
   但**轨迹必须留在 items 里**，否则永远烧录不出用户原本的笔。
3. **文字必须有字。** 空白标签直接报错，不静默降级成点选 ——
   静默会让用户以为写进去了。

### 一个必须避开的通道限制

`compose()` 的结果要经 `CoreWebView2.ExecuteScriptAsync` 回传宿主，
**这条通道对返回值有大小上限**。2K PNG 的 base64 常有 3~8 MB，
超限时不会抛异常，只是**静默拿不回来**，表现为「点了按钮没反应」且日志无痕。

所以：最长边限制 **1536** 等比缩放 + 输出 JPEG。缩放必须**等比**，
坐标按缩放后尺寸换算，否则标记会偏移；线宽 / 箭头 / 字号要跟着缩放后的宽度算，
否则笔迹会相对变粗。

## 三、交互 UI：按「谁更知道」分工

当前工具栏是 XAML 画的，四个按钮。用户要求"负担较重功能"，但**按钮不该无限制堆**。

分工原则：**XAML 只知道 Shell 能力，壳内 JS 只知道 DOM。**

| 动作 | 放在 | 为什么 |
|---|---|---|
标注（切换） | **XAML 按钮** | 要跨内容存在，且状态要能显示在状态栏 |
保存到制品库 | **XAML 按钮** | 要写文件、复制、重建 tab —— Shell 能力 |
添加到对话 | **XAML 按钮** | 要往主 WebView2 发消息 |
下载到本地 | **XAML 按钮** | 文件系统 |
缩放 / 适应宽度 | **壳内浮动条** | 纯 DOM，且随内容滚动 |
原图 ↔ 结果对比 | **壳内浮动条** | 需要知道两张图，Shell 不知道 |
标注计数 / 清空 | **壳内浮动条** | 高频、轻量，走 XAML 每点一次都要跨进程 |

### 工具栏（XAML，最终形态）

```
[标注]  [保存到制品库]  [添加到对话]  [下载到本地]
```

状态栏承载反馈：`已保存 craft-7f3a1b2c（金毛幼犬 · 戴针织帽）`。

### 壳内浮动条（默认隐藏，有图且 ≥1 张时出现）

```
┌─────────────────────────────────────┐
│ 1:1  ⤢ 适应  ⇄ 对比原图   ● 2 个标注  ⌫ | │
└─────────────────────────────────────┘
```

**为什么不把这些也做成 XAML**：每点一次「缩放」都要 `ExecuteScriptAsync` 往返一次，
用户会明显感到迟滞；而它们全部是纯视觉变换，没有任何 Shell 语义。

## 四、如何加载（编辑会话的生命周期）

### 4.1 会话标识

**一个编辑会话 = 一个 `panelId`**，命名：

```
edit-<parentArtifactId 去掉前缀后的前 8 位>
例：edit-7ced1b33
```

`ToolTabIdentity.Panel(panelId)` 天然把它们分成不同 tab，**不需要新增 tab 机制**。

### 4.2 三种进入方式

| 入口 | 行为 |
|---|---|
**Agent 主动推**（生成后） | `render_panel(panel_id="edit-7ced1b33", title="金毛幼犬 · 编辑")` |
**从制成品「继续编辑」** | Desktop 读 craft.json → 用同样方式开 panel，`parent = craft.id` |
**重开已有关闭的 tab** | `render_panel` 同 panelId 会复用/新建，内容从 Core 拉回 |

### 4.3 内容组装（Agent 侧，不需要用户关心）

Agent 推的内容只要符合一件事：**页面里要有 `<img>`**，且建议只有一张。壳负责：

- 注入主题变量
- 注入标注层（已实现）
- 注入浮动条（P2）
- 按最大 `<img>` 定位标注区域

示例（Agent 实际写的全部内容）：

```html
<div style="padding:16px">
  <h1 style="font-size:15px;margin:0 0 10px">金毛幼犬 · 戴针织帽</h1>
  <img src="pudding-image:///D:/Data/workspaces/default/vision-artifacts/vision-abc.jpg"
       style="max-width:100%;border-radius:10px">
</div>
```

### 4.4 多 tab：明确支持，且约定清晰

| 场景 | 结果 |
|---|---|
同时改两张不同的图 | 两个 `panelId` → 两个 tab，互不干扰 |
同一张图改三轮 | 同一个 `panelId`，**revision 递增，只保留最新** |
想留着上一轮看 | 在覆盖前点「保存到制品库」，从制成品里重开 |

**为什么会话内只留最新**：每次改动都留历史会让画布变成版本浏览器，
而 `render_panel` 的 revision 模型本来就是"当前状态"。
需要历史就进制成品库 —— 这也是"保存"这个动作存在的意义。

**待定**：是否给每个面板 tab 加"编辑序号"徽标（如 `金毛幼犬 · 编辑 ·3`）。
倾向加，成本低，能让用户知道已经改到第几轮。（P2）

## 五、用户如何编辑、我如何取回

### 5.1 用户侧动作序列

```
1. 点「标注」            → 图上出现虚线框，光标变十字，浮动条显示"标注中"
2. 在图上拖框 / 点选      → 蓝色半透明标记出现，浮动条计数 +1
3. 点「添加到对话」        → 输入框出现「图一 <bbox>320 180 680 520</bbox>」
4. 补一句「戴上米色针织帽」
5. 回车发送
```

### 5.2 我这一侧的取回链路（已实现部分标 ✅）

```
✅ XAML 点按钮
✅ ExecuteScriptAsync("puddingAnnotation.take()")
     → {"width":800,"height":800,"items":[{kind:"box",x1:..,..}]}
✅ C# PanelAnnotation.TryParsePixels —— 唯一一份归一化实现
✅ PanelAnnotation.DescribeForComposer → "图一 <bbox>320 180 680 520</bbox>"
✅ PostWebMessageAsJson → 前端 composerInsert → IntentConsole 写草稿
```

### 5.3 重新生成（已实现，只差 artifact 接入）

~~问题：我拿到标注和指令，但不知道「图一是哪张图」。~~

**已解决**：`DescribeForComposer(items, sourceUri, allowedRoots)` 把来源图写进文本。
注意 `sourceUri` 必须能经 `PanelImageSource.TryResolve` 还原成白名单内真实路径才会写，
否则静默省略 —— 页面给的任意字符串不能直接进用户的输入框。

现在有标注时的文本形态：

```
【已画标记的图】D:\Data\panel-marks\panel-marked-20261020-210103-421.jpg
【编辑 D:/Data/.../vision-abc.jpg】
图一 <bbox>320 180 680 520</bbox>
涂鸦 <bbox>120 240 380 560</bbox>
文字「把这里换成蓝色」 <point>450 250</point>
```

第一行是**烧录图**（含笔迹，走形式 1），后面是坐标（走形式 2），两者并存。

Agent 据此：
1. 第一行的路径 → 用 `image_reader` 看清用户到底画了什么
2. `generate_image(mode=precision, referenceArtifactIds=[…], prompt=…)`
   —— **注意**：这一步目前只能吃 `vision-*` artifact，而烧录图还不是（见 §十）
3. 新结果 → `render_panel(同 panelId, 新 revision)`

这样即使中间隔了 20 轮对话，也能确定改的是哪张图。

## 六、制成品管理流程

### 6.1 保存（点「保存到制品库」）

```
1. puddingCanvas.describe() → { image, width, height, annotations }
2. 图路径解析为 artifact（或直接文件路径）
3. sha256 → 已存在则复用文件，新建 JSON
4. 复制到 crafts/<id>.<ext>（或硬链接）
5. 写 craft.json（含 parent / prompt / annotations）
6. Desktop「制成品」tab 重建列表
7. 状态栏：已保存 + 可改名的名字
```

**保存时不做的事**：不中断当前编辑会话。用户可能保存完继续改，再保存出第二版。

### 6.2 制成品 tab 的形态（P1 最小可用）

```
┌──────────────────────────────────────────┐
│ 金毛幼犬 · 戴针织帽            2048×2048 │
│ [缩略图]      2026-10-20 18:46           │
│               来源：vision-7ced1b33      │
│               [继续编辑]  [下载]  [删除]  │
├──────────────────────────────────────────┤
│ 金毛幼犬（原图）                2048×2048 │
│ [缩略图]      …                          │
└──────────────────────────────────────────┘
```

按 `createdAt` 倒序。支持：继续编辑 / 下载 / 删除 / 改名。

**P3** 再加：按来源分组（同一张原图的派生链折在一起）、搜索、批量导出。

### 6.3 血缘的可见性

`parent` 字段现在只是数据。P3 在卡片上显示「← 来自 金毛幼犬（原图）」，
点它跳到父制成品。这样"再加工"形成可回溯的链 —— 用户能看清自己改了几轮走了哪条路。

## 七、关键取舍

### T1：制成品存本地，不新增 Core API

**理由**：
- 画布内容已经归 Core（`/api/panels`），但制成品是**用户资产**，不是会话状态
- 本地目录可直接备份、可用资源管理器打开、不依赖 Core 存活
- 新增 Core API 意味着契约 + 存储 + 迁移，收益与成本不成正比

**代价**：换机器不跟随。若将来要做跨设备同步，再上 Core —— 那时 `craft.json`
的 schema 已经稳定，迁移只是搬目录 + 建索引。

### T2：会话内不保留历史，只保留最新

见 §4.4。历史由「保存」动作显式产生。

### T3：标注只认最大的一张图

多图对比场景（改前/改后）会出现两张等大图，标注落点不确定。
**P2 处理方式**：浮动条上选择"标注对象"（图 1 / 图 2），壳按选中项定位。
P1 不处理，并在 SKILL 里要求"面板里只放主要那一张"。

### T4：不引入新消息通道

#### D1（阻塞形式 1）Desktop 要不要持有 Core 凭据？

这是唯一挡住「画完能直接重画」的决策。三个选项：

| 选项 | 做法 | 代价 |
|---|---|---|
**A1 受限凭据** | 给 Desktop 发一个只能写 `vision-artifacts` 的令牌 | 多一份凭据要保管与轮换 |
**A2 签名匿名入口** | Core 开一个需时间戳 + HMAC 签名的上传端点 | 要设计签名方案，且密钥仍在 Desktop |
**A3 复用匿名通道** | 把上传端点也改 `[AllowAnonymous]` | **不建议**：等于开了匿名写盘口子 |

**倾向 A1**。理由：Desktop 是同一台机器上的受信进程，凭据可放它自己的配置里、
不经过网络；A2 的签名密钥若也在 Desktop，安全性等同 A1 但多一层复杂度；
A3 等于把上传口暴露给任何人。

*技术细节见 §十。*

#### D2 烧录图要不要保留？保留多久？

- **B2 保留最近 N 张**（倾向 N=50）：兼顾回溯与磁盘
- **B3 全留**：用户自己管

## 十、D1 的技术附录：烧录图 → vision-artifact

形式 1 要用上烧录图，图必须能作为 `generate_image` 的参考。而该工具的
`reference_artifact_ids` 只接受 `vision-*` 格式的 artifact id。

现在烧录图落在 `{DataRoot}/panel-marks/panel-marked-<ts>.jpg`，是**普通文件**，
不在 artifact 体系里。两条候选路线：

### 路线 A：调 Core 的上传端点（推荐）

Core 已有：

```
POST api/workspaces/{workspaceId}/vision-artifacts
multipart/form-data:
  file                    （image/png | jpeg | webp | gif | bmp）
  width, height, capturedAt（可选）
→ { artifactId, mimeType, width, height, capturedAt }
```

**阻塞点**：该控制器标了 `[Authorize]`；而 Desktop 拉 `/api/panels/{id}`
走的是匿名通道（`PanelHttp.GetAsync` 不带 Authorization），手上没有可用凭据。

需要拍板：给 Desktop 开一个**受限上传凭据**（只允许写 vision-artifacts），
还是给 Core 加一个签名受控的匿名上传入口。

### 路线 B：直接写目录（不推荐）

`{DataRoot}/workspaces/{ws}/vision-artifacts/`，文件名 `vision-[a-f0-9]{32}.{ext}`，
配 metadata（`ArtifactId` / `MimeType` / `FileName` / `Width` / `Height` /
`CapturedAt` / `StoredAt` / **`Sha256`** / **`Bytes`**）。

**否决理由**：要复刻 schema 与哈希计算，服务层一改格式就坏；而且绕过了 Core 的
`VisionImageInspector` 校验（字节内容与声明 MIME 的一致性）。
**不该为了让功能跑起来而绕过服务层。**

### 在接入之前的临时可用性

形式 1 只能**按路径**引用：输入框文本里已有 `【已画标记的图】<绝对路径>`，
Agent 能用 `image_reader` 看它，但 `generate_image` 吃不到。
也就是说「我能看懂」与「模型能吃到」被分开了 —— 图是真的，只是重画那一步还差一截。
