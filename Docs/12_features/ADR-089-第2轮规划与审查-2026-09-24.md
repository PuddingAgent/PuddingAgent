## 3. ⚠️ 父级独立取证：一条**比 codex 批评更严重**的新发现（改写迁移方案）

来源：`temp/codex-verify-pathsets.py`（我自写，`mode=ro` + `PRAGMA query_only=1`）实测 `CodeFiles`：

```
distinct FilePath = 1,246      total rows = 2,849
⇒ 812 条路径被重复索引（样本 count=4 ⇒ 同一文件在 4 个 scope 各存一份）
   例：Source\PuddingCore\Tools\ToolAuthorization.cs → 4 行
根 scope 1,083 行中：706 行落在子 scope 根目录内（= 与子 scope 重复）
                     377 行不在任何子 scope 根下（= 根的"独立贡献"上界）
   而这 377 行里含有仓库外文件：
   C:\Users\huany\.nuget\packages\microsoft.net.test.sdk\18.0.0\build\net8.0\Microsoft.NET.Test.Sdk.Program.cs
```

**结论（三条，皆有实测支撑）**：
1. **864.6 MiB 的主因不是"内容多"，而是跨 scope 重复索引**（2,849 行只承载 1,246 个不同路径；平均每路径 ≈2.3 份）。⇒ **1GB 护栏之所以只剩 15.6% 余量，主要是浪费**。
2. **根 scope 的真实独立价值上界只有 377 行**（而非 1,083）⇒ 方案 **A"重新注册 + 全量重建"会把绝大部分已被子 scope 覆盖的数据再建一遍**，性价比差；我原先的"C 留 3,330 缺口"也因此口径不准。
3. **根 scope 含仓库外文件**（NuGet 缓存，来自 07-24 那次运行，早于 U4-4 的排除表修复）⇒ 印证 §D5 与 U4-4；**"共享库按 ProjectId 原样拆分"会把这个缺陷一起搬走**。

⇒ **父级裁定：采纳 codex §P0-3 的"重扫构建新库，不做原样拆分"**，且此裁定现在有硬数字支撑（不再是它的推断）。零写证明：库 mtime 仍 `2026-09-24 16:25:18`、`-wal` 仍 `0 B`。

## 4. codex 的审查清单（§B）与我的采纳裁定

### P0（全部采纳）

| # | 它的核心主张 | 我的裁定 |
|---|---|---|
**P0-1** | **D1/D2 的根因不是"一个错误映射"，而是**状态模型把三个正交概念揉进一个字段 —— 应拆为 `Coverage`(Owned/CoveredBy) / `ServingState`(Empty/Ready/Degraded/Corrupt) / `RunState`(Queued/Running/Succeeded/Failed/Cancelled/Abandoned) / `DesiredState`；`Registering` **只能映射到恢复态，绝不能映射为 `Covered`**；`Covered` 必须由父 scope 外键+路径不变量**推导**，不能从生命周期状态推断；取消/崩溃正确行为 = 写 `Cancelled`/`Abandoned` Run + **保留上一代成功索引继续服务** + 标 `NeedsReconcile` + 启动恢复器扫无心跳 Running | ✅ **全部采纳，且这是本轮最高价值的一条**。它精确指出了我 U3-G1 只是"止血"（摘掉删除判据 + 写可区分 StatusMessage），**真正修法是状态机正交化**。→ 成为 **M1** |
**P0-2** | **D3 清理规则把"需要恢复"误判为"冗余"**；当前保护来自**操作开关而非数据语义**（单点软保护）。删除资格必须来自**显式 tombstone**（`DeletionRequestedAt`+操作者+原因+确认版本）；清理预览须含 scope/路径/关联行数/物理字节/最后成功代次；`Registering/Running` 超时属**恢复器**职责，不属垃圾清理 | ✅ **采纳**。U3-G1 的 R1（摘掉 `'Registering'`）是**正确的止血子集**；完整解 = tombstone 驱动（**M1**） |
**P0-3** | **共享单库与"每项目一库"冲突，且 1GB 护栏作用域未定义**；不建议按 `ProjectId` 原样拆分（**含陈旧状态与重叠 scope，重扫更可靠**）；应定义 `LibraryId + CanonicalRoot + FormatVersion`；新库放**根内隐藏目录**（如 `.pudding/index/code-index.db`）并由索引器**硬排除**；**迁移期不双写**，旧库只读保留一个明确期限；容量统计须算 `db+wal+shm+向量段+临时重建` | ✅ **采纳**，并由 §3 实测数字强化（重扫，别搬）。→ **M2** |
**P0-4** | **D4 表在但无写入者 ⇒ 运行状态无法恢复或审计**；每次尝试必须产生 Run 并记录 `RunId/Trigger/QueuedAt/HeartbeatAt/State/FailureCategory/计数/git HEAD/忽略规则摘要/代次/checkpoint/队列积压/退避档位`；启动把过期 `Running` 转 `Abandoned` 后**重入队** | ✅ **采纳**。→ **M1**。它也诚实说明"**无法给出静默漏项的可信总数**"，只能给已确认下限（`CodeIndexRuns`）+ 建议建 **ADR 要求—生产入口—测试追踪矩阵** |
**P0-5** | **D5 暴露的是"发现机制错误"，不能只补一次全量索引**：scope/工程发现必须属于**初始化、git 变更、周期 reconcile**，**不得由查询触发承担正确性**（否则"只有知道它存在才能搜到它"）；工程描述文件变化应触发地图重算；watcher 只负责低延迟，**git diff + 周期 sweep 负责最终一致性**；修复后**用 `PuddingCodeIndex` 自身 dogfood 验收** | ✅ **全部采纳**。→ **M3** |

### P1（全部采纳）

- **P1-1** 有界内存队列**必须配持久化 dirty set**（watcher 事件会合并/重复/丢失，不能假设 exactly-once）⇒ 至少一次语义 + 幂等合并键 `(LibraryId, CanonicalPath, ContentHash/Generation)`；队列满写"需全局 reconcile"标志，**不得静默丢弃**；多方只产脏标记，**单 writer 串行提交**。
- **P1-2** **重叠 scope 不变量缺失**：同库内应用**最长路径匹配**或明确父子覆盖，**禁止同一文件由两个 owned scope 写入**；**每库单 writer + 租约 + owner id + fencing token**；查询只读**最后成功发布的 generation**，失败增量不得留半代；rename/delete 处理 Windows 大小写 / reparse point / 长路径。
  - ⚠️ **我的实测把这条从"推断"升级为"已证实"**：812 条重复路径、样本同一文件 4 份 ⇒ 不变量确实不存在（见 §3）。
- **P1-3** **生产结构化检索尚不存在，不能把 U4 评测当交付**：先稳定契约 —— `RetrievalIntent.Auto` 为**序列化默认值**；结构节点/关系为**一等类型**；`File/LSP/Vector/StructuredMap/GrepDegraded` **分别标注来源**；游标含 `LibraryId+generation+查询摘要`（**防跨代分页**）；大结果导出为**带 TTL/大小/generation 清单的受管制品**；收窄建议按实际 facet 分布生成。→ **M4**
- **P1-4** **语言质量失衡比扫描速度更先阻挡产品价值**（C# 0.639 / TS 0.068 / MD 0.023）：**按语言设独立门禁**；先修 outline 提取、分词、Markdown 标题与代码块建模，**再**优化 ANN；"过短代码"规则**只应阻止 `if/else` 成为独立向量 chunk，不得把其结构关系从语法/调用图中删除**。→ **M5**
- **P1-5** **`mismatch=0` 不足以证明 int8 可生产化**（只证明该测试集排序一致）：元数据须固定 provider/model/revision/dimension/dtype/normalization/distance metric/tokenizer-chunker version；**先 feature flag + shadow 对比再切读路径**。→ **M5**
- **P1-6** **"45,677 行超过单线程拐点"只证明单线程不足，不能直接推出必须 ANN**：先做**并行 int8 exact scan** 的端到端基准（并发/内存/冷启动/尾延迟），只有仍不满足**已裁定 SLO** 才引入 ANN（ANN 带来构建、持久化、删除更新、召回损失、版本迁移成本）。→ **M5**
- **P1-7** **LSP 融合边界必须守叶子依赖方向**：`PuddingCodeIndex`=索引/结构化查询/向量**端口**；`PuddingCodeIntelligence`=LSP 查询与**融合**；Host=资源池 adapter / LSP 进程适配 / 配置 / 工具 / Admin API。融合用**可解释 rank fusion**，不直接相加异构原始分；LSP 超时降级到结构化地图但**暴露降级原因**。→ **M6**
- **P1-8** **1GB 不能只在写满后"日志+GC"**（GC 消不掉存活数据，`VACUUM` 还需额外临时空间）：应设**软/高/硬三档精确预算** —— 软：预警+增量回收；高：停止最低优先级全文/冗余 chunk 增长；硬：**拒绝突破预算的新代发布，继续服务上一代**；**始终保留 outline/符号/关系核心地图**；用预估写入量+可用磁盘检查+incremental vacuum/分段重建。→ **M2**

### P2（采纳）

- **P2-1** Admin 面板**后置 UI、前置状态契约**（先稳定只读状态 API，再上暂停/恢复/重建/GC；**不得让 UI 直连或改 SQLite**）。
- **P2-2** 状态输出缺字段：队列深度/容量、最老等待时间、当前 Run、最后成功 generation、退避档位、库总字节、预算、GC 状态、腐败/降级原因、模型路由、LSP 可用性、文件数与排除统计。
- **P2-3** **项目根内数据库会形成自索引与工作树污染风险**：必须隐藏目录 + 索引器硬排除 + `.git/info/exclude`；**默认不改受版本控制的 `.gitignore`**。

| # | 它不同意的 | 我的裁定 |

2 | **"45,677 行 > 拐点 ⇒ 必须 ANN"不成立** | ✅ **接受**（见 P1-6） |
3 | **grep 不能称为结构化检索的等价降级** | ✅ **接受**（见 §2#5） |
4 | **反对在叶子组件里硬编码 Qwen3 Embedding 0.6B**：可以是当前默认路由，但**组件协议只描述 embedding 能力/维度/格式**，不依赖具体模型名；路由由资源池+配置决定 | ✅ **接受，且与我既有裁定一致**（"不得直接读资源池、由资源池提供服务、配置声明路由"）—— 它把这条**收紧为"协议不得出现模型名"**，更干净 |

6 | **反对把"过短代码忽略"应用到结构地图本身**（`if/else` 不该做成 embedding chunk，但控制流/关系仍可能有结构价值；只在 chunk/向量层降权） | ✅ **接受，这是一处真实设计错误** |
7 | **反对"根 scope 选 E 就等于问题完成"**：E 解决复发、**不恢复新鲜度**；若迁移立即进行 ⇒ **E + 在新项目库全量重建**；若迁移延期 ⇒ **E + A**；**不建议在旧共享库执行 B** | ✅ **接受**，并据 §3 强化：因根 scope 独立贡献仅 377 行（含仓库外文件），**"在新库重建"明显优于"旧库 A 全量重建"** |

## 6. 修订后的路线（codex §C 的 M0~M6，父级采纳并加约束）

所有切片继续 **S1 独立实现 → S2 独立测试 → S3 无宿主验证 → S4 边界断言 → S5 宿主接入**。

| 里程碑 | 内容（摘要） | 排序理由 |
|---|---|---|
**M0 冻结风险与语义** | 定义 Library/Scope/Project 词表；固化状态机、Run 记录、**容量单位**；暂停把陈旧 `Registering` 当冗余的清理判据；建 ADR 要求—生产入口—测试追踪矩阵 | **不先解决语义，迁移会把错误状态复制进新库** |
**M1 状态机 + Run + 启动恢复** | 拆 `Coverage/ServingState/RunState`；`CodeIndexRuns` 真实写入链；取消/异常/租约过期/启动恢复；修清理资格 | 修 D1~D4 根因 |
**M2 每项目一库 + 初始化/加载 + 容量治理** | `LibraryId+CanonicalRoot+FormatVersion`；初始化/加载/会话绑定/换项目提示；编译忽略规则；软硬预算+GC+腐败检测；`GrepDegraded`；**逐项目重扫 + 原子切换** | 在旧共享库上继续扩充会**增加**迁移成本 |
**M3 摄取闭环与最终一致性** | 初始化发现工程（不再靠查询）；watcher+git diff+周期 sweep 汇入**持久化 dirty set**；溢出转 reconcile；`ListFilesAsync` 分页；暴露退避档位/进度 | 修 D5 |
**M4 生产结构化地图检索** | 节点/关系/调用图/摘要查询；多条件过滤；`RetrievalIntent.Auto`；跨代安全分页；受管结果制品；facet 收窄建议；来源模型 | 产品能力本体 |
**M5 多语言质量 + 向量生产化** | 语言适配接口；先修 TS/Markdown；int8 接生产（先 flag+shadow）；先并行 exact scan，按 SLO 决定 ANN | 质量失衡先于性能阻挡价值 |
**M6 LSP 接入与混合融合** | 在 `PuddingCodeIntelligence` 接 LSP；来源标注；按 intent 融合；超时/熔断 | 守叶子依赖方向 |

**排序原则（codex 原话，我认同）**：**先避免误删与永久卡死 → 再改存储拓扑 → 然后保证索引正确 → 之后才提升检索质量与性能 → 最后固化 UI。**
