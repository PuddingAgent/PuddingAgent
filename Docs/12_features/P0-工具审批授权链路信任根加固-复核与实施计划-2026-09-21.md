## 2. 三处需要修正/扩展的事实（本复核的主要产出）

### 2.1 发现①：危险不在"名单太长"，而在"名单的语义假设错误"

`ToolApprovalCommandFirewall.cs:59` 起的 `SafeFirstTokens` 中有一组注释为
**「轻度文件操作（不破坏既有内容）」**，但同组实际含：

```csharp
"copy-item", "copy", "cp", "xcopy", "new-item", "mkdir", "md", "touch",
```

**`copy` / `xcopy` 天然覆盖目标文件**，与「不破坏既有内容」**直接矛盾**；`new-item` 亦可 `-Force` 覆盖。
而 `IsSafeSegment`（`:330`）**只校验首词（`:346`）与 git 动词白名单**，全流程**唯一带参数校验的是 `tee-object`**（`HasSafeTeeObjectTarget`）。

⇒ **结论**：仅"收窄白名单"不足以保证闭环 —— 需要**按能力重分类**，并对"写-覆盖"类施加**目标路径校验**。

**可达示例（白名单实测支持）**：
- `copy <任意源> <runtimeRoot>\tool-approval\tickets.json`（首词 `copy` ∈ 白名单，且无目标校验）
- `type D:\data\config\llm.providers.json`（首词 `type` ∈ 白名单 ⇒ 敏感配置可读）

## A 步现场确权（2026-09-21 20:20，只读复核）

**结论**：卡内所称「三类审批存储」经现场定位为 **4 个持久化面**，全部**无签章 / 无序号 / 无 hash 链**。

| # | 文件（相对 RuntimeRoot） | 实现（`Source/PuddingRuntime/Tools/Approval/`） | 结构 | 完整性保护 |
|---|---|---|---|---|
| 1 | `tool-approval/tickets.json` | `FileToolApprovalTicketStore`（`FileToolApprovalStores.cs:17`） | 整文件 JSON 数组，按 `TicketId` 建字典 | **无** |
| 2 | `tool-approval/allowlist.json` | `FileToolApprovalAllowlistStore`（`:52`） | 同上，按 `RuleId`；**每次保存自动注入 `ToolApprovalBuiltInAllowlistRules.Create()`** | **无** |
| 3 | `tool-approval/audit-events.jsonl` | `FileToolApprovalAuditStore` | **追加式 JSONL**，仅进程内 `SemaphoreSlim` 串行化 | **无** |
| 4 | `tool-authorizations.json` | `InMemoryToolAuthorizationService`（`:36`） | `PermanentGrantFile{ Version=1, Grants[] }` | **无** |

### 四条对修复设计有直接影响的现场事实

1. **写入是「整文件重写」**：`SaveUnlockedAsync` ⇒ `File.WriteAllTextAsync(path, 全量数组)`。
   ⇒ 完整性方案**不能**用「逐条序号」；须对整个文件做**签章**（或改造为 append-only + 序号链）。**这是 A 步方案选择的首要约束。**
   例外：`audit-events.jsonl` 已是追加式 ⇒ 可直接上 hash 链 / 单调序号。
2. **损坏即视为空**：`JsonException` → 返回空字典 + `LogWarning`；`tool-authorizations.json` 的 `catch` 走「忽略」。
   ⇒ 这四个面**失败方向都是安全的**（丢失授权只会退回"重新要求授权"），**不可被攻击者用来提权**；但同时也说明**篡改是静默的** —— 正是本卡要修的靶心。
3. ⚠️ **`tool-authorizations.json` 已存在一层天然缓解**：`LoadPermanentGrants` 只接受 `Scope == Permanent` 的条目 ⇒ **无法**通过手改文件注入 `Once`/`Session` 授权。
   **但可注入任意 `Permanent` 授权** ⇒ 与卡内发现⑤ 一致（该文件先于审批被查询，命中即 `Allow`）。
4. ✅ **`DefinitionHash` 匹配校验已存在**（`InMemoryToolApprovalService.cs:1332-1367`）：存储哈希缺失或与当前定义哈希不一致时，以 `Reason = "definition drift: …"` 拒绝。
   ⇒ 卡内 (b) 的 `DefinitionHash` 那一半**已有实现**；A 步只需补 **`Source` 与 `ApprovalTicketId`**（防止「拿一张旧票据的哈希去匹配另一条来源」）。

### 据上述事实对 A 步实施顺序的调整

- `DefinitionHash` 校验已存在 ⇒ **不重复实现**，改为「验证 + 补契约测试」（现有是否已覆盖 drift 拒绝路径待查）。
- 「整文件重写」⇒ 优先选**整文件签章（HMAC + 落盘单调序号）**，而非逐条序号；`audit-events.jsonl` 另行上 hash 链。
- A 步开工前必须定下的**两个决策点**：① 签章密钥来源（应沿用既有密钥设施，待查 `PuddingDataPaths` / 配置层）；② **存量无签章文件的迁移策略**（拒绝 / 首次加载即签章并记一次审计）。倾向于「首次加载即签章 + 审计」，但**需蜜糖确认**（属裁决域）。

### 1. 密钥来源 —— 不新造密钥（此前决策点①，用证据回答）

实测 `D:\data\config\security.json` 顶层键为 `jwt` + `keyVault`；对应
`PuddingSecurityConfig { Jwt, KeyVault }`，其中
`PuddingKeyVaultConfig { Mode = "local-file", MasterKeyRef }`
（`Source/PuddingCore/Configuration/PuddingConfigModels.cs:373+`），且平台侧已存在
`Source/PuddingPlatform/Services/KeyVaultService.cs`。

⇒ **方案**：复用既有 KeyVault 主密钥（`MasterKeyRef` 指向），**按文件域分隔派生签章子密钥**：
`subKey(file) = HMAC-SHA256(masterKey, "tool-approval/v1/" + fileName)`
⇒ 每个文件独立子密钥，**跨文件重放无效**（拿 allowlist 的 mac 去冒充 tickets 不可行）。

⚠️ **待确认（A 步开工第一步）**：runtime 侧是否已有 KeyVault 读取实现。
平台侧已实测存在；runtime 侧未确认 ⇒ 须先查，不得推定。若 runtime 无访问路径，退化为「按 `MasterKeyRef` 直接读同源主密钥文件」，**与平台同源**而非另立。

### 2. 信封格式（整文件签章）

```json
{ "schemaVersion": 2, "seq": 17, "signedAtUtc": "…", "alg": "HMAC-SHA256",
  "payload": [ /* 原有数组，位置不变 */ ], "mac": "<base64>" }
```

- **向后兼容**：`schemaVersion` 缺失 ⇒ 认定为旧格式（根即数组），走 §5 迁移路径。
- `mac` 覆盖 `(seq, signedAtUtc, canonical(payload))` ⇒ 同时防**篡改**与**回滚**。
- ⚠️ **seq 单调性的前提**：必须另有持久化的「已见最大 seq」锚点，否则"把旧文件整体搬回来"仍可绕过 —— 见 §4 风险。

### 3. 逐文件差异化设计（由实测规模决定，**不可一刀切**）

| 文件 | 方案 | 理由 |
|---|---|---|
`audit-events.jsonl` | **不可**整文件签章。改为**逐行 append-only + 前向 hash 链**（每行带 `prev` = 上一行 mac），另立**小锚点文件** `audit-events.anchor.json {seq, mac}`，启动只校验**尾部锚点** | 38.6MB ⇒ 整文件签章须重写 38MB 且每次校验 O(N) |
`tickets.json` | 整文件签章 + **原子写**（temp → `File.Replace`） | 2.6MB 成本可接受；当前非原子写有截断风险 |
`allowlist.json` | 整文件签章 | 30KB |
`tool-authorizations.json` | 整文件签章（**优先**，提权靶心） | 3.6KB |

### 4. ⚠️ 实测暴露的两个量级问题（**超出本卡范围**，但会拖累 A 步验收）

1. **`audit-events.jsonl` 38.6MB 无轮转**：`FileToolApprovalAuditStore.ListAsync` 一次性读全文件 + 逐行 `JsonSerializer.Deserialize` 11,120 次 ⇒ 内存与延迟随运行时间线性恶化。A 步加上 hash 链后若再全量校验会更慢。**建议另开 P2 卡**（轮转 + 只读尾部 N 行 + 拒绝全量加载）。
2. **`tickets.json` 381 条无 TTL 累积**（正是卡内「票补 TTL」的靶心），叠加**非原子整文件重写** ⇒ 崩溃可产生截断文件，而现有实现把 `JsonException` 当作「空」处理 ⇒ **静默丢失 381 张票**（失败方向安全但静默）。A 步的原子写同时也是这一项的缓解。

**另**：seq 回滚检测需要「已见最大 seq」的持久锚点；`audit-events.anchor.json` 可复用为通用锚点文件（`approval-stores.anchor.json`），避免每文件一个。

### 5. 存量迁移策略（此前决策点②）

**选「首次加载即签章 + 记一次审计」**，而非拒绝：

- 拒绝会让 **11 grants + 381 tickets + 28 rules** 全部失效 ⇒ 属可用性事故；
- 「首次加载即签章」**只保留既有内容、不新增任何权限**，且留下审计事件 `ApprovalStoreAdopted`（含文件、条目数、mtime、seq 初值）；
- ⚠️ **该选择的弱点须写明**：它把「未签章 = 首次」与「未签章 = 被降级攻击（攻击者删掉签章）」归到同一路径。
  缓解：① 一次性 adopt 后**立即落盘签章**，此后任何缺签章都判为篡改；② `ApprovalStoreAdopted` 纳入可观测面（仿 `classifier_status`），一旦在生产重复出现即为入侵信号。
- **需蜜糖确认**（属裁决域）：它决定了攻击者能否通过"删掉签名"把系统打回 adopt 路径（只能成功一次，但一次就够）。

## A4 密钥来源确权 + 威胁模型修正（2026-09-21 21:10）

### 1. runtime 侧确权（回答 A3 §1 的待确认项）

| 事实 | 证据 |
|---|---|
`IKeyVaultService` 定义在 **PuddingCore** | `Source/PuddingCore/Abstractions/IKeyVaultService.cs:6`（含 `Encrypt/Decrypt`、`GetSecretAsync(id, includePlainText)`、`Inject/Strip`、`CreateSecretAsync` 等） |
runtime **已在消费**该抽象 | `Services/AgentExecutionService.cs:1224`、`Services/DirectLlmClient.cs:792`、`Services/JevDecisionOptionsProvider.cs:163/185`、`Services/OpenAiEmbeddingService.cs:135` |
存在 **NoOp 回退** | `Services/AgentExecution/NoOpKeyVaultService.cs:9`（internal）；`AgentExecutionService.cs:180` 默认 `?? NoOpKeyVaultService.Instance` |

⇒ **结论：runtime 能取密钥，但可能静默退化为 NoOp** ⇒ 方案**必须显式定义"密钥不可得"的行为**，不得依赖隐式可用性。

### 2. ⚠️ 对 A3 §1 的修正 —— 威胁模型否定了"本地密钥文件"方案

发现①/③ 的攻击者**就是本机 shell 工具本身**，它能 `type` 任何 `D:\data\` 下的文件。
若签章密钥是 data root 下的本地文件（A3 的退化方案），攻击者可**同时：读密钥 → 改文件 → 重算 mac** ⇒ **签章对该攻击者零增益**。

⇒ 由此得到三个必须写进卡的结论：

1. **A 步签章不是对发现①/③ 的主防线**；主防线是 **C2 的路径校验 / 硬边界前移**（步骤 5）。签章的正确价值是：
   (a) 检测**不经该 shell 通道**的篡改（外部进程 / 其他 Agent / 部署事故 / 手工误改）；
   (b) 让任何篡改**事后可证**（审计）；
   (c) 检测**损坏**（截断、半写 —— 实测 `tickets.json` 非原子写确有此风险）。
2. **必须在卡上写明上述边界**，否则「A 步完成后」会被误读为「发现①/③ 已闭环」—— 那是**错误的**闭环声明。
3. 密钥来源改为 **KeyVault**（`GetSecretAsync`；持久键 `approval-store-signing-key`，首次缺失则生成并 `CreateSecretAsync` 写回），**不使用 data root 明文密钥文件**。理由：KeyVault 的值存在平台侧（`PuddingPlatform/Services/KeyVaultService.cs` + `Sm4Crypto`），**不经 data root 明文暴露**，因此对 ①/③ 的攻击者不可读。

### 3. 代价与实施约束（新增）

⚠️ **审批存储当前是「仅凭 `PuddingDataPaths` 的同步构造」**：`new FileToolApprovalTicketStore(PuddingDataPaths, ILogger)`（`PuddingToolServiceCollectionExtensions`）。
而 KeyVault 是**异步**的 ⇒ 不能让构造期阻塞。

⇒ **实施约束**：把密钥解析从「构造期」**推迟到「首次读写期」**（惰性 + 进程内缓存），或引入 `IApprovalStoreIntegrityKeyProvider` 抽象由 DI 注入（推荐后者：可测、可替换、显式表达"密钥可能不可得"）。

### 4. 密钥不可得时的策略（显式，fail-closed 但不清空）

| 场景 | 行为 |
|---|---|
读：文件**有**签章 而密钥不可得 | **拒绝加载该文件**，记 `ApprovalStoreIntegrityUnavailable` 审计 + 暴露到可观测面 —— **不得静默当作空**（当前 `JsonException → 空` 正是这个静默问题） |
读：文件**无**签章（旧格式） | 走 §A3-5 的 adopt 路径（首次签章 + 审计） |
写：密钥不可得 | **拒绝写入**并升为 warning —— 避免产出后续无法验证的文件 |

⚠️ **风险**：NoOp 回退在测试 / 受限环境很常见 ⇒ 上线即可能"自锁"。
⇒ **列为 A 步开工前置检查**：先确认生产宿主**确实注册了** KeyVault（查 DI 注册 + 运行时可观测面），再落签章；否则先只落"检测 + 审计"（记录缺失但不拒绝），分两步上线。

### 5. 顺带

`IKeyVaultService` **无密钥轮换 / 版本概念** ⇒ 签章信封须自带 `keyId` 字段，为将来轮换预留（A3 §2 信封格式需补 `keyId`）。
