## 三、新发现：artifact 回读循环（本轮最重要）

三次 `file_read` 的结果尺寸几乎相同：

| 结果文件 | 字节 | SHA256 前缀 |
|---|---|---|
| `tooluse_J9rey…-file_read.txt` | 21979 | 66E2825CA6B560A1 |
| `tooluse_RpyB…-file_read.txt` | 21936 | CCC741A3DF4DCE6B |
| `tooluse_s80vR…-file_read.txt` | 21853 | A7D590F1A738E67D |

而首次 `file_search` 结果为 21888 字节。差值仅几十字节，来自每次包装里的
artifact 路径与 sha256 不同。

**点击证据**：`file_read` 结果正文的第一行是

```
? Tool 'file_read' succeeded (exit=0):
[META: size=21884 chars, lines=3, encoding=utf-8]
? Tool 'file_search' succeeded (exit=0):
```

即：模型在用 `file_read` **回读上一轮 `file_search` 的 artifact 文件**。

### 机制

1. `file_search` 返回 21 KB，超过模型历史保留上限 ⇒ 历史中只留预览。
2. 运行时在截断处给出提示：
   `use file_read with offset_lines/limit_lines to continue`。
3. 模型照做，但**未传 `offset_lines`/`limit_lines`**，直接读全文。
4. `file_read` 结果同样约 22 KB ⇒ 再次被截断 ⇒ 回到第 2 步。

### 代价

| 时点 | 请求数 | 总 token | 缓存命中率 |
|---|---|---|---|
| 首次查询 | 6 | 588,658 | 89.1% |
| 第二次 | 9 | 917,207 | 92.3% |
| 第三次 | 28 | **3,626,025** | 90.2% |

一个「列出 `.csproj` 路径」的任务，主体在首轮 `file_search` 就已完成，
却因回读循环烧到 362 万 token 仍未收敛。

**结论**：这不是模型能力差异，是截断提示与模型行为之间的闭环缺陷。
提示语建议了正确做法，但没有任何机制阻止「重复读同一个 artifact」。

### 可选修法（未实施，待裁定）

1. 同一 artifact 第二次被 `file_read` 时，返回显式提示「该内容已在上文提供，
   请勿重复读取」，而不是再返回 22 KB。
2. 截断提示改为给出**可直接复制的分页参数**，而非自然语言建议。
3. 对 `file_search` 的 `limit` 命中（本次 `truncated — limit 200`）显式提示
   用更窄的 pattern，而不是让模型去读全文。

## 四、缺陷：`cancel` action 不可达（已修复）

尝试取消上述失控子代理时，工具返回：

```
参数 'task' 或 'tasks' 是必需的。批量模式必须传入 JSON array。
```

根因：`SubAgentTool.cs` 的 `cancel` 分支原先位于 `:245`，
而 `task` 校验在 `:118`（`if (string.IsNullOrWhiteSpace(task) && …) return Fail(...)`）。
只传 `pool_action=cancel` 的调用在参数校验处即被拦下，**永远到不了该分支**。

修复（`45a5078`）：把整个 `cancel` 分支前移到 `task` 解析之前
（`:104`），并在注释里记下这次位置错误的原因。构建 0 错误。

> 教训：上一轮我把该分支放在「池化分支之前」就以为安全，但真正的门槛是
> **参数校验**，不是池化分支。摆放位置必须相对**最靠前的校验点**来判断。

## 六、修复未闭合：`FullFile` / 分页参数绕过字节闸门（2026-11-14 17:2x）

### 现象：`639b5db` 上线后循环仍在

部署 `639b5db`（guardrail 改为行数与字节取更严格者）后重启 Core，
程序集 `17:18:58` 晚于修复提交，`runtime_identity` 判 `at-or-after-head`。
随后派 `claude-sonnet-5-5` 重跑同类任务，它**依旧进入回读循环**：

| 时点 | 请求 | 总 token | 备注 |
|---|---|---|---|
| 09:22:16 启动 | — | — | 同题同模型 |
| 观察点 1 | 6 | 516,771 | 已出现一次 `file_read` |
| 观察点 2 | 15 | 1,758,638 | 未收敛，主动 `cancel` |

工具产物目录里只有 **一次** `file_read`，但其产物尺寸 **21,936 字节**，
`originalLineCount=4`，而源文件是 **3 行** —— 多出来的一行是 `[META]` 头，
即这次调用返回了**整个文件**，guardrail 完全没有生效。

### 根因：四条路径都能绕过行数 guardrail

`FileReadTool` 的 guardrail 条件原文是
`if (!hasExplicitSlice && args.FullFile != true && (totalLines > 300 || fileInfo.Length > 8_192))`。
于是下列四种调用都跳过闸门，直接返回全文：

1. `FullFile=true`（本次实测就是这条）
2. `HeadLines` → `hasExplicitSlice = true`
3. `TailLines` → 同上
4. `OffsetLines` / `LimitLines`（不限行数）→ 同上

以及第 5 条：`MaxChars` 路径按**字符**截断，不按字节，`MaxChars=20000` 仍是 20 KB。

`639b5db` 只修了「默认 guardrail 分支内部的预览取多少」，
**没有覆盖这些旁路**。所以修复对「模型老实按默认参数读」有效，
对「模型主动指定参数」无效——而循环恰恰是后者触发的。

### 反讽的旁证

同一时期 runtime 的 artifact notice 已经在末尾明写
`do not use full_file=true`，模型照用不误。**靠提示语约束模型不可依赖。**

### 修复（`3ad517b`）

新增 `BoundInlineBody(body, startLine, out emittedLines)`，作为**所有返回点的统一字节闸门**：

- 行数仍是软约束（由调用方参数决定想读多少）
- **字节数是硬不变量**（≤ `InlineBudgetBytes` = 8192 − 512）
- 超预算时给出可直接照抄的 `OffsetLines={next}` 续读位置，并标明绝对行号区间
- 大文件流式路径同步跟踪 `windowStartLarge`，避免续读坐标算错

同时改掉两处会骗人的文档：`file_read` 的 description 原称
「默认超过 300 行或 8KB 时返回前 400 行」、`FullFile` 原称
「bypass the guardrail … regardless of size」，都与新行为不符。

### 三态证据

| 阶段 | 结果 |
|---|---|
| 修复后 | 17 / 17 通过 |
| 变异（`BoundInlineBody` 退化为直通） | **15 / 17**，恰好是两条新用例失败 |
| 复原（字节级，SHA `83A3205…` 一致）后 `-t:Rebuild` | 17 / 17 通过 |

变异红的两条报错数字本身就是证据：

- `FullFile=true` → **21,074 字节**（真实现场观测 21,936，量级一致）
- `OffsetLines=0 + LimitLines=2000` → **184,053 字节**

正向对照 `FullFile_SmallFile_ReturnsWholeContentWithoutTruncationNotice` 在变异态仍通过，
说明闸门没有过度截断正常小文件。

### 尚未验证

修复到本文写作时**未部署**（需重启 Core）。因此：
「同一任务在 Claude 下属主请求数能降到个位数」仍未证实。
已撤下正在循环的那个子代理（`CancelAsync` 生效，状态 `cancelled`）。

### 教训

**「修了根因」必须问一句「还有几条路径通向同一个症状」。**
上一轮我按默认调用路径取证、按默认路径修复、按默认路径写测试，
三条旁路全部漏掉；模型偏偏走了旁路。
下一次同类修复的检查项应显式包含：**该工具的所有入参组合是否会绕过新加的不变量。**

## 八、新发现：`shell` 的 Tip 指向一个子代理拿不到的工具

### 8.1 机制

`HostShellTool.cs:118-131` 会按命令首词追加一句「下次用别的工具」提示：

| 命令首词 | 提示推荐的工具 | 代码位置 |
|---|---|---|
| `select-string`/`sls`/`grep`/`findstr`/`rg` | `search_grep` | `:121` |
| `get-childitem`/`gci`/`dir`/`ls` | **`list_dir`** | `:123` |
| `get-content`/`gc`/`cat`/`type` | `file_read` | `:125` |
| `test-path` | `list_dir` 或 `file_read` | `:127` |

设计意图写在 `:97-100` 的注释里：用返回值教育比用工具描述教育有效。这个判断本身没错。

### 8.2 问题：推荐的工具有时不在已加载集合内

本轮子代理的实际状态，三条事实互锁：

1. 它执行了 `dir /s /b Source\*.csproj`（首词 `dir`）⇒ 触发 `:123`，输出被追加 `Tip: use list_dir next time …`
2. `CoreToolIds` 15 项**不含** `list_dir`；`PreloadToolIds` 默认只装载 `file_read`/`file_search`/`search_grep`
3. 该 run 的 9 次工具调用里**没有** `search_tools` ⇒ `list_dir` 从未被加载

结论：**提示推荐的那个工具，它当时调不到。** 要按提示做，得先花一轮 `search_tools` 把 `list_dir` 载入，再调一次。模型自然不会这么干——它转而用已加载的 `file_read` 去分页读那 21,843 字节的 artifact。

这不是循环的成因（循环由 `3ad517b` 修的旁路造成），但它解释了为什么 3× 价差里有一部分是**导航摩擦**。

### 8.3 修法取舍（未实施）

两种方向，成本不同：

| 方案 | 做法 | 代价 |
|---|---|---|
| A | `PreloadToolIds` 补 `list_dir` | 多一份 schema；且只是把摩擦点挪走，tip 仍可能指向别的未装载工具 |
| B | Tip 只在目标工具**已加载**时才追加 | 需要 shell 工具能读到当前可见集，属于跨层依赖 |

倾向 B 的变体：Tip 写「若已加载则用 X，否则直接调 Y」。但这要求 `HostShellTool` 拿到可见工具集合，**当前它拿不到**。是否值得为一句提示引依赖，需要在实施前评估。

**本轮不实施**，理由：这段话只影响效率不影响正确性，而它的修法需要动跨层接口。优先级低于 `file_search` 清单类结果过大（§7.5 第 1 条）。

## 九、子代理的默认工作目录是「工作区根」，不是「仓库根」

### 9.1 现场

该子代理的 shell 输出头一律是：

```
[shell=cmd cwd=D:\Data\workspaces\default]
```

它执行 `dir /s /b …` 并把结果重定向到 `temp\csproj_list.txt`。落地位置：

| 路径 | 是否存在 |
|---|---|
| `D:\Data\workspaces\default\temp\csproj_list.txt` | **存在**，20,386 B / 196 行 / mtime 17:44:49 |
| `D:\CodeProject\PuddingAgent\PuddingAgent\temp\csproj_list.txt` | 不存在 |

文件内容全部指向 `D:\CodeProject\PuddingAgent\PuddingAgent\Source\...`，而 `D:\Data\workspaces\default\Source` 不存在 —— 说明 `dir` 用的是绝对路径，而 `>` 的相对落点按 cwd 解析。

### 9.2 对照实验（排除「重定向与参数基准不一致」这个解释）

我用显式 `working_directory=D:\CodeProject\PuddingAgent\PuddingAgent` 跑 `echo probe-ctrl > temp\pctrl_1750.txt`：

| 路径 | 结果 |
|---|---|
| 仓库 `temp\pctrl_1750.txt` | **存在** |
| 工作区 `temp\pctrl_1750.txt` | 不存在 |

⇒ 重定向跟随 `working_directory`，两者基准一致。**所以差异不在重定向，而在 `working_directory` 本身：子代理拿到的就是工作区根。**

`spawn_sub_agent` 未传 `working_directory` 时默认取工作区根（`D:\Data\workspaces\default`），而仓库在 `D:\CodeProject\PuddingAgent\PuddingAgent`——两者不同。

### 9.3 影响与对照前一次修复

这解释了为什么子代理要花 2 次 `shell` 去试探：它拿到的位置信息里只有 `WorkspaceRoot: D:\Data\workspaces\default`，仓库路径只能靠任务书给。

也暴露了我在 `04c2126` 里那条规则的死角：**「`WorkingDirectory` 与 `WorkspaceRoot` 相同时省略」**。子代理默认两者恰好相同，于是那一行被省略——等于没提供任何有效位置。规则本身没错（相同就不重复），但对「工作区根 ≠ 任务真正根目录」这个常见情形没有帮助。

### 9.4 结论与待办

- 对仓库类任务，派子代理时**必须显式传 `working_directory`**，否则文件工具的相对路径全部无效。
- 我本轮的任务书写的是绝对路径，所以它没在这上面栽跟头——这是运气，不是机制。
- 待办：`SubAgentSpawnRequest` 目前没有「工作目录」这个必填概念，靠调用方自觉。是否要做成「不给就回落到父代理 cwd」，需要先看有多少调用方依赖当前默认。本轮不擅自改。

### 9.5 顺带修正一个投递观测

本条结果 `created_at=17:45:31`，实际到达 17:48:05，滞后 **2.6 分钟**；此前两条是 8.7 / 9.1 分钟。**延迟区间是 2.6–9.1 分钟，不是一个固定值**——这进一步否掉了「按消息时间戳推断执行进度」的做法。
