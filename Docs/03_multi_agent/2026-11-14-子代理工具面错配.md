# 子代理工具面错配

## 一、先纠正本文档的前一版结论

初版标题是「子代理工具说明书设计」，前提是「清单缺失，模型只能盲猜」。**这个前提是错的。**

`ContextPipelineLayers.cs:290` 的注释写得很清楚：

> 2026-08-22 冗余治理：未装载工具必须以名字索引出现（只列 id，不带 schema），
> 否则 Agent 无法知道有哪些延迟能力、只能盲调 search_tools。

机制已经在 `BuildToolsLayerAsync` 里实现：`available` 按 category 分组列出，`deferred` 单独一段只列 id，与 `ToolExposurePlanner` 的可见集同口径（`AgentExecutionService.Streaming.cs:232` 有对应约定）。

**所以不需要新造说明书。** 继续按错误前提施工，等于给一个已经有的功能再写一遍。

## 二、Claude 首轮调 search_tools 是正确行为

链路已完整核实：

| 环节 | 位置 | 事实 |
|---|---|---|
| 新 session 的已加载集合 | `AgentSessionManager.cs:179` | `GetLoadedToolIds` 返回**空集合** |
| 曝光规划输入 | `AgentExecutionService.Buffered.cs:158` | `loadedToolIds` = 空 |
| 可见集计算 | `ToolExposurePlanner.cs:146` | `visible = CoreToolIds ∪ activated` = **CoreToolIds** |
| 核心集内容 | `ToolExposurePlanner.cs:60` | 15 个，见下 |
| 其余去向 | `ToolExposurePlanner.cs:150` | 进 `deferredDescriptors`，只列 id |

**核心集 15 个**：`search_tools`、`plugin_catalog`、`plugin_search`、`plugin_unload`、`plugin_diagnostics`、`goal_read`、`goal_update`、`send_message`、`receive_messages`、`agent_status`、`agent_diagnostics`、`spawn_sub_agent`、`query_sub_agents`、`list_llm_providers`、`sleep`。

**`file_read` / `file_search` / `search_grep` 都不在里面。**

于是子代理首次运行看到的可用工具是「插件管理 + 目标管理 + 消息 + 自省 + 休眠」——**没有一个是干活用的**；它要读代码，必须先把 `file_read` 从 deferred 里加载出来。

Claude 首轮 `search_tools {"query":"file search grep read"}` 完全符合规范。**它是这套设计的正确产物，不是效率缺陷。**

## 三、真实问题：核心集与子代理的活儿错配

一句话：**常驻的是平台管理面，干活面要现加载。**

代价可以量化（同日 A/B 实测）：

- 子代理首轮 `estimated_context_tokens: 54074`、`tool_count: 42`
- Claude 首轮花掉一次工具调用 + 一次 `search_tools` 返回（out=3497 字符）才拿到读文件能力
- 用 Claude 与 GPT 都出现同一动作，说明这是路径性质，不是模型问题

而每加载一次，前缀就变一次——这还会**打断 prompt caching**。GPT 前两轮 `cache_hit_tokens = 0` 与此高度相关（**未做单变量证实**，但机制上吻合：工具集变化会让 provider 侧前缀失效）。

## 四、方案

### 主方案：给子代理预加载「干活包」

在子代理派发时，把它实际需要的工具预先放进该 session 的已加载集合，而不是让它在第一轮现场发现。

- 契约层：`SubAgentSpawnRequest` 增加 `PreloadToolIds`（可空），由派发方声明本次子任务需要的基础工具。
- 运行时：`AgentExecutionService` 装配前若发现是子代理且 `loadedToolIds` 为空，读该字段并入 `RememberLoadedToolIds`。
- 默认值：`file_read` / `file_search` / `search_grep` 三件套。理由——只读调查是子代理的绝大多数用法，而这三个正是 `CapabilityBundleMembers` 里 read 包的成员，语义自洽。

收益：省掉每个新子代理的首次加载轮，且让首轮前缀就稳定（有助缓存）。

### 不采用的方案

| 方案 | 不采用的理由 |
|---|---|
| 把 read 三件套塞进 `CoreToolIds` | 核心集是**所有 agent 共用**的全局常量，改它会同时影响主代理与所有模板；而主代理的首轮并不缺读文件能力（它的 loaded 集合随会话累积）。用全局常量解局部问题，副作用面太大。 |
| 写死一份工具说明书文本 | 已有机制，重复实现会与真实可见集漂移。 |
| 拉低 `DeferredLoadingThreshold` | 只会让更多工具进 deferred，加重而不是减轻。 |

### 顺带值得做的

`DeferredLoadingThreshold = 24` 对子代理是否合适，值得在预加载落地后重测一次。子代理的工具面通常远小于主代理，24 这个阈值主要为主代理设计。

## 五、验收标准

| # | 判据 | 取红方式 |
|---|---|---|
| T1 | 子代理首次运行时 `file_read` / `search_grep` / `file_search` 在 visible 集 | 去掉预加载，断言三者不应在 visible —— 应失败 |
| T2 | 子代理首轮不再出现 `search_tools` 探路调用 | 用 Claude 跑同一只读任务，对比首轮工具序列 |
| T3 | 主代理的可见集不受影响 | 断言主代理 `CoreToolIds` 数量与内容不变 |
| T4 | 未声明 `PreloadToolIds` 时行为与今天一致 | 不传该字段，断言 visible 仍等于 CoreToolIds |
| T5 | 两次运行的首轮前缀逐字节相同 | 跨 run 比较 prefix_hash |

T2 是唯一说明问题解决的判据；T1 是它的机制级前件。

## 六、未证实项

1. **42 这个数字的口径**。`agent_diagnostics` 显示本会话 `tool_count: 48`，而 L9 目录只列 10 个——说明该字段更可能是**注册总数**而非下发 schema 数。子代理的 42 若同口径，则「42 个 schema 全下发」的判断不成立，5.4 万 token 的构成需另行拆解。
2. GPT 前两轮零缓存是否真由工具集变化引起（机制吻合，但没有单变量对照）。
3. 子代理模板是否已有声明的「必需工具」字段可复用（未查 `BuildFrozenToolManifest` 全部分支）。
