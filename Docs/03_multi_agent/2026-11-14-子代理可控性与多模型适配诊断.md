# 子代理可控性与多模型适配诊断

## 一、结论摘要

本轮做了「同一任务、同一时间窗口、同一工具集」的双模型对照实跑，并逐条核对源码，得到：

| # | 结论 | 性质 |
|---|---|---|
| D1 | **三个「停止」入口全部只改标签**，无一中断正在执行的循环 | **已修复并实跑验证（§十）** |
| D2 | 运行中子代理的轮次/工具计数**恒为 0**：投影层回落默认值 | 已证实（代码 + 实测） |
| D3 | 单次运行注入 **42 个工具、首轮估算上下文 5.4 万 token**，模型需先探路 | ~~已证实~~ **已更正（§十）** |
| D4 | 两模型成本差 3.08 倍，**不等于**性能差：GPT 工作量本身大 1.41 倍 | 已证实（实测数字） |

D1 是安全边界问题（钱和资源），D2 是可观测性问题，D3/D4 是性能与选型问题。三者独立，可分别施工。

## 二、实测方法（可复现）

- 时间窗口：2026-11-14 07:26:55Z 同一 turn 内两次 `spawn_sub_agent`。
- 模型：`fastrouter-claude/claude-sonnet-5-5` 与 `fastrouter/gpt-6.1-sol`。
- 任务：**逐字节相同**的 4 段文本——回答「子代理取消能力」的三个事实问题（`SubAgentTool.cs` 路径、全部 action 名称及行号、是否存在 Pause/Cancel 实现），约束为只读、工具调用上限 15 次、结论须带 `file:line`。
- 证据源：`D:\Data\workspaces\default\agents\<agentId>\runs\run_*/events.jsonl`（逐事件）与 `run.json`（汇总）。

## 三、A/B 实测结果（双方均已完成）

统计口径：对 `subagent.llm.completed` 事件累加；成本按资源池登记的 `gpt-6.1-sol` 单价（3.38 / 13.1 / 0.34 美元每百万，账单反演）**对两侧统一折算**，仅用于可比性——Claude 单价未登记，这不是账单金额。

| 指标 | claude-sonnet-5-5 | gpt-6.1-sol |
|---|---|---|
| 终态 | completed | completed |
| 轮次 / LLM 调用 | **8 / 8** | 14 / 14 |
| 工具调用 / 失败 | 10 / **0** | 12 / **0** |
| 扫描文件数 | 1301 | **5089** |
| prompt tokens 累计 | 738,666 | 1,038,717 |
| 缓存命中率 | **92.6%** | 70.3% |
| 未命中 token | **54,343** | 308,169 |
| completion tokens | 2,146 | 5,973 |
| 用时 | **68 s** | 831 s（12.2×） |
| 折算成本 | **$0.4445** | $1.3682（3.08×） |

### 成本差的正解（修正初判）

初版把 3 倍成本差归因于缓存命中率，**这个归因不完整**。拆开算：

- **工作量差 1.41 倍**：prompt 总量 73.9 万 vs 103.9 万。GPT 把任务解读为「穷尽式取证」，扫了 5089 个文件；Claude 解读为「定位式检索」，扫了 1301 个。
- **缓存效率差 4 倍**：未命中占比 7.4% vs 29.7%。

两者相乘才得到 3.08 倍。单说缓存会高估缓存的作用——这点必须改正，否则会去优化一个只占一半的因素。

反过来说，**单位覆盖成本 GPT 更低**：$0.000342/文件 vs $0.000269/文件。它贵是因为它做了更多事。

### 产出质量：GPT 在严谨性上更强

- GPT 给出了 `CancelAllAsync` 的**方法体行范围**（`:474–530`），并明确指出「方法体未见取消执行令牌或暂停执行调用，**不能据此认定运行已被中断**」——这正是 D1 的结论，由它独立得出。
- GPT 做了**阳性对照**（`SubAgentTool.cs=True`），并在 RISKS 中声明「不能外推为任何形式的停止能力均不存在」。
- Claude 的行号更简洁，但结论止于「未找到具名 Pause/Cancel 接口」，未触及「通用原语已存在但未接线」这一层（这与我的任务书关键词给窄了有关，见 §七）。

**选型结论**：窄范围精确定位用 Claude（快 12 倍、省 3 倍）；需要穷尽覆盖与自我校准表述时用 GPT。不能只凭成本判定「GPT 表现差」——那是把工作量差异误读成能力差异。

## 四、缺陷详述

### D1 三个「停止」入口全部只改标签（最高优先级）

| 入口 | 位置 | 实际动作 | 中断执行？ |
|---|---|---|---|
| `CancelAllAsync` | `SubAgentManager.cs:472`（体 `:474–530`） | 筛 running → 写状态记录 → 归档 `cancelled` → 撤销浏览器委派 → 发事件 | **否** |
| `SleepAsync` | `SubAgentPool.cs:313` | `entry.Status = Sleeping`；对 **Busy** 状态仅打印 `is busy, force-sleeping` 告警后照改 | **否** |
| `DestroyAsync` | `SubAgentPool.cs:356`（体 `:367`） | `entry.Status = Dead` + 移除池条目 | **否** |

三个入口都在改动状态字段，都在发事件或写日志，**没有一个向执行链发出取消信号**。

`SleepAsync` 尤其具有误导性：对一个正在执行的池化子代理调用它，日志会打印 `force-sleeping`，读起来像是「已强制停下」，实际执行仍在继续。**日志在说谎**。

真正驱动执行的令牌在 `SubAgentManager.cs:639-640`：

```csharp
using var deadlineCts = new CancellationTokenSource(remaining);
using var runCts = CancellationTokenSource.CreateLinkedTokenSource(ct, deadlineCts.Token);
```

`runCts` 是 `using var` 局部变量，作用域不出 `ExecuteAsyncSubAgentWithLimitsAsync`，**未注册到任何可查询的注册表**。因此它只有两个取消源：外层 `ct`（父 turn 取消，会连父一起停）与 `deadlineCts`（超时）。实测该 run 的 `max_elapsed_seconds = 86386` ≈ **24 小时**，`max_rounds = 600`。

仓库**已有**完整控制原语 `Source/PuddingRuntime/Services/AgentLoop/ExecutionControlRegistry.cs`，注释写明「Controller 可通过此注册表向正在运行的 Agent Loop 下发 Cancel / Freeze / Resume」，`Cancel` 在 `:36`、`Freeze` 在 `:43`、`Resume` 在 `:52`。但 `SubAgentManager` 全文**未引用**该类型（定向 grep 0 命中）。

### D2 运行中状态恒为 0（可观测性）

实测：`query_sub_agents(action=running)` 报 GPT 子代理运行 187 秒、**`totalRounds=0 / totalToolCalls=0`**；同一时刻其 `events.jsonl` 已有 72 行、12 个 `round.started`、10 次 `tool.completed`。`run.json` 的 `totalRounds` / `totalToolCalls` 字段实测为**空值**（缺字段，不是 0）。

成因链：

- `FileSubAgentRunStore.cs:317` 等处，`TotalRounds` 仅在 `CompleteRunAsync`（终态写入）时落盘，**运行中不写**；
- `SubAgentDiagnosticsService.cs:92`：`TotalRounds = manifest.TotalRounds ?? 0` —— 缺失即回落 **0**。

后果：主代理无法区分「正常推进」「原地打转」「已卡死」。同类信号缺失曾导致一次 62 分钟 / 80 轮 / 221 次工具调用后才失败的运行被拖延到终态才暴露。

### D3 工具集过载与探路开销

每轮 `subagent.llm.started` 均记录 `tool_count: 42`、`estimated_context_tokens: 54074`（首轮）。任务只需 3 个工具（`file_search` / `search_grep` / `file_read`），其余 39 个是纯开销，并增加选择错误的概率。

外化行为：Claude 首轮即调 `search_tools`（参数 `{"max_results":3,"query":"file search grep read"}`）探路；两个模型都撞上 `search_grep` 的 `max_enumerated_files` 上限（返回 `coverage: partial — scanned 1300~2000/2000`），需二次缩范围。

## 五、修复方案

### 阶段 S1：让「停止」真的停（最小改动，不跨模块）

**进度（2026-11-14）**：五步全部落地。`f9d0b18`（1–3 步：注入注册表 / 注册 runCts /
CancelAllAsync 真取消）→ `d2295a2`（4 步：CancelAsync 单实例入口）→
`d08c922`（5 步：SubAgentTool 的 cancel 动作 + SubAgentPool 两个入口修正）。
D1 已从「注册表 → 管理器 → 池 → 工具」四层贯通：Agent 侧可用
`subagent(pool_action="cancel", sub_agent_id=...)` 停掉单个运行中的子代理。
测试共 50 条（PoolTests + wiring 9 + registry 12）全绿，关键用例均做过变异取红。

`runCts` 本就诞生在 `SubAgentManager` 内部，**不需要**引入跨模块依赖：

1. `SubAgentManager` 新增字段 `ConcurrentDictionary<string, CancellationTokenSource> _runCancellations`，键用 `subSessionId`。
2. 在 `ExecuteAsyncSubAgentWithLimitsAsync` 中注册 `runCts`（现签名不含 `subSessionId`，需补参数）；`finally` 中移除并释放。
3. `CancelAllAsync` 循环内补一步 `_runCancellations.TryGetValue(sa.SubSessionId, out var c) → c.Cancel()`，**顺序必须在 `CompleteRunAsync` 之前**，否则先报「已结束」再取消，语义倒置。
4. 同理修正 `SubAgentPool.SleepAsync` / `DestroyAsync`：对 `Busy` 条目必须先取消执行再改状态；若无法取消，就不该打印 `force-sleeping`。
5. `ISubAgentManager` 新增 `Task<bool> CancelAsync(string subSessionId, string reason, CancellationToken ct)`；`SubAgentTool` 新增 `action = "cancel"`（与 `destroy` 删池条目、`cleanup` 清已终态记录区分）。

不变量（必须保住）：

- `cancel` 后 `events.jsonl` 必须出现 `subagent.run.cancelled`，且**其后不再有新的 `llm.started`**——这是唯一能取红的判据。
- 父 turn 正常结束的清理路径不变；`ExecutionControlRegistry` 的主会话语义不受影响。

### 阶段 S2：补运行中状态

- `FileSubAgentRunStore` 增加运行中增量写（或在每轮 `round.completed` 时更新 manifest），使 `TotalRounds` / `TotalToolCalls` 在 running 态有真实值。
- `SubAgentDiagnosticsService.cs:92` 的 `?? 0` 改为 `int?` 未知语义。**0 与 unknown 必须可区分**，这是防误判的关键。

### 「暂停」的语义边界（必须先说清）

`ExecutionControlRegistry.Freeze` 是「取消 + 打标记，不自动恢复」，**不保存 LLM 对话状态**。对 agent loop 而言，真正可恢复的暂停只能在**轮次边界**实现：停在两轮之间、保留完整 messages 与 run 记录、`resume` 时重建令牌续跑。

不建议承诺「冻结进程式暂停」——当前架构下无法无损恢复。若需要，应先独立设计「可续跑快照」，不要顺手塞进本轮。

### 日志可见性

`events.jsonl` 已含完整证据（每轮 token、缓存、工具名、耗时、输出长度），但没有面向 Agent 的工具出口。建议补 `subagent_events` 只读工具，按 `sub_agent_id` 分页返回——**先只读，不做控制**，与 S1 解耦。

## 七、方法学教训（比结论更该复用）

1. **用「具名接口」当关键词，搜不到「通用原语已存在但未接线」这种形态。** 本轮任务书让子代理搜 `PauseSubAgent` / `CancelSubAgent` / `AbortSubAgent`，而真实实现是 `Cancel(sessionId)` / `Freeze(sessionId)`。正确做法是两头都搜：先按具名符号找现成接口，再沿「谁持有 `CancellationTokenSource`」反向找实现。
2. **「未找到」必须连同搜索边界一起报。** 两份结果都给了扫描文件数（1301 / 5089）与截断原因，这是可以复核的；只报「未找到」则无法判断是真空缺还是没搜到。
3. **成本差要先拆工作量，再谈效率。** 直接比总价会把「做得多」误判成「做得差」。
4. **子代理的 `totalRounds=0` 本身就是缺陷征兆**，不能当成「它没干活」的证据——D2 已证明该字段在运行中恒为 0。

## 八、未证实项（不得当作结论引用）

1. `TotalRounds` 是否还有第二个写入点（仅核到 `FileSubAgentRunStore` 与 `SubAgentDiagnosticsService`；grep 受 2000 文件枚举上限影响，`coverage: partial`）。
2. GPT 前两轮缓存零命中的真实原因（provider 侧实现 / 前缀变化 / 字段未透传，三者未做单变量区分）。
3. Claude 的 `pricePer1MTokens` 未登记，本文所有成本均为按 GPT 单价折算的可比基准。
4. 「暂停」在轮次边界的可恢复性未做原型验证。

## 十、cancel 可达性验证与 token 构成实测（2026-11-14 17:00）

### 9.1 修复点上线的现场核对

`45a5078` 提交于 **16:54:41**，运行中的 `PuddingRuntime.dll` 落盘于 **16:55:35**，进程 `startedAtUtc` = **16:56:05Z**。三者时序为「提交 → 编译 → 启动」，因此本轮实跑的是**含修复的产物**，不是旧程序集。`agent_diagnostics(runtime_identity)` 报 `verdict: at-or-after-head`。

### 9.2 取消实跑（`sub-066197de`，gpt-6.1-sol）

任务为只读盘点 `.csproj`（quick 档），在它 running 期间调用：

```
subagent(pool_action="cancel", sub_agent_id="…-sub-066197de", cancel_reason="…")
```

| 检查点 | cancel 前 | cancel 后 |
|---|---|---|
| 状态 | `running` | `failed`（完成时间 09:01:39Z） |
| 总 token | 138,051 | **138,051（未变）** |
| 请求数 | 2 | **2（未变）** |
| 工具输出 | — | 34,093 字符 |

**判据取的是 token 冻结，不是工具回执。** 修复前 `CancelAllAsync` 只改状态记录、loop 照跑，token 会继续增长；现在执行链确实被掐断。子代理结果消息同时返回 `Cancelled`，与上述现场一致。

一个语义瑕疵（不影响能力）：终态落的是 `failed` 而非 `cancelled`——`OperationCanceledException` 沿既有异常路径映射所致。工具回执与结果消息都是 `cancelled`，两处口径不统一，待后续收敛。

### 9.3 token 构成实测（同一运行时，主代理会话为对照）

主代理 98% 说明缓存在这套系统里是**能工作**的，不是全局失效。`first_churn_reason=tool_spec_changed` 也印证了「工具集一变，前缀即失效」这条机制。

### 9.4 子代理 138K token 的构成（假设，未经分项实测）

138,051 / 2 请求 ≈ 69K/请求。按次轮增量约 15K（34,093 字符工具输出）反推，首请求约 61.5K。可对应的已实测项：

- system 层 13.7K
- 工具 18 个（CoreToolIds 15 ∪ 预加载 3）≈ 10.4K
- skills catalog（350 条，按 8% 预算上限可达 84K，实际约 11K）

三项相加约 35K，仍有约 26K 无法归因。**因此本条只作为待验假设，不作为结论。** 下一步应读 `ContextPipelineLayers` 的层快照（`layerInfos` 已带 `TokenCount`），而不是继续按预算百分比推算。

### 9.5 与 D3 的关系（结论修正）

D3 原写「工具集过载与探路开销」。实测表明：

1. **探路开销已被消除**——`b176c08` 预加载后，首轮工具序列为 `file_search`，无 `search_tools`。
2. **真正的浪费不在工具 schema，而在系统层与目录层**——它们与任务无关，却按 1.05M 上下文窗口的固定百分比注入。
