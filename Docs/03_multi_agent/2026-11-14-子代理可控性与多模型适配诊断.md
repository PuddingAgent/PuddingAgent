# 子代理可控性与多模型适配诊断

## 一、结论摘要

本轮做了「同一任务、同一时间窗口、同一工具集」的双模型对照实跑，得到两个**硬缺陷**和一个成本结构事实：

| # | 结论 | 性质 |
|---|---|---|
| D1 | 「停止子代理」是**空转**：只改状态记录，不取消正在执行的循环 | 已证实（代码 + 实测） |
| D2 | 运行中子代理的轮次/工具计数**恒为 0**：投影层回落默认值 | 已证实（代码 + 实测） |
| D3 | 单次子代理运行注入 **42 个工具、首轮估算上下文 5.4 万 token**，模型需先探路 | 已证实（实测事件） |
| D4 | 同题对比：GPT-6.1-sol 轮次更多、缓存命中更低、折算成本 **2.26 倍**于 Claude | 已证实（实测数字） |
| — | 主代理**无**单实例暂停/停止入口，只有池级 destroy 与全量取消 | 已证实（接口清单） |

D1 是安全边界问题（钱和资源），D2 是可观测性问题（判断不了子代理在干什么），D3/D4 是性能问题。三者独立，可分别施工。

## 二、实测方法（可复现）

- 时间窗口：2026-11-14 07:26:55Z 同时派发，同一 turn 内两次 `spawn_sub_agent`。
- 模型：`fastrouter-claude/claude-sonnet-5-5` 与 `fastrouter/gpt-6.1-sol`。
- 任务：完全相同的 4 段文本——在仓库中回答「子代理取消能力」的三个事实问题（`SubAgentTool.cs` 路径、全部 action 名称及行号、是否存在 Pause/Cancel 实现），约束为只读、工具调用上限 15 次、结论须带 `file:line`。
- 证据源：`D:\Data\workspaces\default\agents\<agentId>\runs\run_*/events.jsonl`（逐事件）与 `run.json`（汇总）。

任务本身只读、无副作用，因此可作为零干扰基线；两模型拿到的是**逐字节相同**的任务文本。

## 三、A/B 实测结果

统计口径：对 `subagent.llm.completed` 事件累加 token；`rounds` 计 `subagent.round.started`；成本按资源池登记的 `gpt-6.1-sol` 单价（输入 3.38 / 输出 13.1 / 缓存 0.34，美元每百万）**对两侧统一折算**，仅用于可比性，不代表 Claude 真实计价（其单价未登记）。

| 指标 | claude-sonnet-5-5 | gpt-6.1-sol |
|---|---|---|
| 终态 | **completed** | running（统计时已 12 轮未完） |
| 轮次 | **8** | 12 |
| 工具调用 / 失败 | 10 / **0** | 10 / **0** |
| prompt tokens 累计 | 738,666 | 803,435 |
| 缓存命中 | 684,323（**92.6%**） | 574,314（**71.5%**） |
| 未命中 | **54,343** | **229,121**（4.2 倍） |
| completion tokens | 2,146 | 2,644 |
| 折算成本 | **$0.4445** | **$1.0043** |
| 用时 | 67.9 s | >187 s（未完成） |
| 工具组合 | file_read×2, search_grep×6, file_search×1, **search_tools×1** | search_grep×4, **shell×4**, file_read×2 |

三点值得单独指出：

1. **缓存命中差异是成本差的主因**。两侧 prompt 量接近（73.9 万 vs 80.3 万），但未命中量差 17.5 万 token，直接决定 2.26 倍成本。GPT 首轮与第 2 轮 `cache_hit_tokens = 0`，第 3 轮才到 98.9%；Claude 首轮即命中 79%。
2. **Claude 首个动作是 `search_tools`**，参数 `{"max_results":3,"query":"file search grep read"}`——它不确定工具名，先探路。这是 42 工具注入的直接副作用，属 D3。
3. **GPT 用了 4 次 `shell`** 完成只读调查。shell 在本机是 PowerShell，输出经 GBK 解码，中文匹配不可靠；这不是任务书要求的路径。

## 四、缺陷详述

### D1 「停止」是空转（安全边界，最高优先级）

`ISubAgentManager.CancelAllAsync` 的实现位于 `Source/PuddingPlatform/Services/SubAgentManager.cs:472`，循环体只做三件事：

1. `TrackSubAgentCompleteAsync(subSessionId, new SubAgentResult { Error = "Cancelled by parent" })` —— 改状态记录；
2. `_runStore.CompleteRunAsync(runId, new SubAgentRunCompletion { Status = "cancelled" })` —— 写归档；
3. `_eventBus.PublishAsync(new InternalEvent { Type = "subagent.run.cancelled" })` —— 发事件。

**没有任何一处向执行链发出取消信号。** 真正驱动子代理执行的令牌在 `SubAgentManager.cs:639-640`：

```csharp
using var deadlineCts = new CancellationTokenSource(remaining);
using var runCts = CancellationTokenSource.CreateLinkedTokenSource(ct, deadlineCts.Token);
```

`runCts` 是 `using var` 局部变量，作用域不出 `ExecuteAsyncSubAgentWithLimitsAsync`，**未注册到任何可查询的注册表**。因此它只有两个取消源：外层 `ct`（父 turn 取消，会连父一起停）与 `deadlineCts`（超时）。实测该 run 的超时为 `86386` 秒 ≈ **24 小时**，`max_rounds` 为 600。

后果：调用「取消」后，子代理的 agent loop 继续调用 LLM、继续计费，直到自然结束、600 轮用完或 24 小时超时。状态面板却显示已取消——**记录与事实背离**。

对照证据：仓库**已有**完整控制原语 `Source/PuddingRuntime/Services/AgentLoop/ExecutionControlRegistry.cs`，注释写明「Controller 可通过此注册表向正在运行的 Agent Loop 下发 Cancel / Freeze / Resume」，`Cancel` 在 `:36`、`Freeze` 在 `:43`。但 `SubAgentManager` 全文**未引用** `ExecutionControlRegistry`（定向 grep 0 命中）。

### D2 运行中状态恒为 0 轮（可观测性）

实测：`query_sub_agents(action=running)` 报 GPT 子代理运行 187 秒、**`totalRounds=0 / totalToolCalls=0`**；同一时刻其 `events.jsonl` 已有 72 行、12 个 `round.started`、10 次 `tool.completed`。且 `run.json` 的 `totalRounds` / `totalToolCalls` 字段**为空值**（不是 0，是缺字段）。

成因链已定位：

- `Source/PuddingPlatform/Services/FileSubAgentRunStore.cs:317` 等处，`TotalRounds` 仅在 `CompleteRunAsync`（终态写入）时落盘，**运行中不写**；
- `Source/PuddingPlatform/Services/SubAgentDiagnosticsService.cs:92`：`TotalRounds = manifest.TotalRounds ?? 0` —— 缺失即回落 **0**。

后果：主代理无法据状态判断子代理是在正常推进、原地打转、还是已卡死。今天早上那次 62 分钟 / 80 轮 / 221 次工具调用 / 零产物的失败，正是缺少这个信号才拖到最后。

### D3 工具集过载与探路开销

每轮 `subagent.llm.started` 事件均记录 `tool_count: 42`、`estimated_context_tokens: 54074`（首轮）。任务只需要 3 个工具（`file_search` / `search_grep` / `file_read`），其余 39 个是纯开销，且增加选择错误的概率。

实测外化行为：Claude 首轮即调 `search_tools` 探路；两个模型都撞上 `search_grep` 的 `max_enumerated_files` 上限（返回 `coverage: partial — scanned 1300~2000/2000 files`），需二次缩范围。

### D4 缓存命中差异（待归因）

Claude 首轮命中 79%，GPT 首轮与次轮全零。可能原因（**均未证实**）：provider 侧缓存实现不同、请求前缀在头两轮发生变化、或 GPT 通道未透传缓存命中字段。**未做单变量对照，故不写成结论**；但它直接造成 2.26 倍成本差，值得优先归因。

## 五、修复方案

### 阶段 S1：让「停止」真的停（最小改动，不跨模块）

`runCts` 本来就诞生在 `SubAgentManager` 内部，因此**不需要**引入跨模块依赖即可解决：

1. `SubAgentManager` 新增字段 `ConcurrentDictionary<string, CancellationTokenSource> _runCancellations`，键用 `subSessionId`。
2. 在 `ExecuteAsyncSubAgentWithLimitsAsync` 中注册 `runCts`（需把 `subSessionId` 传入该方法，现签名不含此参数）；`finally` 中移除并释放。
3. `CancelAllAsync` 循环内补一步：`if (_runCancellations.TryGetValue(sa.SubSessionId, out var c)) c.Cancel();`——顺序必须在 `CompleteRunAsync` **之前**，否则报「已结束」再取消，语义倒置。
4. `ISubAgentManager` 新增 `Task<bool> CancelAsync(string subSessionId, string reason, CancellationToken ct)`，实现复用第 3 步的单条逻辑，返回是否命中运行中实例。
5. `SubAgentTool` 新增 `action = "cancel"`（参数 `sub_agent_id`），与现有 `destroy`（池条目）语义区分：`cancel` 停执行、`destroy` 删池条目。

不变量（必须保住）：

- `cancel` 后 `events.jsonl` 必须出现 `subagent.run.cancelled`，且**其后不再有新的 `llm.started`**——这是唯一能取红的判据。
- 父 turn 正常结束时的清理路径不变；`ExecutionControlRegistry` 的主会话语义不受影响。

### 阶段 S2：补运行中状态

在 S1 之后做，因为需要同样的 `_runCancellations` 生命周期钩子：

- `FileSubAgentRunStore` 增加运行中增量写（或由 `SubAgentManager` 在每轮 `round.completed` 时更新 manifest），使 `TotalRounds` / `TotalToolCalls` 在 running 态有真实值。
- `SubAgentDiagnosticsService.cs:92` 的 `?? 0` 改为「未知」语义（`int?`），避免把「没数据」显示成「零进展」。这是**防止误判**的关键：0 与 unknown 必须可区分。

### 关于「暂停」的语义边界（必须先说清）

`ExecutionControlRegistry.Freeze` 的语义是「取消 + 打标记，不自动恢复」，**不保存 LLM 对话状态**。对 agent loop 而言，真正可恢复的「暂停」只能在**轮次边界**实现：停在两轮之间、保留完整 messages 与 run 记录、`resume` 时重建令牌续跑。

不建议承诺「冻结进程式暂停」——当前架构下无法做到无损恢复。若需要，应先独立设计「可续跑快照」，不要顺手塞进本轮。

### 日志可见性

`events.jsonl` 已具备完整证据（每轮 token、缓存、工具名、耗时、输出长度），但没有面向 Agent 的工具出口。建议随后补 `subagent_events` 只读工具，按 `sub_agent_id` 分页返回事件——**先只读，不做控制**，与 S1 解耦。

## 六、验收用例（每条都必须能取红）

| # | 用例 | 取红方式 |
|---|---|---|
| T1 | 派发一个长任务子代理，中途 `cancel` | 移除 S1 第 3 步后，必须观察到 cancel 之后仍有 `llm.started` —— 测试失败 |
| T2 | cancel 后的事件序 | 断言 `run.cancelled` 之后无 `llm.started`；把执行顺序改成「先 CompleteRun 后 Cancel」应失败 |
| T3 | 运行中状态非零 | 在子代理跑到第 3 轮时查询，断言 `totalRounds >= 3`；把 `?? 0` 改回原样应失败 |
| T4 | 未知 ≠ 零 | 构造 manifest 缺字段，断言返回 unknown 而非 0 |
| T5 | 单实例 cancel 不误伤 | 同时跑两个子代理，cancel 其一，断言另一个仍为 running |
| T6 | 工具集裁剪后首轮无 search_tools | 限定 tools 子集后，断言 Claude 首轮不出现 `search_tools` |

## 七、未证实项（不得当作结论引用）

1. `SubAgentManager` 中 `TotalRounds` 缺失是否还有第二个写入点（仅核到 `FileSubAgentRunStore` 与 `SubAgentDiagnosticsService`，grep 受 2000 文件枚举上限限制，`coverage: partial`）。
2. GPT 首两轮缓存零命中的真实原因。
3. Claude 的 `pricePer1MTokens` 未登记，本文所有成本均为「按 GPT 单价折算」的可比基准，不是账单金额。
4. 「暂停」在轮次边界的可恢复性未做原型验证。
