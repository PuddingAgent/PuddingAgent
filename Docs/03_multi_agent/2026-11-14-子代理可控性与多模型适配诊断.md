# 子代理可控性与多模型适配诊断

## 一、结论摘要

本轮做了「同一任务、同一时间窗口、同一工具集」的双模型对照实跑，并逐条核对源码，得到：

| # | 结论 | 性质 |
|---|---|---|
| D1 | **三个「停止」入口全部只改标签**，无一中断正在执行的循环 | **已修复并实跑验证（§十）** |
| D2 | 运行中子代理的轮次/工具计数**恒为 0**：投影层回落默认值 | 已证实（代码 + 实测） |
| D3 | 单次运行注入 **42 个工具、首轮估算上下文 5.4 万 token**，模型需先探路 | ~~已证实~~ **已更正（§十）** |
| D4 | 两模型成本差 3.08 倍，**不等于**性能差：GPT 工作量本身大 1.41 倍 | 已证实（实测数字） |

D1 是安全边界问题（钱和资源），D2 是可观测性问题，D3/D4 是性能与选型问题。三者独立，可分别施工。

## 二、实测方法（可复现）

- 时间窗口：2026-11-14 07:26:55Z 同一 turn 内两次 `spawn_sub_agent`。
- 模型：`fastrouter-claude/claude-sonnet-5-5` 与 `fastrouter/gpt-6.1-sol`。
- 任务：**逐字节相同**的 4 段文本——回答「子代理取消能力」的三个事实问题（`SubAgentTool.cs` 路径、全部 action 名称及行号、是否存在 Pause/Cancel 实现），约束为只读、工具调用上限 15 次、结论须带 `file:line`。
- 证据源：`D:\Data\workspaces\default\agents\<agentId>\runs\run_*/events.jsonl`（逐事件）与 `run.json`（汇总）。

## 三、A/B 实测结果（双方均已完成）

统计口径：对 `subagent.llm.completed` 事件累加；成本按资源池登记的 `gpt-6.1-sol` 单价（3.38 / 13.1 / 0.34 美元每百万，账单反演）**对两侧统一折算**，仅用于可比性——Claude 单价未登记，这不是账单金额。

| 指标 | claude-sonnet-5-5 | gpt-6.1-sol |
|---|---|---|
| 终态 | completed | completed |
| 轮次 / LLM 调用 | **8 / 8** | 14 / 14 |
| 工具调用 / 失败 | 10 / **0** | 12 / **0** |
| 扫描文件数 | 1301 | **5089** |
| prompt tokens 累计 | 738,666 | 1,038,717 |
| 缓存命中率 | **92.6%** | 70.3% |
| 未命中 token | **54,343** | 308,169 |
| completion tokens | 2,146 | 5,973 |
| 用时 | **68 s** | 831 s（12.2×） |
| 折算成本 | **$0.4445** | $1.3682（3.08×） |

### 成本差的正解（修正初判）

初版把 3 倍成本差归因于缓存命中率，**这个归因不完整**。拆开算：

- **工作量差 1.41 倍**：prompt 总量 73.9 万 vs 103.9 万。GPT 把任务解读为「穷尽式取证」，扫了 5089 个文件；Claude 解读为「定位式检索」，扫了 1301 个。
- **缓存效率差 4 倍**：未命中占比 7.4% vs 29.7%。

两者相乘才得到 3.08 倍。单说缓存会高估缓存的作用——这点必须改正，否则会去优化一个只占一半的因素。

反过来说，**单位覆盖成本 GPT 更低**：$0.000342/文件 vs $0.000269/文件。它贵是因为它做了更多事。

### 产出质量：GPT 在严谨性上更强

- GPT 给出了 `CancelAllAsync` 的**方法体行范围**（`:474–530`），并明确指出「方法体未见取消执行令牌或暂停执行调用，**不能据此认定运行已被中断**」——这正是 D1 的结论，由它独立得出。
- GPT 做了**阳性对照**（`SubAgentTool.cs=True`），并在 RISKS 中声明「不能外推为任何形式的停止能力均不存在」。
- Claude 的行号更简洁，但结论止于「未找到具名 Pause/Cancel 接口」，未触及「通用原语已存在但未接线」这一层（这与我的任务书关键词给窄了有关，见 §七）。

**选型结论**：窄范围精确定位用 Claude（快 12 倍、省 3 倍）；需要穷尽覆盖与自我校准表述时用 GPT。不能只凭成本判定「GPT 表现差」——那是把工作量差异误读成能力差异。

## 四、缺陷详述

### D1 三个「停止」入口全部只改标签（最高优先级）

| 入口 | 位置 | 实际动作 | 中断执行？ |
|---|---|---|---|
| `CancelAllAsync` | `SubAgentManager.cs:472`（体 `:474–530`） | 筛 running → 写状态记录 → 归档 `cancelled` → 撤销浏览器委派 → 发事件 | **否** |
| `SleepAsync` | `SubAgentPool.cs:313` | `entry.Status = Sleeping`；对 **Busy** 状态仅打印 `is busy, force-sleeping` 告警后照改 | **否** |
| `DestroyAsync` | `SubAgentPool.cs:356`（体 `:367`） | `entry.Status = Dead` + 移除池条目 | **否** |

三个入口都在改动状态字段，都在发事件或写日志，**没有一个向执行链发出取消信号**。

`SleepAsync` 尤其具有误导性：对一个正在执行的池化子代理调用它，日志会打印 `force-sleeping`，读起来像是「已强制停下」，实际执行仍在继续。**日志在说谎**。

真正驱动执行的令牌在 `SubAgentManager.cs:639-640`：

```csharp
using var deadlineCts = new CancellationTokenSource(remaining);
using var runCts = CancellationTokenSource.CreateLinkedTokenSource(ct, deadlineCts.Token);
```

`runCts` 是 `using var` 局部变量，作用域不出 `ExecuteAsyncSubAgentWithLimitsAsync`，**未注册到任何可查询的注册表**。因此它只有两个取消源：外层 `ct`（父 turn 取消，会连父一起停）与 `deadlineCts`（超时）。实测该 run 的 `max_elapsed_seconds = 86386` ≈ **24 小时**，`max_rounds = 600`。

仓库**已有**完整控制原语 `Source/PuddingRuntime/Services/AgentLoop/ExecutionControlRegistry.cs`，注释写明「Controller 可通过此注册表向正在运行的 Agent Loop 下发 Cancel / Freeze / Resume」，`Cancel` 在 `:36`、`Freeze` 在 `:43`、`Resume` 在 `:52`。但 `SubAgentManager` 全文**未引用**该类型（定向 grep 0 命中）。

### D2 运行中状态恒为 0（可观测性）

实测：`query_sub_agents(action=running)` 报 GPT 子代理运行 187 秒、**`totalRounds=0 / totalToolCalls=0`**；同一时刻其 `events.jsonl` 已有 72 行、12 个 `round.started`、10 次 `tool.completed`。`run.json` 的 `totalRounds` / `totalToolCalls` 字段实测为**空值**（缺字段，不是 0）。

成因链：

- `FileSubAgentRunStore.cs:317` 等处，`TotalRounds` 仅在 `CompleteRunAsync`（终态写入）时落盘，**运行中不写**；
- `SubAgentDiagnosticsService.cs:92`：`TotalRounds = manifest.TotalRounds ?? 0` —— 缺失即回落 **0**。

后果：主代理无法区分「正常推进」「原地打转」「已卡死」。同类信号缺失曾导致一次 62 分钟 / 80 轮 / 221 次工具调用后才失败的运行被拖延到终态才暴露。

### D3 工具集过载与探路开销

每轮 `subagent.llm.started` 均记录 `tool_count: 42`、`estimated_context_tokens: 54074`（首轮）。任务只需 3 个工具（`file_search` / `search_grep` / `file_read`），其余 39 个是纯开销，并增加选择错误的概率。

外化行为：Claude 首轮即调 `search_tools`（参数 `{"max_results":3,"query":"file search grep read"}`）探路；两个模型都撞上 `search_grep` 的 `max_enumerated_files` 上限（返回 `coverage: partial — scanned 1300~2000/2000`），需二次缩范围。

## 五、修复方案

### 阶段 S1：让「停止」真的停（最小改动，不跨模块）

**进度（2026-11-14）**：五步全部落地。`f9d0b18`（1–3 步：注入注册表 / 注册 runCts /
CancelAllAsync 真取消）→ `d2295a2`（4 步：CancelAsync 单实例入口）→
`d08c922`（5 步：SubAgentTool 的 cancel 动作 + SubAgentPool 两个入口修正）。
D1 已从「注册表 → 管理器 → 池 → 工具」四层贯通：Agent 侧可用
`subagent(pool_action="cancel", sub_agent_id=...)` 停掉单个运行中的子代理。
测试共 50 条（PoolTests + wiring 9 + registry 12）全绿，关键用例均做过变异取红。

`runCts` 本就诞生在 `SubAgentManager` 内部，**不需要**引入跨模块依赖：

1. `SubAgentManager` 新增字段 `ConcurrentDictionary<string, CancellationTokenSource> _runCancellations`，键用 `subSessionId`。
2. 在 `ExecuteAsyncSubAgentWithLimitsAsync` 中注册 `runCts`（现签名不含 `subSessionId`，需补参数）；`finally` 中移除并释放。
3. `CancelAllAsync` 循环内补一步 `_runCancellations.TryGetValue(sa.SubSessionId, out var c) → c.Cancel()`，**顺序必须在 `CompleteRunAsync` 之前**，否则先报「已结束」再取消，语义倒置。
4. 同理修正 `SubAgentPool.SleepAsync` / `DestroyAsync`：对 `Busy` 条目必须先取消执行再改状态；若无法取消，就不该打印 `force-sleeping`。
5. `ISubAgentManager` 新增 `Task<bool> CancelAsync(string subSessionId, string reason, CancellationToken ct)`；`SubAgentTool` 新增 `action = "cancel"`（与 `destroy` 删池条目、`cleanup` 清已终态记录区分）。

不变量（必须保住）：

- `cancel` 后 `events.jsonl` 必须出现 `subagent.run.cancelled`，且**其后不再有新的 `llm.started`**——这是唯一能取红的判据。
- 父 turn 正常结束的清理路径不变；`ExecutionControlRegistry` 的主会话语义不受影响。

### 阶段 S2：补运行中状态

- `FileSubAgentRunStore` 增加运行中增量写（或在每轮 `round.completed` 时更新 manifest），使 `TotalRounds` / `TotalToolCalls` 在 running 态有真实值。
- `SubAgentDiagnosticsService.cs:92` 的 `?? 0` 改为 `int?` 未知语义。**0 与 unknown 必须可区分**，这是防误判的关键。

### 「暂停」的语义边界（必须先说清）

`ExecutionControlRegistry.Freeze` 是「取消 + 打标记，不自动恢复」，**不保存 LLM 对话状态**。对 agent loop 而言，真正可恢复的暂停只能在**轮次边界**实现：停在两轮之间、保留完整 messages 与 run 记录、`resume` 时重建令牌续跑。

不建议承诺「冻结进程式暂停」——当前架构下无法无损恢复。若需要，应先独立设计「可续跑快照」，不要顺手塞进本轮。

### 日志可见性

`events.jsonl` 已含完整证据（每轮 token、缓存、工具名、耗时、输出长度），但没有面向 Agent 的工具出口。建议补 `subagent_events` 只读工具，按 `sub_agent_id` 分页返回——**先只读，不做控制**，与 S1 解耦。

## 七、方法学教训（比结论更该复用）

1. **用「具名接口」当关键词，搜不到「通用原语已存在但未接线」这种形态。** 本轮任务书让子代理搜 `PauseSubAgent` / `CancelSubAgent` / `AbortSubAgent`，而真实实现是 `Cancel(sessionId)` / `Freeze(sessionId)`。正确做法是两头都搜：先按具名符号找现成接口，再沿「谁持有 `CancellationTokenSource`」反向找实现。
2. **「未找到」必须连同搜索边界一起报。** 两份结果都给了扫描文件数（1301 / 5089）与截断原因，这是可以复核的；只报「未找到」则无法判断是真空缺还是没搜到。
3. **成本差要先拆工作量，再谈效率。** 直接比总价会把「做得多」误判成「做得差」。
4. **子代理的 `totalRounds=0` 本身就是缺陷征兆**，不能当成「它没干活」的证据——D2 已证明该字段在运行中恒为 0。

## 八、未证实项（不得当作结论引用）

1. `TotalRounds` 是否还有第二个写入点（仅核到 `FileSubAgentRunStore` 与 `SubAgentDiagnosticsService`；grep 受 2000 文件枚举上限影响，`coverage: partial`）。
2. GPT 前两轮缓存零命中的真实原因（provider 侧实现 / 前缀变化 / 字段未透传，三者未做单变量区分）。
3. Claude 的 `pricePer1MTokens` 未登记，本文所有成本均为按 GPT 单价折算的可比基准。
4. 「暂停」在轮次边界的可恢复性未做原型验证。

## 十、cancel 可达性验证与 token 构成实测（2026-11-14 17:00）

### 9.1 修复点上线的现场核对

`45a5078` 提交于 **16:54:41**，运行中的 `PuddingRuntime.dll` 落盘于 **16:55:35**，进程 `startedAtUtc` = **16:56:05Z**。三者时序为「提交 → 编译 → 启动」，因此本轮实跑的是**含修复的产物**，不是旧程序集。`agent_diagnostics(runtime_identity)` 报 `verdict: at-or-after-head`。

### 9.2 取消实跑（`sub-066197de`，gpt-6.1-sol）

任务为只读盘点 `.csproj`（quick 档），在它 running 期间调用：

```
subagent(pool_action="cancel", sub_agent_id="…-sub-066197de", cancel_reason="…")
```

| 检查点 | cancel 前 | cancel 后 |
|---|---|---|
| 状态 | `running` | `failed`（完成时间 09:01:39Z） |
| 总 token | 138,051 | **138,051（未变）** |
| 请求数 | 2 | **2（未变）** |
| 工具输出 | — | 34,093 字符 |

**判据取的是 token 冻结，不是工具回执。** 修复前 `CancelAllAsync` 只改状态记录、loop 照跑，token 会继续增长；现在执行链确实被掐断。子代理结果消息同时返回 `Cancelled`，与上述现场一致。

一个语义瑕疵（不影响能力）：终态落的是 `failed` 而非 `cancelled`——`OperationCanceledException` 沿既有异常路径映射所致。工具回执与结果消息都是 `cancelled`，两处口径不统一，待后续收敛。

### 9.3 token 构成实测（同一运行时，主代理会话为对照）

### 9.4 子代理 138K token 的构成（假设，未经分项实测）

138,051 / 2 请求 ≈ 69K/请求。按次轮增量约 15K（34,093 字符工具输出）反推，首请求约 61.5K。可对应的已实测项：

- system 层 13.7K
- 工具 18 个（CoreToolIds 15 ∪ 预加载 3）≈ 10.4K
- skills catalog（350 条，按 8% 预算上限可达 84K，实际约 11K）

三项相加约 35K，仍有约 26K 无法归因。**因此本条只作为待验假设，不作为结论。** 下一步应读 `ContextPipelineLayers` 的层快照（`layerInfos` 已带 `TokenCount`），而不是继续按预算百分比推算。

### 9.5 与 D3 的关系（结论修正）

D3 原写「工具集过载与探路开销」。实测表明：

1. **探路开销已被消除**——`b176c08` 预加载后，首轮工具序列为 `file_search`，无 `search_tools`。
2. **真正的浪费不在工具 schema，而在系统层与目录层**——它们与任务无关，却按 1.05M 上下文窗口的固定百分比注入。

### 9.6 本轮不写进结论的三条

## 十一、artifact 回读循环：根因与修复（2026-11-14 17:10）

### 11.1 现象

上一轮记录（`aebff2c`）里，一个「列出 `.csproj`」的只读任务跑到 **28 个请求 / 362 万 token 仍未收敛**。工具序列呈重复形态：`file_search` 一次拿到目录清单后，模型反复 `file_read` 同一个 artifact，每次结果尺寸都在 21 KB 上下。

### 11.2 根因：两个阈值互不相容

| 组件 | 阈值 | 位置 |
|---|---|---|
| `file_read` guardrail 预览窗口 | **400 行**（宽行文件上可达 40 KiB） | `FileTools.cs` 小文件与大文件两条路径 |
| `ToolResultContextPolicy` inline 上限 | **8 KiB** | `ToolResultContextPolicy.cs:34-35` |

400 行预览必然超过 8 KiB，于是每条 `file_read` 结果都走 `SpillAsync`：

1. `file_search` 返回 21 KB → spill 成 artifact A → 历史留 8 KiB 预览 + `full_output_file` 指针
2. 模型 `file_read(A)` → 返回 400 行 ≈ 20 KB → **再次 spill 成 artifact B** → 历史留 8 KiB 预览 + 新指针
3. 回到第 2 步，永远读不完

关键在 notice 文案：`use file_read with offset_lines/limit_lines to continue; do not use full_file=true.` 它只说了「用 offset/limit」，**没有给出可用的一次性范围**。模型最自然的反应是「那就再读一次」，于是每轮都产出一个新 artifact。

### 11.3 引入时点

`FileTools.cs` 的注释记着：

> 2026-08-22 模型倾向适配：窗口 120→400 行，减少同文件翻页重读

那次放大的目标是对的（120 行窗口实测同文件重读 8 次），但它**跨过了 8 KiB 线**。此后任何宽行文件都会触发二次 spill，而控制台里只表现为「token 消耗偏高」，不会报错。

### 11.4 修复

`FileReadTool.TakeLinesWithinByteBudget`：行数与字节预算取**更严格者**。

```
预算 = ToolResultContextPolicy.MaxInlineUtf8Bytes - 512   // 留给 [META] 头与 GUARDRAIL notice
```

- 小文件路径与大文件（流式）路径同时修正——只改一条会让两种文件尺寸表现不一致
- 单行即超预算时按 UTF-8 字节二分截断，不切断代理对，保证模型至少看到开头
- GUARDRAIL notice 改为报告**实际返回行数与字节**，并给出可直接照抄的 `OffsetLines=N+LimitLines`

后者是这次修复里容易被忽略的一半：只把输出压小、不改提示，模型仍然不知道该读多少。

### 11.5 三态证据

| 阶段 | 结果 |
|---|---|
| 修复前（新增测试） | 失败 2 / 通过 0 |
| 修复后 | **14 / 14 通过** |
| 变异：`InlineBudgetBytes` → `int.MaxValue` | 失败 2 / 通过 12（红的正是两条新测试） |
| 字节级复原（SHA 一致）后 | **14 / 14 通过** |

变异会保留 BOM 与行尾：脚本在字节数组上做等长替换，复原后 `Get-FileHash` 与原值逐一比对一致；随后 `dotnet build -t:Rebuild` 强制重编译（`Copy-Item` 保留 mtime，否则跑的还是变异版）。

### 11.6 未验证

本条修的是**机制**（输出不再超标 → 不会被二次 spill）。**端到端收益未实跑验证**：需要在真实子代理上重跑同类任务，确认请求数从 28 降到个位数。

在此之前只能说「循环的成因已被移除」，不能说「那个任务现在 3 轮就能做完」。

两处都已修：字段名改 `eventType`，`duration_ms` 优先读 `payload`、兼容根级旧格式；轮次计数从 `llm.completed` 改为 `round.completed`（与读取器同一定义，避免两处漂移），LLM 耗时仍用 `llm.started/completed` 配对差。

### 13.2 我之前那个「3 倍」是错的

我拿 `094403`（Claude，958K 总 token）比 `091947`（deepseek，311K），说「Claude 贵 3 倍」。

**总 token 把缓存命中的部分也按全价算进去了。** 缓存命中按折扣价计费（实测 deepseek 缓存价约为输入的 1/25，
gpt-5.6-sol 约 1/10），所以总 token 不是钱。

按唯一按全价计费的量——**未命中 token**——同一道题：

| 对照 | 未命中 | 比值 |
|---|---|---|
| Claude `094403` vs deepseek `091947` | 65,959 vs 54,657 | **1.21×** |
| Claude `072655_4ad5` vs gpt-6.1 `072655_5bbb` | 54,343 vs 308,169 | **5.67×** |

「Claude 比 deepseek 贵 3 倍」这个说法作废；真实差距是 1.21 倍。

### 13.3 GPT 那 5.67 倍也不是「模型更贵」

gpt-6.1 那次扫了 **5,089** 个文件，Claude 那次只扫 **1,301** 个（3.91×）。未命中 ≈ 工作量的函数：

- 单位覆盖成本：gpt `308,169 / 5,089 = 60.6` 未命中 token/文件；claude `54,343 / 1,301 = 41.8`
- 比值 1.45×，与 5.67× 差得很远

⇒ **它贵因为它做得多，且每文件仍贵 45%**。两个因素要分开说，不能笼统归成「模型贵」。

### 13.4 前缀瘦身不是省钱手段（这条改变优先级）

`094403` 的**第 1 轮**就是 `prompt_tokens=74,412 / cache_hit=61,317`——
**子代理第一次请求时，61.3K 的前缀已经命中缓存了**（与父代理/兄弟 run 共享前缀）。

推论：那 61K 的固定开销（系统层 + 工具 schema + skills catalog）**几乎全按缓存价计费**，
把它砍掉省下的钱是零头。瘦身的真实收益是**上下文窗口占用**，不是成本。

所以待办「prompt 瘦身」的定位要改：它解决的是「子代理一开始就吃掉 6 万窗口」，
不是「太贵」。**不该拿它当省钱项排优先级。**

### 13.5 一个必须记住的口径

- 跨模型比成本 → 只看 `cache_miss_tokens`（+ 各自单价）。
- 跨模型比效率 → 看「未命中 token / 单位工作量」，不是总量。
- 比上下文压力 → 才看 `prompt_tokens`。
- 三项混淆会让结论漂移一个数量级——我这次就漂了。

## 十五、`pool_action=logs`：主代理能看到子代理「在做什么」（2026-11-14 20:15）

### 15.2 实现

## 十六、子代理 cwd 继承（2026-11-14 20:50）

### 16.1 缺陷

`spawn_sub_agent` 不传 `working_directory` 时，子代理的工作目录回落到**工作区根**
（`D:\Data\workspaces\<ws>`），而仓库通常在 `D:\CodeProject\PuddingAgent\PuddingAgent`。

### 16.2 修法

```csharp
internal static string? ResolveWorkingDirectory(string? explicitValue, string? parentValue) =>

```

抽成纯函数是为了**能直接断言这条规则**，而不是靠跑一次真子代理去观察。
两边都空时保持 null，不凭空造值——保持与旧行为一致的那一半。

## 十七、`logs` 带延迟分解：把聚合逻辑收敛到一处（2026-11-14 21:25）

### 4. 可做与不可做

**不可做**：改自己的 prompt 结构去「修」它——前缀已经是 1 个 hash，没有可简化的抖动。
**不可做**：对零命中请求立即重试——只会把成本翻倍，且第二次很可能同样落空。


196 条远未到 500，却报「撞了 500 上限」。声明在成因与药方上都说错了。

同一缺陷在小结果集上同样复现，说明它与结果数量无关：


顺带证实 `ls -a` 通道：不加 `include_noise_dirs` 时二进制副本被丢弃且首行声明 `(noise: dropped 2 ...)`；加上后两条 `bin\Debug\...\TextTools.csproj` 原样返回。

### 26.2 成因

`MergeWithBaselineAsync`（Everything 清单不可自证完整时的差分补足）把两种成因合并成一条：

```csharp
if (baseline.Coverage.Status == Truncated || mergedPaths.Count > maxResults)
    return (mergedPaths.Take(maxResults), Truncated($"... result limit {maxResults}"));
```

`BuiltInRecursiveFileSearchProvider` 同时受 `maxResults`（结果数）与 `_maxEntries`（**遍历条目数**，含目录与非匹配文件）约束。`Source` 树含大量 bin/obj 条目，遍历先撞条目上限 → Truncated → 上层把原因写成「result limit 500」。

两种情况的差异是实质性的：

| 成因 | 状态 | 有效药方 |
|---|---|---|
| 结果集满额 | truncated | 调大 `max_results` |
| 遍历条目撞预算 | partial（无法证实完整） | 缩小 `directory` / `pattern`；调 `max_results` **无效** |

### 26.3 修复

拆分两支，并让新文案显式否定错药方：

```
(coverage: partial — differential enumeration stopped early; the result set did not fill
 (narrowing the directory scope helps, raising max_results does not)
 — builtin enumeration reached 2000 entries; narrow directory scope; ...)
```

| 路径本身是否噪声目录 | 目录路径 | 目录名，**要判** | `IsNoiseDirectory`（新增） |

### 28.3 方法教训：字面量不跨程序集

第一次在 `PuddingRuntime.dll` 里搜 `agent:parent`，两种编码都是 0。差一步就会误报「没上线」。

真实原因是 .NET 的两个堆：

| 内容 | 元数据堆 | 编码 | 可见范围 |
|---|---|---|---|
| 类型名 / 成员名 | `#Strings` | UTF-8 | 被引用即出现在**引用方**程序集 |
| 字符串字面量 | `#US` | UTF-16LE | **只在字面量被编译进去的那个程序集里** |

`SubAgentAddressResolver` 定义在 `PuddingCore`，`PuddingRuntime` 只引用它 ⇒
类型名出现（utf8=1），但它函数体里的 `"agent:parent"` 不会跟着过来。
扫遍部署目录全部 `Pudding*.dll`，只有 `PuddingCore.dll` 命中（utf16=3），
与该解释完全一致。

推论（可直接复用）：**验证「某常量/文案是否上线」必须去定义它的程序集**；
验证「类型/方法是否被引用」才该看调用方。

附带一条实现细节：字节级子串计数改用 `Encoding.GetEncoding(28591)`（ISO-8859-1，1:1
字节映射）把整个 DLL 解成字符串再 `IndexOf` 比逐字节双循环快几个数量级；
PowerShell 5.1 没有 `Encoding::Latin1`，28591 是等价替代。

## 二十九、子代理回信额度：把「该不该说」和「真的说了」拆开（2026-11-15 13:55）

自动进度汇报已有节流，但模型仍可每轮主动调 `send_message(to: agent:parent)`。
代价落在**父代理的上下文窗口**上，不出现在子代理自己的账单里，所以需要硬上限。

### 29.1 为什么用时间而不是轮次

`SubAgentProgressReportPolicy` 的输入是轮次：`AgentExecutionService.Buffered.cs:542`
在循环外初始化游标，1678 / 1756 两处跨轮推进，那一层拿得到 round。

但 `send_message` 走工具调用路径，`ToolExecutionContext` 没有轮次字段——
时间才是这条路上可靠可得的信息。两层分工不同，不能互相替代。

### 29.2 设计与取舍

| 决策 | 理由 |
|---|---|
| `TryAcquire` 纯判定、`Commit` 才推进 | 传输失败时白扣额度，日志会出现「没收到却说超额」 |
| 被拒的调用不扣额度 | 否则「试一下」这个动作本身就会把额度磨光 |
| `maxMessages < 1` 钳到 1 | 配成 0 若退化成「永远发不出」，子代理连结论都报不回来 |
| 负数 elapsed 钳到 0 | `minInterval > 0` 时结果不变（仍判 TooSoon）；`minInterval = 0` 时不会被一次系统校时变成永久拒绝 |
| 默认 8 条 / 20 秒 | 一次 run 的合理量级，不是精确科学值 |

最后一行的注释我改过一次。初版写的是「按 0 处理是最保守的一支：宁可拦一次」，
而钳到 0 的实际效果在 `minInterval = 0` 时是**放行**——注释与实现相反，已按真实语义重写。
这类「注释描述了一支并不存在的保守策略」比写错数字更难发现，因为它读起来很合理。

## 三十、子代理回信额度已接入 `send_message`：判定在发出前，提交在送达后（2026-11-15 16:20）

### 30.1 接入点与顺序

`SendMessageTool.ExecuteCoreAsync` 的三步顺序是刻意排的：

| 步骤 | 位置 | 理由 |
|---|---|---|
| 解析 `agent:parent` | 最先 | 父地址缺失要如实失败，不能进入发送 |
| 判定额度 | 解析成功之后、`SendAsync` 之前 | 超额时消息**不能**出网 |
| 提交额度 | `SendAsync` 返回之后 | 传输失败不该白扣一条 |

顺序颠倒的两种后果都不报错：先提交再发送会得到「没收到却说超额」的日志；先发送再判定则是根本没拦住。

### 30.2 两个方向都不能反

- **缺 `RunId` → 拒绝**。所有子代理会共用一份额度，等于把按 run 记账静默换成全局记账。

## 三十二、确证一个假阳性：`Truncated` 表示「停在上限」，不表示「确认还有更多」（2026-11-15 17:35）

默认 `list_dir` 对 `Source` 的实测是 100 条、`Truncated=true`、15,905 字符。顺着这个结果读代码，发现 `Truncated` 的语义有问题。

### 32.1 缺陷

`FileTools.cs` 的 `Walk` 在两处置位，两处都**没有检查是否真的还有匹配条目**：

- 进入函数时：`if (entries.Count >= maxEntries) { truncated = true; return; }`
- 添加条目后：`if (entries.Count >= maxEntries) { truncated = true; return; }`

⇒ 一个**恰好**有 `max_entries` 条目的目录，也会报 `Truncated=true`，尽管一条都没被丢掉。这是假阳性，与前几天修过的「声明成因必须与药方对应」是同一族：标志声称「还有更多」，而事实可能是「刚好够」。

影响有限且能自愈：模型看到 `Truncated=true` 会把 `max_entries` 调大再列一次，第二次若总数小于新上限，`Truncated` 自然变 false。代价是**一次多余调用**，不是错误结论。

### 32.2 为什么本轮只改描述，不改语义

要精确回答「还有没有更多」，在 `recursive=true` 下必须继续扫描剩余子树——那往往就等于全量枚举，而 cap 存在的目的恰恰是避免这个成本。可行的折中是「只探测当前目录的剩余兄弟」：非递归下精确、递归下仍是保守值——**同一个字段在两种模式下含义不同**，比保守值更糟。

所以本轮改的是**让调用方知道该字段怎么读**：`list_dir` 的描述里写明「达到 max_entries 时 Count 等于该上限且 Truncated 置 true——这只表示停在了上限，不代表已确认还有更多条目；要确认是否真被截断，把 max_entries 调大再列一次。」


局部 `noMatch` 是 false（所以没有输出「No files matched」引导文案），但 `BuildResultStatus` 只看 `resultCount == 0`，于是 `status` 仍然是 `no_match`。

输出于是自相矛盾：**首行声明 `(noise: dropped 1 …)`，结构化状态却说「已验证无匹配」。** 对模型而言，「no_match」的信号强度高于一行提示文字，它会据此断定磁盘上没有这个文件。

这条正是当天早些时候修过的镜像问题（那次是状态 `no_match` 与「文案说被排除」不一致的另一半）。

### 35.2 修复：把「已验证」的判定权还给唯一真源

`BuildResultStatus` 增加 `verifiedNoMatch` 参数，由调用方把已经算好的 `noMatch` 传进来，不再用 `resultCount == 0` 反推：

```csharp
private static string BuildResultStatus(RetrievalCoverage coverage, int resultCount, bool verifiedNoMatch) =>
    !coverage.IsComplete ? ToolResultStatuses.Truncated
    : resultCount == 0
        ? (verifiedNoMatch ? ToolResultStatuses.NoMatch : ToolResultStatuses.Ok)
        : ToolResultStatuses.Ok;
```

两处调用（主路径与 provider 降级路径）都传各自的 `noMatch`。

**为什么不新增一个 status 值**：`no_match` / `ok` / `truncated` 是既有契约，新增取值会波及所有消费方；而这里的语义就是「这次查询按默认口径没返回东西，但原因写在首行」——`ok` + 披露行已经自洽。

### 35.3 三态证据

新增 `All_Matches_Dropped_By_Noise_Filter_Is_Not_A_Verified_NoMatch`：临时目录下只放 `bin/noisy.txt`，清单声明完整，默认参数搜索。

| 阶段 | 结果 |
|---|---|
| 绿 | FileSearch 套件 **51 通过 / 0 失败 / 1 跳过** |
| 变异（`verifiedNoMatch` 写死 `true`） | **50 / 1 失败**，红的正是新用例：`actual: "no_match"` vs `expected: "ok"` |
| 复原（SHA `EA036B8B…` 逐字节一致）+ 重建测试工程 | **51 / 0 / 1** |
| 合并 gate（FileSearch + SearchGrep + ListDirectory） | **133 通过 / 0 失败 / 1 跳过** |

变异值与真实值可区分：变异下是 `no_match`，正解是 `ok`。

### 35.4 方法结论

**同一个事实不能有两处独立推导。** 这里「是否已验证无匹配」被算了两次：一次给文案用（`noMatch`），一次给状态用（`resultCount == 0`）。两处一旦走岔，输出就自相矛盾，而两边都没有报错。

修法的要点不是「再补一个条件」，而是**让判定只剩一处，然后把结果传下去**。任何出现「同一个布尔在两条路径分别推导」的地方，都该按这个形状收敛。
