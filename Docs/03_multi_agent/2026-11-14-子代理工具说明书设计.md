# 子代理工具说明书设计

## 一、用户诉求

子代理单次运行注入 42 个工具的完整 schema，首轮估算上下文 5.4 万 token。诉求是：

1. 不必全部加载；
2. 在子代理提示词里附一份「环境说明书」——**只列工具名**，最常用的几个各给一句话用途；
3. 字数越小越好；
4. 清单应由代码扫描工具注册获得，不是手写常量。

## 二、已证实：机制已经存在

**有工具管理 Service。** `IToolRegistry`（`PuddingCore/Abstractions/IToolRegistry.cs`）提供 `Register` / `GetTool(name)` / `GetAllTools()`，实现是 `ToolRegistry`。

**延迟加载机制也已完整实现**，在 `ToolExposurePlanner`（`PuddingRuntime/Services/Tools/ToolExposurePlanner.cs`）：

| 组成 | 位置 | 值 |
|---|---|---|
| 激活阈值 | `:27` `DeferredLoadingThreshold` | **24** |
| 核心工具（永不收缩） | `:60` `CoreToolIds` | **15 个**：search_tools, plugin_*, goal_read/update, send_message, receive_messages, agent_status, agent_diagnostics, spawn_sub_agent, query_sub_agents, list_llm_providers, sleep |
| 能力包（加载其一即整包激活） | `:294` `CapabilityBundleMembers` | **5 组**：read(3) / edit(2) / code(2) / terminal(6) / git(3) |
| 恢复路径 | `:26` `SearchToolId` | `search_tools` |

判定逻辑（`:135`）：

```
工具总数 ≤ 24                         → 全部可见，deferred 关闭
或 工具集里没有 search_tools          → 全部可见，deferred 关闭（防止工具永久不可达）
否则                                  → visible = 核心 ∪ 已激活，deferred 开启
```

**我自己的会话就是 deferred 开着的样子**：5 个 available + 5 个 deferred（只列 id 不加载 schema）。子代理那次没有，说明它走的是前两个分支之一。

## 三、未证实：42 个如何产生

`CoreToolIds` 15 + 能力包全展开 16 = 31，仍不足 42。剩余来源有两个候选，**均未取证**：

- `request.ToolDefinitions`（子代理模板直接下发的工具定义）本身就接近 42；
- `activated` 通过 `previousVisibleToolIds` / `committedToolIds` 被撑大。

取证受阻：`[AgentExec:Tools] Prepared LLM tools` 是 `LogDebug`，默认级别不落盘；`[DirectLlm:Tools]` 也未在近 3 小时日志中出现。**要把这条钉死，需要一次带 Debug 级别的实跑**，代价是要重启宿主。因此本文不把 42 的分项当作结论。

## 四、方案：prompt 里加清单，不动 schema

关键判断：**不需要新机制，只需要在 system prompt 末尾追加一段紧凑清单**。

`AgentExecutionService.Buffered.cs:166` 附近已同时持有两个东西：
- `frozenTools.AllLlmTools` —— 本次可用的全量工具（含名字与描述）
- `frozenTools.VisibleTools` —— 实际下发 schema 的可见集

所以清单可以**从全量里减掉可见集**动态生成，不需要手写常量，也不需要新 Service：

```
## 其他可用工具（未加载 schema）
下列工具可用但未展开。需要时先 search_tools(工具名) 加载，再调用。
search_grep 搜内容 · file_read 读文件 · file_search 找文件 · shell 跑命令
其余：file_write, file_patch, git_diff, git_log, terminal_start, terminal_wait,
      code_explore, code_symbol_search, agent_status, ...
```

设计要点：

1. **名字从数据来**：列表由 `AllLlmTools - VisibleTools` 的 `Name` 生成，工具增删自动跟随，不会腐化。
2. **一句话用途只给前 4 个**：固定选读/搜/写/跑这类高频项；其余只列名字。用户要求「最常用的一句话」，这里刻意限死条数——每多一句就多一份 prompt，而它们大多用不到。
3. **不写参数**：参数在 `search_tools` 加载后才需要，写进 prompt 等于把 schema 换个地方存。
4. **前缀稳定**：这段文本按工具名排序生成，保证同一会话内逐字节一致，不破坏 prompt caching——GPT 的缓存已经吃过一次亏（前两轮零命中）。
5. **只在 deferred 开启时注入**：`DeferredLoadingEnabled == false` 时全量已下发，再加清单是纯浪费。

预估成本：15 个工具名 + 4 句用途 ≈ **80~120 token**，换掉的是「模型不知道有什么、只能先调 search_tools 探路」那一整轮（Claude 实测首轮就是这么花掉的）。

## 五、验收标准

| # | 判据 | 取红方式 |
|---|---|---|
| T1 | 清单里列出的名字 = `AllLlmTools - VisibleTools` | 把生成逻辑改成读 `VisibleTools`，断言应失败 |
| T2 | 同一会话两次生成逐字节相同 | 打乱输入顺序，断言应失败 |
| T3 | `DeferredLoadingEnabled == false` 时不注入 | 强制注入，断言应失败 |
| T4 | 清单长度上限 | 工具数扩到 100 时，断言清单仍 ≤ 设定字节上限 |
| T5 | 端到端：子代理首轮不再调 `search_tools` 探路 | 用 Claude 跑同一任务，对比首轮工具调用 |

T5 是唯一真正说明问题解决的判据，前四条只是防退化。

## 六、与「42 个全暴露」的关系

需要说清楚：本方案解决的是**「模型不知道有什么」**，不解决**「42 个 schema 全下发」**。

若 42 确实全部进了 schema，那首要问题是曝光规划没生效（§三未证实项），清单只是缓解。两者要分开验证：

- 先确认那次运行的 `DeferredLoadingEnabled` 与 `VisibleToolCount`（需要 Debug 日志实跑）；
- 若 deferred 未开启 → 修规划（真正的 token 大头）；
- 若已开启但清单缺失 → 本方案（省一轮探路）。

顺序不能反——否则会拿一条 100 token 的补丁去掩盖 5 万 token 的问题。
