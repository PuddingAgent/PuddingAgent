# 池条目 POST 的前置约束：归属会话是硬边界

## 1. 为什么要写这篇

面板现在能对每个成员：看角色/模型/模板/任务数/最近使用/最近成功/创建时间、改角色/模型/备注、休眠、销毁、看运行历史、看花费。

唯独不能「新建成员」。原计划：先补服务层「只建池条目、不建 run」的方法，再接 `POST /api/admin/sub-agent-pool`。

本轮核源码后结论变了：**形状上可行，但语义上缺一个必须由人裁定的输入**。这不是待写代码，是先要决定的事。

## 2. API 形状确实可行

`SubAgentPool.CreateAsync(name, request, ct)` 实际只消费 `SubAgentSpawnRequest` 的 8 个字段：

| 字段 | 用途 |
|---|---|
| `ParentSessionId` | 生成 `SubSessionId` + 写 `OwnerSessionId` |
| `WorkspaceId` | 写 `OwnerWorkspaceId` |
| `TemplateId` | 落库 |
| `RoleInPlan` | 落库（面板「改角色」可后补） |
| `ParentAgentId` | 落库 |
| `LlmProfile.ProviderId/ModelId` | 拼 `model_id`（面板「改模型」可后补） |
| `Responsibility` / `AvatarKey` | 落库（面板「改备注」可后补） |

它**不消费** `LlmConfig`、`TaskDescription`、`ParentContextSnapshot` —— 这些正是当初 POST 被判定「Web 层拿不到」的那几个必填快照。

所以「只建条目」的方法只需要 name + 一份不含 LLM 快照的 spec。形状上没有障碍。

## 3. 归属才是硬边界

四条代码事实连起来看：

1. `SubAgentPool.cs:516` —— `ownerSessionId: request.ParentSessionId`，归属即创建时的父会话。
2. `AgentPoolEntryStore.cs:113` —— 抢占的 `WHERE "owner_session_id" = {ownerSessionId}` 写在 SQL 里。SQL 三值逻辑下 **NULL 不等于任何值**，所以无主行永远抢不到。
3. `SubAgentPool.cs:712` —— 但 `AcquireInStoreAsync` 在 `OwnerSessionId` 为空时**直接跳过**库操作并 return。于是内存置 Busy，库里仍是 `idle`。
4. `AgentPoolEntryStore.cs:151` —— 收尾要求 `status='busy' AND active_execution_id=@exec`。库里的行从没进过 busy，收尾必然 0 行。

合起来的后果：**无主条目一旦建出来，数据库与内存就永久分叉**——内存显示跑过 N 次、`TaskCount=N`，库里 `task_count` 永远是 0、状态永远 `idle`。这恰好是本池「单一真源在 DB」设计的反面。

`SubAgentPool.cs:785/796` 的 `PoolOwnershipMismatchException` 进一步说明归属是**主动设的闸**：非创建者父会话不能驱动该条目。

## 4. 现状数据（2026-11-25 07:50 实测）

`agent_pool` 活跃 5 行，`owner_session_id IS NULL OR ''` 计数 **0**：

```
'frontend-ui'  sleeping  owner=3f52368a35ef  ws=default  hasModel=0 hasRole=1
'advisor'      idle      owner=3f52368a35ef  ws=default  hasModel=0 hasRole=0
'scout'        sleeping  owner=3f52368a35ef  ws=default  hasModel=0 hasRole=0
'reviewer'     idle      owner=3f52368a35ef  ws=default  hasModel=0 hasRole=0
'probe-model'  sleeping  owner=3f52368a35ef  ws=default  hasModel=1 hasRole=1
```

`3f52368a35ef…` 就是当前这个会话。也就是说：**池是会话作用域的**，不是工作区共享资源。换一个会话，这五个成员全部不可驱动（会先撞归属异常）。

这一点解释了为什么面板上没有「新建」是可以接受的：新成员本来就只能由**将要使用它的那个会话**创建。

## 5. 为什么管理面板补不出这个输入

面板是跨会话的管理视图，它没有「父会话」可归属。若 POST 要求调用方传 `ownerSessionId`，实质是「替未来某个会话预建一个只有它能驱动的条目」——而面板并不知道哪个会话会回来用它。

三个选项：

| 选项 | 做法 | 代价 |
|---|---|---|
| A 由调用方指定 owner | POST body 带 `ownerSessionId` | 语义怪：管理面替别的会话做决定；选错即永久不可用 |
| B 改成工作区作用域 | 去掉 session 归属校验，只管 `workspace_id` | 削弱 D-P0-1 已刻意设的闸（跨会话误驱动） |
| C 不做 POST | 建条目回到对话内 `spawn_sub_agent(pool_name=…)` | 面板功能上留一个缺口，但语义零风险 |

**推荐 C**，理由：`spawn_sub_agent(pool_name=…)` 走的正是 `CreateAsync`——它**只预留、不执行**（源码注释明确写了 create → execute 会重叠启动同一 SubSessionId 的风险，所以刻意拆开）。也就是说「只建条目」的路径今天已经存在，只是入口在对话里而不在面板上。

A 和 B 都不是编码能解决的：A 要定「谁的会话」，B 要放弃一条刻意设的防护。

## 6. 若将来仍要做 POST，先补一件小事

`PooledSubAgent` 快照（`ISubAgentPool.cs:17-27`）不含 `OwnerSessionId`，所以面板今天**无法显示归属**。在归属不可见的前提下让用户新建成员，用户没有判断依据。

顺序应当是：先让归属可见（快照 + DTO + 面板）→ 再看 A 是否可接受。

## 7. 证据边界

- 上述四条代码事实来自读源码（行号为当前 HEAD `d9510b0`），未做运行时注入验证。
- 「无主条目会分叉」是**由代码推出的**结论，没有在生产里造出无主条目来实测——因为造它需要绕过写路径，恰好是本文要避免的事。
- 现状 `owner_null=0` 是时点快照，不是历史断言。
