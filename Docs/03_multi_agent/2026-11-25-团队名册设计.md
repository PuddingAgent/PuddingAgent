# 团队名册设计（里程碑 2）

## 0. 目标与非目标

**目标**：让「团队」成为一个可以有两个以上授权会话共同使用的持久资源 —— 成员有稳定身份、跨重启仍在名册里，面板可以建员，多个会话可以委派任务并各自拿回结果。

**非目标**：本轮不写代码；不改变里程碑 1 已交付的「个人成员归创建会话」语义。

## 1. 四条已核实的硬约束

设计必须服从现状，所以先列我逐条读过源码的事实。这些不是我的假设，任何一条被忽略都会让方案在第 3 步崩掉。

| # | 约束 | 证据 | 后果 |
|---|---|---|---|
| C1 | `agent_pool.name` **全局唯一**（`WHERE deleted_at IS NULL`） | 现场 schema：`CREATE UNIQUE INDEX "IX_agent_pool_name" ON "agent_pool" ("name") WHERE "deleted_at" IS NULL` | 「两个团队各有一个 `reviewer`」今天不可能。要改造唯一索引，属迁移（但见 C5：不能在步 1 做） |
| C2 | 子会话的**父会话归属不可变** | `SessionStateManager.cs` 的 UPSERT：`ON CONFLICT("sub_session_id") DO UPDATE … WHERE "parent_session_id" = excluded."parent_session_id"`，`affected != 1` 直接抛「already owned by a different parent session」 | 会话 B **不能**直接驱动归属 A 的成员。跨会话委派只能由 A 作为真正的派发者，B 拿的是结果回执 |
| C3 | 抢占谓词要求 **owner_session_id 与 owner_workspace_id 同时相等** | `AgentPoolEntryStore.cs`：`WHERE pool_id=… AND owner_session_id=… AND owner_workspace_id=… AND status IN (idle,sleeping)` | 团队成员的 owner 必须解析成一个**真实存活的会话 id**，不能是「团队」这种虚拟主体 |
| C4 | `TeamMemberEntity` 是**用户账号**表（FK → `AppUserEntity`） | `TeamMemberEntity.cs`：`TeamEntityId` + `UserEntityId` + `Role` | Agent 名册必须独立建模，不能复用这张表 —— 它的语义是「人在哪个团队」 |
| C5 | 池的**进程内身份就是名字** | `SubAgentPool.cs:161` `ConcurrentDictionary<string, PoolEntry> _pool`（`StringComparer.Ordinal`）；`:568` `_pool.ContainsKey(name)` 直接拒重复；`:617`/`:1172` 均以 name 为键写入 | 放宽 DB 唯一索引**会直接破坏进程内不变量**：两个同名条目在内存里建不出来或互相覆盖。所以“索引迁移”不是第一步，是最后一步 |

补充两条来自同一批核对：

- `SubAgentPoolAdminController` 只有 `GET` / `GET capacity` / `DELETE {name}` / `POST {name}/sleep` / `PATCH {name}` / `GET {name}/runs`，**没有建员 POST**。
- PATCH 白名单是 `role` / `model_id` / `responsibility` / `avatar_key`，**不含 `template_id`**。

## 2. 方案

**一句话**：团队 = 工作区里的一个持久协调会话 + 一张名册；名册成员的 owner 是那个协调会话。

```
workspace
 └── team (持久记录)  ──coordinator_session_id──> 普通会话（持久，不当对话用）
      └── agent_team_member (team_id, pool_id)  ──> agent_pool 行（owner_session_id = 协调会话）
```

- 个人成员：不变，`owner_session_id` = 创建它的对话会话。
- 团队成员：`owner_session_id` = 团队的协调会话 id。于是 C3 的抢占谓词天然成立，C2 的归属校验也天然成立（协调会话是唯一父会话）。

### 2.1 数据模型

1. `agent_team`：`Id` / `team_id`(文本稳定 id) / `workspace_id` / `name` / `coordinator_session_id` / `created_at` / `deleted_at`。
2. `agent_team_member`：`team_id` / `pool_id` / `role_in_team` / `created_at` / `deleted_at`。成员身份用 `pool_id` 指向 `agent_pool`，不复制字段（复制就会出现两份真源）。
3. `agent_delegation`（里程碑 3 才用）：`delegation_id` / `team_id` / `pool_id` / `initiator_session_id` / `initiator_agent_id` / `status` / `result_summary` / `created_at` / `completed_at`。委托幂等键放这里。

### 2.2 名字唯一性（C1 的迁移）

目标：名字只需在**所属范围内**唯一。

- 新唯一索引：`(owner_workspace_id, owner_session_id, name) WHERE deleted_at IS NULL`；
- 存量 5 行全部是同一个 owner 会话，迁移不冲突；迁移前后用「行数 + 名字集合」双计数对比，不一致即回滚；
- 迁移必须先备份库文件，再在同一次部署里验证 `SELECT count(*) FROM agent_pool WHERE deleted_at IS NULL` 不变。

### 2.3 谁能向团队委托

新增 `agent_team_delegate`（`team_id` / `session_id` / `granted_by` / `created_at` / `revoked_at`），或先以「团队成员所在工作区 + 显式授权列表」二者取交。判据写在服务层，一次判定给出**四种结果**而不是布尔：不在团队 / 在团队但未授权 / 已授权 / 授权已撤销 —— 只有把「未授权」和「已撤销」分开，界面才能给出可行动的提示。

### 2.4 结果回传给谁

结果回到 `agent_delegation.initiator_session_id`，而不是团队或协调会话。理由：协调会话只是执行者，问问题的人是发起委托的那个会话；回给团队等于把结果投进一个没人等的信箱。

### 2.5 容量口径必须分离（用户已指出）

现在的 `capacity` 是全局活跃行数检查（`AgentPoolEntryStore`：`live >= capacity` 就拒绝）。团队化后要分两个数：

- **名册容量**：一个团队最多多少成员（长期存在，允许远超并发数）；
- **并发执行上限**：同一团队同时多少个成员在跑。

两者用一个数字会让「名册满」和「忙」混淆，界面上无法给出正确动作。

## 3. 分步实施与验收

**顺序修正（2026-11-25 14:30）：初版把“索引迁移 + 建表”列为步 1，这是错的。**
C5 说明寻址键先于唯一性：先在 DB 放宽唯一索引，内存与工具层仍在按名字寻址，
两个会话的同名成员会立刻变成“谁先到谁占住”的竞态。所以正确的第一步是**换寻址键**。

| 步 | 做什么 | 验收条件 |
|---|---|---|
| 1 | 寻址键换成稳定成员 id（`pool_id`）：内存字典、工具层解析、`Sleep`/`Destroy` 参数、admin 路由 `{name}` 全部能接受 pool_id；name 降级为「所属范围内唯一」的展示名 | 同一工作区两个会话各自有 `reviewer` 时，两边派活、休眠、销毁互不影响；仅凭名字的调用在跨范围重名时**明确报歧义**而不是随便选一个 |
| 2 | 复合唯一索引迁移（`(owner_workspace_id, owner_session_id, name)`）+ `agent_team` / `agent_team_member` 建表 | 两个团队各有 `reviewer` 可共存；迁移前后活跃行数与名字集合一致 |
| 3 | 建员 POST：面板选团队 → 服务端解析 owner = 协调会话 | 未选团队时明确报错而不是落成无主条目；重复请求只生成一条 |
| 4 | 委托授权 + `agent_delegation` + 结果回传 | 两个授权会话向同一团队派活，各收各的结果；重复提交同一委托只产生一项 |
| 5 | 跨重启恢复 | 重启后名册、子会话、已完成节点均可查回 |

## 4. 待裁定与未验证

- **寻址迁移的兼容窗口**：步 1 会让“只传名字”的调用从“总能成功”变成“重名时歧义”。是永远保留按名寻址（仅当名字在调用方范围内唯一），还是给一个弃用期？未定。
- **协调会话由谁创建、什么时候创建**：建团队时懒创建，还是团队首次被委派时创建？未定。
- **协调会话是否可被用户打开对话**：建议禁止（它是执行凭据，不是聊天窗口）。
- **`template_id` 是否进 PATCH 白名单**：现在只能建时定。若允许改，必须同时同步内存快照，否则又是一次「面板改了不生效」。
- **未验证**：C2 的结论来自 `SessionStateManager` 的 SQL 谓词，未做故障注入实验；若里程碑 3 依赖它，应先写一个隔离实验确认「跨会话 spawn 会被拒」。
