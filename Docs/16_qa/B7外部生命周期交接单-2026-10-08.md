# B7 外部生命周期验收交接单（2026-10-08）

面向**进程外控制器**。每一步都写明：**操作 → 判据 → 证据**。

## 0. 前置（必须满足）

| 项 | 要求 |
|---|---|
| 构建 | 用**明确的新构建**（`--artifacts-path temp/build/recovery`，先 restore/build，再同目录 `--no-restore`） |
| 隔离 | 使用**隔离的 DesktopHome / DataRoot / 端口**（见 `TestScripts/test-pudding-desktop-launcher.ps1`） |
| 前提 | Desktop 可发布（`temp/build/desktop-preview`）、`D:\data` **不被 dev-up 占用**（两者不共享 PID/端口所有权） |

## 1. `startup`

- **操作**：在隔离环境启动 `PuddingDesktop.exe`；
- **判据**：① Shell 出现且 WebView2 就绪；② **Core 子进程**由 Desktop 启动并监督（`core/PuddingAgent.exe --desktop-child`）；③ **不装配进程内 `PuddingHost`**；④ 若 Core 启动失败/配置缺失/DataRoot 未设置，**Desktop 仍可启动**并允许进入设置修复；
- **证据**：进程树（Desktop → Core）、`<DataRoot>/config/system.json` 读取成功、日志中无"进程内 Host"痕迹。

## 2. `restart`

- **操作**：重启 Desktop（或在运行中心执行停止→启动）；
- **判据**：① Core 子进程**被替换**（新 PID）；② 旧 Core 已退出（无孤儿）；③ 端口/锁（`.pudding-host.lock` 文件句柄租约）**未被绕过或删除**；
- **证据**：PID 变化对照、锁文件句柄仍由存活进程持有。

## 3. `crash-recovery`

- **操作**：**强杀 Core 子进程**（模拟崩溃）；
- **判据**：① Desktop **不退出**（单实例产品进程仍在）；② 按配置的自动恢复策略重启 Core；③ 失败时可从设置/运行中心**手动修复**；
- **证据**：Desktop 存活、Core 新 PID、恢复日志。

## 4. `exit-reclamation`

- **操作**：触发「退出 Pudding」（或配置 `ExitAndStopCore`）；
- **判据**：① **Core 被停止**；② **WebView2 被释放**；③ 无残留进程/句柄；④ 与"关闭按钮默认隐藏到托盘"的行为区分（后者**不**停 Core）；
- **证据**：退出后进程列表为空（Desktop/Core）、文件句柄释放。

## 5. 20× 整链 flake 门禁

- **操作**：`TestScripts/delivery-manifest.ps1 -BuildId <id>` 连跑 **20 次**（链式，失败即停并留证据）；
- **判据**：20 次**全部**产出 `ready-for-external-deploy`，且**同一 build**下通过数一致；
- **证据**：每次的 `temp/test-out/delivery-manifest.json` 与日志（**不要**只留最后一次）。

## 6. 250ms 校准

- **判据**：按设计规定的 250ms 时间预算校准项**逐项实测**（不是估算），并记录实测值与偏差；
- **证据**：校准记录表（原始值与结论）。

## 6c. Bridge 路由截图：**有意暂缓**（decided deferral）

- **现状**：Bridge 路由下截图返回**明确的 `UnsupportedCapability`**（"use the capability channel"）⇒ **fail-closed**，不会静默失败。
- **已提交的前置**：`page.screenshot` 命令名（含 `All` 冻结集合）与 Bridge 载荷类型（`PageScreenshotArguments`/`BrowserScreenshotDescriptor`/Chunk，Base64）。

### 6c-补（2026-10-08，后续会话）：暂缓理由**收紧为可核实的事实**

复核后修正 6c 的措辞 —— 原写"合成调用上下文等于**复制身份/准入语义**"，**不够精确**：

| 已核实 | 事实 |
|---|---|
| 准入**逻辑**已有单一真源 | `Source/Pudding.DesktopService/BrowserAdmissionAdapter.cs`：`Admit(...)`/`Revalidate(...)` → `BrowserAdmissionOutcome`（由 `BrowserPageLifecycle.Authority` 驱动） |
| 依赖方向**允许** | `PuddingDesktop.WpfArchive.csproj` **已引用** `Pudding.DesktopService` ⇒ 桥侧**可直接复用同一适配器** |
| 通道侧接线 | `DesktopCapabilityChannelComposition.cs:128` 把 `connectionGeneration` 喂给准入（`ValidateAdmission` 的闸门） |

⇒ **真正缺的不是准入逻辑，而是"Bridge 命令的**可信身份投影**"**：能力通道的身份由 **Core 侧接缝**校验后传入；Bridge 命令目前**没有等价的受信身份来源**。若无该来源就调用 `BrowserAdmissionAdapter`，等于**让 Bridge 自行断言身份** —— 那才是真正的"复制判据"。

**⇒ 暂缓结论不变，但解除条件更具体**：为 Bridge 命令提供**与能力通道同源的可信身份**（例如 Core 侧对 Bridge 命令做同样的身份投影/签名校验），即可**复用既有适配器**闭合缺口，**无需新写准入逻辑**。这也把该缺口的**评估成本大幅降低**（不是"要造第二套准入"，而是"要补一条身份投影"）。
### 6c-补二（2026-10-08，后续会话）：Bridge 截图的**具体改动清单**（读实后的结论）

已核实的两个形状：

| 处 | 形状 |
|---|---|
| `BrowserAdmissionAdapter.Admit(...)` | 入参：**`BrowserCallerIdentity caller`** · `BrowserAutomationOperation operation` · `OperationId` · **`ConnectionGeneration`** · `DesktopPageTarget? target` · `string? frameId`（另有 `Revalidate(lease, …)` 供执行前复检） |
| `BrowserBridgeCommandOrigin`（**Bridge 命令已携带**） | `WorkspaceId` · `AgentInstanceId` · `SessionId` · `ConversationId?` · `RunId?` · `ToolCallId?` · `ToolName` —— **即调用者身份** |

⇒ **改动清单（若决定闭合该缺口）**：

1. **映射**：`BrowserBridgeCommandOrigin` → `BrowserCallerIdentity`（纯映射，**不新造字段**）；
2. **代际**：为 Bridge 传输提供 `ConnectionGeneration` 的**明确语义**（Bridge 的"连接代际"如何取值/如何换代）——**这是唯一的待定项**；
3. **准入**：桌面桥的 `HandlePageScreenshotAsync` 在采集前调用**同一个** `BrowserAdmissionAdapter.Admit(...)`（写操作在入队前、执行前再 `Revalidate`），**不新写准入逻辑**；
4. **桥侧转发**：`BridgeBrowserCapabilitySurface.ScreenshotAsync` 从"明确不支持"改为**发命令 + 解结果**（照其 `SnapshotAsync` 转发写法）；
5. **用例**：Bridge 往返（形状/失败）+ 准入拒绝路径。

**唯一待定（必须先回答，不能猜）**：**Bridge 命令的 `Origin` 是否由可信方（Core 侧）建立并受认证连接保护**？`AGENTS.md` 写明 Bridge 是**认证 WebSocket**，但"认证连接 ⇒ Origin 可信"需要**在代码里找到依据**（谁写入 `Origin`、能否被调用方伪造）。**若可信 ⇒ 按上述 5 步闭合；若不可信 ⇒ 暂缓结论维持**（不得让 Bridge 自行断言身份）。
### 6c-补三（2026-10-08，后续会话）：**待定问题已答** —— `Origin` 由 Core 建立，缺口可闭合

读实两处：

| 事实 | 证据 |
|---|---|
| `Origin` 是**可空**字段 | `Source/PuddingBrowser.Protocol/BrowserBridgeMessages.cs:41`：`public BrowserBridgeCommandOrigin? Origin { get; init; }` |
| 命令**唯一**构造点在 **Core/Host 侧** | `Source/PuddingHost/BrowserBridge/RemoteBrowserRuntime.cs:162`：`await _broker.ExecuteAsync(new BrowserBridgeCommand { … })` —— 由**承载 Agent 的 Core** 写入 |

⇒ **结论**：`Origin` **由 Core 建立**（调用方/模型**不直接**构造该命令）⇒ 其信任级别与**能力通道的身份**同源（两者都源自 Core）。**且链路是认证 WebSocket**（`AGENTS.md`）。

**⇒ 待定问题答案是"可信（以 Core 为源）"，因此 Bridge 截图的暂缓可以解除**，实施时遵守两条硬约束：
1. **缺失 `Origin` ⇒ 明确拒绝**（fail-closed：可空字段不得被当作"默认可信"）；
2. **准入复用 `BrowserAdmissionAdapter`**（入队前 `Admit`、执行前 `Revalidate`），**不新写准入逻辑** —— 唯一还需确定的实现细节是 `ConnectionGeneration` 在 Bridge 传输下的语义（应与通道侧同源或明确其等价物）。

**⇒ 实施顺序（下一轮起，每步构建）**：① `Origin` → `BrowserCallerIdentity` 映射（缺失即拒）；② Bridge 的 `ConnectionGeneration` 语义；③ `HandlePageScreenshotAsync`（复用适配器 + 复用 Automation 采集资产 + 登记观察）；④ 桥侧 `ScreenshotAsync` 真正转发；⑤ 用例（往返 + 准入拒绝路径）⇒ 全量链（核对 buildId）。
### 6c-补四（2026-10-08，后续会话）：① 的落点已定，但暴露两处**缺失字段**（须先决策）

**唯一身份真源**（读实）：`Source/Pudding.Contracts/Desktop/BrowserCallerIdentityProjection.cs` —— 其文档写明**"这是唯一允许产生 `BrowserCallerIdentity` 的地方"**，且：

```csharp
TryProject(bool isSubAgent, string? callerId, string? runId, string? parentRunId,
           out BrowserCallerIdentity? identity, out string reason)
// fail-closed：callerId 空 ⇒ 拒；runId 空 ⇒ 拒；isSubAgent 且 parentRunId 空 ⇒ 拒
```

**已核实的 Bridge 侧字段**（`BrowserBridgeCommandOrigin`）：`WorkspaceId` · `AgentInstanceId` · `SessionId` · `ConversationId?` · `RunId?` · `ToolCallId?` · `ToolName`。

⇒ **可映射**：`callerId ← AgentInstanceId`、`runId ← RunId`（**两者齐全即可满足非子代理场景**）。

⇒ **缺失且必须决策的两项**：
| 缺失 | 影响 |
|---|---|
| **`isSubAgent` 布尔** | 无法判断是否子代理 ⇒ 无法执行"子代理必须有父任务"这条硬规则 |
| **`parentRunId`** | 子代理场景**必须**有它，否则 `TryProject` 一律拒绝 |

**⇒ 因此 Bridge 截图不是"补一条映射"即可闭合**，而取决于对以下之一的决策：
- **A**：扩展 `BrowserBridgeCommandOrigin`（加 `IsSubAgent`/`ParentRunId`）—— 属**协议载荷变更**（契约 + Host 侧写入 + 桌面侧读取 + 冻结守卫），是**真正的工作量**；
- **B**：证明 Bridge 路径**不可能**出现子代理（或其身份已由别处保证），从而只需 `callerId`/`runId`；
- **C**：维持暂缓（**当前状态**），把"Bridge 只支持非子代理截图"或"截图仅走能力通道"写成**明确约束**。

**本轮结论（诚实）**：先前"5 步清单"里的第 ① 步**比预估更深** —— 它牵出**协议字段**问题。**在决策 A/B/C 之前不动手**（避免写一半的准入，或让子代理绕过父授权子集规则）。

### 6c-补五（2026-10-08，后续会话）：实施落点的**可行性事实**（工作量判断）

读实 `BrowserWorkspaceController`（`Source/PuddingDesktop.WpfArchive/Browser/`，L108–130）**已有**：
`_pages: Dictionary<PageId, IBrowserPage>` · `_runtime` · `_surfaceHost` · `_uiDispatcher` · `_automationGates: BrowserAutomationGateSync?` · `_readings` · `_controlState/_bridgeState`
**没有**：`BrowserAdmissionAdapter` / `BrowserPageLifecycle` / `Authority`（准入**未接线**），也没有 Automation 的采集资产与观察登记处。

⇒ 在该控制器里实现 Bridge 截图，等于**同时接进**：① 准入适配器；② 采集资产（几何/计数器/计划/预算）；③ 观察登记处。**这不是"补一条映射"**，而是一次**装配级改动**，且该类位于 `WpfArchive`（`AGENTS.md` 定性为**旧 UI 验证基线**，其非 UI 源码由 WinUI **链接编译**共用）。

**⇒ 更优落点（待下一轮读实）**：桌面进程内**已经同时具备准入与采集**的是**能力通道侧**（`Pudding.DesktopService` 的 `BrowserAdmissionAdapter` + `Pudding.DesktopSurface.Browser` 的表面；两者与控制器**同进程**）。因此 Bridge 命令应由**该侧**执行，并**用 `command.Caller`（Core 权威身份）**喂准入 —— 这样**不新增装配、不复制判据**。

**⇒ 工作量判断（诚实）**：Bridge 截图**可做**，但属**跨组件装配**（≥3 处接线 + 用例 + 全量链），**不是一两轮能收口**的小改。**下一步先读**：① 能力通道侧是**谁**在处理 `Screenshot`（是否已有可被 Bridge 复用的入口）；② 该侧是否已持有 `BrowserAdmissionAdapter` 实例。
