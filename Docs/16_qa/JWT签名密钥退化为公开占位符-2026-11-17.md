# JWT 签名密钥退化为配置里公开可见的占位符

## 一句话

`config/security.json` 的 `jwt.key` 被 KeyVault 迁移改成了 `{{vault:...}}` 引用，
但**配置链不展开 vault 引用**。`PuddingJwtSettings.FromConfiguration` 直接读
`configuration["Jwt:Key"]`，拿到的是那串 42 字符的引用本身，且长度校验门槛只有 16，
于是 **JWT 的 HS256 签名密钥 = 配置文件中明文可见的固定字符串**。

任何人读到 `config/security.json`（它本来就是本地明文可读文件）就能伪造任意身份、
包括 admin 的登录态 token。服务照常运行，没有任何告警——**静默退化**。

## 证据链（全部现场实测）

| # | 判据 | 实测 |
|---|---|---|
| 1 | 配置当前值 | `LEN=42`、`IS_VAULT_REF=True`、`HEAD={{vault:c...` |
| 2 | 长度校验门槛 | `PuddingJwtSettings.MinimumKeyLength = 16` ⇒ 42 ≥ 16 **通过** |
| 3 | 读取点无展开 | `JwtTokenFactory.cs:47` `var key = configuration[KeyPath];` 直取原值 |
| 4 | 配置链无 vault 提供器 | `PuddingApplicationHost.cs:70-71` 只有两个 `AddJsonFile`，无自定义 `ConfigurationProvider` |
| 5 | 消费点 | `PuddingApplicationHost.cs:168` `PuddingJwtSettings.FromConfiguration(builder.Configuration)` |

## 根因

迁移脚本的策略是「把所有形似凭据的叶子字段改成 `{{vault:...}}`」，
但**没有校验该字段的消费方是否会展开 vault 引用**。

PuddingAgent 里存在两套完全不同的凭据消费路径：

| 路径 | 是否展开 `{{vault:}}` | 典型字段 |
|---|---|---|
| 文件服务层（显式调用 `InjectAsync` / `CredentialReference.ResolveAsync`） | **是** | `llm.providers.json`、`search.providers.json`、`voice/providers.json`、`caldav.json` |
| .NET 配置链（`IConfiguration`） | **否** | `security.json → Jwt:Key` |

`Jwt:Key` 属于第二类，却被按第一类的规则迁移了。

这与同一天早些时候发现的「图片生成密钥未走解析链导致 401」是**同一类缺陷的第二次出现**：
迁移只改了数据形状，没逐个核对读取方。

## 同一处的第二份副本（同样是坑）

`config/system.json` 里还有一份 `Jwt.Key`，同样被迁成 `{{vault:...}}`。

而 `PuddingApplicationHost.cs:70-71` 的加载顺序是：

```csharp
.AddJsonFile(SystemConfigFile("system.json"), optional: true, reloadOnChange: true)
.AddJsonFile(SystemConfigFile("security.json"), optional: true, reloadOnChange: true)   // 后加载
```

`jwt.key` 与 `Jwt.Key` 在 `IConfiguration` 里是**同一个键**（大小写不敏感），
后加载的 `security.json` 覆盖前者。所以 `system.json` 的 `Jwt` 节是确定的死数据。

危险之处不在「它是死数据」，而在**它是一层能静默顶上的兜底**：
一旦 `security.json` 的 `jwt.key` 缺失，42 字符的占位符会立刻接管并通过长度校验，
缺陷原样重演，且更难被发现。

## 本次处置（数据层，未改代码）

| 项 | 动作 | 复核 |
|---|---|---|
| `security.json → jwt.key` | 换成 32 字节 CSPRNG 生成的 64 字符 hex | `READBACK_LEN=64`、`IS_VAULT_REF=False`、`READBACK_MATCH=True` |
| 替换精确性 | 断言 JSON 内 `"key":` 锚点唯一 | `ANCHOR_COUNT=1` |
| `system.json → Jwt` 节 | 整体删除（确定的死数据 + 有毒兜底） | `HAS_JWT=False`、`AFTER_KEYS` 少一项、`TOKEN_UNCHANGED=True` |
| 备份 | `security.json.bak-20261117-jwt`、`system.json.bak-20261117-jwt` | 读取前 `Copy-Item` |

**代价：所有已签发的登录态 JWT 失效，管理端需要重新登录一次。**
这是修这个缺陷的必要成本——继续沿用可预测的密钥不是选项。

**残留的不一致**：保管箱里 `cfg.config.security.json.jwt.key` 与
`cfg.config.system.json.Jwt.Key` 两条现在无人引用。不删是刻意的：
保留它们作为回滚素材，且删除需要 KeyVault 写入路径（当前工具未对本 Agent 暴露）。

## 未解决：正解仍待做

上面的处置是**止损**，不是最终形态。最终应该是：

1. 给配置链加一层 vault 解析（`IConfigurationProvider` 或启动期内存注入），
   让 `IConfiguration["Jwt:Key"]` 能返回真实值；
2. 把 `jwt.key` 重新改回 `{{vault:...}}`；
3. 在迁移脚本里加一条**前置校验**：字段被迁移前，必须确认消费方会展开引用，
   否则拒绝迁移并报出该字段与读取位置。

第 3 条是防止这类缺陷第三次出现的关键——前两次（图片生成密钥、JWT 密钥）
都是同一个根因。
