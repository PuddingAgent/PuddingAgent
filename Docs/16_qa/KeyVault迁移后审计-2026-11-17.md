# KeyVault 迁移后审计

只读检查，未修改任何配置、未改写任何 vault 条目、未输出任何明文。

## 方法

1. 解开 `.work/keyvault-migration/20261117/recovery/*.dpapi`（DPAPI CurrentUser，
   熵 `PuddingAgent.MigrationRecovery.v1`），得到**迁移前**的配置原文；
2. 对每个凭据字段只计算 `SHA-256` 前 12 位与长度，**不打印值**；
3. 扫描 `config/`、`channels/`、`agents/` 三处的 `{{vault:NAME}}` 引用，与 21 条条目做集合差；
4. 对照检查：所有引用名都必须能在条目映射中找到。

## 判据与结果

### 1. 飞书 appSecret：两条值相同的独立条目

```
feishu/config            fp=63c2455ee01a len=32
feishu/channel-default   fp=63c2455ee01a len=32   <-- 同值
feishu/channel-59897cf8  fp=46aa7aea7718 len=32   <-- 另一个应用
```

`config/feishu.json` 与渠道 `feishu-default...` 的 manifest 指向**两条不同的 vault 条目**，
但两处明文在迁移时完全一致。

风险：它们在保管箱里是两个独立对象。改其中一条不会影响另一条，运行期读哪一条取决于
调用方走的是配置链还是渠道 manifest —— 一条被改、另一条没改时，两边会给出不同的
appSecret，而且**没有任何检查能发现**。

应为：一条条目 + 两处引用同一名字（或明确只保留一个消费者）。

### 2. JWT：两条原始条目已变孤儿

```
21 条条目 / 19 条被引用
ORPHAN: cfg.config.security.json.jwt.key
ORPHAN: cfg.config.system.json.Jwt.Key
幽灵引用（引用名找不到条目）：NONE   <-- 对照组
```

迁移后 `PuddingDataRootBootstrapper` 重新生成了登录态签名密钥，于是：

- `config/security.json` 现在同时含 `jwt.key` 与 `Jwt.Key`，都是**明文 64 hex**，
  指纹 `3cba3d1cf907`；
- 这个值**既不等于**迁移前 `security.json` 的 `dea7ec1f0b1f`，**也不等于**
  迁移前 `system.json` 的 `94500d2198c0`；
- `config/system.json` 里已无 `Jwt` 段，只剩 `desktop.core.controlToken` 一个引用。

所以两条 JWT 条目现在是死条目：占着保管箱、出现在管理界面上、却无人引用。

### 3. security.json 的 JWT 密钥是明文

这是待办清单里已知的一条，此处给出量化确认：长度 64、高熵、**不是** `{{vault:}}` 引用。
也就是说 21 条里只有 19 条真正生效，而唯一仍在配置文件里的高价值明文正是这条。

## 可以做什么 / 不能做什么

可做且低风险：

- 把飞书两处合并为一条引用（改配置，不动密钥值）；
- 删除两条孤儿条目（**破坏性**，需显式授权，且删除前要先确认引导器不再需要它们）。

需要设计而非补丁：

- `security.json` 的 `jwt.key` 改回引用。堵点在于：`PuddingApplicationHost` 的
  `["Jwt:Key"]` 走 `BootstrapSecretFile.Resolve`（启动前缓存），**不是** vault 解析链；
  直接把 `{{vault:}}` 写进去，会让引导器把占位符当密钥用——这正是之前退化成
  公开占位符的那个坑。必须先给配置链补 vault 解析，并配一条能取红的回归测试。

## 未证实

- 引导器为何判定原密钥不可用而重写（是占位符判定、长度判定还是显式重置），
  本审计只观测到结果，没有复现触发条件。
- `agents/*/secrets/home-assistant.json` 的 token 字段在恢复副本里读为空，
  可能是字段名不同（如 `accessToken`），属探针局限，不作产品结论。

## 追加证据（2026-11-17 22:4x，只读解密恢复副本，未打印明文）

上节把「引导器重写了签名密钥」列为未证实。本节用可复现的指纹把它拆成**已证实**与**仍未证实**两半。

方法：用 `ProtectedData.Unprotect(..., DataProtectionScope.CurrentUser)` 解开
`.work/keyvault-migration/20261117/recovery/*.dpapi`（熵 `PuddingAgent.MigrationRecovery.v1`）
与 `D:\Data\secrets\bootstrap.credentials.dpapi`（熵 `PuddingAgent.BootstrapCredentials.v1`），
只计算 SHA-256 前 12 位与长度，**不输出任何密钥原文**。

| 位置 | 长度 | SHA-256 前 12 位 |
|---|---|---|
| 迁移前 `config/security.json` → `jwt.key` | 64 | `DEA7EC1F0B1F` |
| 迁移前 `config/system.json` → `Jwt.Key` | 64 | `94500D2198C0` |
| 引导缓存 `cfg.config.security.json.jwt.key` | 64 | `DEA7EC1F0B1F` |
| 引导缓存 `cfg.config.system.json.Jwt.Key` | 64 | `94500D2198C0` |
| 引导缓存 `cfg.config.system.json.desktop.core.controlToken` | 64 | `92238C6320C8` |
| **当前** `config/security.json` → `jwt.key` | 64 | **`3CBA3D1CF907`** |

### 已证实

1. 迁移前这两条 JWT 密钥**本身就是明文、且是两个不同的值**（`DEA7…` ≠ `94500D…`），
   即迁移之前就存在「同一用途、两处配置、值不相同」的状态。
2. 引导缓存（磁盘 mtime `11:26:14`）里的两条 JWT 值与迁移前配置**逐条一致**，
   说明迁移的 bootstrap 分支只做了「入库 + 写入启动前缓存」，**没有改写配置文件**。
   这与脚本源码一致：`deferredBootstrap` 就是为这类字段准备的。
3. 当前生效值 `3CBA3D1CF907` **既不等于**迁移前的那两个值，**也不等于**缓存里的任何一个。
   ⇒ 迁移之后确有新密钥被写入 `config/security.json`（文件 mtime `18:14:41`）。
4. 由此产生一个**现在就有害**的状态：缓存与文件不一致。
   若今天把 `jwt.key` 改成 `{{vault:cfg.config.security.json.jwt.key}}`，
   解析会返回 `DEA7…`（缓存值）而不是生效的 `3CBA3D…`，
   等于**静默换掉签名密钥并让所有已签发管理员会话失效**。

### 仍未证实

- 18:14:41 那次写入的**发起者**。仓库内唯一写 `security.json.jwt.key` 的代码是
  `PuddingDataRootBootstrapper.EnsureSecurityJwtKey`，但它只在解析结果「不可用」时才生成，
  而一个 64 字符的明文密钥是「可用」的。所以要么写入前文件被置空/替换过，要么写入方不在本仓库。
  未复现触发条件，不作归因结论。
- 早期 bootstrap 阶段 Serilog 可能尚未就绪，`[Bootstrap] 已在 … 生成新的登录态 JWT 签名密钥`
  在 288 个日志文件中**一次都没出现**；这**不能**当作「没有生成过」的证据（仪器可能丢日志）。

### 对设计的结论

`jwt.key` 现在有**两个事实来源**（配置文件明文 / 启动前 DPAPI 缓存），而迁移只同步了后者。
正确的形态是引导器自己保证一致：生成新密钥时 `Store(name, value)` 写入缓存、随即把配置文件写成
`{{vault:name}}`，让缓存成为唯一副本；迁移脚本不应把这类字段「延期」了事。
这条要配一条能取红的回归测试（构造一个仅含 `{{vault:}}` 的 `security.json`，
断言引导后文件仍是引用、且缓存里有对应值），再动实现。
