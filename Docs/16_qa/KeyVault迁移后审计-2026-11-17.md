# KeyVault 迁移后审计

只读检查，未修改任何配置、未改写任何 vault 条目、未输出任何明文。

## 方法

1. 解开 `.work/keyvault-migration/20261117/recovery/*.dpapi`（DPAPI CurrentUser，
   熵 `PuddingAgent.MigrationRecovery.v1`），得到**迁移前**的配置原文；
2. 对每个凭据字段只计算 `SHA-256` 前 12 位与长度，**不打印值**；
3. 扫描 `config/`、`channels/`、`agents/` 三处的 `{{vault:NAME}}` 引用，与 21 条条目做集合差；
4. 对照检查：所有引用名都必须能在条目映射中找到。

## 判据与结果

### 1. 飞书 appSecret：两条值相同的独立条目

```
feishu/config            fp=63c2455ee01a len=32
feishu/channel-default   fp=63c2455ee01a len=32   <-- 同值
feishu/channel-59897cf8  fp=46aa7aea7718 len=32   <-- 另一个应用
```

`config/feishu.json` 与渠道 `feishu-default...` 的 manifest 指向**两条不同的 vault 条目**，
但两处明文在迁移时完全一致。

风险：它们在保管箱里是两个独立对象。改其中一条不会影响另一条，运行期读哪一条取决于
调用方走的是配置链还是渠道 manifest —— 一条被改、另一条没改时，两边会给出不同的
appSecret，而且**没有任何检查能发现**。

应为：一条条目 + 两处引用同一名字（或明确只保留一个消费者）。

### 2. JWT：两条原始条目已变孤儿

```
21 条条目 / 19 条被引用
ORPHAN: cfg.config.security.json.jwt.key
ORPHAN: cfg.config.system.json.Jwt.Key
幽灵引用（引用名找不到条目）：NONE   <-- 对照组
```

迁移后 `PuddingDataRootBootstrapper` 重新生成了登录态签名密钥，于是：

- `config/security.json` 现在同时含 `jwt.key` 与 `Jwt.Key`，都是**明文 64 hex**，
  指纹 `3cba3d1cf907`；
- 这个值**既不等于**迁移前 `security.json` 的 `dea7ec1f0b1f`，**也不等于**
  迁移前 `system.json` 的 `94500d2198c0`；
- `config/system.json` 里已无 `Jwt` 段，只剩 `desktop.core.controlToken` 一个引用。

所以两条 JWT 条目现在是死条目：占着保管箱、出现在管理界面上、却无人引用。

### 3. security.json 的 JWT 密钥是明文

这是待办清单里已知的一条，此处给出量化确认：长度 64、高熵、**不是** `{{vault:}}` 引用。
也就是说 21 条里只有 19 条真正生效，而唯一仍在配置文件里的高价值明文正是这条。

## 可以做什么 / 不能做什么

可做且低风险：

- 把飞书两处合并为一条引用（改配置，不动密钥值）；
- 删除两条孤儿条目（**破坏性**，需显式授权，且删除前要先确认引导器不再需要它们）。

需要设计而非补丁：

- `security.json` 的 `jwt.key` 改回引用。堵点在于：`PuddingApplicationHost` 的
  `["Jwt:Key"]` 走 `BootstrapSecretFile.Resolve`（启动前缓存），**不是** vault 解析链；
  直接把 `{{vault:}}` 写进去，会让引导器把占位符当密钥用——这正是之前退化成
  公开占位符的那个坑。必须先给配置链补 vault 解析，并配一条能取红的回归测试。

## 未证实

- 引导器为何判定原密钥不可用而重写（是占位符判定、长度判定还是显式重置），
  本审计只观测到结果，没有复现触发条件。
- `agents/*/secrets/home-assistant.json` 的 token 字段在恢复副本里读为空，
  可能是字段名不同（如 `accessToken`），属探针局限，不作产品结论。
