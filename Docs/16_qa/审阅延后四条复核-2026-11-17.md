# 审阅延后四条复核

## 0. 三态判定

| # | 原记录 | 本轮判定 |
|---|---|---|
| 1 | 连接器复核允许根 | **真缺口**（TOCTOU，投递前只复核了凭据类，没复核允许根） |
| 2 | `FeishuFileSplitPlanner.Plan` 死代码 | **不是死代码**，是「已写好但未接线」的功能；删掉会毁掉待做需求 |
| 3 | `Func<FeishuConfig, FeishuClient>` 缝无测试 | **确认**：只有声明，生产不传，测试也不用 |
| 4 | 文件兜底不尊重 `open_id` | **未证实**（本轮没追到判定点，不写结论） |

复核方式：`findstr` 全仓定位 + 读源码原文。本文所有「不存在」类判断都同时给出了阳性对照。

## 1. 连接器复核允许根 —— 真缺口（TOCTOU）

`FeishuConnector.SendWorkspaceFileAsync`（`FeishuConnector.cs:323`）在投递前做三道检查：

```csharp
if (Directory.Exists(full))  throw ...          // 目录
if (!File.Exists(full))      throw ...          // 不存在
if (FeishuFileSourcePolicy.IsCredentialLike(full)) throw ...   // 凭据类
```

方法注释写明设计取舍：

> 取材合法性（允许根、凭据类拦截）在工具层用 `FeishuFileSourcePolicy` 判定，这里只守大小与存在性。

但同段代码自己的注释又承认了风险：

> 排队到投递之间，路径可能已被替换成凭据文件；取材合法性不能只在工具层判一次。

两点合起来意味着：**「凭据类」复核了，「允许根」没复核**。`SendFileTool` 在排队时用
`FeishuFileSourcePolicy(FeishuFileRoots.Resolve(...))` 判过允许根，但队列到投递之间若路径被换成
允许根之外的文件（junction / 符号链接 / 覆盖写），投递侧不会再拦——除非它恰好像凭据文件。

修复方向（尚未实施）：投递侧复用同一条 `FeishuFileSourcePolicy.Evaluate`，而不是只调静态的
`IsCredentialLike`。需要把 DataRoot / WorkspacesRoot / workspace 解析得到的信息带过来，属于接口改动，
不能顺手改。

## 2. `Plan` 不是死代码，是未接线的功能

`Plan` 与 `PartCount` 的调用方为 0：

```
findstr /s /c:"FileSplitPlanner.Plan" /c:"SplitPlanner.Plan" Source\*.cs   → 无命中
findstr /s /n /c:"PartCount" Source\*.cs
  → 3 处，全部是 BoundedCompactionSummary / AgentExecutionService 的另一个同名属性，与本类无关
```

**但「无调用方」≠「该删」。** 同一文件里只有常量 `MaxSingleFileBytes` 是活的，它被用于两处**拒绝**：

```csharp
// SendFileTool.cs:74
return ToolExecutionResult.Fail(
    $"The file is {info.Length} bytes; Feishu caps one file at "
    + $"{FeishuFileSplitPlanner.MaxSingleFileBytes} bytes. Split it first.");
```

也就是说：超过 30 MB 时当前**直接失败并让用户自己切**，而旁边就躺着一份完整的切分实现
（含边界注释「恰好等于上限必须是 1 段」、重组后缀 `.part01of03`）。类注释本来写的就是：

> 大文件的处理不是「传上去」，而是按上限切成若干段，依次发，并在最后给一条重组命令。

结论：这是**功能做了一半**——切分算好了，投递侧没接。处置应是接线（或明确记录不做），**不是 git rm**。
若按「死代码」处理删掉，待做需求会连同测试边界一起消失。

## 3. 测试缝确实无人使用

```csharp
// FeishuConnector.cs:48-54
Func<FeishuConfig, FeishuClient>? clientFactory = null)   // ← 全仓唯一出现处
...
// 测试缝：生产不传，内部照旧在 StartAsync 现造；测试可注入带假 handler 的 client
_client = clientFactory?.Invoke(_config);
```

- `findstr /s /c:"Func<FeishuConfig"` → **1 处**，就是这行声明
- `findstr /s /c:"new FeishuConnector"` → **1 处**，`FeishuConnectorFactory.cs:136`，6 个参数全传，
  `clientFactory` 省略 ⇒ 生产走 `null`
- 测试工程里没有任何 `new FeishuConnector`

所以这个缝是**声明了、注释了、但没人用**。它不造成缺陷，只是说明「用假 HTTP handler 断言分发与元数据」
这件事一直没做。要么补测试用上它，要么删掉以免读者误以为已有覆盖。

## 4. `open_id` 兜底 —— 未证实

`FeishuFileProjection.cs` 里 `open_id` / `OpenId` / `chat_id` / `ChatId` **全部 0 命中**
（同文件 `QueueAsync` 等符号命中正常，检测器有效）。但回复路由的判定不在这个文件里，
而在下游投递服务——本轮没追到判定点。

按「未证实不写结论」的纪律，这条留待后续：下一步应在投递侧定位 `receive_id_type` 的取值来源，
确认 p2p 场景是否真的用了 `chat_id` 而不是 `open_id`。

---

## 5. 建议顺序

1. **接线切分功能**（第 2 条）——已有实现，缺投递侧串联，价值最直接
2. **补投递侧允许根复核**（第 1 条）——安全相关，但涉及接口，需单独设计
3. **处置测试缝**（第 3 条）——补测试或删除，二选一，成本都低
4. **追 `open_id`**（第 4 条）——先定位判定点再谈修
