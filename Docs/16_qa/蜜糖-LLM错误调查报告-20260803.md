## 根因分析（已修订）

Provider 拒绝请求的直接原因是 **Qwen 单次输入超过 983,616 tokens**。原始错误为：

```text
runtime_execution_failed
LLM API error (BadRequest): data: {"error":{"code":"invalid_parameter_error","param":null,"message":"Range of input length should be [1, 983616]","type":"invalid_request_error"},"id":"chatcmpl-f7deb03d-6d9b-4a7e-a4dc-05663a1a5b3c"}
```

第一条错误在 Round 6/200 发生；相邻的最近一次成功调用 UsageJson 显示：

- PromptTokens: 983,418
- CompletionTokens: 1,797
- TotalTokens: 985,215
- ContextWindow: 1,000,000
- CacheHit: 978,816 / Miss: 4,602

`983,418` **没有超过** `983,616`，而是低 198 tokens。原报告“刚好超出”的算术结论错误。这组 Usage 证明上一轮成功请求已经逼近输入硬上限；其 1,797-token completion、工具调用/结果和下一轮消息随后进入历史，使下一次实际请求超过 983,616。错误响应没有返回被拒请求的实际 token 数，因此不能把 983,418 当成失败请求长度。

系统性根因包括：

1. Provider Model 只配置了 `maxContextTokens=1,000,000`，没有表达 Qwen 独立的 `maxInputTokens=983,616`。
2. 上下文健康度此前按完整 ContextWindow 计算，没有扣除输出预算和安全余量。
3. 本地估算没有完整计入 reasoning、tool call 标识/名称/参数，且 Provider usage 曾被较小的本地估算保留，导致实际接近上限时仍可能被判断为可发送。
4. Agent 的 `maxReplyTokens` 没有稳定下传为 Provider 请求的 `max_tokens`，输出预留无法形成闭环。
5. 发送前缺少针对最终 messages + tools payload 的硬预算守卫；收到这一明确 400 后也没有执行一次受控压缩恢复。

后续 8 次错误均在 Round 1/200，说明相同的膨胀上下文被多个上层执行/重试再次提交；它们不是 `DirectLlmClient` 对同一个 HTTP 400 的内部网络重试。

## 修复结果（2026-08-03）

- Provider Model 新增独立 `maxInputTokens`；事故日志中的模型名为 qwen3.8-max-preview，当前开发数据配置中的 qwen3.8-max 已设为 `983616`。
- 有效输入预算统一为 `min(maxInputTokens, maxContextTokens - maxOutputTokens - safetyBuffer)`；健康度、状态接口、自动压缩和发送前守卫使用同一容量定义。
- 每次实际调用前对最终 messages 与 tools 重新计量；超限时按完整会话单元移除最旧历史，保留 System Prompt 和最近消息，并修复工具消息序列。
- 本地估算覆盖 reasoning 与 tool-call payload；收到 Provider usage 后按 session + model 校准，Provider 总用量不会再被更小估算覆盖。
- Agent `maxReplyTokens` 会收紧模型输出上限并下传为 Provider `max_tokens`。
- 对原始 `Range of input length should be [1, 983616]` 错误学习 Provider 上限并在当前执行内只恢复重试一次，避免无界重试。

## 结论

事故根因是“模型总窗口”和“Provider 单次输入硬上限”被混为同一容量，加上估算与 Provider usage 未形成校准闭环。`983,418` 是接近上限的成功请求，不是超限值。修复后无需仅为该错误切换模型：Pudding 会提前压缩，并对 Provider 明确的输入上限错误执行一次受控自恢复；若裁剪后 System Prompt、工具定义和受保护尾部本身仍无法装入，则会在本地以明确的预算错误终止，而不会继续向 Provider 提交无效请求。
