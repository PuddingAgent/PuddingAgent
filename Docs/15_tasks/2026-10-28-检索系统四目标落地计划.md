# 2026-10-28 检索系统四目标落地计划

## 1. 目标（用户 2026-10-28 明示）

| # | 目标 | 可判定的验收口径 |
|---|---|---|
| G1 | 大量文件检索毫秒级 | 单次查询 P50 ≤ 50ms、P95 ≤ 200ms，且**不因目录深度/范围收窄而退化** |
| G2 | 增删改后 1s 内索引更新 | 文件落盘 → 索引可检索到该变更 ≤ 1000ms |
| G3 | 后台自动维护，失效索引不留存 | 源文件已删除的索引条目在 N 分钟内被清除；unresolved 不无限累积 |
| G4 | 低 CPU / 磁盘空间 / 读写 IO / 内存 | 空闲时 CPU ≈ 0；索引目录有上限与治理；查询常驻内存可控 |

## 2. 实测基线（2026-10-28，全部现场测得）

### 2.1 快的那一半：已经达标

| 路径 | 实测 | 证据来源 |
|---|---|---|
| 全文检索 `search_grep backend=index`（仓库根 scope） | **engineMs=6~9，totalMs=6~9** | 今日两次调用返回体 |
| 符号检索 `code_symbol_search` 快路径 | **19ms**（旧路径 950ms / 冷 4227ms） | `2026-10-23-符号检索提速覆盖索引两阶段.md` |
| 索引规模 | `code_index.db` **1.74 GB**；`CodeSymbols` 195,533 行 / 去重名 50,854 | 今日实测 + 10-23 文档 |

**结论：索引能答的部分确实是毫秒级。** G1 没有失效，是**覆盖面**不够。

### 2.2 慢的那一半：三个具体缺口

**缺口 A（直接影响 G1）：目录一收窄，索引就用不上。**

```
search_grep(backend=index, directory=<某子目录>)
→ DependencyWait: "scope '...\Services\StorageManagement' has no index yet"
```

原因在代码里：`LuceneSearchEngine.SearchAsync` 要求 `HasIndex(directoryPath)`，而索引是按**注册项目根**建的。没有任何「上溯到最近的有索引祖先 + 把子目录当过滤前缀」的解析。

**后果**：窄范围检索一律退回托管扫描，撞 2000 文件 / 64MB / 10s 上限。今日实测两次：`scanned 2000/2000 … limit_reason=max_enumerated_files`。

**缺口 B（不满足 G1 的默认路径）**：不带 `backend=index` 的默认调用走托管扫描 + Lucene 候选**预取**。候选预取那处用的是 `SearchAsync(query, directory ?? "", …, subDirectoryFilter: directory)` —— scope 传的是**空串**。

⚠️ **未验证**：`GetIndexDirectoryPath("")` 实际解析到什么尚未确认，因此「候选恒为空」只是**待证实假设**，不能当结论。但无论真假，它只影响**候选排序优先级**，不影响扫描覆盖（覆盖由托管扫描保证）—— 真正的问题是默认路径根本没走索引正文。

**缺口 C（G3 的直接证据）**：

```
index_freshness: state=idle, watcher_attached=true,
                 last_calibration_at_utc=2026-10-27T16:09:13Z,
                 unresolved_source_path_count=6739
```

`unresolved_source_path_count` 在代码里映射到 `SourceMaintenanceUnresolvedPathCount = result.RetryableFileCount`（`CodeIndexMaintenanceService.cs:818`），也就是**可重试但一直没成功的文件数**。6739 是个大数，性质尚未查清：可能是超出项目根、可能是扩展名不支持、可能是被锁或读取失败。

另外 stale 清理的机制是存在的（`CalibrateAsync` 会打 `swept {Swept} stale file(s) ({Unresolved} unresolved)`），**所以 G3 不是「没做」，是「unresolved 这一侧没有治理」**。

### 2.3 完全没测的

- **G2**：watcher 是挂着的（`watcher_attached=true`），但从文件落盘到可检索的实际延迟**没有任何数字**。
- **G4**：CPU / IO / 内存占用没有基线；只知道符号快路径把 `cache_size` 设成 128MB。

> 未测 ≠ 不达标。这一栏必须先补测量，再谈优化。

## 3. 工作项（按依赖排序）

### W1 索引 scope 上溯 + 子目录过滤（解决缺口 A）

- **做法**：在 index backend 里把请求目录上溯到最近的有索引祖先，把原始目录作为 `subDirectoryFilter` 传入（引擎已支持该参数，`LuceneSearchEngine.cs:125`）。
- **边界**：上溯不得越过工作区根；找不到任何有索引祖先时，保留现有 `DependencyWait` 文案（那是正确语义）。
- **可测性**：解析逻辑抽成纯函数（输入目录 + `Func<string,bool> hasIndex` → 输出 (indexRoot, subFilter)），用假谓词覆盖「自身有索引 / 祖先有索引 / 全无索引 / 大小写与尾斜杠」。
- **验收**：对 `Source/PuddingPlatform/Services/StorageManagement` 这类子目录执行 `backend=index` 检索，返回命中而非 DependencyWait，且 totalMs ≤ 200ms。

### W2 默认路径接入索引（解决缺口 B）

- 先修候选预取的 scope 传参（`""` → 实际 scope），使候选真的产生。
- 再决定：默认是否在「有索引」时优先走 index backend。**这是产品决策**，需明确「索引可能滞后」是否可接受（滞后期间会漏掉刚改的内容 —— 与 G2 直接耦合）。
- **前置**：G2 有数字之后才能定默认策略，否则可能用「查不到最新内容」换「快」。

### W3 增量更新延迟实测（G2）

- 用探针：写一个临时文件 → 每 100ms 轮询索引可见性 → 记录延迟；再测「修改」「删除」两个动作。
- **验收**：三动作各 20 次采样，报告 P50/P95/最大值；若 P95 > 1000ms，定位是 watcher 防抖、批处理窗口还是重建触发。

### W4 unresolved 6739 的归因与治理（G3）

- 先分类：超出项目根 / 不支持扩展名 / 读取失败（锁、权限、编码）/ 元数据缺失。
- 再决定策略：可重试的设重试上限并降级为「已知跳过」；确实失效的进 stale 清扫。
- **禁止**：直接把计数清零或静默丢弃 —— 那是把缺陷藏起来。
- **验收**：给出分类计数表；`unresolved_source_path_count` 有明确解释与上限，不再无界增长。

### W5 资源基线（G4）

- 采空闲态与查询态两组：CPU%、工作集、索引目录 IO 读写、`code_index.db` 与索引目录体积变化率。
- **验收**：给出「空闲 / 单次查询 / 批量索引」三档的表；之后任何优化都要能对着这张表说清楚换来了什么。

## 4. 顺序与理由

```
W1 → W3 → W4 → W5 → W2
```

- **W1 先做**：纯增量收益，不依赖任何测量，且修的是「窄范围检索完全用不上索引」这个硬缺口。
- **W3 在 W2 之前**：默认策略取决于索引滞后有多严重。
- **W4 / W5 可并行**：一个治数据正确性，一个治资源，互不阻塞。

## 5. 已排除的方案（省得重复调研）

| 方案 | 结论 |
|---|---|
| 把符号名灌进 FTS5 trigram | 10-23 已实测：建表 219ms、临时库 8.2MB、任意子串 0ms。当前 5 万去重名 plain 表全扫已 0~4ms，**收益边际；符号数 >50 万再上** |
| 用 Lucene 做符号检索 | 已有三条防护测试（分词假阳性 / 零候选 / 语法字符）。符号搜索要结构化 + 子串，Lucene 的打分与分词是负担 |
| 向量检索替代关键词 | 符号名与精确文本检索**不需要**向量；向量只在语义召回场景有意义，与本轮四目标无关 |

## 6. 未验证 / 风险

- 本文所有数字都带时点；索引会随代码变更过期，**引用前先复核**。
- W1 的「上溯到祖先」可能让某些调用方拿到**本该报错**的结果（原先明确说「这里没索引」，改后返回祖先索引的过滤结果）。必须保留一条可分辨的说明，避免又把「没搜到」读成「不存在」。
- G2 若实测远差于 1s，可能需要改 watcher 策略，影响 IO —— 与 G4 直接冲突，届时要在计划里明确取舍。

## 7. W1 已落地（2026-10-28）

### 7.1 改动

- 新增 `IndexScopeResolver`（纯函数）：从请求目录向上找最近的有索引祖先，把请求目录转成**相对该祖先的相对路径**作为 `subDirectoryFilter`。
- `SearchGrepTool` 的 index backend 改为：先解析作用域 → 用祖先目录调用引擎 + 传子目录过滤 → 解析不到任何祖先时保持原 `DependencyWait` 语义（文案补上 "and neither does any ancestor within the workspace"）。
- 上溯边界为工作区根：边界外目录一律返回 null，**不允许借用工作区内的索引**（否则会产生假阳性召回）。

### 7.2 一个必须记下来的语义细节

引擎的子目录过滤是**相对作用域根的相对路径前缀**（`Path.GetRelativePath(directoryPath, path)` 后前缀比较），
所以解析结果必须给相对路径——给绝对路径会静默零命中。

另：`IndexRoot` 保留请求侧写法（`Path.GetFullPath` 不做盘上大小写归一）。这**不是缺陷**：
引擎用 `FullTextIndexPaths.NormalizeCorpusRoot`（`ToUpperInvariant` 后再 SHA256）定位索引目录，大小写不敏感。
我第一版测试就在这里断言过严而失败，已改为大小写不敏感比较，并把依据写进代码注释。

### 7.3 验证（原始输出 `temp/mutation-w1.txt`）

```
突变    if (hasIndex(candidate)) → if (hasIndex(requested))   // 取消上溯
```

### 7.4 尚未验证

- **真实索引上的端到端效果未测**：需要重启后对 `Source/PuddingPlatform/Services/StorageManagement`
  这类子目录跑一次 `backend=index`，确认从 `DependencyWait` 变成命中且 totalMs ≤ 200ms。
  在此之前不能说 G1 的「窄范围」缺口已经关闭。
- 默认路径（不带 backend）的缺口 B 仍未动，属于 W2。

## 8. W3 结论：G2 不是「慢」，是**默认关闭**（2026-10-28 实测）

### 8.1 仪器

索引目录按冻结规则推导（`NormalizeCorpusRoot` → `ToUpperInvariant` → SHA256）后定位到：

```
D:\Data\fulltext-index\f09e86e043ae76b0bc025ef00ed4dd5328fb947dded2a1c8f73db8e3181dbf78
基线 stamp: files=15 bytes=152,395,080 mtimeUtc=2026-10-27T15:55:15Z
```

观测点：在已索引的 `Docs/` 下新建 `.md` 文件，每 50ms 轮询索引目录 `(文件数, 总字节, 最新 mtime)`，
任一变化即判定「已提交」，超过 20s 判超时。脚本：`temp/g2-latency.ps1`，输出 `temp/g2-latency.txt`。

### 8.2 结果

```
SAMPLES=5 WITHIN_20S=0 TIMEOUT=5
SAMPLE 1..5 deltaMs=-1
```

**5 次全部在 20 秒内没有任何提交**——不是「超过 1 秒」，是**一次都没有**。

旁证：`search_grep` 返回的 `indexAge` 在今天多次调用中单调增长（24.2m → 55.7m → 58.3m），
而这段时间我改过多个源文件并提交过 6 次；`lastIndexed` 始终停在 `2026-10-27T15:54:23Z`。

### 8.3 根因

`MaintenanceOptions.Enabled` 的**声明默认值就是 false**，且文档注释写明「默认值 = 关闭，关闭状态零副作用」
（`MaintenanceOptions.cs:32`、`:107`）。

也就是说：watcher / 三源折叠 / 增量 commit 这一整套机制**代码是完整的**，但**默认不启动**。
没有配置显式开启时，全文索引只在显式 build 时更新，之后一直冻结。

宿主侧的状态探针其实早就在如实报告这件事：`FullTextIndexStatusProbe.ObserveMaintenance()`
在配置节缺失时返回 `Enabled = new MaintenanceOptions().Enabled`，即 `false`
（`FullTextIndexStatusProbe.cs:242-260`）。**我此前没有查它，这是本次诊断的疏漏。**

### 8.4 因此 G2 的验收要改口径

原先计划写的是「测文件落盘 → 可检索延迟，P95 ≤ 1000ms」。现在必须拆成两步：

1. **先确认它有没有在跑**（读状态探针的 `maintenance.enabled`，或看索引目录是否随改动推进）
2. 只有在跑的前提下，才谈延迟数字

把「没跑」当成「慢」去优化，会优化一个根本没执行的路径。

### 8.5 下一步（需要一次部署窗口）

开启增量维护的配置路径：

```
{FullTextIndexSupplyOptions.SectionName}:Maintenance:Enabled = true
```

（`SectionName` 的常量值以 `PuddingHost/Services/FullTextIndexStatusProbe.cs:244` 为准，
本轮未逐字确认，下一轮核对后再写死到文档，避免又出现「文档里的路径是陈旧投影」。）

开启后必须重测：① 三动作（新增/修改/删除）延迟；② 空闲 CPU 与索引目录 IO —— 这正是 G4 的代价项。
**「开启」与「G4 低占用」是有张力的**，届时要在同一张表里同时给出延迟与开销，而不是只报一个。

### 8.6 本轮明确不做

- **不擅自开这个开关**：它会在用户机器上引入持续的文件监听与后台 IO，且需要重启才生效（破坏性）。
  这是产品取舍，不是我能单方面决定的。
- 不改默认值：把默认从 false 翻成 true 是生产行为变更，且会与既有「关闭状态零副作用」的承诺冲突。

### 9.2 已补上的配置

```json
"Maintenance": {
  "Enabled": true,
  "Scopes": ["D:\\CodeProject\\PuddingAgent\\PuddingAgent"],
  "WorkspaceRoot": "D:\\CodeProject\\PuddingAgent",
  "IndexRootDirectory": "D:\\Data\\fulltext-index",
```

**唯一偏离默认值的项是 `MaxCoalesceWait`：2s → 1s。** 理由：G2 要求「持续写入时也不超过 1s」，
而默认 2s 在持续写入下会超出口径。其余保持声明默认，因为它们本来就是按低占用调的：
体检 24h 一次、每轮只切 64 个文件、切片间休 250ms、CPU >35% 或磁盘 >20% 就退避 30s、
内容缓存关闭。

`IndexRootDirectory` 填的是**实测发现的现场值**（第 8.1 节推导出的 `D:\Data\fulltext-index` 的父目录），
不是从文档抄的。

`ed2bfcb` 索引上溯、以及本次配置）。**这是一个需要用户点头的动作**，不是我单方面能决定的。

## 10. W4：unresolved 6739 的归因（2026-10-28，只读实测）

### 10.1 先纠正一个预设

计划里把 G3 写成「失效索引条目留存」。实测**这个方向目前是干净的**：

```
CodeFiles 行数 = 5586
逐条 Test-Path 检查 → FILES_MISSING_ON_DISK = 0
```

索引里没有任何指向已删除文件的条目。**G3 的真实问题在另一侧：失败重试表。**

### 10.2 重试表现状

| 指标 | 值 |
|---|---|
| `CodeIndexMaintenanceRetries` 行数 | **11,624** |
| 主因 `the round reached no conclusion for this path` | **6,928** |
| `file disappeared: …` | **4,683** |
| 其中路径形如 `*.tmpdir`（构建/原子写临时目录） | **2,261** |
| `MAX(Attempts)` | **585** |
| 最老 `FirstFailedAtUtc` | **2026-10-06**（21 天前） |
| 重试路径中**文件仍存在**的 | **6,940**（占 11,624 的 60%） |
| `CodeSourceManifest` 中 `Complete = 0` | **0**（清单本身完整） |

关键对比：**6,940 条重试指向的文件都还在**。所以这不是「失效条目」，是「**反复失败、不收敛**」。

### 10.3 机制：根因被后一次覆盖

阅读 `CodeSourceUpdatePlanner` 与 `CodeSourceMaintenanceCoordinator`：

1. 路径首次失败 → `ledger.RecordFailure(path, 真实原因, now)` 进入退避表
2. 后续每轮：`retry.Contains(path)` 为真 → 计划项被标 `RetryLater`（`CodeSourceUpdateReasons.RetryBackoffActive`）
3. 协调器对 `RetryLater` 项再次 `RecordFailure(path, "the round reached no conclusion for this path", now)`

**`RecordFailure` 是覆盖写。** 于是第一次的真实失败原因被这句症状覆盖掉，
表里 6,928 条全是同一句话 —— **你无法据此归因**。这是本次最值得修的一点（见 10.4 F1）。

`MAX_ATTEMPTS = 585` 还说明：协调器里那条「已在待办里的路径不重复记（否则每次都会把下次尝试往后推）」
的保护对部分路径**没有生效**，它们被反复重记。

### 10.4 处置清单（按优先级）

| # | 问题 | 处置 | 为什么这个顺序 |
|---|---|---|---|
| **F1** | 首次失败原因被覆盖，无法归因 | `RecordFailure` 保留首次原因（`FirstReason`）另存最近一次；或改为「同路径只记首次 + 更新计数」 | 不先修它，后面所有归因都是在猜 |
| **F2** | `*.tmpdir` 等瞬时路径被当源文件（2,261 条） | 索引输入排除构建/原子写临时目录 | 纯噪音，且是确定性不会成功的重试 |
| **F3** | 重试表无 TTL/上限，21 天无界累积 | 加保留策略（如 30 天或行数上限）+ 计数上报 | 与刚开启的存储自动清理同源问题：有机制、没兜底 |
| **F4** | 最初失败原因未知 | 修完 F1 后再采一轮才有可靠数据 | 顺序不能颠倒 |

### 10.5 本轮明确没做

- **没有改任何代码**：F1 涉及写入语义变更，必须连带改测试并做变异取红；
  且这一层与「索引正确性」直接相关，不适合在只读诊断轮里顺手改。
- **没有清理重试表**：11,624 行里 6,940 行对应文件仍存在，直接清掉会把
  「这些文件其实没被索引」这件事一并藏起来。清理必须建立在 F1 的归因之上。

### 10.6 顺带确认的两件事

- `code_index.db` 实测 **1,881,780,224 B（1.75 GB）**，与既有记录一致，没有异常膨胀。
- `CodeSymbols` **199,899** 行，`CodeProjects` 4 个，`CodeFiles` 5,586。

## 14. IO 归因 Attempt #2：仪器又坏了一次（`$pid`），但拿到了有效数据（2026-10-28）

### 14.1 又一次"仪器坏了"：`$pid` 是 PowerShell 只读自动变量

第一版细粒度探针写了：

```powershell
$pid = $proc.Id      # ← 静默失败
```

`$pid` 是 PowerShell 的**只读自动变量**。赋值抛 `WriteError`，但脚本继续跑，
于是 `Get-Raw $pid` 采到的是 **pwsh 自己**（15652），不是宿主（52720）。
那一轮输出全是 `readDeltaBytes=0`，差点被读成"没有持续读"。

**已修**：变量改名 `$targetProcessId`，并在开头打印 `target=<进程名> pid=<pid> start=<时间>`
做回读断言。这类"静默用错对象"的探针必须自带身份回显。

### 15.4 找到的可疑根因（**假设，尚未证实**）

`PRAGMA cache_size` 全仓只有两处，都在**代码索引**里：

```
Source/PuddingCodeIndex/Storage/SqliteCodeIndexStore.cs:484  PRAGMA cache_size = -131072;   // 128 MB
Source/PuddingCodeIndex/Storage/SqliteCodeIndexStore.cs:572  PRAGMA cache_size = -131072;
```

而平台库（**11.94 GiB**）的访问路径上**没有搜到任何 cache_size 设置** ⇒ 走 SQLite 默认
**2 MB 页缓存**。

于是形成一条自洽的机制假设：

> 平台库每秒有 KB 级写入（WAL mtime 持续变化）→ 但在 11.94 GiB 的库上只有 2 MB 页缓存
> ⇒ 几乎每次写入都要重新从磁盘读页（B 树遍历 + 索引页）⇒ **读放大到 30–44 MB/s**。

### 15.5 这个假设的**可检验预测**

如果成立，那么把平台库连接的页缓存提到 64–128 MB（与代码索引同级）后：

1. 稳态读应从 30–44 MB/s **下降一个数量级**；
2. 写入量不变（仍 KB/s 级）；
3. 内存工作集上升 64–128 MB 以内。

**若提高缓存后读量不降，则该假设否证**，需转向"某组件在扫表"。

### 15.6 为什么现在不改代码

- 加 cache_size 涉及平台库连接建立位置（EF Core 与手写连接两条路径要分别确认），
  不能靠猜改；且它会影响**内存占用**（G4 的另一条腿），需要与实测一起给。
- 顺序：先**确认平台库的连接初始化点**（下轮第一件事），再改、再用同一探针复测——
  这样"改前/改后"是同一把尺子。

### 15.7 一个副产物：idx=8 的 231 MB/s 尖峰

它出现在本轮结束后的最初几十秒，且伴随 14.6 MB 写——很可能是**turn 收尾**触发的
（记忆/摘要/事件落库）。这条与"稳态读者"是两个现象，下一轮一并观察，
但**不并入同一个结论**。

## 16. 平台库页缓存已显式设置（2026-10-28，待部署验证假设）

### 16.1 找到真正的接缝

平台库的连接设置集中在 `PlatformSqliteConnectionInterceptor`（EF Core `DbConnectionInterceptor`），
原本已设 4 个 PRAGMA：`busy_timeout` / `synchronous` / `temp_store` / `wal_autocheckpoint`，
**唯独没有 `cache_size`** —— 与"全仓只有代码索引设了 128 MB"完全吻合。

### 16.2 改动

```csharp
"PRAGMA cache_size=-32768;",   // 32 MB
```

**为什么是 32 MB 而不是代码索引那样的 128 MB**：`cache_size` 是**按连接**生效的，
而平台上下文是 Scoped、连接可能被多个并发上下文同时持有；128 MB × N 会把内存吃穿。
32 MB 是"先验证假设"的保守起点。

测试同步加了一条断言（`PRAGMA cache_size` 必须为 -32768），并做了变异验证：

```
基线    TOTAL=1 PASSED=1
突变    -32768 → -2000（看起来也像有意设置的数）
        TOTAL=1 PASSED=0 FAILED=1，命中 OpenConnectionAsync_AppliesPlatformPragmas
恢复    SHA-256 bit-identical 6B842329…3F42 → 1/1
构建    PuddingPlatformTests exit 0
```

### 16.3 部署后的验收判据（与 §15.5 的预测一致）

| 指标 | 改前（实测） | 预期 |
|---|---|---|
| 空闲期稳态读 | 30–44 MB/s | **下降一个数量级** |
| 写入量 | KB/s 级 | 不变 |
| 工作集 | 1.30–1.34 GB | 上升 ≤ (并发连接数 × 32 MB) |

用同一把尺子复测：`TestScripts/sample-host-io-shape.ps1 -Intervals 240 -IntervalSeconds 5`
（跨越 turn 边界的空闲期采样）。

**如果读量不降，本节假设即被否证**，下一步转向"某组件在扫表"，而不是继续调缓存。

### 16.4 边界与风险

- 本改动**只作用于平台库**（EF Core 路径）。手写连接路径（`StorageInventorySampler`、
  `StorageMaintenanceQueries` 等）**未改**，它们各自建连接、只被短时使用，不在持续写路径上。
- 若部署后内存明显上涨，第一个要查的是**并发连接数**（Scoped 上下文的实际并发）。
- 本改动与 G4 的另一条腿（低内存）**存在直接张力**，所以验收必须同时报读量与工作集，
  不能只报"读降了"。

## 20. G4 IO 归因：进程读 840 MB/s 是**缓存内热读**，且每次重开项目都在重读

### 20.1 决定性证据：同一区间内进程读与物理磁盘读并排采

## 23. 修正 §22.5：不是「全扫被饿死」，而是**每次全扫重新提取约 2540 个文件**

### 23.1 先看同一份日志里两类轮次

问题 scope `8a48458b…`，最近 8 轮里 2 次完整、6 次提示驱动：

```
08:44:16  1 reindex, 6761 deferred,    0 reuse   complete=false
08:44:33  1 reindex, 6760 deferred,    0 reuse   complete=false
08:44:41  1 reindex, 6760 deferred,    0 reuse   complete=false
08:47:46  2540 reindex, 0 deferred, 4229 reuse   complete=true    ← 周期性校准
08:49:02  99 reindex, 6657 deferred,   9 reuse   complete=false
```

**§22.5 里「周期性完整扫描被提示批次饿死」的猜测不成立**：08:47:46 那次校准确实跑完了，
`complete=true`、`0 deferred`、`4229 reuse`。同一份日志里其他 scope 也有 8 次 `complete=true`。

### 23.2 真正值得注意的是校准轮本身

| 轮次类型 | reindex | reuse | deferred |
|---|---|---|---|
| 提示驱动 | 1 / 99 | 0 / 9 | 6760 / 6657 |
| **完整校准** | **2540** | 4229 | 0 |

`reuse` 才代表"stat 未变、内容未变、直接复用已提交结果"。提示驱动轮 `reuse≈0` 是**结构必然**
（只观测被提示的路径，其余路径本轮压根没被观测），所以 `deferred≈6760` 也是必然，不是故障。

**但完整校准轮 `reindex=2540` 不正常**：校准的本意是"对齐索引与磁盘"，如果索引本来就是好的，
绝大多数文件应当落在 `reuse`（4229 已是多数），可仍有两千多个文件被判为需要**重新提取内容**。

按 §20 的机制（提取 = Roslyn 重开项目 + MSBuild 评估读整套引用程序集），
**这两千多个文件就是每轮校准的主要 CPU 与缓存读成本**。

### 23.3 为什么会被判成需要重提取（代码位置）

`CodeSourceChangeDetector` 判定"需要核验内容"的条件是：

```csharp
var needsContentVerification = statDiffers || hinted || racy || request.DeepVerify
    || entry.Fingerprint is null || !entry.Complete;
...
if (observedHashes.TryGetValue(path, out var observedFingerprint)) { ... }
// 需要核验但还没有 hash：调用方必须先稳定读取 + hash，不得假定未变化。
changes.Add(... CodeSourceAction.ReindexContent ..., RequiresContentHash: true);
```

而生产链路里 `CodeSourceScanService.cs:94` 是 **`ObservedContentHashes: null`** ——
扫描阶段不提供内容哈希。于是凡是 `entry.Fingerprint is null || !entry.Complete` 的路径，
每轮都落到"需要核验但还没有 hash ⇒ ReindexContent"。

**推论（待证）**：这 2540 个文件之所以反复被重提取，是因为它们**从未成功落成完整指纹**
（`Complete=false` 或 Fingerprint 为空），而不是因为它们真的变了。

### 23.4 为什么这对 G4 重要

```
每轮校准 reindex 2540 个文件
  → 每个文件都要 Roslyn/MSBuild 侧重新提取
  → 观测到的正是「进程读 820~854 MB/s、物理磁盘 0、CPU 约 2 核」
```

也就是说 §20 的"缓存内热读"不是凭空的热循环，而是**重复提取**的直接表现。

   而不是每轮重提。
2. **不要先调 Roslyn**：在 23.5-1 之前改索引器是盲改，和之前"把没运行的当成慢"是同一个错。

## 24. §23.3 被证伪；真凶是「每轮把未被观测的路径写成重试」

### 24.1 先证伪自己上一节的推论

只读探针 `temp/probe-manifest-health.ps1`（`Mode=ReadOnly`，直接查 1.89 GB 的
`D:\Data\databases\code-index\code_index.db`）：

```
ProjectId=8a48458b...  Total=6762  Incomplete=0  NoHash=0  Healthy=6762
ProjectId=64d573ef...  Total=521   Incomplete=0  NoHash=0  Healthy=521
ProjectId=8fdcca42...  Total=427   Incomplete=0  NoHash=0  Healthy=427
ProjectId=c4020187...  Total=380   Incomplete=0  NoHash=0  Healthy=380
```

**manifest 一个坏指纹都没有。** 所以 §23.3「2540 个文件因指纹不完整而被反复重提取」**不成立**。
`ContentHash`/`Complete` 全健康，说明"补指纹"不是修法方向——**幸好先量化了，没有去改索引器。**

### 24.2 同一探针抓到的东西（这才是机理）

```
=== pending retries for scope 8a48458b ===
Reason="the round reached no conclusion for this path"   N=6756  MaxAttempts=1
Reason="Python not available (tried 'python' and 'python3')" N=12  MaxAttempts=599
```

两条完全不同的性质：

| 现象 | 解读 |
|---|---|
| 6756 条、**Attempts 全是 1**、原因都是 "no conclusion" | 不是"重试一直失败"，而是**每轮新写进去的一批** |
| 12 条 Python 不可用、**Attempts=599** | 真正的不收敛重试（缺少放弃条件） |

数量关系对得上：manifest 总数 6762，提示驱动轮每轮 `deferred≈6760`，
重试表里正好 6756 条 `Attempts=1` 的 "no conclusion"。

**即：每个提示驱动轮，把"这一轮没被观测到的 6760 个路径"当成失败写进重试表。**
下一轮它们要么被再次覆写、要么被当成待重试项处理。

### 24.3 为什么这很贵

1. **写放大**：一轮约 6760 行写入 SQLite；日志显示这类轮次间隔只有十几秒甚至同秒多轮
   （08:44:16 / 08:44:33 / 08:44:41）。这正是数据库体积与 WAL 持续增长的一个来源。
2. **O(manifest) 开销每轮都付**：`DetectMissing` 要对全部 6762 条 manifest 路径做判定，
   而其中绝大部分在提示轮里**根本没被观测**，无法得出结论。
3. **可观测性被污染**：`unresolved=6666` 这个数看起来像"6666 个文件有问题"，
   实际是"6666 个文件本轮没被问到"。

### 24.4 语义问题（比性能更重要）

提示驱动轮**在原理上**无法对未观测路径下任何结论（§22 已把这点写进原因串）。
既然如此，把它们记成 "the round reached no conclusion for this path" 的**失败重试**
就是把"没问到"伪装成"问失败了"。

真正的修法方向（下一轮做）：

- 提示驱动轮**不**为"未观测路径"写重试记录；它们本就该保留上一轮的状态
- 或至少用**不同类别**记录（如 `NotObservedThisRound`），使重试表只反映真实失败
- 同时给 "Python not available" 这类**环境性不可恢复**的失败加放弃/降级条件
  （Attempts=599 说明现在没有上限）

### 24.5 本轮未做（明确边界）

- 没有改代码：24.4 会改变重试表的写入语义，必须连带改测试 + 变异取红，不能顺手改。
- 没有清表：存量 6756 条 `Attempts=1` 的记录在语义修复后会自然不再产生；
  先删掉它们等于把"每轮都在写"这件事藏起来。

## 27. 补上 extract-requested / extract-failed 两个计数（`df51ada`）

### 27.1 补的是什么

维护摘要日志现在报五个提取相关事实：

```

  {ExtractFailed} extract-failed, {Extract} extracted, {Rebind} rebound,
```

### 37.2 由此排掉的方向

| 假设 | 判决 |
|---|---|
| **托管代码在算哈希**（我在 §34 之后起的怀疑） | ❌ **排除**。SHA256 是纯托管/原生计算，会记在 User Time；实测 User 仅 8–13% |
| **GC 压力** | ❌ 排除。GC 也是 User Time；且 Private Bytes 六区间稳定在 1.298–1.299 GB，无抖动、无增长 |
| 读入的数据被累积/缓存 | ❌ 排除。内存不涨 ⇒ 读完即弃 |

### 37.3 仍然成立的推论

`Privileged ≈ 85%` 意味着 CPU 主要消耗在**用户态→内核态切换与 IO 系统调用路径**上。

与 §34 的形态**互相印证**：`4096 字节 × 约 20 万次/秒`。
每秒 20 万次 4KB `ReadFile`，单核被系统调用开销吃掉 —— **这正是 85% Privileged 应有的样子**。

所以现在的结论比 §34 更紧一格：

> 不是"某处在算"，而是"某处在以 4KB 粒度疯狂发读请求"。
> 每秒 20 万次系统调用，数据读完即弃，不累积。

### 37.4 仍然不知道的

**哪个 handle、哪个文件、哪段代码。** 这一层必须有 ETW/procmon 才能拿到，
本机三者皆缺（§34.3 已记录），`dotnet-trace`/`dotnet-counters` 也未安装。

**另需说明**：曾想用运行时开关做二分（停一个组件看读量变化，避免重启），
查到 `SystemCommandsController` 只是聊天斜杠命令、`RuntimeDiagnosticsController` 为只读诊断，
**没有可用于启停后台组件的运行时接缝**。二分只能靠重启，故本轮不做。

### 37.5 一个副产物：`% User Time` 可以当"是不是业务计算"的判别器

这条对以后有用：任何"CPU 高但不知道在干什么"的场合，
先看 `% Privileged` vs `% User`，一次采样就能把「IO/内核开销」与「应用计算」分开，

### 41.2 本轮排除的三个方向

| 方向 | 依据 |
|---|---|
| **四处 `conversation_events` 查询无界** | `ConversationOpenQueryService.ReadProcessCandidatesAsync` 有 `LIMIT $scanLimit`；`ConversationEventStore.ReadForwardAsync/ReadBackwardAsync` 有 `LIMIT @limit`（批量 256）。**都是分页设计** |
| **SSE 重连风暴** | `SessionEventStreamService` 注释明写"以前每批重读导致 reconnect 读整个会话索引"，**已修**（replay 上界冻结一次）；日志里 replay/reconnect 匹配极少 |
| **上下文组装读会话历史** | 全天 17 次 `Context assembled`：P50=20ms，只有 2 次超过 3 秒（3141/3256ms），其余 17–21ms。**稀疏且平时很快** |

### 41.3 一条需要纠正的判断

`ConversationOpenQueryPerformanceGateTests` 断言「不得 `SCAN conversation_events`」。
但本轮发现：**走 `ix_ce_seq` 的 SEARCH 不算 SCAN，gate 不会拦**。
索引能加速**定位**，不能减少**必须读的页数** —— 一个"按会话取全部"的查询可以完全通过 gate，
却仍然遍历该会话的所有页。

这不构成本次 800 MB/s 的解释（查询都有 LIMIT），但**这个 gate 的覆盖面比它看起来窄**，

## 48. 定案：被高频读的是 `pudding_platform.db`（2026-10-28 16:50）

### 48.1 怎么破的：NTFS 最后访问时间

之前所有手段都只能回答"打开了什么"，不能回答"在读哪个"。这次换了一个角度：

```
fsutil behavior query disablelastaccess
  → DisableLastAccess = 2
```

值 `2` = **用户管理的 last-access 更新禁用、系统管理的启用**。
这是唯一仍会在读操作上更新 `LastAccessTime` 的配置。

30 秒窗口的前后对照（现象在场，读 820–969 MB/s）：

| 文件 | T0 access | T1 access | 判定 |
|---|---|---|---|
| **`pudding_platform.db`** | 08:50:27.937 | **08:50:57.955** | **ACCESS-MOVED（+30s，实时前进）** |
| `pudding_memory.db` | 08:50:11.506 | 08:50:11.506 | **no-change（原地不动）** |
| `code_index.db` | 08:48:56.619 | 08:48:56.619 | **no-change** |
| `pudding_platform.db-wal` | 08:50:27.762 | 08:50:57.946 | moved（但 write 也在动，不能据此判读） |
| `pudding_memory.db-wal` | 08:50:25.422 | 08:50:28.745 | 同上 |

**判据**：如果 `memory.db` 真被 21 万次/秒读，它的 `LastAccessTime` 不可能 30 秒内一动不动。
**`platform.db` 的 access 恰好前进了 30 秒——与采样窗口同步。**

⇒ **被高频读的是 `pudding_platform.db`。** 从"两个库之一"收敛到**确定的一个**。

### 48.2 这个探针的适用边界（必须先说清，否则会被误用）

- 只有 `DisableLastAccess=2` 时有效；若为 `1` 或 `3`，**一律无效**，那时"没动"什么都不能证明。
- NTFS 会**延迟**写 last-access。本机能观察到实时前进，说明这台机器的延迟足够短；
  **换一台机器可能观察不到，那种情况只能记 INCONCLUSIVE，不能记"没在读"**。
- `-wal` / `-shm` 的 access 变化会被**写**污染，单看它们无法区分读和写。
  **判读必须落在主库文件 `.db` 本身上。**

### 48.3 由此浮现的新假设：某个操作在遍历 freelist

`platform.db` 现在有 **5,367 MB 在 freelist 上（43.9%）**，约 **134 万页**。

而这个现象是：

```
每秒约 210,000 次 4 KiB 读  ≈  每秒 860 MB
134 万页 ÷ 21 万页/秒  ≈  6.4 秒遍历一遍 freelist
```

**数量级吻合得很整齐。** 一个反复遍历 freelist 链的操作，会表现为：
- 纯读（freelist 遍历不需要写）
- 4 KiB 页读（SQLite page_size = 4096）
- 内核态高（每页一次 `ReadFile`）
- 不写日志（SQLite 内部操作，不经过应用日志）
- 句柄稳定、内存不涨（读完即弃）

**这条目前是假设，不是结论。** 但它同时解释了三件事：为什么是 platform 而不是 memory
（platform 有 134 万空闲页，memory 只有 294 页）、为什么块大小恰好 4096、为什么写为 0。

### 48.4 一个可检验的预测——这让 VACUUM 变成一箭双雕

如果上面这条成立，那么 **VACUUM 把 freelist 清零之后，这个 900 MB/s 应当随之消失**。

⇒ **VACUUM 不再只是"省 5.24 GB"**，它可能**同时消掉这个持续读了十几分钟的 IO 风暴**。

**这是可以被证伪的**（做 VACUUM 后重测 `IO Read Bytes/sec`）：
- 若读量掉到 10 MB/s 量级 → 假设成立
- 若读完量不变 → 假设被否，回到"不知道哪个操作"的状态

**我不把它写成结论。** 写在这里，是为了下次做 VACUUM 时**一定要顺手验证它**。
