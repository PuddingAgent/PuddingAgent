# 2026-10-28 检索系统四目标落地计划

## 1. 目标（用户 2026-10-28 明示）

| # | 目标 | 可判定的验收口径 |
|---|---|---|
| G1 | 大量文件检索毫秒级 | 单次查询 P50 ≤ 50ms、P95 ≤ 200ms，且**不因目录深度/范围收窄而退化** |
| G2 | 增删改后 1s 内索引更新 | 文件落盘 → 索引可检索到该变更 ≤ 1000ms |
| G3 | 后台自动维护，失效索引不留存 | 源文件已删除的索引条目在 N 分钟内被清除；unresolved 不无限累积 |
| G4 | 低 CPU / 磁盘空间 / 读写 IO / 内存 | 空闲时 CPU ≈ 0；索引目录有上限与治理；查询常驻内存可控 |

## 2. 实测基线（2026-10-28，全部现场测得）

### 2.1 快的那一半：已经达标

| 路径 | 实测 | 证据来源 |
|---|---|---|
| 全文检索 `search_grep backend=index`（仓库根 scope） | **engineMs=6~9，totalMs=6~9** | 今日两次调用返回体 |
| 符号检索 `code_symbol_search` 快路径 | **19ms**（旧路径 950ms / 冷 4227ms） | `2026-10-23-符号检索提速覆盖索引两阶段.md` |
| 索引规模 | `code_index.db` **1.74 GB**；`CodeSymbols` 195,533 行 / 去重名 50,854 | 今日实测 + 10-23 文档 |

**结论：索引能答的部分确实是毫秒级。** G1 没有失效，是**覆盖面**不够。

### 2.2 慢的那一半：三个具体缺口

**缺口 A（直接影响 G1）：目录一收窄，索引就用不上。**

```
search_grep(backend=index, directory=<某子目录>)
→ DependencyWait: "scope '...\Services\StorageManagement' has no index yet"
```

原因在代码里：`LuceneSearchEngine.SearchAsync` 要求 `HasIndex(directoryPath)`，而索引是按**注册项目根**建的。没有任何「上溯到最近的有索引祖先 + 把子目录当过滤前缀」的解析。

**后果**：窄范围检索一律退回托管扫描，撞 2000 文件 / 64MB / 10s 上限。今日实测两次：`scanned 2000/2000 … limit_reason=max_enumerated_files`。

**缺口 B（不满足 G1 的默认路径）**：不带 `backend=index` 的默认调用走托管扫描 + Lucene 候选**预取**。候选预取那处用的是 `SearchAsync(query, directory ?? "", …, subDirectoryFilter: directory)` —— scope 传的是**空串**。

⚠️ **未验证**：`GetIndexDirectoryPath("")` 实际解析到什么尚未确认，因此「候选恒为空」只是**待证实假设**，不能当结论。但无论真假，它只影响**候选排序优先级**，不影响扫描覆盖（覆盖由托管扫描保证）—— 真正的问题是默认路径根本没走索引正文。

**缺口 C（G3 的直接证据）**：

```
index_freshness: state=idle, watcher_attached=true,
                 last_calibration_at_utc=2026-10-27T16:09:13Z,
                 unresolved_source_path_count=6739
```

`unresolved_source_path_count` 在代码里映射到 `SourceMaintenanceUnresolvedPathCount = result.RetryableFileCount`（`CodeIndexMaintenanceService.cs:818`），也就是**可重试但一直没成功的文件数**。6739 是个大数，性质尚未查清：可能是超出项目根、可能是扩展名不支持、可能是被锁或读取失败。

另外 stale 清理的机制是存在的（`CalibrateAsync` 会打 `swept {Swept} stale file(s) ({Unresolved} unresolved)`），**所以 G3 不是「没做」，是「unresolved 这一侧没有治理」**。

### 2.3 完全没测的

- **G2**：watcher 是挂着的（`watcher_attached=true`），但从文件落盘到可检索的实际延迟**没有任何数字**。
- **G4**：CPU / IO / 内存占用没有基线；只知道符号快路径把 `cache_size` 设成 128MB。

> 未测 ≠ 不达标。这一栏必须先补测量，再谈优化。

## 3. 工作项（按依赖排序）

### W1 索引 scope 上溯 + 子目录过滤（解决缺口 A）

- **做法**：在 index backend 里把请求目录上溯到最近的有索引祖先，把原始目录作为 `subDirectoryFilter` 传入（引擎已支持该参数，`LuceneSearchEngine.cs:125`）。
- **边界**：上溯不得越过工作区根；找不到任何有索引祖先时，保留现有 `DependencyWait` 文案（那是正确语义）。
- **可测性**：解析逻辑抽成纯函数（输入目录 + `Func<string,bool> hasIndex` → 输出 (indexRoot, subFilter)），用假谓词覆盖「自身有索引 / 祖先有索引 / 全无索引 / 大小写与尾斜杠」。
- **验收**：对 `Source/PuddingPlatform/Services/StorageManagement` 这类子目录执行 `backend=index` 检索，返回命中而非 DependencyWait，且 totalMs ≤ 200ms。

### W2 默认路径接入索引（解决缺口 B）

- 先修候选预取的 scope 传参（`""` → 实际 scope），使候选真的产生。
- 再决定：默认是否在「有索引」时优先走 index backend。**这是产品决策**，需明确「索引可能滞后」是否可接受（滞后期间会漏掉刚改的内容 —— 与 G2 直接耦合）。
- **前置**：G2 有数字之后才能定默认策略，否则可能用「查不到最新内容」换「快」。

### W3 增量更新延迟实测（G2）

- 用探针：写一个临时文件 → 每 100ms 轮询索引可见性 → 记录延迟；再测「修改」「删除」两个动作。
- **验收**：三动作各 20 次采样，报告 P50/P95/最大值；若 P95 > 1000ms，定位是 watcher 防抖、批处理窗口还是重建触发。

### W4 unresolved 6739 的归因与治理（G3）

- 先分类：超出项目根 / 不支持扩展名 / 读取失败（锁、权限、编码）/ 元数据缺失。
- 再决定策略：可重试的设重试上限并降级为「已知跳过」；确实失效的进 stale 清扫。
- **禁止**：直接把计数清零或静默丢弃 —— 那是把缺陷藏起来。
- **验收**：给出分类计数表；`unresolved_source_path_count` 有明确解释与上限，不再无界增长。

### W5 资源基线（G4）

- 采空闲态与查询态两组：CPU%、工作集、索引目录 IO 读写、`code_index.db` 与索引目录体积变化率。
- **验收**：给出「空闲 / 单次查询 / 批量索引」三档的表；之后任何优化都要能对着这张表说清楚换来了什么。

## 4. 顺序与理由

```
W1 → W3 → W4 → W5 → W2
```

- **W1 先做**：纯增量收益，不依赖任何测量，且修的是「窄范围检索完全用不上索引」这个硬缺口。
- **W3 在 W2 之前**：默认策略取决于索引滞后有多严重。
- **W4 / W5 可并行**：一个治数据正确性，一个治资源，互不阻塞。

## 5. 已排除的方案（省得重复调研）

| 方案 | 结论 |
|---|---|
| 把符号名灌进 FTS5 trigram | 10-23 已实测：建表 219ms、临时库 8.2MB、任意子串 0ms。当前 5 万去重名 plain 表全扫已 0~4ms，**收益边际；符号数 >50 万再上** |
| 用 Lucene 做符号检索 | 已有三条防护测试（分词假阳性 / 零候选 / 语法字符）。符号搜索要结构化 + 子串，Lucene 的打分与分词是负担 |
| 向量检索替代关键词 | 符号名与精确文本检索**不需要**向量；向量只在语义召回场景有意义，与本轮四目标无关 |

## 6. 未验证 / 风险

- 本文所有数字都带时点；索引会随代码变更过期，**引用前先复核**。
- W1 的「上溯到祖先」可能让某些调用方拿到**本该报错**的结果（原先明确说「这里没索引」，改后返回祖先索引的过滤结果）。必须保留一条可分辨的说明，避免又把「没搜到」读成「不存在」。
- G2 若实测远差于 1s，可能需要改 watcher 策略，影响 IO —— 与 G4 直接冲突，届时要在计划里明确取舍。

## 7. W1 已落地（2026-10-28）

### 7.1 改动

- 新增 `IndexScopeResolver`（纯函数）：从请求目录向上找最近的有索引祖先，把请求目录转成**相对该祖先的相对路径**作为 `subDirectoryFilter`。
- `SearchGrepTool` 的 index backend 改为：先解析作用域 → 用祖先目录调用引擎 + 传子目录过滤 → 解析不到任何祖先时保持原 `DependencyWait` 语义（文案补上 "and neither does any ancestor within the workspace"）。
- 上溯边界为工作区根：边界外目录一律返回 null，**不允许借用工作区内的索引**（否则会产生假阳性召回）。

### 7.2 一个必须记下来的语义细节

引擎的子目录过滤是**相对作用域根的相对路径前缀**（`Path.GetRelativePath(directoryPath, path)` 后前缀比较），
所以解析结果必须给相对路径——给绝对路径会静默零命中。

另：`IndexRoot` 保留请求侧写法（`Path.GetFullPath` 不做盘上大小写归一）。这**不是缺陷**：
引擎用 `FullTextIndexPaths.NormalizeCorpusRoot`（`ToUpperInvariant` 后再 SHA256）定位索引目录，大小写不敏感。
我第一版测试就在这里断言过严而失败，已改为大小写不敏感比较，并把依据写进代码注释。

### 7.3 验证（原始输出 `temp/mutation-w1.txt`）

突变    if (hasIndex(candidate)) → if (hasIndex(requested))   // 取消上溯

### 7.4 尚未验证

- **真实索引上的端到端效果未测**：需要重启后对 `Source/PuddingPlatform/Services/StorageManagement`
  这类子目录跑一次 `backend=index`，确认从 `DependencyWait` 变成命中且 totalMs ≤ 200ms。
  在此之前不能说 G1 的「窄范围」缺口已经关闭。
- 默认路径（不带 backend）的缺口 B 仍未动，属于 W2。

## 8. W3 结论：G2 不是「慢」，是**默认关闭**（2026-10-28 实测）

### 8.1 仪器

索引目录按冻结规则推导（`NormalizeCorpusRoot` → `ToUpperInvariant` → SHA256）后定位到：

```
D:\Data\fulltext-index\f09e86e043ae76b0bc025ef00ed4dd5328fb947dded2a1c8f73db8e3181dbf78
基线 stamp: files=15 bytes=152,395,080 mtimeUtc=2026-10-27T15:55:15Z
```

观测点：在已索引的 `Docs/` 下新建 `.md` 文件，每 50ms 轮询索引目录 `(文件数, 总字节, 最新 mtime)`，
任一变化即判定「已提交」，超过 20s 判超时。脚本：`temp/g2-latency.ps1`，输出 `temp/g2-latency.txt`。

### 8.2 结果

```
SAMPLES=5 WITHIN_20S=0 TIMEOUT=5
SAMPLE 1..5 deltaMs=-1
```

**5 次全部在 20 秒内没有任何提交**——不是「超过 1 秒」，是**一次都没有**。

旁证：`search_grep` 返回的 `indexAge` 在今天多次调用中单调增长（24.2m → 55.7m → 58.3m），
而这段时间我改过多个源文件并提交过 6 次；`lastIndexed` 始终停在 `2026-10-27T15:54:23Z`。

### 8.3 根因

`MaintenanceOptions.Enabled` 的**声明默认值就是 false**，且文档注释写明「默认值 = 关闭，关闭状态零副作用」
（`MaintenanceOptions.cs:32`、`:107`）。

也就是说：watcher / 三源折叠 / 增量 commit 这一整套机制**代码是完整的**，但**默认不启动**。
没有配置显式开启时，全文索引只在显式 build 时更新，之后一直冻结。

宿主侧的状态探针其实早就在如实报告这件事：`FullTextIndexStatusProbe.ObserveMaintenance()`
在配置节缺失时返回 `Enabled = new MaintenanceOptions().Enabled`，即 `false`
（`FullTextIndexStatusProbe.cs:242-260`）。**我此前没有查它，这是本次诊断的疏漏。**

### 8.4 因此 G2 的验收要改口径

原先计划写的是「测文件落盘 → 可检索延迟，P95 ≤ 1000ms」。现在必须拆成两步：

1. **先确认它有没有在跑**（读状态探针的 `maintenance.enabled`，或看索引目录是否随改动推进）
2. 只有在跑的前提下，才谈延迟数字

把「没跑」当成「慢」去优化，会优化一个根本没执行的路径。

### 8.5 下一步（需要一次部署窗口）

开启增量维护的配置路径：

```
{FullTextIndexSupplyOptions.SectionName}:Maintenance:Enabled = true
```

（`SectionName` 的常量值以 `PuddingHost/Services/FullTextIndexStatusProbe.cs:244` 为准，
本轮未逐字确认，下一轮核对后再写死到文档，避免又出现「文档里的路径是陈旧投影」。）

开启后必须重测：① 三动作（新增/修改/删除）延迟；② 空闲 CPU 与索引目录 IO —— 这正是 G4 的代价项。
**「开启」与「G4 低占用」是有张力的**，届时要在同一张表里同时给出延迟与开销，而不是只报一个。

### 8.6 本轮明确不做

- **不擅自开这个开关**：它会在用户机器上引入持续的文件监听与后台 IO，且需要重启才生效（破坏性）。
  这是产品取舍，不是我能单方面决定的。
- 不改默认值：把默认从 false 翻成 true 是生产行为变更，且会与既有「关闭状态零副作用」的承诺冲突。

`D:\Data\config\system.json` 里 `FullTextIndex` 顶层节**是存在的且 Enabled=true**：

### 9.2 已补上的配置

```json
"Maintenance": {
  "Enabled": true,
  "Scopes": ["D:\\CodeProject\\PuddingAgent\\PuddingAgent"],
  "WorkspaceRoot": "D:\\CodeProject\\PuddingAgent",
  "IndexRootDirectory": "D:\\Data\\fulltext-index",

```

**唯一偏离默认值的项是 `MaxCoalesceWait`：2s → 1s。** 理由：G2 要求「持续写入时也不超过 1s」，
而默认 2s 在持续写入下会超出口径。其余保持声明默认，因为它们本来就是按低占用调的：
体检 24h 一次、每轮只切 64 个文件、切片间休 250ms、CPU >35% 或磁盘 >20% 就退避 30s、
内容缓存关闭。

`IndexRootDirectory` 填的是**实测发现的现场值**（第 8.1 节推导出的 `D:\Data\fulltext-index` 的父目录），
不是从文档抄的。

`ed2bfcb` 索引上溯、以及本次配置）。**这是一个需要用户点头的动作**，不是我单方面能决定的。

## 10. W4：unresolved 6739 的归因（2026-10-28，只读实测）

### 10.1 先纠正一个预设

计划里把 G3 写成「失效索引条目留存」。实测**这个方向目前是干净的**：

```
CodeFiles 行数 = 5586
逐条 Test-Path 检查 → FILES_MISSING_ON_DISK = 0
```

索引里没有任何指向已删除文件的条目。**G3 的真实问题在另一侧：失败重试表。**

### 10.2 重试表现状

| 指标 | 值 |
|---|---|
| `CodeIndexMaintenanceRetries` 行数 | **11,624** |
| 主因 `the round reached no conclusion for this path` | **6,928** |
| `file disappeared: …` | **4,683** |
| 其中路径形如 `*.tmpdir`（构建/原子写临时目录） | **2,261** |
| `MAX(Attempts)` | **585** |
| 最老 `FirstFailedAtUtc` | **2026-10-06**（21 天前） |
| 重试路径中**文件仍存在**的 | **6,940**（占 11,624 的 60%） |
| `CodeSourceManifest` 中 `Complete = 0` | **0**（清单本身完整） |

关键对比：**6,940 条重试指向的文件都还在**。所以这不是「失效条目」，是「**反复失败、不收敛**」。

### 10.3 机制：根因被后一次覆盖

阅读 `CodeSourceUpdatePlanner` 与 `CodeSourceMaintenanceCoordinator`：

1. 路径首次失败 → `ledger.RecordFailure(path, 真实原因, now)` 进入退避表
2. 后续每轮：`retry.Contains(path)` 为真 → 计划项被标 `RetryLater`（`CodeSourceUpdateReasons.RetryBackoffActive`）
3. 协调器对 `RetryLater` 项再次 `RecordFailure(path, "the round reached no conclusion for this path", now)`

**`RecordFailure` 是覆盖写。** 于是第一次的真实失败原因被这句症状覆盖掉，
表里 6,928 条全是同一句话 —— **你无法据此归因**。这是本次最值得修的一点（见 10.4 F1）。

`MAX_ATTEMPTS = 585` 还说明：协调器里那条「已在待办里的路径不重复记（否则每次都会把下次尝试往后推）」
的保护对部分路径**没有生效**，它们被反复重记。

### 10.4 处置清单（按优先级）

| # | 问题 | 处置 | 为什么这个顺序 |
|---|---|---|---|
| **F1** | 首次失败原因被覆盖，无法归因 | `RecordFailure` 保留首次原因（`FirstReason`）另存最近一次；或改为「同路径只记首次 + 更新计数」 | 不先修它，后面所有归因都是在猜 |
| **F2** | `*.tmpdir` 等瞬时路径被当源文件（2,261 条） | 索引输入排除构建/原子写临时目录 | 纯噪音，且是确定性不会成功的重试 |
| **F3** | 重试表无 TTL/上限，21 天无界累积 | 加保留策略（如 30 天或行数上限）+ 计数上报 | 与刚开启的存储自动清理同源问题：有机制、没兜底 |
| **F4** | 最初失败原因未知 | 修完 F1 后再采一轮才有可靠数据 | 顺序不能颠倒 |

### 10.5 本轮明确没做

- **没有改任何代码**：F1 涉及写入语义变更，必须连带改测试并做变异取红；

  「这些文件其实没被索引」这件事一并藏起来。清理必须建立在 F1 的归因之上。
