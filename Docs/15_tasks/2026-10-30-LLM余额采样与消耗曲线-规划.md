**3．Q1—Q8 裁决**

| 问题 | 推荐、理由与代价 |
|---|---|
| **Q1：采样归属** | 采样编排进入现有 `PuddingLlmUsage`，通过端口访问 probe、目标目录和存储；Host 用薄 `BackgroundService` 驱动。新增 Storage 工程，使用 `<DataRoot>/databases/llm_usage.db`。这样采样可独立测试，存储故障也不会争用约 12 GB 平台库的写锁。代价是增加一个数据库文件及其备份职责 |
| **Q2：时钟与容错** | 使用 `BackgroundService + PeriodicTimer + TimeProvider`，默认十分钟；不用 Agent 心跳，也不引入 Quartz。启动时采一次当前余额，随后对齐 UTC 十分钟边界；休眠恢复只采当前点，不补造历史余额。代价是离线区间无法恢复真实消费，必须展示缺口 |
| **Q3：数据模型** | 分别保存 provider 级采样尝试和币种级观测。失败也有尝试记录，金额未知为 `null`。充值、退款、赠送或调整造成的净上升统一展示“余额净入账/调整”，不推导真实充值额或该区间消费 |
| **Q4：保留策略** | 首版保留全部原始记录，不自动降采样、不自动删除、不建立归档系统。单 provider、单币种每年约 52,560 次采样，先保留可追溯事实。代价是数据库持续增长；超过下述阈值再评估归档 |
| **Q5：曲线实现** | 沿用现有 SVG 技术路线，增加专用余额曲线组件，复用 Token 页的交互模式，不抽取整个统计页为通用图表框架。无需新增依赖，离线构建风险低；代价是自行维护断线、标记、tooltip 和键盘交互 |
| **Q6：工具薄壳** | 在 Runtime 内抽取保留原始字符串的查询服务，让工具和 probe 共用配置解析、HTTP 与响应解析。工具只负责参数默认值、执行结果映射和现有 JSON 回执；probe 负责 decimal 观测映射 |
| **Q7：是否让工具注入 probe** | **不建议。** probe 缺少工具所需的 `host`、`isAvailable`、`note` 及原始金额格式，无法无损恢复回执。工具应注入原始查询服务，采样器才注入 `ILlmBalanceProbe`。代价是保留两个用途不同的输出模型 |
| **Q8：部署边界** | 最多安排两次部署：第一次完整后端链路，第二次前端静态产物及必要修正。所有组件测试、组合验证和前端构建先离线完成；真实加载及生命周期结论留给外部控制器 |

`PeriodicTimer` 会合并未消费的 tick，因此不能把 tick 数当作成功采样次数，也不能在恢复后循环补发历史请求；应按当前 UTC 槽位和实际观测时间判定。[Microsoft 文档](https://learn.microsoft.com/en-us/dotnet/api/system.threading.periodictimer.waitfornexttickasync?view=net-10.0)

“工具保持原路径、只有采样器用 probe”可以作为短期过渡，而且当前 HTTP/解析逻辑已经共用，**不会因此自动重复请求**。它的实际代价是服务代码继续调用工具类的静态成员，配置读取与错误映射仍有重复，后续修改工具容易影响后台采样。建议在第一次部署前完成同程序集内的有限抽取，不新增余额查询组件工程。

保留现有工具静态测试入口为薄转发，原五条测试保持原样；不改变工具 ID、参数名、回执字段、字符串类型、默认 provider 和金额格式。

**4．采样运行规则**

- 默认启用目标为明确配置的 `deepseek`，不因配置存在五个 provider 就向全部 provider 请求 `/user/balance`。不支持的目标记录明确状态。
- 配置采用 `<DataRoot>/config/llm.balance-sampling.json`，保存启用状态、provider 列表和采样参数；不保存凭据。凭据继续走既有解析路径。
- 每轮串行查询目标；单 provider 默认二十秒超时，不立即重试。后台采样的互斥不阻塞手动余额工具。
- HTTP 前先持久化 `Started` 尝试，完成后在一个事务中写入观测并结束尝试。失败写 `Error`；部分币种失败写 `Partial`。
- 进程终止遗留的 `Started`，在下一次启动确认属于旧运行实例后标为 `Interrupted`，不重新冒充历史采样。
- 超时与宿主退出分开处理：超时是失败观测；宿主退出取消是中断。补测当前 probe 尚未覆盖的超时、取消、配置访问异常。
- 初始化、数据库打开和上游请求都在后台执行。采样故障不使 Core readiness 失败，不调整全局后台服务异常策略。
- 只写经过分类的错误码及安全说明，不持久化上游响应正文、认证头、原始配置或完整异常文本。

若数据库本身不可写，就无法保证向该数据库写入 `Error`。此时停止本轮外部查询，暴露采样服务 `degraded` 状态并记录脱敏诊断；恢复后保留时间缺口，不伪造过去的余额。

**5．数据模型**

建议使用 SQLite 参数化 SQL，直接复用已有缓存的两个 SQLite 包，不引入 EF Design 或平台工程依赖。

```sql
PRAGMA foreign_keys = ON;
PRAGMA journal_mode = WAL;

CREATE TABLE llm_balance_attempts (
    sample_id              TEXT PRIMARY KEY,
    process_run_id         TEXT NOT NULL,
    provider_id            TEXT NOT NULL,
    scheduled_slot_utc_ms  INTEGER NOT NULL,
    started_at_utc_ms      INTEGER NOT NULL,
    completed_at_utc_ms    INTEGER,
    status                 TEXT NOT NULL
        CHECK (status IN
            ('Started','Succeeded','Partial','Error','Interrupted')),
    error_code             TEXT,
    error_message          TEXT,

    UNIQUE (provider_id, scheduled_slot_utc_ms),

    CHECK (
        (status = 'Started' AND completed_at_utc_ms IS NULL)
        OR
        (status <> 'Started' AND completed_at_utc_ms IS NOT NULL)
    ),
    CHECK (
        status NOT IN ('Error','Interrupted')
        OR error_code IS NOT NULL
    )
);

CREATE INDEX ix_balance_attempts_provider_time
    ON llm_balance_attempts(provider_id, started_at_utc_ms);

CREATE TABLE llm_balance_observations (
    sample_id              TEXT NOT NULL,
    currency               TEXT NOT NULL,
    observed_at_utc_ms      INTEGER NOT NULL,
    succeeded              INTEGER NOT NULL CHECK (succeeded IN (0,1)),
    total_balance          TEXT,
    granted_balance        TEXT,
    topped_up_balance      TEXT,
    error_code             TEXT,
    error_message          TEXT,

    PRIMARY KEY (sample_id, currency),
    FOREIGN KEY (sample_id)
        REFERENCES llm_balance_attempts(sample_id),

    CHECK (
        (succeeded = 1
            AND total_balance IS NOT NULL
            AND error_code IS NULL)
        OR
        (succeeded = 0
            AND total_balance IS NULL
            AND granted_balance IS NULL
            AND topped_up_balance IS NULL
            AND error_code IS NOT NULL)
    ),
    CHECK (total_balance IS NULL OR typeof(total_balance) = 'text'),
    CHECK (granted_balance IS NULL OR typeof(granted_balance) = 'text'),
    CHECK (topped_up_balance IS NULL OR typeof(topped_up_balance) = 'text')
);

CREATE INDEX ix_balance_observations_currency_time
    ON llm_balance_observations(
        currency, observed_at_utc_ms, sample_id
    );
```

金额规则：

- 内存使用 `decimal`；SQLite 使用 `InvariantCulture` 的十进制 `TEXT`，不使用 `REAL`、`double` 转换或 SQL 浮点聚合。
- 写入时不按“分”舍入，不丢弃上游精度；读回时验证可解析为 decimal。
- 汇总后才舍入：金额展示默认两位，速率沿用现有四位，使用 `MidpointRounding.AwayFromZero`；tooltip 保留原精度。
- 新历史 API 的金额返回字符串。前端只将数值转换用于像素坐标，不重新计算消费金额或速率。
- `grantedBalance`、`toppedUpBalance` 是余额组成，**不是累计赠送或累计充值流水**。
- `isAvailable=false` 与“没有读到余额”分开：有效余额仍是有效观测，不据此伪造失败或零余额。

SQLite 的 `NUMERIC` 亲和性可能转换输入类型，因此不能仅声明 `DECIMAL` 就假定金额会保持十进制精确存储。[SQLite 类型说明](https://www.sqlite.org/datatype3.html)

**失败跨币种的处理是必要门禁：**现有 probe 的网络失败通常返回 `currency="unknown"`。不能直接按币种分组后丢弃它，否则 CNY 序列可能跨过失败点继续差分。

查询服务应读取 provider 级尝试，为请求的币种构建分析序列：

- 有该币种观测：使用真实观测。
- provider 查询失败、中断：生成该币种的失败投影。
- 请求成功但该币种缺失：生成 `CurrencyNotReturned` 失败投影。
- `unknown` 或 `?` 不成为可计费币种曲线。

投影只用于表达失败，不创造余额数值。

首版无限期保留原始数据。满足任一条件再评估归档：观测超过一百万条、数据库主文件超过 256 MiB，或目标机器七日窗口查询优化后仍持续超过 300 ms。达到阈值只触发评估，不自动删除历史。

**6．消耗率与缺口算法**

沿用现有 `LlmUsageAnalyzer`，新增外围的失败投影与覆盖信息，不在 API 或前端复制判定逻辑。

```text
读取指定 provider 的窗口内采样尝试及币种观测
另读窗口前后邻点，用于识别边界；不按比例分摊跨边界消费

对每个请求币种：
    将 provider 级失败、中断、币种缺失映射为 Failure
    以实际 ObservedAtUtc 排序
    intervals = LlmUsageAnalyzer.Analyze(sequence, 默认选项)

    # 既有判定顺序保持：
    任一端点失败：
        Kind = Unavailable；Consumption = null
    否则间隔 > 30 分钟：
        Kind = Gap；Consumption = null
    否则余额上升：
        Kind = Recharge；Consumption = null
    否则余额持平：
        Kind = NoChange；Consumption = 0
    否则：
        Kind = Consumption；Consumption = 前余额 - 后余额

    summaries = LlmUsageAnalyzer.Summarize(
        intervals, fromUtc, toUtc
    )

    消耗合计 = 可判定区间消费之和
    平均速率 = 消耗合计 / 可判定时长
    无可判定区间：
        合计与速率均为 null
    单区间时长为零：
        不计算单区间速率

    返回：
        原始快照、区间类型、汇总
        可判定时长 / 窗口时长
        失败次数、缺失槽位、最后成功时间、边界排除信息
```

具体展示约定：

- 充值区间不产生负消费，也不以零消费代替未知。
- 休眠、停机不补采；恢复后采当前真实余额。
- 漏一两个槽位但间隔未超过三十分钟时，保留既有分析结果，同时标记漏采；不画成连续、完整采样的实线。
- 超过三十分钟、失败点及币种缺失处断线。尾部未采样时间不延伸为水平线。
- 不同 provider、不同币种不相减、不合并金额。
- 存储与 API 使用 UTC；页面明确使用 GMT+8。页面日期边界先带 `+08:00` 转 UTC，再请求。
- `100 → 98 → 148 → 147`，每点相隔十分钟：净消耗估计合计 `3`、可判定时长二十分钟、平均 `9/小时`；中间净上升 `50` 的区间消费未知。

余额快照仍无法发现“区间内充值，同时消费，最终余额下降”的情况。因此页面应称为**“余额差分净消耗估计”**，不能称为供应商精确账单。请求数、tokens、每请求价格和每百万 tokens 价格也不能从余额差分推导。

**8．最多两次部署**

| 阶段 | 部署前独立验证 | 部署及后续验收 |
|---|---|---|
| **第一次：完整后端** | 完成 S1—S4；原始查询服务抽取、存储、worker、API 均通过离线测试和实际组合根验证；真实 SQLite 文件位于 `temp/test-out/`；离线包恢复和构建通过；提交确定版本 | 交付 `ready-for-external-deploy`。外部控制器执行 `bootstrap_reboot`，`target=core`、`action=build-restart`、`frontendMode=skip`。按 requestId 等待 `healthy`，确认新构建、PID、路径及 DataRoot。新进程内会话再执行功能 smoke，至少观察四十分钟采样 |
| **第二次：前端及必要修正** | 使用第一阶段 API 契约完成 fixture 测试、类型检查、SVG 交互与构建；第一次 smoke 发现的必要修正先补测。前端版本递增，正式构建来自干净提交 | 再执行 Core `build-restart`，使用 Guardian 的 `frontendMode=build`，或 `load` 已验证的隔离静态产物。核对运行页面版本、哈希、构建时间，无 `+dirty`；验收历史连续性和真实页面 |

构建、测试、发布串行执行，产物放在仓库 `temp/build/`、`temp/test-out/`；不使用 `dev-up.py` 管理产品进程。

202 仅表示接单，`healthy` 才表示通过稳定观察；`rolled-back` 不算新版本交付成功。两次部署均不改变数据库 v1 格式，旧程序集回滚后可以忽略新增数据库文件。

进程内会话只报告 `in-product-functional-complete`；启动、重启、退出回收及恢复结论由外部控制器判定。生命周期故障注入只在隔离 DesktopHome、DataRoot 和包目录执行。若第二次仍失败，回滚并停止，不默认安排第三次部署。

**10．风险与取舍**

| 选择 | 放弃的能力 | 回头修改的条件 |
|---|---|---|
| 使用余额差分估计 | 精确账单、隐藏充值识别、请求和模型成本归因 | 需要财务对账或模型级成本时，接入供应商账单/交易流水 |
| 独立 SQLite 文件 | 与平台库的统一事务和单文件备份 | 确实出现跨库一致性需求，或现有备份体系无法覆盖新增文件 |
| 保留两个查询输出模型 | 单一 DTO 覆盖工具与采样 | 工具契约允许正式升级，或出现多个相同原始协议消费者 |
| 暂不合并 Platform 余额链路 | 全仓唯一余额实现 | 本功能稳定后，单独处理凭据语义、`/v1` 路径及错误行为差异 |
| 原始记录长期保留 | 自动归档和长周期预聚合 | 达到容量、行数或查询延迟阈值 |
| 以 providerId 标识历史账户 | 自动识别更换账户 | 同一 providerId 要切换计费账户时，先新增账户序列标识；不能直接拼接旧历史 |

**11．不建议做的事**

- 不把采样挂到 Agent 心跳、对话请求、工具调用或浏览器轮询上。
- 不用当前余额补填离线期间，不线性插值伪造历史消费。
- 不让工具通过 decimal probe 重建原始回执。
- 不向所有 provider 盲发 DeepSeek 余额请求。
- 不把赠送/充值余额组成当作累计充值流水。
- 不把充值、缺口、失败或未覆盖时间计为零消费。
- 不合计不同币种，也不默认不同 provider 代表不同计费账户。
- 不新增 Quartz、通用图表框架、后台事件总线或时序数据库。
- 不把本次功能塞进平台大库，不改动平台存量数据来验证。
- 不仅凭编译成功、HTTP 202、旧页面可用或进程内自测宣告部署完成。
