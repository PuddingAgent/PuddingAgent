# G4 归因 · Codex 问询稿

> **状态：未调用。** 本文件按《任务书编写规范》与「好问题胜过好答案」原则组织。
> 调用前须确认成本（一次真规划按几万 tokens 估）。

## 0. 我要的答案形状（先说这个，避免回答跑偏）

**不要**「可能的原因有 A/B/C，建议逐一排查」。**要**：

1. 一个**判别性实验序列**：每一步给出「预期观测 → 若成立说明什么 / 若不成立排除什么」，且每步成本尽量低；
2. 明确指出**哪一步做完后就能定案**（不是无限排查）；
3. 若信息不足以下判断，**直接说缺哪个观测**，不要用推测填坑。

## 2. 已排除（不要重走）

- **`chat_execution_commands` 全表扫**：该表仅 4,806 行，`LIKE` 匹配 0 行，扫它产生不了 580 MiB/s。
- **活跃飞书流式投影**：窗口内一个都没有，尖峰照旧。
- **句柄泄漏**：同负载态 180 秒 Δ0。
- **`conversation_events` 缺 `command_id` 索引**：确认存在该缺陷并已修（`(command_id, sequence)` 索引已建，`EXPLAIN` 走索引，微基准 902×）；但它**不足以解释**本窗口——修完之后现象仍在。
- **粗相关**（热点秒是否落在某类日志标记 ±5 秒内）：46/100，但 233 个标记 × 10 秒已覆盖超过窗口长度，**基数饱和、无判别力**，不作为证据。

## 3. 三个候选假设（我需要你帮我判别，而不是补充更多候选）

- **H1 · 代码索引维护**：`CodeSourceScanService` / `RoslynCSharpIndexer` 反复打开 csproj（含 `external/` 与测试工程），读取全部源文件与被引用程序集 → 大量 4 KiB 随机读。
  - 支持：事实 6/7；栈里 `RandomAccess.ReadAtOffsetAsync` 占比最高。
  - 反证缺口：文件读与 DB 读在「进程 IO 计数」里混在一起，**没有按文件维度拆开**。
- **H2 · SQLite 页读**：虽本窗口 `SqliteDataReader` 栈占比仅 0.36%，但 mmap 路径可能不计入该栈，且 4 KiB 恰好等于 SQLite 页大小。
- **H3 · 两者叠加**：常态 60–90 MiB/s 由 H1 贡献，偶发尖峰由 H2 或 H2+H1 共同触发。

**关键判别难点**：`IO Read Bytes/sec` 是**进程级**计数，不含文件名。所以真正的问题不是"哪个假设对"，而是——

> **在不改代码、不重启宿主的前提下，用什么观测能把「文件读」与「DB 读」的量分开？**

## 4. 我已有的观测手段（请在此范围内设计实验）

| 手段 | 成本 | 限制 |
|---|---|---|
| `dotnet-counters` 进程级 IO | 极低 | 不区分文件 |
| `dotnet-trace` 栈采样 | 低 | 已采过一次，可再采但需重启采集器 |
| `probe-file-handles.ps1`（枚举进程句柄） | 低 | 需管理员 |
| 配置开关关闭代码索引维护后重采 | 低（改配置+重启） | 会扰动宿主的索引行为 |
| SQLite 只读探针（F# + Microsoft.Data.Sqlite） | 低 | 只能看 schema/计划，不含运行期读量 |
| ETW（Windows 文件 IO provider） | 中 | 需要提权与工具链，我这边未验证 |

## 5. 我倾向的第一步（请你评判而不是照做）

**关掉代码索引维护，重采同样 10 分钟**：

- 若 **尖峰与 60–90 MiB/s 常态同时消失** ⇒ H1（或 H1 主导）
- 若 **只有尖峰消失** ⇒ H3（叠加）
- 若 **两者都不变** ⇒ H1 证伪，转向 H2

风险：关闭期间索引不更新，可能影响检索质量；可事后重开。

## 6. 禁止项

- 不要给「加日志/加计数器」类需要改代码的方案作为第一步（要重启宿主，扰动大）。
- 不要输出长篇背景综述，我已给出事实。
- 不要给多个并行候选让我自己挑——**给一个有顺序的判别序列**。
