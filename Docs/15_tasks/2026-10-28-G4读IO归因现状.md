# G4 读 IO 归因现状（一页纸）

> 过程与每次实验的原始数字见 [检索系统四目标落地计划](2026-10-28-检索系统四目标落地计划.md) §34–§51。
> 本文只写结论、判据和下一步。

## 现象

宿主进程 `PuddingAgent` 会**间歇性发作**一段"4 KiB 页读风暴"：

| 量 | 值 |
|---|---|
| 读字节 | 820–955 MB/s |
| 读操作 | 166,888–243,396 次/秒 |
| 每次读 | **恰好 4096 字节**（无一例外） |
| 写 | 约 37 KB/s（读写比 ≈ 13,000 : 1） |
| CPU | 单核 90%+，其中**内核态 56–98%**、用户态 5–20% |
| 句柄数 | 稳定（40 秒内波动 0.25%） |
| 私有内存 | 稳定（3 分钟只变约 58 MB） |
| 物理磁盘读 | ≈ 0（全部命中系统文件缓存） |
| 持续 | 一次发作连续数分钟后**自行结束** |

**它是触发性的，不是常态**：16:14 测得 9.6 MB/s，16:28–16:32 测得 820–955 MB/s，17:34 又回到 13.4 MB/s。

## 已定案

**对象 = `D:\Data\databases\pudding_platform.db`**

判据：NTFS 最后访问时间（`fsutil behavior query disablelastaccess` = 2，系统管理的 last-access 更新启用）。
30 秒窗口内 `platform.db` 的 access 恰好前进 30 秒，而 `memory.db` 与 `code_index.db` **原地不动**。
如果 `memory.db` 真被 21 万次/秒读，它不可能一动不动。

> 探针边界：该手段仅在 `DisableLastAccess=2` 时有效；为 1 或 3 时一律无效；
> 且 NTFS 会延迟写 last-access，换一台机器观察不到时只能记 INCONCLUSIVE，**不能记"没在读"**。

## 已排除（每条都有数据或代码证据）

探针自身 · agent 工作轮次 · 代码索引写入 · 全文索引提交 · 日志刷盘 · 文件枚举 · mmap ·
CodeSymbols 全表扫描 · 计算哈希 · 托管 GC 及其各变体 · `StorageInventorySampler`
（`MAX(rowid)` + `LIMIT` 样本，代码注释明写"避免全表扫"）· 代码索引维护 ·
**所有分钟级以上周期服务**（即使每轮读 1 GB 也只有约 17 MB/s，量级不符）·
四处 `conversation_events` 查询（都有 `LIMIT`）· SSE 重连风暴 · 上下文组装（P50 = 20 ms）·
投影滞后（`lag=0`）· 反复 open/close（句柄 0.25%）· `dotnet build`（单变量实验否定）。

## 未定：库内是哪个操作

两个候选机理，**都带可证伪的判据**：

### 候选 A：freelist 遍历（当前最可疑）

`platform.db` 有 **5,367 MB / 约 134 万页在 freelist 上（43.9%）**，
而 `134 万页 ÷ 21 万页/秒 ≈ 6.4 秒遍历一遍` —— 数量级吻合。

一个反复遍历 freelist 的操作能同时解释：纯读、4 KiB 页读、内核态高、不写日志、句柄稳定、内存不涨；
也解释了为什么是 platform（134 万空闲页）而不是 memory（294 页）。

**判据**：把 freelist 清零后再测。读量掉到 10 MB/s 量级 ⇒ 成立；仍 900 MB/s ⇒ 否。

### 候选 B：某条按会话取全部事件的查询

`conversation_events` 有 3,694,012 行 / 2.96 GB，其中**当前会话占 2,386,870 行（64.6%）**。
若存在 `WHERE conversation_id = X ORDER BY sequence` 且不带 `LIMIT` 的查询，一次就是读约 1.9 GB。

**判据**：语句级统计里 `calls` 与耗时是否与发作时段吻合；换新会话后读量是否下降。

## 下一步（两条都能拿到答案）

1. **打开语句级统计探针**（已实现，默认关闭）：
   配置 `Diagnostics:SqlStatementMetrics:Enabled = true` → 每分钟日志输出 Top10 语句的
   `calls / avg / max / rows`。这直接给出候选 B 的答案，且不需要停机、不需要管理员。
2. **停机窗口做一次页回收**：`TestScripts/swap-compacted-platform-db.ps1`
   —— 回收 5,649.5 MB，**同时**验证候选 A（做完立刻重测读 IO）。
   操作手册见落地计划 §50。

## 附：定案与修复（2026-10-28 21:59）

> **本节取代上文「未定：库内是哪个操作」与「下一步」两节。** 上文保留原样作为过程记录。

### 结论

**元凶是 `conversation_events` 缺 `command_id` 索引**，而飞书流式投影 worker 用它过滤一张 370 万行的表：

| 位置 | 查询形状 |
|---|---|
| `FeishuStreamingProjectionWorker.ProjectContentAsync`（:338） | `command_id = ? AND type = ? AND sequence > ?` ORDER BY sequence LIMIT 100 |
| `FeishuStreamingProjectionWorker` initialEvents（:144） | `command_id = ? AND sequence > ?` ORDER BY sequence |

### 四条证据 + 一条正对照

1. **外部采样差异**（等长 22 秒热/静对照，186,947 / 167,748 样本）：
   `ProjectBatchAsync.MoveNext` 热 4.72% vs 静 0.15%；EF `ToListAsync` 6.96% vs 0.19%；
   `SqliteCommand.ExecuteReader` 5.92% vs 0.19%；`IOCompletionPoller.Poll` 占 12.63%。
2. **代码**：两处都用 `evt.CommandId` 过滤 `conversation_events`。
3. **索引**（`sqlite_master` 权威，共 11 个）：`conversation_id_sequence` / `conversation_id_message_id_sequence` /
   `conversation_id_turn_id_sequence` / `event_id` / `trace_id_seq` / `turn_id_type` / `committed_at`×2 —— **无 `command_id`**。
4. **EXPLAIN**：`CommandId` 形状 → `SCAN conversation_events` + `USE TEMP B-TREE FOR ORDER BY`。
   **正对照**：同样 `sequence > ?` 换成 `conversation_id` 过滤 → `SEARCH ... USING COVERING INDEX ix_ce_seq`。

**量级自洽**：全表扫 2.96 GB ÷ 实测周期约 3.8 s ≈ **780 MB/s** ≈ 观测 800 MiB/s。
（也说明每次查询约 3.7 s，`Task.Delay(100ms)` 叠在其后，实际约 0.26 次/秒而非 10 次/秒。）

### 为什么是「间歇性」

只有存在**活跃流式投影**（`projection.Status == Active`）时才走 `ProjectContentAsync`。
没有正在流式输出的飞书消息时，只扫 `chat_execution_commands`（**4,806 行**）→ 低读。
**这解释了今天下午所有安静窗口。**

### 修复（commit `9ac440c`）

补 `(command_id, sequence)` 索引，沿用 `ConversationReadModelSchema` 单一定义点模式，三处同步：
名称常量 + `ConversationEventLookupIndexes` 清单、Bootstrapper 的幂等 DDL、EF 模型声明。
测试断言从「2 条索引」升到「3 条」，并**新增 `Assert.IsFalse(TEMP B-TREE)`** —— 守索引**形状**而不只是**存在**。

三态证据：基线 5/5 通过 · 变异（`(command_id)` 去掉 `sequence`）4/5 通过、红在 TEMP B-TREE 断言 ·
还原后 SHA 位级一致并 `-t:Rebuild` 重编，5/5 通过。

### ⚠️ 部署后必须另做一步

`conversation_events` 的索引按设计**不在启动期创建**，由
`ConversationReadModelSchemaBootstrapper.EnsureConversationEventIndexesAsync` 在**显式维护窗口**执行。
⇒ **只部署重启不会消除这个现象**，必须在可观测窗口内跑一次该维护动作（3.7M 行建索引有耗时与磁盘成本）。

### 仍未解决

- **只覆盖了 22 秒发作**；用户描述的数分钟长发作没有采到，不宣称已覆盖。
- **轮询本身仍值得质疑**：100–300 ms 轮询一张 370 万行表，加索引后单次变快，但事件驱动才是结构性解法。
  这属于后续设计，不塞进本次修复。
- 共享库仍空闲 5,649.5 MB 待停机回收；`query_session_logs` 的 FTS 仍不可用。
