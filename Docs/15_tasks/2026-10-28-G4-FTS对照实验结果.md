# G4 对照实验：关闭全文索引维护后，稳态读 IO 消失

## 1. 实验设计

| 项 | 值 |
|---|---|
| 自变量 | `FullTextIndex:Maintenance:Enabled`：`true` → `false`（`D:\Data\config\system.json`） |
| 其余 | 同机、同产物（git HEAD `87bdd81`，宿主 PID 15796）、同采集方法 |
| 采集方法 | `Win32_PerfRawData_PerfProc_Process.IOReadBytesPersec` 累计值差分 ÷ 实际采样间隔，1 秒目标间隔 |
| 窗口 | 2026-10-28 23:45:13 – 23:55:05（537 样本，0 缺失） |
| 采集期纪律 | **禁止任何构建 / 测试 / 大规模文件操作**（见 §4 混杂因素） |

**开关生效已核实，不是假设**。宿主 23:44:07 重启后日志第一条相关记录：

```
2026-10-28 23:44:11.026 +08:00 [INF] [tag:FullTextIndexMaintenanceHostedService]
  [FullTextMaintenance] disabled (FullTextIndex:Maintenance:Enabled=false);
  no scope resolution, no watcher, no thread. Zero side effects.
```

## 2. 结果

| 指标 | FTS 开（22:44–22:54，外部采集） | FTS 关（23:45–23:55，本次） |
|---|---|---|
| READ min | 6.64 MiB/s | 5.88 MiB/s |
| READ avg | **29.76** MiB/s | **9.11** MiB/s |
| READ max | **580.85** MiB/s | **38.05** MiB/s |
| 秒数 ≥ 60 MiB/s | **100 / 600（16.7%）** | **0 / 537（0%）** |
| 秒数 ≥ 100 MiB/s | — | 0 |
| 秒数 ≥ 300 MiB/s | **7** | **0** |
| WRITE avg | 未采 | 0.00 MiB/s |

区间最大值 38.05 MiB/s 出现在 23:49:12，为孤立单点，其后即回落到 15–18 MiB/s 量级，**没有形成 60–90 MiB/s 的持续段**。

## 3. 判读

按预设三态判据：

> 安静段 60–90 MiB/s 消失 ⇒ FTS 定案

**判据命中（第一态）**：稳态持续段完全消失。

**结论：H1 成立 —— Lucene 全文索引维护（`FullTextIndexMaintenanceHostedService`）是持久读 IO 的主源。**

第 1 节已核实它是「零副作用关闭」（不解析 scope、不起 watcher、不起线程），因此该窗口里读 IO 的下降**不可能是关闭动作本身引起的测量偏差**。

## 4. 混杂变量（必须同时声明，否则是过度解读）

两个窗口**不是严格的单变量对照**：

1. **基线窗口有外部执行者活动**：22:44–22:54 期间外部采集者在跑 `dotnet-trace` 等工具；同期系统日志有 **233 次** `RoslynCSharpIndexer … Opening project`（平均 2.8 秒一次）。本次实验窗口内我禁跑了所有构建与测试。
2. **FTS 由文件变更驱动**（`Debounce=500ms`）：我自己的 `dotnet build` / `dotnet test` 会写仓库文件，从而**直接喂给 FTS**。这意味着基线窗口里有一部分读是我自己造成的。

**因此：**

- **稳态归因可定案**，因为它还有第二个独立证据：同一次采集内部的窗口切分（安静 60 秒 `PuddingFullTextIndex` 占 8.1%、`PuddingCodeIndex`/Roslyn 均 0.0%）。那是**同一窗口内部**的对比，不受两次采集之间外部活动差异的影响。两条方向一致的证据互相独立。
- **尖峰段的归因仍未定案**。580 MiB/s 的 7 秒尖峰在关闭 FTS 后确实没再出现，但基线窗口同时存在外部工具活动与 Roslyn 建索引——**无法区分「尖峰由 FTS 引起」还是「尖峰由外部活动引起」**。要定案需要第三个窗口：FTS 关闭 + 存在代码变更活动。

## 5. 关闭 FTS 后剩下的 9 MiB/s 是什么

`min 5.88 / avg 9.11 / max 38.05` —— 这部分是 FTS 关闭后的**基底读**，属于正常运行水平，**本次未归因**。候选：代码索引维护、日志轮转、业务读写。若要继续压缩，应另做一次按文件名的 ETW 采样。

## 6. 回滚

实验结束后已恢复 `system.json`（`system.json.bak-20261028-2343` 覆盖回去）并重启宿主加载 `Enabled=true`。**不允许把实验状态留在生产配置里。**

## 7. 对 G4「低资源占用」目标的意义

1. **最大稳定读源已定位到单一子系统**，且它有明确开关，可运维控制。
2. 需要单独评估、但**本次未评估**的三个问题：
   - `Debounce=500ms` 对一个大仓库是否过激（每次变更都可能触发重扫）
   - `Scopes` 是否需要收窄（当前是仓库根，含 `external\` 等第三方目录）
   - `RecoveryScanInterval=15min` / `HealthCheckInterval=1d` 的实际负载贡献
3. 量级：同一套采集方法下，`avg 29.76 → 9.11 MiB/s`（约 **3.3 倍**）；`≥60 MiB/s` 秒数占比 **16.7% → 0%**。

## 8. 与原现象的关系（避免夸大）

用户最初报告的是 **800 MiB/s**，那是**索引修复之前**的观测。本文的 29.76 是索引修复之后的基线。两者不可直接相减来归因；本文只主张「FTS 维护是修复后剩余持久读的主源」。
