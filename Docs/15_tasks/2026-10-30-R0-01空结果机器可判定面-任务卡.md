# R0-01 空结果机器可判定面

> 依据：`Docs/12_features/增强索引分阶段施工计划-2026-10-18.md` §1.1 工作包 R0-01（P0）。
> 实施前置：本卡只做止血切片，**不**接入向量、**不**迁公共合同、**不**动宿主接线。

## 1 规格原文（判据以此为准，不得自行改口径）

设计方案 §8.x 三处硬约束：

1. 「每次响应给出 `claim.kind=none|no_candidates|no_match_in_scope`；后者必须携带 scope/过滤、匹配规则、snapshot、exhaustive 证明，文案只能说"该范围/版本内无符合此规则的匹配"。`no_candidates` 表示未找到证据，不是无实现；`none` 表示执行/覆盖不足以形成否定。」
2. 空结果表：「自然语言 auto，仅词面执行，vector 未配置/未接线 ⇒ **partial / none**；`required_providers` 含 vector；已查词面、语义未查，不能排除相关实现。」
3. 「**所有 auto 零结果都禁止 AcceptAbsence**。`degraded=false` 只能描述已执行分支，不能替代 coverage/claim。即使旧 DTO 暂不能承载全部字段，止血切片也**必须添加机器可判定的已查/未查面及否定类型**，再迁入公共合同，**不只修改提示句**。」

R0-01 退出门禁四条：

- 中文概念 auto + 词面-only ⇒ 返回**缺 vector 的 partial**；
- semantic 健康零召回也**不能** `AcceptAbsence`；
- **完整精确零匹配的正对照成立**（防止实现靠"永远报 partial"蒙混）；
- 容器零边继续提示成员未展开（已由 `e358820` 交付，须保回归）。

## 2 现状（2026-10-30 实测，可复现）

```
workspace_search("签发符号引用的令牌", intent=auto)
  → totalCount 0 · emptyReason GenuinelyAbsent · nextStep AcceptAbsence
  → 只有文案写了「本端口只做词面匹配…不含语义召回」
```

`2547b95` 只改了 `DescribeAbsence` 的**提示句**，`RetrievalNextStep.Kind` 仍是 `AcceptAbsence`，
`RetrievalResult` 里没有任何"已查/未查面"字段 ⇒ 机器无法判定，违反 §1 第 3 条。

## 3 必须新增的机器可判定字段（止血切片最小集）

新增 `PuddingCodeIndex.Contracts.Retrieval` 下两个小类型：

```csharp
public enum RetrievalClaimKind { None = 0, NoCandidates = 1, NoMatchInScope = 2 }

public sealed record RetrievalClaim(
    RetrievalClaimKind Kind,
    IReadOnlyList<string> SearchedSurfaces,     // 本端口实际执行过的面
    IReadOnlyList<string> UnsearchedSurfaces,   // 已知存在但未执行的面（当前恒含 "vector"）
    IReadOnlyList<string> RequiredProviders);   // 形成确定性结论所需 provider（auto 含 vector）
```

`RetrievalResult` 增加可选 `Claim`：
- 构造不变量：`hits.Count == 0 ⇒ Claim != null`（与"0 命中必须有 reason"同级 fail-closed）；
- 有命中时 `Claim` 必须为 `null`（避免"有结果却声明否定面"的自相矛盾）。

## 4 判定规则（唯一实现，不得散落）

| 输入 | ClaimKind | 说明 |
|---|---|---|
| reason ∈ {NotIndexed, IndexCorrupted, LanguageUnsupported, IntentUnsupported, FilteredOut} | `None` | 执行/覆盖不足以形成否定 |
| reason = GenuinelyAbsent 且 `Intent == Auto` | `None` | §1 第 3 条：auto 一律禁止否定 |
| reason = GenuinelyAbsent 且 `Anchor != null`（关系面，已证穷尽该锚点范围） | `NoMatchInScope` | **正对照**：此路必须仍能给出限定范围结论 |
| reason = GenuinelyAbsent、非 auto、非锚点 | `NoCandidates` | 未找到证据 ≠ 无实现 |

`SearchedSurfaces` 由实际执行面决定：词面恒 `"lexical"`；关系意图且已展开成功再追加 `"relations"`。
`UnsearchedSurfaces` 当前恒为 `["vector"]` —— 因为 `IEmbeddingProvider` 在 Runtime/CodeIndex 零引用（实测）。

## 6 验收与变异取红（缺一不算完成）

| # | fixture | 期望 |
|---|---|---|
| 1 | 中文概念 `auto`（如「签发符号引用的令牌」） | `claim.kind=None`、`unsearched` 含 `vector`、nextStep **≠** AcceptAbsence |
| 2 | 标识符 `auto` 且确实无此符号（如 `SymbolRefIssuerZzz`） | `claim.kind=None`（auto 一律不否定） |
| 3 | **正对照**：容器/成员锚点 + `intent=callers` 且该范围零边 | `claim.kind=NoMatchInScope` + 限定范围措辞 |
| 4 | 过滤面导致零命中 | `claim.kind=None`（FilteredOut） |
| 5 | 容器锚点零边 | 仍提示成员未展开（`e358820` 回归） |

变异取红至少覆盖三项：① 跳过 vector 却把 `vector` 从 `unsearched` 去掉；② auto 仍返回 `AcceptAbsence`；
③ 把 `NoMatchInScope` 用于 auto（正对照失效）。要求：变异后恰好对应 fixture 红，还原后全绿。
