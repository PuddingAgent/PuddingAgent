## 2. 背景知识

### 2.1 已定案（不需要你重新判断）

- **根因**：`conversation_events`（约 370 万行 / 2.96 GB）**缺 `command_id` 索引**，
  飞书流式投影的两处查询按它过滤 ⇒ 全表扫 + 临时 B 树排序。
- **现象**：稳定约 **800 MiB/s**、21 万次/秒、每次恰好 4096 字节的逻辑读，内核态 CPU 56–98%。
- **已修复**：`(command_id, sequence)` 索引已在本机库创建（`CREATE INDEX` 用时 5.45 秒）。

### 2.2 已证明（不需要你重复测量）

- **查询计划改善**：`SCAN + TEMP B-TREE` → `SEARCH ... USING INDEX (command_id=? AND sequence>?)`。
- **微基准 902 倍**：同查询走索引 0.26 ms/次 vs 强制全表扫 235.09 ms/次。

### 2.3 还缺什么（这才是本次要采的）

**缺端到端证据。** 此前一次 120 秒监控显示 avg 16.76 MB/s、0 次超 300 MB/s —— **看起来完美，但当时没有活跃流式对话**，
也就是**触发条件根本不存在**。"没发作"不等于"修好了"。

### 2.4 已证伪 / 不必再走的方向

- ~~`chat_execution_commands` 全表扫~~：该表仅 4,806 行，`LIKE` 甚至匹配 0 行，扫它产生不了 800 MB/s。
- ~~SQL 语句统计~~：该采集层**尚未部署**，不必去找对应日志。
- ~~句柄泄漏~~：同负载态 180 秒 Δ0，已撤回该假设。

## 5. 需要解决的问题（一个原子问题）

> **在存在活跃飞书流式对话的前提下，宿主对 `pudding_platform.db` 的读 IO 是否已从 ~800 MiB/s 量级降到常态？**

### 5.1 要采的内容

| # | 内容 | 为什么需要 |
|---|---|---|
| 1 | **10 分钟逐秒 IO 时间线**：`IO Read Bytes/sec`、`IO Read Operations/sec`，另附内核/用户态 CPU | 直接回答"还有没有发作" |
| 2 | **必须覆盖至少一次完整流式对话** | 没有流式就没有触发条件 |
| 3 | 流式窗口内的**托管线程栈采样**（聚合后 top 30–50 + 百分比，文本形式） | 确认原路径是否仍在执行、有无新热点 |
| 4 | 同期逐秒 **GC 与线程池**指标（GC 时间占比、线程池队列长度、线程数） | 排除"IO 降了但 GC 恶化" |
| 5 | **元数据**：索引是否存在、PID 与启动时间、窗口起止、每次流式对话的起止时刻 | 让判读能对上时间轴 |

**「流式对话」的界定**：一次完整的、有可见增量输出的 AI 回复 ——
从用户消息被受理开始，到终态回复结束为止，**期间必须有中间内容逐段出现**（不是一次性给完整答复）。

### 5.2 三态判据（请在报告里明确给出命中哪一条）

| 判据 | 条件 | 结论 |
|---|---|---|
| **一 · 修复有效** | 流式窗口内逐秒 IO 读速率**始终 < 100 MB/s** | 修复生效 |
| **二 · 仍失效** | 流式窗口内出现 **≥ 300 MB/s 的连续段** | 修复未生效，需重新归因 |
| **三 · 无效窗口** | 10 分钟内**流式对话次数为 0** | **不可判读，必须重采** |

**若命中判据三，请如实写「窗口无效」，不要写「修复成功」。** 这是本次任务最容易犯的错。

### 5.3 两条额外观察（如果出现请单独写）

- IO 降了但托管栈里**仍频繁出现** `ProjectContentAsync` / `ToListAsync` —— 正常（查询还在跑但变快了），值得写进结论。
- IO 降了但**内核态 CPU 仍长期偏高** —— 请单独指出，可能是另一个问题。

## 6. 怎么交付

### 6.1 落盘位置

```
D:\Data\g4-verify\<yyyyMMdd-HHmmss>\
```

放在仓库工作树**之外**，便于随时清理。

### 6.2 必须包含的文件

| 文件 | 内容 | 是否必需 |
|---|---|---|
| `manifest.md` | 采集身份与时间、**索引是否存在**、PID 与启动时刻、**每次流式对话起止**、各文件窗口、**命中哪条判据**、**未做到的项目** | **必需** |
| `io-timeline.csv` | 逐秒 IO 读写字节数/操作数、内核与用户 CPU | **必需** |
| `stream-windows.md` | 每次流式对话的起止时刻，及该窗口内 IO 峰值/均值 | **必需** |
| `notes.md` | 采集过程、异常、工具版本、限制 | **必需** |
| `hot-stacks.md` | 流式窗口内托管栈聚合（top 30–50 + 占比） | 若采到则必需 |
| `counters.csv` | 逐秒 GC / 线程池 | 若采到则必需 |

### 6.3 格式要求

- 全部 UTF-8 文本；时间戳用**带时区的完整 ISO 8601**。
- IO 速率**同时给 `bytes/sec` 原值**（避免 MiB 换算歧义）。
- 栈采样给**聚合后**的文本表格，不要二进制或原始事件流。

### 6.4 完成后

在回复里给出 `manifest.md` 的**绝对路径**，并**逐字引用**你在 manifest 里写的「命中判据」那一行。

**判读由维护方做**，你只需把数据与客观事实交回。
