# G4 诊断数据采集任务书

> 执行者：外部 AI / 人工。目标是**一次采集就定案**，不要边采边猜。
> 采集侧的一切命令都可直接复制；判读由我（维护者）负责。

## 0. 一句话背景

宿主进程 `PuddingAgent` 会**间歇性**以 **4 KiB 粒度、约 21 万次/秒（820–955 MB/s）** 持续读
**`D:\Data\databases\pudding_platform.db`**，CPU 内核态占 56–98%，写 ≈ 37 KB/s，句柄与内存都稳定，
一次发作持续数分钟后**自行结束**。

**已确定**：读的是哪个文件（NTFS last-access 定案，三次独立复核）。
**未确定**：哪条 SQL、或哪段代码。**这就是本次采集要回答的唯一问题。**

如果采集数据不足以定案，也请如实交付"不够"，不要补猜——这比一份看起来完整的错结论有用。

## 1. 环境现状（已核实，2026-10-28）

| 项 | 状态 |
|---|---|
| 宿主进程 | `PuddingAgent`，PID 见现场（采集时用 `Get-Process PuddingAgent`） |
| dotnet SDK | 10.0.401 ✔ |
| `dotnet-trace` | **未安装** ← 任务 T1 需要先装 |
| `dotnet-counters` | **未安装** |
| `wpr` | `C:\Windows\System32\wpr.exe` ✔ 但**需要管理员** |
| `procmon` / `xperf` | 未安装 |
| 当前会话权限 | 非管理员（`elevated=False`）—— T1 **不需要**管理员 |

## 2. 关键约束：必须在"发作期"采集

现象是**触发性**的，会自行出现与消失。实测三个时点：16:14 → 9.6 MB/s；16:28–16:32 → 820–955 MB/s；
17:34 → 13.4 MB/s。**固定时长盲采几乎必然落在安静窗口，产不出任何有用信息。**

**判断是否正在发作**：

```powershell
typeperf "\Process(PuddingAgent)\IO Read Bytes/sec" -sc 5 -si 1
```

`> 300 MB/s` 即视为发作中。

**自动化方案（推荐）**：已备好的等待器，检测到发作才启动采集，否则一直等：

```powershell
# 先装一次工具（不需要管理员）
dotnet tool install --global dotnet-trace

# 然后挂着等：最多等 60 分钟；一旦 >300 MB/s 立即采 60 秒托管栈
pwsh -NoProfile -File TestScripts\collect-g4-on-anomaly.ps1 -MaxMinutes 60 -ThresholdMBps 300 -TraceSeconds 60
```

退出码：`0` 等到超时也没发作（**不要**记成"问题消失"）；`2` 工具缺失/宿主未运行；`3` **采到了**；`4` 采到但采集失败。

## 3. 三类数据，按优先级

### T1 · 托管热点栈（**必做，兜底**）

**解决什么**：哪段代码在消耗 CPU 并发起这些读。**即使问题根本不是 SQL，这一路也能定位。**

```powershell
dotnet tool install --global dotnet-trace        # 只需一次
dotnet-trace collect --process-id <PID> --profile cpu-sampling --duration 00:01:00 --output g4-cpu.nettrace
```

- **采样内容**：`--profile cpu-sampling` 自带托管采样剖析器（默认约 1 ms 采样一次）与运行时事件。
- **时长**：**60 秒**。若产物超过 500 MB，改 30 秒重采。
- **最少样本量**：希望覆盖**至少一次完整的发作**（发作通常持续数分钟，60 秒足够落在其中）。
- **不要**手工指定 provider GUID / 关键字位掩码 —— `--profile` 已经选对，手写容易漏。

**可选的补充（同一窗口内）**：

```powershell
dotnet-counters collect --process-id <PID> --refresh-interval 1 --duration 00:02:00 --counters System.Runtime --output g4-counters.csv
```

看 `% Time in GC`、`gc-heap-size`、`alloc-rate`、`threadpool-thread-count`、`monitor-lock-contention-count`。
**用途**：把"是不是 GC / 是不是线程池饥饿"变成一排数字，而不是靠我推断。

### T2 · 数据库语句统计（**必做，最可能直接定案**）

**解决什么**：哪条 SQL 被跑了几百万次。代码已实现，**默认关闭**，需要两步：

**第一步：部署**（把 `2bc24fc` / `8fa3d5d` / `94888e9` / `f36f857` / `aa844b5` 之后的镜像换上去；
宿主重启是破坏性操作，请按你们的发布流程执行）。

**第二步：打开开关**——在宿主的配置文件里加：

```json
"Diagnostics": {
  "SqlStatementMetrics": {
    "Enabled": true
  }
}
```

重启后，日志里**每分钟**会出现一段：

```
[SqlMetrics] window=since-start tracked=<N> overflowed=False total=<N>
  #1 calls=... avg=...ms max=...ms rows=unknown  SELECT ... FROM "conversation_events" WHERE ...
  #2 ...
```

**要交付的**：发作前后的**至少 3 分钟**这段日志原文（含时间戳），以及对应时间段的宿主日志窗口。

- 统计是**累计**的（`window=since-start`），不会自动清零，这正是我们要的。
- `rows=unknown` 表示查询类（回调时行数未知），**不是** 0。
- 若出现 `overflowed=True`，说明语句形状超过 512 种，请告知——那本身是个信号。

### T3 · 文件级 IO（**可选，仅在前面两路都不够时做**）

**解决什么**：确认读的就是 `platform.db`（我这边已定案，所以这一路属于复核，不是必需）。

需要**管理员** shell：

```
wpr -start FileIO -filemode
:: 等 30 秒，且这 30 秒必须落在发作期内
wpr -stop D:\Data\temp\g4-fileio.etl
```

- **产物常有数百 MB 到数 GB**，只上传 WPA 分析后的**文件热力摘要截图或导出表**，不要传 ETL 原文件。
- 用 Windows Performance Analyzer 打开，看 `File I/O` → `Read`，按 `FileName` 汇总。

**不要用** `NtQueryObject` 或自写句柄枚举去替代这一步 —— 那些只能回答"打开了什么"，不能回答"在读哪个"。

## 4. 交付清单

请按下面命名交回（`<stamp>` 用采集开始时刻 `yyyyMMdd-HHmmss`）：

| # | 文件 | 是否必需 |
|---|---|---|
| 1 | `g4-cpu-<stamp>.nettrace` | **必需**（T1） |
| 2 | `g4-counters.csv` | 有则更好（T1 补充） |
| 3 | 含 `[SqlMetrics]` 的日志片段（≥3 分钟） | **必需**（T2） |
| 4 | 同时间段的宿主日志窗口（system 日志目录） | 必需 |
| 5 | 采集时刻的 `typeperf` 五秒读数（证明落在发作期） | 必需 |
| 6 | `g4-fileio.etl` 的分析摘要（非原文件） | 可选（T3） |

**最重要的元数据**：每份文件都要注明**采集时刻（含时区）**。
宿主日志时间戳是 `+08:00`，终端时间可能是 UTC —— 请统一写清楚，否则对不上时间线就等于没采。

## 5. 我拿到之后会怎么判读

| 观察 | 结论 |
|---|---|
| `[SqlMetrics]` 里某条语句 `calls` 与发作强度同量级（每秒数万～数十万） | **定案到语句**，直接改那条查询 |
| `[SqlMetrics]` 全部语句加起来也远达不到 21 万次/秒 | 读**不是** SQL 发起的 ⇒ 转向 T1 栈样本找非 SQL 的 IO 源 |
| `cpu-sampling` 栈里出现反复的同一帧（例如 `Sqlite3`/`ReadFile` 附近的循环） | 定案到代码路径，按帧所属方法改 |
| `% Time in GC` 很高 | 推翻我此前"不是 GC"的结论（我曾据 `privateDropMB=0` 排除，需重估） |
| 栈样本里没有任何 IO 相关帧，且 counters 也正常 | **采集没落在发作期**，判为无效，请重采——不要据此下"问题不存在"的结论 |

## 6. 明确不要做的事

- **不要**在生产高峰做 `VACUUM` 或任何写库操作；回收空闲页是另一件事，需独立停机窗口。
- **不要**为了"让它复现"而人为加压（跑基准、灌数据）。那会污染归因。
- **不要**改 `pudding_platform.db` 的任何内容，也不要删除 `-wal` / `-shm`。
- **不要**把"这次没采到"写成"问题已解决"。它是触发性的，可能几小时后自己回来。

## 7. 如果只能做一件事

做 **T2**（打开语句统计开关并交回 3 分钟日志）。

它最可能直接给出答案，代价最小（一次部署 + 一个配置项），且不需要管理员、不需要理解 ETW。
T1 是它的兜底：万一读根本不是 SQL 发起的，栈样本是唯一还能继续查的东西。
