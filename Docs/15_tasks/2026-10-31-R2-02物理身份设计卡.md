# R2-02 物理身份设计卡

> 为什么现在写它：R1-02 与 R1-03 剩下的门禁都指向同一个前置 —— 索引里**没有「物理项目/程序集」这个维度**。不先定这个维度，那些门禁只能靠近似方案，而近似方案会把错误身份留在索引里。

## 1. 现状（现场实测）

### 注册表（`code_index_list_projects`，2026-10-31 07:10）

```
count = 4，全部是**目录**粒度，且互相嵌套：

PuddingAgent      D:\...\PuddingAgent\PuddingAgent                         Registering  ← 从未完成
PuddingCore       D:\...\PuddingAgent\PuddingAgent\Source\PuddingCore      Active
PuddingPlatform   D:\...\PuddingAgent\PuddingAgent\Source\PuddingPlatform  Active
PuddingRuntime    D:\...\PuddingAgent\PuddingAgent\Source\PuddingRuntime   Active
```

### 契约

```csharp
CodeProjectRecord(WorkspaceId, ProjectId, ProjectPath, Status, DisplayName,
                  AddedAtUtc, UpdatedAtUtc, Source, ScopeState, StatusMessage)
```

**没有任何程序集 / 编译项目 / 目标框架字段。** `ProjectId` 只是注册时生成的哈希，语义上等于「一个目录」。

### 存储主键

```sql
CodeSymbols PRIMARY KEY (WorkspaceId, ProjectId, SymbolId)
```

`SymbolId` 是全限定名（`T:Acme.Service`）。同一 ProjectId 内**两个程序集各有同名类型时，后写覆盖前写**。

## 2. 三个未解决后果

| 后果 | 现状 | 门禁出处 |
|---|---|---|
| **同一 scope 内两程序集同名 → 覆盖** | 未解决（主键冲突，静默丢一条） | R1-02 |
| **重叠 scope 同源重复** | 部分缓解：查询侧按 `(SymbolId, FilePath)` 去重（`5c76554`），但**存储层仍有重复行**，重复行参与关系边计算 | R1-02 |
| **两个 worktree 分开** | 完全未做（无物理路径以外的身份） | R1-02 |

另有一条**独立缺陷线索**：根项目 `PuddingAgent` 自 2026-10-01 注册后状态停在 `Registering`，`updated_at` 为 2026-10-06 —— 6 天没有推进，也没失败。这意味着「不传 project 的跨项目检索」始终带着一个**从未完成的 scope**。原因待查（可能是注册后从未触发首次索引，也可能是中途异常未落 Failed）。

## 3. 设计选项

### 选项 A：符号加程序集维度

`CodeSymbolRecord` 增加 `AssemblyName`（或 `CompilationUnit`），主键改为
`(WorkspaceId, ProjectId, AssemblyName, SymbolId)`。

- 优点：语义最准；同一 scope 内多程序集并存。
- 代价：主键变更 = 存储迁移；所有按 SymbolId 定位的查询、SymbolRef、关系边都要带程序集；影响面最大。

### 选项 B：ProjectId 细化到 csproj

注册粒度从「目录」改为「csproj」，一个 csproj = 一个 project。

- 优点：**不动主键**，复用现有全部机制；`ProjectId` 天然区分程序集。
- 代价：注册语义变化（项目数从 4 变 ~97）；`ProjectPath` 与 `ProjectId` 的关系要重新定义；重叠 scope 问题由「按 csproj 注册」自然消解。
- 未解：一个 csproj 内多 TFM（`net10.0` + `net10.0-windows`）仍会同名 —— 但实践中可用「取首选 TFM」规避。

### 选项 C：只加物理路径字段，主键不变

- 优点：改动最小。
- 代价：**不解决覆盖**。同一 ProjectId 内两程序集同名仍然丢一条。等于没做 R2-02。

## 4. 建议

**B 优先，A 作为长期方向。**

理由：B 用「注册粒度」换掉「主键变更」，把风险从存储迁移降级为注册流程调整；且它顺手解决重叠 scope（根 scope 不再需要把整棵树当一个项目）。

但 B 有一个必须先回答的问题：**根 scope（`D:\...\PuddingAgent\PuddingAgent`）是否还需要作为「一个项目」存在？** 若取消，跨项目检索要改为「对所有 csproj 项目求并集」——需要确认查询侧能承受 97 个 scope。

## 5. 需要裁定

1. 走 A 还是 B（还是先只查清「根 scope 为何卡在 Registering」再决定）？
2. 若走 B：注册表里现有的 4 条如何处理（迁移 / 清空重注册）？
3. 若走 B：跨项目检索的默认 scope 集合怎么定义（全部 csproj / 仅 Active / 按 solution 分组）？

## 6. 本轮不做

不改任何代码、不动数据库、不注册/注销项目。本文档只记录实测现状与选项，等裁定。

## 附录：根 scope 状态投影自相矛盾（2026-10-31 07:32 实测）

上一节把「根项目停在 Registering 6 天」列为待查线索。查到结果，**结论需要修正**。

### 状态字段说什么

`code_index_status(8a48458b…)`：

```json
"status": "Pending",
"message": "Indexing run interrupted: cancelled before a result could be recorded; this scope still owes a full indexing run.",
"completed_at_utc": "2026-10-06T15:08:16Z",
"index_freshness": { "state": "idle", "index_pending": false, "index_in_flight": false,
                     "last_calibration_at_utc": "2026-10-30T23:16:18Z",
                     "unresolved_source_path_count": 1 }
```

### 实际数据说什么

`code_symbol_search("GrepMatcher")` 返回 5 条，`project_id` **全部是根项目 `8a48458b…`**，其中 `Source/PuddingGrep/GrepMatcher.cs` 是 **2026-10-30 当天新建的文件**。

**也就是说：根 scope 的索引其实是新的，并没有「从未完成」。**

### 因此真实缺陷是「状态不诚实」，不是「索引缺失」

| 投影 | 实际 |
|---|---|
| `status = Pending` | 索引可用（`index_freshness.state = idle`） |
| message 说「仍欠一次完整索引」 | 最近一次校准在 10-30 23:16，数据含当日新文件 |
| `completed_at_utc = 10-06` | 之后显然又跑过 |

后果：任何**依赖 `status` 判断「是否需要重建」**的逻辑都会误判 —— 要么反复触发重建（浪费），要么把它当作不可用而跳过（本可返回的结果被挡掉）。

这与 R1-03 修的「失败却把水位推进」是**同一族的反面**：那里是「没做成却说做成了」，这里是「做成了却说自己还欠着」。两者都让状态字段无法作为判据。

### 修法方向（未实施）

`StatusMessage` 与 `status` 应在**每次运行结束时**重写，而不是只在取消/失败时写入后长期保留；「欠一次完整索引」这种承诺性文本，要么兑现后清除，要么由调度器在启动时扫描并真正重新入队（当前 `index_pending=false` 说明内存队列已丢，重启后无人消费这条承诺）。

### 范围

本轮只诊断，未改代码。这条与 R2-02 的注册/状态语义一起处理更合适（都属于「一个 scope 的身份与状态如何如实投影」）。
