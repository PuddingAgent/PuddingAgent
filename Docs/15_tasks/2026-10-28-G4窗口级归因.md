# G4 窗口级归因（切片分析）

> 方法：`dotnet-trace convert --format Speedscope` → 108 个线程 profile、2,657,008 个 open/close 事件、**0 个乱序**；
> 按 `at` 重放栈，把每段时长归到「栈中包含某特征」上。三个窗口对比。
> 为什么这样做：`IO Read Bytes/sec` 是**进程级**计数、不含文件名；只有按时间窗切栈才能回答「是谁在读」。

## 1. 结果

| 特征（栈中包含） | BURST 22:50:15.5–22:50:22.0（7s） | QUIET 22:52:40–22:53:40（60s） | ALL 全程（600s） |
|---|---|---|---|
| **Microsoft.Data.Sqlite** | 6,192 ms · **9.3%** | 4,618 ms · 0.6% | 55,656 ms · 0.4% |
| **PuddingCodeIndex** | 5,974 ms · **8.9%** | 2 ms · **0.0%** | 13,071 ms · 0.1% |
| **Roslyn / CodeAnalysis** | 5,917 ms · **8.9%** | 0 ms · **0.0%** | 34,003 ms · 0.3% |
| **ReplaceFilesAsync** | 5,819 ms · **8.7%** | 0 ms | 9,590 ms · 0.1% |
| **PuddingFullTextIndex**（Lucene） | 326 ms · 0.5% | **62,788 ms · 8.1%** | **626,366 ms · 5.0%** |
| PuddingPlatform（平台库） | 134 ms · **0.2%** | 4,376 ms · 0.6% | 53,111 ms · 0.4% |
| MSBuild | 19 ms | 0 ms | 4,582 ms |

各窗总栈时间：BURST 66,799 ms（7 秒内约 **9.5 个线程**并行）· QUIET 775,686 ms · ALL 12,484,546 ms。

## 2. 结论（三条，逐条可复核）

**① 尖峰 = 代码索引写入路径。**
`ReplaceFilesAsync`（`SqliteCodeIndexStore`）+ Roslyn 解析在 7 秒内各占 8.9% / 8.7%，而同窗 `PuddingPlatform` 仅 0.2%。
⇒ 尖峰读的是**代码索引库**，不是 `pudding_platform.db`。

**② 持久读（60–90 MiB/s 常态）= Lucene 全文索引维护。**
安静段 `PuddingFullTextIndex` 占 **8.1%**（62,788 ms / 775,686 ms），全程 **5.0%**；
同窗 `PuddingCodeIndex` 归零、Roslyn 归零。
⇒ 稳态读与代码索引无关，是全文索引的维护循环。

**③ 平台库（`conversation_events` 所在）不是主因。**
尖峰 0.2%、安静 0.6%。此前为它补 `(command_id, sequence)` 索引**修的是一个真实但次要的缺陷**，
它不能解释 580 MiB/s / 60–90 MiB/s。

## 3. 因此要撤回的（第二次修正）

- 撤回上一份判读里「主成分更像文件读（代码索引维护）」的**单因**说法：
  真实是**两个子系统** —— 尖峰归代码索引写入，稳态归 Lucene 全文维护。
- 保留「不是 DB（平台库）读」的结论，但限定为「不是**平台库**读」，因为代码索引同样走 SQLite。

## 4. 方法学边界（不可忽略）

- 尖峰窗 7 秒内总栈时间 66,799 ms ⇒ 平均 **9.5 线程并行**；百分比是「占该窗总栈时间」，
  **不是占墙钟**。要折算墙钟需再除以并行度。
- 两个窗口的 `UNMANAGED_CODE_TIME` 占比都极高（BURST 98.5% / QUIET 92.3%，全程 94.5%），
  说明采样大量落在原生等待（IO 阻塞）。**因此只做窗口间相对比较，不解读为绝对 CPU 占用**。
- 事件归到「区间起点所在窗口」，窗边界上会有 ≤1 个事件粒度的误差。

## 5. 下一步（按判别力排序，全部无需改代码）

1. **静默 Lucene 全文维护**：若安静段 60–90 MiB/s 消失 ⇒ 结论② 定案。
   （需确认 `FullTextIndexMaintenanceHostedService` 是否已有配置开关；若无，这是可提的改进点。）
2. **静默代码索引维护**：若尖峰消失、常态仍在 ⇒ 两个子系统相互独立（预期如此）。
3. 若 1、2 都做了而读依旧：再采一次带 ETW 文件 IO provider 的 trace，按文件名归因。

6. 无论结果，**恢复 `Enabled=true` 并再次重启**（不把实验状态留在生产）

## 7. 必须写明的混杂因素（否则结论不可信）

- **我自己就是噪音源**：这一晚的大量 `dotnet build` / `dotnet test` / F# 探针都在写仓库文件，
  而 FTS 维护的 `Debounce=500ms` + 变更扫描**正是文件写入驱动的**。
  ⇒ 采集窗口内若有构建活动，60–90 MiB/s 里有一部分是**我造成的**，不能全记在宿主头上。
- 因此对照实验要求：**采集期间不跑任何构建/脚本**，只让宿主自己跑。
- 同理，「恢复 `Enabled=true` 后再跑一次」也应在不构建的窗口内做，否则仍不可比。
