# 任务卡：把两条传输接进共用准入适配器

## 已就位（可直接用）

| 件 | 位置 | 状态 |
|---|---|---|
| 唯一规则 | `Pudding.Contracts/Desktop/BrowserCallerRequirement.cs` | ✅ |
| 签发 | `Pudding.DesktopService/BrowserGrantIssuer.cs` | ✅ 六类拒绝 + 7 用例 |
| 准入适配器 | `Pudding.DesktopService/BrowserAdmissionAdapter.cs` | ✅ Admit/Revalidate/Release（幂等）+ 3 用例 |

## 唯一 lifecycle 在哪（决定接线点）

- 生产：`Source/PuddingDesktop/Hosting/DesktopApplicationCoordinator.cs:30` `_browserAutomation = BrowserPageLifecycle.Create(...)`
- 链接副本：`Source/PuddingDesktop.WpfArchive/Hosting/DesktopApplicationCoordinator.cs:31`（同一逻辑，WinUI 侧链接编译）
- 已有消费者示例：`Source/Pudding.DesktopSurface.Browser/BrowserWorkspaceTargetBridge.cs`（由 lifecycle 取 `BrowserTargets`/`PageTargets`）

⇒ **组合根**构造 `BrowserAdmissionAdapter(_browserAutomation)` 与 `BrowserGrantIssuer(...)`，注入**两条**执行路径。

## 要做的接线（顺序固定，方案 §4.2）

1. **gRPC 能力通道**：`DesktopService.ExecuteAsync`（Browser* 分支之前）→ 用 `call.BrowserCaller` + 操作 + 目标 + `ConnectionGeneration` 调 `Admit`；拒绝 ⇒ 直接返回能力错误，**不进入**任何浏览器分支。
2. **Bridge 派发器**：命令解码后（已在 `DesktopBrowserBridgeClient` 校验过身份）→ 调**同一个**适配器实例。
3. **执行前**：触碰页面前 `Revalidate`；只读也在排队后重新核对连接与 grant。
4. **`finally`**：`Release(lease)`（写操作；只读无租约）。
5. **身份**：只从已校验的作用域/请求上下文取，**不得**从工具参数或模型字段取。

## 验收（可判定）

| # | 判据 |
|---|---|
| 1 | **被拒绝的驱动调用数 = 0**（取红：去掉 `Admit` 调用 ⇒ 用例必须变红） |
| 2 | 无 grant 时读操作也被拒；有 grant 时通过；撤权后 `Revalidate` 拒绝 |
| 3 | 写操作拿到租约并在 `finally` 释放；重复释放安全 |
| 4 | 两条传输走**同一**适配器实例（可用同一 lifecycle 的 grant 状态跨路径验证） |
| 5 | 接管/暂停期间：副作用操作拒绝、只读观察仍可用（方案 §3.2 表格） |

## 边界（不要越界）

- 不加第二份准入策略；判据仍在唯一 authority。
- 不为"看起来接上了"在传输层放行；缺身份仍然是拒绝。
- 不把 `PermissionEvidenceSummary` 当授权。
## 更正（2026-10-08，本轮核实）

**插入点已确认可用，且不需要改组合根**：`Source/Pudding.DesktopService/DesktopService.cs` 的构造函数**已经**接收
`BrowserAutomationAuthority authority` 并暴露 `public BrowserAutomationAuthority Authority { get; }`，
`ExecuteAsync(capability, request, context, ct)` 有**唯一出口**（`RecordObservedPageVersion` 就在那里）——
正是方案 §4.2 要求的那种"唯一位置"。

因此第三步的实际形状是：

1. 在 `DesktopService` 里由**同一个** `Authority` 构造 `BrowserAdmissionAdapter`（或在组合根构造后注入，二选一，但必须**只有一份实例**）；
2. 在 `ExecuteCoreAsync` 的 Browser* 分支**之前**按 `context.BrowserCaller` + 操作 + 目标 + 世代调 `Admit`；
3. 拒绝 ⇒ 返回能力错误（走既有错误通道），**不进入**任何浏览器分支（这就是"驱动调用数=0"的来源）；
4. **预计的同步面**：既有 `Pudding.DesktopServiceTests` 里大量用例直接执行 Browser* 能力而**没有 grant** ⇒
   接线后它们会被正确拒绝。参照前面两次（身份闸门、协议升级）的做法：**先看清失败清单，再用共享测试夹具统一补发 grant**，
   而不是给闸门加例外。这一步的规模应在几十条量级，属于同一切片内的消费方同步。
