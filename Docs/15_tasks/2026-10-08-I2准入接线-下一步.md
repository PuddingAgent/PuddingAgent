# 任务卡：把两条传输接进共用准入适配器

## 已就位（可直接用）

| 件 | 位置 | 状态 |
|---|---|---|
| 唯一规则 | `Pudding.Contracts/Desktop/BrowserCallerRequirement.cs` | ✅ |
| 签发 | `Pudding.DesktopService/BrowserGrantIssuer.cs` | ✅ 六类拒绝 + 7 用例 |
| 准入适配器 | `Pudding.DesktopService/BrowserAdmissionAdapter.cs` | ✅ Admit/Revalidate/Release（幂等）+ 3 用例 |

## 唯一 lifecycle 在哪（决定接线点）

- 生产：`Source/PuddingDesktop/Hosting/DesktopApplicationCoordinator.cs:30` `_browserAutomation = BrowserPageLifecycle.Create(...)`
- 链接副本：`Source/PuddingDesktop.WpfArchive/Hosting/DesktopApplicationCoordinator.cs:31`（同一逻辑，WinUI 侧链接编译）
- 已有消费者示例：`Source/Pudding.DesktopSurface.Browser/BrowserWorkspaceTargetBridge.cs`（由 lifecycle 取 `BrowserTargets`/`PageTargets`）

⇒ **组合根**构造 `BrowserAdmissionAdapter(_browserAutomation)` 与 `BrowserGrantIssuer(...)`，注入**两条**执行路径。

## 要做的接线（顺序固定，方案 §4.2）

1. **gRPC 能力通道**：`DesktopService.ExecuteAsync`（Browser* 分支之前）→ 用 `call.BrowserCaller` + 操作 + 目标 + `ConnectionGeneration` 调 `Admit`；拒绝 ⇒ 直接返回能力错误，**不进入**任何浏览器分支。
2. **Bridge 派发器**：命令解码后（已在 `DesktopBrowserBridgeClient` 校验过身份）→ 调**同一个**适配器实例。
3. **执行前**：触碰页面前 `Revalidate`；只读也在排队后重新核对连接与 grant。
4. **`finally`**：`Release(lease)`（写操作；只读无租约）。
5. **身份**：只从已校验的作用域/请求上下文取，**不得**从工具参数或模型字段取。

## 验收（可判定）

| # | 判据 |
|---|---|
| 1 | **被拒绝的驱动调用数 = 0**（取红：去掉 `Admit` 调用 ⇒ 用例必须变红） |
| 2 | 无 grant 时读操作也被拒；有 grant 时通过；撤权后 `Revalidate` 拒绝 |
| 3 | 写操作拿到租约并在 `finally` 释放；重复释放安全 |
| 4 | 两条传输走**同一**适配器实例（可用同一 lifecycle 的 grant 状态跨路径验证） |
| 5 | 接管/暂停期间：副作用操作拒绝、只读观察仍可用（方案 §3.2 表格） |

## 边界（不要越界）

- 不加第二份准入策略；判据仍在唯一 authority。
- 不为"看起来接上了"在传输层放行；缺身份仍然是拒绝。
- 不把 `PermissionEvidenceSummary` 当授权。
## 更正（2026-10-08，本轮核实）

**插入点已确认可用，且不需要改组合根**：`Source/Pudding.DesktopService/DesktopService.cs` 的构造函数**已经**接收
`BrowserAutomationAuthority authority` 并暴露 `public BrowserAutomationAuthority Authority { get; }`，
`ExecuteAsync(capability, request, context, ct)` 有**唯一出口**（`RecordObservedPageVersion` 就在那里）——
正是方案 §4.2 要求的那种"唯一位置"。

因此第三步的实际形状是：

1. 在 `DesktopService` 里由**同一个** `Authority` 构造 `BrowserAdmissionAdapter`（或在组合根构造后注入，二选一，但必须**只有一份实例**）；
2. 在 `ExecuteCoreAsync` 的 Browser* 分支**之前**按 `context.BrowserCaller` + 操作 + 目标 + 世代调 `Admit`；
3. 拒绝 ⇒ 返回能力错误（走既有错误通道），**不进入**任何浏览器分支（这就是"驱动调用数=0"的来源）；
4. **预计的同步面**：既有 `Pudding.DesktopServiceTests` 里大量用例直接执行 Browser* 能力而**没有 grant** ⇒
   接线后它们会被正确拒绝。参照前面两次（身份闸门、协议升级）的做法：**先看清失败清单，再用共享测试夹具统一补发 grant**，
   而不是给闸门加例外。这一步的规模应在几十条量级，属于同一切片内的消费方同步。
## 更正二（2026-10-08，本轮核实）：真正的闸门点是 `RunOnUiAsync`，且**缺一个前置件**

1. **闸门点**：`DesktopService.ExecuteCoreAsync` 的每个浏览器分支都经过**同一个** `RunOnUiAsync(descriptor, target, expectedVersion, context, …)`。
   在它内部、派发到 UI **之前**做准入，可以一次覆盖全部分支（而不是逐分支改）——这才是"唯一位置"。
   注意：Shell 能力也走 UI，但**不是**浏览器操作 ⇒ 闸门只对 WebView 系能力生效（判据沿用能力目录的 `Kind`，不另建清单）。
2. **前置件（此前被低估）**：`Admit` 需要 `BrowserAutomationOperation`，而仓库里**没有** `DesktopCapability → BrowserAutomationOperation` 的映射
   （现在只有 `Navigate`/`Interact` 两处按分支字面量传入）。⇒ 接线前必须先写这个映射，且它值得单独一条用例：
   **每个 WebView 系能力都有映射，Shell 系能力没有（返回"不适用"）** —— 否则"漏映射的能力"会静默绕过闸门。
3. **消费方同步的实测规模**：直接用 `DesktopService` 执行浏览器能力的用例约 **18 处**（`AgentTargetAdmissionTests` 15、
   `BrowserContextScopeAdmissionTests` 2、组合用例 1）；其余用例走 surface 直连、不受影响。
   ⇒ 同步面比前两次（身份闸门、协议升级）小，但仍然需要**先统一夹具补 grant**，不给闸门加例外。
## 更正三（2026-10-08，本轮核实）：闸门点更精确，且**缺第二个前置件：连接世代来源**

1. **闸门点已精确到一处**：`DesktopService.RunOnUiAsync(capability, target, expectedPageVersion, context, action, ct)`
   **已经**调用 `ValidateAdmission(capability, target, expectedPageVersion, context, out pageState)`，非 null 即提前返回。
   ⇒ 正确做法是**扩展 `ValidateAdmission`**（把 authority 的 `Admit` 接进去），而不是另加一道平行闸门
   （设计 §1.1 反对"第二份策略"）。
2. **缺的输入：连接世代（`ConnectionGeneration`）**。`BrowserAutomationRequest` 构造需要它，但：
   - `DesktopCallContext` **没有** generation 字段（它只有 DesktopId/OperationId/Deadline/CorrelationId/PermissionEvidence/BrowserCaller）；
   - `BrowserControlSnapshot` 也**没有**暴露 generation（只有 ControlEpoch/GrantEpoch/IsPaused/IsUserTakeover/IsClosed/ActiveLease/Reason）；
   - 而 authority 内部**知道**它（`NotifyConnectionGeneration` 推入）。
   ⇒ 接线前必须先定这件事，两种可行做法（择一，不要两处都做）：
   - **(a) Desktop 侧提供**：由组合根/主管线把"当前连接世代"以 `Func<ConnectionGeneration>` 或 options 注入 `DesktopService`
     （handshake/supervisor 本来就知道它）——语义最忠实：请求带世代就是为了**抓陈旧请求**；
   - **(c) authority 暴露**：让 `Admit` 有一个"按当前连接"的重载 / 或在快照里加 generation —— 会改公共契约类型，需权衡。
   **不建议**：在 `DesktopService` 里凭空造一个世代传给 `Admit`（`GateConnectionAndIdentity` 会拒绝，等于把闸门变成"永远拒"）。
3. 至此接线的前置件清单是完整的：① 能力→操作映射（**已完成**，round-188）；② 连接世代来源（**待定 (a)/(c)**）；
   ③ 消费者同步（约 18 处，用共享夹具补 grant）。

## 决策（2026-10-08，本轮）：**不得单独启用闸门** —— 启用必须与"活路径签发"同一次提交

**证据（可复跑）**：全仓 grep 生产代码（排除 Tests）后，`IssueGrant` 只出现在
① 接口 `BrowserControlContracts.cs:518`、② 实现 `BrowserAutomationAuthority.cs:360`、
③ **`BrowserGrantIssuer` 自己**（它**没有任何生产调用方**）。
⇒ 若现在只在组合根注入连接世代、打开闸门，**生产路径上不存在任何 grant** ⇒ 每一个浏览器能力都会被 `Admit` 拒绝：
功能变成"fail-closed 但**完全不可用**"（比不开更糟：用户会看到浏览器能力全线失效，而这不是缺陷修复，是我引入的）。

**因此确定的施工顺序**（把这一条当作验收条件）：

1. **先**把"活路径签发"接上（用户选定目标/任务绑定时由 `BrowserGrantIssuer` 签发；这需要一个可信触发点与 binding 来源，
   方案 §4.1 要求"从可信 Core 元数据取得 binding"）；
2. **同一次提交**里再在组合根注入 `() => <当前连接世代>` 打开闸门；
3. 同日同步约 18 处测试消费方并跑全量链。

**反例（明确不做）**：
- 不为"让闸门能开"而在 `Admit` 前放行无 grant 的调用（那就等于没有闸门）；
- 不在签发路径缺失时打开闸门后"用文档说明暂时不可用"——**不可用的功能不应进入生产装配**。
## 活路径签发的**触发点与缺口**（2026-10-08 本轮核实，含行号）

**已找到的事实（可信触发点）**：

- 用户选定目标的事实由 `BrowserPageLifecycle.SetAgentTarget(contextId, pageId)`（`BrowserPageLifecycle.cs:176`）落库，
  它读写 `_pageTargets.AgentTarget`（`DesktopTargetRegistry.AgentTarget`）；
- 生产调用方只有 `BrowserWorkspaceTargetBridge.SetAgentTarget`（`BrowserWorkspaceTargetBridge.cs:166`）——
  这是 Desktop 表面暴露给 **Shell/UI** 的桥 ⇒ **它就是"用户选定给 Agent 的页"这一可信触发点**。

**仍缺的输入（缺口）**：**grantee（任务身份）从哪来**。
普通能力调用**不能**自动把自己授权为目标页 owner（方案 §4.1 明确禁止），因此签发必须由"用户目标绑定"驱动；
而 binding 按方案要求应"**从可信 Core 元数据取得具体 Agent/会话/运行 binding**"——该来源**目前不存在**：
Desktop 在目标选定时刻并不知道"哪个任务"被授权（它只知道页面）。

**因此下一步的最小可信形状**（三件，缺一不可）：

1. **契约**：Core → Desktop 的"任务绑定"事实（任务运行身份 + 目标页 + 授权范围/期限），来自 Core 的可信元数据（不是模型参数）；
2. **Desktop 侧存储 + 触发**：收到绑定后由 `BrowserGrantIssuer` 在 `SetAgentTarget` 成功路径上签发（过期/切目标/任务结束即撤销）；
3. **同一次提交**打开闸门（注入世代提供者）并同步约 18 处测试消费方 —— 顺序不可颠倒（见上面的"决策"节）。

**明确不做**：把"当前调用者身份"当作 grantee 自动签发（那会让任意一次调用把自己变成 owner，正是 §4.1 禁止的）。
## 绑定传输：字段级方案与**必须先定的四个决定**（2026-10-08 本轮核实）

**核实结论**：目录里**没有**任何控制面能力（`Capabilities.cs` 现有 `browser.*` 8 项全是页面操作），
`BrowserAutomationOperation` 里也**没有**"授权/绑定"操作。⇒ 绑定传输**不是**加十行，而是要新增一类能力面。

### 必须先定的四个决定（动了哪一个都会影响既有策略代码）

| # | 决定 | 选项与影响 |
|---|---|---|
| 1 | **能力类别** | `WebView` 会让 round-188 的守卫（"每个 WebView 能力必须有操作映射"）与编码器的"浏览器能力必须有 caller"同时生效 ⇒ 必须先补一个操作；`Shell` 会**错误地**暗示"无需 browser grant"。建议：**新增 `DesktopCapabilityKind.Control`**（并在策略里显式：需要可信 caller、**不**需要页面 grant） |
| 2 | **操作映射** | 要么加 `BrowserAutomationOperation.BindingApply/Revoke`，要么让守卫显式豁免 `Control` 类（**豁免必须写在守卫里**，不能靠"没映射就跳过"——那正是静默绕过） |
| 3 | **ack 形状** | 方案要求"签发 ack" ⇒ 需要明确的成功/拒绝结构（含 `grantId`/`epoch`/原因），且**拒绝原因可区分**（未选定给 Agent／超上限／目标未登记／世代不活／子代理越权） |
| 4 | **幂等键与撤销** | 建议幂等键 `(任务运行身份, 目标)`；撤销可复用同一能力面（`binding.revoke`）或绑定到连接世代回收——**必须二选一并写明** |

### 之后的施工（一次只改一处 + 每步编译 + TRX 判定）

1. `Capabilities.cs` 加两个能力（`browser.binding.apply` / `browser.binding.revoke`）+ `Kind=Control` + 策略分支 + 守卫更新（含"漏映射即变红"）；
2. 能力通道 DTO/编解码（proto 新字段用未占用编号；两侧映射；未知/空必填拒绝）；
3. `DesktopService` 分支：调 `BrowserTaskBindingService.Accept/Revoke`，把结果映射成 ack；
4. **同一次提交**：组合根注入连接世代 → 打开闸门 → 用共享夹具给约 18 处补 grant → 跑全量链。

### 明确不做
- 不为"省事"把绑定塞进 `Origin`/`PermissionEvidenceSummary`（方案禁止用审计字段当授权）；
- 不给 `Control` 类能力沿用 `WebView` 的"必须有页面 grant"要求（会把控制面自己锁死）。

## **已达成的缺陷：写操作租约泄漏**（2026-10-08 本轮发现，修法已确定但未落地）

**缺陷**：`DesktopService.ValidateAdmission` 里 `Authority.Admit(...)` 的裁决**被丢弃了租约**

**修法（形状已确认，代码位置与 API 都已核对）**：

1. `ValidateAdmission` 增加出参 `out BrowserAutomationLease? lease`（顶部 `lease = null;`）；

4. `RunOnUiAsync` 的 `try`（包住 `_dispatcher.InvokeAsync(...)`）加 **`finally`**：

**本轮踩到的坑（下轮避开）**：
- `linked.Token).ConfigureAwait(false);` 在文件里**不止一处** ⇒ 用它当定位锚会插错位置（我因此两次破坏花括号）；

```csharp
    BrowserPageGrantScope.Read | BrowserPageGrantScope.Write,
    TimeSpan.FromMinutes(5),
    "bridge:agent-target"));
```

**"无会话"时的语义（关键判断）**：**返回（不申请、不抛）**，而不是抛。理由：
- 能力通道未启用是**正常配置**（默认关闭）⇒ 抛异常会把只走 Bridge 的现网路径打成全局失败（round-262 已记的回归）；
- 安全性不因此降低：**最终判据始终在 Desktop 的唯一 authority** —— 一旦闸门开启，没有 grant 的浏览器命令会被 Desktop **拒绝**（fail-closed 在最里层，而不是在最外层）。门的作用是"**尽量提前把授权拿到**"，不是"替 Desktop 判权"。

⇒ 门的职责边界写清楚：**申请 + 缓存 + 把拒绝如实上报**；不承担"没有会话就拒绝一切"的责任。

**下一步实现顺序**：① 新类 `CapabilityChannelBindingGate`（按调用解析会话；无会话 ⇒ 直接返回；有会话 ⇒ 走 `DesktopBrowserBindingProducer`，拒绝 ⇒ 抛）；② 在 L37 之后注册；③ DI 用例：**能力通道无会话 ⇒ `IBrowserBindingGate` 存在但调用是 no-op**（不抛、不发）／**有会话 ⇒ 会发 `browser.binding.apply`**；④ 跑 `PuddingHost.Tests` → 提交。
