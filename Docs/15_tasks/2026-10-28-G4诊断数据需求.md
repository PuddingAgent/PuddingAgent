# G4 诊断数据需求

> **这份文档只说明"我需要什么"，不含命令、脚本或步骤。**
> 用什么工具、怎么采、采几次，由执行方自行决定。
> （仓库内另有一份 `2026-10-28-G4诊断数据采集任务书.md`，含在本机验证过的工具可用性与命令，
> 供参考，**不是必须遵循的流程**。）

## 背景：要我定位什么

宿主进程 `PuddingAgent` 会**间歇性**以 **4 KiB 粒度、约 21 万次/秒（820–955 MB/s）** 持续读一个 SQLite 文件，
CPU 内核态占 56–98%，写约 37 KB/s，句柄与内存都稳定，一次发作持续数分钟后**自行结束**。

**已确定**：读的是 `D:\Data\databases\pudding_platform.db`。
**未确定**：哪条 SQL、或哪段代码。**这就是我需要数据来回答的唯一问题。**

## 需求 1 · 发作期的托管热点栈（最重要）

**要回答**：那 21 万次/秒的读取是**哪段代码**在发起。

**我要的形式**：
- **按方法名聚合后的热点结果**（top 20–50 + 各自占比），**不是**原始 trace 二进制——我读不了二进制。
- 需要能看出**是否存在反复出现的同一帧**（那是循环的标志）。

**精度/范围要求**：
- 必须采在**读速率真正高的窗口内**（发作时 820–955 MB/s 量级）。
- 覆盖**至少一次完整发作**（一次发作持续数分钟）。

## 需求 2 · 一份安静期对照（同样重要）

**要回答**：发作期与安静期**差在哪**。

**我要的形式**：同一台机器、同一个进程，在**读速率低**的时段采一份**等长**的同类数据。

**为什么必须有**：归因的本质是两者的差异。只有发作期数据，我无法区分「这是常态」和「这是病因」——
这几天我已经因为缺对照误判过好几次。

## 需求 3 · GC 与线程池的逐秒数值

**要回答**两件事：
- GC 时间占比是不是真的低（我曾据「内存不涨」排除 GC，这个结论需要被独立检验）
- 线程池有没有饥饿（队列/线程数是否异常）

**我要的形式**：**发作期一组 + 安静期一组**，逐秒数值。

## 需求 4 · 数据库语句统计日志（若采集层已开启）

**要回答**：是不是某条 SQL 被反复执行。

**我要的形式**：发作**前、中、后各 1–2 分钟**的日志原文（含时间戳），能看出各语句的执行次数与耗时排序。

若该统计层尚未开启，请告知——这是需要先部署的前置条件，不是你的问题。

## 需求 5 · 每份数据都必须带的元数据

| 项 | 为什么 |
|---|---|
| **采集时刻 + 时区** | 宿主日志是 `+08:00`、终端可能是 UTC；对不上时间线，数据就白采 |
| **发作的起止时刻** | 我要用它和日志窗口对齐 |
| **采集当时的读速率读数** | 证明这份数据落在发作期，而不是事后假设 |

## 需求 6 · 如果结论是「没采到」或「看起来正常」，也请告诉我

这是两种**不同的负结论**，我不能靠自己分辨：

- **栈里完全没有 IO 相关帧** → 说明读不是托管代码发起的，我该转去查非托管/原生路径。
- **一切正常，读速率也没高** → 说明**没采在发作期**，需要重采。

请如实说明是哪一种。**不要**把「这次没采到」写成「问题已解决」——它是触发性的，可能几小时后自己回来。

## 我不需要的东西

- 原始 trace / ETL 二进制文件（我读不了）
- 完整日志（只要窗口）
- 你替我做归因或猜测

## 一句话总结

**发作期与安静期各一份托管热点栈 + GC/线程池逐秒值，都带准确时刻；能附上 SQL 统计日志更好。**

判读由我做，采集策略由你定。
