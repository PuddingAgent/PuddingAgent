# G4 诊断数据需求

> **本文只说明"我需要什么数据"以及"怎么交给我"，不含采集命令或步骤。**
> 用什么工具、怎么采、采几次，由执行方自行决定。
> 仓库内另有一份 `2026-10-28-G4诊断数据采集任务书.md`，记录了在本机验证过的工具可用性
> 与命令，**可查阅，但不是必须遵循的流程**。

---

## 一、背景：这份数据是为了解决什么

### 1.1 大目标

我们有一个「检索系统四目标」的工程计划，四项分别是：
**毫秒级检索**、**1 秒内增量更新**、**后台自动维护**、**低资源占用**。

前三项已经通过验收。**第四项（低资源占用）没有通过**，卡住的正是这份数据要解决的问题。

### 1.2 具体症状

宿主进程 `PuddingAgent` 会**间歇性**地出现一段持续读风暴：

| 指标 | 实测值 |
|---|---|
| 读速率 | 820–955 MB/s |
| 读操作 | 每秒 16.6 万 – 24.3 万次 |
| 每次读的块大小 | **恰好 4096 字节**（无一例外） |
| 写 | 约 37 KB/s（读写比 ≈ 13,000 : 1） |
| CPU | 单核 90%+，其中**内核态占 56–98%**，用户态仅 5–20% |
| 句柄数 | 稳定（40 秒内波动 0.25%） |
| 私有内存 | 稳定（3 分钟内只变约 58 MB） |
| 物理磁盘读 | ≈ 0（全部命中系统文件缓存） |
| 持续 | 一次发作连续数分钟后**自行结束** |

**它是触发性的，不是常态。** 同一天的三次观测：9.6 MB/s（16:14）→ 820–955 MB/s（16:28–16:32）→ 13.4 MB/s（17:34）。

### 1.3 已经查到哪一步

**已确定**：被反复读的是 `D:\Data\databases\pudding_platform.db`（那个 11.95 GB 的平台数据库）。
判据是 NTFS 最后访问时间——30 秒窗口内该文件的 access 时间恰好前进 30 秒，而另外两个数据库文件
（`pudding_memory.db`、`code_index.db`）**原地不动**。这个结论做过三次独立复核。

**已排除**（每条都有数据或代码证据）：探针自身、agent 工作轮次、代码索引写入、全文索引提交、
日志刷盘、文件枚举、内存映射、符号表全表扫描、计算哈希、托管 GC 及其各变体、
库存采样服务（代码里明确是 `O(log n)` + `LIMIT` 样本）、代码索引维护、
所有分钟级以上周期服务（即使每轮读 1 GB 也只有约 17 MB/s，量级差两个数量级）、
四处会话事件查询（都有 `LIMIT`）、SSE 重连风暴、上下文组装（P50 = 20 ms）、
投影滞后（`lag = 0`）、反复 open/close、以及一次单变量实验排除的「编译触发」。

**未确定**：这个数据库内部，**是哪条 SQL、或哪段代码**在发起这些读。

### 1.4 为什么必须请外部采集

**我在这个进程里面。** 我能从外面采计数器、枚举句柄、看文件时间戳，但：

- 拿不到**托管侧的调用栈**（不知道哪段代码在跑）
- 拿不到**内核 FileIO 事件**（本机缺相应工具，且需要管理员权限）
- 自我观测会污染观测本身——我每次工具调用都会让宿主多干活，而这个现象本身就与负载有关

所以需要一个**在进程外、能拿到运行时内部视角**的执行者。

### 1.5 拿到数据之后会做什么

定案到具体查询或代码路径后，改动方向已经清楚，属于常规优化：
能定位到 SQL 就加索引或改查询形状；定位到代码就改那处循环。
**然后用同一套观测手段复核读风暴是否消失**——所以这份数据同时是改动前的基线。

## 二、我需要的数据（六项）

### 需求 1 · 发作期的托管热点栈（最重要）

**要回答**：那 21 万次/秒的读取是**哪段代码**在发起。

**我要的形式**：
- **按方法名聚合后的热点结果**（top 20–50 + 各自占比），**不要原始 trace 二进制**——我读不了二进制。
- 需要能看出**是否存在反复出现的同一帧**（那是循环的标志）。
- 文本形式即可（Markdown 表格或纯文本），不要截图。

**范围要求**：
- 必须采在**读速率真正高的窗口内**（发作时 820–955 MB/s 量级）。
- 覆盖**至少一次完整发作**（一次发作持续数分钟）。

### 需求 2 · 一份安静期对照（与需求 1 同等重要）

**要回答**：发作期与安静期**差在哪**。

**我要的形式**：同一台机器、同一个进程，在读速率低（约 10 MB/s）的时段采一份**等长**的同类数据，
同样按方法名聚合。

**为什么必须有**：归因的本质是两者的差异。只有发作期数据，我无法区分「这是常态」和「这是病因」——
**这一天我已经因为缺对照误判过好几次，其中一次还写进了记录又被自己撤回。**

### 需求 3 · GC 与线程池的逐秒数值

**要回答**两件事：
- GC 时间占比是不是真的低（我曾据「内存不涨」排除 GC，这个结论需要被独立检验）
- 线程池有没有饥饿（队列长度、线程数是否异常）

**我要的形式**：**发作期一组 + 安静期一组**，逐秒数值。

### 需求 4 · 数据库语句统计日志（若采集层已开启）

**要回答**：是不是某条 SQL 被反复执行。

**我要的形式**：发作**前、中、后各 1–2 分钟**的日志原文（含时间戳），
能看出各语句的执行次数与耗时排序。

若该统计层尚未开启，请直接告知——那属于需要先部署的前置条件，不是你的问题。

### 需求 5 · 每份数据都要带的元数据

| 项 | 为什么 |
|---|---|
| **采集时刻 + 时区** | 宿主日志是 `+08:00`、终端可能是 UTC；对不上时间线，数据就白采 |
| **发作的起止时刻** | 我要用它和日志窗口对齐 |
| **采集当时的读速率读数** | 证明这份数据落在发作期，而不是事后假设 |

### 需求 6 · 如果结论是「没采到」或「看起来正常」，也请告诉我

这是两种**含义完全不同**的负结论，我自己分辨不了：

- **栈里完全没有 IO 相关帧** → 说明读不是托管代码发起的，我该转去查非托管/原生路径。
- **一切正常，读速率也没高** → 说明**没采在发作期**，需要重采。

请如实说明是哪一种。**不要**把「这次没采到」写成「问题已解决」——它是触发性的，可能几小时后自己回来。

## 三、交付方式

### 3.1 输出到哪里

**请放在这个目录下**（按采集时刻建子目录，一次采集一个目录）：

```
D:\Data\g4-capture\<yyyyMMdd-HHmmss>\
```

选这个位置的原因：不在 git 工作树内（不会污染代码仓库），也不会被任何清理任务当临时文件删掉，
我能直接用绝对路径读取。

### 3.2 每份文件叫什么

同一次采集目录下，用固定文件名：

| 文件名 | 内容 | 是否必需 |
|---|---|---|
| `manifest.md` | **元数据清单**（见 3.3） | **必需** |
| `hot-stacks.md` | 发作期按方法名聚合的热点栈（top 20–50 + 占比） | **必需** |
| `quiet-stacks.md` | 安静期同长度对照 | **必需** |
| `counters-hot.csv` | 发作期逐秒 GC / 线程池数值 | 强烈建议 |
| `counters-quiet.csv` | 安静期逐秒同类数值 | 强烈建议 |
| `sqlmetrics.log` | 数据库语句统计片段（前/中/后各 1–2 分钟） | 有则必需 |
| `notes.md` | 采集过程中任何异常、判断与你的观察 | 建议 |

**文件名不要带空格**，避免我这边路径处理出问题。

### 3.3 `manifest.md` 必须写明的内容

我会**先读这个文件**，据此判断其余数据的可信度。请包含：

1. **采集开始 / 结束时刻，明确标注时区**（例如 `2026-10-28T21:05:30+08:00`）
2. **宿主进程 PID 与启动时刻**
3. **发作的起止时刻**（你判断它在发作的依据是什么）
4. **每份采集文件对应的读速率读数**（证明它落在发作期还是安静期）
5. **你用了什么工具与版本**
6. **哪些需求没做到，以及原因**（这一条比做到的部分更重要）

### 3.4 格式要求

- 所有文本文件一律 **UTF-8**。
- 时间统一写完整 ISO 时间并带时区偏移，不要只写 `21:05`。
- **不要交原始二进制**（trace / ETL / dump 等）——我读不了，交了也没用。
- 热点栈请**自带采样点数与百分比**，否则我无法判断哪些帧是噪声。

### 3.5 怎么通知我

采集完成后，把 `manifest.md` 的**绝对路径**告诉我即可（或者直接说"采集完成，目录是 `<路径>`"）。
如果 `manifest.md` 里写了「某项没做到」，我会按 3.3 第 6 条的口径理解，不会当成缺陷。

---

## 四、我不需要的东西

- 原始 trace / ETL / dump 二进制文件（我读不了）
- 完整日志（只要窗口）
- 你替我做归因或猜测结论

---

## 五、一句话总结

**发作期与安静期各一份托管热点栈 + GC/线程池逐秒值，都带准确时刻，放到 `D:\Data\g4-capture\<时间戳>\`，
并写一份 `manifest.md` 说明每份数据的来源与可信度。**

判读由我做，采集策略由你定。
