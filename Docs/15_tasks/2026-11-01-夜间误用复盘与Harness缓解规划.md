# 夜间（10-31 19:55 → 11-01 09:37）误用复盘与 Harness 缓解规划

数据来源：28 个提交、`temp/` 下的原始命令输出、以及本轮被回退的两次实验。
**每条都标了「当时怎么发现的」与「能不能机器判定」**，判不了的不进规则。

## 一、实际发生过的误用（按真实代价排序）

|---|---|---|---|---|
| 1 | `(A) & (B) & (C)` 当成并行（cmd 里是串行） | **30 分钟**空跑，第一个工程都没开跑 | 能（`&` 计数 + 方言） | ✅ 已覆盖 `shell.cmd_ampersand_is_sequential` |

## 二、规则能治的 vs 规则治不了的

**规则能治的**（字面量 + 方言 + 计数即可判定）：1、2、4、5、6、7、8、9、11。

**规则只能提醒、治不了的**：

- **大输出**：需要工具自己落盘 + 只回路径摘要，规则只能事后说一句「下次落文件」；
- **真并行**：cmd 的 `&` 永远串行，规则最多提示「分多次调用」，真正的并行得改 `terminal_*`；
- **编码**：GBK 乱码导致的误读（今晚至少 3 次），根治是工具层强制 UTF-8 或自动转码；
- **「先猜后验」的思维习惯**：这是最贵的（#11），规则只能在第 3 次失败时叫停，
  叫不住第 1 次。真正的解法是把「先 dump 再改」写进工作流，而不是靠事后提示。

## 三、优先级（按今晚实测耗时排）

| 优先级 | 规则 | 理由 |
|---|---|---|
| **P0** | `dotnet test` 缺 `--no-build`；测试连续超时 → `--blame-hang` | #2 与 #3 合计浪费 ≈ 40 分钟，是今晚最大的两笔 |
| **P1** | `git add -A <dir>` 含未跟踪临时件；`git stash` 链；`python` 别名 | 都会造成**看似成功实则没做**，最难自查 |
| **P2** | `search_grep` 参数/覆盖度自检；`--filter` 堆多个条件的空结果 | 空结果最容易被误当成「不存在」 |
| **改造** | 大输出落盘、GBK 自动转码、terminal 并行 | 不是规则能解决的，需要动工具实现 |

## 四、设计约束（沿用已落地的组件）

- 规则必须**纯函数**：只看 `GuidanceInput`，不做 IO、不读文件系统 —— 否则热路径不可测；
- 需要状态的（计数）由 `ConsecutiveFailureTracker` 一类的外部组件承担，规则只读一个数；
- 每条规则配**正反例**，反例专挑最易误伤的写法（如 `findstr bash` 不应判为嵌套 shell）；
- 一次调用最多 3 条提示，按规则 id 去重；
- **不改成功位、不改退出码**。

## 五、一个必须写下来的观察

今晚最贵的两笔（#1、#2）都发生在**开始阶段**：先花 30 分钟确认「三个工程在排队」，
再花 20 分钟等构建 —— 而这两件事在命令发出的那一刻就能判定。

⇒ Harness 的价值不在「更聪明地重试」，而在**在错误的命令发出去之前或之后立刻说一句**。
这也解释了为什么 P0 应该是「构建/测试效率」而不是更复杂的分析类规则。
