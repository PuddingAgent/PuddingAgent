# ADR-088：原生视觉取图与截图统一链路

> 状态：Proposed；日期：2026-09-12。
> 本 ADR 部分修订 ADR-077；后者已完成的 Artifact/typed parts/Files 工作继续有效。
> 详细施工与验收：[原生视觉与统一取图截图优化设计](../Features/原生视觉与统一取图截图优化设计-2026-09-12.md)。

## 2026-09-19 图片预处理与会话恢复补充

默认请求上限改为 600 张、inline 单图 32 MiB、inline 文件字节合计 64 MiB；DeepSeek 最终请求体仍严格限制 48 MiB。请求构建前统计全部历史/用户/工具图片：14 张以内最大边长 8192，15 张起 4096；本地生成派生图，按编码体积降质量和尺寸，原图与 canonical 图片事实不变。完整 JSON 超限时缩减图片预算并有界重建，仍无法满足则返回可读错误。

视觉准备错误属于当前请求的可恢复失败，不计入会话 API 熔断。新图片请求不得缺图发送；后续纯文本输入被历史图片阻塞时，仅对出站请求把旧图片转为明确“未发送像素”的 Artifact 引用，Agent 可以再分批读取。当前轮及随后新工具图片仍完整保留并受预算校验。原消息、工具调用关系与磁盘原图不修改。

本补充已获用户明确实施授权；代码与定向自动测试见[修复记录](../Reports/图片请求官方限制与预处理恢复修复-2026-09-19.md)。不据此声明整份 ADR 或真实产品部署验收完成。

## 背景

### 2026-09-15 预处理能力与附件链路

按[原生阅读与预处理合同](../Features/ImageReader原生阅读与预处理-2026-09-15.md)扩展 metadata/read/prepare、四档 detail、裁剪/旋转/灰度/降噪/编码与多次局部读取。原图保留于 Workspace，low 和超尺寸概览在模型请求前统一准备，派生图复用；移除配置至 ToolContext 的全部 VisionHelper 路由合同。本次用户明确授权对附件生成受控预处理副本，替代“只能原样直传附件”的旧解释；不允许隐式调用其他模型或代理。实现与部署证据见[实施记录](../Reports/ImageReader预处理实施记录-2026-09-15.md)。

### 2026-09-15 故障修复进展

Image Reader 已移除工具内 helper invocation 与 mode 参数，统一返回调用模型自身消费的 typed image parts；设置页不再提供 Vision Helper。流式执行改为每次 LLM MoveNext 绑定冻结快照，修复 yield 后 AsyncLocal 丢失导致原生工具图片准备失败。已有 helper 配置字段尚未做数据迁移；其他协议的工具图片能力合同仍按原计划推进。验证和部署边界见[实施记录](../Reports/原生视觉流式上下文与ImageReader修复-2026-09-15.md)，不据此宣称整份 ADR 验收完成。

用户要求在主力模型升级为多模态后简化用户图片、Image Reader、自主取图、Web/桌面截图流程。当前原生图片链路已经存在，但有效能力依赖标签，两个主力模型的运行配置缺少 vision；Reader 仍内置 Responses 判定和自动 helper；通用 Planner 使用过时预算并耦合 DeepSeek Files；Web Screenshot 只有接口，实际 Unsupported。

这些问题属于能力合同、数据获取、传输和设备层的职责混杂，应在既有模块内收敛，不能再增加自动换模型或重复预识别的补丁。

## 决策

1. 用户附件直接进入当前模型；`image_reader` 保留 URL/绝对路径/Artifact 取图，返回 typed image result，不自动调用 helper。显式第二意见复用通用子代理委派、预算、消息和轨迹。
2. 视觉能力由既有 Execution Snapshot 内的模型/endpoint/Adapter/产品策略交集给出。`vision` 是能力投影；Responses 不是全能力证明。按用户图片、工具图片、inline、Files、格式、限制、估计版本表达合同，不逐工具硬编码协议字符串。
3. 复用 `vision-*` Artifact、ContentPartsJson、原有 canonical 事件和 Remote File Ref Store；元数据与授权流读取分开。只在 Provider Adapter 进行 inline 编码或 Files 上传，Core 规划不引用 DeepSeek 专属上传类型。
4. 原图、裁剪/缩放派生图不可变且可追溯；重复字节复用存储/上传，观察事件仍保留各自时间、目标、版本和 call ID。逻辑图片顺序不能因去重丢失。
5. 对整个最终请求统一校验图片、wire bytes 和 tokens；区分产品默认与 Provider 硬限制。每图 384 不再作为通用上界；估计按模型版本维护，实际 usage 独立计量。
6. Web 扩展既有 `browser_snapshot` 的 structure/image/both；首版指定 page viewport/region，补齐现有 ScreenshotAsync 和 Bridge，遵守 PageVersion/加载状态。Desktop 通过独立 `desktop_capture` 采集目标窗口/屏幕/区域，复用认证 Bridge 与制品接收；业务、模型和数据库仍归 Core。
7. 默认事件/任务驱动采集，DOM/AX 与图像按需组合；不每次心跳截图、不依赖 Web 常开。Desktop 离线/锁屏/目标不可用返回分类错误，不能用旧图伪造当前观察。
8. 图片是可能过期的观察；Memory 保存有界事实、checkpoint 与引用，不保存 Base64 或无限截图 OCR。活动任务证据由本地引用生命周期保护，远端文件只作缓存。
9. Web 用户图片和主/子代理工具图片使用共享内容组件与执行轨迹投影。工具成功、图片进入实际请求、模型完成依赖图片的任务分层验收；不展示内部凭据或要求隐藏思维内容。
10. 缓存验收仍包含图片请求与冷启动。Artifact/fileId 复用与 Provider token cache 分别报告；不以删图、重复无用前缀或省略必要观察换取 >99%。

## 对 ADR-077 的精确修订

- 保留：主代理原生视觉、用户附件不自动预观察、Workspace 制品、有序 typed parts、历史恢复、拒绝静默丢图、显式可观察第二意见。
- 取代：决策摘要第 4 项的 `auto`→helper 回退及工具内 `delegate`；第二意见使用通用委派。既有 helper 配置按一次性显式升级收口，不保留永久双读。
- 取代：把 384、2 MB 或首个试验模型参数泛化为当前通用限制。旧协议表是 2026-08-22 历史快照，现行限制由 V5 的版本化能力合同维护。
- 取代：正文中“当前仅设计”“Files 未实现”等不符合顶部 V0–V3 进展的理解；已经实现不等于 V4 真实运行验收。
- 细化 fail closed：需要的图片无法准备时不提交缺图 LLM 请求；单次取图工具可返回明确错误供当前 Agent 合法调整计划，不因此无条件终止整个长程 Run。

## 备选方案与代价

| 方案 | 结论 |
|---|---|
| 全部图片继续先经 helper 转文字 | 增加推理与上下文损耗，不采纳 |
| 彻底删除取图工具，只支持用户上传 | 破坏 Agent 自主文件/URL/制品阅读，不采纳 |
| 所有模型一律标视觉、所有 Responses 都标 Files/工具图片支持 | 无法保证实际 endpoint 合同，不采纳 |
| 在 Reader/Browser/Desktop 各放一套上传与模型调用 | 重复状态、缓存和授权，难以长程恢复，不采纳 |
| 新建全模态引擎并一次实现音频/视频 | 超出本次问题；先演进现有图像合同 |
| 只采用视觉操作、删除 DOM/AX | 增加识别和定位成本，保留按需组合 |

能力合同和流式制品读取需要跨层修改；显式第二意见迁移需要盘点 helper 配置；Desktop 采集需要真实 Windows 验收。收益是消除隐藏推理、重复编码和分散策略，让长期运行只依赖持久引用与共享执行内核。

### 实测证据摘要（已实测，2026-09-12 宿主 shell 真实请求）

- `deepseek/deepseek-flash` @ Responses endpoint：`{type:"input_image", image_url:"data:image/jpeg;base64,…"}` HTTP 200；单/双图正确，双图可区分顺序与数量；`image_url` 为对象或携带 `detail` = 400。
- `bigmodel/glm-5.3-flash` @ Responses endpoint（baseUrl 含前导空格需 trim）：同形态 HTTP 200，两模型对同一对图片给出一致且各自具体的描述；`/chat/completions` = 403。

- 据此在运行配置（`D:/data/config/llm.providers.json`）为两模型 `capabilityTags` 前置加入 `"vision"`（原文件已备份）。
- 2026-09-12 晚（切片三 T2 落地后）：在**同一运行配置**为 `deepseek/deepseek-flash` 与 `bigmodel/glm-5.3-flash` 补可选 `vision` 合同节（`version` + `estimatedTokensPerImageUpperBound: 1024`，其余字段留空 = 继承产品默认）；三个 embedding / 图像生成模型**保持无 `vision` 节**——合同语义要求这类模型即便误配也不得被标为视觉能力。生效条件 = Core 重启（配置加载一次、不热重载），端到端证据为创建日志 `visionPolicySource=contract`。

### 切片五 T4：视觉合同「只能收紧、不得放宽」（2026-09-12，待父级编译/测试验收）

模型级 `vision` 合同的 7 个上限维度按 §4.1 交集语义收口——产品策略（`VisionRequestPolicy.Default`）是天花板：`maxImagesPerRequest`（份数）、`inlineMaxBytesPerImage`（解码后字节/单图）、`inlineMaxTotalBytes`（解码后字节/累计）、`inlineMaxTotalWireBytes`（wire 字节）、`filesMaxBytesPerImage`（上传原始编码字节）、`filesMaxTotalBytes`（wire 字节）、`estimatedTokensPerImageUpperBound`（单图 token 保守上界）。

- `VisionCapabilityContract.ToPolicy()`：逐维取 `Math.Min(配置值, 产品默认)`（纵深防御：即使绕过 loader 直接构造合同也不放大上限）；未配置字段行为不变，沿用产品默认；`Version` 仍取合同 Version。
- `PuddingFileConfigLoader.ValidateVisionContract`：配置值超过天花板 → 加载期 fail-fast 显式拒绝（不静默钳制后放行），错误信息点名 provider/model、维度名、配置值与天花板，并按各维度自身口径标注（解码后字节 / wire 字节 / 上传原始编码字节，不得混用）。
