# ADR-090：上下文压缩触发口径、来源标注与收益准入收敛

日期：2026-09-13。状态：Proposed（仅审阅与设计；未修改产品代码、运行配置或数据库，未重启进程）。

依据：[上下文频繁压缩诊断](../../Reports/上下文频繁压缩诊断-2026-09-13.md)（含 1db627e 补充）。本 ADR 的源码断言已逐条复核，见"证据核验"。

## 背景

默认助手会话 `206a9b48ec904ebb93e7541131fbb835` 在约 34 小时内触发 45 次自动压缩、44 次写入，两次实际写入最短间隔 195 秒，每次处理消息数中位数仅 5 条，而触发时有效窗口使用率仅 22.84%–59.91%，均低于 65% 相对阈值。

诊断报告给出的机制性归因是"自动压缩的预算口径与压缩对象不一致"。我独立复核了它的六条源码断言，**全部成立**：

| # | 断言 | 证据 |
|---|---|---|
| 1 | `MaxActiveRawTokenBudget=131072`（注释定义为"未压缩活动原文"上限）实际与混合口径的 `usage.UsedTokens` 比较，并与相对阈值构成 OR | `ContextCompactionOptions.cs:72`；`ContextCompactionService.cs:86,102-115` |
| 2 | Provider 快照用 `max(本地估算, Provider.TotalTokens)` 合并，却标注 `Source=provider_usage` / `Confidence=provider_reported`；校准比例 `≥1` 且单调不减 | `LlmOptions.cs:219,242,247,253-255,272-273` |
| 3 | 协调器只有 per-session 单飞锁 + 成功冷却 30 秒，无收益/候选变化/代次准入；failed/no-op/skip/aborted 均不写冷却 | `CompactionCoordinator.cs:25-26,52,70`；`ContextCompactionService.cs:286,290,630,706-741` |
| 4 | `MaxHydrationTokenBudget=49152` 作用于 `TryHydrateStreamHistoryFromDbAsync`（重水合路径），不是"暖会话必须压到 49K" | `ContextCompactionOptions.cs:59-64`；`ContextWindowManager.cs:422,460-461` |
| 5 | `started` 在 flush、锁、冷却、候选检查之前发出；`Succeeded` metric 与 `completed` 事件无条件发出，仅返回值区分 | `ContextWindowManager.cs:1012,1047,1052,1100,1111,1136` |
| 6 | 同一 `started` 分支同时更新压缩卡片与 keyed loading toast（不同 hook 各自投影） | `useCompaction.ts:291-307`；`useSessionEventProjection.ts:738-775` |

既有权威文档已覆盖压缩的对外合同与缓存目标，本 ADR 不改其语义，只收敛触发口径与经济性准入：ADR-042（上下文自动压缩与主动 Compact 命令）、ADR-074（Goal 与压缩集成）、ADR-043 与 [18 上下文缓存可观测性](../18上下文缓存可观测性ADR.md)、[上下文 Token 效率缓存命中与分级压缩优化设计方案](../../Features/上下文Token效率缓存命中与分级压缩优化设计方案.md)。

## 独立判断：这样的设计好不好用

分四个维度，结论是**当前触发设计不可用，而报告的部分建议又过度设计**。

**长任务：不可用。** 触发与真实窗口压力脱钩（22.84%–59.91% 即触发），且每次只处理中位数 5 条消息。这既打断工作，又产生大量薄摘要——不是"压缩上下文"，而是"高频切割上下文"。

**缓存复用：这是最严重的经济影响，报告的论证强度低于其实际重要性。** 服务商前缀缓存要求前缀稳定；压缩会改写前缀，等同于主动使缓存失效。按本环境实测的资源池价格，`deepseek/deepseek-flash` 输入 1 / 1M tokens，缓存命中仅 0.02 / 1M tokens——**破坏前缀缓存的输入成本最多放大 50 倍**。而仓库内既有方案（上下文 Token 效率缓存命中与分级压缩优化设计方案）的目标正是 DeepSeek 缓存 >99%。频繁压缩与该目标**直接冲突**。因此"压缩应少而厚、并批量合并"不是体验偏好，而是有数量级代价的经济约束。

**记忆正确性：薄摘要碎片化。** 40 次压缩 × 中位 5 条消息，意味着把一段连续会话切成许多互相独立、逐层有损的小摘要。相比"少而厚"的合并式压缩，它更容易丢失中程决策与因果链。当前实现缺少**候选下限**，因此会把"还没到值得压缩的规模"也当成压缩对象。

**用户体验：问题不是重复展示，而是状态语义。** 报告自己已证 canonical 事件按 compactionId 没有重复 `started`，因此"toast + 卡片"并存不应算作重复计数缺陷。真正缺陷是：`started` 早于冷却/候选检查发出，`Succeeded`/`completed` 无条件发出，于是 UI 只能显示"完成"，而"完成流程"≠"成功回收"。同一 compactionId 还可能同时出现"已发 started + completed"与"因 30 秒冷却直接返回 0"的组合。

**对报告的独立修正（不盲从）**：

1. §2 称"优先取最近请求/Provider 快照"不完整——实际回退链有五级（`ContextCompactionService.cs:134-176`），仅改 raw cap 比较对象仍可能被后续回退项抬高。
2. §3 的"展示和诊断会放大体感"不应表述为缺陷；它是呈现选择，真正的缺陷是状态语义（见上）。
3. **根因不唯一**：`usage.UsedTokens` 混合口径由三个来源叠加造成——本地估算经 `provider max` 合并、校准比例单调不减地固化本地高估、DB 回退路径使用 `TotalTokens`。只改触发比较对象会留下其余两条继续抬高读数。
4. §1/§2/§7 的全部频次、耗时、间隔、比例与 DB 估算数字，本轮**未复核**，只作为证据来源引用，不作为本 ADR 的门槛依据。§7 新增的 5 次记录同样未经 canonical/Provider 账本核对，**不得**预设其均由 raw cap 触发。

## 决策

1. **预算分层（必须，P0）。** 明确区分五类量并各自独立命名：①整请求安全上界（防超窗）②Provider 实报输入 ③本地保守估算 ④可压缩历史候选区 ⑤固定成本（系统提示 + 工具 schema + 当前轮）。`MaxActiveRawTokenBudget` 只约束它命名的对象（可压缩历史原文）；安全门禁用①，经济性触发用④叠加真实窗口压力。**双门禁并存**，不得只留其一。
2. **来源与置信标注（必须，P0）。** Provider 实报、本地保守上界、回退估算三类值在快照中分别标注，禁止把 `max` 合并结果标为 `provider_reported`。本地高估只允许作为独立字段存在，不得作为经济性压缩的唯一触发值。校准比例不得单调不减地把历史高估固化进判定路径。
3. **准入与抑制（必须，P1；但用最小实现）。** 不新建"压缩计划器"。只用三个廉价不变量：候选原文增量下限（含候选下限，避免薄摘要）、真实窗口压力阈值、同候选集 no-op/膨胀的有界退避。冷却仅是并发保护，不得充当经济性主要手段。
4. **状态语义（必须，P1）。** 结果显式区分 `compacted / deferred / skipped / failed`；`started` 在通过候选与冷却检查后发出，或在 `completed` 载荷中携带明确 result 状态；"流程走完"不得等同于"已回收"。
5. **冷启动水合与暖会话分层（必须，P1）。** hydration 预算只作用于重水合路径；暖会话在窗口充足时保留稳定前缀，不因固定成本跨过 raw cap 而被要求压到水合预算量级。
6. **UI 单状态呈现（轻量，P1）。** 同一 compactionId 只呈现一个主状态；自动压缩不同时永久保留 toast 与大卡片；SSE 重放、断线重连不重复弹 loading。
7. **验收先测后调（必须，P2）。** 硬约束：真实超窗次数 = 0。先只测三个主指标（每百次主模型调用压缩率、候选对应的整请求有效回收率、前缀稳定性），其余指标延后，门槛数值一律经历史请求回放校准后确定。**本 ADR 不拍数字。**

## 被否决的备选方案

- **A. 直接调大阈值或关闭自动压缩**：否决。掩盖口径错误，且以真实超窗风险换取安静。
- **B. 立即构建完整"压缩计划器"与 session/model/request/contextGeneration 全量代次快照体系**：**现在否决（过度设计）**。它引入新的状态机、持久化与测试矩阵，而当前连"回收多少整请求空间"的口径都未定义，门槛无从设定。降级为决策 3 的三个廉价不变量；待决策 1–3 落地并有回放数据后，再评估是否需要计划器。
- **C. 只改 UI 文案与展示**：否决。治症不治因，触发仍会继续。
- **D. 单纯延长冷却时间**：否决。用时间限制掩盖统计错误，且会拦住必要的防溢出压缩（与硬约束冲突）。

## 验收指标

- **硬约束**：真实超窗（整请求上界超过模型窗口）次数 = 0。
- 压缩频率：每 100 次主模型调用触发的自动压缩次数（当前基线见诊断报告 §1，标注未复核）。
- 有效回收率：压缩前后**整请求** Provider 实报 token 差 / 候选区原文差。**禁止**用 DB 活动消息正文估算（如 17,439→12,825）代替整请求收益。
- 前缀稳定性：Provider 加权缓存命中率，对齐 ADR-043 与 Token 效率方案的既有口径。
- 记忆正确性：压缩后关键事实可检索率，以及摘要碎片度（每次压缩处理消息数分布，应显著右移）。
- 反作弊：不得以减少模型调用、删除任务、或以不压缩换取指标改善。

## 风险

- 放宽 raw cap 可能削弱真实超窗保护——由决策 1 的双门禁强制约束，二者不可合并为单一阈值。
- 修改快照标注会改变诊断读数，历史报表基线不再可比，需在报告侧同步说明。
- S3 触及 `useSessionEventProjection`，存在状态双源不一致风险，需与卡片投影同批验证。
- 决策 3 的三个门槛若一开始就拦截而非观测，可能引入新的误杀；建议先观测后拦截（见待确认 2）。
- `Docs/07架构/` 存在 ADR 编号历史冲突（`64ADR-064` 与 `65ADR-064`）；本文只新增 104/ADR-090，不连带触发重编号。
- 本 ADR 的数字类依据未复核，S4 修改门槛前必须先补齐只读核对。
