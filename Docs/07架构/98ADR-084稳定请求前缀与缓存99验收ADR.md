## 背景

冻结运行窗口缓存率95.4834%，并未达到>99%。工具定义变化、历史/记忆重注入、派生会话和后台短请求共同贡献未命中。今天 C01-B 已增加持久定义身份和追加序，下一步应验证并完善最终发送面，不能再造一套 Composition。

## 决策

1. P0指标以 gateway 的真实 Provider hit/(hit+miss) Token加权统计；主/子/后台、冷/热/恢复全部可对账。每个主力计量模型与总体连续7个完整自然日的每日及7日加权率均>99%。未知计量显式报告，warm-only不代替总体。
2. 同时限制每个验收任务的总输入、miss、输出、成本和耗时；禁止padding、无任务价值预热、保留重复历史来抬高比例。新输入/总输入已超过1%时必须如实报告数学约束。
3. Composition唯一所有者负责定义快照、追加序与版本；动态召回、进度、用户新输入放追加消息。权限撤销优先于缓存稳定。
4. 在最终Provider编码边界生成RequestShapeManifest，记录有序片段、实际工具定义、request/attempt、版本和首个变化位置；早期分层估计不是最终请求事实。
5. 必要能力按稳定bundle暴露，现有search_tools在下一LLM轮边界追加；不按每次心跳重排，不全量暴露工具。技能先目录后按需正文。
6. 后台记忆操作使用增量、去重和有界批处理；能确定性完成的操作不调用模型。关键记忆写回不能等待后台批次。
7. S01-B usage幂等/可靠补记、C01恢复和C02 manifest构成共同验收依赖。部署后核实loadedBuildId，源码测试不能直接推进7日验收。

## 所有权与验收

Runtime Composition/DirectLlmClient负责请求；Platform usage和诊断投影负责对账；Frontend只展示canonical数据。验收覆盖工具发现、撤权、压缩、重启恢复、网络重试、短任务与后台调用。统计不能跨来源重复相加。

每次首轮请求另记ContextStartupSnapshot。12个历史新子会话实际首轮20,847–25,148 Tokens；按同类工作负载验证启动开销下降≥30%，P95目标≤12K且≤有效输入容量20%，超额给出完整分层原因。

## 代价与被否决方案

Manifest持久化和分层归因有存储成本，默认保存计数/hash/引用并做有界保留；不是永久落盘完整Prompt。拒绝第二个PromptRegistry、自动切Provider追缓存、把未命中调用剔除、取消必要工具或靠每轮更换Session清理上下文。

Provider缓存行为有外部不确定性，客户端稳定性测试不等于实际命中证明。若7日门槛未达成，保留InProgress并登记剩余miss，不修改口径宣布成功。
