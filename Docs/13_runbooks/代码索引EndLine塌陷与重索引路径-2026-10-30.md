# 代码索引 EndLine 塌陷与重索引路径（实测）

## 1. 现象

用 ref 打开一个类容器，只返回 1 行：

```
resolved_path   …/SymbolRefIssuer.cs
start_line      58
total_line_count 221
line_count      1          ← 只有 "public sealed class SymbolRefIssuer"
```

查证后确认是**普遍现象**：连续两批抽样共 25 个符号（16 + 9），
`start_line == end_line` **无一例外**。

## 2. 根因

`RoslynCSharpIndexer.AddDeclaration`（修复前）：

```csharp
var lineSpan = symbol.Locations.FirstOrDefault(l => l.IsInSource)?.GetLineSpan() ?? default;
var startLine = lineSpan.StartLinePosition.Line + 1;
var endLine = lineSpan.EndLinePosition.Line + 1;
```

`ISymbol.Locations` 指向的是**名称标识符 token**，不是整个声明跨度 ——
对类、方法、属性、字段都一样，所以跨度恒为单行。

影响不止 `workspace_open`：`FileChunkAssembler` 的分块边界同样按行范围切，
`EndLine` 塌陷会让 chunk 边界一起退化。

## 3. 修复

优先取语法声明跨度，无声明语法（元数据符号等）时才回退标识符位置：

```csharp
var declarationSpan = symbol.DeclaringSyntaxReferences
    .FirstOrDefault()?.GetSyntax().GetLocation().GetLineSpan();
var lineSpan = declarationSpan is { IsValid: true } span
    ? span
    : symbol.Locations.FirstOrDefault(l => l.IsInSource)?.GetLineSpan() ?? default;
```

回归测试 `IndexCompilationAsync_EndLineCoversDeclarationSpan_NotJustIdentifierLine`
断言**跨度**而不是绝对行号（对缩进与命名空间布局不敏感，但仍能抓住塌陷回退）：
`Add` 距 3、`Compute` 距 4、`Calculator` 距 ≥ 10。

三态：

```
基线    1/1 绿
变异    IsValid:false（永远走 fallback）→ 1 失败 / 0 通过
还原    SHA 位级一致 + dotnet build -t:Rebuild（0 警告 0 错误）→ 1/1 复绿
```

## 4. 重索引路径：两条中只有一条可用

### 4.1 可用：watcher 逐文件重索引（双向实测）

在 `SymbolRefIssuer.cs` 头部插入一行注释，再还原：

| 状态 | start_line | end_line | content_hash |
|---|---:|---:|---|
| 原文件 | 196 | 196 | `f187ab90…` |
| 插一行后 | **197** | 197 | `c93e0b6e…` |
| 还原后 | **196** | 196 | `f187ab90…` |

行号与 `content_hash` 双向跟随文件现实 ⇒ **watcher 确实在逐文件重索引**，
且没有陈旧。所以「全仓重建」不必依赖专门的重建 API：
让源文件变化（内容或 mtime）即可，watcher 会自己跟上。

附带实测：`symbol_ref` 里的 `content_hash` 与文件 SHA-256 前 32 位完全一致
（`f187ab90`）—— manifest 指纹就是文件内容哈希。此前只是推断。

### 4.2 不可用：`code_index_register_project(index=true)`

在 `temp/` 下建最小 C# 项目（1 文件 / 1 类 / 1 方法）后登记：

```
register(index=true)  → status=registered「Indexing enqueued」
+45 秒后              → 注册记录 status=Active
实际索引              → 0 符号
index_freshness       → state=unknown
reason                → "scope not attached to the maintenance driver"
```

注册表推进了，索引没跑。⇒ 运行中的 Core 不会为新 scope attach 维护驱动器。
同一个根因也解释了根项目 `PuddingAgent` 的 `status` 自 2026-10-01 起长期停在
`Registering` 不动。

## 5. 生效条件与顺序

修复提交后**不会自动生效**，需要两步，且顺序不可颠倒：

1. **部署**（让运行中的索引器是新代码）
2. **让源文件变化触发重索引**（逐文件，或整体触碰）

反过来的话，重索引仍按旧逻辑计算，得到的依旧是塌陷值 —— 白做一次。

## 6. 复用手法：验证重索引是否发生

1. 记录目标符号的 `start_line` 与文件 SHA-256（前 16 位便于比对）
2. 在文件头插入一行注释（保留原换行风格与无 BOM）
3. 等 60~90 秒
4. 再查同一符号：`start_line` 应整体 +1，`content_hash` 应变化
5. 还原文件（先备份再 `Copy-Item`），复验 SHA-256 位级一致

`start_line` 变化是「重索引确实发生」的可观测信号；
`end_line` 是否仍等于 `start_line` 则是「跑的是新逻辑还是旧逻辑」的判据。

## 7. 同轮踩到的两个仪器坑

1. **`file_patch` 会静默替换中文字**：写入「塌陷」落盘成「塔陷」、「绝对」
   落盘成「绕对」。中文改动必须读回逐字核对；必要时用码点构造脚本绕开。
2. **`Get-Command python` 命中 ≠ Python 可用**：本机命中的是 0 字节
   Store 占位 stub（`ReparsePoint`），执行返回 `exit 9009`
   「Python was not found」。因此 `PythonIndexerBatchTests` 的 6 个失败
   属环境缺失，不是代码回归 —— 判断回归前先确认工具真的可执行。
