### 身份门禁需要哪些字段（逐规则对照，**决定验收怎么判**）

`TrustedCallerDesktopCapabilityAuthorizer`（`Source/Pudding.CapabilityBroker/TrustedCallerDesktopCapabilityAuthorizer.cs`）规则：

| 规则 | 触发条件 | 所需字段 |
|---|---|---|
① | 总是 | `SessionId` 非空（否则直接拒） |
② | 能力带 `RequiresTrustedContext` | 加 `AgentInstanceId` |
③ | 能力带 `Mutating` 或 `HasSideEffects` | 加 `ExecutionId`（且要有 `AgentInstanceId`） |
④ | 能力带 `RequiresUserInteraction` | 加 `UserId` |

对照本场景实际 traits（`Source/Pudding.Contracts/Capabilities.cs` 目录）：

| 能力 | traits | 因此需要 |
|---|---|---|
`browser.screenshot` | `RequiresTrustedContext` + `RequiresPageTarget` | SessionId + **AgentInstanceId**（**只要**①②） |
`browser.interact` | `Mutating` + `HasSideEffects` + `RequiresTrustedContext` + `RequiresPageTarget` | 还要 **ExecutionId**（①②③） |

`ExecutionId` 的来源是 `AgentExecutionService.CreateExecutionTrace`：

```csharp
return trace with { ExecutionId = identity?.RunId, ... };   // Source/PuddingRuntime/Services/AgentExecutionService.cs:1081
```

⇒ **取决于 `RuntimeDispatchRequest.ExecutionIdentity.RunId` 是否非空**。
- 已证实：Agent 执行 → 工具调用的传递在（`AgentExecutionService.Buffered.cs:1156/1857`、`Streaming.cs:1593`、`ToolInvocationService.cs:145`）。
- **未证实**：一次普通心跳驱动的回合里 `RunId` 是否非空（生产侧构造点未定位到；grep 枚举触顶）。

> ⚠️ **由此得出一条会影响验收判读的预测**：启用通道后，**截图（只读）很可能通，而 `browser.interact`（变更类）可能因缺 `ExecutionId` 被规则③拒**。
> 因此第五节**必须把「截图」与「真实输入」分开断言**；若截图通、interact 报 `Unauthorized`（规则③），那是**已知的身份门禁行为**，不是「启用失败」——先确认截图已恢复，再把「为变更类能力补 `ExecutionId`」单独立项。

## 三、精确改动（逐键，两份文件）

### A. Core 侧 `D:\Data\config\system.json`
在**已有的 `"desktop"` 对象内**新增 `capabilityChannel`（该节名来自 `CapabilityChannelConfiguration.SectionName = "Desktop:CapabilityChannel"`）：

```json
"desktop": {
  "core": { "...保持原样不动..." },
  "capabilityChannel": {
    "enabled": true,
    "transport": "named-pipe",
    "desktopId": "default",
    "handshakeTimeoutSeconds": 15
  }
}
```

### B. Desktop 侧 `%LOCALAPPDATA%\Pudding\desktop.json`
把 `"desktop": null` 换成：

```json
"desktop": {
  "capabilityChannel": {
    "enabled": true,
    "desktopId": "default",
    "controlTokenHeader": "x-pudding-control-token",
    "handshakeTimeoutSeconds": 15
  }
}
```

> **关于 `grantable` —— 修正一条此前的错误说法。**
> 此前记作「**必须显式列 `grantable`**，否则静默不可用」。**代码事实相反**：`CapabilityChannelConfiguration.ParseGrantable` 对缺省/空白回落到 `DefaultGrantable`（**已含 `BrowserScreenshot`**），而**空集合或未知线名是「整体失败」并抛错**（`Grantable 为空：没有任何能力会被授予` / `含未登记能力线名`）——是 **fail-loud**，不是静默。因此 **A 里不写 `grantable` 是安全的**；若日后要收紧，可显式列线名（逗号分隔，如 `browser.screenshot,browser.interact,...`）。
> 另：Desktop 侧**没有** `grantable` 字段（`DesktopCapabilityChannelSettings` 无此属性），声明集合由代码 `DeclaredCapabilities` 决定。

## 六、⚠️ 风险再评估（修正前一份报告的「回归风险低」）

前一份报告我写「通道不就绪即回落 Bridge ⇒ 回归风险低」。**这个表述过于乐观，此处更正**：
`TransportRoutedBrowserCapabilitySurface` 的判据是「**有活动通道会话**」，不是「通道可用」。**2026-10-13 14:11 的实测**里，通道确实建立了会话、但逐操作被身份门禁拒绝（`AgentInstanceId` 空）⇒ 属于「**就绪但逐操作失败**」形态，此时**不会回落 Bridge**，浏览器会从「能导航」退回「不可用」。
**缓解**：(a) P1 已修好身份来源且确在运行映像内（§二）；(b) 第五节必须**逐项**跑正向断言，任一项失败即**立即执行第七节回滚**。
