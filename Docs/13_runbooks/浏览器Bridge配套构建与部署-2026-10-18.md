# 浏览器 Bridge 配套构建与部署（D9 / R4–R5）

> 本文是**部署手册**，不是验收完成声明。使用前必须确认维护窗口与在飞任务状态。

## 1. 前置条件（缺一不可）

1. 维护窗口：重启会终止所有在飞 Agent/子代理；先记录它们并通知用户。
2. 干净工作树（`git status` 无未提交改动）与明确提交（记录 SHA）。**其他方 WIP 混入时只能做演练，不得作为发布包**。
3. 已确认本次发布包含 Bridge 协议修订 **3**（两端必须同修订；旧端会在握手阶段被拒绝）。
4. 不直接覆盖运行中目录：先在隔离 artifacts 路径构建，再整套替换。
5. 不读取/复制 `D:\data` 中的密钥；不把产物放入 DataRoot。

## 2. 串行构建（隔离 artifacts，Desktop 与 Core 分开做）

```powershell
$art = 'temp/build/browser-companion'
dotnet restore Source/PuddingAgent/PuddingAgent.csproj --artifacts-path $art --nologo
dotnet build   Source/PuddingAgent/PuddingAgent.csproj --no-restore --artifacts-path $art --nologo
dotnet restore Source/PuddingDesktop/PuddingDesktop.csproj --artifacts-path $art --nologo
dotnet build   Source/PuddingDesktop/PuddingDesktop.csproj --no-restore --artifacts-path $art --nologo
```

注意：Desktop 的 WinUI 输出路径可能仍落在 `temp/build/winui3/...`（项目自定义 OutputPath），以实际 `->` 行为准，不要假设在 `$art/bin` 下。

## 3. 配套核对（R4 门禁，必须在切换前完成）

对 Desktop 输出目录与 Core 输出目录按文件核对：

| 检查 | 期望 |
|---|---|
| `PuddingBrowser.Protocol.dll` SHA-256 | 两目录**相同**（同一 Protocol 构建） |
| `Pudding.Contracts.dll` SHA-256 | 两目录**相同** |
| `PuddingHost.dll`/`PuddingAgent.dll` 与 Desktop 侧 Host 相关模块 | 属于同一提交构建（记录哈希） |
| 协议修订 | 两侧 `BrowserBridgeProtocol.CurrentVersion` 均为 3 |
| 构建身份 | 启动后两端日志出现 `build=... mvid=... path=...`，且与本次构建记录一致 |

只替换 `PuddingBrowser.Protocol.dll` **不能**完成修复：命令结果映射在 Desktop 侧程序集里，消费端逻辑在 Core 侧程序集里。

## 4. 切换步骤

1. 外部控制器正常退出 PuddingDesktop（连带停止 Core；确认无残留进程持有产物）。
2. 备份旧配套包（Desktop 目录 + Core 目录连同其依赖），不要混拷单个 DLL。
3. 整套替换 Desktop 与 Core 目录。
4. 确认 Core 实际解析路径（`CoreExecutableResolver`：显式配置 > `core/PuddingAgent.exe` > 同目录 > 开发路径），**以日志/诊断显示为准**。
5. 由外部控制器启动 PuddingDesktop，观察握手日志：transport connected → 协议修订 3 接受 → 构建身份记录。
6. 不改 `D:\data`；如页面/上下文状态异常，按"新构建重新发现"处理，不手工改数据。

## 5. 分层状态（不得合并成"浏览器可用"）

分别验证并记录：

1. **transport**：Bridge WebSocket 已连接；
2. **protocol**：Hello/Ack 修订 3 匹配；
3. **discovery**：`browser_context(list)`、`browser_tabs(list)` 成功且无 `context.getInfo` 解码错误；
4. **handover**：用户选页后会话状态从"等待确认"变为"已交出"；
5. **tools**：snapshot/locate/interact/screenshot 在已交出页面工作；
6. **business**：TestSite 表单任务 → jd.com 三条用户预期（打开/购物车、正文+截图、搜袜子比价加购）。

握手成功不代表 Agent 可控；发现成功不代表已获得页面控制。

## 6. 功能验收顺序（R5）

1. 先用 TestSite 做自然语言导航/表单/观察，保存模型实际工具序列、operationId、页面版本与答复；
2. 再按用户三条预期验证真实站点；登录/验证码明确停在需要用户处理的状态，不绕过；
3. 截图验收同时确认工件有效与模型请求含图像部件（文本模型不得声称已看图）；
4. 任一失败记录具体阶段与错误码，不归因为"权限/版本"而省略证据；
5. 启动/重启/崩溃恢复/退出回收结论只能由外部控制器给出，与功能验收分开提供。

## 7. 回滚

- 使用上次已验证通过的**完整配套包**（Desktop+Core 同批）回滚，禁止只换回 Protocol.dll。
- 回滚前再次记录当前进程模块身份与在飞任务状态，避免把未知结果当失败重试。

## 8. 已知边界

- `UserDataDirectory` 在发现结果中为空串（执行器契约无目录字段；不读取用户目录）。
- 发现面不提供 active/agentTarget 标志（保守值；工具不得据此准入）。
- 协议不匹配时浏览器工具停止派发，但 Shell 仍应能启动并进入运行中心修复。
- 成套构建与哈希记录目前由本手册人工执行；发布清单自动化与 CI stamp 尚未落地。
