# 浏览器 Bridge 配套构建与部署（D9 / R4–R5）

> 本文是**部署手册**，不是验收完成声明。使用前必须确认维护窗口与在飞任务状态。

## 1. 前置条件（缺一不可）

1. 维护窗口：重启会终止所有在飞 Agent/子代理；先记录它们并通知用户。
2. 干净工作树（`git status` 无未提交改动）与明确提交（记录 SHA）。**其他方 WIP 混入时只能做演练，不得作为发布包**。
3. 已确认本次发布包含 Bridge 协议修订 **3**（两端必须同修订；旧端会在握手阶段被拒绝）。
4. 不直接覆盖运行中目录：先在隔离 artifacts 路径构建，再整套替换。
5. 不读取/复制 `D:\data` 中的密钥；不把产物放入 DataRoot。

## 2. 串行构建完整包

```powershell
pwsh -NoProfile -File TestScripts/build-browser-companion.ps1 -OutputRoot temp/build/browser-companion-<唯一批次>
pwsh -NoProfile -File TestScripts/build-browser-companion.ps1 -OutputRoot temp/build/browser-companion-<唯一批次> -VerifyOnly
```

脚本要求新目录，固定 `OutDir`，使用 `temp/build/recovery` 完成 restore/build；Desktop 的 `BuildCoreBundle` 随后串行发布独立 Core 到该包的 `core/`。保留既有已构建前端，包中必须存在 `core/wwwroot/admin/index.html`。禁止把脚本与其他 Desktop 构建并发执行。

默认拒绝脏工作树。开发故障修复可显式加 `-AllowDirty`，清单标记 `dirty=true`、`purpose=development-repair`，不能冒充干净正式交付；不替别人提交 WIP。脚本在构建成功后生成 `browser-companion.json`，包含源 revision、各进程 MVID/InformationalVersion、两侧协议修订及逐文件 SHA-256；`-VerifyOnly` 可在复制后复核。

## 3. 配套核对（R4 门禁，必须在切换前完成）

对 Desktop 输出目录与 Core 输出目录按文件核对：

| 检查 | 期望 |
|---|---|
| `PuddingBrowser.Protocol.dll`、`Pudding.Contracts.dll` SHA-256 | 分别等于清单对应路径的哈希；不同构建路径/目标框架可能产生不同字节，不要求两侧哈希相等 |
| `core/PuddingHost.dll`、`core/PuddingAgent.dll` 与 `PuddingDesktop.dll` | 同次构建记录，各自符合清单；Shell 根目录不放 Host |
| 协议修订 | 两侧 `BrowserBridgeProtocol.CurrentVersion` 均为 3 |
| 构建身份 | 启动后两端日志出现 `build=... mvid=... path=...`，且与本次构建记录一致 |

只替换 `PuddingBrowser.Protocol.dll` **不能**完成修复：命令结果映射在 Desktop 侧程序集里，消费端逻辑在 Core 侧程序集里。

## 4. 切换步骤

1. 外部控制器正常退出 PuddingDesktop（连带停止 Core；确认无残留进程持有产物）。
2. 备份旧配套包（Desktop 目录 + Core 目录连同其依赖），不要混拷单个 DLL。
3. 切换到完整包，或整套替换 Desktop 与 Core 目录并再运行 `-VerifyOnly`。保留旧包供回退。
4. 确认 Core 实际解析路径（`CoreExecutableResolver`：显式配置 > `core/PuddingAgent.exe` > 同目录 > 开发路径），**以日志/诊断显示为准**。
5. 由外部控制器启动 PuddingDesktop，观察握手日志：transport connected → 协议修订 3 接受 → 构建身份记录。
6. 数据仍由应用正常使用；如页面/上下文状态异常，按“新构建重新发现”处理，不重置数据库或手工删锁。

`%LOCALAPPDATA%/Pudding/desktop.json` 中的显式 `coreExecutablePath` 会优先于包内 Core。备份后将它指向当前完整包的 `core/PuddingAgent.exe`，或清空该字段以使用包内发现。不能只更新 Desktop 后继续指向旧 `Source/PuddingAgent/bin/...`。用户的其他 Desktop 设置保持原值。

`bootstrap_reboot(desktop-build)` 当前默认构建的是 `Source/PuddingAgent/PuddingAgent.csproj`，停止/启动的也是 Core；名称不能作为“两个进程已更新”的证据。涉及 Shell/协议变更必须由外部控制器进行完整配套部署。

## 5. 分层状态（不得合并成"浏览器可用"）

分别验证并记录：

1. **transport**：Bridge WebSocket 已连接；
2. **protocol**：Hello/Ack 修订 3 匹配；
3. **discovery**：`browser_context(list)`、`browser_tabs(list)` 成功且无 `context.getInfo` 解码错误；
4. **session**：当前 V1 默认授权路径可在合法主 Agent 调用时建立目标会话；显式撤销、接管及其他所有者冲突仍按权威拒绝，不把 UI “等待确认”文字当成唯一准入证据；
5. **tools**：snapshot/locate/interact/screenshot 在合法目标页面工作；
6. **business**：TestSite 表单任务 → jd.com 三条用户预期（打开/购物车、正文+截图、搜袜子比价加购）。

握手成功不代表 Agent 可控；发现成功不代表已获得页面控制。

## 6. 功能验收顺序（R5）

1. 先用 TestSite 做自然语言导航/表单/观察，保存模型实际工具序列、operationId、页面版本与答复；
2. 再按用户三条预期验证真实站点；登录/验证码明确停在需要用户处理的状态，不绕过；
3. 截图验收同时确认工件有效与模型请求含图像部件（文本模型不得声称已看图）；
4. 任一失败记录具体阶段与错误码，不归因为"权限/版本"而省略证据；
5. 启动/重启/崩溃恢复/退出回收结论只能由外部控制器给出，与功能验收分开提供。

## 7. 回滚

- 使用上次已验证通过的**完整配套包**（Desktop+Core 同批）回滚，禁止只换回 Protocol.dll。
- 回滚前再次记录当前进程模块身份与在飞任务状态，避免把未知结果当失败重试。

## 8. 已知边界

- `UserDataDirectory` 在发现结果中为空串（执行器契约无目录字段；不读取用户目录）。
- 发现面不提供 active/agentTarget 标志（保守值；工具不得据此准入）。
- 协议不匹配时浏览器工具停止派发，但 Shell 仍应能启动并进入运行中心修复。
- 本地配套构建、哈希清单及复制后验证由脚本完成；CI 发布签名和运行时自动清单验证另行实施。
- Core 的 `Hello rejected` 日志包含错误码与 expected/received；没有 `Hello: desktop=` 但立即拒绝时，先检查外层 envelope 版本。Desktop 不应把已收到的协议拒绝报告为超时。坏 JSON 日志不含原始消息。
