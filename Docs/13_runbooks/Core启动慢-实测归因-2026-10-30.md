# Core 启动慢的实测归因（部署候选冷启动）

## 1. 结论摘要（先说能站住的，再说没站住的）

**已证实**

1. 2026-10-30 的部署回滚**不是**代码缺陷导致的崩退，而是「新实例没在 guardian 的
   `startupTimeoutSeconds(120s)` ＋ `stableSeconds(15s)` 窗口内完成启动并稳定」。
   代码位置：`Source/PuddingDesktop.Guardian/GuardianController.cs` 的 `WaitHealthyAsync`
   （`deadline = now + 120s`，另要求连续 15s healthy）。
2. 慢的是 **`services-registered` 这一段**，不是 schema、不是 middleware，也不是网络连接超时：

   | 实例 | logging-ready | services-registered delta | initialized |
   |---|---|---|---|
   | 09:49 部署候选（失败） | 14.7s | **51.9s** | 72.1s |
   | 09:59 部署候选（成功） | 7.1s | **24.7s** | 34.1s |
   | 09:50 回滚恢复实例 | 0.4s | **0.9s** | 3.3s |
   | 当日稳态实例（8 次抽样） | 2.4~3.2s | **6.7~9.6s** | 12.0~15.8s |

   该段标记在 `PuddingApplicationHost.cs:346`，紧跟 `AddPuddingApplicationServices(...)`
   ——**纯 DI 注册，不含网络调用**。
3. 失败那次的时间差是**约 1 秒**：Core ready≈09:50:14，+15s 稳定 = 09:50:29，
   而窗口 09:50:28 到期。

**未证实（不要当结论用）**

- 慢的机制。最早怀疑「MCP 连接阻塞」——**证据不足**：错误日志里确实有
  `ModelContextProtocol.Client.StreamableHttpClientSessionTransport → HttpClient.SendAsync`
  的取消记录，但 MCP 的连接发生在 `McpWorkspaceSkillHostedService.StartAsync`
  （hosted service 启动阶段，日志里排在 `[ConnectorHost] Starting P2P discovery...` 前后），
  而 `services-registered` 在它**之前**。两者是不同的阶段，不能混为一谈。
- 「冷启动」这个解释**方向上有支持**（同一套候选二进制的第二次部署快了一半：51.9s → 24.7s；
  而回滚恢复的旧文件只要 0.9s），但缺少「同一套新文件第二次启动」的直接对照样本。

## 2. 已被证伪的旧说法

- ❌「`system.json` 的 `desktop.core.startupTimeoutSeconds=60` 是闸门」：失败实例在 72s 时仍在
  持续输出 `[StartupPhase]`，从未被打断。该值语义是**无进度静默超时**，不是总时长上限。
  （2026-10-30 曾把它 60→180，对本次故障没有起到解释作用。）
- ❌「`workspace_open` 传非法 ref 报『前缀不符』即可判新代码已上线」：`TokenPrefix` 校验
  早于旧产物，新旧都报同一句。判活产物只认 `runtime_identity.informationalVersion`
  （带 commit sha）＋ 活目录 DLL mtime/SHA。

## 3. 怎么读日志（可复现）

```
D:\Data\logs\system\pudding-<yyyyMMdd>_NNN.log   # 一个进程实例一段，段小=该实例短命
```

- 段首行 `[StartupPhase] logging-ready total=Nms` 的 `N` 即该实例启动到那一刻的耗时，
  用「段首行时间 − N」反推进程起点。
- `services-registered total=Xms delta=Yms` 的 **delta 才是这一段耗时**（total 是累计）。
- 被 guardian 杀掉的实例，日志会在 hosted service 启动处**截断**（例：`[ConnectorHost]`）。

采集脚本：`temp/scan_startup.ps1`（ASCII-only，按实例汇总 ready/init/svcDelta）。

## 4. 处置选项（按代价排序）

| 选项 | 代价 | 覆盖范围 | 备注 |
|---|---|---|---|
| A. guardian 窗口 120s → 240s（或 `stableSeconds` 15 → 8） | 改 `%LocalAppData%\Pudding\guardian.json`，**需 guardian 重启** | 只是兜底 | 不治慢，只把「差 1 秒」变成不致命 |
| B. 对部署目录加 Defender 排除 + 部署后预热一次 | 需管理员权限，属系统级变更 | 若归因成立可直接治本 | **需用户批准** |
| C. 给 `services-registered` 段加细粒度计时探针 | 改代码 + 一次部署 | 把「未证实」变成「已证实」 | 需要一次部署（本身就有冷启动风险，A 应先做） |
| D. 把 MCP 重连/初始化改为非阻塞（不占启动路径） | 改代码 | 只治 MCP 那一段 | 先确认 MCP 是否真在启动路径上贡献耗时 |

**建议顺序**：A（低成本兜底）→ C（取到证据）→ 再决定 B 或 D。

## 5. 判据

- 做 A 之后，同一套候选即使 `initialized` 到 72s 也应成功；
- 做 C 之后，日志应能区分「程序集装载 / 反射扫描 / EF 模型构建」各自耗时，
  若三者都不是主项，则冷启动解释站不住，要换方向。

## 6. 实测结果：分段打点已给出归因（2026-10-30 10:31 实例，`dc8b23f`）

`services-registered` 段按 §4 选项 C 拆成六个打点后，一次成功部署即取到完整数据
（实例 `pudding-20261030_024.log`，`initialized total=47208ms`、`ready total=52445ms`）：

| 打点 | total | delta |
|---|---|---|
| `logging-ready` | 10,727ms | 155ms |
| `services-registering` | 15,910ms | **5,183ms** |
| `services-platform` | 26,035ms | **10,125ms** |
| `services-runtime` | 44,588ms | **18,553ms** ← 主体 |
| `services-connectors` | 44,589ms | 1ms |
| `services-bootstrap` | 44,590ms | 1ms |
| `services-browser` | 44,600ms | 10ms |
| `services-registered` | 44,600ms | 0ms |

**结论（已证实）**

1. 旧口径「`services-registered` 段 24~52s」现在可拆成四块：注册前 wiring 5.2s、
   `AddPlatformServices` 10.1s、`AddRuntimeServices` **18.6s**、其余 12ms。
2. **`AddRuntimeServices` 是主体**（占该段 81%）。`connectors` / `bootstrap` / `browser`
   合计 12ms，**可以排除**。
3. 因此「MCP 连接」与「connectors 注册」都不是这一段的主因，方向应转向
   `AddRuntimeServices` 内部的程序集扫描 / 反射 / EF 模型构建。

**仍未证实**

- `AddRuntimeServices` 内部哪一部分占 18.6s（需要再下一层打点）。
- 冷启动效应是否仍成立：本例只有一次样本，且这次 47.2s 已接近稳态（12~16s）的 3 倍，
  与「第二次启动减半」的观察不矛盾，但也未被独立验证。

**下一层的做法**：在 `AddRuntimeServices` 内部按「平台无关 / 宿主 / 工具体 / 记忆 / 调度」
等分组再加打点，一次部署即可把 18.6s 继续拆开。

## 7. guardian 配置现状（2026-10-30 10:45）

- `%LocalAppData%\Pudding\guardian.json` 的 `startupTimeoutSeconds` 已 120 → **240**
  （备份 `guardian.json.bak-20261030-1045`，JSON 可解析、无 BOM、925 字节）。
- ⚠️ **磁盘是 240，Guardian 进程内存里仍是 120**：`Program.cs` 在进程启动时反序列化一次，
  `GuardianController` 构造时算好 `_startupDeadline`。Guardian（pid 52944）自 10-26 存活，
  且父进程 31888 已退出（orphan，无监督者自动拉起）⇒ **未主动重启它**，
  新值留待 Guardian 下次自然重启生效。判断实际生效值要看 Guardian 进程启动时间，不看配置文件。
- 选项 B（Defender 排除）**未能执行**：当前会话 `IsInRole(Administrator)=False`，
  `Get-MpPreference` 报 `N/A: Must be an administrator to view exclusions`。

## 8. 杀软假设已证伪（2026-10-30 10:55，零成本观测）

```
Get-MpComputerStatus
  RealTimeProtectionEnabled  : False     ← 实时保护未开
  OnAccessProtectionEnabled  : False     ← 按访问扫描未开
  AntivirusEnabled           : True      ← 只是 Defender 服务在，防护没开
```

⇒ **「Defender 扫描部署目录里的 157 个 DLL / 111 MB 导致启动慢」不成立**，
§4 的选项 B（加 Defender 排除）**没有必要做**，与是否具备管理员权限无关。
（此前把「需要管理员权限」列为 B 的阻塞条件，前提本身是错的，一并撤回。）

同时确认 `AddRuntimeServices`（87–611 行，共 524 行）的静态性质：

- 方法体内 100% 是 `AddSingleton` / `AddScoped` / `AddHostedService` 注册；
- 仅有的两处同步阻塞（`LoadSystemAsync().GetAwaiter().GetResult()` @143、
  `LoadLlmProvidersAsync().GetAwaiter().GetResult()` @533）**都在工厂 lambda 内**，
  注册阶段不会执行；
- 方法体内**没有** `Assembly.GetTypes()` / `Activator` / 目录扫描等即时重活。

⇒ 18.5 秒**不可能**来自逻辑 I/O。剩下两个候选：

| 候选 | 检验方式 |
|---|---|
| **H1 冷启动**：首次 JIT + 157 个程序集按需装载 | 同一份二进制**第二次启动**的 `services-runtime` delta 应显著下降 |
| **H2 注册本身有隐藏开销**（某几个 `AddXxx` 触发了意外工作） | 若第二次启动仍 ≈18.5s，则 H1 出局，需在方法体内再分段 |

**判据**：用 `bootstrap_reboot action=restart`（只重启、不重建，产物目录不变）取第二次启动样本。
- `services-runtime delta` 显著小于 18,553ms ⇒ H1 成立，18.5s 是首次成本，非回归；
- 仍接近 18,553ms ⇒ H1 出局，转 H2 继续拆。

## 9. H1 已证实：同一份产物，二次启动快 12 倍（2026-10-30 10:48 实例）

### 9.1 对照条件（单变量）

- **产物完全未变**：`PuddingRuntime.dll` 5,242,880 B / mtime **10:30:34**；两次启动之间没有任何构建、没有部署、没有替换文件。
- **冷样本**：10:31:40 起的进程（部署后首次启动，`dc8b23f`）。
- **温样本**：10:48:58 起的进程（同目录、同一批 DLL，仅重启）。
- **唯一变量**：这批程序集在本机是否已被读过一次。

### 9.2 实测（累计毫秒）

| 打点 | 冷 10:31 | 温 10:48 | 倍数 |
|---|---:|---:|---:|
| `logging-ready` | 10,727 | 111 | 97× |
| `services-registering` | 15,910 | 189 | 84× |
| `services-platform` | 26,035 | 236 | 110× |
| `services-runtime` | 44,588 | 308 | 145× |
| `services-registered` | 44,600 | 312 | 143× |
| `host-built` | 44,734 | 345 | 130× |
| `middleware-mapped` | 45,660 | 479 | 95× |
| `initialized` | 47,208 | **1,791** | 26× |
| `ready` | 52,445 | **4,276** | **12×** |

段内 delta：`AddRuntimeServices` 冷 **18,553ms** → 温 **72ms**（258×）。
`schema-*` 全部段合计冷 1,548ms / 温 1,312ms ⇒ **几乎恒定，不是问题所在**。

### 9.3 能说与不能说

**能说（H1 成立）**：慢的主因是「这批程序集在本机首次被使用」的一次性开销，**不是** `AddRuntimeServices` 里的注册逻辑。
判据是同一份二进制重启一次就把 `initialized` 从 47.2s 压到 1.8s——任何代码级逻辑都不会因重启而消失，**H2（注册隐藏开销）因此出局**。

**不能说（诚实边界）**：尚未把「首次开销」进一步拆成
(a) 系统文件缓存未命中导致的磁盘读，还是 (b) Windows 首次执行新二进制时的 SysMain/Prefetch 行为。
反证线索：部署时文件是会被写入目标目录的，写入本应让页面缓存变热，但 10:31 那次仍然冷 ⇒ 单纯「拷贝后缓存热」的推论不成立。
注意 `logging-ready` 段（几乎不含业务类型装载）也从 10.7s 降到 0.1s，说明影响面覆盖整个进程，不只是 DI 类型图。

**因此**：把 18.5s 归因到「磁盘慢」是**过度解读**，本文件不采用该说法。

### 9.4 这条结论直接解释了 09:49 的部署失败（算术）

`GuardianController.WaitHealthyAsync` 的窗口在 `StartAsync` 返回后起算；而 target=desktop 且 Desktop 已死时，
`StartAsync` 只负责拉起 Desktop 就 `return`（`AutoStartCore` 时 Core 由 Desktop 拉起，窗口不等它）。

09:49 那次的窗口账：

| 项 | 实测 |
|---|---|
| Desktop 冷启动（窗口起点） | 09:48:28 |
| Core 进程 t0（由 `logging-ready 14,698ms` 反推） | 09:49:00.7 |
| Core `initialized` | 09:50:12.8（t0 + 72.1s） |
| Core `ready` | ≈ 09:50:15 |
| 稳定观察 `StableSeconds` | +15s ⇒ ≈ 09:50:30 |
| **窗口到期** | **09:50:28** |

⇒ 差 **约 2 秒**被判 `TimeoutException`。窗口 120s 里被 Desktop 冷启动吃掉约 32s，Core 冷启动吃掉约 75s，
**两次冷启动叠加才刚好越界**——这也解释了为什么四次部署成败看起来像随机的。

### 9.5 处置（按「能否由我独立执行」排序）

| # | 措施 | 性质 | 状态 |
|---|---|---|---|
| A | guardian `startupTimeoutSeconds` 120 → 240 | 磁盘已改（`bak-20261030-1045`），**需 guardian 进程重启才生效**；guardian pid 为 10-26 起的孤儿进程，无监督者，不自杀 | 待用户批准重启 |
| B | 部署前预热：顺序读一遍目标目录全部 DLL 再启动 | 只能解决 (a) 类机制，对 (b) 无效 | 未做，需先定 9.3 的 (a)/(b) |
| C | 减少程序集数量（157 个） | 根治，代价大 | 未做 |
| D | `PublishReadyToRun` | R2R 镜像更大 ⇒ 可能加重冷 I/O，方向不明确 | 不建议先做 |

### 9.6 下一步的判据

- 若要把 9.3 的 (a)/(b) 分开：需要一次「人为制造冷缓存」的实验（如重启系统后立即启动），当前权限与窗口内无法安全构造 ⇒ **暂不开展**，不臆造结论。
- 无论 (a) 还是 (b)，**A 都是必要条件**：冷路径实测已达 75s（Core）+ 32s（Desktop）+ 15s（稳定）= 122s > 120s。
