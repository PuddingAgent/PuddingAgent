# Core 启动慢的实测归因（部署候选冷启动）

## 1. 结论摘要（先说能站住的，再说没站住的）

**已证实**

1. 2026-10-30 的部署回滚**不是**代码缺陷导致的崩退，而是「新实例没在 guardian 的
   `startupTimeoutSeconds(120s)` ＋ `stableSeconds(15s)` 窗口内完成启动并稳定」。
   代码位置：`Source/PuddingDesktop.Guardian/GuardianController.cs` 的 `WaitHealthyAsync`
   （`deadline = now + 120s`，另要求连续 15s healthy）。
2. 慢的是 **`services-registered` 这一段**，不是 schema、不是 middleware，也不是网络连接超时：

   | 实例 | logging-ready | services-registered delta | initialized |
   |---|---|---|---|
   | 09:49 部署候选（失败） | 14.7s | **51.9s** | 72.1s |
   | 09:59 部署候选（成功） | 7.1s | **24.7s** | 34.1s |
   | 09:50 回滚恢复实例 | 0.4s | **0.9s** | 3.3s |
   | 当日稳态实例（8 次抽样） | 2.4~3.2s | **6.7~9.6s** | 12.0~15.8s |

   该段标记在 `PuddingApplicationHost.cs:346`，紧跟 `AddPuddingApplicationServices(...)`
   ——**纯 DI 注册，不含网络调用**。
3. 失败那次的时间差是**约 1 秒**：Core ready≈09:50:14，+15s 稳定 = 09:50:29，
   而窗口 09:50:28 到期。

**未证实（不要当结论用）**

- 慢的机制。最早怀疑「MCP 连接阻塞」——**证据不足**：错误日志里确实有
  `ModelContextProtocol.Client.StreamableHttpClientSessionTransport → HttpClient.SendAsync`
  的取消记录，但 MCP 的连接发生在 `McpWorkspaceSkillHostedService.StartAsync`
  （hosted service 启动阶段，日志里排在 `[ConnectorHost] Starting P2P discovery...` 前后），
  而 `services-registered` 在它**之前**。两者是不同的阶段，不能混为一谈。
- 「冷启动」这个解释**方向上有支持**（同一套候选二进制的第二次部署快了一半：51.9s → 24.7s；
  而回滚恢复的旧文件只要 0.9s），但缺少「同一套新文件第二次启动」的直接对照样本。

## 2. 已被证伪的旧说法

- ❌「`system.json` 的 `desktop.core.startupTimeoutSeconds=60` 是闸门」：失败实例在 72s 时仍在
  持续输出 `[StartupPhase]`，从未被打断。该值语义是**无进度静默超时**，不是总时长上限。
  （2026-10-30 曾把它 60→180，对本次故障没有起到解释作用。）
- ❌「`workspace_open` 传非法 ref 报『前缀不符』即可判新代码已上线」：`TokenPrefix` 校验
  早于旧产物，新旧都报同一句。判活产物只认 `runtime_identity.informationalVersion`
  （带 commit sha）＋ 活目录 DLL mtime/SHA。

## 3. 怎么读日志（可复现）

```
D:\Data\logs\system\pudding-<yyyyMMdd>_NNN.log   # 一个进程实例一段，段小=该实例短命
```

- 段首行 `[StartupPhase] logging-ready total=Nms` 的 `N` 即该实例启动到那一刻的耗时，
  用「段首行时间 − N」反推进程起点。
- `services-registered total=Xms delta=Yms` 的 **delta 才是这一段耗时**（total 是累计）。
- 被 guardian 杀掉的实例，日志会在 hosted service 启动处**截断**（例：`[ConnectorHost]`）。

采集脚本：`temp/scan_startup.ps1`（ASCII-only，按实例汇总 ready/init/svcDelta）。

## 4. 处置选项（按代价排序）

| 选项 | 代价 | 覆盖范围 | 备注 |
|---|---|---|---|
| A. guardian 窗口 120s → 240s（或 `stableSeconds` 15 → 8） | 改 `%LocalAppData%\Pudding\guardian.json`，**需 guardian 重启** | 只是兜底 | 不治慢，只把「差 1 秒」变成不致命 |
| B. 对部署目录加 Defender 排除 + 部署后预热一次 | 需管理员权限，属系统级变更 | 若归因成立可直接治本 | **需用户批准** |
| C. 给 `services-registered` 段加细粒度计时探针 | 改代码 + 一次部署 | 把「未证实」变成「已证实」 | 需要一次部署（本身就有冷启动风险，A 应先做） |
| D. 把 MCP 重连/初始化改为非阻塞（不占启动路径） | 改代码 | 只治 MCP 那一段 | 先确认 MCP 是否真在启动路径上贡献耗时 |

**建议顺序**：A（低成本兜底）→ C（取到证据）→ 再决定 B 或 D。

## 5. 判据

- 做 A 之后，同一套候选即使 `initialized` 到 72s 也应成功；
- 做 C 之后，日志应能区分「程序集装载 / 反射扫描 / EF 模型构建」各自耗时，
  若三者都不是主项，则冷启动解释站不住，要换方向。
