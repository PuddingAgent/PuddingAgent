# 外部部署与产品验收（上下文治理修复）

## 1. 边界（两段式验收，强制）

- **内部 Agent 只能交付 `ready-for-external-deploy`**：它可以测试当前进程已加载的成品，
  但**不能**证明刚改的代码已被加载，也不能独立验收承载自身的 Desktop/Core 生命周期。
- **进程外控制器**负责：重启到明确的新构建、以及启动/重启/崩溃恢复/退出回收结论。
- 部署完成后由**新会话**做功能 smoke；此前**不得**报告「省时」或升级为 `in-product-functional-complete`。

## 2. 身份链路（为什么必须三步都核对）

```
Source/PuddingPlatformAdmin/package.json 的 version            ← 版本唯一真源
        │ pnpm run build
        ▼
Source/PuddingPlatformAdmin/dist/**                            ← 构建产物（带注入身份）
        │ Core 构建时 PuddingHostContent.props 复制
        ▼
Source/PuddingAgent/bin/<Config>/net10.0/wwwroot/admin/**       ← Core **实际读取**的静态产物
        │ 运行中实例
        ▼
页角徽标 v<version>[+dirty] · <短哈希> · <构建时间>              ← 「用的到底是哪一份构建」的唯一凭据
```

**只重新构建前端不会生效；只重启 Core 也不会重新部署静态产物。**
`+dirty` 说明构建时工作树有未提交改动 ⇒ 产物不可复现 ⇒ **不得作为交付构建**。

## 3. 步骤

### 3.1 干净检出到明确提交（不得在工作树脏的副本上出交付产物）

```powershell
git worktree add temp/deploy-build <PINNED_COMMIT>
cd temp/deploy-build
git status --porcelain      # 必须为空；非空 ⇒ 产物必带 +dirty
```

### 3.2 前端构建

```powershell
cd Source/PuddingPlatformAdmin
pnpm install
pnpm run build
```

### 3.3 Core 构建（把 dist 复制进 wwwroot/admin）

```powershell
# 旧实例还在跑时（bin 被占用 ⇒ MSB3027/MSB3021）：用隔离输出，可以**先构建、后停机**
dotnet build Source/PuddingAgent/PuddingAgent.csproj --artifacts-path temp/build/deploy --nologo

# 或者先停旧实例，再直接构建到 bin
dotnet build Source/PuddingAgent/PuddingAgent.csproj --nologo
```

> **顺序很重要**：Core 构建只是把 **`PuddingPlatformAdmin/dist` 当时的内容**复制进 `wwwroot/admin`
> （见 `PuddingHostContent.props`）。因此**必须先重建前端、再构建 Core**；顺序颠倒或前端未重建时，
> Core 会把**旧 dist** 一起打包（2026-10-08 实测：HEAD 已是 `c34a695`，而构建出的
> `wwwroot/admin` 身份仍是上一份 dist 的 `7545ea1`，正是这个原因）。

### 3.4 身份预检（门禁，只读；R5 强化后必须显式给参）

自 2026-10-12 起脚本分 **artifact 阶段**与 **live 阶段**，且**必须显式给** `-ArtifactRoot` 与
`-ExpectedCommit`（不再从仓库里挑"最新 admin 目录"，那只能证明磁盘有新产物，不能证明运行实例已加载）。

```powershell
# ① artifact 阶段（可在旧实例仍在运行时做）：核对 源码 / dist / 构件根（逐文件清单）
#    并要求 HEAD == -ExpectedCommit、工作树干净；同时 pin 构件根里 PuddingAgent.dll 的 SHA256。
& ./TestScripts/verify-external-deploy-identity.ps1 `
    -ArtifactRoot temp/build/deploy -ExpectedCommit <pin 住的提交>

# ② 只验证 artifact、明确不声称运行实例已加载（结论会标 ARTIFACT-ONLY）
& ./TestScripts/verify-external-deploy-identity.ps1 `
    -ArtifactRoot temp/build/deploy -ExpectedCommit <pin 住的提交> -ArtifactOnly

# ③ 完整预检（停机重启之后）：再加 -BaseUri，脚本会
#    - 读取运行中进程目录下 PuddingAgent.dll 的 SHA256 与构件根比对（实际加载的构建）
#    - HTTP 拉取 /admin/index.html 比字节，并拉取其引用脚本核对**运行中前端注入身份**
& ./TestScripts/verify-external-deploy-identity.ps1 `
    -ArtifactRoot temp/build/deploy -ExpectedCommit <pin 住的提交> -BaseUri http://127.0.0.1:<port>
```

退出码：`0` = 全部要求阶段通过（`-ArtifactOnly` 时只代表 artifact 通过，输出会标明）；
`1` = artifact 阶段失败；`2` = live 阶段失败或 **unknown**；`3` = 两者都失败/unknown。
**读不到运行身份（未给 `-BaseUri`、进程不存在、进程路径不可读、HTTP 失败、脚本里读不到注入身份）
一律 unknown + 非零，绝不打印 live 通过。**

每一步都独立拒绝 `+dirty`（工作树 / dist / 构件根 / live 各算一环）；同版本不同 commit 也会被拒。
预检通过后再按 §3.5 起做重启与 §3.6 徽标核对。

### 3.5 外部控制器重启到该构建

- 停止旧 Core → 启动新构建（`--desktop-child` 或 `dev-up`，**同一 DataRoot 不得同时跑两个 Core**）。
- 本步骤的启动/重启/崩溃恢复/退出回收**结论由外部控制器给出**。

### 3.6 徽标与 loaded identity 核对

打开任意页面，右下角徽标应为：

```
v<PINNED_VERSION> · <短哈希> · <构建时间>
```

- **必须与 pinned commit 的短哈希一致**；
- **不得出现 `+dirty`**（出现即说明产物来自脏工作树，需重做 3.1）。

### 3.7 新会话真实 smoke（三项**分别**记录，不得合并）

| 指标 | 含义 | 采集方式 |
|---|---|---|
| accepted→首个推理增量 | 用户提交到 UI 出现第一条 reasoning 的时间 | 前端/服务端计时事实（`providerFirstReasoningMs` 等） |
| accepted→首个正文增量 | 到第一条正文的时间 | 同上（`firstContentFrameMs` / `providerFirstContentMs`） |
| 浏览器首绘 | 页面/流式容器首次绘制 | 浏览器侧观察（DevTools/录像） |

- 三项**分开记录**并各自标注来源与分母；
- 单条样本不得外推；不得把「受理→首推理」写成「首 Token 省时」。

## 4. 当前实测状态（2026-10-08，本机）

预检脚本实测输出（`-ArtifactsRoot temp/build/deploy`）：

| 环节 | 实测 | 判定 |
|---|---|---|
| 源码 | `package.json` = **6.4.4**；HEAD `c34a695`；工作树 **脏**（有并行写入方 WIP） | — |
| `frontend-dist` | **6.4.4** / `7545ea1` / builtAt `2026-10-08T17:40:22Z` / **dirty=true** | ✗ 带 dirty，不可作交付产物 |
| `served(wwwroot/admin)`（运行中的 Core 实际读取） | **6.4.1** / `6e978cb` / builtAt `2026-10-08T13:48:34Z` / dirty=true | ✗ 比 dist 旧，静态产物未重新部署 |
| `artifacts(wwwroot/admin)`（`--artifacts-path` 隔离构建） | **6.4.4** / `7545ea1` / **dirty=true**；308 个文件 | ✓ 复制链路通；✗ 但带 dirty 且 dist 是上一份构建 |
| 结论 | `PREFLIGHT FAILED` | **NOT READY**：需按 §3 在干净检出上**先重建前端**、再构建 Core |

已经在本机验证过的两件事（对控制器有用）：

1. **旧实例在跑也能构建**：`dotnet build … --artifacts-path temp/build/deploy` 成功
   （不碰被占用的 `Source/PuddingAgent/bin`），因此可以「先备好新构建 → 再停旧实例 → 换上新产物」，
   缩短停机窗口。
2. **dist → wwwroot/admin 复制链路有效**：隔离产物里的 `wwwroot/admin` 有完整静态资源，
   身份与 dist 完全一致（版本 + 短哈希）—— 说明链路没问题，**唯一阻碍是产物带 `+dirty`**。

> 该结论与「交付状态 ready-for-external-deploy」并不矛盾：后者指**代码侧**已就绪，
> 前者指**运行中实例**尚未加载新代码 —— 两者必须分开表述，禁止混用。

## 5. 回滚

1. 保留上一份 `wwwroot/admin` 与旧产物目录（部署前先整目录备份）；
2. 回滚 = 停新 Core → 恢复旧 `wwwroot/admin` + 旧 Core 构建 → 启动 → 用 §3.4 预检确认身份回到旧版本。
