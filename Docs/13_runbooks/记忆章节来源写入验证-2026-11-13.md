# 记忆章节来源写入验证

代码已把入站用户消息 id 接到章节写入路径，但**运行中的 Core 是旧二进制**，数据库尚未迁移。本文给出重启后判定「是否真的写入」的最小步骤。

## 前置

1. `bootstrap_reboot(target=core)` 完成并确认新进程在跑
2. 在任意会话里真实触发一次 `save_memory`（不要让脚本伪造上下文，要的是真实执行身份）

## 判据（三态，不要合并）

| 状态 | 观察 | 含义 |
|---|---|---|
| 未迁移 | `PRAGMA table_info(Chapters)` 无 `SourceMessageId` | 新二进制没跑起来，或初始化器没执行 |
| 已迁移未写入 | 有列，但 `count(SourceMessageId)` 全为 NULL | 链路在工具侧断了 |
| 通过 | 有列，且新章节的 `SourceMessageId` 能 join 到 `ChatMessages.message_id` 且该行 `Role='user'` | 写入与语义都成立 |

## 步骤 1：确认列已迁移（只读）

```sql
PRAGMA table_info(Chapters);
```

期望出现 `SourceMessageId` 与 `SourceTurnId`。缺列即判「未迁移」，后续不用继续。

## 步骤 2：触发一次真实写入

在会话里让 Agent 保存一条记忆，例如让它 `save_memory` 一条事实。记下这一刻的**用户消息 id**：它应等于随后写入章节的 `SourceMessageId`。

## 步骤 3：核对（只读）

```sql
SELECT c.ChapterId, c.CreatedAt, c.SourceMessageId, m.Role, m.SessionId = c.SourceSessionId AS same_session
FROM Chapters c
LEFT JOIN ChatMessages m ON m.message_id = c.SourceMessageId
WHERE c.SourceMessageId IS NOT NULL
ORDER BY c.CreatedAt DESC
LIMIT 10;
```

判定要点：

- `SourceMessageId` 非空
- `m.Role = 'user'`（**不是 agent**——`ExecutionIdentity.MessageId` 是助手消息 id，接错会在这里暴露）
- `same_session = 1`

## 常见误判

- **「查询返回 0 行」不等于没写入**：历史 13,213 章的该列恒为 NULL（设计如此），必须看 `CreatedAt` 最近的行，而不是全表计数。
- **`SourceTurnId` 也会非空，但它不是判据**：`turn_id` 在用户行上的覆盖率实测只有 4%，Turn 级只作分组用。
- **两库分离**：`Chapters` 在 `pudding_memory.db`，`ChatMessages` 在 `pudding_platform.db`。上述 SQL 跨库，需在应用侧或分别取数后比对，SQLite 单连接跨不了。

## 通过之后

回到评测侧：`PuddingMemoryLab` 的 `bind_chapters.py` 会优先以 `binding=message` 配对，`binding` 字段可直接用于筛出确定对；新数据从此时开始积累，历史无法回填。

## 实测记录（2026-11-13 09:05 重启后）

**结论：三态全部通过。溯源链路是运行时事实，不再是代码层面推断。**

### 前置：部署与进程

| 项 | 实测值 |
|---|---|
| 进程 | PID `81344`，启动 `2026-11-13T01:05:44Z`（= 09:05:44 +08:00） |
| `PuddingRuntime.dll` | `2026-11-13T01:05:14Z`，SHA256 `7C81FA09…59EEA2` |
| 仓库 HEAD | `ae9b7f0`，verdict `at-or-after-head` |

### 态一：迁移

`PRAGMA table_info(Chapters)` 实测列集合含 `SourceTurnId`、`SourceMessageId`
（共 25 列，两列追加在末尾）。`EnsureColumnAsync` 幂等补列生效，历史 13,240 行未被改写。

### 态二：写入

重启后首次 `save_memory` 落库：

```
chapters_total              13240 → 13241
chapters_with_source_message_id   0 → 1
chapterId      766c70190de84e878c212c4a3cc71165
SourceMessageId  fabric-turn-message:b76d3b3a49b318f5ab31828f9ec51e8d
SourceTurnId     6c2b316604f34442801452b5e80883fa
CreatedAt        1794532545575
```

两列均为非空真值，不是 NULL。

### 态三：语义 join

`SourceMessageId` 在 `ChatMessages` 中**精确命中 1 行，且 `Role='user'`**。

`fabric-turn-message:` 前缀并非异常格式——该前缀在 `ChatMessages.message_id` 中共 1577 行，
是 Message Fabric 入站用户消息的正规标识。本次验证前一度误判「该格式 join 不到」，实测证伪。

### 一条附带发现

`SourceTurnId`（`6c2b3166…`，32 位 hex）在 `ChatMessages.turn_id` 中**精确匹配 0 行**。
即 Turn 级标识不可用于跨库 join，只能作应用侧分组。
这与先前测得的「`turn_id` 在 user 行覆盖率 4%」一致，进一步确认 **`SourceMessageId` 才是配对主键**。

### 复验方法（可重跑）

活库被运行中的 Core 持有，跨 WSL `/mnt/d` 只读打开 WAL 模式活库会报 `disk I/O error`。
已验证的路径是**复制三件套到 `.work/verify/`**（`.(db, -wal, -shm)`，`.work/` 已在 `.gitignore:461`）
再用 WSL python 读副本。探针脚本：`.work/verify/schema_probe.py`、`.work/verify/join_probe.py`。

注意 `Chapters` 主键列名是 `ChapterId`，**不是** `Id`。
