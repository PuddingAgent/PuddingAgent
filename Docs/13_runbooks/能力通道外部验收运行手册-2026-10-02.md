# 能力通道外部验收运行手册（8 步）

## 目的与边界

本手册供**进程外控制器**验收「Desktop 主动建立 gRPC 双向流、Core 经该流下发能力命令」这条迁移目标
（技术方案 §2/§5，切片 F 的启用与退役判据）。

**为什么必须由进程外控制器执行**：运行在 Pudding 内部的 Agent 无法验收承载自身的生命周期 ——
单实例会把第二次启动转发给旧进程、退出后无法观察子进程回收；
内部 Agent 也无法证明"刚改的代码已被当前进程加载"（见 `AGENTS.md` 两段式验收）。

**本手册不覆盖**：普通业务 HTTP 通道、事件通道、WebSocket Bridge 的**代码级**退役
（那是拿到本手册第 6 步证据之后的独立改动）。

## 前置条件

1. **构建**：Release 构建（`--artifacts-path temp/build/recovery`，先 restore 再 `--no-restore`），
   产出明确的新版本号/哈希（用于核对"加载的是新构建"）。
2. **隔离环境**：隔离的 DesktopHome、DataRoot 与端口（参考 `TestScripts/test-pudding-desktop-launcher.ps1`）；
   **不得**在 `D:\data` 上直接试跑旧代码。
3. **浏览器自动化开启**：Desktop 侧 `browserAutomationEnabled`（或产品等价开关）为真，
   否则七个 Browser 工具不会装配。
4. **能力通道开启**：`desktop.json` 的 `desktop:capabilityChannel` **缺省为关闭**，
   必须显式打开：

   ```json
   {
     "desktop": {
       "capabilityChannel": { "enabled": true }
     }
   }
   ```

   其余字段按 `DesktopCapabilityChannelSettings` 的默认值。
   Desktop 侧启动路径为 `DesktopApplicationCoordinator.Capability.StartCapabilityChannelAsync`，
   关闭时会记录「未启用（desktop.json 的 desktop:capabilityChannel 缺省关闭），继续走既有 WebSocket Bridge」。

## 验收步骤

| # | 步骤 | 通过判据 |
|---|---|---|
| 1 | 启动 PuddingDesktop（通道已启用） | Desktop 与 Core 均就绪；Desktop 日志出现能力通道建立信息；**握手声明**里包含 Desktop 实际实现的能力（含 `browser.context.create` / `browser.context.close`，共 16 个） |
| 2 | 在**新**会话中跑七个 Browser 工具：`browser_context`（create/list/get/close）、`browser_tabs`、`browser_navigate`、`browser_snapshot`、`browser_locate`、`browser_interact`、`browser_wait_for` | 七个工具全部返回真实页面结果；`browser_interact` 的空文本 `fill` 可用（清空输入框，缺口 #13） |
| 3 | 逐项核对"事实而非失败"的语义 | 导航被拒仍是**事实**（带回状态码/错误文本）；等待超时标注 `TimedOut` 而非失败；定位命中 0 个不是错误 |
| 4 | 版本固定语义 | 用过期 `PageVersion` 交互 ⇒ 明确拒绝（`stale_page_version` 类错误）；快照/页状态在页面变化后刷新版本 |
| 5 | **Crash 场景**：强杀 Core 进程 | Desktop 窗口存活、可进入设置/运行中心；按自动恢复策略重启 Core；重启后通道重新建立（`ConnectionGeneration` 递增） |
| 6 | **退役判据**：读取传输用量 | 结构化日志出现 `transport(channel=N, legacy=0, noRoute=0, retire=true)` 形态（`DesktopTransportUsage.ToString()`），即窗口内**零次**回退到旧 Bridge、零次无路由；`CanRetireLegacyBridge` 为真 |
| 7 | **正常退出**：从托盘菜单「退出 Pudding」 | Core 子进程被回收（任务管理器无残留）；WebView2 释放；再次启动是**新**进程 |
| 8 | **单实例语义**：在已运行时再次启动 `PuddingDesktop.exe` | 第二次启动被转发给既有实例（不产生第二个 Desktop 进程），既有窗口被激活 |

## 证据清单（交付 `ready-for-external-deploy` → `in-product-functional-complete`）

- 新构建的版本号/哈希（步骤 1 前后各一次，证明加载的是新构建）；
- 握手声明的能力清单（步骤 1）；
- 七个工具的真实结果文本（步骤 2–4），含至少一条"事实而非失败"的样例；
- 步骤 5/7/8 的进程观察记录（进程列表截图或命令输出）；
- 步骤 6 的 `transport(...)` 日志行。

> **已知留白**：传输用量目前**没有 UI/HTTP 状态面**，只能从结构化日志取（`DesktopTransportUsage`
> 已有 `ChannelProven` / `CanRetireLegacyBridge` 判据）。把它暴露成状态字段是后续项。

## 回滚

把 `desktop:capabilityChannel.enabled` 改回 `false`（或删除该节点）后重启 Desktop
⇒ 组合根路由自动回到既有 WebSocket Bridge（`DesktopTransportRouting.Decide`），
七个工具**无需改动**即可继续工作（这正是"分阶段迁移"的意义：两条传输同形）。

## 通过之后才能做的事

- 把能力通道设为**默认开启**（`enabled` 缺省值翻转），并同步更新本手册的前置条件；
- 在**零回退**证据之上退役 WebSocket Bridge 的 Browser 部分（`BridgeBrowserCapabilitySurface`
  与 `IBrowserRuntime` 的 Bridge 实现）；
- 以上两步各需独立的代码改动与验证，不属于本手册的执行范围。
