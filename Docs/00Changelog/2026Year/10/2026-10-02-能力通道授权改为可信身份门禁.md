# 2026-10-02 能力通道授权：从 DenyAll 改为可信身份门禁（切片 D 第一步）

## 目标 / 背景

接线手册 §3 要求产品实现 `IDesktopCapabilityAuthorizer`（「谁能否对哪个目标执行哪个能力」，无法判定即拒绝），
而在此之前产品用的是 `DenyAllDesktopCapabilities`：**启用态下任何能力都会被 Core 拒**，
通道握手成功却什么也做不了。本轮把「身份」这一层接上：身份取自 Core 的**可信运行上下文**，
而不是模型输出、工具参数或网页字段。

## 改动

- `Source/Pudding.CapabilityBroker/TrustedCallerDesktopCapabilityAuthorizer.cs`（新增）——
  身份端口 `IDesktopCallerIdentityProvider` + 身份值对象 `DesktopCallerIdentity` +
  授权器本体。判定规则（全部 fail closed）：
  ① 当前上下文没有身份/没有会话 ⇒ 拒绝；② `RequiresTrustedContext` ⇒ 必须有 Agent 身份；
  ③ `Mutating` 或 `HasSideEffects` ⇒ 必须来自**可识别的 Agent 执行**（`ExecutionId` + `AgentInstanceId`，
  否则事后无从审计"是谁动的手"）；④ `RequiresUserInteraction`（对话框/Picker）⇒ 必须有用户身份
  （弹窗要能归因到人）。拒绝理由只带规则要点，不含页面内容/URL/剪贴板/凭据。
- `Source/PuddingHost/Hosting/RuntimeTraceContextCallerIdentityProvider.cs`（新增）——
  从 `RuntimeTraceContextAccessor`（AsyncLocal，Runtime 执行 Agent/工具时压栈）取身份；
  无会话标识即返回 null，让授权器 fail closed。
- `Source/PuddingHost/Hosting/PuddingApplicationHost.cs` ——
  `AddCapabilityChannel(..., DenyAllDesktopCapabilities.Instance)` 改为
  `new TrustedCallerDesktopCapabilityAuthorizer(new RuntimeTraceContextCallerIdentityProvider())`。
- `Source/Pudding.CapabilityBrokerTests/TrustedCallerDesktopCapabilityAuthorizerTests.cs`（新增，12 项）——
  其中最硬的一条是**把能力目录走一遍**：任何"忘了判身份"的分支都会在
  `MissingIdentity_DeniesEveryCapabilityInTheCatalogue` 露出来。

## 诚实边界（必须写清，避免"看起来接了"）

这是**身份门禁**，**不是**完整的 Tool Runtime 权限/审批链。把「该 Agent/会话是否有权使用浏览器工具」
也接进来属于切片 D 的调用点迁移，尚未做。当前的取舍是：只放行**来源可识别**的调用，
其余一律拒绝——比 `AllowAll` 安全，也比 `DenyAll` 更接近可用。
另外能力通道在 Desktop 侧缺省关闭，因此对今天的运行实例**行为无变化**。
