# 桌面颜色令牌层提案（2026-10-22）

> 字号/圆角令牌层已落地（`ba78e22`）。颜色是同一套方法的下一个目标，但**问题形状完全不同**——
> 这一篇先用实测把形状说清楚，再谈改法。

## 1. 盘点：颜色其实有两层，缺的是下面那层

实测 `MainWindow.xaml`（774 行）与 `App.xaml`（42 行）的全部色字面量：

| 文件 | 色字面量 | 不同色值 | 其中位于主题字典内 | 其中是**使用点裸值** |
|------|---------|---------|-------------------|---------------------|
| `MainWindow.xaml` | 53 | 37 | 44 | **9** |
| `App.xaml` | 8 | 8 | 8 | 0 |

那 9 处使用点裸值，与 XAML 字面量 lint（`PDT-TOKEN-003`）的现有基线 **9** 逐条吻合——
两套独立口径互证，说明这就是全部缺口。

因此"桌面没有颜色令牌"是个误判。真实结构是：

- **语义层（已存在）**：`ThemeDictionaries` 里的 `SolidColorBrush` 键就是令牌，样式与控件都引用它们；
- **值层（不需要）**：再给每个十六进制值起一个 `PaletteXxx` 名字没有意义——语义键一旦引用稳定，
  值就该留在定义点，多一层间接只会让"换肤"更难读；
- **缺口**：有 9 个使用点**没走语义层**，直接写死了颜色。

## 2. 好消息：主题字典的三套键集合已经完全齐平（实测正样本）

| 文件 | Default | Light | HighContrast | 缺失 |
|------|---------|-------|--------------|------|
| `MainWindow.xaml` | 23 键 | 23 键 | 23 键 | 各 0 |
| `App.xaml` | 5 键 | 5 键 | 5 键 | 各 0 |

而且 `HighContrast` 分支并非空壳——它把透明度类刷子一律置 `Transparent`，
把启动面板的颜色一律换成系统色，且**留了明文约定**：

```xml
<!-- 高对比：启动面板只使用系统色，禁止硬编码品牌色（否则 HC 下不可读）。 -->
<SolidColorBrush x:Key="StartupAccentBrush" Color="{ThemeResource SystemColorHighlightColor}"/>
```

这条约定恰好就是那 9 处裸值违反的规则：它们不走字典，所以既拿不到 Light 分支的值，
也拿不到 HC 的系统色——**在高对比模式下等于硬编码深色**。这不是审美问题，是可访问性缺陷。

## 3. 9 处缺口的语义与漂移证据

| 行 | 现状 | 语义 | 说明 |
|----|------|------|------|
| 312 | `Background="#D59F61"` | 品牌强调 | 26×26 Logo 方块；同文件 `StartupAccentBrush` 已是该值 |
| 312 | `Foreground="#202020"` | 强调色上的文字 | Logo 里的 "P" |
| 489 | `Background="#40000000"` | 遮罩 scrim | 工具区浮层，25% 黑；Light 下偏重 |
| 512 | `Fill="#D59F61"` | 品牌强调 | 未读小红点（7×7 圆） |
| 610 | `Foreground="#E2A33C"` | 警告 | ⚠️ 与 `StartupWarningBrush` = `#E7B877` **不一致** |
| 627 | `Foreground="#4C8DF6"` | 信息 | 无对应语义键 |
| 641 | `Foreground="#4C8DF6"` | 信息 | 同上（第二处） |
| 658 | `Foreground="#B07CD6"` | 辅助紫 | 无对应语义键 |
| 672 | `Foreground="#4CB782"` | 成功 | ⚠️ 与 `StartupSuccessBrush` = `#6CCB9C` **不一致** |

两处 `⚠️` 是同一语义在同一文件里漂成两个值——说明这些使用点是在启动面板那套字典之外
被另一处代码写出来的，从来没有对账过。

## 4. 落地分三步，视觉变化的边界划清楚

### A1 · 机械替换（零视觉变化，可直接做）

- 在 `Default` 与 `Light` 两套字典里各加 7 个键，**值逐字节等于现有裸值**：

| 新键 | Default / Light 值 |
|------|-------------------|
| `BrandAccentBrush` | `#D59F61` |
| `OnBrandAccentTextBrush` | `#202020` |
| `ScrimBrush` | `#40000000` |
| `StatusWarningBrush` | `#E2A33C` |
| `StatusInfoBrush` | `#4C8DF6` |
| `StatusAccentAltBrush` | `#B07CD6` |
| `StatusSuccessBrush` | `#4CB782` |

- 9 处使用点改为 `{ThemeResource …}`（同文件已有 96 处 `ThemeResource` 引用，风格一致；
  注意不要用 `StaticResource`——它在加载期取值一次，主题切换不会重解析）。
- `App.xaml` 不动（它的 8 个值全在字典里，本来就合规）。

### A2 · 补 HighContrast 分支（**仅在 HC 模式可见，需签字**）

给这 7 个新键补 `HighContrast` 值，跟现有约定走系统色：
强调/成功/信息一律 `SystemColorHighlightColor`，文字 `SystemColorHighlightTextColor`，
scrim `SystemColorWindowColor`。

**为什么必须单独一步**：A1 若不给 HC 值，WinUI 会回落到 Default 值（= 当前行为，视觉零变化）；
A2 一加，HC 用户看到的就是系统色。这属于"改像素"，不在我能自己签的范围内。

### B · 语义收敛（**改像素，需艺术裁决**）

把 `StatusWarningBrush` 与 `StatusSuccessBrush` 收敛到既有 `StartupWarningBrush` / `StartupSuccessBrush`
的值（`#E7B877` / `#6CCB9C`），或者反过来让启动面板改用新键。二选一都会让人眼看出差别。

## 5. 门禁：三条结构化断言 + 一条基线

1. **基线归零**：`MainWindow.xaml` 裸色基线 9 → 0（A1 完成后），此后任何新裸色直接红。
   现有 lint 已能取红（本轮已证），不需要新规则。
2. **三套字典键集合必须相等**：这条现状就绿（23/23/23、5/5/5），是正样本；
   它的价值在于挡住"只给 Default 加键、忘了 Light/HC"这个最常见的漂移。
3. **`{ThemeResource X}` 必须指向主题字典里的键**：这是"颜色算不算令牌"的判据——
   只在顶层 `Window.Resources` 声明的刷子不随主题变，不能算令牌。这条现在是**未实现**的，
   A1 落地时一并写。
4. **字面量禁令**：`Color="#..."` 只允许出现在 `ThemeDictionaries` 内（定义点），
   出现在使用属性上即红——即现有 003 的加强版（按"是否在主题字典区间内"判定，而非按属性名）。

## 6. 非目标

- 不引入第三方设计系统（Fluent / Material 的主题包），继续用 WinUI 原生 `ThemeResource`；
- 不做"每个 hex 一个令牌"的机械拆分；
- 不碰 `App.xaml` 与 `DesignTokens.cs` 的合并（那属 Stage 5，需单独授权）。

## 7. 建议执行顺序

A1（本轮可做，零视觉变化 + 三条门禁）→ 等你签 A2 与 B → Stage 5 合并 `App.xaml`。
A1 完成后再看一次实测数字：裸色 9 → 0，字典键 23 → 30（每套）。
