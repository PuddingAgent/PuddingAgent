# 工具三级披露与动态加载

## 0. 口径来源（用户裁定 2026-10-25）

> 「我们需要工具的多级披露（建议三级）和动态加载机制（search_tools），
> 对于非常用和冷门的工具可以只要加载工具名称和工具描述（会省非常多的 tokens）。」

同时用户纠正了成本口径：**只看 token 总量不算成本，必须同时看缓存命中率。**
本设计以此为约束——任何"省 token"的方案都要回答"省的是命中价还是未命中价"。

## 1. 现状（实测）

| 事实 | 数值 | 来源 |
|---|---|---|
| 工具定义占 prompt | 13.2%（3 天 1.227 亿 token） | `TokenUsageEvents.ToolDefinitionTokens` |
| 单请求工具定义 | p50 19,546 / p90 28,057 / max 39,604 token | 同上 |
| 运行态可见集 | available=132 → visible=27，40,735 字节（上限 40,960） | `[AgentExec:ToolExposure]` 日志 |
| 正常调用里工具块的计费 | **缺失仅占 prompt 的 0.8%** ⇒ 工具块基本全命中 | 同报告 §12 |

**推论**：工具块是"每轮都存在的固定前缀"，已经被缓存，按命中价（0.02~0.04 元/百万）付费。
把它从 20k 压到 6k，每轮省的命中费可以忽略；真正的收益见 §5。

## 2. 三级定义

| 级别 | 进出请求体的形态 | 体积（每个工具，估） | 谁能调用 |
|---|---|---|---|
| **L0 目录级** | 不在 `tools` 数组里，只在系统提示的工具索引里出现 `name`（+ 一行短描述） | 5~15 token | 不能直接调，要先 `search_tools(name)` |
| **L1 摘要级** | 在 `tools` 数组里，但 `description` 截断、`parameters` 只保留参数名（无逐参说明、无嵌套细节） | 40~80 token | **可以调**（模型看得懂参数名就能试），失败时按 §4 升级 |
| **L2 完整级** | 现有形态：完整 description + 完整 JSON schema | 400~1,200 token | 可以调 |

L1 是本设计的核心新增。现有实现只有 L0（延迟加载，不在数组里）与 L2（全量），
中间缺一层"我大概知道你怎么用，但没拿到完整文档"。

## 3. 选择规则：单调、可归因

1. **核心工具恒为 L2**（`CoreToolIds`：search_tools / goal_* / send_message / spawn_sub_agent …）。
2. **本会话内被调用过、或被 `search_tools` 显式加载过的工具 → 升到 L2，本会话内不再降级。**
3. 其余工具：预算内按现有 `stable_append` 顺序给 **L1**；预算外仍走现有淘汰 → **L0**。
4. 会话结束（新会话开始）一律回到 L1 起点。

**单调性是缓存安全的前提**，见 §4。

## 4. 缓存安全约束（本设计最重要的一节）

请求体是前缀缓存的对象；工具块位于 `input`（消息）之后、请求尾部。因此：

- **任何一次级别变化都会改变 `ToolSpecHash` ⇒ 该次请求的工具块按未命中计费。**
  实测量级：一次 `tool_spec_changed` 平均 15.2k token 未命中。
- 所以级别变化必须**稀有且单调**：
  - 只在「被调用」或「被显式加载」时升级，**不随 recency 抖动降级**；
  - 每会话升级次数设上限（默认 8），超出则拒绝升级并在工具回执里说明；
  - 绝不因为"最近没用"把 L2 降回 L1——那会让每次抖动都重读一块。
- 反例（必须避免）：按最近使用排序重排工具块、按轮次在 L1/L2 之间来回切换。
  这类"看起来更聪明"的策略每轮都在改写前缀，与本设计目标相反。

> 注意：`ToolExposurePlanner` 已实现 `stable_append` 顺序（`previousVisibleToolIds` 基线，
> canonical 只用于新会话初始顺序）。**新增分级时不得破坏这一点**——
> 2026-10-25 曾有一次"改回 canonical 排序"的尝试，因会破坏该策略而被撤回。

## 5. 收益估算（诚实版）

以 10-23 → 10-25 窗口（6,891 次调用、工具块约 20k token、692 次工具集变化）为基数：

| 收益路径 | 估算 | 说明 |
|---|---|---|
| 每轮命中 token 减少 ~12k | 约 ¥2 / 3 天 | 12k × 6,891 × 0.025 元/百万；**很小** |
| 工具集变化时重读块变小（20k → 6k） | 约 ¥14 / 3 天 | 692 × 14k × 2 元/百万 |
| 同一 40KB 预算能容纳更多工具 | 不直接折钱 | 减少"需要 search_tools 才发现"的往返 |
| 对压缩触发的影响 | 基本可忽略 | 相对 935k 输入窗口，10k 量级不改变触发点 |

**结论：这不是省钱主力，省钱主力仍是压缩（占缺失 token 59%）。**
它的价值是"降低单次变化的单价 + 提高工具面容量"，而不是"每轮都省"。
对外表述不得写成"能省一半 token"。

## 6. 失败模式与回执

| 情形 | 处理 |
|---|---|
| L1 工具被调用但参数不合法 | 返回可判错误码 `tool_requires_full_schema`，附 `search_tools(name)` 提示；**同时把该工具升到 L2**，使下一轮直接可用 |
| 升级次数超上限 | 拒绝升级，回执说明 `tool_upgrade_budget_exhausted`；工具仍可按 L1 试调 |
| L1 的截断描述导致误用 | 截断只删"参数说明/示例"，**必须保留"这个工具做什么"的第一句**；不得删掉前置条件（如"需要审批"） |
| `search_tools` 不可用 | 关闭分级，退回现行 L2 全量（fail-closed 到已知安全形态） |

## 7. 配置与计量

`D:\Data\config\runtime.execution.json` 的 `toolExposure` 段（现已存在该节点类型，只是文件里未写）：

```jsonc
{
  "enabled": true,
  "maxVisibleTools": 48,
  "maxVisibleToolBytes": 40960,
  "summaryTierEnabled": true,        // 新增：启用 L1
  "summaryTierDescriptionChars": 160, // 新增：L1 描述截断长度
  "summaryTierMaxUpgradesPerSession": 8 // 新增：会话内升级上限
}
```

计量：`[AgentExec:ToolExposure]` 追加 `tier2=N tier1=N tier0=N`、`upgrades=N`、`upgradeBytes=N`，
与已有 `visibleSchemaBytes` / `topTools` 一起构成"分级到底省了多少"的可核对证据。

## 8. 实施顺序（每步可独立验证、可回滚）

1. **S1 纯函数分级**：`ToolExposurePlanner` 增加 `ApplySummaryTier(...)`，
   输入（可见集、已升级集、配置）→ 输出（带 L1 截断的定义 + 未变部分的原样）。
   单测覆盖：核心恒 L2、升级单调、顺序不变（沿用 `stable_append`）、截断保留首句。
2. **S2 接线**：`BuildFrozenToolManifestCore` 调用 S1；`ToolSpecHash` 自然反映变化；
   日志加计量字段。
3. **S3 升级触发**：工具调用成功后记录"已用"；`search_tools` 加载后记录"已加载"。
4. **S4 失败回执**：`tool_requires_full_schema` 错误码 + 自动升级。
5. **S5 配置开关**：默认关闭，灰度打开对照 `visibleSchemaBytes` / miss 变化。

每步都必须能取红：S1 用单测变异，S2/S4 用日志与回执对照。

## 9. 未决定（需用户裁定）

1. L1 是否允许"直接调用"（本文假设允许，用失败升级收敛）；若改为"只读目录、必须加载"，会更省 token 但每次新工具多一轮往返。
2. 升级上限默认 8 是否合适——取决于一次会话平均用到几种冷工具，需要先用现有 `ToolNames` 数据统计。
3. 是否把"技能目录"也纳入同一分级（现在技能索引在系统提示里，同样占固定前缀）。

## 10. 2026-10-27 补记：成本校准、唯一剩余缺口、一个字段约束

本节只记录 10-25 之后新取得的事实，与上文冲突时以本节为准；上文结论未被推翻的部分不回改。

### 10.1 价格校准（把"假设"换成"实测价目表"）

`list_llm_providers` 实测 `deepseek/deepseek-flash`：**输入 ¥2/M、输出 ¥8/M、缓存命中 ¥0.04/M**。
（此前资源池里 `pricePer1MTokens` 为 0 的是 `fastrouter/*` 与 `volcengine-ark/*`，DeepSeek 一直有值。）

由此可反推并**与厂商后台账单对上**：

```
本会话实测 229,503 token/请求，命中率 97.83%
命中部分  224,454 × ¥0.04/M = ¥0.00898
未命中部分  5,049 × ¥2.00/M = ¥0.01010
──────────────────────────────────────
合计                        = ¥0.0191 / 请求

后台核对：近 7 天 ¥252.72 ÷ 2,619,070,523 token = ¥0.0965/M（总量口径）
上式折算的有效输入价 ¥0.0825/M + 输出部分，量级吻合。
```

### 10.2 一个与直觉相反的结论

**未命中的 2.2% 比命中的 97.8% 更贵**（¥0.0101 vs ¥0.00898）。

推论：只看"命中率 97.83% 很高"是不够的，它是价格差 50 倍之后的合成值。
但也要看到上限——未命中部分基本就是每轮真实新增的内容（新消息 + 工具结果），
**新增内容无法命中，所以 97.83% 已接近该负载的理论上限**，继续追命中率收益有限。

因此 §5「省钱主力是压缩」的判断依然成立，且可以更精确：**主力是压缩掉工具结果体积**
（本会话 tool results 占 49,112 token，全价计入）。

### 10.3 唯一仍然违背 append-only 的位置（上文的空白）

§3 第 3 条写「预算外仍走现有淘汰」——当时只是描述现状，没有指出它与「已创建的块不变」冲突。
现在补上：

`ToolExposurePlanner.ApplyBudget()` 在预算触顶时按「最近使用 → 上一轮可见序 → canonical」
挑选可见集合，**会让集合缩小**。而 `BuildPlan → OrderStableAppend` 只能保住
「幸存项的相对顺序」，**保不住「已经发出去的内容不消失」**——从列表中间删掉一个工具，
其后所有 token 错位，缓存从该点起全部失效。

这是当前唯一与「会话内 append-only」原则冲突的机制。排序层面（§3/§4 已要求的单调性）
其实已经实现了，剩下的就是**这一处集合收缩**。

候选改法（二选一，需裁定）：

| 方案 | 做法 | 代价 |
|---|---|---|
| B-最小版（推荐先做） | 会话内**跳过淘汰**，`visibleSchemaBytes` 超限只记 `budgetExceeded=true` 日志；淘汰推迟到新会话/压缩 | 单会话可见 schema 可能超 `maxVisibleToolBytes`，需显式承认超限 |
| A-长期版 | `tools` 数组发「本会话曾暴露过的并集」，永不删除；「当前哪些可用」改为消息链上的追加授权块 | 前缀体积随会话增长；且需先验证模型是否遵守授权块（见 10.5） |

### 10.4 一个决定方案形态的字段约束（回答"能否只追加配置块"）

**`tools` 是请求的独立字段，不是普通文本块。**

若只在消息链上追一条「你现在拥有 X 工具」，而 `tools` 数组里没有 X：API 侧没有 X 的 schema，
模型无法合法生成对 X 的调用；即便生成了，宿主校验也会拒绝。

⇒ **纯文本式的"链上追加配置块"不能单独成立，必须有 `tools` 数组配合。**
这直接决定了「类似区块链的配置块」只能作为**授权状态**的表达，不能替代 schema 的投递。
方案 A 因此定义为「静态并集 + 追加式授权块」，而不是「只在链上写配置」。

### 10.5 新增的验收指标（可测量，改动前后各测一次）

| 指标 | 来源 | 目标 |
|---|---|---|
| `distinct_prefix_hashes` | `agent_diagnostics(cache_health)` | 单会话内 = 1 |
| `first_churn_reason` | 同上 | 不含 `tool_spec_changed` |
| `average_cache_hit_rate` | 同上 | 不下降（基线 0.978） |
| `ExposureSetChanged` | `ToolExposurePlanner` | 会话内只允许 false→true 一次，不允许反复 |

### 10.6 本节的未验证项

- 会话内不淘汰后，`visibleSchemaBytes` 的实际峰值与超限频率：**未测**；
- 工具输出的**按工具拆分**体积分布（只知道 total 49,112）：**未测**；
- `distinct_prefix_hashes=2` 那次 churn 具体落在第几轮：**未定位**；
- 方案 A 中模型是否遵守授权块里的 enabled 列表：**未做对照实验**。

### 10.7 一条自我更正

我曾在 2026-10-27 口头判断「工具清单变化会击穿整个前缀，一次约 ¥0.46」。
**这是错的**：缓存按最长公共前缀匹配，尾部追加只让尾部未命中，实测命中率始终维持 99.8%/轮，未见整体击穿。
正确的量级是 §4 里的「一次变化平均 15.2k token 未命中」，即约 ¥0.03。

## 11. 2026-10-27 S2 落地与 S3 前置实测：验收指标已经达标，开关暂时是空转

### 11.1 S2 已交付（commit d8f8341）

- `ToolExposureOptions.EvictOnlyAtSessionStart`（**默认 false**，行为不变）
- `ToolExposureBudget` 携带该开关；`ResolveBudget` 透传
- `CreatePlan`：已有上一轮可见集（会话内）⇒ 跳过 `ApplyBudget`；只有会话首个计划才真正收缩
- `ToolExposurePlan.BudgetDeferred` 如实上报「预算被推迟」，`[AgentExec:ToolExposure]` 日志同名字段可见

验证：ToolExposure 相关 20/20 绿；变异（`budgetDeferred` 恒 false）6 个里 1 红且精确命中目标用例；
反向补丁恢复后 20/20、`MUTATION PROBE` 残留 0。

### 11.2 S3 前置实测（2026-10-27T19:5x，本会话窗口，50 条 LLM 调用）

| 指标 | 实测 | §10.5 设定的目标 | 结论 |
|---|---|---|---|
| `distinct_prefix_hashes` | **1** | 1 | **已达标** |
| `status` | **stable** | — | 已稳定 |
| `average_cache_hit_rate` | **0.998457** | 不下降（基线 0.978） | 已高于基线 |
| `first_churn_reason` | **null** | 不含 `tool_spec_changed` | 已达标 |
| 单一致前缀 | `dd985089865d`（50/50 命中） | — | 无 churn |

**这批数据推翻了一个隐含假设**：§10.3/10.5 把「打开开关」当作改善前缀稳定性的手段，
但**在开关关闭的情况下，指标已经全部达标**。

### 11.3 为什么现在测不出差别（机制解释）

`ApplyBudget` 只在 `deferredLoadingEnabled && budget.IsEffective` 时运行，而预算淘汰只有在
**可见工具数超过 `maxVisibleTools`（默认 48）或 schema 超过 `maxVisibleToolBytes`** 时才会真的删东西。

当前本会话可见工具约 43 个 < 48 ⇒ **淘汰路径根本没触发** ⇒ 既没有 `budgetApplied=true`，
也没有 churn。此时打开 `EvictOnlyAtSessionStart` 是一次纯 no-op。

### 11.4 由此修正的实施判据（取代 §10.5 的单一目标）

打开开关的正确时机不是「现在就开」，而是：

1. **先确认存在预算真正绑定的会话** —— 在日志里找到 `[AgentExec:ToolExposure] ... budgetApplied=true`
   （这要求会话内发现足够多工具，越过 48 个 / 40 KiB 阈值）；
2. 在这种会话上开 flag，作为**对照组**，比较 `distinct_prefix_hashes` 与
   `ExposureSetChanged` 的变化；
3. 若从未出现 `budgetApplied=true`，则这个 flag 在当前使用形态下没有收益，
   **不该为了「已实现」而打开**（开启还带来会话内 schema 无上限增长的风险）。

### 11.5 未验证项

- 是否存在过 `budgetApplied=true` 的历史会话：**未检索**（需要查 `agent_llm`/dispatch 日志或历史日志归档）；
- 越过 48 个工具后 flag 的实际收益幅度：**未测**（缺对照组）；
- 会话内 schema 无上限增长是否会触发模型侧输入限制：**未测**。
