# 工具三级披露与动态加载

## 0. 口径来源（用户裁定 2026-10-25）

> 「我们需要工具的多级披露（建议三级）和动态加载机制（search_tools），
> 对于非常用和冷门的工具可以只要加载工具名称和工具描述（会省非常多的 tokens）。」

同时用户纠正了成本口径：**只看 token 总量不算成本，必须同时看缓存命中率。**
本设计以此为约束——任何"省 token"的方案都要回答"省的是命中价还是未命中价"。

## 1. 现状（实测）

| 事实 | 数值 | 来源 |
|---|---|---|
| 工具定义占 prompt | 13.2%（3 天 1.227 亿 token） | `TokenUsageEvents.ToolDefinitionTokens` |
| 单请求工具定义 | p50 19,546 / p90 28,057 / max 39,604 token | 同上 |
| 运行态可见集 | available=132 → visible=27，40,735 字节（上限 40,960） | `[AgentExec:ToolExposure]` 日志 |
| 正常调用里工具块的计费 | **缺失仅占 prompt 的 0.8%** ⇒ 工具块基本全命中 | 同报告 §12 |

**推论**：工具块是"每轮都存在的固定前缀"，已经被缓存，按命中价（0.02~0.04 元/百万）付费。
把它从 20k 压到 6k，每轮省的命中费可以忽略；真正的收益见 §5。

## 2. 三级定义

| 级别 | 进出请求体的形态 | 体积（每个工具，估） | 谁能调用 |
|---|---|---|---|
| **L0 目录级** | 不在 `tools` 数组里，只在系统提示的工具索引里出现 `name`（+ 一行短描述） | 5~15 token | 不能直接调，要先 `search_tools(name)` |
| **L1 摘要级** | 在 `tools` 数组里，但 `description` 截断、`parameters` 只保留参数名（无逐参说明、无嵌套细节） | 40~80 token | **可以调**（模型看得懂参数名就能试），失败时按 §4 升级 |
| **L2 完整级** | 现有形态：完整 description + 完整 JSON schema | 400~1,200 token | 可以调 |

L1 是本设计的核心新增。现有实现只有 L0（延迟加载，不在数组里）与 L2（全量），
中间缺一层"我大概知道你怎么用，但没拿到完整文档"。

## 3. 选择规则：单调、可归因

1. **核心工具恒为 L2**（`CoreToolIds`：search_tools / goal_* / send_message / spawn_sub_agent …）。
2. **本会话内被调用过、或被 `search_tools` 显式加载过的工具 → 升到 L2，本会话内不再降级。**
3. 其余工具：预算内按现有 `stable_append` 顺序给 **L1**；预算外仍走现有淘汰 → **L0**。
4. 会话结束（新会话开始）一律回到 L1 起点。

**单调性是缓存安全的前提**，见 §4。

## 4. 缓存安全约束（本设计最重要的一节）

请求体是前缀缓存的对象；工具块位于 `input`（消息）之后、请求尾部。因此：

- **任何一次级别变化都会改变 `ToolSpecHash` ⇒ 该次请求的工具块按未命中计费。**
  实测量级：一次 `tool_spec_changed` 平均 15.2k token 未命中。
- 所以级别变化必须**稀有且单调**：
  - 只在「被调用」或「被显式加载」时升级，**不随 recency 抖动降级**；
  - 每会话升级次数设上限（默认 8），超出则拒绝升级并在工具回执里说明；
  - 绝不因为"最近没用"把 L2 降回 L1——那会让每次抖动都重读一块。
- 反例（必须避免）：按最近使用排序重排工具块、按轮次在 L1/L2 之间来回切换。
  这类"看起来更聪明"的策略每轮都在改写前缀，与本设计目标相反。

> 注意：`ToolExposurePlanner` 已实现 `stable_append` 顺序（`previousVisibleToolIds` 基线，
> canonical 只用于新会话初始顺序）。**新增分级时不得破坏这一点**——
> 2026-10-25 曾有一次"改回 canonical 排序"的尝试，因会破坏该策略而被撤回。

## 5. 收益估算（诚实版）

以 10-23 → 10-25 窗口（6,891 次调用、工具块约 20k token、692 次工具集变化）为基数：

| 收益路径 | 估算 | 说明 |
|---|---|---|
| 每轮命中 token 减少 ~12k | 约 ¥2 / 3 天 | 12k × 6,891 × 0.025 元/百万；**很小** |
| 工具集变化时重读块变小（20k → 6k） | 约 ¥14 / 3 天 | 692 × 14k × 2 元/百万 |
| 同一 40KB 预算能容纳更多工具 | 不直接折钱 | 减少"需要 search_tools 才发现"的往返 |
| 对压缩触发的影响 | 基本可忽略 | 相对 935k 输入窗口，10k 量级不改变触发点 |

**结论：这不是省钱主力，省钱主力仍是压缩（占缺失 token 59%）。**
它的价值是"降低单次变化的单价 + 提高工具面容量"，而不是"每轮都省"。
对外表述不得写成"能省一半 token"。

## 6. 失败模式与回执

| 情形 | 处理 |
|---|---|
| L1 工具被调用但参数不合法 | 返回可判错误码 `tool_requires_full_schema`，附 `search_tools(name)` 提示；**同时把该工具升到 L2**，使下一轮直接可用 |
| 升级次数超上限 | 拒绝升级，回执说明 `tool_upgrade_budget_exhausted`；工具仍可按 L1 试调 |
| L1 的截断描述导致误用 | 截断只删"参数说明/示例"，**必须保留"这个工具做什么"的第一句**；不得删掉前置条件（如"需要审批"） |
| `search_tools` 不可用 | 关闭分级，退回现行 L2 全量（fail-closed 到已知安全形态） |

## 7. 配置与计量

`D:\Data\config\runtime.execution.json` 的 `toolExposure` 段（现已存在该节点类型，只是文件里未写）：

```jsonc
{
  "enabled": true,
  "maxVisibleTools": 48,
  "maxVisibleToolBytes": 40960,
  "summaryTierEnabled": true,        // 新增：启用 L1
  "summaryTierDescriptionChars": 160, // 新增：L1 描述截断长度
  "summaryTierMaxUpgradesPerSession": 8 // 新增：会话内升级上限
}
```

计量：`[AgentExec:ToolExposure]` 追加 `tier2=N tier1=N tier0=N`、`upgrades=N`、`upgradeBytes=N`，
与已有 `visibleSchemaBytes` / `topTools` 一起构成"分级到底省了多少"的可核对证据。

## 8. 实施顺序（每步可独立验证、可回滚）

1. **S1 纯函数分级**：`ToolExposurePlanner` 增加 `ApplySummaryTier(...)`，
   输入（可见集、已升级集、配置）→ 输出（带 L1 截断的定义 + 未变部分的原样）。
   单测覆盖：核心恒 L2、升级单调、顺序不变（沿用 `stable_append`）、截断保留首句。
2. **S2 接线**：`BuildFrozenToolManifestCore` 调用 S1；`ToolSpecHash` 自然反映变化；
   日志加计量字段。
3. **S3 升级触发**：工具调用成功后记录"已用"；`search_tools` 加载后记录"已加载"。
4. **S4 失败回执**：`tool_requires_full_schema` 错误码 + 自动升级。
5. **S5 配置开关**：默认关闭，灰度打开对照 `visibleSchemaBytes` / miss 变化。

每步都必须能取红：S1 用单测变异，S2/S4 用日志与回执对照。

## 9. 未决定（需用户裁定）

1. L1 是否允许"直接调用"（本文假设允许，用失败升级收敛）；若改为"只读目录、必须加载"，会更省 token 但每次新工具多一轮往返。
2. 升级上限默认 8 是否合适——取决于一次会话平均用到几种冷工具，需要先用现有 `ToolNames` 数据统计。
3. 是否把"技能目录"也纳入同一分级（现在技能索引在系统提示里，同样占固定前缀）。
