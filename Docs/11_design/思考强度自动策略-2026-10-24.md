# 思考强度自动策略：high 是基线，max 要有证据

## 0. 产品口径（用户裁定 2026-10-24）

- provider 提供 `none / low / high / max`；
- PuddingAgent 的实际场景只需 **low / high / max** 三档；
- **high 是默认**；
- `low` 大部分情况下不适用，只用于「聊天解闷」这类不需要推理的对话；
- `max` 适合困难思考、研究、软件开发。

由此推出三条硬性结论，本文后续所有设计都服从它们：

1. 「自动」的基线是 **high**，不是 low。留空让服务端决定等于放弃了可观测性与可控性。
2. 「深入」**不能**映射到 high（high 已是默认，映射过去等于没有深入），只能映射到 **max**。
3. `none` 不对用户暴露，只给压缩摘要这类非推理的内部调用使用（现状已如此，见第 7 节）。

## 1. 问题

用户选「自动」时，系统必须在**生成之前**决定强度。难度在生成之前不可观测——这是核心矛盾。

任何"先验猜难度"的做法，本质上都在用弱信号（消息长度、关键词、问号数量）替代真实信号（模型会不会失败）。弱信号不是没用，而是它的误判代价不对称——见第 2 节。

## 2. 成本结构决定了策略方向

- 思考 token 计入**输出**，按输出计费，延迟随强度增加。
- 强度不足的代价是**失败或多轮往返**：一次往返要把整个上下文重新发送（输入 token 通常远大于输出）。
- 强度过高的代价是输出 token 变多，答案本身不变——但如果每轮都 max，成本按输出线性涨。

⇒ **不对称：低估的代价通常大于高估的代价**，但"永远 max"会把默认成本抬到不可接受。

而 high 已经是默认，意味着**高估这一侧的风险已被产品口径吸收**：剩下的问题不是"要从 low 爬上来"，而是"什么时候值得从 high 再往 max 抬一档"。

## 3. 第一原则

**auto = high 基线 + 有证据才升 max + 只有明确闲聊才降 low。**

三条各自对应一种错误：

| 错误 | 表现 | 本条的作用 |
|---|---|---|
| 起点太低 | 简单任务也要多轮 | 基线直接定 high，不从 low 爬 |
| 无谓升高 | 每轮都 max，成本失控 | max 必须有证据，且每 Turn 至多一次 |
| 过度降档 | 为省钱把正经任务降成 low | 降 low 只认明确信号，不认"上下文大" |

这和本项目在上下文压缩上学到的教训同构：不要先验地把度量算准到小数点，而要用可观测的反馈闭环让误差在决策前被修正。

## 4. 分级与准入

| 档 | 谁触发 | 说明 |
|---|---|---|
| `low` | 用户显式选「快速」；或后续经验证的闲聊分类器（尚未实现） | 特例，不是常态 |
| `high` | **默认**；`auto` 的基线 | 绝大多数对话、工具调用、代码修改 |
| `max` | 用户显式选「深入」；或**证据**触发（见第 5 节） | 困难思考、研究、软件开发 |
| `none` | 仅内部非推理调用（压缩摘要） | 不对用户暴露 |

**max 的准入是硬约束，必须同时满足：**

1. 有证据（第 5 节任一条成立）；
2. 有预算余量（不得因为要 max 而撞到窗口阻塞线）；
3. 同一 Turn 内至多升一次（避免抖动）。

不具备证据时**不得**自动进 max。这条存在的意义，是防止「自动」退化成「永远拉满」。

## 5. 升 max 的证据：只采证据，不采预测器

只列**现有遥测已经能读到**的信号：

| 证据 | 来源 | 判定 |
|---|---|---|
| 工具调用失败 | Turn 内工具结果 error（`toolFailureCount`） | 同 Turn ≥1 次 ⇒ 下一次调用升 max |
| 原地打转 | 连续两轮无 tool_call 且上下文增量极小 | 未收敛 ⇒ 升 max |
| 输出被截断 | `finishReason=length` | 能力不足 ⇒ 升档并提高 `maxOutputTokens` |
| 不可逆操作 | 该轮涉及写盘 / git 推送 / 部署 / 对外发消息 | 判错代价高 ⇒ 直接 max |
| 多步工具链 | 本轮工具调用 ≥ N 且仍有待执行项 | 复杂度证据 ⇒ 升 max |

**明确不采用**：消息长度、关键词命中（"仔细想想"）、问号数量、用户情绪。

理由：这五项是难度的**预测器**，上表五项是难度的**证据**。用户已经可以用「深入」显式表达意图，系统不需要再猜一遍——多一个预测器只会多一个噪声源。

**明确不采用（数据侧）**：`reasoningTokens=0`。当前不可靠，不作为信号。

## 6. 何时可以降 low

只有两种情况允许降：

1. 用户显式选「快速」；
2. 后续加入并经实验验证的闲聊分类器（当前**不实现**）。

**不得**因为"省钱"或"上下文大"在正常对话里降档。降档省下的是输出 token，损失的是正确率——而正确率直接进入 `单位成功任务成本 × pass^k` 的分子。

  并随消息发出 `metadata.reasoningEffort`（`eb36f10` 有断言锁住）。

  `ReasoningEffortPolicy.Resolve(手动, 模板, 已解析)` → `ConfigOverride` → 网关 `reasoning.effort`。

## 8. 接入点核实（2026-10-24 实测）

**结论：不需要改任何契约。** `LlmInvocationRequest`（`Source/PuddingCore/Runtime/LlmInvocationContracts.cs:24`）
只有 `InvocationId / LocalEstimatedTokens / Purpose / Trace / ConfigOverride`，没有也不应该有"本轮失败了几次"。
这个信号不属于 LLM 调用层——它属于 Turn 执行层，而那里本来就有。

| 需要的事实 | 位置 | 状态 |
|---|---|---|
| 本轮工具失败次数 | `AgentExecutionService.Buffered.cs:502`（流式 `:630`） | 已有，跨轮累积 |
| 输出被截断计数 | `toolOutputTruncatedCount` | 已有 |
| 连续 LLM 失败 | `consecutiveLlmFailures`（`Streaming.cs:1261`） | 已有 |
| 轮次号 | 轮循环变量 | 已有 |

**唯一要改的是接缝，不是数据：**

- `effectiveLlmConfig` 在 `Buffered.cs:464` 一次性赋值（只做模板继承），之后冻结；
- 每次调用把冻结的那份传给 `AgentExecutionLlmInvoker.cs:85` / `Streaming.cs:1040` 的 `ConfigOverride`；
- `LlmInvocationService.cs:175` 的 `FirstNonBlank` 永远只是搬运工。

所以接入 = **在每轮 LLM 调用前重算一次 effort**（把 `toolFailureCount` 等喂给决策函数），
而不是在调用服务里想办法看到 Turn 历史。

## 9. 如何验证策略确实有用（预注册）

沿用既有度量：**单位成功任务成本 × pass^k**。

- 任务集 ≥30 条，覆盖三类：闲聊/简单、多步工具链、不可逆或研究型；
- 三个臂：全 `high`（基线）、`auto`（本策略）、全 `max`；
- 记录：pass^k、总成本、失败重试次数、总延迟。

**通过条件**：`auto` 总成本 ≤ 全 `max` 的 70%，**且** pass^k 不低于全 `high` 的 95%。

**失败条件**：若 `auto` 的 pass^k 低于全 `high`，说明升 max 的证据判据没抓到真正难的轮次——判定策略无效，**不做"再调调参数"式抢救**。

基线选全 `high` 而不是全 `low`，是因为产品默认已经是 high：一个比 high 更差或更贵的 auto 没有存在价值。

## 10. 一句话

自动的价值不在于"猜得准"，而在于**在 high 之上，只给已经有证据证明需要它的那一轮抬到 max**。

## 12. 已上线的形态（2026-10-25）

| 能力 | 状态 |
|---|---|
| 手动两档：深入 = `high`（默认）、极致 = `max` | 已实现，待重启生效 |
| `low` | 协议层保留合法值，界面不暴露（收益结构不成立，见 §2） |
| `none` | 仅压缩摘要等内部非推理调用 |
| 「自动」档 | **未上线**。原因见 §1/§3：难度在生成前不可观测，先验猜测只会引入噪声 |
| Agent 自升档（撞墙后请求 max） | 未实现，设计方案见 §5 |

**这一档的界线是刻意划的**：先把「用户能手动选」做对、做可验证，
再谈「系统能自己判断」。反过来的话，一旦自升档判错，用户会同时失去
对成本与质量的控制，而且没有任何一处可以归因。

生效前提：宿主重启。验收两条——日志出现 `reasoningEffort=high|max`；
捕获日志里出站报文带 `reasoning.effort`。

## 13. 一个需要实测的副作用（2026-10-25 登记）

`d3e0e6c` 让合成结果**永不为 null**（没有来源时落 `high`）。这改变了一条既有分支：

```csharp
// AgentExecutionService.Compaction.cs:308
ReasoningEffort = plan.MaxRequestTextBytes > 0 ? "none" : effectiveLlmConfig?.ReasoningEffort
```

| 条件 | 之前 | 现在 |
|---|---|---|
| 有文本预算（`MaxRequestTextBytes > 0`） | `none` | `none`（不变，且有 E2E 断言锁住） |
| 无文本预算 | 继承，可能为 `null` → provider 默认 | 继承，必然为 `high` |

**这是行为变更，不是无副作用的重构。** 无文本预算的压缩摘要在改动前交给服务端默认，
现在明确是 `high`——成本与延迟都可能上升，而摘要任务本身不太需要深推理。

**未判定**：服务端原默认是多少（若本来就是 high，则无差别）。判定手段是重启后看
压缩调用的 `reasoningTokens`；若明显 >0 且摘要质量无提升，应把该分支也固定为 `none`。

这一条不靠推理拍板：先量，再改。

## 14. 一个未解的能力标签（2026-10-25 实测登记）

线上注册表里 `deepseek/deepseek-flash` 的 `capabilityTags` 是：

```
vision, fast, cheap, search, reasoning-low, code, long-context, text,
function-calling, json-mode, streaming, reasoning
```

两件事同时为真：

1. **有 `reasoning`** —— 所以 §13/产品默认那道能力门禁能通过，默认值会生效；
2. **还有一个 `reasoning-low`** —— 这个标签在代码里没有任何引用（全仓 grep 只命中
   JSON 字段名和 token 分项名），语义未知。

第 2 点不能当它不存在。可能的解释有两种，指向相反的结论：

- 它只是历史/描述性标签（"支持 reasoning，偏轻量"）⇒ 发 `max` 没问题；
- 它表示该路由只接受/只支持低强度 ⇒ 发 `max` 会被拒绝或静默降级。

**判定方式**（重启后即可，不需要额外改动）：

| 观察 | 结论 |
|---|---|
| 请求 400 且错误提到 effort/参数 | 该路由不接受 `max` ⇒ 需要在注册表或代码里按模型限制可选档位 |
| 200 但 `reasoningTokens` 与 `high` 无差别 | 静默降级 ⇒ `max` 在该路由上是空承诺，界面上应隐藏或标注 |
| `reasoningTokens` 明显高于 `high` | 支持 ⇒ 保留 |

这一条不进代码猜测，等实测数据。

## 15. 对 §13 / §14 的降级（2026-10-25 06:55，基于既有实测记录）

翻仓库既有报告时找到一条 2026-09-16 的一手核对结论
（`Docs/14_reports/模型输出上限归一与资源池核对-2026-09-16.md`，DeepSeek 章节，
引用 `api-docs.deepseek.com`）：

> 协议/思考 | OpenAI、Responses、Anthropic 均受支持；未设置 reasoning_effort 时
> **服务商默认 high**，未强制覆盖用户思考偏好

据此对前面两节的担心做降级——**注意这是引用既有实测，不是我今天重测的**：

### §13（压缩摘要副作用）→ 大概率为零影响

| 分支 | 改动前 | 改动后 | 差异 |
|---|---|---|---|
| 无文本预算，DeepSeek 路由 | `null` → 服务商默认 **high** | 显式 `high` | **无** |

也就是说，这一支的成本与延迟大概率没变，只是把隐含值显式化了。
仍然要测的理由只剩一个：那条结论只覆盖 DeepSeek；若将来路由到别的 provider，
默认值可能不同，届时才产生真实差异。

### §14（`reasoning-low` 标签）→ 语义已定位为筛选标签

查全部消费方，`capabilityTags` 只有两种用法：

1. **精确能力判定**：`vision`（快照投影）、`audio`（`DirectLlmClient.cs:920`）；
2. **筛选条件**：`ListLlmProvidersTool` 的 capability 过滤、`LlmResourcePoolTool` 展示。

没有任何代码把标签当作"强度上限"或路由权重。`fast`/`cheap`/`search`/`code`/
`long-context`/`json-mode`/`streaming` 与 `reasoning-low` 属同一类——**描述/筛选用**。
所以我那道 `reasoning` 门禁与既有 `audio`/`vision` 的判定方式一致，没有另立规则。

### 仍然开放的一个问题

**`deepseek-v4.1-flash` 是否接受 `effort=max`。** 这一条没有既有证据，
不靠标签语义推断，等重启后的实测：400 / 与 high 无差别 / 明显更高，三种结果各自对应
不同的处理，判定表见 §14。

### 顺带记下一条口径冲突（未处理）

同一份 2026-09-16 报告与 `Docs/07_architecture/14…ADR.md:212` 都出现
`reasoning_effort: "medium"` 的写法，而用户 2026-10-24 裁定 provider 只提供
`none/low/high/max`。本文以用户裁定为准（`medium` 判非法），旧 ADR 属待清理的口径残留。
