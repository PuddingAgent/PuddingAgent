# 浏览器工具注册范围冲突：八项契约与整程序集扫描

## 0. 结论

`AddDesktopBrowserAutomation` 用**整程序集扫描**注册工具，把同程序集里的面板/文档工具
（`ReadPanelTool` / `RenderPanelTool` / `PreviewDocumentTool`）也纳入了浏览器自动化这条路径，
与 `BrowserAgentToolIds` 与既有测试共同表述的「**八项浏览器工具**」契约冲突。

现场表现为 `PuddingHost.Tests` 的 Browser 过滤集 **180 个用例 175 通过 / 5 失败**。

**严重度：契约漂移 + 测试红；不是线上故障**（理由见 §5）。

## 1. 现象（实测）

```
dotnet test Tests\PuddingHost.Tests --filter "FullyQualifiedName~Browser"
失败!  - 失败: 5，通过: 175，总计: 180
```

失败分两类，根因不同：

| 类型 | 用例 | 报错 |
|---|---|---|
| A｜注册集合超集 | `DesktopChild_RegistersRemoteRuntimeAndAllBrowserTools` | 期望 8 个类型名，实际注册集更大 |
| B｜依赖不可解析 | `PreviewDocumentTool_IsDiscoveredAndFailsHonestlyWithoutCapabilityChannel`、`BrowserContextTool_TraversesAuthenticatedBridgeAndReturnsDesktopResult`、`BrowserSnapshotTool_TraversesAuthenticatedBridgeAndReturnsVersionedRefs` 等 4 例 | `Unable to resolve service for type 'PuddingCore.Panels.IPanelCanvasStore' while attempting to activate 'PuddingBrowser.AgentTools.ReadPanelTool'` |

B 类不是「测试写错」，而是 A 类原因的**下游后果**：一旦把 `ReadPanelTool` 注册进来，
容器就必须能构造它；而它的依赖只在别处登记。

## 2. 证据链

### 2.1 两处权威文本都说「八项」

`Source/PuddingBrowser.AgentTools/BrowserAgentToolIds.cs` 类注释：

> Canonical tool IDs for the **eight** browser Agent tools (ADR-097 D1/D5).
> The All collection defines the fixed enumeration order ...

`All` 中恰好 8 个：`browser_context` / `tabs` / `navigate` / `snapshot` / `screenshot` / `locate` / `interact` / `wait_for`。
同文件的 `BrowserAgentCapabilityIds` 同样是 8 个。

测试 `DesktopChild_RegistersRemoteRuntimeAndAllBrowserTools` 断言的也正是这 8 个类型名。

### 2.2 注册侧是整程序集扫描

`Source/PuddingHost/BrowserBridge/BrowserBridgeServiceCollectionExtensions.cs:142`：

```csharp
services.AddPuddingToolsFromAssembly(typeof(BrowserContextTool).Assembly);
```

扫的是**整个 `PuddingBrowser.AgentTools` 程序集**，因此面板/文档工具也被注册。

### 2.3 归因：哪次提交把它改红

| 提交 | 时间 | 事件 |
|---|---|---|
| `8489a3e` | 2026-10-12 22:45 | 八项契约测试诞生，当时报 **Host.Tests 286/286 全绿** |
| `dc1d99d` | 2026-10-20 14:57 | `preview_document` 接入宿主 |
| **`72de494`** | **2026-10-20 16:15** | 面板工具接入（线缆映射 + 入口 + 工具 + WinUI 渲染） |

决定性证据：`git show 72de494:<测试文件>` 显示**该提交下测试仍只列八项**，
即 `72de494` 自己把契约测试改红，而未被发现（`PuddingHost.Tests` 从那时起跑不起来）。

## 3. 为什么不能「直接收窄到八项」

`PuddingBrowser.AgentTools` 程序集的注册点共 4 处扫描，其中**只有一处**扫的是这个程序集：

| 位置 | 扫描的程序集 |
|---|---|
| `PuddingRuntime/DependencyInjection.cs:237` | `PuddingRuntime` |
| `PuddingHost/.../PuddingServiceCollectionExtensions.Runtime.cs:318` | `PuddingHost` |
| 同上 `:319` | `PuddingRuntime` |
| **`BrowserBridgeServiceCollectionExtensions.cs:142`** | **`PuddingBrowser.AgentTools`** |

所以把这里改成白名单八项，等于**把 `ReadPanelTool` / `RenderPanelTool` / `PreviewDocumentTool`
从 DI 里整体删掉**——从「多注册三个」变成「少了三个功能」，性质更差。

## 4. 两条修复路线

| 方案 | 内容 | 前置条件 | 代价 |
|---|---|---|---|
| **A（推荐）** | 先为面板/文档工具建立**独立注册点**（其依赖 `IPanelCanvasStore` 仅在 `PuddingServiceCollectionExtensions.Platform.cs:161` 登记 ⇒ 新注册点需与该扩展同位或显式 `TryAdd`），再把浏览器注册收窄为按 `BrowserAgentToolIds.All` 白名单 | 需要先确定面板/文档工具的归属模块 | 两处改动 + 回归；顺序不可颠倒 |
| B | 保持扫描，在该扩展内 `TryAddSingleton<IPanelCanvasStore>`，并把测试期望改为实际集合 | 无 | 把「浏览器自动化」变成事实上承载面板能力的容器；「八项」文档需一并作废 |

**推荐 A**：文档、测试、命名三处都说八项，只有一行代码不一致；而且 A 保留了两个能力族的边界。

注意 A 的顺序约束：**先建新注册点，再收窄**。反过来会静默丢工具。

## 5. 为什么这不是线上故障

生产组合链为 `PuddingServiceCollectionExtensions` 的分部方法，`AddBrowserBridgeServices`
（`PuddingServiceCollectionExtensions.BrowserBridge.cs:13`）与 Platform 扩展同批调用 ⇒
生产容器里 `IPanelCanvasStore` 可得，`ReadPanelTool` 可构造。

失败的 5 例只发生在测试自建的**窄容器**（仅调用 `AddDesktopBrowserAutomation`）。

因此定性为「契约漂移 + 测试红」，不构成运行时故障。但它暴露了一个真实的结构问题：
**一个注册扩展对外宣称的能力边界，不该由「同程序集里恰好还有谁」决定。**

## 6. 待决

1. 面板/文档工具归属：留在 `PuddingBrowser.AgentTools` 程序集但独立注册，还是迁出为单独程序集。
2. 若选 A：新注册点放在 Platform 扩展内，还是新建 `AddPuddingPanelTools`。
3. 是否顺手把 `AddPuddingToolsFromAssembly` 加一个「按 ToolId 白名单」的重载，让这类边界可被编译期
   或启动期表达，而不是靠人记得。
