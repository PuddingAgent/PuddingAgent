# 浏览器身份委托与凭据安全模型

## 1. 缘起

用户（2026-10-12）在实测 Agent 浏览器时提出三点，并要求**先把一个"Agent 能方便控制 Agent 浏览器"的控制模型跑通**：

1. **Agent 的身份很大程度上依赖人类身份** —— 多数网站不支持 Agent 自助注册/登录，Agent 只能借人类账号行事；
2. **Agent 使用"人类身份"，而 Harness 没有控制与授权机制**；更本质地说，**Agent 使用 WebView2 的 Cookie 既无授权机制也无隔离机制**；
3. **人类登录之后没有有效的审计与撤销机制**（例如撤销浏览器上的全部 Cookie）。

本文把上述三点固化为安全模型，逐条对齐现状代码，并给出控制模型的实现路线。

## 2. 三层安全模型与现状核对（全部证据由本 Agent 亲读）

### L1 身份层：Agent 无独立站点身份，必须以"人类名义"行事

| 事实 | 证据 |
|---|---|
站点侧只认登录态（cookie/session），不认 Harness 内部身份 | 现有 `BrowserCallerIdentity(kind/callerId/taskId/parentTaskId)` 只用于 **Harness 内部**归属；站点不可见 |
内部身份确实已被引入 | `BrowserCallerIdentity` 参与命令、指纹、许可与审计 |

⇒ **结论**：无法期待站点侧区分"人"与"Agent"。因此**责任必须在 Harness 侧显式承担**：谁把身份委托给了谁、允许做什么、多久、如何撤销。当前**没有"委托"这一概念**（只有页级/动作级许可）。

### L2 凭据层：Cookie/Profile **没有任何授权与隔离机制**（比描述更彻底）

| 环节 | 现状（file:line） | 判定 |
|---|---|---|
读 Cookie | `Source/PuddingBrowser.WebView2/WebView2BrowserContext.cs:113-116`：`GetCookiesAsync` **返回空数组** | 桩 |
写 Cookie | 同文件 `:119-122`：`SetCookiesAsync` / `ClearCookiesAsync` → **`Task.CompletedTask`** | 桩 |
站点权限 | 同文件 `:124-129`：`GrantPermissionsAsync` / `ResetPermissionsAsync` → 空实现 | 桩 |
Host 侧镜像 | `Source/PuddingHost/BrowserBridge/RemoteBrowserContext.cs:103-106`：`Set/Clear` → `Unsupported()` | 未实现 |
隔离底座（已具备） | `Source/PuddingBrowser.WebView2/WebView2BrowserRuntime.cs:40`：`userDataDir = options.UserDataDirectory ?? <DataRoot>/browser/contexts/<contextId>/user-data` | **每 context 一个独立 UDF** ✔ |
当前授权粒度 | 页级 `Read`/`Write`（`BrowserBridgeCommandDispatcher` §5.2/§5.3）；context 级 Trust 另有一套 | 与**凭据无关** |

**关键推论**：cookie/session 是 **per-profile（per-context UDF）**，**不是 per-page**。因此"给某个页面写权限"等价于"给该 profile 上**所有已登录站点**的可达性"。这解释了用户的第 2 点：**页级授权解决不了凭据级风险**。

**实测场景（用户自述 + 本 Agent 观察一致）**：人类在 **Agent 浏览器内**登录了知乎 ⇒ 该人类凭据落在 Agent 可达的 profile 里。这不是缺陷本身，但它说明：**"Agent 浏览器"当前同时是"带着人类凭据的浏览器"**。

### L3 审计与撤销层：动作级已有，**凭据级为零**

| 项 | 现状 |
|---|---|
动作级审计 ✔ | 操作账本（幂等/终态）+ `BrowserActivityEvidenceExporter`（脱敏、上限 100 条） |
凭据不外泄 ✔（部分） | `Source/PuddingBrowser.Abstractions/BrowserOperationOrigin.cs:6` 明确"不含 URL/cookie/token/prompt" |
**凭据级审计** ✘ | 无法回答"Agent 以我的身份访问过哪些站点" |
**撤销** ✘ | `ClearCookiesAsync` 是空实现；无"清全部 / 清某 origin / 清某任务 context"入口；无"撤销即在途停止"语义 |

## 3. 设计代际冲突（必须先裁决，否则任何改动都会南辕北辙）

| 代 | 文件 | 口径 |
|---|---|---|
**V1** | `Docs/07_architecture/69…实施规格.md` §1.1（2026-08-02，10-02 复核，`status: active`） | 「Agent Browser 使用**独立 Context、Page、UDF**」；「**V1 使用 `AllowAllBrowserCapabilityPolicy`**」；「暂停、接管和继续是**运行控制，不是权限审批**」 |
**B1/修订方案** | `Docs/12_features/B1身份准入接线与浏览器交付下一阶段实施方案-2026-10-09.md`、`Docs/12_features/浏览器交付修订施工方案-2026-10-12.md` | 可信执行身份 + 任务绑定 + **每页 grant**（Read/Write，fail-closed）；「许可由控制面签发，**普通调用只消费**」 |

**证据**：`AllowAllBrowserCapabilityPolicy` 在 `Source/PuddingBrowser.Automation` 已 **0 命中** ⇒ V1 策略被新授权栈替换，但**没有一份文档裁决这次替换**，69 规格仍 `active`。

**当前后果（实测）**：闸门已开（`BrowserBridgeCommandDispatcher.cs:413-415`），但**签发端在本机生效传输上是 no-op**（见 §4）⇒ **Agent 连 `browser_tabs list` 都被拒**。即：**既丢了 V1 的可用性，也没换来安全**（今天不是"有控"，而是"全拒"）。

## 5. 控制模型目标（本轮要"跑通"的可验收定义）

- **A1** Agent 能对 Agent 浏览器执行：`list` / `locate` / `navigate` / `read` / `click` / `fill` / `scroll`；
- **A2** **不需要每次手工选页**：用户一次显式选择后，Agent 可持续操作该页（含该页内导航）；换页/换任务需重新选择；
- **A3** **未授权仍必须拒**（保留闸门语义），拒绝原因可读；
- **A4** 全部动作留动作级审计（已有），并新增"授权来源"可追溯（谁选的、何时、对哪页）。

## 6. 三条实现路线（含成本与风险；需用户裁定）

### 路线 A —— 零代码：启用能力通道（可用于**今天跑通**）

在 `%LOCALAPPDATA%\Pudding\desktop.json` 增加 `desktop.capabilityChannel`（文件型设置字段：`Enabled` / `DesktopId` / `ControlTokenHeader` / `HandshakeTimeoutSeconds`，映射见 `DesktopApplicationCoordinator.Capability.cs:266-273`），使其非 null 且 `Enabled=true`，随后重启 Desktop。

- **两侧都要开**（`Desktop:CapabilityChannel` 是同名段，两侧各自绑定、**默认都关**）：
  - **Core 侧**：`Source/Pudding.CapabilityBroker.AspNetCore/CapabilityChannelConfiguration.cs:18`（`SectionName = "Desktop:CapabilityChannel"`）→ `PuddingApplicationHost.cs:281` 绑定、`:312` 装配；**校验 fail-closed**：`Enabled` 未开不得构造（`:111`）、**`Grantable` 为空直接报错**（`:117`）、`Transport` 三态（`named-pipe` 缺省 / `loopback-h2c` / `both`）且必须与监听一致（`:126-147,192-206`）、能力线名未知即整体失败（`:235`）。Core 的本机配置载体是 `D:\Data\config\system.json`（其 `desktop` 节点现仅有 `core`）。
  - **Desktop 侧**：`desktop.json` → `desktop.capabilityChannel`（`Enabled` / `DesktopId` 缺省 `default` / `ControlTokenHeader` 缺省 `x-pudding-control-token` / `HandshakeTimeoutSeconds` 缺省 15，须在 1–120），见 `Source/Pudding.DesktopService/DesktopCapabilityChannelSettings.cs:17-30`；**凭据不从配置读**，由主机侧注入（`DesktopConnectionOptions.Authentication`）。
  - **传输二选一**：Desktop 启用即走能力通道，**不做跨传输回退** ⇒ 握手失败会影响浏览器能力可用性（`DesktopCapabilityChannelPreflight` 为前置校验），需实测确认失败时的行为。
  - 效果：使第 4 环 `sessionResolver()` 解析到会话 ⇒ 真的发出 `browser.binding.apply` ⇒ 用户选页后签发 grant ⇒ A1–A4 可达成。
  - 待实测：`Grantable` 的**能力线名**必须取自能力目录（写错即整体失败）；`ControlTokenHeader` 的实际凭据来源待核。
- **风险**：能力通道路径**从未真机验证**（它同时会改变 `TransportRoutedBrowserCapabilitySurface` 的传输路由：通道就绪即走通道）；`controlToken` 的具体来源需核对（`D:\Data\config\system.json` 的 `desktop.core.controlToken` 已存在，是否为同一凭据待确认）。**未验证项，不做承诺**。

### 路线 B —— 代码：为 Bridge 传输接线触发点门（**修默认路径**；成本已上调，见下）

- ⚠️ **新证据（本文撰写时核实）**：`browser.binding.apply` 目前**只在能力通道执行器里处理**（`Source/Pudding.DesktopService/DesktopService.cs:398`；策略 `DesktopCapabilityPolicy.cs:59` 要求 context Trust = `AgentAuthorized`），而 Bridge 路径（`Source/PuddingDesktop.WpfArchive/Browser/`）检索**零命中** ⇒ 路线 B **不是"纯接线"**：要么为 Bridge 增加 `binding.apply` 承载（新协议面 + Desktop handler + 用例），要么改由其他既有通道送达。成本高于初判。
- 为 `DesktopBrowserBindingGate` 提供"经 Bridge 发送 `binding.apply`"的 `DesktopCapabilitySender`（或等价实现），并在 `BrowserBridgeServiceCollectionExtensions` 按**传输决策**注册（通道可用用通道门，否则用 Bridge 门）。
- 补 **Bridge-only 端到端用例**：① 用户选页 ⇒ 首次命令触发签发 ⇒ 读成功；② 未选页 ⇒ 仍拒；③ 换页/任务结束 ⇒ 撤销后拒。
- 成本：Host 组合根 + 一个 sender 适配 + 3 条用例；**收益**：默认传输可用，且**保留**闸门语义（不破坏 F1/F4 的安全结论）。

### 路线 C —— 最小可用补丁（**与既有设计冲突，仅列供裁定**）

把"用户点击「设为 Agent 目标」"直接作为 Desktop 侧签发源（点击即签发 grant 并可见反馈）。

- **冲突点**：修订方案 §4.1 明确「许可由控制面签发，**普通调用只消费**」；本例例 `BrowserTaskBindingService` 也强调"绑定不能替代用户选择"。若采用 C，等于把签发权从控制面下移，需**显式裁决**并同步修订方案。

**建议顺序**：先用 **A** 拿到"能跑通"的观察（同时验证通道路径本身是否成立），并行做 **B** 作为长期修法；**C 不采用**（除非 A/B 均不可行）。

## 7. 凭据层（L2/L3）的后续工作（**不在本轮范围**，先登记）

| 优先级 | 工作 | 验收（能取红） |
|---|---|---|
P0 | `Get/Set/ClearCookiesAsync` 由桩变实（WebView2 `CookieManager`）；三级清理：全部 / 某 origin / 某任务 context | 写入后读回一致；清除后为空；把 Clear 改回空实现 ⇒ 用例必须红 |
P0 | 撤销语义："撤销后在途动作立即停止" | 撤销瞬间正在执行的写操作，driver 调用数不再增长 |
P0 | 授权粒度由"页"提升到"**身份 × origin × 能力 × 期限**"；未授权 origin 即使 cookie 存在也拒（context 选择处强制） | profile 已登录 A 站但未授权 ⇒ 访问 A 站被拒 |
P1 | 凭据级审计（origin + 授权来源 + **不含 cookie 值**）+ 人类一键撤销入口 | 审计可回答"哪些 origin 用过我的身份" |
P1 | 隔离策略：一个任务一个 context；"人类自己的会话"与"给 Agent 用的会话"不得同 UDF | 跨任务 context 不可复用（反例取红） |

- §2 L2 的"桩"结论取自**源码亲读**，未在真机上尝试写/清 Cookie；
- §4 第 8 行的"未被注册"限于已检索目录（Host/Runtime 为完整扫描，跨全 `Source` 为 partial）；
- 路线 A 的字段与凭据来源**尚未实测**，属待验证；
- 本文**不改变**任何代码或配置；69 规格与 B1 方案谁为准**需用户裁定**。

### 9.3 三个 fail-closed / 静默陷阱（务必知道）

| # | 陷阱 | 后果 |
|---|---|---|
① | `grantable` 写入**未登记**的线名 | **整体失败**（不启动半配置端点），Core 侧报错（`CapabilityChannelConfiguration.cs:235`） |
② | `grantable` **合法但漏项**（如漏 `browser.binding.apply`） | **静默**：通道起来、能力未授予 ⇒ 浏览器仍不可用，且报错不指向此因 |
③ | 通道启用后**不做跨传输回退** | 握手失败会直接影响浏览器能力可用性（`DesktopCapabilityChannelSettings` 注释） |

### 9.4 与 `DesktopId` / 凭据的一致性

- `desktopId` 两侧缺省均为 `default`，保持一致即可；
- **凭据不在配置里**：`ControlToken` 仍由既有 `system.json` 流程管理（本类不读取），Desktop 侧由主机注入 `DesktopConnectionOptions.Authentication` ⇒ 无需手填 token（**待实测确认**）。

### 9.5 执行顺序（待用户批准后）

1. 备份两处配置（带时间戳后缀）→ 按 §9.1 / §9.2 写入 → **重启 Desktop**；
2. 重启后按顺序验证：`browser_context list` → 用户点「设为 Agent 目标」→ `browser_tabs list` 应成功（首次调用会触发 `browser.binding.apply` 并签发 Read|Write grant）；
3. 取红对照：不作目标选择时仍应返回 `page_grant_required`（证明闸门未被削弱）；
4. 若失败，按 ③ 判断是握手问题还是能力未授予问题，回滚=删两处节点再重启。
