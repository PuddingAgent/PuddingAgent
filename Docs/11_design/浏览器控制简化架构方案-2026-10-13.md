# 浏览器控制简化架构方案

> **实施基线已替代**：当前施工遵循 [ADR-097](../07_architecture/111ADR-097Agent浏览器控制一期闭环与单一执行链ADR.md) 与[一期整体方案](../12_features/Agent浏览器控制一期整体实施方案-2026-10-18.md)。下文保留为历史方案与审阅记录，不再逐节执行。尤其“旧权威保留/新权威替换”“身份仅审计/会话归属”“接管只翻转布尔值”等相互冲突的条款，以新基线为准。不得照下文清单直接删除生产组件；先修正独立组件并完成单一主链接入。

> 用户裁定（2026-10-13）：「现有的设计过于复杂，缺乏架构设计……我们需要 Agent 可以控制浏览器。」
> 本文是**方案**（status: proposed），不是已完成变更。所有现状断言都带 file:line 或实测原始输出。

## 1. 结论（TL;DR）

现状不是「权限太严」，而是**责任无主**：一条浏览器工具调用要穿过 **5 个环节、3 道 fail-closed 闸门、2 种传输**，每一环由不同变更集落地，**没有任何一条端到端用例能把"整链路是否可用"变成红色**。于是同一个用户意图，在不同配置下会得到**三种不同的拒绝码**，而用户读到的是"点了没反应"。

**目标架构（四减一）：**

| 维度 | 现在 | 目标 |
|---|---|---|
| 授权入口 | 5 环（选页 → 任务绑定 → 通道握手 → Broker 授权器 → 页级 grant） | **1 环**：用户的「设为 Agent 目标」直接开一个 **AutomationSession** |
| 权威对象 | 3 份（Bridge 门 / Broker 授权器 / Desktop authority） | **1 份**：`BrowserAutomationAuthority`（已存在，保留并加固） |
| 传输 | 2 种（WebSocket Bridge + 能力通道），且「启用即不回退」 | **1 种**：WebSocket Bridge 为浏览器工具的唯一必需传输 |
| 身份 | 2 处（Ambient 轨迹 / capability trusted caller） | **1 处**：工具执行期的 Ambient（P1 已落地） |

## 2. 现状：链路的每一环（全部一手证据）

### 2.1 环节与闸门

| # | 环节 | 证据 |
|---|---|---|
| 1 | 工具（Core 进程）发起 | `browser_*` 工具 → `RemoteBrowserRuntime` |
| 2 | 传输 | Desktop **反向**连入 Core 的 WebSocket：`Source/PuddingHost/BrowserBridge/DesktopBrowserBridgeWebSocketEndpoint.cs`（loopback → control token → WS → `registry.TryAttach`（已有连接即拒）→ **5s 内 Hello**）。单槽注册表：`DesktopBrowserConnectionRegistry.cs`（`IsDesktopConnected` 仅当 `IsHandshakeAccepted`） |
| 3 | 第二传输 | 能力通道（named pipe / loopback-h2c），由两侧配置开启：Core `D:\Data\config\system.json`、Desktop `%LOCALAPPDATA%\Pudding\desktop.json` |
| 4 | 授权（3 份） | ① Core 工具缝：`Source/Pudding.CapabilityBroker/TrustedCallerDesktopCapabilityAuthorizer.cs`（四条 fail-closed 规则，第 2 条要 Agent 身份）；② Bridge 侧：`BrowserBridgeServiceCollectionExtensions.cs` 只注册 `CapabilityChannelBindingGate`（无会话即 **no-op**），而内容更完整的 `DesktopBrowserBindingGate` **无任何组合根注册**；③ Desktop 侧权威：`Source/PuddingBrowser.Automation/BrowserAutomationAuthority.cs`（857 行，真决策者） |
| 5 | 签发 | `browser.binding.apply` **只在能力通道执行器**处理：`Source/Pudding.DesktopService/DesktopService.cs`（~:398/419）；Bridge 路径 0 命中 |

### 2.2 权威对象的活性来源（当前阻塞点）

`BrowserAutomationAuthority` 是 **Desktop 侧**对象（其测试在 `Source/Pudding.DesktopServiceTests/`）：

- 内部 `ConnectionGeneration _generation = ConnectionGeneration.None`，构造时不活；
- 只有 `NotifyConnectionGeneration(gen)` 被调用后 `ConnectionGeneration.IsLive` 才为真（`BrowserAutomationAuthorityGenerationTests.cs:22-29` 明确断言 `None ⇒ IsLive == false`）；
- 未活时 `GateConnectionAndIdentity` 直接拒：`DesktopCapabilityError.NotConnected("the desktop connection is not established; no automation permit exists")`（`BrowserAutomationAuthority.cs:664`）。

⇒ **"谁负责调用 `NotifyConnectionGeneration`"就是那个责任无主点**：握手成功与权威置活之间没有端到端契约，也没有能取红的用例。

### 2.3 用户动作不产生授权

`Source/PuddingDesktop/MainWindow.xaml.cs`（~:1069）`OnTarget → AssignAgentTargetAsync(page)` 只写 **page 级 target 标记**；UI 无生效反馈（`MainWindow.xaml:323` 是写死的 `TextBlock`）。用户点按钮 ⇒ 系统状态无任何授权变化。

### 2.4 「启用即不回退」放大器

`Source/Pudding.DesktopService/DesktopCapabilityChannelSettings.cs` 注释原文：**「启用即走能力通道，不做跨传输回退（避免同一操作被执行两次）」**。

> ⚠️ **本条已被证伪（2026-10-13 晚，codex 全权限核验）**：注释如此宣称，但实现是**两条传输同时启动**（`DesktopApplicationCoordinator.cs:761-770`），路由在**无活动 channel 会话时选择 Bridge**（`TransportRoutedBrowserCapabilitySurface.cs:232-247`）；「不回退」只约束**同一次操作**不跨传输重试。⇒ 「握手失败即整体不可用」属我的过度推断，详见 §10.2。

### 2.5 同一意图三种拒绝码（实测原始输出，Agent 侧只读调用）

| 配置态 | 原始返回 |
|---|---|
| 通道双侧关闭（原始） | `page_grant_required: no read page grant for this caller on <contextId>/<pageId>` |
| 通道双侧开启后 | `browser_context_failed: desktop capability not authorized: capability requires a trusted agent context, but the caller has no agent identity` |
| 通道开启 + 进程重启后 | `browser_context_failed: the desktop connection is not established; no automation permit exists` |

同时 Core 日志确有连接：`2026-10-13 17:50:29 [BrowserBridge] Browser Bridge connection attached: "a2446311-…" gen=1`。

## 3. 目标架构

### 3.1 数据模型：AutomationSession（唯一的授权载体）

```text
AutomationSession {
  SessionId            // 幂等键
  DesktopId, ProcessInstanceId
  Caller               // BrowserCallerIdentity { kind, callerId, taskId, parentTaskId }
  Targets[]            // 用户显式选中的页（{contextId, pageId}）
  Scope                // Read | Write（默认 Read；写需二次确认策略）
  IssuedAt, ExpiresAt? // 缺省不过期，随目标切换/撤销而终止
  RevokedAt?           // 撤销即在途停止
}
```

- **签发唯一来源**：用户在 Desktop 上对某页点「设为 Agent 目标」⇒ **开启/更新一个 session**（这就是 V1 规格说的"运行控制"）。
- **page-level 的"谁被允许动哪一页"由 session 派生**，不再单独签发一层 page grant；同一页的写串行化继续用既有 **lease**（`HasWriteCoverage` 不变式保留）。
- **子代理**：继承父 session 的 Targets 与 Scope 子集，**不得扩大**（`BrowserGrantIssuancePolicy.EnsureSubAgentScopeIsSubset` 已存在，保留其判定，输入换成 session 派生的范围）。

### 3.2 权威对象：保留 `BrowserAutomationAuthority`，去掉它的"活性黑箱"

- 保留：`Admit` / `Revalidate` / lease / takeover / 拒绝分类学（这些是本仓库少有的、真正成体系的架构资产；审计已证实"三份互不相通的 takeover 表示"是历史缺陷，收敛方向正确）。
- 修改：**活性不再依赖"别人记得通知我"**——连接建立/断开必须由同一处代码成对驱动：`connection attached ⇒ NotifyConnectionGeneration(gen)`；`detached ⇒ NotifyConnectionGeneration(ConnectionGeneration.None)`。并要求有一条**能取红**的用例。
- 修改：`_generation` 由"传输握手"定义，而**不被"是否启用某个新通道"定义**。

### 3.3 传输：浏览器工具只依赖 WebSocket Bridge

- Bridge 已有：单槽、世代、心跳、watchdog、fail-pending、loopback+token 校验 —— 是一套**完整且已被验证**的传输。
- 能力通道（capability channel）**继续服务于它的其他能力**（Shell 通知/文件选择/剪贴板等），但**浏览器控制不依赖它**。理由：它当前是"浏览器唯一签发者"，把一个可用性关键路径挂在一条默认关闭、无回退的通道上，是**可用性风险**而非安全收益。
- 若某能力确实需要通道，应显式声明为**该能力的**依赖，而不是全局开关。

### 3.4 身份：以 Ambient 痕迹为唯一来源

P1（commit `eb55dee`）已在**工具执行边界**把本次调用的 `RuntimeTraceContext` 发布到 Ambient，`AgentInstanceId` 由此可获得。⇒ Core 侧"可信调用者"判定改为读 Ambient；`TrustedCallerDesktopCapabilityAuthorizer` 的规则 ②/③ 保留语义，但**输入不再是"能力通道会话"**。

### 3.5 凭据层（与本次简化正交，但必须显式登记为 V1 边界）

现状：`WebView2BrowserContext` 的 `GetCookiesAsync` 返回空数组，`SetCookiesAsync` / `ClearCookiesAsync` / `GrantPermissionsAsync` / `ResetPermissionsAsync` 均为空实现；Host 侧 `Set/Clear` → `Unsupported()`。隔离底座已有（每 context 独立 UDF；实测 profile：`D:\Data\browser\agent-browser\user-data`、`D:\Data\browser\workbench\user-data`）。

V1 必须补齐的只有一条：**撤销**（清空指定 context 的凭据 = 一键收回"以你名义行事"）。读/写 cookie 的具体值**不应**开放给 Agent（那会让凭据进入模型上下文）。

## 4. 要删的东西（激进清单）

| 删除对象 | 理由（安全性论证） |
|---|---|
| 「浏览器工具依赖能力通道」这一隐式约束 | 可用性关键路径不应挂在默认关闭、无回退的开关上；能力通道的其他用途不受影响 |
| `browser.binding.apply` 作为**唯一**签发者 | 它与"用户必须亲身选页"这一真正的安全性质无关；session 由用户动作直接产生 |
| 两份 BindingGate 中的一份（建议删 `CapabilityChannelBindingGate` 对浏览器的作用，或在浏览器路径上只留经注册且有测试的那一份） | 双 gate ⇒ 判定漂移；未被注册的 gate 是"以为有防线"的幻觉 |
| `BrowserManagementGrant` 的独立签发链（若仅用于 context 创建/关闭） | 由 session 派生即可，减少一层独立性 |
| `DesktopCapabilityChannelSettings` 对浏览器的「启用即不回退」约束 | 改为按能力声明依赖 + 失败可见（不再静默整体失效） |

**保留**：lease / 写串行化、接管与暂停（作为**运行控制**）、拒绝分类学、操作账本与幂等、脱敏证据导出、"用户未选页则拒"这一条不变式。

## 6. 能取红的验收清单

**宿主无关（S1/S3/S4 单元）**
1. `SessionWithoutUserTargetIsRefused` —— 无 session ⇒ 拒（保护 F4 原有性质）。
2. `UserTargetOpensExactlyOneSession` —— 重复点击不产生第二个 session。
3. `RevokeStopsInFlightAndThenRefuses` —— 撤销后在途写请求被拦。
4. `TakeoverBlocksSideEffectsButKeepsRead` —— 接管是运行控制语义（回 69 规格）。
5. `SubAgentCannotWidenParentScope` —— 子集判定。
6. `DetachedConnectionIsNotLive` —— detach 后 `ConnectionGeneration == None`。

**集成（真机，必须能失败）**
7. 点按钮 ⇒ `browser_tabs list` 返回 page 列表（现状：被拒）。
8. 不点按钮 ⇒ 仍 `page_grant_required`（证明闸门没被削弱）。
9. 断开 Desktop ⇒ 工具报 `NotConnected`（而不是静默超时）。

**变异项（每项必须让至少一条用例变红）**：删除 `NotifyConnectionGeneration`；删除 session 校验；把 scope 子集判定放宽。

## 7. 风险与未证实项（诚实标注）

1. **`NotifyConnectionGeneration` 的生产调用点尚未取证**：本文只确证"权威需要它才活"与"当前它未活"，**未**确证"WS 连接成功时是否本应调用它、以及为何没调用"。S3 的第一步就是把这个调用点找出来并写成能取红的用例。**在此之前不要把 §2.2 的因果写成结论。**
2. 能力通道与本机配置：上一轮我启用过双侧通道配置，**已按备份还原**（`desktop.json` → `"desktop": null`；`system.json` 无 `capabilityChannel`），但**运行中的进程仍持有旧配置**，需重启才生效。还原仅消除"无回退"风险，**不恢复功能**。
3. 删除 `CapabilityChannelBindingGate` 对浏览器的作用，可能影响其他能力的准入语义 —— 需按 §4 的表逐项核对调用方。
4. ~~**codex 规划通道本轮不可用**~~ ⇒ **已恢复，见 §9**。两次失败与解法：① 首次 `chatgpt.com` 全域不可达（`failed to refresh available models: request timed out`，挂起 18 分钟）——根因是**系统代理未被 codex 继承**（注册表 `ProxyServer=127.0.0.1:7897` 且已监听，但环境无 `HTTP(S)_PROXY`），显式注入后模型即可应答；② 随后撞上 **codex Windows 沙箱损坏**（`helper_sandbox_lock_failed: lock sandbox bin dir C:\Users\hyfree\.codex\.sandbox-bin`），它**读不到任何文件** ⇒ 改为**内联简报**并用 Python 直调 `codex.exe`（绕开 cmd 8191 字符上限）。产出见 §9。

## 8. 需要用户裁定的一条

**授权口径**：是否接受把「逐页 grant」收敛为「用户选页开 session」（即回到 69 规格 V1 的"运行控制而非权限审批"）？

- 接受 ⇒ 按 §5 执行，浏览器工具可用性由**一条**链路决定，且失败点可见。
- 不接受 ⇒ 必须为该链条补一条**能取红的端到端用例**，否则"复杂且随时整体失效"会持续存在。

## 9. codex 独立评审（2026-10-13 晚）与合流

### 9.1 运行事实（可复现）

- 调用：`codex exec -m gpt-5.6-sol -s read-only --ephemeral --color never -C <repo> -o temp/codex-plan-browser-simplify.md`，prompt = 简报**内联**（12,084 字符，脚本 `temp/run_codex_inline.py`）。
- 产出：`temp/codex-plan-browser-simplify.md`（**15,138 B**，EXIT=0，耗时约 2 分钟）。
- **权重限制（必须声明）**：codex **未读取仓库**（其 §10 自述"仅依据 brief，未读取仓库"），因为它读文件的那条路径被沙箱故障阻断。⇒ 其结论属**基于简报的纯推理**，对"事实层"**无独立校验力**，只对"设计层"构成独立第二意见。本节据此采信其**设计判断**、不采信其**事实断言**。

### 9.2 合流：采信 codex 的三处修正

| 项 | 我的原方案 | codex | 裁定与理由 |
|---|---|---|---|
| **组件边界** | 保留 `BrowserAutomationAuthority.cs`（857 行）并加固 | **抽成独立可测组件**：`Source/PuddingBrowser.Authorization/AgentTargetSessionAuthority.cs` + `AgentTargetSession.cs` + 独立测试工程 | **采信 codex**。符合第一原则「能拆就拆，首要目的是**可测试**」；现在的权威对象与 Desktop 生命周期纠缠，无法宿主无关地测。**但抽取时禁止顺手重构**（第一原则明示） |

### 9.3 合流：codex 补齐的关键项（我原方案缺失）

1. **统一错误分类学**（直接治"点了没反应"）：`browser_transport_unavailable` / `agent_target_required` / `agent_target_revoked` / `user_confirmation_required` / `browser_busy`。禁止再让同一意图产出三种拒绝码。
2. **可见降级**：Desktop 常驻显示**连接状态 + 目标状态**；Core 健康端点报告 `Connected / HandshakePending / Disconnected`；工具错误携带可行动建议（且不泄露 token）。
3. **生命周期归属的具名答案**（正是我 §2.2 悬而未决的那个"责任无主点"）：Desktop 侧 Bridge connection supervisor 在收到 handshake 成功确认后调 `OnBridgeReady(generation)`，在 socket 关闭 / heartbeat 超时 / handshake 拒绝时调 `OnBridgeLost(generation)` 并**撤销 session**；并要求"删掉 `OnBridgeReady` 调用 ⇒ 测试必红"。
4. **UI 必须显示失败**：`AssignAgentTargetAsync` 创建 session 失败时**保持非目标态并立即报错**，不得只写 marker 静默失败。
5. **高风险动作逐次确认**（结构化动作拦截）：资金类（支付/转账/购买/下单/订阅）、发送类（发布/评论/私信/邮件/提交表单）、敏感域（账户安全/身份认证/密码/API key/授权绑定）。**无法可靠分类的不可逆写操作默认要求确认**；确认 UI 不可用时 **fail closed**。
6. **凭据边界（V1 最小集）**：禁止**读取/导出** cookie 明文与认证 header（不进模型上下文、日志、诊断包）；**允许页面内正常携带** cookie 发请求；**必须撤销**（取消目标/接管/断线/关页/清 profile）；**必须清空**且真实调用 WebView2 清除 API，**失败要显式报错**（不得保留 `Task.CompletedTask` 假成功）；必须审计 origin + 动作类别 + `AgentInstanceId` + 结果（不含秘密值）。
7. **多 Agent 的 V1 最小机制**：每个 Desktop **仅一个 active target session** + 写串行；session **不绑定 Agent**（确认窗口显示发起方 `AgentInstanceId`）；重复"设为目标"**原子替换**旧 session 并留审计事件。**不引入**多租户 grant、多 lease、按 Agent expiry。
