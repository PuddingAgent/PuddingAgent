# 定时自动化任务：设计提案

## 1. 背景：能力已经很宽，缺的是「什么时候动手」

2026-11-17 夜间巡检的实测结果（只读，无推断）：

| 现象 | 证据 |
|---|---|
| 派发链路是活的 | `TaskAutoDispatchWorker` state=running / mode=authoritative，每 5 分钟扫描；`task_scheduler_scan_runs` 已 12,768 次 |
| 时间触发完全没有 | 全仓搜任务语义的 `ScheduledJob` / `TaskTrigger` / `Cron` 均 0 命中；`Recurring` 仅 1 处且与任务无关 |
| 后果一：数据库无清理 | `conversation_events` 涨到 425 万行 / 库 12.2 GB，`retention-archive` 最后一次归档停在 08-20，`config` 里查不到任何 retention 配置 |
| 后果二：队列积压无人知 | `message_deliveries` 有 8 条 `queued` 从 07-23 积到 11-17（117 天），`attempt_count=0` |
| 后果三：假错误淹没真错误 | 最近 20 个非空 error 日志，20 个都是同一个 MCP 连接失败堆栈（每次重启写一条 3.2 KB） |

一句话结论：**平台不会自己按时间做事，所以任何「随时间变坏」的东西都没人发现。**

已有的「潜意识」节律任务（做梦 6h / 模式抽取 12h / 技能改进 4h）是系统自维护，面向 Agent 自身，不能替用户跑业务定时。

## 2. 需求（可判定的）

1. 能定义「每天 08:00 / 每周一 09:00 / 每 2 小时」这类规则，**带时区**。
2. 到点后**不需要人操作**，产出应当出现在既有可见面上（任务看板 / 会话 / 消息）。
3. 同一时刻**不得重复触发**（进程重启、多次 tick、并发扫描都不能导致重复）。
4. 停机期间错过的触发，行为必须**显式可选**，而不是默认静默丢掉。
5. 能停用、能手工触发一次、能看最近一次结果。
6. 触发失败必须留下可查询的痕迹，不能只有日志。

## 3. 设计：只做触发器，不做第二个执行器

### 3.1 链路

```
定时器 tick（每 1 分钟）
  → 取 next_run_at <= now 且 enabled 的 schedule
  → 用 (schedule_id, scheduled_fire_time) 做幂等键建一张任务卡
  → 推进 next_run_at 到下一时刻
  → 现有 TaskAutoDispatch 接手派发与执行
```

**关键取舍**：不新建执行器。派发、模型路由、预算、重试、恢复、终态，这套东西已经跑了一个月（12,768 次扫描是证据）。再写一套只会多一条会漂移的真源——这正是本仓已经吃过亏的模式（`goal.md` vs `GoalRun` 两套目标互不相认）。

### 3.2 数据模型（草案）

```
AutomationSchedule
  Id                Guid
  Name              string        -- 人读名称
  CronExpression    string        -- 5 段（分 时 日 月 周）
  TimeZoneId        string        -- IANA 或 Windows id，显式存
  Handler           string        -- 生成什么卡：inspect_house / prune_events / custom_prompt
  PayloadJson       string?       -- 交给 handler 的参数
  CatchUpPolicy     enum          -- skip | run_once | run_all（默认 skip）
  IsEnabled         bool
  NextRunAtUtc      DateTime?
  LastRunAtUtc      DateTime?
  LastFireTimeUtc   DateTime?     -- 已触发到的时刻，幂等依据
  ConcurrencyPolicy enum          -- allow | forbid（上一轮还在跑则本轮跳过）

AutomationRun                       -- 每次触发一条
  Id, ScheduleId, ScheduledFireTimeUtc, TaskId?, StartedAtUtc, Status, Error
```

`(ScheduleId, ScheduledFireTimeUtc)` 建唯一索引 —— 这是「不重复触发」的**唯一**保证点，不依赖应用层的 if 判断。

### 3.3 幂等与错过补偿

- **幂等**：靠唯一索引 + 首次写入即推进 `LastFireTimeUtc`。并发 tick 时第二个写入者撞唯一约束 → 视为已触发，直接跳过，不报错。
- **错过补偿**：进程 02:00 重启，08:00 的规则已过期。
  - `skip`（默认）：跳过，只推进 `NextRunAtUtc`。适合「巡检」这类有当下价值、补跑无意义的事。
  - `run_once`：补跑一次（用原定 `ScheduledFireTimeUtc` 作为幂等键，所以不会因多次重启而补多次）。
  - `run_all`：逐次补齐。**默认禁用**，因为它可能瞬间灌入几十张卡。

### 3.4 为什么时间判断要抽成纯函数

`NextOccurrence(cronExpr, timeZone, afterUtc)` 是纯函数：无 IO、无时钟依赖（`afterUtc` 由调用方传入）。

这样它可以被单测彻底覆盖，包括最容易错的几类：月末（1/31 → 2 月）、Dst 切换、闰年、`0 0 29 2 *` 这种四年一次。**这类日期逻辑靠人工 review 抓不住，必须靠测试。**

### 3.5 测试策略

| 层 | 怎么测 | 判据 |
|---|---|---|
| 纯函数 | `NextOccurrence` 表驱动单测 | 变异取红：改错边界必须有用例变红 |
| tick 服务 | 注入假时钟 | 同一 `fire time` tick 两次只建一张卡（幂等）；跨过 3 个时刻且 `skip` 只推进不建卡 |
| 落库 | 唯一索引冲突不抛异常 | 并发两次调用，最终只有 1 行 `AutomationRun` |
| 端到端 | 建 schedule → 假时钟推进 → 断言任务卡出现在看板 | 手工触发一次也要能跑通 |

## 4. 明确不做

- **不做秒级精度**。分钟级足够，秒级会把 tick 变成高频轮询，成本和收益不成比例。
- **不做分布式锁**。当前是单 Core 实例；引入分布式语义等于为一个不存在的问题付出复杂度。
- **不替换 `TaskAutoDispatch`**，也不改它的扫描周期（5 分钟）。定时器只负责「提前把卡放进去」，从放到被执行最多延迟一个扫描周期，这个延迟对「每日巡检」完全可接受。
- **不在本期做 UI**。先让 API + 数据落库跑起来，界面后置——否则会在契约还没稳定时先冻结一层前端。

## 5. 未决（需要用户裁定）

1. **cron 解析：自己写还是引库？** 自己写约 150 行且完全可控；引库要多一个依赖。本仓倾向自研纯函数（可测性优先），但需先确认是否已有可复用的实现。
2. **第一条自动化跑什么？** 候选：每日巡检（`inspect-house.ps1` 已有，可直接接）、事件剪枝（`prune-events.ps1` 已有）、A 股简报（需技能）。前两个**不需要新能力**，只差触发。
3. **失败可见性**：是复用现有任务看板的状态，还是额外发消息？倾向复用看板，避免再造一条通知通道。

## 6. 分期

| 期 | 内容 | 可验证性 |
|---|---|---|
| P1 | `NextOccurrence` 纯函数 + 表驱动单测（含变异取红） | 完全可验证，无副作用 |
| P2 | `AutomationSchedule` 实体 + 唯一索引 + tick 服务（假时钟测试） | 可验证，仍不接业务 |
| P3 | 接 `inspect_house` / `prune_events` 两个 handler | 端到端可验证 |
| P4 | API + 界面 | 前端可测 |

P1 是纯增量，不碰任何现有路径，可以立刻做。

## 7. 与「体温计」的关系

`Tools/Maintenance/inspect-house.ps1`（2026-11-17 提交）已经把「该看什么」固化了：进程、磁盘、数据库页与行数、队列滞留天数、error 日志签名聚类、启动校验。

定时层的第一个用户就是它——**每天跑一次，异常就让人看到**。两者合起来才是完整的一条腿：一个负责看，一个负责按时看。
