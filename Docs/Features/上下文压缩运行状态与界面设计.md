# 上下文压缩运行状态与界面设计

日期：2026-09-20。状态：已实现并完成定向回归，现场部署见文末。

## 问题与证据

用户截图的历史卡片停在 09-11，计时达到 12600 分钟。不能由截图判断后端此刻正在压缩。只读检查默认助手会话 `206a9b48ec904ebb93e7541131fbb835`：185 条 started/completed/failed 事件、94 个压缩 ID。最新两个孤儿 started 分别是 09-19 17:41:02 与 21:15:04（北京时间），均为手动请求。最新配对完成事件是 09-14 11:43:33。本次查询没有发现 09-20 新的自动压缩记录，也没有把截图旧卡片直接归因到这两个手动请求。

源码与回归确认三处生命周期缺陷，并补充用量显示核验：

1. `useCompaction` 对未知 ID 回退到当前活动卡片 ID，交错历史终态会覆盖另一次压缩；失败与终态无法始终精确配对。新回归在原代码得到 1 张卡、预期 2 张。
2. 手动和自动入口在候选/冷却检查前发 started，手动与自动取消路径直接抛异常不写 failed。新取消回归在原代码实际终态数 0，预期 1。
3. 手动乐观卡片没有活性定时器；通用 `processPreview` 仅凭 compacting 条目推导 running；卡片不验证后端活性，按旧事件时间无限计时。仅修 replay hook 无法覆盖这些路径。
4. 压缩结束未主动刷新 context-health，可能继续展示旧快照。初查依据前端注释误判 usageRatio 仍以 effectiveWindow 为分母；进一步核对 ContextHealthEvaluator 与部署后的真实接口，确认后端已于 09-19 将对外 usageRatio 改为总窗口口径。本次圆环直接用 used/limit 计算属于一致性防护，不能作为截图数值错误的证据。

## 显示设计

压缩属于会话维护状态，独立显示在消息列表，不使用助手头像、思考状态、工具状态或空答案气泡。删除流光文字与永久 loading toast，只保留一个主要状态区：

```text
▤ 正在整理上下文                       已用时 42 秒  执行中
正在保留关键信息并整理历史内容，请稍候。
──── 细线不定量动画 ───────────────────────────────
```

- 请求已提交：静态“正在检查是否需要整理上下文”，无动画、无计时。
- 执行中：后端确认确切 ID 后播放细线移动；不显示虚构百分比或未上报的阶段。尊重 reduced-motion。
- 完成：静态勾选、实际整理消息数（有事实才显示）、绝对完成时间；起止时间齐全才显示耗时。
- 跳过：静态“本次未执行压缩”，不冒充成功回收空间。
- 失败：静态失败状态和服务端原因。
- 状态待确认：无动画、无计时；不能将失联或没有结束记录推断为失败、成功或后端已被取消。迟到的真实终态仍可修复记录。

圆环只表达上下文占用。按 `usedTokens / contextWindowTokens` 计算，输出预留仍单独展示；面板明示非压缩进度、来源、估算标记与用量采样时间。压缩完成主动刷新；迟到的旧会话/旧请求响应不覆盖新快照。自动压缩阈值保持有效输入窗口的 80%，不为修 UI 任意改变预算、摘要内容或历史保留策略。

## 状态合同与实现

- `ContextCompactionService` 在持有单飞锁且通过冷却、候选、当前轮保护和无收益检查、完成摘要输入选取后，登记 `ActiveCompactionSnapshot(compactionId, startedAt)` 并发 started。三个入口不再抢先宣告运行。finally 清理快照，进程重启自动归零。
- `GET /api/sessions/{sessionId}/compaction-status` 返回当前精确快照，沿用会话 API 认证。只读进程内字典，无全表查询；bootstrap 同样附带快照。
- 前端加载时、收到新 started 时立即确认；之后每 10 秒确认一次，串行请求，无重叠堆积。会话切换/重置及事件交错会丢弃旧响应。
- 动画许可最长 30 秒；网络请求卡住时也到期变为待确认。服务端返回空快照则收敛当前投影。10 分钟请求兜底同样仅表示状态未知。
- 卡片按 compactionId 精确归属；历史完成不能结束另一张活动卡，不改变普通聊天 loading，也不能触发历史会话跳转。终态不能被迟到 started 复活。
- 手动、自动和工具取消/失败终态使用独立于已取消请求的 token 持久化。旧事件不修改或删除。
