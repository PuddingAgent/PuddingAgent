# ADR-089 前置设施与检索增强 · 施工计划

日期：2026-09-23。状态：**进行中**。
上游权威规格：`Docs/Features/Agent统一检索与渐进展开工具链设计-2026-09-13.md`（§10 = U3 详设）、`Docs/07架构/103ADR-089Agent统一检索与渐进展开工具链ADR.md`。

## 0. 目标与硬约束

**终局目标**：Agent 能用新的统一检索工具，在**毫秒级**定位合适目标 —— C#、前端（TS/TSX）、Markdown 一视同仁。

**用户裁决（2026-09-23）**：
1. 总体走 ADR-089（A 方案）。
2. `search_grep` 与 code 族**重叠可合并**；并借助 **outline + 索引**增强 grep 的检索能力。（归 U1/U2，**押后**）
3. **优先完成后端基础设施**：索引更新、异步更新、Windows file watch → 更新队列、基于 git 的监听与索引更新、检查索引指令。
4. **四项前置设施必须在检索增强之前完成封装与对接**：向量增强检索、outline+LSP 增强、并行检索增强、后缀名过滤。
5. **LSP 路线**：**B 起步**（扩展现有仿 LSP）+ **保留真 LSP（A）的接口位**。

**硬约束（不可违反）**：
- 不引入新搜索引擎；不接入 tgrep 的程序/依赖/服务。
- Everything 自身索引**不由 Pudding 写入**。
- 清理范围**仅为 Pudding 拥有的索引/缓存**；**绝不删除源码、工作区文件或 Everything 数据**。
- U4 权限收敛：旧工具授权**逐项映射**，禁止把任一旧权限直接升成全部新视图权限。

## 1. 总顺序

```
U3 索引维护（监听 / 异步 / 校准 / 增量）
  → ①向量检索封装  ②outline+LSP 封装  ③并行检索  ④后缀名过滤合同化
  → U1 workspace_search（含 search_grep 与 code 族合并）
  → U2 workspace_open
  → U5 毫秒级端到端验收
```

前置设施与 U3 的依赖关系：**①④** 依赖 U3 的索引水位与 scope 合同；**②** 依赖 U3 的索引新鲜度（仿 LSP 走索引）；**③** 基本独立，可与 U3 并行推进。

## 2. U3 施工拆分（四个可验证提交）

主要入口：`CodeIndexScheduler/ICodeIndexScheduler`、`ICodeIndexStore/SqliteCodeIndexStore`、各语言 indexer、`LuceneSearchEngine/IFullTextSearchEngine`、`Runtime Services/Search`、Host DI/HostedService。

### U3-A 监听 / 有界 Channel / 防抖 / scope 状态
- 新增 `Source/PuddingCodeIntelligence/Services/CodeIndex/`：
  - `IndexChange`（记录：路径、旧路径、事件类型、epoch/sequence、时间）
  - `CodeIndexChangeQueue`（有界 `Channel<IndexChange>`，容量 8192，**FullMode=Wait 但回调仅 TryWrite**；返回 false → 该 scope 标 `needsReconcile` 并计数）
  - `CodeIndexWatcher`（`FileSystemWatcher`；**回调只记录 + TryWrite，不解析源码/不算哈希/不写库/不阻塞**；排除索引自身与构建输出；**目录过滤必须在事件处理中执行**，不能假定 Windows 递归 watcher 自动排除子树）
  - `CodeIndexScopeState`（`dirty` + `observedVersion` + `needsReconcile`，**独立于队列**，避免依赖已满的队列）
- 防抖：静默窗口 **500ms**、最长等待 **2s**；Created/Changed 合并为"重读最终状态"；Renamed 同时核对旧路径清理与新路径写入。
- 扩容策略：待处理路径上限 20000，超限时细粒度待办**折叠为 scope 校准**并释放路径记录。

### U3-B 持久待办 / 增量提交 / in-flight 补跑
- `ICodeIndexStore` + `SqliteCodeIndexStore` 新增**维护控制记录**（**运行状态，不属于配置表**）：
  `scope/provider/epoch/desiredVersion/committedVersion/needsReconcile/lastSuccessfulScan`；按路径合并的 `operation/attempt/nextRetry/state`。
- **删除已知缺陷**：`CodeIndexScheduler.Enqueue` 的 `if (_inFlight.Contains(...)) return;` ⇒ 改为推进 `desiredVersion/dirtyAgain`；本批次只推进实际处理的版本，结束时仍落后则继续排队。
- `ICodeIndexer` 补**按文件**接口（现仅 `IndexWorkspaceAsync` 全量）。旧解析任务提交前校验 epoch/配置版本/文件指纹，被新版本替代则放弃并补跑。
- 原子替换：单文件更新需**原子替换**文件记录、符号、引用及相关图边；补**按文件删除/替换事务接口**（不能先对外删旧符号再逐条暴露新符号）。

### U3-C manifest 校准 / 失效 / 安全删除与 GC
- 校准：持久文件 manifest 的 **mark-and-sweep** —— 仅当该 scope/subtree **被完整成功遍历且根身份不变**时才可清理"本轮未见"条目；扫描期间收到变化的路径**暂缓 sweep**后再次核对。
- 区分 `父目录不可访问 / 权限异常 / 临时 rename / 真实不存在`；**失败或离线扫描禁止批量删除**。接入 Lucene 现有 `stalePaths` 逻辑的**完整性门禁**。
- GC：逻辑移除**及时提交**；物理目录回收由后台异步执行，须验证（归属 manifest、绝对路径在 PathHelper 管理的索引根内、未被当前 scope 引用、reader/writer 已释放），并经**可配置宽限期（建议 24h）**；Windows 占用则退避重试，**不强删**。
- 周期：正常 metadata 校准每 **15min**；监听不可用时 **60s 轮询 + 退避**；深度 hash 核验按 **24h** 分片预算。均按上次完成后计时，不并发叠加。

### U3-D 查询缓存协同 / 运维状态 / 故障恢复
- **查询线程只读可用快照**、做有界精确复核、提交 dirty 提示；**不等待全量重建或物理 GC**。
- scope 状态分离为 `availability`（available/unavailable）、`maintenance`（idle/queued/running/reconciling/failed）与各 provider 水位 —— 避免单一 Active 掩盖积压。
- 关闭：关闭事件源 → 取消接纳 → 持久化 dirty/checkpoint → 有界超时内结束 writer/reader/worker → 释放 watcher；**未完成待办重启恢复，不阻塞 Desktop 长期退出**。
- 可观测：watcher 模式与错误、队列深度、最老待办年龄、desired/committed 水位、最近成功校准、溢出/重试/失败计数、索引文件数、退休待清理字节、端到端更新延迟。日志沿用 canonical trace，**避免每个 Changed 事件刷日志**。

**驱动归属（待定）**：§10.1 要求由 Core 的**单一 BackgroundService** 统一驱动，避免原 Task worker 与新 HostedService **双写**。当前 `CodeIndexScheduler` 在 `PuddingCodeIntelligence`（被 Runtime/Host 引用）中构造期自建 `Task.Run`；`PuddingHost` 目前**无任何 CodeIndex HostedService**。倾向方案：**HostedService 住 `PuddingHost` 只做生命周期驱动，索引逻辑留 `PuddingCodeIntelligence`**。

## 3. 四项前置设施拆分

### ① 向量增强检索（底座已有，缺接线）
- 复用：`IEmbeddingService`（已在 `PuddingRuntime`，注册 `DependencyInjection.cs:140`）；`MemoryRecallService` 的余弦 Top-K + **RRF**；`SessionChunkIndexer` 的 chunk 化模式。
- 纪律：**query embedding 只生成一次**，多路共享 await；严禁同一次检索重复调 embedding API。
- 原子步：a) 抽出可复用的向量检索/融合服务接口 → b) 新增代码/文件 chunk 表与写入 → c) 接入检索后端并标注来源与新鲜度。

### ② outline + LSP 封装（**B 起步 + 保留 A 接口位**）
- B：扩展现有 `IndexBasedLanguageServerService` 的方法面，统一封装 outline 与 LSP 视图。
- **接口位预留**：抽象出与"真 LSP 进程（A）"无关的上层契约，使后续可替换实现而不动调用方。
- 遵守设计 §2：references **不能用字符串匹配冒充语义引用**；重名返回 disambiguation，解析精度不足的语言标注 `syntactic`/`heuristic`，**不输出伪精确调用图**。

### ③ 并行检索增强
- 现状：`SearchGrepTool` 顺序扫描，受 2000 文件 / 64MB / 10s 三重硬限，实测**产生假否定**。
- 目标：并行化 + **共享总 deadline/取消/扫描预算**（每后端不得各占完整预算）；**未覆盖范围绝不能归纳成 `no_match`**。

### ④ 后缀名过滤合同化
- 现状：`search_grep.file_ext` 已有；glob 语义已由 ADR-089 G3 统一到 `RetrievalGlobMatcher` / `FileSearchPatternMatcher`。
- 目标：抽象为**所有后端共享的过滤合同**（设计 §2：`glob`/`scope` 才是共享过滤；**文件名匹配不是文本搜索的前置过滤**）。

## 4. 验证与纪律

- 每原子步：定向测试 + `dotnet build` → 白名单 `git_add` → `git commit -F temp\*.txt` → `git push`。
- 正确性先行：对照"不使用索引的全扫描基线"验证路径/行号/匹配内容；必须专测
  「Lucene 无候选但源码存在字面/正则命中」与「Everything 清单遗漏新文件」**不被误报为 `no_match`**。
- 禁止用提速补偿漏检；基线与索引辅助路径**必须采用同一匹配合同**。
- 每步须有证据：事件来源、队列深度、水位推进、删除后置条件（查库/查索引/查目标路径），而非只验证"事件已入队"。
