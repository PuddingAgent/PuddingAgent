# 检索增强：需求 → 现状核实 → 缺口 → 施工顺序（2026-09-24）

> 用户需求原文（2026-09-24）：
> 「我认为代码检索，非常适合 LSP 和增强向量检索结合起来，同时，我们需要指定搜索指定的目录或子目录，文件类型。完成之后，我们还需评估性能和准确率。另外，我们还需忽略一些文件夹，比如制成品、node_modules、读取 git 忽略文件的规则进行忽略。」
>
> 本文所有「现状」断言均**实测**（带 `文件:行`），非推测。属 ADR-089 的落地细化，不替代 ADR-089 §10 硬约束。

## 2. 两个缺陷级发现（比"缺功能"更该先修）

### 2.1 「读 gitignore」看起来实现了，其实从未生效 —— 且实现非规范

`IndexExcludePatterns.cs` 的问题不是"没接线"，是**两重**：

1. **零调用方**（该文件外无任何引用）⇒ 索引链路真正只用了 `IsNoisePath`（`:26-36`，按目录名段匹配的 24 项噪声目录表）。唯一真实使用者是 `CodeIndexWatcher.cs:393-410` 的 `IsExcluded`。
2. **即便接上也不正确**（`:84-115` `ParseGitIgnoreFile` 注释自述 `Skip negation rules (simplified handling)`）：
   - **跳过 `!` 取反** ⇒ `!keep.me` 无法恢复被忽略的路径
   - **无 `**` 语义、无字符类 `[]`、无目录专属规则（尾 `/` 仅被 `TrimEnd` 掉）**
   - `MatchesGitIgnore`（`:127-149`）只有三段粗糙匹配：`EndsWith(core)` ∥ `Contains("/{core}/")` ∥ `Contains("/{core}")`
   - 不处理嵌套 `.gitignore` 的**层级作用域**与**父目录否定恢复**（gitignore 的核心语义）

**反证（这条最能说明问题）**：Lucene 把 `.gitignore` 当作**可索引的纯文本扩展名**（`Source/PuddingFullTextIndex/FullTextIndexOptions.cs:60-61` 白名单含 `.gitignore`、`.gitattributes`）⇒ 系统把 `.gitignore` 当成**检索内容**，而不是**排除规则**。

**轮子已存在（不需要自己写）**：
- 首选 `Ignore`（NuGet `Ignore` / `github.com/goelhardik/ignore`）：**按 .gitignore spec 2.29.2 实现**，且**用 LibGit2Sharp 对真实 `git status` 输出做过测试** ⇒ 与 git 行为一致。
- 备选 `GitignoreParserNet`（`Guiorgy/GitignoreParserNet`）：宣称支持 manpage 全部特性。
- 也可用 **LibGit2Sharp 的 ignore API**，但 `LibGit2Sharp` 目前在 `PuddingRuntime`（`:26`），组件边界不允许 `PuddingCodeIndex` 反向引用 ⇒ 不作为首选。

### 2.2 七套排除规则并存（结果不一致的根因）

| 规则集 | 位置 | 规模 |
|---|---|---|
`search_grep` 默认 `exclude_dirs` | `Source/PuddingRuntime/Tools/BuiltIns/Search/SearchGrepTool.cs:34` | 12 项（`$outputWwwroot;dist;node_modules;bin;obj;.git;.pudding;TestResults;artifacts;publish;.venv;.tmp`） |
同上（description 内联**再来一份**） | 同文件 `:20` | 12 项 |
索引噪声目录 | `Source/PuddingCodeIndex/Services/IndexExcludePatterns.cs:12-24` | **24 项** |
索引器 CLI | `Source/PuddingCodeIndexer.Cli` | 自有一套 `excludedDirs` |
`file_search` / `list_dir` / `project_map` | 各自实现 | 各自规则 |

⇒ 两侧并集/交集不一致：`NoiseDirNames` 有 `.vs/.idea/__pycache__/.tox/coverage/Release/x64...` 而 `search_grep` 没有；`search_grep` 有 `publish/artifacts/.pudding` 而索引侧没有。**这正是"同一个目录有的工具忽略、有的不忽略"的原因。**

## 3. 施工顺序（U4 系列；每项独立组件化，按规程 S1→S5）

| 序 | 切片 | 内容 | 为什么在这个位置 |
|---|---|---|---|
**U4-0** | **评测设施（性能 + 准确率）** | 见 §4 | **必须最先做**：用户要"评估性能和准确率"，且后续每次调优都需要它当判据。没有基线就没有"变好了" |
**U4-1** | **统一忽略合同** | 一个 `IIgnoreRules`：① 规范 gitignore 语义（复用轮子）② 内置噪声目录（制成品/node_modules/…的**并集**）③ 显式排除 + 追加 ④ 「禁用默认」语义保留。所有工具共用 | 修 §2.1 + §2.2；这是"准确率"的第一大污染源（命中 node_modules/dist 的噪声结果） |
**U4-2** | **作用域 + 类型过滤合同化** | 统一 `scope`（目录/子目录）+ `fileTypes`，**并补到代码智能族**（R3/R4） | 用户直接需求；代码智能族当前完全缺失 |
**U4-3** | **LSP 增强（B 起步）** | 先把现有仿 LSP 做成**真正被消费**的能力（补 references facade、禁止字符串匹配冒充语义引用），预留真 LSP 进程接口位 | 现有实现零消费者 ⇒ 先让它有用，再谈外部进程 |
**U4-4** | **向量增强（代码 chunk）** | 代码/文件 chunk 表 + 写入 + 检索接入 + 与词法检索 RRF 融合（复用既有 `IEmbeddingService` 与 RRF 实现），**并把融合权重冻结为带敏感性实验的参数** | 量大，且依赖 U4-1/U4-2 的过滤与作用域先就位 |
**U4-5** | **并行检索** | Provider 共享总 deadline；解决当前 `search_grep` 2000 文件/64MB/10s 三重硬上限导致的**假否定** | 性能项；在 U4-1/U4-2 语义稳定后做，避免"并行化了一个错误的过滤" |

## 4. 评测设施设计（U4-0，用户明确要求）

**性能**（每项都要求可复现的原始输出）：
- 延迟：`p50 / p95 / p99`，按 **冷/热**、按 **语言（C# / TS-TSX / md）**、按 **scope 大小**分层
- 规模：不同仓库规模下的退化曲线；索引构建耗时与索引体积
- 并发：并行查询下的 P95
- **门槛**：用户目标是"毫秒级检索到合适目标"⇒ 需把"毫秒级"落成可判定的阈值（建议：本地中型仓库热态 **p95 ≤ 50ms** 为达标线，需用户确认）

**准确率**（当前完全空白）：
- 需要**标注集**：`query → 期望命中的文件/符号`（建议每个语言分层 20~30 条，共 60~90 条；含"符号名精确命中""自然语言意图""跨文件引用"三类）
- 指标：`recall@k`（k=1/5/10）、`MRR`、`precision@k`；噪声率（返回命中落在被忽略目录的比例 —— 直接度量 U4-1 的收益）
- **对照**：词法（grep）基线 vs +向量 vs +outline/LSP，**逐项加测**，证明每一步的增量收益

## 5. 待你裁决（我给出推荐，不反对即按推荐执行）

1. **允许新增 NuGet 包吗？** 推荐引入 **`Ignore`**（spec 2.29.2 + 用真实 git 输出测过）作为 gitignore 语义实现。若不允许新增依赖，则退化为"自己按 spec 实现"，成本高且易出错（现有那份简化实现就是前车之鉴）。
2. **统一忽略合同放哪？** 推荐**放 `PuddingCodeIndex`**（它已是叶子工程，且 `PuddingRuntime` 已引用它 ⇒ **零新增依赖边**，`search_grep` 可直接复用）；若日后超出"检索基础设施"范畴，再按既有模式抽独立叶子组件（与 LSP 的「B 起步、保留 A 接口位」同口径）。备选：现在就新建 `PuddingIgnoreRules` 叶子组件（更纯，但多一个工程与一轮构建成本）。
3. **"毫秒级"的达标线**：建议定为本地中型仓库热态 **p95 ≤ 50ms**；你也可以直接给一个数字。

## 6. 沿用硬约束（不得放宽）

- `PuddingCodeIndex` 不得引用 `PuddingCodeIntelligence` / `PuddingRuntime` / `PuddingHost` / `PuddingAgent`
- 只清理 Pudding 自己拥有的索引/缓存，**绝不删除源码或工作区文件**
- 组件交付顺序：S1 独立工程 → S2 独立测试 → S3 无宿主验证 → S4 边界断言 → **S5 才接入宿主**；S5 前不得改宿主
- 任何 `git mv` / 命名空间变更后，**必须做全解决方案构建**（规程 §4.2）
- 每个切片必须给出**能取红的变异证据**；时序/并发测试单次通过不构成证据
