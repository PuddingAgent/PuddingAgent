## 0. 一句话

把「多模态」从**兜底能力**升级为**主路径**：主模型自己看（图），用户能画（指哪打哪），并且把"共识"从聊天里搬进可编辑、可版本化的共享对象。

## 1. 问题定义

### 1.1 用户裁定（2026-09-12）

当前 Agent 使用 `deepseek-flash`，DeepSeek 官方文档（https://api-docs.deepseek.com/zh-cn/guides/vision ）
确认其支持图片理解。因此"Agent 无法读取用户发送的图片"**属 PuddingAgent 的 BUG**，不是能力缺失。

### 1.2 BUG 的两层解剖（父级已复现）

**现象（三个独立错误，均已实测）**

| 尝试 | 返回 |
|---|---|
| `image_reader` 默认模式（auto→delegate） | `vision_helper_model_required` |
| 把 manifest 的 `visionHelperModel` 由 `null` 改为具体路由后立即重试 | **同一错误，一字未变** |
| `image_reader mode=native` | `vision_model_capability_mismatch: mode=native requires the calling model to declare the vision capability` |

**第一层：运行期能力陈旧且平台静默**

- `llm` 配置**启动时加载一次、不热重载**（`PuddingFileLlmConfigService` 注释已明示）。
- `deepseek-flash` 的 `capabilityTags:["vision"]` 于当日 ~20:50 落盘，而进程最后一次重启为 **16:40**
  ⇒ 进程内旧配置判定"当前模型无视觉能力"。
- `manifest.json` 的修改同样不即时生效 ⇒ **第二次**"改了配置却不生效"，平台**两次都未告警**。
- 结论：即使能力已具备，系统也**不会告诉你它没生效**，只会让你以为"没有这个能力"。

**第二层：设计缺陷（与配置无关，独立存在）**

- `Source/PuddingWebApiTests/Tools/ImageReaderToolTests.cs:148` 断言 helper 缺失必须报
  `vision_helper_model_required` ⇒ **"没配外挂视觉模型 = 失败"被固化为测试契约**。
- 即：默认路径的兜底语义是"再找一个模型替我看"，而不是"我自己看"。
- 这正是本次要推翻的设计。**V6-T1（修陈旧/告警）与 V6-T2（改外挂语义）是两张独立的卡。**

### 1.3 用户提出的设计原则（定性变更）

| 原设计 | 新定性 |
|---|---|
| Image Reader = 主模型不支持视觉时的**兜底** | Image Reader = **主模型的主动图片理解行为** |
| 请求新 Session / 子代理 / 外挂视觉模型 | **主模型自己看**；"我本来就有眼睛，Image Reader 只是让我再凑近精确看一眼" |
| 用户打字描述"你看这里" | 用户**直接在图上圈出来** |

## 2. 目标与非目标

### 2.1 目标

1. **G1** 主模型可直接理解用户通过 Web 发送的图片（无外挂、无 helper 前置条件）。
2. **G2** `image_reader` 成为"精确观察"工具：支持放大/缩小/裁剪/旋转等基础与高级图片操作。
3. **G3** Web 端图片可编辑涂鸦，发送时"消息 + 标注图"一起送出。
4. **G4** 历史消息中的图片可再次编辑并追问（原消息不可变）。
5. **G5** 探索"共识同步"新模态，降低意图对齐的往返成本。

### 2.2 非目标

- 不做 CRDT 实时同屏编辑（优化的是"同步速度"而非"共识质量"，成本高）。
- 不以语音作为主要交互（信息密度低、不可检索/引用）。
- 不引入兼容双读、不以"配 helper 绕过"粉饰问题。

## 5. 关键设计决策（实现前必须遵守）

### 5.1 能力判定单源

- 能力判定**只允许一个来源**（`LlmRouteSnapshot.VisionPolicy` / `CallerLlmSnapshot.SupportsVision`）。
- **禁止**在工具层做第二次判定（工具不得自己判断"模型能不能看图"）。
- 能力声明与运行期投影不一致时，**必须显式告警**，不得静默降级。

### 5.2 图片产物不可变

- **原图不可变**：标注/编辑结果**另存为新 artifact**，禁止就地覆盖（否则历史不可复现）。
- 需明确产物的生命周期与清理策略（落 artifact 还是临时文件），并保证可被后续 `image_reader` 再次读取。

### 5.3 消息载体

- 图片统一走 `ChatMessage.ContentParts`（canonical，`Models/ChatMessage.cs` 末位参数）。
- **禁止**使用旧派生路径 `VisualArtifactIds`（该字段仅为旧构造路径兼容，音频链路使用 `AudioArtifactIds`）。
- ⚠️ 已知易错点：`ChatMessage` 第 3 个**位置**参数是 `string? ToolCallId`，图片必须用**具名参数** `ContentParts:`。

### 5.4 预算联动

- 任何新增图片路径（编辑、切片、多尺度、拼接）都**必须计入 `VisualInputRequestBudget` 五维账本**。
- 越界行为延续 V5 的 **fail-closed**：抛 `RequestLimitExceeded`，**不得静默丢图**，且 **HTTP handler 调用计数 = 0**。

### 5.5 坐标约定

- 沿用归一化 `0..999`，不得另立坐标系。

### 5.6 前端约定

- 标注编辑器**不自研 canvas 引擎**，先做选型（V6-T4）。
- 选型第一判据：**能否以"用户上传图片"为底图**（多数白板库以空白画布为设计前提，这是生死线）。
- 不新增独立路由（任务看板已示范改为模态窗口）。

### 5.7 共识同步（G5）的判据

任何新模态必须能压低三个可观测指标，否则不做：

1. 达成共识所需的**消息数**；
2. **澄清轮次**；
3. **返工次数**。

优先级建议（父级判断）：

1. **共享工作物（Living Spec）**——把共识物化为可编辑对象，聊天只留 diff 摘要（最根本）；
2. **意图确认卡**——Agent 用可点选卡片复述理解（选项/多选/滑块/优先级拖拽），用户点选而非打字（性价比最高，可复用 CardKit）；
3. **图优先（双向）**——用户圈给我看，我也能画给用户改（与 V6-T5/T6 天然合流）；
4. **让我出选择题**——"我打算怎么做"变成带代价/影响面的分叉，用户当判卷人而非出题人。

### A.2 逐项裁决（关键项已由父级独立核实原文）

- **tldraw —— 硬否决。** LICENSE.md **逐字核实**：*"Not to use the Software in Production Environments"*；其中 Production Environment 定义明确涵盖 *"web applications... where the software is used to provide functionality to end users, customers, or the public"*，本产品正落此范围；且含 *"Technical enforcement"*——校验 License Key、探测部署环境。另有 `engines node>=22.12` 与本项目 `node>=20` 冲突。

## 一、问题 A：DeepSeek 视觉输入契约（逐条）

### A1. 图片输入格式与请求体结构

**结论**：【官方文档明确声明】支持**三种**传图方式，且在 OpenAI 兼容端点与 Responses API、Anthropic 兼容端点上结构不同：

1. **Base64 data URI（内联）**——计入 48 MiB 请求体限制；
2. **外部 http(s) URL**——URL ≤8192 字符、图片 ≤32 MiB、须在 60 秒内下载完成；
3. **Files API `file_id` 引用**（形如 `file-api-...`）——单图最大 64 MiB、不受 32 MiB 单图检查限制；另有 `file` 块 + `file_data` 内联 base64 的变体（`file_data` 与 `file_id` 互斥）。

**真实 JSON 片段（Chat Completions，摘自官方文档）**：

```json
{
  "model": "deepseek-flash",
  "messages": [
    { "role": "user", "content": [
      {"type": "text", "text": "这张图片里有什么？"},
      {"type": "image_url", "image_url": {"url": "data:image/jpeg;base64,<BASE64_DATA>"}}
    ]}
  ]
}
```

**Responses API 形态**：图片以 `input_image` 内容块承载，例如
`{"type": "input_image", "image_url": "https://example.com/image.jpg", "detail": "low"}`；
`image_url` 与 `file_id` 互斥，通过 `file_id` 传图时 `detail` 被忽略。

**Anthropic 兼容端点**（`https://api.deepseek.com/anthropic` 的 `/messages`）：使用 `image` 块，`source.type` 为 `base64` / `url` / `file` 之一；base64 需 `media_type` 字段。

**原文摘录**（来源：https://api-docs.deepseek.com/zh-cn/guides/vision ，本报告后文简称 [VISION]）：
> "共有三种方式向模型提供图片，均使用标准的 OpenAI 兼容对话补全格式，即 `content` 为一个块（block）数组，而非纯字符串。同样的三种方式也适用于 Responses API，图片以 `input_image` 内容块承载。"
> "编码后的数据会计入 **48 MiB** 请求体大小限制（见 限制）。"
> "URL 长度最多 **8192 个字符**，图片文件最大 **32 MiB**，且需在 **60 秒**内完成下载。"
> "与内联图片不同，通过 Files API `file_id` 引用的图片最大可达 64 MiB，且不受 32 MiB 单图检查限制。"
> "`input_image` 内容块支持 `detail` 字段，语义与上文一致（`low` / `high` / `original` / `auto`）。通过 `file_id` 传图时 `detail` 被忽略；`image_url` 与 `file_id` 互斥。"

### A2. MIME 类型、单图体积/像素限制、单请求张数

**结论**：【官方文档明确声明】（来源：[VISION]「限制」表，逐字引用）：

| 限制项 | 数值（官方原文） |
| --- | --- |
| 支持的格式 | "JPEG、PNG、GIF、WebP" |
| 外部 URL 长度 | "8192 个字符" |
| 请求体大小 | "48 MiB" |
| 单张图片最大大小（base64 / 外部 URL） | "32 MiB" |
| 单张图片最大大小（Files API `file_id`） | "64 MiB" |
| 单个请求最大图片数 | "600" |
| 单个请求图片总大小 | "不含 `file_id` 图片最多 64 MiB；包含 `file_id` 图片最高 200 MiB" |
| 图片最大尺寸 | "单边最长 8192 像素；单个请求包含 15 张及以上图片时，降为单边最长 4096 像素" |

**MIME 判定方式**【官方声明】：
> "支持的图片格式：**JPEG、PNG、GIF、WebP**。格式由文件实际内容判断，而非文件名或声明的 MIME 类型。"

即：不做 `image/png` 之类 MIME 声明的强校验，按魔数/内容判定；`media_type` 字段仅在 Anthropic 兼容端点的 base64 source 中要求。

**文档未明确**：超出单边 8192 像素的图片是报错还是被缩放（见 RISKS）。

### A3. 图片 token 计费口径

**结论**：【官方文档明确声明】按**图片尺寸**换算、非固定每图 N token；**每图 token 上限 1024**；存在 `detail` 档位参数（low/high/original/auto）。

**原文摘录**（[VISION]「Token 用量」与「细节级别」）：
> "在进入模型前，每张图片都会被自动缩放：
> - 总像素小于约 544×544 的图片会被保持长宽比放大；
> - 更大的图片会被保持长宽比缩小，缩小后的总像素约相当于 **1300×1300** 的图片。"
> "因此，每张图片消耗的 token 数存在上限（**1024** 个）：例如 2000×2000 和 5000×5000 的图片，经缩放后消耗的 token 数是相同的。"
> "单个请求包含多张图片时，每张图片独立按同一规则计算，不存在额外的计算方式。"
> "图片会根据其尺寸换算成 token，并与文本 token 一起计费。"

**detail 档位**（[VISION]「细节级别」表，逐字）：
> | `low` | "推理前将图片缩放到 512×512。当不需要精细视觉细节时更快、更省 token。" |
> | `high` | "保留原图。（为兼容性提供，等价于 `original`。）" |
> | `original` | "保留原图。" |
> | `auto` | "自动选择。当前等价于 `original`。" |

**文档未给出**：`low` 档的具体 token 数，也未给出类似 OpenAI"85+170/块"的固定公式；官方提供了"Token 与用量计算页面的图片 Token 计算器"用于估算。

**与 PuddingAgent 现状的对照**（供父级修复参考）：PuddingAgent 运行配置的 `estimatedTokensPerImageUpperBound: 1024` 与官方"每图上限 1024 token"**一致**；当前文档中不存在"384 token/图"这类更小的全模型上界依据。

### A4. 多图同请求 / 工具调用结果携图

**多图**：【官方声明】支持，单请求最多 600 张，token 独立计算（见 A2/A3 原文）。

**工具结果携图**——两种 API 形态**结论不同**：
- **Chat Completions**：【官方声明，[VISION]「使用限制」】
  > "图片仅支持出现在 `user` 消息中。`system` 或 `assistant` 消息携带图片会返回 `400` 错误。"

  官方明确枚举中图片只允许 `user` 角色 ⇒ `tool` 角色消息**不可**携图（400 同理适用于非 user 消息的语义）。
- **Responses API**：【官方声明，[VISION]「在 Responses API 中使用图片」】
  > "图片以 `input_image` 内容块承载，可出现在 `user` / `developer` 消息或 `function_call_output` / `custom_tool_call_output` item 的 `output` 中"
  > "字段语义、使用限制（`system` / `assistant` 消息中的图片会返回 `400` 错误）以及工具输出中的图片，请参阅 Responses API 指南。"

  ⇒ **`function_call_output` 中携图是官方明确支持的形态**。

**跨平台参照**【官方声明，Anthropic】（https://docs.anthropic.com/en/docs/build-with-claude/vision ，简称 [ANTHROPIC]）：
> "The exception is screenshots and zoom images that you return to the computer use and browser use toolsets: the API rejects a `tool_result` image that exceeds the model's limits"

即 Anthropic 侧 tool_result 携图是常规用法，但超限的 computer-use 截图/zoom 图会被**直接拒绝**（fail-closed 先例）。

### A5. 模型标识：deepseek-flash 是否为官方模型名

**结论**：【官方文档明确声明】`deepseek-flash` **就是**当前官方文档中的真实模型 ID，且是**唯一支持图像理解**的模型。

## 二、问题 B：图片预处理是否真的提升识别精度

### B7. "先裁剪/放大再喂" vs "直接喂整图"

**分层结论**（按证据强度）：

1. 【官方文档明确声明，DeepSeek】**模型侧存在有效分辨率上限**：任何大图在进入模型前都会被等比缩小到 ~1300×1300 等效像素、每图 token 封顶 1024（[VISION] 原文见 A3）。⇒ **对 DeepSeek 而言，把整图"无脑放大"（插值 upscale）不会增加任何模型可见的信息**——放大只增加 wire 传输量与请求体占用，token 与信息量都不变。

2. 【官方文档明确声明，DeepSeek】**小图会被平台主动放大**：
   > "总像素小于约 544×544 的图片会被保持长宽比放大"

   ⇒ 客户端对小图做 upscale 属于重复劳动（平台已做），除非客户端能实现比平台更好的重采样。

3. 【官方文档明确声明，Anthropic】token 按 28×28 patch 计、超限自动降采样、官方最佳实践明确建议**预处理**：
   > "Claude views images in patches instead of pixels. Each patch is a 28×28-pixel block of the image, referred to as a visual token. An image, therefore, costs ⌈width / 28⌉ × ⌈height / 28⌉ visual tokens."
   > "Images larger than either limit are downscaled before processing"
   > "Consider pre-resizing your images, cropping them, or both."
   > "downsample images before sending to control token costs. To minimize latency and to simplify coordinate-based workflows, prefer resizing images before uploading them."

4. 【官方文档明确声明，Anthropic】**裁剪有代价警告**：
   > "Text: If the image contains important text, make sure it's legible and not too small. Avoid cropping out key visual context solely to enlarge the text."

   ⇒ 官方口径：裁剪/放大**不是无条件**提升——"为了放大文字而裁掉关键上下文"被明确列为反模式。

5. 【论文/研究证据】**提高有效分辨率确实提升细节/OCR**——LLaVA-NeXT 官方博客（https://llava-vl.github.io/blog/2024-01-30-llava-next/ ，简称 [LLAVA-BLOG]）：
   > "**Increasing the input image resolution** to 4x more pixels. This allows it to grasp more visual details. It supports three aspect ratios, up to 672x672, 336x1344, 1344x336 resolution."
   > "**Better visual reasoning and OCR capability** with an improved visual instruction tuning data mixture."

   其对照数据（同博客表格）：TextVQA 从 LLaVA-1.5-13B (336²) 的 61.3 提升到 LLaVA-NeXT-Mistral-7B (672²) 的 65.7 / LLaVA-NeXT-13B (672²) 的 67.1。
   HiRes-LLaVA（CVPR 2025，https://openaccess.thecvf.com/content/CVPR2025/papers/Huang_HiRes-LLaVA_Restoring_Fragmentation_Input_in_High-Resolution_Large_Vision-Language_Models_CVPR_2025_paper.pdf ）摘要级内容（来自搜索结果摘要，未逐字核全文）："High-resolution image inputs allow Large Vision-Language Models (LVLMs) to capture finer visual details, improving comprehension."

6. 【社区经验/推断，综合 1–5 的推理】**正确结论是**：提升"细节识别率"的机制是**让目标区域在模型有效分辨率预算（~1300×1300 等效 / 1024 token）内占据更大比例**——即"裁剪 ROI（原生像素）"有效；"对已有像素做插值放大"无效（模型先缩放回预算）。裁剪必须保留关键上下文（Anthropic 官方警告）。

### B8. 放大是否会被拒绝/降采样；业界通行尺寸建议

**DeepSeek**【官方声明】：
- 硬限制：单边最长 8192 像素；≥15 张图时 4096 像素（[VISION] 限制表，原文见 A2）。
- 超过 1300×1300 等效的大图一律**自动等比缩小**（不会拒）；**小于** 544×544 等效的小图自动**放大**。
- 【文档未明确】超出 8192 像素单边的处理行为（报错还是缩放）——[VISION] 限制表只给了上限值，未写超限行为。**如实标注：未找到官方明示**。
- wire 层限制：单图 32 MiB（base64/URL）/ 64 MiB（file_id）、请求体 48 MiB——**放大会同步放大字节数**，更容易撞这些墙。

**Anthropic**【官方声明】：超过 long-edge/visual-token 上限**自动 downscale**；官方建议客户端**预缩放**（原文见 B7-3）。表格数据（[ANTHROPIC]）：2000×1500 → 缩至 1269×952（1564 visual tokens）；3840×2160 → 1456×819（1560 tokens，原图内部先 2576×1449）。

**Gemini**【官方声明】（https://ai.google.dev/gemini-api/docs/image-understanding ，简称 [GEMINI]）：
> "**Note:** Inline image data limits your total request size (text prompts, system instructions, and inline bytes) to 20MB. For larger requests, upload image files using the File API."

**业界通行建议**（综合官方文档口径的归纳【推断，但每条均有官方依据】）：
1. 客户端预处理到**模型有效分辨率附近**（DeepSeek ≈1300×1300 等效；Anthropic 长边 ≤1568 上限以内省 token），不送无效大图；
2. 需要细节时**裁剪 ROI 原生像素**，而不是插值放大；
3. 大字节优先 Files API（DeepSeek file_id 上限 64 MiB > 内联 32 MiB；Gemini >20 MB 必须 File API）。

### B9. "多尺度看图"（先整体再局部）是否为公认实践

**结论**：存在公认实践模式，两类落地：

1. **模型内建多尺度编码（AnyRes / tiling）**【论文/官方工程实践】：
   - [LLAVA-BLOG]（官方博客）：将输入分辨率提升 4×（672×672 及 1344×336 等三档纵横比）以"grasp more visual details"；
   - LLaVA-OneVision（arXiv:2408.03326，https://arxiv.org/abs/2408.03326 ）摘要逐字：
     > "We present LLaVA-OneVision, a family of open large multimodal models (LMMs) developed by consolidating our insights into data, models, and visual representations in the LLaVA-NeXT blog series. Our experimental results demonstrate that LLaVA-OneVision is the first single model that can simultaneously push the performance boundaries of open LMMs in three important computer vision scenarios: single-image, multi-image, and video scenarios."
   - 搜索结果（anysearch，标注为摘要级证据）显示 OneVision/NeXT 的 AnyRes 即"把高分辨率图像切成多个网格 tiles、分别编码再聚合"。AnyRes 机制细节的论文正文原文本次未逐字核实，标注。
   - 平台侧同类机制：OpenAI vision 文档存在 high-detail 切片处理（本次抓取的官方页面片段未包含该节的完整原文，**具体切片数字未核实，标注**）；Gemini 内部按 tile 处理大图（**tile 具体数值未从官方原文核实，标注**）。

2. **Agent 工作流级多尺度（先整体后局部）**【官方声明，Anthropic computer-use 范式】：
   - [ANTHROPIC] 官方原文承认并规范了"模型主动 zoom、把局部放大截图作为 `tool_result` 回传"的用法：
     > "The exception is screenshots and zoom images that you return to the computer use and browser use toolsets: the API rejects a `tool_result` image that exceeds the model's limits"
   - [ANTHROPIC] 多图建议（适合"整图+局部"同请求）：
     > "You can include multiple images in a single request, and Claude analyzes them jointly. … When sending several images, introduce each one with a short text label (`Image 1:`, `Image 2:`, and so on)"

**典型流程（业界通行，归纳）**：
1. 第一轮：喂整图（或自动缩放后的整图）做全局理解/定位；
2. 第二轮：对关注区域做**原生像素裁剪**（必要时放大到有效分辨率），作为新图片输入——Agent 场景下可作为工具结果（Responses API `function_call_output` / Anthropic `tool_result`）或新的 user 消息回传；
3. 聚合两轮结论作答。多图同请求时用 "Image 1/2" 文本标注分隔。

**对 PuddingAgent 的含义**（供父级参考）：DeepSeek Responses API 官方支持 `function_call_output` 携图 ⇒ PuddingAgent 的 Responses 网关允许"工具图"是**官方契约内的形态**；但 Chat Completions 端点只能 user 角色带图 ⇒ 两条网关的视觉合同本就**不对称**，统一"五维账本"时需保留该差异（token 口径相同：每图 ≤1024）。

## 五、风险（RISKS）

1. **时效风险**：DeepSeek 文档更新频繁（旧模型名刚经历"下线但可调用"的迁移）。父级修复若引用本报告数字，建议在 ADR/实施记录中注明"以 2026-09-12 在线文档为准"。
