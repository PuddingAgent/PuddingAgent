## 0. 一句话

把「多模态」从**兜底能力**升级为**主路径**：主模型自己看（图），用户能画（指哪打哪），并且把"共识"从聊天里搬进可编辑、可版本化的共享对象。

## 1. 问题定义

### 1.1 用户裁定（2026-09-12）

当前 Agent 使用 `deepseek-flash`，DeepSeek 官方文档（https://api-docs.deepseek.com/zh-cn/guides/vision ）
确认其支持图片理解。因此"Agent 无法读取用户发送的图片"**属 PuddingAgent 的 BUG**，不是能力缺失。

### 1.2 BUG 的两层解剖（父级已复现）

**现象（三个独立错误，均已实测）**

| 尝试 | 返回 |
|---|---|
| `image_reader` 默认模式（auto→delegate） | `vision_helper_model_required` |
| 把 manifest 的 `visionHelperModel` 由 `null` 改为具体路由后立即重试 | **同一错误，一字未变** |
| `image_reader mode=native` | `vision_model_capability_mismatch: mode=native requires the calling model to declare the vision capability` |

**第一层：运行期能力陈旧且平台静默**

- `llm` 配置**启动时加载一次、不热重载**（`PuddingFileLlmConfigService` 注释已明示）。
- `deepseek-flash` 的 `capabilityTags:["vision"]` 于当日 ~20:50 落盘，而进程最后一次重启为 **16:40**
  ⇒ 进程内旧配置判定"当前模型无视觉能力"。
- `manifest.json` 的修改同样不即时生效 ⇒ **第二次**"改了配置却不生效"，平台**两次都未告警**。
- 结论：即使能力已具备，系统也**不会告诉你它没生效**，只会让你以为"没有这个能力"。

**第二层：设计缺陷（与配置无关，独立存在）**

- `Source/PuddingWebApiTests/Tools/ImageReaderToolTests.cs:148` 断言 helper 缺失必须报
  `vision_helper_model_required` ⇒ **"没配外挂视觉模型 = 失败"被固化为测试契约**。
- 即：默认路径的兜底语义是"再找一个模型替我看"，而不是"我自己看"。
- 这正是本次要推翻的设计。**V6-T1（修陈旧/告警）与 V6-T2（改外挂语义）是两张独立的卡。**

### 1.3 用户提出的设计原则（定性变更）

| 原设计 | 新定性 |
|---|---|
| Image Reader = 主模型不支持视觉时的**兜底** | Image Reader = **主模型的主动图片理解行为** |
| 请求新 Session / 子代理 / 外挂视觉模型 | **主模型自己看**；"我本来就有眼睛，Image Reader 只是让我再凑近精确看一眼" |
| 用户打字描述"你看这里" | 用户**直接在图上圈出来** |

## 2. 目标与非目标

### 2.1 目标

1. **G1** 主模型可直接理解用户通过 Web 发送的图片（无外挂、无 helper 前置条件）。
2. **G2** `image_reader` 成为"精确观察"工具：支持放大/缩小/裁剪/旋转等基础与高级图片操作。
3. **G3** Web 端图片可编辑涂鸦，发送时"消息 + 标注图"一起送出。
4. **G4** 历史消息中的图片可再次编辑并追问（原消息不可变）。
5. **G5** 探索"共识同步"新模态，降低意图对齐的往返成本。

### 2.2 非目标

- 不做 CRDT 实时同屏编辑（优化的是"同步速度"而非"共识质量"，成本高）。
- 不以语音作为主要交互（信息密度低、不可检索/引用）。
- 不引入兼容双读、不以"配 helper 绕过"粉饰问题。

## 5. 关键设计决策（实现前必须遵守）

### 5.1 能力判定单源

- 能力判定**只允许一个来源**（`LlmRouteSnapshot.VisionPolicy` / `CallerLlmSnapshot.SupportsVision`）。
- **禁止**在工具层做第二次判定（工具不得自己判断"模型能不能看图"）。
- 能力声明与运行期投影不一致时，**必须显式告警**，不得静默降级。

### 5.2 图片产物不可变

- **原图不可变**：标注/编辑结果**另存为新 artifact**，禁止就地覆盖（否则历史不可复现）。
- 需明确产物的生命周期与清理策略（落 artifact 还是临时文件），并保证可被后续 `image_reader` 再次读取。

### 5.3 消息载体

- 图片统一走 `ChatMessage.ContentParts`（canonical，`Models/ChatMessage.cs` 末位参数）。
- **禁止**使用旧派生路径 `VisualArtifactIds`（该字段仅为旧构造路径兼容，音频链路使用 `AudioArtifactIds`）。
- ⚠️ 已知易错点：`ChatMessage` 第 3 个**位置**参数是 `string? ToolCallId`，图片必须用**具名参数** `ContentParts:`。

### 5.4 预算联动

- 任何新增图片路径（编辑、切片、多尺度、拼接）都**必须计入 `VisualInputRequestBudget` 五维账本**。
- 越界行为延续 V5 的 **fail-closed**：抛 `RequestLimitExceeded`，**不得静默丢图**，且 **HTTP handler 调用计数 = 0**。

### 5.5 坐标约定

- 沿用归一化 `0..999`，不得另立坐标系。

### 5.6 前端约定

- 标注编辑器**不自研 canvas 引擎**，先做选型（V6-T4）。
- 选型第一判据：**能否以"用户上传图片"为底图**（多数白板库以空白画布为设计前提，这是生死线）。
- 不新增独立路由（任务看板已示范改为模态窗口）。

### 5.7 共识同步（G5）的判据

任何新模态必须能压低三个可观测指标，否则不做：

1. 达成共识所需的**消息数**；
2. **澄清轮次**；
3. **返工次数**。

优先级建议（父级判断）：

1. **共享工作物（Living Spec）**——把共识物化为可编辑对象，聊天只留 diff 摘要（最根本）；
2. **意图确认卡**——Agent 用可点选卡片复述理解（选项/多选/滑块/优先级拖拽），用户点选而非打字（性价比最高，可复用 CardKit）；
3. **图优先（双向）**——用户圈给我看，我也能画给用户改（与 V6-T5/T6 天然合流）；
4. **让我出选择题**——"我打算怎么做"变成带代价/影响面的分叉，用户当判卷人而非出题人。

## 附录 A：V6-T4 前端标注编辑器选型结论（R1 调研，2026-09-12）

**结论：Konva + react-konva，自建标注层**——唯一同时满足全部硬约束的候选。
调研原始报告：`temp/research-r1-image-editor-selection.md`（temp/ 已被 gitignore，故结论落到本附录固化）。

### A.1 硬约束（全部来自本仓库实物，非推测）

| 约束 | 实物证据 |
|---|---|
| React 19 生态 | `Source/PuddingPlatformAdmin/package.json`：`react` / `react-dom` 均为 `^19.1.0` |
| 聊天 bundle 体积受门禁 | `package.json:15` → `"build": "max build && node scripts/check-chat-bundle-budget.cjs"` |
| 标注器必须可懒加载 | 不能进入聊天首屏主 chunk |
| **底图注入必须是一等公民** | 场景是"以用户上传图/历史消息图为底图"，非空白画布 |
| 许可证必须允许生产环境 | 本产品对终端用户提供功能 |

### A.2 逐项裁决（关键项已由父级独立核实原文）

- **tldraw —— 硬否决。** LICENSE.md **逐字核实**：*"Not to use the Software in Production Environments"*；其中 Production Environment 定义明确涵盖 *"web applications... where the software is used to provide functionality to end users, customers, or the public"*，本产品正落此范围；且含 *"Technical enforcement"*——校验 License Key、探测部署环境。另有 `engines node>=22.12` 与本项目 `node>=20` 冲突。
- **Pintura —— 否决。** €749/年/席位；未购授权时输出图带水印，会**污染用户消息内容**。
- **react-image-crop —— 否决。** 仅裁剪，零标注能力，用了仍需全自建。
- **Excalidraw —— 次优保留。** MIT、131k★；但底图需场景序列化注入（是白板心智，非图片编辑器）、unpacked 46.8MB 与 bundle 预算门禁冲突、peer/radix-ui ERESOLVE（issue #11500，修复 PR #11572 仍 open，需 `--legacy-peer-deps`）。
- **Fabric.js —— 兜底。** MIT、零 React 耦合、能力完备；命令式 API 需自建全部 React 集成层，工作量最大。
- **Konva + react-konva —— 采用。** MIT；README **逐字核实**：*"React Konva 19 requires React and React DOM `^19.2.0`"*、定位 *"design editors, whiteboards, diagrams, annotations"*；`react-konva` unpacked 84,801B。

### A.3 父级对 R1 的一处修正（重要，避免无谓动作）

R1 称 `react ^19.1.0` 与 react-konva 要求的 `^19.2.0` 存在"表面冲突"、需升级声明。**此说不准确**：
`^19.1.0` 语义为 `>=19.1.0 <20.0.0`，**已包含 19.2.x**，声明无需改动。
真正的动作项是：**核对 lock 实际解析到的 react 版本并确保 ≥ 19.2.0**；仅当被 pin 在 19.1.x 时才需 `pnpm up`。

### A.4 集成草图（实现前需 1 天 spike 验证）

`ChatInput 缩略图` → `AnnotationEditorModal`（`React.lazy` 懒加载）= `KonvaImageLayer`(底图) + `AnnotationLayer`(shapes[] React state) + `Transformer` + DOM 工具条(antd + ARIA)；
发送时 `stage.toDataURL(底图矩形, pixelRatio)` 合成 PNG → **复用现有 artifact 存储与消息发送链路（零改动）**；
`shapes` 精简 JSON 随消息元数据保存，供历史消息再次编辑。
导出格式 = 合成 PNG + `{ imageRef, shapes[] }`。

### A.5 与本规划既有决策的一致性

- 决策 2「原图不可变」：合成 PNG **另存新 artifact**，标注 JSON 独立保存，原图不动。
- 决策 3「canonical 载体」：发送走 `ChatMessage.ContentParts`。
- 决策 4「预算联动」：合成后图片继续计入 `VisualInputRequestBudget` 五维账本。
- 决策 6「先选型后实现」：本附录即选型交付物，V6-T5 以其为前置。

### A.6 实现期待验证（**标注为未证实，勿当结论**）

Konva `toDataURL` / `toJSON` 精确签名；高 DPI `pixelRatio` 与大图 canvas 内存；konva 核心 gzip 实际增量；`check-chat-bundle-budget.cjs` 门禁是否通过；canvas 方案的无障碍补偿实际效果。
