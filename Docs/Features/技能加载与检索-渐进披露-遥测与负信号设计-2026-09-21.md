## 0. 用户指令要点（原文归纳，作为本文的输入）

1. 「技能会越来越多 ⇒ 需要**渐进性披露**、**技能检索机制**、**动态加载技能**。」
2. 「做之前**先去看是否有合适的技能可以加载**，但我们**不需要理解**全部技能；并不是每个技能都是通用的（例如 MySQL 的技能可能只适用于某个版本或某种场景）。」
3. 「类似于 EVO MAP，我们**实际上需要语义向量检索技能 SKILL 的机制**。」
4. 「RSI **不光要给出好的信号，也要给出不好的信号** —— 不用某个技能时，可能更有利于任务的完成。」
5. 「建立技能的**索引 + 调用次数 + 成功率**统计的基础设施，以便后续优化 RSI。」
6. 「SKILL 实际上应该更接近于**作业指导手册、一本烹饪书籍**，因为随着模型的进化，SKILL 反而**成为任务执行的障碍**。」

## 1. 先回答「这 139 个技能有用吗」——能答的一半与不能答的一半

### 1.1 能答的：静态内容证据（可复现，`report-skill-portfolio.ps1 -Mode content-audit`）

139 个启用技能：

| 指标 | 值 | 含义 |
|------|----|------|
| 标记 `auto-generated` | **133（95.7%）** | 几乎全部由会话自动提炼，非人工编写 |
| 正文含 `## 来源` 段 | 135 | 会话回放式（附会话 id、置信度、turn id） |
| **提到边界知识**（前提/约束/不适用/陷阱/回滚） | **11（7.9%）** | 极少数讲了「什么时候不该用」 |
| **纯回放**（有来源段 + 零边界知识） | **125（89.9%）** | 主体是「调哪几个工具」的步骤抄录 |
| 工具调用行 / 正文总行 | **7%** | 正文主体是自然语言步骤描述，而非纯调用序列 |

**结论（能答的部分）**：这批技能在**形态上高度同质**：从单次会话自动提炼、以「步骤」为主体、**几乎不讲边界**。
按用户的比喻，它们目前更像「**别人家昨晚做菜的过程录像**」，而不是「**烹饪书**」——烹饪书的价值在于**技法与判据**（什么时候该用大火、什么时候不能下锅），
而 95.7% 的自动回放恰恰缺这一层。

### 1.2 不能答的：是否有用（必须等遥测）

没有使用遥测，**无法区分**三种截然不同的情况：

| 情况 | 应有动作 | 现状能否区分 |
|------|----------|--------------|
| ① 确实被命中，且让任务更好 | 保留、甚至晋升 | ❌ |
| ② 从未被命中 | 淘汰或重建触发面 | ❌ |
| ③ 被命中，但把模型带偏（**负价值**） | **优先处理**，这是最危险的 | ❌ |

⇒ 这一格空白正是用户第 5 点要求的基础设施要填的。**在此之前，任何「这 139 个技能有用/没用」的断言都是猜测。**

### 1.3 已知的、与「有用性」直接矛盾的实测事实

- 关键词空间 2490 槽位 / 755 去重，**噪声 89.1%**（治理与溯源标签 824、工具名 957、名称分词 502、语义仅 280）。
- 被 ≥2 技能共享的关键词 165 个 ⇒ **1735 次注入机会被「先到先得」静默挤掉**。
- 语义层面：**139 个技能两两无重叠**（全部单技能家族）⇒ 不存在「因为重复所以该合并」的问题。

即：**当前的技能库既不是「重叠冗余」，也不是「清晰可分」** —— 它是一堆**共享噪声、彼此无交集、且几乎无边界知识**的条目。
这恰好解释了为什么「关键词注入」这条路会退化：它靠的是**噪声的偶然重合**，而不是**语义的精确匹配**。

## 3. 方向重构：从「关键词注入」到「检索式按需加载」

### 3.1 三层渐进披露模型（回答用户第 1 点）

| 层 | 内容 | 体量量级 | 谁决定加载 | 现状 |
|----|------|----------|------------|------|
| **L1 索引层**（常驻） | skillId + 一句话摘要 + 适用场景标签 + 版本 + 使用统计（次数/成功率） | ~50–80 token/技能 | 系统常驻，**必须极小** | 现状把 name+tags+keywords 全量塞进索引（实测索引投影字符数已超万级），**不做筛选** |
| **L2 摘要层**（按需） | 技能的「目标 / 适用前提 / 不适用场景 / 关键判据」 | ~200–400 token/技能 | 检索命中后加载，或由模型主动 `skill_get` | ❌ 不存在（manifest 的 `summary` 只是 front-matter 首行，无信息量） |
| **L3 全文层**（按需） | SKILL.md 全文 | ~3KB/技能（平均） | 确定要用时才加载 | 现状：**要么全量注入，要么完全不注入**（无中间层） |

**核心判断**：现状是「0 层/3 层二选一」，中间缺了 L1/L2 ⇒ 这是「技能越多越糟」的直接机制原因。

### 3.2 语义向量检索（回答用户第 3 点）

- **落点**：为每个技能生成 embedding（源文本建议 = `名称 + 摘要 + 适用场景 + 边界知识`，**不含**工具名与治理标签），存入技能索引库（复用 §2.3 的 SQLite + 向量列）。
- **检索时机**：① 会话开始时按用户首条消息检索 top-K；② 会话中途由模型触发（等价于 `search_tools` 的角色）。
- **与关键词的关系**：**不是二选一**。关键词检索快、可解释、零成本；向量检索解决同义/跨语言/场景相似。
  建议**混合**：向量召回 + 关键词/标签过滤 + 统计加权（§3.4）。
- **评测前提**：必须先有 §3.4 的遥测，才能算出「检索召回是否真的让任务更好」——否则只是换一种猜。
- **可解释性要求**：每次加载必须能回答「为什么这条技能被加载」（命中的是向量相似度还是某个关键词），否则无法审计、无法回滚。

### 3.3 动态加载与 fail-open（回答用户第 1、2 点）

复用 §2.1 的既有范式，四条约束：

1. **全量目录始终可枚举**（不删数据，只控制「可见性」）；
2. **暴露计划决定初始可见集**（技能侧需要一个与 `ToolExposurePlanner` 同构的 `SkillExposurePlanner`）；
3. **检索工具兜底**（模型可以主动找技能）；
4. **fail-open**：检索不可用时退回「全量可见」，**不得**因为检索故障导致技能全部不可用。

### 3.4 场景 / 版本维度（回答用户第 2 点的 MySQL 例子）

用户点出的问题是**同一技能在不同版本/场景下正确性不同**。数据模型上必须能表达：

- **适用前提**（`Preconditions`）：如「MySQL 8.0+」「Windows + pwsh」「仅在部署窗口」；
- **不适用场景**（`NotApplicable`）：显式反例（**这比正向步骤更有价值**）；
- **版本锚点**（`AnchoredVersion`）：技能针对的外部依赖版本；外部版本漂移后技能进入「待复核」。

⇒ 「需要理解的技能越少越好」的正确形式是：**检索时用前提/场景做过滤**，而不是让模型读完全文再自行判断。

### 3.5 「SKILL = 烹饪书」这一判断的设计含义（回答用户第 6 点）

如果 SKILL 是烹饪书，那么：

| 烹饪书的什么 | 对应技能里的什么 | 现状 |
|--------------|------------------|------|
| 技法原理、火候判据 | **判据 / 边界 / 反例** | 仅 11/139 有（§1.1） |
| 食材替换表 | 场景/版本变体 | 无字段承载 |
| 出错的补救 | 失败模式与回滚 | 极少 |
| 「这道菜的做法」 | **步骤序列** | **过载**（95.7% 的自动回放都在这层） |

**并且**：模型越强，「步骤」层的边际价值越低（模型已会），而**「判据 + 反例 + 版本前提」的边际价值越高**。
⇒ 这直接推出两条 RSI 判据（对应用户第 4 点）：

- **负信号**：一个技能若只重复模型已有能力，且增加了上下文成本，其**净价值可能为负** ⇒ RSI 必须能输出「**不用它更好**」。
- **递减判据**：技能价值随**模型版本**与**外部依赖版本**衰减 ⇒ 需要「复核到期」机制（否则技能库里会长期堆积过期指导）。

## 4. 遥测与负信号：最小数据模型（回答用户第 4、5 点）

### 4.1 必须记录的最小事实（一次注入 = 一条记录）

| 字段 | 说明 |
|------|------|
| `SkillId` / `Version` | 被注入的技能及其版本 |
| `TurnId` / `SessionId` / `AgentId` | 归属与可追溯 |
| `TriggerKind` | `keyword` / `vector` / `explicit`(模型主动 `skill_get`) / `pinned` |
| `TriggerDetail` | 命中的具体关键词或相似度分值（**可解释性，必须存**） |
| `InjectedAtUtc` / `InjectedTokens` | 成本（即使只是估算） |
| `ModelRoute` | 当时用的模型（价值随模型衰减，必须绑定） |
| `Outcome` | `unknown` / `task_ok` / `task_failed` / `abandoned`（由后续任务结果回填） |
| `Signal` | `useful` / `unused` / **`harmful`**（负信号，人工或判据判定） |
| `EvidenceRef` | 判定的依据（会话/消息/commit） |

### 4.2 双极性信号（这是 RSI 语义上的扩展，不只是多一张表）

现有 RSI 信号是「**哪个行为值得晋升**」（正向）。新增：

| 信号 | 含义 | 触发条件（示例，先给形态，不预先调参） |
|------|------|------------------------------------------|
| `retire_candidate` | 应淘汰 | 长期零命中（②类） |
| `harmful` | **负价值**：注入了反而更差 | 注入了且任务失败/被用户纠正（③类） |
| `stale_anchor` | 版本漂移、待复核 | 外部依赖版本与技能锚点不符 |
| `redundant_with_model` | 与模型已有能力重叠 | 技能内容与「无技能基线」表现无差异 |

⇒ 与母文档 §14「提炼而非积累」一致：**淘汰与合并必须是一等操作**。
同时满足宪法 **C8（系统必须能「降」）**。

### 4.3 明确不做的

- **不用 LLM 判定「有用」**：先用**可机械统计**的事实（命中次数、任务结果、成本）作第一层判据；
  LLM 只用于「为什么」，不用于「是什么」。
- **不把遥测当绩效**：遥测是**判据输入**，不得反过来成为目标（Goodhart）。

## 5. 反模式清单（明令禁止）

1. **全量注入技能全文**：随技能数线性推高上下文成本，且认知负担放大（现状已到「要么全量要么全无」）。
2. **把工具名/治理标签当技能关键词**：实测 89.1% 噪声、1735 次注入机会被挤掉（G1 报告）。
3. **只靠静态形态过滤做「去噪」**：G5-a 实测证明这会切断现有注入路径（若注入主要靠工具名命中）。
   ⇒ 去噪的实施**必须**在遥测之后，且必须附注入行为对比。
4. **在无遥测时宣布某技能「没用」并删除**：无法区分 ①②③（§1.2），删除是不可逆的破坏。
5. **语义检索上线即取代关键词**：无评测就没有结论（违反 C5：无度量不调参）。
6. **一次重写 `CollectKeywords`**：应通过配置切换口径，保留一键回滚（C4）。
7. **让技能与模型能力做重复投资**：应优先补「判据/边界/反例」，而不是继续抄录步骤。
