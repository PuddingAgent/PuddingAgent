### 0.2 ⚠️ 这两个接缝**在生产中没有任何实现** ⇒ 抽象是惰性的
（与 S1b/S2a 同一类病：定义了端口但没人实现 ⇒ 永远不会被调用。）

### 0.3 既有健康面的键**缺场景维度**（这是本切片要修的正确性缺陷）
`Source/PuddingRuntime/Classification/ClassifierHealthReporter.cs`：
- `private sealed record DeferredKey(string ClassifierId, string ToolId, string ArgumentsHash);`（`:90`，**无 SceneKey**）
- `private readonly Dictionary<DeferredKey, DeferredCounterState> _counters`（`:86`）
- `private readonly Dictionary<string, ClassifierEntry> _classifiers`（`:85`，按 ClassifierId）
- `EnsureRegistered(classifierId)`（`:126`）、`Snapshot() → IReadOnlyList<ClassifierStatus>`（`:203`）、`SnapshotDeferredCounters() → IReadOnlyList<DeferredKeyCounterSnapshot>`（`:228`）
- `DeferredKeyCounterSnapshot`（`:10`）、`DeferredReport`（`:35`）

**缺陷**：多场景共用同一分类器时，`(ClassifierId, ToolId, ArgumentsHash)` 会把不同场景的失败计数**混进同一桶** ⇒ 一个场景的累积失败会把**另一个场景**推到 `Degraded`/`Unavailable`。

### 0.4 不可回退的既有语义
**「裁决先于留痕」**：审计写入失败**不改变已定裁决**，**只记 Warning**（既有实现见 `ToolCallClassifierPipeline`，理由写在它注释里）。

## 1. 为什么现在做（把这段理由写进代码注释）
多场景共存后计数污染是**真实正确性缺陷**。**而现在只有一个场景，是加入场景维度成本最低的时刻**（单场景下行为必然可保持不变）；等有 5 个场景再加，就是同时改 5 处。

**禁止**落到"空字符串键"：空键会让不同来源混进同一桶，正是本切片要消灭的东西。

## 3. 交付物 2：把 S1a 接缝接到既有旁挂（生产实现）

### 3.1 `OperatorHealthObserverAdapter : IOperatorHealthObserver`
- 内部调用 `ClassifierHealthReporter` 的记录 API，按 `(SceneKey, OperatorId)` 分区；
- **必须吞掉自身异常**（接缝契约：实现抛异常不得影响裁决）——**吞掉但必须可探查**（记 Warning），**不得静默**。

### 3.2 `OperatorAuditSinkAdapter : IOperatorAuditSink`
- 内部写既有审计存储；
- **裁决先于留痕**：写入失败**不改变裁决**、**只记 Warning**、**不得抛出**。

### 3.3 关于"双重兜底"
`OperatorBase`（S1a）**已经**对旁挂做了保护（先读它确认）。因此：
- 两层都有兜底是**允许的**（纵深防御），但**必须在代码注释里写明**哪一层是权威兜底、为何两层都存在，避免后人误以为是冗余而删掉一层；
- 若两层都记 Warning 会产生重复日志 ⇒ **明确选择一层负责记日志**（建议：`OperatorBase` 负责记，adapter 只保证不抛），并写进注释。

### 3.4 DI
**追加式**注册两者；不得改动任何既有注册行。
