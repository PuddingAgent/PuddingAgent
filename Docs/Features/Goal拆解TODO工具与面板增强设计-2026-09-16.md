# Goal 拆解 TODO 工具 与 面板增强设计（2026-09-16）

> 触发：用户要求 ① Goal 弹窗面板补「目标拆解 / 步骤显示 / 结构化受阻说明」；② 新增 TODOList 工具，用于**临时拆解记录**、给用户**展示与跟踪**一个目标/任务可拆成哪几个小目标，并在 Goal 模式下支持**勾选步骤完成**；面板打开时**拉取最新进度**。
>
> 本文是设计基线（父级裁决），实现按 §7 的原子刀序推进。
>
> **2026-09-16 用户澄清（已生效）**：TODO 是**用于与用户交流的工具**（临时、直白地传达「我在干什么」）；**不需要归档**；**Agent 之间隔离**；面板**允许手改，保持较高的自由度**。

---

## 1. 一句话设计

**TODO = Agent 的「拆解与自述层」（intent，可临时、可丢弃、可勾选）；`task_nodes` = 平台的「调度与验收层」（execution，有租约、有依赖、被 WorkUnit 执行）。两者语义分离、默认不同步。**

**再定位（用户原话）：TODO 首先是「与用户交流的工具」——它要让用户一眼看懂「Agent 现在在干什么」。** 因此它必须**轻、快、高自由度**，而不是流程闸门；约束设计（§3）已据此放宽。

面板据此**分区显示**，并把「拆解进度」与「验收进度」**分成两个不同的进度**，杜绝用 Agent 自述冒充目标达成。

---

## 2. 为什么不是「直接写 task_nodes」（对上一版建议的修正）

用户澄清 TODO 的定位是**临时拆解记录**后，原方案（写 canonical `task_nodes`）暴露三个硬伤：

| 硬伤 | 说明 |
|---|---|
| 场景不成立 | `task_nodes` 必须挂在 `task_plan_runs` 下；**没有绑定 task 的 Goal、临时任务、甚至普通会话**都没有 plan run ⇒ 写不进去（这正是当前面板恒显示「该目标尚未生成执行计划（暂无步骤）」的根因，见 `GoalQueryService.cs:102`） |
| 语义被污染 | 「临时拆解」一旦落进计划表就成了**正式计划步骤**，可能被调度器当 WorkUnit 处理 ⇒ 重演「假占用 / 双写」 |
| 写入门槛过高 | plan run 有版本/指纹/CAS 语义；勾选一个 TODO 项不该触发计划版本变更 |

⇒ **结论：新增轻量存储 `todo_items`，并把"临时/展示"与"调度/验收"的边界写死在文档与 UI 里。**

## 3. 数据模型（建议）

```
todo_lists
  list_id          PK
  agent_id         string                         // 归属 Agent —— 跨 Agent 隔离：读写均按 agent_id 过滤
  scope_kind       goal | task | session          // 挂载对象类型
  scope_id         goalRunId | taskId | sessionId
  title            string?                        // 可选标题（如「看板梳理拆解」）
  revision         int                            // CAS 版本，全量写入时 +1
  created_at_utc / updated_at_utc
  archived_at_utc  nullable                       // 临时性：作用域结束后归档（默认保留 7 天）

todo_items
  item_id          PK
  list_id          FK → todo_lists
  slug             string    // 稳定标识（写方提供，全量替换时用于 diff：新增/完成/受阻）
  title            string    // ≤120 字
  status           pending | in_progress | completed | blocked
  note             string?   // 可选说明
  evidence_ref     string?   // 可选：commit sha / 文件路径 / 报告 id（勾选完成时建议带）
  blocked_reason   string?   // status=blocked 时必填（见 §5 结构化受阻）
  order_index      int       // 展示顺序
  started_at_utc / completed_at_utc  nullable
```

**约束（2026-09-16 放宽 —— 它是交流工具，不是流程闸门）**：
- **硬约束（拒绝写入）**：`slug` 在列表内唯一；`scope_id` 必填；`expected_revision` CAS 冲突必须**明确报错**（不得静默覆盖）；读写必须按 `agent_id` 隔离。
- **软约束（接受写入，返回 warning 供 UI 提示）**：建议 ≤20 项；建议同时最多 1 个 `in_progress`（多开不拦，仅提示）；`blocked` 项建议给 `blocked_reason`（缺失时提示，不拒绝）。
- 理由：用户要求「保持较高的自由度」—— 工具的价值是让人**看懂 Agent 在干什么**，不是拦它的手。

## 4. 工具族（4 个动作）

| 工具 | 语义 | 关键设计理由 |
|---|---|---|
| `todo_write` | **全量替换**某作用域的拆解表（带 `expected_revision` 做 CAS） | **幂等**：重跑不产生重复项、不累积僵尸项；并强制每轮重新审视拆解（而非只增不减）。返回 diff（added/completed/blocked/removed）供面板与 Agent 共用 |
| `todo_read` | 读取当前拆解 + 汇总（计数、当前 in_progress、受阻项） | **面板与 Agent 同一视图** ⇒ 面板显示的就是 Agent 在执行的东西，不会出现「面板 0 步、Agent 干了 5 件事」 |
| `todo_check` | 勾选单项状态（`completed` / `in_progress` / `blocked`+reason） | 用户点名要的「Goal 模式下勾选步骤已完成」；单项更新比全量替换更适合收尾动作 |
| ~~`todo_promote`~~ | **本阶段不做**（用户 2026-09-16 裁决：不接重看板） | 若将来需要「轻量看板」视图，目标应是**轻量表 + 数据库持久化 + Agent 间隔离**，而**不是** `manage_tasks` 的重看板（后者带 assignment/lease，会重演「看板 194 张 + 假占用」）|

**不做**：`todo_archive`（用户明确：目前不需要归档）。TODO 表本身就是那张「轻量看板」；`archived_at_utc` 列保留备用但**不主动写入**。

**Goal 模式集成**：`todo_write` / `todo_check` 需在 **Goal 迭代信封的工具白名单**中可用（否则 Agent 在 Goal 轮次里无法勾选）。

## 5. 结构化受阻说明（`GoalBlockerStatement`）

三处来源收敛到同一结构（面板同一卡片渲染）：

| 来源 | 现状 | 目标 |
|---|---|---|
| 平台自动（熔断 / 检查超时 / 预算耗尽 / 依赖等待） | 硬编码英文长句（`GoalSettlementStore.cs:1177`） | 改用**已存在的** `blockedCode`（如 `no_progress_circuit_open`）+ 前端「码 → 中文」映射；**未知码显示原始码**，不空白 |
| Agent 主动上报 | `task_update(disposition=blocked, reason=…)` 只有自由文本；TODO 的 `blocked` 项 | 统一五要素：`kind / summary(中文一句话) / evidenceRefs[] / nextAction / needsHuman` |
| 人工补录 | 无入口 | 面板加「补充受阻说明」 |

**不新增表**：复用 `goal_verifications` 的 `blocker_code`，必要时补 `blocker_summary` / `blocker_needs_human`；TODO 侧的受阻说明存 `todo_items.blocked_reason`。

## 6. 面板增强（Goal 弹窗）

### 6.1 修复项（明确缺陷）
- **objective 重复渲染**：`GoalBanner.tsx:281`（加粗首行）与 `:299`（灰底框）**同屏渲染同一段文字** ⇒ 二选一或让灰底框只显示剩余行。

### 6.2 分区结构

```
① 目标区：objective（仅一处）· Iteration n/max · 剩余额度 · objectiveVersion ·
          绑定 task/plan · 起始时间与已运行时长 · 状态 chip
② 拆解区（TODO）：步骤清单（可勾选状态）· 拆解进度 completed/total ·
          in_progress 高亮 · 受阻项置顶并展开说明 · 最近更新时间 · 刷新按钮
③ 执行计划区：来自 GET /api/v1/goals/{goalId}/steps（task_nodes depth-1）·
          planVersion · 每步 startedAt/completedAt/evidenceRefs；
          无计划时显示「尚未生成执行计划」并说明原因（不是空白）
④ 验收与受阻区：必需条件通过数/总数（**验收进度**，平台裁决）·
          上一轮裁决（lastVerdict：outcome/blockerCode/unmetCriteria）·
          受阻卡片（码→中文 + 建议动作 + 是否需你决策）· 最近 3 轮迭代历史
⑤ 操作区：恢复 · 停止 · 重新规划(replan) · 补充受阻说明 · 查看原始 payload
```

### 6.3 两条进度必须分开（重要）

| 进度 | 来源 | 语义 | UI 标注 |
|---|---|---|---|
| **拆解进度** | `todo_items` completed/total | Agent 自述 | 必须标注「自述，不代表目标达成」 |
| **验收进度** | 必要 criterion 通过数 / 必要总数 | 平台裁决（verifier） | 标注「平台裁决」 |

> 这与平台既有纪律一致：**自述只是提案，终态由服务端验收器决定**。两个进度混成一个，就是把今天刚修好的口径又混回去。

### 6.4 拉取策略
面板**打开时拉取最新**（`todo_read` + `GET …/steps` + goal 快照）；面板打开期间按 Goal outbox 事件增量刷新；提供手动刷新按钮（截图中那个 ⟳ 图标保留语义，但要有 loading/失败态）。

## 8. 验收标准（TD-1/TD-2）

1. `todo_write` 同内容重复调用两次 ⇒ 不产生重复项、列表内容与 revision 变化符合预期（幂等）。
2. 并发写入（两个 Agent / 父子）用 `expected_revision` CAS，冲突返回明确错误而非静默覆盖。
3. 软约束：两个 `in_progress` ⇒ **接受写入但返回 warning**；`blocked` 无 `blocked_reason` ⇒ 接受并提示（**不拒绝**）。硬约束：`slug` 重复、CAS 冲突必须拒绝。
4. 勾选完成（`todo_check`）后，`todo_read` 与面板显示一致（同一数据源，无双写）。
5. 面板打开时拉取到最新拆解与最新 Goal 进度（含受阻说明），**不出现 objective 重复渲染**。
6. **拆解进度与验收进度在 UI 上分列**，且拆解进度标注「自述」。
7. **Agent 隔离**：Agent A 既读不到也写不到 Agent B 的列表（即使 `scope_id` 相同）。
8. 全部既有测试不放宽；新增测试覆盖上述 7 条。

## 10. 与「任务看板 / 计划步骤」的边界（是否重复建设？—— 结论：不重复）

**三层正交、数据层零共享：**

| 维度 | 任务看板 `tasks`（manage_tasks） | 计划步骤 `task_nodes` | TODO（todo_lists/items） |
|---|---|---|---|
| 谁写 | 管理者 / 用户 / 派发 | 合同派生 + planner | **Agent 自己** |
| 生命周期 | 长期、跨会话、可归档 | 绑定 plan run 版本 | **临时，随目标/会话存活** |
| 是否被调度 | ✅ assignment / lease / auto_dispatch | ✅ WorkUnit 执行单元 | ❌ 纯展示 |
| 是否被验收 | ✅ AcceptanceCriteria + NeedsReview | ✅ 受控检查 + verifier | ❌ 自述，不是证据 |
| 归属 | workspace 全局 | goal / task 作用域 | **Agent 隔离** |
| 消费者 | 平台调度 + 管理者视图 | 调度器 + 面板步骤区 | **人（用户）** |

⇒ 不同表、不同写入路径、不同作用域、不同消费者。**唯一共享的是面板展示区，那是 UI 组合，不是数据重复** ⇒ **不构成重复建设**。

**判断类比**：看板卡 = **工单**（写一次=一次承诺，要被接手、被验收）；TODO = **白板上的清单**（随时写、随时改、随时擦）。

### 10.1 防漂移硬规则（实现约定，违反即设计腐化）

1. **TODO 永不成为调度源**：TODO 项不得被派发、不得产生 assignment/lease、不得参与验收。
2. **需要调度或验收 ⇒ 去 `manage_tasks` 建看板卡**，而不是把 TODO 表改造成看板。
3. **不做 `promote`，也不做「晋升提示」**（用户 2026-09-16 裁决：平台**不限制、不定义**什么时候一个 TODO 跃迁到看板）。
   - 平台只做**能力分离**：TODO = 零摩擦白板；看板 = 有规则、要验收。**选择权在 Agent**。
   - Agent 想要严谨 ⇒ **直接用既有 `manage_tasks` 建卡**（能力早已存在，无需专门通道）。
   - 收益：不存在「同一件事两个身份」的双写风险，也不存在「平台替 Agent 决定何时升级」的越权。
4. **需要长期保留的结论 ⇒ 写 Memory**（`save_memory`），不塞 TODO（TODO 会随作用域消失）。
5. 面板必须**分区块 + 标注来源**：`拆解（Agent 自述）` 与 `执行计划 / 验收（平台裁决）` 不可合并显示，进度也不可合并。

### 10.2 不做「独立轻量看板页面」（父级建议，待用户确认）

理由：① 用户诉求是「看懂 Agent 在干什么」，面板拆解区已满足；② 独立看板页面 = 又一套视图/权限/生命周期，等于养第二个看板，收益不明；③ 若将来真需要跨会话查看，最小代价是在**既有看板界面加一个「Agent 拆解」筛选视图**，而不是新建一套系统。

## 11. TODO 的真正用途：**抗遗忘的 working memory**（本轮新增，优先级提升）

用户原话点出了核心：「**将需要的拆解的步骤或者 Plan 记录到 TODO 上，从而保持目标或者 Plan 不被打断和遗忘**」。

⇒ 所以 TODO 的价值不止「给人看」，更是**把 Agent 自己的拆解外化成可跨轮次存活的记忆**。据此新增一项设计要求（**并入 TD-3**）：

**TODO 快照必须注入 Goal 迭代信封的 `<goal_payload>`**，与 `lastVerdict` 并列：

```json
{
  "goalRunId": "...", "iterationNo": 5,
  "lastVerdict": { "outcome": "repair", "blockerCode": "...", "unmetCriteria": ["..."] },
  "todo": { "revision": 7, "inProgress": "step-3",
            "items": [{"slug":"step-1","title":"...","status":"completed"}, ...] }
}
```

- 截断纪律与 `lastVerdict` 一致：最多 20 项、标题 ≤120 字，超出截断不劈开代理对。
- 读取失败 **fail-soft**（与 `TryLoadLastVerificationAsync` 同一模式：告警 + 省略字段，绝不中断续行）。
- 指令文本追加一句：若 `todo` 非空，本轮应推进其中的 `in_progress`/`pending` 项；若与拆解不符，先用 `todo_write` 更新拆解再动手。
- **依据**：该模式已在 `6beb04e0`（lastVerdict 回灌）验证过链路可行，复用同一注入点（`GoalContinuationWorker.BuildPrompt`）。

**面板呼应的两个细节**：① 「拆解区」与「上一轮裁决」应**相邻显示**（同属连续性信息）；② 受阻时优先展示「上次卡在哪 + 本次拆解打算怎么绕」，而不是只报错。
