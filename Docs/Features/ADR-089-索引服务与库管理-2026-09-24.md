# ADR-089：增强索引的服务边界、库管理与 Admin 面板（2026-09-24）

> 用户指令原文（2026-09-24 第三轮）：
> 1. 向量使用 **Qwen3 Embedding 0.6B（本地）**，已注册到 LLM 资源池；**增强索引不应该去读取 LLM 资源池，而是让 LLM 资源池提供服务**，保持模块的明显边界和职责清晰。
>    增强索引需在**配置文件中定义使用的索引服务商和模型名称**（如"XX服务商/XX模型"），这样增强索引可以**从 LLM 注册资源池服务获取向量**信息，通过**向量工程服务或向量服务类的实例**。这些都是架构整洁性的体现。
> 2. 后端 Admin 需要一个**管理面板**：管理增强索引工具的参数（使用的服务商和模型、增强索引的运行状态等）。
> 3. 索引位置建议放**项目目录根**；需要**索引初始化功能**和**加载工具**：Agent 调用工具初始化项目索引，并**初始化 git 忽略**（避免索引文件被打包到 git）；初始化完成返回**索引库 id（或路径 id）**，后续可直接搜索或携带该 id。
>    1) Codex/Copilot 打开会话时指向项目目录，故可直接建索引；**PuddingAgent 是拟人化的、工作在整个电脑上、可能同时处理多个项目** ⇒ 需要工具**指定当前会话的工作目录**，以便增强索引正确加载索引库地址。**加载错误须返回友好提示与指导信息**。
>    2) 加载完成后可**隐含该工具**（不必携带库地址）；但要索引另一个项目需**重新初始化**，否则返回友好提示。**待讨论**：一个库维护所有项目索引 vs 每个项目目录各建索引（一库会快速膨胀、难管理、data 目录不断膨胀、**归档项目的索引难卸载清理**）。

## 0. 已核实的事实（不要凭记忆）

| 事实 | 值 |
|---|---|
Qwen3 Embedding 0.6B 路由 | **`lmstudio-local/text-embedding-qwen3-embedding-0.6b`**（provider 名 "LM Studio 本地"，`capabilityTags=["embedding"]`）|
价格 | **0**（本地推理，无 token 费用）|
模型上下文 | `maxContextTokens=8192` ⇒ **长文件必须分块**才能落在窗内 |
同池另一 embedding | `bigmodel-embeddings/embedding-3`（`$0.0005/1M`，远程）|
既有服务契约 | `PuddingCore/Abstractions/IEmbeddingService.cs`（命名空间 `PuddingCode.Abstractions`）：`GenerateEmbeddingAsync(string)` / `GenerateEmbeddingsAsync(texts)` —— **签名里没有 provider/model** |
既有实现 | `PuddingRuntime/Services/OpenAiEmbeddingService.cs`，注册于 `PuddingRuntime/DependencyInjection.cs:142` |

**既有契约的结构性问题**：`IEmbeddingService` 把"用哪个服务商/模型"**固定在实现内部**，因此用户在配置里改 `服务商/模型` 这件事**做不到**。这正是"增强索引需要在配置文件里定义服务商与模型"要解决的缺口。

## 1. 服务边界：增强索引只认端口，资源池提供服务

**端口（新增，由资源池侧实现；增强索引只依赖它）**

```
// 位置：能力侧（与具体提供方解耦），不放在 Core 的旧接口上
public readonly record struct EmbeddingRoute(string ProviderId, string ModelId);

public interface IEmbeddingProvider          // 名字待定，语义 = "向量工程服务"
{
    EmbeddingModelInfo Describe();                       // 维度 / 最大上下文 token / 是否本地 / 可用性
    Task<float[]> EmbedAsync(string text, CancellationToken ct = default);
    Task<float[][]> EmbedBatchAsync(IReadOnlyList<string> texts, CancellationToken ct = default);
}
```

- **route 的来源**：增强索引**自己的配置文件**（见 §2），形式就是用户说的 `"服务商/模型"` 串，
  例如 `"lmstudio-local/text-embedding-qwen3-embedding-0.6b"`。
- **谁把 route 变成实例**：**资源池的服务层**（组合根）——"解析 `providerId/modelId` → 构造/取出向量服务实例"
  这件事由资源池做，增强索引只拿到 `IEmbeddingProvider`。
- ⛔ **禁止**：增强索引不得读 `llm.providers.json`、不得持有 `apiKey`/`baseUrl`、不得直连 HTTP。
- ⛔ **不改既有 `IEmbeddingService`**：它已被记忆域消费（`SessionChunkIndexer`、`EmbeddingGenerationHook`），
  改签名会打穿记忆域。做法是**新增**带 route 的端口，旧接口保持不动（可后续单独收敛）。
- **与既有 `ISearchProbe` 同构**：组件依赖端口 + 外部提供适配器 ⇒ 组件保持零依赖、可独立测试（替身即可）。

**降级与错误语义**（必须可见，不准静默回退）：
模型未注册 / 服务商未启用 / 本地服务未启动 / 维度与既有索引不一致（**换模型会让旧向量失效，必须显式提示重建**）。

## 2. 配置文件：索引自己声明"服务商/模型"

增强索引的配置项（草案，落在索引组件的配置节）：

```jsonc
{
  "enhancedIndex": {
    "embedding": {
      "route": "lmstudio-local/text-embedding-qwen3-embedding-0.6b",
      "fallbackRoutes": []          // 显式声明，不隐式回退
    },
    "chunking": {
      "strategy": "outline",        // outline | plain
      "minTokenLength": 3,
      "languageKeywords": true       // 语言关键字（if/else/for/return/...）不入索引
    },
    "scope": { "include": [], "exclude": [] },
    "storage": { "kind": "ProjectLocal", "directory": ".pudding/index" }
  }
}
```

要点：**换模型 = 改配置**，不是改代码；`route` 与 `chunking` 都进配置，这样"参数可被 Admin 管理"（§3）才有依据。

## 3. Admin 管理面板

- **参数管理**：embedding `route`（下拉选项从**资源池的只读接口**取）、chunking 策略与阈值、scope include/exclude、存储位置。
- **运行状态**：当前作业（阶段 / 已扫·已索引·已跳过文件数 / 字节 / 当前目录 / ETA / 可取消）、最近一次索引的耗时与体积、库清单。
- **边界**：面板**不直接读写索引文件**，一律经后端服务层；与"组件先测试、后接入"的规程一致。
- **只读原则**：面板对资源池**只读**（列服务商/模型），不改资源池配置 —— 避免两处都能改、互相覆盖。

## 4. 索引位置与库管理：**裁决**

### 4.1 结论

> **每个项目一个独立索引库（物理隔离）+ 一张全局"索引库登记表"（账本）统一治理。**
> **物理位置默认放项目根**（`<项目根>/.pudding/index/`），并**允许"中央存储 + 每项目子目录"作为降级后端**。

### 4.2 为什么不是"一个库维护所有项目"

用户指出的问题成立，根因是**生命周期耦合错了**：

- 索引库的生死应**与项目绑定**，而不是与 `data/` 绑定。项目归档 ⇒ 索引该一起消失，
  否则它留在中央库里继续占地方、继续被搜到、且**没有任何触发点提醒你去清理它**。
- 一个中央库还会把"**跨项目误召回**"变成默认行为：搜 A 项目的符号，返回 B 项目的同名结果。
  物理隔离让这个问题从"要靠过滤规则解决"变成"结构上不可能发生"。
- 中央库唯一的真实优势是"不用在项目里放东西"——这个优势可以用**降级后端**换到，不必牺牲隔离性。

### 4.3 为什么"每项目一份"还不够：需要登记表

只有物理隔离的话，Agent 无法回答"现在有哪些库、多大、多久没用过、哪些是孤儿"。
登记表**不是数据仓库，只是账本**：`库id / 项目根 / 存储类型 / 索引格式版本 / 策略 / embedding route / 创建时间 / 最后使用时间 / 体积 / 状态`。

⇒ 两种模型**不是二选一**，而是"**一张账本 + 两种存储后端**"：

| 存储后端 | 用于 | 归档清理方式 |
|---|---|---|
`ProjectLocal`（默认） | 项目根可写、体积可控 | **跟着项目目录一起消失**；登记表负责清理孤儿登记 |
`CentralStore`（降级） | 项目根只读 / 网络盘 / **体积超护栏** | `unregister` + `purge` 显式删除该项目的库目录 |

### 4.4 位置放项目根的**代价**（必须正视）

全仓索引实测 **837.8 MB**（语料 743.7 MB）—— 若原样落在工作树里，会让备份/同步/IDE 索引都很难受。
所以：

1. 这一条**依赖 U4-1a 先把体积压下来**（outline 优先分块 + 过滤）；体积没降下来之前，
   "放项目根"是**有条件的**。
2. 设**体积护栏**：超过阈值（建议先定 **50 MB**，可配）时管理员面板给出警告，并建议改用 `CentralStore`。
3. 库目录名收敛为 **一个**（`.pudding/index/`），并**必须**完成 git 忽略初始化（§5），
   否则用户会在 `git status` 里突然看到几十万个文件。

## 5. 工具设计（初始化 / 加载 / 治理）

### 5.1 `index_init`

- **入参**：项目根（缺省 = **当前会话工作目录**）。
- **动作**：校验目录存在且可写 → 向上寻找**项目根标记**（`.git` / `*.slnx` / `*.sln` / `package.json`）
  → 创建库目录与 manifest（库 id、项目根、策略、embedding route、索引格式版本、创建时间）
  → **初始化 git 忽略**（见下）→ 触发索引作业 → 返回**库 id**。
- **git 忽略初始化（幂等）**：向项目根的 `.gitignore` 追加一条 `/.pudding/`；
  若已存在等价条目**不重复写**；若项目**不是 git 仓库**则明确提示"未初始化 git 忽略（非 git 仓库）"，
  **不静默跳过**。

### 5.2 `index_load` / 加载语义（回答用户第 3 条 1) 与 2)）

- 加载 = 把"**当前会话 ⇄ 库 id**"绑定，绑定后**可隐含**：后续检索工具不必再携带库 id。
- **换项目必须显式**：已绑定库 A，又要求索引/检索项目 B ⇒ **返回友好提示**，不静默切换：
  > "当前会话绑定的是库 `<A>`（项目 `<路径>`）。要切换到项目 `<路径B>`，请先调用 `index_init` 初始化 B，
  > 或显式指定目标库。"
- **加载失败的错误分类（每条都要有指导信息，不许只说失败）**：

| 情形 | 友好提示（要点） |
|---|---|
未初始化 | "`<路径>` 下未找到索引库。请先 `index_init`；若你的工作目录不是项目根，请显式指定项目根。" |
目录不存在 / 无权限 | "`<路径>` 不可访问（原因）。请确认路径，或改用 `CentralStore`。" |
**多个候选库**（嵌套项目） | **列出候选让 Agent 选**，绝不静默挑一个 |
库损坏（manifest 与目录不符） | "库 `<id>` 的 manifest 与磁盘内容不一致，建议 `index_purge` 后重建。" |
**版本不兼容** | "库 `<id>` 的索引格式版本 `<v1>` 与当前组件 `<v2>` 不兼容，请重建。" |
**模型变更致向量失效** | "embedding route 由 `<旧>` 变为 `<新>`，既有向量不可比，需重建。" |
库过期 | "库 `<id>` 的最后索引时间早于源文件最新修改时间，建议重建。" |

### 5.3 治理工具

`index_list`（列举库与体积/最后使用时间）、`index_unregister`（解除会话/账本绑定，**不删文件**）、
`index_purge`（**删除库目录**，必须二次确认，且**只删 Pudding 自己拥有的库目录** —— 沿用 ADR-089 §10 硬约束）。

## 6. 本文件确定的硬约束

1. 增强索引**只依赖端口**；route 解析与向量服务实例由**资源池服务层**提供。
2. **禁止**增强索引读资源池配置、持有密钥或直连 HTTP。
3. 服务商/模型、分块策略与阈值、scope、存储位置**全部进配置文件**（可被 Admin 面板管理）。
4. 索引库**每项目一份**，位置默认项目根 `.pudding/index/`，并**必须**完成 git 忽略初始化。
5. `purge` 只允许删除**库目录**；绝不删源码或工作区文件。
6. 所有降级与错误**必须显式可见**（尤其：本地向量服务未启动、维度不一致、模型变更），**不静默回退**。

## 7. 用户裁定（2026-09-24 第四轮，**取代本文 §4.1/§4.3 的推荐**）

用户对本文两个待决问题给出了裁定：

1. **每项目一库 —— 确认；并且不需要中央库。**
   - 索引库损坏时，**用 grep 作为降级**（文本面兜底），不引入 `CentralStore`。
   - 损坏或丢失都可以**重建索引** ⇒ 索引库被定位为**可重建的派生物**，不是不可替代的数据。
   - 影响：§4.3 的“一张账本 + 两种存储后端”**降为只有 `ProjectLocal` 一种后端**；
     登记表的价值相应变化（不再用于“选择后端”，而用于**列举 / 清理孤儿登记 / 展示体积与最后使用时间 / 触发重建**）。
     `index_purge` 的语义收紧为“删库后可由 `index_init` 重建”，因此**不需要中央备份**。
2. **体积护栏 = 1 GB**（取代本文建议的 50 MB）。
   - 触发护栏时要**留下日志**；并**触发 GC**（该项**留到后续切片实现**）。
   - 影响：§4.4 的“50 MB 体积护栏”按 1 GB 执行。注意 U4-1a 实测显示分块后体积可减半以上，
     1 GB 在单项目尺度上是很宽松的上限。

**降级链（随本次裁定明确）**：结构面/增强索引不可用（未初始化、损坏、语言不支持）
⇒ **文本检索（grep）降级** ⇒ 结果必须**标注为降级结果**并提供重建指引（见
`Docs/Features/ADR-089-结构化地图检索设计-2026-09-24.md` §5.5）。

## 8. U4-7（2026-09-25）：全文索引「供给参数」配置化 + fail-closed 校验

**用户裁定（2026-09-25）**：「1GB 请使用配置文件确定参数，方便后期替换为 XXGB……建议『1GB』的大小使用**项目目录的统计 json 文件**配置决定，**或者**使用 **Data 目录的配置文件**决定，而不是选择一个固定值。」
⇒ 本刀取 **Data 目录的配置文件**（`<DataRoot>/config/system.json`，宿主启动时已加载并支持 hot reload），**不引入代码内固定常量作为唯一来源**。

### 8.1 参数（配置节 `FullTextIndex`，落在 Data 目录 `system.json`）

```jsonc
{
  "FullTextIndex": {
    "Enabled": false,              // 总开关；默认 false ⇒ 不建索引、零索引 I/O
    "Scopes": [],                  // 目标目录：绝对目录，或相对 WorkspaceRoot 的相对目录
    "WorkspaceRoot": null,         // 相对 scope 的**显式绝对基准**（禁止用进程 CWD 兜底）
    "MaxIndexBytes": 1073741824,   // 1 GiB = 2^30（**不是**十进制 1 GB = 1e9）
    "MinRebuildInterval": "12:00:00" // 已有索引足够新则跳过重建；"hh:mm:ss"
  }
}
```

- **默认值＝关闭**：不写这个节 ⇒ `Enabled=false` ⇒ `IndexPrebuildService.StartAsync` 立即返回、零索引 I/O。
  该服务此前一直是 `HOSTED-DISABLED`（`HOSTED-DISABLED: builder.Services.AddHostedService<IndexPrebuildService>()`），
  因此**注册它 + 默认关闭 = 现网行为逐字不变**。
- **单一真源（R2）**：`1_073_741_824` 在生产代码中**只出现一次**（选项类型的默认值）。校验、日志、测试一律从选项取值；
  全仓既有其它 1 GiB 常量属**别的域**（`PuddingCodeIndex` 的「代码索引库容量预算」，见 M2-a），**未动**。
- **体积护栏硬天花板**：`MaxIndexBytes` 超过 **1 TiB = 2^40** 一律拒绝（显式常量，不是猜的边界）。

### 8.2 fail-closed 规则（纯函数，可独立单测）

| 情形 | 行为 |
|---|---|
`Enabled=false` | **永远合法** ⇒ 空动作，且**不做任何 I/O**（连目录探针都不调用） |
`Enabled=true` 且 `Scopes` 为空 | **拒绝**（禁止「开了但不工作」静默空转） |
`Scopes` 含空串 / 不存在 / 非目录 / 重复项 | **逐条**拒绝并给出解析后的绝对路径与原因；accepted / rejected 分别列出 |
相对 scope 且 `WorkspaceRoot` 未声明或非绝对 | **拒绝**（**绝不**退回进程 CWD —— 历史缺陷即用 `Directory.GetCurrentDirectory()`，本机等于运行时 bin 目录） |
`MaxIndexBytes <= 0` 或 `> 1 TiB` | **拒绝**，带参数名与值 |
`MinRebuildInterval < 0` | **拒绝**，带参数名与值（`TimeSpan.Zero` 合法 = 每次都重建） |
任一拒绝 ⇒ | **整体不生效**（fail-closed，不做「合格项先建着」的部分生效），并以 Error 记日志 + 说明原因 |

### 8.3 与 §7.2 裁定的关系（**留白必须明确**）

§7.2 裁定「体积护栏 = 1 GB，触发时留日志并触发 GC」——**执行行为本次仍未实现**：
`MaxIndexBytes` 目前只是**参数 + 校验**（拒收非法值），**没有任何**「达到上限 ⇒ 告警 / 拒写 / GC」的运行时逻辑。
登记为后续切片，**不在本刀顺手实现半套**。

> **更新（2026-09-25，本处留白已由 S5 关闭）**：`MinRebuildInterval` 的新鲜度口径**不再是「索引根目录 mtime」粗粒度代理**。
> S5 已提供宿主端口 `IFullTextIndexSupplyComposition.LiveIndexLastWriteUtc(scopeRootPath)`，改为**per-scope live 索引目录 mtime**
> （实现 `PuddingHost/Hosting/LuceneFullTextIndexSupplyCompositionFactory.cs`，经组件单一真源
> `IFullTextIndexRootedEngine.ResolveIndexDirectory` 解析目录 ⇒ 宿主**不复刻**命名哈希）。
>
> **残留（已知方向，非缺陷）**：该信号是**索引目录 mtime**，与引擎 `.last_indexed` 记录的 `t`（扫描开始时间）**并不等值**
> —— 本机实测两者相差 **80.3 s**（dir mtime `2026-09-25T07:50:06.783Z` vs `.last_indexed.t` `2026-09-25T07:48:46.511Z`）。
> 因为目录 mtime 更晚，用它判定会让索引**显得比实际更旧得更慢**，可能漏判「构建窗口内发生的改动」。
