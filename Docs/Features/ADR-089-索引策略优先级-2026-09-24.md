# ADR-089：索引策略优先级与"不打包全部代码"的设计约束（2026-09-24）

> 用户 5 条指令原文（2026-09-24）：
> 1. 实际上可以做优化，比如取消 Lucene 全文检索，使用向量检索。当然，全文检索也可以，不过需要做一定程度优化，**避免将所有的代码都打包做索引**。
> 2. **优先对 code outline 做索引**，代码全文索引优先级最低；其次，**低于一定长度并且是编程语言的忽略**，比如 `if`、`else` 这种单词没有必要做索引。
> 3. 广度优先 or 深度优先。
> 4. **异步、后台、进度可看**。
> 5. **先对一个小目录做索引**，评估索引质量与性能，并评估不同索引模型的质量（纯向量、全文检索、混合检索）的**检索质量、索引速度、查找速度、索引文件体积**差异。

本文把这些指令落成可执行的约束与施工顺序，并附**实测证据**。属 ADR-089 落地细化。

## 1. 实测证据（同一标注集 seed-v1，80 用例；Lucene 全文面）

索引体积 | — | **837.8 MB**（语料 743.7 MB） | **索引比原文大** |

**结论（这就是用户第 1 条直觉的量化证据）**：把语料从 `Source/` 扩到全仓，**检索质量全面下降**（`recall@5` 掉了 26 个百分点），噪声率涨 2.6 倍，索引耗时 ×9.3、体积 838 MB。根因是语料里 **84% 是工具产物**（`.pudding` 一家 20,932 文件 = 74%，`.json`+`.txt` 占 77%）。

## 2. 由此确定的设计约束（不再走"全量打包"路线）

### C1 分层索引，按价值排序（对应用户第 2 条）

| 优先级 | 索引内容 | 说明 |
|---|---|---|
**P0** | **code outline**（符号名/签名/可见性/归属类型/文档注释） | 复用既有 `IFileOutlinerRegistry`（各语言 outliner）+ Roslyn C# 路径；**每符号一条文档**，天然是"结构化小块" |
**P1** | 文档与注释（`.md`、`///`、`//`、docstring） | 意图类查询主要靠它（当前 md 检索 `recall@1=0.02` ≈ 失效） |
**P2** | **代码全文字块**（最低优先级） | 仅作为兜底；且必须过 §2.1 的过滤 |

### C2 过滤规则（第 2 条后半）

- **最小 token 长度**（按语言给阈值，短 token 不入索引）
- **编程语言关键字停用词**：`if/else/for/while/return/class/public/static/void/var/const/import/export/function/def/…`
- **噪声目录不再"一条条加"**：由统一忽略合同（U4-1）供给，`.pudding`/`.tmp-build`/`.pnpm-store`/`.tmp-test-out`/`.firecrawl` 等一律出局
- 每一条规则都要在报告里**可见**（否则无法解释两个策略间 0.2 的 recall 差从哪来）

### C3 遍历策略：**广度优先（BFS）+ 有界队列**（回答第 3 条）

- **BFS 的理由**：① 索引**逐层可用**（配合"异步/后台/进度可看"，先能用浅层结果）；② 在噪声树（`.pudding`/`.pnpm-store` 这类深目录）上**不会先钻到底**再回头，进度与产出更线性可预期；③ 天然与"按优先级分层索引"（P0 浅层源码先建）同构。
- **DFS 的理由**：内存占用小（只需一条路径栈）。
- **裁定**：主路径用 **BFS + 有界队列**；DFS 仅作为内存受限场景的降级选项。**该选择应被测量**（进度曲线、首 N 条结果可用时间），不靠偏好争论。

### C4 异步 / 后台 / 进度可看（第 4 条）

索引作业必须具备：非阻塞启动、可取消、**结构化进度**（阶段、已扫/已索引/已跳过文件数、字节数、当前目录、ETA）、失败可见。既有范式可复用：`CodeIndexMaintenanceHostedService`（启动路径外、非阻塞 Start、有界 Stop）。

## 3. 施工顺序（修订 U4）

| 序 | 切片 | 内容 |
|---|---|---|
**U4-1a** | **小目录索引策略实验台（全文族）** | 在**一个小目录**上实现 outline 优先分块 + C2 过滤规则，与"plain 全文"对照：索引速度 / 索引体积 / 查找延迟 / 检索质量。产出对比报告 |
**U4-1b** | **向量与混合** | 纯向量（复用 `IEmbeddingService`/`OpenAiEmbeddingService`）与混合（RRF）同台对比；**必须记录 embedding 花费**（按 token 计费） |
**U4-2** | **统一忽略合同**（原 U4-1） | 规范 gitignore 语义（复用 NuGet `Ignore`）+ 内置噪声目录并集；供给全部工具 |
**U4-3** | **分层索引落地**（P0 outline / P1 文档注释 / P2 全文） | 把 U4-1a 验证过的分块与过滤固化进生产路径 |
**U4-4** | LSP 增强（B 起步，保留 A 接口位） | 先把仿 LSP 做成真正被消费，再谈外部 LSP 进程 |
**U4-5** | 作用域/类型过滤合同化（补代码智能族） | 原 U4-2 |
**U4-6** | 异步/后台/进度可看（C4） | 生产路径的索引进度与取消 |

> **实测已下调优先级**：原"U4-5 并行检索"（原性能项）→ 热态 p95 在 Source scope 只有 26.5 ms，**性能不是当前瓶颈**，准确率才是。

## 4. 硬约束（沿用，不放宽）

- 组件边界：`PuddingCodeIndex` 不得引 `PuddingCodeIntelligence`/`PuddingRuntime`/`PuddingHost`/`PuddingAgent`
- 只清理 Pudding 自己拥有的索引/缓存，**绝不删除源码或工作区文件**
- 组件交付顺序 S1→S5；新工程登记进解决方案后**必须**过全解决方案构建门禁（§4.2）
- 每个切片要有**能取红**的变异证据；时序/并发测试单次通过不构成证据
- **任何“变好了”的结论必须有改前/改后两组数字**（U4-0 的仪器就是为此建的）

### 5.3 结论（每句都带两组数字）

1. **outline 分块用更小的索引换来了不差（且 MRR 略好）的质量**：索引目录 283,159 B → 149,556 B（**−47.2%**），而 `recall@1/@5/@10`、`precision@5/@10`、`noiseRate@10` **全部相同**，`MRR` 0.7885 → 0.7941。代价侧：索引耗时 1,987 → 2,037 ms（**+2.5%**）、热 `p50` 3.702 → 3.871 ms（**+4.6%**）、热 `p95` 5.984 → 6.130 ms（+2.4%）、热 `p99` 8.510 → 7.751 ms（**−8.9%**）。冷 `p99` 两侧都由“本进程首次查询”的 Jieba 冷启动主导（546.5 vs 550.0 ms），不能用来比较策略。
2. **只索引 P0+P1（outline+注释、不要代码正文）是本次最划算的配置**：89,769 B = plain 的 **31.7%（−68.3%）**、outline 的 **60.0%（−40.0%）**，而七项质量指标与 outline **逐项相同**（0.7500 / 0.8214 / 0.9286 / 0.7941 / 0.1643 / 0.0929 / 0.0000）。
3. **两条过滤规则各自都有效，且都没有伤质量**：以 `none` 为基准，关键字规则单独 **−10.5%**、长度规则单独 **−4.7%**、两条同开 **−13.9%**；质量上两条同开时 `recall@10` 由 0.8929 升到 **0.9286**（删噪声反而多召回 1 例），长度规则单独开时 `recall@5` 由 0.8214 升到 **0.8571**、`precision@5` 由 0.1643 升到 **0.1714**，四个变体 `recall@1` 均为 0.7500。

### 5.5 诚实留白（哪些结论只在小目录成立）

- **小目录边界**：37 个 C# 文件 / 237 KB。全仓规模、跨语言分层（TS/Markdown）、含文档语料上的结论**未测**。
- **单次运行**：表中每个数字只跑一次，**没有方差**；`repetitionStable=True` 只说明同一 run 内重复调用结果一致，不等于跨进程稳定。
- **冷样本语义**：“本进程内该查询的首次调用”，不是跨进程 / OS 页缓存冷启动。
- **P2 无贡献的适用范围**：本次标注的期望命中都是“定义该符号的那个文件”，符号名已由 P0 块覆盖 ⇒ 该结论**不应外推**为“代码正文无用”。要推翻它需要一批“只有正文能答”的标注（本次未构造）。
- **未测**：并发/多进程检索、增量路径（两策略都是全量重建）、向量与混合（U4-1b）、BFS vs DFS（C3）、统一忽略合同（U4-2）。
- **plain 的文档数**引擎不报告（只有文件数）⇒ 表中留空，不用估算值充数。
- **风险**：`Source/PuddingCodeIndex/Contracts/ICodeIndexer.cs` 在本刀期间被**外部工作流并发修改**（`git status` 显示 ` M`）；索引与测量都发生在其当前工作区版本上，故严格说结论绑定的是那一刻的目录内容（文件清单与字节数已记录：37 文件 / 237,586 B）。

### 6.3 结论（三条必答，每句两组数字）

**① 混合（RRF）是否优于任一单一策略？——是。6 项指标胜 5、并列 1（且那 1 项已是天花板）。**

- vs 全文：`recall@5` 0.8214 → **0.9286（+13.1%）**；`MRR` 0.7941 → **0.8295（+4.5%）**；
  `precision@5` 0.1643 → **0.3000（+82.6%）**；`precision@10` 0.0929 → **0.1750（+88.4%）**；
  `recall@10` 0.9286 → **1.0000（+7.7%）**；`recall@1` **0.7500 = 0.7500（并列）**。
- vs 向量：`recall@1` 0.3571 → **0.7500（+110%）**；`MRR` 0.5810 → **0.8295（+42.8%）**；
  `precision@5` 0.1786 → **0.3000（+68.0%）**；`recall@5` 0.8929 → **0.9286（+4.0%）**；`recall@10` **1.0000 = 1.0000**。
- **代价**：索引 2,060 → 41,253 ms（**20.0×**）、体积 0.143 → 5.787 MB（**40.6×**）、热 p50 3.545 → 48.827 ms（**13.8×**）。
- **机制**（case 0 `ICodeIndexer`）：全文把答案排第 1、向量排第 6；RRF 后答案回到第 1（1/61 + 1/66 = 0.0315 > 1/61 = 0.0164）。
- **增益不是“候选池更深”造成的**：`--fusion-depth 20`（与单策略同深度）下指标**逐项相同**。

**② 向量是否值得？——只作为融合伙伴值得；单独用不值得。**

| 轴 | 判定 | 数字 |
|---|---|---|
质量（单独） | ✗ | `recall@1` 0.3571 vs 0.7500（只有 **47.6%**）、`MRR` 0.5810 vs 0.7941（**−26.8%**）；裸标识符查询无语义信号 |
质量（作融合伙伴） | ✓ | 给融合带来 `recall@5` **+0.1071**、`MRR` **+0.0354**、`precision@5` **+0.1357**；`recall@10` 两侧均已 1.0000 |
体积 | ✗ | **4,378 B/块 vs 110.6 B/块（39.6×）**，主因 dim=1024 × float32 |
延迟 | ✗ | 热 p50 **41.236 vs 3.545 ms（11.6×）**，其中 66% 是查询嵌入 |
成本 | ✓✓ | 本地推理 **$0**（route 价 0/1M）；这是唯一“完胜”的轴，也是通常杀死远程 embedding 的那一轴 |

⇒ **向量不能替代全文（精确符号查找必须走全文面），但能显著提升融合**；是否值得完全取决于「本地免费 + 能否接受 40× 体积 / 12× 延迟」。
此结论**依赖 route 是本地零成本**，**不可外推**到远程 embedding。

**③ 本地向量与全文在延迟上差多少？——热 p50 11.63×（+37.69 ms）。**

- 热 p50 3.545 → 41.236（**+37.691 ms，11.63×**）；热 p95 6.311 → 56.813（**9.00×**）；热 p99 8.088 → 61.826（**7.64×**）。
- 拆项：140 次查询嵌入合计 3,819 ms ⇒ **≈27.3 ms/次**，占 41.236 ms 的 **66%**；其余 **≈13.9 ms** 是 1352×1024 暴力余弦 + 框架开销。
  ⇒ 要压延迟就压“查询嵌入”（缓存/更小模型），而不是优化余弦。
- **对“本地单条 393 ms”的更正**：本刀实测闲置后**首次**调用 **370 ms**，模型热后预检 **97 ms**，热态平均 **27.3 ms/次**。
  ⇒ 393 ms 是**冷/首调用**数字，与热态不可混用。

### 6.4 消融（参数写进报告，并用对照验证）

| 消融 | 结果 | 含义 |
|---|---|---|
`k=10` vs `k=60` | 7 项指标**逐项相同**，top-5/top-10 窗口 **28/28 逐位相同** | 本语料规模下 **k 完全不敏感**（k 相对候选池很小）|
`wVector=2.0`（wf=1） | 指标**整组塌回纯向量**（0.3571/0.8929/1.0000/0.5810/0.1786/0.1000）| 权重是**敏感旋钮**；1:1 是本次最好的配置 |
`fusionDepth=20` vs `100` | 指标**逐项相同** | 混合增益**不是更深候选池**造成的 |

### 6.5 花费：$0.000000（本地推理）

- 全部 HTTP 往返（索引 43+43、预检 3、查询 140×4 ≈ **650 次**）都指向 `http://127.0.0.1:1234/v1/embeddings`；**没有任何远程调用**。
- 资源池配置里该 route 的价格为 `0`/1M input tokens；服务自报 `usage.prompt_tokens = 0`。
- **诚实提醒**：LM Studio 的 `usage.prompt_tokens` **恒为 0** ⇒ 本地路径**拿不到真实 token 数**；
  若换远程 route（池内 `bigmodel-embeddings/embedding-3` = $0.0005/1M），费用必须按服务真实 token 计，而当前服务**不提供**该字段。

### 6.6 诚实留白（含“小目录边界”与“是否外推”）

1. **小目录边界**：37 个 C# 文件 / 237,586 B / 1,352 块。**全仓未测**；按 30.5 ms/块外推，全仓向量索引在时间上不可接受
   ⇒ **§6 结论不可外推到全仓**（全文侧的全仓实测仍是 §1 的 4,286.8 s / 837.8 MB）。
2. **单次运行、无方差**：两次向量构建的 embedding 耗时差 **1,911 ms（4.9%）**，**超过** Lucene 写入耗时（1,471 ms）
   ⇒ “混合索引比纯向量快 371 ms”**不构成任何证据**（应视为相同量级）。
3. **标注集粒度太粗**：28 例、每例 1 个期望文件 ⇒ 分不出 `wv=2` 与纯向量（尽管 top-10 窗口 25/28 不同）
   ⇒ **指标相同 ≠ 排序相同**；下一刀要比“排序质量”需多期望文件或 nDCG 类指标。
4. **查询嵌入未缓存**（故意）：缓存会把主项藏起来，使向量与全文的延迟差看起来比真实小。
5. **暴力余弦的规模边界未测**：**没有**引入 ANN（近似索引会把自身召回损失混进“评估 embedding”的结论）。
6. **向量存储未量化**：4,378 B/块中 4,096 B 是向量本体，int8 理论可降到 ~1,024 B/块（**未实测**）。
7. **融合结果路径拼写不统一**（Lucene 回绝对路径、向量回仓库相对路径）：**指标不受影响**（已实测归一化匹配），
   但用户可见的融合列表不一致 ⇒ 探针侧呈现层小缺陷（未修）。
8. **未测**：并发/多进程检索、增量索引、跨语言（TS/Markdown）分层、BFS vs DFS、LLM 重排、远程 embedding 真实费用、查询长度对嵌入耗时的影响。

### 6.8 对后续切片的直接影响

- **向量侧值得进生产路径，但只能作为融合的一方，且必须配“本地 route 探测 + 不可达即失败”**（ADR-089 索引服务与库管理 §6 的降级语义已给出口径）。
- **体积是首要障碍**：5.64 MB / 1,352 块 ⇒ 外推到 28,208 文件的全仓规模约 **100+ MB 量级**（按线性外推，**未实测**），
  远超单项目 1 GB 体积护栏之前就已难管理 ⇒ **U4-3（分层索引落地）必须把“向量侧只索引 P0/P1”与“量化”作为前置**。
- **精度侧**：本刀证明“混合 > 单一”，但**标注集粒度**是下一个瓶颈 ⇒ 要提升可信度，先扩标注集（多期望文件 + 引用/实现类查询）。
