# 任务规划与实施分工及存量看板施工方案

日期：2026-09-20。状态：**实施设计已登记，未声明下述新增机制已实现或部署**。

本次授权是整理任务和更新设计。任务状态来自 External Task API；源码定位与配置核实属于只读审查。源代码、部署和真实产品验收分别记录，不能互相替代。全量任务逐卡处置见 [看板整理台账](../Reports/任务看板全量整理台账-2026-09-20.md)。

上位设计保持 ADR-072/074、ADR-087、ADR-092 第二版；本文补充 Task 侧施工合同和现有任务实施顺序，不重建 Goal 引擎。

## 1. 已确认的问题与本次决策

基线有 271 条任务：199 Backlog、4 Ready、2 InProgress、15 Completed、51 Archived。大量 Backlog 的更新者为 `task-restore:db-recovery-2026-09-20`。这是恢复后的任务集合，Backlog 不证明“代码尚未实现”，旧 Completed 也不证明当前构建的产品验收。

源码观察：

- `TaskExecutionPlanCompiler.TryCompile` 为 taskType 生成固定 Explore/Plan/Change/Test/Review 阶段；Objective 是通用句子，不能替代文件、修改方法、错误处理和测试断言。
- `TaskBacklogRefinementEvaluator.EvaluateAsync` 检查描述、验收条件、类型和兼容 Agent；目前没有检查描述是否包含足够的实施决策。
- `TaskAgentRouteMatcher.Evaluate` 把任务级 provider/model 与 Agent 偏好匹配。把整卡硬绑昂贵模型不能实现“规划贵、实施便宜”的阶段分工，反而可能使候选为零。
- `GoalSettlementStore.TryReplanBoundPlan` 的 `boundPlan.Plan.PlanVersion++` 与 `ExecutionCommandReader.MapAsync` 的 `PlanVersion != CurrentPlanVersion` 冲突。这是本轮定位到的直接写入点；不是只根据数据库数值推测。
- 本机配置的 fastrouter 模型是 `gpt-6-astra` 和 `gpt-5.6-sol`，没有 `gpt-6`。注册不等于模型请求、工具调用和子代理都已验收。

决策：困难问题先产生经校验的实施合同；PuddingAgent 的实施模型只执行已定案的切片。普通局部修复可走轻量计划；跨模块状态机、事务/租约、权限、协议、证据冲突必须进入规划。不能仅凭模型自评“简单”绕过这些硬条件。

## 2. 规划产物与模型分工（现有任务 b7cdc9a1、cec285c3、54ee0c2a）

### 2.1 产物合同

在 `Source/PuddingCore/Scheduling/` 新增 `TaskImplementationBrief.cs`（拟新增），作为 Task 的版本化实施附件。利用 `TaskPlanRunEntity` / 现有 TaskPlan 存储保存附件及哈希，不把 Markdown 当可写生命周期；不要求独立 Goal 创建 TaskPlan。

```csharp
// 拟议合同；字段的存储接线属于后续实现。
public sealed record TaskImplementationBrief(
    string TaskId, int TaskVersion, string InputIdentity,
    IReadOnlyList<Requirement> Requirements,
    IReadOnlyList<Decision> Decisions,
    IReadOnlyList<ChangeSlice> Slices,
    IReadOnlyList<CheckSpec> Checks,
    IReadOnlyList<DependencyRef> Dependencies,
    IReadOnlyList<string> EscalationConditions);
// ChangeSlice 必须包含 id、dependsOn、文件/符号、允许修改范围、
// 行为前后对照、错误/取消处理、产物、关联 requirementIds/checkIds。
```

`InputIdentity` 包含相关源文件原始字节哈希、依赖清单及适用配置摘要；不保存秘密。采用 `GoalCheckInputIdentity` 的输入身份原则，不能仅用 HEAD、任务 version 或报告时间代替源码身份。

拟新增 `TaskImplementationBriefValidator`（Platform Scheduling）：纯校验，无模型、无工具。拒绝未知 requirement/check 引用、依赖环、越过执行根的路径、没有失败断言的高风险切片、缺失必要部署义务。每项用户要求至少映射一个切片或验收项；“build/test 通过”不能自动覆盖业务要求。

保存时 CAS 核对 TaskVersion；合同冻结后改需求须显式修订并失效受影响检查。Task 状态/进度版本会正常增长，不能把所有元数据版本变化都判为需求变化：执行中按冻结的需求内容哈希及适用输入身份判断有效性。

### 2.2 路由规则

| 阶段 | 默认策略 | 输出与权限 |
|---|---|---|
| 取证 | 已授权的快速、低成本路由 | 文件/运行事实与未知项；只读 |
| 规划 | `fastrouter/gpt-5.6-sol`，先通过 §4 的实际调用门禁 | 实施合同；不直接部署或改业务数据 |
| 困难决策 | 在允许模型与预算内使用 `fastrouter/gpt-6-astra` | 解决明确冲突、修订合同；保留升级理由 |
| 实施 | 已获授权、按同类任务验收表现选出的低成本路由 | 按切片改代码、提交、给证据 |
| 检查 | 确定性测试优先；需要语义判断才使用有界只读模型 | 对必要条件逐项判断，不自授完成权限 |

拟新增 `TaskPhaseRoutePolicy` 于 Platform Scheduling；先按能力、上下文、协议、用户允许集合、成本上限筛选，再比较同类成功率和每个成功单元成本。`FileLlmResolver` 继续只负责解析有效路由；不在 resolver 隐藏重试/降级/规划决策。

冻结 `phase/provider/model/reason/policyRevision/healthObservedAt` 到 Task 执行附件和运行证据。Task 级 requiredModelId 是整个任务的硬约束，不能偷用为 Plan 阶段偏好。`allowAgentFallback` 只表示 Agent 替代许可，不表示可任意换模型。

不要在这次看板整理中开启 autoDispatch、改现有授权预算、强制指定 Agent 或触发 run-now。路由上线先 shadow；只有同类质量合格才比较价格与速度。旧卡中 42/105 tok/s 等数字只是历史观测，不当作今天的健康真值。

### 2.3 实施模型遇到困难的处理

实施输入为本切片合同、必要上下文、上次检查摘要和产物引用；不灌入全部旧报告。以下情况提交结构化 `NeedsReplan(reason, attemptedChanges, evidenceRefs, unchangedInputIdentity)`：

1. 事实与合同假设冲突，或需要跨出允许修改范围；
2. 同一输入、同一失败原因连续两次修复仍无新证据；
3. 需要改变权限、事务边界、协议或用户验收义务；
4. 依赖不可用：持久等待，依赖未改变时不继续调用模型；
5. 即将耗尽已授权输出/费用预算：暂停，不能自动扩额。

平台按 `task/contractRevision/failureFingerprint` 去重升级，保存已用规划次数；重启、换措辞、重发任务不能清零。同一合同最多一次自动重新规划，仍失败就保持可解释的暂停/待决定。该阈值是规划升级策略，不是把所有正常任务限制为两轮；已有 600 正常轮支持及用户授权预算继续有效。

### 2.4 施工顺序与测试

1. `TaskImplementationBrief` + validator + schema/覆盖率负例；先不接生产派发。
2. `TaskBacklogRefinementEvaluator/Store` 接入合同引用；缺合同的高复杂度任务返回 `implementation_brief_required`，不假装 Ready。
3. `TaskExecutionPlanCompiler` 读取已冻结合同生成任务切片；通用阶段不是独立实现方案。保留简单任务轻量路径。
4. `TaskPhaseRoutePolicy` 接入真实调用边界；已有 `TaskAgentRouteMatcher` 仍负责 Agent 资格，不能重复实现两套路由权限。
5. Runtime 接入升级事实，Task/Scheduler 处理持久等待；Goal 只按 ADR-092 消费事实，不承担路由/步骤推进。

新增测试建议：`TaskImplementationBriefValidatorTests`（漏要求、环、路径越界、旧版本）、`TaskPhaseRoutePolicyTests`（Plan/Change 不同路由、显式模型限制、费用不足、服务不可用）、一次 SQLite 重启后升级去重集成测试。产出 plan Skill 只作为该合同的编写助手，不能让 Skill 的自然语言成为绕过服务端校验的入口。

## 3. P0：计划版本循环与 Goal 完成（5413ce1b、b849ef8d、dc0ac9a8）

### 3.1 先修版本混用，不削弱门禁

2026-09-20 事故热修已落源码：`PlanVersion` 保持编译语义，`PlanRevision` 从 1 开始，仅在现有一次性调度重试分支递增；查询 API 与熔断事件同时提供两个字段。该分支只改节点调度状态，不改冻结预算、内容和依赖，因此不重写 fingerprint/binding；既有 Task version、reservation fence、节点顺序和 fingerprint 校验继续生效，PlanRevision 本身不是执行 fence。下段“Task 所属服务修订合同并更新 fingerprint”的要求针对真正改变实施合同的未来重规划，仍待 ADR-092 切换，不能与本次调度计数修复混为一谈。

本次回归与停机修复规程见[计划语义版本与重规划修订分离修复](../Reports/计划语义版本与重规划修订分离修复-2026-09-20.md)。库启动只幂等补列，不自动把历史版本改为 2；原始编译绑定、预算、逐次 replan 事件均匹配后，才允许受控离线修复。

文件：`Source/PuddingPlatform/Services/Goals/GoalSettlementStore.cs` 的 `TryReplanBoundPlan`；`Source/PuddingPlatform/Services/ExecutionCommandReader.cs` 的 `MapAsync`；`TaskExecutionPlanContracts.cs`；`TaskPlanRunEntity.cs`；`TaskGoalDispatchTransactionStore.AddExecutionPlan`。

本次冻结选择：**保留 PlanVersion 作为语义版本；重新规划的修订号使用独立 PlanRevision，禁止递增 PlanVersion。** 不把校验改为 `>= 2`，也不拿 schema_version=1 冒充语义版本2。新编译写 `PlanVersion=CurrentPlanVersion`、`PlanRevision=1`。修订在 Task 所属服务进行，更新 fingerprint、binding 和后续 command metadata；过期命令由 fence 拒绝。ADR-092 切换时删除 Goal 中的步骤重排分支，不能给它继续扩建职责。

回归顺序：编译→启动→制造无进展→一次重规划→构造后续 command→Reader 成功；连续修订到9而 semantic 恒2；旧semantic1、未知semantic仍拒绝；重复事件不重复升级；无进展重规划预算不因 revision 变化清零。覆盖原27次重复失败场景，不能只测一个字段赋值。
