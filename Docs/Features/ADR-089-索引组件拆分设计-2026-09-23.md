# 索引组件独立化（PuddingCodeIndex）设计

日期：2026-09-23。状态：**Proposed（待 U3-A 验收后执行）**。
上游：`Docs/Features/ADR-089-前置设施施工计划-2026-09-23.md` §2（U3）、`Docs/07架构/103ADR-089Agent统一检索与渐进展开工具链ADR.md`。

## 0. 动因（用户裁定 2026-09-23）

> 「我建议把索引作为独立的组件，方便我们的测试和保持架构的整洁性。」

**实测的现状问题**（非推断，逐项已核）：

| 事实 | 证据 |
|---|---|
`PuddingCodeIntelligence` 一个程序集里混了 **5 类关注点** | 索引管线 / SQLite 存储 / 语言索引器 / 8 个 outliner / 查询+LSP |
存储单体 44.7 KB | `Storage/SqliteCodeIndexStore.cs` |
语言索引器 51.9 KB | `RoslynCSharpIndexer.cs` 24.0 KB + `TypeScriptIndexer.cs` 27.9 KB |
该程序集**只有包依赖、零工程依赖**（是叶子） | `PuddingCodeIntelligence.csproj` 无 `ProjectReference` |
消费方 | `PuddingRuntime.csproj:32` 引它；`PuddingCodeIndexer.Cli.csproj` 引它 |
**仓库无 `.sln`** | 全仓 `*.sln` 仅 `external/github.hyfree.GM/` 下 1 个无关文件 ⇒ 新增工程**只需 csproj + 引用**，无需改解决方案 |

**可检验的收益**（不是"感觉更整洁"）：
1. **管线测试不再被迫加载 Roslyn**。`Microsoft.CodeAnalysis.*.Workspaces` + `Microsoft.Build.Locator` 必须在**任何 Microsoft.Build 类型被加载前**注册一次（进程级全局状态），是并行测试宿主上的经典脆弱点。把管线（watcher / 队列 / 防抖 / scope 状态）与语言索引器分到不同程序集后，管线测试的进程里**不会出现 Roslyn/MSBuild**。
2. **依赖方向可机器强制**：新程序集不得引用 `PuddingCodeIntelligence`（无反向引用），这是一条可被编译期检查的规则，而不是文档约定。
3. **可单独打包**：`PuddingCodeIndexer.Cli` 未来可只依赖索引组件，不必拖入 outliner/LSP/查询层。

## 1. 目标结构（本刀新增 **1** 个工程）

```
PuddingCodeIndex                       ← 新增（索引组件本体，叶子）
   Contracts/    CodeFileRecord, CodeIndexContracts, CodeIndexScopeContracts,
                 CodeSymbolContracts, CodeReferenceRecord, CodeRelationContracts,
                 CodeWorkspaceDescriptor, ICodeIndexStore, ICodeIndexer,
                 ICodeIndexScheduler, ICodeIndexScopeRegistry, ICodeIndexScopeResolver
   Pipeline/     U3-A：IndexChange, CodeIndexScopeState, CodeIndexChangeQueue,
                 CodeIndexChangeBatch, CodeIndexWatcher, CodeIndexChangeCoalescer
                 U3-B/C/D：待办账本 / 增量提交 / 校准 / GC / 运维状态
   Storage/      SqliteCodeIndexStore
   Services/     CodeIndexScheduler, CodeIndexScopeRegistry, CodeIndexScopeResolver,
                 CodeProjectRegistry, CodePathIdentity, IndexExcludePatterns
   依赖：Microsoft.Data.Sqlite + Microsoft.Extensions.*.Abstractions  ← 无 Roslyn、无 Host/Runtime
        ▲
        │ ProjectReference
PuddingCodeIntelligence                ← 既有，瘦身为「语言智能 + 消费方」
   CSharp/ TypeScript/ (索引器，实现 ICodeIndexer)
   Outliners（8 语言）+ FileOutlinerRegistry
   Lsp/ + CodeQueryService（**消费者**：只读索引）
        ▲
        │ ProjectReference（原样）
PuddingRuntime.csproj:32 ───────────────┘
```

**为什么不一次拆三个工程**：`PuddingCodeIndex.Languages`（把 Roslyn/TS 索引器再独立）能带来额外隔离，但本刀主诉求（管线测试脱离 Roslyn）**已由上面这一刀满足**。按用户此前对 LSP 的裁定口径 —— **「B 起步、保留 A 的接口位」** —— 索引器继续留在 `PuddingCodeIntelligence` 内，但其实现经由 `ICodeIndexer` 接口被索引组件消费 ⇒ **日后若需要，可零调用方改动地再抽出 `PuddingCodeIndex.Languages`**。

## 2. 边界判定硬规则（避免逐文件争论）

1. **PuddingCodeIndex 不得引用 PuddingCodeIntelligence**（编译期强制）。任何移动后会产生反向引用的文件，**留在 Intelligence**。
2. **索引组件负责"维护索引产物"**：契约、存储、变更捕获、调度、校准、GC、运维状态。
3. **Intelligence 负责"生产与消费"**：语言解析（产出符号/引用的索引器）、outline、查询 facade、LSP 视图。
4. 依赖倒置：`ICodeIndexer` **定义在 Index**，**实现留在 Intelligence**（由运行时 DI 注入进索引维护驱动）。
5. 不确定的文件**一律留在 Intelligence**（保守侧），宁可少移不可留反向引用。

## 3. 施工顺序（硬门禁）

```
① U3-A 验收通过（独立核对 diff / 复跑测试 / 变异取红三份原始输出）
      ↓  必须先完成：U3-A 的 6 个文件此刻就在旧位置，验收对象是"子代理交付的那个状态"
② 抽取 PuddingCodeIndex（纯搬迁，**零行为变更**）：建 csproj → 移动文件 → 改 namespace
   → 加 ProjectReference → 建 PuddingCodeIndexTests 并迁移管线测试 → 提交
      ↓  门禁：搬迁前后测试必须同数同色（见 §4）
③ U3-B/C/D 一律**直接落在 PuddingCodeIndex**（不再往旧位置写）
```

**为什么不能与本刀并行**：U3-A 子代理仍在运行且正在跑 `dotnet build`/`dotnet test`；此刻移动它正在编译的输入，会让它的构建结果不可解释（失败无法归因）。**验收完再搬是唯一可归因的顺序。**

## 4. 验证门禁（零行为变更的证明）

| 检查 | 判据 |
|---|---|
搬迁前基线 | 记录 `PuddingCodeIntelligenceTests` / `PuddingRuntimeTests` / `PuddingPlatformTests` 的**通过/失败数**（含既有失败项，用于区分 pre-existing） |
搬迁后 | 三套件**通过数不减少、失败项集合不变** |
反向引用 | `PuddingCodeIndex.csproj` 的 `ProjectReference` 为空（或仅含允许项） |
新增依赖 | `PuddingCodeIndex` 的 `PackageReference` 不得出现 `Microsoft.CodeAnalysis.*` / `Microsoft.Build*` |
可编译 | `dotnet build` 全仓 exit 0 |
纯净性 | `git log --follow` 可追每个移动文件（用 `git mv` 而非删除+新建，保留历史） |
测试隔离（收益本身的证据） | `PuddingCodeIndexTests` 运行期**不加载** `Microsoft.Build.Locator`（以测试进程模块列表为准） |
