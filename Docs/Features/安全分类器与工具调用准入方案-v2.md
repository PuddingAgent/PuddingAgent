# 安全分类器与工具调用准入 —— 方案 v2（权威规格）

> **v2 取代 v1 的相应条目。** 上一版：`Jev自动审批与白名单自学习改造方案.md`（v1，其 §3.1 决策映射表、
> §2 中「人工兜底」取向、I2「失败折叠为 `DeferredDependency`」均**被本文件取代**；§1 现状锚点、§7 延迟实测仍然有效）。

## 0. 用户下达的需求（原话要点，逐条不可丢）

1. 实现**抽象的分类器/判断器**；系统**依赖该抽象**，**不要直接依赖 Jev**。Jev 分类器只是分类器的一个实现。
2. Agent 的工具调用行为**首先经过系统分类器**判定，一般使用**白名单 / 黑名单**；**命中白名单 → 放行**。
3. 若系统分类器的**黑白名单均未命中** → 使用 **Jev 分类器**：输入 **Agent 最近的轨迹 + 工具调用参数**，
   Jev 必须给出四选一判断：**单次放行 / 永久放行 / 单次拒绝 / 永久拒绝**；系统据此执行。
4. Jev **取代原 LLM 审批审计员的角色**，让审批动作更快。
5. 既有的**白名单与审批机制保留**，后期**人工可随时接入**。
6. 改造完成后，**审计角色下线**（`default.audit-agent.001` 退场）。
7. 硬性约束：
   (a) **Jev 服务商下线不得引起软件崩溃**；
   (b) **Jev API 下线时，系统自带的安全分类器仍能正常运行**，不因 Jev 下线或延迟受影响；
   (c) 用户可配置**不同的服务商与模型**作为安全分类器（后续）；
   (d) 除安全分类器外，Jev 还可用于**决策行为**（工具决策 / PuddingAgent 内部分类）。
8. **抽象分类器（便于后期更换其它分类器）在实际运行中是最终裁决者。**
9. **明确不要过度依赖人工确认**。理由（用户原话）：PuddingAgent 多为**无人值守**；
   LLM 分类器准确率**远高于**人类；不要期望人类去点击确认某个行为是否危险。

> **对 v1 的自我更正**：v1 把「人工为最终兜底」当作安全立场写入，**与用户第 9 条直接冲突，现予撤销**。
> 本方案中**人工不是必经环节**；人工的价值在于「事后可审计、可随时接入干预」，而非「事中必须点击」。

## 1. 判定优先级（不可交换）

```
工具调用
  │
  ├─ ① 黑名单命中        → 拒绝（永久规则 ⇒ DenyPermanent；单次规则 ⇒ DenyOnce）
  │                        *黑名单优先于白名单*（安全侧优先，防白名单挖洞）
  ├─ ② 白名单命中        → 放行（AllowPermanent 规则 ⇒ 直接放行，不调用 Jev）
  │
  ├─ ③ 均未命中 → 抽象分类器裁决（默认实现 = Jev 分类器）
  │       输入：Agent 最近轨迹（截断）+ 工具 id + 调用参数（截断）+ 工作目录 + shell
  │       输出：AllowOnce | AllowPermanent | DenyOnce | DenyPermanent
  │
  └─ ④ 分类器不可用（Jev 下线/超时/解析失败）→ 见 §4 降级契约
```

- ①② 为**确定性规则**，纯本地判定，**零网络依赖** ⇒ 直接满足需求 7(a)(b)。
- Jev 只在 ③ 被调用 ⇒ **Jev 的延迟与可用性只影响"未命中任何规则"的那部分调用**。

## 2. 抽象设计（不依赖 Jev）

### 2.1 抽象接口（放 `PuddingCore/Abstractions`）
```
enum ClassificationOutcome { Unknown, AllowOnce, AllowPermanent, DenyOnce, DenyPermanent }

record ClassificationVerdict(
    ClassificationOutcome Outcome,
    string Reason,
    string? ClassifierId,          // "system" / "jev" / 未来其它
    string? ClassifierModel,
    double? Confidence,
    IReadOnlyList<ClassificationRuleProposal>? RuleProposals)   // 永久裁决 ⇒ 提案落规则

record ClassificationRuleProposal(string Kind /* allow|deny */, string ToolId,
    string? Command, string? ArgumentsJson, string Reason, double? Confidence)

interface IToolCallClassifier
{
    string ClassifierId { get; }
    Task<ClassificationVerdict> ClassifyAsync(ToolCallClassificationRequest request, CancellationToken ct);
}
```
`ToolCallClassificationRequest` 至少含：`ToolId`、`ArgumentsJson`、`WorkingDirectory`、`Shell`、
`Identity`（agent/session/workspace）、`RecentTrajectory`（近期轨迹，**有界截断**）。

**抽象层不得出现任何 Jev 专有词汇**（不得有 `JevQuestion`/`Noul`/`choice` 等）⇒ 满足"不要直接依赖 Jev"。

### 2.2 实现
| 实现 | 位置 | 职责 |
|---|---|---|
`SystemRuleClassifier` | `PuddingRuntime/Classification/` | 读既有 allowlist/blacklist，命中 ⇒ 直接返回；**不命中返回 `Unknown`**；**零网络** |
`JevToolCallClassifier` | `PuddingRuntime/Classification/` | 依赖 `IJevDecisionService`；组装 §1③ 输入 ⇒ 四选一；不可用按 §4 降级 |
（后续）`<其它厂商>ToolCallClassifier` | 同目录 | 满足需求 7(c)：只换实现，不改抽象与调用方 |

> 复用性：同一抽象也供需求 7(d) 的**非安全决策**使用（如"这个工具该不该被选中""该走哪条分支"），
> 因此抽象命名用 `ToolCallClassifier` 之外的通用名亦可；**本方案先落地工具调用准入场景**。

## 3. 四选一的语义与落库

| 输出 | 本次调用 | 对永久规则的影响 |
|---|---|---|
| `AllowOnce` | 放行 | 不写规则 |
| `AllowPermanent` | 放行 | 写入 **allow 规则**（`ClassificationRuleProposal`） |
| `DenyOnce` | 拒绝 | 不写规则 |
| `DenyPermanent` | 拒绝 | 写入 **deny 规则** |

**永久规则的强制属性（不违背用户意图的前提下收紧）**
- **可溯源**：记录来源（哪次调用 / 工单 id / 分类器 id 与模型 / 置信度 / 理由 / 时间）；
- **可撤销**：提供撤销入口（含 CLI/工具面）；
- **尽窄**：`Command` 用**精确文本**；含 shell 元字符或通配符时**拒绝落规则**，退化为 `AllowOnce`/`DenyOnce`；
- **不可越权**：`DenyPermanent` 规则**永远优先于** allow 规则（§1 ①优先②）。

## 4. 降级契约（需求 7(a)(b) 的落地）

| 情形 | 行为 |
|---|---|
Jev 端点不可达 / DNS 失败 / 证书错 | 捕获**全部**异常，**绝不冒泡**至调用方；返回 `DenyOnce`（§4.1） |
Jev 超时（建议 `ClassifierTimeoutMs = 3000`） | 同上；记录超时审计事件 |
Jev 返回非 2xx / 无 answers / 解析失败 | 同上；`Reason` 写明具体失败码 |
Jev provider 未配置（资源池无 `jev`） | 同 7(b)：**系统分类器照常工作**；未命中时应答策略见 §4.1 |
分类器实现为系统规则 | **完全不受 Jev 影响**（无网络调用） |

### 4.1 「Jev 不可用且规则未命中」的默认应答
- **默认 `DenyOnce`**（fail-closed），**且不写永久规则** ⇒ 避免一次故障污染长期策略。
- 可配置 `ToolApproval:Classifier:OnClassifierUnavailable` = `deny_once`(默认) | `allow_once` | `defer`。
- **不引入「必须人工点击」**：`defer` 仅表示"本次不放行、留待重试/人工择机介入"，不是必经流程（符合第 9 条）。
- 崩溃防护：分类器调用外层包 `try/catch(AggregateException|Exception)`；超时用**独立 CTS**，不继承调用方无限等待。

## 5. 与既有机制的关系（需求 4/5/6）

- **保留**：既有 `IToolApprovalService`（工单）、allowlist 存储、`request_tool_approval` 工具、
  人工审批入口 ⇒ 需求 5。
- **替换**：决策来源由 LLM 审批评审器（`LlmToolApprovalReviewer`）改为**抽象分类器**（默认 Jev）⇒ 需求 4。
- **下线**：`default.audit-agent.001` 的审计角色（模板/配置）在改造验收后停用 ⇒ 需求 6。
  ⚠ 属**另一个 Agent 的配置**，须单独作为可回滚变更执行并留证；本方案只登记为后续动作，不擅自删除。
- 旧 `LlmToolApprovalReviewer` **保留代码 + 开关可切回**（便于对照与回滚），但**默认不启用**。

## 6. 验收标准

1. **抽象隔离**：`PuddingCore` 侧的抽象与调用方**不出现**任何 Jev 专有类型/词汇
   （用 grep 证明：抽象文件与调用链中无 `Jev`）。
2. **零网络快路径**：黑/白名单命中时，**不产生任何 HTTP 调用**（测试用 fake 计数断言 = 0）。
3. **四选一全覆盖**：四种输出各有一条用例，且 `AllowPermanent`/`DenyPermanent` 正确产出/落库规则。
4. **不崩溃**：模拟 Jev 抛异常、超时、返回畸形 JSON、provider 未注册 —— 四种情形下**调用方不抛异常**，
   且得到确定的判决（`DenyOnce`）。
5. **不受 Jev 影响**：在"Jev 完全不可用"的前提下，黑/白名单命中路径的**行为与耗时不变**（对照用例）。
6. **不依赖人工**：所有自动化路径**不产生**必须人工确认的阻塞态（无 `NeedHuman` 强制阻塞）。
7. **可更换**：新增一个假分类器实现（`FakeClassifier`）即可替换 Jev，**调用方零改动**。
8. 构建 0 error；既有测试不回归；文档/code_map 同步。

## 7. 明确不做

- 不删除既有审批/白名单机制（需求 5）。
- 不在本方案内删除 `default.audit-agent.001`（需求 6 的"下线"作为独立可回滚变更，登记为后续动作）。
- 不实现前端 UI。
- 不把「人工确认」设为必经环节（第 9 条）。
- 抽象层不引入任何具体厂商词汇。

## 8. 新增需求（用户第二轮，2026-09-20）

用户原话要点：

1. 系统选定的安全分类器（如 Jev）**故障时**：
   ① **前端界面给予明显提示**；
   ② **Agent 本身可以探查安全分类器的状态**，或**请求安全分类器**以便判断和决策；
   ③ Jev 只是其中一种实现，**请不要直接依赖 Jev 或 Jev API**；
   ④ **1 s 延迟也挺快**（LLM 思考通常数秒）；且系统分类器应**缓存 Jev 的分类结果（指永久授权）**，
      以加速判断、避免每次工具调用都请求 Jev；
   ⑤ 请求 Jev 需给出**背景知识**（工具调用之前 Agent 在做什么/思考什么）+ **分类问题**
      （单次拒绝 / 永久拒绝 / 单次允许 / 永久允许）；**Jev 返回各分类的可信度**。
   ⑥ 审计角色去留 —— 请我决策，见 §9。

### 8.1 对 §7.4 第 1 条的**放宽与更正**

先前把「避免每次调用 Jev」当作**生存必需**（基于"~1.1 s 不可接受"的假设）。用户明确 **1 s 可接受**
⇒ 更正为：**缓存是效率与稳定性优化，而非生存必需**。超时预算仍设上限，但理由改为"不无限等待"。
（注：实测 ~1.1 s 的结论不变；变的是它对设计的重要性判断。）

### 8.2 分类器健康与可探查性（需求 ①②）

抽象层新增**厂商中立**的健康面（**以下为 2026-09-21 与实现对齐后的真实契约**，依据 `Source/PuddingCore/Classification/ToolCallClassification.cs`）：

```csharp
enum ClassifierHealth { Unknown, Healthy, Degraded, Unavailable }

sealed record ClassifierStatus
{
    required string ClassifierId;       // 分类器稳定标识（作为**数据**出现，不是硬编码的厂商名）
    required ClassifierHealth Health;
    string? Detail;                     // 人类可读补充（最近一次失败原因 / 降级原因）
    int ConsecutiveFailures;            // 连续失败次数（成功一次即清零）
    DateTimeOffset? LastCheckedAtUtc;   // 从未探测为 null
    double? LastLatencyMs;
}

interface IClassifierHealthReporter { IReadOnlyList<ClassifierStatus> Snapshot(); }
```

> **契约边界（2026-09-21 裁定，供 S6b 实现遵守）**：`Snapshot()` **就是**前端健康面所需的全部——
> §8.2 / §14.9.2 要求前端展示的是**健康档位**（`Degraded`/`Unavailable`）与原因说明，
> 两者都在 `ClassifierStatus` 里。per-key 连续 deferred 计数与退避档（`retry_after_ms`）属
> **Agent 侧诊断**，只由 `classifier_status` 工具输出，**不进前端契约** ⇒
> **不给 `IClassifierHealthReporter` 追加成员**（避免无必要的接口变更）。
>
> 勘误：本节原字段名 `LastSuccessUtc` / `LastFailureUtc` / `LastErrorCode` / `Model` 与实现不符，
> 已按实现修正；其中 `Model` 亦不符合“厂商中立”取向，实现以 `Detail` 承载说明。

- **Agent 侧工具**：`classifier_status`（只读探查）+ `classifier_ask`（把某个判断问题交给分类器，
  得到四选一与逐分类可信度）⇒ 满足"请求分类器以便判断和决策"，并复用需求 7(d) 的非安全决策用途。
- **前端侧**：暴露**只读**健康 API 供 UI 显示**明显提示**（前端改动见 §10 D7）。
- **硬性要求**：健康状态必须**服务端权威上报**，**不得由前端推断**（与既有"服务端权威"原则一致）。

### 8.3 缓存语义（需求 ④）

- 缓存对象 = **永久授权 / 永久拒绝的结果**（即已落地的规则），**不是**某次调用的临时结论。
- 命中缓存 ⇒ **完全不请求 Jev**（§1 的 ①② 已经是零网络路径）。
- 缓存键 = `ToolId` + `ArgumentsHash` + `WorkingDirectory` + `Shell`（与 §4 一致）；
  **不做前缀/通配泛化**（§3「尽窄」）。
- 因为缓存即"规则存储"，所以**必须可撤销、可溯源**（§3）；TTL / 周期复核登记为后续增强。

### 8.4 Jev 请求载荷（需求 ⑤）

- `state` 必须含**背景知识**：Agent **最近轨迹**（最近若干步的工具调用 + **思考/推理摘录**，有界截断）、
  当前工具 id 与参数（截断）、工作目录、shell、身份、**命中的既有规则摘要**。
- `questions`：
  - 主问题（**choice，4 选项**）：`allow_once` / `allow_permanent` / `deny_once` / `deny_permanent`；
  - **逐分类可信度**：对四个分类各问一个 **`noul`**（校准 0..1）。
- **裁定规则（必须用上可信度）**：
  1. 取逐分类可信度的**最高者**作为结论；
  2. 若结论属**永久**类 ⇒ 要求其可信度 ≥ `PermanentConfidenceThreshold`（默认 **0.90**）
     **且** 相对其**对偶单次类**保持领先边际；否则**降级**为对应**单次**类
     （永久放行 → 单次放行；永久拒绝 → 单次拒绝）；
  3. 单次类无此约束。
  ⇒ 既满足"四选一 + 可信度"，又避免以低置信写入永久规则。

## 9. 决策：**移除审计角色**（我的结论）

用户给出两案请我决策：**A** = 保留审计员但改为周期性批量异步维护黑白名单；**B** = 完全移除审计员，

2. **与"最终裁决者是分类器"一致**：方案 A 实质是让第二个模型对第一个模型的结论做**二次裁定**，

## 11. 权威归属的正式表述（用户第三次明确，**更正 §1/§2 并撤销 I1**）

用户原话：

> **「安全分类器拥有最终否决/放行权（包括覆盖 deny），Jev 安全分类器是安全分类器的其中一个实现。
> 未来，我们会实现更高级和可靠的分类器。」**

### 11.1 更正内容

- **权威在抽象层，不在 Jev**：最终裁决者是**安全分类器抽象**（即 `IToolCallClassifier` 这一层），
  **不是 Jev**，也不限任何单一实现。Jev 只是当前实现，未来更高阶/更可靠的分类器可直接替换。
- **分类器可覆盖 deny**：§1 曾把「① 黑名单命中 ⇒ 拒绝、且**不调用分类器**」写成不可交换的优先级，
  与本次表述**直接冲突**，现**更正**。新语义：
  - 系统规则（白/黑名单）与既有确定性防火墙产出的都是**候选结论（provisional）**，**不是终局**；
  - **分类器是终局**，对候选结论拥有**确认或覆盖**权，**包括覆盖 deny**。

### 11.2 ⚠ 撤销 v1/v2 的不变量 I1

> **I1（deny 优先且命中即不调用 Jev）已撤销。**
> 该不变量源自「模型不应是唯一授权者」的行业实践判断；用户已明确要求分类器**可覆盖 deny**，
> 故 I1 与用户意图冲突，**作废**。保留其精神的部分改述为 §11.3 的**防循环**规则。

### 11.3 覆盖机制（既落实覆盖权，又不违反「避免每次都调用 Jev」）

```
① 候选结论按来源区分：
   - 来自「分类器自身的永久规则」（即分类器此前对同一缓存键已作出永久裁决并落库）
     ⇒ 该结论**本身就是分类器的裁决**，**不再重复调用**分类器（缓存命中，不构成绕过权威）。
   - 来自「系统规则」（人工配置的白/黑名单）或「既有确定性防火墙」
     ⇒ 视为**候选**；候选为 deny 时**必须给分类器一次覆盖机会**（否则覆盖权形同虚设）。
② 覆盖**只能由分类器执行**；任何其它组件不得覆盖分类器的结论。
③ 每次覆盖必须落审计事件：原候选、覆盖后结论、分类器 id / 模型 / 逐分类可信度、理由、时间。
④ **防循环**：分类器自身产出的 deny 在缓存命中时**不再回调**分类器
   （对应 ①-1），避免「分类器否认 → 再问分类器 → 再否认」。
⑤ 白名单命中仍走**零调用**快路径（用户第 4 条：缓存加速、避免每次都请求 Jev）。
```

**效率含义**：分类器调用量由「被 deny 的调用数」决定，而非全部工具调用；
白名单命中 **零调用**。该量级必须实测（见 §12），不得凭推测。

### 11.4 与「缓存」不矛盾

缓存的是**分类器的永久裁决**（= 分类器已表过态的结论），因此缓存命中**不是绕过分类器权威**，
而是**复用分类器权威**。

### 14.5 判定与后果

**`classify`**
- 返回：`outcome`（`AllowOnce|AllowPermanent|DenyOnce|DenyPermanent`）、`confidence`（逐分类）、
  `reason`、`classifier_id`、`classifier_model`、`latency_ms`；
- 永久类 ⇒ 交给 `ClassificationRuleCurator`（幂等 / 去重 / **冲突 deny 胜** / 尽窄 / 溯源）落规则，回传 `rule_id`；
- 单次类 ⇒ **不落规则**；
- 分类器不可用 ⇒ 返回 `deferred`（**不落规则、不授予完全访问**）。

**`full_access_request`**
- **必须**走出题单 + 分类器裁决；只有 `AllowOnce` / `AllowPermanent` 才授予；
- 授予 = 对 `agent_instance_id` 生效 `RuntimeExecutionMode.Yolo`（经 `IAgentAccessLevelService`）；

**`rules_update`**
- `add` ⇒ 落规则（`Effect=Allow|Deny`，带溯源：分类器 id / 模型 / 可信度 / 理由 / 身份 / 时间）；
- `disable` ⇒ **不硬删除**，置 `Status=Disabled`（保留审计链，符合 append-only）；
- 尽窄校验：命令含 shell 元字符或通配符 ⇒ **拒绝落永久规则**（退化为单次）。

### 14.6 语义边界（不可越）

### 14.9.1 降级默认值定稿：`deferred`（**已实证**，非推断）

| 证据 | 事实 |
| --- | --- |
| `Source/PuddingRuntime/Tools/Platform/PuddingToolRegistry.cs:661` | `var dependencyWait = fwDecision.Disposition == ToolApprovalDecision.DeferredDependency;` |
| 同上 `:663` | `dependencyWait ? 428 : 403` ⇒ 依赖等待与硬拒绝**使用不同退出码** |

### 14.9.2 降级退避与重试风暴防护（新增要求）

分类器不可用时，Agent 可能立刻重试同一调用 ⇒ 造成对已故障端点的请求风暴。要求：

- 以 `(tool_id, args_hash)` 为键记录**连续 `deferred` 次数**；
- 返回体必须携带 `retry_after_ms`（= `UnavailableBackoffBaseMs × 2^(n-1)`，封顶 `60_000`）；
- 同一键达到 3 次连续 `deferred` ⇒ 该分类器健康面置 `Degraded`（再达 5 次 ⇒ `Unavailable`），供 §8 前端提示与 `classifier_status` 工具读取；
- **不得**因退避把 `deferred` 改写成 `Denied`（ADR-091 §4.4 明令不得折叠）；
- 该计数**仅在分类器成功返回后被重置**，避免「偶发失败」永久降级。

## §14.12 规则建模规范（S2 `ClassificationRuleCurator` 必读）

> 目的：把「Jev 说永久放行/永久拒绝」翻译成**确定性、可审计、可撤销**的规则数据。
> 本节是 S2 的实现依据；所有条目均为**可单测的判定**，不含模糊表述。

### 14.12.1 规则键（唯一键，**禁止通配**）

```
RuleKey = ( workspace_id, tool_id, subject, working_directory, shell )
```

- `subject`：
  - **命令类工具**（`shell`/`terminal_*`）⇒ **规范化后的精确命令串**（去首尾空白 → 内部连续空白折叠为单空格 → 路径分隔符统一为 `/`）；
  - **非命令类工具** ⇒ `arguments_hash` = 规范化 JSON（键排序、忽略空白）后的 **SHA-256**；
- **`*`、`?`、正则、路径前缀（`/repo/**`）、`startsWith` 语义一律不参与匹配**；
- 命中必须是**逐字节相等**。任何形式的泛化都视为「超出该次裁决的授权范围」，拒绝落库。

### 14.12.2 Effect × 来源 ⇒ 权威等级（本次决策的核心）

| Effect | 来源 | 权威 | 命中时是否调用分类器 |
| --- | --- | --- | --- |
| `Allow` | **Classifier（永久类）** | **终局** | **否** —— 复用分类器自身裁决（§11.3） |
| `Deny` | **Classifier（永久类）** | **终局** | **否** —— 防「否认 → 再问 → 再否认」循环 |
| `Allow` | `BuiltIn` / `Human` | 候选 | 否（快路径），但**分类器可覆盖**，覆盖必落审计 |
| `Deny` | `BuiltIn` / `Human` | 候选 | **是** —— 必须给分类器**一次**覆盖机会（§11.3 明令） |

> 关键区分：**由分类器产生的规则 = 分类器的裁决本身**（复用，不重问）；
> **由系统/人工产生的规则 = 候选人**（deny 候选必须让分类器有机会覆盖，否则 §11 的覆盖权形同虚设）。

### 14.12.3 幂等与更新

- 同键**同 Effect** ⇒ **更新既有行**，不新增：刷新 `Reason` / `Confidence` / `ClassifierId` / `LastSeenAtUtc`，`HitCount` 累加；
- 同键**首次**出现 ⇒ 新增；
- 既有 `IToolApprovalAllowlistStore` **无 upsert**（仅 `Save/Get/List`）⇒ 读改写逻辑放在策展器内（**不改 store 契约**）；
- **禁用不删除**：`Status=Disabled`，保留完整审计链。

### 14.12.4 冲突策略

- 同键同时存在 `Allow` 与 `Deny` ⇒ **生效 `Deny`**，并落 `RuleConflictDetected` 审计（须含两侧 `rule_id` 与来源）；
- 策略可配（§14.9 `AllowDenyConflictPolicy`），默认 `deny_wins`，**不建议改动**。

### 14.12.5 尽窄校验（命中任一 ⇒ **拒绝落永久规则**，退化为单次裁决）

1. 命令含 shell 元字符：`|` `&` `;` `>` `<` `` ` `` `$` `(` `)` `{` `}` 或换行；
2. 含通配符 `*` `?` 或正则元字符；
3. 命令是**裸解释器**（`bash`/`sh`/`pwsh`/`powershell`/`cmd`/`python`/`node`）或其 `-c`/`-e`/`-Command` 形式；
4. 参数含**无法静态求值**的占位符（路径/端口等由运行时变量决定）；
5. 目标路径**越出 workspace 根**；
6. `IsIrreversibleOperation=true` 且 `BackupTaken=false`。

> 依据：GuardFall 实测 —— 递归 deny 规则会被 `r''m`、`$IFS`、命令替换、`base64|sh`、破坏性 argv flag 等 5 类重写绕过。
> 与其落一条**看起来安全**的永久规则，不如退化为一次单次裁决。

### 14.12.6 溯源（每条永久规则必备字段）

`SourceClassifierId`、`ClassifierModel`、`OutcomeConfidence`、`Reason`、`CreatedByAgentInstanceId`、`CreatedBySessionId`、`CreatedByUserId`、`CreatedByTicketId?`、`FirstSeenAtUtc`、`LastSeenAtUtc`、`HitCount`。

⇒ 任一永久规则都必须能回答：**谁、依据什么、何时**批准了它。

### 14.12.7 撤销与过期

- `rule_op=disable` ⇒ `Status=Disabled`（§14.4）；
- 可选 `ExpiresAtUtc`：分类器给永久类但**置信度 < 0.95** 时，策展器**建议**设 30 天有效期；
- 启动时**不自动清理**过期规则，仅标记 `Disabled` 并落审计 ⇒ 保持可追溯（append-only 精神）。

### 14.12.8 与既有实现的接线（**不得破坏既有语义**）

- `InMemoryToolApprovalService.CheckAsync:345` 的 `FindMatchingAllowlistRuleAsync` **保持原样**（白名单快路径不变）；
- deny 判定**新增在分类器层**（S2/S3），**不修改** `CheckAsync` 既有判定顺序；
- 既有 **35 个** `JevToolApprovalReviewer` 用例 + `ToolApprovalCommandFirewallTests` 必须保持**全绿**。

### 14.12.9 可测性要求

`ClassificationRuleCurator` 必须**纯函数式可测**：时间经 `TimeProvider`/注入时钟获取，**无静态可变状态**；核心判定（去重 / 冲突 / 尽窄）除 store 外**不依赖任何外部 IO**。
⇒ 上述 §14.12.1–14.12.5 每一条都必须有对应的**离线**单测。

## §14.13 分类器管线（S3）：把「候选 → 覆盖」落成确定性求值序

> 目的：让**抽象分类器**成为终局裁决者（含覆盖 deny），同时保住「白名单命中零调用」的加速路径，
> 并让「依赖不可用」有唯一、可测的处理方式。本节是 S3 的实现依据。

### 14.13.1 形态：管线本身就是一个分类器

```csharp
public sealed class ToolCallClassifierPipeline : IToolCallClassifier
{
    public string ClassifierId => "pipeline";
    // 内部：IReadOnlyList<IToolCallClassifier> 规则类分类器（确定性，零网络）
    //       + IToolCallClassifier 仲裁分类器（默认 Jev 实现，可替换）
}
```

**关键约束**：管线**实现 `IToolCallClassifier`**，因此所有消费方（S4 门户、S5 完全访问、未来的 `IToolApprovalReviewer` 实现）
**只依赖抽象**，不知道 Jev、也不知道"规则"的存在。⇒ 这是"权威在抽象层"落到代码上的方式。

### 14.13.2 求值顺序（不可交换）

| 步骤 | 条件 | 结论 | 是否调用仲裁分类器 |
| --- | --- | --- | --- |
| ① | 确定性规则类分类器命中 `Allow` | **`AllowOnce` → 终局放行** | **否**（快路径，零网络） |
| ② | 确定性规则类分类器命中 `Deny` | **候选**（不终局） | **是** —— 必须给一次覆盖机会（§11.3） |
| ③ | 规则均未命中（`Unknown`） | 未知 ⇒ 需仲裁 | **是** |
| ④a | ③ 场景下仲裁不可用 | `Unknown` + `classifier.pipeline.arbiter_unavailable` | — （上层按 §14.7 转 `deferred`） |
| ④b | ② 场景下仲裁不可用 | `Unknown` + `classifier.pipeline.override_unavailable` | — |

**④b 的语义是本轮最关键的裁定**：候选 deny 遇上仲裁不可用时，
- **不得**折叠为 `Deny`（ADR-091 §4.4 明令：依赖等待不得折叠成拒绝/人工）；
- **不得**放行（不能因故障放行）；
- ⇒ 返回 `Unknown` 并携带专用原因码，由上层转 **`deferred`**。已实测 428/`DependencyWait` **非阻塞、不计熔断**（§14.9.1）⇒ 无人值守不会被卡住，只是这一次调用不被放行、可稍后重试。

### 14.13.3 仲裁结论的采纳规则

- 取仲裁返回的 `ClassificationOutcome`；
- **永久类置信度门槛**：`AllowPermanent` / `DenyPermanent` 需**逐分类可信度 ≥ 0.90**，否则**降级为对应单次类**（`AllowOnce` / `DenyOnce`）；
- 仲裁返回 `Unknown` ⇒ 等同 ④（按场景取 `arbiter_unavailable` / `override_unavailable`）。

### 14.13.4 覆盖审计（**必落**，不可省）

每次「候选 deny → 最终 allow/deny」的覆盖裁决必须落一条审计事件，至少含：
`原候选结论`、`覆盖后结论`、`分类器 id`、`分类器型号`、`逐分类可信度`、`理由`、`时间`、`身份四元组`、`工具 id 与参数`。

> 理由（我保留的一次性风险提示）：**可覆盖 deny 意味着覆盖路径本身是攻击面**——
> 若能污染轨迹/参数，就可能诱导覆盖。缓解手段是**强制留痕 + 覆盖可撤销**，而不是限制分类器的裁决权。

### 14.13.5 防循环与幂等

- **分类器自身产出的永久规则命中时，不再回调仲裁分类器**（§11.3）⇒ 避免「否认 → 再问 → 再否认」无限循环与额度浪费；
- 同一次调用的管线求值**只调用仲裁一次**（不得因子步骤重复请求）。

### 14.13.6 超时与降级

- 仲裁调用使用**独立 CTS**：默认 **3000 ms**（实测 Jev ≈1.1 s，余量 ≈2.7×）；
- 超时 / 异常 / 无 answers / 解析失败 ⇒ 一律按 ④ 处理（**捕获全部异常，绝不冒泡**）；
- 连续失败计数与健康面（`Degraded`/`Unavailable`）由分类器实现自身上报（§8.2）。

### 14.13.7 接线（S3 只做加法）

- 新增 `IToolApprovalReviewer` 的实现（如 `ClassifierToolApprovalReviewer`），内部只用管线；
- **不修改** `InMemoryToolApprovalService.CheckAsync` 的既有判定顺序（§14.12.8）；
- **不删除** `LlmToolApprovalReviewer`（保留为回滚路径）；
- **默认值翻转是单独一步**（`ToolApproval:Reviewer=llm → 分类器`），必须有独立提交 + 更新那条钉住默认值的守护测试，不得与实现混在同一提交里。

### 14.13.8 可测性

- 规则分类器与仲裁分类器**均可注入**（测试用假件，零网络）；
- 管线求值顺序、覆盖审计、永久类降级、不可用分支、防循环 **每条都要有离线用例**；
- 假件需能模拟：allow 命中 / deny 命中 / 未命中 / 抛异常 / 超时 / 低置信度永久类 / 返回 Unknown。

## §14.14 激活（S3c）：接线、默认值翻转的前置与回退

### 14.14.1 接线（S3c-1，只做加法）

  ⇒ 注册为 **`IToolCallClassifier` 单例**；消费方（门户、适配器）**只依赖抽象**；
- `ToolApprovalRuntimeOptions.Reviewer` **新增受支持取值**（如 `classifier`）；
  **本步不得改变默认值（仍为 `llm`）**；

  （分类器缺席时门户按契约降级为 `deferred`，不放行、不报错）。

### 14.14.2 默认值翻转的**三道前置**（缺一不可，父级独立提交）

| # | 前置 | 判定方法 | 2026-09-21 实测 |
| --- | --- | --- | --- |
| 1 | **仲裁器实现存在** | `grep ': IToolCallClassifier'` 盘点生产实现清单 | ✅ `JevToolCallClassifier`（S3d） |
| 2 | **Jev 生产可用** | `dotnet test --filter ~JevDecisionLiveTests`（设 `JEV_LIVE_POOL_PATH`） | ✅ 1/1 通过（~1 s），路径：资源池 → options provider → `https://jevtypesafeai.com` |
| 3 | **真链路解析一致** | 用**真实** Jev 调一次分类器，断言 `Outcome ≠ Unknown` 且 `ReasonCode ≠ classifier.jev.unparsed`，并对照「解析器期望 vs 真实返回形状」 | 见 S3c-2 报告 |

> ⚠️ **为什么第 3 条不能省**：分类器的离线用例全部使用**桩**，而桩返回的 JSON 是按解析器口味构造的 ⇒ 存在

> 桩只能证明内部逻辑自洽，**不能证明与外部契约一致**。

### 14.14.3 回退（无需重新构建）

- `ToolApproval:Reviewer` 是**配置项** ⇒ 运维可直接改回 `llm`（或 `jev`）；
- `LlmToolApprovalReviewer` **保留不删**（§14.13.7），作为回滚路径；
- 翻转提交的 message **必须写明这条回退方式**（见下）。

### 14.14.4 随翻转一并补齐的契约

- 给 `ToolApprovalAllowlistProposal` **append-only 追加可空 `Effect` 属性**：
  适配器为 `AllowPermanent` / `DenyPermanent` 各出一条**唯一区别就是 effect** 的提案，
  若只把 `effect=allow|deny` 编码进面向人类的 `Reason` 文本，上游就必须**靠字符串格式解析规则意图**
  —— 改一句文案即静默破功。**把结构化意图塞进文本字段时按契约缺口处理，而不是实现细节。**

### 14.14.5 激活之后（不在 S3c 范围）

- **S5b**：`IAgentAccessLevelService` / `RuntimeExecutionMode` 接线（让「完全访问」真正放宽 Yolo 执行路径）；
- **S6**：前端健康提示（§8 健康 API）+ `classifier_status` 健康面工具 + §14.9.2 退避。

### 14.14.6 部署前核查与生效验证（2026-09-21 实证）

**部署前必须核实两件事，否则“翻转”可能被静默覆盖：**

1. **宿主真的会组合这段 DI**：`AddPuddingToolRegistry(...)` 的生产调用点**只有 2 处**（已 grep 全仓确认）：
   - `Source/PuddingRuntime/DependencyInjection.cs:240`
   - `Source/PuddingHost/Extensions/PuddingServiceCollectionExtensions.Runtime.cs:237`
   两者均传入 `configuration`，且 `PuddingToolServiceCollectionExtensions` 在同一方法内注册 `IToolCallClassifier`
   与 `IToolApprovalReviewer` 工厂 ⇒ 组合顺序无隐式依赖问题。
2. **没有配置覆盖新默认值**：宿主 `Source/PuddingHost/**` 的 json 与 `D:\data\config\*.json` 中
   **不存在 `ToolApproval` 节**（已逐文件搜 `ToolApproval` 确认）⇒ 重启后 `Reviewer` 取代码默认值 `classifier`。
   若某环境需要临时回退，写入 `ToolApproval:Reviewer=llm` 即可（§14.14.3，免重新构建）。
