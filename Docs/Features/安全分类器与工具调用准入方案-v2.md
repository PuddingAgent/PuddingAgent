# 安全分类器与工具调用准入 —— 方案 v2（权威规格）

> **v2 取代 v1 的相应条目。** 上一版：`Jev自动审批与白名单自学习改造方案.md`（v1，其 §3.1 决策映射表、
> §2 中「人工兜底」取向、I2「失败折叠为 `DeferredDependency`」均**被本文件取代**；§1 现状锚点、§7 延迟实测仍然有效）。

## 0. 用户下达的需求（原话要点，逐条不可丢）

1. 实现**抽象的分类器/判断器**；系统**依赖该抽象**，**不要直接依赖 Jev**。Jev 分类器只是分类器的一个实现。
2. Agent 的工具调用行为**首先经过系统分类器**判定，一般使用**白名单 / 黑名单**；**命中白名单 → 放行**。
3. 若系统分类器的**黑白名单均未命中** → 使用 **Jev 分类器**：输入 **Agent 最近的轨迹 + 工具调用参数**，
   Jev 必须给出四选一判断：**单次放行 / 永久放行 / 单次拒绝 / 永久拒绝**；系统据此执行。
4. Jev **取代原 LLM 审批审计员的角色**，让审批动作更快。
5. 既有的**白名单与审批机制保留**，后期**人工可随时接入**。
6. 改造完成后，**审计角色下线**（`default.audit-agent.001` 退场）。
7. 硬性约束：
   (a) **Jev 服务商下线不得引起软件崩溃**；
   (b) **Jev API 下线时，系统自带的安全分类器仍能正常运行**，不因 Jev 下线或延迟受影响；
   (c) 用户可配置**不同的服务商与模型**作为安全分类器（后续）；
   (d) 除安全分类器外，Jev 还可用于**决策行为**（工具决策 / PuddingAgent 内部分类）。
8. **抽象分类器（便于后期更换其它分类器）在实际运行中是最终裁决者。**
9. **明确不要过度依赖人工确认**。理由（用户原话）：PuddingAgent 多为**无人值守**；
   LLM 分类器准确率**远高于**人类；不要期望人类去点击确认某个行为是否危险。

> **对 v1 的自我更正**：v1 把「人工为最终兜底」当作安全立场写入，**与用户第 9 条直接冲突，现予撤销**。
> 本方案中**人工不是必经环节**；人工的价值在于「事后可审计、可随时接入干预」，而非「事中必须点击」。

## 1. 判定优先级（不可交换）

```
工具调用
  │
  ├─ ① 黑名单命中        → 拒绝（永久规则 ⇒ DenyPermanent；单次规则 ⇒ DenyOnce）
  │                        *黑名单优先于白名单*（安全侧优先，防白名单挖洞）
  ├─ ② 白名单命中        → 放行（AllowPermanent 规则 ⇒ 直接放行，不调用 Jev）
  │
  ├─ ③ 均未命中 → 抽象分类器裁决（默认实现 = Jev 分类器）
  │       输入：Agent 最近轨迹（截断）+ 工具 id + 调用参数（截断）+ 工作目录 + shell
  │       输出：AllowOnce | AllowPermanent | DenyOnce | DenyPermanent
  │
  └─ ④ 分类器不可用（Jev 下线/超时/解析失败）→ 见 §4 降级契约
```

- ①② 为**确定性规则**，纯本地判定，**零网络依赖** ⇒ 直接满足需求 7(a)(b)。
- Jev 只在 ③ 被调用 ⇒ **Jev 的延迟与可用性只影响"未命中任何规则"的那部分调用**。

## 2. 抽象设计（不依赖 Jev）

### 2.1 抽象接口（放 `PuddingCore/Abstractions`）
```
enum ClassificationOutcome { Unknown, AllowOnce, AllowPermanent, DenyOnce, DenyPermanent }

record ClassificationVerdict(
    ClassificationOutcome Outcome,
    string Reason,
    string? ClassifierId,          // "system" / "jev" / 未来其它
    string? ClassifierModel,
    double? Confidence,
    IReadOnlyList<ClassificationRuleProposal>? RuleProposals)   // 永久裁决 ⇒ 提案落规则

record ClassificationRuleProposal(string Kind /* allow|deny */, string ToolId,
    string? Command, string? ArgumentsJson, string Reason, double? Confidence)

interface IToolCallClassifier
{
    string ClassifierId { get; }
    Task<ClassificationVerdict> ClassifyAsync(ToolCallClassificationRequest request, CancellationToken ct);
}
```
`ToolCallClassificationRequest` 至少含：`ToolId`、`ArgumentsJson`、`WorkingDirectory`、`Shell`、
`Identity`（agent/session/workspace）、`RecentTrajectory`（近期轨迹，**有界截断**）。

**抽象层不得出现任何 Jev 专有词汇**（不得有 `JevQuestion`/`Noul`/`choice` 等）⇒ 满足"不要直接依赖 Jev"。

### 2.2 实现
| 实现 | 位置 | 职责 |
|---|---|---|
`SystemRuleClassifier` | `PuddingRuntime/Classification/` | 读既有 allowlist/blacklist，命中 ⇒ 直接返回；**不命中返回 `Unknown`**；**零网络** |
`JevToolCallClassifier` | `PuddingRuntime/Classification/` | 依赖 `IJevDecisionService`；组装 §1③ 输入 ⇒ 四选一；不可用按 §4 降级 |
（后续）`<其它厂商>ToolCallClassifier` | 同目录 | 满足需求 7(c)：只换实现，不改抽象与调用方 |

> 复用性：同一抽象也供需求 7(d) 的**非安全决策**使用（如"这个工具该不该被选中""该走哪条分支"），
> 因此抽象命名用 `ToolCallClassifier` 之外的通用名亦可；**本方案先落地工具调用准入场景**。

## 3. 四选一的语义与落库

| 输出 | 本次调用 | 对永久规则的影响 |
|---|---|---|
| `AllowOnce` | 放行 | 不写规则 |
| `AllowPermanent` | 放行 | 写入 **allow 规则**（`ClassificationRuleProposal`） |
| `DenyOnce` | 拒绝 | 不写规则 |
| `DenyPermanent` | 拒绝 | 写入 **deny 规则** |

**永久规则的强制属性（不违背用户意图的前提下收紧）**
- **可溯源**：记录来源（哪次调用 / 工单 id / 分类器 id 与模型 / 置信度 / 理由 / 时间）；
- **可撤销**：提供撤销入口（含 CLI/工具面）；
- **尽窄**：`Command` 用**精确文本**；含 shell 元字符或通配符时**拒绝落规则**，退化为 `AllowOnce`/`DenyOnce`；
- **不可越权**：`DenyPermanent` 规则**永远优先于** allow 规则（§1 ①优先②）。

## 4. 降级契约（需求 7(a)(b) 的落地）

| 情形 | 行为 |
|---|---|
Jev 端点不可达 / DNS 失败 / 证书错 | 捕获**全部**异常，**绝不冒泡**至调用方；返回 `DenyOnce`（§4.1） |
Jev 超时（建议 `ClassifierTimeoutMs = 3000`） | 同上；记录超时审计事件 |
Jev 返回非 2xx / 无 answers / 解析失败 | 同上；`Reason` 写明具体失败码 |
Jev provider 未配置（资源池无 `jev`） | 同 7(b)：**系统分类器照常工作**；未命中时应答策略见 §4.1 |
分类器实现为系统规则 | **完全不受 Jev 影响**（无网络调用） |

### 4.1 「Jev 不可用且规则未命中」的默认应答
- **默认 `DenyOnce`**（fail-closed），**且不写永久规则** ⇒ 避免一次故障污染长期策略。
- 可配置 `ToolApproval:Classifier:OnClassifierUnavailable` = `deny_once`(默认) | `allow_once` | `defer`。
- **不引入「必须人工点击」**：`defer` 仅表示"本次不放行、留待重试/人工择机介入"，不是必经流程（符合第 9 条）。
- 崩溃防护：分类器调用外层包 `try/catch(AggregateException|Exception)`；超时用**独立 CTS**，不继承调用方无限等待。

## 5. 与既有机制的关系（需求 4/5/6）

- **保留**：既有 `IToolApprovalService`（工单）、allowlist 存储、`request_tool_approval` 工具、
  人工审批入口 ⇒ 需求 5。
- **替换**：决策来源由 LLM 审批评审器（`LlmToolApprovalReviewer`）改为**抽象分类器**（默认 Jev）⇒ 需求 4。
- **下线**：`default.audit-agent.001` 的审计角色（模板/配置）在改造验收后停用 ⇒ 需求 6。
  ⚠ 属**另一个 Agent 的配置**，须单独作为可回滚变更执行并留证；本方案只登记为后续动作，不擅自删除。
- 旧 `LlmToolApprovalReviewer` **保留代码 + 开关可切回**（便于对照与回滚），但**默认不启用**。

## 6. 验收标准

1. **抽象隔离**：`PuddingCore` 侧的抽象与调用方**不出现**任何 Jev 专有类型/词汇
   （用 grep 证明：抽象文件与调用链中无 `Jev`）。
2. **零网络快路径**：黑/白名单命中时，**不产生任何 HTTP 调用**（测试用 fake 计数断言 = 0）。
3. **四选一全覆盖**：四种输出各有一条用例，且 `AllowPermanent`/`DenyPermanent` 正确产出/落库规则。
4. **不崩溃**：模拟 Jev 抛异常、超时、返回畸形 JSON、provider 未注册 —— 四种情形下**调用方不抛异常**，
   且得到确定的判决（`DenyOnce`）。
5. **不受 Jev 影响**：在"Jev 完全不可用"的前提下，黑/白名单命中路径的**行为与耗时不变**（对照用例）。
6. **不依赖人工**：所有自动化路径**不产生**必须人工确认的阻塞态（无 `NeedHuman` 强制阻塞）。
7. **可更换**：新增一个假分类器实现（`FakeClassifier`）即可替换 Jev，**调用方零改动**。
8. 构建 0 error；既有测试不回归；文档/code_map 同步。

## 7. 明确不做

- 不删除既有审批/白名单机制（需求 5）。
- 不在本方案内删除 `default.audit-agent.001`（需求 6 的"下线"作为独立可回滚变更，登记为后续动作）。
- 不实现前端 UI。
- 不把「人工确认」设为必经环节（第 9 条）。
- 抽象层不引入任何具体厂商词汇。
