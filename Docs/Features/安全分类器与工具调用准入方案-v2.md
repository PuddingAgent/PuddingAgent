# 安全分类器与工具调用准入 —— 方案 v2（权威规格）

> **v2 取代 v1 的相应条目。** 上一版：`Jev自动审批与白名单自学习改造方案.md`（v1，其 §3.1 决策映射表、
> §2 中「人工兜底」取向、I2「失败折叠为 `DeferredDependency`」均**被本文件取代**；§1 现状锚点、§7 延迟实测仍然有效）。

## 0. 用户下达的需求（原话要点，逐条不可丢）

1. 实现**抽象的分类器/判断器**；系统**依赖该抽象**，**不要直接依赖 Jev**。Jev 分类器只是分类器的一个实现。
2. Agent 的工具调用行为**首先经过系统分类器**判定，一般使用**白名单 / 黑名单**；**命中白名单 → 放行**。
3. 若系统分类器的**黑白名单均未命中** → 使用 **Jev 分类器**：输入 **Agent 最近的轨迹 + 工具调用参数**，
   Jev 必须给出四选一判断：**单次放行 / 永久放行 / 单次拒绝 / 永久拒绝**；系统据此执行。
4. Jev **取代原 LLM 审批审计员的角色**，让审批动作更快。
5. 既有的**白名单与审批机制保留**，后期**人工可随时接入**。
6. 改造完成后，**审计角色下线**（`default.audit-agent.001` 退场）。
7. 硬性约束：
   (a) **Jev 服务商下线不得引起软件崩溃**；
   (b) **Jev API 下线时，系统自带的安全分类器仍能正常运行**，不因 Jev 下线或延迟受影响；
   (c) 用户可配置**不同的服务商与模型**作为安全分类器（后续）；
   (d) 除安全分类器外，Jev 还可用于**决策行为**（工具决策 / PuddingAgent 内部分类）。
8. **抽象分类器（便于后期更换其它分类器）在实际运行中是最终裁决者。**
9. **明确不要过度依赖人工确认**。理由（用户原话）：PuddingAgent 多为**无人值守**；
   LLM 分类器准确率**远高于**人类；不要期望人类去点击确认某个行为是否危险。

> **对 v1 的自我更正**：v1 把「人工为最终兜底」当作安全立场写入，**与用户第 9 条直接冲突，现予撤销**。
> 本方案中**人工不是必经环节**；人工的价值在于「事后可审计、可随时接入干预」，而非「事中必须点击」。

## 1. 判定优先级（不可交换）

```
工具调用
  │
  ├─ ① 黑名单命中        → 拒绝（永久规则 ⇒ DenyPermanent；单次规则 ⇒ DenyOnce）
  │                        *黑名单优先于白名单*（安全侧优先，防白名单挖洞）
  ├─ ② 白名单命中        → 放行（AllowPermanent 规则 ⇒ 直接放行，不调用 Jev）
  │
  ├─ ③ 均未命中 → 抽象分类器裁决（默认实现 = Jev 分类器）
  │       输入：Agent 最近轨迹（截断）+ 工具 id + 调用参数（截断）+ 工作目录 + shell
  │       输出：AllowOnce | AllowPermanent | DenyOnce | DenyPermanent
  │
  └─ ④ 分类器不可用（Jev 下线/超时/解析失败）→ 见 §4 降级契约
```

- ①② 为**确定性规则**，纯本地判定，**零网络依赖** ⇒ 直接满足需求 7(a)(b)。
- Jev 只在 ③ 被调用 ⇒ **Jev 的延迟与可用性只影响"未命中任何规则"的那部分调用**。

## 2. 抽象设计（不依赖 Jev）

### 2.1 抽象接口（放 `PuddingCore/Abstractions`）
```
enum ClassificationOutcome { Unknown, AllowOnce, AllowPermanent, DenyOnce, DenyPermanent }

record ClassificationVerdict(
    ClassificationOutcome Outcome,
    string Reason,
    string? ClassifierId,          // "system" / "jev" / 未来其它
    string? ClassifierModel,
    double? Confidence,
    IReadOnlyList<ClassificationRuleProposal>? RuleProposals)   // 永久裁决 ⇒ 提案落规则

record ClassificationRuleProposal(string Kind /* allow|deny */, string ToolId,
    string? Command, string? ArgumentsJson, string Reason, double? Confidence)

interface IToolCallClassifier
{
    string ClassifierId { get; }
    Task<ClassificationVerdict> ClassifyAsync(ToolCallClassificationRequest request, CancellationToken ct);
}
```
`ToolCallClassificationRequest` 至少含：`ToolId`、`ArgumentsJson`、`WorkingDirectory`、`Shell`、
`Identity`（agent/session/workspace）、`RecentTrajectory`（近期轨迹，**有界截断**）。

**抽象层不得出现任何 Jev 专有词汇**（不得有 `JevQuestion`/`Noul`/`choice` 等）⇒ 满足"不要直接依赖 Jev"。

### 2.2 实现
| 实现 | 位置 | 职责 |
|---|---|---|
`SystemRuleClassifier` | `PuddingRuntime/Classification/` | 读既有 allowlist/blacklist，命中 ⇒ 直接返回；**不命中返回 `Unknown`**；**零网络** |
`JevToolCallClassifier` | `PuddingRuntime/Classification/` | 依赖 `IJevDecisionService`；组装 §1③ 输入 ⇒ 四选一；不可用按 §4 降级 |
（后续）`<其它厂商>ToolCallClassifier` | 同目录 | 满足需求 7(c)：只换实现，不改抽象与调用方 |

> 复用性：同一抽象也供需求 7(d) 的**非安全决策**使用（如"这个工具该不该被选中""该走哪条分支"），
> 因此抽象命名用 `ToolCallClassifier` 之外的通用名亦可；**本方案先落地工具调用准入场景**。

## 3. 四选一的语义与落库

| 输出 | 本次调用 | 对永久规则的影响 |
|---|---|---|
| `AllowOnce` | 放行 | 不写规则 |
| `AllowPermanent` | 放行 | 写入 **allow 规则**（`ClassificationRuleProposal`） |
| `DenyOnce` | 拒绝 | 不写规则 |
| `DenyPermanent` | 拒绝 | 写入 **deny 规则** |

**永久规则的强制属性（不违背用户意图的前提下收紧）**
- **可溯源**：记录来源（哪次调用 / 工单 id / 分类器 id 与模型 / 置信度 / 理由 / 时间）；
- **可撤销**：提供撤销入口（含 CLI/工具面）；
- **尽窄**：`Command` 用**精确文本**；含 shell 元字符或通配符时**拒绝落规则**，退化为 `AllowOnce`/`DenyOnce`；
- **不可越权**：`DenyPermanent` 规则**永远优先于** allow 规则（§1 ①优先②）。

## 4. 降级契约（需求 7(a)(b) 的落地）

| 情形 | 行为 |
|---|---|
Jev 端点不可达 / DNS 失败 / 证书错 | 捕获**全部**异常，**绝不冒泡**至调用方；返回 `DenyOnce`（§4.1） |
Jev 超时（建议 `ClassifierTimeoutMs = 3000`） | 同上；记录超时审计事件 |
Jev 返回非 2xx / 无 answers / 解析失败 | 同上；`Reason` 写明具体失败码 |
Jev provider 未配置（资源池无 `jev`） | 同 7(b)：**系统分类器照常工作**；未命中时应答策略见 §4.1 |
分类器实现为系统规则 | **完全不受 Jev 影响**（无网络调用） |

### 4.1 「Jev 不可用且规则未命中」的默认应答
- **默认 `DenyOnce`**（fail-closed），**且不写永久规则** ⇒ 避免一次故障污染长期策略。
- 可配置 `ToolApproval:Classifier:OnClassifierUnavailable` = `deny_once`(默认) | `allow_once` | `defer`。
- **不引入「必须人工点击」**：`defer` 仅表示"本次不放行、留待重试/人工择机介入"，不是必经流程（符合第 9 条）。
- 崩溃防护：分类器调用外层包 `try/catch(AggregateException|Exception)`；超时用**独立 CTS**，不继承调用方无限等待。

## 5. 与既有机制的关系（需求 4/5/6）

- **保留**：既有 `IToolApprovalService`（工单）、allowlist 存储、`request_tool_approval` 工具、
  人工审批入口 ⇒ 需求 5。
- **替换**：决策来源由 LLM 审批评审器（`LlmToolApprovalReviewer`）改为**抽象分类器**（默认 Jev）⇒ 需求 4。
- **下线**：`default.audit-agent.001` 的审计角色（模板/配置）在改造验收后停用 ⇒ 需求 6。
  ⚠ 属**另一个 Agent 的配置**，须单独作为可回滚变更执行并留证；本方案只登记为后续动作，不擅自删除。
- 旧 `LlmToolApprovalReviewer` **保留代码 + 开关可切回**（便于对照与回滚），但**默认不启用**。

## 6. 验收标准

1. **抽象隔离**：`PuddingCore` 侧的抽象与调用方**不出现**任何 Jev 专有类型/词汇
   （用 grep 证明：抽象文件与调用链中无 `Jev`）。
2. **零网络快路径**：黑/白名单命中时，**不产生任何 HTTP 调用**（测试用 fake 计数断言 = 0）。
3. **四选一全覆盖**：四种输出各有一条用例，且 `AllowPermanent`/`DenyPermanent` 正确产出/落库规则。
4. **不崩溃**：模拟 Jev 抛异常、超时、返回畸形 JSON、provider 未注册 —— 四种情形下**调用方不抛异常**，
   且得到确定的判决（`DenyOnce`）。
5. **不受 Jev 影响**：在"Jev 完全不可用"的前提下，黑/白名单命中路径的**行为与耗时不变**（对照用例）。
6. **不依赖人工**：所有自动化路径**不产生**必须人工确认的阻塞态（无 `NeedHuman` 强制阻塞）。
7. **可更换**：新增一个假分类器实现（`FakeClassifier`）即可替换 Jev，**调用方零改动**。
8. 构建 0 error；既有测试不回归；文档/code_map 同步。

## 7. 明确不做

- 不删除既有审批/白名单机制（需求 5）。
- 不在本方案内删除 `default.audit-agent.001`（需求 6 的"下线"作为独立可回滚变更，登记为后续动作）。
- 不实现前端 UI。
- 不把「人工确认」设为必经环节（第 9 条）。
- 抽象层不引入任何具体厂商词汇。

## 8. 新增需求（用户第二轮，2026-09-20）

用户原话要点：

1. 系统选定的安全分类器（如 Jev）**故障时**：
   ① **前端界面给予明显提示**；
   ② **Agent 本身可以探查安全分类器的状态**，或**请求安全分类器**以便判断和决策；
   ③ Jev 只是其中一种实现，**请不要直接依赖 Jev 或 Jev API**；
   ④ **1 s 延迟也挺快**（LLM 思考通常数秒）；且系统分类器应**缓存 Jev 的分类结果（指永久授权）**，
      以加速判断、避免每次工具调用都请求 Jev；
   ⑤ 请求 Jev 需给出**背景知识**（工具调用之前 Agent 在做什么/思考什么）+ **分类问题**
      （单次拒绝 / 永久拒绝 / 单次允许 / 永久允许）；**Jev 返回各分类的可信度**。
   ⑥ 审计角色去留 —— 请我决策，见 §9。

### 8.1 对 §7.4 第 1 条的**放宽与更正**

先前把「避免每次调用 Jev」当作**生存必需**（基于"~1.1 s 不可接受"的假设）。用户明确 **1 s 可接受**
⇒ 更正为：**缓存是效率与稳定性优化，而非生存必需**。超时预算仍设上限，但理由改为"不无限等待"。
（注：实测 ~1.1 s 的结论不变；变的是它对设计的重要性判断。）

### 8.2 分类器健康与可探查性（需求 ①②）

抽象层新增**厂商中立**的健康面：

```
enum ClassifierHealth { Unknown, Healthy, Degraded, Unavailable }

record ClassifierStatus(
    string ClassifierId,
    ClassifierHealth Health,
    DateTimeOffset? LastSuccessUtc,
    DateTimeOffset? LastFailureUtc,
    int ConsecutiveFailures,
    string? LastErrorCode,
    int? LastLatencyMs,
    string? Model)

interface IClassifierHealthReporter { IReadOnlyList<ClassifierStatus> Snapshot(); }
```

- **Agent 侧工具**：`classifier_status`（只读探查）+ `classifier_ask`（把某个判断问题交给分类器，
  得到四选一与逐分类可信度）⇒ 满足"请求分类器以便判断和决策"，并复用需求 7(d) 的非安全决策用途。
- **前端侧**：暴露**只读**健康 API 供 UI 显示**明显提示**（前端改动见 §10 D7）。
- **硬性要求**：健康状态必须**服务端权威上报**，**不得由前端推断**（与既有"服务端权威"原则一致）。

### 8.3 缓存语义（需求 ④）

- 缓存对象 = **永久授权 / 永久拒绝的结果**（即已落地的规则），**不是**某次调用的临时结论。
- 命中缓存 ⇒ **完全不请求 Jev**（§1 的 ①② 已经是零网络路径）。
- 缓存键 = `ToolId` + `ArgumentsHash` + `WorkingDirectory` + `Shell`（与 §4 一致）；
  **不做前缀/通配泛化**（§3「尽窄」）。
- 因为缓存即"规则存储"，所以**必须可撤销、可溯源**（§3）；TTL / 周期复核登记为后续增强。

### 8.4 Jev 请求载荷（需求 ⑤）

- `state` 必须含**背景知识**：Agent **最近轨迹**（最近若干步的工具调用 + **思考/推理摘录**，有界截断）、
  当前工具 id 与参数（截断）、工作目录、shell、身份、**命中的既有规则摘要**。
- `questions`：
  - 主问题（**choice，4 选项**）：`allow_once` / `allow_permanent` / `deny_once` / `deny_permanent`；
  - **逐分类可信度**：对四个分类各问一个 **`noul`**（校准 0..1）。
- **裁定规则（必须用上可信度）**：
  1. 取逐分类可信度的**最高者**作为结论；
  2. 若结论属**永久**类 ⇒ 要求其可信度 ≥ `PermanentConfidenceThreshold`（默认 **0.90**）
     **且** 相对其**对偶单次类**保持领先边际；否则**降级**为对应**单次**类
     （永久放行 → 单次放行；永久拒绝 → 单次拒绝）；
  3. 单次类无此约束。
  ⇒ 既满足"四选一 + 可信度"，又避免以低置信写入永久规则。

## 9. 决策：**移除审计角色**（我的结论）

用户给出两案请我决策：**A** = 保留审计员但改为周期性批量异步维护黑白名单；**B** = 完全移除审计员，
由**代码**在 Jev 裁决后更新黑白名单（用户注：成本极低、代码更健壮）。

### 结论：采用 **方案 B**，改为代码化的「规则策展器」

理由：

1. **职责不匹配**：把裁决写进规则库本质是**确定性数据搬运 + 去重 + 冲突检测**，不需要语言模型。
   用 LLM 承担会引入**非确定性**与**额外故障面**（第二条依赖链、消息通道、周期调度可靠性）。
2. **与"最终裁决者是分类器"一致**：方案 A 实质是让第二个模型对第一个模型的结论做**二次裁定**，
   恰是用户明确反对的"额外的判断环节"（需求 9 的反面）。
3. **成本与可测性**：方案 B 是纯逻辑，可单元测试覆盖（去重 / 冲突 / 尽窄 / 溯源）；
   方案 A 的失败模式（漏消息、重复写、时序错乱）难以穷尽。
4. **用户倾向**：用户自述"成本会非常低，代码更加健壮"。
5. **人工并未被封死**：既有审批入口保留 + 新增人工可用的规则管理入口（查看 / 撤销 / 覆盖），
   满足"人工可随时接入"，且不构成事中必经环节。

### 9.1 落地形态：`ClassificationRuleCurator`（代码，非 LLM）

- **输入**：分类器裁决 + 溯源信息（分类器 id / 模型 / 逐分类可信度 / 理由 / 时间 / 身份 / 工具与参数）。
- **动作**（**批量、异步、幂等**）：写入 allow / deny 规则；**去重**；
  **冲突检测**（同键既 allow 又 deny ⇒ **deny 胜**，并告警）；
  **尽窄校验**（命令含 shell 元字符或通配符 ⇒ 拒绝落永久规则并降级为单次）。
- **输出**：规则变更事件 + 审计事件（可追溯）。
- **不**引入必须人工确认的阻塞态；人工可事后通过工具查看/撤销。

### 9.2 由此确定的后续动作

- `default.audit-agent.001` 的审计角色**停用**（对应早期需求 6）。
  执行前必须核对：**心跳路由**是否仍指向该 Agent（历史上曾出现"心跳只投递给 audit-agent"的缺陷），
  避免停用引发别处行为变化；以**可回滚**变更执行并留证。
- 保留 `LlmToolApprovalReviewer` 但**默认不启用**（仅用于回滚与对照）。

## 11. 权威归属的正式表述（用户第三次明确，**更正 §1/§2 并撤销 I1**）

用户原话：

> **「安全分类器拥有最终否决/放行权（包括覆盖 deny），Jev 安全分类器是安全分类器的其中一个实现。
> 未来，我们会实现更高级和可靠的分类器。」**

### 11.1 更正内容

- **权威在抽象层，不在 Jev**：最终裁决者是**安全分类器抽象**（即 `IToolCallClassifier` 这一层），
  **不是 Jev**，也不限任何单一实现。Jev 只是当前实现，未来更高阶/更可靠的分类器可直接替换。
- **分类器可覆盖 deny**：§1 曾把「① 黑名单命中 ⇒ 拒绝、且**不调用分类器**」写成不可交换的优先级，
  与本次表述**直接冲突**，现**更正**。新语义：
  - 系统规则（白/黑名单）与既有确定性防火墙产出的都是**候选结论（provisional）**，**不是终局**；
  - **分类器是终局**，对候选结论拥有**确认或覆盖**权，**包括覆盖 deny**。

### 11.2 ⚠ 撤销 v1/v2 的不变量 I1

> **I1（deny 优先且命中即不调用 Jev）已撤销。**
> 该不变量源自「模型不应是唯一授权者」的行业实践判断；用户已明确要求分类器**可覆盖 deny**，
> 故 I1 与用户意图冲突，**作废**。保留其精神的部分改述为 §11.3 的**防循环**规则。

### 11.3 覆盖机制（既落实覆盖权，又不违反「避免每次都调用 Jev」）

```
① 候选结论按来源区分：
   - 来自「分类器自身的永久规则」（即分类器此前对同一缓存键已作出永久裁决并落库）
     ⇒ 该结论**本身就是分类器的裁决**，**不再重复调用**分类器（缓存命中，不构成绕过权威）。
   - 来自「系统规则」（人工配置的白/黑名单）或「既有确定性防火墙」
     ⇒ 视为**候选**；候选为 deny 时**必须给分类器一次覆盖机会**（否则覆盖权形同虚设）。
② 覆盖**只能由分类器执行**；任何其它组件不得覆盖分类器的结论。
③ 每次覆盖必须落审计事件：原候选、覆盖后结论、分类器 id / 模型 / 逐分类可信度、理由、时间。
④ **防循环**：分类器自身产出的 deny 在缓存命中时**不再回调**分类器
   （对应 ①-1），避免「分类器否认 → 再问分类器 → 再否认」。
⑤ 白名单命中仍走**零调用**快路径（用户第 4 条：缓存加速、避免每次都请求 Jev）。
```

**效率含义**：分类器调用量由「被 deny 的调用数」决定，而非全部工具调用；
白名单命中 **零调用**。该量级必须实测（见 §12），不得凭推测。

### 11.4 与「缓存」不矛盾

缓存的是**分类器的永久裁决**（= 分类器已表过态的结论），因此缓存命中**不是绕过分类器权威**，
而是**复用分类器权威**。

## 12. 审计效率评估（用户要求：改造完成后评估 Jev 的审计效率）

**目的**：用数据回答「Jev 审计是否够快、够省、够准」，**不得只给结论**。

## 13. 「正常样本」不变量（用户第三次明确，**新增 I7**）

用户原话：

> **「理论情况下，jev 安全分类器会放行绝大部分的行为，因为你是一个正常的样本。
> 如果 jev 安全分类器阻止了你，说明实现不正常。」**

这是一条**可测试的验收不变量**，必须固化：

- **I7（正常样本不变量）**：对**正常、良性**的 Agent 行为样本，分类器应**放行绝大部分**；
  一旦出现 **deny，即视为实现缺陷的强信号**（payload 组装错误、问题措辞歧义、选项映射错位、
  阈值过严、身份/工作目录注入错误），**优先排查实现，而不是接受该 deny**。
- **落地为回归测试**：建立**良性样本夹具集**（取自本 Agent 的真实工具调用轨迹：读文件、搜索、
  `git status/diff/log`、构建、测试、记忆读写等），断言分类器对其**放行**；
  若回归中出现 deny ⇒ 测试失败并**打印原始 payload** 供定位。
- **运行期告警**：连续 N 次（默认 3）对良性样本或同类调用判 deny ⇒ 上报「分类器实现异常」
  并使健康面降级（接入 §8.2），**不得静默阻断**。
- 与 §11.2 的关系：I7 是**实现正确性**的守卫，不是对分类器权威的限制 ——
  分类器仍可覆盖 deny；但若它拒绝了正常样本，我们把它当**实现 bug** 处理。

## §14 审批工具增强：`request_tool_approval` → 统一「审批门户」

> 来源：用户 2026-09-20 23:31 指令。目标是把既有的**唯一审批入口**扩展为一个门户，
> 使 Agent 能：请求安全分类器裁决、读写黑白名单、申请**临时完全访问模式（5 分钟）**，且**全部可审计**。

### 14.1 四项动作（统一入口）

| `action` | 语义 | 是否落规则 |
| --- | --- | --- |
| `submit`（**默认，向后兼容**） | 既有行为：按审批单提交工单并取得裁决 | 仅当 `RequestAllowlistRule=true` |
| `classify` | 请求**安全分类器**对「计划中的动作 + 背景」出裁决（四选一 + 逐分类可信度 + 理由），**不建工单** | 仅当裁决为**永久类** |
| `rules_list` / `rules_update` | 读取 / 更新**白名单与黑名单**（新增、禁用） | — |
| `full_access_request` / `full_access_status` / `full_access_revoke` | 申请 / 查询 / 撤销**临时完全访问模式** | — |

### 14.2 为什么「扩参不扩工具」

既有 `request_tool_approval` 已是 Agent 唯一的授权入口，且 `IToolApprovalService` 已同时承载
**工单 + 白名单 + 审计**三件套。再新开一个工具会产生「两个授权入口」的语义分裂（违反 §8 不引入平行结构）。
⇒ 在既有 `RequestToolApprovalArgs` 上**追加参数**，默认值保持 `submit`。

### 14.3 抽象依赖（硬性，可 grep 验收）

门户**只依赖** `IToolCallClassifier`（PuddingCore）与 `IClassifierHealthReporter`，**不依赖任何厂商**。
验收：`RequestToolApprovalTool.cs`、审批门户服务、规则策展器等新增代码中
**不得出现** `Jev` / `Noul` / `choice`（除 `JevToolCallClassifier` 自身实现文件外）。

### 14.4 新增参数

| 参数 | 说明 |
| --- | --- |
| `action` | `submit`(默认) / `classify` / `rules_list` / `rules_update` / `full_access_request` / `full_access_status` / `full_access_revoke` |
| `rule_op` | `add` / `disable`（`rules_update` 必填） |
| `rule_effect` | `allow` / `deny`（`rules_update` 且 `rule_op=add` 必填） |
| `rule_id` | `rules_update` 且 `rule_op=disable` 必填 |
| `full_access_duration_seconds` | 默认 **300**，**上限 300**（超过即**拒绝**，不是静默截断） |

`classify` / `full_access_request` **复用既有审批单字段**
（`purpose`、`necessity`、`fact_basis`、`requested_arguments_json`、`target_resources`、
`is_irreversible_operation`、`rollback_plan`、`operation_context` …），**不新增第二套表单**。

### 14.5 判定与后果

**`classify`**
- 返回：`outcome`（`AllowOnce|AllowPermanent|DenyOnce|DenyPermanent`）、`confidence`（逐分类）、
  `reason`、`classifier_id`、`classifier_model`、`latency_ms`；
- 永久类 ⇒ 交给 `ClassificationRuleCurator`（幂等 / 去重 / **冲突 deny 胜** / 尽窄 / 溯源）落规则，回传 `rule_id`；
- 单次类 ⇒ **不落规则**；
- 分类器不可用 ⇒ 返回 `deferred`（**不落规则、不授予完全访问**）。

**`full_access_request`**
- **必须**走出题单 + 分类器裁决；只有 `AllowOnce` / `AllowPermanent` 才授予；
- 授予 = 对 `agent_instance_id` 生效 `RuntimeExecutionMode.Yolo`（经 `IAgentAccessLevelService`）；
- **TTL 由服务端计时，到期自动失效**，不依赖 Agent 主动撤销；进程重启即失效（不持久化）。

**`rules_update`**
- `add` ⇒ 落规则（`Effect=Allow|Deny`，带溯源：分类器 id / 模型 / 可信度 / 理由 / 身份 / 时间）；
- `disable` ⇒ **不硬删除**，置 `Status=Disabled`（保留审计链，符合 append-only）；
- 尽窄校验：命令含 shell 元字符或通配符 ⇒ **拒绝落永久规则**（退化为单次）。

### 14.6 语义边界（不可越）

「完全访问」**只放行审批 / 授权闸门**，**不放宽**：
角色工具白名单、子代理暴露策略、能力策略（capability）、沙箱路径边界、进程终止类不变量。
作用域 = `workspace_id + agent_instance_id`，**不跨 Agent、不跨 workspace**。

### 14.7 故障与降级（对应需求 7(a)(b)）
