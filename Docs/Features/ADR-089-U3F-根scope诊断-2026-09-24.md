## 3. 三个真实缺陷（这才是要修的东西）

- **D1 · 语义混淆**：`MapStatus` 把 `Registering`/`Unknown` **静默降级为 `Covered`**。而 `Registering` 的语义是"**有一次运行欠着**"，**不是"被父 scope 覆盖"** ⇒ 未迁移的遗留行因此**永久失去被附着的机会，且不出任何错**。
- **D2 · 取消不留痕**：`CodeIndexScheduler.ProcessJobAsync` 在 `:203` 写 `Registering`、`:224` 写 `Active`，但**取消分支 `:235-238` 不写任何状态** ⇒ 被打断的运行把该行**永久留在 `Registering`**；**无启动自愈**。
- **D3 · 把"被中断"当"可删"**：清理判据 `:91-96` 把 `Status='Registering'` + NULL `ScopeState` 列为删除候选 ⇒ 一次人工清理会删掉根 scope 的 **1083 / 34,848 / 96,849 / 143,587** 行 + 注册行。
- **D4 · 运行历史不落盘**：`CodeIndexRuns` **空表且全仓无写入者** ⇒ 事后无法区分"取消 / 被终止 / 挂住"。
- **D5 · 新代码不在任何索引里**（父级自跑探针复核）：全库 **0** 个 scope 覆盖 `Source\PuddingCodeIndex\`；`%CodeIndexMaintenanceService%`、`%PathNoiseRules%` 的 `CodeFiles`/`CodeSymbols` **全 0 命中** ⇒ **U3/U4 这两天新写的组件本体不在任何索引里**（根 scope 冻结 + 新工程只在"首次被查询"时才惰性建 scope，两者叠加）。

## 5. 父级推荐（供裁定，不代为执行）

**先做 E 的防损子集（已派 U3-G1），再谈 A/C。** 理由：
1. **D3 是当前最危险的一条** —— 数据离被误删只差一次人工点击。**U3-G1 已派**：把 `Registering` 从删除判据里摘掉 + 让"被中断"留下可区分的 `StatusMessage`（**不改任何 DB 行、不改枚举语义**）。
2. U3-G1 落地后，**恢复根 scope 的首选会变成"重启即自愈"**（若后续切片补上启动重入队）—— 比手改 DB 干净得多，且**不需要**不可逆的 B。
3. 若用户希望**立刻**恢复可用性而不等自愈：选 **A**（先备份 `code_index.db`，再重注册 + `index=true`，完成后核 `Status='Active'` 与 `CodeFiles ≈ 4413`）。**B 不推荐**（不可逆且收益与 A 相同）。**C 需搭 A**，单做会得到一个"陈旧但被附着"的 scope。
4. ⚠️ **在 E 的防损子集落地前，不要执行任何"清理冗余代码索引作用域"**。

## 7. 操作纪律教训（本刀新踩，已入规范）

⚠️ **读运行中进程正在写的日志会抛共享冲突异常**：`file_read D:\data\logs\system\pudding-*.log` 抛
`The process cannot access the file … because it is being used by another process`（Core 持有写锁）。
与"工具返回错误载荷"不同，这是**抛异常**，`tool_failure_count=1` 即**报废子代理整轮**（U3F 就死在这里）。
⇒ **正确做法**：先复制到 `temp/` 再读，或改用能容忍共享的方式（终端 `Select-String` / `search_grep`）；
**明确禁止子代理直接 `file_read` 运行中的日志**。

⚠️ **报告先落盘、收尾 patch 才失败**：U3F 报告写在 17:58:04、死亡在 17:58:24（**早 20 秒**），与 U3-D 完全同型
⇒ **失败不等于没有交付物**；先取证磁盘再决定"接手验收"还是"续跑"。

### 修正 1：容量占比数字错误

上文/简报中「906,551,296 B 占 1GB 护栏的约 88%」**不成立**，已作废：
- 若按 `1 GB = 1,000,000,000 B` ⇒ **90.66%**；
- 若按 `1 GiB = 1,073,741,824 B` ⇒ **84.43%**。
⇒ **"1GB 护栏"本身有 GB/GiB 歧义**，必须固化为**精确字节数**方可判定（列入待用户裁定的问题）。
`906,551,296 B ≈ 864.6 MiB` 的换算无误。

### 修正 2：根 scope 的"独立价值"远小于 1,083 行（⚠️ 改写迁移方案）

父级对 `CodeFiles` 的只读实测（`mode=ro` + `PRAGMA query_only=1`）：

```
distinct FilePath = 1,246        total rows = 2,849
⇒ 812 条路径被重复索引（样本 count=4 ⇒ 同一文件在 4 个 scope 各存一份）
根 scope 1,083 行中：706 行落在子 scope 根目录内（= 与子 scope 重复）
                     377 行不在任何子 scope 根下（= 根 scope 独立贡献的上界）
   且这 377 行中含仓库外文件：
   C:\Users\huany\.nuget\packages\microsoft.net.test.sdk\18.0.0\build\net8.0\Microsoft.NET.Test.Sdk.Program.cs
```

**三条推论**：
1. **864.6 MiB 的主因不是"内容多"，而是跨 scope 重复索引**（2,849 行只承载 1,246 个不同路径，平均 ≈2.3 份）⇒ 护栏余量紧张**主要是浪费**，不是真实数据量。
2. 上文「C 方案会永久留下约 3,330 文件缺口」的**口径不准**：`4,413 − 1,083 = 3,330` 只是**文件总数差**，未扣除嵌套 scope 的覆盖与重复。**改以上述路径级差集为准**。
3. 根 scope 含**仓库外文件**（NuGet 缓存，来自 2026-07-24 那次运行，早于 U4-4 的排除表修复）⇒ **"共享库按 `ProjectId` 原样拆分"会把这个缺陷一起搬进新库**。

⇒ **父级改推荐**：根 scope 处置从「E + A（旧库全量重建）」改为 **「E + 在新建的项目库中重建」**；**B 仍不推荐**。
理由：根 scope 的独立贡献上界只有 377 行，在旧共享库里做全量重建**主要是在重做已被子 scope 覆盖的数据**。

### 修正 3：措辞歧义 —— "初始化 gitignore"

上文「索引初始化时同时初始化 gitignore」**歧义过大**，按审查意见收窄为：
**读取并编译有效忽略规则**（只读）；**不自动修改受版本控制的 `.gitignore`**；
防自索引改用**索引器硬排除** + `.git/info/exclude`。
理由：自动改 tracked 文件会产生工作树修改，**不应默认发生**。

### 修正 4："永久退出全部自愈环路"的证据边界

该结论的证据是**维护服务层**（`CodeIndexMaintenanceHostedService.cs:165` + `CodeIndexScopeRegistry` 的附着/覆盖判据 + 校准只对已附着 scope 生效）。
**是否存在其它恢复入口**由父级的全仓检索支撑，**未被独立第三方复核**。保留为"已由父级检查、未获外部复核"，不作为绝对断言。

### 修正 5：跨 scope 重复的**成因未证实**

812 条重复是**行级实测**（同一 `FilePath` 对应多个 `ProjectId`），但**是否由 Roslyn 工程引用闭包导致**（而非 scope 路径配置错误）**尚未定位到写入者**。
⇒ 列入 M1/M3 的调查项；在定位前**不得**据此下"排除了多少有效数据"之类的量化结论。
