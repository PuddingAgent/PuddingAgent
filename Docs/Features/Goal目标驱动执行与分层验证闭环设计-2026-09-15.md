# Goal 目标驱动执行与分层验证闭环

日期：2026-09-15。状态：**Proposed，代码级实施方案；不是功能已完成或已部署的声明**。

决策：[ADR-092](../07架构/106ADR-092目标驱动执行与分层验证闭环ADR.md)。任务与派发：[实施记录](../Reports/Goal持续执行方案与任务修订-2026-09-15.md)。本次只修改设计和任务描述，不修改产品源码或运行配置。

## 1. 产品目标与完成定义

用户交给系统的是一个完整目标。系统持续执行、验证、修复和再次验证，直到满足目标的全部必需验收条件。Agent 结束一条回复、完成一个步骤、提交代码、更新 Memory、调用 sleep，都不代表 Goal 完成。

正常工作流：`目标及验收条件 → 当前步骤 → Agent 执行 → 步骤校验 → 自动修复或下一步骤 → 整体校验 → 完成`。这条链路由 Core 持久状态和事件驱动；不要求网页保持打开，不要求用户不断说“继续”，也不依赖 Heartbeat。

例如“修复自动审计并证明普通开发任务能继续执行”：代码提交只是中间交付。构建、相关回归、当前构建功能验证仍属于同一个目标。测试失败产生具体修复工作；需要外部重启时登记依赖，收到对应新构建证据后继续，不能把目标标成已完成。

持续工作仍遵守用户暂停/取消、运行窗口、真实权限边界和授权预算。等待依赖时释放执行资源；“持续”指目标不会失联，不要求模型始终占用 CPU 或反复自言自语。

## 3. 领域边界与权威数据

| 对象 | 负责什么 | 不能被什么替代 |
|---|---|---|
| GoalRun + ObjectiveVersion | 用户目标、生命周期、授权、预算累计 | 聊天回复或 goal.md |
| AcceptanceContract | 完整目标的必需条件、验证方法、证据新鲜度 | 模型临时降低的标准、任务状态 |
| WorkUnit / PlanRevision | 为达成目标可调整的步骤、依赖、退出条件 | 固定 Explore/Plan/Change/Test/Review 模板的序号 |
| GoalIteration / canonical Turn | 一次物理执行及使用量 | 已完成步骤或完成目标 |
| VerificationRun | 某版本目标/单元的实际检查及裁决 | 自报“测试通过”或 shell 已启动 |
| AwaitHandle | 在等谁、什么事件、截止时间、恢复动作 | sleep 或重复查询 |
| Memory / 外部文档 | 当前决定、导航、必要背景 | 验证账本与调度状态 |

允许一个 WorkUnit 执行多轮，也允许一轮产生多个可检验的结果；只能依据各自证据推进。模板只生成初始计划，不能以“每轮自动前进一个模板节点”解释完成。

普通 Goal 与 Task-bound Goal 使用相同验收合同。独立 Goal 可复用 task_plan_runs/task_nodes 的计划存储，但需明确 `ownerKind=Goal/Task` 与 ownerId，不能伪造一个已完成 Task 才能验收 Goal。若当前表要求 TaskId，先扩展所有权合同和约束，再接独立 Goal；不新增第二份 WorkUnit 存储。

## 4. 验收合同与证据合同

以下为建议合同，不是现有 API。实现时保持已有稳定 enum wire 值，新增枚举置末尾或使用显式字符串。

```csharp
record GoalCriterion(
    string Id, int Revision, string Requirement, bool Required,
    VerificationSpec Spec, IReadOnlyList<string> DependencyIds);

record VerificationSpec(
    string Kind,                    // build / test / postcondition / artifact / semantic / external
    string DefinitionRef,           // 版本化检查定义，不是自由 shell 字符串
    string DefinitionHash,
    IReadOnlyList<string> InputRefs,
    string ExecutorRole,            // core / external_controller / human
    string FreshnessPolicy);

record CriterionResult(
    string CriterionId, int CriterionRevision,
    string Status,                  // pending / passed / failed / waiting / invalidated
    IReadOnlyList<string> EvidenceRefs,
    string InputFingerprint, string? FailureCode);

record GoalVerificationOutcome(
    string Scope,                   // work_unit / goal
    string Disposition,             // continue_current / repair / advance / verify_goal / complete / wait / needs_user / stop
    IReadOnlyList<CriterionResult> Results,
    NextAction? NextAction, WaitRequest? Wait,
    string SnapshotHash, string ProgressFingerprint);
```

`NextAction` 必须包含目标中的未满足条件 ID、当前/下一个 WorkUnitId、具体动作、预期产物和下次检查方式，不能只说“继续完成目标”。`WaitRequest` 必须包含 dependency kind/id、触发事件、deadline/nextEligibleAt、恢复策略；不能填空泛的“等下一次心跳”。

新 Goal 建立验收合同：保存用户原始要求；从 Task acceptanceCriteria 或用户目标提取结构化必需条件。普通实施细节可由 Agent 细化，不逐项询问用户。范围、成功标准或授权的实质变化须独立显示，不得为了过检悄悄删除必需条件。无明确完成定义时先执行一个有界规划步骤产生合同，不能空列表 vacuous pass。

每条证据至少携带：EvidenceId、producer、GoalRunId/epoch、WorkUnitId、criterion revision、source/artifact fingerprint、check definition hash、BuildId（适用时）、environment fingerprint、InvocationId/RunId、start/end、outcome、摘要和外部原始产物引用。模型提交的是 claim + refs；服务端必须解析真实证据，不能接受模型自己拼出的 EvidenceId 或 pass 字段。

代码检查的 fingerprint 必须覆盖实际工作树内容（包括相关未提交改动）和检查输入，不能只用 HEAD。未知影响范围保守失效，不以“git commit 没变”复用旧绿灯。目标修订、相关源码/配置/检查定义/运行环境变动，自动使相关结果失效；无关文件变化不必重跑全部测试。

## 5. 两级校验与真正执行测试

### 5.1 每轮步骤校验

`GoalIterationVerifier` 消费本轮 canonical 新事实和当前单元条件：

1. 证据尚未齐全：AwaitEvidence，登记事实/子代理/进程完成事件；不要生成修复轮或 Goal Failed。
2. 编译/测试/后置条件失败，Agent 可修复：Repair，保持当前 WorkUnit，附具体失败证据和下一动作。
3. 当前步骤只部分完成：ContinueCurrent，不前进 Plan 序号。
4. 当前步骤条件全部通过：Advance；若还有可执行步骤立即投递；没有则 VerifyGoal。
5. 当前步骤在等待，而同一 Goal 有不冲突的就绪步骤：先调度可运行步骤；没有时持久等待。

每轮先做低成本确定性检查。没有新增相关证据、不涉及完成提议时，不调用大型模型审阅整段历史。

### 5.2 整体目标校验

整体 gate 必须检查：合同非空且版本有效、全部必需条件通过、必需交付物与必要子任务已落实、相关检查没有失效、没有仍待完成的必需验证/部署义务。无关后台审计不无限阻挡 Goal 完成。

`Task.Status == Completed`、`Turn.completed`、Agent 说 DONE、生成了报告文件，都不能绕过 gate。Goal/Task 状态是裁决的输出，不能循环成为裁决的前提。

对代码目标，先使用 build/test/runtime postcondition 等可复现检查。对文档、设计、研究等目标，使用文件存在与内容结构检查，加有界只读语义审阅。仅编译通过不能证明 UI 好用；仅截图存在也不能证明交互成功。合同必须选能验证实际用户要求的检查。

### 5.3 执行检查与裁决分离

保留 `IGoalIterationVerifier` 的只读边界。新增 `IGoalCheckRunner`（可由通用验证执行器实现）负责实际执行受控检查，再由 Verifier 裁决；不得在 `VerifyAsync` 中执行任意 shell 或写 Task。

检查流程：版本化 VerificationSpec → 共用 CommandExecutionPlan/工具准入（ADR-091）→ canonical 执行 → 检查报告及后置证据 → 验证结果。定义必须经服务器校验 cwd、参数、输入和权限；模型不能以“测试”名义绕过执行准入。既有授权足够时直接运行，无须增加专门人工审批。依赖未就绪走 typed wait，不能误报用户拒绝。

检查必须确认实际结束和目标后置状态：例如 dotnet test 既要结束码，又要新生成的运行报告及运行到预期测试，不能接受 0 tests、复用旧报告、terminal_start 已创建或终端 exit 0 但目标文件未改变。

语义 verifier 使用独立的单次无工具调用、有界事实输入、严格 schema。它不继承实施 Agent 的整段思考，不允许编造通过的检查。可使用同一模型服务，不要求预先存在一个“审计 Agent”。关键端到端指标仍以可复现证据为准，同模型第二意见并不是绝对独立的正确性保证。

产品自修复的外部验证分层：源码提交/测试 → ready-for-external-deploy → 外部控制器加载明确 BuildId → 新产品会话功能 smoke → 外部生命周期验收。承载自己的进程不能证明新源码已加载；等待外部部署是目标未完成的合法等待。

## 6. 持久结算与自动续行

### 6.1 统一结算算法

```text
canonical Turn terminal / verification result / dependency signal
    -> 合并到同一 Goal 验证快照，去重并冻结版本
    -> 计划尚缺的检查；等待检查完成，不占用 Agent Loop
    -> 步骤或整体 verifier 输出结构化 outcome
    -> 短事务重验 Goal/epoch/contract/plan/input hash/lease
       -> 写 verification + criterion results
       -> repair/continue: 当前单元不变，写下一 continuation
       -> advance: 仅已验证单元完成，选下一就绪单元
       -> wait: 保留 Goal 和绑定，登记 AwaitHandle，释放执行 permit
       -> complete: 必需整体条件全通过，Goal/Plan/绑定 Task 同事务完成
       -> needs_user/pause/stop: 写明确状态、保留证据和用户控制权
    -> 事务提交后发信号；恢复扫描兜底，不依赖信号不丢
```

每次 outcome 的幂等键建议为 `(goalId, epoch, verificationId)`；next outbox 使用 `(goalId, epoch, nextIteration)` 唯一键。检查去重键使用 `(scope, criterionRevision, definitionHash, inputFingerprint)`。旧 epoch/版本结果可保存为历史，但不得写当前状态、消耗当前预算或唤醒已取消目标。

检查需要长时间或模型调用时：先提交租约/快照再执行；执行阶段不持有 SQLite 写事务。完成后 CAS。实际改变了相关输入时重新快照验证，不能把旧 Pass 应用到新代码。

### 6.2 等待不关闭目标身份

复用 `work_unit_await_handles`，增加或规范 GoalRunId/epoch、事件游标、deadline、resume action、去重键；为独立 Goal 支持相同 Owner 合同。每个 AwaitHandle 必须有恢复事件和超时处理；不能永远 waiting 且无人负责。

区分 **逻辑归属** 与 **执行租约**：Goal/task binding 持续存在；当前 Agent execution/reservation 在等待期间释放，避免占满资源。恢复时统一 admission 重验策略/窗口/预算/取消状态，原子取得新 assignment 或新租约及 fencing token，再构造当前 ActiveTask。不能携带已释放 assignmentId，也不能放松 `assignment.stale` 校验。

修订旧死胡同卡的 F1：一律 NeedsReview 并永久保留 assignment 不是最终方案，会制造新的 false-busy。NeedsReview/NeedsUser 只表示真的需要人作决定。恢复性基础设施错误、证据延迟、子代理等待不应升级为人工复核。

Goal 生命周期沿用 Active/Paused/Blocked 等主阶段；增加结构化活动子状态 Executing/Verifying/Waiting。依赖等待为非终态 Waiting；BudgetExhausted 表示可补充授权后恢复的暂停原因，不能为了释放唯一性约束把整个 Goal 标 Failed。终态只有已验证 Completed、明确 Cancelled、不可恢复 Failed。数据库 active 唯一索引、Tracker、Availability 和恢复逻辑必须同步更新，不能只改一个 if。

### 6.3 续行、消息与心跳

复用 GoalContinuationWorker、ConversationAcceptance、ChatExecutionWorker；Turn 受理成功才消费外层 iteration。普通 external message 只是消息，不保证建立 Goal。Web/Connector 的明确 `/goal` 或结构化 StartGoal 命令应统一走现有命令入口；不能根据模型回复推断“已经进入 Goal 模式”。不把所有聊天自动升级为目标。

Goal 管理的当前轮里 `sleep` 可记录闲时心跳偏好，但必须明确返回 `goalContinuationUnaffected=true`，不得推迟 Goal outbox、结束 Goal 或标记完成。HeartbeatPrompt 与 Host 内嵌提示统一改为：存在 runnable Goal 时由 Goal 内核续行，Heartbeat 只维护/发现工作或恢复信号；不要要求 Agent 每小步设置 sleep。

增加明确的 `goal_status` / `goal_report` 薄工具（名字在实现时查冲突）：前者查询当前受信 Goal 上下文；后者提交进展/完成提议、证据引用和等待请求。客户端不能自行提供另一个 Goal 的授权上下文。`goal_update/goal_read` 保留 Memory 笔记用途，描述中明确不改变 GoalRun。既有 Task 完成命令对绑定 Goal 返回 `completion_proposed/verification_pending`；未绑定 Task 保留原有生命周期。所有 Task 写入口都必须经过相同 Goal 完成门禁，不能只改 Agent 工具留下 Admin/API 直写缺口；真正人工强制关闭若业务需要应作为独立明确命令，不能伪装 verified completion。

## 7. 预算、长程运行与无进展处理

外层 Goal iteration、内层 Agent round、子代理 round、检查执行时间、输入容量与累计成本必须分别显示。600 轮子代理不等于 600 个 Goal iteration。禁止恢复之前错误的“统一改小所有轮次”的做法。

将硬编码 256 的外层 iteration 上限改为配置/授权合同：支持合理的正整数（例如 600、2000），输入范围与溢出检查保留；系统部署预算与用户授权共同决定有效额度，不擅自改成无限。用持久检查点跨 session/进程推进，同一个 Goal 身份和费用账本不变。重试、验证、子代理的成本全部归集，不能通过换 epoch/新 Goal 归零。

长程 unattended Goal 可在创建时选择 `ResumePolicy=AfterRestart`，当前默认未授权目标维持 Paused；恢复前重验授权、租约、执行窗口和未决副作用。显式 Pause/Cancel 永远不被重启恢复覆盖。现有 7 天/24 小时类硬限制若阻断合法长程工作，应分辨服务 deadline 与目标寿命后改为配置；不能简单删除工具的故障超时。

连续失败按根因指纹收敛：`criterionId + failing check + relevant input hash + failure family`。相同输入下重复失败没有新策略时不再反复重试；先改变修复策略/缩小实验/选择另一就绪步骤。建议同一指纹 3 次无变化后触发一次 Replan 或审计 finding；仍无可行路径则结构化暂停并给出证据。这个阈值不是整个 Goal 只许 3 轮，也不是等待 3 次就失败。实际等待依赖不计作无进展。

不同已授权 Goal 之间需要公平调度；单次物理 Turn 结束时检查用户插话和其他高优先级工作。执行饱和不意味着一个 Goal 永久独占所有资源。

## 8. 内存、缓存和审计复用

每轮注入稳定的规则前缀和短 Goal capsule：目标版本、当前单元、未满足条件 ID、最近一次验证失败摘要、下一动作、证据索引。稳定信息不重排；动态状态放尾部。完整检查输出、历史日志、计划修订存在外部 artifact/数据库，不每轮灌入历史全文。

Memory 保存鲜活决定和项目索引，不复制不断增长的验收账本。Session 压缩继续使用既有压力/收益门禁；目标切换步骤本身不强制压缩。

与 ADR-091 共享 EvidenceRef/InvocationId/BuildId、执行准入、失败分类、finding 和任务派发。Goal verifier 是目标完成的同步结算门禁；行为审计是旁路增量诊断，不能互相等待形成死锁。审计发现潜在问题时先限定与目标的关系：相关缺陷纳入当前修复计划；无关问题登记 backlog，不让 Agent 永远扩展目标。

本功能评价使用 verified Goal goodput、修复成功率、无效等待和每个达成目标的成本。缓存率作为辅助指标，不能靠重复相同提示或不执行测试刷到 99%。

## 13. 完成路径合同（D1/D2 裁决）

来源：Codex 外部裁决（2026-09-15 12:45，canonical）。本节把裁决固化成实现合同，是刀 B/C/D 的验收依据。

### 13.1 D2 收敛路径（合同）

`单元完成 → VerifyGoal（待整体验证）→ 原子完成`。

**0 个 Running 不是错误的充分条件**，计划结构与状态必须分开判定：

| 计划状态 | 规定处理 |
|---|---|
| 恰好 1 个必需节点 Running | 验证当前单元；其验收通过后才推进 |
| 0 Running 且所有必需 WorkUnit 已验证完成 | **合法收敛态**：进入/恢复 VerifyGoal（待整体验证），Goal/Plan 保持非终态，调度尚缺的整体验证 |
| 0 Running 但仍有必需单元 | 有 ready ⇒ 认领推进；等依赖 ⇒ 登记 typed wait；**不得误 Complete，也不得单凭 running=0 判 Failed** |
| root 缺失/重复、ownership 或版本冲突、多 Running 违反串行计划约束、真正不可恢复图损坏 | 才按对应结构错误处理（如 `task_plan_state_invalid`） |

**剩余工作计数**：`RemainingWorkUnits` 表示**本次裁决后**仍未完成的必需工作数。必须按绑定计划**同一版本的全部必需 depth1 节点**（以及其完成所依赖的必需后代/子任务）核验，**不能**用"是否存在 SequenceNo 更大的下一个节点"做布尔近似，也不能只取第一个更大序号的节点。Cancelled/Superseded **不自动等于**义务消失，只有合法计划修订明确移除或替代才算满足；**未知必须保持 `null`**，不得冒充 0。当前单元只有真实验收通过后才能从剩余数中扣除。**最后一个 Running 可以在一次结算内被验证并完成**，不需要先用 task 工具把它置 Completed。

**实现约束**：`LoadBoundPlan`、候选装配、verifier、`ApplyBoundPlanGates`、`ApplyBoundPlanVerdict`、continuation 与重启恢复**全部**必须接受"无 Current"的合法收敛态，消除空指针与重复 advance；不为保持 running=1 造虚拟节点，不重复完成最后节点，不新增第二套事务或独立循环。

### 13.2 原子完成与结算权限

必需 Goal 条件全部通过**且**新鲜度有效后，在**短 Serializable 事务**内重验 Goal/epoch、Task 版本、binding、plan 版本、assignment/reservation fencing，并原子写入：Task `Completed`/`CompletedAtUtc`、Goal `Completed`、Plan/root/node、verification、binding/reservation/assignment 释放、canonical `TaskCompleted` 事件。**提交前验证 active fence，提交内释放**；严禁"先调 task 完成工具释放，再回来结算"。

- `CanSettleCompleted` 单列结算权限：正常 `InProgress` 可结算；`Assigned` 仅当匹配当前 active assignment/binding/epoch **且**已有真实执行与完整验收证据；`Blocked`/`NeedsReview`/`Failed`/`Cancelled` 不得被强行完成。**不放宽通用 Task 状态迁移表**。
- 重复结算必须幂等：只有一次 `TaskCompleted`/释放，完成后没有额外 continuation。
- 历史已释放 reservation / 旧 epoch **不得**为通过而强置 active 或放松 fence：走显式恢复/admission 重新取得合法 assignment 与 fence；等待期间保留逻辑 Goal/Task 绑定、释放执行占用、给出明确恢复事件。取消与用户暂停始终优先。

### 13.3 封旁路 + completion proposal

绑定中 Task 被 Agent 直接提交 `Completed` 时拒绝（不写状态、不释放 reservation），返回 `completion_owned_by_goal_settlement`；**同时必须提供真实可用的 completion proposal 入口**由结算消费——只封不疏等于把完成路堵死。需再审一遍其他能写 Task `Completed` 的路径是否仍可先释放 reservation。不得阻断用户合法取消/暂停。

**本仓库采用的 completion proposal 入口（已实现，无需新工具）**：当前 WorkUnit 的必需条件取得**真实 passed 的检查证据** + 该迭代按 canonical Turn **正常结束**；结算扫描把这一组合当作完成提议，整体验证通过后在同一事务内原子写 Goal/Task/Plan 双终态。因此 Agent **不需要**（也**不应该**）先把 Task 置为 Completed。注意 `NeedsReview` 是"等人工复核"的否决态（P3 门禁会拦下完成），Agent 不得用它代替证据充当完成提议。
