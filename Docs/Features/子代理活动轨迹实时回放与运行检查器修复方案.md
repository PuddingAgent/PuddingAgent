## 1. 结论

本次现象不是子代理没有执行，也不是运行归档没有写入。故障发生在“权威事件已经持久化之后，浏览器活动运行投影之前”。

现场抽屉在 Run 已运行约 29 分钟时仍显示：

- 阶段“启动运行时”；
- 轮次、Token、工具均为 0；
- 时间线为“暂无运行事件”。

同一时刻的运行归档和平台事件库却持续增长。Run 最终于 2026-08-26 19:48:15 完成，归档终值为：

| 证据 | 结果 |
|---|---|
| `run.json` | `completed`，19:16:21 开始，19:48:15 完成 |
| `events.jsonl` | 383 条，首事件 `subagent.run.created`，末事件 `subagent.run.completed` |
| `conversation-projection.cursor` | `383`，与归档事件数一致 |
| 轮次 | 59 次 `round.started` + 59 次 `round.completed` |
| 模型调用 | 59 次 started + 59 次 completed |
| 工具调用 | 71 次 started，66 次 completed，5 次 failed |
| `conversation_events` | 运行期间已查询到同一父会话、同一 Run 的持续增长 canonical 事件 |

因此故障边界是：

```text
SubAgent Runtime
  → run archive（正常）
  → conversation-projection.cursor（正常）
  → conversation_events（正常）
  → Session SSE / bootstrap / gap replay（需要修复和验收）
  → subAgentReducer / SubAgentActivityDock（当前页面状态失真）
```

另一个已确认的放大因素是前端构建漂移：当前浏览器页加载 `umi.ec3e4c41.js`，而服务器入口和 `Source/PuddingPlatformAdmin/dist/index.html` 均已指向 `umi.918d59c5.js`；服务器对旧 Bundle 已返回 404。也就是说，当前页没有执行仓库和服务器上最新的前端实现。旧 Bundle 清理、入口缓存策略和 build identity 由《Chat图片消息回放与前端旧Bundle缓存修复方案》统一负责，本方案不再建设第二套缓存兼容层。

## 2. 当前实现审计

### 2.1 已经正确的边界

`SubAgentActivityDock.tsx` 已明确：活动 Run 只消费 Conversation SSE 的 `subAgentReducer` 状态；只有终态 Run 才一次性读取 `events.jsonl` 归档。这个边界必须保留。

原因是 Windows 上活动期间读取 `events.jsonl` 曾与归档 writer 发生 sharing violation。禁止用“每 3 秒轮询活动归档”掩盖 SSE/投影问题。

`SessionEventsController` 当前也已经：

- 用 `conversation_events` 提供历史和 SSE；
- Bootstrap 返回最多 500 条最近的 `subagent.*` 事件；
- SSE 支持 `Last-Event-ID` / `afterSequence`；
- cursor 低于保留窗口时返回 `snapshot_required`。

`subAgentReducer` 已经：

- 只接受 canonical `subagent.run.* / round.* / llm.* / tool.*`；
- 以 canonical `runId` 合并事件与状态快照；
- 对 eventId 去重；
- 对终态做单调保护。

这些能力说明修复应落在同一 canonical 链路中，而不是增加 legacy 事件或归档轮询兼容分支。

### 2.2 仍存在的缺口

#### 缺口 A：回放补偿只把“主消息活动”当作活跃条件

`useSessionEventReplay.ts` 的补偿判定只传入 `hasActiveMessages`。当异步子代理仍运行、父 Turn 已结束时，低频 gap replay 可以被跳过。SSE 一旦断开、浏览器休眠或漏收，该 Run 只能靠 10 秒状态接口重建一张“运行中、0 轮、0 工具”的空卡片，内部轨迹不会自动追平。

#### 缺口 B：状态快照能重建卡片，但不能证明活动投影已经追平

`GET /api/sessions/{sessionId}/sub-agents` 当前状态快照包含 Run 身份和终态，但没有 `lastEventSequence`、`lastActivityAt`、轮次、Token 和工具聚合。前端无法区分：

- 子代理真的刚创建、尚无事件；
- canonical 事件已经推进，但浏览器漏收；
- 浏览器正在使用旧 Bundle；
- reducer 收到事件但因身份或协议错误拒绝。

#### 缺口 C：空活动卡片没有显式降级状态

活动 Run 的 `activities` 为空时，检查器直接显示“暂无运行事件”，阶段仍来自状态快照的 `starting`。即使已持续几十分钟，也不会提示“实时轨迹未同步”，导致用户误判 Runtime 卡死。

#### 缺口 D：活动工具计数被展示列表上限截断

reducer 只保留最近 50 个 `tools`，而 `projectSubAgentRunsToCards` 使用 `run.tools.length` 作为 `toolCount`。长 Run 的活动工具计数最多显示 50；失败数也只统计最近 50 个工具。列表有界是正确的，但聚合计数必须与有界详情分离。

#### 缺口 E：Bootstrap 的 500 事件窗口不足以提供长 Run 的权威累计值

500 条最近事件足够恢复本次 383 条事件的 Run，但对 600 轮上限的长任务不保证覆盖完整执行。它可以恢复“最近活动”，不能同时承担“全量计数快照”。

#### 缺口 F：部署态缺少可见 build identity

当前页加载服务器已不存在的旧 Bundle，但 Chat 页面和诊断日志没有直接显示“浏览器 build / 服务器 build 不一致”。这使业务故障和部署缓存故障难以区分。

## 3. 目标状态

活动子代理的 UI 数据源固定为：

```text
conversation_events
  ├─ Bootstrap：当前状态 + 最近活动 + snapshot cursor
  ├─ SSE：snapshot cursor 之后的实时增量
  ├─ Gap replay：主 Turn 或子代理任一活跃时均可追平
  └─ Status snapshot：Run 身份、终态与聚合校验水位

终态 run archive
  └─ 只在终态一次性读取，用于完整历史和 output.md
```

必须满足：

1. 活动 Run 不读取、轮询或 tail `events.jsonl`。
2. 同一事件在 Bootstrap、Replay、SSE 重叠到达时只累计一次。
3. 父 Turn 结束但异步子代理仍运行时，SSE 与 gap replay 继续工作。
4. UI 能明确区分“确实尚无事件”和“canonical 水位已前进但客户端未追平”。
5. 详情列表可以有界，但轮次、Token、工具和失败计数不能被列表窗口截断。
6. 浏览器 build 与服务器 build 不一致时先提示刷新，不把旧前端错误归因给 Runtime。

## 4. 代码级修改方案

### P0：先消除旧 Bundle 执行态

Owner：已有任务 `ceba781342aa4353901654d1897092cb` 与《Chat图片消息回放与前端旧Bundle缓存修复方案》。

- `index.html` / 路由入口使用 `no-store` 或强制重新验证；哈希静态资源使用 immutable 长缓存。
- `pwa=false` 时在 `localhost` HTTP 和 Desktop WebView2 中也注销历史 Service Worker、删除 Pudding 命名 Cache Storage；不能以 HTTPS / `isSecureContext` 作为清理前提。
- 服务器响应或 HTML meta 暴露不含敏感信息的 `buildId`；Chat 诊断记录 `clientBuildId/serverBuildId`。
- 发现 build 不一致时显示可操作提示并执行一次受控刷新；不得无限 reload。

本 P0 是本事故在线验收前置，但不复制到本任务中重复实现。

### P1-A：把活动子代理纳入 SSE 回放补偿

文件：

- `Source/PuddingPlatformAdmin/src/pages/chat/hooks/useSessionEventReplay.ts`
- `Source/PuddingPlatformAdmin/src/pages/chat/hooks/useSessionEventConnection.ts`
- `Source/PuddingPlatformAdmin/src/pages/chat/utils/chatStateUtils.ts`

修改：

1. 从现有 `subAgentRuns` 计算 `hasActiveSubAgentRuns`，活跃集合为 `created/running`。
2. `shouldRunSessionReplayCompensation` 输入改为 `hasActiveMessages || hasActiveSubAgentRuns`，但埋点分别记录两者，避免再次混淆父 Turn 与子代理状态。
3. 活跃异步 Run 使用低频补偿；SSE 健康时不产生额外 REST 请求，超过 watchdog 窗口才 replay。
4. Replay 起点仍以 canonical `lastSequenceNumRef` 为准；不得以 Run archive offset 代替 Conversation sequence。
5. session 切换、generation 变化和 `snapshot_required` 继续 fail closed，旧连接不得向新会话写入。

### P1-B：增加可对账的子代理状态快照

文件：

- `Source/PuddingPlatform/Controllers/Api/SessionEventsController.cs`
- `Source/PuddingPlatform/Services/SessionStateManager.cs` 或新增只读 `SubAgentRunProjectionQuery`
- `Source/PuddingPlatformAdmin/src/services/platform/api.ts`
- `Source/PuddingPlatformAdmin/src/pages/chat/reducer/subAgentReducer.ts`

对每个 active Run 的状态响应增加：

- `lastEventSequence`；
- `lastActivityAt`；
- `currentRound`；
- `totalToolCalls` / `failedToolCalls`；
- `promptTokens` / `completionTokens` / `totalTokens`；
- `providerId` / `modelId`；
- `projectionState`：`current | lagging | unavailable`。

这些字段必须来自 canonical Conversation Event 投影或专用物化读模型，不得在请求中读取活动 `events.jsonl`。查询只覆盖当前会话的 active Run，并建立 `(conversation_id, run_id, sequence)` 所需索引或等价物化索引，避免每 10 秒全表扫描。

前端合并规则：

- 事件流提供过程详情；状态快照提供身份、终态和聚合对账值。
- 快照不能用较旧的 `lastEventSequence` 覆盖较新的 reducer 状态。
- 发现服务端 Run 水位高于客户端 Run 水位时触发一次有界 bootstrap/replay；相同水位重复失败进入 degraded，不循环请求。

### P1-C：修正 reducer 聚合与有界详情的职责

文件：

- `Source/PuddingPlatformAdmin/src/pages/chat/reducer/subAgentReducer.ts`
- `Source/PuddingPlatformAdmin/src/pages/chat/reducer/subAgentReducer.test.ts`

修改：

- 新增独立累计字段 `toolCallCount`、`failedToolCallCount` 和 `lastEventSequence`。
- `tools` 继续只保留最近 50 条详情，`activities` 继续只保留最近 100 条；UI 计数不再从数组长度派生。
- 工具 started/completed/failed 按 `toolCallId` 与 `eventId` 幂等累计，乱序到达不得重复计数。
- Bootstrap、Replay、SSE 和状态快照共享同一合并函数；不新增 legacy event 映射。
- 迟到的非终态事件不得把终态降级，较旧 sequence 不得倒退 phase、round 或 lastActivityAt。

### P1-D：检查器显示同步健康状态，而不是假“启动中”

文件：

- `Source/PuddingPlatformAdmin/src/pages/chat/components/SubAgentActivityDock.tsx`
- `Source/PuddingPlatformAdmin/src/pages/chat/components/SubAgentActivityDock.test.tsx`
- 对应样式文件

状态设计：

- `created` 且 canonical 水位没有过程事件：显示“等待运行时首事件”。
- active Run 超过 5 秒仍只有状态快照、但服务端水位已推进：显示“实时轨迹同步中”。
- 一次 bootstrap/replay 后仍未追平：显示“轨迹同步异常”，附最后客户端/服务端 sequence、build identity 和“重试同步”按钮。
- build identity 不一致：优先显示“前端版本已更新，请刷新”，不把它展示为 Runtime 启动故障。
- 终态后按现有规则一次性加载 archive；若 archive 读取失败，保留 canonical 终态和聚合，单独标记“完整归档加载失败”。

### P2：修正文档和诊断合同

- `Source/PuddingPlatformAdmin/code_map.md` 当前仍写“实时运行每 3 秒追平”，与源码的“活动 Run 零归档轮询”冲突；实施时改为 SSE + gap replay。
- `How-Debuge.md` 增加本次判定表：archive 增长、projection cursor 增长、`conversation_events` 存在而 UI 为空时，优先检查 build identity、SSE cursor/generation、replay gate 和 reducer 拒绝原因。
- 诊断事件增加 `chat.subagent.replay.requested/applied/degraded`，字段只含 sessionId/runId/sequence/count/buildId，不记录 prompt、工具参数或密钥。

## 5. 兼容性设计

项目仍处于开发阶段，本方案不建设长期兼容层：

- canonical `subagent.*` 事件名和 `runId` 是唯一协议；不恢复 `subagent.spawned/delta/completed` 映射。
- API 新字段为同版本前后端的附加读模型；部署必须 Core + Admin 同批切换，不维持两套 reducer。
- 旧 Bundle 只做检测、清理和一次受控刷新，不让新后端长期兼容旧前端错误行为。
- `events.jsonl` 归档格式不因本修复改变；活动读取继续禁止，终态 reader 保持一次性分页读取。
- 老的运行归档缺少聚合字段时，终态仍可从事件重放计算；这只是终态历史读取，不是活动兼容路径。

## 6. 测试与验收矩阵

### 后端

1. `SessionEventsController`：Bootstrap 含目标 Run 的有序 subagent 事件和可对账水位。
2. SSE：`Last-Event-ID` 后精确补发，断线重连不丢不重。
3. 状态快照：active Run 返回聚合与 `lastEventSequence`，且请求期间不打开 `events.jsonl`。
4. 保留窗口 gap：返回 `snapshot_required`，前端完成一次 Bootstrap 后恢复。
5. 查询性能：10 个 active Run、100 万行 `conversation_events` 下走索引且满足既定 API 延迟门。

### 前端

1. 父 Turn 已终态、异步子代理仍 active：低频 replay 继续运行。
2. 状态接口先到、created/started 漏收：卡片被重建，随后 Bootstrap/SSE 填充轨迹。
3. Bootstrap + Replay + SSE 重叠：同一 eventId 只累计一次。
4. 71 次工具调用：活动工具计数显示 71，详情仍最多保留 50 条。
5. active Run 超过阈值且服务端水位领先：显示“轨迹同步中/异常”，不得长期显示“启动运行时、0、暂无事件”。
6. 终态：停止活动补偿，archive 只读一次；加载失败不抹除 canonical 终态。
7. build identity 不一致：显示刷新提示并且最多自动刷新一次。

### 产品 smoke

1. 外部控制器部署明确的新 Core/Admin 构建，记录 server/client buildId。
2. 新建主会话，分别执行 sync 与 async 子代理；检查器在 2 秒或一个 SSE frame 内出现 round/llm/tool 活动。
3. 子代理执行中刷新页面、切换会话再返回、让 WebView2 短暂休眠，轨迹均能追平。
4. 执行超过 50 个工具调用的 Run，聚合数准确、DOM 仍有界。
5. 完成后检查 archive 一次性回放和完整输出。
6. 分别交付 `ready-for-external-deploy`、`in-product-functional-complete`；进程生命周期结论仍由外部控制器验收。
