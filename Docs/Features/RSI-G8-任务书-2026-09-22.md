### B. 节奏循环本体 ✅

`SubconsciousWorkerService.cs:779-805`：

```csharp
private async Task RunPeriodicEnqueueLoopAsync(
    string jobType, TimeSpan initialDelay, TimeSpan interval, CancellationToken ct)
{
    await Task.Delay(initialDelay, _timeProvider, ct);              // :781

    while (!ct.IsCancellationRequested)                             // :784
    {
        try
        {
            if (_runtimeControl?.IsPaused != true)                  // :789
                await EnqueuePeriodicJobAsync(jobType, interval, ct); // :792
        }
        catch (OperationCanceledException) when (ct.IsCancellationRequested) { break; }
        catch (Exception ex) { _logger.LogWarning(ex, "...Periodic enqueue failed jobType={JobType}", jobType); }

        await Task.Delay(interval, _timeProvider, ct);              // :804
    }
}
```

⭐ **关键事实**：这个循环**不做任何时间判定**（不看小时、不看工作日、不看堆积量）。它只有"等 `interval` → 入队一次"。

### D2 非工作时段判定器（**显式**本地时间 + 窗口）

- **落点**：与 D1 同侧（纯判定，无 IO）。
- **内容**：输入 `DateTimeOffset now`（由调用方用 `_timeProvider.GetLocalNow()` 提供）+ 窗口 ⇒ `bool IsOffPeak`（含**跨午夜**窗口语义）。
- **不变式**：P3、P5。
- **必须能变红的用例**：
  - 边界包含性（窗口起点/终点是否含）；
  - **跨午夜窗口**（如 22:00–08:00）在 23:30 与 07:30 均为真、12:00 为假；
  - `IsOffPeak_ShouldUseLocalTime_NotUtc`（构造 UTC 与本地不同的小时 ⇒ 断言取本地）；
  - 时区/窗口缺失 ⇒ 返回"沿用默认"（P5）。
- **取红方式**：①把 `GetLocalNow()` 换成 `GetUtcNow()` ⇒ 红；②把 `<=` 换 `<` ⇒ 红；③去掉跨午夜分支 ⇒ 红。

### §4.4 D3 前置可行性裁决（2026-09-22；**发现「窗口内加速」在现有幂等键下是空操作**）

> 本节写在 D3 **实现之前**，因为盘查发现：按 D3/D4 原文实现会交付一个
> **看得见记录、看不见效果**的幻影功能。**本节优先于 §4.1 中 D3/D4 行的原始期望**。

**证据（父代理亲读，落点逐行）**

1. `SubconsciousWorkerService.RunPeriodicEnqueueLoopAsync`（`:779-805`）循环体只做两件事：
   `EnqueuePeriodicJobAsync(jobType, interval, ct)` 与 `Task.Delay(interval)`。
2. `EnqueuePeriodicJobAsync`（`:807-850`）：`bucket = GetUtcNow().UtcTicks / Math.Max(1, interval.Ticks)`（`:817`）；
   键 = `periodic:{jobType}:{workspaceId}:{agentInstanceId}:{bucket}`（`:818`）；
   以该键 `FindLatestAsync({ IdempotencyKey })` 命中则直接 `return`（`:819-827`）。
3. `SubconsciousJobQueue.FindLatestAsync`（`PuddingMemoryEngine/Services/SubconsciousJobQueue.cs:166-196`）：
   过滤条件只有 `JobId / IdempotencyKey / SourceHookName / SourceCompactionId / WorkspaceId / SessionId`
   （`:186-196`），**没有任何 Status 过滤** ⇒ 已完成 / 重试中 / 死信的**历史行同样参与去重**。
4. `SubconsciousJobQueue.EnqueueAsync`（同文件 `:64`）：插入前
   `FirstOrDefaultAsync(j => j.IdempotencyKey == request.IdempotencyKey)` ⇒ **队列自身也按 key 去重**
   （独立第二层保证，与 worker 的预查互为冗余）。

**推论（确定性，不依赖运行时观测）**

- 周期作业的**创建速率** = 每个 `(jobType, workspace, agent)` 每个 **bucket 窗口 ≤ 1 条**，
  而窗口长度 = **配置间隔**（`bucket` 的除数就是传进来的 `interval`）。
- `Task.Delay(interval)` 只决定「在窗口内**何时**尝试」⇒ **只缩短 delay、不换 bucket 除数，作业数量一条不变**
  （只是更频繁地做一次幂等查询）。⇒ D4 原文的字面实现（“非工作时段 ⇒ 采用策略间隔”）**对频率零影响**。
- 要真正提高频率，必须让 `bucket` 的除数一起变小 ⇒ 同一 jobType 在一个配置窗口内产生多个新键
  ⇒ **等于引入第二套 bucket 口径**（与已冻结的 P6 直接冲突）；并且幂等键是**持久化行**，
  口径变更会同时影响历史键与跨升级去重；窗口切换处还会多出 1 次入队（上界需单独证明）。

**三个选项**

| 选项 | 内容 | 结论 |
|---|---|---|
| A | 只缩短 `Task.Delay`，bucket 不动（D4 原文） | **零效果**，而日志/记录会显示“采用间隔已缩短”⇒ 典型幻影；**否决** |
| B | 同时把 bucket 除数换成采用间隔 | 真能加速；但 = 第二套 bucket 口径（违反 P6）、改变持久化幂等键口径、且**无度量**（宪法 C5：无度量不调参）；**不在本切片** |
| C | 本切片只交付「纯判据 + 决定记录」 | 保留 P1 零回归与全部可观测价值；**采纳** |

**裁决（冻结）**

1. **采 C**：D3 只交付**决定记录通道**（尾随可选参数默认 `null` ⇒ 走今天的分支），
   ⛔ **不改 `Task.Delay`、不改 `bucket`、不改配置绑定**。
2. **记录字段一律使用“提案”语义命名**：`rhythm_proposed_interval_seconds`（而非裸 `rhythm_interval_seconds`）、
   `rhythm_configured_interval_seconds`、`rhythm_reason_code`、`rhythm_off_peak`、`rhythm_backlog`、
   `rhythm_shortened`、`rhythm_policy`（`{policyId}@{version}`）。
   理由：采用间隔**当前不改变任何调度**，裸名会被后来者读成已生效
   （同 G4「记录 ≠ 生效」与 G7「只写日志不算被记录」的教训）。
3. **D4 / D5 的“采用间隔”降级为“记录 + 显式标注未生效”**；其取红用例期望同步修改（§4.1 / §5 / §6 三处）。
4. **新增不变式 P9**：*记录中的字段名必须与行为的真实影响一致（提案 ≠ 生效）*；违反即视为幻影生效。
   载体：D3 的 metadata 键集合**等值断言**（多出一个裸 `rhythm_interval_seconds` ⇒ 红）。
5. **P6 原文不动**。将来要做选项 B，必须先：①显式修改 P6 并给出边界重复上界证据；
   ②先有度量（“跑得更频繁”到底改善了什么）；③评估幂等键持久化口径变更的影响。
6. **本切片诚实边界（必须与 D1/D2 的禁令一起读）**：非工作时段与条件触发在 G8 内
   **不会改变任何作业频率**；G8 交付的是**判据 + 可解释记录**，不是“重活已落在非工作时段”。
