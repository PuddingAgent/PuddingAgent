### 1.1 「只从成功学」（ADR-064）的**可执行形态**

`ConversationSkillEvolutionTrajectorySource` 里三处把语义钉死：

1. 事件里出现任何 `ToolCallFailed` ⇒ `TryBuildSuccessfulSteps` **`return null`**（**整条轨迹丢弃**，不是跳过该步）；
2. `IsSuccessful(payload)` 要求 **`exitCode == 0` 且 `error` 为空**；
3. 且要求 `steps.Count >= 2`（单工具调用不构成可学习轨迹）。

⇒ 结论：既有管道**在语义上根本看不到失败**。这正是"不可改它"的原因——改它等于让既有技能提取**静默开始把失败当经验学**，且不会有任何报错。

### 1.2 已有可复用的**选择钩子**

`IsExcludedFromLearning(metadataJson)` 读 `ExecutionCommandRow.MetadataJson` 里的 **`excludeFromLearning`**（接受 `true` 或字符串 `"true"`）。
⇒ 这是**既有的"某条命令不参与学习"机制**。任何新增的轨迹消费（含 RSI）应**复用同一钩子**，不要另造一套排除语义。

## 2. ⭐ 关键发现：成功约束被**执行了两次**，S3 不能只"加一个 source"

| 层 | 约束 |
|---|---|
契约层 | 接口名与文档都限定 **successful** |
数据访问层 | **`GetRecentSuccessfulCommandsAsync` —— 名字与语义都是 success-only**；`ISkillEvolutionDataAccess` **没有**"取最近命令（不论成败）"的方法 |

**这条直接改变实施方案**：RSI 需要**失败与结局**（用来学"什么不该做"），而失败的**入口在下层就被切掉了**。若按直觉"再写一个轨迹源"，实现到一半才会发现**查不到失败命令** —— 典型的中途撞墙（也是典型的补丁起点）。

## 3. 方案取舍（S3 正式规格须二选一并说明理由）

| 方案 | 做法 | 代价 / 风险 |
|---|---|---|
**A 扩展既有数据接缝** | 给 `ISkillEvolutionDataAccess` 加 `GetRecentCommandsAsync(...)`（含成败）| 动到 ADR-064 所在的那条链的**邻接面**；方法一旦存在，未来任何人都可能拿它喂既有提取管道 ⇒ **语义护栏只剩约定**。且要同时改 PuddingCore 契约 + PuddingPlatform 实现 + 既有测试 |
**B 独立数据接缝**（倾向） | 新增 RSI 自己的数据访问/轨迹源（如 `IRsiTrajectoryDataAccess` / `IRsiTrajectorySource`），**ADR-064 那条链一行不改** | 需要一份（小）重复的查询实现；换来的是**失败语义只存在于 RSI 路径**，既有管道在类型层面就够不到它 |

**倾向 B 的理由（不是"更干净"，而是"更难被误用"）**：
A 的护栏是**命名与约定**；B 的护栏是**类型系统**。在"错用一次就静默学错"的场景里，类型护栏优先。

> ⚠️ 但 B **不得**被误读为"复制一套 ADR-064 逻辑"：RSI 与既有管道对"成功"的定义**本来就不同**（既有：整条轨迹全成功；RSI：需要**结局标注**而不是过滤）。B 应直接消费**带结局的事件**，而不是在 RSI 侧重写一遍过滤规则。

## 4. 与 T2 的闭环（重要）

T2 规格 §2.1 故意把「**回合结局**」**排除**在打分器上下文之外（不用 0 占位）。
本文给出它的**来源与到达时点**：

- 结局事实存在于 **canonical conversation 事件**（`ToolCallRequested / ToolCallCompleted / ToolCallFailed` + payload 的 `exitCode` / `error`）；
- 但**既有数据访问只暴露成功命令** ⇒ 结局目前**拿不到**；
- ⇒ **「回合结局」进入打分输入的时点 = S3**，不是 T2。

⇒ 这正是 T2 §2.1 那条规矩的价值：**缺的输入不进类型**，于是"什么时候能补上"变成一个**有明确答案的问题**，而不是一个悄悄填 0 的历史包袱。

## 5. 待核清单（S3 规格开工前必须核实，**不得猜测**）

1. `SkillEvolutionTrajectory` / `SkillEvolutionToolStep` 的完整字段（`Source/PuddingCore/Platform/SubconsciousDtos.cs:387` 起）——判断能否直接复用，还是 RSI 需要自己的形状。
   → ✅ **已核（2026-09-21 23:15）：RSI 必须有自己的形状，不得复用。**原文（`SubconsciousDtos.cs:388-402`）：
   - `SkillEvolutionTrajectory` = `WorkspaceId`/`AgentInstanceId`/`SessionId`/`TurnId`/`Goal`（均 required）+ `Steps`
   - `SkillEvolutionToolStep` = `ToolName`(required) + `Arguments`(?="{}") + `Output`(?)
   类型注释原文：`Canonical successful tool trajectory used by the experience-to-Skill pipeline.`
   **三条不可复用的理由（逐条对应字段事实）**：
   - `SkillEvolutionToolStep` **无 `Outcome`/`exitCode`/`error` 字段**，也**无 `Sequence`/`EventId`/时间戳**
     ⇒ 它**在类型层面就装不下「回合结局」**，而结局正是 T2 缺、S3 要补的那个输入（§4）；
   - 它的语义是 **successful-only**（注释原文）⇒ 复用它等于**把 ADR-064 的“只从成功学”约束原样搬回 RSI**，
     正是本片要避开的东西（§3 的“成功定义本就不同”）；
   - 给这个 **PuddingCore/Platform 共享 DTO 加字段**会同时（a）动到 ADR-064 那条链的公共类型，与 §6 标准 1「零回归」直接冲突；
     （b）把“成功步”与“带结局标注的步”语义混为一谈。
   **结论**：本项是 **B 方案（独立 RSI 数据接缝）的第二个独立证据** —— 不是“更干净”，而是**A 方案在类型上就做不到**。
2. 既有管道**谁**在调用 `GetRecentSuccessfulAsync`、调用频率与并发（决定新增查询的成本与索引需求）。
   → ✅ **已核（2026-09-21 22:40）**：见 §2.1，**零生产消费方**（调用点仅在一个测试文件里）。
3. 事件 store 的**可用索引**：按 `CommandId` + `Sequence` 取事件是否已建索引（否则 RSI 的全量扫描会拖慢宿主）。
   → ⛔ **已核（2026-09-21 23:10）：没有 `CommandId` 索引 —— 现有查询是“无索引支撑”的**。
   `conversation_events` 的**全部**索引（`PlatformDbContext.cs:587-595`，表名 `conversation_events`）：
   ① `(ConversationId, Sequence)` UNIQUE　② `EventId` UNIQUE　③ `(TurnId, Type)`　④ `CommittedAt`（ADR-076 retention）。
   ⇒ **`CommandId` 上没有任何索引**，而既有 `GetEventsByCommandIdsAsync`（`SkillEvolutionDataAccess.cs:47-60`）
   正是 `WHERE command_id IN (...) AND type IN (...) ORDER BY sequence`
   ⇒ 计划器只能**全表扫描** `conversation_events`；append-only + 按 committed_at 裁剪 ⇒ 表长期很大 ⇒ 代价随**事件总量线性增长**。
   **对 S3 的三条后果（本项最有价值的产出）**：
   - ⚠️ **不得原样复用** `GetEventsByCommandIdsAsync` 的查询形状作为 RSI 的取数方式；
   - ✅ **存在已索引的可行路径**：`(TurnId, Type)` 已被索引 ⇒ 按 **TurnId + 事件类型**取事件是**索引支撑**的，
     而 T2 需要的「回合结局」（`ToolCallCompleted` / `ToolCallFailed`）**本来就是按 turn 定位**的 ⇒ 正好走这条路；
   - 若确实需要按 `CommandId` 查，必须**显式**新增 `(CommandId, Sequence)` 索引（= 平台迁移 + 写放大评估），
     不得“看起来能跑”就上线；且必须在 S3 规格里给出**实测**行数与耗时，而非推断。
   - 🔎 **附带发现（同源问题）**：既有管道的**第一个查询**同样缺索引 ——
     `chat_execution_commands` 的**全部**索引（`PlatformDbContext.cs:535-542`）= `CommandId` UNIQUE /
     `(BatchId, AgentInstanceId)` UNIQUE / `(WorkspaceId, ClientRequestId)` / `(SessionId, Status)` /
     `(Status, LeaseUntil)` / `(Status, CreatedAt)`；
     而 `GetRecentSuccessfulCommandsAsync` 的谓词是 `(WorkspaceId, AgentInstanceId, Status='succeeded')`、
     排序键是 `CompletedAt ?? CreatedAt` ⇒ **没有支撑该谓词的索引，`CompletedAt` 也没有索引**；
     最接近的 `(Status, CreatedAt)` 只能覆盖 `Status` 前缀、**无法提供排序**。
   - 🧭 **因果（比缺陷本身重要）**：这两条“无索引查询”能活到今天，正因为该管道**零生产消费方**（§2.1 冬眠）
     ⇒ **冬眠解释了缺陷为何未被发现**。若 RSI 直接复用这条形状并**定期**跑在大事件表上，
     **RSI 会成为第一个付代价的人**。 ⇒ 「不得复用」不是审美偏好，而是**有证据的风险判断**。

6. 是否存在**跨 workspace** 的轨迹聚合需求（当前接口签名是单 workspace + 单 agent）。
   → ✅ **已核（2026-09-21 23:20）：不需要 —— 而且在本层做是语义错误。**
   **代码事实**：`AgentSkillFileService` 的每一个 API 都以 `agentInstanceId` 为键，**没有任何 workspace 参数** ——
   `GetSkillsRoot(agentInstanceId)` / `ResolveSkillRoot(agentInstanceId, skillId)` / `GetIndexPath(agentInstanceId)` /
   `_paths.AgentInstanceRoot(agentInstanceId)`（文件头注释原文：`Filesystem-backed SKILL service for runtime-private Agent instance skills.`；
   目录形如 `agents/{agentInstanceId}/skills`，见 `PuddingDataPaths.cs:32`）。
   ⇒ **技能身份是 agent 级的**（不同 agent 的同名 `skillId` 是**不同产物**：不同目录、不同 `contentHash`、可能不同版本/内容）。
   因此跨 workspace 聚合会把**不同产物算在同一 id 下**，得到一个“描述不了任何东西”的数；
   也会让 T2 上下文里已包含的 `SkillId` 在 `InputDigest` 中变成**歧义身份**。
   ⇒ **RSI 的轨迹/用量查询保持 (workspace, agentInstanceId) 双键作用域**（与既有接口签名一致）；
   “跨 agent 学同一个技能”属于**技能传播/共享**问题（skill hub / package），**不是用量聚合问题**。
   - ⚠️ **顺带发现一个会静默污染指标的陷阱（必须写进 S3 规格）**：
     遥测落点是 `DataRoot/skill-usage/skill-usage-{yyyyMMdd}.jsonl`（`PuddingDataPaths.cs:35`）——
     **路径里没有 agent 段**，而**同一个 DataRoot 下住着多个 agent**（如 `D:\data\agents\<agentId>\` 与 `D:\data\skill-usage` 同根）。
     ⇒ **文件路径不是作用域，`SkillUsageRecord.AgentInstanceId` 字段才是作用域**；
     RSI 读取时**必须按字段过滤**，否则会把同根下**其他 agent 的用量算进来**
     （典型的静默错误：某技能“被注入 3 次”变成 12 次，而分数看上去仍然“合理”）。

## 6. S3 验收标准草稿（正式规格时细化并冻结）

1. **ADR-064 零回归**：`Source/PuddingCore/Abstractions/ISkillEvolution.cs`、`Source/PuddingCore/Platform/ISkillEvolutionDataAccess.cs`、`ConversationSkillEvolutionTrajectorySource.cs` **均无改动**（用 `git diff --stat` 证据，而不是口头声明）。
2. **结局可得**：能取到带 `outcome`（成功/失败/未知）的轨迹步，且**失败步不被整体丢弃**（有专门用例）。
3. **选择钩子一致**：`excludeFromLearning=true` 的命令在 RSI 路径**同样被排除**（用例覆盖 `true` 与字符串 `"true"` 两种形态）。
4. **确定性**：同一 (workspace, agent, 时间窗) 两次查询结果稳定（排序键显式，不依赖 DB 返回顺序）。
5. **成本可证**：给出查询在真实库上的**行数上限**与耗时量级（不得"看起来很快"）。
6. **空态 ≠ 无使用**：无轨迹时返回空集合 + 明确原因码，**不得**用 0 值对象冒充。
