### 1.1 「只从成功学」（ADR-064）的**可执行形态**

`ConversationSkillEvolutionTrajectorySource` 里三处把语义钉死：

1. 事件里出现任何 `ToolCallFailed` ⇒ `TryBuildSuccessfulSteps` **`return null`**（**整条轨迹丢弃**，不是跳过该步）；
2. `IsSuccessful(payload)` 要求 **`exitCode == 0` 且 `error` 为空**；
3. 且要求 `steps.Count >= 2`（单工具调用不构成可学习轨迹）。

⇒ 结论：既有管道**在语义上根本看不到失败**。这正是"不可改它"的原因——改它等于让既有技能提取**静默开始把失败当经验学**，且不会有任何报错。

### 1.2 已有可复用的**选择钩子**

`IsExcludedFromLearning(metadataJson)` 读 `ExecutionCommandRow.MetadataJson` 里的 **`excludeFromLearning`**（接受 `true` 或字符串 `"true"`）。
⇒ 这是**既有的"某条命令不参与学习"机制**。任何新增的轨迹消费（含 RSI）应**复用同一钩子**，不要另造一套排除语义。

## 2. ⭐ 关键发现：成功约束被**执行了两次**，S3 不能只"加一个 source"

| 层 | 约束 |
|---|---|
契约层 | 接口名与文档都限定 **successful** |
数据访问层 | **`GetRecentSuccessfulCommandsAsync` —— 名字与语义都是 success-only**；`ISkillEvolutionDataAccess` **没有**"取最近命令（不论成败）"的方法 |

**这条直接改变实施方案**：RSI 需要**失败与结局**（用来学"什么不该做"），而失败的**入口在下层就被切掉了**。若按直觉"再写一个轨迹源"，实现到一半才会发现**查不到失败命令** —— 典型的中途撞墙（也是典型的补丁起点）。

## 3. 方案取舍（S3 正式规格须二选一并说明理由）

| 方案 | 做法 | 代价 / 风险 |
|---|---|---|
**A 扩展既有数据接缝** | 给 `ISkillEvolutionDataAccess` 加 `GetRecentCommandsAsync(...)`（含成败）| 动到 ADR-064 所在的那条链的**邻接面**；方法一旦存在，未来任何人都可能拿它喂既有提取管道 ⇒ **语义护栏只剩约定**。且要同时改 PuddingCore 契约 + PuddingPlatform 实现 + 既有测试 |
**B 独立数据接缝**（倾向） | 新增 RSI 自己的数据访问/轨迹源（如 `IRsiTrajectoryDataAccess` / `IRsiTrajectorySource`），**ADR-064 那条链一行不改** | 需要一份（小）重复的查询实现；换来的是**失败语义只存在于 RSI 路径**，既有管道在类型层面就够不到它 |

**倾向 B 的理由（不是"更干净"，而是"更难被误用"）**：
A 的护栏是**命名与约定**；B 的护栏是**类型系统**。在"错用一次就静默学错"的场景里，类型护栏优先。

> ⚠️ 但 B **不得**被误读为"复制一套 ADR-064 逻辑"：RSI 与既有管道对"成功"的定义**本来就不同**（既有：整条轨迹全成功；RSI：需要**结局标注**而不是过滤）。B 应直接消费**带结局的事件**，而不是在 RSI 侧重写一遍过滤规则。

## 4. 与 T2 的闭环（重要）

T2 规格 §2.1 故意把「**回合结局**」**排除**在打分器上下文之外（不用 0 占位）。
本文给出它的**来源与到达时点**：

- 结局事实存在于 **canonical conversation 事件**（`ToolCallRequested / ToolCallCompleted / ToolCallFailed` + payload 的 `exitCode` / `error`）；
- 但**既有数据访问只暴露成功命令** ⇒ 结局目前**拿不到**；
- ⇒ **「回合结局」进入打分输入的时点 = S3**，不是 T2。

⇒ 这正是 T2 §2.1 那条规矩的价值：**缺的输入不进类型**，于是"什么时候能补上"变成一个**有明确答案的问题**，而不是一个悄悄填 0 的历史包袱。

## 5. 待核清单（S3 规格开工前必须核实，**不得猜测**）

1. `SkillEvolutionTrajectory` / `SkillEvolutionToolStep` 的完整字段（`Source/PuddingCore/Platform/SubconsciousDtos.cs:387` 起）——判断能否直接复用，还是 RSI 需要自己的形状。
2. 既有管道**谁**在调用 `GetRecentSuccessfulAsync`、调用频率与并发（决定新增查询的成本与索引需求）。
3. 事件 store 的**可用索引**：按 `CommandId` + `Sequence` 取事件是否已建索引（否则 RSI 的全量扫描会拖慢宿主）。
4. `excludeFromLearning` 当前**由谁写入**（是否有管理入口），决定 RSI 是否可以直接依赖它。
5. 事件保留期 / 裁剪策略（若事件会被裁剪，轨迹窗口必须与之对齐，否则"可用轨迹"会随裁剪凭空消失）。
6. 是否存在**跨 workspace** 的轨迹聚合需求（当前接口签名是单 workspace + 单 agent）。

## 6. S3 验收标准草稿（正式规格时细化并冻结）

1. **ADR-064 零回归**：`Source/PuddingCore/Abstractions/ISkillEvolution.cs`、`Source/PuddingCore/Platform/ISkillEvolutionDataAccess.cs`、`ConversationSkillEvolutionTrajectorySource.cs` **均无改动**（用 `git diff --stat` 证据，而不是口头声明）。
2. **结局可得**：能取到带 `outcome`（成功/失败/未知）的轨迹步，且**失败步不被整体丢弃**（有专门用例）。
3. **选择钩子一致**：`excludeFromLearning=true` 的命令在 RSI 路径**同样被排除**（用例覆盖 `true` 与字符串 `"true"` 两种形态）。
4. **确定性**：同一 (workspace, agent, 时间窗) 两次查询结果稳定（排序键显式，不依赖 DB 返回顺序）。
5. **成本可证**：给出查询在真实库上的**行数上限**与耗时量级（不得"看起来很快"）。
6. **空态 ≠ 无使用**：无轨迹时返回空集合 + 明确原因码，**不得**用 0 值对象冒充。
