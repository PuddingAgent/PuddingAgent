## 0. 本片只解决一件事

把「**回合结局**」变成 RSI 可消费的输入 —— 且**一行都不改 ADR-064 那条链**。

T2 规格 §2.1 故意把「回合结局」排除在打分器上下文之外（**不用 0 占位**），因此"什么时候能补上"是一个
**有明确答案的问题**。本片就是那个答案：**结局进入打分输入的时点 = S3**。

## 1. 事实基础（全部已核，附文件:行）

### 1.1 ⭐⭐ 最重要的一条：`tool.call.failed` **没有生产者**

- 常量确实存在：`Source/PuddingCore/Platform/ConversationContracts.cs:105-106`
  （`ToolCallCompleted = "tool.call.completed"`、`ToolCallFailed = "tool.call.failed"`）；
- **但折叠层自己写着**（`Source/PuddingCore/Platform/ConversationTranscriptFold.cs:403-406`，注释原文）：

  ```
  // 证据来源：tool.call.failed 当前无生产写入点；防御性按同一字段契约读取。
  ```

⇒ **结局不能靠"等一个 `tool.call.failed` 事件"获得** —— 那样的实现会**永远拿不到失败**。
真实结局**编码在 `tool.call.completed` 的 payload 里**。

- 生产写入点（同一文件注释原文）：`AgentExecutionService.Streaming` 写入
  `{ name, toolCallId, exitCode, output, error }`；
- payload 读取契约（`ConversationTranscriptFold.cs:409-419` 实测）：
  `toolCallId`、`name`、`output`、`error`、`exitCode`（**含 `exit_code` 回退**）。

⇒ 这与 ADR-064 的 `IsSuccessful(payload)`（要求 `exitCode == 0` 且 `error` 为空）**自洽**：
那条链本来就是在读 `completed` 的 payload，而不是在读一个 failed 事件。

### 1.2 三态结局的判定规则（本规格冻结，实现不得另发明）

| 结局 | 判定 |
|---|---|
`Failed` | `exitCode` 非 0 **或** `error` 非空 |
`Completed` | `exitCode == 0` **且** `error` 为空 |
**`Unknown`** | **两者都缺失**（如本身无 exitCode 语义的工具） |

**`Unknown` 必须是一等公民**：不得退化成"成功"或"失败"，**不得**用 `0` / `false` / 空字符串冒充。
（与 T2 §4「无数据 ≠ 低分」是同一条纪律；`exitCode` 缺失时把"成功"当默认值是**最危险的偷懒**。）

#### 1.2.1 读取必须**宽容**，但**宽容 ≠ 宽松**（2026-09-21 追加，实测依据）

**新证据**：`TurnExecutorAdapter.ConvertFrame` 把运行时帧 `"tool_result"` 映射为 `ToolCallCompleted`，
而 **payload 原样透传**（`Payload: payload`，未做任何字段改造）⇒
**`tool.call.completed` 的 payload 形状由运行时帧写入方决定，平台不保证**。
另一个同向证据：读取端自带了 `exitCode` **与** `exit_code` 双键回退（`ConversationTranscriptFold.cs:409-419`）
—— **防御性双键回退本身就是“形状不统一”的证据**。

⇒ **读取器必须同时接受下列形态（否则会出现“全部 Unknown”或“全部 Completed”的静默灾难）**：
- 键名：`exitCode` 与 `exit_code` **都要认**；
- 类型：**数值**（`0`）与**数字字符串**（`"0"`）**都要认**；
- 空串 / 纯空白字符串 ⇒ **视同缺失**（**显式规定**，否则 `error: " "` 会让 Failed/Completed 的判定产生歧义）。

⚠️ **但宽容不得放宽语义**：凡“解析不出来/根本不存在”的情况，一律 ⇒ **`Unknown`**；
**绝不允许**在解析失败时落到 `Completed`（这是本片最危险的失败模式：
把“读不懂”当成“成功”，会让 RSI 在错误的正面信号上学习，**而且不会报错**）。

⇒ 本小节给测试矩阵**追加两条硬用例**（编号 S11/S12，与 §4 同等效力）：
- **S11**：`{"exitCode":"0"}`（**字符串**型成功）⇒ `Completed`；变异：只支持数值型 ⇒ 必红；
- **S12**：`{"exitCode":"1"}`（**字符串**型失败）⇒ `Failed`；变异：同上 ⇒ 必红。

### 1.3 既有 DTO 装不下结局 ⇒ **不得复用**

`Source/PuddingCore/Platform/SubconsciousDtos.cs:388-402`：

- `SkillEvolutionTrajectory` = `WorkspaceId`/`AgentInstanceId`/`SessionId`/`TurnId`/`Goal`（均 required）+ `Steps`
- `SkillEvolutionToolStep` = `ToolName` + `Arguments` + `Output` ← **就这三个字段**
- 类型注释原文：`Canonical successful tool trajectory used by the experience-to-Skill pipeline.`

三条不可复用理由：① 无 `Outcome`/`exitCode`/`error`，也**无 `Sequence`/时间戳** ⇒ 类型层面装不下结局；
② 语义是 **successful-only** ⇒ 复用等于把 ADR-064 的「只从成功学」原样搬回 RSI；
③ 给这个 **PuddingCore 共享 DTO 加字段**会动到 ADR-064 链的公共类型，与「零回归」标准直接冲突，
且把"成功步"与"带结局标注的步"混为一谈。

### 1.4 索引事实（决定查询形状 —— **硬约束**）

`conversation_events` 的**全部**索引（`Source/PuddingPlatform/Data/PlatformDbContext.cs:587-595`）：
`(ConversationId, Sequence)` UNIQUE、`EventId` UNIQUE、**`(TurnId, Type)`**、`CommittedAt`（ADR-076 retention）。

⇒ **`CommandId` 上没有任何索引**，而既有 `GetEventsByCommandIdsAsync`（`SkillEvolutionDataAccess.cs:47-60`）
正是 `WHERE command_id IN (...) AND type IN (...) ORDER BY sequence` ⇒ **全表扫描**。

`chat_execution_commands` 的**全部**索引（同文件 `:535-542`）：`CommandId` UNIQUE、
`(BatchId, AgentInstanceId)` UNIQUE、`(WorkspaceId, ClientRequestId)`、`(SessionId, Status)`、
`(Status, LeaseUntil)`、`(Status, CreatedAt)` —— 而既有 `GetRecentSuccessfulCommandsAsync` 谓词是
`(WorkspaceId, AgentInstanceId, Status='succeeded')`、排序键 `CompletedAt ?? CreatedAt`
⇒ **无支撑谓词的索引，`CompletedAt` 也无索引**。

**⇒ 本片的两条硬约束**：
1. RSI 的取数**必须落在已索引键上**：按 **`(TurnId, Type)`** 走（该索引已存在）；
2. **不得**原样复用既有两条查询形状；若确需按 `CommandId` 查，必须**显式**新增索引（平台迁移 + 写放大评估），
   并在规格里给**实测**行数与耗时。

### 1.5 作用域与过滤（**硬约束**）

- **技能身份是 agent 级的**：`AgentSkillFileService` 的每个 API 都以 `agentInstanceId` 为键、**无 workspace 参数**
  （目录 `agents/{agentInstanceId}/skills`）⇒ 不同 agent 的同名 `skillId` 是**不同产物** ⇒
  **跨 workspace 聚合技能用量是语义错误**，RSI 保持 `(workspace, agentInstanceId)` 双键作用域。
- **遥测落点路径里没有 agent 段**（`DataRoot/skill-usage/skill-usage-{yyyyMMdd}.jsonl`，`PuddingDataPaths.cs:35`），
  而**同一个 DataRoot 下住着多个 agent** ⇒ **路径不是作用域，`SkillUsageRecord.AgentInstanceId` 字段才是**
  ⇒ 读取**必须按字段过滤**。否则某技能"注入 3 次"会变成"12 次"，**而分数看上去仍然合理**（无断言会失败）。
- **retention 的定位键是 `CommittedAt`**（`PlatformDbContext.cs:594` 注释：ADR-076 retention 按 committed_at 定位）
  ⇒ 轨迹时间窗必须以 **committed_at** 对齐，**不是** `occurred_at`。

### 1.6 ADR-064 零回归 & 冬眠事实

- `GetRecentSuccessfulAsync` 的**零生产消费方**（调用点仅在一个测试文件）⇒ ADR-064 保护的是一个**休眠**管道；
- 因此 1.4 那两条"无索引查询"能活到今天 —— **冬眠解释了缺陷为何未被发现**；
- **RSI 会成为该接缝的第一个真实消费方**：若复用其查询形状并**定期**跑，**RSI 就是第一个付代价的人**。

### 1.7 `excludeFromLearning` 契约（必须同样尊重）

#### 1.7.1 实测真值表（`ConversationSkillEvolutionTrajectorySource.cs:154-173`）
签名：`internal static bool IsExcludedFromLearning(string? metadataJson)`

| 输入 | 结果 |
|---|---|
| null / 空白 | `false`（不排除） |
| 非 Object 根 / 无该属性 | `false` |
| `"excludeFromLearning": true`（**bool**） | `true` |
| `"excludeFromLearning": "true"`（**字符串**，过 `bool.TryParse`） | `true`；`"false"` ⇒ `false` |
| **JSON 解析失败（`JsonException`）** | **`false`（fail-open：元数据坏了不排除）** |

#### 1.7.2 RSI 的决定：**复用该方法本身，不写第二份**
该方法与 RSI **在同一程序集**（`PuddingRuntime`：`Services/Skills/**` 与 `Services/Improvement/Rsi/**`）
⇒ `internal` **可直接调用**。

⇒ **RSI 必须调用 `ConversationSkillEvolutionTrajectorySource.IsExcludedFromLearning(...)`**，不得复制判断逻辑：
- 复制 ⇒ 两份实现会在将来 ADR-064 规则变化时**静默漂移**，而“尊重 `excludeFromLearning`”恰恰**要求语义完全一致**；
- 调用 ⇒ **不修改 ADR-064 任何文件**（零回归不受影响），语义自动一致。

#### 1.7.3 必须如实报告的已知弱点（**继承，不悄悄“改进”**）
fail-open 的后果：元数据解析失败 ⇒ **不排除** ⇒ 理论上“被排除的数据仍可能进入学习”。
RSI **刻意镜像**该语义（而不是自行改成 fail-closed），三条理由：
1. §1.7 的“尊重” = **语义一致**；静默分叉会让两个管道对同一数据给出不同判定，**比弱点本身更危险**；
2. 改它会**改变既有管道的行为**（该方法是共享 `internal`），属平台级决定，**不在本片权限内**；
3. 生产端写的是合法 JSON，**触发条件窄**。
⇒ 记录为**已继承的弱点 + 触发条件 + 影响面**，并已在 §7 留一条未决项（是否改 fail-closed 需平台级裁决）。

- 写入者 = **基准评测工具**（`Tools/Diagnostics/run_benchmarks.py:141`），写的是**字符串** `"true"`；
- 读取端**同时接受 bool 与字符串 `"true"`**（`ConversationSkillEvolutionTrajectorySource.cs:154/163`）
  ⇒ 两种形态都是**有意支持**的契约；
- 语义 = 把**基准/评测轨迹**挡在学习管道外（防"用评测数据自证进步"），**不是**用户逃生阀、**无管理入口**
  ⇒ RSI 必须同样排除，且**不得**把它扩展成可配置开关。

## 2. 方案：接缝 **B**（独立 RSI 数据接缝）

### 2.1 为什么 A 不可行（不是"B 更干净"）

A = 复用 `ISkillEvolutionTrajectorySource` + 既有 DTO。**已证伪**：既有 `SkillEvolutionToolStep`
在**类型层面就装不下「结局」**（§1.3）⇒ A 不是"次优"，而是**做不到**。

### 2.2 接口草案（实现时可调名，但**形状**不得违背）

```csharp
// PuddingCore/Abstractions/IRsiTrajectorySource.cs
public interface IRsiTrajectorySource
{
    Task<IReadOnlyList<RsiTrajectory>> GetRecentAnnotatedAsync(
        string workspaceId, string agentInstanceId, int limit, CancellationToken ct);
}

// PuddingCore/Platform/IRsiTrajectoryDataAccess.cs
public interface IRsiTrajectoryDataAccess
{
    // 只暴露"按 TurnId 批量取事件"——即已索引的形状；不得暴露按 CommandId 的查询。
    Task<IReadOnlyList<RsiEventRow>> GetEventsByTurnIdsAsync(
        string[] turnIds, string[] eventTypes, CancellationToken ct);
}
```

### 2.3 形状草案（结局是一等字段）

```csharp
public enum RsiToolOutcome { Unknown = 0, Completed = 1, Failed = 2 }  // Unknown 必须是 0

public sealed record RsiToolStep
{
    public required string TurnId { get; init; }
    public required string ToolName { get; init; }
    public required long Sequence { get; init; }      // 有据可依的稳定排序键（不得依赖 DB 返回顺序）
    public required RsiToolOutcome Outcome { get; init; }
    public int? ExitCode { get; init; }               // 缺失就是 null，不得填 0
    public string? Error { get; init; }
    public string? Output { get; init; }
    public required DateTimeOffset OccurredAtUtc { get; init; }
}

public sealed record RsiTrajectory
{
    public required string WorkspaceId { get; init; }
    public required string AgentInstanceId { get; init; }
    public required string SessionId { get; init; }
    public required string TurnId { get; init; }
    public required IReadOnlyList<RsiToolStep> Steps { get; init; }
    public required bool HasOutcomeAnomaly { get; init; }  // 有 Unknown/Failed 步时为 true（供上层显式判断）
}
```

**要点**：**失败步不得被整体丢弃**（既有管道是 `Any(Failed) ⇒ return null` 整条丢弃，RSI **不得**模仿）；
`Unknown` 用**独立枚举值**而不是"空值"，使"没数据"与"数据说是失败"在类型上就分开。

### 2.4 查询必须落在已索引键上（伪 SQL）

```sql
-- ✅ 走 (TurnId, Type) 索引
SELECT turn_id, type, payload, sequence, occurred_at, committed_at
FROM conversation_events
WHERE turn_id IN (…) AND type IN ('tool.call.requested','tool.call.completed','tool.call.failed')
ORDER BY turn_id, sequence;

-- ⛔ 禁止（无索引 ⇒ 全表扫描，代价随事件总量线性增长）
SELECT … FROM conversation_events WHERE command_id IN (…) …
```

**注意**：`tool.call.failed` 可以**照收**（防御性，§1.1），但**不得依赖**它出现。

### 2.5 取 turn 列表也必须走索引

按 §1.4，`chat_execution_commands` 无 `(WorkspaceId, AgentInstanceId, Status)` 索引 ⇒
**RSI 不得以它为入口做范围扫描**。可行入口二选一，且**须实测成本**：
- （a）**按 turn 反查**：由上层给出 `turnIds`（本轮/本窗口的 turn 集合），RSI 只做"按 turn 取事件"——
  **这是本规格推荐路径**（全部落在已索引键上，无新索引需求）；
- （b）若确需"按 agent 找最近 turn"，则必须**显式**提出索引需求，走平台迁移，并给出**实测**行数与耗时。

### 2.6 B2（数据访问接缝）的两条前置裁决（2026-09-21 实测后冻结）

#### 2.6.1 ⛔ **不得复用 `ConversationEventRow`**
实测 `Source/PuddingPlatform/Services/SkillEvolutionDataAccess.cs:51-67`：既有行形状 `ConversationEventRow` 只有
`CommandId / Type / Payload / Sequence` 四个字段 ——**没有 `TurnId`、没有 `OccurredAtUtc`**。
而 `RsiToolStep.OccurredAtUtc` 是 **required**，且 RSI 的查询入口是 **turn** 而非 command ⇒
**复用它在类型层面就做不到**（与 §1.3 拒绝复用 `SkillEvolutionToolStep` 是同一类错误，不得重犯）。

⇒ B2 自带行形状（**turn 内不带 turn 身份**，turn 身份由上层 turn 列表提供）：
```csharp
public sealed record RsiEventRowWithTurn
{
    public required string TurnId { get; init; }
    public required string Type { get; init; }
    public required long Sequence { get; init; }
    public string? Payload { get; init; }
    public required DateTimeOffset OccurredAtUtc { get; init; }
}
```
（与 B1 的 `RsiEventRow` 分开：后者已在 `RsiTurnSlice` 内，无需重复 `TurnId`。）

#### 2.6.2 入口裁决：**只做 §2.5(a)，本片不做“按 agent 扫 turn”**
`IRsiTrajectorySource.GetRecentAnnotatedAsync(workspaceId, agentInstanceId, limit, ct)` 这个签名
**隐含了一次 `chat_execution_commands` 的范围扫描**，而该表**无 `(WorkspaceId, AgentInstanceId, Status)` 索引**（§1.4）
⇒ 该形态在本片**不实现**，避免把一个无索引的全表扫描钒进 RSI 的第一版。

**本片实现形态**：入参为**显式的 `turnIds` 集合**（由上层/调用方提供），RSI 只做“按 turn 取事件”——
**全部落在已索引键 `(TurnId, Type)` 上，零新索引需求**。

若将来确需“按 agent 找最近 turn”，**必须单独开片**：显式提出索引需求 + 给出**实测**行数与耗时 +
评估写入放大，**不得夹带在本片里**（这正是“避免打补丁方式施工”的具体含义）。

#### 2.6.3 必须模仿的既有实现模式（B2 参照物）
`SkillEvolutionDataAccess` 的成熟模式（**逐条照抄**，不另发明）：
- 注入 `IDbContextFactory<PlatformDbContext>`（`PuddingPlatform.Data`），每次 `await _dbFactory.CreateDbContextAsync(ct)`；
- 查询链：`.AsNoTracking().Where(...).OrderBy(evt => evt.Sequence).ToListAsync(ct)`，最后**投影成 row record**（不向外泄 EF 实体）；
- **空入参早退**：`if (ids is null || ids.Length == 0) return [];` —— 避免 `Contains` 空数组生成退化 SQL；
- 事件类型过滤在 SQL 侧做（`eventTypes.Contains(evt.Type)`），不得取回后再内存过滤。

### 2.7 ⭐ `occurred_at` 是 **string 列** ⇒ 解析契约（2026-09-21 实测后冻结；B2 必须照此实现）

**新事实（本轮实测，修订了 §2.3 的默认假设）**

`Source/PuddingPlatform/Data/Entities/ConversationEventEntity.cs`：`OccurredAt` / `CommittedAt` 均为 **`[Required] string`**
（列名 `occurred_at` / `committed_at`），**不是 `DateTimeOffset`**。
⇒ B2 必须做「字符串 → `DateTimeOffset`」转换 —— 这是本片**唯一一处时间语义转换**，必须显式定契约，**不得由实现者临场发明**。

**写入约定（实测，不是推测）**

所有生产写入者均为 `DateTimeOffset.UtcNow.ToString("O")`（`ConversationEventStore.cs:44`、`ConversationAcceptanceStore.cs:197-198`、`GoalRunStore.cs:307-308` 等）
⇒ 磁盘形态为 `2026-09-21T15:00:00.0000000+00:00`（**带 `+00:00` 偏移**，不是 `Z`）。

**解析契约（冻结，B2 逐字执行）**

```csharp
if (DateTimeOffset.TryParse(raw, CultureInfo.InvariantCulture, DateTimeStyles.AssumeUniversal, out var parsed))
    occurredAtUtc = parsed.ToUniversalTime();
```

- **必须** `CultureInfo.InvariantCulture`：⛔ 不得照抄平台既有的 `DateTimeOffset.Parse(...)`（`ConversationEventStore.cs:573`、`RawSessionLogService.cs:542`、`SessionStateManager.cs:1590` 等 **7+ 处**走 CurrentCulture）——非公历文化（`ar-SA` Umm al-Qura、`th-TH` 佛历）下会解析成**不同年份**。
- **必须** `DateTimeStyles.AssumeUniversal`：字符串**不含偏移**时按 **UTC** 解释。⛔ 不得用 `DateTimeStyles.None`（无偏移串会按**本机时区**解释 —— **本机是 UTC+8**，误读恰好错 **8 小时**）。
- **必须** `.ToUniversalTime()`：字段名是 `OccurredAtUtc`，**类型名不得撒谎**。
- ⛔ 本族错误的**同源实例**已在本仓出现过（`TestScripts/report-skill-usage.ps1` 把本地墙钟贴上 `Z`，实测错 8 小时，见该脚本注释）—— **同一张坑换个语言再踩一次不可接受**。

**不可解析时：fail-closed 抛出**

- 边界层（B2）遇到不可解析的时间戳 ⇒ **抛出**；异常消息必须含 **`turn_id`** 与**原始字符串片段**（可定位，不是“解析失败”四个字）。
- 为什么**不是「可空」**：可空会让**格式漂移**变得不可见 —— RSI 照常产出结论，只是时间全为 `null`，**没有任何断言会失败**。这正是本片一直在猎杀的模式（与 §1.2.1「宽容 ≠ 宽松」同理）。
- 为什么**不是「丢弃该行」**：与「失败步不得丢弃」同源（丢行 = 静默丢一个工具步）。
- 为什么**不是默认值 / `MinValue`**：把“读不懂”伪装成一个真实时刻（1970 族错误）。
- **纯度分界（新增，明确）**：纯函数层（增量 A / B1）**绝不抛异常**（已冻结，逐字不动）；**边界层（B2）对不可解析输入 fail-closed 抛出**。两者不矛盾 —— 一个是**数据契约**，一个是 **IO 契约**。

**派生影响（重要，避免无谓返工）**

本契约**零改动**到已验证的增量 A / B1：其 `OccurredAtUtc` 保持 `required DateTimeOffset` 不变 ⇒ **不触发重新验收**（既有 23 条保持绿）。

**未纳入本片（防夹带）**

若将来需要按 `committed_at` 做窗口/保留期对齐，**单独加字段 + 单独开片**（当前无消费者 ⇒ 不进类型，§2.1 纪律）。

### 2.9 B3 的 feeder：turnIds 从哪来（2026-09-21 实测，**防造出第二个休眠接缝**）

**为什么要问这个**
§2.6.2 裁决“入参为显式 `turnIds`，由上层提供”。若不回答“**上层是谁、它怎么拿到**”，

**实测事实（`PlatformDbContext.cs:556-562` + `ConversationTurnEntity.cs`）**

- `TurnId` UNIQUE
- `(ConversationId, Status)`
- **`(ConversationId, CreatedAt)`** ← 已索引的“最近 N 个 turn”路径
- `CommandId`

且该实体**没有 `agent_instance_id` 列**（只有 `user_id`）。

1. ⛔ **“按 agent 找最近 turn”在 `conversation_turns` 上也不可行**：不是“缺索引”，而是**该表根本没有 agent 维度**。

2. ✅ **合法 feeder = 会话维度**：`(ConversationId, CreatedAt)` 索引支撑“某会话最近 N 个 turn”。
   而会话↔agent 归属在 `chat_messages` 的 `(WorkspaceId, AgentInstanceId, CreatedAt)`（`PlatformDbContext.cs:437`）
   与 `(SessionId, TurnId)`（`:438`）上。
   ⇒ **B3 的入口形状应为 `(ConversationId/SessionId, limit)`**，**不是** `(workspace, agent)`。
3. ✅ **作用域不因此改变**：§1.5 的 agent 级作用域仍成立（统计/聚合时按 `AgentInstanceId` **字段**过滤）；
   变的只是**取数入口的维度**。

**⚠️ 一处更优但有代价的替代（登记，不在本片换）**
`ConversationTurnEntity` 自带 `AcceptedSequence` / `TerminalSequence`
（实体注释原文：“Turn.AcceptedSequence 和 Turn.TerminalSequence 构成事件窗口”），

⇒ 理论上可用**连续区间扫描**替代 `turn_id IN (…)`。
- 优点：区间扫描天然覆盖该 turn 内**全部**事件类型（不必枚举 type）；
- 代价：多一次按 `TurnId`（UNIQUE）取窗口的查询。
⇒ **B2 正按 §2.4/§2.6 实现，本片不改其契约**；该替代登记在此，供后续片评估
（避免“边做边改”——本片已经在 §4.2.2 上付过一次“改了才发现归因错”的代价）。
