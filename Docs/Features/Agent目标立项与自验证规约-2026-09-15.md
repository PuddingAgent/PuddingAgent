## 0. 为什么需要这份规约

我们已有过的真实失败，全部可归因到"目标立项不合格"：

| 失败实例 | 现象 | 根因 |
|---|---|---|
| 任务卡 `dc0ac9a8`（P0 统一 Scheduler 内核） | 显示 `Goal 失败 · 1/32`，`work_unit_budget_exhausted` | 目标**无法派生出验收条件** ⇒ 每轮 `acceptance_contract_missing` ⇒ Repair 空转到预算耗尽 |
| `iteration_failed` 终态化（已回退） | 3 个旧测试转绿，但与 ADR-092 冲突 | 用**测试红绿**倒推语义正确性（裁决顺序错误） |
| `/goal clear` 空操作 | 命令提示"已清除"，界面纹丝不动 | 写入的 `ClearedAtUtc` **无任何读路径**（死字段） |

共同点：**缺少"目标合格性"的事前判定与事后自验证**，只能靠事后发现。

## 1. 核心定义

### 1.1 什么是"正确的目标"

> **一个正确的目标 ≡ 能派生出可执行验收条件的目标。**
> 派生不出来的（"更高效""更好用"）不是目标，是**愿望（aspiration）**。

在 PuddingAgent 里，"可执行验收条件"的具体形态是 `goal_acceptance_contracts` 中的
`GoalCriterion` + `GoalCheckSpec`（含 `DefinitionRef` / `DefinitionHash` / `InputRefs` /
`InputFingerprint` / `ExpectedTestCount`）。**没有任何一条 Criterion 的目标，不得进入执行。**

### 1.2 学术支撑（本轮核实）

- **Huang et al. 2023, `arXiv:2310.01798`（LLMs Cannot Self-Correct Reasoning Yet）**：无外部信号的自我纠错会让推理**变差**。
- **CRITIC, `arXiv:2305.11738`**：只有引入**外部工具/环境反馈**，自我修正才有稳定增益。

⇒ **推论（我们已在前沿）**：裁决信号必须外置（真实 ExitCode / 测试计数 / 文件哈希），
**不得采信执行者自述**。这条与 PuddingAgent 现有 verifier 原则一致，不要因为"对标"而放松。

## 2. 九步立项流程（可执行版）

> **第 0 步（前置，强制）：先查轮子。** 立项前必须先检索开源生态与官方文档，确认同一问题是否已有成熟实现。
> 已有实现时**直接参考其设计、阈值与话术**（提示词模板跨语言可直接复用），只对“确实没有现成实现”的部分自行设计，
> 并在方案里显式写明：哪些是借鉴、借鉴自谁、**为什么能/不能照搬**。
> 反面教训：我们曾为“目标续行 / 无进展熔断”从零设计，事后发现 `openai/codex` 的
> `codex-rs/ext/goal/src/accounting.rs` 已有几乎同构的三个连续计数（`consecutive_execution_failure_turns` /
> `consecutive_empty_turns` / `descendant_token_usage`）与阈值 3。
>
> **但第 0 步不等于盲从**：必须先分辨“对方实现了什么”与“**对方刻意没做什么**”。
> 例：Codex 对跨重启恢复的选择是“resume/fork 后一律 disarmed、需人显式授权”——
> 这属于有意的安全取舍，若要超出它（如 `auto_resume_on_restart`），必须自行补安全阀并单独论证。

| # | 步骤 | 产物 | PuddingAgent 落点 |
|---|---|---|---|
| 1 | **愿望** | 一句话描述想要什么 | 用户 `/goal <文本>` |
| 2 | **可观测结果 outcome** | 环境状态变化（**不是** agent 自述） | `GoalCriterion.Requirement` |
| 3 | **判定证据 evidence** | 具体命令/检查 + 期望输出 | `GoalCheckSpec`（`DefinitionRef` + `ExpectedTestCount`） |
| 4 | **独立判定者** | 谁判定通过、不得由执行者兼任 | `AIterationVerifier` + `GoalCheckEvidencePolicy` |
| 5 | **边界与非目标** | 明确**不做什么**（out-of-scope） | 目标文本 + 合同注释（当前薄弱） |
| 6 | **约束与预算** | 迭代上限、成本、**谁能改** | `GoalRunOptions` / `GoalLimits.MaxIterationsHardLimit` |
| 7 | **失败码与终止/升级条件** | 每类失败落到哪个处置 | `GoalCheckFailureCodes` / `ComputeDisposition` |
| 8 | **分解为 DAG 并逐节点验收与回滚** | 子目标图 + 每节点验收与回滚 | Plan/WorkUnit + `RemainingWorkUnits`（§13.1 四分流） |
| 9 | **冻结 spec + 回归门禁** | 版本化合同 + 回归基线 | `criteria.Revision` + 定向测试套件 |

**关键约束**：第 2、3、4 步缺任意一步，目标即判定为"愿望"，**必须拒绝进入执行**（fail-closed）。
这正是 P1-3（Agent 侧创建目标）必须内建的门禁 —— 从源头杜绝不可验证的宏大目标。

## 3. 目标质量 Checklist（12 项）

来源：GORE/KAOS（可精化、责任人、obstacle 分析）+ SMART / 目标设定理论（Locke & Latham 2002）
+ SDD/EARS 验收标准（机器可读、显式 out-of-scope）+ 本仓库实践。

| # | 检查项 | 不合格的后果 |
|---|---|---|
| 1 | 达成时有**环境可观测**的变化（非自述） | 无法判定完成 |
| 2 | 有**具体命令/检查**能产生证据 | 只能信自述 |
| 3 | 证据有**期望值**（退出码/数量/内容） | 绿灯无意义 |
| 4 | 判定者**独立于执行者** | 自证自夸 |
| 5 | 明确写出**非目标**（不做什么） | 目标无限扩张 |
| 6 | 有**迭代/成本上限**，且上限**不能由执行者自增** | 自我延长 |
| 7 | 每类失败都有**明确的下一步** | 无差别 Repair ⇒ 空转 |
| 8 | 有**不可达判定**（何时承认做不到） | 无限尝试 |
| 9 | 可**分解**为可独立验证的子目标 | 无法并行/无法定位失败 |
| 10 | 每个子节点有**验收与回滚** | 半途无法收敛 |
| 11 | 目标是**具体、可度量、有反馈**（SMART + 目标设定理论） | 方向漂移 |
| 12 | 有条件变化时的**失效规则**（什么变了使旧绿灯作废） | 旧证据被误用 |

## 4. 分解规则

- **HTN**（Erol/Hendler/Nau 1994）是唯一有形式化与复杂度结论的分解框架，可借其"方法（method）+ 前置条件"结构。
- **WBS 100% 规则**（PMI）：子项之和必须 100% 覆盖父项，**不多不少** ⇒ 给"验收粒度"提供判据。
- **ADaPT（`arXiv:2311.05772`）主张"按需分解"**，且允许 agent 判定**不可解**并停止 —— 与我们的 `NeedsUser` / typed wait 同向。
- **PlanBench（`arXiv:2206.10498`）警告：LLM 长程规划不可靠** ⇒ **不要一次性规划长链**；采用"短程按需分解 + 每步验证"。
- 我们已有 `TaskExecutionPlanCompiler` + `RemainingWorkUnits`（depth1 必需节点）—— 与上述一致，属正确方向。

## 5. 自验证：每次自我升级后必做

用户要求"每次自我升级之后进行自我验证"。落地为**两类 eval + 一道门禁 + 三级发布**：

### 5.1 两类 eval（来源：Anthropic《Demystifying evals for AI agents》）

| 类型 | 起点 | 作用 | 我们对应 |
|---|---|---|---|
| **回归 eval** | 近 100% 通过 | 守护**既有能力**不被破坏 | `dotnet test --filter ~Goal`（当前 127/127）等定向套件 |
| **能力 eval** | 低起点 | 衡量**新能力爬坡** | 真实 Goal 跑通率、首条 `goal_check_records`、真实 Complete 次数 |

**判据**：只跑回归不跑能力 ⇒ 无法证明升级有效；只跑能力不跑回归 ⇒ 可能破坏既有能力。**两者都要。**

### 5.2 门禁：`pass^k`

新能力必须**连续 k 次**通过才算稳定（k 次全部成功，而非"平均成功率"）。用于对抗"偶发通过"。

### 5.3 三级发布

**shadow（0% 暴露）→ canary（5–10%）→ 全量**（来源：Google SRE Book 发布工程章节）。
我们的降级版本：新检查/新语义先在 `shadow` 模式只记录不裁决 → 定向单测 + 真实 canary 一轮 → 默认路径。

### 5.4 硬性纪律（本仓库已执行，写入规约）

1. **改动前后都有真实运行证据**：`dotnet build` + 定向测试真实计数 + 关键路径的真实运行。
2. **不接受自述**：不得用"代码看起来对""语法无错"替代可编译/可运行证据。
3. **语义裁决顺序固定**：权威 ADR 原文 > 设计文档 > 代码现状 > **测试红绿**（最后一位，不得倒推）。
4. **不为变绿而放宽门禁**：测试预期与 ADR 冲突时，改测试基线或改设计，不得放宽产品门禁。
5. **每次原子改动独立提交**，便于按边界回归与回滚。

## 7. 反面案例（必须避免）

1. **目标不可派生验收条件** ⇒ 空转到预算耗尽（`1/32` 卡）。
2. **用测试红绿倒推语义** ⇒ 与权威 ADR 冲突（`iteration_failed` 终态化，已回退）。
3. **写了没人读的字段** ⇒ 命令提示成功但行为不变（`ClearedAtUtc`，已修）。
4. **完成判据与上限混淆** ⇒ `budget_exhausted` 被当"自然结束"，用户无法区分"做完了"与"做不下去了"。
5. **计划与上下文脱节** ⇒ 计划落库但不回灌模型（Codex `update_plan` 的已知弱点，勿学）。
