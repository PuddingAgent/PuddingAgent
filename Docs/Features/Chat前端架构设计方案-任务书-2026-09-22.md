## 1. 背景：为什么现在要做这件事

聊天页出现两个**用户可直接感知**的缺陷，且已被证明**不在数据层**：

| 缺陷 | 用户原话 | 表现 |
|---|---|---|
| **A 晚一条** | 「用户发送消息之后，agent 的消息不显示。用户发送下一条的时候，上一条的 Agent 消息才显示」 | 本轮回复在本轮不出现 |
| **B 渲染不全** | 「很明显，并没有完全渲染完成」 | 助手卡片正文从开头渲染到中途截断；同一卡片上下各出现一次「8 段思考 · 17 次工具」；页面无滚动条 |

**已完成的取证（父级亲验，可作既定事实引用，不必重复验证）**：
对样本消息 `messageId=8c65d43f70ad414aa7fd0351a818e4d2` / `turnId=cf7fa224…` 做**四源对拍**，全部等于 **2355 字符**：
1. DB `ChatMessages.content` = 2355
2. `GET /api/.../conversation` 该消息 `content` = 2355（`status=succeeded`）
3. `GET /api/.../messages/{id}/process-items` 的 **63 个 `text` 项拼接** = 2355（缺 `sequence` 项 = 0，`hasMoreBefore=false`）
4. 事件流 `message.content.appended` **63 条 `delta` 求和** = 2355，且 `turn.completed` 在最后一条 delta **之后**（seq 1394414 → 1394416）

⇒ **数据层完整，缺陷 100% 在客户端展示链。**

**已证伪的假设（勿再走）**：
- ❌ 内容块窗口丢尾部：`execution-flow/TurnContentStream.tsx:228-232` 的 `visibleBlocks = blocks.slice(hiddenBlockCount)` 切的是**数组头部**，**尾部恒保留**，方向相反。
- ❌ 末条 `system` 消息导致 `conversationNeedsProjectionCatchUp` 误判追平：该函数实现仅 `messages[last].role === 'user'`，单凭末条 role 不足以触发跳过（还需 cursor 等条件同时成立）。
- ❌ 本地乐观 Turn 因 `projectedAssistantIsTerminal` 恒假而压制投影：`AgentConversationProjectionService.cs:691` 把 conversation DTO 全部消息状态**硬编码为 `succeeded`** ⇒ 投影 turn 永不 pending。

**当前收敛（父级已亲自读源码定位，行号以 2026-09-22 磁盘为准）**：缺陷 A 疑似来自 `src/pages/chat/client/chatClientStore.ts` 的**两处 P0-perf 启发式短路**：
- **门 1**（入口跳过，`:379-406` 附近）：`matchingStatus.eventCursor === existingConv.eventCursor && !activeRunId && !activeRun && !projectionCatchUpPending` ⇒ **完全不发 API 请求**。其自身注释已承认风险（cursor 可能先于 assistant 消息行到达），但保护条件只覆盖「末条是 user」一种形态。
- **门 2**（`isConversationSame`，`:99-111` 附近）：判「语义相同」用 `eventCursor && messages.length && activeRun.runId && mainSessionId` —— **只比消息条数，不比内容**。若正文是在**同一条已存在消息上被填充**（条数不变），新快照会被判「相同」而丢弃（不写 IndexedDB、不 `setState`）。

⚠️ 父级注：其中一处的精确行号在小通信通道内**无法对位**，请以你自己读到的实际行号为准，并**在方案中写明你实测的行号**。

2. **不得超出 bundle 预算**：Chat 路由 chunk ≤ 496 KB、同步入口 ≤ 1536 KB。方案若引入新依赖或增大体积，必须给出**净增量估算与腾挪来源**。
3. **不得删改测试来「通过」**，也不得放宽既有断言。新增守卫必须能**取红**（施加变异后必须失败）。
4. **文件写盘为无 BOM UTF-8**。
5. **诚实边界**：凡未经代码/实测确证的结论，必须显式标注「**未证实**」；禁止推测填空白。方案中引用代码**必须给 `file:line`**，且行号须是你实际读到的。
6. **保留既有架构与命名风格**；若主张推翻某个 ADR，必须**指名该 ADR 编号与条款**并给出推翻理由，不得含糊。
7. **不新建目录树**，除非方案明确论证并给出理由。
8. 本任务**只出设计**：禁止修改源码、禁止提交、禁止运行构建（读代码与读文档是允许且必要的）。

## 4. 必须解决的问题（方案的评审对象）

方案要对以下**七类问题**给出可评审的答复（每类都要有明确取舍与理由）：

- **P1 状态真值归属**：现在 turn/message 的真值散落在「本地乐观 / SSE 事件投影 / agent-client 轮询快照 / 历史读模型投影 / TurnSurfaceStore」五处，且互相覆盖。**谁应当是唯一真值源？** 其余各处的角色如何降级为纯派生视图？
- **P2 覆盖顺序**：请求「在所有条件下都不会丢弃比当前更完整的数据」的合并规则（而不是启发式「看起来一样就跳过」）。给出**可判定的等价性判据**（例如内容指纹/版本号/事件序号），并说明为何它不会造成重复渲染或卡片重复。
- **P3 完成即物化**：缺陷 A 的候选修法之一是「turn 完成时触发一次权威转录回拉」。请评估：是否应把「完成事件」作为**唯一的物化触发点**？触发后如何避免与轮询/SSE 重复（幂等键是什么）？
- **P4 事件与读物的一致性**：当事件流缺失/乱序/游标已到终态而 read model 尚未可见时，客户端应**依据什么做判定**（而不是靠「末条是不是 user」这类启发式）？请给出**可观测的判据**。
- **P5 死代码与骨架**：13 个零引用模块中，哪些应删除（无计划）、哪些应接线（有明确计划）？给出**逐模块结论**与理由；对「接线」类给出成本与依赖关系。ADR-057 的重连与缺口恢复为何未接线，方案是否需要重启该方向？
- **P6 体量与分层**：`useChatState` 1606 行 / `MessageList` 1442 行 / `index.tsx` 814 行的拆分策略；**分层边界如何强制**（是否引入 import 边界守卫测试 / lint 规则）；如何与 `check-chat-bundle-budget.cjs` 的 chunk 约束协同。
- **P7 可验证性**：为每个新增不变量设计**取红测试**（施加什么变异必须失败）。特别是 P2 的等价性判据、P3 的幂等性。
