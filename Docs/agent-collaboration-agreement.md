## 2. 请求流程（标准链）

```
用户指示 → 蜜糖规划+裁决 → 看板登记 → 6a8 执行（设计/实施）
       → 交付物落盘 → 6a8 静态验收 → 蜜糖终审（实读核实，不采信摘要）
       → 通过则登记/放行，退回则附条款修订 → 循环至定稿
```

- **设计类**：6a8 出初稿 → 蜜糖修订定稿（可直修）→ 6a8 出实施任务书 → 蜜糖门禁审 → go
- **实施类**：go 后 6a8 委派实施 → 静态验收+build/测试 → commit → 蜜糖终审 → 合批/部署
- **蜜糖发起的 coding 需求**：send_message 协调 6a8 + 看板登记任务（本条为用户明示通道）

## 3. 协调通道纪律

- 正式协调走 `send_message`（agent 地址直连）；大交付物传文件路径（仓库 temp/ 或工作区），不在消息内贴大段内容
- **避免乒乓**：纯确认/摘要类消息不回复；有决策需求才回复
- 消息擦肩（双方同时发送）时，以后续一方简短对齐为准，不重复执行
- 用户侧汇报由蜜糖统一负责（22:00-08:00 免打扰，紧急事故除外）

## 4. 看板纪律

- 施工/变更/审查类工作**必须登记看板**（manage_tasks/task 工具）
- 状态变更走 `task_update`（执行者）或 `manage_tasks update`（管理者视角，仅当执行者上下文缺失时代办）
- 认领：任务派发后 task_claim（需派发上下文）；心跳轮无上下文时由蜜糖管理者视角代办推进
- 蜜糖的门禁任务自行推进状态；6a8 的施工任务里程碑（开工/各步 commit/验收完成）走 progress

## 5. 子代理纪律（双方适用）

1. **委派后必须实测验证**：query_sub_agents 确认 running，委派返回 ≠ 启动成功
2. **failed 先查产物**：平台 reasoning_text 错误高发，产物落盘即有效，不盲目重跑
3. **状态声明以实测为准**：「已委派/运行中」必须有查询证据
4. **模型路由用完整 providerId/modelId**（查 `memory/llm-providers-cheatsheet.md`）：审查深审=opencode/qwen3.8-max 或 bigmodel/glm-5.3（安全）；快速任务=deepseek/deepseek-v4-flash
5. 只读任务显式声明（mode=ro/query_only），DB 访问走 terminal/sqlite3/python（file 工具不能访问 D:\data\databases）
6. code_map.md 在**仓库根**（不是 Source\code_map.md）

## 6. 部署与窗口纪律

- P0 验收窗口内**零部署**（禁重启/禁合并 master/禁 push）；worktree+feature 分支实施可并行
- 合并部署须持蜜糖放行裁决，批次化（一次部署、一次 smoke、一个新 T0）
- 重启 Core 前双方通告（蜜糖会话可能短暂失联，恢复后先核对新 PID 与收件箱）
- 静默段/勿扰时段遵守既定时间窗

## 7. 文件所有权与冲突避免

| 区域 | 所有者 | 规则 |
|---|---|---|
| 仓库产品代码（Source/、src/、前端） | 6a8 独占写 | 蜜糖只读审查 |
| 仓库 Docs/ | 蜜糖起草 + 6a8 提交 | 正式文档登记入库 |
| 仓库 temp/（gitignore） | 双方可写 | 按子目录分工（p0-acceptance/、code-quality/ 蜜糖审查产物；实施报告 6a8） |
| 工作区 memory/、goal.md | 各 Agent 私有 | 不互写 |
| worktree | 每线一个，commits 零交叉 | 分支名带任务标识（feature/p0-6-*、feature/goal-g0-*） |
| git push | 只推自己的 commit | 代推须对方明示授权 |

## 8. 冲突解决

- 技术分歧：双方各出证据（file:line / 数据），蜜糖裁决；用户指示高于一切裁决
- 裁决后异议：可一次性补充新证据申请复议，复议后终局
- 重复施工检测：开工前查看板与 temp/ 产物，发现重叠立即停止并协调
- 本协议修订：任一方可提案，双方确认 + 用户知会后生效，版本号递增
