## 2. 请求流程（标准链）

```
用户指示 → 蜜糖规划+裁决 → 看板登记 → 6a8 执行（设计/实施）
       → 交付物落盘 → 6a8 静态验收 → 蜜糖终审（实读核实，不采信摘要）
       → 通过则登记/放行，退回则附条款修订 → 循环至定稿
```

- **设计类**：6a8 出初稿 → 蜜糖修订定稿（可直修）→ 6a8 出实施任务书 → 蜜糖门禁审 → go
- **实施类**：go 后 6a8 委派实施 → 静态验收+build/测试 → commit → 蜜糖终审 → 合批/部署
- **蜜糖发起的 coding 需求**：send_message 协调 6a8 + 看板登记任务（本条为用户明示通道）

## 3. 协调通道纪律（v1.1 强化：防「细节风暴」）

**原则：消息只承载「决策点 + 路径」，不承载细节。细节一律落文件。**

1. 正式协调走 `send_message`（agent 地址直连）；**大交付物给路径不贴内容**（仓库 `temp/` 或 `Docs/`）。
2. **消息预算（硬约束）**：
   - 单条消息 **≤ 1200 字符**；超出即说明"细节应落文件"。
   - **一条消息一个决策点**；多议题拆多条，或落文件后只问"是否通过"。
   - 禁止在消息内贴：代码块（>5 行）、表格（>5 行）、完整日志、完整 diff。
3. **intent 分级（默认最省打扰）**：
   - `inform`：**无需回复**，不唤醒对方模型 —— **默认选项**。
   - `ask` / `request_review`：**确有决策需求才用**；每条须自带明确决策点，且**不得追问**（对方未回视为"未阻塞"，继续其他工作）。
   - **禁止**用 `ask` 发纯确认/纯摘要/纯致谢。
4. **避免乒乓**：纯确认/摘要类消息不回复；**有决策需求才回复**。
5. 消息擦肩（双方同时发送）时，以后续一方简短对齐为准，**不重复执行**。
6. **不主动打扰**：心跳轮**不得**为"未收到回复"而重发；确需回复超过 1 个心跳周期，改走看板（异步）而非再加消息。
7. 用户侧汇报由蜜糖统一负责（22:00-08:00 免打扰，紧急事故除外）。

## 4. 看板纪律

- 施工/变更/审查类工作**必须登记看板**（manage_tasks/task 工具）
- 状态变更走 `task_update`（执行者）或 `manage_tasks update`（管理者视角，仅当执行者上下文缺失时代办）
- 认领：任务派发后 task_claim（需派发上下文）；心跳轮无上下文时由蜜糖管理者视角代办推进
- 蜜糖的门禁任务自行推进状态；6a8 的施工任务里程碑（开工/各步 commit/验收完成）走 progress
- **跨 Agent 协调优先走看板**（异步、可追溯、不打扰），而非实时消息（v1.1 新增）

## 5. 子代理纪律（双方适用）

1. **委派后必须实测验证**：query_sub_agents 确认 running，委派返回 ≠ 启动成功
2. **failed 先查产物**：平台 reasoning_text 错误高发，产物落盘即有效，不盲目重跑
3. **状态声明以实测为准**：「已委派/运行中」必须有查询证据
4. **模型路由用完整 providerId/modelId**，且**以资源池实测为准**（`list_llm_providers` 或 `D:\data\config\llm.providers.json`）：当前有效 provider = `bigmodel` / `deepseek` / `fastrouter` / `jev` / `volcengine-ark`；**快速任务=`deepseek/deepseek-flash`，实施=`bigmodel/glm-5.3-flash`**。
   > ⚠️ v1.0 曾记载 `opencode/qwen3.8-max` —— **该 provider 不存在**（见 §9-G4），v1.1 已剔除。**禁止引用未实测的路由。**
5. 只读任务显式声明（mode=ro/query_only），DB 访问走 terminal/sqlite3/python（file 工具不能访问 D:\data\databases）
6. code_map.md 在**仓库根**（不是 Source\code_map.md）；注意本仓库 `code_map.md` 为**按工程分文件**（`Source/<Project>/code_map.md`），**不存在**单一 `Source/code_map.md`（v1.1 新增）

## 6. 部署与窗口纪律

- P0 验收窗口内**零部署**（禁重启/禁合并 master/禁 push）；worktree+feature 分支实施可并行
- 合并部署须持蜜糖放行裁决，批次化（一次部署、一次 smoke、一个新 T0）
- 重启 Core 前双方通告（蜜糖会话可能短暂失联，恢复后先核对新 PID 与收件箱）
- 静默段/勿扰时段遵守既定时间窗
- **重启前必须确认无并行在途未提交改动**（v1.1 新增）：重启会编译并把他人的未完成代码一起送进生产 —— 这比"晚一点生效"严重得多。

## 7. 文件所有权与冲突避免

| 区域 | 所有者 | 规则 |
|---|---|---|
| 仓库产品代码（Source/、src/、前端） | 6a8 独占写 | 蜜糖只读审查 |
| 仓库 Docs/ | 蜜糖起草 + 6a8 提交 | 正式文档登记入库 |
| `Docs/agent-collaboration-agreement.md` | **本协议唯一事实源** | memory/ 副本为指针，不独立演进（v1.1） |
| 仓库 temp/（gitignore） | 双方可写 | 按子目录分工（p0-acceptance/、code-quality/ 蜜糖审查产物；实施报告 6a8） |
| 工作区 memory/、goal.md | 各 Agent 私有 | 不互写 |
| worktree | 每线一个，commits 零交叉 | 分支名带任务标识（feature/p0-6-*、feature/goal-g0-*） |
| git push | 只推自己的 commit | 代推须对方明示授权 |

## 8. 冲突解决

- 技术分歧：双方各出证据（file:line / 数据），蜜糖裁决；**用户指示高于一切裁决**
- 裁决后异议：可一次性补充新证据申请复议，复议后终局
- 重复施工检测：开工前查看板与 temp/ 产物，发现重叠立即停止并协调
- **在途声明（v1.1 新增）**：改动共享区域（Source/、前端）前，在会话或看板留下"我正在改 X"的一句话声明；完工即清除。**目的：把"撞车后的争执"前移为"开工前的避让"。**
- 本协议修订：任一方可提案，双方确认 + 用户知会后生效，版本号递增

## 10. 外部 Agent 与身份标识（v1.1 新增，针对 G3）

**背景**：本仓库存在平台内 Agent（蜜糖/6a8/审计员/dsh）与**外部 Agent 链路**（Codex/MCP 等，经 `mcp__codex_*` 工具接入）**并发写入同一工作区**，且**共享同一 git 身份**。这带来两个风险：**无法追溯**与**互不知情地撞车**。

**规则**：

1. **提交信息必须带 Agent 标识前缀**，格式：`[agent:<name>] <type>(<scope>): <subject>`
   - 示例：`[agent:6a8] feat(operators): S2b …`、`[agent:codex] feat(http): 统一出站 UA`
   - 目的：**在不改变 git 身份的前提下恢复可追溯性**（成本最低、无需改配置）。
2. **外部 Agent 同样受本协议约束**（§3 消息纪律、§6 部署窗口、§7 文件所有权）。
3. **推送到 master 前先 `git log` 确认行首**：若发现他人新提交与自己的改动**在相同文件**，先协调再推（避免覆盖或语义冲突）。
4. **跨 Agent 的"事实"必须实测**：不得以"我听说/我记得"为依据改共享文件。
5. **冲突优先由 6a8 收敛**（施工方持有仓库写权限），蜜糖持终审与裁决。

## 11. 总协调与代码协调（v1.2 新增，依用户 2026-09-21 指示）

**授权**：用户指示 —— *「你在负责总的协调和代码协调，代码提交、合并和 push、重启、编译等可能发生冲突的节奏，每个 Agent 负责管理各自的任务。」*

1. **职责边界**：
   - **6a8（总协调 + 代码协调）**：决定**何时**提交、合并、push、重启、编译；**批次如何切分**；**何时执行**。
   - **各 Agent**：管理**自己的任务内容与进度**（任务域内自主），但**触发上述共享资源动作前须与 6a8 对齐节奏**。
   - **蜜糖**：保留**放行裁决**（go/no-go）、终审、仲裁 —— 即「**能不能做**」由蜜糖定，「**什么时候做、按什么批次做**」由 6a8 定。
2. **共享资源清单（受节奏协调约束）**：`git commit` / `merge` / `push`、Core 重启（`bootstrap_reboot`）、编译（`dotnet build`、前端 `pnpm build`）、数据库/配置写入、部署。
3. **冲突节奏的硬规则**：
   - **编译/重启前**必须确认**无并行在途未提交改动**（见 §6）—— 否则会把他人未完成代码一并送入生产。
   - **同一时间窗口内只允许一个「重型动作」**（编译 / 重启 / 全量测试 / 大规模 push）—— 因其会锁输出目录（如 Core 运行时锁定 `PuddingGateway.dll` ⇒ 相关测试套件**根本测不了**）。
   - **一次部署、一次 smoke、一个新 T0**（沿用 §6 批次化）。
   - 提交信息带 `[agent:<name>]` 前缀（§10），使 6a8 能在 push 前**识别来源**并排期。
4. **对 6a8 自身的约束**：节奏协调权**不等于优先权** —— 6a8 **不得**用排期权阻止他人任务，只能**调整顺序**，且须给出理由与预计时间。

## 12. 成本窗口与节奏纪律（v1.2 新增，依用户 2026-09-21 指示）

**用户告知的成本事实（以此为准）**：
- **工作日**（**节假日与法定假期除外**）token **定价为 2 倍**；
- **非工作时段 / 周六日 / 节假日（国庆节、中秋节等）** token 费用**最低**。

**由此形成的纪律**：
1. **重型动作（重启、部署、全量测试、大规模子代理委派、批量重构）优先排在非工作时段 / 周末 / 节假日**；工作时段只做**必要的、轻量的、阻塞他人的**动作。
2. **心跳间隔按窗口调整**：非工作时段可缩短（加快执行）；**工作时段拉长**（默认 **3600s**，减少唤醒与 token 消耗）。
3. **子代理预算同样受窗口约束**：工作时段避免「探索型」大批量委派；非工作时段可放开。
4. **事实源**：模型单价以**资源池实测**为准（`list_llm_providers` / `D:\data\config\llm.providers.json` 的 `pricePer1MTokens`）；**不得凭记忆引用价格**（与 §9-G4 同类问题）。
5. **例外**：**阻塞他人的紧急修复**、**用户明确的即时指示**、**安全事故**不受窗口限制。

## 13. 单 Agent 优先原则（v1.3 · 依用户判断）

**用户判断**：「**单 Agent 的效率，一般要高于多 Agent。**」——本协议据此将**委派从默认动作降为例外动作**。

**本项目的实测支持（6a8 自身经验，非理论）**：
- 子代理**看不到父代理的对话历史** ⇒ 上下文靠「任务书」传递：**写全则贵，写略则错**。
- **委派返回 ≠ 成功**（与 §5.1 同源），父级必须**独立验证** ⇒ 验证成本常接近自己做。
- **串行化损失**：本仓库共享 git / 编译输出目录 / 数据库 ⇒ 多 Agent **实操上难以真并行**，反而要加锁、排队、协调。
- **实测反例**：RSI 整合轮，两个子代理 **1 个直接失败（exit=1）**，父级**接手直接读 3 个契约文件**即拿到全部证据；协作协议轮（v1.1/v1.2）**全程自做**、零委派，一次成型。
- **协调开销本身要花 token**：协议、消息、看板 —— 这些不是免费的，只在**防止高频高代价冲突**时才值得。

**纪律**：
1. **默认自己做完**。委派前先自问：**「我自己 5–10 次工具调用能否完成？」** 能则自做。
2. **只有同时满足以下三条才委派**：
   - **必然超出我的上下文**（如全仓 / 跨工程审计）；
   - **真独立**（不依赖我的隐性知识：项目约定、踩过的坑、未写下的判断）；
   - **产物可机械验证**（测试计数、`grep` 命中、build 退出码）。
3. **委派计入 §12 的「重型动作」**（多个模型调用），受成本窗口约束。
4. **不得为「看起来并行」而委派** —— 共享资源会把它变成串行 + 额外协调开销。
5. **反向情形（必须委派）**：需要**不知情的审查者**以规避确认偏差时（如独立复核自己的产出）。

> **与本协议的关系**：§1–§12 的价值**不在日常协调，而在冲突避免**（提交/重启撞车、成本窗口）—— 那些是**低频但高代价**事件，故**保留一页纸**即可；**但不得让协议本身制造额外的日常协调开销**。
