# Known timing-flaky tests (one full test name per line; '#' starts a comment).

# Purpose: when a suite fails and then passes on retry, delivery-manifest.ps1 records WHICH tests failed.
# This list is what lets the manifest say "that was a KNOWN flake" instead of silently accepting any retry.
# A failing test that is NOT on this list is recorded as NEW INSTABILITY and (by default) REFUSES the manifest.
#
# Evidence for each entry must live in Docs/00_changelog (observation rounds + failure kind).
#
# --- registry maintenance note (round-164) --------------------------------------------------------------
# The first version of this file listed only ONE of the three timing flakes that earlier changelogs already
# documented. On round 164 the second one flaked for real, the refusal rule fired (correctly), and this file
# was completed. Lesson: a registry that is less complete than one's own documentation silently turns
# "known" failures into "new instability" -- which is safe (it stops) but noisy.
# -------------------------------------------------------------------------------------------------------

# FIXED (2026-10-08): DesktopBrowserBridgeHandshakeTests.SecondConnection_CannotReplaceAwaitingHelloConnection
# was removed from this registry. Root cause was a RACE IN THE TEST, not load: it connected twice back-to-back,
# so either socket could win Registry.Current; when the second won, the server closed the FIRST socket and the
# test waited forever for a close on the second (OperationCanceledException from ReceiveAsync). The test now
# waits on a STATE BARRIER (Registry.Current is set) before the second connect, and its 2s clock is a 30s
# documented watchdog. Evidence: old form failed 10/20 runs in isolation; fixed form 0/20 (plus a chain run).
# Do not re-add it here without fresh failure evidence.

# FIXED (2026-10-08): DesktopConfigurationLoadingTests.LlmConfigurationLoad_DoesNotDeadlockOnDesktopSynchronizationContext
# was removed from this registry. Its "does not deadlock" criterion used to be a wall-clock Join(5s), which
# false-failed under load. The test now asserts a DETERMINISTIC property (the desktop SynchronizationContext
# must never be posted to) with a documented watchdog for real hangs; production already used
# ConfigureAwait(false) everywhere. Evidence: mutation (ConfigureAwait(true)) makes it fail via the watchdog,
# and the fixed test passed 20/20 consecutive runs. Do not re-add it here without fresh failure evidence.

# HARDENED, STILL REGISTERED (2026-10-08): HiddenSurface_ParksLateSdkFramesAndStopsObservingAfterDisposal.
# The test used two time-based criteria (a single priority-ranked no-op as a "drain", and thread.Join(10s));
# both are now state-based (pump the dispatcher until the parked state is observed) with a documented watchdog.
# IMPORTANT: the failure was NOT reproduced on this machine -- isolation 20x showed 0 failures BOTH before and
# after the change, so the hardening is root-cause-targeted but UNPROVEN. It stays on this registry because the
# plan's stability gate (20 consecutive chain-level runs, or a live failure) has not been met; remove it only
# with that evidence, and never treat the hardening itself as proof.
